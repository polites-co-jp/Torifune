# 016-home-routing 実装プラン

`設計.md` を唯一の入力とする。**マイグレーションは無い**（データモデルの変更なし）。

## 1. 順序

```text
1. test   結合テスト（resolveHomeDestination の3状態）→ 失敗する状態で確定させる
2. ui     ui/server/home-destination.ts を実装
3. app    app/page.tsx を遷移だけの Server Component へ置き換える
4. test   E2E（smoke.spec.ts の更新 + 遷移の確認）
```

Application 層・Domain 層・Infrastructure 層への変更は無い。
既存の `isSetupOpen` と `buildAuthorizationContext` をそのまま使う。

## 2. 新規ファイル

### `apps/web/src/ui/server/home-destination.ts`

```ts
export type HomeDestination = '/setup' | '/login' | '/dashboard';

export async function resolveHomeDestination(
  sessionToken: string | undefined,
  request: RequestInfo,
): Promise<HomeDestination>
```

判定は設計 §4 の順序で行う。

1. `isSetupOpen()` が true → `/setup`（**セッションを見る前に返す**。受け入れ条件5）
2. `buildAuthorizationContext(sessionToken, request)` の `identity` が null → `/login`
3. それ以外 → `/dashboard`

`cookies()` / `headers()` をこの関数の中で呼ばない（設計 §5）。引数で受け取る。

## 3. 置き換えるファイル

### `apps/web/src/app/page.tsx`

`export const dynamic = 'force-dynamic'` を付ける（受け入れ条件7）。
これが無いと Next.js がビルド時に静的化し、セットアップやログインの前後で
遷移先が変わらなくなる。既存の `/setup` `/login` `/dashboard` も同じ指定を持つ。

戻り値の型は `Promise<never>`。`redirect()` は例外を投げて必ず遷移するため、
**この関数から通常の値が返ることはない**。JSX を返す経路を残さない（受け入れ条件6）。

Cookie とヘッダの読み出しは `page-session.ts` と同じ形にする。

```ts
const cookieStore = await cookies();
const headerStore = await headers();
redirect(
  await resolveHomeDestination(cookieStore.get(SESSION_COOKIE)?.value, {
    ipAddress: headerStore.get('x-forwarded-for'),
    userAgent: headerStore.get('user-agent'),
  }),
);
```

**`redirect()` を `try` で囲まない。** Next.js の `redirect()` は内部で例外を投げる仕組みで、
捕まえると遷移が止まる。

## 4. テスト

### 結合テスト：`apps/web/src/ui/server/home-destination.integration.test.ts`（新規）

**専用のスクラッチデータベースを使う。**「管理者が0人」の状態が要るため、
他のテストファイルとデータベースを共有できない（`auth.integration.test.ts` と同じ理由）。

```ts
scratch = await useScratchDatabase('home-destination');
```

| # | 状態 | 期待 | 受け入れ条件 |
| --- | --- | --- | --- |
| 1 | 管理者0人・セッションなし | `/setup` | 1 |
| 2 | 管理者0人・**有効なセッションあり** | `/setup` | 5 |
| 3 | 管理者あり・セッションなし | `/login` | 2 |
| 4 | 管理者あり・不正なトークン | `/login` | 4 |
| 5 | 管理者あり・期限切れのセッション | `/login` | 4 |
| 6 | 管理者あり・有効なセッション | `/dashboard` | 3 |

テスト2は「管理者が0人ならセッションより先にセットアップを判定する」ことの確認。
判定順を逆に書いても他のテストは通ってしまうため、**この1本が順序を守らせる**。

管理者の作成は `completeSetup` を通す（`users` への直接 INSERT ではロールが付かない）。
セッションの作成は `login` UseCase を通す。期限切れは `sessions` の `expires_at` を
過去へ更新して作る。

### E2E：`apps/web/e2e/smoke.spec.ts`（更新）

既存のテストを差し替える。

```ts
// 削除する（トップページは表示を持たなくなる）
test('トップページが「とりふね」を表示する', ...)
```

E2E 環境は `global-setup.ts` が管理者を1人シードするため、
**「管理者が0人」の状態は E2E では作れない**（受け入れ条件1・5 は結合テストで担保）。

| テスト | 内容 | 受け入れ条件 |
| --- | --- | --- |
| 未ログインで `/` を開くと `/login` へ着く | `page.goto('/')` 後の URL を確認 | 2 |
| ログイン済みで `/` を開くと `/dashboard` へ着く | 保存済みの認証状態を使う | 3 |
| ログイン後に `/dashboard` へ到達する | `/login` からログイン → URL を確認 | 12 |

未ログインのテストは、既存の `ui-shell.spec.ts` と同じく
`page.context().clearCookies()` で保存済みのセッションを落としてから実行する。

### E2E：`apps/web/e2e/ui-shell.spec.ts`（更新）

**ログインのヘルパが `/` で待っている。**

```ts
async function loginViaUi(page: Page): Promise<void> {
  ...
  await page.waitForURL('**/');   // ← `/` に留まる前提。リダイレクト後は `/dashboard` へ抜ける
}
```

`/` が遷移するようになると、ログイン直後の URL は `/dashboard` になる。
`'**/'` は末尾がスラッシュの URL にマッチするため、`/dashboard` では待ちが解けない。
**`'**/dashboard'` へ変える。**

これは既存テストの巻き添えであり、`loginViaUi` を使うテスト
（「ログイン画面からログインしてダッシュボードへ行ける」「ログアウトすると
ログイン画面へ戻り、認証が切れる」）が落ちる。実装前に直す。

## 6. 想定される落とし穴

* **`dynamic = 'force-dynamic'` の付け忘れ。** ビルド時に静的化されると、
  最初にビルドした時点の遷移先へ固定される。受け入れ条件7で検査する
* **`redirect()` の戻り値を `return` しない。** `redirect()` は `never` を返すため
  `return redirect(...)` でも動くが、`await` を忘れると判定前に遷移する
* **既存 E2E の削除漏れ。** 「トップページが『とりふね』を表示する」は
  `/login` の見出しも「とりふね」であるため、リダイレクト後も**偶然通ってしまう**。
  通るからといって残さない。テストの意図（トップページが表示を持つ）が失われている
