# トップページの振り分け 設計

## 1. 目的

トップページ（`/`）を、**状態に応じて適切な画面へ送り出すだけの入口**にする。

現状の `apps/web/src/app/page.tsx` は固定文言を返す静的なプレースホルダで、
セットアップ状態もログイン状態も見ていない。

```tsx
// 現状。状態を見ずに常にこれを返す
<h1>とりふね</h1>
<p>Torifune はまだセットアップされていません。</p>
```

このため2つの不具合が起きている。

1. **セットアップが完了していても「まだセットアップされていません」と表示される。**
   利用者は初期化に失敗したと受け取る
2. **ログインに成功しても同じ画面へ戻される。**
   `/login` の `redirectTo` が `/` を指しているため、ログインが失敗したように見える
   （実際には成功しており、`/dashboard` を手で開けば使える）

`/` に来た利用者を、そのとき入るべき画面へ送る。

## 2. 上位仕様との対応

| 文書 | 節 | 具体化する内容 |
| --- | --- | --- |
| `06_画面設計.md` | §4 | 画面構成。**トップページは画面一覧に無い**。`/` は表示を持つ画面ではなく入口として扱う |
| 〃 | §30 | URL アクセス制御。直接 URL を入力された場合も Authentication → Authorization の順で処理する |
| `04_認証設計.md` | 初回セットアップ | 管理者が0人の間だけ `/setup` が開く。管理者がいれば 404（状態を漏らさない） |

## 3. スコープ

### やること

* `/` を状態に応じた振り分けにする（表示を持たせない）
* 振り分け先を決めるロジックを、テスト可能な関数として切り出す
* 既存の E2E（トップページの表示を確かめるもの）を新しい振る舞いへ更新する

### やらないこと

* `/login` の `redirectTo` の変更（**`/` のままにする**。理由は §7）
* 未ログインでも見せる公開トップページ（ランディングページ）の新設
* `/dashboard` の内容の変更
* Middleware の導入（`/` 1枚で足りる。§6）

## 4. 振る舞い

`/` へアクセスしたとき、次の順序で判定して遷移する。

| # | 条件 | 遷移先 |
| --- | --- | --- |
| 1 | 管理者が1人もいない（未セットアップ） | `/setup` |
| 2 | 管理者がいる・ログインしていない | `/login` |
| 3 | ログイン済み | `/dashboard` |

**この順序でなければならない。** 管理者が0人の状態ではログインする相手が存在せず、
`/login` へ送っても利用者は先へ進めない。セットアップの判定を先に置く。

`/` 自身は**いかなる場合も画面を描画しない**。必ずいずれかへ遷移する。

### 状態の露出について

`/` の遷移先から「セットアップ済みかどうか」が匿名の相手に分かる。
これは**既存の可視性を超えない**。`/setup` は管理者が0人なら誰にでも開き、
1人でもいれば 404 を返すため、`/setup` を1回叩けば同じことが分かる。
`/` の振り分けが新しい情報を与えるわけではない。

一方で、**`/` が「管理者の人数」や「ログイン中のユーザー」を本文へ出すことはしない**。
遷移だけを行う。

## 5. レイヤ配置

```text
apps/web/src/
├── app/page.tsx                 遷移するだけ。判定は持たない
└── ui/server/home-destination.ts  遷移先を決める（新規）
```

判定を `ui/server/` へ置くのは、既存の `page-session.ts`（ログインが要る画面の共通の入口）
と同じ役割だから。**Server Component から Application 層を直接呼ぶ**（決定事項 D-06）。

`page.tsx` に判定を書かないのは、**Server Component のままではテストを書けない**ため。
遷移先を返す関数に分ければ、結合テストで3状態すべてを確かめられる。

```ts
// ui/server/home-destination.ts
export type HomeDestination = '/setup' | '/login' | '/dashboard';
export async function resolveHomeDestination(sessionToken, request): Promise<HomeDestination>;
```

セッショントークンとリクエスト情報を**引数で受け取る**。`cookies()` / `headers()` を
この関数の中で呼ぶと Next.js のリクエスト文脈が要り、テストから呼べなくなる。
Cookie の読み出しは `page.tsx` に残す。

## 6. Middleware を使わない理由

Next.js の Middleware でも同じことはできるが、採らない。

* 判定に**データベースアクセスが要る**（管理者の人数・セッションの検証）。
  Middleware は全リクエストを通る場所であり、そこに DB アクセスを置くと
  静的アセットを含むあらゆる要求へ影響が及ぶ
* 対象は `/` の1枚だけで、ページ側で完結する

## 7. `/login` の `redirectTo` を変えない理由

ログイン後の遷移先を `/dashboard` へ直接変える案もあるが、採らない。

**遷移先の判断を `/` の1箇所に集約する**ため。`redirectTo` を個別に持つと、
「ログイン後にどこへ行くか」の判断がログイン画面とトップページの2箇所に分かれ、
将来どちらかだけを直したときに食い違う。

`/login` は成功したら `/` へ戻し、`/` が状態を見て `/dashboard` へ送る。
遷移は2段になるが、判断は1箇所で済む。

## 8. データモデル

なし。

## 9. API

なし。既存の UseCase（`isSetupOpen` / `buildAuthorizationContext`）を使う。

## 10. 権限（Permission）

新しい Permission は追加しない。

`/` は**認可の判定をしない**。ログイン済みかどうかだけを見て `/dashboard` へ送り、
その先の認可は `/dashboard` が `requirePageSession` で行う（§30 の順序を崩さない）。

## 11. Plugin API への影響

なし。`/` は Plugin の拡張点を持たない（拡張点はダッシュボードとログイン画面にある）。

**`/` で Plugin を起動しない。** 遷移するだけの画面であり、
起動の分だけ遷移が遅くなる。起動は遷移先（`/login` は
`ensurePluginsStartedAnonymously`、`/dashboard` は `requirePageSession`）が行う。

## 12. 受け入れ条件

### 振り分け

1. 管理者が0人のとき、`/` が `/setup` へ遷移する
2. 管理者がいてログインしていないとき、`/` が `/login` へ遷移する
3. ログイン済みのとき、`/` が `/dashboard` へ遷移する
4. セッショントークンが無効・期限切れのとき、`/` が `/login` へ遷移する
5. 管理者が0人であれば、**セッションの有無にかかわらず** `/setup` へ遷移する
6. `/` がいずれの場合も本文を描画しない（必ず遷移する）

### 実装上の制約

7. `/` が静的化されない（管理者の追加やログインの前後で遷移先が変わる）
8. 遷移先を決める関数が、Next.js のリクエスト文脈なしで呼べる（テストできる）
9. `/` が Plugin を起動しない

### 既存の振る舞いを壊さない

10. `/setup` は管理者がいるとき 404 のまま（`/` からの遷移で開くようにはしない）
11. `/dashboard` は未認証のとき `/login` へ遷移するまま
12. ログイン成功後、最終的に `/dashboard` へ到達する
