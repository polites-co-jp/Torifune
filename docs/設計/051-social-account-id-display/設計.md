# 051 SNS アカウントの ID を画面に出してコピーできるようにする — 設計

> 外部アプリは `POST /api/v1/social/posts` の `socialAccountId` に**アカウントの ID（UUID）**を入れて投稿を登録する。
> ところが管理画面（`/social`）のアカウント一覧はこの ID をどこにも出しておらず、**運用者が画面で登録したアカウントの ID を外部アプリへ渡す手段が無い**
> （`social.read` のトークンで `GET /social/accounts` を叩く回避策しか無い）。一覧に ID を出し、ボタンでクリップボードへ写せるようにする。
> **データモデル・HTTP API・OpenAPI・Permission・公開 Plugin API・共通 UI Component の公開入口は変えない。**

## 1. 目的

### 1.1 何が困るか

外部アプリが投稿を登録するには、投稿先のアカウントの `id` が要る（`docs/マニュアル/SNS投稿API仕様.md` §4.2「`id` … **投稿の `socialAccountId` に入れる値**」、§4.4）。
同じ仕様書の §4.2 は「アカウントと資格情報の登録は**通常、運用者が画面から行う**」と書いている。ところが、

* 画面で登録したアカウントの `id` は画面のどこにも出ない。運用者は外部アプリの作り手へ「このアカウントに投稿して」と ID で伝えられない
* 手順書（`docs/マニュアル/SNS投稿の外部連携.md` §2）は「外部アプリが `POST /social/accounts` でアカウントを作り、応答の `id` を持つ」流れだけを書いていて、
  画面で登録したアカウントの扱いが無い
* 回避策は、`social.read` を持つトークンで `GET /api/v1/social/accounts` を叩き、`displayName` / `handle` から目当ての行を探すこと。
  運用者が API を叩く前提になり、トークンの発行も要る

### 1.2 調査の結果（2026-10-02。コードを読んで確かめた）

**1. 一覧の部品は `id` を持っているが、出していない。**

* 行の型 `AccountRow` は `id` を持つ（`apps/web/src/ui/social/social-accounts.tsx:53-60`）。Server Component も `id` を渡している（`apps/web/src/app/social/page.tsx:208-219`）
* 列の宣言（`social-accounts.tsx:357-402`）は「サービス」「表示名」「ハンドル」「資格情報」「状態」「操作」の 6 つ。**`id` は `rowKey`（`:444`）にしか使われない**。
  React の `key` は DOM に出ないので、画面の HTML にも ID は無い
* 投稿一覧・手動投稿待ち・承認待ちは、アカウントを ID ではなく「表示名（サービス）」で出している（`page.tsx:127-133`「投稿一覧はアカウントIDではなく人が読める名前で出す」）

**2. ID は秘密ではなく、`social.read` で API から読める。**

* `GET /api/v1/social/accounts` は `social.read` の UseCase `listSocialAccounts`（`apps/web/src/application/social/social-use-cases.ts:189-200`）で、応答に `id` を含む（API 仕様 §4.2）
* `/social` の画面も `social.read` が無ければ「権限なし」を出して何も描かない（`page.tsx:104-110`）。**画面を開ける人は、API でも同じ ID を読める**
* ID は Torifune の中の識別子で、SNS 側の接続情報ではない（`06_画面設計.md` §13・§38 の「再表示しない Secret」に当たらない）。ID だけでは何もできず、投稿の登録には `social.write` のトークンが要る

**3. ID は UUIDv7 で、先頭が時刻。**

* アカウントの ID は `uuidv7()` で作る（`social-use-cases.ts:263`）。UUIDv7 の先頭 48 ビットはミリ秒の時刻なので、**同じ頃に登録したアカウントは先頭の桁が揃う**
  （先頭 8 桁は約 65 秒ごとにしか変わらない）。「先頭 8 桁＋…」のような短縮表示では、続けて登録した 2 つのアカウントが同じに見える

**4. 画面でのコピーの前例が 1 つある。**

* アナリティクスの設定タブの「タグをコピー」（`apps/web/src/ui/analytics/settings-tab.tsx:128-140`・`:202-204`）。`navigator.clipboard.writeText` を `try` で呼び、
  成功したらボタンの文字を 2 秒「コピーしました」に変え（`:71-72`）、失敗したら Toast（`danger`）で「コピーできませんでした。タグを選択して写してください。」と出す。
  **`document.execCommand('copy')` の代替は置いていない**（`028` 設計 §7.3.6）
* `navigator.clipboard` は**安全なコンテキスト**（https、または `localhost` / `127.0.0.1`）でしか生えない。コンテナを別のマシンから `http://<アドレス>:<ポート>` で開くと
  `undefined` になり、`writeText` を呼ぶと `TypeError` で落ちる。前例の `try` はこれを拾って Toast に回している
* API トークンの発行直後の表示（`apps/web/src/ui/settings/api-settings.tsx:154-173`）は `<pre>` に出すだけでコピーのボタンは無い。一覧の「プレフィックス」は `<code>`（`:117`）

**5. 共通部品について。**

* `Table`（`apps/web/src/ui/components/table.tsx`）は表を `.tf-table-scroll` で包み、幅の広い表は**表の中で**横にスクロールさせる。列の `width` は自動レイアウトの表では最小幅として効く
* `Toast`（`apps/web/src/ui/components/overlays.tsx:152-191`）は `role="status"`・`aria-live="polite"` で、4 秒で消える。`SocialAccounts` は登録・削除・資格情報の結果をすべてこれで知らせている（`social-accounts.tsx:248`・`:263-265`・`:330`・`:353`・`:664`）
* `ui/components/index.ts` は **Plugin が見る公開入口**（`06_画面設計.md` §32、`docs/UI Componentリファレンス.md`）。コピーの部品はここに無い
* SNS 画面の文言は `ui/social/labels.ts` に置く（同ファイル冒頭の方針。`039` §7.8 で静的検査がある）

## 3. スコープ

### やること

1. `/social` のアカウント一覧に列「アカウントID」を足し、行ごとに ID の全桁と「コピー」ボタンを出す（§7.1・§7.2）
2. 「コピー」で ID をクリップボードへ写し、結果を Toast で知らせる。写せないときは手で選んで写せるようにする（§7.3）
3. 文言を `ui/social/labels.ts` に置く（§7.6）
4. 列が増える分、既存の列の最小幅を中身に合わせて詰める（§7.4）
5. API 仕様書・手順書・関係する設計書と Plugin の README に「ID は画面のどこで写せるか」を書く（§12）

### やらないこと（理由つき）

* **API・DB・OpenAPI を変えない。** 画面に出す値は行が既に持っている `id`
* **手動投稿待ち・承認待ち・投稿一覧・投稿の編集・配信履歴・入れ直しの Modal に出さない。** 理由は §7.5
* **投稿の ID を投稿一覧に出さない。** 外部アプリは自分が登録した投稿の `id` を `POST` の応答で受け取る。画面で作った投稿を外部アプリが扱う流れは無い（§11.2 の 1）
* **共通 UI Component に「コピーのボタン」を足さない。** 公開入口は Plugin との契約で、足すなら別に設計する（§9、§11.2 の 2）
* **アナリティクスの「タグをコピー」を新しい関数へ寄せない。** 動いている画面に触る理由が本件に無い（§11.2 の 3）
* **`document.execCommand('copy')` などの代替を置かない。** 理由は §7.3.3
* **アカウントの一覧の上限（100 件。`page.tsx:115`）を変えない**（§11.2 の 4）

## 7. 画面（決めたこと）

### 7.1 置き場所：一覧の列「アカウントID」

アカウントの表に列を 1 つ足し、**「ハンドル」と「資格情報」の間**に置く。列の並びは次のとおり。

| 順 | 列 | 中身 |
| --- | --- | --- |
| 1 | サービス | 今までどおり |
| 2 | 表示名 | 今までどおり |
| 3 | ハンドル | 今までどおり |
| 4 | **アカウントID** | **ID の全桁と「コピー」ボタン**（§7.2） |
| 5 | 資格情報 | 今までどおり（「••••••••」/「未設定」） |
| 6 | 状態 | 今までどおり |
| 7 | 操作 | 今までどおり（`social.write` / `social.delete` で出し分け） |

* **列にする理由**：外部アプリに渡すとき、運用者は「どのアカウントの ID か」を表示名・ハンドルと見比べて選ぶ。同じ行に並んでいれば取り違えにくい。
  **`social.read` だけの人にも見える場所**である必要があり、`social.write` が要る「資格情報を設定」の Modal（`social-accounts.tsx:389-393`）には置けない
* 識別に使う列（サービス・表示名・ハンドル・ID）を左に、状態を表す列（資格情報・状態）と操作を右にまとめる
* 行ごとの「詳細」の Modal を新しく作る案は採らない。1 回のクリックが増え、一覧に要るのは ID 1 つだけ

### 7.2 見せ方：全桁を出す

```text
┌ アカウントID ──────────────┐
│ 0192b7a0-5c1e-7a3b-9f10-     │   ← 列の幅が足りなければハイフンの後で折り返す
│ 2d7c4e8a1b23                 │
│ [コピー]                     │   ← 幅があれば ID の右に並ぶ
└──────────────────────────────┘
```

* **36 文字の全桁を出す。短縮しない。** 理由は 2 つ。(1) ID は UUIDv7 で先頭の桁が登録の時刻なので、短縮すると続けて登録したアカウントが同じに見える（§1.2 の 3）。
  (2) クリップボードが使えない環境では、画面の文字を手で選んで写すしかない（§7.3.3）。短縮すると写せない
* 値は行の `id` をそのまま出す（大文字・小文字を変えない。API の応答と同じ文字列）
* ID は `<code>` に入れ、`data-account-id="<id>"` を付ける（E2E の手がかり。`api-settings.tsx` の `data-issued-token`、`settings-tab.tsx` の `data-tracking-snippet` と同じ流儀）
* `<code>` の見た目：`fontFamily: 'var(--tf-font-mono)'`、`fontSize: 'var(--tf-text-caption)'`。色は本文と同じ（読み取る値なので薄くしない）。**生の px・hex を書かない**（`ui-shell.test.ts`「デザイントークン」）
* **ハイフンの直後に `<wbr>` を入れる**（4 か所）。列の幅が足りないとき、折り返しを区切りの位置に限る（ハイフンの前後で折り返すかはブラウザと続く文字で変わるので、明示する）。
  `<wbr>` は文字を足さないので、画面から選んで写した文字列も、`innerText` も 36 文字のまま
* **`userSelect: 'all'`（Safari 向けに `WebkitUserSelect: 'all'` も）** を `<code>` に付ける。1 回のクリックで ID の全体が選ばれ、折り返していても選び損ねない（§7.3.3 の手で写す経路）
* 「コピー」ボタンは `<code>` の後に置く。ID とボタンを `display: flex`・`flexWrap: 'wrap'`・`alignItems: 'center'`・`gap: 'var(--tf-space-2)'` の箱に入れ、
  幅があれば横に、無ければボタンが下に回る。ボタンの文字は折り返さない（`whiteSpace: 'nowrap'`）

### 7.3 コピーの振る舞い

#### 7.3.1 ボタン

* `Button`（`variant="ghost"`。行の操作のボタンと同じ）。見える文字は **「コピー」**
* **`aria-label` は `「<表示名>（<サービスの表示名>）」のアカウントIDをコピー`**。行ごとに同じ「コピー」が並ぶので、支援技術では名前で行を見分けられるようにする。
  見える文字「コピー」を名前に含む（WCAG 2.5.3 Label in Name）。サービスの表示名は「サービス」列と同じく `ownValue(providerLabels, provider) ?? provider`（`047` 設計 §4.1。
  provider が `constructor` などでも原型の値を拾わない）。入れ直しの Modal の「対象：表示名（サービス）」（`credentialTargetLabel`）と同じ組み合わせ
* `type="button"`（`Button` の既定）。押しても要求を出さない

#### 7.3.2 写す処理（`ui/client/clipboard.ts`）

```ts
/** 書き込みだけを使う（読み取りの権限は要らない）。 */
export interface ClipboardWriter {
  writeText(text: string): Promise<void>;
}

/**
 * 文字列をクリップボードへ写す（051 設計 §7.3）。写せたら true、写せなければ false。**例外を投げない。**
 *
 * `navigator.clipboard` は安全なコンテキスト（https / localhost）でしか生えない。http で開いた画面では
 * undefined なので false を返し、呼び出し側が「選択して写す」よう伝える。execCommand の代替は置かない。
 */
export async function copyText(
  text: string,
  clipboard: ClipboardWriter | undefined = globalThis.navigator?.clipboard,
): Promise<boolean> {
  if (clipboard === undefined) return false;
  try {
    await clipboard.writeText(text);
    return true;
  } catch {
    return false;
  }
}
```

* 写すのは**行の `id` の文字列だけ**（前後に空白・改行・説明を付けない）
* 部品の側は次のとおり。行の値だけを使い、要求を出さない

  ```ts
  async function copyAccountId(account: AccountRow): Promise<void> {
    const copied = await copyText(account.id);
    setToast({
      id: `${account.id}:copy`,
      text: copied ? ACCOUNT_ID_COPIED : ACCOUNT_ID_COPY_FAILED,
      tone: copied ? 'success' : 'danger',
    });
  }
  ```

#### 7.3.3 写せないとき（決めたこと）

| 状況 | 振る舞い |
| --- | --- |
| `navigator.clipboard` が無い（http で開いた・古いブラウザ） | `copyText` が false。Toast（`danger`）「**コピーできませんでした。アカウントIDを選択して写してください。**」 |
| `writeText` が断られる（権限・フォーカスが無い など） | 同じ |
| どちらでも | ID は表に出たまま。`<code>` を 1 回クリックすると全体が選ばれる（§7.2）ので、そのまま写せる |

* **代替の書き込み（`document.execCommand('copy')`、隠した `<textarea>` を選ぶ など）は置かない。** `execCommand` は廃止予定で、前例（`028` の「タグをコピー」）も置いていない。
  http で開く環境（同じネットワークの別のマシンからコンテナを開く場合）は起こりうるが、**ID は画面に全桁出ていて 1 クリックで選べる**ので、手で写す経路で足りる。
  写せない環境のために仕組みを足すのは、利用者の体験に実質的な差を生まない
* 写せたかどうかを確かめるためにクリップボードを読み返さない（読み取りには別の権限が要る）

#### 7.3.4 知らせ方

* 成功：Toast（`success`）「**アカウントIDをコピーしました。**」。失敗：§7.3.3 の文言（`danger`）
* **Toast にする理由**：`SocialAccounts` は登録・削除・資格情報の結果をすべて Toast で知らせている（§1.2 の 5）。`Toast` は `role="status"`・`aria-live="polite"` で、
  支援技術にも結果が届く。前例の「タグをコピー」のようにボタンの文字を変える形は、行ごとに状態とタイマーが要り、ボタンのアクセシブルな名前も変わるので採らない
* Toast の `id` は `<アカウントの id>:copy`。続けて押しても毎回新しい通知として出る（`setToast` に新しい値を渡すので `Toast` のタイマーが掛け直される）
* フォーカスはボタンに残す（動かさない）

### 7.4 列の幅（決めたこと）

列が 1 つ増えるぶん、既存の列の**最小幅**を中身に合わせて詰める。`Table` の列の `width` は自動レイアウトでは最小幅として効くので、中身が広ければ列はその分広がる（詰めても中身は欠けない）。

| 列 | 今 | 本設計 | 理由 |
| --- | --- | --- | --- |

### 7.5 出さない場所（決めたこと）

### 11.1 要裁定

### 11.2 設計で決めず、後の判断に回すもの（記録のみ）

1. **投稿の ID を画面に出すか**：外部アプリは投稿の `id` を `POST` の応答で受け取るので、今は要らない。画面で作った投稿を外部アプリから `GET` / `PATCH` したい運用が出てきたら、投稿一覧に同じ形で足す

3. **アナリティクスの「タグをコピー」を `copyText` に寄せるか**：振る舞いは同じ（失敗を Toast で伝える）。触る理由ができたとき（2 と一緒に）寄せる
4. **アカウントが 100 件を超えると一覧に出ない**（`page.tsx:115` の `perPage: 100`。既存の制限）。101 件目以降の ID は画面で写せない。アカウント一覧にページ送りを足すときに一緒に解消する
