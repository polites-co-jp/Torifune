## 2. 進める順番

**先にサンプルを書き、足りないものを見つけてから足す。**
先に API を増やすと、使われない機能を作り込むことになる。

```text
サンプルを書いてみる
   ↓
足りないものが出る（§3）
   ↓
Plugin API を足す → 本体側を繋ぐ
   ↓
サンプルを仕上げる
   ↓
テスト（境界・有効化・無効化・設定・Provider）
   ↓
E2E（実際の画面で現れる／消える）
   ↓
手引きを書く
```

## 3. サンプルを書いて分かったこと

| 足りなかったもの | 対応 |
| --- | --- |
| Database Provider を登録する口が無い | `context.database.registerProvider` |
| 設定画面を作る口が無い | `ui.registerSettings`（項目の宣言だけ） |
| Core イベントの Payload に型が付かない | `CoreEventPayloads` と多重定義 |
| 画面の Data API が起動時のユーザーに縛られる | 描画時に要求ごとの Data API を渡す |
| `plugins/` から `@torifune/plugin-api` を解決できない | ルートの依存に加える |
| `plugins/` から `react` を解決できない | 同上 |

## 4. 判断が要るところ

### 4.1 サンプルのための分岐を本体に書かない

書いた時点で「Plugin だけで作れる」ことの証明にならなくなる。
本体に入れたのは**すべての Plugin が使える機能**だけ。

### 4.2 サンプルは既定で Database Provider を差し替えない

差し替えると本体のすべてのデータアクセスがダミーを通り、何も読めなくなる。
`EXAMPLE_PLUGIN_REPLACE_DATABASE=1` のときだけ差し替える。

差し替えが成立することは、`database-adapter.test.ts` で確かめる。

### 4.3 設定は「宣言するだけ」にする

Plugin ごとにフォームと保存を書かせると、Secret の扱いが Plugin ごとに変わり、
どこかで平文が表に出る。**項目の宣言だけを受け取り、描画と保存は本体が持つ。**

### 4.4 `plugins/` の依存をルートで解決する

Plugin ごとに `package.json` を置く案もあったが、
**zip を展開しただけで動く**という導入の流れと噛み合わない
（展開後に `pnpm install` は走らない）。

`@torifune/plugin-api` と `react` をリポジトリのルートの依存に加えた。

### 4.5 E2E は必ず後始末する

サンプルを有効にすると本体の画面が変わる。
E2E は直列（`workers: 1`）で走るため、`afterAll` で無効化と削除を行えば
他のテストの前提を壊さない。

**それでも「Plugin が1つも無い」ことに依存する assert は書き換えた。**
そういう assert は、Plugin を1つ足すたびに壊れる。

## 5. やらないこと

* Authentication Provider の差し替え口（`extensions: ['authentication']` は
  宣言できるが使えない状態。検証レポート §4.2 に記す）
* 実用的な Database Provider
* Plugin の npm 公開
