# Example Plugin 設計

## 1. 目的

**Plugin API が本当に使えることを、Torifune 自身のコードを1行も変えずに示す。**

`010`〜`012` で契約・ランタイム・管理画面を作った。
それらが噛み合っているかは、実際に Plugin を1つ書いてみないと分からない。

このスプリントの成果物は2つ。

1. `plugins/example-plugin/` — 拡張点を1つずつ使うサンプル
2. `docs/Plugin開発ガイド.md` — サンプルを題材にした手引き

## 3. スコープ

### やること

* `plugins/example-plugin/`
  * 左ナビへの項目追加と独自ページ（`/plugins/example-plugin`）
  * ダッシュボードへの Widget 追加
  * Webサイト一覧への Action 追加（`site.list.actions`）
  * Webサイト編集画面のサイドバーへの追加（`site.edit.sidebar`）
  * 自分の拡張点の定義（`example-plugin.page.footer`）
  * `site.created` の購読と、自分のイベントの発火
  * 設定（一般設定と Secret を1つずつ）
  * Data API で Webサイトを読む
  * ログを出すだけのダミー Database Provider
* Plugin 開発ガイド
* 上を成り立たせるための Plugin API の不足分（§5）

### やらないこと

| 対象 | 理由 |
| --- | --- |
| Authentication Provider のサンプル | 差し替えの入口自体が未整備。§7 に記す |
| 実用的な Database Provider | 差し替えが成立することの実証で足りる |
| Plugin の npm 公開 | Plugin Registry と合わせて設計する |

## 4. サンプルの構成

```text
plugins/example-plugin/
├── plugin.json          Manifest
├── index.tsx            エントリポイント（activate / deactivate）
├── database.ts          ダミー Database Provider
└── ui/
    ├── components.tsx   Widget / Action / 拡張点の部品
    └── pages.tsx        独自ページ
```

**`@torifune/plugin-api` 以外の Torifune のモジュールを import しない。**
これは自動テストで検査する（受け入れ条件 #1〜#3）。

## 5. Plugin API の不足分

サンプルを書いてみて足りないと分かったもの。**ここで足す。**

### 5.1 Database Provider を差し替える入口が無かった

`PluginDatabaseProvider` の型はあったが、登録する口が `PluginContext` に無かった。

```ts
context.database.registerProvider(provider);
```

**Manifest で `extensions: ['database']` を宣言していなければ使えない。**
宣言なしに差し替えられると、Plugin を入れた側が
「何がデータアクセスを握っているか」を知らないまま運用することになる。

本体側では、`query(sql, params)` だけの契約を Kysely の Dialect で包んで
本体の `DatabaseProvider` に合わせる（`plugin/database-adapter.ts`）。
**公開契約にクエリビルダの型を出さない**という約束を守ったまま繋ぐため。

### 5.2 設定画面を作る口が無かった

`06_画面設計.md` §27 の「設定画面の拡張」に対応するものが無かった。

```ts
context.ui.registerSettings({ fields: [...], validate });
```

**Plugin は項目を宣言するだけ。** 画面の描画と保存は本体が行う。
Plugin ごとにフォームと保存を書かせると、Secret の扱いが Plugin ごとに変わり、
どこかで平文が表に出る。

### 5.3 Core のイベントの Payload に型が付かなかった

`subscribe<T = unknown>` だったため、Plugin 側が Payload の形を書き写すことになる。
書き写すと、Payload が増えたときに Plugin 側が古い形のまま残る。

`CoreEventPayloads` を足し、Core のイベント名では型が付く多重定義にした。

### 5.4 画面に渡る Data API が「起動したときのユーザー」に縛られていた

`activate()` で受け取る `context.data` は、そのとき起動したユーザーの
認可文脈を握っている。**それを画面の描画で使うと、見ている人と違う権限で読む。**

Widget・拡張点・ページには、**その要求の Data API を props で渡す**ようにした。

## 6. 本体側の変更

| 対象 | 変更 |
| --- | --- |
| `plugin-api` | `context.database` / `registerSettings` / `CoreEventPayloads` |
| `plugin/database-adapter.ts` | Plugin の Provider を Kysely で包む |
| `plugin/registry.ts` | 収集したものに「どの Plugin のものか」を添える |
| `ui/plugin/plugin-slot.tsx` | 描画時に要求ごとの Data API を渡す |
| `application/plugin/plugin-settings-use-cases.ts` | 設定の読み書き |
| `app/plugins/[pluginId]/settings` | 設定画面 |
| `api/v1/plugins/{id}/settings` | 設定の API |

**サンプルのための分岐は本体に一切書かない。**
書いた時点で「Plugin だけで作れる」ことの証明にならなくなる。

## 7. 受け入れ条件

### 境界

1. サンプルが `apps/web` の内部モジュールを import していない
2. Torifune のパッケージは `@torifune/plugin-api` しか使っていない
3. `pg` / `kysely` を直接使っていない

### Manifest

4. Manifest の検証を通る
5. 要求する Permission を宣言している
6. 使う高権限の拡張点を宣言している

### 有効化で現れる

7. 左ナビに項目が増える
8. 独自ページが `/plugins/example-plugin` で開く
9. ダッシュボードに Widget が出る
10. Webサイト一覧に Action が出る
11. Webサイト編集のサイドバーに欄が出る
12. 設定項目が宣言される
13. Key-Value Store に既定値が入る
14. `site.created` を購読している

### 無効化で消える

15. 左ナビの項目が消える
16. Widget が消える
17. Action が消える
18. 拡張点の欄が消える
19. 独自ページが 404 になる
20. 設定項目が消える
21. **保存したデータは消えない**

### Data API

22. 独自ページから Webサイトを読める
23. 読み込みは**見ているユーザーの権限**を通る
24. 宣言していない Permission の操作は失敗する

### 設定

25. 一般設定の現在値が出る
26. 一般設定を保存できる
27. Secret を保存できる
28. **Secret の平文が画面に出ない**
29. **Secret の平文が API 応答に出ない**
30. **Secret が DB 上で平文になっていない**
31. Secret の欄を空で保存しても消えない
32. 宣言されていない項目は保存できない
33. Plugin の検証が働く
34. `plugin.manage` を持たないユーザーは読めない・保存できない

### Database Provider

35. 宣言していなければ差し替えられない
36. 既定では差し替えない（差し替えると本体が何も読めなくなる）
37. 差し替えると本体のデータアクセスがその Provider を通る

### 手引き

38. `docs/Plugin開発ガイド.md` がサンプルを題材に一通りを説明している
