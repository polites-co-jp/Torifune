### 3.2 結合テストが実際に確かめたこと

**外部サービスへ繋がずに往復を成立させている**（テスト内でループバック）。

* 認可開始 → コールバックでログインが成立し、**Core が発行したセッションが DB にある**
* State / Nonce / Redirect URI が Core から Plugin へそのまま渡る
* **State を平文で保存していない**（`state_hash` にハッシュだけがある）
* **同じ State を2回使うと2回目が落ちる**（使い捨て）
* 存在しない State / State 無し / 期限切れ が落ちる
* **期限切れと存在しないを理由で区別しない**（State の生死を外から探れない）
* **発行時と違う Redirect URI では落ちる**
* `returnTo` に `//evil.example` を渡しても `/` に落ちる
* **Plugin 経由**（`adaptPluginAuthenticationProvider`）で実在しない `userId` を名乗っても落ちる
* Plugin 経由で実在するユーザーなら成立し、**Plugin の申告した `loginId` は採用されない**
* 成功・失敗が `auth_audit_logs` に `flow: 'redirect'` つきで残る
* **標準認証のままなら `unsupported`**（開始もコールバックも受け付けない）

### 3.3 既存テストへの影響

## 4. `endpoints.ts` へ登録が必要な内容（**未編集**）

`apps/web/src/api/endpoints.ts` は他の作業と競合するため触っていない。
次の2行を、既存の `auth` の並びへ足す必要がある。

```ts
import '@/app/api/v1/auth/authorize/route';
import '@/app/api/v1/auth/callback/route';
```

**足さなくても機能は動く**（Next.js はルートを個別に読み込む）。
足さないと `defineRoute` の副作用による登録が走らないため、
`api/registry.ts` の一覧に載らない。

ただし2本とも `documented: false` のため、
**OpenAPI の出力と `openapi-coverage.test.ts` には影響しない**
（`listDocumentedEndpoints()` の対象外）。追加しても既存テストは落ちない。

## 5. E2E を実行していない理由

`pnpm test:e2e` は `pnpm build && pnpm start` を伴い、Next.js のビルドが型検査を通す。
**現在、別作業中のファイル（`social` 系）に型エラーが2件残っており、ビルドが通らない。**
本機能の変更が原因ではない（§6）。

`apps/web/e2e/redirect-auth.spec.ts` は書いてあるが**未実行**である。

**往復そのものは結合テストで確かめてある**（§3.2）。
E2E で見るのは、E2E でしか見られない次の2つに絞った。

1. `login.methods` のボタンが `AUTHORIZATION_START_PATH` へのリンクになっている
2. Core の2つの口が、外から叩かれたときに安全に落ちる
   （偽 State でセッションを張らない、理由を出し分けない）

なお **E2E で往復そのものを通すことはできない。**
サンプル Plugin の Provider 差し替えは `EXAMPLE_PLUGIN_AUTH_USER_ID`
（プロセス起動時の環境変数）で有効になるが、その値は E2E の
`global-setup` が作る管理者の UUID であり、**サーバー起動時にはまだ存在しない。**
この制約は既存の `plugin-example.spec.ts` でも同じで、本機能で新たに生じたものではない。

## 8. 残った懸念

| # | 内容 | 判断 |
| --- | --- | --- |
| 1 | **`response_mode=form_post`（POST でのコールバック）に対応していない** | 設計 §14 で範囲外と決めた。POST になると CSRF の扱いが変わり、別途の設計が要る。Azure AD 等が既定で使う構成があるため、要求が出たら足す |
| 2 | **PKCE の Code Verifier を Core が持っていない** | 設計 §14。Plugin が `PluginStore` に `state` をキーとして保管できる。ただしそれを**強制する仕組みは無い**ため、PKCE を実装しない Plugin が書けてしまう |
| 3 | **JIT プロビジョニング（初回ログインでのユーザー自動作成）が無い** | 既存方針を変えていない。外部の利用者を Torifune へ迎え入れるには、あらかじめユーザーを作っておく必要がある。実運用では手間になりうる |
| 4 | **Provider は同時に1つしか有効にできない** | `authentication/registry.ts` の構造。「Googleでログイン」と「SSOでログイン」を**同時には出せない**。`06_画面設計.md` §5 は2つ並べた図を載せており、厳密には未達 |
| 5 | 期限切れ State の掃除を認可開始のついでに行っている | 認可開始が呼ばれない環境では溜まる。行数は小さく、`expires_at` に索引があるため実害は薄いと判断した |
| 6 | Remember Me をリダイレクト型で効かせていない | 設計 §9。選ばせる画面が無いため。外部認証で長期ログインを望む要求が出たら再考する |
| 7 | E2E 未実行 | §5 |

### 4 について

`06_画面設計.md` §5 の `[ Googleでログイン ] [ SSOでログイン ]` は、
**2つの Plugin が別々の Provider を登録する形では実現できない。**
1つの Plugin が複数の IdP を内部で切り替える（`?idp=google` のような
クエリを `returnTo` 以外に受ける）形なら書けるが、Core は今それを渡していない。

本機能の範囲を「往復を表現できるようにする」に絞ったため、ここは踏み込んでいない。
**複数 Provider の同時有効化は別の設計として起こすべき**であり、
本レポートでは未達として記録するに留める。
