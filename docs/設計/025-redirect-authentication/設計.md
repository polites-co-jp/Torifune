# 025-redirect-authentication 設計

## 1. 目的

**リダイレクト往復を伴う外部認証（OIDC / SAML / SNS ログイン）を、Plugin が実装できるようにする。**

`002-Torifune機能完成` T11。

`04_認証設計.md` は §17 §19 §21 で OpenID Connect を外部認証の第一候補として繰り返し挙げ、
§22 で「ID Token をユーザー認証結果として利用し、Torifune 自身のセッションを確立する方式を基本とする」と定めている。
`06_画面設計.md` §5 は `[ Googleでログイン ] [ SSOでログイン ]` を
OIDC Plugin が `login.methods` 拡張点へ差し込む例として明示している。

しかし現状の公開 Plugin API では、**これを Plugin 側でも実装できない。**

| 足りないもの | 現状 |
| --- | --- |
| リダイレクト往復の口 | `PluginAuthenticationProvider.authenticate()` が受け取るのは `PluginCredentials = { loginId, password }` のみ。認可エンドポイントへ送り出す口も、コールバックを受け取る口も無い |
| コールバックの受け口 | `app/api/v1/auth/` に外部からのリダイレクトを受ける API ルートが無い |
| State / Nonce の保管 | どこにも無い |
| Redirect URI の確定 | Plugin も Core も、コールバック URL を「これだ」と決める場所を持たない |

結果、`plugins/example-plugin/authentication.ts` は合言葉照合のダミーに留まり、
`login.methods` は「押しても何も起きない枠」だけがある状態になっている。

**UI の受け口だけがあって、認証の往復が無い。** ここを埋める。

---

## 2. 何を Core が持ち、何を Plugin が持つか

これが本設計の中心である。**境界を最初に決める。**

`04_認証設計.md` §27（Plugin Security）は、Authentication Provider Plugin が考慮すべき項目として
Token 検証 / Redirect URI 検証 / CSRF 対策 / State 検証 / Nonce 検証 / Secret 管理 / HTTPS を挙げている。

このうち **State・Redirect URI・セッション発行は Core が持つ。**

> **理由**：Plugin ごとに書かせると、**どれか1つの Plugin の実装ミスが認証全体の穴になる。**
> State を検証しない Plugin が1つ入るだけで、その環境はログイン CSRF に対して無防備になる。
> Plugin は「信頼されたコード」として扱う前提（`CLAUDE.md`）だが、
> 信頼することと、間違えようのない形にすることは別である。
> Database Provider の差し替えでトランザクション境界を Core に残しているのと同じ考え方をとる。

| 項目 | 担当 | 根拠 |
| --- | --- | --- |
| State の発行・保管・照合・有効期限・使い捨て | **Core** | Plugin ごとに書かせない。1つの実装ミスが全体の穴になる |
| Nonce の発行・State への束縛・使い捨て | **Core** | 同上。**「新鮮で、この往復専用で、一度きり」を Core が保証する** |
| Nonce と ID Token の `nonce` Claim の照合 | Plugin | Claim は JWT の中にあり、Core は JWT を解釈しない（解釈すると Core が OIDC を知ることになる） |
| Redirect URI の決定と照合 | **Core** | Plugin に選ばせない。Plugin が受け取るのは Core が決めた値だけ |
| CSRF（コールバックの正当性） | **Core** | State 検証がその役目を担う（§6.3） |
| Authorization Request の組み立て（scope / client_id / PKCE 等） | Plugin | 方式ごとに違う。Core が知ると Core が OIDC を知ることになる |
| Token Exchange（Authorization Code → Token） | Plugin | 同上 |
| Token 検証（iss / aud / exp / 署名 / Claim）、Discovery、JWKS | Plugin | 同上。`04` §23 |
| Secret（client_secret 等）の保管 | Plugin | `PluginStore` の `secret` 種別を使う（暗号化して保存される） |
| 外部の識別子 → Torifune のユーザーの解決 | Plugin | 「この外部 ID は Torifune のこのユーザーだ」を返すところまで |
| ユーザーが実在することの確認 | **Core** | `authentication-adapter.ts` が既に行っている。往復型でも同じ経路を通す |
| セッションの発行・再生成・有効期限・アイドルタイムアウト | **Core** | `04` §22。`authentication-adapter.ts` の既存方針を崩さない |
| ログイン後の遷移先の検証 | **Core** | Open Redirect を Plugin ごとに防がせない |
| 監査ログ | **Core** | `login.succeeded` / `login.failed` を Core が記録する |

## 3. 全体の流れ

```text
Browser                    Torifune Core                 Plugin              外部 IdP
   │                            │                          │                    │
   │ 1. [Googleでログイン]      │                          │                    │
   ├───── GET /api/v1/auth/authorize ──────────►           │                    │
   │                            │                          │                    │
   │                    2. state / nonce を発行            │                    │
   │                       redirect_uri を確定             │                    │
   │                       DB へ保管（使い捨て・期限つき） │                    │
   │                            ├─ startAuthorization ────►│                    │
   │                            │                          │ 3. 認可URLを組む   │
   │                            │◄──── authorizationUrl ───┤                    │
   │◄──── 302 authorizationUrl ─┤                          │                    │
   │                            │                          │                    │
   ├──────────────────── 4. 認可要求（state / nonce 付き）─────────────────────►│
   │                            │                          │        5. 利用者が認証
   │◄──────────────────── 6. 302 redirect_uri?code=…&state=… ───────────────────┤
   │                            │                          │                    │
   ├───── GET /api/v1/auth/callback?code=…&state=… ────────►                    │
   │                            │                          │                    │
   │                    7. state を照合（存在・未使用・未期限・provider 一致）  │
   │                       その場で使用済みにする                               │
   │                       redirect_uri が発行時と同一か照合                    │
   │                            ├─ completeAuthorization ─►│                    │
   │                            │   { params, nonce,       │ 8. Token Exchange ►│
   │                            │     redirectUri }        │◄─ ID Token ────────┤
   │                            │                          │ 9. Token 検証      │
   │                            │                          │    nonce 照合      │
   │                            │◄──── PluginUserIdentity ─┤                    │
   │                   10. ユーザーが実在するか確認                             │
   │                       セッションを発行（Core）                             │
   │                       監査ログを記録                                        │
   │◄──── 302 returnTo + Set-Cookie ─┤                                          │
```

**2 と 7 が Core の要**である。Plugin は 3 と 8-9 だけを書く。

## 4. 公開 Plugin API の追加

`packages/plugin-api/src/authentication.ts` に足す。**既存の型・メソッドは1つも変えない。**

### 4.1 後方互換

* `PluginAuthenticationProvider.authenticate()` は **残す。**
  標準認証を差し替える Plugin・合言葉型の Plugin・LDAP のような
  往復を伴わない方式は、これまでどおり `authenticate()` だけを実装すればよい。
* 追加する2つのメソッドは **どちらも optional。**
  実装しない Provider は今までと完全に同じ挙動になる。
* 型の追加のみで、既存の型からフィールドを削らない。
  `PLUGIN_API_VERSION` は **上げない**（後方互換な追加のため。`03_プラグイン設計.md` の互換方針）。

### 4.2 追加する型

```ts
/** 認可開始のときに Core が Plugin へ渡すもの。 */
export interface PluginAuthorizationStartContext extends PluginAuthenticationContext {
  /**
   * Core が発行した state。
   * **Plugin はこれを認可要求の `state` へそのまま載せる。自分で作らない。**
   * 照合は Core がコールバックで行う。
   */
  readonly state: string;
  /**
   * Core が発行した nonce。OIDC では認可要求の `nonce` へ載せる。
   * **Core が保証するのは「新鮮・この往復専用・一度きり」まで。**
   * ID Token の `nonce` Claim との照合は Plugin が行う（Core は JWT を解釈しない）。
   */
  readonly nonce: string;
  /**
   * Core が受け付けるコールバック URL（絶対 URL）。
   * **Plugin はこれをそのまま `redirect_uri` に使う。別の URL を使わない。**
   * コールバック時に Core が同じ値であることを照合する。
   */
  readonly redirectUri: string;
}

/** 認可開始の結果。 */
export type PluginAuthorizationStart =
  | { readonly ok: true; readonly authorizationUrl: string }
  /** 設定が足りない・外部が応答しない等。**理由は利用者へ出さない。** */
  | { readonly ok: false; readonly reason: 'unavailable' };

/** コールバックで戻ってきたもの。**state の照合は Core が済ませてある。** */
export interface PluginAuthorizationCallback {
  /** コールバック URL のクエリ文字列。`code` などが入る。 */
  readonly params: Readonly<Record<string, string>>;
  /** 認可開始時に渡したのと同じ redirect_uri。Token Exchange で必要になる。 */
  readonly redirectUri: string;
  /** 認可開始時に渡したのと同じ nonce。ID Token の Claim と照合する。 */
  readonly nonce: string;
}

/** `login.methods` から辿る入口。**Plugin がパスを推測しないよう定数で渡す。** */
export const AUTHORIZATION_START_PATH = '/api/v1/auth/authorize';
export const AUTHORIZATION_CALLBACK_PATH = '/api/v1/auth/callback';
```

### 4.3 `PluginAuthenticationProvider` への追加

```ts
export interface PluginAuthenticationProvider {
  readonly id: string;
  authenticate(...): Promise<PluginAuthenticationResult>;   // 変更なし
  getIdentity(...): Promise<PluginUserIdentity | null>;     // 変更なし
  logout(...): Promise<void>;                                // 変更なし
  refresh(...): Promise<void>;                               // 変更なし

  /**
   * 認可エンドポイントへの誘導を始める（任意実装）。
   *
   * **両方を実装するか、両方とも実装しないか。** 片方だけでは往復が閉じない。
   */
  startAuthorization?(
    context: PluginAuthorizationStartContext,
  ): Promise<PluginAuthorizationStart>;

  /** コールバックを受けて利用者を確定する（任意実装）。 */
  completeAuthorization?(
    callback: PluginAuthorizationCallback,
    context: PluginAuthenticationContext,
  ): Promise<PluginAuthenticationResult>;
}
```

`completeAuthorization` の戻りは `authenticate` と同じ `PluginAuthenticationResult`。
**成功の表現を2つ作らない。** 返した `userId` が Torifune に実在することを Core が確かめる点も同じ。

### 4.4 なぜ `PluginContext` にセッション発行 API を足さないのか

Plugin へ「セッションを張れ」という口を渡さない。渡すと、

* Session Fixation 対策（ログインのたびに新しいトークンを出す）
* 有効期限・アイドルタイムアウト・Remember Me の期間
* 失効（パスワード変更時の全セッション破棄）

の責任が Plugin ごとにばらける。
`apps/web/src/plugin/authentication-adapter.ts` が既に立てている方針であり、**崩さない。**

代わりに、**Core の口（`/api/v1/auth/callback`）が Plugin を呼び、
戻ってきた Identity を見て Core がセッションを張る。** 制御は常に Core にある。

## 5. Core 内部の型（`authentication/provider.ts`）

公開 API と同じ形を本体側にも置く。**HTTP の型（Request / Response / Cookie）を出さない。**

```ts
export interface AuthorizationStartContext extends AuthenticationContext {
  readonly state: string;
  readonly nonce: string;
  readonly redirectUri: string;
}

export type AuthorizationStart =
  | { readonly ok: true; readonly authorizationUrl: string }
  | { readonly ok: false; readonly reason: 'unavailable' };

export interface AuthorizationCallback {
  readonly params: Readonly<Record<string, string>>;
  readonly redirectUri: string;
  readonly nonce: string;
}

export interface AuthenticationProvider {
  // ...既存はそのまま
  startAuthorization?(context: AuthorizationStartContext): Promise<AuthorizationStart>;
  completeAuthorization?(
    callback: AuthorizationCallback,
    context: AuthenticationContext,
  ): Promise<AuthenticationResult>;
}
```

`createLocalProvider`（標準認証）はどちらも実装しない。
**標準認証にリダイレクト往復は無い。** 実装していないことをもって
「この環境ではリダイレクト型ログインは使えない」と判定できる。

## 6. State の保管

### 6.1 どこに置くか

**DB に置く。** 新しいテーブル `auth_authorization_states` を作る。

既存の使い捨てトークンの流儀（`password_reset_tokens`、`migrations/002_password_reset.sql`）に合わせる。

> **Cookie に置く案を採らない。** 署名付き Cookie で state を持たせる方式もあるが、
> それでは「一度しか使えない」を Core が保証できない（Cookie は利用者が複製できる）。
> **使い捨てを DB の `used_at` で担保する。** パスワードリセットと同じ形。
>
> **メモリに置く案も採らない。** Torifune は複数プロセスで動かせる想定であり、
> 認可開始とコールバックが別プロセスに当たると往復が成立しなくなる。
> Rate Limit（`login_attempts`）を Redis ではなく DB に置いたのと同じ判断。

### 6.2 テーブル定義（`migrations/017_authorization_states.sql`）

```sql
CREATE TABLE auth_authorization_states (
    id           uuid        PRIMARY KEY,
    -- state そのものは保存しない。ハッシュだけ（password_reset_tokens と同じ）。
    state_hash   text        NOT NULL UNIQUE,
    -- nonce は平文で持つ。コールバック時に Plugin へ「元の値」を渡す必要があり、
    -- ハッシュでは ID Token の Claim と照合できない。
    -- **nonce 単体では何の権限も無い**（往復の鍵は state のほう）。
    nonce        text        NOT NULL,
    -- 認可開始を行った Provider。差し替わっていたらコールバックを受け付けない。
    provider_id  text        NOT NULL,
    -- Core が Plugin へ渡した redirect_uri。コールバック時に同じ値かを照合する。
    redirect_uri text        NOT NULL,
    -- ログイン後の遷移先。**アプリ内の絶対パスだけ**（Open Redirect 対策）。
    return_to    text        NOT NULL DEFAULT '/',
    expires_at   timestamptz NOT NULL,
    -- 一度使った state を無効にする。
    used_at      timestamptz,
    created_at   timestamptz NOT NULL DEFAULT now()
);

CREATE INDEX auth_authorization_states_expires_at_idx
    ON auth_authorization_states (expires_at);
```

`user_id` を持たない。**認可開始の時点では、まだ誰か分かっていない。**

### 6.3 有効期限

`AUTHORIZATION_STATE_LIFETIME_MS = 10 * 60 * 1000`（10分）。

短すぎると IdP 側の入力（多要素認証など）が終わる前に切れ、長すぎると盗まれたときに危ない。
`RESET_TOKEN_LIFETIME_MS`（1時間）より短いのは、**往復が数十秒で終わる想定**だから。

### 6.4 コールバックで検証すること

順に、**1つでも合わなければ即座に失敗**とする。

1. `state` クエリがある
2. `state` のハッシュに一致する行がある
3. `used_at` が null
4. `expires_at` を過ぎていない
5. **その場で `used_at` を立てる**（`WHERE used_at IS NULL` 付きの UPDATE。
   同時に2本来ても1本しか通らない）
6. 保存された `provider_id` が、いま有効な Provider の ID と一致する
7. 保存された `redirect_uri` が、**いま到達しているコールバック URL と一致する**

失敗の理由を利用者へ返さない。すべて同じエラーにする。
「state が期限切れ」と「state が存在しない」を分けると、state の生死を外から探れる。

## 7. Core 側の API ルート

`05_API設計.md` の `/api/v1` 配下、既存の `app/api/v1/auth/` の流儀に合わせる。

### 7.1 `GET /api/v1/auth/authorize` — 認可開始

| 項目 | 値 |
| --- | --- |
| `operationId` | `startAuthorization` |
| `permission` | `null`（`reason`: 認証前に呼ばれる。ログインを始めるための口そのもの） |
| `documented` | `false`（ブラウザのリダイレクト用の口であり、API クライアントが叩くものではない） |
| `rateLimit` | `{ windowMs: 60_000, max: 30 }`（`login` と同じ） |
| クエリ | `returnTo`（任意。ログイン後の遷移先） |
| 応答 | 成功: `302` + `Location: <authorizationUrl>` ／ 失敗: 通常のエラー応答 |

**なぜ GET か。** `login.methods` へ差し込まれるのは Plugin が書いた部品であり、
**アンカー1つで辿れる形でなければ「Googleでログイン」ボタンが書けない。**
リダイレクト型ログインの入口が GET なのは、あらゆる IdP 連携で共通の形でもある。

**CSRF はかからない（`defineRoute` の `SAFE_METHODS`）。かけない理由**：

* この口はセッションに紐づく操作を一切していない。**まだ誰とも分かっていない相手**が叩く
* 仮に他所のサイトから叩かれても、起きるのは「IdP のログイン画面へ飛ばされる」だけ。
  **セッションはここでは張られない**（張るのはコールバック側）
* コールバック側は state で守る（§7.2）

### 7.2 `GET /api/v1/auth/callback` — コールバック

| 項目 | 値 |
| --- | --- |
| `operationId` | `completeAuthorization` |
| `permission` | `null`（`reason`: 外部 IdP からのリダイレクトを受ける。認証を成立させる口そのもの） |
| `documented` | `false` |
| `rateLimit` | `{ windowMs: 60_000, max: 30 }` |
| クエリ | 素通し（`code` / `state` / `error` など、方式ごとに違う） |
| 応答 | 成功: `302 returnTo` + `Set-Cookie`（セッション）／ 失敗: `302 /login?error=...`（詳細は出さない） |

**CSRF の扱い（コード中にも同じ理由を残す）**：

外部の IdP からのリダイレクトなので、**通常の CSRF 判定はそのままでは効かない。**

* `Origin` は IdP のオリジン（または欠落）になる。`isSameOriginRequest()` は必ず false になる
* `Sec-Fetch-Site` は `cross-site`
* CSRF トークン（`torifune_csrf` Cookie と `x-csrf-token`）は、
  **IdP が張るリダイレクトに載せられない**

したがって `verifyCsrf()` をここへ当てると、正当なコールバックが100%落ちる。

**その代わりを state 検証が担う。** state は

* Core が乱数（256bit）で発行し、DB にハッシュで保管する
* 認可要求と一緒に IdP へ渡り、IdP がそのまま返す
* **一度しか使えない**（`used_at`）
* **10分で切れる**
* Provider と redirect_uri に束縛されている

ため、攻撃者が有効な state を用意してコールバックを偽造することはできない。
これは OAuth 2.0 / OIDC で state が担う役割そのもの（`04_認証設計.md` §27「State検証」）である。

なお実装上、この口は **GET なので `defineRoute` の CSRF 検証はもともと通らない**。
`csrfExemptReason` は書かない（書けるのは非安全メソッドの話であり、
書くと「非安全メソッドで CSRF を外した」ように読める）。**理由はコードコメントで残す。**

**セッション Cookie を GET の応答で張ることについて**：
通常なら避けたい形だが、コールバックは
「state という一度きりの秘密を持って到達した要求」であり、
偽造も再送もできない。ログイン成立の一点に限って許す。

### 7.3 `endpoints.ts` への登録

2本とも `apps/web/src/api/endpoints.ts` へ import 行を足す必要がある
（`defineRoute` の副作用でエンドポイント登録が走るため）。

```ts
import '@/app/api/v1/auth/authorize/route';
import '@/app/api/v1/auth/callback/route';
```

## 8. 遷移先（`returnTo`）の検証

`isSafeReturnTo(path)` を Domain 層に置く。**Core が検証する。**

通すのは以下すべてを満たすものだけ。合わなければ `/` にする。

* `/` で始まる
* `//` で始まらない（`//evil.example` はプロトコル相対 URL として外部へ飛ぶ）
* `/\` で始まらない（一部のブラウザが `//` と同じに解釈する）
* 制御文字を含まない

**Plugin に検証させない。** Open Redirect は「1箇所で漏れれば終わり」の類の穴である。

```text
apps/web/src/application/auth/redirect-login.ts  UseCase（トランザクション境界はここ）

apps/web/src/app/api/v1/auth/authorize/route.ts  認可開始
apps/web/src/app/api/v1/auth/callback/route.ts   コールバック

migrations/017_authorization_states.sql
```

**Domain 層は `pg` / `kysely` を知らない。**
**API ルートは Cookie とリダイレクトだけを扱い、判断は UseCase に置く。**

### UseCase の形

```ts
// application/auth/redirect-login.ts

export type StartRedirectLoginOutcome =
  | { readonly ok: true; readonly authorizationUrl: string }
  | { readonly ok: false; readonly reason: 'unsupported' | 'unavailable' };

export async function startRedirectLogin(input: {
  readonly redirectUri: string;   // API Layer が組み立てた絶対 URL
  readonly returnTo: string | undefined;
  readonly request: RequestInfo;
}): Promise<StartRedirectLoginOutcome>;

export type CompleteRedirectLoginOutcome =
  | {
      readonly ok: true;
      readonly user: PublicUser;
      readonly sessionToken: string;
      readonly expiresAt: Date;
      readonly returnTo: string;
    }
  | { readonly ok: false; readonly reason: 'invalid_state' | 'invalid_credentials' | 'too_many_attempts' };

export async function completeRedirectLogin(input: {
  readonly params: Readonly<Record<string, string>>;
  readonly redirectUri: string;   // いま到達しているコールバック URL
  readonly request: RequestInfo;
}): Promise<CompleteRedirectLoginOutcome>;
```

`unsupported` は「いまの Provider が往復型を実装していない」。
**`unavailable`（Plugin が開始できなかった）と区別する**が、
**画面へは同じ文言を出す**（どちらも「ログインを開始できませんでした」）。

`completeRedirectLogin` は `login()` と同じく `withTransaction` の中で

1. state の照合と使用済み化
2. `provider.completeAuthorization()`
3. `provider.issue()`（**Core のセッション発行**）
4. 監査ログ（`login.succeeded` / `login.failed`、`detail: { flow: 'redirect' }`）

を一括で行う。途中で失敗したら何も残さない。

Remember Me は**効かせない**。リダイレクト型では「ログインしたままにする」を
選ばせる画面が Torifune 側に無く、**利用者が選んでいないものを勝手に長期化しない。**
既定の期間（`SESSION_LIFETIME_MS`、システム設定に従う）で発行する。

### redirect_uri の組み立て

`APP_URL` を最優先し、無ければリクエストの `x-forwarded-host` / `host` から組み立てる。
`api/csrf.ts` の `expectedHost()` と同じ優先順位にそろえる
（`api/absolute-url.ts` として切り出し、両方が同じ判断を使う形にはしない
—— `csrf.ts` は他のエージェントが触っている `route.ts` から使われるため、
**この機能では新しいヘルパを足すだけに留め、既存を書き換えない**）。

**`request.url` を使わない。** Next.js が `localhost` へ正規化するため、実際のホストと一致しない。

## 10. `login.methods` から実際に使えること

Plugin の `login.methods` 部品は、`AUTHORIZATION_START_PATH` へのリンクを描くだけでよい。

```tsx
import { AUTHORIZATION_START_PATH } from '@torifune/plugin-api';

export function SsoLoginButton() {
  return <a href={AUTHORIZATION_START_PATH}>SSOでログイン</a>;
}
```

`PublicExtensionPoint`（`ui/plugin/plugin-slot.tsx`）は既にログイン画面へ枠を描いており、
**本体側の描画は1行も変えない。**

Provider は同時に1つしか有効にならない（`authentication/registry.ts`）ため、
**パスに Provider を指定しない。** どの Provider が担うかは Core が知っている。

## 11. サンプル Plugin（`plugins/example-plugin/`）

既存の合言葉型ダミーを**置き換えず、同じ Provider に往復型を足す。**
`authenticate()` はそのまま残り、`startAuthorization` / `completeAuthorization` が増える。

**外部サービスへは繋がない。** ループバックさせる。

* `startAuthorization` は、**Core から渡された `redirectUri` へそのまま戻る URL** を返す
  （`${redirectUri}?state=<state>&code=example-code`）。
  「IdP が0ホップで即座にリダイレクトを返した」のと同じ形になる
* `completeAuthorization` は `params.code` が `example-code` であることだけを確かめる
  （本物はここで Token Exchange と ID Token 検証を行う）
* `login.methods` の部品（`ExampleLoginMethod`）を、
  `AUTHORIZATION_START_PATH` へのリンクへ差し替える

これで **ブラウザの往復・Core の state 発行・照合・使い捨て・セッション発行が
すべて本番と同じ経路を通る。** 短絡しているのは「外部 IdP が居るかどうか」だけ。

有効化の条件は既存と同じ `EXAMPLE_PLUGIN_AUTH_USER_ID`。
**既定では差し替えない**（差し替えると以後のログインがダミーを通る）。

## 12. テスト

### 12.1 ユニット

| 対象 | 見るもの |
| --- | --- |
| `domain/authorization-state.ts` | 期限切れ・使用済みで使えない／`isSafeReturnTo` が `//evil` `/\evil` `http://…` 制御文字を落とす |
| `plugin/authentication-adapter.ts` | 往復メソッドを持たない Plugin では本体側にも生えない／持つ Plugin では Identity が実在確認を通る／**`issue` が `options` を転送し続ける（既存の回帰）** |
| `packages/plugin-api` | 追加した型が既存を壊していない（既存 Provider がそのまま型検査を通る） |

### 12.2 結合（DB あり）

| 対象 | 見るもの |
| --- | --- |
| `application/auth/redirect-login` | 往復が成立してセッションが張られる |
| 同 | **同じ state を2回使うと2回目が失敗する**（使い捨て） |
| 同 | 期限切れの state が失敗する |
| 同 | 存在しない state が失敗する（理由が期限切れと区別できない） |
| 同 | `redirect_uri` が発行時と違うと失敗する |
| 同 | Plugin が実在しない `userId` を返すと失敗する（`invalid_credentials`） |
| 同 | 往復型を実装していない Provider では `unsupported` |
| 同 | `returnTo` に外部 URL を渡しても `/` に落ちる |
| 同 | 成功・失敗が `auth_audit_logs` に残る |

### 12.3 E2E

`plugins/example-plugin` のループバック Provider を有効にし、

* ログイン画面に Plugin のログイン手段が出る
* リンクを押すと往復してログインが成立し、`/` へ着く
* 同じコールバック URL をもう一度開くと失敗する

E2E は本番ビルドを要するため、**実行できない環境では結合テストで往復を確かめる**
（`redirect-login` の結合テストが同じ経路を通る）。

## 14. 決めなかったこと（この設計の範囲外）

| 項目 | 理由 |
| --- | --- |
| PKCE の Code Verifier を Core が持つか | **Plugin が持つ。** `code_challenge_method` は方式ごとに違い、Core が知ると Core が OAuth を知ることになる。Plugin は `PluginStore` に state をキーとして保管できる |
| Response Mode `form_post`（POST でのコールバック） | GET のコールバックだけを実装する。`form_post` は POST になるため CSRF の扱いが変わり、別途の設計が要る。**必要になったときに足す** |
| 外部の利用者を初回ログインで自動作成する（JIT Provisioning） | 既存の方針（`authentication.ts` のコメント）を変えない。実在するユーザーを返すこと |
| ログアウト時の IdP へのシングルログアウト | `logout()` は既にあり、Plugin が外部へ通知できる。リダイレクトを伴う RP-Initiated Logout は範囲外 |
| 複数の Authentication Provider の同時有効化 | `authentication/registry.ts` が1つしか持たない構造。変えるのは別の設計 |
