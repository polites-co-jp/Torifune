### 確定事項（設計書から。プランで蒸し返さない）

* 項目名 **`publishTiming`**、値 **`now` / `scheduled` / `after_approval`**。新しい状態 **`awaiting_approval`**（表示「承認待ち」）。`deliveryMode` とは別の軸（設計 §6.1。裁定 3・6）
* `publishTiming` を**送らない要求は今の振る舞い**（裁定 1）。`POST` の `status` から Zod の `.default('draft')` を外し、省略時の `draft` は UseCase が補う。`publishTiming` と `status` の同時指定は 422 `status`、`now` と `scheduledAt` の値の同時指定は 422 `scheduledAt`（Zod の `superRefine`。違反はまとめて返す）（設計 §6.2.1・§6.2.4 の 1b）
* 解決は Domain の純関数 **`resolveCreateTiming`**（設計 §6.2.2 の表）。`now` の `scheduledAt` は**サーバのいまの時刻**。`externalRef` の再送は既存を返す（`publishTiming` が違っても）。1b は再送でも掛かる（設計 §6.2.4）
* 承認は専用の操作 **`POST /api/v1/social/posts/{id}/approve`**（Permission **`social.approve`**）。要求は `publishTiming: now | scheduled`（必須）・`scheduledAt`（任意）・**`expectedUpdatedAt`（必須）**。`updated_at` は**ミリ秒に切り詰めて**比べ、合わなければ **409 `CONFLICT`**・`details.expectedUpdatedAt`。承認待ちでなければ **422 `status`（409 より先）**。条件付きの `UPDATE` 1 文で判定と更新を行う（設計 §6.4）
* 時刻は Domain の純関数 **`resolveApprovalSchedule`**。決めた日時が**いま以前（等しいときも）なら 422 `scheduledAt`**。過去を即投稿に読み替えない（設計 §6.4.5。裁定 4）。承認では `next_attempt_at` を NULL にし、`skip_count` / `skip_reason` / `attempt_count` は触らない
* 裁定 5 の判定は **(b)**：その provider の配信 Plugin が `manual()` を持ち `publish()` を持たない（Domain `isManualOnlyPublisher`、Application `isManualOnlyProvider`）。**provider 名で分岐しない**。掛ける範囲は **(i)** `publishTiming` を送った `POST` と承認だけ（設計 §6.7。裁定 7・8）。読み替えは 201 / 200 で返し、422 にしない
* `PATCH` の遷移は設計 §6.6.2 の表。`awaiting_approval → scheduled` は 422 `status`（「承認待ちの投稿は、承認の操作でだけ予約にできます。」）。`→ published / failed` も 422。`PATCH` に `publishTiming` を送ると**どの値でも 422 `publishTiming`**（設計 §6.3）
* **承認済みの予約（`approvedAt` あり）の内容・日時・配信方法を値として変えたら承認待ちへ戻す**（Domain `revokesApproval`。`media` は順序込み、`providerOptions` はキーの順序に依らず比べる）（設計 §6.3.3。裁定 10）
* 承認待ちへ移すときと承認のときに `next_attempt_at` を NULL にする。`→ draft` と `→ awaiting_approval` は `approved_at` を NULL にし、`→ published / failed` は残す（設計 §6.3.2・§6.3.3）
* 事前検査：`checkSchedulable` は変更後が `draft` / `awaiting_approval` / `scheduled`、`checkPublisherRules` は変更後が `scheduled` / `awaiting_approval`。作成は状態を問わず全部掛かる。承認は `{ checkSchedulable: true, checkPublisherRules: true, checkManualSupport: deliveryMode === 'manual' }`（設計 §6.2.4・§6.3.2・§6.4.4）
* マイグレーション **`025_social_post_approval.sql`** は設計 §5.1 の SQL のとおり（CHECK の張り替えを 1 文の `ALTER TABLE` で、`approved_at` と CHECK、`social.approve` を administrator / editor に）。索引は足さない
* 新しい Permission **`social.approve`**。説明は `'承認待ちのSNS投稿を承認して配信に回す（投稿を登録する外部アプリのトークンには付けない）'`。`HIGH_PRIVILEGE_PERMISSIONS` に入れない（設計 §8.2。裁定 9）
* 新しいイベント **`social.post.approved`**（Payload は既存の `SocialPostEventPayload`、`status: 'scheduled'`）。**`PLUGIN_API_VERSION` は 1 のまま**。`SocialPostView` に `approvedAt` を足さない。`PublisherRegistration` を変えない（設計 §6.8・§9）
* 監査：承認は `approved`（`detail` は `{ requestedTiming, effectiveTiming, scheduledAt, deliveryMode, approvalForced, via }`）、登録の `detail` に `publishTiming` と `approvalForced`、更新の `detail` に `status`（更新後）（設計 §6.9）
* **配信ジョブ（`publish.ts`）は変えない**。取り出し・着手・記録・手動投稿待ちは `status = 'scheduled'` を条件にしているので承認待ちを拾わない（設計 §6.10）
* 画面：`/social` の「手動投稿待ち」の**上**に「承認待ち」区画（カード。全文・リンク・画像の URL と代替テキスト。サムネイルは出さない）、承認のダイアログ（manualOnly は「即投稿」だけ）、差し戻し（`PATCH { status: 'draft' }`）、投稿一覧・投稿フォームの追随、ダッシュボードの `ApprovalPendingReminder`（設計 §7。裁定 11）
* 文書の書き戻しは設計 §12 の範囲。**`docs/仕様書/` は変えない**（設計 §2 に上位仕様との矛盾は無いとある。`04` / `05` への書き戻しは §12 に無い）
* 検証は **`spec-verifier` / `boundary-guardian` / `security-reviewer` の 3 つ**（Core の状態・公開 HTTP API・Plugin から見える振る舞い・新しい Permission を変えるため）
* **SaaS 固有機能（テナント・課金・コンテナ管理）に触るタスクは本プランに無い**

## 3. タスク分解

原則：**1 タスク = 1 コミット**。各タスクは「テストを書いて失敗を確認 → 実装 → 通す」の順。
各まとまり（G1〜G8）の最後で `pnpm test` / `pnpm typecheck` / `pnpm lint` / `pnpm format:check` が通る。E2E は T26 でだけ全件流す（作業機では流さない。§4 の注）。

**test-writer → implementer への受け渡しの単位は G（まとまり）。** test-writer は G の中の全タスクのテスト（と既存テストの追従）を先に書いて失敗を確かめ、`test:` でコミットする。implementer は G の中のタスクを順に通し、タスクごとに `feat:`（文書は `docs:`）でコミットする。
**implementer はテストを書き換えない。** テストが設計と食い違うと判断したら、設計書のどこと食い違うかを報告して止まる。

**着手順の骨子**：DB と Core の定数 → Domain の状態と純関数 → 登録（応答の `approvedAt` を含む）→ 更新の規則 → 承認・一覧・イベント → UI の部品 → 画面の組み立てと E2E → 文書 → 最終確認と 3 つの検証。
**G は前の G に依存する**（G2 は G1、G3 は G2、G4 は G3、G5 は G4、G6 は G5 の UseCase の型、G7 は G6）。G8 は G5 の後ならいつでもよいが、振る舞いが入ってから書く。

## 7. リスクと注意点

1. **`status` の Zod の既定を外すと、UseCase の入力の型が変わる（T8・T9）。** `CreatePostInput.status` が任意になる。省略時の `draft` は `resolveCreateTiming` の表の 1 行目で補う。ルートは `body.status` が `undefined` のときキーごと渡さない（`exactOptionalPropertyTypes` の下で `status: undefined` を渡さない）
2. **`superRefine` の掛かる条件（T8）。** 設計 §6.2.4 の 1b は「1 が通ったときだけ」。Zod 4 のオブジェクトの `superRefine` が項目の誤りのある入力でも走るかを実装で確かめ、走るなら `publishTiming` の列挙の誤りと同時指定の誤りが同じ 422 に並ばないようにする（§8 の 6 の対照の件）
3. **`resolveCreateTiming` は再送の判定の後（T9）。** 設計 §6.2.4 の順（再送なら 5 以降を行わない）。ただし 1b（Zod）は再送でも掛かる（#23）
4. **承認の条件付き更新は 1 文（T15）。** 読んでから書く 2 段にすると、その間の `PATCH` を承認してしまう。`updated_at` は `date_trunc('milliseconds', …)` で比べる（R5。#41 の作成直後の件が守る）
5. **422 `status` を 409 より先に見る（T16）。** 他の人が承認し終えた投稿は `updatedAt` も変わっているが、「もう承認されている」を返す（設計 §6.4.4 の 3）。0 行のやり直しでも同じ順
6. **事前検査の区分（T12）。** `→ draft` に配信 Plugin の検査を掛けない（出口を塞がない。#27）。承認待ちには掛ける（#28）
7. **`next_attempt_at` の消し方（T12・T16）。** 承認待ちへ入るときと承認のときに NULL。`skip_count` / `skip_reason` / `attempt_count` は触らない（#25・#48）。既存の `clearsSkipWait` の条件は変えない
8. **`approved_at` の CHECK（T12）。** `draft` / `awaiting_approval` へ移すのに `approvedAt: null` を渡し忘れると DB の制約違反（500）になる。#30 の `→ draft` と承認の取り消しの件がこれを踏む
9. **`Record<PostStatus, …>` の追従（T5）。** `ALLOWED_TRANSITIONS` と `POST_STATUS_LABEL` は型で追従が強いられるが、**ダッシュボード専用の `POST_STATUS_LABEL`（`Record<string, string>`）は型で気づけない**（要裁定 2）
10. **文書の静的検査の文字列を消さない（T25）。** `static-checks.test.ts` #81 は `Plugin開発ガイド.md` の `registerPublisher`・「自動配信の予約は断られない」・`Eventリファレンス.md` の `social.post.failed` の行と「`social.post.failed` なら `'failed'`」などを見る。`text-input-docs-static-checks.test.ts` #54 は `SNS投稿API仕様.md` §1.3 / §1.4 の語を見る。書き換えるときにこれらを残す
11. **`social.approve` はマニュアルの Permission 名の検査に拾われない（T25）。** #81 の正規表現は `read|write|delete|manage` だけを拾う。`SNS投稿の外部連携.md` の「できてしまうこと」の表に `social.approve` を書くなら、その行に「このトークンには無い」を添える（#81 の「social.write のトークンでできる」の検査の趣旨に合わせる）。検査そのものは変えない
12. **E2E の後片付けと順序（T23）。** `social-approval.spec.ts` は `social-credentials.spec.ts`・`social-publishing.spec.ts`・`social.spec.ts` より前に走る。`example-plugin` と承認待ちの投稿を残すと、後の spec の前提（Plugin の無い状態、承認待ち 0 件で区画が描かれない）を壊す。**`afterAll` で必ず片付ける**
13. **`GET /api/v1/auth/csrf` の Rate Limit（1 分 300 回）（T23）。** API での準備を最小にし、アカウントとトークンは spec の中で使い回す
14. **`router.refresh()` の費用（T20）。** 承認・差し戻しのたびに `/social` の Server Component（手動投稿待ちの `resolveManualHandoff` を含む）が描き直される。操作 1 回分
15. **`toLocalInputValue` の移動（T19）。** `social-post-form.tsx` の振る舞いを変えない（既存の `social-post-form.test.ts` と E2E が守る）
16. **公開リポジトリ（全コミット）。** コメント・コミットメッセージ・文書に外部の製品名や運営側の事情を書かない
17. **`verify-container-rebuild.sh` は Docker が要る（T26）。** 無い環境では飛ばし、検証レポートへ申し送る
