# 048 SNS 投稿の承認待ち 検証レポート

外部アプリが API で SNS 投稿を依頼するときに「即投稿」「指定の時間」「人の承認を待つ」を選べるようにし、
承認する人が管理画面で「即投稿」か「指定の時間」かを選べるようにした作業単位（ユーザー裁定 2026-09-30）。

実装完了時点（`b6f05b6`）に対し、3 つの検証エージェントを**互いの結果を見せずに独立して**走らせた。

| 担当 | 判定 |
| --- | --- |
| `spec-verifier`（設計との整合） | **条件付き合格**（重大 1・軽微 5。受け入れ条件 #1〜#77 は全件充足、指定の 13 種の変異はすべて検出） |
| `boundary-guardian`（境界・公開 API） | **合格**（低 2・情報 3） |
| `security-reviewer`（セキュリティ） | **条件付き合格**（中 1・低 3・情報 3） |

`spec-verifier` の重大 1 と `security-reviewer` の中 1 は**同じ不具合**で、両者が独立に見つけた（§1）。
修正（`c15c163`）の後、`security-reviewer` に修正の差分だけを見直させた（§3）。

## 1. 見つかった不具合：PATCH と承認の競合（重大／中-1・低-1）

`PATCH /social/posts/{id}` は投稿を読み、配信 Plugin の検査（`validate()`。最長 5 秒）を経てから書く。
承認を外すか・承認の記録を消すかは**読んだ時点の行**で決めていて、書き込みは `WHERE id = $id` だけだった。

* 承認待ちへの `PATCH { body }` の途中で人が承認すると、200 が返り、行は `scheduled`・`approved_at` ありのまま、
  **本文だけが人の見ていないものに替わる**。`now` で承認していれば 1 分以内に SNS へ出る。設計 §1 の 3
  （見た内容だけを承認する／承認の後の書き換えは承認を外す）が両方とも破れる
* 承認待ちへの `PATCH { status: 'draft' }`（差し戻し）の途中で承認すると、`approved_at` を残したまま状態を変えようとして
  CHECK に落ち、**500** が返る

受け入れ条件 #42 は「承認と承認」の同時実行だけを固定していて、「PATCH と承認」は設計にも条件にも無かった。

### 直し方（`c15c163`。設計 §6.3.6）

* Repository の `updatePost` に**読んだ時点の `status` と `approved_at` を条件として渡し**、1 文で判定して書く
  （READ COMMITTED では、行ロックを待った UPDATE は WHERE を最新の行で評価し直すので、承認の後の行には当たらない）
* 当たらなければ読み直し、無ければ 404、あれば **409 `CONFLICT`**（`details.status`「投稿の状態が変わっています。
  読み直してからやり直してください。」）。何も変えず、監査 `updated` も残さない
* `updated_at` の一致では見ない（`PATCH` には `expectedUpdatedAt` が無く、状態の変わらない書き換えどうしは従来どおり後勝ち）。
  `SELECT … FOR UPDATE` は `validate()` の最長 5 秒の間ロックを持つので採らない
* OpenAPI の `updateSocialPost` に 409 を宣言し、API 仕様書（§2.3・§3.2・§3.3・§3.7・§4.7・§9）を更新した

**再現テストを先に書き、修正前に落ちることを確かめた**（#78・#79 の 5 件。「expected 200 to be 409」「本文が置き換わる」
「expected 500 to be 409」）。割り込みは、PATCH がアカウントを読むところで止めて承認を通す形で作る
（差し戻しは `validate()` を呼ばないので、`validate()` では止められない）。修正から条件を外すと 5 件とも落ちる。

## 2. その他の指摘と対応

| 出所 | 指摘 | 対応 |
| --- | --- | --- |
| spec 軽微 2 | 承認の 1 文の条件から `updated_at` の比較だけを抜いても通る（UseCase の比較が先に断るため） | **テストを足した**（#80。Repository の `approvePost` を古い `expectedUpdatedAt` で直接呼ぶと null で行は変わらない）。条件を抜くと落ちることを確かめた |
| spec 軽微 3 | 「承認待ちでない」の 422 を 409 より先に見る順が固定されていない | **テストを足した**（#80。下書きを古い `updatedAt` で承認すると 422 `status`）。順を入れ替えると落ちることを確かめた |
| spec 軽微 4 | UseCase の `social.approve` を `social.write` に替えても通る（ルートの検査が同じことをするため） | **テストを足した**（#81。`social.read` + `social.write` だけの文脈で UseCase を呼ぶと `ForbiddenError`）。替えると落ちることを確かめた |
| spec 軽微 5 | 承認時に `next_attempt_at` を NULL にする処理を抜いても通る | **記録のみ**。承認待ちの行が `next_attempt_at` を持つ経路が無く、結果の変わらない変異 |
| spec 軽微 6・boundary 低 1 | API 仕様書の変更履歴で 2026-10-01 の行が空行の後ろにあり、表から切れる | **直した** |
| boundary 低 2 | Plugin 開発ガイドで、承認の注記が「自動配信の予約は断られない」と「支度が整うまで…待ち」の間に挟まり、意味が取りにくい | **直した**。独立の段落にし、判定が登録のときと承認のときの登録簿で行われること（後の版で `publish()` を足すと承認のときから扱いが変わる）を足した |
| boundary 情報 1 | マイグレーション 025 の戻し方の注記に、API トークンの Scope から `social.approve` を外す手順が無い | **025 は変えない**（適用済みの DB でファイルの照合値が変わるため）。手で戻すときは注記の手順に加えて `UPDATE api_tokens SET scopes = array_remove(scopes, 'social.approve');` を流す。監査 `approved` の行は残り、`approved_at` は列ごと消える |
| boundary 情報 2 | Plugin の ID が Core の名前空間（`social` など）と衝突しうる | **048 の範囲外（既存）。** 公開前に別に裁定を仰ぐ（§4） |
| boundary 情報 3 | `CORE_EVENTS` の並び | 対応不要 |
| security 低-2 | 承認の後でも `social.write` でアカウントの資格情報を差し替えられ、承認は外れない（承認した投稿が別の SNS アカウントから出うる） | **文書に明記した**（API 仕様書 §2.3）。既存の `social.write` の権限で、048 で新しく生じたものではない |
| security 低-3 | 承認画面に `providerOptions` が出ない | **記録のみ**（§4）。同梱の Plugin が受け付けるのは Bluesky の `langs` だけで実害は無い。画面に足すのは計画に無い追加なので裁定を仰ぐ |
| security 情報-1 | 承認はトークン自身には強制されない | 設計どおり（§6.6.3・裁定 8）。API 仕様書 §6.1 に既に明記 |
| security 情報-2 | `expectedUpdatedAt` はミリ秒の時刻で厳密な版番号ではない | 記録のみ。同じミリ秒に人の操作を挟む必要があり現実的でない。精度の扱いは 0〜999 の全値で整合を確認済み |
| security 情報-3 | `social.approve` だけを持ち `social.read` を持たない独自ロールでも承認 API から投稿の状態を知れる | 記録のみ。既定のロールでは両方を持つ |
