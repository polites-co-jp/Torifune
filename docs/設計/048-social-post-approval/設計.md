## 1. 目的

1. **外部アプリが、投稿ごとに「すぐ出す／この時刻に出す／人が確かめてから出す」を選べるようにする。**
   いまの API で選べるのは「下書き（`draft`）」か「予約（`scheduled` ＋ `scheduledAt`）」だけで、
   「すぐ出す」は `scheduledAt` に現在時刻を入れる約束事（仕様書 §1.1）でしか表せず、
   「人が確かめてから出す」は表す手段が無い。外部アプリが生成した本文をそのまま SNS へ出してよいかを、
   運用する人が画面で確かめてから出したい、という使い方ができない
2. **「確かめてから出す」を、Torifune の管理画面の 1 か所で完結させる。** 承認待ちの投稿を `/social` に並べ、
   本文・リンク・画像の URL・投稿先を見て、「即投稿」か「指定の時間に投稿」を選んで承認する。
   差し戻す（下書きへ戻す）こともできる
3. **承認が意味を持つようにする。** 承認は「この内容を、この時刻に出してよい」という人の判断の記録である。
   次の 3 つを守る
   * 承認できるのは**承認の権限を持つ者だけ**（§8。外部アプリのトークンが自分の依頼を自分で承認できない）
   * 承認するのは**画面で見た内容**（見た後に書き換えられていれば 409。§6.4.3）
   * 承認した後に**内容や日時を書き換えたら、承認待ちへ戻る**（§6.3.3）
4. **既存の外部アプリを壊さない。** 新しい項目を送らない要求は今までどおりに動く（裁定 1）。
   `deliveryMode`（誰が SNS へ出すか）とは別の軸として足し、名前も値も重ねない（裁定 6）

## 3. スコープ

### 3.1 やること

1. `POST /api/v1/social/posts` に **`publishTiming`**（`now` / `scheduled` / `after_approval`）を足す（§6.2）
2. 投稿の状態に **`awaiting_approval`（承認待ち）** を足す。状態の CHECK を変えるマイグレーション `025`（§5）
3. **承認の操作** `POST /api/v1/social/posts/{id}/approve`（`publishTiming: now | scheduled`、`expectedUpdatedAt`）（§6.4）
4. 新しい Permission **`social.approve`**（既定で管理者・編集者）（§8）
5. `PATCH /api/v1/social/posts/{id}` の状態遷移の規則の更新（承認待ちへの移行、差し戻し、承認済みの予約の書き換えで承認が外れる）（§6.3）
6. **裁定 5**：手動投稿しかできない配信 Plugin（いまは `sns-x-manual` だけ）の provider では、`publishTiming` を送った登録は常に承認待ちになり、承認は常に即投稿になる（§6.7）
7. イベント **`social.post.approved`** と監査の `approved`（§6.8・§6.9）
8. `/social` の **「承認待ち」区画**（一覧・内容の確認・承認［即投稿／指定の時間］・差し戻し）、投稿一覧・投稿フォーム・ダッシュボードの追随（§7）
9. OpenAPI・仕様書（`docs/マニュアル/SNS投稿API仕様.md`）・関連文書の書き戻し（§12）

### 3.2 やらないこと

* **承認の強制**（「このトークンからの投稿は必ず承認を経る」のような運用者側の設定）。裁定 1 のとおり、承認を待つかは
  **外部アプリが要求ごとに選ぶ「確認の依頼」**である。`social.write` を持つ者は、承認を経ない予約（`status: "scheduled"`）も
  今までどおり作れる（§6.6.3・§13 の R3）
* **差し戻しの理由の記録と、差し戻しのイベント**。差し戻しは既存の「取りやめ」と同じ `→ draft` の遷移で、
  取りやめにもイベントは無い（§11.2 の 1）
* **承認待ちの期限切れ**（一定時間で自動的に取りやめる）。放っておかれた承認待ちは残り続ける（§11.2 の 2）
* **複数人の承認・承認の段階**。1 人が承認すれば予約になる
* **Plugin からの承認**。Data API に承認の口は足さない（承認は人の判断の記録である）
* **画像のサムネイル表示**。画面のセキュリティヘッダ（`img-src 'self' data: blob:`）が外部の画像を読ませないので、
  承認待ちの区画には画像の URL と代替テキストを出す（§7.1.2）。ヘッダは変えない
* `deliveryMode` の自動の切り替え（X の無料版で `auto` を送った要求は、今までどおり配信 Plugin の検査で 422 `deliveryMode`）
* `PATCH` に `publishTiming` を足すこと（`PATCH` は今までどおり `status` と `scheduledAt` で表す。送ったら 422。§6.3.5）

### 3.3 全体の流れ

```text
外部アプリ ──POST /social/posts { publishTiming }──▶ Torifune
   now            → status: scheduled, scheduledAt: いま     ─┐
   scheduled      → status: scheduled, scheduledAt: 指定      ─┼─▶ 定期実行（auto）／手動投稿待ち（manual）
   after_approval → status: awaiting_approval（承認待ち）     ─┐│
   （手動投稿しかできない配信 Plugin の provider では、どれを送っても awaiting_approval。裁定 5）
                                                              ││
管理画面 /social「承認待ち」 ◀─────────────────────────────────┘│
   [承認する] → 即投稿 or 指定の時間に投稿                         │
        POST /social/posts/{id}/approve ─▶ status: scheduled ────┘  （イベント social.post.approved）
   [差し戻す] → PATCH { status: "draft" }
```

## 5. データモデル

### 5.1 マイグレーション `migrations/025_social_post_approval.sql`

```sql
-- SNS 投稿の承認待ち（048-social-post-approval 設計 §5）。
--
-- 1. 状態に awaiting_approval（承認待ち）を足す。**既存の 4 値の意味は変えない。**
-- 2. 承認した時刻 approved_at を足す。承認を経た予約だけが値を持つ（承認を外す判定に使う。設計 §6.3.3）。
--    誰が承認したかは audit_logs に残す（列にはしない。設計 §5.2）。
-- 3. Permission social.approve を足し、administrator と editor に割り当てる（設計 §8）。
--
-- 既存行はすべて approved_at = NULL になり、意味は変わらない。索引は足さない（設計 §5.3）。
--
-- **戻すとき**（手で戻す場合。承認待ちの行が残っていれば先に draft へ移す）:
--   UPDATE social_posts SET status = 'draft' WHERE status = 'awaiting_approval';
--   ALTER TABLE social_posts DROP CONSTRAINT social_posts_approved_at_check, DROP COLUMN approved_at;
--   ALTER TABLE social_posts DROP CONSTRAINT social_posts_status_check,
--     ADD CONSTRAINT social_posts_status_check CHECK (status IN ('draft', 'scheduled', 'published', 'failed'));
--   DELETE FROM role_permissions WHERE permission_name = 'social.approve';
--   DELETE FROM permissions WHERE name = 'social.approve';
ALTER TABLE social_posts
    DROP CONSTRAINT social_posts_status_check,
    ADD CONSTRAINT social_posts_status_check
        CHECK (status IN ('draft', 'awaiting_approval', 'scheduled', 'published', 'failed')),
    ADD COLUMN approved_at timestamptz,
    -- 承認の記録を持てるのは、承認を経て予約になった行と、その結果（配信済み・失敗）だけ。
    ADD CONSTRAINT social_posts_approved_at_check
        CHECK (approved_at IS NULL OR status IN ('scheduled', 'published', 'failed'));

INSERT INTO permissions (name, display_name, description, is_system) VALUES
    ('social.approve', 'SNS投稿の承認', '承認待ちのSNS投稿を承認して配信に回せる', true);

INSERT INTO role_permissions (role_id, permission_name) VALUES
    ('01900000-0000-7000-8000-000000000001', 'social.approve'),   -- administrator
    ('01900000-0000-7000-8000-000000000002', 'social.approve');   -- editor
```

* **CHECK の張り替えは 1 文の `ALTER TABLE` の中で行う**（`DROP` と `ADD` の間に他の書き込みが割り込まない）。
  `ADD CONSTRAINT … CHECK` は既存行を検査するので `social_posts` に ACCESS EXCLUSIVE のロックが掛かるが、
  既存行はすべて 4 値のどれかで通り、行数は SNS 投稿の件数（数万件でも数百ミリ秒）に留まる。`NOT VALID` にはしない
  （張り替えの直後から新しい制約で守られていることを、後続の検査に頼らず保証する）
* `approved_at` の CHECK は、承認待ち・下書きの行が承認の記録を持たないことを DB でも守る
  （承認を外す・差し戻すときに Application が NULL に戻し忘れると、ここで落ちる）
* Permission の追加は `011_api_tokens.sql`（`token.manage`）と同じ形。administrator への割り当ては
  `001` の方針（動的に拾わず、マイグレーションで明示する）に従う

### 5.2 `approved_at` だけを持ち、承認者の列を持たない理由（決めたこと）

* **承認を外す判定（§6.3.3）に要るのは「承認を経た予約か」だけ**で、それは `approved_at IS NOT NULL` で決まる
* 誰が承認したかは **監査ログ**（`audit_logs.actor_user_id` と `detail`）が持つ。列に複製すると、ユーザーを削除したときの
  外部キーの扱い（`SET NULL` にするか）と、応答に出すか（他のユーザーの ID を `social.read` の誰にでも見せることになる）を
  別に決めなければならない。画面が承認者の名前を出す要求は無い
* 応答には **`approvedAt`** を出す（§6.11）。外部アプリが「人が承認した予約か」を見分けられる

### 5.3 索引

足さない。承認待ちの一覧（§6.5）は `WHERE status = 'awaiting_approval' ORDER BY created_at, id LIMIT 50` で、
既存の `(status, scheduled_at, id)` 索引（`024`）が `status` の絞り込みに効く。承認待ちの行は人が捌く量
（数十件）に留まる前提で、並べ替えの費用は無視できる。

### 5.4 `database/schema.ts`

`SocialPostsTable` に `approved_at: Date | null` を足す。`status` は `string` のまま（Domain で `isPostStatus` が見る）。

## 6. API

### 6.1 項目名と値（決めたこと。裁定 3・6）

| | 決めたこと | 理由 |
| --- | --- | --- |
| 項目名 | **`publishTiming`** | 「**いつ**配信へ回すか」を言う項目。既存の `deliveryMode` は「**誰が** SNS へ出すか（Torifune か人か）」で、2 つは直交する（どの組み合わせも意味を持つ。§6.1.1）。`delivery…` / `manual…` / `mode` を名前に含めない（裁定 6） |
| 値 | **`now`** / **`scheduled`** / **`after_approval`** | `now`＝即投稿、`scheduled`＝`scheduledAt` の時刻に投稿、`after_approval`＝ユーザの確認を待ってから投稿。`deliveryMode` の値（`auto` / `manual`）と 1 つも重ならない。`after_approval` は「承認の**後**に回す」ことを値だけで読めるようにした（`approval` だけでは「承認のしかた」とも読める）。複数語の値は既存の `skipReason`（`no_publisher` など）に倣って snake_case |
| 状態の名前 | **`awaiting_approval`**（表示「承認待ち」） | 「待っている」状態であることを名前で言う。`pending` は「手動投稿待ち」（`035` §5.8）とも読めるので避けた |

**`status` を流用しない理由。** `status` は投稿の**いまの状態**で、`publishTiming` は登録の時の**指示**である。
`now` はどの時点でも状態として残らない（登録した瞬間に `scheduled` になる）ので、状態の値にできない。
`status` に「即投稿」を足すと、`GET` で読んだ値と `POST` で送れる値の集合がずれる。

**`scheduled` が状態の値と同じ綴りであること。** `publishTiming: "scheduled"` は `status: "scheduled"`（＋`scheduledAt`）と
**同じ結果**になるので、同じ綴りで困らない（むしろ対応が読める）。

#### 6.1.1 `deliveryMode` との組み合わせ

| | `deliveryMode: "auto"` | `deliveryMode: "manual"` |
| --- | --- | --- |
| `now` | 次の定期実行（既定 1 分以内）で Torifune が配信 | すぐ「手動投稿待ち」に並ぶ |
| `scheduled` | `scheduledAt` の後の最初の定期実行で配信 | `scheduledAt` を過ぎると「手動投稿待ち」に並ぶ |
| `after_approval` | 承認待ち → 承認で上のどちらか | 承認待ち → 承認で上のどちらか |

### 6.2 `POST /api/v1/social/posts`（`social.write`。現行どおり）

#### 6.2.1 要求項目（差分）

| 項目 | 型 | 必須 | 既定 | 制約（違反は 422。キーはその項目名） |
| --- | --- | --- | --- | --- |
| `publishTiming` | `'now' \| 'scheduled' \| 'after_approval'` | 任意 | なし（省略＝今の振る舞い） | 列挙 → `publishTiming` |
| `status` | enum | 任意 | **Zod の既定を外す**（省略時の `draft` は UseCase で補う） | **`publishTiming` と同時に送ると 422 `status`**（値が `draft` でも） |
| `scheduledAt` | string \| null | §6.2.2 | `null` | `publishTiming: "now"` と同時に**値を**送ると 422 `scheduledAt`（`null` は可） |

* `status` の列挙には `awaiting_approval` も入る（`postStatusSchema` を共有するため）。`publishTiming` を送らずに
  `status: "awaiting_approval"` を送った要求は `after_approval` と同じ結果になる。**推奨は `publishTiming`**（仕様書に書く）
* `status` から Zod の `.default('draft')` を外すのは、**送られなかったのか `draft` を送ったのかを区別する**ため
  （区別できないと、`publishTiming` との同時指定を断れない）。省略時の `draft` は UseCase が補うので、振る舞いは変わらない。
  OpenAPI の `status` から `default` が消え、`description` に「省略時は `draft`（`publishTiming` を送らないとき）」と書く
* **同時指定を 422 にする理由**：`publishTiming: "now"` と `status: "draft"` のような矛盾を、どちらかを黙って優先して
  通すと、送った側の誤りが見えない。`credential` と `credentials` の同時指定を 422 にしている先例（仕様書 §4.2）に揃える

#### 6.2.2 解決の表（`status` / `scheduledAt` の実効値）

| `publishTiming` | `status` | `scheduledAt` | 結果の `status` | 結果の `scheduledAt` |
| --- | --- | --- | --- | --- |
| 省略 | 省略 | 任意 | `draft` | 送った値（今の振る舞い） |
| 省略 | `scheduled` | **必須** | `scheduled` | 送った値（今の振る舞い） |
| 省略 | `awaiting_approval` | 任意 | `awaiting_approval` | 送った値（希望日時として保存） |
| 省略 | `draft` / `published` / `failed` | 任意 | そのまま（今の振る舞い） | 送った値 |
| `now` | 送らない | 送らない（`null` は可） | `scheduled` | **サーバのいまの時刻** |
| `scheduled` | 送らない | **必須**（`null` も不可） | `scheduled` | 送った値（**過去も可**。今の `scheduled` と同じ） |
| `after_approval` | 送らない | 任意 | `awaiting_approval` | 送った値（**希望日時**。承認のときに「指定の時間」の既定になる） |

* **`now` の `scheduledAt` はサーバが決める**（UseCase の `new Date()`）。応答の `scheduledAt` に実際の値が返り、
  外部アプリは「いつ配信へ回ったか」を読める。クライアントの時計がずれていても結果が変わらない
* **`now` に `scheduledAt` の値を送ると 422**（「publishTiming が now のときは scheduledAt を指定できません。」）。
  黙って捨てると「この時刻のつもりで送ったのに即時に出た」が起きる
* **`scheduled` で `scheduledAt` が無い／`null` は 422 `scheduledAt`**（既存の文言「予約するときは予約日時を指定してください。」）
* 裁定 5 の上書き（§6.7）は、この表を解決した**後**に掛かる。表の段階の 422 は provider によらず同じに返る
  （送った要求の形の誤りは、どの SNS に出すかに関係なく誤りとして返すほうが外部アプリが直しやすい）

### 6.3 `PATCH /api/v1/social/posts/{id}`（`social.write`。現行どおり）

#### 6.3.1 状態の遷移（§6.6 の表を `canTransition` に入れる）

* `draft` → `awaiting_approval`：**承認を依頼する**（画面・API）
* `scheduled` → `awaiting_approval`：**予約を承認待ちへ戻す**
* `awaiting_approval` → `draft`：**差し戻し・取りやめ**（画面の「差し戻す」、外部アプリの取りやめ）
* `awaiting_approval` → `awaiting_approval`：内容の修正（状態はそのまま）
* **`awaiting_approval` → `scheduled` は `PATCH` ではできない**（422 `status`「承認待ちの投稿は、承認の操作でだけ予約にできます。」）。
  予約にするのは承認（§6.4）だけ。`social.write` だけのトークンが自分の依頼を予約へ進められない（§8）
* **`awaiting_approval` → `published` / `failed` もできない**（422 `status`。既存の文言「awaiting_approval から published へは変更できません。」）。
  承認待ちは「まだ誰も出してよいと言っていない」状態で、そこから配信の結果を記録するのは筋が通らない。
  人が SNS へ別の手段で出してしまった場合は、差し戻して（`draft`）から記録する（`draft` → `published` は今までどおりできる）

#### 6.3.2 検査の掛け方（`PreflightOptions` の条件の差分）

| 区分 | 今 | 本設計 |
| --- | --- | --- |
| `checkSchedulable`（e：予約なら日時、f：手動投稿は媒体なし） | 変更後が `draft` / `scheduled` | 変更後が `draft` / **`awaiting_approval`** / `scheduled`（e は `scheduled` のときだけ意味を持つので、承認待ちでは f だけが効く） |
| `checkPublisherRules`（8a・8b） | 変更後が `scheduled` | 変更後が `scheduled` / **`awaiting_approval`** |
| `checkManualSupport`（g） | `deliveryMode: "manual"` を送ったとき | 変更なし |

* 承認待ちに `checkPublisherRules` を掛けるのは §6.2.4 と同じ理由（承認待ちの内容は、承認すれば予約になる）
* **出口を塞がない原則（`035` §6.2 の R-6）は保たれる**：`→ draft`（差し戻し・取りやめ）は変更後が `draft` なので、
  配信 Plugin の検査を通らない
* 承認待ちへ移すとき（`draft` / `scheduled` → `awaiting_approval`）は **`next_attempt_at` を NULL にする**
  （支度待ちの待ち時刻を持ったまま承認待ちに入ると、応答に意味の無い `nextAttemptAt` が出る。承認のときにも NULL にする。§6.4.5）。
  `skip_count` / `skip_reason` は触らない（`035` 裁定 #14-a と同じ）

#### 6.3.3 承認済みの予約を書き換えると承認待ちへ戻る（ユーザー裁定 10。2026-09-30）

**条件**（Domain の純関数 `revokesApproval(current, next)`）：

1. `current.status === 'scheduled'` かつ `current.approvedAt !== null`（承認を経た予約）
2. 変更後の状態が `scheduled`（明示でも省略でも）
3. 次のどれかが**値として変わる**：`body`・`media`（要素の順序込みで比べる）・`link`・`providerOptions`（キーの順序に依らず比べる）・
   `deliveryMode`・`scheduledAt`（ミリ秒で比べる）

**満たしたら**：保存する状態を `awaiting_approval` にし、`approved_at` を NULL にする。応答の `status` は `awaiting_approval`。

* **「送ったか」ではなく「値が変わったか」で見る。** 画面の編集フォームは変えていない項目も送る（`035` §6.2 の R-1 と同じ事情）。
  送っただけで承認が外れると、同じ内容で保存し直しただけで承認し直しになる
* **理由**：承認は「この内容を、この時刻に出してよい」という判断で、内容か時刻が変われば判断の対象が変わる。
  外さないと、外部アプリが承認の後に本文を書き換え、承認していない本文が承認済みとして SNS へ出る
* **配信中は今までどおり 422**（配信中のガードが先。`035` §6.2）
* `→ draft`（取りやめ）・`→ awaiting_approval`（明示）は `approved_at` を NULL にする。`→ published` / `→ failed`（記録）は
  `approved_at` を残す（「承認を経て出た投稿」の記録として）
* 承認を経ていない予約（`approved_at IS NULL`。既存の予約はすべてこれ）は、書き換えても今までどおり `scheduled` のまま

#### 6.3.4 監査

`social.post.update` の監査の `detail` に **`status: <更新後の状態>`** を足す（今は `changed` だけ）。
承認が外れた更新は `changed` に `body` などが、`status` に `awaiting_approval` が並ぶので追える。

#### 6.3.5 `publishTiming` を送ったら 422

`updatePostSchema` に `publishTiming` を足し、**どんな値でも 422 `publishTiming`**
（「publishTiming は登録のときだけ指定できます。承認を依頼するときは status に awaiting_approval を指定してください。」）。

**理由**：知らない項目は黙って無視される（仕様書 §1.3）。`POST` で覚えた `publishTiming` を `PATCH` にも送ると、
**承認を依頼したつもりで何も起きない**。新しい項目を `POST` だけに足す以上、`PATCH` で黙って捨てない。

#### 6.3.6 読んでから書くまでに承認が割り込んだら 409（検証で追加。2026-10-01）

`updateSocialPost` は投稿を読み、配信 Plugin の検査（`validate()`。最長 5 秒）を経てから書く。§6.3.3 の判定（承認を外すか・
`approved_at` を消すか）は**読んだ時点の行**で決まる。その間に承認がコミットされると、

* 承認待ちへの `{ body }` は、読んだ時点では「承認待ちの修正」なので状態を書かない。結果、承認済みの予約の本文が
  人の見ていないものに替わり、承認も外れない（§1 の 3 が破れる。`now` で承認していれば 1 分以内に SNS へ出る）
* 承認待ちへの `{ status: 'draft' }` / `{ status: 'awaiting_approval' }` は `approved_at` を消さずに状態を変え、
  `social_posts_approved_at_check` に落ちて 500 になる

**決めたこと**：Repository の `updatePost` に**読んだ時点の `status` と `approved_at` を条件として渡し**、1 文で判定して書く。

```sql
UPDATE social_posts SET ...
 WHERE id = $id
   AND status = $current.status
   AND approved_at IS NULL                                             -- 読んだ approvedAt が null のとき
   -- AND date_trunc('milliseconds', approved_at) = $current.approvedAt  -- 読んだ approvedAt があるとき
RETURNING *;
```

* 0 行なら読み直す。無ければ 404、あれば **409 `CONFLICT`**、`details.status` に
  「投稿の状態が変わっています。読み直してからやり直してください。」。**何も変えず、監査 `updated` も残さない**
* READ COMMITTED では、行ロックを待った UPDATE は WHERE を最新の行で評価し直すので、承認の後の行には当たらない
* **`updated_at` の一致では見ない。** `PATCH` には `expectedUpdatedAt` が無く、外部アプリの部分更新どうしは今までどおり
  後勝ちにする（競合を 409 にするのは、承認の判定を古い行で下した場合だけに絞る）
* `SELECT … FOR UPDATE` で読む案は採らない。`validate()` の最長 5 秒の間、行ロックを持ち続けることになる
* 配信ジョブが同じ間に `scheduled → published / failed` を確定させた場合も同じく 409 になる（今までは確定した投稿へ本文を
  上書きしていた。安全側に倒れる）
* `PATCH /social/posts/{id}` の OpenAPI に 409 を宣言する（`openapi-additional-responses.test.ts` の表も `[404, 409]`）

### 6.4 承認 `POST /api/v1/social/posts/{id}/approve`（`social.approve`。新規）

#### 6.4.1 要求

| 項目 | 型 | 必須 | 制約（違反は 422。キーはその項目名） |
| --- | --- | --- | --- |
| `publishTiming` | `'now' \| 'scheduled'` | **必須** | 列挙（`after_approval` も 422） |
| `scheduledAt` | string \| null | 任意 | §1.4 の形式と範囲。`scheduled` のときだけ使う（`now` のときは無視する） |
| `expectedUpdatedAt` | string | **必須** | 画面（または `GET`）で読んだ投稿の `updatedAt`。ISO 8601 |
| `csrfToken` | string | 任意 | 画面用 |

* **項目名を `POST /social/posts` と揃える**（`publishTiming` の `now` / `scheduled`）。登録と承認で同じ語彙を使う
* `now` のときに `scheduledAt` を送っても 422 にしない（画面は日時の欄の値を持ったまま即投稿を選べる。承認は人の操作で、
  欄の値を消させる手間に意味が無い）。応答の `scheduledAt` がいまの時刻になるので結果は読める

#### 6.4.2 応答

200 で投稿（§4.3 の形）。`status: "scheduled"`、`approvedAt` に承認の時刻、`scheduledAt` に実際に回る時刻。

| HTTP | `code` | いつ |
| ---: | --- | --- |
| 404 | `NOT_FOUND` | 投稿が無い（UUID の形でない ID も） |
| 409 | `CONFLICT` | `expectedUpdatedAt` と投稿の `updatedAt` が合わない（`details.expectedUpdatedAt`：「投稿の内容が変わっています。内容を確かめてから承認し直してください。」） |
| 422 | `VALIDATION_ERROR` | 承認待ちでない（`status`）、日時の誤り（`scheduledAt`）、要求の形、配信 Plugin の規則（§6.4.4 の 7） |

#### 6.4.3 見た内容を承認する（`expectedUpdatedAt`。決めたこと）

**承認するのは画面で見た内容**でなければならない。承認待ちの投稿は `social.write` で書き換えられる（§6.3.1）ので、
人が画面を開いてから「承認する」を押すまでの間に外部アプリが本文を書き換えると、**見ていない本文を承認する**ことになる。

* 画面は描画したときの `updatedAt` を持ち、承認の要求に `expectedUpdatedAt` として添える
* UseCase は**条件付きの更新 1 文**で「承認待ちで、`updated_at` が一致する行」だけを予約にする（§6.4.6）。合わなければ 409
* **必須にする**（API で承認する場合も）。任意にすると、付け忘れた承認が黙って最新の内容を承認する
* **時刻の精度**：`updated_at` は作成時は DB の `now()`（マイクロ秒）、更新時は Application の `new Date()`（ミリ秒）で入る。
  応答の `updatedAt` は `toISOString()`（ミリ秒。node-postgres は小数 6 桁を切り捨てて `Date` にする）なので、
  **比較は `date_trunc('milliseconds', updated_at) = $expected` で行う**（`035` §6.5.3 のカーソルと同じ事情。
  生の比較だと、作成直後の投稿が必ず 409 になる）

#### 6.4.4 UseCase `approveSocialPost` の手順（`social.post.approve`、Permission `social.approve`）

1. 要求の形（Zod）。`publishTiming` / `expectedUpdatedAt` の欠落・列挙外は 422
2. 投稿を引く。無ければ 404
3. **`status !== 'awaiting_approval'` なら 422 `status`**（「承認待ちの投稿ではありません（いまの状態：scheduled）。」）。
   409 より先に見る（他の人が承認し終えた投稿では、`updatedAt` も変わっているが、「もう承認されている」ほうが状況の説明になる）
4. **`updatedAt` のミリ秒が `expectedUpdatedAt` と違えば 409**（§6.4.3）
5. アカウントを引く（`ON DELETE CASCADE` なので通常は必ずある。無ければ 422 `socialAccountId`）
6. **`manualOnly = isManualOnlyProvider(account.provider)`**（§6.7）
7. **時刻を決める**（Domain の純関数 `resolveApprovalSchedule`。§6.4.5）
8. 事前検査：変更後（`status: 'scheduled'`、決めた `scheduledAt`）に `assertPostIsDeliverable` を
   `{ checkSchedulable: true, checkPublisherRules: true, checkManualSupport: post.deliveryMode === 'manual' }` で掛ける。
   **承認は出口ではない**ので配信 Plugin の検査を掛ける（予約になる更新と同じ。`035` §6.2）。publisher が無い provider は
   今までどおり通す（予約は支度待ちで待つ。`035` 裁定 #8）
9. 条件付き更新（§6.4.6）。0 行なら 2〜4 をやり直して 404 / 422 / 409 のどれかを返す（競合した承認）
10. イベント `social.post.approved`（§6.8）。監査 `approved`（§6.9。`defineUseCase` の `audit`）

#### 6.4.5 時刻の決め方 `resolveApprovalSchedule`（裁定 4）

```ts
export function resolveApprovalSchedule(input: {
  readonly requested: ApprovalTiming;
  readonly scheduledAtInput: Date | null | undefined; // 要求の scheduledAt
  readonly registered: Date | null;                   // 登録された希望日時
  readonly manualOnly: boolean;
  readonly now: Date;
}):
  | { readonly ok: true; readonly timing: ApprovalTiming; readonly scheduledAt: Date; readonly approvalForced: boolean }
  | { readonly ok: false; readonly field: 'scheduledAt'; readonly message: string };
```

| 条件 | 結果 |
| --- | --- |
| `manualOnly` | **`timing: 'now'`、`scheduledAt: now`**（要求が `scheduled` でも。`approvalForced: requested === 'scheduled'`）。裁定 5 |
| `requested: 'now'` | `scheduledAt: now` |
| `requested: 'scheduled'`、`scheduledAtInput` あり | その値。範囲外は 422（既存の範囲の文言） |
| 同、`scheduledAtInput` 無し（`undefined` / `null`） | `registered`。**`registered` も `null` なら 422**（「承認して予約するときは日時を指定してください。」） |
| 決めた日時が **`now` 以前**（等しいときも含む） | **422 `scheduledAt`**（「指定の日時を過ぎています。即投稿を選ぶか、未来の日時を指定してください。」） |

**過去の日時を「即投稿」に読み替えない理由（裁定 4 で任された判断）。**

* 承認する人は「指定の時間に投稿」を**明示して選んでいる**。黙って即時に出すと、選んだものと違う結果になる
* 時刻に意味のある投稿（「明日 9 時から」「解禁は正午」）は、予定より早く出ても遅く出ても困る。遅れて出してよいかは人が決める
* 選び直しの手間は小さい（画面は過去なら「即投稿」を既定にし、注意を出す。§7.1.3）
* 登録（`POST`）の `scheduled` は過去を許す（今の振る舞い。仕様書 §4.4）が、あれは外部アプリの機械的な登録で、
  「過去＝いますぐ」の約束が文書化されている。承認は人が画面で選ぶ操作で、前提が違う。**登録の振る舞いは変えない**

**承認のときに `next_attempt_at` を NULL にする。** 人が時刻を選んだので、前に付いた支度待ちの待ち時刻を引きずらない
（`clearsSkipWait` は「未来の予約」でしか消さないが、承認では即投稿でも消す）。`skip_count` / `skip_reason` / `attempt_count` は触らない
（`035` 裁定 #14-a・§6.5.6）。

#### 6.4.6 条件付き更新（Repository `approvePost`）

```sql
UPDATE social_posts
   SET status = 'scheduled', scheduled_at = $scheduledAt, approved_at = $now,
       next_attempt_at = NULL, updated_at = $now
 WHERE id = $id
   AND status = 'awaiting_approval'
   AND date_trunc('milliseconds', updated_at) = $expectedUpdatedAt
RETURNING *;
```

* 1 文で判定と更新を行うので、**同時に 2 人が承認しても 1 人だけが通る**（もう 1 人は 0 行 → 手順 9 で 422 `status`）
* `id` が UUID の形でなければ 0 行（Repository の既存の流儀。`findPostById` が先に `null` を返すので 404 になる）

### 6.5 一覧

* `GET /api/v1/social/posts?status=awaiting_approval` で承認待ちだけを引ける（`postStatusSchema` の列挙が増えるだけ）
* 画面用の UseCase **`listApprovalPendingPosts({ limit })`**（`social.post.listApprovalPending`、Permission `social.read`）：
  `WHERE status = 'awaiting_approval' ORDER BY created_at ASC, id ASC LIMIT ?` と全件数（`SocialPostPage` の `{ items, total }`）。
  **古い依頼から**並べる（依頼を受けた順に捌く）。画面は 50、ダッシュボードは 1 を渡す（`listManualPendingPosts` と同じ形）

### 6.6 状態遷移

#### 6.6.1 図

```text
            ┌──────── 差し戻し・取りやめ（PATCH draft）────────┐
            ▼                                                │
draft ──承認を依頼（PATCH）──▶ awaiting_approval ──承認（approve）──▶ scheduled ──▶ published
  │  ▲                              ▲                         │  │
  │  └──────────── 取りやめ（PATCH draft）───────────────────────┘  │
  │                                 └── 承認待ちへ戻す（PATCH / 承認済みの書き換え）
  └────────────── 予約（PATCH scheduled。承認を経ない）──────────▶ scheduled
  draft / scheduled ──────────────────────────────────────────────▶ failed
```

#### 6.6.2 表（`canTransition`＝`PATCH` の規則。承認は別の操作）

| 現在 ＼ 変更後 | `draft` | `awaiting_approval` | `scheduled` | `published` | `failed` |
| --- | --- | --- | --- | --- | --- |
| `draft` | ○ | **○（新）** | ○ | ○ | ○ |
| `awaiting_approval` | **○（新）** | **○（新）** | **×（承認の操作だけ）** | **×** | **×** |
| `scheduled` | ○ | **○（新）** | ○ | ○ | ○ |
| `published` | × | **×** | × | ○ | × |
| `failed` | × | **×** | × | × | ○ |

`awaiting_approval → scheduled` は `canTransition` では偽で、`approveSocialPost` だけが行う（Domain に
`canApprove(status) = status === 'awaiting_approval'` を置く）。

#### 6.6.3 承認は強制ではない

`social.write` を持つ者は、承認待ちを差し戻し（`draft`）てから予約（`scheduled`）にできる。**承認を経ない予約は `approvedAt: null`**
で、承認済みとは区別される。これは裁定 1（承認を待つかは要求ごとに外部アプリが選ぶ）の帰結で、承認は外部アプリが自ら求める
「確認の依頼」である。承認済みの記録（`approvedAt`）が**人の承認を経たときにだけ付く**ことを本設計は保証する（§8）。

### 6.7 裁定 5：X の無料版は常に「承認待ち」かつ「即投稿」

#### 6.7.1 判定の方法（ユーザー裁定 7。2026-09-30 に (b) で確定）

| 案 | 判定 | 評価 |
| --- | --- | --- |
| (a) | `deliveryMode: "manual"` の投稿すべて | Bluesky・Threads・X 有料版の手動投稿まで常に承認待ちになる。裁定 5 が名指ししたのは X の無料版だけで、**範囲が広すぎる** |
| **(b)（採用）** | **その provider に登録された配信 Plugin が `manual()` を持ち `publish()` を持たない**（＝手動投稿しかできない） | Plugin API を変えない（`publish?` と `manual?` は既に任意）。同梱の Plugin では **`sns-x-manual` だけが当てはまる**（`sns-x-api`・`sns-bluesky`・`sns-threads` は両方、`sns-instagram` は `publish` だけ）。Core が provider 名 `x` を知らずに済む |
| (c) | Plugin API に任意の宣言（例：`requiresApproval: true`）を足す | 意図は明示できるが、公開 Plugin API の追加になり、`sns-x-manual` の変更も要る。「手動投稿しかできない」という事実から導けることを、別の宣言で二重に持つことになる |

**(b) を採る理由**：裁定 5 の「X の無料版」の本質は「**API で配信できず、人が投稿画面から出すしかない**」ことで、
それは登録の形（`publish()` が無い）にそのまま表れている。**手動投稿しかできない SNS では、人が画面の前にいることが配信の前提**
なので、「人が確かめて、確かめたらすぐ出す」は X に限らず筋が通る。第三者が手動投稿だけの配信 Plugin を作れば、同じ扱いになる
（利用者への影響：その Plugin の provider でも `publishTiming` を送った登録は承認待ちになる。§13 の R6。この帰結を含めて 2026-09-30 に裁定された）。

#### 6.7.2 判定の関数

* Domain：`isManualOnlyPublisher(publisher: { readonly publish: boolean; readonly manual: boolean } | null): boolean`
  ＝ `publisher !== null && publisher.manual && !publisher.publish`
* Application：`isManualOnlyProvider(provider)` ＝ `findPublisher(provider)` の `registration.publish !== undefined` /
  `registration.manual !== undefined` を渡す。**判定はそのときの登録簿で行う**（登録と承認のそれぞれの時点）
* 配信 Plugin が 1 つも無い provider は偽（知らないものを手動投稿だけとは決めない。今までどおり予約を受け付け、支度待ちで待つ）

#### 6.7.3 どこで効くか・何を返すか（決めたこと）

| 場面 | 振る舞い |
| --- | --- |
| **登録**（`publishTiming` を送った `POST`） | `now` / `scheduled` / `after_approval` のどれでも **`status: "awaiting_approval"`、201**。`scheduledAt` は `now` なら `null`、それ以外は送った値（希望日時として残す。承認では使わない） |
| **承認**（`approve`） | `publishTiming` が `scheduled` でも **即投稿**（`scheduledAt` はいまの時刻）。200。承認すると、すぐ「手動投稿待ち」に並ぶ |
| 画面の承認のダイアログ | 「即投稿」だけを出し、「この SNS は手動投稿のみのため、承認するとすぐ『手動投稿待ち』に並びます。」を添える（§7.1.3） |

* **422 にしない理由**：裁定 5 は「値によらず常に」なので、外部アプリの指定は誤りではなく、Torifune の側の規則で読み替えるもの。
  断ると、外部アプリは X の無料版かどうかを先に知っていなければならない（それを問い合わせる API は無い。仕様書 §5.1）
* **読み替えたことは応答で分かる**：送った `publishTiming` が `now` / `scheduled` なのに `status` が `awaiting_approval` で返る。
  仕様書に「X の無料版では常に承認待ちで返る」と書く（§12）。応答に専用の項目は足さない（`status` で足りる）
* 登録の監査の `detail` に `approvalForced: true` を残す（§6.9）
* `deliveryMode` は変えない。X の無料版は今までどおり `deliveryMode: "manual"` を送る必要がある（`auto` は `sns-x-manual` の
  `validate()` が 422 `deliveryMode`。`037` §9.3）
* **配信 Plugin の入れ替え**（`037` §7.2）で判定が変わりうる。無料版の間に承認待ちになった投稿は、有料版へ入れ替えた後の承認では
  「指定の時間」も選べる。逆に有料版の間の承認待ちは、無料版へ入れ替えた後の承認では即投稿になる。どちらも承認の時点の登録簿で決まる

#### 6.7.4 掛ける範囲（ユーザー裁定 8。2026-09-30 に (i) で確定）

| 案 | 範囲 | 評価 |
| --- | --- | --- |
| **(i)（採用）** | **`publishTiming` を送った `POST` と、承認** | 裁定 1（省略したら今の振る舞い）と両立する。`status: "scheduled"` で X の無料版へ手動投稿を予約している既存の外部アプリと、管理画面から予約する人の操作は変わらない |
| (ii) | (i) ＋ `publishTiming` を送らない `POST` の `status: "scheduled"` | 裁定 1 に反する（既存の外部アプリの X の無料版の予約が、承認しないと手動投稿待ちに並ばなくなる） |
| (iii) | (ii) ＋ `PATCH` の `→ scheduled` | 管理画面で X の無料版の投稿を予約するたびに、自分で承認する手間が挟まる |

裁定 5 の「パラメタによらず」は、**新しい項目 `publishTiming` のどの値でも**、と読むのが裁定 1 と両立する読み方である。

### 6.8 イベント `social.post.approved`（決めたこと）

| 項目 | 内容 |
| --- | --- |
| いつ | `approveSocialPost` が成功したとき（1 回の承認で 1 回） |
| Payload | 既存の **`SocialPostEventPayload`**：`{ postId, accountId, status: 'scheduled' }`。**時機・日時・承認者は載せない**（必要なら `GET` で `scheduledAt` / `approvedAt` を読む。既存のイベントと同じ方針） |
| Webhook | `CORE_EVENTS` に入るので、`POST /api/v1/webhooks` の `events` に指定できる（`webhook-use-cases.ts` は `CORE_EVENTS` を見ている） |
| Plugin | `context.events.subscribe('social.post.approved', …)` で型が付く（`CoreEventPayloads` に足す） |

* **理由**：承認を依頼した外部アプリが、承認されたこと（とその後の配信の予定）をポーリングせずに知れる。
  配信の結果は既存の `social.post.published` / `failed` で届く
* `social.post.created` は承認待ちの登録でも発火し、`status: 'awaiting_approval'` が載る（Payload の型は変わらない。TSDoc と文書を直す）
* **差し戻し（`→ draft`）のイベントは足さない**。既存の取りやめ（`scheduled → draft`）にもイベントは無く、同じ遷移である
  （§11.2 の 1）。承認が外れたとき（§6.3.3）もイベントは足さない（更新のイベントが元々無い）

### 6.9 監査

| 操作 | `action` | `detail` |
| --- | --- | --- |
| 承認 | **`approved`**（新。`AUDIT_ACTIONS` に足す。DB の CHECK は無い） | `{ requestedTiming, effectiveTiming, scheduledAt（ISO）, deliveryMode, approvalForced, via: 'session' \| 'api_token' }` |
| 登録 | `created`（既存） | 既存の `{ socialAccountId, status, replayed }` に **`publishTiming`（送った値か `null`）と `approvalForced`** を足す |
| 更新 | `updated`（既存） | 既存の `{ changed }` に **`status`（更新後）** を足す（§6.3.4） |

  （`sanitizeAuditDetail` がトークンらしいキーを落とすので、トークン ID ではなく経路の種類だけを残す）
* 本文は残さない（既存の方針）

### 6.10 配信ジョブ・手動投稿・再試行への影響

**変えない。** 次のどれも `status = 'scheduled'` を条件にしているので、承認待ちの行は一切拾われない。

| 処理 | 条件（`035` §6.5.3・§6.6） |
| --- | --- |
| 期限の来た予約の取り出し（`listDue`） | `status = 'scheduled' AND delivery_mode = 'auto' AND …` |
| 中断した配信の判定 | `status = 'scheduled' AND publish_started_at IS NOT NULL` |
| 支度待ちへ送る（`deferSkipped`）・着手（`claimForPublish`）・結果の記録 | `status = 'scheduled'` |
| 手動投稿待ち（`listManualPending`・`isManualPending`） | `status = 'scheduled' AND delivery_mode = 'manual' AND scheduled_at <= now()` |

Domain の `isDue` / `isInterrupted` / `isManualPending` も `status === 'scheduled'` を見ているので、承認待ちでは偽になる。
**受け入れ条件で固定する**（§10.6）。承認して予約になった投稿は、既存の予約と同じ経路（再試行・支度待ち・3 回上限）を通る。

### 6.11 応答とOpenAPI

* 投稿の形（仕様書 §4.3）に **`approvedAt: string | null`** を足す（`postResponseSchema` / `toPostResponse`）。
  **`SocialPostView`（Plugin）には足さない**（`035` §6.1.4 の `skipCount` と同じ判断。Plugin に要る場面が無い）
* `status` の列挙に `awaiting_approval`（`postStatusSchema`。応答・一覧の絞り込み・`PATCH`）
* `createSocialPost`：`publishTiming`（`enum`、`description`「即投稿（now）・指定の時間に投稿（scheduled）・承認を待ってから投稿（after_approval）。省略すると status と scheduledAt で決まる（従来どおり）。」）。
  `status` の `default` が消える
* `updateSocialPost`：`publishTiming`（`description`「指定すると 422。登録のときだけ使う。」）
* **`approveSocialPost`**（新）：`POST /social/posts/{id}/approve`、`x-required-permission: social.approve`、
  応答 200・401・403・**404**・**409**・422・429・500（`additionalResponses` で 404 と 409 を宣言する。`042` §6.4 の仕組み）

### 6.12 互換性（外部アプリへの影響）

API のバージョンは **`v1` のまま**。

| 変更 | 既存の外部アプリへの影響 |
| --- | --- |
| `POST` に任意の `publishTiming` | なし（送らなければ今の振る舞い。裁定 1） |
| `POST` の `status` の既定を Zod から UseCase へ移す | なし（省略時は今までどおり `draft`）。OpenAPI の `status` から `default` が消える（生成クライアントの既定値が消えることがある。送る値は変わらない） |
| 状態の値 `awaiting_approval` が増える | **自分が承認待ちを使わなければ、自分の投稿には現れない。** ただし **`GET /social/posts`（一覧）には他のアプリや人が作った承認待ちが含まれうる**（仕様書 §2.3）。状態を網羅的に分岐しているクライアント（OpenAPI から列挙型を生成したものなど）は、**知らない値を受け取る**。仕様書に「状態の値は増えうる。知らない値は無視するか『その他』として扱う」と書く |
| `PATCH` の新しい 422（`awaiting_approval → scheduled` / `published` / `failed`、`publishTiming`） | 承認待ちを使わないアプリには起きない（`publishTiming` を `PATCH` に送っていたアプリは、今まで黙って無視されていた要求が 422 になる。正当な使い方ではない） |
| 承認済みの予約の書き換えで承認待ちへ戻る | 承認を経た予約（`approvedAt` あり）だけ。既存の予約はすべて `approvedAt: null` で、振る舞いは変わらない |
| 応答に `approvedAt` | 追加だけ |
| 新しい操作 `approve`・新しい Permission `social.approve` | 追加だけ。既存のトークンの Scope に `social.approve` は無い（Scope は明示の一覧）ので、既存のトークンは承認できない |
| 新しいイベント `social.post.approved` | 購読しなければ何も起きない |
| `social.post.created` の `status` に `awaiting_approval` | 承認待ちを使ったときだけ |

## 8. 権限（Permission）

### 8.1 対応表

| 操作 | Permission | 権限なし | 未認証 |
| --- | --- | --- | --- |
| `POST /social/posts`（`publishTiming` を含む） | `social.write`（現行どおり） | 403 `FORBIDDEN` | トークンの形は合うが無効 → 401。`Authorization` が無い → 403 `CSRF_FAILED`（仕様書 §2.1） |
| `PATCH /social/posts/{id}`（承認の依頼・差し戻し・内容の修正） | `social.write`（現行どおり） | 403 | 同上 |
| **`POST /social/posts/{id}/approve`** | **`social.approve`（新）** | 403 | 同上 |
| `GET /social/posts`（`status=awaiting_approval`） | `social.read`（現行どおり） | 403 | 401 |
| `listApprovalPendingPosts`（区画・ダッシュボード） | `social.read` | 403（UseCase） | —（画面はログインへ） |
| 画面の「承認する」 | 表示は `social.approve` | ボタンを出さない | — |
| 画面の「差し戻す」「編集」 | 表示は `social.write` | ボタンを出さない | — |

### 8.2 新しい Permission `social.approve` を作る理由（ユーザー裁定 9。2026-09-30 に (A) で確定）

| 案 | 内容 | 評価 |
| --- | --- | --- |
| **(A)（採用）** | **`social.approve` を新設し、既定で administrator と editor に割り当てる** | 外部アプリのトークンは `social.read` + `social.write` に絞る運用（仕様書 §2.2）なので、**そのトークンでは自分の依頼を承認できない**。人（管理者・編集者）は画面で承認できる |
| (B) | `social.approve` を新設し、administrator だけ | 編集者は承認待ちを捌けない。編集者は `social.write` で承認を経ない予約を直接作れるので、承認を取り上げても安全は増えず、承認の流れだけが使えなくなる |
| (C) | 承認も `social.write` | Permission を増やさずに済むが、**外部アプリのトークンが自分の依頼を API で承認できる**。`approvedAt` が「人が確かめた」ことを意味しなくなる |

**(A) の理由の補足。**

* **Torifune の認可の単位は Permission で、トークンはその上限を絞る道具**（`035` 裁定 #10、`04` §28、`05` §37）。
  「トークン経由の承認だけを断る」（認証の経路で分岐する）形にはしない。経路で分けると、承認用に作った運用者のトークン
  （例：社内の承認ツール）が使えなくなり、認可の規則が Permission の表から読めなくなる
* 承認に使うトークンを作ることはできる（所有者が `social.approve` を持ち、Scope に含めたとき）。
  **外部アプリに渡すトークンの Scope に `social.approve` を含めない**ことを、仕様書と手順書に書き、
  Permission の説明（トークンの Scope を選ぶ画面に出る）にも書く：
  `'social.approve': '承認待ちのSNS投稿を承認して配信に回す（投稿を登録する外部アプリのトークンには付けない）'`
* ロールは今は固定の 3 つ（管理者・編集者・閲覧者）で画面から組み替えられないが、Permission を分けておけば、
  将来ロールを編集できるようになったときに「書けるが承認できない」役割を作れる
* `HIGH_PRIVILEGE_PERMISSIONS` には入れない（Torifune 全体を掌握する権限ではない）

### 8.3 ID の差し替え

投稿は利用者ごとの所有物ではない（`035` §8.1）。ID を差し替えて他人の投稿を承認できる、は `social.approve` を持つ者の正当な操作である。
検証するのは「存在しない ID・UUID の形でない ID は 404」「承認待ちでない投稿は 422」（§10.5）。

### 9.2 動作の変更（`010` §9 の追記の形で記録する）

1. **`socialPosts.list` / `get` が `status: 'awaiting_approval'` の投稿を返す。** 状態を網羅的に分岐している Plugin
   （例：「`draft` / `published` / `failed` でなければ予約」とみなすもの）は誤る。同梱の Plugin は状態で分岐していない
   （`plugins/*` に投稿の `status` を読む箇所が無い）
2. **`markPublished` / `markFailed` を承認待ちの投稿に呼ぶと reject** される（`updateSocialPost` の遷移の規則。§6.3.1）。
   承認待ちは本設計で初めて現れる状態なので、**今まで成功していた呼び出しが失敗に変わることは無い**
3. `publish()` / `manual()` / `validate()` に渡るものは変わらない（`publish()` は予約になった投稿だけを受け取り、`manual()` は手動投稿待ちの行だけ、
   `validate()` は `status` を受け取らない）

### 9.3 `PLUGIN_API_VERSION` は `1` のまま

* 既存の型・関数・Payload を 1 つも変えていない。`CoreEventName` にイベント名が増えるのは共用体の拡張で、`032` の `analytics.purged` と同じ
* `SocialPostView.status` は `string` で、値の集合が増えても型は変わらない
* §9.2 の 2 は「新しい状態に対する呼び出し」で、既存の正しい呼び出しは何も変わらない。`043` の判断（版を上げても何も伝わらず、
  無関係な Plugin の `context.apiVersion` の分岐と型だけを壊す）がそのまま当てはまる
* 伝達手段は TSDoc（`SocialPostView.status`・`SocialPostEventPayload.status`・`CORE_EVENTS`）と `docs/Plugin開発ガイド.md`・`docs/Eventリファレンス.md`（§12）

### 9.4 同梱の Plugin

変更なし。`sns-x-manual` は `publish` を持たない形のまま、裁定 5 の判定に当てはまる（§6.7.1）。
`plugins/example-plugin` は `publish` と `manual` の両方を持つので当てはまらない（受け入れ条件の D では、手動投稿だけの偽の publisher を

## 10. 受け入れ条件

| ③ | 承認に要る Permission | **(A) `social.approve` を新設し、既定で管理者と編集者に**。退けた案：(B) 管理者だけ／(C) `social.write` | §8.2 |
| ④ | 承認済みの予約を書き換えたら承認を外すか | **外す（承認待ちへ戻す）** | §6.3.3 |
| ⑤ | ダッシュボードの「承認待ちが n 件」の案内 | **含める** | §7.5 |

### 11.2 設計で決めず、後の判断に回すもの

1. **差し戻しの理由と、差し戻しのイベント**：外部アプリは差し戻されたことを `status: "draft"` のポーリングでしか知れず、理由も分からない。
   足すなら `social.post.rejected`（`awaiting_approval → draft` で発火）と理由の列になる（どちらも追加で足せる）
2. **承認待ちの期限**：放置された依頼は残り続ける。ダッシュボードの案内（§7.5）で気づける前提にした
3. **トークン単位の「承認必須」**：運用者が「このトークンの投稿は必ず承認を経る」と決める設定。本設計の承認は外部アプリが選ぶ依頼で、強制ではない（§6.6.3）
4. **承認者の表示**：画面は承認の時刻（「承認済み」）だけを出し、誰が承認したかは監査ログで見る（§5.2）

| # | リスク | 対処 |
| --- | --- | --- |
| R1 | 状態を網羅的に分岐している外部アプリ・Plugin が、一覧で `awaiting_approval` を受け取って誤る | 仕様書・開発ガイドに「状態の値は増えうる」と書く（§12）。自分で承認待ちを使わないアプリは、自分の投稿では出会わない |
