# 026 画面の欠落を埋める（キャンペーン分析 / SNS履歴 / Webサイト設定 / Action の対象リソース）

## 1. 背景

`docs/仕様書/06_画面設計.md` と実装を突き合わせた再監査で、次の4点が「部分的」と確定した。

| # | 仕様 | 実態 |
| --- | --- | --- |
| 課題1 | §14 キャンペーン画面に「分析」。「キャンペーンとWebサイト、SNS投稿等を関連付けられる構造」 | 一覧・新規・編集のみ。`Campaign` は `siteIds` しか持たず、SNS投稿と繋がらない |
| 課題2 | §13 SNS画面に「履歴」 | アカウント・投稿・予約日時のみ。配信結果を見る画面が無い |
| 課題3 | §11 Webサイト画面に「設定」 | 「編集」しか無い |
| 課題4 | §26「Actionは、対象リソースとPermissionを定義する」 | `ActionRegistration` に対象リソースの定義が無く、描画先も2箇所 |

この設計は4点をまとめて埋める。**新しい集計テーブルは作らない**、
**Plugin API の後方互換を壊さない**、の2つを守る。

---

## 2. 課題3 の判断：「設定」画面は作らず、仕様書 §11 を実態に合わせる

先に判断を要する課題3から片付ける。

### 2.1 「編集」画面が持っているもの

`apps/web/src/ui/site/site-form.tsx` が扱うのは4項目だけ。

| 項目 | 性質 |
| --- | --- |
| 名前 | サイトそのものの属性 |
| URL | 同上 |
| 説明 | 同上 |
| 状態（active / paused / archived） | 同上 |

`sites` テーブルにはこの他に `public_key`（計測タグの公開キー）があるが、
これは**利用者が設定する値ではない**。DB 側の既定値で自動採番され、更新もされない。
表示は既にアナリティクス画面（§15）が「計測タグ」として受け持っている
（`apps/web/src/ui/analytics/analytics-view.tsx`）。

### 2.2 判断：分ける実質が無い

「設定」として編集から切り出せるものが1つも無い。
4項目しかない画面を2枚に割ると、利用者は毎回「どちらに入っているか」を探すことになる。

サイトごとの追加設定は、そもそも Core の責務ではない。

* サイト単位の Plugin 設定 → Extension Point `site.edit.sidebar`（§21, §26）
* Plugin 自身の設定 → `registerSettings` と `/plugins/<id>/settings`（§27）

つまり「Webサイトの設定」を名乗る画面を Core に置くと、
**Plugin が持つべき設定を Core へ引き寄せる置き場**になってしまう。

### 2.3 決定

**画面は増やさない。`docs/仕様書/06_画面設計.md` §11 を実態に合わせて改訂する。**
サブ画面を `一覧 / 新規作成 / 編集` とし、「設定」を編集へ統合した理由と、
サイト単位の追加設定が Extension Point 側であることを本文に書く。
改訂は `docs/仕様書/改訂履歴.md` へ記録する。

## 3. 課題1：キャンペーンとSNS投稿の関連付け／分析画面

### 3.1 関連付けのデータ構造

**`campaign_sites` と同じ流儀にそろえる。** 同じ形のものを違う形で作らない。

```sql
CREATE TABLE campaign_social_posts (
    campaign_id    uuid NOT NULL REFERENCES campaigns (id)     ON DELETE CASCADE,
    social_post_id uuid NOT NULL REFERENCES social_posts (id)  ON DELETE CASCADE,
    PRIMARY KEY (campaign_id, social_post_id)
);
CREATE INDEX campaign_social_posts_post_idx ON campaign_social_posts (social_post_id);
```

* 多対多。1キャンペーンが複数投稿を持ち、1投稿が複数キャンペーンに属しうる
* 投稿を消したら関連も消える。**キャンペーン自体は残す**（`campaign_sites` と同じ判断）
* 逆引き（この投稿はどのキャンペーンのものか）のために `social_post_id` に索引を張る

Domain / Repository / UseCase では `siteIds` と完全に対称に扱う。

* `Campaign.socialPostIds: readonly string[]`
* `NewCampaign.socialPostIds` / `CampaignUpdate.socialPostIds`（**指定したら丸ごと置き換える**）
* Repository は `socialPostIdsOf()` でまとめ読みし、`replaceSocialPosts()` で置換する

**新しい Permission は作らない。** 関連付けはキャンペーンの属性であり、
`campaign.write` を持つ相手が編集できて困る場面が無い。
ただし**選択肢としてSNS投稿の一覧を出すのは `social.read` を要求する**
（新規作成画面がサイト一覧に `site.read` を要求しているのと同じ扱い）。

### 3.2 分析画面

* 経路：`/campaigns/<id>/analytics`
* 権限：`campaign.read`（無ければ `forbidden`）
* **新しい集計テーブルを作らない。** 既存の UseCase を組み合わせるだけ

出すもの。

| 区画 | 出所 |
| --- | --- |
| キャンペーンの概要（名前・状態・期間） | `getCampaign` |
| 対象サイトごとの期間内アクセス（ページビュー・訪問者） | `listAnalytics` をサイトごとに呼ぶ |
| 合計 | 上をアプリ側で足す |
| 紐づくSNS投稿の件数と状態の内訳 | `listSocialPostsByIds`（3.3） |

集計期間は**キャンペーンの期間**とする。分析対象が期間で定義される取り組みである以上、
既定を「直近30日」にすると、終わったキャンペーンを開いたとき 0 が並ぶ。

* `from = startsOn`
* `to = min(endsOn ?? 今日, 今日)` — 未来の日付を問い合わせても値は無い
* `listAnalytics` は `MAX_RANGE_DAYS`（400日）を超えると 422 を投げる。
  **画面側で `from` を `to` の 399日前まで切り上げる。** 長く続くキャンペーンで
  分析画面がエラーになるのは、利用者から見て理由が分からない
* 画面には実際に集計した期間を表示する（切り詰めたことが分かるように）

権限が足りない場合の振る舞い。**画面全体を落とさない。**

* `analytics.read` が無い → アクセス集計の区画に「権限が無い」旨を出す
* `social.read` が無い → 投稿の区画に同上

### 3.3 SNS投稿をIDでまとめて引く

分析画面は「このキャンペーンに紐づく投稿」の状態が要る。IDは判っている。
1件ずつ `getSocialPost` を呼ぶと件数分の往復になるため、まとめ読みを1つ足す。

* `SocialRepository.findPostsByIds(connection, ids): Promise<readonly SocialPost[]>`
* `listSocialPostsByIds`（UseCase、`social.read`）

## 4. 課題2：SNS の履歴画面

### 4.1 いま記録されているもの

`social_posts` は `status` / `published_at` / `failure_reason` を持ち、
状態遷移は `updateSocialPost` が一元管理している（`published` / `failed` は終端）。
Plugin からは `data.socialPosts.markPublished(id)` / `markFailed(id, reason)` が入口。

### 4.2 足りない記録（2つ）

1. **`markFailed(id, reason)` の `reason` が捨てられている。**
   `apps/web/src/plugin/data-api.ts` は `updateSocialPost(context, { id, status: 'failed' })`
   としか呼んでおらず、`UpdatePostInput` に `failureReason` が無い。
   公開 API が受け取ると宣言している値が、どこにも保存されていない。
   **これが「失敗した理由が見えない」の根本原因**であり、まずここを直す。
2. **失敗した時刻が無い。** `published_at` はあるが、失敗側に対応する列が無い。
   `updated_at` は「最後に触った時刻」であって「失敗した時刻」ではない。

よって次を足す。

* `UpdatePostInput.failureReason` を通し、`markFailed` が理由を渡す
* `social_posts.failed_at timestamptz` を追加し、`failed` へ移すときに記録する
* 既存行への遡及更新はしない。**無かった記録を後から作らない。**
  読み出し側が `COALESCE(published_at, failed_at, updated_at)` で落とす

### 4.3 履歴として作らないもの

**配信の試行履歴テーブルは作らない。**
`published` と `failed` は終端状態で、1つの投稿が持つ配信結果は高々1つ。
1対多の履歴表を作っても、常に0行か1行しか入らない。

「履歴」とは**配信結果が確定した投稿の一覧**である、と定義する。

### 4.4 画面

* 経路：`/social/history`
* 権限：`social.read`
* 対象：`status IN ('published', 'failed')`
* 並び：結果が確定した時刻の新しい順（`COALESCE(published_at, failed_at, updated_at) DESC`）
* 列：アカウント / 本文の抜粋 / 結果 / 日時 / **失敗理由**
* 絞り込み：結果（すべて / 配信済み / 失敗）。失敗だけを見る用途が実際にある
* SNS画面（`/social`）から「履歴」へのリンクを置く

### 4.5 Repository への影響

`SocialPostListQuery.status: PostStatus | null` を
`statuses: readonly PostStatus[]` へ変える。**新旧2つの絞り込み方を残さない。**
`CampaignListQuery.statuses` と同じ形になり、UseCase 側で
「単一指定 → 配列」に畳む形も `listCampaigns` と同じになる。

並び順は `orderBy: 'created' | 'delivered'` を足す。
`delivered` は上記 `COALESCE` 式の降順。

`ListPostsInput`（UseCase の入力）は `status: PostStatus | null` のまま変えない。
既存の呼び出し（API・Data API・画面）に影響を出さない。

## 5. 課題4：Action の対象リソース

### 5.1 型

`ActionRegistration` へ**任意項目**として足す。

```ts
export interface ActionRegistration {
  readonly location: string;
  readonly label: string;
  readonly component: PluginComponent;
  readonly permission?: string;
  /** 対象リソース（06_画面設計.md §26）。'site' / 'campaign' / 'social_post' など。 */
  readonly resource?: string;
}
```

**必須にしない。** 必須にすると既存の登録がすべて型エラーになる。
Plugin API の後方互換は最優先（`CLAUDE.md`）。

`resource` の値は列挙で縛らない。Plugin は自分の画面と自分のリソースを持てるため
（`CORE_EXTENSION_POINTS` が閉じた集合でないのと同じ理由）。
Core が扱うリソース名は `CORE_ACTION_RESOURCES` として**参考値**を公開する。

### 5.2 絞り込み

`collectActions(location, permissions, resource?)` に任意の第3引数を足す。

* 省略 → 従来どおり `location` と Permission だけで絞る（既存の呼び出しは無変更）
* 指定 → その `resource` を対象にした登録と、`resource` を宣言していない登録を返す。
  **宣言していない登録を落とさない。** 落とすと、`resource` を書いていない
  既存の Plugin が画面から消える

### 5.3 描画先

SNS一覧（`apps/web/src/app/social/page.tsx`）へ `PluginActions` を足す。
`social.list.actions` は既に `CORE_EXTENSION_POINTS` にあり、
同名の `ExtensionPoint` も描画済みなので、`ui-shell.test.ts` の
宣言↔描画の双方向検査は現状のまま通る（新しい名前を足さない）。

**`ui/plugin/plugin-slot.tsx` は触らない**（別作業が保持中）。
そのため `PluginActions` から `resource` を渡す配線は本作業に含めない。
`resource` は宣言とレジストリの絞り込みまでを提供する。

## 6. マイグレーション

1ファイルにまとめる（`NNN_campaign_social_posts.sql`）。
番号は**追加時点で空いている次の連番**を採る。

```sql
CREATE TABLE campaign_social_posts (...);
CREATE INDEX campaign_social_posts_post_idx ON campaign_social_posts (social_post_id);

ALTER TABLE social_posts ADD COLUMN failed_at timestamptz;
CREATE INDEX social_posts_delivery_idx
    ON social_posts (COALESCE(published_at, failed_at, updated_at) DESC)
    WHERE status IN ('published', 'failed');
```

`apps/web/src/database/schema.ts` に `CampaignSocialPostsTable` と
`social_posts.failed_at` を足す。

## 7. Plugin API への追加（すべて後方互換）

| 場所 | 追加 | 互換性 |
| --- | --- | --- |
| `ui.ts` `ActionRegistration.resource?` | 任意項目 | 既存の登録はそのまま通る |
| `ui.ts` `CORE_ACTION_RESOURCES` | 新しい定数 | 追加のみ |
| `data.ts` `CampaignView.socialPostIds` | Core だけが作る読み取り用の型 | Plugin は読むだけ |
| `data.ts` `CampaignInput.socialPostIds?` | 任意項目 | 省略時は空 |
| `data.ts` `SocialPostView.failureReason` | Core だけが作る読み取り用の型 | Plugin は読むだけ |
| `events.ts` `CampaignEventPayload.socialPostIds?` | 任意項目 | Plugin も `emit` しうるため必須にしない |

`PLUGIN_API_VERSION` は上げない。**項目の追加は破壊的変更ではない**
（`07_開発者向けガイド.md` §47）。
