## 2. 責務境界・API互換

* **Plugin API の破壊的変更は無い。** 追加した項目は
  `ActionRegistration.resource?` / `CampaignInput.socialPostIds?` /
  `CampaignEventPayload.socialPostIds?`（いずれも任意）と、
  Core だけが作る読み取り用の型への項目追加
  （`CampaignView.socialPostIds` / `SocialPostView.failureReason`）。
  Plugin が構築しうる型には必須項目を足していない。`PLUGIN_API_VERSION` は据え置き。
* **`CORE_EXTENSION_POINTS` に新しい名前を足していない。**
  `ui-shell.test.ts` の宣言↔描画の双方向検査は現状のまま通る。
* **レイヤの向き**：分析の畳み込みは `domain/campaign/campaign-analysis.ts`（Domain）。
  画面は Application 層の UseCase だけを呼ぶ。`connection.db` を Application 層で
  触っていない（新しい SQL はすべて `infrastructure/*-repository.ts`）。
* **境界**：SaaS 前提のもの（テナント・課金・ユーザー登録）は入れていない。

## 3. セキュリティ

* 追加した UseCase はすべて `defineUseCase` を通し、Permission を宣言している
  （`social.post.history` / `social.post.listByIds` は `social.read`）。
  権限が無い相手が 403 になることを結合テストで固定した。
* 分析画面は `campaign.read` で入り、`analytics.read` / `social.read` が無い区画は
  **データを出さずに理由だけを出す**。権限の無い相手に数字が漏れない。
* 失敗理由は外部サービスの応答が入りうる。**長さで例外にせず切り詰める**方針にし、
  上限（2000文字）を Domain に置いた。表示は React が自動でエスケープする。
* 資格情報まわりは変更していない。`SocialPostView` に足したのは
  `failureReason` だけで、Secret を新たに露出させていない。
* `findPostsByIds` は UUID 形式でないIDを問い合わせ前に落とす。

## 5. 残る指摘

* `ActionRegistration.resource` は**宣言とレジストリの絞り込みまで**であり、
  `PluginActions` から `resource` を渡す配線は入っていない。
  描画側（`apps/web/src/ui/plugin/plugin-slot.tsx`）が別作業の保持下にあるため。
  配線は「`PluginActionsProps` に `resource?` を足して `collectActions` へ渡す」だけで済む。
* `social_posts.failed_at` は既存行へ遡って埋めていない。
  この列を足す前に失敗した投稿は、履歴の日時が `updated_at` で代替される。
