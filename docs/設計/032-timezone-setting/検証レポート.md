## 3. 判断の積み重ね（この機能の性格）

032 は**設計の判断がユーザーの裁定で 2 度覆り、検証がその適用範囲の想定外を 2 度見つけた**機能である。
経緯を残しておかないと、後から読んだ人が「なぜこうなっているのか」を再構成できない。

| 段 | 誰が | 何を |
| --- | --- | --- |
| 1 | 設計 | Plugin が入れた集計値（`source <> 'core'`）は**消さない**と判断（元データが本体に無く復元不能。Plugin の `metricDate` は外部サービスの暦） |
| 2 | **ユーザー** | 理由を承知のうえで**一律に消す**と裁定（`要件.md` §7-1） |
| 3 | 責務境界の検証 | **裁定の前提より削除範囲が広い**と発見。計測タグを一度も貼っていないサイトは、保持期間に関係なく Plugin データが**全期間・全件**消えていた |
| 4 | **ユーザー** | **生ログが 1 行も無いサイトは対象外**と裁定 |
| 5 | 責務境界の検証 | 削除が**イベントを 1 つも発火しない**と指摘。「◯◯日まで取り込み済み」を持つ Plugin は永久に再取得しない |
| 6 | **ユーザー** | **`analytics.purged` を 032 に含める**と裁定 |
| 7 | セキュリティの検証 | 未認証で読める口に `analyticsTimeZone` が加わり、**許可リストがルート 1 ファイルにしか無い**と指摘 |
| 8 | **ユーザー** | **構造の穴を直す**と裁定 → Domain に射影型 `PublicSystemSettings` を置いて型で閉じた |

**設計 §9.1.1 に、段 1 で「消さない」と判断した理由がそのまま残してある。**
段 2 で覆ったことは §9.1.2 に書かれており、後から読む人が「帰結を承知のうえで選ばれた」と分かる。

## 4. 各検証が確認した範囲

### 4.1 設計との整合

* 受け入れ条件 1〜154 の全件について、対応するテストの**中身**を読んで条件を検証しているかを確認
* **#120 が回帰条件として実際に効く**（生ログ 0 件の環境で 1 行も消えない＝従来は全件消えていた）。
  Infrastructure 直呼びとジョブ経路の両方で `coreRows` / `pluginRows` / `sites` が全 0 かつ全行不変
* **#130 に対照が同一テスト内にある**（削除を失敗させて未発火 → `mockRestore()` して発火）。空振り不可能
* **#98 と #122 が両立**（同一テストで、計測サイトの Plugin 行が 0 になることと、未計測サイトの行が残ることを続けて検査）
* **既存 1〜115 の検査内容が維持されている。** 裁定 A で対象サイトが選ばれなくなると #32・#35・#36・#38・#92・#93・#94 は
  「消えない」で**空振りのまま通ってしまう**ため、`markTracked()`（消したい日とは**別の日**に生ログを 1 行置く）で
  下ごしらえを補っている。`analytics` 行は増やさないので、アサーションは 1 つも変わっていない
* 設計 §12 の文書改訂が全件入っている

### 4.2 責務境界・API 互換

* **`analytics.purged` の追加は安全。** `CORE_EVENTS` / `CoreEventName` / `CoreEventPayloads` の全参照を洗い、
  **列挙を網羅前提で扱っているコードが 1 つも無い**ことを確認（`webhook-use-cases.ts` と `plugin/context.ts` は
  どちらも `Set.has()` の帰属判定）。`switch` の網羅チェック・`Record<CoreEventName, …>`・zod enum は存在しない
* **ペイロードは復旧に必要な最小集合**（自分が影響を受けたか＝`sources` に自分の `pluginId`／どのサイトを＝`siteId`／
  どの期間を＝`from`・`to`）。**消えた後なので `data.analytics.list` では確かめようがない**という制約に答えている
* **`sources` は自由文ではない。** `plugin/data-api.ts` が `source: pluginId` と Core 側で束縛し、`pluginId` は
  Manifest の `[a-z][a-z0-9-]{1,63}` を通る。Webhook へ中継しても 023 §3.1 の立場は破られない
* **`'use client'` ならぬ層の配置**：`emit` は Application（`rollup.ts` の先例と同じ）、集約は Infrastructure（SQL 内で畳む）、
  `domain/analytics/time-zone.ts` は `Intl` のみに依存
* **単体成立性**：新しい環境変数 0。`TORIFUNE_TIMEZONE` だけを置いている既存環境は、画面を触るまで従来どおり動く

### 4.3 セキュリティ

* **認可**：新規 3 本すべて `permission: 'system.manage'`。`defineRoute` と UseCase の二重。
  `app/api/v1` 配下の全 route の `permission:` を突き合わせ、`null` の口は増えていない
* **SQL**：`AT TIME ZONE ${timeZone}` はバインド値。`sql.raw` / `sql.lit` の文字列連結は無い。
  **検証されない `timeZone` が `deleteStalePoints` に届く経路は存在しない**（呼び出し元は 2 つで、どちらも `selectableTimeZone()` を通る）
* **`tracked_sites` は JOIN による絞り込みなので、対象は単調に減るだけ**
* **`analytics.purged` は新たな境界を越えない。** Webhook の登録・更新・削除はすべて `system.manage` で、
  購読を作れる主体はそもそもタイムゾーンを変えられ `siteId` も導入済み Plugin も読める
* **射影で型が閉じた**：`getSystemSettings` / `loadSystemSettings()` の戻り値が `PublicSystemSettings` に狭まり、
  `analyticsTimeZone` は認可なしの経路から**型として到達できない**

### 5.2 テストが検査になっていなかったもの（**2 件とも空振り**）

1. **#151** — import 句の名前が `SystemSettings` と完全一致するかだけを見ていたが、
   **危険なのは型ではなく関数 `toSystemSettings` のほう**。実装後は型を import する製品ファイルが 0 件になり、
   **テストごと削除しても通る**状態だった。判定を関数まで広げ、
   `expect(importers).toEqual(['application/analytics/timezone.ts'])` と**等値で固定**して非空振り性を構造的に担保
2. **#154** — `\s*` のつもりが**エスケープが落ちて `s*` になっており**、`analyticsTimeZones` ＋ `,`/`}` という
   決して現れない形を探していた。**常に真＝空振り。** 禁止する形を素の部分文字列の一覧にし、
   **一覧が実際に捕まえることを合成した文字列で確かめる `it.each` を追加**

**教訓**：`expect(x).toEqual([])` や `not.toContain(...)` だけで成り立つ検査は、対象が 0 件でも通る。
**許可した側が実際に一致することを等値で固定する**と、非空振り性がその検査自身から分かる。
032 の他の静的検査は全数を洗い、いずれも同じ `describe` に正の対照があることを確認した。

### 5.3 文書の誤り

* **`010-plugin-api/設計.md` §9 に、成り立たない因果が 2 度書かれた。**
  「`PLUGIN_API_VERSION` を上げると既存 Plugin が導入できなくなる」——`SUPPORTED_API_VERSIONS` は**独立した定数**で、
  `manifest.ts` の検証は後者だけを見る。前者を上げても既存の `apiVersion: 1` は導入でき、
  **拒否されるのは逆に「2 を宣言した新しい Plugin」**。010 §9 は将来の判断が引く**規範文書**なので、
  成り立たない因果を残すと次の判断がその前提で決まる。**訂正の引用ブロックを残して差し替えた**
* 監査記録の順序の記述が逆（**ジョブ起動が先、監査記録が後**）。
  `recordAudit` は失敗を握るので「監査が無い ⇒ 走っていない」とは読めない、という限界も明記
* 未決 #14 の「新旧が混ざらない」という断定（生ログを prune されたサイトに再びアクセスが来れば混ざる）

## 6. 残していること（未解決の指摘ではない）

1. **プレビューの `summarizeStaleDays` に `statement_timeout` が無い。** `analytics` 全体の `GROUP BY` と
   `access_logs` の `NOT EXISTS` が `GET /api/v1/settings/timezone` から同期で走る。`system.manage` 限定だが、
   同じリポジトリの `getTodayAnalytics` には前例がある（`TODAY_AGGREGATION_TIMEOUT_MS`）
2. **`analytics.purged` のペイロードに上限が無い。** `sites[]` はサイト数、`sources[]` は導入済み Plugin 数まで伸び、
   `webhook_deliveries.payload` に保存されて外部へ POST される。機密ではなく行の大きさと再送の問題
3. **`'core'` が予約 Plugin ID になっていない**（設計 §11 未決 #16）。`id: "core"` の Plugin は
   `source = 'core'` の行を書けるため、確認ダイアログが「Plugin の値は消えません」と出したまま消す。
   **032 が作った問題ではない**（既に `replaceCorePoints` が上書きしている）が、032 が衝突を 3 か所へ波及させる。
   修正は `RESERVED_PLUGIN_IDS` に 1 行だが**Manifest 検証を厳しくする変更**なので、別の要件として立て直す
4. **保持期間で生ログを全部消したサイトが削除の対象外に落ちる**（未決 #14）。元の裁定 §3.3 は消したかった側だが、
   誤りの向きが安全側（消しすぎは不可逆、残しすぎは可逆）であることを理由に許容した
5. **E2E は同時に 1 つしか流せない。** `playwright.config.ts` の `reuseExistingServer: !CI` と
   `apps/web/.next/lock` の両方が二重実行で壊れる。加えて **Playwright は `webServer` を起動してから
   `globalSetup` を走らせる**ため、中断した実行が `system_settings` に残した値をサーバー起動時の暖機が掴み、
   **TTL 30 秒の間だけ次の実行の最初の spec に効く**（実際に `analytics.spec.ts` の 5 件が落ちた）。
   根本原因（`afterAll` の復旧が CSRF で失敗）は修正済み
6. **`test-results/` の成果物の有無を全緑の根拠にできない。** `page.goto` の中断は `expect.poll` の
   コールバック内で投げるため、Playwright が失敗時スナップショットを撮る経路に乗らず成果物が作られない。
   **passed / failed の件数そのもので判定すること**
