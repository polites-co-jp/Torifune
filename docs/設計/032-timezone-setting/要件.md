# 032 基準タイムゾーンの画面設定と集計の洗い替え — 要件と裁定

設計書（`設計.md`）を書くための入力。ユーザーの要望と裁定をまとめる。
**この裁定は決定事項であり、設計書はこれに従う。**

## 1. 要望（2026-09-06）

> 設定画面に基準タイムゾーンを設定できるようにする。
> 各ページで集計する日付は、そこで設定されているタイムゾーンで統一される。
> すでにある集計データは、タイムゾーンが変更されたときに洗い替えする
> （利用者には時間がかかる旨を表示してもよい）。既定のタイムゾーンは UTC とする。

## 2. 着手前に確認した現状（2026-09-06 時点）

* **既定は既に `UTC`**（`application/analytics/timezone.ts` の `DEFAULT_TIME_ZONE`）。
  要望の「既定は UTC」は**現状のまま**で満たされる
* 現在の設定元は環境変数 `TORIFUNE_TIMEZONE` のみ。不正な値は落とさず警告して UTC へ落ちる
* `analyticsTimeZone()` は **同期関数**で、次から呼ばれる
  * `application/analytics/collect.ts` の `saltDay`（**アクセス受信のたび。ホットパス**）
  * `application/analytics/rollup.ts`、`application/jobs/definitions.ts`
  * `app/analytics/page.tsx`（「今日」の決定）
* 設定の置き場は `system_settings`（`key` / `value jsonb` の key-value）。
  型付きアクセサ `getSystemSettings` / `updateSystemSettings` と `SYSTEM_SETTING_KEYS` が既にある
* 画面は `ui/settings/general-settings.tsx`（いまは「サービス表示名」のみ）
* **029 の定期実行基盤と `job_runs` がある。** 設定画面に実行状況の表示も既にある
  （`ui/settings/job-status.tsx`）
* 生ログは `pruneAccessLogs(olderThanDays)` で消える。**消した期間は洗い替えできない**

### 2.1 避けられない制約（訪問者数は完全には直らない）

**訪問者ハッシュのソルトは、集計の 1 日の境目で回っている**（`collect.ts` の `saltDay` が
`todayInTimeZone(analyticsTimeZone())` を使う）。そして **ソルトは保存されない**
（プロセス内の `Map` に持ち、日が変わると捨てる。018 設計 §3.2 の
「追跡できてしまうほうが問題なので、数え漏れを受け入れる」という判断）。

したがって、過去の `visitor_hash` は**旧タイムゾーンの日付で回ったソルト**で作られている。
洗い替えで日付の区切りを動かすと、**新しい境目をまたぐ訪問者が別人として数えられる**。

* **ページビュー・Bot のページビューは正確に直る**（1 行 1 件を数え直すだけ）
* **訪問者数・セッション数・直帰率・滞在は、境目付近で実際より多く（悪く）出る**

これは仕組み上どうにもならない。**洗い替えは「完全な再計算」ではないことを画面で断る。**

## 3. 裁定（2026-09-06）

### 3.1 環境変数との関係 — **画面設定を優先。`TORIFUNE_TIMEZONE` は初期値のみ**

* `system_settings` に値が無い間は `TORIFUNE_TIMEZONE`（さらに無ければ `UTC`）
* 画面で保存されたら、以後は `system_settings` の値を見る
* 既存環境は env のまま動き続け、画面で変えたらそちらが効く。移行が滞らない

### 3.2 洗い替えの実行方式 — **ジョブとして非同期に走らせる**

* 保存は即座に返す。洗い替えは 029 のジョブ基盤で走らせる
* 進捗と完了は `job_runs` から見られる（設定画面に実行状況の表示が既にある）
* 長期間の生ログでも画面がタイムアウトしない

### 3.3 洗い替えできない期間の集計値 — **消す**

生ログが残っていない期間の集計値（旧タイムゾーンで畳まれた値）は**削除する**。
残った集計値はすべて新しいタイムゾーンで揃う。

* **これは不可逆で、生ログを先に消している期間の数字が完全に失われる。**
  020 の既定方針（「集計値は消さない」）を、この操作に限って覆す裁定である
* したがって**保存前に、何が失われるかを具体的に示して明示的な確認を取る**こと
  （既存の `ConfirmDialog` の先例に倣う。028 の公開キー再発行と同じ扱い）

### 3.4 ブランチ — `main` から切る

`feature/032-timezone-setting`。031（チャート部品）とは領域が重ならないので独立してマージできる。

## 4. 制約

* **新しい Permission を作らない。** 設定の変更は既存の `system.manage`
  （`updateSystemSettings` が使っているものに揃える）
* **`collect` のホットパスに DB 読み取りを増やさない。** `analyticsTimeZone()` は
  アクセス受信のたびに呼ばれる。DB 由来の値をどう持つか（キャッシュと無効化）は設計で解く
* Domain 層は DB 製品に依存しない。1 日の境目の計算は `domain/analytics/day.ts` のまま
* 公開リポジトリである。特定の導入環境を指す記述を書かない
* `chartPolyline` のような公開契約に触らない（本件は無関係のはず。触るなら理由を書く）

## 5. 受け入れ条件の骨子

* 設定画面でタイムゾーンを選べ、保存できる
* 保存した値が、集計・画面の「今日」・ソルトの回り方のすべてで使われる
* `system_settings` に値が無ければ `TORIFUNE_TIMEZONE`、それも無ければ `UTC`
* 不正な値を保存できない（保存時に弾く。現在の env は警告して UTC へ落ちるが、
  画面からの入力は**保存を拒否する**）
* 保存すると洗い替えのジョブが始まり、`job_runs` から進捗が見える
* 洗い替え後、生ログのある期間の集計値が新しいタイムゾーンで揃う
* 生ログの無い期間の集計値が消えている
* **保存前に、消える期間と失われる数字を示した確認が出る**
* タイムゾーンを変えていない保存では洗い替えが走らない
* 権限なしで 403、未認証で 401
* `collect` の 1 リクエストあたりの DB 問い合わせ回数が増えていない

## 6. 設計で決めること（裁定していない）

1. **`analyticsTimeZone()` をどう DB 由来にするか。** 同期のまま保つのか、非同期にするのか。
   キャッシュの持ち方と無効化（複数プロセス構成では他プロセスのキャッシュをどう更新するか）
2. **洗い替えの範囲の決め方。** 生ログの最古の日から今日まで。400 日を超える場合の分割
3. **洗い替え中に新しいアクセスが届いたときの扱い**（走行中の日を二重に畳まないか）
4. **ソルトの境目が変わる瞬間の扱い**（3.1 の制約は過去分。変更した当日の分をどう扱うか）
5. **タイムゾーンの選び方の UI**（自由入力か、一覧からの選択か。`Intl.supportedValuesOf('timeZone')` の可否）
6. **洗い替えジョブの名前と `job_runs.summary` の形**（029 の `JOB_NAMES` に足す）
7. **確認ダイアログに出す「失われるもの」の算出方法**（生ログの最古の日と、
   それより前の集計値の件数・期間）

## 7. 設計後の追加裁定（2026-09-06）

`設計.md` を受けて確認した事項。**これも決定事項であり、実装プラン以降はこれに従う。**

1. **Plugin が入れた集計値（`source <> 'core'`）も削除の対象にする。**
   設計は「消さない」（元データが本体に無く復元不能。Plugin の `metricDate` は外部サービスの暦で
   決まっており、本体の境目で畳まれた値ではない）と判断したが、**裁定 §3.3 を字義どおり一律に適用する**。
   洗い替え後の `analytics` は、生ログのある期間だけが残る。

   **帰結として必ず守ること**：
   * **本体の操作で Plugin のデータを消す**ことになる。Plugin 側に再取得の手段が無ければ永久に失われる
   * したがって**確認ダイアログに、Plugin が入れた値も消えることを明示する**。
     消える件数の内訳（`source = 'core'` と `source <> 'core'`）を分けて示すこと
   * 設計 §9（Plugin API への影響）に、この帰結を記録する
2. **洗い替えジョブが失敗・中断したときのやり直しは、設定画面の再実行ボタンで行う。**
   自動再試行はしない（失敗が繰り返すと重い集計が延々と走り続け、中断の手段も要る）。
   タイムゾーンは既に保存済みなので、再実行は冪等に同じことをする。
   `job_runs` に残る失敗を見て手で押せること。
3. `設計.md` のその他の決定（同期の `analyticsTimeZone()` は `collect` だけが呼ぶ／
   他は非同期版へ／TTL 30 秒の pull のみ／`analytics.rollup` と同じ鍵で排他／削除は最後／
   30 日チャンク／`listTimeZones()` は `UTC` を先頭に足す／既定値は `null`）をそのまま採る。
