# 032 基準タイムゾーンの画面設定と集計の洗い替え 設計

**入力は `要件.md`（2026-09-06 のユーザー裁定）。裁定は決定事項として扱い、蒸し返さない。**

---

## 1. 目的

集計の「1 日の境目」を決める基準タイムゾーンを、環境変数だけでなく**設定画面から変えられる**ようにする。
変更したときは、保存済みの日次集計（`analytics` の `source = 'core'`）を**新しい境目で洗い替える**。

いまは `TORIFUNE_TIMEZONE` を書き換えて再起動し、`POST /api/v1/analytics/rollup` を手で範囲指定して
流し直すしかない（`migrations/020_analytics_breakdown.sql` の運用手順、`docs/マニュアル/アクセス解析設置.md` §4）。
その手順を知らずに環境変数だけ変えると、**保存済みの `metric_date` は前の境目で畳まれたまま**残り、
画面の日付と集計値が静かに食い違う（`018` §4.1.1 が「変えたら流し直すこと」と書いているのはこのため）。

本設計は、その「変えたら流し直す」を**画面の 1 操作にまとめ、機械が行う**ようにする。

## 3. スコープ

### やること

* `system_settings` に基準タイムゾーンを持ち、`analyticsTimeZone()` を **DB 由来**にする（§6.1）
  * `system_settings` に値が無い間は `TORIFUNE_TIMEZONE`、それも無ければ `UTC`（裁定 §3.1）
* 設定 → 一般に**基準タイムゾーンの区画**を足す（一覧から選ぶ。§7.1）
* 変更を保存すると、**洗い替えジョブ `analytics.timezoneRebuild`** が非同期で走る（裁定 §3.2、§6.2）
  * 生ログのある期間を新しい境目でロールアップし直す
  * **生ログの無い期間の集計値を消す**（裁定 §3.3 ＋ `要件.md` §7-1、§5.4）。
    出所は問わない（Plugin の値も消える）。ただし**生ログが 1 行も無いサイトは対象外**（§5.4.1）
  * 消したことを **`analytics.purged`** で Plugin へ知らせる（§9.3）
* 保存前に、**何が失われるかを数えて示す確認ダイアログ**を出す（裁定 §3.3、§7.2）
* 洗い替えの進捗・結果を `job_runs` に残し、設定画面の「定期実行」区画から見られるようにする

### やらないこと

| やらないこと | 理由 |
| --- | --- |
| サイトごと・ユーザーごとのタイムゾーン | `018` §4.1.1 の裁定。同じ集計値が見る人によって違う日に属すると、保存した日次の値を説明できなくなる |
| 表示だけをローカル時刻に直す（集計は UTC のまま） | 「境目」と「表示」を分けると、`salt` と `metric_date` と画面の 3 つを別々にそろえる話に戻る（`018` §4.1.1 が解いた問題の再発） |
| 訪問者ハッシュのソルトの保存 | `018` §3.2 の裁定（保存すると過去のソルトで同じ人を追える）。**洗い替えで訪問者数が完全には直らないのはこれが理由**であり、直すために方針を覆さない |
| 生ログの無い期間を「元の値のまま残す」選択肢 | 裁定 §3.3 で「消す」と決まっている。残す／消すを利用者に選ばせない（選ばせると、混在した集計値の意味を誰も説明できない） |
| 洗い替えの中断・再開 | 途中で落ちたら**やり直す**（冪等なので安全。§6.2.2）。中断点の保存は入れない |
| 環境変数 `TORIFUNE_TIMEZONE` の廃止 | 既存環境をそのまま動かし続ける（裁定 §3.1）。初期値としての役割は残す |
| `analytics` の `source <> 'core'`（Plugin が入れた値）の**洗い替え** | 本体に元データが無く、作り直せない。**削除は行う**（`要件.md` §7-1 の追加裁定。§5.4 / §9.1） |

### 4.1 「設定の保存」を `updateSystemSettings` に相乗りさせない理由

**循環参照になる。** 基準タイムゾーンの保存は、書いたあとに

1. そのプロセスのキャッシュを更新し（`application/analytics/timezone.ts`）
2. 洗い替えジョブを起こす（`application/analytics/rebuild.ts`）

必要がある。`application/system-settings/system-settings-use-cases.ts` からこれらを呼ぶと、
`system-settings → analytics → system-settings`（キャッシュが設定を読むため）の輪ができる。

**独立した UseCase と独立した口にする。** 設定の置き場（`system_settings`）は共有するが、
読み書きの経路は `application/analytics/` 側に置き、`system-settings-use-cases.ts` は**触らない**。

UX 上もこのほうが正しい。表示名の保存は「保存する」を押すだけだが、
タイムゾーンの変更は**確認を挟む不可逆な操作**であり、同じボタンに乗せてはいけない。

## 5. データモデル

### 5.1 マイグレーションは要らない

**新しいマイグレーションを追加しない。** 根拠は次の 3 つ。

| 置き場 | 既存の定義 | 足りている理由 |
| --- | --- | --- |
| 設定値 | `migrations/012_system_settings.sql`（`key text PK` / `value jsonb`） | key-value なので**キーを足すだけ**。`system_settings_key_format` の CHECK（`^[a-z][a-z0-9_]*(\.[a-z][a-z0-9_]*)*$`）に `analytics.time_zone` は適合する |
| ジョブの記録 | `migrations/021_job_runs.sql` | `job_runs_job_name_not_blank` は空白だけを弾く CHECK で、**ジョブ名を列挙していない**。新しい名前がそのまま入る |
| 集計値・生ログ | `migrations/014_analytics.sql` / `020_analytics_breakdown.sql` | 洗い替えは既存の行を**差し替える・消す**だけ。列も索引も足さない |

削除に使う条件（§5.4）は `analytics (site_id, metric_date)` の GROUP BY と
`access_logs_site_time_idx (site_id, occurred_at DESC)` の範囲検索で足りる。**索引も足さない。**

### 5.2 設定のキーと型（`domain/system-settings.ts`）

```ts
export const SYSTEM_SETTING_KEYS = {
  serviceName: 'general.service_name',
  rememberMeEnabled: 'auth.remember_me_enabled',
  analyticsTimeZone: 'analytics.time_zone',   // 追加
} as const;

export interface SystemSettings {
  readonly serviceName: string;
  readonly rememberMeEnabled: boolean;
  /** 基準タイムゾーン。**null は「未設定」**で、環境変数へ落ちることを表す */
  readonly analyticsTimeZone: string | null;
}
```

* **既定値を `'UTC'` にしない。`null`（未設定）にする。** 既定を `'UTC'` にすると、
  `TORIFUNE_TIMEZONE=Asia/Tokyo` の既存環境が、画面で一度も触っていないのに UTC へ落ちる。
  裁定 §3.1（「`system_settings` に値が無い間は `TORIFUNE_TIMEZONE`」）を型で守る
* `toSystemSettings` は「文字列であり、かつ `isValidTimeZone` を通る」ときだけ値を返し、
  それ以外は `null`（＝未設定として扱い、環境変数へ落ちる）。
  **読み出しでは一覧との照合をしない**（§5.3 の「保存時は厳しく、読み出しは緩く」）

### 5.3 タイムゾーン名の扱い（`domain/analytics/time-zone.ts`、新規）

`day.ts` は「**境目の計算**」、`time-zone.ts` は「**タイムゾーン名そのものの扱い**」に分ける。
`day.ts` の既存 export は動かさない（動かすと 9 箇所の import が無意味に散らかる）。

```ts
/** IANA 名を正規化する。解釈できなければ null（`utc` → `UTC`、`Japan` → `Asia/Tokyo`） */
export function canonicalTimeZone(value: string): string | null;

/** 選べるタイムゾーンの一覧（`UTC` を先頭に、`Intl.supportedValuesOf('timeZone')` を続ける） */
export function listTimeZones(): readonly string[];

/** 保存を許すか。**正規化した値が `listTimeZones()` に含まれること** */
export function isSelectableTimeZone(value: string): boolean;

/** 画面へ渡す選択肢。地域ごとにまとめ、現在のオフセットを添える */
export function timeZoneOptions(now: Date, extra: readonly string[]): readonly TimeZoneGroup[];
```

#### 5.3.1 `isValidTimeZone` だけでは保存の入口として緩すぎる（実測）

`isValidTimeZone`（＝`new Intl.DateTimeFormat('en-US', { timeZone: value })` が例外を投げないか）は、
IANA の地域名以外も通す。Node 22 以降の実測：

| 入力 | `isValidTimeZone` | `resolvedOptions().timeZone`（正規化後） |
| --- | --- | --- |
| `Asia/Tokyo` | 通る | `Asia/Tokyo` |
| `utc` | 通る | `UTC` |
| `Japan` / `US/Pacific` / `Zulu` / `GMT` | 通る | `Asia/Tokyo` / `America/Los_Angeles` / `UTC` / `UTC` |
| `+09:00` / `-0800` | **通る** | `+09:00` / `-08:00` |
| `Etc/GMT+5` | **通る** | `Etc/GMT+5` |
| `Foo/Bar` / `''` / `'UTC '`（末尾空白） | 弾く | — |

* **別名をそのまま保存しない。** `Japan` を保存すると、画面の一覧（`Asia/Tokyo` しか無い）に
  一致する項目が無くなり、選択欄が空で表示される。**保存する値は必ず正規化後の値にする**
* **オフセット表記（`+09:00`）は保存を拒否する。** 夏時間を持たない固定オフセットであり、
  一覧に無く、「どの地域の 1 日か」を画面で説明できない。判定は
  `isSelectableTimeZone`（正規化後の値が `listTimeZones()` に含まれること）1 つで済む

#### 5.3.2 一覧の作り方（実測に基づく）

`Intl.supportedValuesOf('timeZone')` は Node 22 以降（フル ICU）で使える。**実測（Node 24 / ICU 同梱ビルド）：**

* **418 件。すべて `地域/都市` の形**（`Africa` / `America` / `Antarctica` / `Arctic` / `Asia` /
  `Atlantic` / `Australia` / `Europe` / `Indian` / `Pacific` の 10 地域）
* **`UTC` は含まれない。`Etc/*` も含まれない。** 既定値が一覧に無いと選び直せないので、
  `listTimeZones()` は **`['UTC', ...Intl.supportedValuesOf('timeZone')]`** を返す（重複は除く）
* オフセット併記（`Intl.DateTimeFormat(..., { timeZoneName: 'longOffset' })`）を 418 件ぶん組み立てて
  **23 ms**。設定画面 1 回の描画で払う分には問題にならない（頻繁に描かれる画面ではない）

**ブラウザ側の `Intl.supportedValuesOf` には依存しない。** 一覧は Server Component
（`app/settings/page.tsx`）で組み立て、props で渡す。ブラウザの実装差・ICU の差が画面に出ない。

`Intl.supportedValuesOf` が無い実行環境（ICU を削ったビルド）では `['UTC']` だけを返す。
このとき**保存済みの値が一覧から消えて選択欄が壊れる**ので、`timeZoneOptions` は
`extra`（現在の値）を必ず一覧へ混ぜる。

### 5.4 「生ログの無い期間の集計値」の定義（裁定 §3.3 の具体）

**消す行の条件を SQL で言い切る。**

> **2026-09-06 の追加裁定（`要件.md` §7-1）により、`source <> 'core'`（Plugin が入れた値）も削除の対象になった。**
> 本設計は当初「Core の行だけを消す」と判断していた。**その判断と理由は §9.1 に残してある**
> （帰結を承知のうえでユーザーが一律適用を選んだことが、後から読んで分かるようにするため）。

> **2026-09-06 の追加裁定（検証後、§5.4.1）により、生ログが 1 行も無い（＝一度も計測していない）
> サイトは削除の対象から外れた。** 下の SQL はその絞り込みを含む。

```sql
-- ① 「集計値がある (サイト, 日)」を先に畳む。**出所で絞らない**
WITH metric_days AS (
    SELECT site_id, metric_date
    FROM analytics
    GROUP BY site_id, metric_date
),
-- ② **生ログが 1 行でもあるサイト**だけを残す（§5.4.1）
tracked_sites AS (
    SELECT DISTINCT d.site_id
    FROM metric_days d
    WHERE EXISTS (SELECT 1 FROM access_logs l WHERE l.site_id = d.site_id)
),
-- ③ そのうち、新しいタイムゾーンで見て生ログが 1 行も無い日
stale AS (
    SELECT d.site_id, d.metric_date
    FROM metric_days d
    JOIN tracked_sites t ON t.site_id = d.site_id
    WHERE NOT EXISTS (
        SELECT 1
        FROM access_logs l
        WHERE l.site_id = d.site_id
          AND l.occurred_at >= (d.metric_date::timestamp AT TIME ZONE $1)
          AND l.occurred_at <  ((d.metric_date + interval '1 day')::timestamp AT TIME ZONE $1)
    )
)
DELETE FROM analytics a
USING stale s
WHERE a.site_id = s.site_id
  AND a.metric_date = s.metric_date;
```

決めていることを 1 つずつ書く。

* **サイトで絞る。** 生ログが 1 行も無いサイトは対象外（§5.4.1）
* **出所では絞らない。** 対象になったサイトの中では、`source = 'core'` も `source <> 'core'`（Plugin が入れた値）も、
  同じ 1 つの規則で消える（裁定 §3.3 を字義どおり一律に適用する。`要件.md` §7-1）。
  洗い替えのあと `analytics` に残るのは**生ログのある期間だけ**になる。
  **本体の操作で Plugin のデータを消す**ことになるので、その帰結と評価は §9.1 に書く
* **「範囲の外」ではなく「その日に生ログが無い」で判定する。** 範囲の外で切ると、
  境目が動いたせいで空になった**端の日**を取りこぼす。
  例：生ログが `2026-01-01T00:30Z` から始まる環境で `UTC` → `Asia/Tokyo` にすると、
  その 1 行は `2026-01-01 09:30 JST` になり日付は動かないが、`UTC` → `America/Los_Angeles` では
  `2025-12-31 16:30` になり、**新しい最古の日が 1 日早くなる**。逆向き（西→東）では
  旧 `2026-01-01` の行が新しい境目ではどの生ログにも対応せず、空のまま残る。
  「その日に生ログが無い」で判定すると、この 2 つを別扱いせずに 1 つの条件で拾える
* **`GROUP BY` を先に置く。** `NOT EXISTS` を `analytics` の全行に掛けると、
  パス・参照元の内訳キーぶん（1 日 1 サイトで数百行）だけ無駄に索引を叩く。
  (サイト, 日) に畳んでから 1 回ずつ判定する
* **タイムゾーンは 1 箇所（`$1`）で束ねる。** `occurred_at >= '...'::date` のような
  接続 TimeZone 依存の比較は書かない（`018` §4.1.1）
* **生ログが 1 行も無い環境では、何も消えない**（§5.4.1。対象になるサイトが 1 つも無い）。
  **計測しているサイトで、保持期間を過ぎて生ログを消した期間は全部消える**（Core も Plugin も）。
  これが裁定 §3.3 のそのままの帰結であり、隠さない。§7.2 の確認ダイアログでその件数を先に見せる
* **停止中（`archived`）のサイトの行も同じ規則で消える。** サイトの状態で例外を作らない
  （状態で分けると、停止したサイトだけ旧境目の値が残り、混在の説明が付かない）

**プレビューと削除で条件を二重に持たない**（同じ SQL 断片を共有する）。

* `summarizeStaleDays(connection, timeZone)`（プレビュー用。§6.5）は、上の `stale` に `analytics` を
  join し直して **出所ごとの内訳**を返す。
  `count(*) FILTER (WHERE source = 'core')` と `count(*) FILTER (WHERE source <> 'core')`、
  (サイト, 日) 数、サイト数、`min` / `max` の `metric_date`、および
  `SELECT DISTINCT source WHERE source <> 'core'`（消える値を入れた Plugin の ID。
  導入済み Plugin の数で上限が付くので件数の上限は掛けない）
* `deleteStalePoints(connection, timeZone)`（洗い替え用）は同じ条件で消し、
  **消した実績を 1 文の中で数えて**返す。`analytics.purged` イベントの Payload（§9.3）と
  `job_runs.summary` の `deletedDays` / `deletedCoreRows` / `deletedPluginRows`（§5.5）が、
  どちらもこの戻り値から出る。

  ```ts
  {
    /** 消した (サイト, 日) の数。**全サイトぶんの合計。** */
    days: number;
    coreRows: number; pluginRows: number;
    sites: readonly {
      siteId: string;
      /** 消えた `metric_date` の最古・最新。**この範囲の日がすべて消えたとは限らない。** */
      from: string; to: string;
      rows: number;
      /** そのサイトで消えた行の `source`（`'core'` を含む）。 */
      sources: readonly string[];
    }[];
  }
  ```

  **サイトごとの集約は SQL の中で行う。**

  ```sql
  ${staleDaysCte}
  , deleted AS (
      DELETE FROM analytics a
      USING days_without_access_logs s
      WHERE a.site_id = s.site_id AND a.metric_date = s.metric_date
      RETURNING a.site_id, a.metric_date, a.source
  )
  SELECT site_id,
         min(metric_date) AS from_date, max(metric_date) AS to_date,
         count(DISTINCT metric_date) AS days,          -- ← 実績の (サイト, 日) 数
         count(*) AS rows,
         count(*) FILTER (WHERE source = 'core')  AS core_rows,
         count(*) FILTER (WHERE source <> 'core') AS plugin_rows,
         array_agg(DISTINCT source) AS sources
  FROM deleted
  GROUP BY site_id
  ```

  1 行ずつ返させてアプリで畳むと、消した行数だけメモリに載る。返る行数はサイト数で上限が付く。

  **`days` も同じ 1 文で数える。** 列を 1 つ（`count(DISTINCT metric_date)`）足すだけで、
  **実際に消えた (サイト, 日) の数**が出る。これには 2 つの意味がある。

  1. **実績値である。** 削除の直前に `summarizeStaleDays` をもう一度呼んで数える形にすると、
     **「数えた瞬間」と「消した瞬間」が別のスナップショットになる。**
     その隙間に生ログが届く／`pruneOlderThanDays` が走ると、記録に残す件数が実際に消した件数とずれる。
     `RETURNING` から数えれば、**消した行そのもの**を数えるので原理的にずれない
  2. **`analytics` の全走査が 1 回減る。** `metric_days` の `GROUP BY` は `analytics` を舐める（未決 #5）。
     数えるためだけにもう 1 往復する理由が無い

  > **検証で挙がった「`deletedDays` が削除と同じスナップショットで数えられていない」という指摘は、
  > これで解消した。** 洗い替えの本体（§6.2.2）は削除の前に `summarizeStaleDays` を呼ばない。
  > プレビュー（`summarizeStaleDays`）は**保存前の見積り**、`deleteStalePoints` の戻り値は**事後の実績**、
  > という役割の切り分けが、呼ぶ回数の面でもそろう。

> **メソッド名から `Core` を外す。** 追加裁定の前は `summarizeStaleCoreDays` /
> `deleteStaleCorePoints` としていたが、Core 以外も消すようになった以上、名前が嘘になる。

#### 5.4.1 生ログが 1 行も無いサイトは対象外にする（検証後の裁定）

**責務境界の検証が見つけた穴。** 初版の条件は `analytics` の全 (サイト, 日) を母集合にしていたため、
**計測タグを一度も貼っていないサイト**——Plugin が外部サービスの数値を取り込むためだけに作られたサイト——は
`access_logs` が 0 行であり、**保持期間に関係なく、全期間・全件が消えた。**

`要件.md` §3.3 の裁定は「**保持期間で生ログを消した期間**の集計値」として書かれており、
このケースは想定に入っていない。**ユーザーの裁定：生ログが 1 行も無いサイトは対象外にする。**

**理由：削除の根拠がそのサイトに当てはまらない。** 消すのは「**旧タイムゾーンで畳まれた値**が、
新しい境目で畳み直した値に混ざるから」である。本体が一度も畳んでいないサイトの `analytics` には、
旧境目で畳まれた値が 1 行も無い。境目を変えても**そのサイトの数字は 1 つも意味を変えない**ので、
消す理由が無い。

* 絞り込みは**サイト単位**（`EXISTS (SELECT 1 FROM access_logs WHERE site_id = …)`）。
  日付の条件（`AT TIME ZONE`）を含まないので、`access_logs_site_time_idx` の先頭列だけで判定できる
* **計測しているサイトの中では、`要件.md` §7-1 の裁定をそのまま維持する。**
  出所で例外を作らない（Plugin の行も消える）。緩めたのは「どのサイトを見るか」だけで、
  「そのサイトの中で何を消すか」は変えていない
* 生ログを 1 行でも受けたことがあり、その後すべて `pruneOlderThanDays` で消したサイトは
  **対象に入らない**（`access_logs` が 0 行になるため）。これは裁定に照らして緩い側の誤りだが、
  **消しすぎるより残しすぎるほうが安全**なので許容する（未決 #14）
* **この絞り込みで、確認ダイアログと文書の「生ログが残っていない期間」という説明が正確になる。**
  初版の条件は「生ログを持ったことのないサイト」まで巻き込んでおり、説明と実装がずれていた（§7.2 / §12）

### 5.5 `job_runs.summary` の形

| ジョブ | summary |
| --- | --- |
| `analytics.rollup`（既存） | `{ from, to, days, points }` |
| `webhook.deliver`（既存） | `{ attempted, delivered, failed }` |
| **`analytics.timezoneRebuild`（新規）** | `{ timeZone, previousTimeZone, from, to, completedThrough, days, points, deletedDays, deletedCoreRows, deletedPluginRows }` |

| キー | 意味 |
| --- | --- |
| `timeZone` / `previousTimeZone` | 何から何へ変えた洗い替えか（`previousTimeZone` は未設定なら解決後の実効値）。**やり直し（§6.5 の `POST /analytics/timezone-rebuild`）では両者が同じ値になり、それが「やり直しの印」になる**（§6.2.6） |
| `from` / `to` | 流し直した期間。**生ログが 1 行も無ければ両方 `null`**（ロールアップする対象が無い） |
| `completedThrough` | **進捗。** 最後に終えたチャンクの末日（`YYYY-MM-DD`）。完了時は `to` と等しい |
| `days` / `points` | `rollupAnalytics` の戻り値の合計（書いた (site, day) 数と行数） |
| `deletedDays` | 消した (site, day) 数。削除の前は `null`（まだ実行していない）。**`deleteStalePoints` の戻り値の `days`**（削除と同じ 1 文で数えた実績値。§5.4） |
| `deletedCoreRows` / `deletedPluginRows` | 消した行数を**出所ごとに**分けて残す（`source = 'core'` と `source <> 'core'`）。**Plugin の値をいくつ消したかが記録に残らないと、後から説明できない**（`要件.md` §7-1） |

`summary` は**チャンクごとに更新する**（§6.2.5）。`job_runs.summary` は `jsonb NOT NULL DEFAULT '{}'` で
型の制約が無いため、マイグレーションは要らない。

### 6.1 `analyticsTimeZone()` を DB 由来にする（要件 §6-1）

#### 6.1.1 経路を 2 つに分ける

```ts
// application/analytics/timezone.ts

/**
 * **同期。キャッシュを読むだけ。DB を読まない。**
 * 呼んでよいのは `collect` のホットパス（`saltDay`）だけ。
 */
export function analyticsTimeZone(): string;

/**
 * **非同期。キャッシュが古ければ読み直してから返す。**
 * ジョブ・UseCase・画面はこちらを使う（どれも既に非同期の文脈にある）。
 */
export function resolveAnalyticsTimeZone(): Promise<string>;

/** 画面に「いまどこの値が効いているか」を出すため。**認可の文脈を持たない**（`loadSystemSettings` と同じ扱い） */
export function analyticsTimeZoneSetting(): Promise<{
  readonly value: string;
  readonly source: 'database' | 'environment' | 'default';
}>;
```

| 呼び出し元 | いま | これから |
| --- | --- | --- |
| `application/analytics/collect.ts`（`saltDay`） | `analyticsTimeZone()` | **`analyticsTimeZone()` のまま**（同期・DB を読まない） |
| `application/analytics/rollup.ts` | `analyticsTimeZone()` | `await resolveAnalyticsTimeZone()`（引数で渡された場合はそちら） |
| `application/jobs/definitions.ts`（`scheduledRange`） | `analyticsTimeZone()` | `await resolveAnalyticsTimeZone()` |
| `application/analytics/analytics-use-cases.ts`（`getTodayAnalytics`） | `analyticsTimeZone()` | `await resolveAnalyticsTimeZone()` |
| `app/analytics/page.tsx` / `app/dashboard/page.tsx` / `app/settings/page.tsx` / `app/campaigns/[id]/analytics/page.tsx` | `analyticsTimeZone()` | `await resolveAnalyticsTimeZone()` |
| `app/api/v1/analytics/rollup/route.ts`（`daysAgo`） | `analyticsTimeZone()` | `await resolveAnalyticsTimeZone()` |

`campaigns/[id]/analytics/page.tsx` の `today()` と `rollup/route.ts` の `daysAgo()` は同期の私有関数なので、
非同期にして呼び出し側で `await` する。**どれも既に非同期の Server Component / ハンドラの中にある。**

#### 6.1.2 キャッシュの持ち方と無効化

置き場は `processState('analytics.time-zone', …)`（`infrastructure/process-state.ts`）。
**モジュール変数にしない。** Next.js は Route Handler・Server Component を別バンドルへ分けることがあり、
同じファイルの実体が複数になると「画面で変えたのに `collect` に効かない」という壊れ方をする
（`process-state.ts` の doc がまさにこの事故を説明している）。

```ts
interface TimeZoneCache {
  /** DB から読めた値。null は「まだ一度も読めていない」 */
  value: string | null;
  /** 最後に読んだ時刻（ミリ秒）。0 は未読み込み */
  loadedAt: number;
  /** 進行中の読み直し。二重に走らせない */
  inflight: Promise<void> | null;
}

/** キャッシュを古いとみなすまでの時間。 */
const TIME_ZONE_TTL_MS = 30_000;
```

* `analyticsTimeZone()`（同期）
  1. `value === null` なら**環境変数の値**（無効なら `UTC`。いまの `timezone.ts` の判定をそのまま使う）を返す
  2. `value !== null` なら `value` を返す
  3. どちらの場合も `Date.now() - loadedAt > TIME_ZONE_TTL_MS` なら**待たずに**読み直しを起こす
     （`inflight` があれば起こさない。例外は握って `log.warn`。
     **ここも `redactSecrets` を通す**——同期経路の読み直しも同じ `withConnection` を通るため）
  * **`await` しない。例外を投げない。DB の問い合わせを 1 回も増やさない**（§6.1.4）
* `resolveAnalyticsTimeZone()`（非同期）
  * 古ければ**読み直しの完了を待ってから**返す。読み直しに失敗したら、直前のキャッシュ（無ければ環境変数）を返して
    `log.warn` を出す。**集計や画面を DB の一時的な失敗で落とさない**（`analyticsTimeZone` が
    「不正な設定でアクセス記録まで止めない」としているのと同じ立場）
  * **例外のメッセージは `redactSecrets` を通してからログへ入れる**（`infrastructure/secret-text.ts`）。
    これは `029` §6.1.7 が規約化したもので、既存 5 箇所（`api/route.ts` / `jobs/run-job.ts` /
    `jobs/scheduler.ts` / `job-lock.ts` / `database/postgres-provider.ts`）がすべて従っている。
    **根拠はここの脅威モデルそのもの**：読み直しは `withConnection` → Provider の `connect()` を通るので、
    **Database Provider を差し替えた Plugin の例外**を受けうる。その文字列は標準 Provider の秘匿を通らず、
    接続文字列やトークンを含みうる。`logging.ts` の `maskSecrets` はキー名で落とす仕組みなので自由文には効かない。
    しかも `resolveAnalyticsTimeZone` はダッシュボード・アナリティクス・設定・rollup ルート・起動時から呼ばれ、
    **DB が不調な間は繰り返しログに残る**
* 読み直しは `withConnection` → `systemSettingsRepository.loadAll` → `toSystemSettings`。
  `system_settings` は数行の表で、索引は主キーだけ
* **保存したプロセスは即座に反映する。** `analytics.timeZoneUpdate`（§6.4）は書き込みの直後に
  キャッシュへ新しい値を入れる（`loadedAt = Date.now()`）。読み直しを待たない
* 起動時に**best-effort で暖める**。`instrumentation.ts` の `register()` で
  `void resolveAnalyticsTimeZone().catch(() => undefined)` を呼ぶ（`pg` を Edge バンドルへ入れないため**動的 import**）

  **`instrumentation.ts` のヘッダコメントを直す。** 冒頭は `029` §6.1.1 のまま
  「**DB に触らない。** DB が起動待ちでも本体の起動を止めない」と宣言しているが、
  この暖機は `resolveAnalyticsTimeZone()` → `withConnection` → `pool.connect()` で**実際に接続を張る**。
  **文字どおりには成り立たなくなった**ので、実態に合わせて書き換える。

  ただし **`029` が守ろうとした不変条件（起動時要件を増やさない）は保たれている。**
  コメントはそれが読み取れる形にする。

  | `029` §6.1.1 の意図 | 暖機での実際 |
  | --- | --- |
  | 起動を DB の準備完了に依存させない | `void … .catch(() => undefined)` で**待たず、失敗も握る**。`register()` は即座に返る |
  | DB が落ちていても起動する | 起動する。警告が 1 組出て、値は env → `UTC` へ落ちる。次の `resolveAnalyticsTimeZone()` が TTL 超過で読み直す |
  | Edge ランタイムへ `pg` を入れない | 動的 import のまま。`NEXT_RUNTIME !== 'nodejs'` なら `register()` は何もせず戻る |

  したがって、コメントは「**DB に触らない**」ではなく
  「**DB を待たない・DB の失敗で起動を止めない**（暖機は best-effort で接続を張るが、待たず握る）」と書く

#### 6.1.3 複数プロセス構成での収束と、古いままだと何が起きるか

`job_runs.runner` が `hostname:pid` を記録しているとおり（`029` §5.1）、**複数プロセスは想定内**である。
キャッシュはプロセスごとに独立していて、**他プロセスへ変更を push する仕組みは持たない**
（`LISTEN` / `NOTIFY` も、共有メモリも入れない）。収束は **TTL による pull だけ**で行う。

> **なぜ push しないか。** `NOTIFY` を使うには常時 `LISTEN` する接続を各プロセスで 1 本 pin する必要があり、
> `029` §6.1.6 が「Pool の pin は数えて使う」と決めた資源をもう 1 本恒常的に使うことになる。
> 得られるのは「30 秒が数百ミリ秒になる」だけで、下に書くとおり 30 秒のずれは新しい壊れ方を生まない。

**キャッシュが古いままの最大 30 秒に何が起きるか。**

| 経路 | 古い値を使うと | 収束したあと |
| --- | --- | --- |
| `collect` のソルト（同期経路） | ソルトの回るタイミングがプロセス間で最大 30 秒ずれる | 次の日付キーの切り替わりでそろう |
| 定期ロールアップ（`analytics.rollup`） | **旧境目で直近 7 日を畳み直しうる** | 15 分後の周期で新境目に上書きされる（`replaceCorePoints` は (site, day) ごとの差し替えなので跡が残らない） |
| 画面の「今日」 | プロセスによって 1 日ずれて見えうる | 再読み込みでそろう |

**ソルトについては、ずれによる追加の害はほぼ無い。** `collect.ts` の `salts` は**プロセス内の `Map`** であり、
複数プロセス構成では**もともとプロセスごとに違うソルト**が使われている（`018` §3.2 が
「再起動でソルトが変わると訪問者が二重に数えられるが、追跡できてしまうほうが問題」として受け入れた性質）。
30 秒のずれが増やすのは「回る**時刻**が少しずれる」ことだけで、新しい種類の壊れ方は生まない。

**洗い替えとの競合は、TTL ではなくロックで防ぐ。** 洗い替えジョブは定期ロールアップと**同じ鍵**で排他する
（§6.2.3）ので、洗い替えの最中に旧境目のロールアップが走ることはない。
洗い替えが終わった直後の最大 30 秒に他プロセスのロールアップが重なると、直近 7 日が一度だけ旧境目に戻るが、
そのプロセスも 30 秒以内にキャッシュを更新し、次の周期（15 分後）で新境目へ戻る。**跡は残らない。**

#### 6.1.4 `collect` のホットパスに DB 読み取りを増やさない（要件 §4）

`collectAccess` の 1 リクエストの DB 問い合わせは、現状 **`findSiteByPublicKey` と `recordAccess` の 2 本**。
本設計のあとも **2 本のまま**である。

* `saltDay` が呼ぶのは同期の `analyticsTimeZone()` だけで、**その中で DB を読む経路が無い**
* TTL 超過で起きる読み直しは**別の接続・別の非同期処理**であり、リクエストの応答を待たせない。
  頻度はプロセスあたり最大 2 回／分（TTL 30 秒）で、リクエスト数に比例しない
* 読み直しの失敗は握る。**計測が落ちる経路を新たに作らない**

> 受け入れ条件 #29（§10）で「`collect` の 1 リクエストあたりの問い合わせ回数が増えていない」を検査する。

### 6.2 洗い替えジョブ `analytics.timezoneRebuild`（要件 §6-2 / §6-3 / §6-6）

```ts
// domain/jobs/job.ts
export const JOB_NAMES = ['analytics.rollup', 'webhook.deliver', 'analytics.timezoneRebuild'] as const;
```

```ts
// application/jobs/definitions.ts
export interface RebuildInput {
  readonly timeZone: string;
  readonly previousTimeZone: string;
}

export const TIMEZONE_REBUILD_JOB: JobTask<RebuildInput> = {
  name: 'analytics.timezoneRebuild',
  /** **定期ロールアップと同じ鍵で排他する**（§6.2.3） */
  lockName: 'analytics.rollup',
  run: (connection, input, job) => rebuildAnalyticsForTimeZone(connection, input, job),
};
```

**周期を持たない。** `JobDefinition`（`intervalMs` を持つ）から `JobTask`（`name` / `lockName?` / `run`）を切り出し、
`runJob` は `JobTask` を受ける形にする。`runJob` はもともと `job.name` と `job.run` しか使っておらず、
**既存の呼び出しは 1 文字も変わらない**（`JobDefinition extends JobTask`）。
`bootScheduler` の `jobs` にはこのジョブを載せない（周期実行しない）。

#### 6.2.1 範囲の決め方（要件 §6-2）

```
from = 生ログの最古の occurred_at を、新しいタイムゾーンで日付にしたもの
to   = 新しいタイムゾーンでの今日
```

* `from` は `analyticsRepository.findOldestAccessAt(connection)`（`SELECT min(occurred_at) FROM access_logs`）。
  `access_logs_occurred_at_idx (occurred_at)` の端を 1 回読むだけで、全走査しない
* **生ログが 1 行も無ければロールアップの段は丸ごと飛ばす**（`from = to = null`）。
  削除の段（§5.4）だけを行う
* **400 日の上限は掛けない。** 400 日は「利用者が任意の広い範囲を API に渡せる」ことに対する入力の検査
  （`029` §6.3 の `assertRollupRange`）であって、集計そのものの限界ではない。
  このジョブは**範囲を入力として受け取らない**（生ログから導く）ので、守るべき入力が無い
* 代わりに **30 日ずつのチャンク**に切って順に流す。理由は 3 つ。
  1. `aggregateDailyBreakdown` は範囲全体の集計結果を**一度にメモリへ**返す（`rollupAnalytics` が
     `groupBySiteDay` で畳む）。数年ぶんを 1 回で返させない
  2. 1 チャンクが失敗しても、それまでのチャンクの結果は `analytics` に残る（次のやり直しは冪等に上書きする）
  3. 進捗を出せる（§6.2.5）
* **古い日から今日へ向かって進む。** 最後のチャンクに今日が入るので、
  走行中に届いた分をできるだけ拾える（§6.2.4）。順序の理由はもう 1 つあり、§6.2.2 に書く

#### 6.2.2 手順（削除は最後）

1. `timeZone` を確定する（`analytics.timeZoneUpdate` が保存済みの値を入力として渡す。ジョブの中で読み直さない）
2. `from` / `to` を決める（§6.2.1）
3. `from` から 30 日ずつ `rollupAnalytics(connection, { from: c.from, to: c.to, timeZone })` を呼ぶ。
   チャンクごとに `job.report({ …, completedThrough: c.to, days, points })`
4. **すべてのチャンクが終わってから**、`deleteStalePoints(connection, timeZone)`（§5.4）を 1 回だけ実行する。
   **記録に残す件数はこの戻り値から取る**（`days` / `coreRows` / `pluginRows`）。
   **削除の前に `summarizeStaleDays` を呼んで数え直さない**——別のスナップショットになり、実績とずれる（§5.4）
5. **1 行でも消えていれば `analytics.purged` を 1 回だけ発火する**（§9.3）。
   削除が成功したあと、`summary` を返す前。0 件なら発火しない
6. `summary` を最終形で返す

**削除を最後に置く理由：途中で落ちたときに、消してしまって直せない状態を作らないため。**

| 落ちた場所 | 状態 | やり直すと |
| --- | --- | --- |
| ロールアップの途中 | 一部の日が新境目、残りが旧境目。**何も失っていない** | 冪等（`replaceCorePoints` は (site, day) ごとの差し替え）なので、頭からやり直して同じ結果になる |
| 削除の途中 | 削除は 1 文 = 1 トランザクション。**途中の状態が残らない** | 同じ条件でもう一度実行するだけ |

先に削除すると、「消したのにロールアップが終わっていない」＝**取り返しのつかない損失を出したまま未完**という
最悪の中断点ができる。順序を逆にしない。

**`rollupAnalytics` に `timeZone` を渡す。** いまは関数の中で `analyticsTimeZone()` を呼んでいるが、
チャンクごとに解決し直すと、走行中に誰かがもう一度タイムゾーンを変えた場合に**チャンクごとに違う境目**で
畳んでしまう。引数で受けて 1 回に固定する（省略時は従来どおり解決するので、既存の呼び出しは変わらない）。

#### 6.2.3 排他 — 定期ロールアップと**同じ鍵**を取る（要件 §6-2）

洗い替えと `analytics.rollup` は、**同じ資源（`analytics` の Core 行）を (site, day) 単位で差し替える。**
別々の鍵にすると、`029` §6.3 が「同じロックに載せることで起きなくなる」と書いた
`replaceCorePoints` の DELETE → INSERT の衝突が、そのまま復活する。

**`runJob` で「記録するジョブ名」と「取る鍵の名前」を分ける。**

```ts
export interface JobTask<TInput = undefined> {
  readonly name: JobName;
  /** 排他に使う鍵。省略すると `name`。**既存のジョブは省略する（挙動が変わらない）** */
  readonly lockName?: JobName;
  run(connection: Connection, input: TInput, job: JobContext): Promise<Readonly<Record<string, unknown>>>;
}
```

* `jobLock.acquire(connection, job.lockName ?? job.name, …)`。`job_runs.job_name` は `job.name` のまま
* 待機枠のゲート（`029` §6.1.6）も鍵の名前で数えるので、**ロールアップと洗い替えの待ちが合算されて 1 本**になる。
  これは正しい（守っている資源は同じ鍵の待ち行列である）
* **起動は `wait: true`（10 秒待つ）。** 定期ロールアップは数秒で終わるので、
  たまたま重なっても待てば取れる。それでも取れなければ `skipped` が記録され、
  画面から**やり直せる**（§6.5 / §7.3）。応答をブロックしないので、待つコストは利用者に見えない
* 洗い替えが鍵を握っている間、定期ロールアップは（待たない設定なので）`skipped` になる。
  **これは 029 の設計どおりの挙動**であり、洗い替えが終われば次の周期で追いつく
  （`scheduledRollupFrom` が最後の**成功**の開始日から最大 7 日さかのぼる）

**洗い替えが 7 日を超えて掛かった場合**、その間に届いた分は定期ロールアップの遡り上限（7 日）を超える。
ただし洗い替えの最後のチャンクが「今日」を含み、その時点までの生ログを畳んでいるので、
取りこぼすのは「洗い替え終了後に届いた分」だけであり、それは 7 日以内に収まる。

#### 6.2.4 実行中に新しいアクセスが届いたとき（要件 §6-3）

**二重に畳むことは起きない。** 理由：

* `replaceCorePoints` は (site, day) ごとに `DELETE`（`source = 'core'`）→ `INSERT` を 1 トランザクションで行う。
  同じ日を何度処理しても行は増えない（`018` §4.1 / `028` §5.3.3）
* 同じ鍵の排他（§6.2.3）により、洗い替えと定期ロールアップが同じ日を同時に触ることがない

**取りこぼしは起きうるが、放置されない。**

| 届いた時点 | 集計値への反映 |
| --- | --- |
| その日のチャンクを処理する前 | そのチャンクに含まれる |
| その日のチャンクを処理したあと（＝実質「今日」だけ） | **含まれない。**次の定期ロールアップ（15 分ごと・最大 7 日さかのぼる）が拾う |

**削除の段と新着の関係。** `DELETE` は 1 文なので単一のスナップショットで判定する。
判定の直後に届いた生ログがある日は「生ログの無い日」として消されうるが、消されるのは**旧境目で畳まれた古い値**であり、
新しく届いた 1 行は次のロールアップで新境目のまま入り直す。**新しいデータは失われない。**

#### 6.2.5 進捗（`job_runs` から見える形）

`029` のままでは、`job_runs` に残るのは「開始した」と「終わった」の 2 点だけである。
洗い替えは長い時間走りうる（要件 §1 が「時間がかかる旨を表示してもよい」と言っているのはそのため）ので、
**チャンクごとに `summary` を更新する。**

```ts
export interface JobContext {
  readonly runId: string;
  /** 途中経過を `job_runs.summary` へ書く。**失敗は握って続ける**（記録できないことと処理できないことは別） */
  report(summary: Readonly<Record<string, unknown>>): Promise<void>;
}
```

* `run-job.ts` が `job.run(connection, input, { runId, report })` の形で渡す。
  第 3 引数なので、**既存の 2 つのジョブは受け取らずにそのまま動く**
* `report` は `jobRunRepository.updateSummary(connection, id, summary)`（`UPDATE job_runs SET summary = $2 WHERE id = $1`）。
  主キー 1 行の更新で、チャンクあたり 1 回
* 失敗は `run-job.ts` 既存の `record()` と同じ扱い（`log.error` に出してジョブの結果は変えない）
* `finishOk` は最後にもう一度 `summary` を書く。**途中経過と最終結果で 2 系統の書き方をしない**

#### 6.2.6 `previousTimeZone` は**記録にしか使わない**。やり直しでは `timeZone` と同じ値にする

やり直し（§6.5 の `POST /analytics/timezone-rebuild`）は「何から変えたか」を知らない。
`system_settings` には**変更後の値しか無く**、変更前の値は監査ログにしか残っていない（§6.4 手順 6）。
ジョブ入力の `previousTimeZone` に何を入れるかを決める。

**決定：やり直しでは `previousTimeZone = timeZone`（そのとき有効な値）にする。**
`summary.previousTimeZone === summary.timeZone` を「**これはやり直しである**」と読み取れる印として使う。

* **記録だけを見て、通常の変更契機とやり直しを区別できる。** `PUT /settings/timezone` から起きた洗い替えは
  必ず `previousTimeZone !== timeZone` である（同じ値なら洗い替えを起こさない。§6.4 手順 2）。
  したがって両者が一致するのは、やり直しから起きたときだけ
* **`null` を入れる案は採らない。** `summary` を読む側が「値が無い」と「同じだった」を区別できず、
  `RebuildInput` の型も `string | null` に緩む。
  `triggeredBy`（`scheduled` / `manual`）は `job_runs` の列にあるが、
  **やり直しも最初の起動もどちらも `manual`** なので、これでは分けられない

**この印を使ってよい理由 ＝ `previousTimeZone` は処理に 1 度も使われない。**

洗い替えの処理（§6.2.1 / §6.2.2）が読むのは `timeZone` だけである。

| 段 | 使う値 |
| --- | --- |
| 範囲の決定（`findOldestAccessAt` の日付化・今日の決定） | `timeZone` |
| ロールアップ（`rollupAnalytics(connection, { from, to, timeZone })`） | `timeZone` |
| 削除（`deleteStalePoints(connection, timeZone)`） | `timeZone` |
| 進捗と結果（`job_runs.summary`） | `timeZone` と `previousTimeZone` |

**`previousTimeZone` は 1 つの分岐にも条件にも入らない。**
旧タイムゾーンで畳まれた値を読み直すことも、旧境目で何かを消すこともない
（消す条件は §5.4 のとおり「**新しい**タイムゾーンで生ログが無い日」だけで、旧境目を参照しない）。
洗い替えは「新しい境目で畳み直し、生ログの無い日を消す」だけの、**現在の状態から決まる冪等な処理**である。

したがって、

* **やり直しで `previousTimeZone === timeZone` になっても、洗い替えの結果は 1 ビットも変わらない**
  （受け入れ条件 #108 の冪等性と矛盾しない。#114 で明示的に検査する）
* **処理に効く値を印に流用していない。** 記録専用の欄を記録のために使っているだけである

> **将来この印が使えなくなる条件を書いておく。** 旧タイムゾーンを処理に使う段
> （例：「旧境目で畳まれた行だけを選んで消す」）を足すと、やり直しで前後が同じ値になることが
> **処理の意味を変える**。そのときはこの印をやめ、`summary` に `trigger: 'update' | 'retry'` のような
> 明示的な欄を足すこと。**印と処理の値を兼ねさせない。**

### 6.3 ソルトの境目が変わる瞬間（要件 §6-4）

`collect.ts` の実装を読むと、変更の瞬間に起きることは次のとおり。

```ts
function dailySalt(day: string): string {
  const existing = salts.get(day);
  if (existing !== undefined) return existing;
  salts.clear();                       // ← 見つからなければ全部捨てる
  const salt = randomBytes(32).toString('hex');
  salts.set(day, salt);
  return salt;
}
```

`saltDay(now)` が返す日付キーが変わると `salts` が miss し、**その場で `clear()` して新しいソルトを作る。**

| 変更の向き | 例（変更の瞬間） | 日付キー | 起きること |
| --- | --- | --- | --- |
| 東へ（UTC → `Asia/Tokyo`） | `2026-09-06T20:00Z` | `2026-09-06` → `2026-09-07` | 新しいキーで miss → 即座に新しいソルト |
| 西へ（UTC → `America/Los_Angeles`） | `2026-09-06T05:00Z` | `2026-09-06` → `2026-09-05` | **過去の日付キー**で miss → 新しいソルト。さらにその日のうちに `2026-09-06` へ戻るとき**もう一度**回る |
| 同じ日付になる場合 | `2026-09-06T12:00Z` に UTC → `Europe/Berlin` | `2026-09-06` のまま | **回らない。**その日は何も起きない |

**したがって、変更した当日の訪問者数・セッション数・直帰率・滞在時間は、実際より多く（悪く）出る。**
同じ訪問者が、ソルトが回る前と後で別のハッシュになるためである。
これは要件 §2.1 が「仕組み上どうにもならない」と整理した制約の、**変更当日版**である。

* **直せない。** 直すにはソルトを保存する必要があり、`018` §3.2 の裁定（保存すると過去に遡って
  同じ人を追跡できる）を覆すことになる。覆さない
* **洗い替えでも直らない。** その日の生ログには、同じ人の 2 通りのハッシュが**すでに記録されている**。
  何度畳み直しても 2 人と数えられる
* **画面で断る。** §7.2 の確認ダイアログに「変更した当日の訪問者数は多めに出ます」を明記する
* **複数プロセスでは、プロセスごとに回るタイミングが最大 30 秒ずれる。** ただし §6.1.3 のとおり
  ソルトはもともとプロセスごとに別なので、新しい種類の壊れ方は生まない
* **`resetDailySalts()` は変えない。** テスト用の入口であり、本番の経路に手を入れない

### 6.4 UseCase

| UseCase 名 | Permission | 入出力 |
| --- | --- | --- |
| `analytics.timeZonePreview` | `system.manage` | `{ timeZone }` → `TimeZoneChangePreview` |
| `analytics.timeZoneUpdate` | `system.manage` | `{ timeZone }` → `{ timeZone, previousTimeZone, rebuildStarted }` |
| `analytics.timeZoneRebuild` | `system.manage` | `{}` → `{ started: boolean }`（やり直し）。**監査ログを残す**（§6.4.1） |

```ts
export interface TimeZoneChangePreview {
  /** 正規化した候補。 */
  readonly timeZone: string;
  /** いま効いている値と、その出所。 */
  readonly currentTimeZone: string;
  readonly currentSource: 'database' | 'environment' | 'default';
  /** 候補が現在値と同じか（同じなら洗い替えは走らない）。 */
  readonly unchanged: boolean;
  /** 洗い替える期間。生ログが無ければ null。 */
  readonly rebuildFrom: string | null;
  readonly rebuildTo: string | null;
  readonly rebuildDays: number;
  /** **失われるもの。出所ごとに分けて返す**（`要件.md` §7-1）。 */
  readonly lostDays: number;        // (サイト, 日) の数
  readonly lostCoreRows: number;    // 消える `source = 'core'` の行数
  readonly lostPluginRows: number;  // 消える `source <> 'core'` の行数
  /** 消える値を入れた Plugin の ID（`source` の値）。導入済み Plugin の数で上限が付く。 */
  readonly lostSources: readonly string[];
  readonly lostSites: number;       // 対象のサイト数
  readonly lostFrom: string | null;  // 消える日の最古
  readonly lostTo: string | null;    // 消える日の最新
}
```

`analytics.timeZoneUpdate` の手順：

1. `canonicalTimeZone` で正規化し、`isSelectableTimeZone` を通らなければ
   `ValidationError('SystemSettings', 'timeZone', 'タイムゾーンを選び直してください。')`
   （**保存を拒否する。**環境変数のように警告して UTC へ落とす扱いにはしない。要件 §5）
2. **洗い替えを走らせるかは「いま効いている値」との比較だけで決める。**
   `previousTimeZone = await resolveAnalyticsTimeZone()` と等しければ `rebuildStarted = false`
   （要件 §5「変えていない保存では洗い替えが走らない」）
3. `systemSettingsRepository.put(tx, SYSTEM_SETTING_KEYS.analyticsTimeZone, timeZone)`。
   **値が同じでも書く。** `system_settings` に行が無く、環境変数と同じ値を選んだ場合に
   出所を「データベース」へ固定するため（以後、環境変数を変えても効かない状態にそろう）。
   値は変わらないので洗い替えは起きない
4. そのプロセスのキャッシュへ即座に反映（§6.1.2）
5. `rebuildStarted` のときだけ `startJobInBackground(TIMEZONE_REBUILD_JOB, { timeZone, previousTimeZone })` を呼び、
   **待たずに**返す
6. 監査ログ：`{ action: 'updated', resourceType: 'system_settings', resourceId: null,
   detail: { setting: 'analytics.time_zone', from: previousTimeZone, to: timeZone } }`
   （既存の `updateSystemSettings` と同じ `action` / `resourceType` を使う。**列挙値を足さない**）

```ts
// application/jobs/run-job.ts
/**
 * 応答を待たせずにジョブを起こす。
 *
 * **要求の接続を使わない。** 自分で `withConnection` を張るので、
 * 応答を返したあとに要求のスコープが閉じても影響を受けない。
 * 例外は握ってログに出す（呼ぶ側は「起こした」ことだけを知る）。
 */
export function startJobInBackground<TInput>(job: JobTask<TInput>, input: TInput): void;
```

> **これは「fire and forget」である。** プロセスが落ちれば止まる。Torifune は
> `instrumentation.ts` で定期実行を持つ常駐サーバーとして動く前提なので採る（`029` §6.1.1）。
> 止まったときの立て直しは `analytics.timeZoneRebuild`（やり直し）で行い、画面に導線を置く（§7.3）。

#### 6.4.1 やり直し（`analytics.timeZoneRebuild`）も監査ログを残す（検証後の裁定）

**セキュリティ検証の指摘。** 兄弟の `analytics.timeZoneUpdate` は `audit:` を持つのに、
やり直しは持っていなかった。やり直しは `system_settings` を書かないが、
**`analytics` から Core と Plugin の行を出所を問わず削除する。**

**追跡がどこにも残らなかった。**

| 残りうる場所 | 実際 |
| --- | --- |
| `audit_logs` | `audit:` が無いので**残らない** |
| `job_runs` | `startJobInBackground` は `AuthorizationContext` を捨てる。そもそも **actor の列が無い**（`021_job_runs.sql`） |
| アプリログ | 誰が起こしたかは出していない |

`system.manage` は**複数人が持ちうる**権限である。
**Plugin の数値を永久に失わせた操作について、誰がやったかが分からない**のは受け入れられない。

```ts
audit: {
  // 既存の `updateSystemSettings` / `timeZoneUpdate` と同じ。**列挙値を足さない**
  action: 'updated',
  resourceType: 'system_settings',
  resourceId: () => null,
  detail: () => ({ setting: SYSTEM_SETTING_KEYS.analyticsTimeZone, rebuild: 'retry' }),
}
```

* **順序は「ジョブ起動が先、監査記録が後」。** `defineUseCase` は `handler` の戻り値を得てから
  `recordAudit` を呼び（`application/authorization/use-case.ts`）、`startJobInBackground` は
  その `handler` の中で走る。**記録が確定してからジョブが始まるのではない。**
  ジョブの完了は待たない——**記録するのは「誰がやり直しを起こしたか」**であって、集計の結果ではない
* **限界：「監査ログが無い ⇒ 走っていない」とは読めない。** `recordAudit` は書き込みの失敗を握って
  `log.error` に落とす（`application/audit.ts`。記録できないことと処理できないことは別、という
  `029` §6.1.5 と同じ立場）。したがって、記録が残っていないのに洗い替えだけが走った状態はありうる。
  **追跡の目的（誰が起こしたかを事後に辿れる）は満たすが、「起きていないことの証明」には使えない。**
  実行そのものの痕跡は `job_runs`（`runner` = `hostname:pid`）に残る
* `detail.rebuild = 'retry'` で、保存に伴う洗い替え（`from` / `to` を持つ）と読み分けられる
* **`detail` にタイムゾーンの値は入れない。** この UseCase の出力は `{ started: boolean }` だけで（§6.4 の表、
  受け入れ条件 #140 / #141）、`detail` から読める値が無い。**入れる必要も無い**——
  やり直しは「**そのとき有効な値で走らせ直す**」操作であって値を決める操作ではなく、
  値そのものは保存経路の監査（`from` / `to`）と `job_runs.summary.timeZone`（§5.5）に残っている
* **この 1 件が、セキュリティ検証 L-1（「API 直叩きに確認ダイアログが無いこと」）を許容できる前提である。**
  確認ダイアログは誤操作を防ぐもので、セキュリティ対策ではない（`06` §37）。
  API を直接叩けば確認は通らない。それを許容できるのは、**事後に「誰が・いつ」を追跡できるとき**に限る。
  監査ログが無いと、この前提が崩れて L-1 は「許容」ではなく「未対処」になる

#### 6.4.2 やり直しでもタイムゾーンを検証する（検証後の裁定）

**セキュリティ検証の指摘。** 保存経路は `canonicalTimeZone` ＋ `isSelectableTimeZone`（一覧に含まれること）を
通すが、**やり直し経路は通らない**。やり直しは `resolveAnalyticsTimeZone()` の値をそのまま使い、
その値は `system_settings` に行が無い環境では `TORIFUNE_TIMEZONE` 由来で、
**検証は `isValidTimeZone` だけ**である（§5.3.1 の実測どおり `+09:00` と `Etc/GMT+5` が通る。
どちらも `Intl.supportedValuesOf('timeZone')` には**無い**）。
その値が削除条件の `AT TIME ZONE` に入る。

* **注入は無い。** バインド値であり、PostgreSQL が解釈できなければ削除の前に落ちる
* **危ないのは「解釈が割れる」場合。** 日付の切り出しは JS 側（`dateInTimeZone` / `todayInTimeZone`）と
  PostgreSQL 側（`AT TIME ZONE`）の両方で行う。両者の解釈が食い違うと、
  **生ログのある日を「無い日」と誤判定して消す**ことが起こりうる。消すのは不可逆である

**やり直し経路でも `isSelectableTimeZone` を確認し、通らなければ `ValidationError`（422）にして走らせない。**

* 保存経路と同じ関数（`selectableTimeZone`）を通す。**入口を 2 つ持たない**
* 落ちるのは「一覧に無い `TORIFUNE_TIMEZONE` を設定したまま、画面で一度も保存していない環境で
  やり直しを叩いた」ときだけ。**そのときは走らせないのが正しい**——
  同じ値で洗い替えを走らせれば、同じ危険が削除にまで及ぶ
* 応答の文言は保存経路と同じ「タイムゾーンを選び直してください。」。
  設定画面から一度保存すれば解消する（保存経路が正規化した値を書くため）

### 6.5 エンドポイント

| メソッド | パス | Permission | 役割 |
| --- | --- | --- | --- |
| `GET` | `/api/v1/settings/timezone?timeZone=<IANA>` | `system.manage` | 変更の影響を数える（**何も変えない**） |
| `PUT` | `/api/v1/settings/timezone` | `system.manage` | 保存して洗い替えを起こす |
| `POST` | `/api/v1/analytics/timezone-rebuild` | `system.manage` | 洗い替えだけをやり直す |

* **`PUT /api/v1/settings`（既存）には足さない**（§4.1）。既存の応答も body も変えない
* **`GET /api/v1/settings`（既存）の応答からも `analyticsTimeZone` を落とす**（検証後の裁定。§6.5.1）
* `GET` を分けるのは、**確認ダイアログを出す前に数える**必要があるから。
  数えるのは「消える行」であり、`PUT` の中で数えて返しても手遅れになる
* `POST /analytics/timezone-rebuild` を分けるのは、要件 §5 の「変えていない保存では洗い替えが走らない」を
  守りながら、**失敗・中断した洗い替えを立て直す経路**を残すため（`要件.md` §7-2。§7.3）。
  body は取らない（範囲は生ログから導く。§6.2.1）。**タイムゾーンは既に保存済みなので、
  再実行は保存し直さない**（`system_settings` に触らず、ジョブだけを起こす）。
  ジョブへ渡す入力は `{ timeZone: 現在有効な値, previousTimeZone: 同じ値 }` で、
  **前後が同じであること自体が「やり直し」の印になる**（§6.2.6）
* 応答：`GET` は `TimeZoneChangePreview`（§6.4。**消える行数を `lostCoreRows` /
  `lostPluginRows` に分けて返す**）、`PUT` は `{ timeZone, previousTimeZone, rebuildStarted }`、
  `POST` は `{ started }`。
  **ジョブの完了は待たない。** 進捗は `GET /api/v1/jobs`（既存）と設定画面から見る
* 3 つとも `defineRoute` の既定に従う（未認証 401 / 権限不足 403 / Rate Limit 既定 / OpenAPI に応答スキーマを宣言）
* `GET` の `timeZone` が不正なら 422（`ValidationError`）。**「不正だから UTC で数えました」という応答を返さない**

#### 6.5.1 `GET /api/v1/settings` は `analyticsTimeZone` を返さない（検証後の裁定）

**セキュリティ検証の指摘。** `getSystemSettings` は `permission: null`（理由「サービス表示名は認証後の
全画面で使う。**秘密の値を含まない**」）で、`GET /api/v1/settings` は **Cookie 無しでも叩ける**。
`SystemSettings` に `analyticsTimeZone` を足したことで、
**インスタンスの運用地域が未認証の 1 リクエストで分かる**ようになった。

**落とす。** 応答から外す。

* **画面はこの API に依存していない。** 設定画面は Server Component から
  `analyticsTimeZoneSetting()`（`application/analytics/timezone.ts`）を直接呼んでおり、
  値と**出所**の両方が要る。この API はそもそも出所を返さないので、使い道が無い
* 変更する側の口（`GET` プレビュー / `PUT`）は `/api/v1/settings/timezone` で、
  どちらも `system.manage` を要求する（§6.5）。**読む必要のある利用者は、そちらから読める**
* **Domain の `SystemSettings` からは外さない。** キャッシュの解決（`toSystemSettings`）に要る。
  外すのは**API の応答**だけである

**やり方：許可リストを Domain の型として持つ（ルートに置かない）。**

初版は「`route.ts` が `{ serviceName, rememberMeEnabled }` を明示的に組み立てる」としていた。
**それでは塞いだのがルート 1 ファイルだけになる**（セキュリティ再検証の指摘）。

* `getSystemSettings`（`permission: null`）と `loadSystemSettings()` は、
  **どちらも `toSystemSettings(...)` の全項目を返したまま**である
* 将来「未認証で読める公開設定」の口をもう 1 つ足す人が、その戻り値をそのまま返せば
  `analyticsTimeZone` はまた未認証へ出る。**1 ファイルを見る静的検査は新しいファイルを見ない**

**認可の文脈を持たない口が、そもそも `analyticsTimeZone` に触れないようにする。**

```ts
// domain/system-settings.ts
/**
 * **未認証で読んでよい項目だけ。**
 *
 * ここへ項目を足すことが「未認証へ公開する」という判断そのものになる。
 * 判断を 1 か所に閉じ込めるための型であって、単なる部分集合ではない。
 */
export interface PublicSystemSettings {
  readonly serviceName: string;
  readonly rememberMeEnabled: boolean;
}
export function toPublicSystemSettings(stored: ReadonlyMap<string, unknown>): PublicSystemSettings;
```

| 関数 | 認可 | 戻り値 |
| --- | --- | --- |
| `getSystemSettings`（UseCase） | `permission: null` | **`PublicSystemSettings`** |
| `loadSystemSettings()`（認可の文脈を持たない読み出し） | 無し | **`PublicSystemSettings`** |
| `toSystemSettings`（Domain の全項目） | — | `SystemSettings`（`analyticsTimeZone` を含む） |

**振る舞いは変わらない。** 現在の呼び出し元はどれも 2 項目しか使っていない。

| 呼び出し元 | 使っている項目 |
| --- | --- |
| `app/layout.tsx` / `ui/layout/app-shell.tsx` | `serviceName` |
| `app/login/page.tsx` | `serviceName` / `rememberMeEnabled` |
| `application/auth/login.ts` | `rememberMeEnabled` |
| `app/settings/page.tsx` → `GeneralSettings` / `AuthSettings` | `serviceName` / `rememberMeEnabled` |

**`analyticsTimeZone` を読むのは `application/analytics/timezone.ts` の 1 か所だけ**で、
そこは `systemSettingsRepository.loadAll` ＋ `toSystemSettings` を直接使っており、
上の 2 つのアクセサを通らない。**API へ出る経路に無い。**

* `route.ts` は UseCase の戻り値をそのまま返してよくなる。
  **許可リストをルートで組み立て直さない**——判断の置き場が 2 か所になると、片方だけ直る
* **(b)（静的検査の対象を広げる）を採らない理由。** 検査は「呼び出し元を全部見る」ことになり、
  新しい書き方（Repository を直接使う等）のたびに追随が要る。
  (a) は**型で落ちる**ので、検査の網羅性に依存しない
* 残す検査は 1 つ。**`SystemSettings`（全項目）を import している製品コードが
  `domain/` と `application/analytics/timezone.ts` だけであること。**
  ファイル名の列挙ではなく、`analyticsTimeZone` に触れる範囲そのものを固定する

**UseCase の `reason` を実態に合わせる。** 現在の
「サービス表示名は認証後の全画面で使う。秘密の値を含まない」は、
`analyticsTimeZone`（インスタンスの運用地域）が戻り値に入った時点で**事実と食い違っていた**。
`PublicSystemSettings` を返す形にしたうえで、**戻り値が公開してよい項目に射影されている**ことを
理由として書く。**`reason` は 1 行に収める**（`route.ts` / UseCase の静的検査が
`reason:` の行を正規表現で見るため、prettier が折り返す長さにすると落ちる）。
理由の全文は直上の JSDoc へ置く。

### 6.6 既存の型・応答への影響

| 対象 | 変更 | 影響 |
| --- | --- | --- |
| `JobStatus.intervalMinutes` | `number` → `number \| null` | `analytics.timezoneRebuild` は周期を持たない。`GET /api/v1/jobs` の応答で `null` が返りうる |
| `listJobStatuses` の `configuredMinutes` | `Record<JobName, number \| null>` | `analytics.timezoneRebuild` は `null` |
| `JOB_LABEL` | 1 件追加 | `'analytics.timezoneRebuild': 'タイムゾーン変更の洗い替え'` |
| `rollupAnalytics` の第 2 引数 | `timeZone?: string` を追加 | 省略時は従来どおり解決する。**既存の呼び出しは変わらない** |
| `analytics-repository.ts` で `access_logs` に触る関数 | 7 → **10**（`findOldestAccessAt` / `summarizeStaleDays` / `deleteStalePoints`） | 下記 |

**`access_logs` を読む関数が 3 つ増える（8 ではなく 10）。**
`infrastructure/analytics-repository.test.ts` の静的検査 `ALLOWED_ACCESS_LOG_READERS` は、
いま次の **7 つ**を許可している。

```
aggregateDailyBreakdown / countAccessSince / deleteAccessLogsOlderThan /
findLatestAccessAt / findSiteByPublicKey / maxOccurredAtBySite / recordAccess
```

ここへ **3 つ**足して **10** になる。

| 足す関数 | なぜ `access_logs` を読む関数として数えられるか | 生ログへの当たり方 |
| --- | --- | --- |
| `findOldestAccessAt` | `SELECT min(occurred_at) FROM access_logs` | `access_logs_occurred_at_idx` の端を 1 回 |
| `summarizeStaleDays` | §5.4 の `stale` CTE が `NOT EXISTS (SELECT 1 FROM access_logs …)` を含む | (サイト, 日) ごとに `access_logs_site_time_idx` の存在判定 1 回 |
| `deleteStalePoints` | 同上（削除の条件が同じ CTE を使う） | 同上 |

**`summarizeStaleDays` / `deleteStalePoints` を数え落としていた**（初版は「7 → 8」と書いていた）。
検査はメソッドの本文に `access_logs` の文字列が出るかを見るので、
「集計するために読む」か「有無を確かめるために読む」かを区別しない。

**3 つとも「期間で集計する読み取り」ではない**ので、`018` §4.1 / `029` §6.4 の原則
（画面・API が期間で集計するために読むのは `analytics` に限る）は保たれる。
存在判定は (サイト, 日) 単位の索引参照であって、生ログを畳む処理ではない。

`GET /api/v1/jobs` は監視から「最後の成功が N 分より古ければ警告」に使う想定（`029` §6.5）で、
その用途は `lastSuccess` を見る。`intervalMinutes` が `null` になりうることは OpenAPI に宣言し、
`docs/` 側にも書く（§12）。

## 7. 画面

### 7.1 設定 → 一般：「基準タイムゾーン」の区画（`ui/settings/timezone-settings.tsx`）

**タブは足さない**（`06` §16）。「一般」タブに、サービス表示名のカードと「定期実行」のカードの間へ置く。

```text
┌─ 基準タイムゾーン ────────────────────────────────┐
│ 集計の「1日の境目」と、画面の「今日」を決めます。   │
│                                                    │
│ 現在の設定  Asia/Tokyo（データベース）             │
│                                                    │
│ [ Asia/Tokyo (GMT+09:00)              ▾ ]          │
│                                                    │
│ [ 変更する ]                                       │
│                                                    │
│ 変更すると、保存済みの集計値を新しい区切りで        │
│ 計算し直します。時間がかかります。進捗は下の        │
│ 「定期実行」で確認できます。                        │
└────────────────────────────────────────────────────┘
```

* **現在値と「出所」を必ず出す。** 裁定 §3.1 で環境変数は初期値だけになったので、
  `データベース` / `環境変数（TORIFUNE_TIMEZONE）` / `既定（UTC）` のどれが効いているかを書かないと、
  運用者は「env を変えたのに効かない」で迷う
* 選択欄は `Select`（既存の primitive）。**`<optgroup>` で地域ごとにまとめる**（`Africa` … `Pacific` の 10 群と、
  先頭に `UTC` だけの群）。418 件を素の `<select>` に平らに並べると探せない。
  ネイティブの `<select>` を使うので、キーボードの先頭一致検索がそのまま効く
* 各項目は `Asia/Tokyo (GMT+09:00)` の形。**オフセットを添える**と、名前を知らなくても目的の地域に辿り着ける
* 選択肢は Server Component（`app/settings/page.tsx`）が `timeZoneOptions(new Date(), [現在値])` で組み立てて渡す。
  ブラウザ側の `Intl` 実装に依存しない（§5.3.2）
* `system.manage` が無ければ**選択欄を `disabled`、ボタンを出さない**（既存 `GeneralSettings` と同じ形）。
  これは表示制御であって認可ではない。認可は UseCase 側（§8）
* 現在値と同じものを選んで押した場合は、確認を出さずに保存して
  「変更はありません。」の Toast を出す（洗い替えは走らない）

### 7.2 確認ダイアログ（要件 §6-7、裁定 §3.3）

「変更する」を押すと、まず `GET /api/v1/settings/timezone?timeZone=…` を呼び、**数えてから**ダイアログを出す。

```text
┌─ 基準タイムゾーンを Asia/Tokyo に変えますか？ ─────────────┐
│ 保存済みの集計値を、新しい 1 日の区切りで計算し直します。   │
│                                                            │
│ ・計算し直す期間：2025-08-01 〜 2026-09-06（402 日）        │
│ ・消える集計値：3 サイト / 120 日分                        │
│   （2025-01-01 〜 2025-07-31。生ログが残っていません）      │
│     Torifune の集計値      8,640 行                        │
│     Plugin が入れた値        420 行                        │
│     （ga-import, ads-import）                              │
│                                                            │
│ 消える期間の数値は戻せません。**Plugin が取り込んだ値も**   │
│ **消えます。**Plugin 側に取り込み直す手段が無ければ、       │
│ その数値は永久に失われます。                               │
│ ページビューは正確に計算し直せますが、訪問者数・セッション  │
│ 数・直帰率・滞在時間は、新しい区切りをまたぐ訪問者が        │
│ 別人として数えられるため、実際より多め（悪め）に出ます。    │
│ 変更した当日の訪問者数も同じ理由で多めに出ます。            │
│                                                            │
│ 計算には時間がかかります。進捗は設定 → 一般の「定期実行」   │
│ で確認できます。                                           │
│                                                            │
│                          [キャンセル] [変更する]           │
└────────────────────────────────────────────────────────────┘
```

* **数え方は §5.4 の SQL の `count` / `min` / `max` 版**（`summarizeStaleDays`）。
  削除と同じ条件を 2 か所に書かない
* 追加の問い合わせは **`GET /api/v1/settings/timezone` の 1 回だけ**で、
  押したときにしか走らない（画面の描画では走らない）
* **消える件数は `source = 'core'` と `source <> 'core'` に分けて出す**（`要件.md` §7-1）。
  合計だけを出すと、**Plugin が取り込んだ値も消えることが読み取れない**。
  `lostPluginRows > 0` のときは、消える値を入れた Plugin の ID（`lostSources`）も並べる
  —— どの Plugin で取り込み直せばよいかが、この画面だけで分かるようにする
* **`lostPluginRows > 0` のときは、Plugin の行を強調して出す。** Core の値は生ログのある期間なら
  作り直せるが、**Plugin の値は本体では作り直せない**（§9.1）
* **消える集計値が 0 件のときも同じダイアログを出す。** 訪問者数の断りは常に要る。
  そのときは「消える集計値：ありません」と書く
* **生ログが 1 行も無い環境では、何も消えない**（§5.4.1）。
  「計算し直す期間：ありません（生ログが残っていません）」「消える集計値：ありません」と出す。
  **Plugin が取り込んだ数値だけを持つサイトは、この画面から失われない**
* **「生ログが残っていない期間」という説明は、§5.4.1 の絞り込みで正確になった。**
  対象は「計測しているサイトの、生ログを消した期間」であり、
  「一度も計測していないサイト」は含まれない。文言をそのまま使ってよい
* プレビューと実際の削除の間に生ログが消える（`pruneOlderThanDays`）と件数はずれる。
  **見積りである**ことをダイアログに書き、実際の件数は `job_runs.summary` の
  `deletedCoreRows` / `deletedPluginRows` で確認する
* `ConfirmDialog` は `message: string` しか取らないので、**任意の `children` を足す**（既存の props は変えない。
  `message` の下、「この操作は取り消せません。」の上に描く）。`028` の公開キー再発行（`ui/analytics/settings-tab.tsx`）と
  同じ部品・同じ作法を使う

### 7.3 「定期実行」の区画と、洗い替えの再実行（`ui/settings/job-status.tsx`）

`要件.md` §7-2 の裁定：**失敗・中断したときのやり直しは、設定画面の再実行ボタンで行う。自動再試行はしない。**

> **自動再試行を入れない理由**（裁定の根拠をここに写しておく）：失敗が繰り返す状況
> （DB が重い、生ログが壊れている等）で**重い集計が延々と走り続ける**。
> しかも 029 の基盤には走行中のジョブを止める手段が無い（`scheduler.stop()` は次回の予約を消すだけで、
> 走っているジョブは止まらない）。**始めるのを人が決める**形にすれば、止めるかどうかも人が決められる。

* 行が 3 つになる。`analytics.timezoneRebuild` の **「間隔」は `—`**（周期を持たない）
* 実行中（`lastRunStatus === 'running'`）は、`summary.completedThrough` から
  「洗い替えを実行中です（2026-03-31 まで完了）」を出す

#### 7.3.1 再実行ボタンを出す条件 ＝ **`analytics.timezoneRebuild` の直近の実行が `ok` でないとき**

| 直近の実行（`lastRun.status`） | ボタン | 添える文言 |
| --- | --- | --- |
| 記録が無い（一度も走っていない） | **出さない** | — |
| `ok` | **出さない** | — |
| `error` | 出す | 「洗い替えが失敗しています。やり直してください。」 |
| `skipped` | 出す | 「他の集計と重なって実行されませんでした。やり直してください。」 |
| `running` | **出す** | 「実行中です（〜まで完了）。応答が無いまま止まっている場合はやり直せます。」 |

* **常時は出さない。** タイムゾーンを変えていないのに押せると、意味のない重い集計を誰でも起こせる。
  「保存」の導線（§7.1）とは別物で、こちらは**立て直しのための口**である
* **`running` のときも出す。** 029 未決 #2 のとおり、**プロセスが実行中に落ちると
  `running` の行が残り続ける**（回収する仕組みは無い）。
  「`running` なら隠す」にすると、その状態でボタンが**永久に出なくなる**。
  実行中に押しても壊れないので（§7.3.2）、隠すより出すほうが安全側に倒れる
* `system.manage` を持つときだけ描く（区画自体がそもそもそう）。**表示制御であって認可ではない**（§8）
* 押すと `POST /api/v1/analytics/timezone-rebuild`（§6.5）。
  **タイムゾーンは既に保存済みなので、確認ダイアログは出さない。**
  §7.2 の確認は「これから失われるものを承知するか」を問うもので、
  **その承知はすでに取れており、消える対象も同じ**（同じ条件で冪等に走る）
* 応答は `{ started: true }` だけを返す。結果はこの表の行がそのまま更新される（画面を再読み込みして見る）

#### 7.3.2 走行中に押されたときの挙動（実物で確認）

**029 の排他がそのまま効き、`skipped` が 1 行記録されて何も起きない。**
`run-job.ts` / `job-lock.ts` を読むと、次の順で進む。

1. `runJob` が `jobLock.acquire(connection, 'analytics.rollup', { waitMs: 10_000 })` を呼ぶ
   （鍵は `lockName`。§6.2.3）
2. **同じプロセスに既に待機中の呼び出しがあれば**、接続を取らずに即座に `{ ok: false, reason: 'busy' }`
   （`029` §6.1.6 の待機枠ゲート。ジョブごと 1 本）
3. そうでなければ専用接続を 1 本 pin し、`SET LOCAL lock_timeout = '10000ms'` の下で
   `pg_advisory_lock` を待つ。取れなければ `55P03` → `busy`
4. `busy` なら `jobRunRepository.insertSkipped` で `status = 'skipped'` の行を 1 つ入れ、
   **ジョブ関数を呼ばずに**戻る

したがって、

* **二重に走らない。** 洗い替えが 2 つ同時に `analytics` を書き換えることはない
* **接続を長く占有しない。** 待つのは最大 10 秒、待機枠はジョブごと 1 本
* `job_runs` に `skipped` が 1 行増える。**これは雑音ではなく答えである**
  （「押したが、他が動いていたので何もしなかった」が記録に残る）。
  画面は次の再読み込みでその行を「他の集計と重なって実行されませんでした」として出す
* 定期ロールアップと重なった場合も同じ。10 秒待てばたいてい取れる（ロールアップは最大 7 日ぶんで短い）

**待たずに（`wait: false`）起こす選択は採らない。** 15 分ごとの定期ロールアップとたまたま重なるだけで
`skipped` になり、運用者が何度も押すことになる。`POST /api/v1/analytics/rollup` が
`wait: true` にしているのと同じ判断（`029` §6.3）。

#### 7.3.3 そのほか

* 既存の注記（「複数プロセスで動かしている場合、『次回』はこの画面を返したプロセスの予定です」）はそのまま
* 洗い替えが `ok` で終わったあとは、行が「前回の成功」を示すだけの読み取り専用の行に戻る

### 7.4 アナリティクス画面への影響

#### 7.4.1 「当日」は矛盾しない（要件 §6-7 の確認）

`030` §13-3 のとおり、**当日タブは `analytics` を読まない。生ログだけを見る。**
`getTodayAnalytics` は `resolveAnalyticsTimeZone()` で決めた `date` を `from = to` として
`aggregateDailyBreakdown` に渡し、同じタイムゾーンで日境界を切る。

したがって、タイムゾーンを変えた瞬間から**当日は新しい境目で自己完結して計算される**。
`analytics` に旧境目で畳まれた「本日」の行が残っていても、当日タブはそれを読まないので**矛盾しない**。
`030` の「当日 = 生ログ、それ以外 = 確定した集計値」という 1 文はそのまま成り立つ。

ただし **`date` そのものは動きうる**（下記）。当日タブが指す「今日」が別の日になることはある。

#### 7.4.2 `presetRange` と「当日」「前月」の見え方（要件 §6-8）

`todayInTimeZone` の結果が変わると、`presetRange` の窓が丸ごとずれる。
`2026-09-01T02:00Z` に `UTC` から変えた場合を具体例で示す。

| 変更先 | その瞬間の「今日」 | `当日` | `month` | `prev-month` | `7d` |
| --- | --- | --- | --- | --- | --- |
| （変更前）`UTC` | `2026-09-01` | 2026-09-01 | **`null`（空状態）** | 2026-08-01 〜 2026-08-31 | 2026-08-25 〜 2026-08-31 |
| `Asia/Tokyo`（+9） | `2026-09-01` | 2026-09-01 | `null` | 2026-08-01 〜 2026-08-31 | 変わらず |
| `America/Los_Angeles`（−8） | **`2026-08-31`** | 2026-08-31 | 2026-08-01 〜 2026-08-30 | **2026-07-01 〜 2026-07-31** | 2026-08-24 〜 2026-08-30 |

**「前月」は一月まるごと別の月に変わりうる。** 月初（および月初の前日）にタイムゾーンを西へ変えると、
`prev-month` が 8 月から 7 月へ飛ぶ。`presetRange` の実装は正しく、
入力の `today` が動いたことがそのまま出ているだけである。**`presetRange` は変えない。**

同様に、`month` は今日が月の 1 日のとき `null`（空状態）を返す（`030` §7.2）。
東へ変えて今日が 2 日になれば `null` でなくなり、西へ変えて今日が前月末になれば前月の期間が出る。
**これも仕様どおりの挙動**で、期間の表示（`YYYY-MM-DD 〜 YYYY-MM-DD`）に出るので読み取れる。

#### 7.4.3 洗い替え中の見え方

洗い替えは古い日から進むので、**終わるまでの間、直近の日は旧境目の値のまま**である。
一方、画面の窓（`presetRange`）は**変更した瞬間から新しい `today`** で計算される。
そのため、洗い替えの最中は「窓は新しい、値は古い」という状態になりうる。

* 一時的であり、洗い替えが終われば解消する
* 進行中であることは 設定 → 一般の「定期実行」で分かる（§7.3）
* **アナリティクス画面に専用のバナーは出さない。** `030` が入れた当日バナー・空状態の案内に加えて
  もう 1 つ状態表示を増やすほどの頻度（タイムゾーンの変更は導入時にほぼ 1 回）ではない。
  §7.2 のダイアログで「時間がかかること」と「どこで進捗を見るか」を先に伝える

アナリティクス → 設定タブの「日付の区切り」の行（`029` §7.1.2）は `analyticsTimeZone()` 由来なので、
`resolveAnalyticsTimeZone()` に置き換えるだけで**自動的に新しい値を表示する**。

## 8. 権限（Permission）

**新しい Permission を作らない。**

| 操作 | Permission | 根拠 |
| --- | --- | --- |
| 基準タイムゾーンの**表示**（設定画面・アナリティクス設定タブ） | 不要 | 現在も `analyticsTimeZone()` の値をアナリティクス設定タブに出している（`029` §7.1.2）。秘密ではない |
| `GET /api/v1/settings/timezone`（プレビュー） | `system.manage` | 集計値の件数を数える。変更の前段であり、変更と同じ水準に置く |
| `PUT /api/v1/settings/timezone`（保存＋洗い替え） | `system.manage` | `updateSystemSettings` と同じ。システム全体に効く設定 |
| `POST /api/v1/analytics/timezone-rebuild`（やり直し） | `system.manage` | 集計値を消しうる。参照（`analytics.read`）より強い権限を要求する |
| 洗い替えの実行状況（設定画面の「定期実行」） | `system.manage` | `listJobStatuses`（`029` §6.6）のまま |

* **`POST /analytics/rollup`（`analytics.read`）に相乗りさせない。** そちらは閲覧者ロールも持つ権限であり
  （`migrations/014_analytics.sql`）、集計値を**消す**操作をその水準に置いてはいけない。
  `pruneOlderThanDays` が `system.manage` を要求しているのと同じ判断（`029` §6.3）
* 洗い替えジョブそのものは認可の外（`029` §6.6 と同じ。本体が自分の処理として走らせる）
* 未認証は 401、権限不足は 403。`defineRoute` / `defineUseCase` の既定に乗る

## 9. Plugin API への影響

2 つの変化がある。

1. **`data.analytics.record` で書いた値が、本体の操作で消えうる**ようになる（§9.1）。
   既存の型・関数の**形**は変わらないが、**書いたデータの寿命の保証**が変わる
2. **それを知らせるイベント `analytics.purged` を足す**（§9.3）。
   `packages/plugin-api` に**本設計で初めて差分が出る**

**`PLUGIN_API_VERSION` は 1 のまま**（§9.1.3 / §9.3.3）。
既存の型・関数・Payload は 1 つも削っておらず、狭めてもいない。足しただけである。

### 9.1 `analytics.record` で Plugin が書いた値も削除の対象にする（`要件.md` §7-1 の裁定）

#### 9.1.1 本設計は当初「消さない」と判断した（その理由を残す）

**設計の初版では `source <> 'core'` の行に一切触らないことにしていた。** 理由は次の 3 つだった。

1. **Torifune の境目で畳まれた値ではない。** Plugin は外部サービスから取り込んだ値を、
   その**サービス側の暦の日付**で `metricDate` に入れている（`018` §4.2）。
   Torifune の基準タイムゾーンはその日付の決定に関与していない。
   洗い替えの目的は「本体が畳んだ値を新しい境目にそろえる」ことなので、対象にならない
2. **本体には再計算する材料が無い。** Core の値は `access_logs` から作り直せるが、
   Plugin の値の元データは本体の中に無い。**消せば二度と戻らない**
3. **本体の操作で Plugin のデータを消さない。** `01_アーキテクチャ設計.md` の
   「Plugin は本体の内部 DB 構造に直接依存しない」の裏返しとして、
   本体も Plugin のデータを自分の都合で消すべきではない。`replaceCorePoints` が
   `source <> 'core'` に触らないのも同じ理由（`028` §5.3.3）

#### 9.1.2 ユーザーはこの理由を承知のうえで「消す」と裁定した

**上の 3 点はユーザーへ提示済みである。** そのうえで `要件.md` §7-1 は、
**裁定 §3.3 を字義どおり一律に適用する**（洗い替え後の `analytics` には生ログのある期間だけが残る）と決めた。
**この設計はそれに従う**（§5.4 の `DELETE` は `source` で絞らない）。

理由の記述を消さずに残すのは、後から読む人が
**「帰結を承知のうえで一律適用が選ばれた」**ことを読み取れるようにするためである。
「気づかずに消す設計になった」のではない。

裁定を支える側の理屈も書いておく。**混在した `analytics` は誰も説明できない。**
Core だけを新しい境目にそろえ、Plugin の行だけ旧来の日付のまま残すと、
同じ画面の同じ日の数字が**出所によって別の 1 日**を指すことになる。
「`analytics` に残っているのは生ログのある期間だけ」という 1 文で言い切れる状態のほうが、
運用上の説明可能性は高い。

#### 9.1.3 破壊的変更にあたるか ＝ **あたらない。`PLUGIN_API_VERSION` は 1 のまま上げない**

判断基準は `010-plugin-api/設計.md` §9（＝ `07_開発者向けガイド.md` §47）の列挙である。

| 基準 | 本件 |
| --- | --- |
| 既存の関数・プロパティを削除する | 削除していない |
| 引数を増やす（省略可能を除く） | 増やしていない |
| 戻り値の型を狭める | 狭めていない |
| Event の Payload から項目を削除する・型を変える | 変えていない（`analytics.rolledUp` の形はそのまま） |
| Extension Point を削除する | 削除していない |
| Manifest の必須項目を増やす | 増やしていない |

**どれにも当たらない。** `record(point)` の引数・意味・成否は 1 つも変わらず、
呼んだ直後に `list` で読み返せることも変わらない。

**上げても意味が無い、というのが本当の理由である。**

> **訂正（検証後）。** 本設計の初版はここに「`SUPPORTED_API_VERSIONS` は `[1]` なので、
> 2 へ上げると既存の Plugin が一律に導入できなくなる」と書いていた。**これは事実として誤りである。**
> `packages/plugin-api/src/version.ts` の `SUPPORTED_API_VERSIONS` は `PLUGIN_API_VERSION` とは
> **独立した定数**で、`[1, 2]` にすれば `apiVersion: 1` の Plugin はそのまま導入できる。
> **結論（上げない）は変わらないが、理由を差し替える。**

**版数は「Plugin が何を期待してよいか」の記述子であって、
運用者が起こすデータ寿命の変化を伝える器ではない。**

* `apiVersion: 1` を宣言した Plugin と `apiVersion: 2` を宣言した Plugin は、
  **本設計に関してまったく同じ扱いを受ける。** 削除はどちらの行にも等しく起きる。
  版数で分岐する挙動が 1 つも無いのだから、**上げても誰にも何も伝わらない**
* 版数を上げることで Plugin 作者が受け取れるのは「何かが変わったらしい」という信号だけで、
  **何が変わったかは変更履歴を読みに行かないと分からない。** 既に出荷され、
  誰も更新していない Plugin には届かない
* **伝達手段としては `analytics.purged`（§9.3）が正しい。** 版数の変化は「作者がいつか読む」ものだが、
  イベントは「動いている Plugin が、実際に消えたその瞬間に、消えた範囲つきで」受け取る。
  伝えたい事実（**このサイトのこの期間の値が消えた**）を、行動できる形で運べるのはイベントだけである

**§9.3 のイベント追加も破壊的変更ではない**（`010` §9「足すことは破壊的変更ではない」。§9.3.3）。
したがって本設計全体で `PLUGIN_API_VERSION` は **1 のまま**である。

#### 9.1.4 それでも Plugin 作者に伝えるべき事実（文書で伝える。**プログラムへは §9.3 で伝える**）

形式的な基準に当たらないことと、Plugin 作者にとってどうでもよいことは別である。
**次の 1 文が成り立たなくなる**ので、文書を改訂する（§12）。

> `030` §9.0（同じ 1 文が `018` §6 の 2026-09-05 追記にもある）:
> 「**書いた値は失われない。** `analytics` に入り、API からも翌日以降の画面からも読める」

改訂後に伝えること：

* **運用者が基準タイムゾーンを変えると、生ログが残っていない期間の集計値は
  出所を問わず消える**（`source <> 'core'` を含む）
* **本体に取り込み直す手段は無い。** 取り込み直せるかは Plugin 側の実装しだいであり、
  取り込み直せなければ**永久に失われる**
* **勝手には起きない。** `system.manage` を持つ運用者が、消える件数（`source` ごとの内訳と、
  どの Plugin の値かの一覧）を見たうえで確認ダイアログに答えたときだけ起きる（§7.2）。
  操作は監査ログに残る（§6.4）
* 実際に消した件数は `job_runs.summary` の `deletedPluginRows` に残る（§5.5）

書き足す先は `018-analytics/設計.md` §6（Plugin から）と `030-analytics-today/設計.md` §9.0（§12）。
`docs/Plugin開発ガイド.md` は Data API の `analytics` を扱っていないので、そちらには足さない。

> **文書だけでは足りない。** ここに書けるのは**人**への伝達であり、
> **既に出荷され、誰も更新していない Plugin には届かない**。
> 動いているプログラムへ伝える手段は §9.3 の `analytics.purged` である。

### 9.2 Plugin から見える変化

* Plugin は `analyticsTimeZone()` を呼べない（Application の内部関数であり、Plugin API に出していない）。
  **出さない。** 出すと Plugin が本体の境目に依存し始める
* Plugin からのジョブ登録は無い（`029` §9 / §11 #6 のまま）。`analytics.timezoneRebuild` は Core のジョブである
* `analytics.rolledUp` イベントは洗い替えでもチャンクごとに発火する（`rollupAnalytics` の中の `emit`）。
  ペイロード `{ from, to, points }` の形は変えない。**Plugin から見ると「範囲を指定したロールアップが
  何回か走った」のと区別が付かない**——これは既存の契約どおりで、区別する必要も無い

### 9.3 削除を Plugin へ知らせる ＝ `analytics.purged` を足す（検証後の裁定）

**責務境界の検証の指摘。** 削除の段は `log.info` を出すだけで、イベントを 1 つも発火していなかった。
「◯◯日まで取り込み済み」という状態を持つ Plugin は、**取り込み済みだと信じたまま行が消えた状態**になり、
二度と再取得しない。**本体の文書を改訂しても、既に出荷済みの Plugin には届かない。**
§9.1.4 で「文書で伝える」と決めたのは**人**への伝達であって、**プログラムへの伝達ではなかった。**

#### 9.3.1 イベントの形

```ts
// packages/plugin-api/src/events.ts
export const CORE_EVENTS = [ …既存…, 'analytics.rolledUp', 'analytics.purged' ] as const;

/**
 * 基準タイムゾーンの変更に伴う洗い替えで、集計値を消したとき（032-timezone-setting）。
 *
 * **消えたのは「その日に生ログが 1 行も無い (サイト, 日)」の行**で、出所を問わない。
 * 自分の Plugin が `data.analytics.record` で入れた値も含まれる。
 * **本体には取り込み直す手段が無い。** 必要なら Plugin 側で再取得すること。
 */
export interface AnalyticsPurgedEventPayload {
  /** 消す根拠になった、新しい基準タイムゾーン（IANA 名）。 */
  readonly timeZone: string;
  /** 消した集計値の総行数（出所を問わない）。 */
  readonly rows: number;
  /** サイトごとの、消えた範囲。 */
  readonly sites: readonly {
    readonly siteId: string;
    /** 消えた `metric_date` の最古・最新（`YYYY-MM-DD`）。 */
    readonly from: string;
    readonly to: string;
    readonly rows: number;
    /** 消えた行の `source`（Core の分は `'core'`）。**自分の値が消えたかをここで判定できる。** */
    readonly sources: readonly string[];
  }[];
}
```

**この 4 つを載せる理由**（Plugin が「再取得すべきか」をこれだけで決められること）：

| 項目 | 無いと何ができなくなるか |
| --- | --- |
| `sites[].siteId` | どのサイトを取り直せばよいか分からない |
| `sites[].from` / `to` | 取り直す期間が決められない。全期間を取り直すしかなくなる |
| `sites[].sources` | **自分の値が消えたのかが分からない。** 消えた後なので `data.analytics.list` で確かめようがない（行が無い）。これが無いと、無関係な Plugin まで毎回フル再取得する |
| `timeZone` | 取り直した値をどの日付で入れ直せばよいかの手掛かり（外部サービス側の暦との突き合わせ） |

**集計値そのものは載せない。** 量が読めない（`analytics.rolledUp` と同じ立場。`018` §6）。
**`from` 〜 `to` の日がすべて消えたとは限らない**（そのサイトの生ログに欠けがあれば飛び地になる）。
正確な現況は `data.analytics.list` で引き直す——これも `rolledUp` と同じ作法である。

#### 9.3.2 発火の位置と回数 ＝ **削除の後に 1 回だけ**

* **削除が成功したあと**（§6.2.2 手順 5）。失敗すればジョブごと落ちるので、そのときは発火しない
* **1 回だけ。サイトごとには発火しない。** `018` §4.1 が `analytics.rolledUp` について
  「1 アクセスごとではなく、**集計が済んだ単位で 1 回だけ**知らせる」と決めた立場に合わせる。
  削除は洗い替え 1 回につき 1 回の操作なので、単位は「洗い替え 1 回」である。
  サイトごとに発火すると、遅い Plugin のハンドラがサイト数だけ直列に走る
* **1 行も消えなかったときは発火しない。** 起きていないことを知らせない
  （毎回のタイムゾーン変更で全 Plugin を叩き起こさない）
* ハンドラの失敗は `emit` が握る（`application/events.ts`）。**洗い替えを Plugin の不具合で落とさない**
* `emit` は Webhook の予約も行うので、`analytics.purged` は **Webhook でも受け取れる**
  （`CORE_EVENTS` が `webhook-use-cases.ts` の `CORE_EVENT_NAMES` に入る）。
  運用者が外部へ通知を飛ばせるのは副次的な利点で、狙って足すものではないが、妨げる理由も無い

#### 9.3.3 `packages/plugin-api` の差分と版数

**本設計で初めて `packages/plugin-api` に差分が出る**（それまではゼロだった）。

* `CORE_EVENTS` に `'analytics.purged'` を足す
* `AnalyticsPurgedEventPayload` を足し、`CoreEventPayloads` に対応を足す
* `index.ts` から両方を export する

**`PLUGIN_API_VERSION` は 1 のまま。** `010-plugin-api/設計.md` §9 は破壊的変更を
「削除する／引数を増やす／戻り値の型を狭める／**Payload から項目を削除する・型を変える**／
Extension Point を削除する／Manifest の必須項目を増やす」と定めており、
**イベントを 1 つ足すことはどれにも当たらない**（同 §9「足すことは破壊的変更ではない」）。

* 既存の Payload は 1 つも変えていない
* `CoreEventName` に名前が 1 つ増えるのは**共用体の拡張**であり、既存の `subscribe('site.created', …)` は
  そのまま型が付く。Plugin 側で `CoreEventName` を網羅した `switch` を書いていれば
  `default` の分岐が増えるだけで、`exhaustive` を要求する書き方をしていても
  **Plugin は自分がビルドした時点の型で閉じている**（`packages/plugin-api` は Plugin 側の依存）
* 購読していない Plugin には何も起きない
