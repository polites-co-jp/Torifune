### 確定事項（設計書・要件から。プランで蒸し返さない）

* 同期の `analyticsTimeZone()` を**残す**。呼んでよいのは `collect.ts` の `saltDay` **だけ**。他はすべて非同期の `resolveAnalyticsTimeZone()`（§6.1.1）
* キャッシュは `processState('analytics.time-zone', …)`。**TTL 30 秒の pull だけ**。`LISTEN` / `NOTIFY` も共有メモリも入れない（§6.1.2 / §6.1.3）
* 洗い替えは `analytics.timezoneRebuild` ジョブ。**周期を持たない**（`bootScheduler` に載せない）。排他は `analytics.rollup` と**同じ鍵**（§6.2 / §6.2.3）
* **削除は必ず最後**。30 日ずつのチャンクが全部終わってから 1 回だけ（§6.2.2）
* 消す条件は 2 段。**(1) サイトで絞る**——`access_logs` を 1 行でも持つサイトだけを母集合にする（**追加 A**。§5.4.1）。**(2) その中では出所で絞らない**——「その (サイト, 日) に**新しいタイムゾーンで見て**生ログが 1 行も無い」なら `source <> 'core'` も消える（要件 §7-1 / §5.4）
* **削除の実績は `DELETE … RETURNING` を集約した 1 文で数える**（§5.4）。削除の直前に `summarizeStaleDays` を呼び直さない（数えた瞬間と消した瞬間が別のスナップショットになるため）。プレビューは**保存前の見積り**、`deleteStalePoints` の戻り値は**事後の実績**
* **1 行でも消したら `analytics.purged` を削除の後に 1 回だけ発火する**（**追加 B**。§9.3.2）。サイトごとには発火しない。0 件なら発火しない
* **やり直し（`POST /analytics/timezone-rebuild`）も監査ログを残す**（**追加 D**。§6.4.1）。`detail.rebuild = 'retry'`。列挙値は足さない
* **やり直し経路でも `isSelectableTimeZone` を通す**（**追加 E**。§6.4.2）。通らなければ 422 で、ジョブを起こさない
* **`GET /api/v1/settings` の応答は許可リストで組み立てる**（**追加 F**。§6.5.1）。`analyticsTimeZone` は載せない。**Domain の `SystemSettings` からは外さない**（キャッシュの解決に要る）
* 新しい Permission を作らない。3 つの口とも `system.manage`（§8）
* **マイグレーションを追加しない。索引も足さない**（§5.1）
* `domain/analytics/day.ts` は 1 文字も変えない（§4）
* `packages/plugin-api` は **`analytics.purged` の追加ぶんだけ**差分が出る（`CORE_EVENTS` / Payload / export の 3 点）。**既存の型・関数は 1 つも変えず、`PLUGIN_API_VERSION` は 1 のまま**（§9.1.3 / §9.3.3）
* `listTimeZones()` は `['UTC', ...Intl.supportedValuesOf('timeZone')]`。保存する値は**正規化後**で、オフセット表記は保存を拒否する（§5.3）
* `SystemSettings.analyticsTimeZone` の既定は **`null`（未設定）**。`'UTC'` にしない（§5.2）
* 失敗・中断のやり直しは**設定画面の再実行ボタン**。自動再試行は入れない（要件 §7-2 / §7.3）

## 7. リスクと注意点

1. **`analyticsTimeZone()` の移行漏れが最大のリスク。**
   移行し忘れたプロセス・経路だけが古い境目で動き、**「プロセスによって集計日が違う」**という、
   ログにも例外にも出ない壊れ方になる。実行時テストでは再現しにくい。
   → **T9 の静的検査 (a)（同期版を import してよいのは `collect.ts` だけ）で入口を閉じる。**
   併せて (d)（8 ファイルが非同期版を含む）で検査の空振りを防ぐ。`await` の付け忘れは `pnpm typecheck` が捕まえる
   （`Promise<string>` を `string` の引数へ渡そうとして落ちる）。**この 3 段が揃うまで T9 を終わりにしない**

2. **E2E の `GET /api/v1/auth/csrf` の Rate Limit（300 回/60 秒、`operationId:IP`）に余裕が無い。**
   `apps/web/e2e/` の**全ファイルが 1 つのバケツを共有**しており、030 でサイト作成数を削ったばかりである
   （`e2e/analytics.spec.ts` L1757〜 の注記）。
   → **新しい E2E は 1 ファイルに閉じ、追加の csrf を 8 回以内に収める。**
   具体的には (a) サイトは 1 つだけ作る、(b) Plugin の集計値と `job_runs` の行は `withDatabase` で直接入れる（csrf 0 回）、
   (c) #81〜#84 は 1 本のテストにまとめる、(d) 1 つのテストの中で取った token を複数の要求で使い回す。
   **T14 / T18 の完了条件に「`pnpm test:e2e` 全件」を置き、429 が出たらテストを足すのではなく削る**

3. **E2E の前提が「画面設定 > 環境変数」で変わる。**
   `playwright.config.ts` は `TORIFUNE_TIMEZONE: 'Asia/Tokyo'` を渡しており、`e2e/jobs.spec.ts` と
   `e2e/analytics.spec.ts` は `Asia/Tokyo` で「今日」を組み立てている。
   **画面から保存すると `system_settings` の値が勝ち、`global-setup` はテスト実行のたびにしか消さない**ため、
   同じ実行の後続ファイルに効き続ける。
   → 3 段で守る。
   (a) 新しい E2E をファイル名 `settings-timezone.spec.ts` に置く（辞書順で `analytics` / `jobs` / `responsive` / `settings-tabs` より**後**）。
   (b) **`test.afterAll` で必ず `Asia/Tokyo` へ戻す**（`settings-tabs.spec.ts` が表示名を戻しているのと同じ作法）。
   (c) 後続に走るファイル（`settings.spec.ts` / `sites.spec.ts` / `smoke` / `social` / `ui-shell` / `z-rate-limit`）に
   **集計値・日付に依存する検査が無いこと**は確認済み（§1 の表）。この前提が崩れたら (a) の位置を見直す。
   加えて、洗い替えが `analytics.rollup` の鍵を握るため、**その間 1 分周期の定期ロールアップが `skipped` になる。**
   `settings-tabs.spec.ts` の「60 秒以内に `ok`」は先に走るので影響しないが、**E2E の実行順が変わると壊れる**

4. **`ALLOWED_ACCESS_LOG_READERS` が 7 → 10 になる**（初版の設計 §6.6 は「8」。**指摘して訂正済み**。#111）。
   `summarizeStaleDays` と `deleteStalePoints` は `NOT EXISTS (SELECT 1 FROM access_logs …)` を含むため、
   静的検査の対象に入る。**「増やす方向に動かさない」と書かれた一覧を 3 つ増やす**ので、

   走るのは `system.manage` の操作と洗い替えの最後だけ）。**029 §6.4 への追記も「10」で書く**（T19）

5. **`instrumentation.ts` に静的 import を書くと Edge バンドルに `pg` が入る。**

   → T10 で暖機も**動的 import・`NEXT_RUNTIME` の判定の中**に置き、静的検査を 2 件足す

6. **`JOB_NAMES` を 3 件にした瞬間、`Record<JobName, …>` の 2 箇所が型検査で落ちる**
   （`JOB_LABEL` と `configuredMinutes`）。これは**望ましい**（埋め忘れを型が捕まえる）。

   「2 件」という**文言**が古くなる。T4 で同じコミットで直す

   → #39〜#47 は**ジョブ本体と `runJob` を直接呼ぶ**テストで見る。UseCase 側（#56 / #58）だけを

   `processState` は `globalThis` に置かれ、Vitest の同一プロセス内で共有される。

   今回は分割しない。**サイトごとに分ける改善は、行数が問題になったときに根拠を持って入れる**

10. **プレビューと実際の削除で件数がずれうる**（間に `pruneOlderThanDays` が走る等）。
    ダイアログに「見積り」と書き、実績は `job_runs.summary` の `deletedCoreRows` / `deletedPluginRows` で見る（設計 §7.2）

11. **洗い替え後も訪問者数・セッション数・直帰率・滞在時間は完全には直らない**（要件 §2.1、設計 §6.3）。
    仕組み上どうにもならない。**直すために `018` §3.2 の裁定（ソルトを保存しない）を覆さない。**
    §7.2 のダイアログで断る（#76）

12. **【実測で判明】Playwright は `webServer` を起動してから `globalSetup` を走らせる。**
    この順序のせいで、**中断した実行が `system_settings` に残した基準タイムゾーンを、
    次の実行のサーバー起動時の暖機（T10）が先に掴む。** `globalSetup` がその行を消しても、
    **TTL 30 秒の間はプロセス内のキャッシュが古い値を返し続ける**ため、
    **その実行の最初に走る spec（`analytics.spec.ts`）だけが別の境目で動く。**

    実際にこれで `analytics.spec.ts` の 5 件が落ちた。**根本原因は §7 #3 の復旧が失敗していたこと**
    （`test.afterAll` の `PUT` が CSRF で 403 になり、値が残留した）。
    **`GET /api/v1/auth/csrf` は呼ぶたびに新しいトークンを生成して Cookie に置く**ので、
    別のコンテキストで取ったトークンは Cookie と一致しない。

    → 2 段で守る。
    (a) **トークンは、それを使うコンテキストから取り、そのコンテキストを通しで使う**
    （`test.afterAll` の復旧も同じ `adminRequest` から出す）。
    (b) **復旧の応答が 200 であることを `expect` で確かめる。**
    黙って失敗させると、壊れるのは**次の実行の別のファイル**になり、原因に辿り着くのが難しい。

    残留が疑われるときの回復手順は「`system_settings` の `analytics.time_zone` を消して
    **サーバーを再起動する**」（行を消すだけでは TTL のぶん古い値が残る）。
