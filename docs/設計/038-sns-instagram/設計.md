# 038 Instagram 配信 Plugin（`plugins/sns-instagram`） 設計

> **035 が作った拡張点 `social` の 2 つ目の実利用者**（1 つ目は `036` Bluesky）。
> 本設計は `docs/設計/035-social-publishing/設計.md` §13「038 `sns-instagram`」の骨子を具体化する。
> **Core（`apps/web` / `packages/plugin-api` / `migrations`）には 1 行も足さない。**
>
> この Plugin は `035` の口のうち、**`036` が使わなかった 3 つを初めて使う**：
> `limits.mediaRequired`（媒体が必須）、`rotatedCredential`（資格情報の書き戻し）、
> **`manual()` を実装しない**（手動投稿を Core に断らせる）。

## 1. 目的

Torifune に登録された SNS 投稿を、**Instagram（Graph API の Content Publishing）へ実際に配信する。**

`035` は配信の駆動・再試行・記録・画面を Core に作り、`036` が Bluesky で「Core の口だけで Plugin が書ける」ことを示した。
Instagram は Bluesky と事情が大きく違い、**`036` が踏まなかった道**を踏む：

| 事情 | Bluesky（036） | Instagram（本設計） |
| --- | --- | --- |
| 媒体 | 任意 | **必須**（画像か動画が無い投稿は作れない） |
| 媒体の渡し方 | Plugin が取得してアップロード | **Instagram が公開 URL から取りに来る**（Torifune は取りに行かない） |
| 送信の段数 | `createRecord` の 1 回 | **container 作成 → 処理待ち（ポーリング）→ `media_publish`** の 2 段 |
| 資格情報 | App Password（固定） | **long-lived token（60 日で失効）**。延長して書き戻す必要がある |
| 手動投稿 | Web Intent がある | **無い** |

この Plugin が満たすべきことは **`publish()` の 1 つだけ**である：
1 回の呼び出しで 1 件を Instagram へ投稿し、結果を返す。必要ならトークンを延ばして返す。

`manual()` は**実装しない**（§9.3）。それ以外（予約・排他・着手印・再試行・記録・イベント・画面）は**すべて Core にある**。

## 3. スコープ

### 3.1 やること

* `plugins/sns-instagram/` を新設する（`plugin.json` / `index.ts` / publisher / Graph API の呼び出し / キャプションの数え方 / トークンの期限の判定 / `README.md`）
* `provider: 'instagram'` の publisher を `context.social.registerPublisher()` で登録する
* `credentialFields`：`igUserId`（text）/ `accessToken`（secret）/ `accessTokenExpiresAt`（text）（§5.1。**3 つ目は `035` §13 の骨子に無い**。§5.2）
* `limits: { bodyMaxLength: 2200, mediaRequired: true, mediaMax: 10 }` と `validate()`（ハッシュタグ数・メンション数・`link`・`providerOptions`）
* `publish()`：**画像**の container 作成（1 枚なら単体、2〜10 枚なら carousel）→ 状態のポーリング → `media_publish` → `permalink` の取得 → 必要ならトークンの延長
* 延長したトークンを `rotatedCredential` で返す（§6.7）
* `README.md`：トークンの取り方、Business / Creator アカウントが要ること、JPEG の公開 URL が要ること、トークンが 60 日で切れること・**配信のたびにしか延ばせない**こと、猶予 24 時間（`035` 裁定 #9）

### 3.2 やらないこと

| やらないこと | 理由 |
| --- | --- |
| Core（`apps/web` / `packages/plugin-api` / `migrations`）への変更 | `035` の口だけで書けることを示すのが本設計の目的（`035` §13「Plugin が Core に要求する追加は無い」） |
| `manual()`（手動投稿） | Instagram に投稿画面の Web Intent が無い（要件 §3）。**実装しなければ Core が `deliveryMode: 'manual'` を 422 で断る**（`035` §6.1.2 の g）。§9.3 |
| **動画（Reels）・ストーリーズ** | ①`SocialMediaView` は `url` と `alt` しか持たず、**画像か動画かを Plugin が知る手段が無い**（Torifune は媒体を取りに行かないので `Content-Type` も見えない）。②動画の container は処理に数十秒〜数分かかり、**Core の 30 秒に収まらない**（`035` §11 #6、`036` §11 #6 と同じ問題）。§11 #1 |
| 画像の代替テキスト（`alt_text`）の送信 | Graph API 側の受け口を実機で確かめていない。**知らない引数を送って container 作成ごと失敗させない**。§6.12 / §11 #2 |
| `link` の送信 | Instagram はキャプション内の URL をリンクにしない。**黙って捨てず `validate()` で断る**（§6.12） |
| Facebook Login 版の Graph API（`graph.facebook.com`） | トークンの延長に **App Secret** が要り、`credentialFields` が増える。**Instagram Login 版**（`graph.instagram.com`）は `refresh_access_token` だけで延ばせる（§6.1） |
| 画面からの OAuth「接続」 | Plugin の HTTP ルート（`027` §3.1）が前提。`035` 裁定 #6 で後回し |
| 自前のタイマー・ジョブ・HTTP ルート・テーブル・設定 | Core が持つ（`035` 裁定 #1）。**トークンの定期延長もしない**（§6.7 / §11 #3） |
| 投稿の削除・編集・コメント・位置情報・タグ付け・共同投稿者 | Core に対応する操作・項目が無い。`providerOptions` で受ける形は要望の形が見えてから |
| container の再利用（再試行のあいだで container ID を持ち回る） | Plugin に状態を持たせることになる。**使わなかった container は公開されず 24 時間で失効する**ので、作り直して害が無い（§6.9 の「container は投稿ではない」） |

> **2026-09-23 ユーザー裁定：画像のみで作る。** 動画は §11 #1 へ後回しにした。動画を扱うには Core の手当て（`media` に種別を持たせる、処理待ちを複数回の配信にまたがせる）が要り、036 まで守ってきた「Core を変えない」が崩れるため。
> **動画の URL は登録時には断れない**（Plugin に見分ける手段が無い）。配信時に Instagram が画像として処理できず `failed`（`retryable: false`）になる。README とマニュアルでこの挙動を利用者に伝える

### 3.3 Core が持つもの／この Plugin が持つもの

```text
Core（035）                                   Plugin（038）
─────────────────────────────────────────    ─────────────────────────────────
予約の受付・冪等キー・権限                    —
ジョブ social.publish（1 分周期・排他）        —
着手印・中断行の判定・再試行の回数と間隔       —
資格情報の復号・監査・書き戻し                 rotatedCredential を組み立てて返す
limits の適用（mediaRequired を含む）          limits の宣言
validate() の呼び出し（登録時・配信直前）      validate() の中身
manual 未実装なら deliveryMode:'manual' を 422 manual() を実装しない
publish() の呼び出しと 30 秒の打ち切り         publish() の中身（Graph API）
結果の記録・イベント・履歴画面                 —
provider の表示名の対応表                      label（対応表より優先される）
```

**この Plugin は状態を 1 つも持たない。** 設定も Key-Value Store も使わない（§5.3）。
トークンの期限は**資格情報の中**に持ち、Core の暗号化・監査・書き戻しの内側に置く（§5.2）。

## 4. レイヤ配置

**すべて Plugin 層（`plugins/sns-instagram/`）に置く。** 本体の `apps/web/src/` には 1 ファイルも足さない（テストを除く。§4.1）。

```text
plugins/sns-instagram/
├── plugin.json      Manifest（id / apiVersion / permissions / extensions）
├── index.ts         activate(): publisher の登録だけ
├── social.ts        createInstagramPublisher(): PublisherRegistration を組み立てる。publish() の段取り
├── graph.ts         Graph API への HTTP と、応答の分類（phase / status / code → retryable）
├── caption.ts       キャプションの数え方（ハッシュタグ・メンション）。純関数
├── token.ts         トークンの形の検査・期限の読み取り・延長の要否。純関数
└── README.md        トークンの取り方と運用上の注意
```

* **`@/` や `apps/web` を import しない。** 使ってよいのは `@torifune/plugin-api` の型と、Node の標準（`fetch` / `URL` / `URLSearchParams` / `AbortSignal` / `setTimeout`）だけ
* **`pg` / `kysely` / `react` を使わない。** データベースへも画面部品へも触らない
* `console` を使わない。出力は `PublishInput.logger` だけ
* **外へ出る HTTP は `graph.ts` に閉じる**（`036` の `atproto.ts` と同じ）。`caption.ts` と `token.ts` は純関数で、`fetch` も時計も持たない（時刻は引数で受ける）

Domain 層・Application 層に Instagram の語彙（`ig-user-id`、`media_publish`、`status_code`、`creation_id`）を 1 つも出さない。
Core から見ると、この Plugin は `PublisherRegistration` という 1 つのオブジェクトにすぎない。

### 5.1 `credentialFields`

```ts
credentialFields: [
  {
    key: 'igUserId',
    label: 'Instagram ユーザー ID',
    description:
      'Instagram のプロアカウント（ビジネスまたはクリエイター）の ID。数字だけの文字列です。' +
      '@ で始まるユーザーネームではありません。',
    kind: 'text',
    placeholder: '17841400000000000',
  },
  {
    key: 'accessToken',
    label: '長期アクセストークン',
    description:
      'Instagram API（Instagram ログイン）で発行した長期アクセストークン。' +
      'instagram_business_basic と instagram_business_content_publish の権限が要ります。' +
      '60 日で失効します。Torifune は配信のたびに残り日数を見て、必要なら延長して保存し直します。保存後は再表示されません。',
    kind: 'secret',
  },
  {
    key: 'accessTokenExpiresAt',
    label: 'トークンの有効期限',
    description:
      'トークンの有効期限（例：2026-11-22T00:00:00Z）。分からなければ unknown と入れてください。' +
      '次に配信が成功したとき、Torifune がトークンを延長して正しい期限に書き換えます。',
    kind: 'text',
    placeholder: 'unknown',
  },
]
```

* **`igUserId` は数字だけ**（§6.2 で検査する。要求の URL のパスに入るため）。ユーザーネームと取り違えやすいので `description` に書き切る
* **2026-09-24 追記（`041` §6.4。ユーザー裁定 U1）：`igUserId` に決まった語 `auto`（`/^auto$/i`。前後の空白は不可）を入れられる。**
  `accessTokenExpiresAt` の `unknown`（§5.2）と同じ「分からなければ決まった語を入れる」扱い。`auto` なら配信の入口で R0（§6）が数字の ID を問い合わせ、
  公開に成功したら 3 項目で書き戻す（§6.7）。`description` の末尾に「分からなければ auto と入れてください。次の配信のとき、Torifune がアクセストークンから ID を確かめて保存し直します。」を足し、
  `placeholder` を `'auto'` にした（`label` は変えない）。**数字の ID を入れたときの挙動は変わらない**
* **形式検証は Core ではしない**（Core が見るのは「空でない・宣言に無いキーが無い」だけ。`validateCredentialAgainstFields`）。
  形の検査は `publish()` の入口で Plugin が行い、通らなければ**外へ 1 本も出さずに** `retryable: false`（§6.9 の P0）
* **3 つとも `kind` を決め切る。** `accessTokenExpiresAt` は秘密ではないが、どの項目も保存後は再表示されない（`035` §7.5）

### 5.2 トークンの期限を資格情報に持つ（決めたこと）

**`credentialFields` に `accessTokenExpiresAt` を足し、3 項目で確定させる。`035` §13 の骨子（2 項目）から外す。**

トークンを延ばすには「**いつ切れるか**」を知る必要がある。知り方の候補は 4 つあった。

| 案 | 採否 | 理由 |
| --- | --- | --- |
| A. `debug_token` で問い合わせる | **採らない** | `graph.facebook.com` の口で、**App のアクセストークン（App ID と App Secret）** が要る。`credentialFields` が 2 つ増え、しかも App Secret を配信のたびに Plugin へ渡すことになる。Instagram Login 版には同等の口が無い |
| B. 配信のたびに無条件で延長する | **採らない** | 書き戻しと監査ログ（`updated` / `rotated: true`）が**投稿の数だけ**積まれる。延長の口は「発行から 24 時間以上たったトークン」しか受けないので、登録直後は毎回失敗する要求が 1 本増える |
| C. 期限を Plugin の Key-Value Store に持つ | **採らない** | **トークンと期限が別々の場所に書かれる。** Plugin が期限を書いた後で Core の書き戻し（§6.7）が失敗すると、「期限は 60 日後」と記録されたまま**古いトークンが残る**。以後は延長の判定が働かず、トークンは黙って切れる。2 つを 1 回で書く手段は Plugin に無い |
| **D. 期限を資格情報の 3 つ目の項目に持つ** | **採る** | トークンと期限が **1 つの暗号化された値**に入り、**Core が 1 回で書き戻す**（`035` §6.5.6）。片方だけ更新される状態が生まれない。監査・暗号化も Core の内側に収まる |

**`credentialFields` は後から足せない**（`036` §5.2。足すと既存のアカウントの配信が全部 `failed` になる）。
したがって**最初の版で 3 つ目まで決め切る。** 後から「期限も持ちたい」と気づいても直せない。

D の代償は **登録する人に期限を書かせる**ことである。これを軽くするために：

* **期限が読めない値は「不明」として扱う**（`unknown`、空白、日付として読めない文字列）。不明なら**次に配信が成功したときに延長を試みる**（§6.7）。
  成功すれば正しい期限が書き戻されるので、**不明で登録しても 1 回の配信で直る**
* **ありえない未来（いまから 61 日より先）も「不明」として扱う。** 60 日を超える長期トークンは存在しない。
  打ち間違い（`2099-…`）を信じると、**延長の判定が永久に働かず、トークンが黙って切れる**
* 外部アプリが API で登録する場合（`035` 裁定 #6 の運用）は、トークンを交換したときの応答の `expires_in` から期限を計算して入れられる

### 5.3 状態を持たない（決めたこと）

**この Plugin は `store` を読みも書きもしない。`registerSettings` も呼ばない。**

* **Graph API の宛先（`https://graph.instagram.com`）は定数**にする。Bluesky の PDS と違い、Instagram に「自分で運用するサーバ」は無い。
  変えられるようにすると、**アクセストークンを任意のサーバへ送らせる口**が 1 つ増えるだけになる
* **版（`v…`）も定数**にする（§6.1）。版の更新は Plugin の更新で行う（`03` §9）
* **container の ID を持ち回らない**（§3.2）。再試行は container から作り直す
* したがって `createInstagramPublisher` は **`store` を受け取らない**（§10.1）。Manifest の `extensions` は **`social` だけ**（`ui` を宣言しない。§8.1）

## 6. 外部への要求（Graph API）

新しい Torifune の API エンドポイントは**作らない**。この Plugin が外へ出す HTTP 要求は次の 6 種類だけである。

| # | 要求 | 用途 | 投稿との関係 |
| --- | --- | --- | --- |
| R1 | `POST {graph}/{v}/{igUserId}/media`（`image_url`） | 画像 1 枚の container、または carousel の子 | **投稿ではない** |
| R2 | `POST {graph}/{v}/{igUserId}/media`（`media_type=CAROUSEL`） | carousel の親 container | **投稿ではない** |
| R3 | `GET {graph}/{v}/{containerId}?fields=status_code` | 処理待ちのポーリング | 読むだけ |
| R4 | `POST {graph}/{v}/{igUserId}/media_publish`（`creation_id`） | **公開する** | **これが「送る」** |
| R5 | `GET {graph}/{v}/{mediaId}?fields=permalink` | 履歴から辿る URL | 公開の後 |
| R6 | `GET {graph}/refresh_access_token?grant_type=ig_refresh_token&access_token=…` | トークンの延長 | 公開の後 |

`{graph}` は `https://graph.instagram.com`、`{v}` は `GRAPH_API_VERSION`（§6.1）。

**2026-09-24 追記（`041` §6.4。ユーザー裁定 U1）：R0 を足した（7 種類になる）。**

| # | 要求 | 用途 | 投稿との関係 |
| --- | --- | --- | --- |
| R0 | `GET {graph}/{v}/me?fields=user_id` | `igUserId` が `auto` のときだけ、トークンの持ち主の数字の ID を得る | 読むだけ。**R1 の前** |

* トークンは R1〜R5 と同じ **`Authorization: Bearer`**。**URL のクエリに `access_token` を載せない**。`redirect: 'manual'`、本体の上限は `sendGraphRequest` のまま
* 制限時間は **`ME_TIMEOUT_MS = 3_000`**（`graph.ts`。R5 / R6 と同じ読むだけの長さ）。**準備の期限（`PREPARE_BUDGET_MS`）の中で、準備の signal の下で**送る（合計の期限は変えない）
* 応答の `user_id` が文字列で §6.2 の `igUserId` の形に合うとき、または JSON の数値で `Number.isSafeInteger` のとき（`String(値)`）だけ使う。**安全な整数を超える数値は使わない**（下の桁が失われている）
* 得た ID をその配信の R1〜R5 に使う。成功のログは `'instagram user id resolved'`（`phase: 'me'`）で、**ID の値を載せない**。R0 は 1 回の配信につき 1 回まで。失敗したら R1 以降を送らない

### 6.1 宛先と版（決めたこと）

* **Instagram Login 版**（`graph.instagram.com`）を使う。Facebook Login 版（`graph.facebook.com`）は**延長に App Secret が要る**（§3.2）
* `GRAPH_API_BASE_URL = 'https://graph.instagram.com'` と `GRAPH_API_VERSION` を **`graph.ts` の定数**として持つ。設定にも資格情報にも入れない（§5.3）
* **`GRAPH_API_VERSION` の値は実装時点の最新の安定版**（`v` ＋ 数字 ＋ `.` ＋ 数字）にし、`README.md` に書く。
  Graph API の版はおよそ 2 年で廃止されるので、**Plugin の更新で上げる**（`03` §9「その Plugin を更新するだけで追従」）。
  設計には値を書かない（書くと、版が変わったときに設計が嘘になる。`036` §11 #13 と同じ判断）
* 要求の URL は **`new URL(path, GRAPH_API_BASE_URL)` の解析結果から組み立てる**。パスの各部分（`igUserId`・container ID・media ID）は
  **§6.2 の形の検査を通した値だけ**を使う。文字列の連結で作らない（`036` §7.2 の低-2 と同じ理由）
* R6 だけは**版の付かないパス**（`/refresh_access_token`）である（公開ドキュメントの形に従う）

### 6.2 共通の要求の形

| 項目 | 値 | 理由 |
| --- | --- | --- |
| 認証（R1〜R5） | `Authorization: Bearer <accessToken>` | **トークンを URL に載せない。** URL はプロキシやエラーの文面に残りやすい |
| 認証（R6） | クエリの `access_token`（公開ドキュメントの形） | 延長の口はこの形しか公開されていない。**この URL をログにも `reason` にも載せない**（§6.11） |
| POST の本体 | `application/x-www-form-urlencoded`（`URLSearchParams`） | Graph API が全版で受ける形 |
| リダイレクト | **追わない**（`redirect: 'manual'`。3xx は `kind: 'http'` の失敗） | Bearer を付けた要求を別の宛先へ移らせない。**`'error'` にしない**（3xx を観測できず `network` に落ちる。`036` 検証レポート R-1） |
| 応答の読み方 | `response.text()` を **64 KiB で打ち切って**から `JSON.parse` | 相手が何を返しても Plugin のメモリを食わせない |

**外へ出す前の形の検査**（通らなければ 1 本も出さずに `retryable: false`。§6.9 の P0）：

| 値 | 形 | 理由 |
| --- | --- | --- |
| `credential.igUserId` | `^[0-9]{1,64}$` | URL のパスに入る。`../` や `?` を入れさせない |
| `credential.accessToken` | `^[\x21-\x7E]{1,2048}$`（空白・制御文字・非 ASCII を含まない） | ヘッダ値に入る。改行を含む値は `fetch` が**同期で投げ**、`network` に化けて `retryable: true` を 5 回繰り返す |
| Graph API が返した container ID / media ID | `^[0-9]{1,64}$` | 次の要求のパスに入る。**外から来た文字列をそのままパスへ差し込まない** |

### 6.3 container の作成（R1 / R2）

| `media` の件数 | 作るもの |
| --- | --- |
| 0 | **作らない**（`mediaRequired` で Core が弾く。来たら P0 で `retryable: false`） |
| 1 | R1：`image_url=<media[0].url>`、`caption=<body>` |
| 2〜10 | 子 R1 × N：`image_url=<media[i].url>`、`is_carousel_item=true`（`caption` を付けない）→ 子がすべて `FINISHED`（§6.4）→ 親 R2：`media_type=CAROUSEL`、`children=<子 ID をカンマで連結>`、`caption=<body>` |

* **`caption` は `post.body` そのまま。** 足しも削りもしない（`link` を末尾へ足さない。§6.12）
* **子は並行に作る。ただし同時に 5 本まで**（`CAROUSEL_CHILD_CONCURRENCY = 5`）。
  10 枚を 1 本ずつ作ると、Instagram が 1 枚ごとに画像を取りに行く時間が積み上がり、**準備に使える 15 秒（§6.8）に収まらない。**
  上限を付けるのは、Graph API の呼び出し回数の制限を 1 回の配信で使い切らないため
* **子の 1 つが失敗したら、残りの子の要求を打ち切る**（共通の `AbortController` を子の signal に混ぜる）。
  結果の分類は §6.9 の「複数の失敗」の規則で 1 つにまとめる
* **子の順序は `media` の順を保つ。** `children` に並べるのは作成が終わった順ではなく**`media` の添字の順**
* **Instagram が `image_url` を取りに来る。Torifune のサーバからは媒体の URL へ 1 本も要求を出さない**（`036` §6.2 の SSRF の論点はこの Plugin には無い。§8.2）

### 6.4 状態のポーリング（R3）

container は作成の応答が返った時点ではまだ処理中のことがある。**`FINISHED` になるまで `media_publish` を送らない。**

```text
作った container の集合 S（単体なら 1 つ、carousel なら子の N 個 → 子が揃った後に親の 1 つ）
round = 0
loop:
  S のうち FINISHED でないものについて R3 を送る（並行・同時 5 本まで）
  全部 FINISHED → 抜ける
  ERROR / PUBLISHED / EXPIRED があれば → その場で失敗（§6.9 の P3）
  round += 1
  round >= POLL_MAX_ROUNDS、または 次の round を始める前に準備期限を過ぎる → kind: 'budget'（retryable: true）
  wait(POLL_INTERVAL_MS, signal)
```

| `status_code` | 扱い |
| --- | --- |
| `FINISHED` | 次へ進む |
| `IN_PROGRESS` | 待って再度見る |
| `ERROR` | **失敗・`retryable: false`**。画像を取得できない・形式が違うなど、**人が `media[].url` を直すまで直らない** |
| `EXPIRED` | 失敗・`retryable: true`。作ったばかりの container では起きないはずだが、**公開はされていない**ので作り直してよい |
| `PUBLISHED` | **失敗・`retryable: false`。** 自分は `media_publish` をまだ送っていないのに公開済みと言われている。**何が起きたか分からないので安全側** |
| 上記以外・項目が無い・JSON でない | 失敗・`retryable: true`（公開の要求をまだ出していない） |

* **最初の確認は作成の直後に行う**（画像はたいてい作成の時点で `FINISHED` になっており、待たずに済む）
* `POLL_INTERVAL_MS = 1_000`、`POLL_MAX_ROUNDS = 10`。**上限は回数と準備期限（§6.8）の早いほう**
* **待ちは注入できる `wait(ms, signal)` で行う**（§10.1）。既定は `setTimeout` を `signal` の発火で打ち切る実装。
  **テストが実時間を待たずに `budget` の分岐を通せる**ようにするため（`036` §6.6 の「通らない分岐は無いのと同じ」）
* **`status` 項目（自由文）は読まない。** 取るのは `status_code` だけ（`fields=status_code`）。自由文を取らなければ、外へ出す心配もない（§6.11）
* **`IN_PROGRESS` のまま準備期限に達したら `retryable: true`**（`035` §13 の骨子は `false`。§9.4 の 2）。
  container を作っただけでは**何も公開されていない**。作った container は使われないまま 24 時間で失効する（§6.9）

### 6.5 公開（R4）

```text
POST {graph}/{v}/{igUserId}/media_publish
creation_id=<単体の container ID、または carousel の親 ID>
→ 200 { "id": "<media ID>" }
```

* **残り時間が `MEDIA_PUBLISH_TIMEOUT_MS` 以上あるときだけ送る。** 足りなければ送らずに `kind: 'budget'`（`retryable: true`）。
  **打ち切られた `media_publish` は「届いたか分からない」＝ `retryable: false` になる**ので、途中で切られる見込みの要求は**始めない**ほうが得である
* 応答の `id` が無い・JSON でない → **`retryable: false`**（公開されたか分からない）
* 応答の `id` が §6.2 の形（`^[0-9]{1,64}$`）に合わない、または 200 文字を超える → **失敗にしない。** `externalId` も `externalUrl` も付けずに `{ ok: true }`（§6.6）。
  **200 を返した以上、公開されている。** 失敗にすると再試行で二重投稿になる（`036` 検証レポート 低-1 の型）

### 6.6 戻り値の組み立て（R5）

```ts
{
  ok: true,
  externalId: mediaId,              // §6.5 の形の検査に通ったときだけ
  externalUrl: permalink,           // R5 が返し、下の検査に通ったときだけ
  rotatedCredential: { … },         // §6.7 で延長できたときだけ
}
```

* **`externalId` は `media_publish` の `id`**（≤ 200 文字、`^[0-9]{1,64}$`）。`social_posts.external_id` の CHECK（200 文字）に**必ず収まる形でしか返さない**
* **`externalUrl` は R5 の `permalink`**。Instagram の投稿 URL は media ID から組み立てられない（ショートコードが要る）ので、問い合わせる。
  **載せる前に次をすべて確かめ、1 つでも外れたら `externalUrl` を付けない**（`externalId` は残す）：
  * `new URL()` に通る・`https:`・`username` / `password` を含まない
  * ホスト名が `instagram.com` か、`.instagram.com` で終わる
  * **2048 文字以内**（`social_posts.external_url` の CHECK）
* **R5 は公開の後の要求である。何が起きても `ok: true` を覆さない。** 失敗・制限時間・形の不一致は `externalUrl` を省くだけ（`logger.warn` は出す）
* **R5 は残り時間が `PERMALINK_TIMEOUT_MS` 以上あるときだけ送る。** 足りなければ送らない（§6.8）

### 6.7 トークンの延長（R6。`rotatedCredential`）— 決めたこと

**公開に成功した後で、期限が近ければ延長し、新しいトークンと期限を `rotatedCredential` で返す。**

```text
公開に成功（R4 が 200 と id を返した）
  → R5（permalink）
  → expiresAt = parseExpiry(credential.accessTokenExpiresAt, now)   // 読めない・61 日より先 → 'unknown'
  → shouldRefresh = expiresAt === 'unknown' || expiresAt - now < TOKEN_REFRESH_THRESHOLD_MS
  → shouldRefresh かつ 残り時間 ≥ REFRESH_TIMEOUT_MS なら R6
  → R6 が 200 で access_token が §6.2 の形に合う
       → rotatedCredential = {
            igUserId: credential.igUserId,                            // そのまま
            accessToken: <新しいトークン>,
            accessTokenExpiresAt: <now + expires_in 秒 の ISO 文字列、読めなければ 'unknown'>,
          }
     それ以外 → rotatedCredential を付けない（logger.warn）
```

* **延長するのは公開の「後」である。** 理由は 2 つ：
  * **`rotatedCredential` は `ok: true` にしか載せられない**（`035` §9.2 の `PublishResult`）。公開の前に延長して公開が失敗すると、
    **新しいトークンを Core へ渡す手段が無い。** 延長の口が古いトークンを無効にする場合、そのまま資格情報が死ぬ
  * **延長の失敗を投稿の成否に混ぜない。** 公開の後なら、延長がどう失敗しても `ok: true` のまま返せる
* **延長の失敗は投稿の成否に影響させない。** R6 の失敗・制限時間・形の不一致・残り時間の不足は、`rotatedCredential` を付けないだけ。
  `logger.warn('instagram token refresh skipped', { postId, attempt, phase: 'refresh', status?, code? })` を出す
* **閾値は残り 30 日**（`TOKEN_REFRESH_THRESHOLD_MS = 30 日`。`035` §13 の骨子は 7 日。§9.4 の 3）。
  延長できるのは**配信が成功したときだけ**（§11 #3）なので、窓が 7 日だと**週 1 回より少ない運用では窓を踏まずに失効する。**
  30 日にすると月 1 回の配信でも窓に入る。代償は書き戻し（と監査ログ 1 行）がおよそ月 1 回起きることだけ
* **`rotatedCredential` のキーは `credentialFields` の 3 つちょうど**。`igUserId` を落とすと Core の `validateCredentialAgainstFields` が
  不足を検出して**書き戻しを捨てる**（`035` §6.5.6。`log.warn` だけで投稿には影響しない）。`...credential` で写さず、**3 つを明示して組む**
  （Core が将来 `credential` に何かを足しても、それを書き戻さない）
* **新しいトークンの形を確かめる**（§6.2 の `accessToken` と同じ形、2048 文字以内）。
  Core は「空でない」「4096 文字以内」しか見ないので、**改行を含むトークンを返すと保存されてしまい、以後の配信が全部失敗する。**
  形に合わなければ返さない
* `expires_in` は正の整数で、**61 日以下**のときだけ期限に使う。それ以外は `'unknown'` を書く（トークンは書き戻す。次の成功でもう一度延長を試みる）
* **期限が既に過ぎている**トークンは、そもそも R1 が 190 で失敗する（§6.9）。延長の出番は無い
* **R6 の URL にはトークンが入る**（§6.2）。この URL を `logger` にも `reason` にも渡さない。例外の文面も載せない（§6.11）
* **2026-09-24 追記（`041` §6.4.3。ユーザー裁定 U1）：`auto` を R0 で解決した配信は、公開（R4）に成功したときだけ書き戻す。**
  延長しなければ `{ igUserId: <得た数字>, accessToken: <入っていた値>, accessTokenExpiresAt: <入っていた値そのまま（unknown を含む）> }`、
  延長もすれば上の延長の書き戻しの `igUserId` が得た数字になる。どちらも 3 項目を明示して組む（`...credential` で写さない）。
  延長の要る期限で延長に失敗しても、`auto` の解決の書き戻しは返す。
  Core は `039` §6.1 の比較更新で書き戻すので、配信の間に運用者が資格情報を入れ直した・消した場合は捨てられる（運用者の値が `auto` のままなら次の配信でもう一度 R0 を送る）。
  公開に失敗した配信では書き戻せない（`ok: false` に載せられない）ので、次の配信でもう一度 R0 を送る。書き戻しの後の配信は数字の ID を使い、R0 を送らない

### 6.8 制限時間と `signal`

Core は `publish()` を **30 秒**で打ち切り、**結果不明として `failed`** にする。**この Plugin は自分で早く諦める。**

| 定数 | 値 | 何に渡るか |
| --- | --- | --- |
| `PUBLISH_TOTAL_BUDGET_MS` | 25 秒 | `publish()` 全体。**入口で 1 つ作り、すべての要求の外側の signal に混ぜる**（`036` R-2） |
| `PREPARE_BUDGET_MS` | 15 秒 | 準備（R1 / R2 / R3 と待ち）。= 合計 − `MEDIA_PUBLISH_TIMEOUT_MS` |
| `CREATE_CONTAINER_TIMEOUT_MS` | 10 秒 | R1 / R2 の 1 本ごと |
| `STATUS_TIMEOUT_MS` | 5 秒 | R3 の 1 本ごと |
| `POLL_INTERVAL_MS` | 1 秒 | R3 の round のあいだの `wait` |
| `POLL_MAX_ROUNDS` | 10 | R3 の round の上限 |
| `MEDIA_PUBLISH_TIMEOUT_MS` | 10 秒 | R4 |
| `PERMALINK_TIMEOUT_MS` | 3 秒 | R5 |
| `REFRESH_TIMEOUT_MS` | 3 秒 | R6 |
| `CAROUSEL_CHILD_CONCURRENCY` | 5 | R1（子）と R3 の同時本数 |

* **外側の signal** ＝ `AbortSignal.any([input.signal, AbortSignal.timeout(PUBLISH_TOTAL_BUDGET_MS)])`。
  **準備の signal** ＝ `AbortSignal.any([外側, AbortSignal.timeout(PREPARE_BUDGET_MS)])`。
  **要求ごとの signal** ＝ `AbortSignal.any([外側または準備の signal, AbortSignal.timeout(その要求の定数)])`
  （carousel の子には、さらに子どうしで共有する打ち切り用の signal を混ぜる。§6.3）
* **期限の判定は `now()` で数える。** 「次の round を始めるか」「R4 を送るか（残り ≥ 10 秒）」「R5 / R6 を送るか（残り ≥ 3 秒）」は
  **入口で記録した `now()` からの経過**で決める。実時間を断ち切るのは `AbortSignal.timeout` だが、
  **判定を実時間だけに預けると、`budget` の分岐をテストが通せない**（`036` §6.6）
* **R4 は準備の signal ではなく外側の signal の下で送る**（準備期限の 15 秒で公開の要求を切らない）。
  R4 を始めるのは残り ≥ 10 秒のときだけなので、R4 は**必ず合計 25 秒の内側で終わる**
* **最悪の形でも 25 秒 ＋ 結果の組み立てで返る。** Core の 30 秒との差 5 秒は、打ち切りを検知して `PublishResult` を返すための余白（`036` と同じ）
* **どの定数がどの要求へ渡るかは固定する**（`036` #81 の型。§10.10）。値が合っていても**結線が入れ替われば意味が変わる**
  （R4 に `STATUS_TIMEOUT_MS`（5 秒）が渡る取り違えは、公開を途中で切って `retryable: false` を量産する）
* **`input.signal` が発火したら、その場で処理をやめて `publish()` を抜ける**（Core は既に結果を確定させている）

### 6.9 `retryable` の基準 — Graph API の応答への対応づけ

契約は「**送る前に失敗したなら `true`、届いたか分からないなら `false`、迷ったら `false`**」（ガイド §9）。
Instagram で「送る」に当たるのは **R4（`media_publish`）の 1 回だけ**である。

> **container は投稿ではない。** R1 / R2 で作った container は、R4 を送らない限り**誰にも見えず、公開もされず、24 時間で失効する**。
> したがって container を作った後に失敗して作り直しても、**二重投稿にはならない**（使われなかった container が 1 つ残るだけ）。
> 害として考えられるのは container の作成数の上限を食うことだけで、これは §11 #4 に残す。

> **支配的な規則（これだけ覚えればよい）**
>
> 1. **R4 を送る前の失敗は既定で `retryable: true`。**
>    ただし**時間が経っても直らないもの**（資格情報・権限・投稿の内容・1 日の上限）は `false`
> 2. **R4 を送った後の失敗は既定で `retryable: false`。**
>    ただし**レート制限（書き込む前に断られたと読める）だけ `true`**
> 3. **R4 が成功した後に起きたことは、`ok: true` を覆さない**（R5 / R6）

* `retryable` は **すべての失敗が `true` のときだけ `true`**（1 つでも直らない失敗があれば、作り直しても同じところで落ちる）
* `reason` と `logger` に使うのは **`retryable: false` の失敗のうち `media` の添字がいちばん小さいもの**、無ければ添字がいちばん小さい失敗
* 添字で選ぶのは、**完了の順（実行ごとに変わる）で選ぶと、同じ入力で `reason` が変わる**ため

### 6.10 `retryAfterMs`

Graph API のレート制限の応答には、待つべき時間が**ヘッダで**付くことがある。次の順に見て、最初に取れたものを使う。

1. `Retry-After`（秒の整数）
2. `X-Business-Use-Case-Usage`（JSON）の中の `estimated_time_to_regain_access`（**分**）の最大値

```text
retryAfterMs = 取れた値をミリ秒にしたもの
```

* ヘッダが無い・4096 文字を超える・JSON として読めない・値が正の有限数でない → **`retryAfterMs` を付けない**（Core の既定 1 → 2 → 4 → 8 分）
* **Core が 24 時間で切り詰める**（`035` §5.6.2）。Plugin 側で丸めない
* ヘッダの値は `retryAfterMs` の計算にだけ使い、**`reason` にもログにも載せない**

### 6.11 例外を投げない・外へ出す範囲

* **`publish()` は例外を投げない。** すべての経路を `try` で包み、`PublishResult` として返す（`036` §6.11 と同じ理由）。
  **「R4 を送ったかどうか」を 1 つの変数で持ち、予期しない例外の分類はそれで決める**（送っていなければ `true`、送っていれば・分からなければ `false`）
* **`reason` に載せてよいもの**（これ以外は載せない）：
  * フェーズの言葉（「container の作成」「公開」など、固定の日本語）
  * **HTTP の status**（数値）
  * **既知の `code` と `error_subcode`**（数値。下の集合に含まれるものだけ。含まれなければ `unknown` と書く）
  * 固定の案内文（例：「長期アクセストークンを発行し直してください」）
* **載せないもの**：`error.message` / `error.error_user_title` / `error.error_user_msg` / `error.type` / `fbtrace_id` /
  container の `status`（自由文）/ 応答の本文 / **要求の URL**（R6 の URL にはトークンが入る）/ 例外の `message`
* **理由**：Graph API の自由文は**要求の値をそのまま混ぜ返すことがある**（パラメータの値・トークンの断片・`image_url`）。
  Core の伏せ字（`redactCredentialValues`）は **4 文字以上の完全一致しか消せない**（ガイド §9）ので、切られたり符号化されたりした断片は素通りする。
  **伏せ字を当てにせず、載せない。** `code` / `error_subcode` を集合で絞るのは、**数値でも知らない値を素通しする口は作らない**という `036` §6.11 の原則による
* **既知の `code` の集合**：{1, 2, 4, 9, 10, 17, 24, 25, 32, 100, 190, 200〜299, 368, 613}。**既知の `error_subcode` の集合**は
  Meta の公開しているエラーコード表から、**Content Publishing と トークンに関わるもの**（2207xxx 系と 460 / 463 / 467 など）を実装時に定数として固定する。
  集合の中身は `graph.ts` の 1 か所に置き、テストはその定数を読む
* **`reason` の文面は、運用者が次に何をすればよいかが読めるものにする。** 例：
  * `Instagram のアクセストークンが無効か期限切れです（HTTP 400 / code 190）。長期アクセストークンを発行し直し、SNS アカウントの資格情報を登録し直してください。`
  * `Instagram が画像を処理できませんでした（container の状態 ERROR）。media の URL が公開された JPEG 画像を指しているか確かめてください。`
  * `Instagram の 24 時間あたりの公開数の上限に達しました（code 9 / subcode 2207042）。時間をおいて新しい投稿として登録し直してください。`
* **`logger` に渡してよいもの**：`postId` / `attempt` / フェーズ名 / HTTP status / 既知の `code` / 既知の `error_subcode` / 媒体の件数 / ポーリングの round 数 /
  **`fbtrace_id`（`^[A-Za-z0-9_-]{1,64}$` に合うときだけ）**。
  `fbtrace_id` は Meta に問い合わせるときの手がかりで、秘密ではない。ただし**外から来た文字列**なので形で絞り、`reason` には載せない
* **`logger` に渡さないもの**：`credential` の 3 つの値、`igUserId`、`post.body`、`media[].url`、container ID、media ID、`permalink`、応答の本文、要求の URL、ヘッダ

**Torifune から見て「外部の応答を外へ出す範囲」の論点（`036` 検証レポート 中-1 の型）は、この Plugin では次の形になる。**
`036` では **Torifune のサーバが** `media[].url` を取りに行き、その HTTP status を `reason` に出すと内部ネットワークを走査できた。
この Plugin では **Torifune は `media[].url` へ要求を出さない。** 取りに行くのは Instagram のサーバで、私有アドレスは Instagram からは届かず、
**一律に「取得できない」側の失敗になる。** Torifune の内部ネットワークについて観測できることは無い。
それでも Graph API の**自由文は**出さない（上の理由。混ぜ返しの問題は取得先と関係なく残る）。

### 6.12 `link` / `alt` / 動画（黙って捨てない）

| 項目 | 扱い | 理由 |
| --- | --- | --- |
| `link` | **`validate()` が断る**（`field: 'link'`）。`publish()` でも断る（P0） | Instagram はキャプション内の URL を**リンクにしない。** 本文の末尾へ足すと、**Core が数えた 2200 文字と実際に送る本文が食い違い**（`036` §6.8）、しかも押せない URL が載る。**捨てれば登録した側は気づけない**。断るのが唯一「黙らない」形 |
| `media[].alt` | **送らない。断りもしない**（`README.md` に書く） | Graph API の代替テキストの受け口を実機で確かめていない（§11 #2）。**知らない引数で container 作成ごと失敗させる**より、送らないほうが投稿は通る。`alt` は付随情報で、投稿の意味を変えない（`link` と違う）。**複数の SNS へ同じ内容を登録する外部アプリにとって、`alt` を理由に 422 にされるほうが害が大きい** |
| 動画 | **扱わない**（§3.2）。動画の URL を渡されたら Instagram が `image_url` として処理できずに失敗する（P1 / P3 の `false`） | 画像か動画かを Plugin が知る手段が無い（拡張子で判定する案は `036` §9.3 と同じ理由で採らない） |

**無し。`packages/plugin-api` を 1 行も変えない。Core への追加要求も無い。**

### 9.1 `limits`

**`limits: { bodyMaxLength: 2200, mediaRequired: true, mediaMax: 10 }`。`035` §13 の骨子どおり。**

* **`bodyMaxLength: 2200` は厳しい側に置いたまま**にする。`036` §9.2 は「Core の `String.length`（UTF-16）は Bluesky の grapheme より厳しいので緩めた」が、
  **Instagram がキャプションをどう数えるかは公開されていない**（UTF-16 か、コードポイントか、grapheme か）。
  **分からないときは、登録時に断るほうを取る。** 緩めた結果 Instagram 側で断られると、**配信時刻に初めて失敗する**（`035` §6.1.2 が最も避けたいこと）。
  `String.length` はどの数え方よりも大きい数を返すので、**2200 で断った本文は Instagram でも通らないとは限らないが、通した本文は必ず Instagram でも 2200 以内**である。
  Instagram の数え方が分かって緩めたくなったら緩める（緩めるのは後方互換。§11 #5）
* **`mediaMax: 10`** は carousel の上限。Core が枚数を正確に数えるので、`validate()` では数えない
* **`mediaRequired: true`**。Core は `deliveryMode: 'auto'` のときだけ見る（手動投稿は Core が g で断る）
* **`PublisherLimits` にキーを足さない**（`036` §9.1。キーを足すのは Core の変更）

### 9.2 `validate()`

**5 秒で打ち切られる。外部へ問い合わせない。同期で返す。例外を投げない。**

| # | 検査 | `field` | 文言の趣旨 |
| --- | --- | --- | --- |
| 1 | ハッシュタグの数 ≤ **30** | `body` | `Instagram のハッシュタグは30個までです。いまは N 個です。` |
| 2 | メンション（`@ユーザーネーム`）の数 ≤ **20** | `body` | `Instagram のメンションは20件までです。いまは N 件です。` |
| 3 | `link` が `null` でも空文字でもない | `link` | `Instagram はキャプション内の URL をリンクにしません。link は指定できません（URL を見せたい場合は本文に書いてください。リンクにはなりません）。` |
| 4 | `providerOptions` にキーがある | `providerOptions.<key>` | `<key> は Instagram では使いません。` |

* **数え方（`caption.ts`）**：
  * ハッシュタグ：`#` または `＃` の直後に、文字・数字・`_`（Unicode の `\p{L}\p{N}_`）が 1 つ以上続くもの。
    `#` の直前が行頭か、文字・数字・`_`・`&` 以外のときだけ数える（`a#b` や `&#123;` を数えない）
  * メンション：`@` の直後に英数字・`.`・`_` が 1 つ以上続くもの。直前の条件は同上（メールアドレス `a@b.com` を数えない）
  * **多めに数える側に倒す**（全角の `＃` も数える）。Instagram の数え方より多く数えれば、**登録時に断られることはあっても配信時に断られることは無い**（§9.1 と同じ向き）
* **本文の長さは見ない**（Core の `bodyMaxLength` が同じ数え方で正確に効く。同じ判定を 2 か所に書かない）
* **媒体の枚数・有無も見ない**（Core の `mediaMax` / `mediaRequired`）
* **`media[].url` の形も見ない。** Core の `isValidMediaUrl` が https・資格情報なし・2048 文字を見ている。
  **拡張子で JPEG かどうかを見る案は採らない**（`036` §9.3。`035` §13 の骨子とは食い違う。§9.4 の 4）。
  **私有アドレスを字面で断る案も採らない**（§11 #6）
* **Business / Creator アカウントかどうかは見ない**（外部への問い合わせになる。`035` §13 の骨子とは食い違う。§9.4 の 4）。
  個人アカウントなら配信時に `permission` で `false`（§6.9）になり、理由に「プロアカウント」と出る
* `deliveryMode` で分岐しない（`manual` は Core が g で先に断る）
* 複数の違反は**すべて**返す
* **`providerOptions` / `media` / `link` は型を確かめてから触る**（外から来た任意の JSON。循環参照もありうる）

### 9.3 `manual()` を実装しない（決めたこと）

**`PublisherRegistration` に `manual` のキーを置かない**（`manual: undefined` も書かない）。

* Instagram には投稿内容を反映した投稿画面の URL（Web Intent）が無い（要件 §3）
* Core は `manual` が無い publisher について、`deliveryMode: 'manual'` の登録を **422「このSNSは手動投稿に対応していません。」**で断る（`035` §6.1.2 の g）。
  **断るのは Core の仕事であり、Plugin は何もしない**（`validate()` で同じことを言わない。先に g が効くので届かない）
* 代わりの URL（`https://www.instagram.com/` のトップ）を返す案は採らない。**投稿内容が反映されない画面を「手動投稿」と呼ぶと、利用者は本文を手で写すことになり**、それは Torifune が手動投稿の画面で約束していること（`035` §7.1）と違う

### 9.4 `035` §13 の骨子から外した判断

`035` §13「038 `sns-instagram`」の骨子と、本設計が食い違う点を列挙する。**`035` の設計そのものは書き換えない。** ただし、**§13 の骨子から外した判断を `035` 側へ書き戻すことだけは行う**（2026-09-23、`035` §13 の末尾へ追記済み。§2 の但し書き）。

| # | 骨子 | 本設計 | 理由 |
| --- | --- | --- | --- |
| 1 | `credentialFields` は `igUserId` / `accessToken` の 2 つ | **`accessTokenExpiresAt` を足して 3 つ** | 延長の要否を決めるのに期限が要り、置き場は資格情報の中しか安全でない（§5.2）。**後から足せない**ので最初に決める |
| 2 | 処理待ちが 30 秒に収まらなければ `retryable: false` | **`retryable: true`**（R4 を送る前なら） | container は投稿ではなく、R4 を送らない限り公開されない（§6.9）。`false` にすると、**一時的に処理が遅かっただけの投稿が再試行されずに終わる** |
| 3 | 残り 7 日を切っていたら延長 | **残り 30 日を切っていたら延長。公開に成功した後だけ** | 延長の機会は配信の成功時しか無い（§11 #3）。7 日の窓は週 1 回未満の運用で踏み外す。公開の後にするのは `rotatedCredential` が `ok: true` にしか載らないため（§6.7） |
| 4 | `validate()` で Business / Creator の前提や `media[].url` の拡張子を見る | **どちらも見ない** | 前者は外部への問い合わせ（`validate()` は 5 秒・外へ出ない）。後者は `036` §9.3 の判断（拡張子の無い画像 URL は普通にある）に揃える |
| 5 | 1 件なら `image_url` / `video_url` | **画像のみ。`video_url` を扱わない** | 画像か動画かを知る手段が無く、動画の処理は 30 秒に収まらない（§3.2 / §11 #1） |

### 9.5 `plugins/sns-instagram/README.md`

次を書く。

* **Instagram のプロアカウント（ビジネスまたはクリエイター）が要る**こと
* Meta の開発者向け画面で App を作り、**Instagram API（Instagram ログイン）** で `instagram_business_basic` と `instagram_business_content_publish` の権限を持つ**長期アクセストークン**を発行する手順の概略。ユーザー ID の確かめ方

* **手動投稿（`deliveryMode: 'manual'`）には対応しない**
* 導入してから資格情報を入れるまでの猶予は**約 24 時間**（`035` 裁定 #9）

* 使っている Graph API の版（`GRAPH_API_VERSION`）と、版が廃止されたら Plugin の更新が要ること

### 10.9 偽物と本物の一致（A。036 の型 1 を先に潰す）
