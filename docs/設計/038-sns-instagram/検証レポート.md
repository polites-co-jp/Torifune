## 2. 見つかった欠陥と処置

### 1. テスト名と中身が別物だった（`spec-verifier` 軽微-1）

「R4（公開）を送った後の予期しない例外は `retryable: false`」というテストが、**実際にはその分岐（`social.ts` の外側の catch）に到達していなかった**。
偽の fetch が投げた例外は `sendGraphRequest` の中で「接続断」に分類され、P4 の通常の経路で `false` になっていただけで、
**外側の catch の `publishSent` を消しても落ちなかった**。036 の R-1（緑なのに何も守っていない）と同じ型である。

**しかも、今のコードではその分岐へ到達する経路が無い**（R4 の後の例外は `afterPublish` が握り、`sendGraphRequest` は投げない）。

**処置**：テスト名を実態（R4 の後の接続断は `false`）に合わせ、外側の catch を通っていないことをアサートで確かめる形にした。
外側の catch の後半は**防御的なコードで、テストで到達を確かめたものではない**ことをコードのコメントに明記した。
**到達できない分岐を「検証済み」と名乗るテストを残さない。**

### 2. 偽物と本物の食い違いが 1 点残っていた（`spec-verifier` 軽微-2）

**本物の fetch（Node v24.16.0 で実測）は、ヘッダを受け取った後で signal が abort されると、本体を全部受信済みでも読み込みが reject する。**
偽物の `new Response()` の本体は signal と結びついておらず、最後まで読めていた。

**処置**：(a) 本物がそう振る舞うことを確かめるテストを conformance に 8 件足した。
(b) 偽物（`test-support/instagram-graph.ts` の `toResponse`）の本体を signal と結びついた stream にし、本物と揃えた。
あわせて「R4 の応答のヘッダの後、本体を読み切る前に合計の期限が発火すると `retryable: false`」を足した（**二重投稿の向きに倒れないこと**の確認）。

**#50（失敗した子が混在する carousel）の期待値は変わらなかった。** 偽物では応答がすぐ返るので、打ち切りが発火する前に 3 本とも本体を読み終えている。
**ただし「ヘッダの後に打ち切られた子は失敗に数えない」経路には、今の #50 の偽物では入らない**（§5 の 2）。

### 4. Core 側で見つかったもの（この作業単位では直さない）

**security 低-1：`rotatedCredential` の書き戻しが運用者の変更を上書きしうる。**
配信中（最長 25 秒）に運用者が資格情報を差し替えると、配信成功後の延長が古い資格情報で上書きする。以後の投稿は旧アカウントへ出る。
攻撃者が起こせるものではなく、運用者の操作と配信が重なったときの事故。**この経路を使う最初の Plugin が 038** なので、ここで初めて表に出た。
直すには Core の書き戻しを比較更新にする必要があり、**035 の範囲の変更**になる。`035` §11 #25 に記録した。
