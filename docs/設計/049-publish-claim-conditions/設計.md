## 1. 目的

### 1.1 何が起きるか

配信ジョブ（`application/social/publish.ts` の `publishDuePosts`）は 1 回の実行を次の順で進める（`035` §6.5.2）。

1. 中断した行を `failed` にする（`failInterrupted`）
2. **期限の来た自動配信の行を読み進め、列（`ready`）を作る**（`listDue`）。配信の支度ができていない行はこの場で後ろへ送る（`deferSkipped`）
3. **列の行ごとに、直列に**、着手印を立て（`claimForPublish`）、`publish()`（最長 30 秒）を呼び、結果を書く（`recordOutcome`）

3 は 1 行の `publish()` を待ってから次の行へ進むので、列の末尾の行は最長で約 10 分（20 行 × 30 秒）待つ。
**その間にその行へ `PATCH` がコミットされうる。** ところが `claimForPublish` の UPDATE は `status = 'scheduled'`・
`publish_started_at IS NULL`・`next_attempt_at` が無いか過去、の 3 つしか見ておらず、`listDue` が見ている
`delivery_mode = 'auto'` と `scheduled_at IS NOT NULL AND scheduled_at <= now()` を見ていない。そのため、

* 承認を経ていない予約へ **`PATCH { scheduledAt: <未来> }`** がコミットされても、ジョブは着手して**その場で送る**。
  利用者は「後で出す」と言ったのに、いま出る
* 同じく **`PATCH { deliveryMode: 'manual' }`** がコミットされても着手して送る。行は手動投稿になっているので、
  画面の「手動投稿待ち」に並び、**人が後で手で出せば二重投稿になる**（SNS の投稿は取り消せない。`035` 要件 §4 裁定 #1）
* `PATCH { status: 'draft' }` の後に `PATCH { status: 'scheduled', scheduledAt: <未来> }` で予約し直した場合も、
  状態は `scheduled` に戻っているので着手して即時に送る

承認を経た予約（`approvedAt` あり）は、日時・配信方法を書き換えると承認待ちへ戻って `status` が変わるので、
`status = 'scheduled'` の条件で弾かれる（`048` §6.3.3・§6.3.6）。**ただし承認待ちへ戻った後、ジョブが着手する前に
人が「指定の時間（未来）」で承認し直すと、`status` は `scheduled` に戻り、やはり即時に送る**（承認した人が選んだ時刻を守らない）。

同じ形の穴が、2 で後ろへ送る `deferSkipped` にもある（§1.2 の 2）。こちらは窓が短い（読んだページを判定する間だけ）が、
手動投稿へ変えられた予約の `skip_count` を増やし、3 回目には **手動投稿の予約をジョブが `failed` にする**（「ジョブは手動投稿を一切触らない」`035` §6.5.3 に反する）。

### 1.2 調査の結果（2026-10-01。コードを読んで確かめた）

**1. 着手（`claimForPublish`）は取り出しの条件の一部しか見ていない。**

| 条件 | `listDue`（`infrastructure/social-repository.ts:675-687`） | `claimForPublish`（同 `:742-775`、WHERE は `:759-769`） |
| --- | --- | --- |
| `status = 'scheduled'` | ○ | ○ |
| `delivery_mode = 'auto'` | ○ | **×** |
| `publish_started_at IS NULL` | ○ | ○ |
| `scheduled_at IS NOT NULL AND scheduled_at <= now()` | ○ | **×** |
| `next_attempt_at IS NULL OR next_attempt_at <= now()` | ○ | ○（`035` 4 回目の検証の低-1 で足した。§6.5.4） |

* ジョブは `ready` の行を `for (const row of ready)` で直列に回し、行ごとに `claimForPublish` を呼ぶ（`application/social/publish.ts:995-1033`）。
  呼ぶ直前に行を読み直さない。着手できた行（`claimed`）は UPDATE の `RETURNING` なので内容は新しいが、**着手してよいかの判定は UPDATE の WHERE だけ**が担っている
* `035` 設計 §6.5.2（`docs/設計/035-social-publishing/設計.md:1157`）は「着手印（b）は 3 で改めて条件つき UPDATE を打つので、
  2 と 3 のあいだに人が触った行は 0 行で弾かれる」と書いているが、**弾かれるのは `status` を変えた `PATCH` だけ**で、
  `scheduledAt` と `deliveryMode` の `PATCH` は `status` を変えないので弾かれない
* `PATCH` 側には着手の前に止める仕組みが無い。配信中のガード（`application/social/social-use-cases.ts:1052-1063`、対象の項目は `:988-996` の
  `PUBLISH_GUARDED_FIELDS`）は**着手印が立った後**の行だけを断る。`048` で足した条件付きの書き込み（`:1159-1205`、Repository は `:477-541`）も
  「読んでから書くまでに着手された」ことしか見ない。**着手の前に `PATCH` が先にコミットされた場合は、どちらも何もしない**（正しい振る舞いで、直すのはジョブの側）

**2. 支度待ちへ送る（`deferSkipped`）も同じ。**

* 2 の走査は `listDue` の 1 ページ（最大 20 行）を読み、行ごとに `findAccountById`（キャッシュが無ければ 1 回の SELECT）を経て
  `deferSkipped` を呼ぶ（`publish.ts:864-893`・`:941-972`）。WHERE は `status = 'scheduled' AND publish_started_at IS NULL` だけ（`social-repository.ts:732-735`）
* その間に**手動投稿へ変えられた**行（資格情報が未設定で `credential_missing` として飛ばされる行。配信 Plugin が `manual()` を持てば `PATCH` で手動投稿にできる）：
  `skip_count` が増え、`skip_reason` と `next_attempt_at` が書かれる。`skip_count` が 2 の行なら **`status = 'failed'`・`failure_reason` が
  「約24時間が過ぎたため取りやめました」になり、`social.post.failed` が発火する**。手動投稿の予約をジョブが取りやめる
* その間に**予約日時を未来へ直された**行：`PATCH` は待ち時刻を消す（`clearsSkipWait`。`social-use-cases.ts:617-622`・`:1201`）のに、
  直後の `deferSkipped` が `next_attempt_at = now() + 1 時間` を書き戻す。直した予約日時が 1 時間以内なら**指定した時刻に出ない**
  （`035` 裁定 #14-a が塞いだのと同じ症状）。`skip_count` も、期限の来ていない予約に対して 1 つ増える（3 回目なら未来の予約を取りやめる）
* `decideSkipOutcome`（`domain/social/publishing.ts:294-319`）が使う `skipCount` / `skipReason` は走査で読んだ値だが、
  これらを書くのはジョブ（同時に 1 つしか走らない）と `claimForPublish` だけで、`PATCH` は触らない（裁定 #14-a）。**古い値で上書きする問題は無い**

**3. 0 行のときのジョブの振る舞いは既に「黙って飛ばす」。**

* 着手が `null` なら `continue` するだけで、`attempted` にも内訳にも数えず、ログもイベントも出さない（`publish.ts:1000-1004`）
* 後ろへ送るのが 0 行なら `return` するだけで、`skipped` / `skipFailed` に数えない（`publish.ts:870-874`）
* `summary.due` は走査の時点で数えているので、こうした行は `due` にだけ入る。`035` §6.5.7 は不変条件を
  `due >= skipped + skipFailed + attempted`（**着手印の `UPDATE` が 0 行だった行はどれにも入らない**）と決めてあり、
  `POST /api/v1/social/publish` の応答（`app/api/v1/social/publish/route.ts`）も `summary` の 9 キーを写すだけ

**4. Domain には同じ判定の純関数がある。** `isDue`（`domain/social/publishing.ts:103-121`）は「`035` §6.5.3 の SQL と同じ判定」で、
5 つの条件をすべて見ている。**本番のコードからは呼ばれていない**（テストだけが使う。SQL の条件の写しとして置かれている）。

### 1.3 書き込み経路の洗い出し

ジョブ（`publishDuePosts`）が `social_posts` に書く経路はこの 4 つ。ほかに `replaceCredentialIfUnchanged`（`social_accounts` への比較更新。§6.4）がある。

| 経路 | 書く行の選び方 | 前に作った列の行に書くか | 本設計 |
| --- | --- | --- | --- |
| `failInterrupted`（`social-repository.ts:636-660`） | 自分の WHERE（`status = 'scheduled' AND delivery_mode = 'auto' AND publish_started_at IS NOT NULL`）で 1 文 | **書かない**（列を使わない） | 変えない（§6.4.1） |
| `deferSkipped`（`:708-740`） | 走査で読んだページの行（`id`） | **書く**（読んだページ → 判定 → 書く） | **述語を掛ける**（§6.3） |
| `claimForPublish`（`:742-775`） | `ready` の行（`id`） | **書く**（列 → 前の行の `publish()` を待つ → 書く） | **述語を掛ける**（§6.2） |
| `recordOutcome`（`:777-820`） | 自分が着手した行（`id`） | 着手した行に書く（着手の後は配信中のガードが `PATCH` を断る） | 変えない（§6.4.2） |

手動投稿の経路（`listManualPending`・`resolveManualHandoff`）は画面からの読み取りで、ジョブは手動投稿の行に書かない。
人が手で出した結果は `PATCH`（`updateSocialPost`）で記録する。`approvePost` は承認の操作で、ジョブの経路ではない。

## 6. ジョブと Repository（決めたこと）

### 6.1 述語 `dueForAutoPublish`（単一の正）

`infrastructure/social-repository.ts` に、`listDue` の今の条件（`:678-687`）をそのまま切り出した関数を置く。
`listManualPending` が `conditions(eb)` で条件を共有している（`:554-561`）のと同じ流儀。

```ts
/**
 * 自動配信の期限が来ている（035 §6.5.3 の取り出し条件。049）。
 *
 * **`listDue`・`deferSkipped`・`claimForPublish` が同じものを使う。** 列を作ってから書くまでに
 * `PATCH` で予約日時を未来へ直された・手動投稿へ変えられた行に書かないため、書く側も取り出しと同じ条件を
 * **同じ 1 文の中で**見る。Domain の `isDue` が同じ判定の純関数。
 */
function dueForAutoPublish(eb: ExpressionBuilder<Schema, 'social_posts'>): Expression<SqlBool> {
  return eb.and([
    eb('status', '=', 'scheduled'),
    // 手動投稿はジョブが一切触らない（035 §6.5.3）。
    eb('delivery_mode', '=', 'auto'),
    eb('publish_started_at', 'is', null),
    // 022 より前に作られた「予約日時の無い予約」は、これまでどおり誰も取り出さない。
    eb('scheduled_at', 'is not', null),
    eb('scheduled_at', '<=', sql<Date>`now()`),
    eb.or([eb('next_attempt_at', 'is', null), eb('next_attempt_at', '<=', sql<Date>`now()`)]),
  ]);
}
```

* **`listDue`** は `.where(dueForAutoPublish)` に置き換える。カーソルの比較（`:691-695`）・並び・`LIMIT` はそのまま。生成される SQL の条件は今と同じ
* 述語は**関数**にする（定数の配列にしない）。`now()` を文ごとに DB で評価させるため、値を JavaScript 側で作らない
* 名前を変えるのは自由だが、**3 つのメソッドが同じ 1 つを参照する**ことは変えない（受け入れ条件 #24 が固定する）

### 6.2 `claimForPublish`

```sql
UPDATE social_posts
   SET publish_started_at = now(), attempt_count = attempt_count + 1, next_attempt_at = NULL,
       skip_count = 0, skip_reason = NULL, updated_at = now()
 WHERE id = $id
   AND status = 'scheduled'
   AND delivery_mode = 'auto'                                   -- 049 で足す
   AND publish_started_at IS NULL
   AND scheduled_at IS NOT NULL AND scheduled_at <= now()       -- 049 で足す
   AND (next_attempt_at IS NULL OR next_attempt_at <= now())
RETURNING *;
```

* `SET` は変えない。WHERE を `.where('id', '=', id).where(dueForAutoPublish)` にする
* 自分のトランザクションでコミットしてから返すこと（`035` §6.5.4）、形の合わない `id` は `null`（`:743`）は変えない
* 当たらなければ `null`。ジョブは今までどおり黙って次の行へ進む（§6.5）

### 6.3 `deferSkipped`

```sql
UPDATE social_posts
   SET skip_count = $n, skip_reason = $reason, updated_at = now(),
       next_attempt_at = $next                                  -- deferred のとき
       -- status = 'failed', failed_at = now(), failure_reason = $f, next_attempt_at = NULL  -- failed のとき
 WHERE id = $id
   AND <dueForAutoPublish>                                      -- 049 で status・publish_started_at の 2 条件から置き換える
```

* `SET` は変えない。WHERE を `.where('id', '=', id).where(dueForAutoPublish)` にする
* **`next_attempt_at` の条件も入る。** 走査で後ろへ送るのは `listDue` が返した行（待ち時刻が無いか過去）だけなので、通常の流れでは結果が変わらない。
  入れておくと、同じ実行の中で同じ行を二度後ろへ送ること（`skip_count` を一度に 2 つ増やすこと）も 0 行で弾かれる
* 当たらなければ 0。ジョブは今までどおり何もしない（`skipped` / `skipFailed` に数えず、`social.post.failed` も `log.error` も出さない。§6.5）
* **3 回上限の回避路は開かない。** 弾かれるのは「書く時点で期限の来た自動配信の予約でなくなった」行だけで、その行は数えないのが正しい
  （手動投稿・未来の予約を支度待ちとして数える理由が無い）。期限の来た自動配信の予約に戻れば、次に見た周期で数える。
  `PATCH` は `skip_count` / `skip_reason` を減らさない（裁定 #14-a）ので、予約し直しで回数が戻ることも無い

### 6.4 述語を掛けないもの

#### 6.4.1 `failInterrupted`

前に作った列を使わず、自分の WHERE で 1 文で判定して書く。**期限が来ているかを見てはならない。** 着手印の残った行は、
予約日時がいつであれ、前の実行が `publish()` の途中で死んだ行で、`failed`（結果不明）に落とす必要がある（`035` §6.5.4）。
着手印が立った後は配信中のガードが `scheduledAt` / `deliveryMode` の `PATCH` を断るので、手動投稿の行に着手印が残ることも無い。

#### 6.4.2 `recordOutcome`

**SNS へ送った後の記録で、条件を足すと起きたことが記録されなくなる。** 着手した行に `published` を書けなければ
`unrecorded` になり、次の実行で「中断」の `failed` に落ちる（実際には投稿されている）。

* 着手の後は、配信中のガード（`PUBLISH_GUARDED_FIELDS`）と `048` §6.3.6 の条件付きの書き込みが、`scheduledAt` / `deliveryMode` / `status` の
  `PATCH` を 422 / 409 で断る。本体の経路では、着手した行の予約日時・配信方法は結果の記録まで変わらない
* 仮に変わっても（DB を直接書き換えた場合など）、送った事実は記録する。今の WHERE（`status = 'scheduled' AND publish_started_at IS NOT NULL`）のまま
* 受け入れ条件 #21 がこの判断を固定する（後から誰かが述語を `recordOutcome` にも掛けると落ちる）

#### 6.4.3 そのほか

* `replaceCredentialIfUnchanged`：アカウントの資格情報の比較更新（`039` §6.1）。投稿の行を選ばないので関係しない
* `listManualPending`：読み取り。条件（`delivery_mode = 'manual'`）は自動配信の述語の補集合で、共有しない
* `updatePost`（`PATCH`）・`approvePost`（承認）：人の操作。`048` §6.3.6・§6.4.6 の条件のまま

### 6.5 0 行になったときのジョブの振る舞い

**今までどおり黙って飛ばす。** `publish.ts` の処理は変えない（`claimForPublish` の `null` → `continue`、`deferSkipped` の 0 → `return`）。
コメント（`:998-1003`・`:871-873`）を「`PATCH` で予約日時・配信方法・状態が変わった行は 0 行で弾かれる」に直すだけ。

| 項目 | 振る舞い |
| --- | --- |
| `publish()` | 呼ばない |
| 行 | 何も書かない（`attempt_count`・`skip_count`・`skip_reason`・`next_attempt_at`・`updated_at` も変わらない） |
| `summary` | `due` にだけ入る（走査で数え済み）。`attempted`・`skipped`・`skipFailed`・`failed`・`unrecorded` には入らない。キーは 9 つのまま |
| ログ | 出さない |
| イベント | 出さない（`social.post.published` / `social.post.failed` のどちらも） |
| `POST /api/v1/social/publish` の応答 | `summary` の写しなので同じ（形も変わらない） |

* **失敗として数えない。** 行は人が「まだ送らない」と決めたもので、ジョブの失敗ではない。`failed` に入れると運用者が SNS 側を確かめに行くことになる
* **キーを足さない。** `035` §6.5.7 が `due - skipped - skipFailed - attempted` の差を「着手印の `UPDATE` が 0 行だった行」と決めてあり、
  意味がそのまま当てはまる。キーを足すと `publishSummarySchema`（OpenAPI）が変わる
* **ログを足さない。** 人の正当な操作で、運用者が対処することは無い。行の今の状態は投稿一覧で見える

### 6.6 時刻と並行性

* **`now()` は DB が同じ文の中で評価する。** JavaScript の `Date` を条件に使わない。`claimForPublish` / `deferSkipped` は 1 文だけのトランザクションなので、
  `now()`（トランザクションの開始時刻）は文の時刻と同じ
* **普通の行の結果は変わらない。** 走査の `listDue` で期限が来ていた行は、後の `claimForPublish` の `now()` でも期限が来ている（`now()` は進む向きにしか動かない）。
  `scheduled_at` を書き換えない限り、新しい条件で弾かれる行は無い
* **`PATCH` と着手のどちらが先でも安全。**
  * `PATCH` が先にコミット → 着手の UPDATE は新しい行を見て 0 行（本設計）
  * 着手の UPDATE が `PATCH` の行ロックを待つ → READ COMMITTED では、待った UPDATE は WHERE を**最新の行で評価し直す**ので 0 行（`048` §6.3.6 と同じ仕組み）
  * 着手が先にコミット → `PATCH` は配信中のガードで 422、読んでから書くまでの着手なら `048` §6.3.6 で 409
* **精度**：条件は DB の中で `timestamptz` どうし（`scheduled_at` / `next_attempt_at` と `now()`）を比べ、ミリ秒への切り詰めは関係しない。
  ただし**書き込む待ち時刻**（`next_attempt_at`）は、`035` からアプリの時計（`new Date(now + delay)`）で作っている。アプリの時計が DB より
  60 秒以上遅れていると、再試行の行が同じ実行の中でもう一度条件に当たりうる（同じ行が列に二度積まれる稀な場合だけ。検証の低-1。本件では変えず記録する。§11）

### 6.7 互換性

| 対象 | 影響 |
| --- | --- |
| HTTP API（`PATCH /social/posts/{id}`・`POST /social/publish` ほか） | 要求・応答の形は変わらない。OpenAPI も変わらない |
| 外部アプリから見える振る舞い | **予約日時を未来へ直した・手動投稿へ変えた・取りやめてから未来へ予約し直した予約は、配信ジョブがその周期の列に並べた後でも送られなくなる。** 今までは「`PATCH` が 200 を返したのに、直前の内容（日時・配信方法）のまま即時に出る」ことがあった。正しく使っているアプリが困る変化は無い |
| `POST /social/publish` の件数 | 形は同じ。こうした行は今までどおり `due` にだけ入る（今までは送られて `attempted` / `published` に入っていた） |

### 11.2 設計で決めず、後の判断に回すもの（記録のみ）

1. **列を作った後のアカウント・publisher の変化**（§3「やらないこと」）：走査で読んだアカウント（資格情報の設定の有無）と publisher（`publish` の関数）は着手まで持ち回る。
   その間に運用者が資格情報を消すと、その行は「支度待ち」ではなく `failed`（`資格情報が設定されていません。`。未送信）になる。
   Plugin を無効にしても、その実行の中では持ち回った `publish` が呼ばれる（`035` §6.5.2 が許した範囲）。どちらも二重投稿・意図しない時刻の送信にはならないので本設計では扱わない
2. **0 行で飛ばした件数を `summary` に出すか**：今は `due` との差でしか読めない（§6.5）。運用で「なぜ送られなかったか」を件数で知りたくなったら、キーを足す（`publishSummarySchema` の追加。後方互換）

### 11.3 検証で記録したもの（2026-10-01）

* 待ち時刻（`next_attempt_at`）をアプリの時計で書き、比べるのは DB の時計（§6.6。`035` から）。厳密にするなら SQL で `now() + interval` として作る。本件の範囲外
