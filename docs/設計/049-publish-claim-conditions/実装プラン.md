### テストの方法（設計書に無い、プラン側で決める手段）

* **配置の作り方**：「期限の来た自動配信の予約」は `createSocialPost`（`status: 'scheduled'`・`deliveryMode: 'auto'`・過去の `scheduledAt`）で作る。設計が「SQL で直接作る」と書いた配置（`scheduled_at` が NULL、`publish_started_at` あり、`status` が `published` / `failed` / `awaiting_approval` など）と、時刻の書き換え（`scheduled_at = now() + interval '1 hour'` など）は `sql` で直接書く。CHECK（`approved_at` は `draft` / `awaiting_approval` で NULL）に合わせる
* **列の並び**：(i) の割り込みでは A の `scheduledAt` を 2 時間前、B を 1 時間前にして A を列の先頭に置く。**#10・#12〜#16 は `summary.due === 2` も見る**（B が列に並んだ＝割り込みが「列を作った後」に起きたことの確かめ。§8 の 3）
* **(i) の割り込み**：偽の publisher の `publish` を `vi.fn` にし、受け取った `post.id` が A のときだけ、`updateSocialPost(admin, …)`（`approveSocialPost` を含む）を `await` してから成功を返す。UseCase は自分で接続を取ってコミットするので「ジョブとは別の接続でコミット」になる
* **(ii) の割り込み**：`048` の結合テストの流儀（§1 の確認結果）。元の関数は spy の**前に** `bind` して取っておき、`mockImplementation` の中で `PATCH` を `await` してから元の関数を呼ぶ。`afterEach` で `vi.restoreAllMocks()`
* **「行が変わらない」の見方**：書き込みの前に `social_posts` の対象列（`publish_started_at`・`attempt_count`・`next_attempt_at`・`skip_count`・`skip_reason`・`updated_at`、#6〜#8 は `status`・`failed_at`・`failure_reason` も）を SQL で読み、呼んだ後に同じ列を読んで `toEqual` で比べる。`updated_at` も含める（0 行の UPDATE は `updated_at` も書かない）
* **#9 の突き合わせ**：配置ごとに**2 行**（`claimForPublish` 用と `deferSkipped` 用）を作り、書き込みの前に 2 行とも `isDue(findPostById の行, new Date())` と「`listDue(connection, 200)` の `id` の集合に含まれるか」を取る。その後に片方へ `claimForPublish`、もう片方へ `deferSkipped`（`{ kind: 'deferred', skipCount: 1, reason: 'no_publisher', nextAttemptAt: 1 時間後 }`）を呼び、4 つ（isDue・listDue・掴めたか・1 を返したか）が配置の期待値（真 2 配置・偽 9 配置）と一致することを `it.each` で見る。時刻は ±1 時間で置く（設計 #9）

## 3. タスク分解

原則：**1 タスク = 1 コミット**。G1 の最後で `pnpm test` / `pnpm typecheck` / `pnpm lint` / `pnpm format:check` が通る。E2E は T6 でだけ全件流す。

**test-writer → implementer への受け渡しの単位は G（まとまり）。** test-writer は G1 の全テスト（と #25 の追加）を先に書いて失敗を確かめ、`test:` でコミットする。implementer は T2〜T4 を順に通し、タスクごとにコミットする。
**implementer はテストを書き換えない。** テストが設計と食い違うと判断したら、設計書のどこと食い違うかを報告して止まる。

**着手順の骨子**：テスト（赤）→ 述語の切り出し（振る舞いを変えない）→ 着手に掛ける → 支度待ちに掛ける → 文書 → 最終確認 → 3 つの検証。
