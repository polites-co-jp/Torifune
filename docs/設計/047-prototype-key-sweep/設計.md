## 1. 目的

### 1.1 何が起きるか

JavaScript の素のオブジェクト（`{}`・`Object.fromEntries(...)`・`JSON.parse` の結果）は `Object.prototype` を継承する。
キーが `constructor`・`toString`・`valueOf`・`hasOwnProperty` などのとき、`obj[key]` は**そのオブジェクトに無くても関数を返す**。

* `(obj[key] ??= []).push(x)`：`obj['constructor']` が `Object` 関数なので `??=` が代入せず、`.push` が無くて **TypeError**
* `obj[key]?.includes(x)`：`?.` は `Object` 関数を通すので、`includes` が無くて **TypeError**
* `obj[key] ?? 既定値`：`??` は関数を通すので、**表示に `function Object() { [native code] }` が出る**か、React が関数を子として描かず空欄になる
* `obj[key] = 値`（キーが `__proto__`）：値が文字列なら**黙って落ちる**。値がオブジェクトなら、その辞書の原型が差し替わって**その項目が消える**（`Object.prototype` そのものは汚れない）

## 3. スコープ

### やること

1. Domain に `ownValue` を足す（§4.1）
2. K1：`allGrants` を `Map` に積み、`Object.fromEntries` で返す
3. K2〜K6：読む側を `ownValue` に替える（`permission-matrix.tsx`・`social.ts` の `providerLabel`・`social-accounts.tsx` の 2 か所・`social-posts.tsx` の `publisherProviders`・`permission.ts` の `describePermission`）
4. K17：`openapi.ts` の `paths` を `Map` に積んで `Object.fromEntries` で返す（出力は同じ）
5. 静的検査（§10 #12）：角括弧で引いた先を `??=`・`||=` で空の配列・オブジェクトに初期化する形を、テスト以外のソースで禁じる

### やらないこと（理由つき）

* **K7（`/auth/callback`）**：値は常に文字列なので原型は差し替わらず、`__proto__` という名前が落ちるだけ。Core は名前を読まない。直すと認証の Plugin に渡す `params` の中身が変わる（`__proto__` が自分のキーとして届く）ので、観測できる不具合の無いまま Plugin への入力を変えない
* **K8（`searchParamsToObject`）**：本番の呼び出し元が無い。消すのは本件の範囲外
* **K9・K10（ログの伏せ字）**：自分のキー `__proto__` の部分木が出力から消えるだけで、伏せ字は掛かったまま・`Object.prototype` は汚れない（確かめた）。値を渡すのは Core と信頼された Plugin
* **K12・K13（Plugin が宣言した項目名）**：Plugin が `constructor` などを項目名に宣言したときだけ起きる。Plugin は信頼されたコードで、その宣言の誤りは Plugin 側で直す（`validateManifest` と同じ扱い）
* **名前の拒否リスト**：`isValidProvider`・`roles` の CHECK に原型の名前を足すことはしない（§11 の 1）
* **定数の表（K21）の書き換え**：キーが閉じているので害が無い。規則（§4.1）の対象外
* ロールの作成・編集の画面や API を足すこと（`015` の判断のまま）

## 4. レイヤ配置

### 4.1 規則と部品

**規則**（外から影響を受けるキー＝HTTP の入力、HTTP で書ける DB の値、運用者が DB に直接書ける値、Registry の配信内容）

1. **引く**ときは、自分のプロパティだけを見る。`Map` を使うか、素のオブジェクトなら `ownValue(辞書, キー)` を通す。`obj[key]`・`obj?.[key]`・`key in obj` で直接引かない
2. **作る**ときは、`Map` に積むか `Object.fromEntries` で作る。素のオブジェクトへ代入で作らない。特に「無ければ空の配列・オブジェクトを置いてから足す」（`(obj[key] ??= []).push`）を素のオブジェクトで書かない
3. 返す形がオブジェクトである必要があるとき（型が `Record`、React の props、JSON の応答）は、`Object.fromEntries` で作る。`__proto__` も自分のプロパティになる

**部品**：`apps/web/src/domain/own-value.ts`（新規）

```ts
/** 辞書の自分のプロパティだけを返す。継承したもの（`constructor`・`toString` など）は `undefined`。 */
export function ownValue<T>(
  dictionary: Readonly<Record<string, T>> | undefined,
  key: string,
): T | undefined;
```

* `dictionary` が `undefined` なら `undefined`（`overrides?.[provider]` の置き換えに使う）
* `Object.hasOwn(dictionary, key)` が真なら `dictionary[key]`、偽なら `undefined`
* 純関数。DB 製品・外部サービスに依存しない

**`Map` にしない理由（K2〜K5）**：辞書は Server Component から Client Component へ props で渡る（`grants`・`providers` から作る表・`publisherProviders`）。
`Record` の型を変えると呼び出し側と既存のテストの形が広く変わる。読む側を `ownValue` に替えれば、型を変えずに規則を満たせる。

## 10. 受け入れ条件

**A = 単体（純関数・`renderToStaticMarkup` で描く部品）、B = 結合（DB を通す。UseCase）、C = API（Route Handler を直接呼ぶ。DB あり）、E = 静的検査。D（E2E）の条件は無い（§10.3）。**
「原型の名前」は `constructor`・`toString`・`valueOf`・`hasOwnProperty`・`__proto__` の 5 つ。

### 10.1 部品と表示（A）

1. (A) `ownValue`：`{ a: 1 }` の `'a'` → `1`。同じ辞書の原型の名前 5 つ → すべて `undefined`。`Object.fromEntries([['constructor', 2]])` の `'constructor'` → `2`、`Object.fromEntries([['__proto__', 3]])` の `'__proto__'` → `3`。
   `Object.create(null)` に `a: 4` を置いた辞書の `'a'` → `4`。辞書が `undefined` → `undefined`
2. (A) `providerLabel`：`('constructor')`・`('constructor', {})`・`('constructor', { x: 'X' })`・`('toString', { x: 'X' })` → 引数の provider そのもの（`typeof` が `'string'`）。
   従来どおり：`('x')` → `'X'`、`('x', { x: 'X（登録）' })` → `'X（登録）'`、`('unknown_sns')` → `'unknown_sns'`、`('constructor', Object.fromEntries([['constructor', 'C']]))` → `'C'`
3. (A) `describePermission`：原型の名前 5 つ → すべて `null`。`'site.read'` → 従来の説明の文字列。
   `PluginManager` を、`permissions: ['toString', 'constructor', 'site.read']` の導入済みの行で描くと、`toString`・`constructor` の `<li>` に説明の区切り ` — ` が無く、`site.read` の `<li>` にはある。描画中に `console.error` へ `Functions are not valid as a React child` が出ない
4. (A) `PermissionMatrix`：`roles` に `constructor` を含め、`grants` にそのキーが無い（標準の 3 ロールだけの）辞書で描くと例外を投げず、`constructor` の列はすべて「なし」。
   `grants` が `Object.fromEntries` で作った `{ administrator: [...], constructor: ['site.read'] }` なら、`site.read` の行の `constructor` の列が「あり」、ほかの行は「なし」
5. (A) `SocialAccounts`：provider が `constructor` の行（`providers` は `buildProviderOptions([])`）を描くと、「サービス」列が `constructor`、HTML に `function Object` が無く、`console.error` に `Functions are not valid as a React child` が出ない。
   `initialEditingAccountId` でその行の Modal を開いて描くと `対象：<表示名>（constructor）`。従来どおり：provider が `x` の行は `X`
6. (A) `SocialPosts`：`scheduled`・`auto` の投稿で、アカウントの provider が `constructor` のとき、`publisherProviders` が `{}` なら「配信の支度ができていない」の Badge が出る（`no_publisher` の文言）。
   `publisherProviders` が `Object.fromEntries([['constructor', { label: 'C', manual: false, publish: true, credentialFieldKeys: [] }]])` なら Badge が出ない。
   **注**：前半は変更前も通る（`Object` 関数に `publish` が無いので偶然 `no_publisher` になる）。回帰の守りとして置く

### 10.2 ロールの grants（B）

7. (B) 標準の 3 ロールだけのとき、`listRoleGrants` のキーが `administrator`・`editor`・`viewer`（この順）で、各値が `role_permissions` をそのロールで絞って `permission_name` の順に並べたものと等しい（従来どおり）
8. (B) `roles` に `constructor` を直接入れて `site.read` を付けると、`listRoleGrants` が例外を投げず、`Object.hasOwn(grants, 'constructor')` が真で値が `['site.read']`、キーの順が `administrator`・`constructor`・`editor`・`viewer`、ほかの 3 ロールの値が #7 と同じ
9. (B) Permission を持たない `constructor` のロールを入れると、`listRoleGrants` の結果に自分のキー `constructor` が無く、`listRoles` には `constructor` が現れる（#4 の前半の前提）
10. (B) 前提の記録：`roles.name` に `__proto__`・`toString`・`valueOf`・`hasOwnProperty`・`isPrototypeOf` を入れると CHECK 違反で入らない。`constructor` は入る（原型の名前で届くのは `constructor` だけ。§1.2）

### 10.3 API（C）

## 13. リスク

1. **規則の対象の見落とし**：将来、外から影響を受けるキーで素のオブジェクトを引く箇所を足すと再発する。#12 はグループ化の形（`??= []`）だけを機械で止め、引く形（`obj[key] ?? 既定値`）は止めない（定数の表の正しい使い方と区別できず誤検知が多い）。
   新しい辞書を書くときは §4.1 を見ること
2. **`ownValue` の型**：`Readonly<Record<string, T>>` を受けるので、`Record<'a' | 'b', T>` の定数の表（`PERMISSION_DESCRIPTIONS` など）はそのまま渡せる（型の別名の `Record` は文字列の添字の型へ代入できる。確かめた）。`describePermission` の `as Record<string, string>` の付け替えは要らなくなる
3. **Client Component への Domain の import**：`own-value.ts` は依存を持たない純関数なので、ブラウザ向けの束に DB 製品などが混ざらない（`next build` で確かめる）
4. **K1 の順**：`Map` の挿入順は SQL の `ORDER BY roles.name` の順なので、`Object.fromEntries` の結果のキーの順は従来と同じ（#7・#8）
