## 7. リスクと注意点

1. **#12 の `withoutComments` の限界**：`//.*$` で行の末尾を落とすので、文字列の中の `//`（URL）より後ろは走査から漏れる。`application/analytics/static-checks.test.ts` の既存の形を写し、漏れは受け入れる（対象の形が URL の後ろに来ることは無い）
2. **#12 の除外の過不足**：`apps/web/src/plugin/generated-registry.ts` は `pnpm generate:plugins` の生成物で Git 管理外。在っても無くても結果が同じになるよう除外する。`dist`・`node_modules` を辿らない
3. **#4・#5 の `console.error` の拾い方**：`vi.spyOn(console, 'error')` を各件の中で作って戻す。拾った文言に `Functions are not valid as a React child` が無いことを見る（React の開発時の警告。`renderToStaticMarkup` でも出る。設計 §1.2 で確かめた）
4. **#8 の後始末**：`constructor` のロールを残すと、同じデータベースの他の件（#7 のキーの順）が崩れる。各件の `afterEach` で自分で入れた行を消す。データベースはファイルごとの `useScratchDatabase`
5. **`ownValue` の型**：`PERMISSION_DESCRIPTIONS`（`Readonly<Record<CorePermission, string>>`）はそのまま渡せる（設計 §13 の 2）。`overrides` の `Readonly<Record<string, string>> | undefined` もそのまま渡す
6. **`openapi.ts` の出力**：`Map` の挿入順で `Object.fromEntries` するので、`paths` のキーの順は従来と同じ（パスは `/` で始まり整数のキーにならない）。既存の OpenAPI のテストが無変更で緑であることで確かめる
7. **E2E**：新しい spec は無い。回帰で落ちたら、本件の差分（3 つの UI 部品）に関係するかを先に切り分ける（`046` の最終で `jobs.spec.ts` の同時実行の件が 1 度だけ落ちた前例がある）
