# SNS管理 実装プラン

入力：`設計.md`

## 1. 設計上の判断

### 1.1 `provider` を DB の CHECK 制約で固定しない

Plugin が新しいSNSを足せる必要がある（`03_プラグイン設計.md` §9）。
Core が知っている値は表示名の対応表として持つが、**未知の値も受け入れる**。

ただし**形式は制限する**（英小文字・数字・アンダースコア）。
任意の文字列を通すと、画面や URL で扱いにくくなる。

### 1.2 Entity に資格情報の平文を載せない

`SocialAccount` は `credentialConfigured: boolean` だけを持つ。
平文が要る処理は `findAccountWithCredential` を使い、`Secret` 型で受け取る。

**平文を Entity に載せると、一覧の応答やログに載る経路ができる。**

### 1.3 「指定しない」と「消す」を区別する

資格情報の更新で、`undefined` は「変えない」、空文字は「消す」。
区別しないと、**表示名だけ直したつもりで資格情報が消える。**

### 1.4 DB 側でも暗号化済みの形式を確かめる

`CHECK (credential IS NULL OR credential ~ '^v[0-9]+\.')`

アプリ側で暗号化しているが、平文をうっかり入れる経路を1つ塞ぐ。

### 1.5 復号できない資格情報を「無い」として扱う

例外にすると、**鍵を入れ替えた直後に一覧すら開けなくなる**。
`credentialConfigured` は真のまま、復号結果は `null` になる。

### 1.6 資格情報の読み出しに `social.write` を要求する

読めれば外部サービスで何でもできるため、`social.read` では弱すぎる。

### 1.7 存在しないアカウントへの投稿を 422 にする

FK 違反をそのまま通すと 500 になる。UseCase で存在を確かめて 422 を返す。

### 1.8 `published` / `failed` から戻せない

起きた事実は書き換えない。「配信した」を「下書き」に戻せると、記録が信用できなくなる。

**同じ状態への遷移は許す。** 本文だけを更新するとき、状態を触らない更新が弾かれないように。

### 1.9 画面に「配信はプラグインが行う」旨を出す

出さないと、**投稿したつもりで配信されていない**、という誤解が起きる。

## 2. 影響範囲

| 対象 | 影響 |
| --- | --- |
| `006-secret-storage` | 初めての実利用 |
| `007-sites` | 型を踏襲した |
| CI | **暗号鍵が 34 バイトで無効だった**（下記） |

**破壊的変更：なし**

## 3. CI の設定不備を発見した

CI の `TORIFUNE_ENCRYPTION_KEY` が 34 バイトで、鍵として無効だった。
`006-secret-storage` の「鍵が 32 バイトでなければ例外」という検証が効いて発覚した。

このスプリントまで暗号化を使う処理が無かったため、CI では気づけていなかった。
32 バイトの値へ修正した。

## 4. リスク

| リスク | 対応 |
| --- | --- |
| `expose()` の呼び出しが増える | いまは `readSocialCredential` の1箇所。S10 で Plugin へ渡すときに再検討する |
| 予約投稿が実行されない | Core の責務外。画面に明示した。実行は次計画のワーカー |
| provider の表示名が増え続ける | 対応表に無ければそのまま表示する。Plugin が表示名を登録できる口は S10 で検討 |
