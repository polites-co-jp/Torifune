# 015-settings 設定画面（ユーザー・権限）詳細設計

## 1. 目的

**インスタンス管理者が、自分以外の利用者を増やせるようにする。**

いま Torifune で利用者を作る手段は `/setup`（最初の1人）だけで、
2人目を作る経路が無い。API も画面も無く、`users.status` の `disabled` は
テーブルにあるだけで誰も使わない。

あわせて、`04_認証設計.md` §26 が挙げる監査イベントのうち、
定数だけあって発火箇所が無かった3つを繋ぐ。

## 2. 上位仕様との対応

| 文書 | 節 | 内容 |
| --- | --- | --- |
| `05_API設計.md` | §15 | User API。**パスワードHash等を応答に含めない** |
| 〃 | §30 | クライアントから受け取った User ID / Role / Permission でアクセス制御しない |
| `04_認証設計.md` | §14 | RBAC（User → Role → Permission） |
| 〃 | §26 | セキュリティログ。ユーザー作成 / ユーザー無効化 / パスワード変更 / Role変更 |
| 〃 | §28 | 権限昇格対策 |
| `06_画面設計.md` | §16 | 設定画面。今回は「ユーザー」「権限」の2タブ |
| 〃 | §37 | 危険な操作は確認ダイアログ |

## 3. スコープ

### やること

* User API：`/api/v1/users` の一覧・取得・作成・更新・削除
* 設定画面の「ユーザー」タブ：一覧・作成・編集・無効化・削除
* 設定画面の「権限」タブ：**参照のみ**（ロールと Permission の対応表）
* ユーザーへのロール割り当て・解除
* 監査ログ：`user.created` / `user.disabled` / `password.changed` の発火と、
  `role.changed` の追加・発火

### やらないこと

| 対象 | 理由 |
| --- | --- |
| 「一般」「認証」「API」タブ | `015b`。一般タブの項目が仕様に無く、決めるところから要る |
| `system.manage` を要求する UseCase | 消費先は一般タブ（システム設定）。`015b` へ持ち越す |
| Remember Me | `015b`。**方式はセッション延長で決定済み**（§9） |
| Data API の Users | `015b`。Plugin がユーザーを読む要求がまだ無い |
| カスタムロールの作成・編集 | ロールを編集できると自分へ権限を足す経路が生まれる。§8 |
| 監査ログの Permission変更 / 外部認証連携設定変更 | **その操作自体がまだ無い。** 操作を作るときに同時に足す |
| 自分のパスワード変更（現在のパスワード確認つき） | プロフィール画面の話。`015b` |

## 4. レイヤ配置

```text
apps/web/src/
├── domain/
│   ├── user.ts                  更新用の型と検証を足す
│   └── user-repository.ts       list / update / deleteById / ロール解除を足す
├── application/user/
│   └── user-use-cases.ts        UseCase 5種 ＋ ロール割り当て
├── infrastructure/
│   └── user-repository.ts       実装
├── api/schemas/user.ts          Zod スキーマと応答の形
├── app/api/v1/users/            Route Handler
└── app/settings/                タブと画面
```

## 5. データモデル

**マイグレーションは要らない。** `users` / `roles` / `user_roles` /
`role_permissions` は `001_initial.sql` で揃っている。

`users.status` は `active` / `disabled` の2値（`domain/user.ts`）。
**`disabled` のユーザーはログインできない**（`canSignIn` が既に判定している）。

## 6. API

```text
GET    /api/v1/users          一覧（Pagination / status 絞り込み / キーワード）
POST   /api/v1/users          作成
GET    /api/v1/users/{id}     取得
PATCH  /api/v1/users/{id}     更新（表示名 / メール / 状態 / パスワード / ロール）
DELETE /api/v1/users/{id}     削除
```

すべて `user.manage` を要求する。

### 応答の形

```ts
{ id, loginId, displayName, email, status, roles: string[],
  createdAt, updatedAt, lastLoginAt }
```

**`passwordHash` を含めない。** 型として持たせない（`toUserResponse` が選ぶ）。

### 並び替え

`created_at` / `login_id` / `display_name` / `last_login_at` のみ許す。
未許可の値は 422（`004-api-foundation` の共通実装）。

## 7. 画面

`/settings` にタブを置く。タブは URL のクエリ（`?tab=users`）で切り替える。
**Plugin が足すタブ（`settings.tabs`）は既存のまま**下へ並べる。

### ユーザータブ（型A）

一覧は Table＋Pagination。行に「編集」「削除」。

* 作成：ログインID / 表示名 / メール / パスワード / ロール
* 編集：表示名 / メール / 状態 / ロール / パスワード再設定（空なら変えない）
* 削除：確認ダイアログ。**ログインIDの入力を求めない**（Plugin 削除ほど不可逆ではない）

### 権限タブ

ロールを行、Permission を列にした対応表。**操作は無い。**
「ロールの編集は行えません」と明示する。

## 8. 権限昇格への防御（04_認証設計.md §28）

**この機能は権限昇格の入口になりうる。** 次を不変条件とする。

1. すべての UseCase が `user.manage` を要求する
2. **自分自身を無効化・削除できない。** 締め出しと、自分の権限を消して
   復旧できなくなる事故を防ぐ
3. **最後の administrator を無効化・削除できず、ロールも外せない。**
   `countByRoleForUpdate`（行ロックつきの件数取得）で数え、
   同一トランザクション内で判定する。`/setup` が使っているものと同じ
4. ロールはクライアントから受け取った名前で**存在を検証**してから割り当てる。
   存在しないロール名は 422
5. 無効化・削除・パスワード再設定では、**そのユーザーのセッションをすべて失効させる**
   （`revokeAllForUser`）。失効させないと、無効化しても開いている画面が動き続ける

## 9. Remember Me（`015b` で実装。方式のみ確定）

`04_認証設計.md` §11 は「長期セッションを利用する場合は、通常のセッションとは
異なるToken管理方式を**検討する**」としている。検討した結果、
**セッションの有効期限を延ばす方式を採る。**

* ログイン画面のチェックボックスで `expires_at` を長くする
* 別テーブルの永続トークンは作らない

**トレードオフを記録しておく。** 別トークン方式なら、使うたびに
ローテーションさせて盗難を検知できる。セッション延長にはそれが無く、
長期トークンが漏れたときの窓が長くなる。実装量と引き換えにこれを受け入れる。
再検討するのは、盗難検知が要る運用が出てきたとき。

## 10. 受け入れ条件

### 作成

1. ユーザーを作成できる
2. ログインIDが重複したら 409
3. メールが重複したら 409
4. ログインIDの形式が不正なら 422
5. パスワードが短すぎたら 422
6. **応答に `passwordHash` が含まれない**
7. ロールを指定して作成できる
8. 存在しないロール名を指定したら 422
9. **`user.created` が監査ログに残る**
10. 監査ログにパスワードが残らない

### 取得・一覧

11. 一覧が `{ data, meta }` の形で返る
12. `status` で絞り込める
13. キーワードでログインID・表示名・メールを検索できる
14. 並び替えが許可フィールドだけで動く
15. 未許可の並び替えは 422
16. 存在しないIDで 404
17. 不正な形式のIDで 404（500 にしない）
18. **一覧・単体のどちらの応答にも `passwordHash` が含まれない**

### 更新

19. 表示名・メールを更新できる
20. ロールを付け替えられる
21. **`role.changed` が監査ログに残る**
22. パスワードを再設定できる
23. **`password.changed` が監査ログに残る**
24. パスワード再設定でそのユーザーのセッションが失効する
25. 状態を `disabled` にできる
26. **`user.disabled` が監査ログに残る**
27. 無効化でそのユーザーのセッションが失効する
28. **無効化したユーザーはログインできない**
29. **自分自身を無効化できない**
30. **最後の administrator を無効化できない**
31. **最後の administrator から administrator ロールを外せない**

### 削除

32. ユーザーを削除できる
33. 削除でそのユーザーのセッションが失効する
34. **自分自身を削除できない**
35. **最後の administrator を削除できない**
36. 存在しないIDの削除で 404
37. 削除しても監査ログの記録が消えない（`ON DELETE SET NULL`）

### 権限

38. 未認証で 401、`user.manage` を持たないユーザーで 403
39. **`user.manage` を持たないユーザーが直接 API を叩いても 403**

### 画面

40. ユーザー一覧が表示される
41. 画面からユーザーを作成できる
42. 画面からユーザーを編集できる
43. 削除に確認ダイアログが出る
44. **画面のどこにもパスワードハッシュが出ない**
45. 権限タブにロールと Permission の対応が表示される
46. 権限タブに操作用のボタンが無い

### 境界

47. `domain/` が `pg` / `kysely` を import していない
48. すべての UseCase が Permission を要求する
