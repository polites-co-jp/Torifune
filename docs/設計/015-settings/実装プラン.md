# 015-settings 実装プラン

`設計.md` を唯一の入力とする。**マイグレーションは無い**（既存テーブルで足りる）。

## 1. 順序

```text
1. domain      User の更新型・検証、Repository Interface の追加
2. infra       Repository の実装（一覧・更新・削除・ロール解除）
3. audit       role.changed を AUTH_AUDIT_EVENTS へ追加
4. application UseCase 5種。**不変条件（設計 §8）はここに置く**
5. api         Zod スキーマ・応答の形・Route Handler
6. ui          設定画面のタブ、ユーザー一覧・フォーム、権限表
7. test        結合テスト → E2E
```

## 2. Repository へ足すもの

| メソッド | 用途 |
| --- | --- |
| `list(connection, { page, perPage, status, keyword, sort })` | 一覧 |
| `update(connection, id, patch)` | 表示名 / メール / 状態 |
| `deleteById(connection, id)` | 削除 |
| `removeRole(connection, userId, roleName)` | ロール解除 |
| `countActiveByRoleForUpdate(connection, roleName)` | **有効な**管理者の数 |

`countByRoleForUpdate` は既にあるが、**状態を見ていない。**
最後の管理者の判定には「有効な管理者が何人か」が要るため、別に足す。
既存の `/setup` は「管理者が0人か」を見るだけなので、そのままにする。

## 3. 不変条件をどこへ置くか

**すべて UseCase（Application 層）に置く。** 理由は2つ。

* 画面と API の両方から同じ判定を通す必要がある（決定事項 D-06）
* 「最後の管理者か」の判定は行ロックと同一トランザクションが要る。
  Domain 層は Connection を知らない

```ts
await withTransaction(async (tx) => {
  if (input.id === actor.userId) throw new ValidationError(...);   // 自分自身
  const admins = await userRepository.countActiveByRoleForUpdate(tx, 'administrator');
  if (admins <= 1 && targetIsAdmin) throw new ValidationError(...); // 最後の管理者
  ...
});
```

**判定と更新を同じトランザクションに入れる。** 分けると、2つの要求が
同時に来たときに管理者が0人になる。

## 4. 監査ログ

| イベント | 発火する UseCase |
| --- | --- |
| `user.created` | `createUser` |
| `user.disabled` | `updateUser`（status を disabled へ変えたとき） |
| `password.changed` | `updateUser`（パスワードを渡したとき） |
| `role.changed` | `updateUser`（ロールが変わったとき） |

**`detail` にパスワードを入れない。** `sanitizeAuditDetail` が機械的に落とすが、
そもそも渡さない。

## 5. 画面

`/settings` をタブ切り替えにする。`?tab=users` / `?tab=permissions`。
既定は `users`。**Plugin のタブ（`settings.tabs`）はタブの下へ並べる**
（既存の描画位置を変えない）。

ユーザーの作成・編集は `007-sites` と同じ型B。ただし**画面遷移ではなく
Modal**にする。ユーザー数はサイト数ほど増えず、一覧から離れないほうが扱いやすい。
