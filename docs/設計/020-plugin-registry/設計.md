# 020-plugin-registry 設計

## 1. 目的

Plugin の配布と検証（`03_プラグイン設計.md` §14.1 §15 §20.1、
`06_画面設計.md` §18、`07_開発者向けガイド.md` §29-30）。
`002-Torifune機能完成` T8。

あわせて S-8 の #3（`install()` / `uninstall()` が呼ばれない）と
#4（Plugin を更新できない）を解消する。

## 2. 決めたこと

### 2.1 Registry は「静的な JSON インデックス」とする

**中央のサービスを作らない。** OSS 本体が特定の配布元へ依存すると、
`CLAUDE.md` の「特定のクラウド／SaaS運営基盤への依存」に触れる。

代わりに、**HTTPS で取れる JSON を Registry と定義する**。

```json
{
  "plugins": [
    {
      "id": "com.example.seo",
      "name": "SEO レポート",
      "version": "1.2.0",
      "description": "…",
      "downloadUrl": "https://…/seo-1.2.0.zip",
      "sha256": "…",
      "signature": "…",     // ed25519, base64
      "publisher": "example.com"
    }
  ]
}
```

* 誰でも自前の Registry を置ける（静的ファイルで足りる）
* 組織内の配布にもそのまま使える
* `TORIFUNE_PLUGIN_REGISTRY_URL` で指す。**未設定なら Registry 機能は出ない**

### 2.2 Registry からの導入には署名を必須にする

`03` §20.1 が求める「Package の署名・作者情報・改竄検知」。

* 配布物の **SHA-256 を照合**する（壊れた・すり替わったファイルを弾く）
* **ed25519 の署名を検証**する。検証鍵は `TORIFUNE_PLUGIN_TRUSTED_KEYS`
  （base64、カンマ区切り）で明示する
* **信頼鍵が未設定なら Registry からは入れない。** 「署名は見るが誰の署名でもよい」は
  検証していないのと同じ

一方、**ローカルの zip アップロードは今までどおり署名を求めない**。
自分で作った Plugin を試すたびに署名させるのは過剰で、
そこは「Plugin は信頼されたコード」という既存の前提（`CLAUDE.md`）の範囲。
**画面で扱いの違いを明示する。**

### 2.3 署名の対象は「配布物そのもの」

`sha256(zip)` に署名する。マニフェストだけに署名すると、
中身を差し替えられる。

### 2.4 更新は「同じIDの新しい版を入れる」

いまは同じ ID の再導入が `ValidationError` で拒否される（S-8 #4）。

* 版が**上がる**場合だけ更新を許す。下げるのは拒否する
  （下げたい理由があるなら、それは別の要求として設計する）
* **Plugin のデータ（`plugin_store`）は消さない。** 更新でデータが消えると、
  設定を入れ直すことになる
* 更新は「ファイルを置き換えて再ビルド」。導入と同じ経路に乗せる

### 2.5 `install()` は「導入後の最初の有効化の直前」に1度だけ呼ぶ

S-8 #3 の決めるべきこと。

導入は再ビルドを伴うため、**導入の瞬間には Plugin のコードをまだ読み込めない**。
読み込めるようになるのは再ビルド後の起動から。

したがって、

* `plugins` に「`install()` を呼んだか」を持つ（`installed_hook_at`）
* 有効化の直前、まだ呼んでいなければ呼ぶ
* `uninstall()` は削除時に呼ぶ。**このときはコードが読み込まれている**
  （削除前に無効化されているか、少なくとも読み込み済み）ので、その場で呼べる

**`install()` が失敗したら有効化しない。** 初期化に失敗した Plugin を
動かすと、あとで分かりにくい失敗をする。

### 2.6 依存関係を一覧に出す

`03` §13。いまは `PluginSummary.dependencies` が返っているのに画面が描いていない。
**返しているものを出すだけ**なので、ここで片付ける。

## 2-A. 追記（再監査を受けた変更）

初回の実装で **API だけができて画面が無かった**。`/api/v1/plugins/registry` に
GET / POST があるのに呼ぶ画面が無く、その結果 **署名検証（`domain/plugin/package-signature.ts`）が
UI から到達不能**になっていた（ローカル zip 経路は §2.2 のとおり署名を求めない）。
以下はその是正。**§1〜§2.6 の決定は変えていない。**

### 2.7 Registry タブを Plugin 管理画面に作る（`03` §14.1、`06` §18）

* `/plugins?tab=registry` で開く。タブの選択状態は URL に持つ（`06` §32、設定画面と同じ作法）
* 一覧・検索・導入をこのタブから行う。**既存の「Pluginを追加」（zip）の導線は残す**
* Registry の取得は **Server Component ではなく画面から `/api/v1/plugins/registry` を叩く**。
  Server Component で取ると、Plugin 管理画面を開くたびに外部の配布元へ取りに行くことになる
* 取得は**タブに関係なく1回**。インストール済みの一覧にも「新しい版があります」を出すため、
  タブごとに取ると同じ配布元を二度叩く
* **未設定・信頼鍵なし・取得失敗を、画面を壊さずに伝える。** それぞれ何を設定すればよいかを書く
* 導入の確認では、**経路によって検証の強さが違うこと**（§2.2）を明示する。
  高権限 Permission の警告（`022-hardening` の `HIGH_PRIVILEGE_PERMISSIONS`）は
  Registry 経由でも出す

### 2.8 `RegistryEntry` に `03` §15 の保持項目を足す

`03` §15 が Registry に保持を求める項目のうち、**Plugin API Version・依存関係・
対応 Torifune Version・更新日時**が型にも読み取りにも無かった。
これらが無いと、**zip を落として展開するまで互換性・依存を判断できない**。

あわせて **要求 Permission**（`03` §20.2、`06` §39）も持てるようにする。
導入前に権限を見せるために要る。

読み取りの決め：

| 状態 | 扱い |
| --- | --- |
| 宣言が無い | `null`（依存は `{}`、Permission は `null`）。**「不明」として画面に出す** |
| 宣言があるが形が違う | **その項目（entry）を落とす**。既存の「壊れた項目は個別スキップ」方針を維持 |

**値があるのに形が違うものを推測しない。** 「不明」へ丸めると、
合わない Plugin を「判定できないだけ」に見せてしまう。

Permission は `null`（宣言なし）と `[]`（要求しない）を区別する。
混ぜると、画面が「権限は要りません」と言い切ってしまう。

### 2.9 導入する前に「合うかどうか」を判定する

`plugin/registry-compatibility.ts`（新規）。Registry の宣言と、いま入っている
Plugin だけで判定する。**押してから失敗させない。**

* **Plugin API Version が合わない** → 導入させない。導入しても Manifest の検証で必ず弾かれる
* **依存が足りない** → 出すが**止めない**。依存 Plugin をあとから入れれば有効化できる。
  止めると、入れる順番によっては入れられなくなる（§3 で依存の自動解決を作らないと決めた）
* **対応 Torifune Version** → 本体の版が分かるときだけ判定する。
  本体はまだ版を切っていない（`package.json` は `0.0.0`）ため、既定は「不明」。
  `TORIFUNE_VERSION` を与えた環境でだけ判定に使う。
  **`0.0.0` を名乗って判定すると、`^1.0.0` を求める正しい Plugin まで弾く**

### 2.10 更新の導線を作る（`03` §13）

`assertUpgradable`（§2.4）はあったが、画面には
「新しい版の zip を『Pluginを追加』から上げ直す」経路しか無く、
**新しい版が出ていること自体に気づけなかった**。

* Registry の各項目に、いま入っている版（`installedVersion`）と
  **Registry のほうが新しいか**（`updateAvailable`）を付ける
* インストール済みの一覧に「新しい版 X があります」と出し、そこから更新できる
* 更新は導入と同じ経路（`POST /api/v1/plugins/registry`）。版を下げる更新は
  `assertUpgradable` が拒否するので、**押せる形にしない**（同じ版・古い版はボタンを無効にする）
* 更新の確認では「保存した設定・データは残る」（§2.4）ことを伝える

### 2.11 作者を画面に出す（`03` §11 §13）

`PluginManifest.author` は元から任意項目としてあるのに、`PluginSummary` が持たず
**画面に作者が出ていなかった**。`author: string | null` を足して一覧に出す。
Manifest 側は変更しない（後方互換）。文字列でない値は無いものとして扱う。

## 3. やらないこと

* 中央 Registry の運営（§2.1）
* 自動更新。**いつ更新されたか分からない状態を作らない**。
  更新は人が押す
* 依存関係の自動解決（依存 Plugin を勝手に入れる）。
  入るものを人が把握できなくなる
* サンドボックス実行（`03` §23。仕様上「初期実装で必須としない」）

## 5. 受け入れ条件

1. 署名の無い／壊れた Package を Registry から入れられない
2. 信頼鍵が未設定なら Registry からの導入ができない
3. 改竄された配布物（checksum 不一致）を弾く
4. 更新でデータを失わない。版を下げられない
5. `install()` が導入後の最初の有効化で1度だけ呼ばれる
6. `install()` が失敗したら有効化されない
7. `uninstall()` が削除時に呼ばれる
8. 依存関係が一覧に出る
9. ローカルの zip アップロードは今までどおり動く

### 追記分（§2.7〜§2.11）

10. Plugin 管理画面の Registry タブから、Registry の Plugin を検索・一覧・導入できる
11. Registry が未設定・信頼鍵なし・取得失敗のいずれでも画面が壊れず、理由が出る
12. Registry 経由の導入でも、高権限 Permission の警告が出る
13. `RegistryEntry` が Plugin API Version・依存関係・対応 Torifune Version・更新日時を持つ
14. 「Plugin API Version が合わない」「依存が足りない」が**導入前に**一覧へ出る
15. 導入済みより新しい版が Registry にあれば一覧に出て、そこから更新できる
16. 作者が一覧に出る（宣言が無ければ出ない）
17. Registry からの導入で、**署名・checksum を通らないものが導入されない**ことが
    結合テストで確かめられている（検証関数の単体テストだけでは配線の抜けを検出できない）
