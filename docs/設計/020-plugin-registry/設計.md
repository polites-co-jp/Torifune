# 020-plugin-registry 設計

## 1. 目的

Plugin の配布と検証（`03_プラグイン設計.md` §14.1 §15 §20.1、
`06_画面設計.md` §18、`07_開発者向けガイド.md` §29-30）。
`002-Torifune機能完成` T8。

あわせて S-8 の #3（`install()` / `uninstall()` が呼ばれない）と
#4（Plugin を更新できない）を解消する。

## 2. 決めたこと

### 2.1 Registry は「静的な JSON インデックス」とする

**中央のサービスを作らない。** OSS 本体が特定の配布元へ依存すると、
`CLAUDE.md` の「特定のクラウド／SaaS運営基盤への依存」に触れる。

代わりに、**HTTPS で取れる JSON を Registry と定義する**。

```json
{
  "plugins": [
    {
      "id": "com.example.seo",
      "name": "SEO レポート",
      "version": "1.2.0",
      "description": "…",
      "downloadUrl": "https://…/seo-1.2.0.zip",
      "sha256": "…",
      "signature": "…",     // ed25519, base64
      "publisher": "example.com"
    }
  ]
}
```

* 誰でも自前の Registry を置ける（静的ファイルで足りる）
* 組織内の配布にもそのまま使える
* `TORIFUNE_PLUGIN_REGISTRY_URL` で指す。**未設定なら Registry 機能は出ない**

### 2.2 Registry からの導入には署名を必須にする

`03` §20.1 が求める「Package の署名・作者情報・改竄検知」。

* 配布物の **SHA-256 を照合**する（壊れた・すり替わったファイルを弾く）
* **ed25519 の署名を検証**する。検証鍵は `TORIFUNE_PLUGIN_TRUSTED_KEYS`
  （base64、カンマ区切り）で明示する
* **信頼鍵が未設定なら Registry からは入れない。** 「署名は見るが誰の署名でもよい」は
  検証していないのと同じ

一方、**ローカルの zip アップロードは今までどおり署名を求めない**。
自分で作った Plugin を試すたびに署名させるのは過剰で、
そこは「Plugin は信頼されたコード」という既存の前提（`CLAUDE.md`）の範囲。
**画面で扱いの違いを明示する。**

### 2.3 署名の対象は「配布物そのもの」

`sha256(zip)` に署名する。マニフェストだけに署名すると、
中身を差し替えられる。

### 2.4 更新は「同じIDの新しい版を入れる」

いまは同じ ID の再導入が `ValidationError` で拒否される（S-8 #4）。

* 版が**上がる**場合だけ更新を許す。下げるのは拒否する
  （下げたい理由があるなら、それは別の要求として設計する）
* **Plugin のデータ（`plugin_store`）は消さない。** 更新でデータが消えると、
  設定を入れ直すことになる
* 更新は「ファイルを置き換えて再ビルド」。導入と同じ経路に乗せる

### 2.5 `install()` は「導入後の最初の有効化の直前」に1度だけ呼ぶ

S-8 #3 の決めるべきこと。

導入は再ビルドを伴うため、**導入の瞬間には Plugin のコードをまだ読み込めない**。
読み込めるようになるのは再ビルド後の起動から。

したがって、

* `plugins` に「`install()` を呼んだか」を持つ（`installed_hook_at`）
* 有効化の直前、まだ呼んでいなければ呼ぶ
* `uninstall()` は削除時に呼ぶ。**このときはコードが読み込まれている**
  （削除前に無効化されているか、少なくとも読み込み済み）ので、その場で呼べる

**`install()` が失敗したら有効化しない。** 初期化に失敗した Plugin を
動かすと、あとで分かりにくい失敗をする。

### 2.6 依存関係を一覧に出す

`03` §13。いまは `PluginSummary.dependencies` が返っているのに画面が描いていない。
**返しているものを出すだけ**なので、ここで片付ける。

## 3. やらないこと

* 中央 Registry の運営（§2.1）
* 自動更新。**いつ更新されたか分からない状態を作らない**。
  更新は人が押す
* 依存関係の自動解決（依存 Plugin を勝手に入れる）。
  入るものを人が把握できなくなる
* サンドボックス実行（`03` §23。仕様上「初期実装で必須としない」）

## 4. 構成

```text
migrations/015_plugin_install_hook.sql
apps/web/src/
├── domain/plugin/package-signature.ts   署名と checksum（新規）
├── plugin/registry-client.ts            Registry の取得と検索（新規）
├── plugin/lifecycle.ts                  install/uninstall フックと更新
├── application/plugin/plugin-use-cases.ts
├── app/api/v1/plugins/registry/         （新規）
└── ui/plugin/plugin-manager.tsx         Registry タブと依存の表示
```

## 5. 受け入れ条件

1. 署名の無い／壊れた Package を Registry から入れられない
2. 信頼鍵が未設定なら Registry からの導入ができない
3. 改竄された配布物（checksum 不一致）を弾く
4. 更新でデータを失わない。版を下げられない
5. `install()` が導入後の最初の有効化で1度だけ呼ばれる
6. `install()` が失敗したら有効化されない
7. `uninstall()` が削除時に呼ばれる
8. 依存関係が一覧に出る
9. ローカルの zip アップロードは今までどおり動く
