### 指摘

#### S-1（対応済み）Permission の登録失敗を握り潰していた

`enablePlugin` が `registerPermission` の例外を `catch {}` で捨てていた。
Plugin が権限を持たないまま `enabled` になり、**あとで分かりにくい失敗をする**。
`system.*` を宣言した Plugin が「有効だが権限が無い」状態で動いてしまう。

登録できなかった Plugin は `disabled` に落として理由を返すよう直した。
検証は `lifecycle.integration.test.ts`「system.\* は登録できない」
「Permission を登録できなかった Plugin は disabled になる」。

#### S-2（対応済み）Plugin が自分の Permission を定義できなかった

`validateManifest` に `knownPermissions` を渡すと、**本体の Permission 以外を
すべて拒否**していた。Plugin は自分の機能に対する権限を作れない。

`<plugin-id>.…` を許すよう直した。他の Plugin の名前空間は引き続き拒否する
（名乗れると、他の Plugin の権限を横取りできる）。

#### S-3（記録）Plugin の描画コードは本体と同じ権限で動く

`PluginWidgets` / `ExtensionPoint` は Plugin のコンポーネントを
本体の Server Component と同じ文脈で描画する。Plugin は信頼されたコードとして
扱う前提（`CLAUDE.md`）に沿うが、**Plugin の導入は実質的にアプリへのコード導入**である。

`012-plugin-manager` の導入画面で、要求する Permission を導入前に見せる。

#### S-4（記録）Plugin の描画が例外を投げたときの扱い

現状は React の既定に従う（そのページが落ちる）。
本体の他の画面には波及しないが、**その画面は白くなる**。

Error Boundary で Plugin の枠だけを落とす案がある。
Server Component では Error Boundary が使えないため、
Plugin の枠を Client Component にするか、`013-example-plugin` で
実際の壊れ方を見てから決める。`03_リスクと未決事項.md` へ回す。

## 4. 設計書との相違（2件）

### 4.1 #32「Permission を持たないユーザーが 403」

設計書は 403 と書いている。実装は **`AsyncState status="forbidden"` を描画する**
（HTTP ステータスは 200）。

`/sites` `/social` が既に同じ扱いをしており、**画面では「権限が無い」表示を返し、
API では実際の 403 を返す**という区別がこのリポジトリの既存の約束である。
Next.js の `forbidden()` は `experimental.authInterrupts` を要するため採らなかった。

なお、当初は `notFound()` にしていたが改めた。導入済みの Plugin は
同じインスタンスの利用者から隠すものではなく、隠すと利用者は理由が
分からないまま行き止まりになる。

**表示の E2E は Plugin が要るため `013-example-plugin` へ持ち越す。**

> **2026-08-31 追記**：持ち越したまま 013 の検証レポートにも記載が無く、
> **どこにも残っていない状態だった。** `e2e/plugin-example.spec.ts` に
> 「Permission を持たないユーザーが Plugin ページへ直接来ると
> 「権限がありません」になる」を追加して解消した。
>
> ロールを1つも持たないユーザーを作って確かめている。
> このサンプルのメニューは `permission` を宣言していないので**メニューには出る**が、
> ページへ直接来ても中身は描画されない。**見えることと使えることは別**という
> 拡張点の要点が、そのままテストになっている。

### 4.2 `validateManifest` の `knownPermissions` の意味を変えた

S-2 のとおり。`010-plugin-api` の契約に対する破壊的変更にあたる。
検証は `plugin-api.test.ts`「自分の名前空間の Permission は新しく定義できる」
「他の Plugin の名前空間は名乗れない」。

## 5. 途中で見つけた本体の不具合（1件）

### F-1 Permission 名がハイフンを許していなかった

Plugin ID はハイフンを許す（`seo-plugin`）のに、Permission 名は
`^[a-z][a-z0-9_]*(\.[a-z][a-z0-9_]*)+$` でハイフンを弾いていた。
そのため **Plugin は自分の ID を Permission の名前空間にできなかった**。

`011` のテストで発覚した。`migrations/008_permission_name_hyphen.sql` で
DB 側の CHECK 制約も合わせた（`001_initial.sql` は適用済みのため書き換えない）。

`apps/web/src/domain/permission.test.ts` の「ハイフンを拒否する」は
前提が誤りだったため「ハイフンを許す」に改め、
先頭ハイフンを拒否する検証を足した。

### 再現しなかった失敗（1件）

`lifecycle.integration.test.ts` に2件テストを足した直後の1回だけ、
`pnpm test` が「1 failed | 644 passed」で終わった。
**失敗したテスト名を取り逃がした。**

その後 `pnpm vitest run` / `pnpm test` を合わせて **24 回連続で実行し、
すべて 645 件通過**した。再現しないため原因を特定できていない。

使い捨てデータベースの名前は乱数を含み衝突しない。
マイグレーションの advisory lock はデータベース単位のため競合しない。
**握り潰さず記録に残す。** 再発したらテスト名を控えてここへ追記する。
