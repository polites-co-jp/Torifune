## 2. 進める順番

依存の向きに沿って下から積む。上から作ると、下が決まっていない状態で
インターフェースを想像することになり、あとで作り直しになる。

```text
007_plugins.sql
   ↓
dependencies.ts ── 単体で完結する。先に確定させる
   ↓
registry.ts ── 状態の置き場。ここが決まらないと lifecycle が書けない
   ↓
context.ts ── registry へ書き込む口
   ↓
lifecycle.ts ── 状態遷移
   ↓
loader.ts + generate-plugin-registry.mjs ── ファイルから Plugin を取り出す
   ↓
runtime.ts ── 起動
   ↓
catch-all ルート / plugin-slot / page-session ── 画面へつなぐ
```

## 4. 判断が要るところ

### 4.1 Plugin の読み込みをビルド時にする

決定事項 D-02 のとおり。実行時ロードは Module Federation か iframe が要り、
ビルド基盤・セキュリティ・型安全性のすべてでコストが跳ね上がる。

生成物 `apps/web/src/plugin/generated-registry.ts` は Git に入れない。
入れると、`plugins/` の中身と生成物がずれた状態をコミットできてしまう。

### 4.2 起動を1度だけにする

`ensurePluginsStarted` は Promise を握って使い回す。
リクエストごとに `activate` を呼ぶと、登録が積み重なってメニューが増殖する。

有効・無効を切り替えたあとは `resetPluginRuntime()` で握った Promise を捨てる。

### 4.3 失敗した Plugin を落とす

`activate` が例外を投げたら、その Plugin を `disabled` にして本体は起動を続ける。
Plugin ひとつの不具合で Torifune 全体が使えなくなるのは重すぎる。

失敗は `BootResult.failed` に残す。黙って無かったことにすると、
「入れたはずの Plugin が動かない」理由が誰にも分からなくなる。

### 4.4 Plugin のメニューをどこで足すか

`AppShell` が `collectMenus()` を呼ぶ。ただし `collectMenus()` は
Plugin が起動済みでなければ空を返すため、**ログインが要る画面すべてで
起動を済ませておく必要がある**。

各ページが Cookie の読み出しと起動を書き写すと、どこか1枚で書き忘れる。
`requirePageSession()` に集約する。

## 5. やらないこと

* Plugin の導入・有効化を画面から行う（→ `012-plugin-manager`）
* 実際の Plugin を伴う描画の E2E（→ `013-example-plugin`）
* Authentication Provider / Database Provider の Plugin 実装（→ `013`）
