# 036 Bluesky 配信 Plugin（`plugins/sns-bluesky`） 設計

> **035 が作った拡張点 `social` の最初の実利用者。**
> 本設計は `docs/設計/035-social-publishing/設計.md` §13 の骨子を具体化する。
> **Core（`apps/web` / `packages/plugin-api` / `migrations`）には 1 行も足さない。**

## 1. 目的

Torifune に登録された SNS 投稿を、**Bluesky（AT Protocol）へ実際に配信する。**

`035` は「いつ送るか・再試行・記録・画面」までを Core に作ったが、
**送る当人がまだ居ない**。素の Torifune では `social_posts` に予約を積めるだけで、
どこにも届かない（`plugins/example-plugin` のループバック publisher は外部へ繋がない）。

Bluesky を最初に作るのは `035` 要件 §4 の裁定 #5 による。**App Password だけで端から端まで通る**
（OAuth のコールバックを受ける HTTP ルート＝`027` §3.1 が未実装でも成立する）唯一の SNS で、
`037 sns-x` / `038 sns-instagram` が踏む道を、資格情報の受け渡し・再試行・手動投稿まで含めて先に踏む。

この Plugin が満たすべきことは 2 つだけである。

* **`publish()`**：1 回の呼び出しで 1 件を Bluesky へ投稿し、結果を返す
* **`manual()`**：投稿内容を反映した Bluesky の投稿画面（Web Intent）の URL を返す

それ以外（予約・排他・着手印・再試行・記録・イベント・画面）は**すべて Core にある**。
本設計は「Plugin 側に何を書くか」と同じ重さで、**Plugin 側に何を書かないか**を決める。

## 3. スコープ

### 3.1 やること

* `plugins/sns-bluesky/` を新設する（`plugin.json` / `index.ts` / publisher の実装 / AT Protocol の呼び出し / 本文の数え方 / `README.md`）
* `provider: 'bluesky'` の publisher を `context.social.registerPublisher()` で登録する
* `credentialFields`：`identifier`（text）/ `appPassword`（secret）
* `limits` と `validate()`（本文の grapheme 数とバイト数、`media[].alt`、`link` と `media` の同居、`providerOptions.langs`）
* `publish()`：`com.atproto.server.createSession` → 媒体の取得 → `com.atproto.repo.uploadBlob` → `com.atproto.repo.createRecord`
* `manual()`：`https://bsky.app/intent/compose?text=…` の組み立て
* PDS の URL を `context.ui.registerSettings()` で変えられるようにする（既定 `https://bsky.social`）
* `README.md`：App Password の取り方、**導入から資格情報を入れるまでの猶予が約 24 時間**であること（`035` 裁定 #9）

### 3.2 やらないこと

| やらないこと | 理由 |
| --- | --- |
| Core（`apps/web` / `packages/plugin-api` / `migrations`）への変更 | `035` の口だけで書けることを示すのが本設計の目的（`035` §13「Plugin が Core に要求する追加は無い」） |
| OAuth（`https://bsky.social/oauth/…`）での接続 | AT Protocol は App Password で足りる（要件 §3）。OAuth は Plugin の HTTP ルート（`027` §3.1）が前提で、`035` 裁定 #6 で後回し |
| 自前のタイマー・ジョブ・HTTP ルート・テーブル | Core が持つ（`035` 裁定 #1）。複数プロセスで二重投稿になる |
| 返信・引用・スレッド（`reply` / `embed.record`） | 親投稿の `uri` と `cid` の両方が要り、Core の `social_posts` に親子の概念が無い。§11 #5 |
| 動画（`app.bsky.embed.video`）・GIF | `uploadBlob` の上限とジョブの 30 秒に収まらない。§11 #6 |
| 画像の `aspectRatio` | 画像を復号して寸法を読む処理が要る。無くても投稿は通る。§11 #7 |
| メンション（`did` の解決を伴う facet）・ハッシュタグの facet | リンクの facet と違い、外部への追加の問い合わせ（`resolveHandle`）が要る。§11 #8 |
| 投稿の削除・編集（`deleteRecord`） | Core に「配信済みの投稿を取り消す」という操作が無い（`published` は終端。`035` §5.8） |
| 資格情報の画面からの登録以外の入口 | Core の `POST /api/v1/social/accounts`（`credentials`）と `/social` の画面が既にある（`035` §6.4 / §7.5） |

### 3.3 Core が持つもの／この Plugin が持つもの

```text
Core（035）                                   Plugin（036）
─────────────────────────────────────────    ─────────────────────────────────
予約の受付・冪等キー・権限                    —
ジョブ social.publish（1 分周期・排他）        —
着手印・中断行の判定・再試行の回数と間隔       —
資格情報の復号・監査・書き戻し                 —
limits / validate() の適用（登録時・配信直前） limits の宣言 / validate() の中身
publish() の呼び出しと 30 秒の打ち切り         publish() の中身（AT Protocol）
結果の記録・イベント・履歴画面                 —
手動投稿待ちの画面・子ウィンドウ・「投稿した」 manual() が返す URL と注意書き
provider の表示名の対応表                      label（対応表より優先される）
```

**この Plugin が状態を持つのは `pds-url` の 1 件だけ**である。投稿の状態も資格情報も持たない。

## 4. レイヤ配置

**すべて Plugin 層（`plugins/sns-bluesky/`）に置く。** 本体の `apps/web/src/` には 1 ファイルも足さない。

```text
plugins/sns-bluesky/
├── plugin.json      Manifest（id / apiVersion / permissions / extensions）
├── index.ts         activate(): 設定の宣言と publisher の登録だけ
├── social.ts        createBlueskyPublisher(): PublisherRegistration を組み立てる
├── atproto.ts       AT Protocol への HTTP（createSession / uploadBlob / createRecord）
├── text.ts          本文の数え方と facets の組み立て（純関数。外部へ出ない）
├── settings.ts      PDS の URL の宣言・検証・読み出し
└── README.md        App Password の取り方と運用上の注意
```

* **`@/` や `apps/web` を import しない。** 使ってよいのは `@torifune/plugin-api` の型と、Node の標準（`fetch` / `URL` / `Intl.Segmenter` / `TextEncoder` / `AbortSignal`）だけ
* **`pg` / `kysely` を使わない。** データベースへは触らない（`store` 越しに `pds-url` を読むだけ）
* **`react` を使わない。** 画面部品を持たない（設定画面は Core が描く）
* `console` を使わない（リポジトリの ESLint が全域で禁じている）。出力は `context.logger` / `PublishInput.logger` だけ
* **純関数（`text.ts`）と外部 I/O（`atproto.ts`）を分ける。** 数え方の検査に HTTP を差し替える必要が無くなる

Domain 層・Application 層に Bluesky の語彙（`at://`、`app.bsky.feed.post`、`accessJwt`）を 1 つも出さない。
Core から見ると、この Plugin は `PublisherRegistration` という 1 つのオブジェクトにすぎない。

### 4.1 テストの置き場（`plugins/` にテストを置けない）

**`vitest.config.mts` の `include` は `{apps,packages}/**/*.{test,spec}.{ts,tsx}`** である。
`plugins/` に `*.test.ts` を置いても**収集されない**（置いても走らないテストになる）。

したがってこの Plugin のテストは **`apps/web/src/plugin/` に置く**。既に前例がある
（`apps/web/src/plugin/example-plugin.integration.test.ts` が `plugins/example-plugin` を検査している）。

| ファイル | 種別 | 見るもの |
| --- | --- | --- |
| `apps/web/src/plugin/sns-bluesky.test.ts` | A（単体） | `validate()` の判定、`manual()` の URL、`publish()` の分岐（`fetch` は偽物） |
| `apps/web/src/plugin/sns-bluesky.integration.test.ts` | B（結合） | Core のジョブを通した配信（DB。`fetch` は偽物） |

**`vitest.config.mts` を変えて `plugins/` を収集対象にする案は採らない。**
`plugins/` は「利用者が Plugin を置く場所」で、第三者が置いた Plugin のテストを本体の `pnpm test` が
走らせる形にすると、**本体の検証が第三者のコードの成否に左右される**。前例（`013`）に揃える。

## 5. データモデル

**マイグレーションは不要。テーブルもカラムも足さない。**

| 置き場 | 値 | 備考 |
| --- | --- | --- |
| `social_accounts.credential`（既存） | `{"identifier":"…","appPassword":"…"}` を暗号化した 1 つの文字列 | 形式は `035` §5.7。Core が暗号化・復号・監査する |
| Plugin の Key-Value Store | `pds-url` = `https://bsky.social`（既定） | `registerSettings` が宣言した項目。**Secret ではない**（URL は秘密ではない） |
| `social_posts`（既存） | `body` / `media` / `link` / `providerOptions` / `external_id` / `external_url` | この Plugin は書かない。Core が `publish()` の戻り値から書く |

### 5.1 `credentialFields`

```ts
credentialFields: [
  {
    key: 'identifier',
    label: 'ハンドルまたはメールアドレス',
    description: 'Bluesky のハンドル（例：example.bsky.social）。先頭の @ は書かない。',
    kind: 'text',
    placeholder: 'example.bsky.social',
  },
  {
    key: 'appPassword',
    label: 'App Password（アプリパスワード）',
    description:
      'Bluesky にログインするパスワードではありません。Bluesky の「設定 → プライバシーとセキュリティ → アプリパスワード」で発行した、xxxx-xxxx-xxxx-xxxx の形の文字列を入れます。' +
      'ログイン用のパスワードをここへ入れないでください。App Password はいつでも個別に取り消せます。保存後は再表示されません。',
    kind: 'secret',
  },
]
```

* **「App Password は本パスワードではない」を `description` に書き切る。** 入力欄は Core が描き、
  `description` がそのまま画面（`/social` のアカウント編集）と `POST /api/v1/social/accounts` の 422 の
  文言に出る（`035` §6.4 / §7.5）。**ここに書かないと、利用者はログインパスワードを入れる。**
  形式（`xxxx-xxxx-xxxx-xxxx`）まで書くのは、**入れ間違えたことに気づける手がかり**を残すためである
* **形式検証はしない。** `credentialFields` は「何が要るか」の宣言だけで、形式の検査は Core が持つ
  （空でないこと・宣言に無いキーが無いこと。`validateCredentialAgainstFields`）。
  App Password の形はハイフンの有無も含め Bluesky 側の都合で変わりうるので、**Plugin が形で弾くと、
  正しい資格情報を拒む側に倒れる**。間違っていれば `createSession` が 401 を返し、その理由が履歴に残る
* **`identifier` を 3 つ目の項目（表示名など）に分けない。** 項目を増やすと、**後から減らせない**（§5.2）
* **キーは `035` §13 / `docs/Plugin開発ガイド.md` §9 の例と同じ 2 つのまま**にする

### 5.2 `credentialFields` を後から増やせないこと（決めたこと）

**`credentialFields` に項目を足す変更は、既存のアカウントを壊す破壊的変更である。**

Core は復号した平文を `validateCredentialAgainstFields` に掛け、**宣言した項目が 1 つでも欠けていれば
その投稿を `failed`** にする（`credentialMismatchReason`。`035` §6.5.2 の c）。更新も 422 になる。
つまり「v1.1 で `pdsHost` を `credentialFields` へ足す」と、**v1.0 で登録済みのアカウントは全部止まる。**

したがって：

* **`credentialFields` は `identifier` / `appPassword` の 2 つで確定させる。** 増やさない前提で設計する
* アカウントごとに変えたい値が将来出てきたら、`credentialFields` を増やすのではなく
  **ハンドルから PDS を解決する**（§11 #2）。そちらは資格情報の形を変えない
* PDS の URL は**アカウントごとではなく installation ごと**の設定として持つ（§7.1）。この判断の代償は §11 #2

## 6. 外部への要求（AT Protocol）

新しい Torifune の API エンドポイントは**作らない**。この Plugin が外へ出す HTTP 要求は次の 3 種類だけである。
`{pds}` は §7.1 の設定値（既定 `https://bsky.social`）。

### 6.1 `POST {pds}/xrpc/com.atproto.server.createSession`

```jsonc
// 要求
{ "identifier": "<credential.identifier>", "password": "<credential.appPassword>" }
// 応答（200）
{ "did": "did:plc:…", "handle": "example.bsky.social", "accessJwt": "…", "refreshJwt": "…" }
```

* **`did` と `accessJwt` を使う。** `handle` は `externalUrl` の組み立てに使う（§6.4）
* **`refreshJwt` は使わない。捨てる**（§6.5）
* `Content-Type: application/json`

### 6.2 `POST {pds}/xrpc/com.atproto.repo.uploadBlob`（媒体 1 件につき 1 回）

* 先に `media[].url` を **GET** して中身を得る（`035` §5.2「Torifune はファイルを預からない」。URL だけが渡る）
* `Authorization: Bearer <accessJwt>`、`Content-Type` は**既知の値へ丸めたもの**（下の表）、本体は取得したバイト列
* 応答（200）：`{ "blob": { "$type": "blob", "ref": { "$link": "…" }, "mimeType": "…", "size": 0 } }`。
  **`blob` をそのまま `createRecord` の `embed.images[].image` に入れる**（中身を組み立て直さない）

媒体の取得（GET）には次の枠をはめる。**`media[].url` は `social.write` を持つ誰かが書いた値**であり、
Torifune のサーバから取りに行かせる先を外から指せる（Core の検査は「https で資格情報付きでないこと」までしか見ない。
`isValidExternalHttpsUrl`）。

| 枠 | 値 | 理由 |
| --- | --- | --- |
| リダイレクト | **追わない**（`redirect: 'manual'`。3xx はその場で失敗にする） | 検査を通った URL から、検査していない URL へ移らせない |
| 上限サイズ | `MEDIA_MAX_BYTES = 1_000_000` | Bluesky の `uploadBlob` が受ける画像の上限に合わせる。**先に `Content-Length` を見て、無ければ読みながら打ち切る** |
| 受け付ける種別 | **既知の画像だけ**（`image/png` / `image/jpeg` / `image/gif` / `image/webp`）。`; charset=…` などの引数は落として比べる | 画像以外を blob にしても投稿に載らない。**知らない値を素通しする口は作らない** |
| PDS へ送る `Content-Type` | **丸めた既知の値**（取得先の応答ヘッダそのままではない） | 取得先は利用者が指した任意のサーバである。その文字列を Torifune の資格情報つきの要求のヘッダへ転記しない |
| 制限時間 | 1 件 10 秒（§6.6） | 30 秒の枠に 4 件が収まらない |
| 応答の中身 | **ログにも `reason` にも載せない** | 取得先が返す任意のバイト列である |

> **`redirect: 'error'` から `'manual'` に改めた（2026-09-23）。**
> もとは `redirect: 'error'` と書いていたが、**`'error'` では 3xx を観測できない。**
> `redirect: 'error'` の `fetch` は 3xx を `Response` として返さず**その場で `TypeError` で reject する**ので、
> 「status が 3xx なら失敗」の分岐は**本番では 1 度も通らない。**
> 実際には reject が「接続できない（`kind: 'network'`）」に落ち、**`retryable: true`** になって
> §6.9 の P2（リダイレクトは `false`）と**逆の結果**になっていた。
>
> `'manual'` は**転送を追わずに 3xx をそのまま `Response` として返す**（Node の `fetch`。
> ブラウザの opaque-redirect（`status: 0`）とは違い、status もヘッダも読める）。
> これで「追わない」という本質を保ったまま、§6.9 P2 が**本番でも成立する。**
> `'follow'` は論外（検査していない URL へ移る）。
>
> **テストが緑だったのは、偽の `fetch` が 302 の `Response` を返していたから**である。
> 偽物が本番と違う振る舞いをしていたことが問題の核なので、
> **本番の `fetch` がこの `init` で何を返すかを、ループバックのサーバを立てて直に見る条件**を足した（#74）。

### 6.3 `POST {pds}/xrpc/com.atproto.repo.createRecord`

```jsonc
{
  "repo": "<session.did>",
  "collection": "app.bsky.feed.post",
  "record": {
    "$type": "app.bsky.feed.post",
    "text": "<本文>",
    "createdAt": "2026-09-23T12:34:56.789Z",
    "langs": ["ja"],                       // providerOptions.langs があるときだけ
    "facets": [ /* 本文中の URL。§6.7 */ ],  // 見つかったときだけ
    "embed": { /* 画像 or 外部埋め込み。§6.8 */ }  // media か link があるときだけ
  }
}
// 応答（200）
{ "uri": "at://did:plc:…/app.bsky.feed.post/3k…", "cid": "bafy…" }
```

* `Authorization: Bearer <accessJwt>`
* **`createdAt` は「実際に送った時刻」**（`new Date().toISOString()`）。`post.scheduledAt` は使わない。
  再試行で 8 分遅れて届いた投稿に予約時刻を書くと、**Bluesky 側の並びが実際の投稿順と食い違う**
* **`uri` の最後のセグメントが rkey。** `externalId` に使う
* **rkey の長さを確かめる（200 文字以内）。** `social_posts.external_id` には
  **200 文字以内**の CHECK があり（`migrations/022`）、`publish()` の経路にはこの検査が無い。
  長い rkey をそのまま返すと Core の記録が CHECK 違反の例外で落ち、**`unrecorded`** になる。
  そのとき**着手印（`attempt_count`）は残り、投稿は Bluesky に作られたまま**なので、
  次の周期で中断行として拾われ **二重投稿**になる（§6.9 の P4 が避けたかったことが、記録の側から起きる）

  > **2026-09-23 に足した（`security-reviewer` 低-1）。**
  > **失敗にはしない。** 200 文字を超えて返ってくる時点で相手は Bluesky ではないが、
  > **`createRecord` は 200 を返しており、投稿は作られている。** 失敗にすると再試行で二重投稿になる。
  > **`externalId` と `externalUrl` を付けずに `ok: true` を返す**（`externalUrl` も rkey を含み、
  > `external_url` の 2048 文字の CHECK に同じ形で掛かるため、片方だけ残さない）。
  > 記録は「配信済みだが Bluesky 側の識別子が分からない」になる

### 6.4 戻り値の組み立て

```ts
{
  ok: true,
  externalId: rkey,                                                 // 例: 3kabcdefghij2
  externalUrl: `https://bsky.app/profile/${handle}/post/${rkey}`,   // handle は session.handle
}
```

* **`handle` は `createSession` の応答**を使う。`account.handle`（Torifune 側の登録値）は利用者が書いた表示用の値で、
  実際のハンドルと食い違いうる。食い違ったまま URL を作ると、**履歴の「投稿を見る」が 404 になる**
* `handle` は `encodeURIComponent` を通す（ハンドルは英数字とドットとハイフンだが、
  **外から来た文字列をそのまま URL へ差し込まない**）
* `externalUrl` は **`bsky.app` 固定**。セルフホストの PDS でも、連合していれば `bsky.app` から見える。
  見えない構成もありうる（§11 #3）が、**Core は `externalUrl` が https であることしか要求しない**（`isValidExternalUrl`）ので、
  辿れない URL を返しても記録そのものは壊れない
* **rkey が 200 文字を超えていたら、`externalId` も `externalUrl` も付けない**（§6.3）
* **`rotatedCredential` は返さない**（§6.5）

### 6.5 セッション（`accessJwt` / `refreshJwt`）の扱い — 決めたこと

**`publish()` 1 回につき 1 回 `createSession` を呼び、`accessJwt` はその呼び出しの間だけ持つ。
`refreshJwt` は使わずに捨てる。`store` にも `store.setSecret` にも入れない。プロセス内にも残さない。**

理由：

* **`rotatedCredential` は使えない。** キーは `credentialFields` のままでなければ Core が書き戻さない
  （`035` §6.5.6：宣言に合わないものは `log.warn` して捨てる）。`accessJwt` を書き戻すには
  `credentialFields` に項目を足すことになり、**既存のアカウントが全部止まる**（§5.2）
* **`store.setSecret` に入れるのは、資格情報の 2 つ目の置き場を作ることである。** 開発ガイド §5 は
  「SNS の配信 Plugin は資格情報を自分で持たない。二重に持つと、どちらが正かが分からなくなる」と
  書いている。`refreshJwt` は App Password から導かれた**同じ資格**で、これを Plugin の名前空間へ
  写すと、**Core が暗号化・監査・書き戻しを持つという `035` 裁定 #2 の外側に、同じ資格の複製ができる。**
  App Password を取り消しても、写した `refreshJwt` は Core の知らないところに残る
* **App Password は固定なので `rotatedCredential` が要らない**（`035` §13 の骨子どおり）。
  トークンを延ばす必要がそもそも無い

代償：**1 件につき `createSession` が 1 回増える。** Bluesky は `createSession` に回数制限を設けているので、
1 つのアカウントへ短時間に多数の投稿が集中すると 429 になりうる。そのときは
`retryable: true` と `retryAfterMs` で Core が待つ（§6.9）ので、**投稿は失われない。**
回数を減らす必要が出たら、**プロセス内メモリのセッションキャッシュ**を検討する（§11 #4）。
`store` へ書く案は上の理由により採らない。

### 6.6 制限時間と `signal`

Core は `publish()` を **30 秒**で打ち切り、**結果不明として `failed`** にする（再試行しない）。
30 秒に達してから打ち切られるのは最悪の形なので、**この Plugin は自分で早く諦める。**

| 要求 | 自前の制限時間 | 定数 |
| --- | --- | --- |
| `createSession` | 10 秒 | `CREATE_SESSION_TIMEOUT_MS` |
| 媒体の取得（最大 4 件） | 1 件 10 秒 | `MEDIA_FETCH_TIMEOUT_MS` |
| `uploadBlob`（最大 4 件） | 1 件 10 秒 | `UPLOAD_BLOB_TIMEOUT_MS` |
| `createRecord` | 15 秒 | `CREATE_RECORD_TIMEOUT_MS` |
| **`publish()` 1 回の合計** | **25 秒** | `PUBLISH_TOTAL_BUDGET_MS` |
| 媒体の処理の合計 | 20 秒（ただし合計の残り時間を超えない） | `MEDIA_TOTAL_BUDGET_MS` |

* **要求ごとの `AbortSignal` は `AbortSignal.any([外側の signal, AbortSignal.timeout(ms)])` で作る**
  （Node 22。`AbortSignal.any` / `AbortSignal.timeout` とも標準）。
  Core が打ち切ったときも、自前の上限に達したときも、同じ 1 つの signal で止まる
* **「外側の signal」は `input.signal` そのものではなく、`AbortSignal.any([input.signal,
  AbortSignal.timeout(PUBLISH_TOTAL_BUDGET_MS)])` である。** これが `publish()` 全体の期限で、
  **どの要求から抜け出しても合計が 25 秒を超えない**（Core の 30 秒に**自分から届かない**）
* **どの定数がどの要求へ渡るかは固定する**（#81）。値が合っていても**結線が入れ替われば意味が変わる**
  （`createRecord` に 10 秒を渡す取り違えは、値を見るだけのテストでは落ちない）
* **媒体は 1 件ずつ順に処理する。** 4 件を並行に取りに行くと、相手側の Rate Limit を自分で踏む。
  **媒体の処理に使ってよい合計時間は、`createSession` の後の残り時間から取った
  `min(MEDIA_TOTAL_BUDGET_MS, 合計の期限 - いま)` である。**
  各件の処理に入る前にこの期限を見て、過ぎていたらそこで諦める
  （`kind: 'budget'`・`retryable: true`。まだ `createRecord` を呼んでいない）
* **期限の「いま」は `now()`（§10.1）で数える。** 合計の 25 秒を実際に断ち切るのは
  `AbortSignal.timeout` の実時間だが、**期限切れの判定を実時間だけに預けると、
  `budget` の分岐はテストから 20 秒待たずに通せない**（通らない分岐は無いのと同じである）
* **`input.signal` が発火したら、その場で処理をやめて `publish()` を抜ける。**
  Core 側は既に `timeout` として結果を確定させているので、**何を返しても記録されない**

> **合計 25 秒の期限を足した（2026-09-23、`spec-verifier` R-2）。**
> もとは「媒体の合計 20 秒」を `createSession` の後の残り時間から取ると書いていたのに、
> **実装は媒体の処理を始めた時点から固定で 20 秒を数えていた**（設計と実装が食い違っていた）。
> さらに**期限の検査は各件の処理に入る前だけ**なので、1 件が取得 10 秒＋アップロード 10 秒を使うと
> 期限を越えて走り、最悪 **10（session）＋ 20（媒体）＋ 15（record）＝ 45 秒**になる。
> これは §6.6 の主旨（**Core の 30 秒に達する前に自分で諦める**）を実装が満たしていない、ということである。
>
> **寄せ先は実装のほうにした。** 期限の検査を増やすだけでは、検査の直後に始まった 1 件が
> 20 秒走るのを止められず、どう数えても合計は縛れない。**縛れるのは signal だけ**なので、
> `publish()` の入口で 1 つ期限を作り、**すべての要求の外側の signal に混ぜる**。
> 媒体の合計 20 秒は「そこから取る」形になり、設計の文（「残り時間から取る」）とも一致する。
>
> 25 秒にしたのは、`createSession`（10）＋ `createRecord`（15）が**媒体なしの最悪の形**で、
> ここを削ると正常な配信を自分で切ってしまうためである。Core の 30 秒との差 5 秒は、
> **打ち切りを検知して `PublishResult` を組み立てて返すための余白**である。

### 6.7 `facets`（本文中の URL）

**Bluesky は本文の URL を自動ではリンクにしない。** `facets` を付けない投稿の URL は、
ただの文字列として表示される。この Plugin は本文中の `http(s)://…` を見つけて `facets` を組み立てる。

* 位置は **UTF-8 のバイト単位**（`byteStart` / `byteEnd`）。`TextEncoder` で数える。
  **`String` の添字（UTF-16）をそのまま渡すと、日本語や絵文字を含む本文でリンクの位置がずれる**
* 末尾の句読点・閉じ括弧（`.,;:!?)]」）` と全角の句読点）は URL から外す
* `feature` は `{ $type: 'app.bsky.richtext.facet#link', uri: <見つけた URL そのまま> }`
* **`text.ts` の純関数**にする（`detectLinkFacets(text)`）。外部へ出ないので単体で検査できる
* 見つからなければ `facets` を**付けない**（空配列も入れない）

### 6.8 `embed`（画像と外部埋め込み）— 同居できない

**`app.bsky.feed.post.embed` は 1 つしか持てない。** 画像と外部リンクカードは同居できない。

| `media` | `link` | `embed` |
| --- | --- | --- |
| 無し | 無し | 付けない |
| 1〜4 件 | 無し | `app.bsky.embed.images`（`images[].image` は `uploadBlob` の `blob`、`images[].alt` は `media[].alt ?? ''`） |
| 無し | 有り | `app.bsky.embed.external`（`external: { uri: link, title: <link のホスト名>, description: '' }`） |
| 1〜4 件 | 有り | **`validate()` が断る**（下） |

* **`media` と `link` を同時に指定したら `validate()` で問題を返す**（`field: 'link'`）。
  片方を黙って捨てる案は採らない。**登録した側は捨てられたことに気づけない**
* **`publish()` でも同じ組み合わせを断る**（`createRecord` を呼ばずに `{ ok: false, retryable: false }`）。
  > **2026-09-23 に足した。** G2 の実装者が入れ、「受け入れ条件に無い行動なので差し戻すなら言ってほしい」と報告した。**残す。**
  > `validate()` は登録時と配信直前の両方で掛かる（`035` §6.5.2.2）ので通常ここへは来ないが、
  > **来たときに黙って片方を捨てないことが、この節の主旨**である。`validate()` が担うのは「早く知らせる」ことで、
  > 「捨てない」ことの担保ではない。防御が二重になるだけで、仕様は広がっていない
  >
  > **2026-09-23 に足した（`spec-verifier` R-5）。** この経路だけ `logger.warn` が出ていなかった
  > （`fail()` を通らない早期 return だったため）。**失敗して戻るのに運用者のログに何も残らない**のは、
  > 「通常ここへは来ない」経路ほど困る。**`phase: 'embed'` で `logger.warn` を出す**
  > （`media` と同じく、出すのは `postId` / `attempt` / フェーズ名 / 媒体の件数だけ）
* **`link` を本文の末尾へ足す案も採らない**（`deliveryMode: 'auto'` では）。本文が変わると
  `validate()` が数えた 300 grapheme と実際に送る本文が食い違い、**登録時に通った投稿が配信時に弾かれる**
* **外部埋め込みの `title` / `description` を取りに行かない。** OGP を読むには**リンク先へ HTTP 要求を出す**ことになり、
  5 秒の `validate()` にも 30 秒の `publish()` にも新しい外部依存が増える。`title` は `link` のホスト名、
  `description` は空文字にする。**リンクカードの見た目は素っ気なくなるが、リンクは開ける**（§11 #9）
* `thumb`（カードの画像）も付けない（取りに行くことになるため）

### 6.9 `retryable` の基準 — AT Protocol の応答への対応づけ

契約（`docs/Plugin開発ガイド.md` §9）は「**送る前に失敗したなら `true`、届いたか分からないなら `false`、
迷ったら `false`**」である。AT Protocol では**「送る」は `createRecord` の 1 回だけ**であり、
そこへ到達する前の失敗は**投稿が作られていないことが確かめられる。**

> **支配的な規則（これだけ覚えればよい）**
>
> 1. **`createRecord` を送る前の失敗は既定で `retryable: true`。**
>    ただし**時間が経っても直らないもの**（資格情報・設定・投稿の内容）は `false`
> 2. **`createRecord` を送った後の失敗は既定で `retryable: false`。**
>    ただし **429（書き込む前に断られたと読める）だけ `true`**

| # | フェーズ | 起きたこと | `retryable` | 理由 |
| --- | --- | --- | --- | --- |
| P0 | 設定の読み出し | `pds-url` が不正（§7.1 の検査に通らない） | **false** | 人が設定を直すまで直らない |
| P0 | 〃 | `store.get` が失敗した | **true** | まだ何も送っていない |
| P1 | `createSession` | 接続できない（DNS・TCP・TLS。`fetch` が reject） | **true** | セッションすら取れていない＝投稿は作られていない |
| P1 | 〃 | 自前の制限時間（10 秒）に達した | **true** | 同上 |
| P1 | 〃 | 429 `RateLimitExceeded` | **true** ＋ `retryAfterMs` | 受け付けられていない。§6.10 |
| P1 | 〃 | 5xx | **true** | **一般則「5xx は false」は「送った後」の話。** ここでは投稿は作られていない |
| P1 | 〃 | 401 `AuthenticationRequired` / `InvalidPassword` | **false** | App Password が違う・取り消された。**再試行しても直らず、Bluesky のログイン試行の回数を食う** |
| P1 | 〃 | 400 `AuthFactorTokenRequired` | **false** | 2 要素認証が要求された。App Password なら出ないはずで、人が資格情報を入れ直す |
| P1 | 〃 | `AccountTakedown` / `AccountDeactivated` / `AccountSuspended` | **false** | アカウント側の事情。人が直すまで直らない |
| P1 | 〃 | 応答が JSON でない・`accessJwt` が無い | **true** | **解釈できなくても、次の要求を出していない。** 一般則の「応答の解釈に失敗 → false」は `createRecord` の話 |
| P2 | 媒体の取得 | 接続断・5xx・制限時間 | **true** | 投稿は作られていない |
| P2 | 〃 | 媒体の処理の合計時間を使い切った（`kind: 'budget'`） | **true** | まだ `createRecord` を呼んでいない。§6.6 |
| P2 | 〃 | 4xx（404 など）・**既知の画像**でない・上限（1MB）超過・リダイレクト（3xx） | **false** | 投稿の内容の問題。人が `media[].url` を直す |
| P3 | `uploadBlob` | 接続断・5xx・429・制限時間 | **true** | **blob は投稿ではない。** `createRecord` を呼んでいない限り投稿は作られない |
| P3 | 〃 | 400 `BlobTooLarge` / `UnsupportedMimeType` / その他 4xx | **false** | 内容の問題 |
| P3 | 〃 | 401 | **false** | 資格情報の問題（P1 と同じ扱い） |
| P4 | `createRecord` | 429 `RateLimitExceeded` | **true** ＋ `retryAfterMs` | **書き込む前に断られたと読める。** §6.10 |
| P4 | 〃 | 接続断・制限時間（15 秒）・5xx・応答が JSON でない・`uri` が無い | **false** | **届いたか分からない。SNS の投稿は取り消せない** |
| P4 | 〃 | 401 `ExpiredToken` / `InvalidToken` | **false** | 数秒前に取ったセッションが切れている異常。**その場で取り直して送り直す形にはしない**（§11 #4） |
| P4 | 〃 | その他の 4xx（`InvalidRequest` など） | **false** | 内容の問題だが、**書き込まれていないとは言い切れない**ので安全側 |
| — | どこでも | 予期しない例外 | **false** | **例外を投げない。** catch して上の分類へ落とし、分類できなければ `false`（§6.11） |
| — | どこでも | `input.signal` が発火 | — | Core が「結果不明」として確定させている。何を返しても記録されない |

> **P2 の「リダイレクト」は `redirect: 'manual'` でなければ成立しない（2026-09-23）。**
> `redirect: 'error'` の `fetch` は 3xx を `Response` として返さず reject するので、
> 3xx は「接続できない（`kind: 'network'`）」に落ち、**この表と逆の `retryable: true`** になっていた。
> **表の行が本番で成立することは、`init` の綴り 1 つに掛かっている。** 経緯と直し方は §6.2 の引用枠。

**`createSession` の 401 を `false` にするのは、ガイドの表（「まだ送っていない認証エラー」は `true`）より狭い。**
狭くするのは契約上いつでも許される（「迷ったら `false`」）。狭くする理由は 2 つある：

* **直らない。** 資格情報が違うのは人が直すまで直らない。1 → 2 → 4 → 8 分の再試行を 4 回重ねても結果は同じで、
  **`failed` になるのが 15 分遅れるだけ**になる。運用者が理由に気づくのは早いほうがよい
* **害がある。** Bluesky は `createSession` の失敗を回数で制限している。間違った App Password で
  再試行を重ねると、**同じアカウントの正しい投稿まで巻き添えで 429 になる**

### 6.10 `retryAfterMs`

429 の応答には `ratelimit-reset`（UNIX 秒）が付く。

```text
retryAfterMs = max(0, Number(ratelimit-reset) * 1000 - Date.now())
```

* ヘッダが無い・数値でない・過去を指す → **`retryAfterMs` を付けない**（Core の既定 1 → 2 → 4 → 8 分が使われる）
* Core は `MAX_RETRY_AFTER_MS`（24 時間）で切り詰める（`035` §5.6.2）。Plugin 側で丸めない

### 6.11 例外を投げない・資格情報を漏らさない

* **`publish()` は例外を投げない。** 投げると Core は**常に「結果不明」として `failed`** にし、再試行しない
  （`035` §5.6.2 の `decidePublishOutcome`）。`createRecord` より前の失敗まで `failed` になるのは損である。
  **すべての経路を `try` で包み、`PublishResult` として返す**
* **媒体（`media` フェーズ）の失敗だけは、HTTP の status も `reason` に載せない。**
  載せてよいのは「**一時的な失敗か、`media[].url` を直す必要がある失敗か**」の二分までである

  > **2026-09-23 に足した（`security-reviewer` 中-1）。**
  > 媒体の取得先は **`social.write` を持つ誰かが書いた任意の URL** であり（§8.2）、
  > `reason` は `social_posts.failure_reason` に保存されて **`social.read` で読める。**
  > status をそのまま載せると、**投稿を 1 件ずつ積むだけで、Torifune のサーバから見える
  > 内部ホストの生死と 200 / 401 / 403 / 404 の別を列挙できる。**
  > `social.write` と `social.read` は「SNS へ投稿する人」の権限であって、
  > **ネットワークを走査してよい権限ではない。**
  >
  > **`retryable` の判断には status を使い続けてよい**（4xx は `false`、5xx は `true`。§6.9 の P2）。
  > **判断に使うことと、外へ出すことは別**である。外へ出るのは「再試行します」か
  > 「URL を確かめてください」かの 1 ビットだけで、これは運用者が次にすることを選ぶのに足りる。
  >
  > **`createSession` / `uploadBlob` / `createRecord` の status はそのまま載せる。**
  > 送り先は `plugin.manage` を持つ運用者が設定した PDS ただ 1 つ（§7.1）であり、
  > **運用者が自分の設定を直すための情報**である。走査に使える自由度が無い。
  >
  > **取得先をどう絞るかは Core（`isValidMediaUrl`）の話だが、
  > 取得先の応答をどこまで外へ出すかは、この Plugin が自分で引き受けた範囲である**（§8.2）。
  > 「Core が通した URL を Plugin が黙って拒まない」（§11 #10）は**取りに行く/行かない**の話で、
  > **取りに行った結果をどう書くか**まで Core に預けているわけではない

* **`reason` に載せてよいのは、HTTP の status と、既知の `error` コードだけ**（`media` フェーズを除く。上）**。**
  PDS が返した `message`（自由文）は**載せない**。PDS の URL は設定で変えられる（§7.1）ので、
  **応答の自由文は「Torifune の管理者が指した先のサーバが書いた文字列」**である。
  Core の伏せ字（`redactCredentialValues`）は**4 文字以上の完全一致しか消せない**（ガイド §9）ので、
  符号化して混ぜ返されれば素通りする。**伏せ字を当てにせず、載せない**
* 既知の `error` コードの集合（`AuthenticationRequired` / `RateLimitExceeded` / `ExpiredToken` /
  `InvalidToken` / `AccountTakedown` / `BlobTooLarge` / `UnsupportedMimeType` / …）に無い値は
  **`reason` に出さず `unknown` と書く**。コードそのものは短い識別子だが、**知らない値を素通しする口は作らない**
* **`logger` に渡してよいのは `postId` / `attempt` / フェーズ名 / HTTP status / 媒体の件数だけ。
  ただし `media` フェーズでは status も渡さない**（上と同じ理由。ログは `system.manage` で読める）**。**
  `credential`、`identifier`、`accessJwt`、`refreshJwt`、`post.body`、媒体の中身、応答の本文、
  **`session.handle` と `account.handle`（`identifier` と同じ値になりうる）**を渡さない
* `reason` は日本語で、**運用者が次に何をすればよいか**が読める文言にする
  （例：`Bluesky へのログインに失敗しました（401 AuthenticationRequired）。App Password を確認してください。`）

### 7.1 PDS の URL を設定で変えられるようにする（決めたこと）

```ts
context.ui.registerSettings({
  fields: [
    {
      key: 'pds-url',
      label: 'PDS の URL',
      description:
        '投稿先の PDS（Personal Data Server）。通常は変更しません。空欄なら https://bsky.social を使います。'
        + '自分で PDS を運用している場合だけ、その URL を入れてください。'
        + 'ここで指定したサーバへ、登録された App Password がそのまま送られます。',
      kind: 'text',
      placeholder: 'https://bsky.social',
    },
  ],
  validate: (values) => { /* §7.2 の検査。問題があれば { 'pds-url': '…' } */ },
});
```

**変えられるようにする。** 理由：

* **セルフホストの PDS は AT Protocol の建て付けそのもの**であり、「自分のサーバで動かす」利用者は
  Torifune（OSS・自己ホスト前提）の利用者像とそのまま重なる
* 固定にすると、自前の PDS を使う人は **Plugin を fork するしかない。** 外部サービス連携を Plugin に
  切り出した意味（`01` §12「第三者が独自の連携 Plugin を開発できる構造」）が薄れる
* 代償は `extensions` に `'ui'` が 1 つ増えることだけで、**足すのは入力欄 1 つ**である

**`credentialFields` には入れない**（§5.2）。この選択の意味は「**1 つの installation は 1 つの PDS を見る**」で、
別々の PDS のアカウントを同じ Torifune から配信することはできない（§11 #2）。

* **キーは `pds-url`。** 設定の項目名はそのまま Key-Value Store のキーになり、
  `STORE_KEY_PATTERN`（`^[a-z0-9][a-z0-9._/-]{0,127}$`）に従う。**`pdsUrl` は大文字を含むので保存できない**
* `kind` は `'text'`。**Secret ではない**（URL は秘密ではなく、`secret` にすると設定済みかしか見えず、
  **どこへ送っているかを運用者が確かめられなくなる**）
* 既定値は Plugin の定数 `DEFAULT_PDS_URL = 'https://bsky.social'`。**未設定・空文字は既定へ落とす**
* 読むのは **`publish()` の中だけ**（`store.get<string>('pds-url')`）。`activate()` の時点で読んで
  閉じ込めると、**設定を変えても再起動するまで効かない**
* **`manual()` は `store` を読まない**（§8.2 の 2 秒。1 画面で最大 50 回呼ばれる）。
  手動投稿の URL は `bsky.app` 固定で、PDS の設定と関係がない

### 7.2 PDS の URL の検査（保存時と配信時の両方）

| 検査 | 落ちたときの扱い |
| --- | --- |
| 空文字 | 問題としない（既定へ落とす） |
| `new URL()` に通らない | 保存時：`{ 'pds-url': 'URL の形式が不正です。' }`／配信時：`retryable: false` |
| `https:` でない | 「https の URL を入れてください。」 |
| `username` / `password` を含む | 「URL に利用者名やパスワードを書かないでください。」 |
| パス（`/` 以外）・クエリ・フラグメントを含む | 「PDS の URL はホストまでを入れてください（例：https://bsky.social）。」 |
| 2048 文字超 | 「長すぎます。」 |

* **保存時に通っても、配信時にもう一度見る。** 設定は Key-Value Store の値であり、
  Plugin の版を上げて検査を厳しくしたときに古い値が残る。**「保存時に検査したから配信時は信じる」にしない**
* **`http` を許さない。** そこへ App Password を平文で送ることになる。開発用の例外も作らない
* **要求の URL は `new URL('/xrpc/' + nsid, pdsUrl).href` で組み立てる。** 文字列の連結にしない

  > **2026-09-23 に足した（`security-reviewer` 低-2）。**
  > 検査は `new URL()` の**解析結果**を見るのに、組み立ては**生の文字列**を繋いでいた。
  > 同じ値を 2 つの規則で読むと、その差が抜け道になる。実例：`https://example.com/?` は
  > `new URL()` で `search === ''`（`?` の後ろが空）になるので検査を通り、
  > 連結では `https://example.com/?/xrpc/com.atproto.server.createSession` になる——
  > **パスがクエリ文字列に化け、App Password がクエリつきの別の宛先へ飛ぶ。**
  > `#` でも同じ形になる。**解析した結果から組み立てれば、2 つの規則が 1 つになる。**

## 8. 権限（Permission）

**新しい Permission を作らない。** `plugin.json` の `permissions` は **空**（`[]`）である。
この Plugin は Data API（`context.data`）を 1 度も呼ばない。投稿も資格情報も、`publish()` / `manual()` の
**引数として渡ってくる**（`035` §6.5.5）。

| 操作 | Permission | 権限なし | 未認証 |
| --- | --- | --- | --- |
| `/plugins/sns-bluesky/settings` を開く・保存する | `plugin.manage`（Core） | 403 | 401（画面は `/login` へ） |
| `/plugins` で導入・有効化・無効化 | `plugin.manage`（Core） | 403 | 401 |
| SNS アカウントに資格情報を入れる | `social.write`（Core） | 403 | 401 |
| 投稿を予約する・手動投稿待ちを見る | `social.write` / `social.read`（Core） | 403 | 401 |
| ジョブ `social.publish`（`publish()` を呼ぶ） | 認可の外（本体の処理。`035` §6.8） | — | — |

### 8.1 拡張点の宣言

```json
{
  "id": "sns-bluesky",
  "name": "Bluesky配信",
  "version": "1.0.0",
  "apiVersion": 1,
  "description": "予約したSNS投稿を Bluesky（AT Protocol）へ配信する。App Password で動く。",
  "author": "Torifune",
  "license": "MIT",
  "permissions": [],
  "extensions": ["social", "ui"]
}
```

* **`social` は必須。** 宣言しないと `registerPublisher` が `PluginExtensionNotDeclaredError` を投げ、
  Plugin が `disabled` に落ちる（`035` §9.4）
* **`ui` も宣言する。** 使うのは `registerSettings` の 1 つだけだが、
  **`registerSettings` は `context.ui` の関数**である。Core は `ui` の宣言を強制していないが、
  開発ガイド §12 は「拡張点は宣言したものだけを使う」と書いている。**強制されていないから宣言しない、はしない**
* **`extensions` は導入前の `/plugins` に出る**（`035` §7.9）。
  「SNS配信（SNSアカウントの資格情報を受け取ります）」が、**入れる前に読まれる**前提で宣言している

### 8.2 高権限であることの自覚

この Plugin は `social_accounts` に登録された **Bluesky の App Password を平文で受け取る**
（`publish()` の `credential`。その呼び出しの間だけ）。したがって：

* **App Password の送り先（PDS の URL）を変えられるのは `plugin.manage` を持つ者だけ**である。
  `plugin.manage` は Plugin の導入そのものを許す権限（＝アプリへのコード導入。`01` §14）なので、
  **設定で送り先を変えられることが新しい危険を生むわけではない。** ただし
  「ここで指定したサーバへ App Password がそのまま送られる」と `description` に書く（§7.1）
* **媒体の取得先（`media[].url`）は `social.write` を持つ者が指せる**（§6.2）。
  Torifune のサーバから任意の https へ GET が飛ぶ。リダイレクトを追わない・種別と大きさを絞る・
  中身をログにも `reason` にも載せない、までをこの Plugin が受け持つ。**取得先そのものの制限は Core の
  `isValidMediaUrl` が決めることで、Plugin から広げも狭めもしない**（§11 #10）
* **取得先の応答を「どこまで外へ出すか」は、Plugin が自分で引き受けた範囲である。**
  `isValidMediaUrl` は「https・資格情報なし・2048 文字以内」しか見ず、**私有アドレスもループバックも通る。**
  そこへ GET を出すのは Core が決めたことだが、その**応答の HTTP status を
  `failure_reason`（`social.read` で読める）とログへ書くかどうか**は、この Plugin が決めている。
  **書かない**（§6.11）。書くと、`social.write` を持つ者が**投稿を積むだけで内部ネットワークを走査できる。**
  取得先を絞れないこと（§11 #10）と、絞れないぶん**観測結果を外へ出さないこと**は、別々の判断である

## 9. Plugin API への影響

**無し。`packages/plugin-api` を 1 行も変えない。Core への追加要求も無い。**

`035` §13 の主張（「本設計の口だけで 3 つの Plugin が書ける」）は Bluesky について成り立つ。
使う口と、それで足りた理由：

| 使う口 | 用途 | 足りたか |
| --- | --- | --- |
| `PublisherRegistration.provider` / `label` | `'bluesky'` / `'Bluesky'` | 足りた。`label` が `PROVIDER_LABELS` より優先される |
| `credentialFields`（`PluginSettingsField`） | `identifier` / `appPassword` | 足りた。`description` に注意書きを書ける |
| `PublisherLimits` | `bodyMaxLength` / `mediaMax` | **キーを足さずに済んだ**（§9.1） |
| `validate()` / `PublisherValidationProblem` | grapheme・バイト数・alt・link と media の同居・`providerOptions.langs` | 足りた。`field` に `providerOptions.langs` を書ける |
| `PublishInput`（`post` / `account` / `credential` / `attempt` / `signal` / `logger`） | 配信 | 足りた。`account.handle` は使わず `createSession` の `handle` を使う（§6.4） |
| `PublishResult` | `externalId` / `externalUrl` / `reason` / `retryable` / `retryAfterMs` | 足りた。`rotatedCredential` は使わない |
| `ManualInput` / `ManualHandoff` | intent URL と注意書き | 足りた |
| `PluginStore` | `pds-url` の読み出し | 足りた |
| `PluginUiApi.registerSettings` | PDS の URL の入力欄 | 足りた |
| `PluginLogger` | フェーズと status | 足りた |

### 9.1 `PublisherLimits` にキーを足さない（受け入れ条件 #87 / #103 / #104 が効く）

`035` は `PublisherLimits` について「**キーを足したら、同じ変更で `checkPublisherLimits` にも判定を足す**」
と決め、**キーの集合が一致していることを受け入れ条件 #87 の (E) で固定**している。
つまり **`PublisherLimits` にキーを足すのは Core（`packages/plugin-api` と `apps/web/src/domain`）の変更**であり、
Plugin 側だけでは閉じない。

Bluesky に「300 grapheme」「3000 バイト」「画像は 4 枚」という上限があっても、
**新しいキー（`bodyMaxGraphemes` のような）を足さない。** 数え方が SNS ごとに違うことは
`035` §11 #8 が既に「`limits.bodyMaxLength` は粗い上限（`String.length`）で、**厳密な判定は `validate()`**」
と決めている。本設計はその決定に従う。

同じ理由で、**`103` / `104`（Plugin マネージャが Manifest の `extensions` を導入前に表示する）が
要求する形を壊さない。** `extensions` に書くのは `PLUGIN_EXTENSION_KINDS` にある値
（`social` / `ui`）だけで、独自の値を足さない。足すと `/plugins` に**生の値がそのまま**出る（#103）。

### 9.2 `limits.bodyMaxLength` を 300 にしない（決めたこと）

**`limits: { bodyMaxLength: 3000, mediaMax: 4 }` とする。`035` §13 の骨子が書いた `300` は採らない。**

理由：**`checkPublisherLimits` は `post.body.length`（UTF-16 の要素数）で数える。**
grapheme の数は常に `String.length` 以下なので、`bodyMaxLength: 300` は
**Bluesky が受け付ける投稿を Core が 422 で弾く**側に倒れる。
絵文字（サロゲートペアで 2 要素）や異体字セレクタ・肌色修飾を含む本文では、
**200 grapheme しかないのに `length` が 400 を超える**ことが普通に起きる。
`035` §11 #8 が `bodyMaxLength` を「**早く弾くための粗い上限**」と定めた以上、
**粗い側（緩い側）に置くのが正しく、厳しい側に置くと粗さが誤判定になる。**

`3000` にしても利用者の体験は悪くならない。**`validate()` は登録時にも呼ばれる**（ガイド §9 の表）ので、
301 grapheme の本文は `limits` ではなく `validate()` が、**正確な数と理由つきで** 422 にする。
`limits` の役目は「明らかに大きすぎる本文を、Plugin を呼ばずに落とす」ことだけである。

`3000` という数の根拠は、Bluesky の `app.bsky.feed.post` が `text` に宣言しているもう 1 つの上限
（**3000 バイト**）である。`String.length` とバイト数は一致しないので、**3000 は「これを超えたら
どう数えても確実に超過」という粗い線**として使う。厳密な 3000 バイトの判定は `validate()` が行う（§9.3）。

### 9.3 `validate()` が見るもの

**5 秒で打ち切られる。外部へ問い合わせない。純関数だけで判定する**（`text.ts`）。

| # | 検査 | `field` | 文言の趣旨 |
| --- | --- | --- | --- |
| 1 | 本文の grapheme 数 ≤ **300** | `body` | `本文は300文字以内にしてください（Bluesky は絵文字や結合文字を1文字として数えます）。いまは N 文字です。` |
| 2 | 本文の UTF-8 バイト数 ≤ **3000** | `body` | `本文が長すぎます（Bluesky の上限は3000バイトです）。` |
| 3 | `media[].alt` の grapheme 数 ≤ **1000** | `media` | `画像の説明（alt）は1000文字以内にしてください（N 件目）。` |
| 4 | `deliveryMode: 'auto'` で `media` と `link` の同時指定 | `link` | `Bluesky は画像とリンクカードを同時に付けられません。リンクは本文に含めてください。` |
| 5 | `providerOptions.langs` の形（配列・要素は文字列・3 件以内・各 2〜16 文字） | `providerOptions.langs` | `langs は言語コードの配列で指定してください（3件まで。例：["ja"]）。` |
| 6 | `providerOptions` に 5 以外のキーがある | `providerOptions.<key>` | `<key> は Bluesky では使いません。` |

* **数え方は `Intl.Segmenter`**（`new Intl.Segmenter(undefined, { granularity: 'grapheme' })`）。
  Node 22（`lib: ES2023`）に型も実装もある。**`Segmenter` は生成が重いので module スコープで 1 つ作って使い回す**
  （`validate()` は 1 画面の描画で何度も呼ばれうる）
* **`deliveryMode: 'manual'` のときは、本文ではなく `body + '\n' + link` を数える**（§9.4 で実際に渡す文字列だから）。
  手動投稿に `media` は付けられない（Core が 422。`035` §6.1.2 の f/l）ので、4 の検査は `auto` のときだけ
* **`media` の枚数は数えない。** `limits.mediaMax = 4` が Core 側で**正確に**効く（枚数は数え方が 1 つしかない）。
  同じ判定を 2 か所に書かない
* **`media[].url` の形式も数えない。** Core の `isValidMediaUrl` が https・資格情報なし・2048 文字を見ている。
  拡張子で画像かどうかを見る案は採らない（拡張子の無い URL が画像であることは普通にある）。
  実際に画像かどうかは `Content-Type` で分かる（§6.2）
* **`alt` の 1000 は Bluesky 側の事実ではない。** `app.bsky.embed.images` の `alt` に公開された上限は無く、
  この 1000 は Core の `MEDIA_ALT_MAX_LENGTH`（1000 **文字**）に数を合わせたものである。
  数え方だけ grapheme に揃えてあるので、**Core より先に、Plugin の言葉で断る**ための検査になる。
  §11 #11 に残す
* **例外を投げない。** `validate()` が投げると、登録は 500、配信直前なら `failed`（未送信）になる
  （`035` §6.5.2.2 の 3）。`providerOptions` は外から来た任意の JSON なので、
  **型を確かめてから触る**（`Array.isArray` / `typeof`）

### 9.4 `manual()`

```ts
manual({ post }): ManualHandoff {
  const text = post.link === null ? post.body : `${post.body}\n${post.link}`;
  return {
    url: `https://bsky.app/intent/compose?text=${encodeURIComponent(text)}`,
    note: 'Bluesky の投稿画面が開きます。内容を確かめて投稿してください。画像を添える場合はその画面で添付してください。',
  };
}
```

* **`link` は本文の末尾へ改行して足す。** intent URL に外部埋め込みを指定する口は無い。
  本文に入れておけば、Bluesky の投稿画面がリンクとして扱う
* **`store` を読まない・`await` しない・例外を投げない。** 2 秒で打ち切られ、
  1 画面で最大 50 行ぶん呼ばれる（ガイド §9）。**文字列を組み立てるだけ**にする
* **`note` の文面**：`035` §13 の骨子は「画像は投稿画面で添付してください」だが、
  **手動投稿に `media` は付けられない**（Core が 422 で断る）ので、そのままでは
  「付けたはずの画像が落ちた」と読まれる。**「添える場合はその画面で」**と書き換えた
* **`account` を使わない。** intent URL は公開の投稿画面で、誰のアカウントかを指定できない
  （ブラウザでログイン中のアカウントで開く）。`035` §11 #15 のとおり、資格情報は渡らない
* `note` は Core が `redactSecrets` を通してから画面へ出す（`035` §6.6）。**固定文なので何も消えない**

### 9.5 `plugins/sns-bluesky/README.md`

Plugin を配る側の責務として、次を書く（開発ガイド §9 が「README に書いておくとよい」と言っているもの）。

* App Password の発行手順（Bluesky の設定画面から。**ログインパスワードではない**）と、取り消せること
* **導入してから資格情報を入れるまでの猶予は約 24 時間**であること（`035` 裁定 #9）。
  Plugin を有効にしないまま、あるいは資格情報を入れないまま予約した投稿は、
  **予約時刻から約 24 時間で `failed`** になり、`failed` は終端で**新しい投稿として登録し直す**ことになる

79. (A) 取得した媒体の `Content-Type` が `image/png` / `image/jpeg` / `image/gif` / `image/webp`
    以外（`image/svg+xml`・`image/x-icon` など）なら **`retryable: false` で断る。**
    `image/png; charset=utf-8` は受け付け、**`uploadBlob` へ送る `content-type` は `image/png`**
    （取得先の応答ヘッダそのままではない。§6.2）
80. (A) **媒体の処理の合計時間を使い切ったら `kind: 'budget'` で諦める**
    （`retryable: true`、`createRecord` を呼ばない、残りの媒体を取りに行かない）。
    `now()` を進める偽の時計で再現する。**この分岐を実際に通るテストがあること自体が条件**（§6.6）
81. (A) **どの定数がどの要求へ渡っているかを見る。** 1 件の媒体を添えた配信で、
    `createSession` に `CREATE_SESSION_TIMEOUT_MS`、媒体の GET に `MEDIA_FETCH_TIMEOUT_MS`、
    `uploadBlob` に `UPLOAD_BLOB_TIMEOUT_MS`、`createRecord` に `CREATE_RECORD_TIMEOUT_MS` が渡り、
    `publish()` 全体に `PUBLISH_TOTAL_BUDGET_MS` が掛かる。
    **値が合っていても結線が入れ替われば落ちる**ようにする（§6.6）
82. (A) **画像とリンクカードが同居した投稿を `publish()` が断るときも `logger.warn` が出る**
    （`phase: 'embed'`。`fail()` を通らない早期 return でもログが残る。§6.8）
83. (E) **結合テストも `beforeEach` で `globalThis.fetch` を「呼ばれたら投げる」に置いてから、
    偽の PDS で上書きする。** 偽 PDS を用意しないテストが素の `fetch` のまま走らないこと
    （いまは `publish()` へ到達しないが、**到達するようになったときに気づけない**のが問題である。#52 の結合側）

### 11.1 `035` §11 #17 の実地の判断 — `bluesky` は Core に残す

`035` §11 #17 はこう残していた。

> `KNOWN_PROVIDERS` に `bluesky` を足した結果、**SNS が増えるたびに Core Domain を触る導線**が残る。
> `036` を実際に作って「無効時に生の値が出る」がどれだけ困るかを見てから、
> `PROVIDER_LABELS` を Core から外すかを決める。外すなら `037` / `038` の前に。

**036 を書いた結果、次の 2 つが分かった。**

**1. 懸念された導線は、036 では現実化しなかった。**
本設計は Core を 1 行も変えていない（§9）。`bluesky` は `035` が既に `KNOWN_PROVIDERS` へ足してあり、
`x` / `instagram` も元からある。**`037` / `038` も Core を触らずに書ける。**
「SNS が増えるたびに Core Domain を触る」という導線は、`KNOWN_PROVIDERS` に無い SNS
（Mastodon、Threads など）を第三者が Plugin にするときに初めて現れる。
そのとき何が起きるかは `providerLabel(provider, overrides)` が答えを持っている——
**Core を触らなくても `label` で表示名は出る。** 表は「Core が表示名を知っている provider」の
列挙にすぎず、**新しい SNS の追加を妨げない。**

**2. 「無効時に生の値が出る」は、いちばん見たくない場面で起きる。**
`PROVIDER_LABELS` から `bluesky` を外すと、Plugin が無効な間だけ画面の provider 列が `bluesky` に落ちる。
その「Plugin が無効な間」は次のときに現れる：

* Plugin の更新中（導入は**再ビルドと再起動を伴う**。ガイド §10）
* ビルドを壊して**隔離された**とき（`.torifune-quarantine`）
* 依存の無効化に巻き込まれたとき
* **資格情報を入れる前の、猶予 24 時間のあいだ**（`035` 裁定 #9）

最後のものが決め手である。**その 24 時間は、運用者が `/social` を開いて
「なぜ配信されないのか」を確かめている時間そのもの**であり、そこで一覧の SNS 名が生の値に落ちるのは、
**困り方がいちばん大きい瞬間に表示が劣化する**ということになる。
一方、表を残す代償は `domain/social/social.ts` の配列に 1 行あることだけで、
**新しい SNS の追加を妨げない**（1 で見たとおり）。

**したがって `PROVIDER_LABELS` / `KNOWN_PROVIDERS` を Core から外さない。#17 を閉じる。**
`037` / `038` の前に決めるべきことは、これで無くなった。
（`x` / `instagram` は既に表にあるので、`037` / `038` も Core を触らない。）

> **この判断が覆る条件**：`KNOWN_PROVIDERS` に無い provider の Plugin が実際に現れ、
> **無効時の表示が生の値に落ちることが受け入れられている**と分かったとき。
> そのときは「Core が知っている provider」と「知らない provider」で振る舞いが違うことのほうが
> 説明しにくくなるので、表ごと外すのが筋になる。**036 の時点では、その Plugin はまだ無い。**
