## 2. 見つかった欠陥と処置

### R-1（`spec-verifier` が重大扱い）— テストが偽物の振る舞いに依存していた

**`fetchMedia` は `redirect: 'error'` で出していたが、`redirect: 'error'` の fetch は
3xx を `Response` として返さず reject する。** したがって `status >= 300 && < 400` の分岐は
**本番で到達しない**。実際のリダイレクトは `kind: 'network'` → **`retryable: true`** になり、
設計 §6.9 P2 の `false` と**逆**だった。

**テストが緑だったのは、偽 `fetch` が 302 の `Response` を返していたから。**
この 1 件だけ判別力が無かった。

**処置**：Node で実測してから直した。

```
redirect: 'error'  → reject（TypeError: unexpected redirect）
redirect: 'manual' → status 302 / type 'basic' がそのまま返る  ← 採用
redirect: 'follow' → 追ってしまう
```

`'manual'` は**追わずに 3xx を観測できる**（ブラウザの opaque-redirect（status 0）とは違う）。
これで設計の表が本番でも成立し、「追わない」という本質も守られる。

**あわせて、偽物と本物が一致することを直接確かめるテストを足した**（#74）。
`node:http` のループバックサーバを立て、**本物の `fetch`** で
(a) `'manual'` が 302 を返すこと、(b) `'error'` が reject すること、
(c) **偽 PDS と本物の `fetch` を混ぜて `publish()` を通し、本物の 302 を踏んでも偽の 302 と同じ結果になること**
を見る。外部への通信は 1 本も出ない。

### 中-1（`security-reviewer`）— 媒体の失敗理由が HTTP status を反射していた

`mediaReason` が `（404）` の形で status を本文へ差し込み、`social_posts.failure_reason` に保存され
**`social.read` で読めた**。`media[].url` は**利用者が指定した任意の URL**で、
Core の `isValidMediaUrl` は https・資格情報なし・2048 文字しか見ない（私有アドレスもループバックも通る）。
つまり**投稿を 1 件ずつ積むだけで、内部ホストの生死と 200 / 401 / 403 / 404 を列挙できた**。

**「Plugin の話ではない」で流せなかった理由**が的確だった。設計 §11 #10 は
「取得先の制限は Core が決めることで Plugin では広げも狭めもしない」としており**その判断自体は妥当**だが、
§8.2 は直後に Plugin 側の受け持ちを自分で宣言している——「リダイレクトを追わない・種別と大きさを絞る・
**中身をログにも `reason` にも載せない**」。
**「取得先をどう絞るか」は Core の話でも、「取得先の応答をどこまで外へ出すか」は Plugin が引き受けた範囲**である。

**処置**：`media` フェーズの `reason` とログから status を落とした。
粒度は「一時的な失敗／`media[].url` を直す必要がある失敗」の二分まで。
**`retryable` の判断には status を使い続ける**（**判断に使うことと外へ出すことは別**）。
`createSession` / `uploadBlob` / `createRecord` の status は**そのまま**（送り先は運用者が指した先で、
運用者が自分で直すための情報）。

### 低-1（`security-reviewer`）— `rkey` の長さが二重投稿につながりうる

`createRecord` は `uri` の最終セグメントを**空判定だけ**で通していた。
`external_id` は **200 文字以内**の CHECK があり、`publish()` 経路にこの検査が無い。
200 文字超が返ると `recordOutcome` が CHECK 違反で例外 → Core が握って `unrecorded` →
**着手印が残ったまま投稿は Bluesky に存在** → 中断行として拾われ**二重投稿**。
**この機能が最も避けたい結果である。**

**処置**：200 文字以内を確かめ、超えたら**失敗にせず** `externalId` を省いて `ok: true`
（投稿は実際に作られている）。**`externalUrl` も同じ扱い**にした——`externalUrl` にも `rkey` が含まれ、
`external_url` の 2048 文字 CHECK に同じ形で掛かる（指摘に無かった波及を実装側が見つけた）。

## 4. `boundary-guardian` を回していない理由

**Core を 1 行も変えていないことが機械的に確かめられている**（§1）。
公開契約（`packages/plugin-api`）も無変更で、`migrations` も足していない。
`035` で 2 回目に**合格**を出した観点（SaaS 混入・API 互換・レイヤ・単体成立性）のいずれにも
触れる変更が無いため、今回は回していない。**必要になれば後から回せる。**

なお `security-reviewer` が**第三者 Plugin の手本として妥当か**という観点で見ており、
境界の関心の一部（本体の内部モジュールを import しないこと、`permissions: []` であること）は
そちらで確認されている。

## 5. 残る限界

| # | 内容 |
| --- | --- |
| 1 | `spec-verifier` は**テストを実行して**判定したが、`security-reviewer` は**1 本も実行していない**（DB 競合を避けるため）。中-1 と低-1 は**コードの読解に基づく推論で、実機で再現させていない** |
| 2 | `security-reviewer` は `sns-bluesky.test.ts` / `sns-bluesky-publish.test.ts` / `sns-bluesky.integration.test.ts` の**全文を読んでいない**（狙った assertion を grep で引いて周辺だけ） |
| 3 | 動的な検証（実際に偽 PDS を立てて publish を通す、内部アドレスへの GET が本当に出ることの実測）は**行っていない** |
| 4 | 実際の Bluesky（`bsky.social`）に対する疎通は**一度も試していない**。AT Protocol の応答の形は仕様と公開ドキュメントに基づく |

**4 が最も大きい。** この Plugin は実機の Bluesky で 1 度も動かしていない。
`credentialFields` に本物の App Password を入れて配信するところまでは、**運用者の手で確かめる必要がある**。
