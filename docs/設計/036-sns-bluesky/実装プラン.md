### 確定事項（設計書から。プランで蒸し返さない）

* **Core（`apps/web` / `packages/plugin-api` / `migrations`）に 1 行も足さない。** 作るのは `plugins/sns-bluesky/` の 7 ファイルと、`apps/web/src/plugin/` に置くテストだけ（設計 §1 / §3.2 / §9）
* この Plugin が持つ状態は **`pds-url` の 1 件だけ**。投稿の状態も資格情報も持たない（設計 §3.3）
* `credentialFields` は **`identifier` / `appPassword` の 2 つで確定**。増やすのは既存アカウントを壊す破壊的変更なので、増やす前提で設計しない（設計 §5.1 / §5.2）
* `limits` は **`{ bodyMaxLength: 3000, mediaMax: 4 }`**。`035` §13 の骨子が書いた `300` は採らない（設計 §9.2）。`PublisherLimits` にキーを足さない（設計 §9.1）
* **`publish()` 1 回につき `createSession` 1 回。`refreshJwt` は捨てる。`rotatedCredential` は返さない**（設計 §6.5）
* **`retryable` はフェーズで決まる。** `createRecord` を送る前は既定 `true`、送った後は既定 `false`、例外は投げずに分類へ落とす（設計 §6.9 / §6.11）
* **`facets` はバイト位置（UTF-8）**。`String` の添字を渡さない（設計 §6.7）
* **`embed` は 1 つだけ。** `media` と `link` の同居は `validate()` が断る（設計 §6.8 / §9.3 の 4）
* `plugin.json` の `permissions` は **空**。`extensions` は `['social', 'ui']`（設計 §8 / §8.1）
* 画面部品を 1 つも持たない。`registerSettings` 以外の `context.ui` の関数を呼ばない（設計 §7）
* `reason` に載せてよいのは **HTTP の status と既知の `error` コードだけ**。PDS の `message`（自由文）は載せない（設計 §6.11）
* **マイグレーションは無い。** テーブルもカラムも Permission も足さない（設計 §5）
* **TorifuneHub への変更は無い。** SaaS 固有機能（テナント・課金・コンテナ管理）に触るタスクは本プランに無い

### テストの方法（設計書に無い、プラン側で決める手段）

* **偽の PDS（A 群）**：`fetch` の偽物は「要求の列を記録し、URL ごとに用意した `Response` を返す関数」を各テストファイルにローカルで持つ。
  `new Response(JSON.stringify(body), { status, headers })` で組み立てる。**`createBlueskyPublisher({ store, fetch: fake, now })` に注入する**（設計 §10.1）
* **本物の `fetch` を呼ばない仕掛け（#52）**：A 群の 3 ファイルそれぞれの `beforeEach` で
  `globalThis.fetch = (() => { throw new Error('本物の fetch が呼ばれた'); }) as typeof fetch` を置き、`afterEach` で元へ戻す。
  **共有ヘルパを `apps/web/src/plugin/` に作らない**（テスト以外のファイルを本体へ足さないため。§8 の 2）。
  静的検査（#52 の E 側）が「`sns-bluesky*.test.ts` のすべてにこの差し替えがある」ことを読む
* **偽の `store`（A 群）**：`Map` を包んだ最小の `PluginStore` をローカルに持つ。`get` / `set` だけ実装し、
  残りは `throw new Error('使わない')`。#62（毎回読む）は `Map` の値を差し替えて 2 回呼ぶ
* **`now` の注入**：`now: () => new Date('2026-09-23T12:34:56.789Z')`。#35 はこの ISO 文字列と `record.createdAt` を比べる
* **媒体の本体（#37 / #44 の 1MB 打ち切り）**：`new Response(new ReadableStream({ start(c) { … } }), { headers: { 'content-type': 'image/png' } })` で
  `Content-Length` の無い応答を作る。1MB 超は「読みながら打ち切る」経路を通す
* **媒体を 1 件ずつ順に処理すること（#43）**：偽 `fetch` が受け取った URL を配列に積み、
  `[media0, uploadBlob, media1, uploadBlob, createRecord]` の順であることを見る
* **`input.signal`（#50 / #51）**：`AbortController` を作り、#50 は先に `abort()` してから `publish()` を呼ぶ。
  #51 は**解決しない `fetch`**（`new Promise(() => {})`。ただし `init.signal` の `abort` で reject する）を渡し、
  テスト側から `controller.abort()` して `retryable: true` が**即座に**返ることを見る。
  **自前の 10 秒という値そのものは `atproto.ts` が export する制限時間の定数で固定する**（§8 の 3）
* **B 群の偽 PDS**：`plugins/sns-bluesky/index.ts` は `fetch` を注入しないので、**`globalThis.fetch` を偽物へ差し替える**
  （設計 §10 冒頭「B（結合）… `fetch` は偽物」）。`afterEach` で元へ戻す
* **B 群の Plugin の有効化**：`example-plugin.integration.test.ts` を写す
  （`discoverPlugins().plugins.find((p) => p.manifest.id === 'sns-bluesky')` → `installPlugin` → `enablePlugin`）
* **#14（`social` を外した Manifest）**：`plugin.json` を書き換えず、`enablePlugin` に
  `{ ...entry.manifest, extensions: ['ui'] }` と実物の `entry.plugin` を渡す（`social-extension.integration.test.ts` と同じ口）
* **#70（provider の衝突）**：sns-bluesky を有効化したうえで、`{ provider: 'bluesky', label: 'x', credentialFields: [] }` を
  登録するだけの合成 Plugin を `enablePlugin` に渡す（同上）
* **C 群（#60 / #61）の実行手段**：`import { GET, PUT } from '@/app/api/v1/plugins/[id]/settings/route'` して
  `GET(new Request('http://127.0.0.1:3000/api/v1/plugins/sns-bluesky/settings'), { params: … })` の形で直接叩く。
  未認証・`plugin.manage` なし・ありの 3 通りを `contextFor` で作り分ける（`035` §8 の 1 と同じ判断）
* **#72 の置き場**：`apps/web/e2e/plugin-manager.spec.ts` に 1 件足す。**`social-publishing.spec.ts` は触らない**（#73）
* **#73 の固定**：E2E の spec を読み、`sns-bluesky` という文字列がどこにも現れないことを静的検査で見る
* **`afterEach` の掃除（B / C）**：`social_posts` → `social_accounts` → `plugin_store` → `plugins` → `users` の順に `deleteFrom`（FK の向き）。

## 3. タスク分解

原則：**1 タスク = 1 コミット**。各タスクは「テストを書いて失敗を確認 → 実装 → 通す」の順。
各まとまり（G1〜G5）の最後で `pnpm generate:plugins` → `pnpm test` / `pnpm typecheck` / `pnpm lint` / `pnpm format:check` が通る。
E2E（`pnpm test:e2e`）は **G4 と G5 の終わり**に全件流す。

**着手順の骨子**：純関数（外部 I/O 無し）→ 外部 I/O → Core を通した結合 → API と画面 → 文書と静的検査。
設計 §4 が `text.ts`（純関数）と `atproto.ts`（外部 I/O）を分けているので、**数え方と facet は HTTP の差し替え無しで先に潰せる。**

### G1. 骨格と純関数（`fetch` を 1 度も使わない）

#### T1. Manifest と登録の骨格

* **何をするか**：`plugins/sns-bluesky/plugin.json` を設計 §8.1 のまま置く。
  `social.ts` に `BlueskyPublisherOptions` と `createBlueskyPublisher()` を置き、
  **`provider` / `label` / `credentialFields` / `limits` だけ**を返す（`validate` / `manual` / `publish` はまだ無い）。
  `index.ts` は `context.social.registerPublisher(createBlueskyPublisher({ store: context.store }))` の 1 行
* **テストを先に書く**：`sns-bluesky.test.ts`（#9〜#12）、`sns-bluesky-static-checks.test.ts`（#4）
* **対象**：`plugins/sns-bluesky/plugin.json`、`index.ts`、`social.ts`、テスト 2 本

## 7. リスクと注意点

1. **`fetch(` の綴りを増やさない（T7 / #2）。** `atproto.ts` の内部では `impl(url, init)` のような変数名で呼び、
   `globalThis.fetch` は `resolveFetch()` の中の **1 か所だけ**にする。
   `fetch(` と書いた瞬間に #2 が落ちる。**この制約は実装の書き方を縛るので、T7 の最初に決めきる**
2. **静的検査は実装が無いうちは素通りする（T1 / T21）。** #2 / #3 / #5 / #6 は「無いこと」を見る検査なので、
   ファイルが空のうちは必ず通る。**判別力が付くのは実装が入った後**であり、T21 で改めて全件走らせる
   （`035` の「リスク4 の宿題」と同じ失敗をしない）
3. **`Intl.Segmenter` の生成は重い（T2）。** module スコープで 1 つ作って使い回す（設計 §9.3）。
   `validate()` の中で毎回 `new` すると、1 画面の描画で何十回も作ることになる
4. **`validate()` は同期で返す（T3 / #25）。** `PublisherRegistration.validate` は `Promise` も許すが、
   `Promise` を返すと #25 が落ちる。**`async` を付けない**
5. **`providerOptions` は外から来た任意の JSON（T3 / #24）。** 循環参照を含みうるので、
   `JSON.stringify` で舐めない。`Array.isArray` / `typeof` で確かめてから触る
6. **`AbortSignal.any` は 1 要求ごとに作る（T7）。** 使い回すと、1 件目の制限時間で 2 件目まで止まる。
   `AbortSignal.timeout` は Node 22 の標準だが、**vitest の fake timer では進まない**（§8 の 3）
7. **媒体の合計 20 秒の残り時間の計算（T8）。** `createSession` の後に残り時間から取る（設計 §6.6）。
   ここを実時間で測ると、結合テストが遅い環境で不安定になる。**`now()` ではなく `Date.now()` の単調差**で測り、
   テストは「合計を超えたら諦める」経路を短い上限を注入せずに踏めるよう、
   **偽 `fetch` を遅らせるのではなく、媒体を多数（5 件以上）にして `mediaMax` の外側から踏む**ことはできない
   （Core が 4 件で切る）。**この経路は `atproto.ts` が export する上限の定数を注入可能にせず、
   `input.signal` の発火で代替する**（#51 と同じ手）
8. **B 群では `globalThis.fetch` を差し替える（T16）。** `index.ts` は `fetch` を注入しないので、
   偽 PDS を挿す口はここしかない。**`afterEach` で必ず元へ戻す。** 戻し忘れると後続のテストが道連れになる
9. **`plugins/` を変えたら `pnpm generate:plugins`（全タスク）。** `pnpm test` が先に走らせるが、
   `pnpm typecheck` は走らせない。**`typecheck` だけを先に叩くと `generated-registry.ts` が古いまま**になる
10. **`credentialFields` を後から増やせない（T1）。** 増やすと既存アカウントが全部止まる（設計 §5.2）。
    実装中に「PDS をアカウントごとに持ちたい」と思っても、**`credentialFields` へ足さない。**
    設計 §11 #2 がその場合の解き方（ハンドルから PDS を解決する）を決めてある
11. **`reason` の文言は運用者が読む（T14）。** Core は `reason` を `failure_reason` に入れて履歴画面へ出す。
    英語のコードだけを返すと、運用者は次に何をすればよいか分からない。
    かといって PDS の `message` を混ぜると資格情報が漏れうる。**「日本語の固定文 ＋ status ＋ 既知コード」**で組み立てる
12. **`createSession` の 401 を `retryable: false` にする（T11）。** ガイドの表より狭い。
    実装中に「ガイドと違う」と見えるが、**設計 §6.9 / §11 #12 が意図して狭めている。** 勝手に広げない
13. **`createRecord` の後は疑わしきを `false` に倒す（T13）。** 500 も「応答が JSON でない」も `false`。
    **SNS の投稿は取り消せない。** ここで `true` に倒すと二重投稿になる
14. **`externalUrl` は `bsky.app` 固定（T7）。** セルフホストの PDS では開けない構成がありうるが、

### 設計書の不足点（推測で埋めず、上の表で手段だけを決めたもの）

**計画を止めるほどの不足は無い。** 実装仕様は §5〜§9 で確定しており、受け入れ条件 73 件はすべて
テスト種別とファイルへ対応づけられた（§4）。上の表のうち **#3（`51` の 10 秒の確かめ方）と
