### 確定事項（設計書から。プランで蒸し返さない）

* 配信を駆動するのは **Core のジョブ 1 本**（`social.publish`、1 分周期）。Plugin は `publish()` と `manual()` だけを書く（§3.3）
* **着手印（`publish_started_at`）を書いてコミットしてから `publish()` を呼ぶ。** 中断行は再送せず `failed`（結果不明）に落とす（§6.5.4）
* 再試行は Plugin が `retryable: true` を返したときだけ。回数 5・間隔 1 → 2 → 4 → 8 分（Webhook と同じ）。**例外とタイムアウトは常に `failed`**（§5.6.2）
* 資格情報は `social_accounts.credential` に集約し、配信のたびに Core が復号して**その 1 アカウント分だけ**を `publish()` の引数で渡す。読み出しを `audit_logs`（`credential_read`）に残す（§6.5.5 / §6.5.8）
* 投稿の状態は増やさない。「手動投稿待ち」「再試行待ち」「配信中」はすべて既存 4 状態と列から導出する（§5.8）
* `publisherRegistry` は **Application**（`application/social/publisher-registry.ts`）。Application から `plugin/` を import しないため（§4.1）
* Domain（`domain/social/publishing.ts` / `credential.ts`）は `pg` / `kysely` / `@torifune/plugin-api` / `process.env` / タイマーを知らない（§4.1）
* `Secret.expose()` を新たに呼ぶのは `application/social/publish.ts` の 1 か所だけ（§6.5.5、受け入れ条件 #83）
* Plugin API は**追加のみ**。`PLUGIN_API_VERSION` は `1` のまま上げない（§9.1）
* マイグレーションは `022_social_publishing.sql`。**新しいテーブル・Permission は作らない。** 索引は 2 本だけ足す（§5.1 / §5.2）
* 手動投稿待ちの操作は `/social` の 1 か所。ダッシュボードは件数と導線だけ（§7.1 / §7.6）
* `TorifuneHub` への変更は無い。SaaS 固有機能（テナント・課金・コンテナ管理）に触るタスクは本プランに無い（§3.2）

### テストの方法（設計書に無い、プラン側で決める手段）

  publisher が要らない条件（#62 / #63 / #65 と画面）は E2E に置く

* **`PUBLISH_TIMEOUT_MS` の差し替え（#48）**：`const` は `vi.spyOn` で差し替えられず、`vi.mock` でモジュールごと差し替えると他の純関数まで偽物になる。

## 7. リスクと注意点

1. **`PluginContext.social` を必須にした瞬間に typecheck が落ちる（T5 → T7）**。`packages/plugin-api/src/context.ts` の変更と `apps/web/src/plugin/context.ts` の組み立ては**同じコミット**に入れる。T5 では `social.ts` と `manifest.ts` だけを入れ、`context.ts` には触らない
2. **`createSocialPost` の戻り値の変更（T11c）**。ルートとテスト 3 ファイルを同じコミットで追随させる。`defineUseCase` の `audit.detail` が出力を見られるので、`replayed` の判定は UseCase 側で完結する
3. **`SocialPost` に項目を足すと「構築している箇所」が落ちる（T2）**。読むだけの箇所は落ちない。構築しているのは `infrastructure/social-repository.ts` の写像だけ（UI は文字列化済みの行の型を持つ）。テストのフィクスチャも `createSocialPost` 経由なので落ちない
4. **`ensurePluginsStartedAnonymously()` をルートの先頭で呼ぶ（設計 §6.7）**。結合テストでルートを直接叩くと Plugin の起動が走る。使い捨て DB には `plugins` の行が無いので何も起動しないが、**偽の publisher は `registerPublisher` で直接登録しているので消されない**ことを確認する（`ensurePluginsStarted*` は `unregisterPlugin` を呼ばない）。もし消えるなら、テストは `beforeEach` ではなく各 `it` の中で登録する
5. **着手印とトランザクションの分離（T16a）**。`claimForPublish` は `connection.transaction` を自分で開いて**コミットしてから返す**。`publishDuePosts` 全体を 1 つのトランザクションで包まない。包むと「プロセスが死んだとき印がロールバックされ、次の実行がもう一度送る」になる
6. **`publish()` を直列に呼ぶ（設計 §11 #6）**。1 回の実行が最長 20 件 × 30 秒 = 10 分になりうる。結合テストでは `{ timeoutMs: 200 }` と件数を絞り、実時間で待たない
7. **`AbortSignal.timeout` は Node 18+ の標準**。`publish()` が `signal` を無視して解決しない場合、`Promise.race([publish(input), timeoutPromise])` で打ち切る必要がある。`AbortSignal` を渡すだけでは Core 側は待ち続ける。**`race` で打ち切り、放置された Promise の `unhandledRejection` を握る**（`.catch(() => {})` を付ける）
8. **`redactCredentialValues` は既知の値しか伏せない**。Plugin が資格情報を加工して `reason` に混ぜたら防げない。だからイベント payload に `failureReason` を載せない（設計 §9.6）。#55 は「Core が渡した値そのもの」が出ないことだけを見る
9. **`rotatedCredential` の書き戻しは別トランザクションで先に**（設計 §6.5.6）。投稿側の書き戻しが 0 行でも、トークンが更新された事実は変わらない。順序を逆にすると「更新済みのトークンを保存し損ねる」窓ができる
10. **E2E のファイル名順**（T26）。`social-publishing.spec.ts` は `social.spec.ts` より前に走る。`afterAll` で example-plugin を必ず無効化・削除しないと #79 が壊れる。`plugin-example.spec.ts` も同じ Plugin を導入するので、**両方が `beforeAll` で `POST /api/v1/plugins` を叩くと 2 本目が 409 になりうる**。`plugin-example.spec.ts` の `afterAll` が削除まで行うことと、`workers: 1` で直列なことを前提にするが、落ちたら `social-publishing.spec.ts` 側で「既に導入済みなら有効化だけ」に倒す
11. **E2E の子ウィンドウ（#73）**。`noopener` を付けると `window.open` は `null` を返し、Playwright では `context.waitForEvent('page')` で拾う。`popup` イベントは `opener` が無いと発火しないことがあるので、`context.waitForEvent('page')` を使う
12. **E2E の 90 秒待ち（#75 / #78）**。初回遅延 15 秒 + 間隔 1 分。`expect.poll` の `timeout` は 90 秒、`intervals` は 5 秒、`test.setTimeout(120_000)`
13. **`window.open` の単体テスト（#68）**。vitest の `environment: 'node'` には `window` が無い。`ManualPending` の props に `open?: (url, name, features) => unknown`（既定 `window.open`）を持たせ、テストは `vi.fn()` を渡す。**本番コードにテスト専用の分岐を入れない**（既定値なので通常経路は変わらない）
14. **`processState('social.publishers', …)`**。`plugin/registry.ts` と同じ理由でプロセスに 1 つ。`resetPublisherRegistry()` は `Map.clear()`（`processState` 自体は消せない）
15. **`/social` の N+1**（設計 §7.1）。Server Component が行ごとに `resolveManualHandoff` を呼ぶ。50 件上限で、`manual()` は純粋な URL 組み立てなので許容する。`manual()` が外部へ問い合わせる Plugin が現れたら見直す（設計 §6.6 は `Promise` を許している）
16. **`social-accounts.tsx` の provider 選択肢を props にする（T23）**。いまは部品の中に固定 5 択がある。`app/social/page.tsx` からしか使われていないことを確認してから置き換える

19. **実装の都合で設計書を書き換えない。** §12 の「追記」は対象文書の節末へ。`docs/仕様書/` の `00`〜`07` は変更しない（設計 §2 が矛盾は無いと結論している）
    > **2026-09-23 に文言を直した（検証レポート §5 の 6）。** もとは「**設計書に手を入れない**」と書いていたが、
    > 実際には `03a0963` / `0e6ff7a` / `04ec0a7` が設計書を書き換えており、プランと運用が食い違っていた。

**UI 部品テストの限界（G6 で判明。G7 の E2E が引き取る）**
`apps/web` の vitest は `environment: 'node'` で、部品テストは `createElement` + `renderToStaticMarkup` の静的描画である。
したがって**入力・送信・開閉といった DOM 操作を伴う挙動は単体では見られない**。次はいずれも E2E 側が唯一の砦になる：
`credentials` を含む送信 body（#76）／`deliveryMode` を含む送信 body（#70 は「入力要素が無い」までで固定）／
「投稿した」の `Modal` と `PATCH`（#73）／「取りやめ」の `ConfirmDialog`（#74）。
**E2E を薄くすると、これらは誰も見ていない状態になる。** T26 で削らないこと。
