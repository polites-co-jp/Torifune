# 035 SNS 自動投稿と手動投稿 — 要件と裁定

設計書（`設計.md`）を書くための入力。ユーザーの要求、現行実装の調査結果、
ユーザーが裁定した方針をまとめる。**この裁定は決定事項であり、設計書はこれに従う。**

## 1. 要求（2026-09-22）

外部のサービス（Torifune の外にあるアプリケーション）が、Torifune の API 経由で
「アプリケーションID・投稿内容・投稿時間・認証情報・他必要な情報」を登録すると、
指定時刻に X / Instagram / Bluesky へ**自動投稿**される仕組みがほしい。

ただし X は API が有料であるため、無料ユーザー向けに**手動投稿**の経路も設ける。
投稿内容が反映された状態で X の投稿画面を子ウィンドウに開き、あとは人が投稿ボタンを
押すだけ、という UI である。

つまり「3 種類の SNS への自動投稿」と「X の手動投稿」を Plugin として作る。

## 2. 現行実装の事実（調査 2026-09-22）

1. Core は SNS の「データの箱」まで持つ。`social_accounts`（`credential` は AES-256-GCM で暗号化）と
   `social_posts`（`draft → scheduled → published / failed`）。**実配信は Plugin の責務**と明記されている
   （`domain/social/social.ts`、`01_アーキテクチャ設計.md` §12、`03_プラグイン設計.md` §9）
2. `social_posts(status, scheduled_at)` の索引は「予約投稿の取り出し（将来のワーカー用）」として
   `005_social.sql` にあるが、**予約投稿を回すワーカーは存在しない**
3. 外部から Torifune を叩く認証は **API Token（`tfp_` Bearer）1 本**（`021-api-token`）。
   Token の権限は「所有者の権限 ∩ scope」で、増やせず絞るだけ。
   「外部アプリケーション」「client_id」のモデルは無い
4. `POST /api/v1/social/posts` / `POST /api/v1/social/accounts` は既にあり、API Token で叩ける。
   投稿の作成は `socialAccountId` / `body` / `scheduledAt` / `status` だけを受ける
5. Plugin API v1 に**無いもの**：HTTP ルート登録（`027` §3.1 は設計済み・未実装）、
   ジョブ登録（`029` §11 #6「要望が出たら Plugin API として設計する」）、
   `socialAccounts` / `socialPosts` の作成（Data API は read と `markPublished` / `markFailed` だけ）、
   Plugin 専用テーブル（`03` §19.2 将来課題）
6. 本体スケジューラ（`029`）は `instrumentation.ts` から起動し、ジョブごとに advisory lock で排他して
   `job_runs` に記録する。`JOB_NAMES` は Core 固定
7. Core → Plugin への資格情報の受け渡しは、`009-social` §9 が「監査できる読み出し口」として予定し
   `readSocialCredential` UseCase（`social.write`）まであるが、Plugin API へは公開されていない。
   一方 `docs/Plugin開発ガイド.md` は「Core は Plugin へ資格情報を渡さない」と書いており、
   **文書同士が矛盾したまま**になっている
8. `KNOWN_PROVIDERS` は `x / facebook / instagram / youtube / other`。`bluesky` は無いが、
   provider は開いた集合で DB 制約（`^[a-z][a-z0-9_]{0,31}$`）は通る
9. Plugin のコードは `plugins/` からビルド時に静的に取り込む（`generated-registry.ts`）。実行時ロードは無い

## 3. SNS ごとの事情（設計の前提として確認済み）

| | X | Bluesky | Instagram |
| --- | --- | --- | --- |
| 自動投稿 | API v2 `POST /2/tweets`。無料枠はごく小さく条件が頻繁に変わる | AT Protocol `com.atproto.repo.createRecord`。**App Password で足りる**（OAuth 不要） | Graph API（Content Publishing）。**Business / Creator アカウント必須、画像または動画が必須**、container 作成 → publish の 2 段階。long-lived token は 60 日で失効し更新が要る |
| 手動投稿（Web Intent） | `https://x.com/intent/post?text=…&url=…`。**画像は添付できない** | `https://bsky.app/intent/compose?text=…` | **無い** |
| 本文の上限 | 280 文字（Premium は長い） | 300 grapheme | キャプション 2,200 文字 |
| 資格情報の入手 | 開発者ポータルで発行した OAuth 1.0a の 4 値（または OAuth 2.0 の token） | 画面で App Password を発行 | Graph API で long-lived token を取得 |

## 4. 裁定（ユーザー決定、2026-09-22）

| # | 論点 | 裁定 |
| --- | --- | --- |
| 1 | 配信を駆動する主体 | **Core のジョブ 1 本**（`social.publish`、1 分周期）。`029` の advisory lock / `job_runs` にそのまま載せる。**Plugin に自前タイマーを持たせない**（複数プロセスで二重投稿するため。SNS の投稿は取り消せない） |
| 2 | SNS 側の認証情報の置き場 | **`social_accounts.credential` に集約する。** 外部アプリは `POST /api/v1/social/accounts` で登録できる。配信時に Core が復号し、その 1 アカウント分だけを Plugin の `publish()` へ渡す。**読み出しは監査ログに残す。** `docs/Plugin開発ガイド.md` の「渡さない」はこの設計で改訂する（`009` §9 が予定していた形を実装する） |
| 3 | 手動投稿の位置づけ | **Core の汎用概念**とする。投稿は `deliveryMode: 'auto' \| 'manual'` を持ち、Plugin は `manual()` で「投稿内容を反映した外部の投稿画面の URL」を返すだけ。Core が「手動投稿待ち」の画面・子ウィンドウ・「投稿した／取りやめ」の操作を持つ。X と Bluesky で同じ画面を使う。Instagram のように手動の導線が無い provider は `manual` を 422 で断る。**投稿の状態は増やさない**（`manual` かつ `scheduled` かつ期限到来、で導出する） |
| 4 | 「アプリケーションID」 | **API Token 1 本 = 外部アプリ 1 つ。** 新しいモデルは作らない。`api_tokens.name` にアプリ名を持たせ、scope を `social.read` + `social.write` に絞る運用 |
| 5 | Plugin の分割 | Core 側（本設計 `035`）と、provider ごとの Plugin `036-sns-bluesky` → `037-sns-x` → `038-sns-instagram` に分ける。**Bluesky を最初に作る**（App Password だけで端から端まで通る） |
| 6 | 画面からの OAuth「接続」ボタン | **後回し。** Plugin がコールバックを受ける HTTP ルート（`027` §3.1）が前提。Phase 1 は外部アプリが API で資格情報を登録する運用 |
| 7 | ブランチ | `main` から `feature/035-social-publishing` を切る |

## 5. 裁定を踏まえた骨子（設計書はこれを具体化する）

```text
外部アプリ ──POST /api/v1/social/posts (Bearer tfp_…)──▶ Core: social_posts に登録（Plugin の validate() で早く弾く）
                                                            │  scheduled_at 到来
                                                            ▼
                                        Core ジョブ social.publish（1 分周期・advisory lock・job_runs）
                                                            │  provider で振り分け
                            ┌───────────────────────────────┼──────────────────────────┐
                            ▼                               ▼                          ▼
                    Plugin sns-x                    Plugin sns-bluesky          Plugin sns-instagram
                    publish() = X API               publish() = AT Protocol     publish() = Graph API
                    manual()  = intent URL          manual()  = intent URL      manual なし
                            │
                            ▼（deliveryMode = manual の投稿だけ）
                    Core 画面「手動投稿待ち」→ 子ウィンドウで投稿画面 → 人が投稿 → 「投稿した」→ published
```

### 5.1 Plugin API の新しい拡張点 `social`（v1 への追加。後方互換）

Manifest の `extensions` に `'social'` を足す。`context.social.registerPublisher(...)` で
provider ごとの「配信手段」を登録する。**Plugin は 1 回配信する関数だけを実装する。**
スケジュール・再試行・記録・画面は Core が持つ。

```ts
interface PublisherRegistration {
  readonly provider: string;                  // 'x' | 'bluesky' | 'instagram' | …
  readonly label: string;                     // 表示名。Core の providerLabel はこちらを優先する
  readonly credentialFields: readonly PluginSettingsField[];   // 資格情報の形。Core が形式検証と入力欄を持つ
  readonly limits?: { bodyMaxLength?: number; mediaRequired?: boolean; mediaMax?: number };
  validate?(post, account): readonly ValidationProblem[];      // 登録時の事前検査
  publish?(input: PublishInput): Promise<PublishResult>;       // 自動配信
  manual?(input: ManualInput): ManualHandoff;                  // 手動配信。未実装なら manual を 422
}
interface PublishInput { post; account; credential: Readonly<Record<string, string>>; signal: AbortSignal; logger }
type PublishResult =
  | { ok: true; externalId?: string; externalUrl?: string; rotatedCredential?: Record<string, string> }
  | { ok: false; reason: string; retryable: boolean; retryAfterMs?: number };
interface ManualHandoff { url: string; note?: string }
```

型名・引数の細部は設計側で決めてよい。**`publish()` に渡す資格情報は、その呼び出しの間だけ。**
Plugin が保存し直す必要は無い（トークン更新は `rotatedCredential` で返し、Core が書き戻す）。

### 5.2 `social_posts` に足すもの

`delivery_mode`（`auto` / `manual`）、`media`（URL と alt の配列。**Torifune はファイルを預からない**）、
`link`、`provider_options`（provider 固有の追加項目。中身の検証は Plugin）、
`external_ref`（外部アプリ側の ID。冪等キー）、`created_by_token_id`（どの外部アプリが登録したか）、
`external_id` / `external_url`（配信後の投稿の ID と URL）、`publish_started_at`（配信の着手印）。

### 5.3 二重投稿を起こさない

* ジョブは **`publish_started_at` を先に書いてから** `publish()` を呼ぶ
* ジョブ開始時に `scheduled` のまま `publish_started_at` が付いている行は、**前回の実行が途中で死んだ**
  ことを意味する（advisory lock により同時実行は無い）。**再送せず `failed`（結果不明・要確認）に落とす。**
  二重投稿より未投稿のほうがまし
* 再試行は Plugin が `retryable: true` を返したときだけ。送信前のネットワーク断・429 が対象。
  5xx のような「届いたか分からない」失敗は retryable にしない

### 5.4 冪等な登録

`(created_by_token_id, external_ref)` で一意。同じ組で再送されたら新しく作らず既存を返す。
外部アプリはネットワーク断で再送しても二重登録にならない。

### 5.5 登録時の事前検査

`POST /api/v1/social/posts` は、対象アカウントの provider に登録された publisher の `limits` と `validate()` で
早く弾く（X の文字数、Instagram の媒体必須、manual 非対応 provider への manual 指定、manual への media 指定）。
配信時刻に初めて失敗するのが一番困る。

## 6. 制約・やらないこと

* TorifuneHub には手を入れない。SNS 連携は OSS 側の責務（`01` §12）
* Plugin が自前のタイマー・HTTP ルート・テーブルを持つ設計にしない
* 投稿の状態（`draft / scheduled / published / failed`）を増やさない
* 画面からの OAuth 接続（裁定 #6）、メディアファイルの預かり、投稿の編集画面の刷新は範囲外
* `027` §3.1（Plugin の HTTP ルート）は本設計で実装しない
* SaaS 固有のもの（テナント・課金・コンテナ管理）は本体に入れない
* Plugin 3 つ（`036`〜`038`）の中身は本設計の範囲外。本設計は**それらが乗れる Core 側の口**を作る

## 7. 設計側で決めてよいこと

* 再試行の列（`attempt_count` / `next_attempt_at` 等）と回数。Webhook（`023`）の 1 → 2 → 4 → 8 分に揃える
* `scheduled` かつ `auto` の投稿を、対象 provider の publisher が登録されていない状態で作ろうとしたときの扱い
  （案：422「このSNSの配信 Plugin が有効ではありません」。作成後に Plugin が無効化された投稿はジョブが飛ばし、
  画面に警告を出す）
* 資格情報の保存形式。既存の `credential` は自由文字列（≤ 4096）なので、publisher がある provider では
  `credentialFields` に従う JSON 文字列とし、既存の文字列との互換をどう取るか
* 資格情報の読み出しの監査（`audit_logs` にどう残すか。`defineUseCase` の `audit` と同じ書式）
* 「手動投稿待ち」の置き場（`/social/posts` 内の区画か、ダッシュボードの widget か、その両方か）と、
  子ウィンドウの開き方（`window.open` の寸法・名前）
* `PATCH /api/v1/social/posts/{id}` で「投稿した」を受けるときの `externalUrl` の受け方
* `social.post.failed` イベントを足すか（`009` §9 は予定していたが `CORE_EVENTS` に無い）
* `bluesky` を `KNOWN_PROVIDERS` / `PROVIDER_LABELS` に足すか、publisher の `label` だけで済ませるか
* ジョブ名（`social.publish`）、`JOB_NAMES` の追加位置（設定画面「定期実行」の行順になる）、環境変数名
