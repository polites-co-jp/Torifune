# 035 SNS 自動投稿と手動投稿（配信基盤と Plugin 拡張点 `social`） 設計

**この設計書は現行実装（`009-social` / `010-plugin-api` / `021-api-token` / `023-webhook` / `029-scheduled-jobs`）からの差分として書く。**
差分の基準となる現行のファイルは §4 に列挙する。要件 §4 の裁定は決定事項として従い、
§7「設計側で決めてよいこと」は本設計で決めて「決めたこと」として理由つきで書く（§5.7 / §6.1.3 / §6.5.6 / §6.5.8 / §7.1 / §7.2 / §9.6 / §5.6.1 / §6.5.1）。

## 1. 目的

1. **外部アプリが API で登録した投稿を、指定時刻に Core が SNS へ流す。** いまの Core は「投稿の箱」までで、
   `social_posts(status, scheduled_at)` の索引を「将来のワーカー用」と書いたまま、予約投稿を回す主体が無い
   （要件 §2-2）。`029` のジョブ基盤に **`social.publish`（1 分周期）を 1 本**載せ、provider ごとの配信手段は
   Plugin が `publish()` として登録する（裁定 #1 / #5）
2. **資格情報の受け渡しを、監査できる 1 本の経路に閉じる。** `social_accounts.credential` を配信の唯一の置き場とし、
   配信のたびに Core が復号して**その 1 アカウント分だけ**を `publish()` の引数として渡し、読み出しを `audit_logs` に残す
   （裁定 #2。`009` §9 が予定していた形）。「Core は Plugin へ資格情報を渡さない」と書いた開発ガイドは本設計で改訂する（§12）
3. **手動投稿を Core の汎用概念にする。** X の無料枠のように API で流せない場面のために、投稿は `deliveryMode: 'auto' | 'manual'` を持つ。
   Plugin は「投稿内容を反映した外部の投稿画面の URL」を返すだけで、待ち行列の画面・子ウィンドウ・「投稿した／取りやめ」の操作は Core が持つ（裁定 #3）。
   **投稿の状態は増やさない**（`manual` かつ `scheduled` かつ期限到来、で導出する）
4. **二重投稿を起こさない。** SNS の投稿は取り消せない。着手印（`publish_started_at`）を先に書いてから `publish()` を呼び、
   途中で死んだ行は再送せず `failed`（結果不明）に落とす。再試行は Plugin が「送る前に失敗した」と言ったときだけ（要件 §5.3）
5. **「配信時刻に初めて失敗する」を減らす。** 登録時に publisher の `limits` と `validate()` で早く弾き、
   同じ組の再送を冪等にする（要件 §5.4 / §5.5）。ただし**弾けるのは publisher が居るときだけ**なので、
   **配信直前にも同じ検査を掛ける**（§6.5.2.2。2026-09-23 に足した）。
   裁定 #8 で publisher が無くても登録できる以上、事前検査だけでは Core の保証にならない

「アプリケーション ID」は作らない。**API Token 1 本 = 外部アプリ 1 つ**とし、どの Token が登録したかを投稿に残す（裁定 #4）。

## 3. スコープ

### 3.1 やること

* Plugin API の拡張点 `social`：`context.social.registerPublisher(...)`、型 `PublisherRegistration` / `PublishInput` / `PublishResult` / `ManualHandoff` 等（§9）
* `social_posts` の列追加（`delivery_mode` / `media` / `link` / `provider_options` / `external_ref` / `created_by_token_id` /
  `external_id` / `external_url` / `publish_started_at` / `attempt_count` / `next_attempt_at`）とマイグレーション `022_social_publishing.sql`（§5）
* **配信できない予約を後ろへ送る仕組み**（`skip_count` / `skip_reason`）とマイグレーション `023_social_publish_skip.sql`（§5.1.1 / §6.5.2）
* **Plugin マネージャの導入前の画面に、Manifest の `extensions`（どの拡張点を握るか）を出す**（§7.9）
* `POST /api/v1/social/posts` の拡張（項目・事前検査・冪等な再送）、`PATCH` での「投稿した／取りやめ」、応答項目の追加（§6.1〜§6.3）
* `POST /api/v1/social/accounts` / `PATCH` に `credentials`（`credentialFields` に従う JSON）を足す（§6.4）
* Core ジョブ `social.publish`（1 分周期、advisory lock、`job_runs`）と、外部スケジューラ運用向けの `POST /api/v1/social/publish`（§6.5）
* 資格情報の復号と `publish()` への受け渡し、監査ログ、`rotatedCredential` の書き戻し、平文をログ・例外・イベントに出さない措置（§6.5.5〜§6.5.8）
* 画面：`/social` の「手動投稿待ち」区画と子ウィンドウ、投稿一覧の配信方法列と Plugin 未登録の警告、投稿フォームの配信方法、
  アカウント追加の `credentialFields` 入力欄、ダッシュボードの導線、設定「定期実行」の行（§7）
* イベント `social.post.failed` の追加、`SocialPostView` の項目追加（§9.5 / §9.6）
* `AuthorizationContext.apiToken`（どの Token で認証されたか）を `buildApiTokenContext` が積む（§6.1.3）
* サンプル Plugin（`plugins/example-plugin`）にループバックの publisher を足す（E2E と開発ガイドの題材。§9.8）
* ドキュメント改訂（§12）

### 3.2 やらないこと（要件 §6）

* Plugin 3 つ（`036-sns-bluesky` / `037-sns-x` / `038-sns-instagram`）の中身。本設計はそれらが乗る口だけを作る（§13 に見え方を示す）
* Plugin が自前のタイマー・HTTP ルート・テーブルを持つ形。`027` §3.1（Plugin の HTTP ルート）は実装しない
* 投稿の状態（`draft / scheduled / published / failed`）の追加
* 画面からの OAuth「接続」ボタン（裁定 #6）。Phase 1 は外部アプリ（または画面の入力欄）が資格情報を登録する運用
* メディアファイルの預かり。`media` は **URL と alt だけ**を持ち、取得は Plugin が行う
* 投稿の編集画面の刷新。フォームに足すのは「配信方法」の 1 項目だけで、`media` / `link` / `providerOptions` は API からのみ（§7.4、§11 #3）
* Data API への `socialPosts.create`（Plugin が投稿を作る口）。要望が出たら別途
* TorifuneHub への変更。SaaS 固有のもの（テナント・課金・コンテナ管理）

### 3.3 Core が持つもの／Plugin が持つもの

境界を先に決める。**Plugin は「1 回配信する関数」と「投稿画面の URL を返す関数」だけを書く。**

| 項目 | 担当 | 根拠 |
| --- | --- | --- |
| いつ配信するか（スケジュール、周期、排他、実行記録） | **Core** | Plugin ごとにタイマーを持たせると複数プロセスで二重投稿する（裁定 #1）。`029` の基盤にそのまま載せる |
| 着手印と中断行の扱い（二重投稿の防止） | **Core** | 1 つの Plugin の実装ミスが「同じ投稿が 2 回出る」になる。Core が先に印を書く（§6.5.4） |
| 再試行の回数・間隔・打ち切り | **Core** | Plugin は `retryable` を言うだけ。間隔は Webhook（`023`）と同じ 1 → 2 → 4 → 8 分（§6.5.6） |
| **配信の支度が整うまで待つ／諦める**（後ろへ送る回数・間隔・打ち切り） | **Core** | Plugin の有無・資格情報の有無は Plugin 自身には見えない。1 → 23 時間、3 回目で `failed`（裁定 #9。§6.5.2.1） |
| 「送る前に失敗した」か「届いたか分からない」かの判定 | Plugin | 外部 API の応答を読めるのは Plugin だけ。**判定基準は Core が契約として書く**（§9.2 `PublishResult`） |
| 資格情報の保存・暗号化・復号・監査 | **Core** | `social_accounts.credential` に集約（裁定 #2）。読み出しを `audit_logs` に残す（§6.5.8） |
| 資格情報の形（どの項目が要るか）と入力欄 | Plugin が宣言、**Core** が描画・形式検証 | `credentialFields`。Plugin ごとにフォームを書かせると Secret の扱いがばらける（`06` §38） |
| 資格情報の更新（トークンの期限延長など） | Plugin が `rotatedCredential` で返し、**Core** が書き戻す | Plugin は保存し直さない。書き戻しも監査に残る |
| 外部 SNS の API 呼び出し（認証方式・エンドポイント・媒体のアップロード） | Plugin | Core が知ると Core が SNS を知ることになる（`01` §12） |
| 本文の上限・媒体の要否などの制約の宣言 | Plugin（`limits` / `validate()`） | SNS ごとに違う。**適用は Core** が登録時（§6.1.2）**と配信直前**（§6.5.2.2）の両方で行う |
| 手動投稿の URL（投稿画面に内容を反映した外部 URL） | Plugin（`manual()`） | Web Intent の形は SNS ごとに違う |
| 手動投稿の待ち行列・子ウィンドウ・「投稿した／取りやめ」 | **Core** | X と Bluesky で同じ画面を使う（裁定 #3） |
| 冪等な登録（`externalRef`）と「どの Token が登録したか」 | **Core** | 外部アプリとの契約は Core の API |
| `published` / `failed` の確定、イベントの発火 | **Core** | `publish()` の戻り値を Core が写す。Plugin が `markPublished` を呼ぶ必要は無い |
| 配信の結果（`externalId` / `externalUrl`）の記録 | Plugin が返し、**Core** が保存 | 履歴画面から投稿へ辿れるようにする |

### 3.4 全体の流れ

```text
外部アプリ ──POST /api/v1/social/accounts (Bearer tfp_…, credentials)──▶ Core: social_accounts（暗号化）
外部アプリ ──POST /api/v1/social/posts    (Bearer tfp_…, externalRef)──▶ Core: social_posts
                                          │ publisher の limits / validate() で早く弾く（§6.1.2）
                                          │ (created_by_token_id, external_ref) が同じなら既存を 200 で返す（§6.1.3）
                                          │  scheduled_at 到来
                                          ▼
                    Core ジョブ social.publish（1 分周期・advisory lock・job_runs。§6.5）
                      1. 前回の中断行（scheduled かつ publish_started_at あり）を failed（結果不明）に落とす
                      2. 期限の来た auto の投稿を scheduled_at 順に最大 20 件
                      3. 行ごとに：支度が整っていなければ後ろへ送る（3 回目で failed。裁定 #9）
                                   → 着手印を書いてコミット → limits / validate() を再検査
                                   → 復号（監査）→ publish() → 結果を書き戻す
                                          │ provider で振り分け（publisherRegistry）
              ┌───────────────────────────┼───────────────────────────┐
              ▼                           ▼                           ▼
       Plugin sns-x               Plugin sns-bluesky          Plugin sns-instagram
       publish() = X API          publish() = AT Protocol     publish() = Graph API
       manual()  = intent URL     manual()  = intent URL      manual なし（manual は 422）
              │
              ▼（deliveryMode = manual の投稿だけ。ジョブは触らない）
       Core 画面 /social「手動投稿待ち」→ 子ウィンドウで投稿画面 → 人が投稿 → 「投稿した」→ published
                                                                       └─「取りやめ」→ draft
```

### 4.1 publisher の登録簿を Application に置く理由

置き場の候補は `plugin/registry.ts`（他の登録と同じ場所）と `application/social/`。**Application に置く。**

* 登録簿を読むのは `createSocialPost`（事前検査）と `publishDuePosts`（配信）で、どちらも Application の処理。
  `029` §4.1 のとおり **Application から `plugin/` を import しない**ので、`plugin/registry.ts` に置くと読めない
* 依存の向きは既存と同じになる：`plugin/context.ts` → `application/social/publisher-registry.ts`（`plugin/data-api.ts` が
  Application の UseCase を呼ぶのと同じ向き）。`plugin/registry.ts` の `unregisterPlugin` も同じ向きで `unregisterPublishersOf` を呼ぶ
* 実体は `processState('social.publishers', …)` の `Map<provider, { pluginId, registration }>`。プロセスに 1 つ
  （`plugin/registry.ts` と同じ理由：Route Handler と Server Component が別の実体を見ると「API では弾かれるのに画面には出る」になる）

Domain（`domain/social/publishing.ts` / `credential.ts`）は型と純関数だけで、`pg` / `kysely` / `@torifune/plugin-api` / タイマー / `process.env` を知らない。
`PublisherRegistration` の型は `@torifune/plugin-api` のものを Application が使い、Domain には Core 側の最小の型
（`CredentialField { key; kind }`、`PublishVerdict`）だけを置く。復号（`decryptSecret`）は Infrastructure の `cipher` で、
呼ぶのは Application の `publish.ts` だけ（`Secret.expose()` の呼び出し箇所を増やさない。§6.5.5）。

### 5.2 索引

* **取り出し（ジョブ・手動投稿待ち）には既存の `social_posts_status_scheduled_idx (status, scheduled_at)` を使う。**
  `005_social.sql` が「予約投稿の取り出し（将来のワーカー用）」として張ったもので、`status = 'scheduled'` を先頭で絞り
  `scheduled_at <= now()` を範囲で読む。`delivery_mode` / `next_attempt_at` / `publish_started_at` は取り出した数行に対する
  フィルタで足りる（`scheduled` の行は少なく、取り出しは 1 分に 1 回・最大 20 件）。新しい索引を足さない
* 履歴の索引 `social_posts_delivery_idx`（`018`）はそのまま。`external_url` を履歴に出すだけで並びは変えない
* 足すのは冪等キーの部分一意索引と、外部キーの参照側の索引の 2 本（§5.1）

### 5.3 既存行の扱い

* 既存の投稿は `delivery_mode = 'auto'` になる。**`status = 'scheduled'` で `scheduled_at` が NULL の既存行は、これまでどおり取り出されない**
  （取り出し条件が `scheduled_at <= now()` を含むため）。DB の CHECK で「`scheduled` なら `scheduled_at` 必須」を強制しない。
  既存行を制約違反にしないため。以後の作成・更新では UseCase が要求する（§6.1.2 の d）
* `media` / `provider_options` は空。`attempt_count` は 0。`failed_at`（`018`）は変えない
* `campaign_social_posts`（`018`）は関係しない

### 5.4 `api_tokens` との関係（FK・失効・削除）

| 事象 | `api_tokens` の行 | `social_posts.created_by_token_id` | 冪等キー |
| --- | --- | --- | --- |

`decideSkipOutcome` の規則（裁定 #9 の細目。`now` は Application が渡す）：

| `post.skipReason` | 今回の `reason` | 結果 |
| --- | --- | --- |
| `null` | 任意 | `deferred`、`skipCount = 1`、`nextAttemptAt = now + 1 時間` |
| 今回と**同じ** かつ `skipCount = 1` | 同じ | `deferred`、`skipCount = 2`、`nextAttemptAt = now + 23 時間` |
| 今回と**同じ** かつ `skipCount >= 2` | 同じ | **`failed`**、`skipCount = 3`、`failureReason = skipFailureReason(reason)` |
| 今回と**違う** | 任意 | `deferred`、`skipCount = 1`、`nextAttemptAt = now + 1 時間`（**数え直す**） |

**間隔を 1 時間 → 23 時間にした理由**（裁定 #9 の細目）。ジョブの周期（1 分）で 3 回数えると 3 分で `failed` になり、
「Plugin を後から入れる」という裁定 #8 の趣旨を壊す。**丸一日待って支度が整わなければ諦める**、と運用者に説明できる長さにした。
運用者はその間に `/social` の `Alert`（§7.3）とダッシュボードの導線で気づける。

`skipFailureReason` の文言（`failure_reason` に入り、投稿一覧・履歴画面にそのまま出る）：

| `reason` | 文言 |

| `no_publisher` | `配信 Plugin が有効にならないまま予約日時から約24時間が過ぎたため、この予約を取りやめました。Plugin を有効にしてから、新しい投稿として登録し直してください。` |
| `credential_missing` | `資格情報が設定されないまま予約日時から約24時間が過ぎたため、この予約を取りやめました。SNSアカウントに資格情報を設定してから、新しい投稿として登録し直してください。` |
| `account_missing` | `SNSアカウントが見つからないまま予約日時から約24時間が過ぎたため、この予約を取りやめました。` |

### 5.7 資格情報の保存形式（決めたこと）

**保存形式は変えない。** `social_accounts.credential` は暗号化した 1 つの文字列（`v1.<keyId>.…`）のまま。
変えるのは**平文の中身の約束**だけ。

* publisher が `credentialFields` を宣言している provider では、平文を **JSON オブジェクトの文字列**
  （`{"identifier":"…","appPassword":"…"}`）にする。キーは `credentialFields[].key`
* API は `credentials`（オブジェクト）を受け、Core が JSON にして暗号化する（§6.4）。画面も同じ（§7.5）。
  既存の `credential`（自由文字列）は残す（互換）。**両方を同時に指定したら 422**
* 配信時は復号 → `parseCredentialObject`。**オブジェクトでなければ、その投稿は `failed`（`credentialMismatchReason`）**。
  自由文字列で登録済みのアカウントに後から Plugin を入れた場合がこれに当たる。登録時に復号して確かめる案は採らない
  （投稿の作成のたびに資格情報を読むことになり、監査ログが投稿数だけ増える）。理由文に要求するキー名を書くので、
  運用者は登録し直せば直る
* `credentialFields` が空の publisher（資格情報の要らない配信手段）では、`credential` が無くても配信できる
* `kind: 'text'` と `'secret'` の違いは**入力欄の見え方だけ**。保存は丸ごと 1 つの暗号文で、**Core はどの項目も再表示しない**
  （`06` §38。「設定済み」だけを見せる）。`kind` は Plugin が「打ち込むときに見えていてよい項目か」を宣言するためにある

### 5.8 状態は増やさない：導出される状態

| 見た目の状態 | 定義（すべて既存の 4 状態と列から導く） |
| --- | --- |
| 配信待ち（自動） | `status = 'scheduled' AND delivery_mode = 'auto' AND publish_started_at IS NULL` |
| 再試行待ち | 同上 かつ `next_attempt_at IS NOT NULL` かつ `skip_reason IS NULL`（`attempt_count >= 1`、`failure_reason` に前回の理由） |
| 支度待ち（後ろへ送られた） | 同上 かつ `skip_reason IS NOT NULL`（`next_attempt_at` に次に見る時刻、`attempt_count` は **0 のまま**、`failure_reason` は NULL のまま。§6.5.2 の a） |
| 配信中 | `status = 'scheduled' AND delivery_mode = 'auto' AND publish_started_at IS NOT NULL`（次のジョブ開始時にまだ残っていれば「中断」） |
| 手動投稿待ち | `status = 'scheduled' AND delivery_mode = 'manual' AND scheduled_at <= now()`（裁定 #3） |
| 手動投稿の予定 | `status = 'scheduled' AND delivery_mode = 'manual' AND scheduled_at > now()` |

**`publish_started_at` は結果を書き戻すときに必ず NULL に戻す**（成功・失敗・再試行のいずれでも）。
「非 NULL ⇔ 進行中」を不変条件にすると、中断行の判定（§6.5.4）と編集のガード（§6.2）が同じ 1 つの列で決まる。
いつ着手したかは `published_at` / `failed_at` / `updated_at` が持つ。

#### 6.1.3 冪等な再送（決めたこと。要件 §5.4）

**`(created_by_token_id, external_ref)` が同じなら新しく作らず既存を返す。**

* UseCase の出力を `{ post: SocialPost; created: boolean }` に変える（内部の型で、API の形ではない）。
  ルートは `created ? createdResponse(…) (201) : dataResponse(…) (200)`。**OpenAPI の `successStatus` は 201 のまま**とし、
  「同じ `externalRef` の再送は 200 で既存を返す」を `summary` と開発ガイドに書く（`defineRoute` の `successStatus` は 1 つしか宣言できない）
* **本文が違っても既存を返す**（更新しない、409 にもしない）。冪等キーの意味は「同じ登録要求の再送」であり、
  内容を変えたいなら `PATCH`。再送で内容が変わる設計にすると、ネットワーク断の再送で本文が巻き戻る事故が起きる（§11 #10）
* 同時に同じ要求が 2 本来たときは、Repository の `insertPostIdempotent` が
  `INSERT … ON CONFLICT (created_by_token_id, external_ref) WHERE created_by_token_id IS NOT NULL AND external_ref IS NOT NULL DO NOTHING RETURNING *`
  で 1 本だけ挿入し、挿入できなかった側は `findByExternalRef(tokenId, externalRef)` で既存を引いて返す。**どちらも 200 / 201 の違いだけで同じ ID を返す**
* 監査ログ（`created`）は再送でも記録される（`defineUseCase` は成功を記録する）。`detail` に `replayed: true` を入れて区別する
* イベント `social.post.created` は**作成したときだけ**発火する
* セッション認証（画面）からは `externalRef` を指定できない（c）。Token が無いと一意の名前空間が無く、
  PostgreSQL の一意索引は NULL を区別しないので「冪等のつもりで二重登録」が黙って起きる。422 で断る

  `identity.providerId = 'api-token'` は既存のままで、Token の ID はここからしか取れない

### 6.2 `PATCH /api/v1/social/posts/{id}`（`social.write`。現行どおり）

`updatePostSchema` に `deliveryMode` / `media` / `link` / `providerOptions`（§6.1.1 と同じ検証）と、次を足す。

| 項目 | 型 | 検証 |
| --- | --- | --- |
| `externalId` | `string \| null` | 200 文字以内 → `externalId` |
| `externalUrl` | `string \| null` | https・2048 文字以内 → `externalUrl` |

UseCase `social.post.update` の追加規則：

* **「投稿した」**：`{ status: 'published', externalUrl?: string, externalId?: string }`。`scheduled → published` は既存の遷移規則で許されている。
  `publishedAt` は現行どおり Core が入れる。`social.post.published` を発火（現行どおり）。`externalUrl` は任意
  （X の Web Intent は投稿の URL を返さないので、人が貼るとは限らない）
* **「取りやめ」**：`{ status: 'draft' }`。`scheduled → draft` は既存の遷移規則で許されている。手動投稿待ちの一覧から消える。
  `failed` に落とす案は採らない（取りやめは失敗ではなく、後で予約し直せる）
* **配信中のガード**：`status = 'scheduled' AND delivery_mode = 'auto' AND publish_started_at IS NOT NULL` の投稿に対し、
  `body` / `media` / `link` / `providerOptions` / `scheduledAt` / `deliveryMode` / `status` のいずれかを変える要求は
  `ValidationError('SocialPost', 'status', '配信を開始しているため変更できません。結果が記録されるまで待ってください。')` → 422。
  ジョブは着手時に読んだ内容を送るので、その間の編集は「送った内容と保存内容が食い違う」を生む。
  窓は最長でも `PUBLISH_TIMEOUT_MS`＋次のジョブまで（中断行は次の実行で `failed` に落ちてガードが外れる）。
  Data API の `markPublished` / `markFailed` もこの UseCase を通るので同じガードが効く
* **事前検査の掛け方**（2026-09-23 に書き直した。下の枠を見よ）。`next = { …current, …input }` を作り、次の区分で掛ける。

  | 検査 | 掛ける条件 |
  | --- | --- |
  | g（manual 非対応 provider → 422 `deliveryMode`） | **`input.deliveryMode === 'manual'`**。つまり `deliveryMode` を `manual` に**しようとする**更新にだけ |
  | e（`scheduled` なら `scheduledAt` 必須）／ f（`manual` に `media` を付けない）／ j〜m（`limits` / `validate()`） | **`next.status` が `'draft'` または `'scheduled'`** |
  | 配信中のガード（`publish_started_at`） | 従来どおり無条件 |

  掛けるときの順序・文言は §6.1.2 と同じ。

  > **2026-09-23 に直した（検証レポート S-3）。** もとは「事前検査（e〜m）を変更後の値に対して**同じ順で**掛ける」とだけ書き、
  > 実装は publisher の有無を問わず検査 g を掛けていた。その結果、**`manual` の投稿がある状態でその Plugin を無効化すると、
  > 以後その投稿は `published` にも `draft` にもできなくなる**（`markPublished` / `markFailed` も同じ UseCase を通る）。
  > これは §7.1 の「`handoff.ok === false` の行でも**「投稿した」「取りやめ」は押せる**（人が別の手段で投稿した場合を閉ざさない）」と
  > 正面から矛盾する。UI はボタンを押せる形で出すのに PATCH が 422 で落ち、**失敗を記録する経路まで塞がれていた**。
  >
  > 直し方の根拠：
  > * 検査 g が守っているのは「`manual` にしても投稿画面の URL を作れない」ことで、それは **`manual` にしようとするとき**にしか問われない。
  >   既に `manual` である行に、あとから Plugin が消えたことを理由に**出口を塞ぐ**のは、検査の目的を超えている
  > * `limits` / `validate()` が守っているのは「配信時刻に初めて失敗しない」ことで、これは**これから配信される状態**
  >   （`draft` / `scheduled`）に向かう更新の話である。**`published` / `failed` への遷移は「起きた事実の記録」**であって
  >   予約の検証ではない。起きた事実を、いまの Plugin の宣言に照らして拒むのは筋が悪い

* **`externalUrl` / `externalId` を UseCase で検証する**（2026-09-23 に足した）。
  `externalUrl` は `isValidExternalUrl`（https のみ・資格情報付き URL 不可・`EXTERNAL_URL_MAX_LENGTH` 以内）、
  `externalId` は `EXTERNAL_ID_MAX_LENGTH` 以内。合わなければ `ValidationError('SocialPost', 'externalUrl' | 'externalId', …)` → 422。

  > **2026-09-23 に足した（検証レポート S-4）。** https の検証は `api/schemas/social.ts`（HTTP 経路）と
  > `domain/social/publishing.ts`（`publish()` の戻り値）にしか無く、**`updateSocialPost` は検証せずに書いていた**。
  > Data API の `markPublished(id, { externalUrl })` は Zod を通らないので、Plugin から任意の文字列が入り、
  > 投稿一覧と履歴の `href` にそのまま出ていた。`body` は同じ UseCase の中で `isValidPostBody` を再検証しているのに
  > `externalUrl` はしていない、という不揃いでもある。**「検証は UseCase に書く」（`CLAUDE.md`）に揃える。**

* **`status` が `scheduled` へ変わる更新では、飛ばした履歴を消す**（§5.1.1）。
  `skip_count = 0` / `skip_reason = NULL` / `next_attempt_at = NULL` に戻す。取りやめ（`draft`）から予約し直したのに
  後ろへ送られた予定を引きずると、指定した時刻に出ない
* `failureReason` は現行どおり

#### 6.5.2 1 回の実行の手順（`application/social/publish.ts` の `publishDuePosts`）

```text
1. 中断行を failed に落とす（§6.5.4）。件数 → summary.interrupted。各行に social.post.failed
2. 期限の来た auto の投稿を scheduled_at 順に最大 PUBLISH_BATCH_SIZE 件引く（§6.5.3）→ summary.due
3. 行ごとに（直列。並列にしない）：
   a. publisher = publisherRegistry.find(account.provider)。配信の支度ができていなければ **その行を後ろへ送る**（裁定 #9。下の §6.5.2.1）
      ・reason = 'no_publisher'      … publisher が無い／publish 未実装
      ・reason = 'credential_missing' … credentialFields が空でなく account.credentialConfigured が偽（要件 §4 裁定 #8）
      ・reason = 'account_missing'    … アカウントを引けない（FK があるので通常は起きない防御）
      decideSkipOutcome(post, reason, now) → deferred なら next_attempt_at を置いて summary.skipped++、
      failed（3 回目）なら status='failed' にして summary.skipFailed++ と social.post.failed
      **着手印は書かない**（attempt_count は 0 のまま。provider ごとに 1 回 log.warn）
   b. 着手印：UPDATE … SET publish_started_at = now(), attempt_count = attempt_count + 1,
      next_attempt_at = NULL, skip_count = 0, skip_reason = NULL
      WHERE id = ? AND status = 'scheduled' AND publish_started_at IS NULL RETURNING *。**自分のトランザクションでコミット。** 0 行なら誰かが触った → 次へ
   b2. **配信直前の再検査**（S-2。下の §6.5.2.2）：checkPublisherLimits と validate() を、着手した行の内容に掛ける。
      問題があれば publish() を呼ばずに f で failed（理由つき）。
   c. 資格情報：findAccountWithCredential → parseCredentialObject → validateCredentialAgainstFields。読めた時点で監査（§6.5.8）。
      **復号できない／形が合わない → 書き戻し failed**（それぞれの理由。§5.6.2）。publish() は呼ばない。
      「まだ設定されていない」は a で飛ばしてあるのでここへは来ない（来たら壊れているとみなして failed）。
      credentialFields が空の publisher には `{}` を渡して呼ぶ（§6.5.5）
   d. publish({ post, account, credential, attempt, signal, logger }) を AbortSignal.timeout(PUBLISH_TIMEOUT_MS) つきで呼ぶ。
      戻り値・例外・タイムアウトを PublishAttemptResult に写し、decidePublishOutcome で PublishVerdict にする
   e. rotatedCredential があれば書き戻す（§6.5.6）
   f. 結果を書き戻す：UPDATE … WHERE id = ? AND status = 'scheduled' AND publish_started_at IS NOT NULL（§6.5.6）。0 行なら summary.unrecorded++
   g. published → social.post.published、failed → social.post.failed を発火（書き戻しがコミットされた後）
4. summary を返す（§6.5.7）
```

* **並列にしない。** 同じ provider の API を同時に叩くと Rate Limit を自分で踏む。1 分周期・20 件・30 秒上限で、最悪でも 10 分で 1 回の実行が終わる。
  その間は次の周期がスキップされる（`setTimeout` の連鎖＋ロック）。§11 #6
* 例外はどこで出ても**その行だけ**を止め、次の行へ進む。ジョブ全体を落とすのは DB の取り出し（2）に失敗したときだけ（`runJob` が `error` として記録する）
* `AuthorizationContext` を持たない（`029` §8 と同じ。本体の処理として走る）。Repository を直接使い、UseCase を通らない

#### 6.5.2.1 配信できない予約を後ろへ送る（裁定 #9）

> **2026-09-23 に書き直した。** もとの a は「**行に触らずに** `summary.skipped++`」だった。
> 行を一切更新しないため、飛ばした 20 件が `ORDER BY scheduled_at ASC LIMIT 20` の先頭に居座り続け、
> **配信可能な投稿が永久に送られない**（検証レポート S-1）。Plugin を入れ忘れた provider の期限切れ予約が
> 20 件溜まるだけで、その installation の SNS 自動配信が全部止まる。悪意がなくても起きる。
> 裁定 #9 に従い、**飛ばすときに行を後ろへ送り、同じ理由で 3 回飛ばされたら `failed` にする**。

```text
verdict = decideSkipOutcome({ skipCount: post.skipCount, skipReason: post.skipReason }, reason, now)
```

| `verdict.kind` | `social_posts` への UPDATE（`WHERE id = ? AND status = 'scheduled' AND publish_started_at IS NULL`） | summary |
| --- | --- | --- |
| `deferred` | `skip_count = <verdict>`, `skip_reason = <reason>`, `next_attempt_at = <verdict.nextAttemptAt>`, `updated_at = now()`。**`attempt_count` / `publish_started_at` / `failure_reason` / `status` は触らない** | `skipped++` |
| `failed` | `status = 'failed'`, `failed_at = now()`, `failure_reason = skipFailureReason(reason)`, `skip_count = 3`, `skip_reason = <reason>`, `next_attempt_at = NULL`。**`attempt_count` は 0 のまま** | `skipFailed++`、`social.post.failed` を発火 |

* **`listDue` の SQL は変えなくてよい。** 取り出し条件は既に
  `(next_attempt_at IS NULL OR next_attempt_at <= now())` を見ている（§6.5.3）ので、`next_attempt_at` を置くだけで
  その行は次に見る時刻まで候補から外れる。**§6.5.3 の SQL は `022` のときと 1 文字も変わらない**
* **`attempt_count` は据え置き**（裁定 #9 の細目）。`publish()` を呼んだ回数という意味を保つ。
  飛ばした行の回数は `skip_count` が持つ。受け入れ条件 #27(B) / #49 はこの約束の上に立っている
* **着手印は書かない。** b まで進めてから戻すと、`attempt_count` を無駄に減らせず、`publish_started_at` を消し忘れた行が
  次の実行で「中断」として `failed` になる（§6.5.4）
* **理由が変われば数え直す**（裁定 #9 の細目）。「publisher が無い → 入った → 今度は資格情報が無い」は別の事象で、
  運用者は 1 つずつ直している最中である。まとめて数えると、直している途中で打ち切られる
* **`UPDATE` が 0 行だった場合**（その間に人が `PATCH` した等）は何もしない。次の周期で判定し直す
* ログは provider ごとに 1 回 `log.warn('social publisher is not registered', { provider, count })` /
  アカウントごとに 1 回 `log.warn('social account credential is not configured', { accountId, provider })`（現行どおり）。
  `failed` にしたときは `log.error('social post skipped too many times', { postId, provider, reason, skipCount })`
* **飛ばした行の分だけ、その周期の配信枠は減る。** 20 件すべてが後ろへ送られた周期では配信可能な投稿に届かない。
  バッチを埋め直すことはしない（1 回の実行時間の上限 §11 #6 を保つため）。**次の周期には枠が空く**ので、
  止まるのは最大 1 周期（既定 1 分）にとどまる。受け入れ条件 #89 がこれを固定する

#### 6.5.2.2 配信直前の再検査（S-2）

> **2026-09-23 に足した。** 裁定 #8 で publisher が無くても登録できるようになった結果、
> **publisher が無い間に登録された投稿は `limits` も `validate()` も一度も通っていない**。
> そして配信側に再検査が無かったため、280 文字を超える本文が X の publisher へ渡って外部 API へ飛び、
> Instagram の `mediaRequired` も provider 固有の `validate()` も素通りしていた（検証レポート S-2）。
> 「Plugin を後から入れる」という**裁定 #8 が想定した運用そのもの**で起きる。
> §5.5 / §6.1.2 の「配信時刻に初めて失敗するのが一番困る」は、事前検査だけでは Core の保証にならない。
> **publisher が無い間に登録された投稿にとって、配信時が唯一の判定機会である。**

着手印を書いた直後（b の後、資格情報を読む c の前）に、`publishOne` の中で掛ける。

| # | 検査 | 通らなかったときの `failure_reason` |
| --- | --- | --- |
| 1 | `checkPublisherLimits(post, registration.limits ?? {}, registration.label)`（§5.6.2。**§6.1.2 の j〜l と同じ関数**） | `publisherRejectedReason(problems)` |
| 2 | `registration.validate({ post, account })`（あれば）。`VALIDATE_TIMEOUT_MS` で打ち切り | `publisherRejectedReason(problems)` |
| 3 | 2 が例外／制限時間超過 | `validateErrorReason(message)` |

* いずれも **`publish()` を呼ばない。** 結果は `{ kind: 'failed', reason }` として f の書き戻しへ渡す
  （`status = 'failed'`、`failed_at = now()`、`publish_started_at = NULL`、`social.post.failed` を発火）
* **再試行しない。** 宣言に合わない投稿は、時間が経っても合うようにはならない。人が本文を直して登録し直す
* **理由は「未送信」と読める文言にする。** `publisherRejectedReason` は
  `配信 Plugin の検査に通らなかったため、配信していません: <field>: <message>; …`、
  `validateErrorReason` は `配信前の検査で配信 Plugin がエラーを返しました（未送信）: <message>`。
  §5.6.2 の `pluginErrorReason` / `TIMEOUT_REASON`（どちらも**結果不明**）と混ぜない。
  「送ったか分からない」と「送っていない」は運用者の次の行動が違う
* Plugin 由来の自由文（`message`）はログ・DB に載せる前に `redactSecrets` → `normalizeFailureReason` を通す（§6.5.5）。
  この時点では資格情報をまだ復号していないので `redactCredentialValues` は掛けない（掛ける値が無い）
* **`attempt_count` は 1 になる**（b で着手印を書いた後だから）。ここで `failed` になった投稿は「1 回試して、送る前に弾かれた」

#### 6.5.3 取り出し条件（SQL 相当）

```sql
-- 2. 期限の来た自動配信の投稿
SELECT p.*
  FROM social_posts p
 WHERE p.status = 'scheduled'
   AND p.delivery_mode = 'auto'
   AND p.publish_started_at IS NULL
   AND p.scheduled_at IS NOT NULL AND p.scheduled_at <= now()
   AND (p.next_attempt_at IS NULL OR p.next_attempt_at <= now())

```

`social_posts_status_scheduled_idx (status, scheduled_at)` で `status` を先頭で絞り `scheduled_at` を範囲で読む。
`FOR UPDATE SKIP LOCKED` は使わない。advisory lock で実行は 1 プロセスに限られ、行の取り合いは起きない。
手動投稿（`delivery_mode = 'manual'`）は**この条件に掛からない**（ジョブは手動投稿を一切触らない）。

> **2026-09-23 の確認。** 裁定 #9（配信できない予約を後ろへ送る）で **この SQL は変えない。**
> `(next_attempt_at IS NULL OR next_attempt_at <= now())` が既にあり、飛ばすときに `next_attempt_at` を置けば
> その行は次に見る時刻まで候補から外れる。`skip_count` / `skip_reason` を取り出し条件に入れる必要も無い
> （回数の判定は取り出した行に対して Domain の `decideSkipOutcome` が行う）。
> 索引（`social_posts_status_scheduled_idx`）も変えない。

#### 6.5.4 着手印と中断行（要件 §5.3）

* **着手印を先に書いてコミットしてから `publish()` を呼ぶ。** 同じトランザクションの中で呼ぶと、プロセスが死んだときに印がロールバックされ、
  次の実行が同じ投稿をもう一度送る
* **中断行の規則**：ジョブ開始時に `status = 'scheduled' AND delivery_mode = 'auto' AND publish_started_at IS NOT NULL` の行は、
  前回の実行が `publish()` の途中で死んだ行である（advisory lock により同時実行は無く、正常に終われば印は必ず NULL に戻る。§5.8）。
  **再送せず `failed` に落とす。** `failure_reason = INTERRUPTED_REASON`、`failed_at = now()`、`publish_started_at = NULL`。
  二重投稿より未投稿のほうがまし（裁定）。人が SNS 側を見て、必要なら投稿し直す（履歴画面に理由が出る）

```sql
-- 1. 中断行
UPDATE social_posts
   SET status = 'failed', failed_at = now(), failure_reason = $1, publish_started_at = NULL, updated_at = now()
 WHERE status = 'scheduled' AND delivery_mode = 'auto' AND publish_started_at IS NOT NULL
RETURNING id, social_account_id;
```

* 例外的に「中断ではないのに中断扱い」になる経路が 1 つある：ロック専用接続だけが切れて前の実行が生きたまま、
  次の実行が別プロセスで始まった場合。前の実行の書き戻し（f）は `publish_started_at IS NOT NULL` の条件で 0 行になり、
  結果は `failed`（結果不明）で確定する。**安全側（未投稿と報告する）に倒れる**ので許容する（§11 #1）

#### 6.5.5 資格情報の受け渡し（裁定 #2）

* **復号する場所は Application**（`application/social/publish.ts`）。`socialRepository.findAccountWithCredential`（既存。Infrastructure の
  `decryptSecret` を中で呼ぶ）が返す `Secret` を、`publish.ts` が `expose()` して `parseCredentialObject` に通す。

  Core はローカル変数として持ち、呼び出しが返ったら参照を捨てる（`PublishInput` を保持しない・ログに載せない・`summary` に入れない）
* `credentialFields` が空の publisher には `{}` を渡す（`credential` が無くても呼ぶ）
* 他のアカウントの資格情報・他の provider の資格情報は**渡らない**（1 行ずつ、その行のアカウントの分だけ）
* Plugin は保存し直さない（`store.setSecret` に写す必要が無い）。更新は `rotatedCredential` で返す（§6.5.6）
* **平文を出さない措置**（要件・受け入れ条件 #55）：
  * `log.*` の `fields` に `credential` / `PublishInput` / `post.body` を入れない。入れるのは `postId` / `accountId` / `provider` / `pluginId` / `attempt` / `outcome` / `durationMs` / `reason`
  * Plugin が返した `reason`・例外メッセージは `redactCredentialValues(redactSecrets(text), values)` → `normalizeFailureReason`（2000 文字）の順で通してから
    `failure_reason` とログに載せる（伏せてから切る。`029` §6.1.7 と同じ順）
  * `job_runs.summary` は固定キーの数値だけ（§6.5.7）
  * イベントの payload は `{ postId, accountId, status }` だけ（§9.6）
  * `publish()` に渡す `PluginLogger` は、既存の `maskSecrets`（キー名 `credential` / `token` / `secret` 等を落とす）に加えて、
    **`message` と `fields` の文字列値へ `redactCredentialValues(…, secretValues)` を掛ける**。
    `publishOne` はその行の資格情報の値を既に持っているので、渡す直前に包むだけで済む
    > **2026-09-23 に直した（検証レポート L-1）。** もとは「**値まで守るのは Core の措置ではない**
    > （Plugin が `logger.info('x', { pw: credential.appPassword })` と書けば出る）」として、開発ガイドの契約に委ねていた。
    > しかし `publishOne` の中には既に `secretValues` があり、`failure_reason` と例外メッセージには同じ伏せ字を掛けている。
    > **契約でなく機構で守れるものは機構で守る。** 開発ガイドの「資格情報の値をログに渡さない」は残す（§12。
    > 伏せ字は 4 文字以上の完全一致しか消せないので、機構は契約の代わりにはならない）
  * `manual()` には資格情報を**渡さない**（`ManualInput` に `credential` が無い。Web Intent は公開 URL）

#### 6.5.6 結果の書き戻しと再試行（決めたこと。要件 §7）

| `PublishVerdict` | `social_posts` への UPDATE（`WHERE id = ? AND status = 'scheduled' AND publish_started_at IS NOT NULL`） |
| --- | --- |
| `published` | `status = 'published'`, `published_at = now()`, `external_id`, `external_url`, `failure_reason = NULL`, `next_attempt_at = NULL`, `publish_started_at = NULL` |
| `retry` | `status` は `'scheduled'` のまま, `next_attempt_at = <verdict>`, `failure_reason = <reason>`, `publish_started_at = NULL` |
| `failed` | `status = 'failed'`, `failed_at = now()`, `failure_reason = <reason>`, `next_attempt_at = NULL`, `publish_started_at = NULL` |

* 再試行の列は `attempt_count`（着手時に +1）と `next_attempt_at`。回数は **5 回**（初回＋4 回）、間隔は **1 → 2 → 4 → 8 分**
  （Webhook `023` に揃える。要件 §7）。Plugin の `retryAfterMs` が長ければそちらを使い、上限 24 時間で切り詰める
* 再試行は **`retryable: true` のときだけ**。送信前のネットワーク断・429・認証エラー以外の 4xx のうち送っていないもの、が対象。
  5xx やタイムアウトのような「届いたか分からない」失敗は Plugin が `retryable: false` にする（契約。§9.2）。Core は例外・タイムアウトを機械的に `failed` にする
* 中断行の理由（`INTERRUPTED_REASON`）と `retry` の途中の理由は `failure_reason` に入る。**`scheduled` のまま `failure_reason` がある**のは
  「再試行待ち」の印で、一覧の状態列に「予約済み（再試行待ち・N 回目）」と添える（§7.3）
* **`rotatedCredential`**：`publish()` が返したら、`validateCredentialAgainstFields` を通したうえで `JSON.stringify` → `encryptSecret` →
  `socialRepository.updateAccount(tx, accountId, { encryptedCredential })`。投稿の書き戻しとは**別のトランザクションで先に**行う
  （投稿側が 0 行でも、トークンが更新された事実は変わらない）。監査ログ `updated` / `social_account` / `detail: { changed: ['credential'], rotated: true, pluginId }`。
  宣言に合わない（キー不足・未知のキー・4096 文字超）なら書かずに `log.warn`、投稿の結果には影響しない
* 書き戻しが 0 行（`unrecorded`）：その間に人が `PATCH` した（ガード §6.2 は `publish_started_at` が立っている間は弾くので、
  実際には別プロセスの中断判定 §6.5.4 の経路だけ）。`log.warn('publish result could not be recorded', { postId, verdict })`。イベントは発火しない

#### 6.5.7 `job_runs.summary` とログ

```jsonc
{ "interrupted": 0, "due": 3, "skipped": 1, "skipFailed": 0, "attempted": 2, "published": 1, "retried": 1, "failed": 0, "unrecorded": 0 }
```

> **2026-09-23 に直した（裁定 #9）。** `skipped` の意味を改め、`skipFailed` を足して **9 キー**にする。
> 前は `skipped` が「行に触らずに見送った件数」だったが、裁定 #9 で飛ばした行は**後ろへ送られる**（行を更新する）。
> そして 3 回目は `failed` になる。**この 2 つを 1 つのキーにまとめない。**
> まとめると、設定画面「定期実行」に出る数字を見ても「待っているだけ」と「諦めた」の区別がつかず、
> `failed`（送って失敗した件数）とも混ざる。運用者が次に何をすべきかが読めなくなる。

* `due` は取り出した件数（≤ 20）
* **`skipped`** は**配信の支度ができておらず、後ろへ送った件数**（publisher が無い／`publish` 未実装／資格情報が未設定。§6.5.2.1 の `deferred`）。
  この件数はその周期では配信されないが、`scheduled` のまま残る
* **`skipFailed`** は**同じ理由で 3 回飛ばされ、諦めて `failed` にした件数**（§6.5.2.1 の `failed`）。
  `failed`（`publish()` を呼んだうえでの失敗）とは別に数える
* `attempted = published + retried + failed + unrecorded`。`due >= skipped + skipFailed + attempted`
  （着手印の `UPDATE` が 0 行だった行はどれにも入らない）
* `publishSummarySchema`（`POST /api/v1/social/publish` の応答。§6.5.9）にも `skipFailed` を足す
* ログ：`log.info('social post published', { postId, accountId, provider, pluginId, attempt, durationMs })`、
  `log.warn('social post publish retried', { …, attempt, nextAttemptAt, reason })`、`log.error('social post publish failed', { …, reason })`、
  `log.warn('social publisher is not registered', { provider, count })`（provider ごとに 1 回）、
  `log.error('social post skipped too many times', { postId, provider, reason, skipCount })`（§6.5.2.1 の `failed`）、
  `log.error('social post interrupted', { postId })`。**本文・資格情報・`PublishInput` は載せない**
* `job_runs.error` に入るのはジョブ全体の失敗（取り出しの SQL の失敗など）だけ。行ごとの失敗は `failure_reason`

### 6.6 手動投稿の UseCase

```ts
/** 手動投稿待ち（§5.8 の導出状態）。scheduled_at の古い順、最大 limit 件。`total` は全件数（ダッシュボードの件数に使う）。 */
export const listManualPendingPosts = defineUseCase<{ readonly limit: number }, SocialPostPage>({
  name: 'social.post.listManualPending', permission: 'social.read', … });   // SocialPostPage = { items, total }

export type ManualHandoffOutcome =
  | { readonly ok: true; readonly url: string; readonly note: string | null }
  | { readonly ok: false; readonly reason: 'unsupported' | 'invalid_url' | 'plugin_error' };

/** その投稿の「投稿画面の URL」を publisher に作らせる。資格情報は渡さない。 */
export const resolveManualHandoff = defineUseCase<{ readonly id: string }, ManualHandoffOutcome>({
  name: 'social.post.manualHandoff', permission: 'social.read', … });
```

* `resolveManualHandoff`：投稿が `deliveryMode = 'manual'` でなければ `ValidationError('SocialPost', 'deliveryMode', …)`。
  publisher が無い／`manual` 未実装 → `unsupported`。`manual()` が投げた・制限時間を超えた → `plugin_error`（`log.error`、内容は画面に出さない）。
  返った `url` が下の `isValidManualUrl` に通らなければ `invalid_url`
* **`isValidManualUrl` は `domain/social/social.ts` に独立して置く**（2026-09-23。下の枠）。判定は
  「**https の絶対 URL で、`isValidExternalUrl` と同じ規則**（資格情報付き URL を拒否・2048 文字以内）」
  **または**「`/` で始まる Torifune 内のパス（`//` / `/\` で始まらない）」

  > **2026-09-23 に直した（検証レポート L-2 と「判断が分かれる」6）。** 実装は `isSafeReturnTo`（`025` §8、
  > ログイン後の戻り先を決める関数）を絶対 URL の判定にまで流用していた。2 つの問題がある。
  > * **判定が `isValidExternalUrl` より緩い。** `https://user:pass@evil/` が通る（`isValidExternalUrl` は userinfo を拒否する）。
  >   長さ上限も無い。同じ「Plugin が返した URL」なのに、`publish()` の `externalUrl` より甘い門になっていた
  > * **目的が違う関数を共有している。** 片方の都合で `isSafeReturnTo` を緩めると、もう片方が黙って緩む。
  >   相対パスの判定だけは `isSafeReturnTo` に委ね、絶対 URL の判定は `isValidExternalUrl` に揃える

* `manual()` は同期でも `Promise` でもよい。**`MANUAL_TIMEOUT_MS`（2 秒）で打ち切る**（`Promise.race`）。
  超えたら `plugin_error` とし、`log.error('social publisher manual timed out', { provider, pluginId, postId })`
  > **2026-09-23 に足した（検証レポート L-3）。** `publish()` には 30 秒の上限と `AbortSignal` があるのに
  > `manual()` には無く、応答しない `manual()` は **`/social` の画面を丸ごと止められた**（Server Component が最大 50 行ぶん呼ぶ）。
  > 50 行 × 2 秒でも最悪 100 秒かかるので、**1 回の描画で掛ける合計にも上限を置く**：
  > `resolveManualHandoff` を行ごとに呼ぶ側（`app/social/page.tsx`）は、累計が `MANUAL_TIMEOUT_MS * 5`（10 秒）を超えた時点で
  > 残りの行を `plugin_error` として描く。**画面は必ず返る。**
  > 同期の無限ループは打ち切れない（§11 #20）
* `limit` は画面が 50 を渡す（区画に 50 件を超えて溜まる運用は想定しない。溢れた分は投稿一覧に「手動」として見える）
* SQL：`WHERE status = 'scheduled' AND delivery_mode = 'manual' AND scheduled_at IS NOT NULL AND scheduled_at <= now() ORDER BY scheduled_at ASC, id ASC LIMIT ?`
  （既存の `(status, scheduled_at)` 索引）

### 6.7 Plugin の起動との関係

publisher の登録簿は `activate()` で埋まる。**Bearer 認証の API 経路は `ensurePluginsStarted*` を通らない**
（`api/route.ts` は呼ばない。画面は `requirePageSession`、ログイン系のルートは自前で呼んでいる）。
定期実行は `prepare` で起動するが、起動から 15 秒以内の要求や `TORIFUNE_SCHEDULER=off` の構成では登録簿が空のままになる。
そうなると `deliveryMode = 'manual'` が g で 422 になり（publisher があるのに「手動投稿に対応していません」と断ってしまう）、
`limits` / `validate()`（j〜m）も掛からずに通ってしまう。

**登録簿を引くルートは、ハンドラの先頭で `ensurePluginsStartedAnonymously()` を呼ぶ**（`app/api/v1/auth/login/route.ts` と同じ形）：
`POST /social/posts`、`PATCH /social/posts/{id}`、`POST /social/accounts`、`PATCH /social/accounts/{id}`、`POST /social/publish`。
`defineRoute` に共通の仕組みを足す案（`pluginsRequired: true`）は API 基盤の変更なので別途（§11 #7）。

## 7. 画面

### 7.1 `/social` の「手動投稿待ち」区画（決めたこと。要件 §7）

**置き場は `/social`（投稿一覧の上）とダッシュボード（件数と導線だけ）の両方。**

* 操作する場所は 1 つにする。「投稿した／取りやめ」は投稿の状態を変える操作で、投稿一覧のすぐ上にあるのが自然
* ただし手動投稿は「その時刻に人が動く」ことが前提で、`/social` を開かない限り気づけないのでは成り立たない。
  ダッシュボードには**件数と導線**だけを出す（§7.6）。操作を 2 か所に置くと、片方だけ直す事故が起きる
* `/social/posts` という画面は無い（投稿は `/social` に並ぶ）。要件の「`/social/posts` 内の区画」はこの位置を指す

```text
┌ 手動投稿待ち（2 件） ───────────────────────────────────────────────────────────────┐
│ ⓘ 予約時刻を過ぎた手動投稿です。「投稿画面を開く」で投稿内容が入った画面が開きます。       │
│   投稿し終えたら「投稿した」を押してください。                                          │
│ アカウント            本文                     予約日時            経過   操作           │
│ 公式（X）             新製品のお知らせ…          2026-09-22 10:00    12 分  [投稿画面を開く] │
│                                                                    [投稿した] [取りやめ] │
│ 公式（Bluesky）       新製品のお知らせ…          2026-09-22 10:00    12 分  [投稿画面を開く] │
│                       ⚠ 投稿画面を開けません（この SNS の Plugin が無効です）。         │
│                                                                    [投稿した] [取りやめ] │
└──────────────────────────────────────────────────────────────────────────────────┘
```

* Server Component（`app/social/page.tsx`）が `listManualPendingPosts({ limit: 50 })` を呼び、各行に `resolveManualHandoff` を掛けて
  `{ post, handoff }` を Client Component `ManualPending`（`ui/social/manual-pending.tsx`）へ渡す。**URL は描画時に確定させる**
  （`window.open` はクリックの同期処理の中で呼ばないとポップアップとして扱われず、ブロックされる）
* 0 件なら区画そのものを描かない（`PluginWidgets` と同じ。空の枠は見た目を崩す）。`social.write` が無ければ操作ボタンを出さない（表示制御。認可は UseCase）
* 「投稿した」：小さな `Modal` に「投稿の URL（任意）」の `Input` を出し、`PATCH { status: 'published', externalUrl? }`。成功したら行を消して `Toast`
* 「取りやめ」：`ConfirmDialog`（「下書きに戻します。予約は解除されます。」）→ `PATCH { status: 'draft' }`
* `handoff.ok === false` の行は「投稿画面を開く」を `disabled` にし、理由の文言（`unsupported`「この SNS の Plugin が無効です」／
  `invalid_url`「Plugin が返した URL を開けません」／`plugin_error`「Plugin でエラーが起きました」）を添える。**「投稿した」「取りやめ」は押せる**
  （人が別の手段で投稿した場合を閉ざさない）
* `note`（Plugin が添える注意書き。例：「画像は投稿画面で添付してください」）があれば本文の下に出す
* 文言は `ui/social/labels.ts` に置く（`MANUAL_PENDING_LABEL` 等）
* **「経過」列は Server Component が文字列にして渡す**（2026-09-23 に補った。設計が「誰が『いま』を判定するか」を書いていなかった）。
  `elapsedText: string`（例：`'12 分'`）を行の props に持たせる。**Client Component の中で `Date.now()` を見ない。**
  見ると Server と Client で描画が食い違う（hydration mismatch）。
  既存も日時は Server Component が文字列化して部品へ渡している（`app/social/page.tsx` が `toISOString()` するのと同じ流儀）。
  **ページを開いたままだと値が古くなる**が、この区画は「いま投稿しに行く」ための一覧で、分単位の古さは実害が無い。
  自動更新は入れない（`019` の通知と違い、人が見ている前提の画面である）。
  同じ理由で §7.3 の「手動投稿待ち」の補足行も Server Component 側で判定する

### 7.2 子ウィンドウ（決めたこと。要件 §7）

```ts
const MANUAL_WINDOW_NAME = 'torifune-manual-post';
const MANUAL_WINDOW_FEATURES = 'popup=yes,width=600,height=720,noopener=yes,noreferrer=yes';
window.open(handoff.url, MANUAL_WINDOW_NAME, MANUAL_WINDOW_FEATURES);
```

* **名前を固定する**（`torifune-manual-post`）。同じ名前を使い回すので、2 件目を開いても窓が増えず、前の窓が置き換わる
* **`noopener` を付ける。** 開いた先は X / Bluesky の画面で、`window.opener` から Torifune の画面へ戻れる状態にしない
  （`rel="noopener"` と同じ意味。同時に `noreferrer` も付け、Torifune の URL を Referer で渡さない）。
  `noopener` を付けると `window.open` は `null` を返し、ブロックされたかどうかを判別できない。
  そのため同じ URL を `<a href target="_blank" rel="noopener noreferrer">別のタブで開く</a>` としても並べる（ブロックされたときの逃げ道）
* 寸法 600 × 720 は X / Bluesky の投稿画面（モバイル幅で崩れない）に合わせた既定で、ブラウザが尊重しなくても構わない
* 子ウィンドウでの投稿の成否を Core は知らない（Web Intent は結果を返さない）。だから「投稿した」を人が押す

### 7.3 投稿一覧（`ui/social/social-posts.tsx`）

  `{ provider: { label, manual: boolean, publish: boolean, credentialFieldKeys: string[] } }` を組み立てて渡す。

  **予約日時から約24時間が過ぎても支度が整わない投稿は、取りやめ（失敗）になります。**」を出す

  > 画面がそれを言わないと、運用者は取りやめられて初めて知ることになる。
  > 警告は「いま配信されない」だけでなく「いつまでに直せばよいか」まで伝える
* `published` の行で `externalUrl` があれば本文の脇に「投稿を見る ↗」（`target="_blank" rel="noopener noreferrer"`）。履歴画面（`social-history.tsx`）も同じ

### 7.9 Plugin マネージャに「握る拡張点」を出す（2026-09-23 に足した）

> **2026-09-23 に足した（検証レポート §6「判断が分かれる」1 と 3、裁定 #11）。**
> `docs/Plugin開発ガイド.md` と本設計 §9.2 は、資格情報を Plugin へ渡すことの正当化として

> （＝ Manifest の `extensions` 宣言）を挙げている。ところが `ui/plugin/plugin-manager.tsx` が導入前に見せているのは
> **要求 Permission だけ**で、`extensions` はどの画面にも出ていない（`grep "extensions" apps/web/src/ui apps/web/src/app` が 0 件）。
> **035 が作った穴ではない**（`database` / `authentication` も同じ）。しかし
> **平文の資格情報を渡す拡張点が入った以上、放置すると「宣言すれば安全」という説明が空文になる。**
> 宣言を根拠に設計を通したのだから、宣言が見えるところまでが本設計の責任である。

* **導入前の一覧（Plugin マネージャ）に「拡張点」を出す。** Manifest の `extensions` を、要求 Permission の隣に並べる。

* 表示名は `ui/plugin/plugin-manager.tsx` の `EXTENSION_KIND_LABEL` に置く。**何を握るかが読める文言にする**

  | `kind` | 表示 |
  | --- | --- |
  | `social` | `SNS配信（SNSアカウントの資格情報を受け取ります）` |
  | `database` | `データベース接続（接続情報を受け取ります）` |
  | `authentication` | `認証（利用者の認証を担います）` |
  | `data` | `データ参照（本体のデータを読み書きします）` |
  | `events` | `イベント購読` |
  | `ui` | `画面の拡張` |

  負けた側は `disabled` になり `reason` に理由が出る形は変えない
* Plugin の詳細（設定画面）ではなく**導入前に見える一覧**に出すことが要点である。
  入れてしまった後に分かるのでは、宣言の意味が無い

## 8. 権限（Permission）

§6.8 のとおり。画面側の出し分け（`social.write` で操作ボタン、`social.read` で区画とダッシュボードの導線、`system.manage` で定期実行の行）は
**表示制御であって認可ではない**。認可は UseCase（`CLAUDE.md`「認可を書く場所」）。

定期実行は誰の権限でもない本体の処理として走り、`publishDuePosts` は `AuthorizationContext` を受け取らない。
資格情報の読み出しは Permission ではなく**監査**で統制する（§6.5.8）。API Token の実効 Permission は現行どおり
「所有者の Permission ∩ scope」で、外部アプリ用の Token は `social.read` + `social.write` に絞る運用（裁定 #4）。

### 8.1 API Token は名前空間であって分離境界ではない（裁定 #10）

> **2026-09-23 に足した（検証レポート A-1、裁定 #10）。実装は変えない。**
> `externalRef` の冪等キーは `(created_by_token_id, external_ref)` で Token ごとに分離されているが、
> **リソースそのものへの到達は Permission だけで決まり、`created_by_token_id` は参照されない。**
> これは裁定 #4（Token = 外部アプリ 1 つ。新しいモデルは作らない）が意図して選んだ形で、
> `created_by_token_id` は**マルチテナントの区別列ではなく、誰が登録したかの記録**である。

`social.read` + `social.write` を持つ Token を 2 つのアプリ A / B に発行した場合、次が**できる**：

* A は `GET /social/posts` で B が登録した投稿を本文込みで全件読める
* A は `PATCH /social/posts/{B の投稿id}` で本文を書き換えられる。配信ジョブは **B のアカウントの資格情報でその本文を SNS へ投稿する**
* A は B のアカウントの資格情報を `PATCH` で上書き・削除できる（読み出しはできない。`05` §18）

**`created_by_token_id` による絞り込みは入れない**（裁定 #10）。入れると Token が所有権の単位になり、
「Token を作り直したら前の投稿が見えなくなる」「画面（セッション認証）からは Token 作成分が見えない」という
別の筋の悪さが生まれる。Torifune の認可の単位は Permission であって、Token はその上限を絞る道具である（`04` §28、`05` §37）。

**代わりに、運用者が判断できるようにマニュアルへ明記する**（§12）。`docs/マニュアル/SNS投稿の外部連携.md` は
「トークン 1 本 = 外部アプリ 1 つ」と書きながら**分離が無いことを一言も書いていない**のが問題の核で、
これを読んだ運用者が第三者のアプリへトークンを配ると上の状況になる。

## 9. Plugin API への影響

### 9.1 後方互換

* **追加のみ。`PLUGIN_API_VERSION` は `1` のまま上げない**（`010` §9 の判断基準。`032` の実例と同じ）
* 既存の型・メソッドは 1 つも消さない。**Plugin が実装・入力する側の型に必須項目を足さない**
  （Manifest、`PluginSettingsField`、`registerX` の引数など）。`PluginContext.social` は Core が組み立てて渡す側の型で、
  **Plugin が実装する対象ではない**ので必須で足してよい（`authentication` / `database` に先例がある）
  > **2026-09-23 に直した（検証レポート §6「判断が分かれる」2）。** もとは「必須項目を足さない」とだけ書いていたが、
  > `PluginContext.social` は必須プロパティなので、文字どおりに読むと自分の設計と矛盾する。**実装は正しく、文言だけが不正確だった。**
  > 「誰が作る型か」で線を引く。Core が作って渡す型に項目が増えても既存 Plugin は壊れない。
  > Plugin が作って渡す型（Manifest など）に必須項目が増えると壊れる
* **`markPublished` / `markFailed` の失敗条件を増やさない**
  > **2026-09-23 に足した（検証レポート S-3）。** `markPublished` / `markFailed` は `updateSocialPost` を通るため、
  > 本設計が `updateSocialPost` に足した事前検査が**そのまま Data API の失敗条件になっていた**。
  > 具体的には、`manual` の投稿がある状態でその Plugin を無効化すると、`markPublished` / `markFailed` が
  > 422（`ValidationError`）で落ちるようになっていた。**これは後方互換の破壊であり、§9.1 の一覧に挙がっていなかった。**
  > §6.2 の掛け方の見直し（`published` / `failed` への遷移には予約の検査を掛けない）でこれを解消する。
  > 失敗を記録する経路（`markFailed`）が検証で塞がれるのは特に筋が悪い。**今後 `updateSocialPost` に検査を足すときは、
  > その検査が `markPublished` / `markFailed` にも掛かってよいかを必ず見る**
* `SocialPostView` の項目追加、`CoreEventName` への `'social.post.failed'` の追加、`markPublished` の**省略可能な**第 2 引数はいずれも共用体・省略可の拡張
* `PLUGIN_EXTENSION_KINDS` に `'social'` を足す。**`'social'` を宣言した Manifest は、本設計より前の Torifune では検証で弾かれる**
  （未知の種類は拒否する既存の規則）。これは「新しい拡張点を使う Plugin は新しい本体が要る」という当然の関係で、既存 Plugin には影響しない
* `SocialAccountView` に資格情報は**足さない**。Data API 経由では今までどおり平文は渡らない（渡るのは `publish()` の引数だけ）

### 9.2 `packages/plugin-api/src/social.ts`（新規）

```ts
import type { PluginLogger } from './context';
import type { SocialAccountView, SocialPostView } from './data';
import type { PluginSettingsField } from './ui';

/**
 * SNS 配信（035-social-publishing 設計 §9）。
 *
 * **Plugin が書くのは「1 回配信する関数」と「投稿画面の URL を返す関数」だけ。**
 * いつ送るか・再試行・記録・画面は Torifune が持つ。Plugin は自前のタイマーを持たない
 * （複数プロセスで二重投稿するため。SNS の投稿は取り消せない）。
 */

/**
 * Torifune が適用する制約。SNS ごとの上限をここで宣言する。
 *
 * **登録時（`POST /social/posts`）と配信直前の両方で掛かる。**
 * publisher が無い間に登録された投稿は登録時の検査を一度も通っていないので、
 * 配信直前が唯一の判定機会になる（§6.5.2.2）。
 */
export interface PublisherLimits {
  /** 本文の上限（文字数の数え方は SNS ごとに違う。厳密な判定は validate() で行い、ここは早く弾くための粗い上限）。 */
  readonly bodyMaxLength?: number;
  /** 自動配信に媒体が必須か（Instagram）。手動投稿には適用されない。 */
  readonly mediaRequired?: boolean;
  readonly mediaMax?: number;

/** 登録前の投稿（まだ ID を持たない）。validate() が受け取る。 */

  'body' | 'scheduledAt' | 'deliveryMode' | 'media' | 'link' | 'providerOptions'

/** validate() が返す問題。`field` は要求のフィールド名（`body` / `media` / `link` / `providerOptions.<key>` など）。 */
export interface PublisherValidationProblem {
  readonly field: string;
  readonly message: string;
}

export interface PublishInput {
  readonly post: SocialPostView;
  readonly account: SocialAccountView;
  /**
   * このアカウントの資格情報。**この呼び出しの間だけ有効。**
   *
   * `credentialFields` で宣言したキーがそのまま入る。保存し直さない（`store.setSecret` に写さない）。
   * 更新が要るとき（トークンの延長など）は `rotatedCredential` で返す。**ログに値を渡さない。**
   */
  readonly credential: Readonly<Record<string, string>>;
  /** 何回目の着手か（1 始まり）。 */
  readonly attempt: number;
  /** Torifune が 30 秒で発火する。以後の処理は打ち切ってよい（結果は「不明」として記録される）。 */
  readonly signal: AbortSignal;
  readonly logger: PluginLogger;
}

/**
 * 配信の結果。
 *
 * **`retryable` の基準：「送る前に失敗した」なら true、「届いたか分からない」なら false。**
 * 送信前のネットワーク断・429・（送っていない）認証エラーは true。5xx・タイムアウト・応答の解釈失敗は false。
 * 迷ったら false（二重投稿より未投稿のほうがまし）。**例外を投げると常に「不明」として failed になる。**
 */
export type PublishResult =
  | {
      readonly ok: true;
      readonly externalId?: string;
      /** https の URL。履歴画面から辿れるようにする。 */
      readonly externalUrl?: string;
      /** 更新後の資格情報（キーは credentialFields のまま）。Torifune が暗号化して書き戻す。 */
      readonly rotatedCredential?: Readonly<Record<string, string>>;
    }
  | {
      readonly ok: false;
      /** 利用者に見せる理由（履歴画面に出る）。**資格情報を含めない。** 2000 文字で切られる。 */
      readonly reason: string;
      readonly retryable: boolean;
      /** 再試行までの待ち（ms）。Torifune の既定（1 → 2 → 4 → 8 分）より長いときだけ使われる。上限 24 時間。 */
      readonly retryAfterMs?: number;
    };

  readonly post: SocialPostView;
  readonly account: SocialAccountView;

  readonly url: string;
  /** 画面に添える注意書き（例：「画像は投稿画面で添付してください」）。 */
  readonly note?: string;

export interface PublisherRegistration {
  /** `social_accounts.provider` と同じ値（`^[a-z][a-z0-9_]{0,31}$`）。 */
  readonly provider: string;
  /** 表示名。Torifune の対応表より優先される。 */
  readonly label: string;
  /**
   * 資格情報の形。**入力欄と形式検証は Torifune が持つ。**
   * `kind: 'secret'` は打ち込むときに伏せる項目。保存はどの項目も暗号化され、どの項目も再表示されない。
   * 空なら資格情報無しで publish() が呼ばれる（`credential` は `{}`）。
   */
  readonly credentialFields: readonly PluginSettingsField[];
  readonly limits?: PublisherLimits;
  /**
   * 事前検査。問題が無ければ空配列。
   *
   * **登録時と配信直前の両方で呼ばれる**（`limits` と同じ理由。§6.5.2.2）。副作用を持たせない。
   * 制限時間は 5 秒（`VALIDATE_TIMEOUT_MS`）。超えると登録は 500、配信は `failed`（未送信）になる。
   */
  validate?(input: {
    readonly post: SocialPostDraftView;
    readonly account: SocialAccountView;
  }): readonly PublisherValidationProblem[] | Promise<readonly PublisherValidationProblem[]>;
  /**
   * 自動配信。
   *
   * **実装しなくても、この provider への自動配信の予約は断られない**（要件 §4 裁定 #8）。
   * 支度が整うまでジョブが予約を後ろへ送って待つ（§6.5.2.1）。利用者には画面で警告が出る（§7.3）。
   * **ただし待つのはおよそ 24 時間まで**で、それを過ぎた予約は `failed` になる（裁定 #9）。
   */
  publish?(input: PublishInput): Promise<PublishResult>;
  /**
   * 手動投稿。実装しなければ、この provider の `deliveryMode: 'manual'` は 422 で断られる。
   *
   * **制限時間は 2 秒**（`MANUAL_TIMEOUT_MS`）。`/social` は最大 50 行ぶん呼ぶので、外部へ問い合わせない
   * 純粋な URL の組み立てにすること（§6.6）。
   */
  manual?(input: ManualInput): ManualHandoff | Promise<ManualHandoff>;
```

### 9.4 登録の規則（Core 側）

| 場面 | 挙動 |
| --- | --- |
| `extensions` に `'social'` が無い | `registerPublisher` が `PluginExtensionNotDeclaredError(pluginId, 'social')` を投げる（`database` / `authentication` と同じ流儀）。`activate()` の中なら Plugin は `disabled` に落ちる |
| `provider` の形式が不正（`isValidProvider` 偽） | `Error('provider の形式が不正')` を投げる |
| 同じ provider を**別の** Plugin が既に登録している | `PluginPublisherConflictError(provider, registeredBy)`。`activate()` で投げれば後から来た Plugin が `disabled` になり、理由（provider 名と先に登録した Plugin ID）が管理画面に出る。**先に有効化されたほうが勝つ**（起動順＝`discoverPlugins` の順） |
| 同じ Plugin が同じ provider をもう一度登録 | 置き換える（`next dev` の再有効化で増殖しない） |
| Plugin を無効化・削除 | `unregisterPlugin(pluginId)` が `unregisterPublishersOf(pluginId)` を呼び、その Plugin の登録をすべて外す。以後その provider の自動配信の予約は**引き続き登録でき**（§6.1.2）、予約済みの投稿ともどもジョブが後ろへ送って画面に警告（§7.3）。**約 24 時間で `failed`**（裁定 #9。§6.5.2.1）。手動投稿を**新しく**予約するときだけ 422（§6.1.2 の g）。**既にある `manual` の投稿は「投稿した」「取りやめ」で動かせる**（§6.2・§7.1） |
| `Registrations.publishers` | 登録した provider を記録する（`databaseProviders` と同じ。管理画面で「何を握っているか」を出せるように） |

### 9.6 イベント `social.post.failed`（決めたこと。要件 §7）

**足す。** `009` §9 が予定していて `CORE_EVENTS` に無かったもの。自動配信が入ると「失敗」が人手を介さず起きるようになり、
通知 Plugin や Webhook が拾えないと運用者が気づけない。

* `CORE_EVENTS` に `'social.post.failed'`、`CoreEventPayloads['social.post.failed'] = SocialPostEventPayload`（`{ postId, accountId, status: 'failed' }`）
* **理由（`failureReason`）は載せない。** Plugin が返した自由文で、資格情報が混じる可能性を Core が完全には否定できない（`redactCredentialValues` は既知の値しか伏せない）。
  要るなら Data API（`socialPosts.get`）で引く（`docs/Eventリファレンス.md`「Payload に Secret を入れない」）
* 発火するのは：ジョブの `failed`（中断行・再試行の上限・非再試行の失敗・資格情報の不備）、`updateSocialPost` で `status: 'failed'` にしたとき
  （Data API の `markFailed` を含む。**現行は発火していない**ので、これも増える）
* `social.post.published` はジョブからも発火する（payload は現行の `{ postId, accountId }` に `status: 'published'` を添える。任意項目）
* Webhook の対象（`CORE_EVENTS` に入るので自動的に選べる）。`docs/Eventリファレンス.md` に行を足す（§12）

### 9.8 サンプル Plugin（`plugins/example-plugin/social.ts`）

外部サービスへ繋がない**ループバックの publisher**を足す（`025` §11 のダミー IdP と同じ考え方）。E2E と開発ガイドの題材になり、
Core の経路（着手印・復号・監査・書き戻し・イベント・手動投稿の画面）を本番と同じ形で通せる。

* `provider: 'example'`、`label: 'サンプルSNS'`、`credentialFields: [{ key: 'handle', kind: 'text' }, { key: 'appPassword', kind: 'secret' }]`、
  `limits: { bodyMaxLength: 100, mediaMax: 2 }`
* `validate()`：本文に `[invalid]` を含めば `{ field: 'body', message: '…' }`（422 の経路を E2E で踏むため）
* `publish()`：`store` に `{ postId, at }` を書き、`{ ok: true, externalId: post.id, externalUrl: '<APP_URL>/plugins/example-plugin/posts/<id>' }`。
  > **2026-09-23 に但し書きを足した（検証レポート §5 の 4）。** `APP_URL` は開発環境では `http://localhost:3000` で、
  > そのまま返すと `decidePublishOutcome` が `isValidExternalUrl`（https のみ）で落として `externalUrl: null` にする。
  > **履歴画面の「投稿を見る」導線が開発環境だけ消え、E2E #75 が空振りする。**
  > サンプル Plugin は `APP_URL` の scheme を `https` に強制して返す（外部へ繋がないループバックなので、
  > URL が実在しなくても題材として成り立つ）。これは**サンプル側の都合**であり、
  > 実在の publisher（`036`〜`038`）は SNS 側が返す https の URL をそのまま使う。
  本文が `[fail]` で始まれば `{ ok: false, retryable: false, reason }`、`[retry]` なら `{ ok: false, retryable: true, reason }`、
  `[throw]` なら例外、`[rotate]` なら `rotatedCredential: { ...credential, appPassword: 'rotated' }`
* `manual()`：`{ url: '/plugins/example-plugin/manual-post?text=' + encodeURIComponent(post.body), note: 'サンプルです。実際にはどこにも投稿されません。' }`。
  対応するページ（`registerPage`）はクエリの本文を表示するだけ
* `plugin.json` の `extensions` に `'social'` を足す。`permissions` は変えない（publisher は Data API を使わない）

### マイグレーションとスキーマ

### Domain 純関数

5. (A) `isDeliveryMode`：`'auto'` / `'manual'` → true、`'Auto'` / `''` → false。`isValidMediaUrl`：`https://a/b.png` → true、`http://a/b.png` / `https://u:p@a/b.png` / 2049 文字 / `javascript:` → false
6. (A) `publishRetryDelayMs(1)` = 60 000、`(2)` = 120 000、`(3)` = 240 000、`(4)` = 480 000。`(1, 900_000)` = 900 000（Plugin の指定が長い）、`(4, 1_000)` = 480 000（短い指定は無視）、`(1, 48h)` = 24h（上限）。`canRetry(4)` = true、`canRetry(5)` = false
7. (A) `decidePublishOutcome`：`{ ok: true, externalId: 'x', externalUrl: 'https://…' }` → `published`（両方入る）。`externalUrl: 'http://…'` → `published` で `externalUrl: null`。
   `{ ok: false, retryable: true }` attempt 1 → `retry` で `nextAttemptAt = now + 60s`。同 attempt 5 → `failed` で理由に「再試行の上限」。`{ ok: false, retryable: false }` → `failed`。
   `{ type: 'thrown', message }` → `failed` で理由が `pluginErrorReason(message)`（「結果不明」を含む）。`{ type: 'timeout' }` → `failed` で `TIMEOUT_REASON`。**`thrown` / `timeout` は attempt によらず `retry` にならない**
8. (A) `isDue`（`now` 固定）：`scheduled` / `auto` / `scheduledAt = now − 1s` / `nextAttemptAt = null` / `publishStartedAt = null` → true。`nextAttemptAt = now + 1s` → false。`nextAttemptAt = now − 1s` → true。
   `deliveryMode = 'manual'` → false。`status = 'draft'` → false。`scheduledAt = null` → false。`publishStartedAt` あり → false
9. (A) `isInterrupted`：`scheduled` / `auto` / `publishStartedAt` あり → true。`published` → false。`manual` → false。`isManualPending`：`scheduled` / `manual` / `scheduledAt <= now` → true、`scheduledAt > now` → false、`auto` → false
10. (A) `parseCredentialObject('{"a":"b"}')` → `{ a: 'b' }`。`'plain-token'` / `'[1]'` / `'{"a":{"b":1}}'` / `'{"a":1}'` → null。
    `validateCredentialAgainstFields({ a: 'x' }, [{ key: 'a' }, { key: 'b' }])` → `[{ field: 'credentials', message: /b を指定/ }]`。`({ a: 'x', z: 'y' }, [{ key: 'a' }])` → `z は指定できません`。`({ a: 'x' }, [])` → `[]`
11. (A) `redactCredentialValues('boom s3cretpw leaked', ['s3cretpw'])` → `'boom *** leaked'`。値が 3 文字以下（`'ab'`）は置換しない。空配列は入力のまま
12. (A) `providerLabel('bluesky')` → `'Bluesky'`、`providerLabel('x', { x: 'X（Plugin）' })` → `'X（Plugin）'`、`providerLabel('mastodon')` → `'mastodon'`

19. (C) 追加項目を省略した作成が 201 で、応答に `deliveryMode: 'auto'`、`media: []`、`link: null`、`providerOptions: {}`、`externalRef: null`、`externalId: null`、`externalUrl: null`、`attemptCount: 0`、`nextAttemptAt: null` がある。既存の項目はそのまま

### 11.1 #2b を撤回する（2026-09-23、裁定 #9）

> **2026-09-23 に撤回した。** #2b は「配信の支度が整わない予約が、期限を過ぎたまま静かに溜まりうる」を
> **許容する**と書き、「期限から N 日過ぎた予約を `failed` に落とす規則は、日数の根拠が無いので作らない」としていた。
>
> **#2b が許容したのは「その投稿が配信されずに溜まること」であって、「他の投稿まで配信されなくなること」ではない。**
> 実装は飛ばした行を一切更新しなかったため、溜まった 20 件がバッチの先頭を占有し、
> **その installation の SNS 自動配信が丸ごと止まる**という別の事象になっていた（検証レポート S-1）。
> 裁定 #8 はここまで含めて裁定されていない。
>
> 裁定 #9 が定めた結論：**飛ばした行は後ろへ送り、同じ理由で 3 回飛ばされたら `failed` にする。**
> 「日数の根拠が無い」という #2b の理由も解消している。根拠は日数ではなく**回数と間隔**で、
> 「1 時間 → 23 時間 → 諦める」＝**丸一日待って支度が整わなければ諦める**、と運用者に説明できる。
> `/social` の `Alert`（§7.3）はその期限を明示し、ダッシュボードの導線と
> `job_runs.summary` の `skipped` / `skipFailed`（§6.5.7）で件数が見える。
>
> したがって本設計に「支度が整わない予約は静かに溜まる」という未決事項はもう無い。

## 13. 後続 Plugin からの見え方（036〜038）

本設計の口だけで 3 つの Plugin が書けることを、provider ごとに示す。**Plugin が Core に要求する追加は無い。**

### 036 `sns-bluesky`（最初に作る。裁定 #5）

* `credentialFields: [{ key: 'identifier', label: 'ハンドル', kind: 'text' }, { key: 'appPassword', label: 'App Password', kind: 'secret' }]`。OAuth は要らない
* `limits: { bodyMaxLength: 300, mediaMax: 4 }`。`validate()` で `Intl.Segmenter` により 300 grapheme を厳密に数え、`media[].alt` の長さも見る
* `publish()`：`com.atproto.server.createSession`（`identifier` / `appPassword`）→ `media[].url` を取得して `uploadBlob` → `createRecord`（`app.bsky.feed.post`。`link` は外部埋め込み）。
  `{ ok: true, externalId: <rkey>, externalUrl: 'https://bsky.app/profile/<handle>/post/<rkey>' }`。セッション作成の失敗（401）は `retryable: false`、接続断は `true`。`rotatedCredential` は不要（App Password は固定）
* `manual()`：`{ url: 'https://bsky.app/intent/compose?text=' + encodeURIComponent(body + (link ? '\n' + link : '')) }`。媒体は付けられない（Core が `manual` + `media` を 422 にする）

### 037 `sns-x`

* `credentialFields`：OAuth 1.0a の 4 値（`apiKey` text / `apiKeySecret` secret / `accessToken` text / `accessTokenSecret` secret）。OAuth 2.0 を使うなら `accessToken` / `refreshToken` の 2 値で、更新した `accessToken` を `rotatedCredential` で返す
* `limits: { bodyMaxLength: 280, mediaMax: 4 }`。`validate()` で `providerOptions.replyTo` の形式などを見る
* `publish()`：`media[].url` を取得して v1.1 `media/upload` → `POST /2/tweets`。429 は `retryable: true` に `x-rate-limit-reset` から `retryAfterMs` を添える。5xx とタイムアウトは `false`。
  `{ ok: true, externalId: <id>, externalUrl: 'https://x.com/<handle>/status/<id>' }`
* `manual()`：`{ url: 'https://x.com/intent/post?text=…&url=…', note: '画像は投稿画面で添付してください。' }`。無料枠の利用者はこちらを使う（`deliveryMode: 'manual'`）

### 038 `sns-instagram`

* `credentialFields: [{ key: 'igUserId', label: 'Instagram ユーザー ID', kind: 'text' }, { key: 'accessToken', label: '長期アクセストークン', kind: 'secret' }]`
* `limits: { bodyMaxLength: 2200, mediaRequired: true, mediaMax: 10 }`。`validate()` で Business / Creator の前提や `media[].url` の拡張子を見る
* `publish()`：Graph API で container を作る（1 件なら `image_url` / `video_url`、複数なら carousel）→ `media_publish`。容器の処理待ちは `signal` を見ながらポーリングし、30 秒に収まらなければ `retryable: false`。
  long-lived token が 60 日で切れるので、残り 7 日を切っていたら `refresh_access_token` を呼び、新しいトークンを `rotatedCredential` で返す（Core が書き戻す）
* `manual` は**実装しない**。`deliveryMode: 'manual'` は Core が 422 で断る（§6.1.2 の g）。手動の導線が無い SNS はこれで正しい
