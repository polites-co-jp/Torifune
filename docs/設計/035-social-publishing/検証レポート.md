## 1. 修正が要る（マージ前）

### S-1. 配信できない予約がバッチを占有し、配信可能な投稿が永久に送られない

**`boundary-guardian` 観点4 と `security-reviewer` M-1 が独立に指摘。** 本レポートで最も重い。

* **場所**：`apps/web/src/infrastructure/social-repository.ts:530-549`（`listDue`）、
  `apps/web/src/application/social/publish.ts:542`（取り出し）・`:550-577`（`continue` で飛ばす）
* **裏取り**：`listDue` は publisher の有無で絞らず `ORDER BY scheduled_at ASC, id ASC LIMIT 20`。
  飛ばした行は**一切更新されない**（着手印も `attempt_count` も `next_attempt_at` も動かない）ので、
  **次の周期も同じ 20 件が先頭に並ぶ**。

**悪意がなくても起きる。** Plugin を入れ忘れた provider の期限切れ予約が 20 件溜まれば、
その installation の SNS 自動配信は完全に停止する。止まっている側の投稿は `scheduled` のままなので
画面上は「予約済み」に見え、エラーにもならない。

**悪意があれば `social.read` + `social.write` のトークン 1 本で成立する**（`security-reviewer` の手順）：

1. `POST /social/accounts` に `{"provider":"other","displayName":"x"}`（`credentials` を送らない）→ 201
2. そのアカウントへ `{"status":"scheduled","deliveryMode":"auto","scheduledAt":"2000-01-01T00:00:00Z"}` を 20 回 → 201。
   **過去日時を弾く検査が無い**ので、これらが `scheduled_at` 最古としてソート先頭に居座る
3. 以後、毎分のジョブは `due:20 / skipped:20 / attempted:0` を返し続け、**他アカウントの予約は 1 件も配信されない**

§11 #2b は「期限から N 日過ぎた予約を `failed` に落とす」規則を意図的に作らないと決めたため、時間では解消しない。

**§11 #2b が許容したのは「その投稿が配信されずに溜まること」であって、「他の投稿まで配信されなくなること」ではない。**
裁定 #8 はここまで含めて裁定されていない。

### S-2. 配信時に `limits` / `validate()` を再検査していない

**`boundary-guardian` 観点4。**

* **場所**：`apps/web/src/application/social/publish.ts`（`limits` / `validate` の呼び出しが 1 件も無い。
  呼んでいるのは `validateCredentialAgainstFields` だけ）
* 裁定 #8 で publisher が無くても登録できるようになった結果、
  **publisher が無い間に登録された投稿は `limits` も `validate()` も一度も通らない。**
  そして配信側に再検査が無い。

「Plugin を後から入れる」という**裁定 #8 が想定した運用そのもの**で、280 文字超の本文が X の publisher へ渡り外部 API へ飛ぶ。
Instagram の `mediaRequired`、provider 固有の `validate()` も素通りする。

設計 §5.5 / §6.1.2 の「配信時刻に初めて失敗するのが一番困る」という約束が、**Core の保証ではなくなっていた。**

### S-3. `markPublished` / `markFailed` が塞がれ、投稿が動かせなくなる

**`boundary-guardian` 観点2。設計 §7.1 と正面から矛盾する。**

* **場所**：`apps/web/src/application/social/social-use-cases.ts:505-518`（検査 g が
  `if (publisher === null) return;` より**前**にある）、`:829`（`updateSocialPost` が無条件に呼ぶ）、
  `apps/web/src/plugin/data-api.ts:374-394`（`markPublished` / `markFailed` も同じ UseCase を通る）

manual の投稿がある状態でその Plugin を無効化すると（Plugin マネージャの通常操作）、
以後その投稿は `published` にも `draft` にもできない。**画面からも詰み、削除以外に出口が無い。**

設計 §7.1 は明示的にこう書いている：

> `handoff.ok === false` の行は「投稿画面を開く」を `disabled` にし、理由の文言（`unsupported`「この SNS の Plugin が無効です」…）を
> 添える。**「投稿した」「取りやめ」は押せる**（人が別の手段で投稿した場合を閉ざさない）

`unsupported` はまさに publisher が無い場合である。**UI はボタンを押せる形で出すが、PATCH が 422 で落ちる。**
`markFailed` まで塞がれる（＝**失敗を記録する経路が検証で塞がれる**）のは特に筋が悪い。

§9.1「後方互換」の一覧にこの振る舞いの変化は挙がっていない。

### S-4. `externalUrl` が UseCase で検証されず、Plugin 経由で素通しになる

**`security-reviewer` M-3。**

* **場所**：`social-use-cases.ts:860`（`updateSocialPost` が検証せずに書く）、
  `plugin/data-api.ts:374-384`（`markPublished(id, { externalUrl })` は Zod を通らない）、
  出力先は `ui/social/social-posts.tsx:184` と `social-history.tsx:89` の `href={post.externalUrl}`

https 検証は `api/schemas/social.ts`（HTTP 経路）と `domain/social/publishing.ts`（`publish()` の戻り値）にしか無い。
**`body` は `updateSocialPost` の中で `isValidPostBody` を再検証しているのに `externalUrl` はしていない**という不揃いで、
「検証は UseCase に書く」という本プロジェクトの原則（`CLAUDE.md`）から外れている。

React 19 は `href` の `javascript:` を実行しないため XSS には直結せず、Plugin は信頼されたコードなので
実害は限定的。ただし原則からの逸脱として直す。

## 2. 裁定が要る

### A-1. API トークンは分離境界ではない（`security-reviewer` M-2）

**実装は設計どおり**（設計 §8 と裁定 #4 が「Token = 名前空間であって分離境界ではない」を意図的に選んでいる）。
`externalRef` の冪等キーは `(created_by_token_id, external_ref)` で正しく分離されているが、
**リソースそのものへの到達は Permission だけで決まり、`created_by_token_id` は参照されない。**

運用者がアプリ A と B にそれぞれ `social.read` + `social.write` のトークンを発行すると（マニュアルが推奨する運用そのもの）：

* A は `GET /social/posts` で **B が登録した投稿を本文込みで全件読める**
* A は `PATCH /social/posts/{B の投稿id}` で本文を書き換えられる。
  配信ジョブは **B のアカウントの資格情報でその本文を SNS へ投稿する**（A は B の SNS アカウントで任意の文章を公開できる）
* A は B のアカウントの資格情報を `PATCH` で上書き・削除できる（読み出しはできない）

問題は、**新設した `docs/マニュアル/SNS投稿の外部連携.md` が「トークン 1 本 = 外部アプリ 1 つ」と書きながら、
分離が無いことを一言も書いていない**点にある。これを読んだ運用者が第三者のアプリへトークンを配ると上の状況になる。

**選択肢**：(a) マニュアルに明記する（裁定 #4 を維持）／(b) `created_by_token_id` による絞り込みを入れる（裁定 #4 の変更）

### A-2. `scheduledAt` に過度な過去日時を許すか（S-1 に付随）

現状は無制限（`assertPostIsDeliverable` は非 null しか見ない）。S-1 の攻撃手順はこれを使う。
S-1 を直せば攻撃は成立しなくなるが、「2000 年の予約」を受け付けること自体の是非は別途。

## 7. 確認して問題が無かったもの

3 者が独立に確認し、いずれも問題が見つからなかった範囲：

* **資格情報の受け渡し**：`Secret.expose()` は `publish.ts` / `webhook/deliver.ts` / `plugin/store.ts` の 3 ファイルのみ
  （静的検査 #83 が件数で固定）。`resolveCredential` はその 1 アカウント分だけを引く。
  平文の出口（API 応答・`job_runs.summary`・`failure_reason`・イベント payload・ログの `fields`・例外）を個別に追跡し、
  **L-1 の `logger` 以外に出口は見つからなかった**。`credential_read` の監査は `publish()` の前に残り、
  `detail` に値もキー名も入っていない。`ManualInput` に `credential` は無い
* **冪等な登録**：`externalRef` の名前空間はトークンごとに正しく分離（他トークンの `externalRef` を乗っ取って既存行を返させることはできない）。
  `apiToken` は Token 行から積まれ、リクエスト値が入る経路は無い
* **Permission**：全ルートで `defineRoute` と `defineUseCase` の**二重**に宣言。CSRF は状態変更メソッドに掛かり Bearer では掛けない（正しい）
* **マイグレーション**：`022` は純粋な追加のみ。既存行を壊さず、部分一意索引も既存行（全件 NULL）と衝突しない。
  `api_tokens` への FK は `ON DELETE SET NULL` で、失効（`revoked_at`）では行が消えない
* **SQL インジェクション**：全て Kysely のクエリビルダ。ID は `UUID_PATTERN` で事前検証
* **XSS**：`dangerouslySetInnerHTML` の新規使用なし。`failureReason` と `note` はテキストとして描かれる
* **子ウィンドウ**：`noopener,noreferrer` と逃げ道の `<a rel>` を実装済み。
  URL のクエリに本文が乗ることは設計 §11 #15 が明示的に承知
* **SaaS 固有機能の混入**：`tenant` / `billing` / `saas` 等の grep で、コード・コメント・命名・コミットメッセージに 0 件。
  `created_by_token_id` はマルチテナントの区別列ではなく既存 API Token への FK
* **テストの空振り**：`static-checks.test.ts` は「検査対象が空でない」メタ検査を自分で持つ。
  `api/schemas/social.test.ts` は「項目を 1 つずつ削ると失敗する」形で見かけの検証になっていない。
  401 / 403 の取り違えには「未認証は ForbiddenError ではない」という対のテストが置かれている

## 8. 検証の限界

* `security-reviewer` は指示により**テストを実行していない**。S-1 の枯渇は**コードの読解に基づく推論であり、実機で再現させていない**。
  再現させるなら「publisher の無い provider の期限切れ予約 20 件 ＋ 配信可能な予約 1 件」でジョブを 1 回回し、
  `summary` が `due:20 / skipped:20 / attempted:0` になることを見れば足りる。**修正時のテストはこの形で書く**
* `security-reviewer` は設計書の §10 と §12 以降、実装プランを未読
* 既存の認証基盤（Token 検証そのもの、セッション Cookie の `HttpOnly`）は本差分で変更されていないため未確認
