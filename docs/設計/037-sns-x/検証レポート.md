## 2. 見つかった欠陥と処置

### 1. 空白の無い日本語の後ろまで URL と数えていた（`spec-verifier` 中-1）

設計 §9.4 の規則「`https?://` から空白までを URL とし 23 と数える」のため、
`'詳しくはhttps://example.com/aをご覧ください' + 'あ'.repeat(200)` を **31** と数えていた（X の数え方では 445）。
登録を通してしまい、自動投稿は予約時刻に 400 で `failed`、手動投稿は X の画面で送信できない。**日本語では URL の後に空白を置かない書き方がふつうにある。**

**処置**：URL の並びを **ASCII の可視文字（`[\x21-\x7E]`）だけ**にした（非 ASCII の文字で URL が終わる）。
表に 9 行足した。規則を元に戻すと 40 件落ちることを確かめた。
残る食い違い（IDN のホスト、path の非 ASCII 文字）は設計 §11 #3 (b) に向きとともに記録した。

**設計の誤りを実装がそのまま写した型**で、実装もテストも設計どおりだったため、設計を読む検証でしか見つからなかった。

### 3. 無料版の説明が Core の画面と違っていた（`security-reviewer` 低-1）

README と設計は「無料版には資格情報の入力欄が無い」「既存のアカウントに `/social` で 4 値を入れる」と書いていたが、実際は：

* `credentialFields: []` の provider にも Core が汎用の「資格情報（アクセストークン等）」欄を出す（`035` §7.5 の仕様どおり）
* `/social` には既存のアカウントの編集画面が無い。資格情報は `PATCH /api/v1/social/accounts/{id}` でしか入れ直せない
* 汎用の欄に何か入れたまま `sns-x-api` へ入れ替えると、「未設定で待つ」に入らず**直ちに `failed`**

**処置**：README と設計を実態に合わせた（欄は空のままにする、4 値は PATCH で入れる、入れてしまったら入れ替えの前に消す）。
**（ユーザー裁定）Core も直す。** 欄を出さないことと、画面で資格情報を入れ直せることを **`039`** で Core に足す（設計 §11 #15）。

## 4. 検証の方法

* `spec-verifier` は全件のテストを流し、**38 通りの変異**を入れて判別力を確かめた（生き残った 4 つのうち 3 つを §2 の 2 で潰した。残る 1 つは到達できない分岐で、想定どおり）
* `security-reviewer` は**テストを 1 本も実行していない**（DB の競合を避けるため）。判定はコードの読解と、署名の計算例の独立な再計算に基づく
* 処置の後に検証を回し直してはいない。処置した変異が落ちることは処置した側が確かめた
