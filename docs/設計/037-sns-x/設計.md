# 037 X 配信 Plugin（`plugins/sns-x-manual` / `plugins/sns-x-api`） 設計

> **035 が作った拡張点 `social` の 3 つ目・4 つ目の実利用者**（`036` Bluesky、`038` Instagram に続く）。
> 本設計は `docs/設計/035-social-publishing/設計.md` §13「037 `sns-x`」の骨子を具体化する。
> **Core（`apps/web` / `packages/plugin-api` / `migrations`）には 1 行も足さない。**
>
> **ユーザー裁定（2026-09-23）：X への配信 Plugin を 2 つに分ける。** 1 つの設計書に両方を書く。
>
> | Plugin | 対象 | 持つもの |
> | --- | --- | --- |
> | **`plugins/sns-x-manual`**（無料版） | X API の料金を払っていない利用者 | **`manual()` だけ**。資格情報の入力欄なし（`credentialFields: []`） |
> | **`plugins/sns-x-api`**（有料版） | X API の料金を払っている利用者 | **`publish()` と `manual()` の両方**。投稿ごとに `deliveryMode` で選べる（有料版でも手動を選べる） |
>
> **どちらも `provider: 'x'`。** 同時に有効にできるのは片方だけで（`035` §9.4）、
> **入れ替えても登録済みのアカウントと予約はそのまま使える**（§7.2）。これが 2 つに分けた設計の利点であり、本設計で成り立たせる。
>
> この 2 つは `035` の口のうち、**まだ誰も使っていない 2 つの形**を初めて使う：
> **`publish()` を持たない publisher**（`sns-x-manual`）と、**同じ provider を奪い合う 2 つの Plugin**（入れ替え）。

## 1. 目的

Torifune に登録された SNS 投稿を X へ届ける。**X API の料金を払うかどうかで、届け方を 2 通り用意する。**

| 事情 | Bluesky（036） | Instagram（038） | X（本設計） |
| --- | --- | --- | --- |
| API での自動投稿 | 無料（App Password） | 無料（Graph API） | **有料**（従量課金。§6.1） |
| 手動投稿（Web Intent） | ある | 無い | **ある**。画像は渡せない |
| 媒体の渡し方 | Plugin が取得してアップロード | Instagram が取りに来る | **Plugin が取得してアップロード**（036 と同じ経路。§6.5） |
| 資格情報 | App Password（固定） | 60 日で失効するトークン | **OAuth 1.0a の 4 値（失効しない）**（§5.2） |
| 本文の数え方 | 300 grapheme | 2200（数え方は非公開） | **重み付きで 280**（URL は 23、CJK と絵文字は 2） |

X の API は料金を払わないと投稿に使えない（§6.1）。一方で Web Intent（投稿内容の入った投稿画面）は誰でも開ける。
**料金を払わない利用者にも「予約した時刻に、投稿内容の入った画面が開く」ところまでは届けたい。** それが `035` 裁定 #3 で
手動投稿を Core の汎用概念にした理由そのもので、X はその最初の本命の利用者である。

2 つの Plugin が満たすべきことは次だけである。

* **`sns-x-manual`**：`manual()` が、投稿内容を反映した X の投稿画面の URL を返す。**自動配信の予約は登録の時点で断る**（§9.3）
* **`sns-x-api`**：`publish()` が 1 回の呼び出しで 1 件を X へ投稿し、結果を返す。`manual()` は `sns-x-manual` と**同じ URL を返す**

それ以外（予約・排他・着手印・再試行・記録・イベント・手動投稿の画面）は**すべて Core にある**。

## 3. スコープ

### 3.1 やること

* `plugins/sns-x-manual/` を新設する（`plugin.json` / `index.ts` / `social.ts` / `x-text.ts` / `README.md`）
* `plugins/sns-x-api/` を新設する（`plugin.json` / `index.ts` / `social.ts` / `x-text.ts` / `xapi.ts` / `oauth1.ts` / `README.md`）
* どちらも `provider: 'x'`、`label: 'X'` の publisher を `context.social.registerPublisher()` で登録する
* **2 つの `x-text.ts` をバイト単位で同じ内容にする**（intent URL の組み立て・本文の組み立て・重み付きの数え方。§4.2）
* `sns-x-manual`：`credentialFields: []`、`validate()`（`deliveryMode: 'auto'` を断る・重み付きの長さ・intent URL の長さ・`providerOptions`）、`manual()`
* `sns-x-api`：`credentialFields`（OAuth 1.0a の 4 値）、`limits: { mediaMax: 4 }`、`validate()`、`publish()`（画像の取得 → `POST /2/media/upload` → `POST /2/tweets`）、`manual()`
* OAuth 1.0a の署名（HMAC-SHA1）を Plugin の中で書く（`oauth1.ts`。Web Crypto を使い、依存を足さない。§6.3）
* `README.md`（2 つ）：どちらを選ぶか、**入れ替えの手順**（§7.2）、同時に有効にできないこと、猶予 24 時間（`035` 裁定 #9）

## 4. レイヤ配置

**すべて Plugin 層に置く。** 本体の `apps/web/src/` には 1 ファイルも足さない（テストとテスト用の共有定義を除く。§4.3）。

```text
plugins/sns-x-manual/
├── plugin.json      Manifest（extensions: ['social']）
├── index.ts         activate(): publisher の登録だけ
├── social.ts        createXManualPublisher(): PublisherRegistration（validate / manual）
├── x-text.ts        ★ 本文の組み立て・重み付きの数え方・intent URL。純関数（sns-x-api と同一内容）
└── README.md

plugins/sns-x-api/
├── plugin.json      Manifest（extensions: ['social']）
├── index.ts         activate(): publisher の登録だけ
├── social.ts        createXApiPublisher(): PublisherRegistration（validate / publish / manual）。publish() の段取り
├── xapi.ts          X API と媒体の取得への HTTP、応答の分類（phase / status → retryable）
├── oauth1.ts        OAuth 1.0a の署名と Authorization ヘッダの組み立て
├── x-text.ts        ★ sns-x-manual/x-text.ts とバイト単位で同じ
└── README.md
```

* **`@/` や `apps/web` を import しない。** 使ってよいのは `@torifune/plugin-api` の型と、Node の標準の global
  （`fetch` / `URL` / `FormData` / `Blob` / `TextEncoder` / `AbortSignal` / `Intl.Segmenter` / `crypto`（Web Crypto））だけ。
  **`node:` の import も置かない**（`036` / `038` の静的検査「import するのは `@torifune/plugin-api` と同じ Plugin のファイルだけ」を保つ）
* `pg` / `kysely` / `react` / `console` を使わない。出力は `PublishInput.logger` だけ
* **外へ出る HTTP は `xapi.ts` に閉じる**（`038` の `graph.ts` と同じ）。`x-text.ts` と `oauth1.ts` は `fetch` を持たない。
  `oauth1.ts` は時刻と nonce を**引数で受ける**（§6.3）

Domain 層・Application 層に X の語彙（`media_ids`、`oauth_signature`、`intent/tweet`）を 1 つも出さない。

### 4.1 Plugin 同士の関係

* **`sns-x-manual` と `sns-x-api` は互いを知らない。** Manifest の `dependencies` で結ばない
  （依存先は有効でなければならない（ガイド §8）が、2 つは同時に有効にできない。結ぶと**どちらも有効にできなくなる**）
* 両者を繋ぐのは **`provider: 'x'` という値だけ**である。Core は provider で publisher を引く（`035` §9.4）ので、
  アカウントと投稿は「どちらの Plugin が登録したか」を持たない。**これが入れ替えを成り立たせる**（§7.2）

### 4.2 `manual()` の実装を共有する方法（決めたこと）

**複製する。`plugins/sns-x-manual/x-text.ts` と `plugins/sns-x-api/x-text.ts` を、バイト単位で同じファイルとして置く。**
食い違わないことは静的検査と振る舞いの突き合わせの 2 段で固定する（§10.2 の #9 / #10）。

| 案 | 採否 | 理由 |
| --- | --- | --- |
| A. `sns-x-api` が `../sns-x-manual/x-text` を import する | **採らない** | ①**Plugin Package（zip）はトップレベル 1 ディレクトリ**（ガイド §10）で、隣の Plugin のファイルを持ち込めない。配布の単位が壊れる。②`sns-x-manual` を削除・隔離（`.torifune-quarantine`）すると、**有効な `sns-x-api` のビルドが壊れる**。③`036` / `038` の静的検査（import は同じ Plugin のファイルだけ）と食い違い、「Plugin は `@torifune/plugin-api` だけを見る」という手本を崩す |
| B. Manifest の `dependencies` で共通 Plugin に依存する | **採らない** | 依存先を有効にしておく必要があり、共通 Plugin が 1 つ増える（`/plugins` に「何も配信しない Plugin」が並ぶ）。しかも依存は**実行時の有効化の順序**を縛るだけで、**import を許すものではない**（A の①②はそのまま残る） |
| C. `packages/` に共有パッケージを作る | **採らない** | リポジトリのワークスペースを増やす変更で、「Core を 1 行も変えない」の外に出る。第三者が同じことをするには npm 公開が要り、手本にならない |
| **D. 同じ内容のファイルを両方に置き、一致をテストで固定する** | **採る** | 各 Plugin が単独で配布・導入・削除できる。複製の弱点（片方だけ直る）は**テストで機械的に止める**。共有するのは純関数 1 ファイルだけで、複製の量は小さい |

* **共有するのは `x-text.ts` の 1 ファイルだけ**（本文の組み立て・重み付きの数え方・intent URL の組み立て・それらの検査）。
  `validate()` の全体は共有しない（`sns-x-manual` だけが `auto` を断る。§9.3）が、**`validate()` が本文について言うことは
  必ず `x-text.ts` の関数から来る**ようにし、両者の `manual` の投稿への判定が一致することを振る舞いで確かめる（#10）
* `x-text.ts` の先頭のコメントに「**このファイルは `sns-x-manual` と `sns-x-api` に同じ内容で置く。片方だけを直さない**」と書く
* 直すときは 2 ファイルを同じコミットで直す。片方だけ直すと #9 が落ちる

### 5.1 `credentialFields`

**`sns-x-manual`：`credentialFields: []`。** 資格情報を読まない。

* Core は `credentialFields` が空の publisher について「資格情報 未設定」を理由に飛ばさない（`035` §6.5.2 の a）が、
  `sns-x-manual` は `publish()` を持たないので、そもそも `auto` の投稿で Core が資格情報を復号する経路に入らない。
  **`credential_read` の監査ログは 1 行も出ない**（#64）
* `manual()` には資格情報が渡らない（`035` §6.5.5。`ManualInput` に `credential` が無い）

**`sns-x-api`：OAuth 1.0a の 4 値。**

```ts
credentialFields: [
  {
    key: 'apiKey',
    label: 'API Key（Consumer Key）',
    description: 'X の開発者向け画面（Developer Console）でアプリに発行される API Key です。',
    kind: 'text',
  },
  {
    key: 'apiKeySecret',
    label: 'API Key Secret（Consumer Secret）',
    description: 'API Key と対になる Secret です。保存後は再表示されません。',
    kind: 'secret',
  },
  {
    key: 'accessToken',
    label: 'Access Token',
    description:
      '投稿するアカウントの Access Token です。アプリの権限を「Read and write」にしてから発行してください' +
      '（権限を変えた後は発行し直す必要があります）。',
    kind: 'text',
  },
  {
    key: 'accessTokenSecret',
    label: 'Access Token Secret',
    description: 'Access Token と対になる Secret です。保存後は再表示されません。',
    kind: 'secret',
  },
]
```

* **キーは `035` §13 の骨子の 4 つのまま**（`apiKey` / `apiKeySecret` / `accessToken` / `accessTokenSecret`）
* **形式検証は Core ではしない。** 形の検査は `publish()` の入口で Plugin が行い、通らなければ**外へ 1 本も出さずに** `retryable: false`（§6.8 の P0）
* 「Read and write」を `description` に書くのは、**読み取り専用のまま発行したトークンでは投稿が 403 で落ちる**ため。
  入力の時点で読まれる場所に書く（`036` §5.1 の「ここに書かないと利用者は間違える」と同じ理由）

### 5.2 認証方式を OAuth 1.0a に決める（決めたこと）

**`sns-x-api` は OAuth 1.0a（User Context）だけに対応する。OAuth 2.0 には対応しない。`credentialFields` は 4 値で確定させる。**

`POST /2/tweets` と `POST /2/media/upload` は、どちらも **OAuth 1.0a User Context と OAuth 2.0 User Context の両方**を受ける
（根拠：<https://docs.x.com/x-api/posts/create-post>、<https://docs.x.com/x-api/media/upload-media>。2026-09-23 に確認）。
どちらを選んでも投稿はできる。決め手は**資格情報の寿命**と、**`035` の口で寿命を扱えるか**である。

| | OAuth 1.0a（採る） | OAuth 2.0 PKCE（採らない） |
| --- | --- | --- |
| アクセストークンの寿命 | **失効しない**（利用者が取り消すまで）。<br>「These tokens do not expire but can be revoked by the user at any time.」<br><https://docs.x.com/fundamentals/authentication/oauth-1-0a/obtaining-user-access-tokens> | **2 時間**。<br>「the access token … will only stay valid for two hours」。更新には `offline.access` と refresh token が要る<br><https://docs.x.com/fundamentals/authentication/oauth-2-0/authorization-code> |
| 配信のたびの更新 | **不要**。`rotatedCredential` を使わない | 予約の間隔はたいてい 2 時間を超えるので、**ほぼ毎回** `POST /2/oauth2/token` で更新してから投稿する |
| 更新したトークンを Core へ返す口 | 要らない | **`rotatedCredential` は `ok: true` にしか載らない**（`035` §9.2）。更新した後で投稿が失敗すると、**新しい refresh token を返す手段が無い** |
| refresh token が使い捨ての場合 | — | 上の失敗で**資格情報が死ぬ**（古い refresh token は使えず、新しいものは捨てられた）。X の refresh token が使い捨てかどうかは公開ドキュメントの本文で確かめられなかった（§11 #2）が、**使い捨てでない保証も無い** |
| `035` §11 #25（書き戻しが運用者の変更を上書きする競合） | **及ばない**（書き戻しが起きない） | **毎回の配信で及ぶ** |
| `credentialFields` | 4 値 | `clientId` /（機密クライアントなら）`clientSecret` / `accessToken` / `refreshToken` の 3〜4 値 |
| 署名 | 要る（HMAC-SHA1。§6.3） | 要らない（Bearer） |

`038` は「延長を公開の**後**に置く」ことで同じ問題（更新した資格情報を失敗時に返せない）を避けたが、
**X の OAuth 2.0 では更新しないと投稿できない**（2 時間を過ぎたトークンでは送れない）ので、更新は必ず公開の**前**になる。
`038` の解き方が使えない。**Core の口（`rotatedCredential` を失敗時にも返せるようにする）を変えずに OAuth 2.0 を安全に扱う方法が無い。**

OAuth 1.0a の代償は **署名を Plugin の中で書くこと**（§6.3）だけである。署名は公開ドキュメントに計算例があり、
**例を再現するテストで正しさを固定できる**（#27）。

* **`credentialFields` は後から足せない**（`036` §5.2）。OAuth 2.0 に後から対応するなら、**`sns-x-api` の中で分岐させるのではなく、
  別の Plugin にする**（同じ provider の Plugin を入れ替える形は本設計で用意される。§7.2）
* 4 値は **X の開発者向け画面で自分のアカウント向けに発行できる**（3-legged の画面遷移が要らない）。
  `035` 裁定 #6（画面からの OAuth「接続」は後回し）のもとで、**利用者が自分で入力して端から端まで通る**のは 1.0a だけである

### 5.3 状態を持たない（決めたこと）

**どちらの Plugin も `store` を読みも書きもしない。`registerSettings` も呼ばない。**

* X API の宛先（`https://api.x.com`）は `xapi.ts` の定数にする。X に「自分で運用するサーバ」は無い。
  変えられるようにすると、**資格情報で署名した要求を任意のサーバへ送らせる口**が 1 つ増えるだけ（`038` §5.3 と同じ）
* intent URL の宛先（`https://x.com/intent/tweet`）は `x-text.ts` の定数にする
* 媒体の ID を再試行のあいだで持ち回らない（使われなかった媒体は X 側で失効する。§6.5）
* したがって Manifest の `extensions` は **`social` だけ**（`ui` を宣言しない。§8.1）

新しい Torifune の API エンドポイントは**作らない**。

* **`sns-x-manual` は外へ 1 本も要求を出さない。** `fetch` を持たない（#6）
* **`sns-x-api` が外へ出す HTTP 要求は次の 3 種類だけ**である

### 6.2 宛先と組み立て（決めたこと）

* `X_API_BASE_URL = 'https://api.x.com'` を **`xapi.ts` の定数**にする。R2 / R3 の URL は `new URL('/2/media/upload', X_API_BASE_URL)` の形で組み立てる。
  **文字列の連結にしない**（`036` §7.2 の低-2）
* R2 / R3 のパスは固定で、外から来た値をパスに差し込まない。**R3 の本体に入る `media_ids` は §6.5 の形の検査を通した値だけ**
* R1 の URL は `media[i].url` そのもの（Core の `isValidMediaUrl` を通った https の URL）。**R1 には `Authorization` を付けない**（資格情報を取得先へ送らない）

### 6.3 OAuth 1.0a の署名（`oauth1.ts`）

```ts
export interface OAuth1Credential {
  readonly apiKey: string;
  readonly apiKeySecret: string;
  readonly accessToken: string;
  readonly accessTokenSecret: string;
}

/** Authorization ヘッダの値（`OAuth oauth_consumer_key="…", …`）を作る。 */
export async function buildOAuth1Header(input: {
  readonly method: 'POST';
  readonly url: string;                                   // クエリを含まない（R2 / R3 はクエリを持たない）
  readonly params: Readonly<Record<string, string>>;      // 署名に含める form / クエリの値。R2 / R3 では常に {}
  readonly credential: OAuth1Credential;
  readonly nonce: string;
  readonly timestamp: number;                             // UNIX 秒
}): Promise<string>;
```

* 手順は RFC 5849 §3.4.1 / 公開ドキュメントのとおり：パラメータ（oauth_* 7 つ＋`params`）を**RFC 3986 でエンコード**して並べ、
  `POST&<エンコードした URL>&<エンコードしたパラメータ列>` を基底文字列にし、
  鍵 `<エンコードした apiKeySecret>&<エンコードした accessTokenSecret>` で **HMAC-SHA1**、base64
* **HMAC は Web Crypto（`crypto.subtle.importKey` / `sign`）で計算する。** Node 22 の global にあり、`node:crypto` の import も依存の追加も要らない
* **RFC 3986 のエンコード**は `encodeURIComponent` の後で `!'()*` を `%XX` にする（`encodeURIComponent` はこの 5 文字を残す）
* **R2（multipart）と R3（JSON）の本体は署名に含めない**（公開ドキュメント：基底文字列に入るのはクエリと form の本体だけ）。
  したがって R2 / R3 では `params` は常に `{}` になる。`params` を引数に持つのは**公開ドキュメントの計算例を再現するため**（#27）
* **nonce と timestamp は呼ぶ側が渡す**（`oauth1.ts` は時計も乱数も持たない純粋な計算。`crypto.subtle` は決定的）。
  既定の nonce は `crypto.getRandomValues` の 32 バイトを 16 進にしたもの（64 文字）、timestamp は `Math.floor(now() / 1000)`。
  **どちらも `createXApiPublisher` の引数で差し替えられる**（§10.1）
* ヘッダの形：`OAuth oauth_consumer_key="…", oauth_nonce="…", oauth_signature="…", oauth_signature_method="HMAC-SHA1", oauth_timestamp="…", oauth_token="…", oauth_version="1.0"`（値は RFC 3986 でエンコード）
* **資格情報を URL にもクエリにも載せない**（ヘッダだけ）。**署名の基底文字列・鍵・ヘッダの値をログにも `reason` にも載せない**（§6.9）
* **サーバの時計がずれていると 401 になる**（timestamp の検査）。README に書く

### 6.4 R3：投稿（`POST /2/tweets`）

```jsonc
// 要求（Content-Type: application/json）
{ "text": "<composeXText(post) の結果>", "media": { "media_ids": ["<R2 の id>", …] } }   // media はあるときだけ
// 応答（201）
{ "data": { "id": "1800000000000000000", "text": "…" } }
```

* **`text` は `x-text.ts` の `composeXText(post)`**（§9.4）。`manual()` が intent URL に入れるものと**同じ文字列**
* `media` は `media_ids` が 1 件以上のときだけ付ける（空の `media` を送らない）
* **残り時間が `CREATE_TWEET_TIMEOUT_MS` 以上あるときだけ送る。** 足りなければ送らずに `kind: 'budget'`（`retryable: true`）。
  打ち切られた R3 は「届いたか分からない」＝ `false` になるので、途中で切られる見込みの要求は**始めない**（`038` §6.5）
* 成功の判定は **HTTP 201（200 も受ける）かつ `data.id` が文字列**。`data.id` が無い・JSON でない → **`retryable: false`**（届いたか分からない）
* `data.id` が §6.7 の形に合わない → **失敗にしない**。`externalId` も `externalUrl` も付けずに `{ ok: true }`（`036` 低-1 の型。§6.7）

### 6.5 R1 / R2：画像の取得とアップロード（036 の中-1 の経路）

**X はバイト列のアップロードが要る。Torifune のサーバが `media[].url` を取りに行く。**
これは **`036` の中-1（取得先の status を `reason` に反射して、`social.write` を持つ者が内部ネットワークを走査できた）がそのまま再発しうる経路**である。
`036` の処置にすべて揃える。

| 枠 | 値 | 理由 |
| --- | --- | --- |
| リダイレクト | **追わない**（`redirect: 'manual'`。3xx は `retryable: false`） | 検査を通った URL から検査していない URL へ移らせない。**`'error'` にしない**（3xx を観測できず `network` に落ちる。`036` R-1） |
| 上限サイズ | **`MEDIA_MAX_BYTES = 5_000_000`**。先に `Content-Length` を見て、無ければ**読みながら打ち切る** | X の画像の上限（5 MB。§6.1）に合わせる。`036` の 1 MB は **Bluesky の上限に合わせた値**で、原則は「送り先の上限に揃える」。X で 1 MB にすると、**X が受ける普通の写真を Torifune が断る** |
| 受け付ける種別 | **`image/jpeg` / `image/png` / `image/webp` だけ**。`; charset=…` などの引数は落として比べる | **GIF を入れない**（アニメーション GIF は `tweet_gif` の別枠で、処理待ちがある。§11 #4）。知らない値を素通しする口は作らない |
| X へ送る種別 | 丸めた既知の値（`Blob` の `type`）。取得先の応答ヘッダそのままではない | 取得先の文字列を資格情報つきの要求へ転記しない（`036` 低-3） |
| `Authorization` | **付けない** | 資格情報を取得先へ送らない |
| 応答の中身・status | **`reason` にも `logger` にも載せない**（下） | `036` 中-1 |
| 順序 | **1 件ずつ順に**（R1 → R2 → 次の R1 → R2） | 相手側の Rate Limit を自分で踏まない（`036` §6.6） |

* **R1 の失敗は、HTTP の status を `reason` にも `logger` にも載せない。** 載せてよいのは「**一時的な失敗か、`media[].url` を直す必要がある失敗か**」の二分だけ。
  **`retryable` の判断には status を使い続ける**（4xx・3xx は `false`、5xx は `true`）。**判断に使うことと外へ出すことは別**（`036` §6.11）
* **R2（X API）の status は載せてよい。** 送り先は固定の `api.x.com` で、**運用者が自分の資格情報を直すための情報**である（走査の自由度が無い）
* R2 は `FormData` に `media`（`Blob`。種別は丸めた値）と `media_category=tweet_image` を入れて送る。`Content-Type`（boundary つき）は `fetch` に任せる
* R2 の応答の `data.id` は **`^[0-9]{1,20}$`** に合うときだけ使う。合わない・無い → **`retryable: true`**（R3 をまだ送っていない）
* R2 の応答に `processing_info` があり `state` が `succeeded` 以外 → **`retryable: true`**（R3 を送らない。画像では通常現れない。§11 #4）
* **媒体は投稿ではない。** R2 で上げて R3 を送らなかった媒体は誰にも見えず、X 側で失効する（応答の `expires_after_secs`）。
  作り直して二重投稿にはならない（`038` の「container は投稿ではない」と同じ）
* 取得先の制限（私有アドレスを断るか）は **Core の `isValidMediaUrl` の話で、Plugin からは広げも狭めもしない**（`036` §11 #10 と同じ判断）

### 6.6 制限時間と `signal`

Core は `publish()` を **30 秒**で打ち切り、**結果不明として `failed`** にする。**この Plugin は自分で早く諦める。**

| 定数 | 値 | 何に渡るか |
| --- | --- | --- |
| `PUBLISH_TOTAL_BUDGET_MS` | 25 秒 | `publish()` 全体。**入口で 1 つ作り、すべての要求の外側の signal に混ぜる**（`036` R-2） |
| `MEDIA_BUDGET_MS` | 15 秒 | 画像の処理（R1 / R2）の合計。= 合計 − `CREATE_TWEET_TIMEOUT_MS` |
| `MEDIA_FETCH_TIMEOUT_MS` | 10 秒 | R1 の 1 本ごと |
| `MEDIA_UPLOAD_TIMEOUT_MS` | 10 秒 | R2 の 1 本ごと |
| `CREATE_TWEET_TIMEOUT_MS` | 10 秒 | R3 |

* **外側の signal** ＝ `AbortSignal.any([input.signal, AbortSignal.timeout(PUBLISH_TOTAL_BUDGET_MS)])`。
  **媒体の signal** ＝ `AbortSignal.any([外側, AbortSignal.timeout(MEDIA_BUDGET_MS)])`。
  **要求ごとの signal** ＝ `AbortSignal.any([外側または媒体の signal, AbortSignal.timeout(その要求の定数)])`
* **R3 は媒体の signal ではなく外側の signal の下で送る**（媒体の期限で投稿の要求を切らない）。
  R3 を始めるのは残り ≥ 10 秒のときだけなので、**R3 は必ず合計 25 秒の内側で終わる**
* **期限の判定は `now()` で数える**（`038` §6.8）。「次の画像に取りかかるか」「R3 を送るか」は入口で記録した `now()` からの経過で決める。
  判定を実時間だけに預けると `budget` の分岐をテストが通せない
* **どの定数がどの要求へ渡るかは固定する**（`036` #81 の型。#72）
* **`input.signal` が発火したら、その場で処理をやめて `publish()` を抜ける**（Core は既に結果を確定させている）

### 6.7 戻り値の組み立て

```ts
{
  ok: true,
  externalId: tweetId,                          // ^[0-9]{1,20}$ に合うときだけ
  externalUrl: `https://x.com/i/status/${tweetId}`,   // 同上
}
```

* **`externalUrl` はハンドルを使わない `https://x.com/i/status/<id>` にする**（`035` §13 の骨子は `https://x.com/<handle>/status/<id>`）。
  | 案 | 採否 | 理由 |
  | --- | --- | --- |
  | `/2/users/me` を呼んでハンドルを得る | 採らない | **R3 の後に要求が 1 本増え、従量課金で料金がかかる**（§6.1）。投稿の後の要求は何が起きても `ok: true` を覆せない（`038` §6.6）のに、失敗の経路だけが増える |
  | `account.handle`（Torifune の登録値）を使う | 採らない | 利用者が書いた表示用の値で、実際のハンドルと食い違いうる（`036` §6.4）。食い違えば履歴の「投稿を見る」が 404 になる |
  | **`https://x.com/i/status/<id>`** | **採る** | 投稿 ID だけで投稿へ辿れる X の URL。**要求を増やさず、登録値にも依存しない**。ただしこの形は公開ドキュメントの本文で確かめられていない（§11 #7） |
* **tweet id の形は `^[0-9]{1,20}$`**（X の ID は 64 ビットの整数で、10 進で最大 20 桁）。
  これに合えば `externalId`（≤ 200 文字の CHECK に必ず収まる）と `externalUrl`（≤ 2048 文字に必ず収まり、Core の `isValidExternalUrl` に通る）を付ける。
  **合わなければ両方付けずに `{ ok: true }`**。**201 を返した以上、投稿はある。** 失敗にすると再試行で二重投稿になる（`036` 低-1）
* **`rotatedCredential` を返さない**（OAuth 1.0a は更新しない。§5.2）。したがって **`035` §11 #25 はこの Plugin には及ばない**

### 6.8 `retryable` の基準 — X API の応答への対応づけ

契約は「**送る前に失敗したなら `true`、届いたか分からないなら `false`、迷ったら `false`**」（ガイド §9）。
X で「送る」に当たるのは **R3（`POST /2/tweets`）の 1 回だけ**である。

> **支配的な規則（これだけ覚えればよい）**
>
> 1. **R3 を送る前の失敗は既定で `retryable: true`。** ただし**時間が経っても直らないもの**（資格情報・権限・投稿の内容・画像）は `false`
> 2. **R3 を送った後の失敗は既定で `retryable: false`。** ただし **429（書き込む前に断られたと読める）だけ `true`**

| # | フェーズ | 起きたこと | `retryable` | 理由 |
| --- | --- | --- | --- | --- |
| P0 | `input` | 資格情報の 4 値のどれかが §6.9 の形（`^[\x21-\x7E]{1,256}$`）に合わない | **false** | 人が資格情報を直すまで直らない。**外へ 1 本も出さない** |
| P0 | 〃 | `media` が 5 件以上（Core の `mediaMax` が見ているので通常来ない） | **false** | 投稿の内容。外へ出さない |
| P0 | 〃 | `validate()` と同じ本文の検査（重み付き 280）に通らない（配信直前の再検査が見ているので通常来ない） | **false** | 同上。**送れば 400 で断られるだけの要求に料金を払わない** |
| P1 | R1（画像の取得） | 接続できない・自前の制限時間・5xx | **true** | 投稿は作られていない |
| P1 | 〃 | 4xx・3xx・既知の種別でない・5 MB 超過 | **false** | 人が `media[].url` を直す |
| P1 | 〃 | 媒体の合計時間を使い切った（`kind: 'budget'`） | **true** | R3 を送っていない |
| P2 | R2（アップロード） | 接続できない・自前の制限時間・5xx・429 | **true**（429 は `retryAfterMs` つき） | **媒体は投稿ではない** |
| P2 | 〃 | 401 / 403 | **false** | 資格情報・アプリの権限・クレジット。人が直すまで直らない |
| P2 | 〃 | その他の 4xx・3xx | **false** | 画像の内容。迷ったら `false` |
| P2 | 〃 | 2xx だが JSON でない・`data.id` が無い・形に合わない・`processing_info.state` が `succeeded` 以外 | **true** | R3 を送っていない |
| P3 | 準備 | R3 を送るだけの残り時間（10 秒）が無い（`kind: 'budget'`） | **true** | **送らずに諦める**（§6.4） |
| P4 | R3（`POST /2/tweets`） | 429 | **true** ＋ `retryAfterMs` | **書き込む前に断られたと読める**（`036` の 429 と同じ扱い） |
| P4 | 〃 | 401 | **false** | 認証に失敗しており投稿されていないと読めるが、**直らない**ので `false`（`036` §6.9 と同じく、ガイドの表より狭める） |
| P4 | 〃 | 403（重複した内容・権限・アカウントの状態・クレジットなど） | **false** | 直らない。理由の文は X の自由文に頼らず固定文にする（§6.9） |
| P4 | 〃 | 接続断・制限時間・5xx・3xx・その他の 4xx・JSON でない・`data.id` が無い | **false** | **届いたか分からない。SNS の投稿は取り消せない** |
| — | どこでも | 予期しない例外 | **R3 の前なら true／後か不明なら false** | **例外を投げない。** 「R3 を送ったか」を 1 つの変数で持って分類する（`038` §6.11） |
| — | どこでも | `input.signal` が発火 | — | Core が「結果不明」として確定させている。何を返しても記録されない |

* **P4 の 401 / 403 を `true` にしない。** 401 は「送っていない」と読めても、1 → 2 → 4 → 8 分の再試行で直ることは無く、
  **`failed` が 15 分遅れるだけ**になる。403 は X の重複検出（同じ本文の連投）でも返り、**再送しても同じ結果**になる
* **ヘッダを受け取った後で合計の期限が発火すると、本物の `fetch` は本体の読み込みも reject する**（`038` 検証 §2 の 2）。
  **R3 の応答のヘッダの後・本体を読み切る前に打ち切られたら `false`**（二重投稿の向きに倒さない。#74）

### 6.9 例外を投げない・外へ出す範囲

* **`publish()` は例外を投げない。** すべての経路を `try` で包み、`PublishResult` として返す
* **`reason` に載せてよいもの**（これ以外は載せない）：
  * フェーズの言葉（「画像の取得」「画像のアップロード」「投稿」など、固定の日本語）
  * **R2 / R3 の HTTP の status**（数値）。**R1 の status は載せない**（§6.5）
  * 固定の案内文
* **載せないもの**：X API の応答の `title` / `detail` / `type` / `errors[].message` / `errors[].detail` / 応答の本文全体 /
  `x-rate-limit-*` などのヘッダの値 / 要求の URL / 例外の `message` / 署名の基底文字列 / `Authorization` の値
* **理由**：X API の自由文は**要求の値を混ぜ返すことがある**（本文の断片・パラメータ名・ID）。Core の伏せ字は
  **4 文字以上の完全一致しか消せない**（ガイド §9）。**伏せ字を当てにせず、読まない。**
  `036` / `038` は「既知のエラーコードの集合」だけを載せたが、X の problem 形式の `type` は URL の文字列で、既知の集合を固定する根拠が
  公開ドキュメントから取れなかった。**status だけで分類と案内が足りる**ので、応答の本体はエラーの分類に**読まない**（§11 #8）
* **資格情報の形の検査**（P0）：4 値とも `^[\x21-\x7E]{1,256}$`（空白・制御文字・非 ASCII を含まない）。
  値は署名の鍵とヘッダ（エンコード後）に入る。**改行を含む値でヘッダが作れず `fetch` が同期で投げ、`network` に化けて `true` を繰り返す**（`038` §6.2）のを入口で止める
* **`reason` の例**：
  * `X API の認証に失敗しました（投稿、HTTP 401）。API Key・Access Token とそれぞれの Secret を確かめてください。サーバの時計がずれていても起きます。`
  * `X が投稿を受け付けませんでした（投稿、HTTP 403）。同じ内容の連投、アプリの権限（Read and write）、X API のクレジットの残高を確かめてください。`
  * `画像を取得できませんでした。media の URL が、インターネットから取得できる 5MB 以下の JPEG・PNG・WebP 画像を指しているか確かめてください。`
  * `画像を取得できませんでした（一時的な失敗）。再試行します。`
* **`logger` に渡してよいもの**：`postId` / `attempt` / フェーズ名 / **R2・R3 の** HTTP status / 画像の件数 / 何件目の画像か
* **`logger` に渡さないもの**：`credential` の 4 値、`post.body`、`post.link`、`media[].url`、**R1 の status**、媒体の ID、tweet id、
  応答の本文、要求の URL、ヘッダ、署名に関わる値、`account.handle`

### 6.10 `link` / `alt` / GIF（黙って捨てない）

| 項目 | 扱い | 理由 |
| --- | --- | --- |
| `link` | **本文の末尾へ改行して足す**（`composeXText`。自動・手動とも同じ） | `POST /2/tweets` に URL を別に渡す項目は無い。本文に入れれば X がリンクにする（t.co）。**数えるのも足した後の文字列**（§9.4）なので、`036` §6.8 が避けた「数えた本文と送る本文の食い違い」は起きない |
| `media[].alt` | **送らない。断りもしない**（`README.md` に書く） | 送るには画像 1 件ごとに `POST /2/media/metadata` が増え、**料金と失敗の経路が増える**。`alt` は付随情報で投稿の意味を変えない（`038` §6.12 と同じ判断）。§11 #5 |
| GIF | **受け付けない**（R1 の種別で `false`） | §6.5。登録時には見分けられない（拡張子で判定しない。`036` §9.3） |
| URL の料金 | **断らない。`README.md` で知らせる** | `link` や本文中の URL を含む投稿は割高（§6.1）。**どの投稿が割高かは Torifune の判断ではない**（本文中の URL を断ると正当な投稿を拒む） |

### 7.1 無料版と有料版の選び方（`README.md` に書く）

| | `sns-x-manual`（無料版） | `sns-x-api`（有料版） |
| --- | --- | --- |
| X API の契約 | 要らない | **要る**（従量課金のクレジット。§6.1） |
| 予約時刻に起きること | `/social` の「手動投稿待ち」に並ぶ。**人が投稿画面を開いて送信ボタンを押す** | Torifune が自動で投稿する（`deliveryMode: 'auto'`）。手動も選べる |
| 画像 | 付けられない（投稿画面で添付する） | 自動配信なら 4 枚まで |
| 資格情報 | 入れない | OAuth 1.0a の 4 値 |

### 7.2 入れ替え（決めたこと）

**同時に有効にできるのは片方だけ。入れ替えは「有効な方を無効化してから、もう片方を有効化する」。**
登録済みの SNS アカウントと投稿は provider（`x`）で publisher に結びつくので、**入れ替えても作り直さない。**

**無料版 → 有料版**

```text
1. /plugins で sns-x-api を「導入」する（再ビルドと再起動。この間 sns-x-manual は有効のまま動く）
2. /plugins で sns-x-manual を「無効化」する
3. /plugins で sns-x-api を「有効化」する
4. /social で X のアカウントを開き、4 値を入れる（入れるまで自動配信の予約は「資格情報 未設定」で待つ。約 24 時間まで）
5. 以後の予約は「自動」を選べる。手動の予約はそのまま手動投稿待ちに並ぶ（同じ intent URL が開く）
```

* **1 を先にする**のは、導入に再ビルドと再起動が伴う（ガイド §10）ため。2〜3 のあいだ（数秒）は手動投稿待ちの行が
  「投稿画面を開けません（この SNS の Plugin が無効です）」になるが、**「投稿した」「取りやめ」は押せる**（`035` §7.1）
* **4 の資格情報は、無料版の間に API で先に入れておける。** `sns-x-manual` の `credentialFields` は空なので、
  Core は `POST` / `PATCH /api/v1/social/accounts` の `credentials` を突き合わせずに暗号化して保存する（`035` §5.6.3「宣言が空なら常に `[]`」）。
  **画面には入力欄が出ない**（宣言が空のため）ので、画面から入れるのは 3 の後になる
* **順序を間違えた場合**（`sns-x-manual` を有効にしたまま `sns-x-api` を有効化した）：`sns-x-api` の `activate()` で
  `PluginPublisherConflictError` が投げられ、`sns-x-api` は `disabled` に落ち、`/plugins` に理由が出る（`035` §9.4）。
  **`sns-x-manual` は動き続け、何も失われない。** 2 からやり直せばよい

**有料版 → 無料版**

```text
1. /plugins で sns-x-api を「無効化」し、sns-x-manual を「有効化」する
2. 残っている「自動」の予約を「手動」に直す（PATCH { deliveryMode: 'manual' }。画像を付けた予約は画像を外す）
```

* 直さずに残した `auto` の予約は、Core が「配信 Plugin なし」として後ろへ送り、**約 24 時間で `failed`** になる（`035` 裁定 #9。§9.3）。
  `/social` の Badge と Alert が知らせる
* 保存済みの 4 値は**残るが読まれない**（`sns-x-manual` は `publish()` を持たず、Core が復号しない）。消したければアカウントの資格情報を空にする

**起動時の扱い。** DB で両方が `enabled` になることは通常無い（負けた側は `disabled` に保存される）。
何らかの理由で両方が `enabled` のまま起動した場合は、`discoverPlugins` の順に有効化され、**後に来たほうが `disabled` に保存される**（`035` §9.4 の規則のまま）。

## 8. 権限（Permission）

**新しい Permission を作らない。** 2 つとも `plugin.json` の `permissions` は **空**（`[]`）。Data API（`context.data`）を 1 度も呼ばない。

### 8.2 高権限であることの自覚

* **`sns-x-manual` は資格情報を 1 つも受け取らない**（`credentialFields: []`、`publish()` を持たない、`manual()` には渡らない）。
  `social` を宣言するのは `manual()` を登録するためだけである
* **`sns-x-api` は OAuth 1.0a の 4 値を平文で受け取る**（`publish()` の `credential`。その呼び出しの間だけ）。
  4 値があれば**そのアカウントとして投稿できる**（有効期限が無い。§5.2）。送り先は `api.x.com` に固定（§5.3）
* **`sns-x-api` の画像の取得先は `social.write` を持つ者が指せる**（§6.5）。Torifune のサーバから任意の https へ GET が飛ぶ。
  リダイレクトを追わない・種別と大きさを絞る・**status も中身も外へ出さない**までをこの Plugin が受け持つ（`036` §8.2）
* **`sns-x-api` は利用者の X API のクレジットを消費する。** 再試行（429 / 送る前の失敗）は R3 を送っていないので投稿の料金は増えないが、
  R2（画像のアップロード）は再試行のたびにやり直す（§11 #10）

## 9. Plugin API への影響

**無し。`packages/plugin-api` を 1 行も変えない。Core への追加要求も無い。**

`035` §13 の主張は X についても、**2 つに分けた形でも**成り立つ。使う口と、それで足りた理由：

| 使う口 | 用途 | 足りたか |
| --- | --- | --- |
| `PublisherRegistration.provider` / `label` | 2 つとも `'x'` / `'X'` | 足りた。`x` は Core の `KNOWN_PROVIDERS` に元からある（`036` §11.1） |
| `credentialFields: []` | `sns-x-manual` が資格情報を持たない | **足りた。最初の利用者**（`example-plugin` を除く） |
| `credentialFields`（4 値） | `sns-x-api` | 足りた |
| **`publish` を実装しない** | `sns-x-manual` | **足りた。最初の利用者。** Core は `auto` の予約を断らず後ろへ送る（裁定 #8 / #9）。**利用者が黙って待たされないよう `validate()` で断る**（§9.3） |
| `PublisherLimits.mediaMax` | `sns-x-api`：4 | 足りた |
| `validate()` | 本文の重み付きの長さ・intent URL の長さ・`providerOptions`・（`sns-x-manual` だけ）`auto` を断る | 足りた。**`field` に `deliveryMode` を書ける**（`035` §6.1.2 の m：`^[A-Za-z][A-Za-z0-9_.]{0,63}$` に合う） |
| `manual()` / `ManualHandoff` | intent URL と注意書き | 足りた。2 つの Plugin で同じ実装（§4.2） |
| `PublishInput` / `PublishResult` | 配信 | 足りた。`rotatedCredential` は使わない（§5.2） |
| **`PluginPublisherConflictError`（同じ provider は 1 Plugin）** | 入れ替え | **足りた。最初の実利用。** 同時に有効にできないことを Core が保証する（§7.2） |
| `PluginLogger` | フェーズ・status | 足りた |

**Core に足りないと感じたが、足さないもの**（§11 に残す）：

* **`validate()` に投稿の `status` が渡らない**（`SocialPostDraftView` に `status` が無い）。`sns-x-manual` は「予約（`scheduled`）の `auto` だけを断る」ことができず、
  **`auto` の下書きも断る**（§9.3 / §11 #1）
* **`/plugins` の「資格情報を受け取ります」が `credentialFields: []` の Plugin にも出る**（§7 / §11 #9）
* **Plugin 同士でコードを共有する口が無い**（§4.2）。複製とテストで足りた

### 9.1 `limits`

| Plugin | `limits` | 理由 |
| --- | --- | --- |
| `sns-x-manual` | **宣言しない** | `auto` は `validate()` が断り、`manual` は媒体を持てない（Core の f）。粗い上限を置く意味が無い |
| `sns-x-api` | **`{ mediaMax: 4 }`**。**`bodyMaxLength` を宣言しない** | 下 |

**`bodyMaxLength` を宣言しない（`035` §13 の骨子の `280` は採らない）。** `036` §9.2 の学びのとおり、Core は `post.body.length`（UTF-16）で数える。
X の数え方では **URL は長さによらず 23**（§6.1）なので、2,000 文字の URL を含む本文でも X は受ける。
**`String.length` に対して「必ず緩い側」になる有限の値が存在しない**（URL を何本含むかで上限が決まる）。
どの値を置いても X が受ける投稿を Core が 422 で弾く側に倒れうるので、**置かない**。
粗い上限は Core 自身の `POST_BODY_MAX_LENGTH`（10,000）が既に掛けており、厳密な判定は `validate()` が行う（§9.2）。

**`mediaMax: 4`** は X の画像の上限（§6.1）。Core が枚数を正確に数えるので `validate()` では数えない。**`mediaRequired` は宣言しない。**

### 9.2 `validate()`

**5 秒で打ち切られる。外部へ問い合わせない。同期で返す。例外を投げない。**
**本文に関する判定はすべて `x-text.ts` の `checkXText(post)` から来る**（2 つの Plugin で同じ関数。§4.2）。

| # | 検査 | 掛かる Plugin | `field` | 文言の趣旨 |
| --- | --- | --- | --- | --- |
| 1 | `deliveryMode === 'auto'` | **`sns-x-manual` だけ** | `deliveryMode` | §9.3 |
| 2 | `composeXText(post)` の重み付きの長さ ≤ **280** | 両方 | `body` | `X の本文は280（半角換算）以内にしてください（日本語・絵文字は1文字を2、URLは長さによらず23と数えます。link を指定した場合はそれも含みます）。いまは N です。` |
| 3 | `deliveryMode === 'manual'` のとき、`buildXIntentUrl(post)` の長さ ≤ **2048** | 両方 | `body` | `投稿画面の URL が長くなりすぎます。本文中の URL を短くしてください。` |
| 4 | `providerOptions` にキーがある | 両方 | `providerOptions.<key>` | `<key> は X では使いません。` |

* **2 は自動・手動とも同じ文字列を数える**（`composeXText`。`link` があれば `body + '\n' + link`）。自動なら `POST /2/tweets` の `text`、手動なら intent URL の `text` に入る文字列そのもの
* **3 が要る理由**：Core は `manual()` が返した URL を `isValidManualUrl`（2048 文字以内）で見て、長ければ**画面で `invalid_url`**（「Plugin が返した URL を開けません」）にする（`035` §6.6）。
  重み付きで 280 以内でも、**本文中の長い URL は 23 と数えられるのに、URL エンコード後の intent URL では全長が効く**。
  登録時に断らないと、**予約時刻に手動投稿待ちへ並んでから初めて開けないと分かる**（`035` §6.1.2 が最も避けたいこと）
* **`media` の枚数・`media[].url` の形・`alt` は見ない**（Core の `mediaMax` / `isValidMediaUrl`。`alt` は送らないので断らない。§6.10）
* **`providerOptions` はすべて断る**（`035` §13 の骨子にあった `replyTo` を受けない。§3.2）
* 複数の違反は**すべて**返す。`providerOptions` / `media` / `link` / `body` は**型を確かめてから触る**（外から来た任意の JSON）

### 9.3 無料版で `auto` を選んだときの扱い（決めたこと）

**`sns-x-manual` の `validate()` は `deliveryMode: 'auto'` を断る**（`field: 'deliveryMode'`）。

```text
X（無料版の配信 Plugin）は手動投稿だけに対応しています。deliveryMode に manual を指定してください。
自動で投稿するには、X API の契約と配信 Plugin「X配信（X API）」（sns-x-api）が必要です。
```

**断らないと何が起きるか。** `sns-x-manual` は `publish()` を持たないので、Core は `auto` の予約を断らずに受け付け、
ジョブが「配信 Plugin なし」として後ろへ送り、**約 24 時間後に `failed`** にする（`035` 裁定 #8 / #9）。
画面の Badge と Alert は出るが、**API で登録する外部アプリには 201 が返り、何も知らされないまま 24 時間後に失敗する。**
しかも Core の既定の `deliveryMode` は `'auto'` なので、**省略しただけでこの道に入る。**
無料版を選んだ利用者に「自動」は決して届かないので、**待たせる理由が無い。登録の時点で断るのが唯一「黙らない」形**である。

**`035` 裁定 #12 の R-6（`validate()` の掛かる範囲）の中で成り立つかを確かめた。**

| 場面 | Core が `validate()` を掛けるか | 結果 |
| --- | --- | --- |
| 作成（`POST /social/posts`）：`status` を問わず | 掛ける（§6.1.2 の m。作成は `status` を問わない） | **`auto` なら `draft` でも 422**。§11 #1 |
| 作成：冪等な再送（同じ `externalRef`） | 掛けない（§6.1.2 の d） | 既存を返す。**問題なし**（既存は既に検査を通っている） |
| 更新：`next.status === 'scheduled'`（予約・予約し直し・本文の修正） | 掛ける | `auto` のままなら 422。**`deliveryMode: 'manual'` を同じ要求に含めれば通る**（`next` で判定される） |
| 更新：`{ status: 'draft' }`（取りやめ） | **掛けない**（R-6） | **取りやめは必ず通る。** 出口を塞がない |
| 更新：`published` / `failed` への記録 | 掛けない | 通る |
| 配信直前の再検査（`035` §6.5.2.2） | **来ない** | `auto` の予約は `publish` が無いので a で飛ばされ、着手印も再検査も通らない |

* **R-6 の範囲で成り立つ。** 既にある行の出口（取りやめ・記録）は `validate()` を通らないので、この検査が行を閉じ込めることは無い
* **Plugin を入れ替えた直後に残った `auto` の予約**（有料版 → 無料版。§7.2）は、**予約し直す・本文を直すと 422** になり、`manual` への切り替えを促される。
  **何もしなければ約 24 時間で `failed`**（Core の規則のまま）。これは運用者が選んだ入れ替えの帰結で、Badge と Alert が知らせる
* **`validate()` に `status` が渡らない**（`SocialPostDraftView` は `status` を持たない）ので、「予約だけを断る」形は書けない。
  `auto` の下書きまで断るのは、Core の口の制約から来る代償である（§11 #1）

### 9.4 `x-text.ts`（2 つの Plugin で同じ内容）

```ts
/** X の本文の上限（重み付き）。 */
export const X_WEIGHTED_LENGTH_MAX = 280;
/** URL が数えられる長さ（t.co）。 */
export const X_URL_WEIGHT = 23;
/** Web Intent の宛先。 */
export const X_INTENT_BASE_URL = 'https://x.com/intent/tweet';
/** Core の isValidManualUrl（isValidExternalUrl）と同じ上限。Plugin は Core の定数を import しないので値を持つ。 */
export const MANUAL_URL_MAX_LENGTH = 2048;

/** 実際に X へ渡す本文。link があれば改行して末尾に足す。 */
export function composeXText(post: { body: unknown; link: unknown }): string;
/** X の数え方による重み付きの長さ。 */

/** 手動投稿の URL。 */

/** 手動投稿の注意書き。 */

/** validate() の 2 と 3（§9.2）。 */
export function checkXText(post: { body: unknown; link: unknown; deliveryMode: unknown }): PublisherValidationProblem[];
/** manual() の中身。 */

```

**重み付きの長さの数え方**（公開ドキュメントの規則に揃える。§6.1）：

1. 文字列を **NFC** に正規化する
2. `https?://` で始まり空白までの並びを URL とし（末尾の `.,;:!?)]」）` と全角の句読点は外す。`036` の `detectLinkFacets` と同じ規則）、**1 つにつき 23** と数えて取り除く
3. 残りを **`Intl.Segmenter` の grapheme** に分け、各 grapheme について
   * 絵文字（`\p{Extended_Pictographic}` または地域指示子を含む）なら **2**（ZWJ で繋いだ並びも 1 つで 2）
   * それ以外は、含まれる各コードポイントについて **U+0000–U+10FF / U+2000–U+200D / U+2010–U+201F / U+2032–U+2037 なら 1、それ以外は 2** を足す
     （公式の `twitter-text` の設定（v3）の重みの範囲。CJK は 2）
4. 合計が重み付きの長さ

* **`twitter-text` を依存に足さない。** Plugin は `@torifune/plugin-api` 以外を import しない（§4）。規則は短く、表で固定できる（#12）
* **食い違う方向を知っておく**：`twitter-text` は `https://` の無いドメイン（`example.com`）も URL として 23 と数える。本設計は数えない（§11 #3）
* `link` は Core が https だけを許す（`isValidExternalHttpsUrl`）ので、`composeXText` が足した `link` は必ず 23 と数えられる

**Web Intent の URL**：

```ts
buildXIntentUrl(post) === `${X_INTENT_BASE_URL}?text=${encodeURIComponent(composeXText(post))}`
```

* **`url=` の引数を使わず、`link` を `text` に入れる**（`035` §13 の骨子は `text=…&url=…`）。
  * `url=` を使うと、X の投稿画面が本文と URL を**どう繋ぐか**（区切りの文字）を X が決める。公開ドキュメントはそれを書いていない。
    **Torifune が数えた文字列（`composeXText`）と、画面に入る文字列を一致させる**には、自分で繋いで `text` に入れるしかない
  * 自動配信（`POST /2/tweets`）には `url` の項目が無く、どのみち本文に繋ぐ。**手動と自動で同じ文字列になる**（#10 が固定する）
* **宛先は `https://x.com/intent/tweet`**（`035` §13 の骨子は `https://x.com/intent/post`）。公開ドキュメントが示しているのは `/intent/tweet` である（§6.1、§11 #7）
* 返す URL は Core の `isValidManualUrl`（https・資格情報なし・2048 文字以内）に通る（#20）。長さは §9.2 の 3 で登録時に保証する
* **対になっていないサロゲート（`\ud800` など）で例外を投げない**（2026-09-23 に G1〜G3 の実装中に見つけて追記。#93）。
  API の JSON に `\ud800` と書けば本文に片割れが入り、`encodeURIComponent` は `URIError` を投げる。そのままだと `validate()` が例外になり、登録が 500 で返る
  * `checkXText` は本文（`composeXText` の結果）に片割れがあれば **`[{ field: 'body' }]`**（文言「本文に扱えない文字が含まれています。」）を返し、intent URL の長さ（§9.2 の 3）は数えない。**`auto` でも断る**（X へ送っても受け付けられない）
  * `buildXIntentUrl` は片割れを **U+FFFD に置き換えてから** `encodeURIComponent` に渡す。`manual()` は `validate()` を通っていない投稿でも呼ばれうる（provider の Publisher が無いうちに登録された予約）ので、そこでも投げない
  * 判定と置き換えは正規表現で書く（`String.prototype.isWellFormed` / `toWellFormed` は `tsconfig` の `lib`（ES2023）に型が無い）。正しい文字列には何もしないので、#17 の等式は変わらない

### 9.5 `manual()`

```ts
manual({ post }): ManualHandoff {
  return buildXManualHandoff(post);   // { url: buildXIntentUrl(post), note: X_MANUAL_NOTE }
}
```

* **`X_MANUAL_NOTE`**：`X の投稿画面が開きます。内容を確かめて投稿してください。画像を添える場合はその画面で添付してください。`
  * `035` §13 の骨子「画像は投稿画面で添付してください。」は、**手動投稿に `media` を付けられない**（Core の f が 422）ことと合わせると
    **「付けたはずの画像が落ちた」と読まれる**（`036` §9.4 の学び）。**「添える場合はその画面で」**にする
* **`store` を読まない・`await` しない・例外を投げない・`fetch` しない。** 2 秒で打ち切られ、1 画面で最大 50 行ぶん呼ばれる（ガイド §9）
* **`account` を使わない。** Web Intent はブラウザでログイン中のアカウントで開く。どのアカウントかを指定できない（`036` §9.4）
* **2 つの Plugin の `manual()` は同じ入力に同じ値を返す**（§4.2。#10）

### 9.7 `retryAfterMs`

R2 / R3 が 429 を返したとき、`x-rate-limit-reset`（UNIX 秒）を見る。

```text
retryAfterMs = Number(x-rate-limit-reset) * 1000 - now()
```

* ヘッダが無い・64 文字を超える・整数でない・結果が 0 以下 → **`retryAfterMs` を付けない**（Core の既定 1 → 2 → 4 → 8 分）
* **Core が 24 時間で切り詰める**（`035` §5.6.2）。Plugin 側で丸めない
* ヘッダの値は計算にだけ使い、**`reason` にもログにも載せない**
* `now()` は注入できる時計（§10.1）

### 9.8 `README.md`

**両方の README に書く**：

* 無料版と有料版の違い（§7.1 の表）と、**同時に有効にできない**こと
* **入れ替えの手順**（§7.2。無料 → 有料、有料 → 無料。順序を間違えたときに何が起きるか）
* 手動投稿の流れ：予約時刻に `/social` の「手動投稿待ち」に並ぶ → 「投稿画面を開く」→ X で送信 → 「投稿した」を押す
* **手動投稿には画像を付けられない**（投稿画面で添付する）。本文は重み付きで 280、`link` は本文の末尾に足される
* 導入は再ビルドと再起動を伴うこと

**`sns-x-manual` の README に書く**：`deliveryMode` を省略すると `auto` になり 422 で断られること（`manual` を明示する）

**`sns-x-api` の README に書く**：

* **X API は有料（従量課金）**で、クレジットの購入が要ること。**料金の数値は書かず**、X の料金表（§6.1 の URL）を見るよう案内する。
  **URL を含む投稿（`link` を指定した投稿を含む）は料金が高い**こと
* 4 値の取り方の概略（開発者向け画面でアプリを作る → 権限を **Read and write** にする → 自分のアカウントの Access Token と Secret を発行する。
  **権限を変えたら発行し直す**）。**OAuth 2.0 のトークンは使えない**こと
* 4 値に**有効期限は無い**が、X 側で取り消せば止まること。**サーバの時計がずれていると認証に失敗する**こと
* 画像は **Torifune が預からない**。`media[].url` は **インターネットから取得できる 5MB 以下の JPEG・PNG・WebP の https URL**。**GIF・動画は扱わない**。
  **`alt` は X へ送られない**
* 資格情報を入れるまでの猶予は**約 24 時間**（`035` 裁定 #9）

## 10. 受け入れ条件

**A = 単体（純関数・`fetch` / `now` / `nonce` を差し替えた publisher）、B = 結合（DB。Core のジョブを通す。`fetch` は偽物）、
C = API（結合）、D = 画面（E2E）、E = 静的検査。**

> **どの条件も実際の X を叩かない。** 口は `createXApiPublisher({ fetch, now, nonce })` である（§10.1）。
> **本物の `fetch` が外へ出たらテストが落ちる**ことを #92 が固定する。§10.9 の本物の `fetch` は**ループバックだけ**に当てる。
