### G1. Domain の純関数（DB 不要・独立）

#### T1. 点の集合から内訳を作る `breakdownFromPoints`

   要件 §7-2「ダッシュボードは変えない」は自動的に満たされる。T4 のあと `pnpm typecheck` で `null` の取りこぼしが無いことを確かめる
   （`ResolvedPeriod.range` を `DateRange | null` にしたので、`from` / `to` を直接使っていた箇所はすべて型で落ちる）
2. **プリセットの `to` を昨日にした瞬間に既存 E2E が壊れないか**（T4）。データを見る E2E は
   `todayUrl(siteId)` ＝ `period=custom&from=今日&to=今日` を使っており影響を受けない（確認済み）。
   影響しうるのは (a) 既定 `30d` で概要を開くテスト（数字を見ていない）、(b) `?period=7d` の選択状態（数字を見ていない）。
   **落ちたら「テストの前提が設計のどこと食い違うか」を報告して止まる。E2E の期待値を勝手に緩めない**
3. **#63 の E2E は 1 分周期のロールアップと競合する。** `collect` して `?period=7d` を開くまでの間に定期ロールアップが走ると、
   `pending.total` が 0 になり `pending-rollup` ではなく `receiving`（0 が並ぶ通常タブ）になる。
   既存 #57 と同じく `.or()` で許容し、**決定的な担保は `not-tracked.test.ts` のユニット（§7.5 の 4 通り）で取る**
4. **`statement_timeout` が実際に発火することは決定的に検査できない。** 行数依存で、小さな scratch DB では必ず間に合う。
   検査するのは (a) 渡さなければ設定しない（静的）、(b) `SET LOCAL` がプールへ漏れない（結合）、
   (c) 例外時に縮退する（#37、`vi.spyOn` で `mockRejectedValue`）の 3 つ。
   「時間切れの再現」を作り込むテスト（大量行の投入や `pg_sleep`）は入れない
5. **`aggregateDailyBreakdown` の `siteId` は `sql` テンプレートの中で書く。** 既存の `siteCondition` は
   `ExpressionBuilder<Schema, 'analytics'>` を取る Kysely の関数で、素の SQL テンプレートからは使えない。
   **UUID の判定（`UUID_PATTERN`）を共有し、条件だけ SQL 片として組む**。UUID でなければどの行にも当たらない条件に落とす（#23）
6. **#61（今日が月の 1 日）を E2E で決定的に作れない。** 実行日が 1 日でなければ再現できない。
   `presetRange('month', '2026-09-01') === null` は #5 のユニットで、空状態の解決は `analytics-query.test.ts` の
   `range === null` で決定的に担保する。E2E は `?period=month` が 500 にならないことだけを見る（§8 #14）
7. **T9 → T10 の順序で typecheck が一時的に落ちる。** `perDay` を `{...} | null` にすると `visitors-tab.tsx` の
   `data.perDay.value` が落ちる。**T9 の中で両ファイルを同時に直し、`page.tsx` は確定期間の値を渡したまま変えない**
   （当日の分岐は T10）。T9 と T10 の間でコミットは切ってよいが、`pnpm typecheck` は T9 の時点で通す
8. **`Alert` の `tone` は `info`（設計 §7.4.3 / §7.5.1）。** `AlertTone` に `neutral` は無く、
   2026-09-05 の改訂で設計書側が `info` に直っている（§8 #4）。`info` の `role` は `status` なので、
   既存の `getByRole('alert')`（Bot の警告 ＝ `danger`）と衝突しない。
   逆に `role` からは `info` / `success` / `warning` を見分けられないので、#77 / #86 は静的検査を併せる（§8 #18）
9. **当日バナーの「約 {intervalMinutes} 分ごと」の出どころ**は `getAnalyticsStatus` の `status.rollup.intervalMinutes`。
   すでに `page.tsx` が読んでいるので追加の問い合わせは要らない
10. **`getTodayAnalytics` は `access_logs` を読む 8 番目の経路ではない。** 読むのは `aggregateDailyBreakdown` のままなので、
    `analytics-repository.test.ts` の `ALLOWED_ACCESS_LOG_READERS`（7 つ）は**増やさない**。
    増やす必要が出たら設計違反として止まる
11. **性能の実測（設計 §11.1 の宿題）**。T5 のあと `EXPLAIN ANALYZE` で `siteId` あり / なしを比べ、
    `access_logs_site_time_idx` が入口になっていることを確かめる。**見積りと大きく食い違ったら実装を進めず報告する**
12. **SaaS 固有機能への踏み込み：無し。** テナント・課金・コンテナ管理・デプロイ基盤に関わるタスクは 1 つも無い。
    当日の集計は 1 インスタンス内の 1 サイトに閉じており、`TorifuneHub` の都合はコード・文書のどちらにも書かない
13. **公開リポジトリである。** コミットメッセージ・コードコメント・設計書のいずれにも、
    特定の導入環境を指す記述（ホスト・構成・運用インシデントの経緯）を書かない。
    `要件.md` §1 は「029 より前の版では集計が外部 cron 任せになる」という**製品側の事実**だけを残し、
    どの環境で起きたかは書かない
