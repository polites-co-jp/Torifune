# 030 アナリティクスの「当日」表示と前日までの確定値 設計

`要件.md` の裁定（2026-09-05）を具体化する。裁定そのものは蒸し返さない。
`要件.md` §6 の「設計で決めること」4 点は、本設計で案を確定させた（§13 に一覧）。

## 1. 目的

アナリティクス画面に、**いまこの瞬間の、まだ確定していない本日の値**を出す。
同時に、既存のタブ（概要 / ページ / 参照元 / 訪問者）から本日を外し、
そこに出ているのが**前日までの確定値**であることを画面上で分かるようにする。

解くのは次の 2 つ。どちらも `029-scheduled-jobs` の定期ロールアップが正常に動いていても残る。

* **進行中の日を前日までと同じ折れ線・同じ合計に混ぜると、必ず低く見える。**
  午前 10 時の本日は、集計が正しくても「急落」に見え、前期間比も本日の分だけ目減りする
* **最大 15 分の遅れがある。** 計測タグを貼った直後の確認では「入っていない」ように見える

「本日が 0 で描かれる」という報告の直接原因（`029` を含むデプロイが届いていなかったこと）は
本設計の対象ではない。それが解決した後に残る上の 2 点だけを扱う。

## 3. スコープ

### やること

* 期間に `today`（「当日」）を足す。URL は `?period=today`
* 「当日」の値を、`access_logs` を**その日 1 日・そのサイト 1 件**で集計して出す
* 既存プリセット（`7d` / `30d` / `90d` / `month`）の `to` を**昨日**にする
* 「集計は前日まで。本日は『当日』で見る」と分かる表示を出す
* カスタム期間で今日を明示的に指定したときは、従来どおり今日を含める（集計値から）
* 受信状況（`029` §5.5）の判定の入力を、`to` が昨日になったことに合わせて直す
* 前日までの確定値が空で、今日のアクセスだけがある状態の見せ方を決める

### やらないこと

* **当日の集計結果を `analytics` へ書かない。** 画面の表示が DB 書き込みを起こす作りにしない（裁定 3.1）
* **参照 API（`GET /api/v1/analytics`）に `today` を足さない。** §6 に理由
* **ダッシュボード（`/dashboard`）は変えない。** 要件の対象はアナリティクス画面の 4 タブ。
  ダッシュボードは独自に「直近 7 日（今日を含む）」を組み立てており（`app/dashboard/page.tsx`）、
  `presetRange` を使っていないので本設計の変更は届かない
* **新しい Permission を作らない**（参照は既存の `analytics.read`）
* **マイグレーションを増やさない。** 既存の索引だけで足りる（§5 / §11）
* セッション定義・指標の定義を当日用に変えない（`028` §5.2 / §5.3.1 のまま。§13-2 に理由）
* 当日の値のキャッシュ・事前計算。「いまこの瞬間」が目的なので、要求のたびに集計する

### 4.1 「画面から生ログを集計しない」原則の例外である理由

`018` §4.1 / `028` §5.3 の原則の根拠は「**期間が延びるほど遅くなり、1 年分を見たら固まる**」ことにある。
「当日」は対象が

* **常に 1 日**（`from = to = 運用タイムゾーンの今日`）
* **常に 1 サイト**（画面が選択中のサイトだけ。§5.2 で SQL に絞り込みを足す）

に有界であり、この根拠に当たらない。原則を捨てるのではなく、**有界であることを型と引数で固定した例外**として扱う。
例外の範囲が広がらないよう、次を守る。

* 期間を引数で受ける UseCase にしない。`getTodayAnalytics` は `siteId` しか受けず、日付は自分で決める
* API へ露出しない（§6）
* Plugin へ露出しない（§10）

## 5. データモデル

**マイグレーションを増やさない。** 当日の値は保存せず、読むだけである。スキーマは変わらない。

### 5.1 使う索引と、当日 1 日分の集計の形

当日の集計は既存の `aggregateDailyBreakdown` を `from = to = 今日` で呼ぶ。関わる索引は次の 3 つ。

| 索引 | 定義 | 当日の集計での役割 |
| --- | --- | --- |
| `access_logs_site_time_idx` | `(site_id, occurred_at DESC)`（`014_analytics.sql`） | **`siteId` を足したときの入口。** 「このサイトの今日」だけを範囲で取り出す |
| `access_logs_occurred_at_idx` | `(occurred_at)`（`014_analytics.sql`） | `siteId` を足さない場合の入口（＝ロールアップの現行経路） |
| `access_logs_visitor_idx` | `(site_id, visitor_hash, occurred_at)`（`020_analytics_breakdown.sql`） | **当日の経路では使われない**（下記） |

`access_logs_visitor_idx` が効かない理由を明記しておく。SQL の窓関数は
`PARTITION BY site_id, day, visitor_hash ORDER BY occurred_at, id` で並べるが、

* `day` は `(occurred_at AT TIME ZONE tz)::date` という**計算列**であり、索引の列順（`site_id, visitor_hash, occurred_at`）と一致しない
* `logs` CTE は `human` と `bots` から 2 回参照されるため PostgreSQL は materialize する。
  materialize された中間結果に索引順は残らない

したがって当日の経路は「範囲取り出し 1 回 → 中間結果の並べ替え 1 回（窓関数）→ ハッシュ集約 10 数回」になる。
`access_logs_visitor_idx` はロールアップでも同じ理由で効いていないが、**落とさない**
（診断や将来の絞り込みに使える可能性があり、本設計で判断する話ではない）。

### 5.2 `aggregateDailyBreakdown` の引数を広げる（SQL の本体は変えない）

```
aggregateDailyBreakdown(connection, {
  from, to, timeZone,
  siteId?: string | null,        // 追加。null / 省略は全サイト（ロールアップの現行動作）
  statementTimeoutMs?: number,   // 追加。省略なら設定しない（ロールアップの現行動作）
})
```

* `siteId` を渡したときだけ `logs` CTE の `WHERE` に `site_id = ?` を足す。
  **UUID でない値は既存の `siteCondition` と同じく「どの行にも当たらない条件」にする**（キャストエラーで 500 にしない）
* 窓関数のパーティションは元から `site_id` を含むので、絞っても値は変わらない
* **ロールアップは引数を渡さない。** 既存の呼び出し（`rollupAnalytics`）は 1 文字も変わらない
* `statementTimeoutMs` を渡したときだけ、同じセッションで `SET LOCAL statement_timeout` を設定した
  トランザクション内で実行する（§11）

「新しい集計 SQL を増やさない」という裁定 3.1 の条件は満たす。増えるのは絞り込み 1 条件と実行の器だけで、
指標の定義・セッションの定義・出力の規則は 1 箇所のまま（当日とロールアップで食い違わないことの保証でもある）。

### 5.3 当日の点は保存しない

`replaceCorePoints` / `putPoint` を呼ばない。`analytics` に書かない。
`sites.analytics_last_seen_at` も更新しない（`touchLastSeen` を呼ばない）。
**画面の表示が DB 書き込みを起こす作りにしない**（裁定 3.1）。
最終受信の表示は従来どおり `findLatestAccessAt`（生ログ 1 行）から出す。

## 6. API

**参照 API は変更しない。** `GET /api/v1/analytics` に `period=today` 相当を足さない。

理由：

* 生ログを直接集計する例外は、有界であることを保証できる経路にだけ開く。
  API に開くと、外部から任意の頻度で重い集計を起こせる口になる（画面は人の操作 1 回につき 1 度）
* API の利用者が要るのは確定値である。ロールアップは既定 15 分間隔で回っており、
  当日分も最大 15 分遅れで `GET /api/v1/analytics` から読める（`029` §6.2）
* `05_API設計.md` §20 / §33 の応答形（`analytics` の集計値）を変えずに済む

`POST /api/v1/analytics/rollup` も変更しない。

## 7. 画面

### 7.1 期間の選択（`028` §7.3.1 / §7.3.2 の改訂）

#### 7.1.1 URL パラメータ

| 名前 | 値 | 既定 / 不正時 |
| --- | --- | --- |
| `period` | **`today`** / `7d` / `30d` / `90d` / `month` / `prev-month` / `custom` | `30d`。未知の値も `30d`（現行どおり）。`period` が無く `from` / `to` があれば `custom`（現行どおり） |
| `from` / `to` | `YYYY-MM-DD` | `custom` のときだけ読む（現行どおり）。**今日を指定できる**（裁定 3.3） |

その他のパラメータ（`siteId` / `tab` / `bots` / `page`）は変更しない。

プリセットの計算（`domain/analytics/day.ts`。`today` は引数で受ける。**`yesterday = today − 1`**）：

| preset | from | to | 変更 |
| --- | --- | --- | --- |
| `7d` | `today − 7` | `yesterday` | **変更**（末尾が昨日。長さ 7 日は不変） |
| `30d` | `today − 30` | `yesterday` | **変更**（長さ 30 日は不変） |
| `90d` | `today − 90` | `yesterday` | **変更**（長さ 90 日は不変） |
| `month` | 今月 1 日 | `yesterday` | **変更**。今日が 1 日のときは `null`（§7.2） |
| `prev-month` | 前月 1 日 | 前月末日 | 変更なし |

**長さを保つ。** `7d` を `[today−6, yesterday]`（6 日）にはしない。`7日` と書いてあるものが 6 日分になると、
前期間比の分母も 6 日になり、期間の意味が変わる。

`today`（当日）は `presetRange` の対象にしない。範囲は `from = to = 今日` で、値は集計値ではなく生ログから出す。

#### 7.1.2 `today` を `PeriodPreset` に入れない

**型の扱い**：

* `domain/analytics/day.ts` の `PeriodPreset` / `PERIOD_PRESETS` / `isPeriodPreset` は
  **`'7d' | '30d' | '90d' | 'month' | 'prev-month'` のまま**。`today` を入れない
* `ui/analytics/labels.ts` の `AnalyticsPeriod` を `PeriodPreset | 'today' | 'custom'` に広げる。
  `today` は `custom` と同じく「プリセットの範囲計算では表せない期間の選び方」である
* 期間セグメントの並び `ANALYTICS_PERIODS` は 6 個のまま（`today` を入れない）。
  `TODAY_PERIOD = 'today'` と `PERIOD_LABEL.today = '当日'` を足す

**理由**：`PeriodPreset` は「`presetRange(preset, today)` で `DateRange` が求まるもの」という契約を持つ。
`today` はそこに入れると `presetRange` が「確定値ではない別経路のデータ」を指す範囲を返すことになり、
契約が崩れる。裁定 3.2 の「見た目上は今の項目と分けたグループ」とも、型の扱いが一致する。

#### 7.1.3 「当日」ボタンの実現手段

既存の `SegmentedControl`（`ui/components/segmented-control.tsx`）を**もう 1 つ置く**。新しい部品は作らない。

```text
[SegmentedControl: 当日]  [SegmentedControl: 7日 30日 90日 今月 前月 カスタム]  [from] – [to]
```

* 左の `SegmentedControl` は項目 1 つ（`{ key: 'today', label: '当日', href }`）、`label="当日"`、`current={query.period}`
* 右の `SegmentedControl` は現行のまま、`current={query.period}`。
  `SegmentedControl` は `active = item.key === current` で選択を決めるので、
  `period === 'today'` のときは**どの項目も選択状態にならない**（裁定 3.2）。部品側の変更は要らない
* 期間セグメントを押せば `period` がそのプリセットになり、「当日」から抜ける（裁定 3.2）
* 2 つは別の `<nav>` になるので、支援技術からも別グループとして読める

#### 7.1.4 日付入力（開始日 / 終了日）の見せ方 ＝ 無効化しない（`要件.md` §6-4 の答え）

**`disabled` にしない。** `period === 'today'` のときは値に今日／今日を入れて表示し、
触ったら現行どおり `period=custom` へ抜ける。

理由：

* 「触ったら custom」は既存の規則（`028` §7.3.1）。当日だけ例外にすると規則が 2 つになる
* 無効化すると「なぜ押せないのか」の説明が要る。押せる方が説明が要らない
* 当日は今日 1 日なので、日付欄に今日／今日を出すのは嘘ではなく、当日が指す範囲の明示になる
* 裁定 3.3 の逃げ道（カスタムで今日を明示）と地続きになる。
  「当日 → 日付欄を触る → 今日を含む custom」という道が自然につながる

**当日（`period=today`）とカスタムの今日（`period=custom&from=to=今日`）は値が違いうる。**
前者は生ログ、後者は集計値（最大 15 分遅れ）である。これは意図した違いなので、
**今日を含むカスタム期間のときだけ**注記を出す（§7.4）。

### 7.2 `month` が今月 1 日に空になる問題（境界値）

`to` を昨日にすると、**今日が月の 1 日のとき `month` は `from = 今月 1 日 > to = 前月末日`** となり、
範囲が逆転する。そのまま `listAnalytics` に渡すと `isValidRange` に落ちて `ValidationError` になり、
画面が 500 で落ちる。

**`presetRange` の戻り値を `DateRange | null` にする。**
`null` は「このプリセットに、確定値のある期間が存在しない」を表す。`null` を返すのは `month` の 1 日だけ。

* 画面は `null` を受けたら**集計を一切行わず**、`EmptyState` を出す：
  「今月の確定値はまだありません。前日までの集計が 1 日分もありません。」
  * ボタン「当日を見る」（`?period=today`）と、「前月」への導線を添える
* **前月へ倒さない。**「今月」というラベルで前月を見せるのは嘘になる
* **`to = from`（今日 1 日）に丸めない。** その日は未確定で、確定値の期間としては空になる

`7d` / `30d` / `90d` は `from = today − N` で必ず `from ≤ yesterday` になるので、`null` にならない。
`prev-month` も変わらない。

**空状態は `analytics-view.tsx` から named export した部品として描く。**
`StaleRangeNotice`（§7.5.1）と同じ要領で、`AnalyticsView` の中に JSX を直書きしない。

```
// ui/analytics/analytics-view.tsx
export function EmptyPeriodNotice(props: {
  readonly todayHref: string;          // ?period=today
  readonly previousMonthHref: string;  // ?period=prev-month
}): JSX.Element
```

`AnalyticsView` は `tab.kind === 'empty-period'` のときにこれを 1 つ置くだけにする。
**理由**：空状態が出るのは月の 1 日だけで、画面全体を組み上げるテストでは
実行日が 1 日のときしか通らない（検証レポート §3.1 #61）。部品として単独で描画できれば、
実行日に依らず決定的に確かめられる。

**他の状態との優先順位**（画面が上から順に判定する）：

| 順 | 条件 | 出すもの |
| --- | --- | --- |
| 1 | 確定期間が求まらない（`range === null`。月の 1 日の `month`） | `EmptyPeriodNotice`（この節） |
| 2 | `notTrackedState !== null` かつ `tab !== 'settings'` | 導線（`not-tracked.tsx`。§7.5） |
| 3 | それ以外 | 通常のタブ（＋条件が揃えば §7.5.1 の案内） |

**月の 1 日 × 一度も受信していないサイト**は 1 が勝ち、`not-received` の導線は出ない。
集計する期間そのものが存在しない以上、「集計を待つ」という説明が成り立たないため。
サイトに計測タグを貼る導線は、翌日以降か「当日」から辿れる（`EmptyPeriodNotice` の
「当日を見る」→ そこで `not-received` の導線が出る）。

### 7.3 当日タブの中身（`028` §7.3.6 との差分）

**タブ（概要 / ページ / 参照元 / 訪問者 / 設定）は増やさない**（裁定 3.2）。
`period === 'today'` のとき、同じ 4 タブが本日の実測値を出す。

| 区画 | 当日での扱い |
| --- | --- |
| 概要の Stat × 5 | 出す。**前期間比は出さない**（§13-1） |
| 概要「日次の推移」カード | **出さない。** 1 日の折れ線に意味が無い。`OverviewData.daily` を `null` にし、`null` のときカードを描かない |
| 概要の時間帯別 PV | 出す。**当日はここが「推移」の役割を担う**（`pageviews_hour`） |
| 概要のデバイス / 上位ページ / 参照元 | 出す |
| ページタブ / 参照元タブ | 出す（表・Pagination とも）。並び順と 1 ページの件数は確定期間と同じ |
| 訪問者タブの「1 日あたり訪問者」 | **出さない**（`VisitorsData.perDay` を `null` 可にする）。1 日しかないので「訪問者」と同じ数になり、同じ数が 2 枚並ぶ |
| 訪問者タブの「Bot のアクセス」 | 出す。「最も多かった日」は当日 1 日なので今日になる（値としては正しい） |
| 設定タブ | 期間に依存しない。変更なし |

**「Bot を集計に含める」スイッチは当日でも同じ規則で効く**（`028` §7.3.4）。
当日の点にも `bot_pageviews` / `bot_visitors` が含まれるため、計算規則を分けなくてよい。

### 7.4 「確定値ではない」ことの表示

#### 7.4.1 ヘッダ行（`analytics-view.tsx`）

現行は常に「前期間（… 〜 …）と比較 · 日付の区切りは {timeZone}」を出している。期間ごとに出し分ける。

| 期間 | ヘッダ行 |
| --- | --- |
| `today` | 「**当日 · {YYYY-MM-DD HH:mm} 時点の速報値** · 日付の区切りは {timeZone}」 |
| 当期が今日を含まない（`7d` / `30d` / `90d` / `month` / **`prev-month`** / 今日を含まない `custom`） | 「前期間（… 〜 …）と比較 · **集計は前日まで** · 日付の区切りは {timeZone}」 |
| 当期が今日を含む（`custom` のみ。裁定 3.3） | 「前期間（… 〜 …）と比較 · 日付の区切りは {timeZone}」 |

**出し分けの基準は「当期が今日を含むか」だけである**（`rangeIncludesToday`）。プリセットの種類では分けない。

「集計は前日まで」は**この画面全体の集計の規則**を述べたもので、当期の `to` が昨日であるという意味ではない。
`prev-month`（`to` は前月末）にも出るが、「本日は集計対象に入っていない。本日は『当日』で見る」という
裁定 3.3 の趣旨は `prev-month` でも同じであり、誤りではない。期間そのものは同じ行の
「前期間（… 〜 …）」と日付欄で示している。**条件を `prev-month` だけ特別扱いしない**
（分岐が増えるほど、どの期間で何が出るかを説明できなくなる）。

`{HH:mm}` は `getTodayAnalytics` が返す `generatedAt` を `formatDateTimeInTimeZone` で整形した値。
**サーバーが集計した瞬間**であり、ブラウザの時計ではない。

#### 7.4.2 当日のバナー（`AnalyticsView` に 1 つ。4 タブ共通）

`period === 'today'` のとき、タブの上に注記を 1 つ出す。タブごとに書かない。

* 「この画面は確定値ではありません。集計は約 {intervalMinutes} 分ごとに確定します。」
* 「前日（{昨日の日付}）の確定値：ページビュー {n} · 訪問者 {m}」（§13-1 の並記）
* 今日のアクセスが 0 件のとき：「今日のアクセスはまだありません（最終受信 {…}）」を添える
* 集計を時間内に終えられなかったとき（§11）：`Alert tone="warning"`
  「当日の集計に時間がかかっています。前日までの確定値をご覧ください。」

#### 7.4.3 今日を含むカスタム期間の注記

`period === 'custom'` かつ `to >= 今日` のとき、`Alert tone="info"` の注記
（`AlertTone` は `'info' | 'success' | 'warning' | 'danger'` の 4 つ。`neutral` は無い。
`apps/web/src/ui/components/primitives.tsx`）：
「今日を含む期間です。今日の値は最後の集計（{最終集計の時刻}）までの分です。
いまの値は「当日」で見られます。」＋「当日を見る」リンク。

裁定 3.3 の「逃げ道を塞がない」を満たしつつ、値が古く見える理由を画面で説明する。

### 7.5 前日までが空で、今日だけアクセスがある状態（`要件.md` の重点）

計測を始めた初日、あるいは前日までのロールアップが一度も走っていない環境では、
`7d`（`to = 昨日`）が空になる。この状態を**「集計待ち」と誤って説明しない**。

`029` §7.1.3 の導線（`not-tracked.tsx`）に次を足す。

* `receivedToday: boolean` — 最終受信が運用タイムゾーンの今日か
  （`dateInTimeZone(lastReceivedAt, timeZone) === today`。**追加の問い合わせは要らない**）
* `todayHref: string | null` — 「当日」（`?period=today`）への導線。当期が既に当日なら `null`

| 状態 | `receivedToday` | 出す文言 |
| --- | --- | --- |
| `pending-rollup` | true | 「アクセスは届いていますが、**届いているのは今日の分です**。この期間（前日まで）の確定値はまだありません。今日の値は「当日」で見られます。」＋「当日を見る」リンク |
| `pending-rollup` | false | 現行どおり（「次回の集計は {HH:mm} 頃で、そのあとにこの画面へ数字が出ます。」） |
| `bots-only` | true | 現行の Bot の説明に「届いたアクセスは今日の分です。「当日」でも同じく Bot だけが見えます。」を足し、「当日を見る」リンクを添える |
| `not-received` | — | 現行どおり（変更なし。既存 E2E の locator を保つ） |

**`receivedToday` が真のとき「次回の集計のあとに数字が出ます」と書いてはならない。**
次の集計が走っても、今日の分は `7d`（末尾が昨日）には入らないので、その文は嘘になる。

#### 7.5.1 集計が済んだあとの同じ状態（`receiving` のときの案内）

上の表は `pending-rollup` / `bots-only`、すなわち**未集計の生ログが 1 件以上ある**状態しか扱えていない。
ところが定期ロールアップが走った直後は `pending.total === 0` になり、`diagnoseReception` は
`receiving` を返す。**計測タグを貼った初日の利用者はちょうどここを踏む**。

* 今日の生ログは集計され、`analytics` に本日の行がある
* しかし当期（`7d`。`to = 昨日`）には 1 行も無く、`currentPoints.length === 0`
* `receiving` なので導線（`not-tracked.tsx`）は出ず、**0 が並ぶだけの概要タブ**が出る

これは `要件.md` §2.2 の狙い（前日までであることを分かるようにする）に直結するので、ここで塞ぐ。

**これは受信状況の診断ではなく、`receiving` のときの表示の追加である。**
`diagnoseReception` の 4 状態と優先順位は変えない（§9.1 のとおり）。

**出す条件**（すべて満たすとき）：

| # | 条件 | 根拠 |
| --- | --- | --- |
| a | `period !== 'today'` | 当日を見ているのに当日への導線は出さない |
| b | `notTrackedState === null`（＝ `state === 'receiving'`） | 導線が出ているときはタブの中身ごと差し替わっている。**二重に出さない** |
| c | `currentPoints.length === 0`（当期の `key = ''` の点が 1 つも無い） | 数字が出ていないときだけ案内する |
| d | `receivedToday === true` | §7.5 で導入した判定と同じもの。`dateInTimeZone(status.lastReceivedAt, timeZone) === today`。`lastReceivedAt === null` なら偽（そのときは `not-received` の導線が出るので b でも落ちる） |
| e | `tab !== 'settings'` | 設定タブは期間に依存しない |
| f | **確定期間が求まる（`range !== null`）** | 月の 1 日の `month` では §7.2 の空状態だけを出す。導線が 2 つ並ばない |

**この 6 条件はすべて 1 つの述語 `shouldShowStaleRangeNotice` が持つ**（§12.3）。
`app/analytics/page.tsx` の分岐に散らさない。散らすと、どれか 1 つを取り違えても
画面全体を組み上げるテストでしか気づけない（検証レポート §3.1 #84）。

**追加の問い合わせを増やさない。** `status.lastReceivedAt` は `getAnalyticsStatus` が既に返しており、
`currentPoints` はどのタブでも読んでいる（受信状況の判定に使うため）。判定に必要な値は全部そろっている。

**出すもの**：`AnalyticsView` に 1 つ、タブの上に `Alert tone="info"`（§7.4.2 の当日バナーと同じ場所）。

* 「この期間（{from} 〜 {to}）の確定値はまだありません。**アクセスは今日届いています。**
  今日の分は「当日」で見られます。集計は前日までが対象です。」
* ＋ Button「当日を見る」（`?period=today`。`analyticsHref` で組む）

`AnalyticsView` に 1 つ置くので、概要・ページ・参照元・訪問者のどのタブでも同じ案内が出る。
タブごとに書かない（`028` §7.3.6 の各タブは「数を計算しない・並べるだけ」を保つ）。

**`month` が `null` の空状態（§7.2）と重なったとき ＝ §7.2 を優先し、この案内は出さない。**
理由は 2 つある。

1. §7.2 の空状態には既に「当日を見る」導線が含まれており、並べると同じ導線が 2 つ出る
2. `month` が `null` のとき画面は**集計を一切行わない**ので `currentPoints` 自体が無く、
   条件 c を評価できない

**この優先順位は条件 f として述語の中に置く。** §7.2 を優先するという判断は変えず、
それを担保する場所を `page.tsx` の分岐から `shouldShowStaleRangeNotice` へ移すだけである。
述語が `range === null` を自分で弾くので、呼び出し側の分岐の順序に依らず決まる。

### 7.6 当日で今日のアクセスが 0 件のとき

* `not-received`（一度も届いていない）のときだけ、従来どおり導線（`not-tracked.tsx`）を出す
* それ以外は**通常のタブを出す**。値はすべて 0、ランキングと表は空メッセージ、
  時間帯別は 24 本すべて 0。§7.4.2 のバナーに「今日のアクセスはまだありません」を添える
* **当日で `pending-rollup` / `bots-only` の導線を出さない**（§9 に理由）

## 8. 権限（Permission）

**新しい Permission を作らない。**

| 経路 | 要求 | 権限なし | 未認証 |
| --- | --- | --- | --- |
| `getTodayAnalytics`（UseCase 名 `analytics.today`） | `analytics.read` | `ForbiddenError`（API 経由なら 403） | `UnauthenticatedError`（API 経由なら 401） |
| `/analytics?period=today`（画面） | `analytics.read` | `AsyncState status="forbidden"`（現行と同じ。403 相当の表示） | `requirePageSession` が `/login` へリダイレクト（現行と同じ） |

認可は `defineUseCase` の `permission` で宣言し、UseCase が代わりに呼ぶ（`CLAUDE.md`「認可を書く場所」）。
画面側の `permissions.has('analytics.read')` は表示制御であって認可ではない（現行どおり）。

**`analytics.read` しか持たない利用者が、当日の集計で生ログを間接的に読むことになる**が、
返るのは既存の指標に畳んだ値だけで、生ログの行（パス・訪問者ハッシュ・参照元）そのものは返さない。
`path_pageviews` / `referrer` などの key は、ロールアップ後に同じ Permission で読める値と同一である。
露出は増えない。

### 9.0 帰結：Plugin が記録した「本日分」は、翌日まで画面のどこにも出ない

上の 2 つ目の箇条書きだけでは書き足りない。**プリセットの `to` が昨日へ動いた（§7.1.1）ことで、
Plugin が `metricDate = 今日` で入れた点は `7d` / `30d` / `90d` / `month` からも消える。**

| 経路 | 変更前 | 変更後 |
| --- | --- | --- |
| `7d` / `30d` / `90d` / `month`（`to = today` → `to = yesterday`） | 記録した直後に折れ線・合計へ載った | **載らない**（当期に今日が入っていない） |
| `today`（当日） | — | **出ない**（生ログだけを見るため。`analytics` を読まない） |
| `custom` で今日を明示（裁定 3.3） | 出る | **出る**（変わらない） |
| `prev-month` | 出ない（元から過去の期間） | 出ない |
| `GET /api/v1/analytics`（`from` / `to` を直接指定） | 出る | **出る**（API は変更しない。§6） |

つまり `analytics.record` で本日分を書いた Plugin 作者は、**既定の画面（`30d`）で自分の値を見つけられない**。
翌日になれば確定期間に入って表示される。**Plugin 作者は自分の Plugin の動作確認で必ずここを踏む**ので、
逃げ道（本日分をすぐ確かめるなら `?period=custom&from=今日&to=今日`、または `GET /api/v1/analytics`）を
`018-analytics/設計.md` §6「Plugin から」へ追記する（§16）。**`docs/仕様書/` は変更しない**
（Plugin API の契約は変わっておらず、仕様と矛盾しないため。§2）。

**破壊的変更ではない。**

* `PLUGIN_API_VERSION` は 1 のまま。`analytics.record` の引数・意味・成否は 1 つも変わらない
* 書いた値は失われない。`analytics` に入り、API からも翌日以降の画面からも読める
* 変わったのは**本体の画面が既定で見せる期間**であって、Plugin API の契約ではない
* 逃げ道が塞がっていない（上の表の 3 行目・6 行目）

`source <> 'core'` の値を当日タブへ混ぜて解決しない。混ぜると §13-3 の「当日は生ログだけ」という
1 文の規則が崩れ、二重計上の余地ができる。

### 9.1 受信状況（`029` §5.5）との整合 ＝ 出力は変えず、入力 1 つの意味を直す

`diagnoseReception` の**出力（4 状態）と判定の優先順位は変えない**。変えるのは入力 1 フィールドである。

```
ReceptionInput.periodIncludesToday   →   ReceptionInput.periodMayLackRollup
```

| 項目 | 現行 | 本設計 |
| --- | --- | --- |
| 意味 | 当期の `to` が今日以降か | 当期の末尾が、まだ集計が追いついていない可能性のある日に掛かるか |
| 呼び出し側が渡す値 | `resolved.to >= today` | `resolved.to >= yesterday` |

**改名する理由**：プリセットの `to` が昨日になると、`periodIncludesToday` は
プリセットでは**常に false** になる。すると「昨日届いたがまだ集計されていない」状態で
`pending-rollup` が二度と出なくなり、`029` が足した診断性が失われる。
`to >= 昨日` を `periodIncludesToday` という名前のフィールドに渡すのは嘘なので、
**判定の意図（集計が追いつく余地があるか）を表す名前に直す。** 規則の表（`029` §5.5）は
`periodIncludesToday` の行を `periodMayLackRollup` に読み替えるだけで、順序も結果も変わらない。

**当日（`period === 'today'`）での入力の作り方**：

| 入力 | 渡す値 | 理由 |
| --- | --- | --- |
| `lastReceivedAt` | 現行どおり（`findLatestAccessAt`） | 変えない |
| `pending` | 現行どおり | 変えない |
| `hasPointsInPeriod` | **当日の集計結果に点があるか**（`todayPoints.length > 0`） | `analytics` ではなく生ログ由来で判定する。生ログが 1 行でもあれば keyless 8 指標が 0 でも返るので、`length > 0` は「今日の生ログがある」と同値 |
| `periodMayLackRollup` | `true`（今日は常に未確定） | — |

**当日で導線を出すのは `not-received` のときだけ**にする（§7.6）。
「当日」は未集計の値を見るための期間なので、`pending-rollup`（届いているが未集計）を理由に
タブの中身を隠すのは矛盾する。届いていれば数字を出せばよい。
この出し分けは `app/analytics/page.tsx` の `notTrackedState` の決め方の話であり、
`diagnoseReception` の規則は変えない。

## 11. 性能

### 11.1 見積り

当日 1 日分・1 サイトの集計の作業量は、その日その サイトの生ログ行数 N でほぼ決まる。

1. `access_logs_site_time_idx` の範囲走査で N 行を取り出す
2. `logs` CTE を materialize（N 行）
3. 窓関数のための並べ替え 1 回（人のアクセス行、O(N log N)）
4. ハッシュ集約 10 数回（各 O(N)）

| N（1 日 1 サイトの PV） | 見込み | 判断 |
| --- | --- | --- |
| 〜 1 万 | 数 ms 〜 数十 ms | 問題なし |
| 〜 10 万 | 数十 ms 〜 数百 ms | 画面表示として許容 |
| 〜 100 万 | 秒オーダー。並べ替えが `work_mem` を超えるとディスクに落ちる | 遅いが表示はできる |
| 100 万超 | 数秒〜。ページ表示が体感で止まる | **許容しない** |

これは索引と処理の形からの見積りであり、実測ではない。実装時に `EXPLAIN ANALYZE` で確かめる
（実装プランの項目）。

`siteId` の絞り込みを足すのは、この見積りを「インスタンス全体の 1 日」から
「1 サイトの 1 日」へ落とすためである。サイトを 20 件持つインスタンスでは、これだけで 1 桁変わりうる。

### 11.2 上限は行数ではなく**時間**で掛ける

**行数の上限は設けない。** 上限を掛けるには先に行数を数える必要があり、
その数え上げ自体が同じ範囲の走査になる（`countAccessSince` は「新しい順に最大 1000 件」で
打ち切る形なので、「今日が 20 万件か 100 万件か」の判別には使えない）。
数えてから集計すると、遅い環境でコストが 2 回掛かる。

代わりに、**当日の集計にだけ `statement_timeout` を掛ける**（`TODAY_AGGREGATION_TIMEOUT_MS = 5000`）。

* `aggregateDailyBreakdown` は `statementTimeoutMs` を受けたときだけ、
  `connection.transaction` の中で `SET LOCAL statement_timeout` を設定してから SQL を流す
  （`SET LOCAL` はトランザクション終了で戻るので、プールされた接続に設定が残らない）
* **ロールアップは渡さない。** 定期実行は長く掛かってよい。現行の挙動は変わらない
* 打ち切られた場合、`getTodayAnalytics` は例外を**握り潰さずに `log.warn` へ残し**、
  `unavailable: true` と空の点を返す。画面は §7.4.2 の警告を出し、
  確定値の期間（前日まで）は従来どおり表示できる
* 環境変数を増やさない。値は定数で持つ（設定項目を増やすほどの判断材料が無い）

**縮退の方が安全である理由**：当日は「あると便利な速報値」であり、確定値は別経路（`analytics`）で
必ず見られる。当日の集計が重い環境で画面全体を止めるより、当日だけ諦める方が損害が小さい。

### 11.3 呼ぶ回数

* `getTodayAnalytics` は 1 画面につき **1 回**。4 タブが必要とする指標はすべて 1 回の結果に含まれる
  （keyless 8 指標 + `pageviews_hour` / `pageviews_device` / `landing` / `referrer` /
  `referrer_visitors` / `referrer_bounces` / `path_*`）。タブごとに引き直さない
* 当日では `listAnalytics` / `listAnalyticsBreakdown` を**呼ばない**（§13-3）。
  例外は前日確定値の並記（`listAnalytics` を昨日 1 日・`key = ''` で 1 回。§13-1）
* 内訳の合算・並べ替え・ページ送りはメモリ上で行う（1 日 1 サイト分なので有界）

## 12. 追加する関数の形

実装コードではなく、受け渡しの形を固定するための宣言。

### 12.1 Application（新規 UseCase）

```
// application/analytics/analytics-use-cases.ts
export interface TodayAnalytics {
  readonly date: string;                       // 運用タイムゾーンの今日（YYYY-MM-DD）
  readonly generatedAt: Date;                  // 集計した瞬間（サーバーの時計）
  readonly unavailable: boolean;               // 集計できなかった（打ち切り等）。true なら points は空
  readonly points: readonly AnalyticsPoint[];  // source は常に CORE_SOURCE
}

export const getTodayAnalytics: UseCase<{ readonly siteId: string }, TodayAnalytics>
// name: 'analytics.today' / permission: 'analytics.read' / audit: なし（参照系）
```

処理：

1. `timeZone = analyticsTimeZone()` / `date = todayInTimeZone(timeZone)`
2. `analyticsRepository.aggregateDailyBreakdown(connection, { from: date, to: date, timeZone, siteId, statementTimeoutMs })`
3. `DailyBreakdownRow`（`siteId` / `metricDate` / `metric` / `key` / `value`）を
   `AnalyticsPoint`（＋ `source: CORE_SOURCE`）へ写す。**指標も値も変換しない**
4. 例外は `log.warn` に残して `{ unavailable: true, points: [] }` を返す

**変換をここに置く理由**：`DailyBreakdownRow` はロールアップの中間結果という Infrastructure の都合の型で、
`AnalyticsPoint` は Domain の読み取りモデルである。両者の橋渡しは Application の仕事であり、
これを画面に置くと Presentation が Infrastructure の型を知ることになる。
写した後は、既存の `summarize` / `summarizeDaily` / `botShare` / `deviceRows` が**そのまま使える**
（確定期間と当日で、数の出し方が 1 箇所に保たれる）。

### 12.2 Domain（新規の純関数）

```
// domain/analytics/summary.ts
export function breakdownFromPoints(
  points: readonly AnalyticsPoint[],
  metric: string,
): readonly BreakdownItem[];
```

* 指定した `metric` の点を `key` ごとに合算する（`key === ''` は含めない）
* 並び順は **`value` 降順、同値なら `key` 昇順** ＝ Repository の `sumByKey`
  （`ORDER BY sum(value) DESC, key ASC`）と一致させる。
  当日と確定期間で行の順番が変わらないようにするため
* 出所（`source`）はまたいで合算する（現行の内訳と同じ規則）
* 空配列・未知の指標・全部 0 を通す

ページ送りは、この結果を画面側で `total = 件数` としてスライスする（`domain` に持ち込まない）。
スライスは §12.3 の純関数が担う。

### 12.3 Presentation（純粋モジュール `ui/analytics/analytics-query.ts`）

`resolvePeriod` / `analyticsHref` と同じ、**React も I/O も持たないモジュール**に置く。
`app/analytics/page.tsx` の中に算術と条件を直書きしない。

```
// ui/analytics/analytics-query.ts
export function pageSlice<T>(
  items: readonly T[],
  page: number,
  perPage: number,
): { readonly items: readonly T[]; readonly total: number };
```

* `page` は **1 起点**。`total` は**スライス前の全件数**（`listAnalyticsBreakdown` の
  `meta.total` と同じ意味。ページ送りの総ページ数がここから出る）
* 取り出す範囲は `[(page − 1) × perPage, page × perPage)`
* 範囲外のページ（`page` が大きすぎる）は `items` が空、`total` はそのまま
* 防御：`page < 1` は 1 として扱う。`perPage <= 0` は `items` を空にする
  （`parsePage` が 1 以上を保証しているが、関数単体でも壊れない形にする）

**`domain/` に置かない理由**：ページ送りは画面の都合（1 ページ 50 件）であって、
分析データの意味ではない。Domain にページ送りの語彙を入れると、
「Domain は表示の都合を知らない」という境界が 1 つ崩れる。
`breakdownFromPoints`（合算と並び順＝データの意味）と `pageSlice`（切り出し＝表示の都合）は、
意図的に別の層に置く。

**切り出す理由**：現状のスライスは `page.tsx` のクロージャの中の算術で、
オフセットを取り違えても全テストが通る（検証レポート §3.1 #58）。
純関数にすれば「51 件目が 2 ページ目の先頭に来る」を単体で固定できる。

```
export function shouldShowStaleRangeNotice(input: {
  readonly period: AnalyticsPeriod;
  readonly notTracked: NotTrackedState | null;
  readonly currentPointCount: number;
  readonly receivedToday: boolean;
  readonly tab: AnalyticsTab;
  readonly hasConfirmedRange: boolean;   // resolvePeriod().range !== null（条件 f）
}): boolean;
```

§7.5.1 の 6 条件（a〜f）をすべてこの述語が持つ。**同期関数にしておく。**
I/O を持てない形にすることで、判定のために問い合わせが増えないことを構造で保証する（#85）。

## 13. `要件.md` §6 で裁定していない 4 点の決定

### 13-1. 「当日」の前期間比 ＝ **比較を出さない。代わりに前日の確定値を並記する**

* 概要タブと訪問者タブの `Stat` に `delta` を渡さない（`Stat` の `delta` は元から任意）。
  矢印も `—` も出ない（`—` は「比を出せない」の意味で使っているが、
  当日は「比べていない」であって「比べたが出せない」ではない）
* 代わりに §7.4.2 のバナーへ「前日（{日付}）の確定値：ページビュー {n} · 訪問者 {m}」を出す

**「昨日の同じ時刻まで」を採らない理由**：

1. **新しい集計 SQL が要る。** `aggregateDailyBreakdown` は日単位でしか切れない。
   時刻で切るには別の SQL が必要で、「新しい集計 SQL を増やさない」という裁定 3.1 の根拠が崩れる
2. **コストが 2 倍になる。** 当日 1 日に加えて昨日 1 日を生ログから集計することになり、
   §11 の見積りがそのまま倍になる
3. **比が跳ねる。** 15 分ごとに時刻の境目が動くので、更新のたびに前期間比が変わる。
   「増えたのか減ったのか」を読むための指標が、読むたびに変わる
4. **確定値と比べられない。** 昨日の同じ時刻までの値は `analytics`（日次の確定値）に無い。
   画面のどこにも根拠が出せない数字になる

前日の確定値の並記は、この 4 つのどれにも当たらない（`listAnalytics` を昨日 1 日で 1 回呼ぶだけ）。
「今日はいまのところ n、昨日は 1 日で m だった」という読み方ができれば、目的（進み具合の把握）は足りる。

### 13-2. 当日の `sessions` / `bounces` / 平均滞在 ＝ **同じ定義のまま出し、偏りを注記する**

補正しない。除外しない。ロールアップと**同一の定義**（`028` §5.3.1、30 分区切り）で出す。

**理由**：`要件.md` §4 の受け入れ条件に「当日の値が、ロールアップ済みの本日分と食い違わない
（同じ生ログから同じ定義で出す）」とある。進行中セッションを除外したり直帰の数え方を変えたりすると、
15 分後にロールアップが `analytics` へ書く本日分と食い違い、この条件を破る。
「30 分以内に始まったセッションを除く」案は、計測タグを貼った直後の確認
（`要件.md` §1 のもう 1 つの動機）でちょうど 0 件になるという致命的な副作用がある。

**代わりに注記で担保する。** 当日タブの直帰率と平均滞在時間の `Stat` に `note`（`Stat` の既存の props）：

* 直帰率：「進行中のセッションを含むため、確定後より高めに出ます。」
* 平均滞在時間：「セッション最後のページは測れないため、実際より短めに出ます。進行中のセッションを含む当日はその差が大きく出ます。」
  （後段は `028` §7.3.6 の既存の注記と同じ趣旨。当日ぶんを足す）

### 13-3. `analytics` に本日の集計値が既にある場合 ＝ **当日は生ログだけを見る。集計値は読まない**

* 当日タブは `listAnalytics` / `listAnalyticsBreakdown` を呼ばない（前日確定値の並記を除く）
* `analytics` に本日の行があっても**足さない・混ぜない・優先しない**

**理由**：

1. **二重計上を構造的に起こせなくする。** 足せば必ず 2 倍になる。「新しい方を採る」規則にすると、
   指標ごと・key ごとに出所が変わり、同じ画面の中で数の出どころが揃わなくなる
2. **生ログの方が常に新しく、常に正しい。** `analytics` の本日行はその生ログから作られたもので、
   生ログの部分集合に対する集計である。新しい方を選ぶ規則は、常に生ログを選ぶ
3. **説明できる。** 「当日 = 生ログ、それ以外 = 確定した集計値」は 1 文で言い切れる

**帰結として明記すること**：Plugin が `analytics.record` で本日分に入れた値（`source <> 'core'`）は
当日タブに出ない（§9）。確定期間では従来どおり合算される。§7.4.2 のバナーで説明する。

### 13-4. 当日での日付入力 ＝ **無効化せず、今日／今日を表示して操作も許す**（§7.1.4 に詳細）

## 14. 受け入れ条件

テストコードに 1 対 1 で落とせる粒度で書く。括弧内は想定するテストの層。

### 期間プリセット（Domain 純関数 `presetRange` / `previousRange`）

1. `presetRange('7d', '2026-09-05')` が `{ from: '2026-08-29', to: '2026-09-04' }`（末尾が昨日、長さ 7 日）
2. `presetRange('30d', '2026-09-05')` が `{ from: '2026-08-06', to: '2026-09-04' }`（長さ 30 日）
3. `presetRange('90d', '2026-09-05')` が `{ from: '2026-06-07', to: '2026-09-04' }`（長さ 90 日）
4. `presetRange('month', '2026-09-05')` が `{ from: '2026-09-01', to: '2026-09-04' }`
5. **`presetRange('month', '2026-09-01')` が `null`**（今日が月の 1 日。確定値のある期間が無い）
6. `presetRange('prev-month', '2026-09-05')` が `{ from: '2026-08-01', to: '2026-08-31' }`（変更なし）
7. `presetRange('prev-month', '2026-03-01')` が `{ from: '2026-02-01', to: '2026-02-28' }`（閏年でない 2 月。変更なし）
8. `presetRange('7d', '2026-01-01')` が `{ from: '2025-12-25', to: '2025-12-31' }`（年をまたぐ）
9. `presetRange('7d', '2026-03-01')` が `{ from: '2026-02-22', to: '2026-02-28' }`（月末をまたぐ）
10. `previousRange` は変更しない。`previousRange('2026-08-29', '2026-09-04')` が `{ from: '2026-08-22', to: '2026-08-28' }`（`7d` の前期間が 7 日で連続する）
11. `PeriodPreset` に `'today'` は含まれない。`isPeriodPreset('today')` が `false`

### 内訳の純関数（Domain `breakdownFromPoints`）

12. 同じ `metric` / 同じ `key` の点が複数の出所にあるとき、合算した 1 行になる
13. 並び順が `value` 降順。同値なら `key` 昇順（`sumByKey` の SQL と一致する）
14. 指定した `metric` 以外の点を含めない
15. `key === ''` の点を含めない
16. 空配列を渡すと空配列。未知の `metric` を渡しても落ちず空配列
17. すべての値が 0 の点しか無いとき、行は出るが値は 0（並び順は `key` 昇順）

### 受信状況（Domain `diagnoseReception`）

18. `ReceptionInput` のフィールド名が `periodMayLackRollup`（`periodIncludesToday` は無い）
19. 4 状態と優先順位は `029` §5.5 と同一（`lastReceivedAt === null` → `not-received`、
    `hasPointsInPeriod` → `receiving`、`!periodMayLackRollup` → `receiving`、
    `pending.total === 0` → `receiving`、`pending.bots === pending.total` → `bots-only`、それ以外 → `pending-rollup`）
20. `periodMayLackRollup: false` かつ `pending.total > 0` で `receiving`（過去の期間に「集計待ち」を出さない）

### 当日の集計（Infrastructure `aggregateDailyBreakdown`、結合テスト）

21. `siteId` を渡すと、そのサイトの行だけが返る（別サイトの生ログは 1 行も混ざらない）
22. `siteId` を渡さない（省略 / `null`）と、現行どおり全サイトの行が返る（ロールアップの経路が変わらない）
23. `siteId` に UUID でない文字列を渡すと、**例外にならず空配列**が返る
24. `from = to = 今日` で呼んだ結果が、同じ生ログに対して `rollupAnalytics` が `analytics` へ書く
    本日分の行と、`metric` / `key` / `value` のすべてで一致する（**同じ定義であることの担保**）
25. その日の生ログが 1 行も無いサイトでは、空配列が返る（0 行の指標も作らない）
26. その日の生ログが 1 行でもあれば、`key = ''` の 8 指標が値 0 でも返る
27. 運用タイムゾーンの日の境目で切られる（`TORIFUNE_TIMEZONE=Asia/Tokyo` のとき、
    UTC で前日 23:00 の生ログが「今日」に入る）
28. `statementTimeoutMs` を渡さない呼び出しでは `statement_timeout` を設定しない（ロールアップが影響を受けない）

### 当日の UseCase（Application `getTodayAnalytics`）

29. `analytics.read` を持つ主体が呼ぶと成功し、`date` が運用タイムゾーンの今日
30. **`analytics.read` を持たない主体が呼ぶと `ForbiddenError`**（API 経由なら 403）
31. **未認証で呼ぶと `UnauthenticatedError`**（API 経由なら 401）
32. 返る点の `source` がすべて `CORE_SOURCE`、`metricDate` がすべて `date` と等しい
33. `analytics` に本日の集計値が 1 行も無い状態でも、生ログから値が出る（`要件.md` §4 の 1 つ目）
34. `analytics` に本日の集計値が**既にある**状態でも、返る値は生ログの集計だけで、集計値を足していない
35. `source <> 'core'` の本日の点（Plugin が入れた値）が結果に含まれない
36. 生ログが 1 件も無い日でも例外にならず、`points` が空・`unavailable` が `false`
37. Repository が例外を投げたとき、UseCase は例外を伝播せず `unavailable: true` と空の `points` を返し、
    警告ログを 1 件残す
38. `getTodayAnalytics` の結果を `summarize` に渡した値が、同じ生ログを `rollupAnalytics` で
    集計した後に `listAnalytics` → `summarize` で出した値と一致する（`要件.md` §4 の 2 つ目）

### URL とクエリの解決（Presentation `resolvePeriod` / `analyticsHref`）

39. `?period=today` が `period: 'today'`、`from = to = 運用タイムゾーンの今日` に解決される
40. `?period=today` のとき `previousRange` を使わない（前期間を計算しない）
41. 未知の `period`（例 `?period=tommorow`）は現行どおり `30d`
42. `period` が無く `from` / `to` があれば現行どおり `custom`
43. `?period=custom&from=今日&to=今日` は `custom` のまま解決され、今日を含む（裁定 3.3）
44. `?period=custom` の不正（形式・逆転・400 日超）は現行どおり警告 + `30d`（変更なし）
45. `analyticsHref({ period: 'today', ... })` が `period=today` を含む URL を返す
46. `analyticsHref` は `period: '30d'` のとき現行どおり `period` を書かない（既定の短い URL を保つ）
47. 当日から期間セグメントを押した URL に `period=today` が残らない

### 画面（Presentation / E2E）

48. **「当日」ボタンが期間セグメントの左に、別のグループ（別の `nav`）として出る**（`要件.md` §4）
49. `?period=today` のとき「当日」が選択状態（`aria-current="page"`）で、
    期間セグメントの 6 項目は**どれも選択状態でない**
50. 期間セグメントを押すと「当日」が非選択になる
51. `?period=7d` で「7日」が選択状態（現行の E2E を保つ）
52. `?period=today` で、**確定値ではないことと、いつ時点かが表示される**（`YYYY-MM-DD HH:mm` 時点の速報値）
53. `?period=today` で、前日の確定値（ページビュー・訪問者）が並記される
54. `?period=today` で、概要タブに前期間比（`+…%` / `−…%` / `—`）が出ない
55. `?period=today` で、概要タブに「日次の推移」カードが出ない
56. `?period=today` で、訪問者タブに「1 日あたり訪問者」が出ない
57. `?period=today` で、直帰率と平均滞在時間に偏りの注記が出る
58. `?period=today` で、ページタブ・参照元タブの表が本日の値で出る。ページ送りは
    `pageSlice`（§12.3）で検証する：**51 件の内訳で 1 ページ目に 1〜50 件目、
    2 ページ目の先頭が 51 件目**（オフセットを 1 つ取り違えたら落ちる）、
    範囲外のページは空で `total` は 51、`page < 1` は 1 ページ目、`perPage <= 0` は空

60. 既存の期間で「集計は前日まで」と分かる表示が出る（裁定 3.3）
61. **今日が月の 1 日のとき `?period=month` が 500 にならず**、「今月の確定値はまだありません」と
    「当日を見る」導線が出る（§7.2）。空状態の描画は `EmptyPeriodNotice`（named export）を
    単体で描いて確かめる：文言・「当日を見る」の遷移先が `?period=today`・
    「前月を見る」の遷移先が `?period=prev-month`。**実行日に依らず通ること**
62. `?period=custom` で今日を含む期間を指定すると、今日を含む集計値が出て、
    「いまの値は『当日』で見られます」の注記が出る
63. 今日だけ生ログがあり前日までの確定値が無い状態で `?period=7d` を開くと、
    「届いているのは今日の分です」と「当日を見る」導線が出る（「次回の集計のあとに数字が出ます」は出ない）
64. 一度も受信していないサイトでは、当日でも現行どおり「計測タグ未設置」の導線が出る（既存 E2E の locator を保つ）
65. 今日の生ログが 0 件で過去には受信があるサイトを `?period=today` で開くと、
    導線ではなく通常のタブが出て、値がすべて 0、「今日のアクセスはまだありません」が出る
66. `?period=today&bots=1` で Bot を含めた値になる（`028` §7.3.4 の規則が当日でも同じに効く）
67. `analytics.read` を持たない利用者が `/analytics?period=today` を開くと、現行どおり forbidden の表示
68. 未認証で `/analytics?period=today` を開くと、現行どおり `/login` へリダイレクト
69. 存在しない `siteId` / UUID でない `siteId` は現行どおり 404

### 書き込みが起きないこと

70. `?period=today` の画面表示の前後で、`analytics` の行数・内容が変わらない（裁定 3.1）
71. `?period=today` の画面表示で `sites.analytics_last_seen_at` が更新されない

### 既存の振る舞いを壊さないこと

72. `rollupAnalytics` の挙動が変わらない（全サイト対象、`statement_timeout` 無し、書き込む行も同じ）
73. ダッシュボード（`/dashboard`）の期間と数値が変わらない
74. `GET /api/v1/analytics` の要求・応答が変わらない（`period` を受け付けない）
75. `PLUGIN_API_VERSION` が変わらない

### 確定期間が空で本日に受信がある状態の案内（§7.5.1）

76. **未集計が 0 件（`pending.total === 0`。定期ロールアップが走った直後）で、当期の集計値が 0 件、
    かつ最終受信が今日**のとき、`?period=7d` に「この期間の確定値はまだありません」の案内と
    「当日を見る」導線が出る（`diagnoseReception` は `receiving` を返している）
77. 同じ状態で、案内の `Alert` の `tone` が `info`（`AlertTone` に `neutral` は無い）
78. 最終受信が**昨日以前**のとき、当期の集計値が 0 件でもこの案内は出ない
79. 最終受信が `null`（一度も受信していない）のとき、この案内は出ず、
    現行どおり `not-received` の導線が出る
80. 当期に集計値が 1 件でもあるとき（`currentPoints.length > 0`）、この案内は出ない
81. **`?period=today` ではこの案内が出ない**（当日を見ているのに当日への導線を出さない）
82. **`not-tracked` の導線が出ている状態（`pending-rollup` / `bots-only` / `not-received`）では、
    この案内が出ない**（導線と案内が二重に出ない）
83. 設定タブ（`?tab=settings`）ではこの案内が出ない
84. 今日が月の 1 日で `?period=month` のとき、出るのは §7.2 の空状態だけで、
    この案内は出ない（「当日を見る」導線が 2 つ並ばない）。判定は `shouldShowStaleRangeNotice` に
    `hasConfirmedRange: false` を渡して確かめる（他の 5 条件をすべて満たしていても `false` になる。
    §12.3）。**実行日に依らず通ること**
85. この案内の判定のために、DB への問い合わせが 1 つも増えない
    （`getAnalyticsStatus` の `lastReceivedAt` と、既に読んでいる当期の点だけで判定する）
86. §7.4.3 の「今日を含むカスタム期間」の注記も `tone="info"` で出る

## 15. 未決事項

| # | 論点 | 本設計での扱い |
| --- | --- | --- |
| 1 | `statement_timeout` は PostgreSQL 固有である。別の Database Provider が差し替わったとき、`SET LOCAL statement_timeout` が通らない可能性がある | 許容する。`analytics-repository.ts` は既に `AT TIME ZONE` / `to_char` / 窓関数など PostgreSQL 固有の SQL で書かれており（`02` §7 が Repository に SQL を置くと定めている）、新しい依存を増やしてはいない。Provider の契約に実行時間の上限を持たせる話は、`029` 未決 #11（`DatabaseProvider` の契約）と同じ場所で扱うべき別の設計 |
| 2 | 打ち切り（`unavailable`）の原因が「重すぎる」なのか「SQL のバグ」なのかを画面から区別できない | 画面には出さない。区別が要るのは運用者であり、`log.warn` に例外の内容が残る。画面に SQL の失敗理由を出さない方針（`029` §6.1.7）に合わせる |
| 3 | 訪問者タブの「Bot のアクセス」の「最も多かった日」は、当日では常に今日になる | そのままにする。値としては正しく、欄ごと消すと確定期間と当日で区画の数が変わる |
| 4 | `7d` の名前と範囲（`[today−7, yesterday]`）は「直近 7 日」と読めるが、「今日を含む 7 日」と思っている利用者には 1 日ずれて見える | 期間の表示（`YYYY-MM-DD 〜 YYYY-MM-DD`）とヘッダの「集計は前日まで」で示す。ラベルは変えない（`7日` のまま） |
| 5 | 当日の値は要求のたびに集計するので、同じ画面を短時間に何度も開くと同じ集計が繰り返される | 今回はキャッシュを入れない。「いまこの瞬間」が目的であり、1 日 1 サイトに有界なコストである。頻度が問題になる規模が観測されたら、短い TTL のメモリキャッシュを別途設計する |
| 6 | 複数サイトを一度に見る「全サイト合算の当日」は無い（`siteId` 必須） | 入れない。画面は元から 1 サイトずつであり（`028` §7.3.2）、合算は有界性の根拠（1 サイト 1 日）を崩す |
| 7 | **`aggregateDailyBreakdown` を外側トランザクションの中から `statementTimeoutMs` つきで呼ぶと、`SET LOCAL statement_timeout` が外側トランザクション全体に掛かる。** 接続の解決は既にトランザクション内なら外側に参加するため、5 秒の上限がロールアップなど無関係な処理まで巻き込みうる | **現状は到達不能**（`statementTimeoutMs` を渡す呼び出しは `getTodayAnalytics` 1 箇所で、トランザクションの外から呼んでいる）。今回は防御コードを足さず、**メソッドの doc に「`statementTimeoutMs` を渡すときはトランザクションの外から呼ぶこと」と、その理由を書く**。呼び出しが増えるときに気づける形にしておく。実行時に検知するには「いまトランザクション内か」を `Connection` から問える必要があり、`DatabaseProvider` の契約変更（`029` 未決 #11 と同じ場所）になる |
| 8 | `statement_timeout` の値の組み立ては、`NaN` を渡すと `SET LOCAL statement_timeout = NaN` という SQL になる | **現状は到達不能**（渡すのは定数 1 つだけで、外部入力が届く経路が無い）。検証も足さない。防御を足すなら値を受け取る口を広げたときで、そのときは受け入れ条件も併せて足す |
