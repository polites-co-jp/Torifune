# 030 アナリティクスの「当日」表示と前日までの確定値 — 要件と裁定

設計書（`設計.md`）を書くための入力。「折れ線に本日の日付があるのに 0 になる」事象の
調査結果と、ユーザーが裁定した方針をまとめる。
**この裁定は決定事項であり、設計書はこれに従う。**

## 1. 背景と事実（2026-09-05）

運用中の環境のアナリティクス画面で、**本日の日付が折れ線グラフにあるのに値が 0** になり、
「本日データは無視され、日をまたいでから集計される仕様」に見える、という報告があった。

調査した事実は次のとおり。

1. **本日は無視されていない。** `analytics.rollup` ジョブは `to = 今日` を対象に 15 分ごとに回る
   （`application/jobs/definitions.ts` の `scheduledRange` と `ROLLUP_JOB.intervalMs`）。
   029-scheduled-jobs で入った仕組みで、本日分は最大 15 分遅れで集計値になる
2. **報告は 029 より前の版で運用されていた環境から来ている。** 029 より前はロールアップが
   `POST /api/v1/analytics/rollup` を叩いたときだけ走るため、外部 cron の実行間隔が
   そのまま「集計されるタイミング」になる。夜間に 1 回だけ流していれば、
   「日をまたいでから集計される」ように見える
3. **0 に見えるのは「記録の無い日は 0 で埋める」ため**（`ui/analytics/overview-tab.tsx` の
   `OverviewData.daily`）。まだ一度も集計されていない本日は、欠損ではなく 0 として描かれる

つまり報告の直接原因は 029 が入っていないことであり、029 が動けば本日分は出る。
ただし **029 が動いても次の 2 点は残る**。これが本要件の対象である。

* **進行中の日を前日までと同じ折れ線・同じ合計に混ぜると、必ず低く見える。**
  午前 10 時の本日は、集計が正常でも「急落」に見え、前期間比も本日の分だけ目減りする
* **最大 15 分の遅れがある。** 計測タグを貼った直後の確認では「入っていない」ように見える

## 2. やってほしいこと

### 2.1 「当日」を追加する

いまこの瞬間の、**まだ確定していない（fix していない）本日のデータ**を見られるようにする。

### 2.2 既存の表示から本日を除き、前日までであることを強調する

「当日」があるなら、概要・ページ・参照元・訪問者の各タブは本日を含めず、
「ここに出ているのは前日までの確定値である」と分かる表示にする。

## 3. 裁定（2026-09-05）

### 3.1 「当日」のデータ源 — 生ログを当日分だけ直接集計する

`access_logs` を `from = to = 今日` で集計し、いまこの瞬間の値を出す。

* `application/analytics/rollup.ts` の **「画面から生ログを集計しない」原則に対する、明示的な例外**とする
* 例外を認める理由：原則の根拠は「期間が延びるほど遅くなり、1 年分を見たら固まる」ことにある。
  「当日」は対象が **常に 1 日**で有界であり、この根拠に当たらない
* 既存の `analyticsRepository.aggregateDailyBreakdown` をそのまま 1 日分で呼べるため、
  新しい集計 SQL を増やさずに済む
* **集計結果を `analytics` へ書かない。** 画面の表示が DB 書き込みを起こす作りにしない

### 3.2 「当日」は期間セレクタの左に、別グループのボタンとして置く

**タブバー（概要 / ページ / 参照元 / 訪問者 / 設定）には足さない。**
期間のセグメント（`7日` / `30日` / `90日` / `今月` / `前月` / `カスタム`）の **左**に、
**見た目上は今の項目と分けたグループ**として `当日` ボタンを置く。

* すなわち `当日` は**タブではなく期間の一種**である（URL は `?period=today` を想定）。
  選ぶと既存のタブ（概要 / ページ / 参照元 / 訪問者）はそのまま使え、中身が本日の実測値になる
* `当日` を選んでいる間は、期間セグメントのどれも選択状態にならない。
  期間セグメントを押せば `当日` から抜ける

### 3.3 既存タブは期間の `to` を昨日にする

* `7d` / `30d` / `90d` / `month` のプリセットが「昨日まで」を指すようにする
* グラフ・表・統計・前期間比のすべてが前日までで揃う
* 画面に「集計は前日まで。本日は『当日』で見る」と分かる表示を出す
* **カスタム期間で利用者が明示的に今日を指定したときだけ、今日を含める。**
  逃げ道を塞がない

### 3.4 進め方

* 030 として `/feature` の流れ（設計 → 実装プラン → テスト → 実装 → 検証）を通す
* ブランチ `feature/030-analytics-today`

## 4. 受け入れ条件の骨子

設計書の「10. 受け入れ条件」はこれを具体化する。

* 「当日」が、`analytics` に本日の集計値が 1 行も無い状態でも、生ログから値を出す
* 「当日」の値が、ロールアップ済みの本日分と食い違わない（同じ生ログから同じ定義で出す）
* 「当日」に、その値が確定値ではないことと、いつ時点かが表示される
* 「当日」ボタンが期間セグメントの左に、別グループとして出る
* プリセット期間（`7d` / `30d` / `90d` / `month`）の `to` が昨日になる
* カスタム期間で今日を指定した場合は今日を含む
* 既存の期間のグラフに本日の点が現れない
* 権限なし（`analytics.read` を持たない）で 403、未認証で 401
* 生ログが 1 件も無い日でも落ちない（0 件の「当日」が正しく空表示になる）

## 5. 制約

* **新しい Permission を作らない。** 参照は既存の `analytics.read`
* Domain 層は DB 製品に依存しない。集計 SQL は `infrastructure/analytics-repository.ts` に置く
  （02_データベース設計.md §7）
* 1 日の境目は運用タイムゾーン（`application/analytics/timezone.ts`）で決める。
  「当日」・既存の期間・ロールアップが同じ境目を使う
* マイグレーションを増やさない（本要件はスキーマ変更を必要としない）
* 公開リポジトリである。TorifuneHub 側の事情を設計書に書かない

## 6. 設計で決めること（裁定していない）

次は設計書で案を示し、承認を受けてから実装へ進む。

1. **「当日」を選んだときの前期間比。** 進行中の本日と、確定した昨日 1 日を比べると必ず低く出る。
   「比較を出さない」「昨日の同じ時刻までと比べる」のどちらか
2. **「当日」の `sessions` / `bounces` / 平均滞在の扱い。** セッションは 30 分区切りで組むため、
   まだ終わっていないセッションが末尾に残る。直帰率が実際より高く出る恐れがある
3. **`analytics` に本日の集計値が既にある場合の扱い。** 裁定 3.1 は生ログを見ると決めたが、
   集計値と生ログが併存する状態でどちらを出すかを明示する
4. **「当日」を選んでいるときの日付入力（開始日・終了日）の見せ方。**
   期間セグメントと同じく非選択にするのか、無効化するのか

## 7. 設計後の追加裁定（2026-09-05）

`設計.md` を受けて確認した事項。**これも決定事項であり、実装プラン以降はこれに従う。**

1. **`要件.md` §6 の 4 点は、`設計.md` §13 の決定をそのまま採る**
   （前期間比は出さず前日の確定値を並記 / セッション・直帰率・滞在は補正せず注記 /
   当日は生ログだけを見る / 日付入力は無効化しない）。
2. **ダッシュボード（`/dashboard`）は今回変えない。** 「直近 7 日」は今日を含んだまま。
   ダッシュボードは `presetRange` を使わず自前で範囲を組んでおり、本設計の変更は届かない。
   結果として当面「ダッシュボードは今日を含む進行中の値／アナリティクスは前日まで」と割れるが、
   揃えるかどうかは別件として扱う（`設計.md` §3「やらないこと」のとおり）。
3. **今日が月の 1 日のとき `month` は空状態を出す**（`設計.md` §7.2）。
   前月へ自動で倒さない。その日だけ今日を含める例外も作らない。
