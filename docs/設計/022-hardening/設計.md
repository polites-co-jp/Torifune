## 3. 決めたこと

### 3.1 監査ログは2本立てにする

`auth_audit_logs`（既存）はそのまま**認証・認可のセキュリティログ**として残し、
**一般API操作の監査は新しい `audit_logs` へ**書く。

| テーブル | 根拠 | 記録するもの |
| --- | --- | --- |
| `auth_audit_logs` | `04_認証設計.md` §26 セキュリティログ | ログイン・ログアウト・パスワード・ロール変更 |
| `audit_logs` | `05_API設計.md` §42 Audit Log | リソースの作成・更新・削除、Plugin の導入・有効化 |

**1本にまとめない。** まとめるには適用済みの `auth_audit_logs` を作り替える必要があり、
`02_データベース設計.md` §10.1 の「適用済みのファイルは書き換えない」に反する。
また2つは読み手が違う（前者は侵害調査、後者は操作の追跡）。
イベント名の集合を共有すると、片方の都合でもう片方が歪む。

`audit_logs` は「誰が・何に・何をしたか」を持つ。

```text
audit_logs
  id, actor_user_id, action, resource_type, resource_id, detail, ip_address, user_agent, occurred_at
```

`detail` のサニタイズは `sanitizeAuditDetail` を共用する。
**規約ではなく機械で落とす**という既存の判断を変えない。

### 3.2 Rate Limit は `defineRoute` の既定にする

各ルートへ手で足すと必ず抜ける（`api/route.ts` の「各ルートで手順を並べると、
いつか1つ抜ける」と同じ理屈）。**既定で全ルートにかけ、外すときだけ明示する。**

* 既定：IP ＋ operationId ごとに 300回/分
* 認証系など厳しくしたいものは、これまでどおり `rateLimit` で上書き
* 意図的に外す場合は `rateLimit: 'none'`（理由をコメントに書く）

既定値は「まともな利用では絶対に当たらないが、総当たりと大量取得は止まる」水準。
一覧APIの大量取得（`05` §36 の重点対象）はこれで塞がる。

> **限界を明記する**：実装はインメモリ・単一プロセス前提のまま。
> 複数プロセスで動かすと上限がプロセス数倍になる。
> 共有ストアが要る規模になったら差し替える。今はその規模ではない。

### 3.3 CSP・HSTS・Preflight は `middleware.ts` に集約する

3つとも「すべてのリクエストに対して同じことをする」処理で、
置き場所が同じになる。ルートごとに書くと抜ける。

* **Preflight**：`/api/` への `OPTIONS` を middleware が返す。
  許可 Origin のときだけ `Allow-Methods` / `Allow-Headers` / `Max-Age` を返す。
  許可していない Origin には CORS ヘッダを付けない（404 ではなく 204 を返し、
  ヘッダの有無で判断させる）
* **CSP**：nonce 方式。middleware が nonce を生成し、
  `Content-Security-Policy` と `x-nonce` に載せる。
  Next.js は CSP ヘッダの nonce を自分の inline script へ引き継ぐ
* **HSTS**：HTTPS で受けたときだけ付ける。
  HTTP で付けても意味が無く、開発環境（http://localhost）を壊す

**`unsafe-inline` をスクリプトに許さない。** 許すと CSP を入れる意味がほぼ無い。
スタイルは Next.js と Tailwind が inline style を使うため `unsafe-inline` を許す。
`style-src` の `unsafe-inline` は XSS の主要経路ではない。

### 3.4 Plugin の名前空間は「囲い」で与える

完全な隔離（iframe / Shadow DOM）は採らない。Plugin は本体と同じ React ツリーで
動くことが前提で（`06` §20-21）、隔離すると共通コンポーネントも
Extension Point も使えなくなる。**隔離のために拡張性を捨てることになる。**

代わりに、

* 本体が Plugin の描画を `data-torifune-plugin="<id>"` の要素で囲む
* Plugin 作者向けに、その属性へ閉じたセレクタを書くための
  クラス名ヘルパを公開 API に足す（`pluginClassName(pluginId, name)`）
* 「Plugin は信頼されたコード」という前提（`CLAUDE.md`）は変えない。
  これは事故を減らす仕組みであって、悪意を止める仕組みではない。
  **そう明記する。**

### 3.5 高権限 Plugin の警告は「何ができるか」で出す

権限コードを並べても、読む人は危険度を判断できない。
`system.manage` と `extensions: ['database' | 'authentication']` を
**高権限として区別し、日本語の説明と警告を出す**。

## 5. ロギング基盤

```ts
export type LogLevel = 'debug' | 'info' | 'warn' | 'error';
export interface Logger {
  log(level: LogLevel, message: string, fields?: Record<string, unknown>): void;
}
```

* 出力は1行のJSON。集約基盤で扱えることを優先する
* **`maskSecrets` を通す。** `plugin/logger.ts` が既に同じことをしており、
  そちらを共通実装へ寄せる
* 差し替え可能にする（`setLogger`）。テストで出力を捕まえるため
* `console.*` を直接呼ぶことを ESLint で禁止する。
  禁止しないと、また直接呼ばれる

## 6. やらないこと

* 監査ログの画面（`06` §16 の一般タブに載せる話は `015b-settings`）
* 監査ログの保持期間・ローテーション（運用の話。文書だけ書く）
* Rate Limit の共有ストア（§3.2 の限界に書いたとおり）
* Plugin の完全な隔離（§3.4）

## 7. 受け入れ条件

1. `x-csrf-token` を伴うクロスオリジン更新がプリフライトを通る
2. 許可していない Origin のプリフライトに CORS ヘッダを返さない
3. 一覧APIで既定の Rate Limit がかかり、超過で429と `Retry-After` を返す
4. サイト削除・Plugin導入が `audit_logs` に残り、Secret が混ざらない
5. CSP と HSTS が応答ヘッダに出る。CSP 違反でアプリが壊れない（E2E が通る）
6. HTTP では HSTS を付けない
7. `console.*` の直接呼び出しが ESLint で止まる
8. 2つの Plugin が同名クラスを使っても互いの描画を壊さない
9. 高権限を要求する Plugin の導入前に、警告と日本語の説明が出る
