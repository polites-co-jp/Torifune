### #8 について

受け入れ条件の書き方が実装と合っていなかった。

**「壊さない」ことは、いまの構成では保証できない。** Plugin は本体と同じ
React ツリー・同じ DOM で動くことが前提で（`06_画面設計.md` §20-21）、
CSS の衝突を機構として防ぐには iframe か Shadow DOM が要る。
それを入れると共通コンポーネントも Extension Point も使えなくなり、
**隔離のために拡張性を捨てる**ことになる。

そこで設計 §3.4 のとおり「囲いを与える」に留めた。

* 本体が Plugin の描画を `[data-torifune-plugin="<id>"]` で囲う
* Plugin 作者がそこへ閉じたセレクタを書くための `pluginScope()` /
  `pluginClassName()` を公開 API に足した

**これは事故を減らす仕組みであって、悪意を止める仕組みではない。**
そう明記した（`packages/plugin-api/src/scope.ts`、設計 §3.4）。
「Plugin は信頼されたコード」という前提（`CLAUDE.md`）は変えていない。

## 残る限界（意図的に残したもの）

1. **Rate Limit はインメモリ・単一プロセス前提のまま。**
   複数プロセスで動かすと上限がプロセス数倍になる。
   設計 §3.2 に明記した。共有ストアが要る規模になったら
   `RateLimiter` のまま差し替える。

2. **監査ログは操作と原子的ではない。**
   `defineUseCase` の handler 成功後、同じトランザクションの外で記録する。
   原子的にするには各 UseCase のトランザクション内で呼ぶ必要があり、
   それは「書き忘れられる」形になる。**忘れられる危険のほうが大きい**と判断した
   （設計 §3.1、`application/audit.ts` のコメント）。
   記録に失敗しても操作の応答は変えず、error ログに残す。

3. **`style-src` に `unsafe-inline` を許している。**
   Next.js と Tailwind がインライン style を使うため。
   `script-src` は許していない。

4. **監査ログの画面と保持期間は範囲外。**
   画面は `015b-settings`、保持期間は運用の話として文書のみ。

## 後から見つかった欠陥（2026-09-01、`019-notification` 中に発覚）

**CSP が、静的に生成されるページを壊していた。**

静的生成のHTMLには nonce が焼き込まれないのに、応答ヘッダには
リクエストごとの新しい nonce が載る。そのページのスクリプトだけが
全部ブロックされ、**画面は出るのに操作できない**状態になる。

下記の E2E 124件は**これを検出できなかった**。当時静的だったのは
`/logout` と `/password-reset` の2つだけで、`/logout` は JS を要さず、
`/password-reset` にはまだテストが無かった。

`019-notification` で直した（同スプリントの検証レポート参照）。

* `middleware.ts` がリクエスト側にも `Content-Security-Policy` を載せる
* ルートレイアウトで `export const dynamic = 'force-dynamic'`

**教訓**：「表示される」ことだけを確かめる E2E は、この壊れ方を通す。
操作できるところまで見る。
