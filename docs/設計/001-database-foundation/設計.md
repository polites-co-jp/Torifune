# データベース基盤 設計

## 1. 目的

Torifune の全機能が乗るデータ永続化の土台を作る。

解決したいことは3つ。

1. **Domain 層が特定のDB製品を知らないままデータを扱えるようにする。**
   これができていないと、後から Database Provider を差し替えられなくなる
2. **スキーマ変更を再現可能な手順として管理する。**
   本番で直接 DDL を打つ運用に落ちないようにする
3. **空のデータベースへ Torifune のスキーマを適用する手段を、アプリケーションの外から呼べる形で提供する。**
   単体構成でも初期化に必要であり、外部のプロビジョニング処理からも使える

## 3. スコープ

### やること

* Database Provider Interface と PostgreSQL 実装
* 接続の生成・破棄・ヘルスチェック
* トランザクション境界の仕組み（Application 層が制御する）
* Repository Interface（Domain）と実装（Infrastructure）の分割規約
* マイグレーションランナー（連番SQL、`schema_migrations`、advisory lock、冪等）
* `migrations/001_initial.sql`（認証・認可に必要なテーブル）
* `torifune migrate` CLI

### やらないこと

* 認証・認可のロジック本体（`002-authentication` / `003-authorization`）
* Secret の暗号化（`006-secret-storage`）。本設計では列を用意するだけ
* マーケティング系テーブル（`007-sites` 以降で各機能が自分のマイグレーションを足す）
* Plugin 用の Schema 分離（`011-plugin-runtime`）
* Connection Pool のチューニング、レプリカ対応

## 4. レイヤ配置

```text
apps/web/src/
├── domain/
│   └── repository.ts            Repository の基底型と検索条件の型（DB非依存）
├── database/
│   ├── provider.ts              DatabaseProvider インターフェース
│   ├── postgres-provider.ts     pg Pool による実装
│   ├── connection.ts            Connection / Transaction の型（Kysely を内包）
│   ├── schema.ts                テーブルの型定義（Kysely 用）
│   └── registry.ts              既定 Provider の登録と解決
├── application/
│   └── transaction.ts           UseCase がトランザクション境界を張るための入口
└── infrastructure/
    └── （各 Repository 実装は該当機能のスプリントで追加）

packages/cli/src/
├── migrate/
│   ├── runner.ts                マイグレーション適用ロジック
│   ├── loader.ts                連番SQLの読み込みと検証
│   └── lock.ts                  advisory lock
└── index.ts                     コマンド解釈

migrations/
└── 001_initial.sql
```

**Domain 層は `pg` も `kysely` も import しない。** ESLint で検査する（S0 で設定済み）。

Repository Interface は Domain に置き、実装は Infrastructure に置く。
実装は `Connection` を受け取る。`Connection` の実体が Pool 由来かトランザクション由来かを
Repository は知らない。これにより、同じ Repository がトランザクションの内外どちらでも動く。

## 5. データモデル

### 5.1 `schema_migrations`

マイグレーションの適用状況。ランナーが自動生成する。

| カラム | 型 | 制約 |
| --- | --- | --- |
| `version` | `text` | PK |
| `name` | `text` | NOT NULL |
| `checksum` | `text` | NOT NULL。SQL本文の SHA-256 |
| `applied_at` | `timestamptz` | NOT NULL DEFAULT `now()` |
| `execution_ms` | `integer` | NOT NULL |

`checksum` は**適用済みマイグレーションの改変を検出**するために持つ。
既に適用済みの版のファイルが変わっていたら、適用せずエラーで止める。

### 5.2 `users`

| カラム | 型 | 制約 |
| --- | --- | --- |
| `id` | `uuid` | PK |
| `login_id` | `text` | NOT NULL, UNIQUE（大文字小文字を区別しない） |
| `email` | `text` | NOT NULL, UNIQUE（大文字小文字を区別しない） |
| `display_name` | `text` | NOT NULL |
| `password_hash` | `text` | NULL 可（外部認証のみのユーザーはパスワードを持たない） |
| `status` | `text` | NOT NULL, CHECK in (`active`, `disabled`) |
| `created_at` / `updated_at` | `timestamptz` | NOT NULL DEFAULT `now()` |
| `last_login_at` | `timestamptz` | NULL 可 |

大文字小文字を区別しない一意性は `citext` ではなく **`lower()` の式インデックス**で表現する
（拡張機能に依存しないため）。

### 5.3 `roles` / `permissions` / `user_roles` / `role_permissions`

| テーブル | 主な列 |
| --- | --- |
| `roles` | `id` uuid PK / `name` text UNIQUE / `display_name` / `is_system` boolean / timestamps |
| `permissions` | `name` text PK（`site.read` 等）/ `display_name` / `description` |
| `user_roles` | `user_id` / `role_id`、複合PK、両方に FK（ON DELETE CASCADE） |
| `role_permissions` | `role_id` / `permission_name`、複合PK、両方に FK（ON DELETE CASCADE） |

`permissions.name` を自然キーにしているのは、**Plugin が自分の Permission を登録できる**
必要があるため（`03_プラグイン設計.md` §20.2）。文字列で参照できるほうが素直になる。

`is_system` が真の Role は削除・改名できない（画面と UseCase で防ぐ。本設計では列のみ用意）。

### 5.4 `sessions`

| カラム | 型 | 制約 |
| --- | --- | --- |
| `id` | `uuid` | PK |
| `user_id` | `uuid` | NOT NULL, FK → `users(id)` ON DELETE CASCADE |
| `token_hash` | `text` | NOT NULL, UNIQUE |
| `created_at` | `timestamptz` | NOT NULL DEFAULT `now()` |
| `last_accessed_at` | `timestamptz` | NOT NULL DEFAULT `now()` |
| `expires_at` | `timestamptz` | NOT NULL |
| `revoked_at` | `timestamptz` | NULL 可 |
| `ip_address` | `inet` | NULL 可 |
| `user_agent` | `text` | NULL 可 |

**Cookie に入るトークンそのものは保存しない。ハッシュだけを保存する**（`04_認証設計.md` §7）。
DBが漏れてもセッションを乗っ取れないようにするため。

### 5.5 `auth_audit_logs`

| カラム | 型 |
| --- | --- |
| `id` | `uuid` PK |
| `event` | `text` NOT NULL（`login.succeeded` 等） |
| `user_id` | `uuid` NULL 可, FK → `users(id)` ON DELETE SET NULL |
| `login_id_attempted` | `text` NULL 可 |
| `ip_address` | `inet` NULL 可 |
| `user_agent` | `text` NULL 可 |
| `detail` | `jsonb` NOT NULL DEFAULT `'{}'` |
| `occurred_at` | `timestamptz` NOT NULL DEFAULT `now()` |

`user_id` を SET NULL にしているのは、**ユーザーを消しても監査記録を消さない**ため。
`detail` にパスワード・トークンを入れてはならない（`04_認証設計.md` §26）。

### 5.6 Index

| 対象 | 目的 |
| --- | --- |
| `users(lower(login_id))` UNIQUE / `users(lower(email))` UNIQUE | 大文字小文字を区別しない一意性 |
| `sessions(user_id)` | ユーザーの全セッション失効 |
| `sessions(expires_at)` | 期限切れセッションの掃除 |
| `auth_audit_logs(occurred_at DESC)` | 監査ログの新着順表示 |
| `auth_audit_logs(user_id, occurred_at DESC)` | ユーザー単位の追跡 |

## 6. API

このスプリントは HTTP API を持たない。外部との接点は CLI のみ。

### `torifune migrate`

```text
torifune migrate [--database-url=<url>] [--migrations-dir=<path>] [--dry-run]
```

| 引数 | 既定値 | 説明 |
| --- | --- | --- |
| `--database-url` | 環境変数 `DATABASE_URL` | 接続先 |
| `--migrations-dir` | パッケージからの相対で `migrations/` | 連番SQLの場所 |
| `--dry-run` | false | 適用せず、適用対象の一覧だけを出す |

終了コード：成功 `0` / 引数不正 `1` / 適用失敗 `1`。

出力に接続文字列を含めない（パスワードが混じるため）。

## 7. 画面

なし。

## 8. 権限（Permission）

このスプリントは Permission チェックの対象になる操作を持たない。
`003-authorization` が使う `permissions` テーブルと初期データを用意するのみ。

`001_initial.sql` に投入する初期 Permission：

```text
site.read     site.write     site.delete
content.read  content.write  content.delete
social.read   social.write   social.delete
user.manage   plugin.manage  system.manage
```

初期 Role と割り当て：

| Role | Permission |
| --- | --- |
| `administrator` | 全部 |
| `editor` | `*.read` + `site.write` `content.write` `social.write` |
| `viewer` | `*.read` |

`administrator` / `editor` / `viewer` は `is_system = true`。

## 9. Plugin API への影響

このスプリントでは `packages/plugin-api` に何も公開しない。

ただし `DatabaseProvider` インターフェースは、`010-plugin-api` でそのまま公開契約になる。
**そのつもりで設計する。** 具体的には：

* `pg` や `kysely` の型をインターフェースの signature に露出させない
* Provider が「どのDBに繋ぐか」を決める余地を残す（引数に接続先の解決コンテキストを取る）
* 実装の差し替えがレジストリ経由でできる形にする

## 10. 受け入れ条件

### マイグレーションランナー

1. 空のDBに対して実行すると、`001_initial.sql` が適用され `schema_migrations` に1行記録される
2. 続けてもう一度実行しても、何も適用されず、既存データが変化しない
3. 適用済みバージョンのSQLファイルを書き換えてから実行すると、**適用せずエラーで終了する**
4. 適用対象が複数あるとき、バージョン番号の昇順で適用される
5. 途中のマイグレーションが失敗したとき、そのマイグレーションの変更はロールバックされ、
   それ以降のマイグレーションは適用されない
6. 2つのプロセスから同時に実行しても、同じマイグレーションが二重に適用されない
7. ファイル名が `NNN_name.sql` の形式でないファイルがあるとエラーになる
8. バージョン番号が重複しているとエラーになる
9. `--dry-run` では適用されず、適用対象の一覧だけが出力される
10. エラーメッセージに接続文字列（パスワードを含む）が現れない

### CLI

11. `torifune migrate` を `--database-url` も `DATABASE_URL` も無い状態で実行すると、
    終了コード 1 と使い方の案内で終わる
12. 未知のコマンドを渡すと終了コード 1 になる
13. `torifune --help` は終了コード 0 で使い方を出す

### Database Provider

14. `healthCheck()` が接続できるとき true、接続できないとき false を返し、例外を投げない
15. `transaction()` に渡した関数が例外を投げると、その中の変更がすべてロールバックされる
16. `transaction()` に渡した関数が正常終了すると、変更がコミットされる
17. トランザクションの中で使った Repository と、外で使った Repository が同じ実装で動く
18. `disconnect()` 後に `healthCheck()` を呼んでも例外を投げない

### スキーマ

19. `users.login_id` が大文字小文字を区別せず一意である（`Alice` と `alice` は共存できない）
20. `users.email` も同様
21. `users.status` に定義外の値を入れようとすると失敗する
22. ユーザーを削除すると、その `user_roles` と `sessions` も削除される
23. ユーザーを削除しても `auth_audit_logs` の行は残り、`user_id` が NULL になる
24. `sessions.token_hash` が一意である
25. 初期 Role 3種と初期 Permission 12種が投入されている
26. `administrator` が全 Permission を持つ

### 境界

27. `apps/web/src/domain/` 配下のファイルが `pg` / `kysely` を import していない（ESLint）
28. `DatabaseProvider` インターフェースの signature に `pg` / `kysely` の型が現れない
