## 2. テストの置き場と種類

| 種類 | 置き場 | DB |
| --- | --- | --- |
| ユニット | 対象ファイルの隣（`*.test.ts`） | 不要 |
| 結合 | `*.integration.test.ts` | 必要 |

結合テストは `DATABASE_URL` が設定されていないと**失敗させる**（黙ってスキップしない）。
スキップにすると CI で DB が落ちていても緑になり、テストが意味を失うため。

ローカルでは `docker compose up -d postgres-test` を使う。
`TORIFUNE_TEST_DATABASE_URL` があればそれを、無ければ `DATABASE_URL` を使う。

各結合テストは**自分専用のスキーマではなく専用のデータベース**を使わず、
テストごとにトランザクションで囲んでロールバックする方式にする。
ただしマイグレーションのテストだけは DDL を伴うため、テスト用に**使い捨てのデータベースを作る**。

## 3. 実装順序（テスト先行）

```text
Step 1  T6 loader のテスト → 実装        （DB不要。ファイル名検証・順序・checksum）
Step 2  T10 初期スキーマ                  （テストは Step 5 の結合テストで検証）
Step 3  T8 runner のテスト → 実装         （結合。冪等・改変検出・失敗時ロールバック・同時実行）
Step 4  T9 CLI のテスト → 実装            （引数解釈はユニット、実行は結合）
Step 5  T2-T5 Provider のテスト → 実装    （結合。transaction / healthCheck）
Step 6  スキーマ制約のテスト               （結合。一意性・CHECK・FK の挙動）
```

Step 3 と Step 5 は独立しているので入れ替え可能。
**Step 1 を最初に置く**のは、DB なしで回せてフィードバックが速いため。

## 4. 設計上の判断

### 4.1 advisory lock の掛け方

`pg_advisory_lock(key)` をセッションレベルで取る。キーは固定値
（`hashtext('torifune:migrations')` 相当の定数）を使う。

トランザクションレベル（`pg_advisory_xact_lock`）にしない理由：
各マイグレーションを個別のトランザクションで実行するため、
ロックはトランザクションをまたいで保持する必要がある。

ロックは**待つ**（`pg_advisory_lock`。`try_` ではない）。
デプロイ時に複数インスタンスが同時に起動するケースで、
先行するプロセスの完了を待って「適用済みなので何もしない」に落ち着くのが正しい振る舞い。

### 4.2 マイグレーション1本 = 1トランザクション

各SQLファイルを1つのトランザクションで実行し、`schema_migrations` への記録も同じ
トランザクションに含める。失敗したらその版の変更は残らない。

PostgreSQL は DDL をトランザクションに入れられるので、この方式が取れる。

> `CREATE INDEX CONCURRENTLY` 等のトランザクション内で実行できない文が必要になったら、
> ファイル名に `.no-transaction` を付ける等の仕組みを後から足す。今回は不要。

### 4.3 checksum で改変を検出する

適用済みマイグレーションのファイルが変わっていたら**エラーで止める**。
警告で流すと、環境ごとにスキーマが食い違ったまま進行する。

### 4.4 Connection の抽象

```text
DatabaseProvider
  ├── connect(): Promise<Connection>
  ├── disconnect(): Promise<void>
  └── healthCheck(): Promise<boolean>

Connection
  ├── db: Kysely<Schema>         ← 内部利用。plugin-api には出さない
  └── transaction<T>(fn: (tx: Connection) => Promise<T>): Promise<T>
```

`Connection` の中に Kysely を持つが、**Repository はこの `Connection` を受け取る**。
Repository の signature に Kysely を出さないことで、
Provider を差し替えても Repository の呼び出し側が変わらない。

> `010-plugin-api` で公開するときは、`db` を露出しない別の型に絞る。
> 一般 Plugin に自由な SQL 実行権限を与えない（`05_API設計.md` §27）。

### 4.5 UUIDv7 をアプリケーション側で生成する

PostgreSQL 17 には `uuidv7()` が無いため、`uuidv7` パッケージで生成する。
時系列順にソートでき、かつ推測しにくい。
DB 側の `DEFAULT` には頼らず、アプリケーションが明示的に採番する
（テストで ID を固定でき、Repository の外から採番できる）。

## 5. 影響範囲

| 対象 | 影響 |
| --- | --- |
| 既存コード | なし（S0 の雛形のみ） |
| Plugin API | なし。ただし §4.4 の型は `010-plugin-api` の下敷きになる |
| CI | 結合テストのため `DATABASE_URL` が必要。S0 で設定済み |
| Docker | `migrations/` をイメージに含める必要がある。`.dockerignore` を確認する |

**破壊的変更：なし**（初回実装のため）

## 6. リスク

| リスク | 対応 |
| --- | --- |
| 結合テストが CI の PostgreSQL に依存し、不安定になる | ヘルスチェック待ちを CI 側（`options: --health-cmd`）で済ませてある |
| テスト間でデータが干渉する | 各テストをトランザクションで囲みロールバックする。マイグレーションのテストだけ使い捨てDB |
| 使い捨てDBの作成に `CREATE DATABASE` 権限が要る | 開発・CI の PostgreSQL では所有者ロールで動くため問題ない。本番の権限分離とは無関係 |
| `lower()` の式インデックスによる一意性が、アプリ側の重複チェックと食い違う | 一意制約違反を UseCase 側で 409 に変換する。`002-authentication` で扱う |
