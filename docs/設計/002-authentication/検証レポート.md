### 指摘

#### F-3（軽微・記録）`local-provider` が `SessionIssuer` を兼ねている

`AuthenticationProvider` と `SessionIssuer` は別インターフェースだが、
標準実装は両方を1つのオブジェクトで満たしている。

外部認証 Provider（OIDC）でも Torifune 自身のセッションは張るため、
S10 でこの2つの関係を整理する。**セッション発行は Provider ではなく本体の責務**に
寄せたほうが、Plugin 側の実装が軽くなる可能性がある。

### 指摘

#### S-3（要注意・記録）`x-forwarded-for` を信頼している

`requestInfoOf` は `x-forwarded-for` の先頭を IP として扱う。
**信頼できる Reverse Proxy の背後にいることが前提。**
直接インターネットへ晒すと、攻撃者がヘッダを詐称して IP 単位の試行制限を回避できる。

アカウント単位の制限が主な防御なので致命的ではないが、
デプロイ時の前提として文書化が要る。`007-デプロイ` 相当のスプリントで扱う。

#### S-4（記録）CSRF のホスト判定が Host ヘッダに依存する

`APP_URL` が未設定のとき、`x-forwarded-host` / `host` を基準にする。
Host ヘッダは詐称されうるが、**CSRF の文脈では「ブラウザが送った Origin と、
リクエストが届いた Host が一致するか」を見ており、両方を同時に詐称しても
被害者のブラウザからのリクエストにはならない**ため、成立する。

ただし**本番では `APP_URL` を明示するのが確実**。`.env.example` に記載済み。

## 4. 指摘の詳細と対応

### F-1（対応済み・条件を変更）`Secure` の判定を `APP_ENV` からリクエストのスキームへ

**受け入れ条件 10 は「`APP_ENV=production` のとき `Secure` が付く」だったが、
この実装は壊れる。**

`next start` は常に `NODE_ENV=production` を立てる。当初 `NODE_ENV` も見ていたため、
HTTP で提供している環境（E2E、ローカルの `pnpm start`、TLS を上流で終端しない構成）で
`Secure` が付き、**Cookie が送られず一切ログインできなかった**。E2E で発覚した。

**変更後の条件 10'**

> 10'. `Secure` はリクエストのスキーム（`x-forwarded-proto` ?? URL）で決まる。
> HTTPS なら付き、HTTP なら付かない。
> ただし `APP_ENV=production` が明示されている場合は、TLS 終端が上流にあって
> ヘッダが落ちていても付ける（付け忘れより安全側に倒す）。

`cookies.test.ts` に「NODE_ENV では判定しない」というテストを置き、
同じ壊れ方を再発させないようにした。

### F-2（未検証・次スプリントへ）時間に依存する試行制限のテスト

条件 29（IP 単位）と 31（時間窓の経過）は自動テストで検証していない。

* 29 は、既定値が IP 30 回・アカウント 10 回のため、
  **IP の閾値へ到達する前にアカウント側で弾かれる**。
  検証するには複数アカウントを使うか閾値を注入する必要がある
* 31 は時間の経過を要する。時計を注入できる形にすれば検証できる

**対応**：`createRateLimiter` は既にポリシーを引数で受け取れる。
`003-authorization` と同時に、ポリシーと時計を注入したユニットテストを追加する。
ロジック自体（`isAllowed` の閾値比較）は単純で、結合テストで実装経路が通っていることは確認済み。
