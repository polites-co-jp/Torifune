# 認証 設計

## 1. 目的

Torifune 単体でログイン・ログアウトが完結する状態を作る。

満たすべきことは4つ。

1. **認証方式を Authentication Provider として抽象化する。**
   これができていないと、後から OIDC 等へ差し替えられない
2. **認証済みユーザーを、認証方式によらない統一表現（User Identity）で扱う。**
   本体のどこにも「標準認証だから」という分岐を作らない
3. **セッションを安全に管理する。**
   DB が漏れてもセッションを乗っ取られない、ログアウトが本当に効く、を成立させる
4. **管理者が誰もいない状態から、安全に最初の管理者を作れる。**
   Secret をイメージにも環境変数にも置かずに済ませる

## 3. スコープ

### やること

* Authentication Provider Interface と標準（ローカル）Provider
* User Identity（認証方式によらない統一表現）
* パスワードハッシュ（Argon2id）
* セッション管理（発行・検証・更新・失効）
* Cookie（`HttpOnly` / `SameSite=Lax` / 本番 `Secure`）
* CSRF 対策（Origin 検証＋二重送信トークン）
* ログイン試行制限（IP 単位・アカウント単位）
* 認証監査ログ
* `/setup` 初回セットアップ画面
* ログイン画面・ログアウト
* パスワードリセット（トークン発行・検証・再設定）。**通知はログ出力実装まで**

### やらないこと

* Permission による認可（`003-authorization`）。本設計は「誰であるか」までを扱う
* パスワードリセットの実メール送信（`019-notification`）
* OIDC / 外部認証（Plugin の責務。契約は `010-plugin-api` で公開）
* API Token（`016-api-token`）
* 二要素認証
* 共通 UI コンポーネント（`005-ui-shell`）。本設計の画面は最低限の素の HTML で作る

> `/setup` とログイン画面は `005-ui-shell` より前に必要になる。
> 先に素朴な形で作り、`005-ui-shell` で共通レイアウトへ載せ替える。

## 5. データモデル

`001_initial.sql` のテーブルを使う。追加するのは次の2つ。

### 5.1 `password_reset_tokens`（`migrations/002_password_reset.sql`）

| カラム | 型 | 制約 |
| --- | --- | --- |
| `id` | `uuid` | PK |
| `user_id` | `uuid` | NOT NULL, FK → `users(id)` ON DELETE CASCADE |
| `token_hash` | `text` | NOT NULL, UNIQUE |
| `expires_at` | `timestamptz` | NOT NULL |
| `used_at` | `timestamptz` | NULL 可 |
| `created_at` | `timestamptz` | NOT NULL DEFAULT `now()` |

**トークンは平文で保存しない**（`04_認証設計.md` §24）。
`used_at` を持つのは、一度使ったトークンを無効にするため。

### 5.2 `login_attempts`（同じマイグレーション）

| カラム | 型 |
| --- | --- |
| `id` | `uuid` PK |
| `key` | `text` NOT NULL（`ip:1.2.3.4` / `login:alice`） |
| `occurred_at` | `timestamptz` NOT NULL DEFAULT `now()` |

INDEX：`(key, occurred_at DESC)`

失敗の記録だけを持つ。時間窓の中の件数で判定する。

> Redis 等の外部依存を増やさず DB で持つ。単体構成で動くことを優先する
> （`00_システム概要.md` §2.1）。件数が問題になるまで最適化しない。

## 6. API

すべて `/api/v1/auth/` 配下。レスポンスの統一形式は `004-api-foundation` で整えるため、
本設計では最低限の形にする。

| メソッド | パス | 認証 | 説明 |
| --- | --- | --- | --- |
| POST | `/api/v1/auth/login` | 不要 | ログイン。成功で Set-Cookie |
| POST | `/api/v1/auth/logout` | 必要 | ログアウト。サーバー側セッションを失効 |
| GET | `/api/v1/auth/me` | 必要 | 現在の UserIdentity |
| POST | `/api/v1/auth/password-reset/request` | 不要 | リセットトークンの発行 |
| POST | `/api/v1/auth/password-reset/confirm` | 不要 | 新しいパスワードの設定 |
| POST | `/api/v1/setup` | 不要※ | 初回セットアップ。※管理者が0人のときのみ |

### 6.1 リクエストとレスポンス

```jsonc
// POST /api/v1/auth/login
{ "loginId": "alice", "password": "…", "csrfToken": "…" }
// 200
{ "data": { "id": "…", "loginId": "alice", "displayName": "Alice", "email": "…" } }
```

**レスポンスに `passwordHash` を含めない**（`05_API設計.md` §15）。

### 6.2 エラー応答

| 状況 | ステータス | code |
| --- | --- | --- |
| 入力不備 | 422 | `VALIDATION_ERROR` |
| CSRF 検証失敗 | 403 | `CSRF_FAILED` |
| ログイン失敗（ID が無い／パスワード違い／無効化済み） | 401 | `INVALID_CREDENTIALS` |
| 試行回数超過 | 429 | `TOO_MANY_ATTEMPTS` |
| 未認証で保護 API | 401 | `UNAUTHENTICATED` |
| `/setup` が既に閉じている | 404 | — |

**ログイン失敗の理由を区別しない。**
「そのIDは存在しない」と「パスワードが違う」を返し分けると、
アカウントの存在を列挙できてしまう。

### 6.3 パスワードリセット要求の応答

**メールアドレスが登録済みかどうかにかかわらず 204 を返す。**
存在するアドレスだけ 200 を返すと、登録の有無を調べられる。

## 8. 権限（Permission）

本設計では Permission チェックを行わない（`003-authorization` の責務）。
ただし以下は本設計で決める。

* `/setup` で作られる最初のユーザーには `administrator` ロールを割り当てる
* `/api/v1/auth/me` と `/api/v1/auth/logout` は**認証されていること**だけを要求する

## 9. Plugin API への影響

`packages/plugin-api` にはまだ公開しない（S10 でまとめて公開する）。

ただし `AuthenticationProvider` と `UserIdentity` は S10 でそのまま公開契約になる。
そのつもりで設計する。

```text
AuthenticationProvider
├── id: string
├── authenticate(credentials, context): Promise<AuthenticationResult>
├── getIdentity(session): Promise<UserIdentity | null>
├── logout(session): Promise<void>
└── refresh(session): Promise<void>
```

* signature に Cookie / Request / Response の型を出さない
  （HTTP の詳細は API Layer の責務。Provider を CLI から呼べる形にしておく）
* `AuthenticationResult` は成功・失敗を型で区別し、失敗理由を呼び出し側へ返さない

## 10. 受け入れ条件

### パスワード

1. 同じパスワードを2回ハッシュ化すると異なる文字列になる（ソルトが効いている）
2. ハッシュから元のパスワードを検証できる
3. 違うパスワードでは検証に失敗する
4. ハッシュ文字列が Argon2id の形式（`$argon2id$` で始まる）である
5. 空文字のパスワードは登録できない
6. 極端に長いパスワード（1MB）でもサービスが停止しない（上限で弾く）

### セッション

7. ログインすると Set-Cookie が返る
8. Cookie に `HttpOnly` が付いている
9. Cookie に `SameSite` が付いている
10. `APP_ENV=production` のとき Cookie に `Secure` が付く
11. **DB に保存されているのはトークンのハッシュであり、Cookie の値そのものではない**
12. ログイン前後でセッション識別子が変わる
13. ログアウト後、同じ Cookie で `/api/v1/auth/me` を呼ぶと 401
14. ログアウトでサーバー側のセッションが失効する（`revoked_at` が入る）
15. 有効期限を過ぎたセッションでは 401
16. 失効済みセッションでは 401
17. 存在しないトークンでは 401
18. 別ユーザーのセッショントークンを推測して当てられない（256bit の乱数）

### ログイン

19. 正しい資格情報でログインできる
20. 誤ったパスワードで 401
21. 存在しないログインIDで 401
22. **20 と 21 のレスポンスが本文・ステータスとも同一である**
23. `status = disabled` のユーザーはログインできない（401）
24. ログイン成功時に `users.last_login_at` が更新される
25. レスポンスに `passwordHash` が含まれない
26. CSRF トークンが無い POST は 403
27. Origin が異なる POST は 403

### ログイン試行制限

28. 同一アカウントへ規定回数失敗すると 429 になる
29. 同一 IP から規定回数失敗すると 429 になる
30. 429 のときは正しいパスワードでも通らない
31. 時間窓を過ぎると再び試行できる
32. ログイン成功で、そのアカウントの失敗記録がリセットされる

### 初回セットアップ

33. 管理者が0人のとき `/setup` が 200 を返す
34. `/setup` で作ったユーザーが `administrator` ロールを持つ
35. 管理者が1人以上いるとき `/setup` が 404 を返す
36. 管理者が1人以上いるとき `/api/v1/setup` への POST が拒否される
37. `/setup` を同時に2回叩いても管理者が2人作られない
38. `/setup` で作成したあと、そのままログインできる

### パスワードリセット

39. リセット要求で、DB にはトークンのハッシュだけが保存される
40. **登録済みアドレスでも未登録アドレスでも同じ応答（204）を返す**
41. 有効なトークンでパスワードを再設定できる
42. 一度使ったトークンは再利用できない
43. 期限切れのトークンは使えない
44. 存在しないトークンでは失敗する
45. パスワード再設定後、そのユーザーの既存セッションがすべて失効する

### 監査ログ

46. ログイン成功が記録される
47. ログイン失敗が記録される（存在しないIDへの試行も）
48. ログアウトが記録される
49. パスワード変更が記録される
50. **監査ログにパスワード・トークンが記録されない**

### 境界

51. `domain/` が Argon2・Cookie・HTTP の型を import していない
52. `AuthenticationProvider` の signature に Cookie / Request / Response 型が現れない
53. 標準認証が Authentication Provider の契約として登録されている
