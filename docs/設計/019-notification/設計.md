# 019-notification 設計

## 1. 目的

`002-Torifune機能完成` T2。**パスワードリセットのフローを完結させる**
（`04_認証設計.md` §24、`001/03_リスクと未決事項.md` S-8 #1）。

## 2. いまの状態

トークンの発行・保存・検証・失効はすべて実装済みで、
`POST /api/v1/auth/password-reset/confirm` も動く。**欠けているのは2つだけ。**

| 欠けているもの | 影響 |
| --- | --- |
| トークンの配達手段（メール送信） | `loggingNotifier` は**意図的にトークンを出さない**ため、誰もトークンを受け取れない |
| トークンを受けて新パスワードを設定する画面 | 受け取っても入力する場所が無い |

**片方だけ入れても使えない。** 画面だけ足しても配達手段が無く、
メールだけ足しても着地する画面が無い。**同じスプリントで両方入れる。**

## 3. 決めたこと

### 3.1 SMTP は「設定されていれば使う」

`TORIFUNE_SMTP_URL` が設定されていれば SMTP で送り、
無ければ `loggingNotifier` のまま（＝送らない）。

**起動を失敗させない。** 自己ホスト型では SMTP を用意しない運用が普通にあり、
そこで起動できなくなるのは過剰。復旧手段は `torifune reset-password` にある
（S-8 #2 で用意済み）。

ただし**黙って送らないのは不親切**なので、起動時に一度だけ警告を出す。

### 3.2 送信ライブラリは nodemailer を使う

SMTP を自前で書かない。認証方式・TLS・エンコーディング・添付の扱いなど、
間違えると届かないか、最悪ヘッダインジェクションになる箇所が多い。

### 3.3 リセットURLの組み立て

`APP_URL` を基点にする。

**リクエストの `Host` ヘッダから組み立てない。** 攻撃者が `Host` を差し替えると、
自分のサーバーを指すリセットURLをメールで送れてしまう（Host header injection）。
`APP_URL` が無く SMTP が設定されている場合は、
**設定の誤りとして送信時に失敗させる**（誤った宛先へ送るより送らないほうがよい）。

### 3.4 トークンは `Notification.secret` のまま運ぶ

`application/notification.ts` の `Notification` は既に
「`data` にトークンを入れてはならない / `secret` は受け取り側だけが扱う」と
決めている。この形を変えない。

`loggingNotifier` が `secret` を出さないという判断も変えない。
**ログの閲覧権限がアカウント乗っ取りの権限になってはならない。**

### 3.5 確認画面はトークンを URL クエリで受ける

`/password-reset/confirm?token=...`。

メール本文のリンクをそのまま踏める形が一般的で、
`019-notification` 以降に実メールを入れてもそのまま使える。

トークンが Referer や履歴に残る点は、**単回使用・1時間期限**で緩和されている
（既に実装済み）。手入力させる案は、利用者にコピペを強いる割に得るものが小さい。

### 3.6 結果の出し分けをしない

トークンが無効・期限切れ・使用済みのいずれでも**同じメッセージ**を返す。
出し分けると、トークンの有効性を調べる手段になる。
（API 側は既に `invalid_token` に一本化済み。画面もそれに合わせる。）

## 4. 構成

```text
apps/web/src/
├── infrastructure/notification/smtp-notifier.ts   （新規）
├── infrastructure/notification/message.ts         本文の組み立て（新規）

```

## 5. メール本文

宛名を入れない。`Notification.data` に名前を入れると、
**アドレスの持ち主が誰かをメール本文で確認できてしまう**（列挙の材料になる）。

件名と本文は日本語。リンクの有効期限を明記する。

## 6. やらないこと

* メールテンプレートの仕組み（HTML メール、多言語）。
  **いま必要なのは1種類だけ**で、仕組みを先に作ると使われない形が固まる
* 送信の再試行・キュー。落ちたら落ちたままにする。
  利用者はもう一度要求すればよく、再送の仕組みは複雑さに見合わない
* 通知の種類を増やすこと（`kind` は `password_reset` のみ）

## 7. 受け入れ条件

1. 要求 → メール受信 → リンク → 再設定 → 旧セッション全失効、が通る
2. トークンは単回使用。2回目は失敗する
3. 期限切れ・使用済み・改竄で**同じ**メッセージになる
4. SMTP 未設定でも起動し、リセット要求もエラーにならない（送られないだけ）
5. `APP_URL` 未設定で SMTP だけ設定した場合、送信時に失敗する
6. メール本文とログにトークン以外の機密が載らない。ログにトークンが載らない
