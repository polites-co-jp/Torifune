## 設計から変えたこと

### `TORIFUNE_APP_URL` をやめ、既存の `APP_URL` を使う

設計 §3.3 は新しい変数を導入するつもりだったが、`.env.example` に
**すでに `APP_URL` があった**（CSRF の同一オリジン判定と Cookie の Secure 付与に使う）。

URLを2つ持つと、片方だけ変えたときに気づけない。既存のものへ寄せた。

### 確認画面でトークンをサーバー側から読む

設計 §3.5 は「URL クエリで受ける」とだけ書いていた。
当初 `useSearchParams()`（クライアント）で読んだが、これが**動かなかった**。

`useSearchParams()` を使うと Next.js がクライアント描画へ退避し
（`BAILOUT_TO_CLIENT_SIDE_RENDERING`）、その shell に CSP の nonce が入らない。
結果、そのページのスクリプトが全部ブロックされ、**画面は出るのに操作できない**。

Server Component の `searchParams` から読む形へ変えた。退避が起きず、
サーバー側で描画されるため nonce が入る。

## 022-hardening（T1）の欠陥を1件直した

**T1 で入れた CSP が、静的に生成されるページを壊していた。**

静的生成のHTMLには nonce が焼き込まれないのに、応答ヘッダには
リクエストごとの新しい nonce が載る。そのページのスクリプトだけが
全部ブロックされ、画面は出るのに操作できない状態になる。

T1 の E2E 124件は**これを検出できなかった**。当時静的だったのは
`/logout` と `/password-reset` だけで、`/logout` は JS を要さず、
`/password-reset` にはまだテストが無かった。

直したこと：

1. `middleware.ts` がリクエスト側にも `Content-Security-Policy` を載せる
   （Next.js はここから nonce を取り出す）
2. ルートレイアウトで `export const dynamic = 'force-dynamic'`。
   ページごとに書くと必ず忘れる。管理画面はもともとほぼ全ページが動的で、
   静的生成を失う損は小さい

**テストの書き方も直した。** 「表示される」ことだけを確かめるテストは
この壊れ方を通してしまう。`/password-reset` のテストを
「送信できる」まで見る形に変えた。
