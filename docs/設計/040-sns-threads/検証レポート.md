## 2. 見つかった欠陥と処置

### 1. 記号でつないだ URL を 1 本と数えていた（`spec-verifier` 中-1。`037` にも同じ穴）

設計 §9.4 の URL の規則（「`https?://` から ASCII の可視文字が続くかぎり」）のため、
`https://a.example,https://b.example,…` のように `,` `|` `(` `)` `"` でつないだ URL が 1 本にまとまっていた。
6 本でも 1 本と数えて「リンクは 5 本まで」を登録で通し、配信の時刻に Threads が `LINK_LIMIT_EXCEEDED` で断る（`failed`。二重投稿にはならない）。
**「分からない部分は多めに数え、登録の時点で断る」という設計の方針に、設計自身の規則が負けていた。**

同じ規則を持つ `037` の `x-text.ts` も、つないだ URL を何本あっても 23 と数えていた（少なく数える）。

**処置**：URL は次の `https?://` の直前でも終わる。Threads の表に 13 行、X の共有の表に 7 行を足し、旧い規則に戻すと落ちることを確かめた。
X の修正は別のコミット（`5b50c45`）にし、`037` の設計と検証レポートにも記録した。

**`037` の中-1（空白の無い日本語の後ろまで URL と数えた）に続いて、URL の規則の穴は 2 度目。** どちらも実装とテストが設計どおりで、設計を読む検証でしか見つからなかった。

### 2. 公開の要求への 5xx でも再試行しうる（`security-reviewer` 低-1）

分類が「上から順に」で、レート制限の code（4 / 17 / 32 / 341 / 613）が付いていれば HTTP 500 でもレート制限として `retryable: true` になっていた。
公開の要求（R4）が相手側で実は通っていたなら、Core が作り直して送り直し、**二重投稿になる**。実装は設計どおりで、あいまいなのは設計の表だった。

**処置**：R4 で `true` にするのは 4xx（429 を含む）のレート制限だけ。5xx は常に `false`（§6.9 の支配的な規則 2）。旧い規則に戻すと 8 件落ちることを確かめた。

## 4. 検証の方法

* `spec-verifier` は全件のテストを流し、**68 通りの変異**を入れて判別力を確かめた（64 が落ち、生き残った 4 つを §2 の 3 で潰した）
* `security-reviewer` は**テストを 1 本も実行していない**（DB の競合を避けるため）。判定はコードの読解に基づく
* テストを書く段階でも、使い捨ての参照実装に 49 通りの変異を入れてテストの判別力を確かめた（実装プラン §8）
* 処置の後に検証を回し直してはいない。処置した変異が落ちることは処置した側が確かめた

## 6. 残る限界

| # | 内容 |
| --- | --- |
| 1 | **実機の Threads では一度も動かしていない。** Bearer ではなく引数でトークンを渡す形で全要求が通るか、permalink のドメイン、延長で新しい文字列が返るか、エラーの封筒の形、テキストにも処理待ちがあるか、は運用者の手で確かめる必要がある（設計 §11） |

| 4 | 手動投稿は日本語でおよそ 223 文字まで（ユーザー裁定） |
