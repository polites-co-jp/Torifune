## 1. 目的

Torifune に登録された SNS 投稿を、**Threads（Meta の Threads API）へ実際に配信する。** API の料金がかからない利用者向けの自動配信に加え、
**投稿画面（Web Intent）を開く手動投稿**も用意する。

Threads は Meta の Graph API と同じ流儀の API で、Instagram（`038`）とよく似ている。ただし次の点が違う：

| 事情 | Instagram（038） | Threads（本設計） |
| --- | --- | --- |
| 媒体 | **必須** | **任意**（テキストだけの投稿ができる） |
| 媒体の渡し方 | Instagram が公開 URL から取りに来る | **同じ**（Meta が公開 URL から取りに来る。Torifune は取りに行かない） |
| 送信の段数 | container 作成 → 処理待ち → `media_publish` | **同じ形**（container 作成 → 処理待ち → `threads_publish`） |
| 資格情報 | 長期トークン（60 日）。延長して書き戻す | **同じ**（長期トークン 60 日。`th_refresh_token` で延長） |
| トークンの渡し方 | `Authorization: Bearer`（`038` §6.2。実機未確認） | **クエリか form の引数 `access_token`**（公式の例がこの形だけ。§6.2） |
| 本文の数え方 | 2200（数え方は非公開） | **500。絵文字は UTF-8 のバイト数**、それ以外は非公開（§9.4） |
| リンク | キャプションの URL はリンクにならない（`link` を断る） | **本文の URL がリンクになる。重複を除いて 5 本まで**（§9.2） |
| 手動投稿 | Web Intent が無い | **Web Intent がある**（`https://www.threads.com/intent/post`。§9.5） |

この Plugin が満たすべきことは次の 2 つだけである。

* **`publish()`**：1 回の呼び出しで 1 件を Threads へ投稿し、結果を返す。必要ならトークンを延ばして返す
* **`manual()`**：投稿内容を反映した Threads の投稿画面の URL を返す。**自動配信の `publish()` が送る本文と同じ文字列**を入れる

それ以外（予約・排他・着手印・再試行・記録・イベント・手動投稿の画面）は**すべて Core にある**。

**すべて `https://developers.facebook.com/docs/threads/` の配下を 2026-09-24 に読んだ。**

## 3. スコープ

### 3.1 やること

* `plugins/sns-threads/` を新設する（`plugin.json` / `index.ts` / `social.ts` / `threads-api.ts` / `threads-text.ts` / `token.ts` / `README.md`）
* `provider: 'threads'`、`label: 'Threads'` の publisher を `context.social.registerPublisher()` で登録する
* `credentialFields`：`threadsUserId`（text）/ `accessToken`（secret）/ `accessTokenExpiresAt`（text）（§5.1）
* `limits: { mediaMax: 10 }`（`bodyMaxLength` と `mediaRequired` は宣言しない。§9.1）と `validate()`（本文の数え方・リンクの本数・intent URL の長さ・対になっていないサロゲート・`providerOptions`。§9.2）
* `publish()`：**テキスト**（`TEXT`）・**画像 1 枚**（`IMAGE`）・**画像 2〜10 枚**（`CAROUSEL`）の container 作成 → 状態のポーリング → `threads_publish` → `permalink` の取得 → 必要ならトークンの延長（§6）
* 延長したトークンを `rotatedCredential` で返す（§6.7）
* `manual()`：`https://www.threads.com/intent/post?text=…`（§9.5）
* `README.md`（§9.6）

### 3.2 やらないこと

| やらないこと | 理由 |
| --- | --- |
| Core（`apps/web` / `packages/plugin-api` / `migrations`）への変更 | `035` の口だけで書けることを示すのが本設計の目的。**`KNOWN_PROVIDERS` にも足さない**（ユーザー裁定。§11 #1） |
| **動画**（`VIDEO`、carousel の動画の子） | ①`SocialMediaView` は `url` と `alt` しか持たず、**画像か動画かを Plugin が知る手段が無い**（Torifune は媒体を取りに行かないので `Content-Type` も見えない）。②**動画の処理は非同期**（F15）で、Core の 30 秒に収まらない。`038` のユーザー裁定（画像のみ）と同じ理由。§11 #4 |
| `link_attachment` | `TEXT` の投稿にしか付けられない（F6）。**画像・carousel の投稿では使えない**ので、`link` の扱いが媒体の有無で変わる。本文の末尾に足せば、どの形でも同じ扱いになり、自動と手動で同じ文字列になる（§6.12・§9.4） |
| `auto_publish_text`（一段での公開） | 応答の形を確かめられなかった（F11）。**公開が起きたかを判定する応答が分からない要求は、`retryable` を正しく決められない。** テキストも他の形と同じ 2 段で送る（§11 #6） |
| 返信・引用・`reply_control`・トピック（`topic_tag` / intent の `tag`）・位置・投票・`text_attachment`（F21）・スポイラー | Core に対応する項目が無い（返信は親子の概念が無い。`036` §11 #5）。`providerOptions` はすべて断る（§9.2） |
| 画面からの OAuth「接続」 | Plugin の HTTP ルート（`027` §3.1）が前提。`035` 裁定 #6 で後回し |
| 自前のタイマー・ジョブ・HTTP ルート・テーブル・設定 | Core が持つ（`035` 裁定 #1）。**トークンの定期延長もしない**（§6.7・§11 #7） |
| 投稿の削除・編集 | Core に対応する操作が無い |
| container の再利用（再試行のあいだで container ID を持ち回る） | Plugin に状態を持たせることになる。**使わなかった container は公開されず 24 時間で失効する**（F9）ので、作り直して害が無い（§6.9） |
| `threads_publishing_limit` の問い合わせ | 要求が 1 本増える割に、得るのは「上限に近いと早めに分かる」ことだけ（`038` §11 #7 と同じ判断）。§11 #8 |
| `sns-instagram` とのコードの共有 | §4.2 |

### 3.3 Core が持つもの／この Plugin が持つもの

```text
Core（035 / 039）                             Plugin（040）
─────────────────────────────────────────    ─────────────────────────────────
予約の受付・冪等キー・権限                    —
ジョブ social.publish（1 分周期・排他）        —
着手印・中断行の判定・再試行の回数と間隔       —
資格情報の復号・監査・比較更新での書き戻し     rotatedCredential を組み立てて返す
limits の適用（mediaMax）                      limits の宣言
validate() の呼び出し（登録時・配信直前）      validate() の中身
manual + media を 422（f）                     —
手動投稿待ちの画面・子ウィンドウ・「投稿した」 manual() の URL と注意書き
publish() の呼び出しと 30 秒の打ち切り         publish() の中身（Threads API）
結果の記録・イベント・履歴画面                 —
provider の表示名（無効な間は生の値）          label（有効な間はこれが出る）
```

**この Plugin は状態を 1 つも持たない。** トークンの期限は**資格情報の中**に持ち、Core の暗号化・監査・書き戻しの内側に置く（§5.2）。

## 4. レイヤ配置

**すべて Plugin 層（`plugins/sns-threads/`）に置く。** 本体の `apps/web/src/` には 1 ファイルも足さない（テストとテスト用の共有定義を除く。§4.3）。

```text
plugins/sns-threads/
├── plugin.json      Manifest（id / apiVersion / permissions / extensions）
├── index.ts         activate(): publisher の登録だけ
├── social.ts        createThreadsPublisher(): PublisherRegistration を組み立てる。publish() の段取り・validate()・manual()
├── threads-api.ts   Threads API への HTTP と、応答の分類（phase / status / code → retryable）
├── threads-text.ts  本文の組み立て・数え方・URL の数え方・intent URL。純関数
├── token.ts         資格情報の形の検査・期限の読み取り・延長の要否。純関数
└── README.md        トークンの取り方と運用上の注意
```

* **`@/` や `apps/web` を import しない。** 使ってよいのは `@torifune/plugin-api` の型と、Node の標準の global
  （`fetch` / `URL` / `URLSearchParams` / `AbortSignal` / `AbortController` / `setTimeout` / `TextEncoder` / `TextDecoder` / `Intl.Segmenter`）だけ。**`node:` の import も置かない**
* **`pg` / `kysely` / `react` / `console` を使わない。** 出力は `PublishInput.logger` だけ
* **外へ出る HTTP は `threads-api.ts` に閉じる**（`038` の `graph.ts` と同じ）。`threads-text.ts` と `token.ts` は純関数で、`fetch` も時計も持たない（時刻は引数で受ける）

Domain 層・Application 層に Threads の語彙（`threads_publish`、`creation_id`、`th_refresh_token`、`intent/post`）を 1 つも出さない。

### 4.1 Plugin 同士の関係

* **`sns-threads` は他の Plugin を知らない。** Manifest の `dependencies` を持たない
* provider `threads` を登録する Plugin は**これ 1 つ**。第三者が同じ provider の別の Plugin を作れば、`035` §9.4 の規則（後から有効化したほうが `disabled`）がそのまま効く

### 4.2 `sns-instagram` とコードを共有しない（決めたこと）

**`graph.ts` / `token.ts` に似たコードを `sns-threads` の中に書く。`sns-instagram` のファイルを import も複製（バイト単位の一致）もしない。**

| 案 | 採否 | 理由 |

### 5.2 トークンの期限を資格情報に持つ（決めたこと）

**`038` §5.2 と同じ判断（案 D）を採る。** 期限を知る手段の候補と採否は `038` §5.2 の表のとおりで、Threads でも結論は変わらない：

* `debug_token` 相当の問い合わせは App のトークン（App Secret）が要る → 採らない
* 配信のたびに無条件で延長する → 書き戻しと監査が投稿の数だけ積まれ、**発行から 24 時間未満のトークンでは毎回失敗する**（F5）→ 採らない
* 期限を Key-Value Store に持つ → トークンと期限が別々に書かれ、片方だけ更新される状態が生まれる → 採らない
* **期限を資格情報の 3 つ目の項目に持つ → 採る。** トークンと期限が 1 つの暗号化された値に入り、Core が 1 回で書き戻す

**期限が読めない値は「不明」として扱う**（`unknown`・空白・日付として読めない文字列・**いまから 61 日より先**）。不明なら次に配信が成功したときに延長を試みる（§6.7）。

### 5.3 状態を持たない（決めたこと）

**この Plugin は `store` を読みも書きもしない。`registerSettings` も呼ばない。**

* **宛先（`https://graph.threads.net`）は定数**にする（§6.1）。変えられるようにすると、**アクセストークンを任意のサーバへ送らせる口**が 1 つ増えるだけ（`038` §5.3）
* **版（`v1.0`）も定数**にする
* **container の ID を持ち回らない**（§3.2）
* したがって `createThreadsPublisher` は **`store` を受け取らない**（§10.1）。Manifest の `extensions` は **`social` だけ**（§8.1）

## 6. 外部への要求（Threads API）

新しい Torifune の API エンドポイントは**作らない**。この Plugin が外へ出す HTTP 要求は次の 6 種類だけである。**`manual()` は要求を出さない。**

| # | 要求 | 用途 | 投稿との関係 |
| --- | --- | --- | --- |
| R1 | `POST {api}/{v}/{threadsUserId}/threads`（`media_type=TEXT` か `IMAGE`） | テキストか画像 1 枚の container、または carousel の子 | **投稿ではない** |
| R2 | `POST {api}/{v}/{threadsUserId}/threads`（`media_type=CAROUSEL`） | carousel の親 container | **投稿ではない** |
| R3 | `GET {api}/{v}/{containerId}?fields=status&access_token=…` | 処理待ちのポーリング | 読むだけ |
| R4 | `POST {api}/{v}/{threadsUserId}/threads_publish`（`creation_id`） | **公開する** | **これが「送る」** |
| R5 | `GET {api}/{v}/{mediaId}?fields=permalink&access_token=…` | 履歴から辿る URL | 公開の後 |
| R6 | `GET {api}/refresh_access_token?grant_type=th_refresh_token&access_token=…` | トークンの延長 | 公開の後 |

`{api}` は `https://graph.threads.net`、`{v}` は `THREADS_API_VERSION`（§6.1）。

### 6.1 宛先と版（決めたこと）

* `THREADS_API_BASE_URL = 'https://graph.threads.net'` と `THREADS_API_VERSION` を **`threads-api.ts` の定数**として持つ。設定にも資格情報にも入れない（§5.3）
* **`graph.threads.net` を選ぶ**（`graph.threads.com` も有効。F1）。**公式の例（延長の口を含む）がこの宛先で書かれている**ため。どちらを使っても同じ API で、ドメインの移行が要るなら Plugin の更新で行う
* **`THREADS_API_VERSION` は `'v1.0'`**（2026-09-24 時点で公開されている唯一の版。F1）。`038` §6.1 は版の値を設計に書かなかったが、Threads API は版が 1 つしか無く、
  **書かないと「最新の安定版」を実装者が推測することになる**。値が変わったら Plugin の更新で上げ、`README.md` と同時に直す（#10 が一致を見る）
* 要求の URL は **`new URL(path, THREADS_API_BASE_URL)` の解析結果から組み立てる**。パスの各部分（`threadsUserId`・container ID・media ID）は
  **§6.2 の形の検査を通した値だけ**を使う。文字列の連結で作らない（`036` 低-2）。クエリは `URLSearchParams` で付ける
* R6 だけは**版の付かないパス**（`/refresh_access_token`）である（F5）

### 6.2 共通の要求の形

| 項目 | 値 | 理由 |
| --- | --- | --- |
| 認証（R1 / R2 / R4：POST） | **form の本体の `access_token`** | 公式の例がこの形（F2）。**URL に載らない** |
| 認証（R3 / R5 / R6：GET） | **クエリの `access_token`** | GET に本体は無く、公式の例がこの形（F2）。**この 3 つの URL にはトークンが入る**。URL を `logger` にも `reason` にも載せない（§6.11）。README に注意を書く（§9.6） |
| `Authorization` ヘッダ | **付けない** | 公式の文書に `Bearer` の記述が無い（F2）。**文書に無い渡し方で全配信を失敗させるより、文書の形に従う**（`038` §11 #9 が残した「Bearer を受けるか」の論点を、この Plugin では最初から避ける） |
| POST の本体 | `application/x-www-form-urlencoded`（`URLSearchParams`） | Graph API の流儀。`access_token` と他の引数を同じ本体に入れる |
| リダイレクト | **追わない**（`redirect: 'manual'`。3xx は `kind: 'http'` の失敗） | トークンを載せた要求を別の宛先へ移らせない。**`'error'` にしない**（3xx を観測できず `network` に落ちる。`036` R-1） |
| 応答の読み方 | `response.text()` を **64 KiB（`RESPONSE_BODY_MAX_BYTES`）で打ち切って**から `JSON.parse` | 相手が何を返しても Plugin のメモリを食わせない（`038` 軽微-4 / `037` 軽微-1） |

**外へ出す前の形の検査**（通らなければ 1 本も出さずに `retryable: false`。§6.9 の P0）：

| 値 | 形 | 理由 |
| --- | --- | --- |
| `credential.threadsUserId` | `^[0-9]{1,64}$` | URL のパスに入る。`../` や `?` を入れさせない（F20：数字の文字列。**数値にしない**。16 桁を超えると `Number` で丸まる） |
| `credential.accessToken` | `^[\x21-\x7E]{1,2048}$`（空白・制御文字・非 ASCII を含まない） | クエリと form に入る。`URLSearchParams` は何でも符号化して送ってしまうので、**壊れた値を送って 190 で `failed` にするより、入口で理由つきで止める**。長さの上限は `rotatedCredential` が Core の 4096 文字に収まるため（#86） |
| Threads API が返した container ID / media ID | `^[0-9]{1,64}$` | 次の要求のパスに入る。**外から来た文字列をそのままパスへ差し込まない** |

### 6.3 container の作成（R1 / R2）

| `media` の件数 | 作るもの |
| --- | --- |
| 0 | R1：`media_type=TEXT`、`text=<composeThreadsText(post)>` |
| 1 | R1：`media_type=IMAGE`、`image_url=<media[0].url>`、`text=<composeThreadsText(post)>`、`alt_text=<media[0].alt>`（空でないときだけ） |
| 2〜10 | 子 R1 × N：`media_type=IMAGE`、`image_url=<media[i].url>`、`is_carousel_item=true`、`alt_text`（空でないときだけ。**`text` を付けない**）→ 子がすべて `FINISHED`（§6.4）→ 親 R2：`media_type=CAROUSEL`、`children=<子 ID をカンマで連結>`、`text=<composeThreadsText(post)>` → 親が `FINISHED` |

* **`text` は `composeThreadsText(post)`**（`body` に、`link` があれば改行して足したもの。§9.4）。`manual()` が intent URL に入れるものと**同じ文字列**
* **`link_attachment` を使わない**（§3.2）。本文の最初の URL が Threads のプレビューになる（F13）
* **`alt_text` を送る**（F6 に公式の引数として載っている）。`038` §6.12 は Instagram の受け口を確かめられず送らなかったが、Threads は**文書に載っている**。
  空文字・`null` のときは引数ごと付けない。長さの上限は文書に無い（§11 #9）
* **子は並行に作る。ただし同時に 5 本まで**（`CAROUSEL_CHILD_CONCURRENCY = 5`。`038` §6.3 と同じ理由）
* **子の 1 つが失敗したら、残りの子の要求を打ち切る**（共通の `AbortController` を子の signal に混ぜる）。結果は §6.9 の「複数の失敗」の規則で 1 つにまとめる
* **子の順序は `media` の順を保つ**（`children` に並べるのは完了の順ではなく `media` の添字の順）
* **Meta が `image_url` を取りに来る。Torifune のサーバからは媒体の URL へ 1 本も要求を出さない**（F14。`036` / `037` の SSRF の論点はこの Plugin には無い。§8.2）
* `media` が 11 件以上は Core の `mediaMax`（と Core の `MEDIA_MAX` = 10）が弾くので来ない。来たら P0 で `false`

### 6.4 状態のポーリング（R3）— 決めたこと

container は作成の応答が返った時点ではまだ処理中のことがある。**`FINISHED` になるまで `threads_publish` を送らない。**

**固定の 30 秒は待たない**（オーケストレーター判断）。公式は「平均 30 秒待つ」（F8）と「1 分に 1 回・5 分以内の確認」（F9）を推奨するが、
Core は `publish()` を 30 秒で打ち切る（`035` §6.5.5）。30 秒を待てば**公開の要求を送る時間が残らない。**
代わりに**状態を確かめ、`FINISHED` になった時点で進む。** 準備に使える 15 秒（§6.8）で `FINISHED` にならなければ、**公開を送らずに `retryable: true`** で返す。
使われなかった container は公開されず、24 時間で `EXPIRED` になる（F9）。Core の再試行（1 → 2 → 4 → 8 分）で container から作り直す。

```text
作った container の集合 S（単体なら 1 つ、carousel なら子の N 個 → 子が揃った後に親の 1 つ）
round = 0
loop:
  S のうち FINISHED でないものについて R3 を送る（並行・同時 5 本まで）
  全部 FINISHED → 抜ける
  ERROR / PUBLISHED / EXPIRED があれば → その場で失敗（§6.9 の P3）
  round += 1
  round >= POLL_MAX_ROUNDS、または 次の round を始める前に準備期限を過ぎる → kind: 'budget'（retryable: true）
  wait(POLL_INTERVAL_MS, signal)
```

| `status` | 扱い |
| --- | --- |
| `FINISHED` | 次へ進む |
| `IN_PROGRESS` | 待って再度見る |
| `ERROR` | **失敗・`retryable: false`**。画像を取得できない・形式が違うなど、**人が `media[].url` を直すまで直らない** |
| `EXPIRED` | 失敗・`retryable: true`（公開はされていない） |
| `PUBLISHED` | **失敗・`retryable: false`。** 自分は R4 をまだ送っていないのに公開済みと言われている。**何が起きたか分からないので安全側** |
| 上記以外・項目が無い・JSON でない | 失敗・`retryable: true`（公開の要求をまだ出していない） |

* **最初の確認は作成の直後に行う**（待たずに済む場合がある）
* `POLL_INTERVAL_MS = 1_000`、`POLL_MAX_ROUNDS = 10`。**上限は回数と準備期限（§6.8）の早いほう**。
  公式の推奨（1 分に 1 回）より頻繁に問い合わせるが、1 回の配信で多くても 10 round（carousel の子を含めて並行）であり、これは §11 #3 に残す
* **待ちは注入できる `wait(ms, signal)` で行う**（§10.1）。テストが実時間を待たずに `budget` の分岐を通せるようにするため
* **`fields=status` だけを取る。`error_message`（自由文）を取らない**（F9 の例は `status,error_message`）。自由文を取らなければ外へ出す心配もない（§6.11）
* **テキストの container も同じ手順で確かめる。** テキストでも処理待ちがありうるかは文書に書かれていない。確かめて `FINISHED` なら R3 が 1 本増えるだけで、確かめずに送って失敗するより安い

### 6.5 公開（R4）

```text
POST {api}/{v}/{threadsUserId}/threads_publish
creation_id=<単体の container ID、または carousel の親 ID>&access_token=<token>
→ 200 { "id": "<media ID>" }
```

* **残り時間が `PUBLISH_REQUEST_TIMEOUT_MS` 以上あるときだけ送る。** 足りなければ送らずに `kind: 'budget'`（`retryable: true`）。
  打ち切られた R4 は「届いたか分からない」＝ `retryable: false` になるので、途中で切られる見込みの要求は**始めない**（`038` §6.5）
* **成功の候補は HTTP 200 だけ**（それ以外の 2xx は「その他」として `false`。`037` 軽微-2 の型）。応答の `id` が無い・JSON でない・本体が 64 KiB を超える → **`retryable: false`**
* 応答の `id` が §6.2 の形に合わない（**数値型・空文字・65 桁以上**を含む）→ **失敗にしない。** `externalId` も `externalUrl` も付けずに `{ ok: true }`。R5 を呼ばない（§6.6）。
  **200 と `id` が返った以上、公開されている。** 失敗にすると出し直しで二重投稿になる（`036` 低-1 の型）

### 6.6 戻り値の組み立て（R5）

```ts
{
  ok: true,
  externalId: mediaId,              // §6.5 の形の検査に通ったときだけ
  externalUrl: permalink,           // R5 が返し、下の検査に通ったときだけ
  rotatedCredential: { … },         // §6.7 で延長できたときだけ
}
```

* **`externalId` は R4 の `id`**（`^[0-9]{1,64}$`。`social_posts.external_id` の 200 文字の CHECK に必ず収まる）
* **`externalUrl` は R5 の `permalink` を、返った値のまま使う。自前で組み立てない。** 例は `threads.net` と `threads.com` が混在しており（F17）、ユーザーネームとショートコードの両方が要るので、
  組み立てると**ドメインの移行や URL の形の変更に Plugin が追従し損ねる。** 載せる前に次をすべて確かめ、1 つでも外れたら `externalUrl` を付けない（`externalId` は残す）：
  * `new URL()` に通る・`https:`・`username` / `password` を含まない
  * ホスト名が `threads.net` / `threads.com` か、`.threads.net` / `.threads.com` で終わる
  * **2048 文字以内**（`social_posts.external_url` の CHECK）
* **R5 は公開の後の要求である。何が起きても `ok: true` を覆さない。** 失敗・制限時間・形の不一致・`permalink` が返らない（F17：著作権などで省かれる）は `externalUrl` を省くだけ（`logger.warn` は出す）
* **R5 は残り時間が `PERMALINK_TIMEOUT_MS` 以上あるときだけ送る**

### 6.7 トークンの延長（R6。`rotatedCredential`）— 決めたこと

**`038` §6.7 と同じ規則にする。公開に成功した後で、期限が近ければ延長し、新しいトークンと期限を `rotatedCredential` で返す。**

```text
公開に成功（R4 が 200 と id を返した）
  → R5（permalink）
  → expiresAt = parseExpiry(credential.accessTokenExpiresAt, now)   // 読めない・61 日より先 → 'unknown'
  → shouldRefresh = expiresAt === 'unknown' || expiresAt - now < TOKEN_REFRESH_THRESHOLD_MS（30 日）
  → shouldRefresh かつ 残り時間 ≥ REFRESH_TIMEOUT_MS なら R6
  → R6 が 200 で access_token が §6.2 の形に合う
       → rotatedCredential = {
            threadsUserId: credential.threadsUserId,                  // そのまま
            accessToken: <R6 の access_token>,
            accessTokenExpiresAt: <now + expires_in 秒 の ISO 文字列、読めなければ 'unknown'>,
          }
     それ以外 → rotatedCredential を付けない（logger.warn）
```

* **延長は公開の「後」**（`038` §6.7 の 2 つの理由：`rotatedCredential` は `ok: true` にしか載らない／延長の失敗を投稿の成否に混ぜない）
* **閾値は残り 30 日**。延長できるのは**配信が成功したときだけ**なので、月 1 回の配信でも窓に入る幅を取る（`038` §9.4 の 3）
* **延長の口は「発行から 24 時間以上」のトークンしか受けない**（F5）。残り 30 日未満のトークンは必ず発行から 30 日以上たっているので、**期限が分かっていれば延長の失敗は起きない。**
  期限が `unknown` で発行直後のトークンだけが R6 で断られうる。その場合は `rotatedCredential` を付けず `logger.warn` を出すだけで、**次に成功した配信でもう一度試みる**
* **R6 が同じ文字列を返しても書き戻す**（F5：新しい文字列かどうかは文書に無い）。期限は延びているので、`accessTokenExpiresAt` を更新する意味がある。
  値が同じかを Plugin は比べない（比べる必要が無い。書き戻しは Core の監査に 1 行残るだけ）
* **`rotatedCredential` のキーは `credentialFields` の 3 つちょうど**。`...credential` で写さず、**3 つを明示して組む**（`038` §6.7）
* **新しいトークンの形を確かめる**（§6.2 の `accessToken` と同じ形、2048 文字以内）。合わなければ返さない
* `expires_in` は正の整数で **61 日以下**のときだけ期限に使う。それ以外は `'unknown'` を書く（トークンは書き戻す）
* **期限が既に過ぎている**トークンは、そもそも R1 が 190 で失敗する（§6.9）。F5 のとおり**失効したトークンは延長できない**ので、人が発行し直す
* **R6 の URL にはトークンが入る**（§6.2）。この URL を `logger` にも `reason` にも渡さない。例外の文面も載せない（§6.11）

**Core の書き戻しは比較更新である（`039` §6.1）。** 返した `rotatedCredential` は、次のどれかなら**保存されない**：
配信の間に運用者が資格情報を変えた・消した（同じ値を入れ直した場合を含む）／宣言と合わない／Core の書き戻しが例外で失敗した。
どの場合も**投稿の結果は `published` のまま**で、Core が `log.warn` か `log.error` を出す。この Plugin は保存されたかを知らない（知る口が無い）。

* **捨てられた場合、延長の口が古いトークンを即座に無効にするかで帰結が変わる**（F5 に書かれていない。§11 #10）。
  運用者が別のトークンに差し替えていれば、そちらが正なので問題は無い。**運用者が同じトークンを入れ直していた**場合に限り、
  延長で古いトークンが無効になっていれば、保存されているのは無効なトークンになり、次の配信は 190 で `failed`（理由に「発行し直し」）になる。**黙っては失敗しない**

### 6.8 制限時間と `signal`

Core は `publish()` を **30 秒**で打ち切り、**結果不明として `failed`** にする。**この Plugin は自分で早く諦める。**

| 定数 | 値 | 何に渡るか |
| --- | --- | --- |
| `PUBLISH_TOTAL_BUDGET_MS` | 25 秒 | `publish()` 全体。**入口で 1 つ作り、すべての要求の外側の signal に混ぜる**（`036` R-2） |
| `PREPARE_BUDGET_MS` | 15 秒 | 準備（R1 / R2 / R3 と待ち）。= 合計 − `PUBLISH_REQUEST_TIMEOUT_MS` |
| `CREATE_CONTAINER_TIMEOUT_MS` | 10 秒 | R1 / R2 の 1 本ごと |
| `STATUS_TIMEOUT_MS` | 5 秒 | R3 の 1 本ごと |
| `POLL_INTERVAL_MS` | 1 秒 | R3 の round のあいだの `wait` |
| `POLL_MAX_ROUNDS` | 10 | R3 の round の上限 |
| `PUBLISH_REQUEST_TIMEOUT_MS` | 10 秒 | R4 |
| `PERMALINK_TIMEOUT_MS` | 3 秒 | R5 |
| `REFRESH_TIMEOUT_MS` | 3 秒 | R6 |
| `CAROUSEL_CHILD_CONCURRENCY` | 5 | R1（子）と R3 の同時本数 |

* **外側の signal** ＝ `AbortSignal.any([input.signal, AbortSignal.timeout(PUBLISH_TOTAL_BUDGET_MS)])`。
  **準備の signal** ＝ `AbortSignal.any([外側, AbortSignal.timeout(PREPARE_BUDGET_MS)])`。
  **要求ごとの signal** ＝ `AbortSignal.any([外側または準備の signal, AbortSignal.timeout(その要求の定数)])`
  （carousel の子には、さらに子どうしで共有する打ち切り用の signal を混ぜる。§6.3）
* **期限の判定は注入できる `now()` で数える**（`038` §6.8）。「次の round を始めるか」「R4 を送るか（残り ≥ 10 秒）」「R5 / R6 を送るか（残り ≥ 3 秒）」は入口で記録した `now()` からの経過で決める。
  **境界はちょうど**：経過が `PREPARE_BUDGET_MS` ちょうどなら次の round を始めない（`037` 軽微-3 の型。#79）
* **R4 は準備の signal ではなく外側の signal の下で送る**（準備期限で公開の要求を切らない）
* **最悪の形でも 25 秒 ＋ 結果の組み立てで返る**（Core の 30 秒との差 5 秒は、打ち切りを検知して返すための余白）
* **どの定数がどの要求へ渡るかは固定する**（`036` R-3。#80）。**R4 と R1 はどちらも 10 秒なので、値の入れ替えは値の比較では見分けられない**（`037` 検証 §1 の注）。
  結線は「要求ごとに作った controller（signal）がどの期限と混ざっているか」で確かめる（#80・#81）
* **`input.signal` が発火したら、その場で処理をやめて `publish()` を抜ける**（Core は既に結果を確定させている）

### 6.9 `retryable` の基準 — Threads API の応答への対応づけ

契約は「**送る前に失敗したなら `true`、届いたか分からないなら `false`、迷ったら `false`**」（ガイド §9）。
Threads で「送る」に当たるのは **R4（`threads_publish`）の 1 回だけ**である。

> **container は投稿ではない。** R1 / R2 で作った container は、R4 を送らない限り**誰にも見えず、公開もされず、24 時間で `EXPIRED` になる**（F9）。
> したがって container を作った後に失敗して作り直しても、**二重投稿にはならない**。

> **支配的な規則（これだけ覚えればよい）**
>
> 1. **R4 を送る前の失敗は既定で `retryable: true`。** ただし**時間が経っても直らないもの**（資格情報・権限・投稿の内容・ポリシー）は `false`
> 2. **R4 を送った後の失敗は既定で `retryable: false`。** ただし**レート制限（書き込む前に断られたと読める）だけ `true`**
> 3. **R4 が成功した後に起きたことは、`ok: true` を覆さない**（R5 / R6）

**Threads API のエラーの分類**（応答の本体 `{ "error": { … } }` から読むのは**数値の `code`・`error_subcode` と真偽値の `is_transient` だけ**。F18：封筒は推定）：

| 分類 | 条件（上から順に判定） |
| --- | --- |
| `rateLimit` | HTTP 429、または `code` ∈ {4, 17, 32, 341, 613} |
| `token` | `code` = 190 |
| `permission` | `code` = 10、または 200 ≤ `code` ≤ 299 |
| `rejected` | `code` ∈ {368, 506}（ポリシー違反・重複） |
| `transient` | `is_transient === true` |
| `other` | 上のどれでもない（`code` が数値でない・`error` が無い・JSON でないを含む） |

| # | フェーズ | 起きたこと | `retryable` | 理由 |
| --- | --- | --- | --- | --- |
| P0 | `input` | `threadsUserId` / `accessToken` が §6.2 の形に合わない | **false** | 人が資格情報を直すまで直らない。**外へ 1 本も出さない** |
| P0 | 〃 | `media` が 11 件以上（Core が見ているので通常来ない） | **false** | 投稿の内容。外へ出さない |
| P0 | 〃 | `validate()` と同じ本文の検査（§9.2 の 1・2・4）に通らない（配信直前の再検査が見ているので通常来ない） | **false** | 同上。**送れば断られるだけの container を作らない** |
| P1 | R1 / R2（container 作成） | 接続できない・自前の制限時間・5xx | **true** | 公開の要求をまだ出していない |
| P1 | 〃 | `rateLimit` | **true** ＋ `retryAfterMs`（§6.10） | 同上 |
| P1 | 〃 | `transient` | **true** | Threads API 自身が一時的と言っている |
| P1 | 〃 | `token`（190） | **false** | トークンが無効・期限切れ。**人が発行し直すまで直らない** |
| P1 | 〃 | `permission` | **false** | `threads_content_publish` が無いなど |
| P1 | 〃 | `rejected` | **false** | ポリシー・重複。同じ内容を送り直しても同じ |
| P1 | 〃 | その他の 4xx（画像を取得できない・形式が違う・リンクが多すぎるなど） | **false** | 投稿の内容。人が直す |
| P1 | 〃 | 3xx | **false** | 追わない（§6.2） |
| P1 | 〃 | 200 だが JSON でない・本体が 64 KiB を超える・`id` が無い・`id` が形に合わない・200 以外の 2xx | **true** | **次の要求を出していない。** container ができていても公開されない |
| P2 | R3（ポーリング） | 接続できない・制限時間・5xx・`rateLimit`・`transient`・形が読めない | **true** | 読むだけの要求 |
| P2 | 〃 | `token` / `permission` / `rejected`・その他の 4xx・3xx | **false** | P1 と同じ規則。**迷ったら `false`**（`038` §6.9 P2 の書き戻しと同じ） |
| P3 | 状態 | `ERROR` | **false** | 画像の問題。人が直す |
| P3 | 〃 | `EXPIRED` / 知らない値 | **true** | 公開されていない |
| P3 | 〃 | `PUBLISHED`（自分はまだ R4 を送っていない） | **false** | 何が起きたか分からない。**迷ったら `false`** |
| P3 | 準備期限 | `IN_PROGRESS` のまま準備期限・`POLL_MAX_ROUNDS` に達した（`kind: 'budget'`） | **true** | 公開の要求をまだ出していない（§6.4） |
| P3 | 〃 | R4 を送るだけの残り時間（10 秒）が無い（`kind: 'budget'`） | **true** | **送らずに諦める**（§6.5） |
| P4 | R4（`threads_publish`） | `rateLimit` | **true** ＋ `retryAfterMs` | **書き込む前に断られたと読める**（`038` P4 と同じ） |
| P4 | 〃 | 接続断・制限時間・5xx・3xx・その他の 4xx（`token` / `permission` / `rejected` / `transient` を含む）・200 以外の 2xx・JSON でない・本体が 64 KiB を超える・`id` が無い・**ヘッダを受け取った後で本体の読み込みが打ち切られた** | **false** | **届いたか分からない。SNS の投稿は取り消せない**（`038` 軽微-2：本物の `fetch` はヘッダの後の abort で本体の読み込みも reject する） |
| P5 | R5 / R6 | 何が起きても | —（`ok: true` のまま） | 公開は済んでいる。`externalUrl` / `rotatedCredential` を省くだけ |
| — | どこでも | 予期しない例外 | **R4 の前なら true／後か不明なら false** | **例外を投げない。** 「R4 を送ったか」を 1 つの変数で持って分類する（`038` §6.11）。**R4 の後の予期しない例外は、今の設計では到達する経路が無い。その分岐を「検証済み」と名乗るテストを作らない**（`038` 軽微-1。#65） |
| — | どこでも | `input.signal` が発火 | — | Core が「結果不明」として確定させている |

* **P4 の `transient` を `true` にしない**（「もう一度送れば通るかもしれない」は「今回は公開されていない」を言っていない）
* **1 日の公開数の上限（F16：250 件）がどの `code` で返るかは確かめられなかった**（`038` の 2207042 に当たる値が Threads の文書に無い）。
  `rateLimit` の `code` で返れば `true` になり、Core の再試行の上限（5 回）を使い切って `failed` になる。**投稿はされていない**（書き込む前に断られた）。§11 #8
* **P1 の `token` を `false` にするのは、ガイドの表（「まだ送っていない認証エラーは `true`」）より狭い。** `036` / `038` と同じ理由（直らない・`failed` が 15 分遅れるだけ）

**複数の失敗（carousel の子）。** `038` §6.9 と同じ：子どうしの打ち切りで止まったものは失敗に数えない。
`retryable` は**すべての失敗が `true` のときだけ `true`**、`reason` と `logger` に使うのは **`retryable: false` の失敗のうち `media` の添字がいちばん小さいもの**、無ければ添字がいちばん小さい失敗。

### 6.10 `retryAfterMs`

レート制限の応答に **`Retry-After`（秒の整数）**があれば、それをミリ秒にして返す。

* ヘッダが無い・64 文字を超える・正の整数でない → **`retryAfterMs` を付けない**（Core の既定 1 → 2 → 4 → 8 分）
* **`X-Business-Use-Case-Usage` などの Meta の使用量ヘッダは読まない**（`038` §6.10 は読んだが、**Threads の文書にこれらのヘッダの記述が無い**。形を確かめられないヘッダを解釈しない。§11 #8）
* **Core が 24 時間で切り詰める**（`035` §5.6.2）。Plugin 側で丸めない
* ヘッダの値は計算にだけ使い、**`reason` にもログにも載せない**

### 6.11 例外を投げない・外へ出す範囲

* **`publish()` は例外を投げない。** すべての経路を `try` で包み、`PublishResult` として返す
* **`reason` に載せてよいもの**（これ以外は載せない）：
  * フェーズの言葉（「投稿の準備」「画像の処理」「公開」など、固定の日本語）
  * **HTTP の status**（数値）
  * **既知の `code` と `error_subcode`**（数値。下の集合に含まれるものだけ。含まれなければ `unknown`）
  * 固定の案内文
* **載せないもの**：`error.message` / `error.error_user_title` / `error.error_user_msg` / `error.type` / `fbtrace_id` / container の `error_message`（取らない。§6.4）/
  応答の本文 / **要求の URL**（R3 / R5 / R6 の URL にはトークンが入る）/ **要求の本体**（R1 / R2 / R4 の本体にはトークンが入る）/ 例外の `message`
* **理由**：Graph API 系の自由文は**要求の値をそのまま混ぜ返すことがある**。Core の伏せ字は **4 文字以上の完全一致しか消せない**（ガイド §9）。
  **しかもこの Plugin はトークンを URL と本体に載せる**（§6.2）ので、URL や本体の断片がエラーの文面・例外の `message` に混ざれば、**符号化されたトークンが伏せ字を素通りしうる。** 伏せ字を当てにせず、載せない
* **既知の `code` の集合**：{1, 2, 4, 10, 17, 24, 32, 100, 190, 200〜299, 341, 368, 506, 613}。**既知の `error_subcode` の集合**：{458, 459, 460, 463, 464, 467, 492}（トークンとセッションに関わるもの。F18）。
  集合は `threads-api.ts` の 1 か所に置き、テストはその定数を読む。**数値でない `code`（`"THREADS_API__LINK_LIMIT_EXCEEDED"` のような文字列を含む）は `unknown`**
* **`reason` の例**：
  * `Threads のアクセストークンが無効か期限切れです（HTTP 400 / code 190）。長期アクセストークンを発行し直し、/social のアカウントの「資格情報を設定」から入れ直してください。`
  * `Threads が画像を処理できませんでした（container の状態 ERROR）。media の URL が、インターネットから取得できる 8MB 以下の JPEG か PNG の画像を指しているか確かめてください。`
  * `Threads の処理が時間内に終わりませんでした（投稿の準備）。公開はしていません。再試行します。`
  * `Threads の公開の結果が分かりません（公開、HTTP 500）。二重に投稿しないよう再試行しません。Threads 側で投稿されたか確かめてください。`
* **`logger` に渡してよいもの**：`postId` / `attempt` / フェーズ名 / HTTP status / 既知の `code` / 既知の `error_subcode` / 媒体の件数 / 投稿の形（`text` / `image` / `carousel`）/ ポーリングの round 数 /
  **`fbtrace_id`（`^[A-Za-z0-9_-]{1,64}$` に合うときだけ）**
* **`logger` に渡さないもの**：`credential` の 3 つの値、`threadsUserId`、`post.body`、`post.link`、`media[].url`、`media[].alt`、container ID、media ID、`permalink`、応答の本文、要求の URL・本体、ヘッダ、`account.handle`

### 6.12 `link` / `alt` / 動画（黙って捨てない）

| 項目 | 扱い | 理由 |
| --- | --- | --- |
| `link` | **本文の末尾へ改行して足す**（`composeThreadsText`。自動・手動とも同じ） | Threads は本文の URL をリンクにし、最初の URL をプレビューにする（F13）。**数えるのも足した後の文字列**なので、`036` §6.8 が避けた「数えた本文と送る本文の食い違い」は起きない。`link_attachment` を使わない理由は §3.2 |
| `media[].alt` | **`alt_text` として送る**（空なら送らない） | 公式の引数（F6）。`038` / `037` は送らなかったが、理由（受け口が未確認／要求と料金が増える）が Threads には当たらない |
| 動画 | **扱わない**（§3.2）。動画の URL を渡されたら Threads が `IMAGE` として処理できずに失敗する（P1 / P3 の `false`） | 画像か動画かを Plugin が知る手段が無い（拡張子で判定する案は `036` §9.3 と同じ理由で採らない） |

### 8.2 高権限であることの自覚

* この Plugin は `social_accounts` に登録された **Threads の長期アクセストークンを平文で受け取る**（`publish()` の `credential`。その呼び出しの間だけ）
* **トークンの送り先は `graph.threads.net` に固定**（§5.3）。設定で変えられる口を作らない

  README に「外向きの要求の URL を記録する仕組みを足すときはクエリを伏せる」と書く（`038` の security 低-2 と同じ）
* **トークンを延長して Core へ返す**（§6.7）。返したものは Core が比較更新で書き戻し、監査ログ（`rotated: true`）を残す。Plugin は保存しない
* **媒体の URL（`media[].url`）は Meta へ渡すだけで、Torifune のサーバから取りに行かない**（F14）。`social.write` を持つ者が私有アドレスを指しても、
  Torifune の内部ネットワークへの要求は発生しない。代わりに **`media[].url` は Meta へ送られる**（署名付き URL のクエリ文字列を含めて）。README に書く
* **`manual()` は資格情報を受け取らない**（`ManualInput` に無い）。返す URL のクエリに本文が乗り、ブラウザの履歴と Threads のアクセスログに残る（`035` §11 #15。本文は公開する前提の文章）

### 9.1 `limits`

**`limits: { mediaMax: 10 }`。`bodyMaxLength` と `mediaRequired` を宣言しない。**

* **`bodyMaxLength` を宣言しない。** 本文の判定は `validate()` が §9.4 の数え方で**正確に（多めの側に）**行い、登録時に数と理由つきで 422 にする。
  `bodyMaxLength` は Core の `String.length`（UTF-16）で数える粗い上限で、置くなら「Threads の数え方に対して必ず緩い側」でなければならない（`036` §9.2）。
  §9.4 の数え方は `String.length` 以上になるので `500` を置いても `validate()` より厳しくはならないが、**後で実機の確認を経て `validate()` を緩めたとき**（§11 #2）、
  `bodyMaxLength: 500` が**黙って `validate()` より厳しい側に残る**。二重に書いた判定の片方だけが直る形を作らない（`035` §6.1.2 の注と同じ理由）。
  粗い上限は Core 自身の `POST_BODY_MAX_LENGTH`（10,000）が既に掛けている
* **`mediaMax: 10`**。Threads の carousel は 20 件まで受ける（F10）が、**Core の `MEDIA_MAX` が 10**（投稿の API の上限）なので、10 を超える値を宣言しても意味が無い。
  20 件に広げるのは Core の変更（§11 #5）
* **`mediaRequired` を宣言しない**（テキストだけの投稿ができる）
* **`PublisherLimits` にキーを足さない**（キーを足すのは Core の変更）

### 9.2 `validate()`

**5 秒で打ち切られる。外部へ問い合わせない。同期で返す。例外を投げない。**
**本文に関する判定はすべて `threads-text.ts` の `checkThreadsText(post)` から来る。**

| # | 検査 | `field` | 文言の趣旨 |
| --- | --- | --- | --- |
| 1 | `composeThreadsText(post)` に**対になっていないサロゲート**がある | `body` | `本文に扱えない文字が含まれています。`（あれば 2・3 を数えない） |
| 2 | `composeThreadsText(post)` の長さ（§9.4 の数え方）≤ **500** | `body` | `Threads の本文は500文字以内にしてください（絵文字は1つを UTF-8 のバイト数で数えるため、多くは4文字以上になります。link を指定した場合はそれも含みます）。いまは N です。` |
| 3 | `composeThreadsText(post)` の中の**異なる URL の数** ≤ **5** | `body` | `Threads の投稿に含められるリンクは5本までです（本文の URL と link を合わせて数えます）。いまは N 本です。` |
| 4 | `deliveryMode === 'manual'` のとき、`buildThreadsIntentUrl(post)` の長さ ≤ **2048** | `body` | `投稿画面の URL が長くなりすぎます。本文を短くしてください。` |
| 5 | `providerOptions` にキーがある | `providerOptions.<key>` | `<key> は Threads では使いません。` |

* **1〜4 は自動・手動とも同じ文字列（`composeThreadsText`）を見る。** 自動なら R1 / R2 の `text`、手動なら intent URL の `text` に入る文字列そのもの
* **4 が要る理由**：Core は `manual()` が返した URL を `isValidManualUrl`（2048 文字以内）で見て、長ければ画面で `invalid_url` にする（`035` §6.6）。
  Web Intent の長さの上限は文書に無い（F19）ので、**Core の上限に合わせて登録時に断る**。日本語 1 文字は percent-encoding で 9 文字になるので、**500 文字以内の本文でも 2048 を超えうる**（日本語でおよそ 223 文字）。
  自動（`auto`）では 4 を見ない（`037` §9.2 の 3 と同じ）。§11 #13
* **媒体の枚数・`media[].url` の形・`alt` の長さは見ない**（Core の `mediaMax` / `isValidMediaUrl` / `MEDIA_ALT_MAX_LENGTH`（1000）。`alt_text` の Threads 側の上限は §11 #9）
* **`link` を断らない**（本文に足す。§6.12）
* **ハッシュタグ・メンションの数を見ない**（Threads の文書に上限が無い）
* 複数の違反は**すべて**返す。`providerOptions` / `media` / `link` / `body` は**型を確かめてから触る**（外から来た任意の JSON。循環参照もありうる）
* `deliveryMode` が `'manual'` でも `'auto'` でも 1〜3・5 は同じ（手動でも Threads の画面で送信できない本文は断る）

### 9.4 本文の数え方（決めたこと。オーケストレーター判断）

**公開されているのは「500 文字」と「絵文字は UTF-8 のバイト数」だけである（F12）。公開されていない部分は、多めに数える側に倒す。**
多く数えれば、Threads が受ける本文を**登録の時点で断る**ことはあっても、Torifune が通した本文が**配信の時刻に Threads で断られる**ことは起きない（`035` §6.1.2 が最も避けたいこと）。

```text
countThreadsLength(text):
  1. 正規化しない（NFC にも NFD にもしない）
  2. Intl.Segmenter（granularity: 'grapheme'）で grapheme に分ける
  3. 各 grapheme について
       絵文字の grapheme なら → その grapheme 全体の UTF-8 のバイト数（TextEncoder）
       それ以外           → その grapheme の UTF-16 の長さ（String.length）
  4. 合計
```

**絵文字の grapheme**：次のコードポイントを 1 つでも含む grapheme。

* `\p{Extended_Pictographic}`（絵文字の本体。`©` `®` `™` などの記号も含む）
* `\p{Regional_Indicator}`（国旗の組）
* `\p{Emoji_Modifier}`（肌の色）
* U+FE0F（絵文字の表示を求める異体字セレクタ）、U+20E3（キーキャップ）
* U+E0020〜U+E007F（タグ文字。地域の旗）

| 公開されていない点 | この数え方 | 多めに倒れる理由 |
| --- | --- | --- |
| 絵文字以外を何で数えるか（UTF-16 / コードポイント / grapheme） | **UTF-16 の長さ** | UTF-16 の長さは、コードポイントの数・grapheme の数のどちらよりも**小さくならない** |
| 正規化するか | **しない** | 分解された文字（`e` ＋ U+0301）は正規化しないほうが長い。Threads が正規化して数えても、しないで数えても、この数え方以上にはならない |
| 何を「絵文字」とみなすか | **広く取る**（上の 5 種を 1 つでも含めば grapheme 全体をバイト数で） | 同じ grapheme では UTF-8 のバイト数 ≥ UTF-16 の長さ。**広く取るほど多く数える**。ZWJ（U+200D）で繋いだ家族の絵文字は grapheme 全体（25 バイト）で数える |
| URL を 500 に数えるか | **数える**（本文の文字として、URL も同じ規則で） | 数えないより多い。X の 23 のような短縮の規則は文書に無い |

* **この数え方は `String.length` を下回らない**（どの grapheme でも UTF-8 のバイト数 ≥ UTF-16 の長さ）。§9.1 の議論の前提
* **代償**：Threads が「絵文字以外は grapheme で数える」「`©` を絵文字とみなさない」なら、Threads が受ける本文を断ることがある（例：分解された文字が多い本文・`©` を多用する本文）。
  日本語・英語の普通の本文（絵文字以外）では 1 文字 1 と数えるので影響は小さい。§11 #2
* **`Intl.Segmenter` の grapheme の区切りは Node の ICU の版に依る。** 区切りが変わっても、各 grapheme の UTF-16 の長さの合計は変わらず、絵文字の判定は「含むか」で決めるので、
  **区切りの違いで数えが大きく変わるのは、絵文字と非絵文字が同じ grapheme に入る場合だけ**（その場合も多めの側に倒れる）
* 対になっていないサロゲートを含む本文は数えない（§9.2 の 1 で先に断る。`TextEncoder` は U+FFFD の 3 バイトに置き換えて数えてしまう）

**URL の数え方**（`countThreadsLinks`。§9.2 の 3）：

* `037` §9.4 の 2（検証 中-1 で直した規則）と同じ：`https?://`（大文字・小文字を問わない）で始まり、**ASCII の表示文字（`[\x21-\x7E]`）が続く限り**の並びを URL とする。
  末尾の `.,;:!?)]` を外し、`https://` だけが残ったものは URL と数えない
* **異なる URL の数**を返す。**同じかどうかは文字列の完全一致**で決める（大文字・小文字・末尾の `/` の違いは別の URL として数える＝多めの側）
* **`https://` の無いドメイン（`example.com`）を URL と数えない。** Threads がそれを数えるなら少なく数えることになる（§11 #2 の (b)）。TLD の表を Plugin に持たせない（`037` §11 #3 と同じ判断）

### 9.5 `manual()`

```ts
manual({ post }): ManualHandoff {
  return buildThreadsManualHandoff(post);   // { url: buildThreadsIntentUrl(post), note: THREADS_MANUAL_NOTE }
}

buildThreadsIntentUrl(post) === `${THREADS_INTENT_BASE_URL}?text=${encodeURIComponent(toWellFormedText(composeThreadsText(post)))}`
```

* **宛先は `https://www.threads.com/intent/post`**（F19。公式の文書の宛先。`threads.net` ではない）
* **`url=` の引数を使わず、`link` を `text` に入れる**（`037` §9.4 と同じ理由）。`url=` は「リンクの添付」で、**画面でどう見えるかを Threads が決める**。
  **Torifune が数えた文字列（`composeThreadsText`）と、画面に入る文字列を一致させる**には、自分で繋いで `text` に入れるしかない。自動配信とも同じ文字列になる（#44）
* **`tag` / `reply_control` などの他の引数を使わない**（§3.2）
* **対になっていないサロゲートで例外を投げない**（`037` #93）。`buildThreadsIntentUrl` は片割れを **U+FFFD に置き換えてから** `encodeURIComponent` に渡す。
  `manual()` は `validate()` を通っていない投稿でも呼ばれうる（Plugin が無効な間に登録された予約）ので、そこでも投げない。
  判定と置き換えは正規表現で書く（`String.prototype.isWellFormed` / `toWellFormed` は `tsconfig` の `lib` に型が無い。`037` §9.4）
* **`THREADS_MANUAL_NOTE`**：`Threads の投稿画面が開きます。内容を確かめて投稿してください。画像を添える場合はその画面で添付してください。`
  （`036` §9.4 の学び：「画像は投稿画面で添付してください」と断定すると、手動投稿に `media` を付けられない（Core の f）ことと合わせて「付けた画像が落ちた」と読まれる）
* **`store` を読まない・`await` しない・例外を投げない・`fetch` しない。** 2 秒で打ち切られ、1 画面で最大 50 行ぶん呼ばれる（ガイド §9）
* **`account` を使わない。** Web Intent はブラウザでログイン中のアカウントで開く。どのアカウントかを指定できない
* 返す URL は Core の `isValidManualUrl`（https・資格情報なし・2048 文字以内）に通る（長さは §9.2 の 4 で登録時に保証する。#40）

### 9.6 `plugins/sns-threads/README.md`

次を書く（英語の併記は他の SNS Plugin の README に揃えて書かない）。

* この Plugin がすること：予約した投稿を Threads へ自動配信する／手動投稿（投稿画面を開く）にも対応する
* **Threads のアカウントと、Meta の開発者向け画面で作った App が要る**。`threads_basic` と `threads_content_publish` の権限を持つ**長期アクセストークン**を発行する手順の概略（短期トークン → 長期トークンへの交換）。
  ユーザー ID の確かめ方（`/me` を問い合わせる。**数字だけの ID で、ユーザーネームではない**）
* **トークンは 60 日で失効する。Torifune が延長するのは、配信が成功したときだけ**（残り 30 日を切っていれば）。
  **30 日以上配信しない期間があると、そのまま失効しうる。失効したトークンは延長できない**ので、発行し直して `/social` の「資格情報を設定」から入れ直す
* `accessTokenExpiresAt` が分からなければ `unknown` と入れてよいこと。**発行から 24 時間たたないうちの最初の配信では延長に失敗することがあり、次の配信で延長される**こと
* **配信中に資格情報を入れ直すと、その配信で延長したトークンは保存されない**（入れ直した値が正になる。`039` §6.1）
* 画像は **Torifune が預からない**。`media[].url` は **インターネットから取得できる 8MB 以下の JPEG か PNG の https URL** であること。**その URL は Meta へ送られる**こと
* 画像は 0〜10 枚（2 枚以上で carousel）。**動画は扱わない**（動画の URL は登録時には断られず、配信時に失敗する）
* `alt`（代替テキスト）は Threads へ送られること
* 本文は 500 文字まで。**絵文字は 1 つを UTF-8 のバイト数（多くは 4）で数える**。**Torifune は数え方の分からない部分を多めに数えるので、Threads が受ける本文を断ることがある**。
  `link` は本文の末尾に改行して足され、**本文と合わせて数える**。**リンクは本文の URL と `link` を合わせて 5 本まで**
* **手動投稿**の流れ（予約時刻に `/social` の「手動投稿待ち」に並ぶ → 「投稿画面を開く」→ Threads で送信 → 「投稿した」を押す）。**手動投稿には画像を付けられない**（投稿画面で添付する）。
  **手動投稿では、日本語の多い本文は短めにする**（投稿画面の URL が長くなりすぎると登録時に断られる）
* 公開の前の処理待ちは**最大でおよそ 15 秒**しか待たない。間に合わなければ公開せずに再試行する（何度も続けば `failed`）。§11 #3
* Threads には **24 時間あたりの公開数の上限**があること（数値は書かない。`038` §11 #7 と同じ）
* **Plugin を無効にしている間は、アカウントの SNS の表示が「threads」になる**こと。資格情報の入れ直しは Plugin を有効にしてから行う（§7）
* 導入してから資格情報を入れるまでの猶予は**約 24 時間**（`035` 裁定 #9）
* 使っている Threads API の宛先と版（`graph.threads.net` / `THREADS_API_VERSION` の値）と、版が変わったら Plugin の更新が要ること
* **トークンは Threads API への要求の URL（クエリ）と本体に載る**。**外向きの要求の URL を記録する計測・プロキシを足すときは、クエリを伏せる**こと（§8.2）
* 再ビルドが要ること（`plugins/` に置いてから `/plugins` で導入 → 再ビルド・再起動）
* 他の Plugin とコードを共有していないこと（`sns-instagram` と似た作りだが独立している。§4.2）

| 8 | **1 日の公開数の上限（250 件。F16）がどのエラーで返るか確かめていない。** `Retry-After` 以外の使用量ヘッダを読まない（§6.10）。`threads_publishing_limit` を使わない | `rateLimit` の `code` で返れば、`retryAfterMs` 無しで Core の既定の間隔で 5 回再試行して `failed`（投稿はされない）。その他の 4xx なら `false` で即 `failed`。どちらでも二重投稿にはならない。実機で確かめ、問題なら `reason` の案内か、残数の問い合わせを足す |
| 9 | **`alt_text` の長さの上限を確かめていない**（§6.3）。Core は 1000 文字まで受ける | 送る。上限を超えて Threads が断れば、R1 が 4xx で `false`（投稿はされない。配信時に初めて分かる）。上限が分かったら `validate()` に足す（登録時に断る） |
| 10 | **延長の口が古いトークンを即座に無効にするか、同じ文字列を返すことがあるかを確かめていない**（F5） | どちらでも動くように書いた（§6.7：返った値を保存し、`expires_in` から期限を出す）。`039` の比較更新で書き戻しが捨てられ、かつ古いトークンが無効になる組み合わせでは、次の配信が `token` で `failed` になる（黙らない） |
| 11 | **実機の Threads で一度も動かしていない**（`036`〜`038` と同じ限界）。特に次の前提が未確認：①**`Authorization: Bearer` を使わず `access_token` を引数で渡す**形で全要求が通ること（文書の例はこの形）、②`permalink` のドメイン（`threads.net` か `threads.com` か。両方を受けるようにした）、③延長で新しい文字列が返るか（#10）、④**エラーの封筒が Graph API と同じ形か**（`code` / `error_subcode` / `is_transient`。§6.9 の分類の前提。形が違えば、分類はすべて `other` に落ち、R4 の前なら 4xx は `false`・5xx は `true`、R4 の後は `false`＝安全側に倒れる）、⑤テキストの container にも処理待ちがあるか（§6.4）、⑥`graph.threads.net` が `v1.0` のパスを受けること | 受け入れ条件はすべて偽の Threads API とループバックで閉じる。§10.13 は「偽物が本物の `fetch` と同じに振る舞う」ことまでしか保証しない。**Threads のアカウントと本物のトークンでの疎通は運用者の手で確かめる**（検証レポートの「残る限界」に書く） |
| 12 | **`sns-instagram` と似たコードを別々に持つ**（§4.2。`token.ts` はほぼ同じ中身） | 一致をテストで強制しない（別の SNS で振る舞いを揃える理由が無い）。Plugin 同士でコードを共有する口を Core に作るかは、`037` §11 #13 と合わせて要望が重なってから |
| 13 | **Web Intent の URL の長さの上限が文書に無い**（F19）。Core の 2048 に合わせて登録時に断る（§9.2 の 4） | 日本語が多い本文（およそ 223 文字を超える）は、500 文字以内でも**手動投稿では登録できない**。自動なら通る。Threads 側が 2048 より長い URL を受けるとしても、Core の `isValidManualUrl` が 2048 を上限にしている（`035` §6.6）ので、これ以上は Plugin では広げられない。広げるなら Core の変更 |
| 14 | **テストの共有定義の置き場**（#93）。`apps/web/src/test-support/threads-api.ts` を足す | `038` §11 #14・`037` §11 #14 と同じく「Core を変えない」の範囲内とする（本番のコードからは読まれない。#106 の除外） |
