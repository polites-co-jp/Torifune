## 3. タスク分解

原則：**1 タスク＝1 コミット**。各タスクは「テストを書いて失敗を確認 → 実装 → 通す」の順。
各タスクの終わりで `pnpm test` / `pnpm typecheck` / `pnpm lint` / `pnpm format:check` が通る。
`pnpm test:e2e` は **T6 の終わり**と **T7 の終わり**に全件流す。

**純関数（T1〜T3）と、それを使う描画（T4〜T5）を分ける。**
Vitest は `environment: 'node'` で DOM が無く、`pointermove` を起こして状態遷移を確かめられない。
「どの点が選ばれるか」を検査できるのは純関数側だけである（設計 §4 末尾）。

**F 群（2026-09-06 追加）にタスクを新設しない。** F1 / F2 は**既に正しく動いている経路を縛る回帰条件**であり、

## 7. リスクと注意点

1. **`GET /api/v1/auth/csrf` の Rate Limit（最大のリスク）。**
   上限は **300 回/60 秒**、キーは **`operationId:IP`** で、**`apps/web/e2e/` の全ファイルがこの 1 つのバケツを共有する**。
   030 で「当日」の 36 件がテストごとにサイトを作り、40 回以上を消費して**後続ファイル（jobs / api-token / social など）が
   実行のたびに別の場所で 429 で落ちた**実績が `analytics.spec.ts` の doc に記録されている。
   その対策として `pristineSite` / `todayHitsSite` / `rolledUpTodaySite` の使い回しが入ったばかりであり、**余裕は少ない**。
   本プランの E2E は次を守る：
   * **`analytics.spec.ts` では新しいサイトを 1 件も作らない。** 既存の `rolledUpTodaySite` と `pristineSite` を使う
     （どちらも**読むだけ**なので、使い回しの前提「サイトの状態を変えない」を壊さない）
   * `dashboard.spec.ts` のサイト作成は**遅延生成 ＋ モジュール変数で 1 件だけ**。テストごとに作らない
   * E12 の権限なし利用者も**モジュール変数で 1 回だけ**作る
   * **追加で消費する csrf は合計 4 回程度**（サイト作成 1 ＋ 集計 1 ＋ 利用者作成 1 ＋ そのログイン 1）
   * **E2E のテスト本数を増やさないため、関連する条件は 1 本にまとめる**（E1〜E4＋E11 で 1 本、E8＋E9 で 1 本）
   T7 の完了条件に「`pnpm test:e2e` 全件で 429 が 1 件も出ないこと」を置く。**落ちたら本数を減らす方向で直す。既存テストを削らない**
2. **`<figcaption>` は「点が 1 つも無いとき」には描かれない。** `Chart` は空のとき `<>{fallback}</>` を返し、
   `<figure>` ごと出さない（現行の挙動）。D6 は「`fallback` の中身が必ず描かれ、チャートが描かれる経路ではそれが
   `<figcaption>` の中にある」と読む（§8 #4）。**現行の挙動を変えて `<figcaption>` を必ず出す、という方向へ直さない**
3. **`chartPolyline` は非有限を守っておらず、落ちる点の範囲は入力によって 2 通りに分かれる**（設計 §5.4.1）。
   `span` を全点で 1 組しか持たないので、`NaN` / `-Infinity` を含む入力では**全点の `y` が `NaN`** になり、
   `chartHoverPoints` は空配列を返して膜も出ない。**一方 `+Infinity` だけを含む入力では
   `min = Math.min(...values, 0)` が 0 のまま**なので `span = Infinity` となり、**その点だけ**が落ちて残りは生き残る。
   B7 はこの 2 通りを別々に検査する（§8 #5）。
   **`chartPolyline` を「直す」誘惑に乗らない。** 出力を変えない、が公開契約である（設計 §5.1）
4. **`'use client'` の位置はテストで検出できない。** `vitest.config.mts` にバンドラの解釈が無く、
   `renderToStaticMarkup` からはただの文字列リテラルである。**`pnpm test` が通ることは、要件 §6-1 の裁定を
   守れている証拠にならない。** D7 / D8 の静的検査（T6）が唯一の担保であり、これを外したり緩めたりしない。
   静的検査は文字列一致なので、**整形（引用符・改行）の揺れで空振りしやすい**。引用符の両方を許し、
   「空振りしていない」ガード（`export function Chart(` などの存在確認）を必ず併せる
5. **`chartLayout` に必須フィールドを足すので、`ChartLayout` を自前で組み立てている箇所があると型が落ちる。**
   `grep` では `chart.tsx` と `chart.test.ts` の 2 ファイルのみ。T1 のあと `pnpm typecheck` で取りこぼしが無いことを確かめる
6. **`hover` を別関数に切り出さない**（設計 §5.3）。`polyline` と別の関数で座標を作り直すと、
   片方だけ直したときにマーカーが線から静かにずれる。**同じループの中で、同じ `x` / `y` から作る**
7. **`chartHoverPoints` は `chartLayout` から作らない**（設計 §5.5）。2 つの経路は Y のスケールが違う
   （`chartPolyline` は底が `min(...values, 0)`、`chartLayout` は常に 0）。流用すると 1 系列のときだけマーカーが浮く。
   式が二重に存在することは B4 で縛る
8. **スロットリング（`requestAnimationFrame` での間引き）を入れない**（設計 §11.1）。
   「`pointermove` が重そう」という感触で足さないこと。間引きは「最後のイベントを取りこぼす」
   「離した瞬間に古い点が残る」という別の壊れ方を持ち込む。再描画を抑えるのは
   **選ばれた点の参照比較**（`chartHitTest` が配列の要素をそのまま返す。C10）で足りる
9. **`offsetX` / `offsetY` を使わない**（設計 §11.4）。膜の中にマーカーとポップアップという子要素があるため、
   基準を `getBoundingClientRect()` で固定する。`rect.width` / `rect.height` が 0 のときは何もせず抜ける（0 除算を作らない）
10. **膜に `touch-action: pan-y` を必ず付ける。** 無いとチャートの上で縦スクロールできなくなる。
    横方向は当たり判定に使うので渡さない。**Playwright では本物のスワイプを合成できない**ので、
    E10 は計算済みスタイルで見る。**この検査を外すと、縦スクロールが死んだことに誰も気づけない**

12. **半径を設けないので、線から遠い場所を指しても必ず 1 点が出る**（設計 §15-4）。
    「遠すぎるから消す」を後から足さないこと。列と列の間隔は 90 日で要素幅の約 1.1% しかなく、
    半径を入れると不感帯ができてポップアップが明滅する
13. **キーボード操作を新設しない**（要件 §6-2）。点ごとの `tabindex` も、チャート全体の tabstop ＋ 矢印キーも作らない。

14. **`ChartProps` に項目を足さない**（設計 §9.2）。「既定でオフにできるように」と `hover?: boolean` を足さないこと。
    オプトインにすると、既存 2 か所と Plugin の呼び出しを全部書き換えない限り誰も恩恵を受けない
15. **`index.ts` の公開面を増やさない**（A7）。`ChartHoverLayer` / `ChartHoverPoint` / `chartHitTest` / `chartHoverPoints` を

    Presentation の共通部品に閉じており、`TorifuneHub` の都合はコード・文書のどちらにも書かない
17. **公開リポジトリである。** コミットメッセージ・コードコメント・設計書のいずれにも、
    特定の導入環境を指す記述（ホスト・構成・運用の経緯）を書かない
