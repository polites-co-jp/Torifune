## 1. 目的

折れ線の**ある日の実際の値を読めるようにする**。

いま `Chart` は `<polyline>` だけを描いており、Y 軸の目盛りは上限・中間・0 の 3 つ、
X 軸の目盛りは点数に応じて間引かれている（`chart-geometry.ts` の `xTickIndexes`）。
90 日を選ぶと 90 点の折れ線に対して目盛りは 7 本しか無く、線の高さから値を目分量で読むしかない。

同じ値は `<figcaption>` の表に既に出ているが、`<details>` に畳んであり、
「線のこの山は何日の何件か」を知るには表を開いて 90 行から探すことになる。
**線を指したその場で読めるようにする**のが本設計の範囲である。

## 3. スコープ

### やること

* 折れ線チャート（`Chart`）で、カーソル／指の位置に**最も近い 1 点**の
  X 軸の値・Y 軸の値・系列名をポップアップで出す
* その 1 点だけにマーカーを描く（ホバー中のみ。常時は描かない）
* マウス位置からデータ点を引く計算を `chart-geometry.ts` の**純関数**として置く
* `series`（複数系列）と `points`（1 系列・従来契約）の**両方**を対象にする（§12-1）
* タッチでも出す。指を離しても消えない（§7.4）
* 枠からはみ出さない寄せ方を決める（§7.5）

### やらないこと

* **`chartPolyline` の出力を変えない。** `points` だけを渡したときの `<polyline points>` は 1 文字も変わらない（§5.1）
* **`<figcaption>` の表を消さない・弱めない。** ポップアップは補助であって、値を読む唯一の手段にしない（§7.7）
* **常時のマーカーを描かない**（裁定 §3.3）。90 点並ぶと線の形が読めなくなる
* **`BarChart` は対象にしない**（§12-2）
* **キーボード操作を新設しない**（§12-3）。点ごとに `tabindex` を作らない
* **`ChartProps` に項目を足さない**（§9.2）。ポップアップは常に有効で、オプトインにしない
* 縦のガイド線・十字線を引かない（裁定 §3.2「指した 1 点」）
* 同じ X の全系列をまとめて出さない（裁定 §3.2）
* 新しい依存・Permission・環境変数・マイグレーション・デザイントークンを増やさない
* サーバーへの新しい要求を作らない（§6）

## 5. データモデル

**マイグレーションを増やさない。DB を読み書きしない。**
ポップアップが出す値は、既に `Chart` へ渡っている `ChartPoint`（`label` / `value`）そのものである。

以下は `chart-geometry.ts` の型の話であり、永続データではない。

### 5.1 `chartPolyline` の出力を変えない（公開契約）

`chart-geometry.ts` に「1 系列の従来契約。ここの出力は変えない（Plugin から使われる公開契約）」と
明記されている。本設計は `chartPolyline` の**本体に一切触れない**。

正確に言うと、`chartPolyline` は `ui/components/index.ts` から export されていない。
Plugin が触れるのは `<Chart points={...}>` の**描画結果**である。したがって守るべきものは

> `points` だけを渡したときに出る `<polyline points="...">` の文字列が変わらないこと

であり、これは既存テスト
（`chart.test.ts`「points だけを渡したときの polyline は chartPolyline(points) と同じ」）が
既に押さえている。**このテストを 1 行も変えない**ことを受け入れ条件にする（§10-A1）。

### 5.2 追加する型 — `ChartHoverPoint`

```ts
export interface ChartHoverPoint {
  /** 系列の識別子。1 系列（`points`）の経路では ''。 */
  readonly seriesKey: string;
  /** 凡例に出る系列名。1 系列の経路では ''（出す相手がいない）。 */
  readonly seriesLabel: string;
  /** マーカーの色。1 系列の経路では 'chart-1'（線は --tf-color-primary で、値は同じ）。 */
  readonly tone: ChartTone;
  /** 系列内の添字。 */
  readonly index: number;
  /** X 軸の値。`ChartPoint.label` をそのまま持つ。 */
  readonly label: string;
  /** Y 軸の値。**描かれている値**（§5.4）。 */
  readonly value: number;
  /** SVG 要素の左端を 0、右端を 100 とした位置。 */
  readonly xPercent: number;
  /** SVG 要素の上端を 0、下端を 100 とした位置。 */
  readonly yPercent: number;
}
```

**割合（パーセント）で持つ理由。** `<svg>` は `preserveAspectRatio="none"` で
`viewBox`（600×160）を要素の箱へ**非等比に**引き伸ばしている。実寸は
コンテナ幅（レスポンシブ）と `height`（`sm` / `md` / `lg` / 数値）で毎回変わるため、
`viewBox` 座標のままではカーソル位置と比べられない。

一方 `preserveAspectRatio="none"` は **X と Y をそれぞれ独立に線形写像する**ので、

```
xPercent = (x_viewBox / 600) * 100
yPercent = (y_viewBox / 160) * 100
```

が要素の箱の中での位置に**厳密に**一致する。ここに `CHART_VIEW_PADDING`（8）が既に織り込まれるので、
当たり判定側は余白の存在を知らなくてよい。

### 5.3 `chartLayout` に `hover` を足す（既存フィールドは変えない）

```ts
export interface ChartLayout {
  readonly series: readonly ChartLayoutSeries[];   // 変更なし
  readonly yMax: number;                            // 変更なし
  readonly yMid: number;                            // 変更なし
  readonly yLabels: readonly number[];              // 変更なし
  readonly ticks: readonly ChartTick[];             // 変更なし
  readonly hover: readonly ChartHoverPoint[];       // 追加
}
```

**既存の出力が変わらないことの根拠。**

1. `hover` は `laidOut` を作るループの中で、`points` 文字列に使う **`x` / `y` と同じ値**から
   `xPercent = x / 600 * 100`、`yPercent = y / 160 * 100` として作る。
   `series` / `yMax` / `yMid` / `yLabels` / `ticks` の計算式には手を入れない
2. 既存テストは `layout.series` / `layout.ticks` / `layout.yMax` / `layout.yMid` を
   **フィールドごとに**見ており、戻り値オブジェクト全体を `toEqual` で比べている箇所が無い
   （`chart.test.ts` を全件確認した）。フィールドの追加でこれらは落ちない
3. `ChartLayout` / `chartLayout` は `ui/components/index.ts` から export されていない。
   リポジトリ内の利用は `chart.tsx` と `chart.test.ts` だけである（`grep` で全件確認）。
   Plugin が `ChartLayout` を実装している経路は存在しないので、必須フィールドとして足してよい

`hover` を別関数にせず `chartLayout` に相乗りさせるのは、**マーカーが線からずれないため**である。
別の関数で座標を作り直すと、片方だけ直したときに静かにずれる。
`polyline` の文字列は `toFixed(1)`（`viewBox` 単位）で丸めるが、`hover` は丸める前の値から作る。
差は最大 0.05 `viewBox` 単位（幅 1000px の要素で 0.08px）で、目に見えない。

### 5.4 `hover.value` は「描かれている値」

`chartLayout` は非有限な値を 0 として描く（既存。`Number.isFinite(point.value) ? point.value : 0`）。
`hover.value` も**同じ 0** を持つ。ポップアップに出る数と線の高さが食い違わないようにする。

`chartHoverPoints`（1 系列の経路。§5.5）は逆に、**座標が非有限になった点を配列から落とす**。
`chartPolyline` は非有限を守っておらず、その点は**そもそも描かれていない**。
描かれていない点を指せてしまうと、ポップアップだけが「NaN」と言うことになる。

一つの規則から出ている。**描かれている点だけを、描かれているとおりの値で出す。**

#### 5.4.1 落ちる点の範囲 — `span` を全点で共有するので、2 通りになる

`chartPolyline` は `max`・`min`・`span` を**全点から 1 組だけ**求め、
すべての点の `ratio` をその `span` で割る。したがって「1 点が非有限だと 1 点だけ壊れる」とは限らない。
実際の挙動（`chart-geometry.ts` の式をそのまま評価して確認した）は次のとおり。

| 入力 | `span` | `y` が `NaN` になる点 | `chartHoverPoints` の結果 |
| --- | --- | --- | --- |
| `NaN` を 1 つでも含む | `NaN` | **全点** | **空配列** |
| `-Infinity` を 1 つでも含む | `Infinity`（`min` が `-Infinity`） | **全点**（有限点も `Infinity / Infinity` で `NaN`） | **空配列** |
| `+Infinity` を含む（`NaN` / `-Infinity` は無い） | `Infinity` | **その点だけ**（他は `有限 / Infinity = 0`） | **その点だけを落とす** |
| すべて有限 | 有限 | 無し | 全点 |

**これを設計として確定させる。** `chartHoverPoints` は「非有限な点を落とす」のではなく、
**「`chartPolyline` が非有限な座標を出した点を落とす」**。判定の対象は入力値ではなく**出力座標**である。
こう定めると、上の 4 通りすべてが 1 つの規則で説明でき、
`chartPolyline` の内部の丸め方や `min` の取り方が将来変わっても、規則のほうは変わらない。

`x` は `PADDING + step * index` だけで決まり、値に依存しない。**非有限になるのは `y` だけ**である。

**`chartLayout`（複数系列）はこの問題を持たない。** 非有限を 0 に寄せてから `yMax` を求めるので
（`Number.isFinite(point.value) ? point.value : 0`）、`span` が壊れず、点も落ちない。
`hover` は全点そろい、`value` は 0 になる（B6）。**2 つの経路で扱いが違うのは、
それぞれが「描かれているとおり」だからである。**

#### 5.4.2 有限性の規約は、2 つの経路で同じにする

上の表は「いま何が起きるか」であり、**規約はもう一段上に置く**。

> **`hover` に載せてよいのは、`xPercent` と `yPercent` がどちらも有限な点だけである。**
> これは `chartHoverPoints`（1 系列）と `chartLayout`（複数系列）の**両方に等しく掛かる**。

`chartLayout` 側では、この規約は**いま何も落とさない**。
`value` は 0 に潰れ、`yMax` は `niceMax` が必ず正の有限値を返すので、非有限な座標が生まれる経路が無い。
それでも**規約として両方に置く**理由は次の 2 つである。

* **片方だけ壊れる形にしない。** `yMax` の式（`niceMax` の切り上げ方、0 起点をやめる、など）が
  将来変われば、`chartLayout` にも非有限な座標が生まれうる。
  そのとき `chartHoverPoints` にだけガードがあると、**同じ入力で片方の経路だけが静かに壊れる**。
  「1 系列では出ないのに 2 系列では NaN が出る」は、原因を追いにくい壊れ方である
* **`chartHitTest` の前提を、入口で 1 つに固定できる。** `chartHitTest` はカーソル位置の有限性を
  見る（C2）が、**点の側の有限性は見ない**。非有限な `yPercent` を持つ点が混ざると、
  `|NaN − y|` はどの比較にも勝たないため「決して選ばれない点」になり、
  走査の初期値の取り方によっては逆に「必ず選ばれる点」にもなりうる。
  入口で落としておけば、`chartHitTest` は**全要素が有限であること**だけを前提にできる

したがって `chartLayout` 側にも同じ有限性の判定を置く。**いまは何も落とさないガード**であり、
既存の受け入れ条件（B1 / B6 / B10 / B11）の結果は 1 つも変わらない。
検査は F3 に置く。

**やらないこと。** 非有限を「0 に寄せて載せる」方向で揃えることはしない。
それは `chartPolyline` の出力（＝描かれている線）と食い違い、§5.4 の一つの規則
「描かれている点だけを、描かれているとおりの値で出す」を壊す。
`chartPolyline` の出力は変えられない（§5.1）ので、**揃える先は「落とす」側**である。

### 5.5 1 系列（`points`）の経路 — `chartHoverPoints`

```ts
export function chartHoverPoints(points: readonly ChartPoint[]): readonly ChartHoverPoint[]
```

**`chartLayout` から作ってはならない。** 2 つの経路は Y のスケールが違う。

| | 底（Y の 0 位置） | 上限 |
| --- | --- | --- |
| `chartPolyline`（1 系列） | `Math.min(...values, 0)` | `Math.max(...values)`。全点同値なら中央へ |
| `chartLayout`（複数系列） | 常に 0 | `niceMax(全系列の最大値)` |

`chartLayout` の座標でマーカーを描くと、**1 系列のときだけマーカーが線から浮く**。
`chartHoverPoints` は `chartPolyline` と同じ式（同じ `min` / `span` / `step` / 全点同値の 0.5 寄せ）で
`x` / `y` を求め、それを割合に直す。

**式が二重に存在することを、テストで縛る。**
`chartHoverPoints(p)[i]` の `(xPercent, yPercent)` は、`chartPolyline(p)` の i 番目の座標を
`(600, 160)` で割ったものと一致しなければならない（丸めぶんの許容差つき）。§10-B4 に条件を置く。

## 7. 画面

### 7.1 構造 — SVG の上に、当たり判定の膜を 1 枚重ねる

**不可視の矩形を点ごとに置かない。** 90 日 × 2 系列で 180 個の要素が増え、
それぞれに `onMouseEnter` が付く。要素の数だけ描画コストとメモリが増えるうえ、
線の間（点と点の中間）を指したときに何も起きない穴ができる。

代わりに、SVG の箱**ちょうどに重なる `<div>` を 1 枚**置き、そこで `pointermove` を受ける。
カーソル位置は要素の箱に対する割合に直し、`chartHitTest`（純関数）へ渡す。

**この節を読んだだけで実装できるように、先に境界を書いておく。**
`要件.md` §6-1 の追加裁定により、**`chart.tsx` は Server Component のまま据え置く**。
`'use client'` を書くのは新設する `chart-hover.tsx` だけであり、
`chart.tsx` には `'use client'` を**付けない**。
下の図で `chart.tsx` が描くのは外側の `<div>` と `<svg>` まで、
`chart-hover.tsx` が描くのは膜（`data-chart-hover-area`）から内側である。理由は §13。

```text
<div style="position: relative; min-width: 0">   ← 新設。SVG の箱と同じ大きさ
  <svg role="img" aria-label={title} …>          ← 現行のまま。polyline / 格子線
  <div aria-hidden="true" data-chart-hover-area  ← 新設（chart-hover.tsx / 'use client'）
       style="position: absolute; inset: 0; touch-action: pan-y pinch-zoom">
    <span data-chart-marker …/>                  ← ホバー中の 1 点だけ
    <div  data-chart-tooltip …/>                 ← ポップアップ
  </div>
</div>
```

* `yAxis` を使うときの grid は現行のまま。**新設した `<div>` が grid の子になる**ので、
  列の構成（`auto 1fr`）は変わらない
* **その `<div>` に `min-width: 0` が要る（`Chart`（`series` 経路）側だけ）。**
  grid item の既定は `min-width: auto` で、**min-content 幅より縮まない**。
  `<svg>` は `viewBox` の比（600 : 160 ＝ 3.75 : 1）と CSS の固定 `height` を持つので、
  そこから min-content 幅が生まれる（`height: lg` の 220px なら 220 × 3.75 ＝ 825px）。
  これが `1fr` の列を押し広げ、**幅 375px の画面でページごと横に伸びる**。
  `min-width: 0` を書いて縮めるところまでが設計である。**書き忘れると
  `024-responsive` の「ページ全体が横スクロールしない」が壊れる**（§10-E7 が拾う）
* **`SingleSeriesChart`（`points` 経路）側は要らない。** そちらの `<div>` の親は `<figure>` で、
  grid ではなく通常のブロックである。ブロックの子は min-content 幅に縛られない。
  **この非対称は意図したもの**で、両方に書いても害は無いが、要るのは grid の子のほうだけである
* `role="img"` の `<svg>` は膜の**兄弟**であり子ではない。読み上げの木は変わらない
* 膜と、その中のマーカー・ポップアップには `aria-hidden="true"` を付ける。
  凡例（`<ul aria-hidden="true">`）・軸ラベル・目盛りが既に装飾扱いであるのと揃える。
  読み上げの経路は `aria-label` と `<figcaption>` の表のまま（§7.7）
* マーカーとポップアップには `pointer-events: none` を付ける。
  自分自身が当たり判定を遮ると、ポップアップの下に入った瞬間に点が切り替わって暴れる

**マーカーを SVG の `<circle>` にしない。** `preserveAspectRatio="none"` の下では
円が横に潰れた楕円になる（幅 1000px・高さ 220px の要素では約 3.6 : 1）。
膜の上に HTML の `<span>`（`border-radius: 50%`）を `left/top` の % で置けば、真円のまま出る。

**マーカーに背景色の縁取りを付ける。**
`box-shadow: 0 0 0 var(--tf-border-emphasis) var(--tf-color-bg)`。
折れ線と同じ色の点を線の上に重ねるだけでは、**線と溶けてどこを指しているか分からない**。
面の色（`--tf-color-bg`）で 2px の輪を描くと、線から浮いて見える。
`border` ではなく `box-shadow` にするのは、`border` だと要素の箱が広がり、
`left/top` の % で置いた中心がずれるためである。
**既存トークンだけで組む**（新しいトークンを作らない。§7.3 と同じ方針）。
塗りは系列色（`--tf-color-chart-1` / `-2`。1 系列の経路は `--tf-color-chart-1`）。

### 7.2 当たり判定 — `chartHitTest`（純関数）

```ts
export function chartHitTest(
  points: readonly ChartHoverPoint[],
  xPercent: number,
  yPercent: number,
): ChartHoverPoint | null
```

**規則（この順で決める）。**

1. `points` が空、または `xPercent` / `yPercent` が非有限なら `null`
2. **X で列を決める。** `|p.xPercent - xPercent|` が最小の点を選ぶ
3. **同点なら `xPercent` が大きいほう（右＝新しい日）の列**を採る
4. **その列の中で、`|p.yPercent - yPercent|` が最小の系列**を選ぶ
5. **同点なら配列の先に現れるほう**（＝ `series` に渡した順＝凡例の並び順）を採る

**「X で絞ってから系列を選ぶ」を採り、2 次元の距離を採らない理由。**

* 折れ線が並べているのは時系列であり、利用者が指しているのはまず「どの日か」である。
  2 次元距離だと、日をまたいで斜めに近い点が選ばれ、指した日と違う日が出ることがある
* **2 次元距離は要素の実寸に依存する。** 割合空間の距離をそのまま使うと、
  幅 1000px × 高さ 220px の要素では X の 1% が 10px、Y の 1% が 2.2px となり、
  「近い」の意味が縦横で 4.5 倍ずれる。実寸で補正すれば直せるが、
  そうすると**判定結果がコンテナ幅と `height` によって変わる**。純関数として検査できなくなる
* X で絞る規則は寸法に一切依存しない。`chart-geometry.ts` の他の関数と同じく、
  入力だけで結果が決まる

**当たり判定の半径を設けない理由。** 膜の内側であれば必ず 1 点が決まる。

* 90 日では列の間隔が要素幅の約 1.1% しかない。ここに半径を設けると
  列と列の間に不感帯ができ、カーソルを横へ動かすたびにポップアップが**明滅する**。
  値が読めないという困りごとに対して、これは悪化である
* Y にも半径を設けない。線がグラフの下端に貼り付いている日に、
  上のほうを指しても「その日の値」は答えられるべきである。
  どの点を指しているかはマーカーが示す
* 半径の代わりに、**膜そのものが範囲**である。カーソルが SVG の箱を出れば消える（§7.4）

**同点の扱いを明示的に決める理由。** 3 と 5 が無いと、点の並びや浮動小数の丸めで
選ばれる点が変わる。テストに落とせる形にしておく（§10-C5 / §10-C6）。

### 7.3 ポップアップの中身

```text
┌──────────────────┐
│ ● ページビュー    │ ← 系列名。色の点は凡例と同じ（--tf-color-chart-1 / -2）
│ 9/03             │ ← X 軸の値（ChartPoint.label をそのまま）
│ 128              │ ← Y 軸の値
└──────────────────┘
```

* **系列名を出す。** 2 系列（ページビュー・訪問者）が同じスケールで重なっているので、
  「128」だけではどちらの線の値か分からない。裁定 §3.2 が求めているのはこれである
* **1 系列（`points`）の経路では系列名の行を出さない。** 区別すべき相手がいない。
  `ChartPoint` に系列名は無く、`title`（「推移」など）はチャート全体の名前であって
  系列の名前ではない
* 数値は `toLocaleString('ja-JP')`。`chart.tsx` の `formatAxis` と**同じ形**にする。
  同じ画面で同じ数が違う形で出ないようにする
* 単位を付けない。`ChartPoint` は単位を持たない
* トークンだけで組む。面 `--tf-color-bg`、枠 1px `--tf-color-border`、
  角丸 `--tf-radius-md`、影 `--tf-shadow-1`、余白 `--tf-space-2`、
  系列名と日付は `--tf-text-label` / `--tf-color-text-muted`、値は `--tf-text-body` の等幅
  （`--tf-font-mono`。軸ラベルと揃える）
* **`--tf-z-*` トークンを新設しない。** ポップアップは `position: relative` の入れ物の中に閉じており、
  同じ入れ物の中で重なる相手は SVG だけである。膜が SVG より後ろに置かれるので、
  重なり順は文書順で決まる。`z-index` を書かない
* 文字を `white-space: nowrap` にしない。狭い画面で枠を破る

### 7.4 出す・消すの契機（マウスとタッチを Pointer Events で 1 本にする）

`onMouseMove` を使わない。マウス・タッチ・ペンを 1 つの経路で扱う。

| 契機 | 動き | 理由 |
| --- | --- | --- |
| `pointermove` | 位置から点を引き直す | マウス・ペンの追従。タッチのドラッグでも同じ |
| `pointerdown` | 位置から点を引く | **タッチの最初の接地で出す。** タッチには「動かさずに触る」がある |
| `pointerleave`（`pointerType` が `mouse` / `pen` のときだけ） | 消す | カーソルがチャートを出たら消えるのが自然 |
| `pointerleave`（`touch`） | **消さない** | タッチでは指を離した直後に `pointerleave` が飛ぶ。ここで消すと、**指の下に隠れていた値を読む前に消える** |
| `pointercancel` | 消す | スクロールなどに操作を奪われた |
| 膜の外での `pointerdown`（`document` で拾う） | 消す | タッチで出しっぱなしになったものを閉じる手段 |
| `Escape` | 消す | `Modal` が `window` の `keydown` で `Escape` を拾っている作法に揃える |

* `document` / `window` のリスナは、**点が出ている間だけ**張る（`useEffect` の依存に選択中の点を置く）。
  出ていないチャートがページに何枚あっても、常時のリスナは増えない
* 膜に **`touch-action: pan-y pinch-zoom`** を付ける。
  **これが無いと、チャートの上で縦スクロールできなくなる**。横方向は当たり判定に使うので渡さない
* **`pinch-zoom` を必ず含める。** `pan-y` だけにすると、膜の上では**二本指の拡大が効かなくなる**。
  チャートは細い線と小さな文字の集まりで、拡大して見る動機が最も強い区画である。
  ここでズームを奪うのは `06_画面設計.md` §2 の
  「SVG は読み上げも**拡大も**効かない」という問題意識に真っ向から反する
  （WCAG 1.4.4 Resize text）。**当たり判定のために奪ってよいのは横のパンだけ**である
* この値でも §10-E10 の検査（膜の計算済み `touch-action` に `pan-x` が含まれないこと）は
  そのまま成立する。E10 の文言は変えない
* `pointerType` で分岐するのは「消す契機」だけである。**どの点を選ぶかは同じ規則**（§7.2）で、
  入力装置によって値が変わることはない

### 7.5 枠からのはみ出し — 点の左右・上下に振り分ける

既存の X 軸ラベルは `xPercent <= 0 → none / >= 100 → translateX(-100%) / それ以外 → translateX(-50%)` で
端だけ内側へ寄せている。ラベルは幅が狭く、点の真上に置きたいのでこれでよい。
ポップアップは**幅があり、点を隠したくない**ので、同じ「枠から出さない」という考え方を、
部品の性質に合わせて次の形にする。

| 条件 | 置き方 |
| --- | --- |
| `xPercent <= 50` | 点の**右**へ。`left: {xPercent}%` に `--tf-space-2` ぶん離す |
| `xPercent > 50` | 点の**左**へ。`right: {100 - xPercent}%` に `--tf-space-2` ぶん離す |
| `yPercent <= 50` | 点の**下**へ。`top: {yPercent}%` |
| `yPercent > 50` | 点の**上**へ。`bottom: {100 - yPercent}%` |

* 大きさの上限は、**左右と上下で値が違う**。

  | 軸 | 上限 |
  | --- | --- |
  | 左右 | **`max-width: calc(50% - var(--tf-space-2))`** |
  | 上下 | **`max-height: 50%`** |

  **非対称なのは、離し幅が左右にしか無いからである。**
  左右は点を避けて `--tf-space-2`（8px）離すので、そのぶんを上限から差し引く。
  **上下は離していない**（上の置き方の表のとおり `top` / `bottom` だけで、マージンを付けない）ので、
  差し引く量は 0 になる。

  この 2 つと置き方を合わせて、**はみ出しを規則から保証する**。

  | 置き方 | ポップアップの外側の端 |
  | --- | --- |
  | 左半分（`xPercent ≤ 50`）：`left: {x}%` ＋ 8px、幅 ≤ `50% − 8px` | 右端 ≤ `x% + 8px + 50% − 8px` ＝ `x% + 50%` ≤ `100%` |
  | 右半分（`xPercent > 50`）：`right: {100−x}%` ＋ 8px、幅 ≤ `50% − 8px` | 左端 ≥ `x% − 8px − (50% − 8px)` ＝ `x% − 50%` ≥ `0%` |
  | 上半分（`yPercent ≤ 50`）：`top: {y}%` ＋ **0**、高さ ≤ `50%` | 下端 ≤ `y% + 50%` ≤ `100%` |
  | 下半分（`yPercent > 50`）：`bottom: {100−y}%` ＋ **0**、高さ ≤ `50%` | 上端 ≥ `y% − 50%` ≥ `0%` |

  **等号でちょうど枠に接するところまでで、超えない。**
  ただし、**この保証の強さは軸によって違う**。

  * **左右は厳密である。** 幅の上限に達した内容は折り返す（`nowrap` にしない。§7.3）ので、
    **箱も文字も**枠の中に収まる。**寸法・文字数・フォントに依存しない**
  * **上下は「箱」までである。** 上の表が言っているのは
    **箱の位置と上限**（下端 ≤ 100% / 上端 ≥ 0%）であって、中身が収まることではない。
    折り返しに当たる機構が高さには無く、しかも**ポップアップに `overflow` を書いていない**ので、
    内容の自然な高さが上限を超えると**箱は枠内のまま文字だけが枠の外へ出る**。
    これは下で述べる理由（`overflow: hidden` にすると数値が隠れ、
    値を読ませるという機能の目的そのものを壊す）の裏返しであり、
    **隠さないことを選んだ以上、溢れうることは引き受ける**

  上下の余裕は薄い。`--tf-size-chart-md`（160px）で上限 80px に対し実測 79.19px である。
  `height` は `ChartProps` として Plugin へ公開されているので、
  **本体の 2 箇所（`md` / `lg`）だけを見て「収まっている」と考えない**。具体値は §15.1-14。

  **左右の `50%` は足りず、上下の `50% − 8px` は狭すぎる。** どちらも間違え方が実害になる。
  * 左右で 8px を引かないと、`xPercent = 50`（ちょうど真ん中の点）で右端を 8px はみ出す
  * 上下で 8px を引くと、`--tf-size-chart-md`（160px。ダッシュボードの既定 `height`）では
    上限が 72px になり、**3 行のポップアップ（実測 79.19px）が入らない**。
    `50%` なら 80px で収まる。ここで `overflow: hidden` に逃げると
    **数値が隠れて機能の目的そのものを壊す**ので、上限のほうを正しく取る
* 上下も振り分けるので、**ポップアップが指している点そのものを隠さない**
* ポップアップは常に SVG の箱の内側に収まる。したがって `Card` の外へ出ない。
  `024-responsive` が守っている「ページ全体が横スクロールしない」も壊れない（§10-E4 / §10-E7）
* 幅 375px の画面で上限は約 180px。3 行の短い内容なら収まり、
  収まらなければ折り返す（`nowrap` にしない。§7.3）

### 7.6 狭い画面

`024-responsive` §3.1「作り込みはしない。壊れないところまで」に従う。
**断点を増やさない**（同 §3.2）。狭い画面向けの作り分けをしない。

* `@media` を要する切り替えが無いので、`globals.css` に追記しない
* `@media (hover: hover)` で分岐しない。§7.4 の `pointerType` による分岐で足りる
* タッチで指の下に隠れる問題は、§7.5 の上下振り分け（点が上半分なら下、下半分なら上）で緩む。
  **指の位置に合わせた追加の逃がしを入れない。** そこまでやると「作り込み」になる

### 7.7 `<figcaption>` の表を弱めない（要件 §4）

ポップアップは**補助**である。次を維持する。

* `<figcaption>{fallback}</figcaption>` を必ず描く。`series` の経路も `points` の経路も現行のまま
* `<details>`（summary「日ごとの値を表で見る」）で畳む現行の形も変えない
* `role="img"` と `aria-label={title}` を変えない
* ポップアップに `aria-hidden="true"` を付ける。**読み上げの二重化を作らない**。
  読み上げ利用者が値を読む経路は表のままである
* ポップアップでしか読めない情報を 1 つも作らない。出す 3 つ（系列名・X 軸の値・Y 軸の値）は
  すべて凡例と表に既にある

**「見えている人にだけ伝わる」画面にしない**（`06_画面設計.md` §2 / `014` 設計 §3.1）。
ポップアップはマウスと指を持つ人にしか届かない。だから表を消さないし、畳み方も強めない。

**変更なし。**

## 9. Plugin API への影響

### 9.1 `packages/plugin-api` — 変更なし

`packages/plugin-api/src/ui.ts` に `Chart` への言及は無い（`grep` で確認）。
`PLUGIN_API_VERSION` を上げない。破壊的変更は無い。

### 9.2 `ui/components/index.ts` の公開面 — 増やさない

* `ChartProps` に項目を足さない。**ポップアップは常に有効**にする。
  `yAxis` / `xTicks` / `legend` が任意項目なのは、それらが**描画領域の外に要素を増やす**からである。
  ポップアップは既定の見た目を一切変えず（裁定 §3.3。常時のマーカーを描かない）、
  操作したときだけ出る。オプトインにすると、既存の 2 か所と Plugin の呼び出しを
  すべて書き換えない限り誰も恩恵を受けない
* `ChartHoverLayer` を公開しない。`Chart` の内部部品である
* `ChartHoverPoint` / `chartHitTest` / `chartHoverPoints` を `index.ts` から出さない。
  公開面は後方互換の義務を伴う。まだ外から使う理由が無い
* 既に公開している `Chart` / `ChartHeight` / `ChartProps` / `ChartPoint` / `ChartSeries` / `ChartTone` を
  1 つも変えない

### 9.3 Plugin の画面での振る舞い

Plugin が `<Chart points={...}>` を使っていれば、**Plugin 側の変更なしにポップアップが付く**。
`points` の経路を対象に含めた理由でもある（§12-1）。

そのために、**`Chart` が Server Component のままであることを維持する**（§13）。
`plugin-boundary.tsx` は「Plugin の部品は Server Component のまま描画してよい。
**Plugin 作者に『Client Component で書くこと』を要求しない**」と明記している。
`Chart` を Client Component にすると、この約束が `Chart` の呼び出しについて破れる。

3. `hover` の `seriesKey` / `seriesLabel` / `tone` / `index` / `label` が、
   渡した `ChartSeries` と `ChartPoint` の内容と一致する
4. **`chartHoverPoints(points)` の各要素 `h` について、`(h.xPercent, h.yPercent)` が
   `chartPolyline(points)` の **`h.index` 番目**の座標を `(600, 160)` で割った値と一致する**
   （2 つの式がずれていないことの担保）。
   **配列の添字ではなく `h.index` で引く。** 非有限の点は配列から落ちるので（B7）、
   `chartHoverPoints` の配列の添字と元の点の添字は一致しない。
   `h.index` で引けば、落ちた点がある入力でも B7 と両立する
5. `chartHoverPoints` の `seriesKey` と `seriesLabel` が `''`、`tone` が `'chart-1'`
6. 値が非有限の点を含む入力で、`chartLayout(...).hover` の `value` が `0`（描かれている値と一致）
7. 値が非有限の点を含む入力で、`chartHoverPoints` は**座標が非有限になった点を配列に含めない**。
   `chartPolyline` は全点で 1 つの `span` を共有するため、落ち方は 2 通りになる（§5.4）。
   **両方を条件にする**：
   * `NaN` または `-Infinity` を 1 つでも含む入力 → `span` が `NaN` になり**全点**の y が `NaN`。
     **配列は空**（`[1, NaN, 3]` → `[]`、`[1, -Infinity, 3]` → `[]`）
   * `+Infinity` を含む入力 → **その点だけ** y が `NaN` で、他の点は有限。
     **その点だけが落ち、残った要素の `index` は元の添字を保つ**
     （`[1, Infinity, 3]` → 長さ 2、`index` は `0` と `2`）
8. `xPercent` / `yPercent` に `NaN` / `Infinity` が 1 つも現れない（B6 / B7 の入力すべてで）
9. 空配列で `hover` が `[]`、`chartHoverPoints([])` が `[]`
10. 1 点だけの系列で `hover` の長さが 1、`xPercent` が有限
11. 系列ごとに点数が違うとき、短い系列の点は長い系列の同じ添字と**同じ `xPercent`** になる
12. 全点が同じ値のとき、`chartHoverPoints` の `yPercent` がすべて等しい（`chartPolyline` の 0.5 寄せと一致）

### C. `chartHitTest`（純関数）

1. 空配列を渡すと `null`
2. `xPercent` に `NaN`、`yPercent` に `NaN` / `Infinity` を渡すと `null`（例外を投げない）
3. ある点の `(xPercent, yPercent)` をそのまま渡すと、その点が返る
4. 3 点 × 1 系列で、左端寄り（`xPercent = 0`）を指すと添字 0、右端寄り（`100`）を指すと添字 2 が返る
5. **X が同点のとき（2 つの列のちょうど中間を指したとき）、`xPercent` が大きいほうの列が返る**
6. **同じ列で Y も同点のとき（2 系列の値が同じ日）、`points` 配列の先に現れるほうが返る**
7. 2 系列で値が違う日に対し、上側を指すと**値が大きい系列**、下側を指すと**値が小さい系列**が返る
8. Y がグラフの外側の値（`yPercent = 0` / `100`）でも `null` を返さず、その列のいずれかの点が返る
   （半径を設けない。§7.2）
9. 90 点 × 2 系列で、i 番目の点の `xPercent` を指すと添字 i の点が返る（全 90 通り）
10. 同じ引数を 2 度渡すと**同一の参照**が返る（`ChartHoverPoint` を作り直さない。§11-2 の前提）

### D. ポップアップの初期描画（静的描画。`renderToStaticMarkup`）

1. 初期状態の HTML に、ポップアップ（`data-chart-tooltip`）もマーカー（`data-chart-marker`）も
   出ていない（操作前は何も出ない＝裁定 §3.3）
2. 当たり判定の膜（`data-chart-hover-area`）が、`series` の経路でも `points` の経路でも 1 つ出る
3. 膜に `aria-hidden="true"` が付いている
4. 膜が `<svg role="img">` の**子ではない**（読み上げの木を変えない）
5. 系列に点が 1 つも無いとき、膜が出ない（`fallback` だけが描かれる）
6. **`fallback` の中身が、膜の有無にかかわらず必ず描かれる。** そのうえで、
   チャートが描かれる経路（点が 1 つ以上ある）では、それが `<figure>` の中の
   `<figcaption>` に入っている。点が 1 つも無いときは `Chart` が `<figure>` を出さず
   `fallback` だけを返すので、`<figcaption>` は現れない
   （`chart.tsx` の `Chart` の `series.every(...)` と `SingleSeriesChart` の
   `points.length === 0` の早期 return。**現行の挙動であり、本設計は変えない**。
   既存テスト「fallback は series が空でも描かれる」と同じことを言っている）。
   **`要件.md` §4 の「`<figcaption>` の表を消さない・弱めない」を弱める条件ではない。**
   値を読む経路が常に `fallback` として存在することを、現行の振る舞いに合わせて言い直しただけである
7. `chart.tsx` の先頭に `'use client'` が**無い**（§13。ファイル内容の静的検査）
8. `chart-hover.tsx` の先頭に `'use client'` が**ある**（同上）

### F. 検証で見つかった穴を塞ぐ条件（2026-09-06 に追加）

**A1〜E14 の番号と文言は動かさない。** 検証（`検証レポート.md` §3.2 / §3.4）が
「実装は正しいが、それを縛るテストが 1 件も無い」と指摘した経路を、末尾に足す。
どれも**実装の振る舞いを変えない**。いま通ることを固定するための条件である。

1. **`ChartHoverLayer` 自身の空ガードを通す**（静的描画）。
   `<Chart points={[{ label: 'a', value: NaN }]} />` の静的 HTML で、
   **`<polyline>` は出る**（座標が `NaN` で線は見えないが、要素は描かれる）が、
   **膜（`data-chart-hover-area`）もマーカーもポップアップも出ない**。
   `chart.tsx` の早期 return は `points.length === 0` を見ており、この入力は点が 1 つあるので
   `<figure>` ごと出る。膜が出ないのは `chartHoverPoints` が `[]` を返し、
   **`ChartHoverLayer` が自分で `points.length === 0 → null` を返すから**である。
   D5 の 3 入力はいずれも `chart.tsx` の早期 return で止まるため、この分岐を通っていない
2. **`label` に markup を入れても、そのまま HTML に出ない**（静的描画。XSS の回帰）。
   `Chart` は `ui/components/index.ts` から Plugin へ公開されており（§9.2）、
   `ChartPoint.label` と `ChartSeries.label` には**任意の文字列が入りうる**。
   `label: '<script>alert(1)</script>'` を渡した静的 HTML に、
   * `series` の経路（`legend` / `xTicks` を有効にして、凡例と目盛りに `label` が出る状態）
   * `points` の経路

   のどちらでも、**生の `<script>` タグが現れず**、エスケープされた形（`&lt;script&gt;`）で出る。
   純関数側（`chartLayout(...).hover[].label` / `chartHoverPoints(...)[].label`）は
   **文字列をそのまま持ち回ってよい**（エスケープは描画側の責務であり、
   純関数がエスケープ済み文字列を返すと二重エスケープになる）。
   現状の実装は JSX の子として描いており安全だが、**それを縛る条件が 1 件も無い**。
   `dangerouslySetInnerHTML` / `innerHTML` を使う実装への変更が、この条件で止まる
3. **`hover` の有限性の規約が 2 経路で同じ**（純関数。§5.4.2）。
   `chartLayout(...).hover` の全要素で `xPercent` / `yPercent` が有限であり、
   `hover` の長さが「座標が有限になった点の数」と一致する。
   `chartHoverPoints` と**同じ判定**であることを、両方に同じ入力群
   （`0` / 全点同値 / `NaN` / `+Infinity` / `-Infinity` / `Number.MAX_VALUE` を含む極端な値）を
   通して確かめる。
   **`chartLayout` 側ではいま 1 点も落ちない**（`value` は 0 に潰れ、`niceMax` は必ず正）。
   落ちないことも含めて固定する。将来 `yMax` の式が変わったときに、
   片方の経路だけが静かに壊れることを止めるための条件である

## 11. 性能

### 11.1 ホバー 1 回あたりの計算量

90 日 × 2 系列 = 180 点。`chartHitTest` は配列を**1 回走査**し、
1 要素あたり減算 2 回・絶対値 2 回・比較数回を行う。

`pointermove` はディスプレイのリフレッシュ頻度が上限（60〜120 Hz）なので、
最悪でも 120 × 180 = 21,600 回/秒 の比較になる。数値比較だけであり、問題にならない。

**スロットリング（`requestAnimationFrame` での間引き）を入れない。**
間引きは「最後のイベントを取りこぼす」「離した瞬間に古い点が残る」という別の壊れ方を持ち込む。
まず入れないほうがよい。

### 11.2 点数の上限を設けない

`chartLayout` は既に任意の点数を受ける（`xTickIndexes` は 400 点まで試験済み）。
1 万点でも走査は 1 万回であり 1ms を切る。上限を設けると
「上限を超えたときにどう振る舞うか」という新しい状態が増える。**設けない。**

### 11.3 再描画を起こす条件

**選ばれた点が変わったときだけ `setState` する。** 走査より React の再描画のほうが高い。

`chartHitTest` は配列の要素を**そのまま**返す（新しいオブジェクトを作らない。§10-C10）。
したがって「同じ点か」は参照比較 1 回で判定でき、カーソルが同じ列の中を動いている間は
再描画が 1 回も起きない。

### 11.4 `getBoundingClientRect()` の扱い

カーソル位置を割合に直すには要素の実寸が要る。`pointermove` のたびに
`event.currentTarget.getBoundingClientRect()` を呼ぶ。

* **`offsetX` / `offsetY` を使わない。** これは「イベントの対象要素」基準であり、
  膜の中にはマーカーとポップアップという子要素がある。`pointer-events: none` を付けていても、
  読み手が後で外したときに静かにずれる。基準を要素で固定する
* 強制同期レイアウトを起こさない。ハンドラの中で**読み取り（`getBoundingClientRect`）を先に済ませ、
  書き込み（`setState`）は React の次の描画へ回す**。同じハンドラ内でレイアウトを
  無効化する DOM 変更を行わない
* `rect.width` / `rect.height` が 0 のとき（非表示・折り畳み中）は 0 除算になるので、
  何もせず抜ける。`chartHitTest` に `NaN` を渡す経路を作らない

### 11.5 常時のリスナ

`document` / `window` のリスナは、**ポップアップが出ている間だけ**張る（§7.4）。
出ていない状態のチャートは、膜の JSX と React のイベント委譲だけで、
グローバルなリスナを 1 つも増やさない。

## 12. `要件.md` §5 の 5 点の決定

### 12-1. `points`（1 系列・従来契約）の経路 ＝ **対象に含める**

**理由。**

* 困りごと（線の高さから値を目分量で読むしかない）は系列数に関係なく同じである
* リポジトリ内に利用箇所は無いが、`chartPolyline` は「Plugin から使われる公開契約」と
  明記されている。**Plugin が使っている前提で設計するなら、Plugin の画面でも同じ操作で
  値が読めるほうがよい**。「本体の画面だけ良くなる」を作らない
* 追加コストは小さい。当たり判定（`chartHitTest`）と描画（`ChartHoverLayer`）は共通で、
  必要なのは「`chartPolyline` と同じ座標規則で点の配列を作る関数」1 つだけである（§5.5）

**守ること。** `chartLayout` の座標を流用しない（Y のスケールが違い、マーカーが線から浮く）。
2 つの式がずれていないことを §10-B4 で縛る。

**ポップアップの中身。** 系列名の行を出さない。区別すべき相手がいない（§7.3）。

### 12-2. `bar-chart.tsx` ＝ **対象に含めない**

**理由。**

* 要望は「線グラフのプロット点」であり、裁定 §3.1 / §3.2 も折れ線を前提に書かれている
* **困りごとの程度が違う。** `BarChart` は棒そのものが図形として存在し（`<rect>`）、
  高さの比較が目で足りる。使われているのは時間帯別ページビューの 24 本で、
  軸ラベル（`0` / `6` / `12` / `18`）と代替表が既にある。
  「90 点の折れ線で目盛りが 7 本しか無い」という状況とは違う
* 実装も別物になる。棒は当たり判定の図形を既に持っており、
  「不可視の当たり判定を作る」という本設計の中心が要らない

**片方だけ出る状態をどう扱うか（要件 §5-2 が求めている判断）。**

**同じ画面に折れ線と棒が並び、折れ線にだけポップアップが出る状態を受け入れる。**
中途半端なホバーを棒にも足して揃えるより、困りごとが実在する側だけを直す。
`024-responsive` §3.1 と同じ考え方（「壊れないところまで」「足りなくなったらそのとき足す」）である。

**将来 `BarChart` に足すときのために、規則を流用可能な形にしておく。**
`chartHitTest` は `ChartHoverPoint` の**配列しか見ない**（棒か線かを知らない）。
棒の上端中央を `ChartHoverPoint` として渡せば、同じ関数・同じ規則で解ける。
`BarChart` 側に何も準備しないが、足すときに当たり判定を書き直すことにはならない。

### 12-3. タッチとキーボードの到達性

**タッチ ＝ 出す。** Pointer Events で経路を 1 本にし、`pointerdown` で出し、
**指を離しても消さない**（§7.4）。裁定 §3.1 が `<title>` を却下した理由の 1 つが
「タッチでは出ない」ことであり、タッチで出ることは裁定の要求である。

**キーボード ＝ 新しい操作を作らない。**

* **点ごとに `tabindex` を作らない。** 90 日では tabstop が 90 個（2 系列なら 180 個）増える。
  Tab キーだけで画面を渡り歩く利用者にとって、これは**表より遥かに遅い**経路であり、
  チャートを通り抜けるだけで 180 回 Tab を押すことになる。改善ではなく妨害である
* チャート全体に 1 つ tabstop を置いて矢印キーで点を移動する案も採らない。
  `024-responsive` §3.1 の「作り込みはしない」に沿う。**足りなくなったらそのとき足す**
* 代わりに、**`<figcaption>` の表がキーボードと読み上げの正規の経路であることを維持する**（§7.7）。
  表は既に全点の値を持ち、`<details>` はキーボードで開ける。
  ポップアップが出す 3 つは、すべて表と凡例に既にある

**マウスが無い環境で値を読む手段は表で足りるか（要件 §5-3 の問い）＝ 足りる。**
表は全 90 日 × 2 系列の値を持ち、ポップアップより情報量が多い。
ポップアップの利点は「線の形と値を同時に見られる」ことであり、
これはそもそも線が見える人にしか成立しない。**足りない部分を作らない**ことが要件 §4 の趣旨である。

### 12-4. 「最も近い点」の判定規則

**X で列を決めてから、その列の中で Y が最も近い系列を選ぶ。半径は設けない。**
同点は X なら右（新しい日）、系列なら配列の先。詳細と理由は §7.2。

### 12-5. はみ出しの寄せ方

**点の左右・上下に振り分ける。左右は `max-width: calc(50% - var(--tf-space-2))`、
上下は `max-height: 50%` と合わせて、はみ出しを規則から保証する。**
**上限の値が軸で違うのは、離し幅が左右にしか無いからである**
（左右は点を 8px 避けるのでそのぶん差し引く。上下は離していないので差し引かない）。
X 軸ラベルの「端で内側へ寄せる」と同じ考え方（枠から出さない）を、
幅と高さのある部品に合わせて言い直したものである。詳細と理由は §7.5。

## 13. `'use client'` の置き場所（`要件.md` §6-1 の追加裁定。確定）

**`chart.tsx` は Server Component のまま据え置き、`'use client'` は新しい子モジュール
`chart-hover.tsx` に閉じ込める。**

これは `要件.md` §6-1 の追加裁定（2026-09-05）であり、**拘束力を持つ決定である**。
裁定 §3.1 の「`chart.tsx` を `'use client'` にする」という文言は、これに**置き換わっている**。
本設計の他の節が `chart.tsx` を client にすると読める書き方をしていた場合も、この節が優先する。

採る手段（`<title>` を採らず、client で自前のポップアップを出す）は裁定 §3.1 のとおりである。
置き換わったのは**どのモジュールに `'use client'` を書くか**だけで、方式は変わっていない。

以下は、この追加裁定に至った調査（§13.1）と、決定の内容（§13.2）である。

### 13.1 調べたこと

* **`<Chart` の利用箇所は 2 件だけ**（`grep` で全件確認）。

  `badge` / `stat` / `meter` / `tabs` / `segmented-control` / `bar-chart` / `chart` はサーバーのままである。
  **巻き込みは起きない**（要件確認事項 6 の後半に対する答え）
* **ただし Plugin の経路に 1 つ実害がある。** `ui/plugin/plugin-boundary.tsx` は
  「Plugin の部品は Server Component のまま描画してよい。**Plugin 作者に
  『Client Component で書くこと』を要求しない**」と明記している。
  Plugin の Server Component が

  ```tsx
  <Chart points={…} title="…" fallback={<Table columns={[{ key, header, render: (row) => … }]} … />} />
  ```

  と書いたとき、`chart.tsx` が client だと `fallback` が server → client の境界を越える。
  この木に含まれる `render` 関数は直列化できず、**実行時に落ちる**。
  いまは `Chart` がサーバー側なので落ちない。`fallback` に `Table` を渡す形は
  本体の 2 か所がまさにそう書いており、Plugin が真似するのは自然である

### 13.2 決めたこと

**`chart.tsx` はサーバーのままにし、`'use client'` を `chart-hover.tsx` に置く。**

```text
chart.tsx （Server Component。現行のまま）
  └─ <ChartHoverLayer points={ChartHoverPoint[]} />   ← chart-hover.tsx / 'use client'
```

* `ChartHoverLayer` に渡すのは `ChartHoverPoint` の配列だけである。
  文字列と数値しか持たない（§5.2）。**直列化できる**
* `fallback`（`ReactNode`）は `chart.tsx` の中に留まり、**境界を越えない**
* 裁定 §3.1 の狙い（`<title>` を採らず、client で自前のポップアップを出す）は満たす
* 副次的な利点：client へ送られるのは膜とポップアップだけで、
  凡例・軸・目盛り・`polyline`・代替表（最大 90 行）はサーバー描画のまま残る

### 13.3 テストへの影響

`vitest.config.mts` にはバンドラの `'use client'` 解釈が無く、
`renderToStaticMarkup` から見れば `'use client'` はただの文字列リテラルである。
どちらの置き方でも、既存の静的描画テストは同じように動く。
**テストが通るかどうかでは、この差分を検出できない。** だから §10-D7 / §10-D8 で
ファイルの内容そのものを検査する（`static-checks.test.ts` が
`analytics-query.ts` の export をファイル内容で確かめている先例に揃える）。
