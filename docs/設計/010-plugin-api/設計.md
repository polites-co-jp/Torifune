# Plugin API 設計

## 1. 目的

Plugin が Torifune を拡張するための**公開契約**を確定させる。

`03_プラグイン設計.md` §25 が最重要とする4つを揃える。

```text
UI Extension / Data API / Authentication Provider / Database Provider
```

加えて、`009-social` の検証で残した課題（S-1）を解く。

> 外部SNSを叩くのは Plugin なので、資格情報をどう扱うか。

**答え：Core が資格情報を渡すのではなく、Plugin が自分の名前空間に自分で持つ。**
そのための Key-Value Store をホスト機能として開放する。

## 3. スコープ

### やること

* `packages/plugin-api`：**型とインターフェースだけ**の公開契約
* Manifest スキーマと検証
* `PluginContext`（Plugin に渡す唯一の入口）
* **名前空間つき Key-Value Store**（Plugin のデータと設定）
* UI Extension の型（Menu / Page / Widget / Action / Extension Point）
* Event API の型
* Data API の型（Sites / Social）
* Authentication Provider / Database Provider の公開契約
* Plugin API Version と後方互換性の判断基準

### やらないこと

* Plugin の読み込み・実行（`011-plugin-runtime`）
* 管理画面（`012-plugin-manager`）
* Plugin Registry・署名検証

## 4. レイヤ配置

```text
packages/plugin-api/src/
├── index.ts          公開する入口
├── version.ts        Plugin API Version
├── manifest.ts       Manifest の型と検証
├── context.ts        PluginContext
├── store.ts          Key-Value Store の契約
├── ui.ts             UI Extension の型
├── events.ts         Event の型
├── data.ts           Data API の型
├── authentication.ts Authentication Provider の契約
└── database.ts       Database Provider の契約
```

**`apps/web` へ一切依存しない**（ESLint で検査済み）。
実装は `apps/web/src/plugin/` に置き、`011-plugin-runtime` で繋ぐ。

## 5. データモデル

### `plugin_store`（`migrations/006_plugin_store.sql`）

Plugin が自分のデータと設定を置く場所。

| カラム | 型 | 制約 |
| --- | --- | --- |
| `plugin_id` | `text` | PK の一部 |
| `key` | `text` | PK の一部 |
| `value` | `jsonb` | NOT NULL |
| `is_secret` | `boolean` | NOT NULL DEFAULT false |
| `created_at` / `updated_at` | `timestamptz` | NOT NULL DEFAULT `now()` |

PK は `(plugin_id, key)`。

**Plugin は自分の `plugin_id` の範囲しか触れない。**
`PluginContext` が `plugin_id` を閉じ込め、Plugin から指定させない。
指定できると、他の Plugin の資格情報を読めてしまう。

`is_secret` が真の値は**暗号化して保存**し、
一覧や設定画面へは「設定済み」だけを返す（`05_API設計.md` §25）。

### なぜ KVS にするか

Plugin が必要とするデータの形は、Core には決められない。

* SNS 連携Plugin：アクセストークン、リフレッシュトークン、有効期限
* アクセス解析Plugin：計測ID、API キー、除外IP の一覧
* 独自機能Plugin：まったく別のもの

`03_プラグイン設計.md` §19 は「Core のテーブルへ列を足さない」としており、
Plugin ごとにテーブルを作る方式も許している。
しかし**設定と少量のデータのために毎回マイグレーションを書かせるのは重い**。

KVS を既定の置き場にし、大量データや検索が要る Plugin だけが
専用テーブルを持つ（`011-plugin-runtime` で Plugin のマイグレーションを扱う）。

### 資格情報の扱い（`009-social` S-1 への回答）

**Core は `social_accounts.credential` を Plugin へ渡さない。**

Plugin は自分の設定画面で資格情報を受け取り、自分の名前空間へ
`setSecret()` で保存する。外部APIを叩くときは `getSecret()` で取り出す。

これにより、

* Plugin は他の Plugin の資格情報を読めない
* 「Core が持っている資格情報を誰に渡すか」という判断が不要になる
* 認証方式がSNSごとに違っても Core が知らずに済む

> **既知の重複**：`social_accounts.credential` は、この方針では
> Core 自身が使う当てが無くなる。画面から入力できる場所として残すか、
> 削除するかは次の計画で判断する（`03_リスクと未決事項.md` に記録）。

## 6. API

Plugin から見た API は関数呼び出しであり、HTTP ではない
（`05_API設計.md` §29「同一プロセス内の Service Interface を利用する」）。

```ts
export interface PluginContext {
  readonly pluginId: string;
  readonly apiVersion: number;

  /** この Plugin 専用の Key-Value Store。他の Plugin の領域は見えない。 */
  readonly store: PluginStore;

  /** Torifune のデータ。**呼び出し元 Plugin の Permission を通る。** */
  readonly data: PluginDataApi;

  /** UI 拡張の登録。 */
  readonly ui: PluginUiApi;

  /** イベントの購読。 */
  readonly events: PluginEventApi;

  /** ログ。**Secret を渡しても落とされる。** */
  readonly logger: PluginLogger;
}
```

### `PluginStore`

```ts
export interface PluginStore {
  get<T>(key: string): Promise<T | null>;
  set<T>(key: string, value: T): Promise<void>;
  delete(key: string): Promise<void>;
  keys(prefix?: string): Promise<string[]>;

  /** Secret として保存する。暗号化され、一覧にも設定画面にも平文で出ない。 */
  setSecret(key: string, value: string): Promise<void>;
  /** Secret を取り出す。**Plugin 自身の領域のみ。** */
  getSecret(key: string): Promise<string | null>;
  /** 設定済みかどうかだけを見る。 */
  hasSecret(key: string): Promise<boolean>;
}
```

## 7. 画面

なし（型の定義のみ）。

## 8. 権限（Permission）

Plugin は Manifest で要求 Permission を宣言する（`03_プラグイン設計.md` §20.2）。

**Data API の呼び出しは、宣言した Permission を通る。**
宣言していない Permission の操作は失敗する。
「Plugin は信頼されたコード」だが、**必要以上の権限を取得しない設計を目指す**（同 §21）。

Plugin が自分の Permission を登録することもできる（`003-authorization` のレジストリ）。

## 9. Plugin API への影響

このスプリントが Plugin API そのもの。

### 後方互換性の判断基準

以下は**破壊的変更**として扱う（`07_開発者向けガイド.md` §47）。

* 既存の関数・プロパティを削除する
* 引数を増やす（省略可能なものを除く）
* 戻り値の型を狭める
* Event の Payload から項目を削除する、型を変える
* Extension Point を削除する
* Manifest の必須項目を増やす

**足すことは破壊的変更ではない。** 常に「足せる形」で設計する。

## 10. 受け入れ条件

### パッケージの境界

1. `packages/plugin-api` が `apps/web` を import していない
2. `packages/plugin-api` が `pg` / `kysely` / `next` を import していない
3. 公開する入口が `index.ts` の1つである

### Manifest

4. 妥当な Manifest を受け入れる
5. `id` が不正な形式なら拒否する（大文字・空白・記号）
6. `version` が Semantic Versioning でなければ拒否する
7. `apiVersion` が対応外なら拒否する
8. 未定義の Permission を宣言していたら拒否する
9. 必須項目が欠けていたら拒否する
10. 未知の項目があっても拒否しない（前方互換）
11. 依存 Plugin を宣言できる

### Key-Value Store

12. 値を保存して取り出せる
13. 保存していないキーは `null` を返す
14. 値を上書きできる
15. 値を削除できる
16. キーの一覧を取れる
17. 接頭辞でキーを絞り込める
18. **他の Plugin の領域が見えない**
19. **他の Plugin の領域へ書き込めない**
20. オブジェクト・配列・数値・真偽値を往復できる
21. キーの形式が不正なら拒否する
22. 値が大きすぎたら拒否する

### Secret

23. Secret を保存して取り出せる
24. **Secret が DB 上で平文になっていない**
25. 通常の `get()` で Secret の平文が取れない
26. `keys()` に Secret のキーは出るが、値は出ない
27. `hasSecret()` が設定済みかを返す
28. **他の Plugin の Secret が読めない**
29. Secret を削除できる

### Data API

30. Plugin が宣言した Permission の範囲で Sites を読める
31. 宣言していない Permission の操作が失敗する
32. **Data API 経由でも Permission チェックが働く**

### ログ

33. Plugin のログに `pluginId` が付く
34. **`Secret` 型の値をログへ渡しても平文が出ない**

### 型

35. Plugin API Version が定数として公開されている
36. Manifest の型が公開されている
37. `PluginContext` の型が公開されている
