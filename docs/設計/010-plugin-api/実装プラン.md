# Plugin API 実装プラン

入力：`設計.md`

## 1. 設計上の判断

### 1.1 資格情報を Plugin へ渡さない（`009-social` S-1 への回答）

**Core が `social_accounts.credential` を Plugin へ渡す経路を作らない。**

代わりに、Plugin が自分の名前空間へ `setSecret()` で保存し、
`getSecret()` で取り出す。これにより、

* Plugin は他の Plugin の資格情報を読めない
* 「Core が持っている資格情報を誰に渡すか」という判断が不要になる
* 認証方式がSNSごとに違っても Core が知らずに済む

`SocialAccountView` は `credentialConfigured: boolean` だけを持つ。

### 1.2 `pluginId` を Store の実装で閉じ込める

`createPluginStore({ connection, pluginId })` で束縛し、
`get(key)` / `set(key, value)` は `pluginId` を受け取らない。

**引数で渡せると、他の Plugin の資格情報を読めてしまう。**
「渡さないよう気をつける」ではなく、渡せない形にする。

### 1.3 Secret を `get()` で取り出せなくする

`is_secret` の値は `get()` が `null` を返す。`getSecret()` を使わせる。
取れてしまうと、うっかり一覧や画面へ載る。

### 1.4 Manifest の未知の項目を拒否しない

拒否すると、新しい項目を足した Plugin が古い本体で一切動かなくなる。
**前方互換性**のため、知らない項目は無視する。

### 1.5 Plugin ID にドットを許さない

`03_プラグイン設計.md` §16 の例は `example.plugin` だが、
**URL（`/plugins/<id>/`）とデータの名前空間になる**ため、
ドットは扱いにくい。英小文字・数字・ハイフンに限る。

> 仕様書の例と食い違うが、仕様書は「例」として挙げているだけで、
> 形式を規定してはいない。ここで確定させる。

### 1.6 Data API が二重に認可する

1. Plugin が Manifest で宣言したか（`PluginPermissionError`）
2. 操作しているユーザーが権限を持つか（`ForbiddenError`）

**Plugin が宣言していても、ユーザーが権限を持たなければ通らない。**
Plugin を入れただけで権限が増える、という状態を作らない。

### 1.7 ログの整形を出力の直前で行う

Plugin 作者が気をつけることに頼らない。
`Secret` 型と、機密になりうるキー名の値を機械的に落とす。

## 3. 残した未決

`social_accounts.credential` は、この方針では **Core 自身が使う当てが無い**。

* 画面から入力できる場所として残す（利用者が「とりふねに入れておく」）
* 削除して、資格情報は Plugin の store だけにする

どちらにするかは `012-plugin-manager` / `013-example-plugin` で
実際の使われ方を見てから判断する。`03_リスクと未決事項.md` に記録した。

## 4. リスク

| リスク | 対応 |
| --- | --- |
| Plugin が store を無限に使う | 1値 256KB の上限。全体の上限は `012` で検討 |
| `getSecret()` の呼び出しが増える | Plugin 自身の領域に限られるため、Core の資格情報は漏れない |
| Manifest の項目が将来増える | 未知の項目を無視する形にしてある |
