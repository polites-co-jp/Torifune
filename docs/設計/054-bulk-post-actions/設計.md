## 1. 目的（背景）

1. **投稿がどの外部アプリから来たかを、画面で見分けられるようにする。** 投稿は登録したトークンを `created_by_token_id` に
   記録している（`035` 裁定 #4「トークン 1 本 = 外部アプリ 1 つ」）が、画面には出していない。投稿一覧では誰が登録したかが分からず、
   承認待ちの区画も「API」か「画面」かしか出さない（`apps/web/src/app/social/page.tsx:203-204`）。複数の外部アプリを
   つないだ運用では、「このアプリの投稿だけをまとめて確かめたい・止めたい」ができない
2. **たくさんの投稿を、1 件ずつではなくまとめて捌けるようにする。** 外部アプリが承認待ち（`048`）の投稿をまとめて登録すると、
   今は 1 件ずつ「承認する」を押すしかない。不要になった予約も 1 件ずつ「削除」する。件数が増えると、押し間違い・押し忘れが増える
3. **一括でも、1 件の操作で守ってきた約束を崩さない。**
   * 承認するのは**画面で見た内容**（`048` §6.4.3。見た後に変わっていれば、その投稿だけ承認しない）
   * 承認できるのは **`social.approve` を持つ人**、削除できるのは **`social.delete` を持つ人**（`048` §8・`035` §6.8）
   * 配信中の投稿は書き換えない・消さない（`035` §6.2・`048` §6.3.6・`049`）
   * 操作の記録は**投稿ごとに**監査ログへ残り、承認のイベントも**投稿ごとに**出る

### 3.5 1 件の操作と権限

| 操作 | UseCase（行） | Permission | 振る舞いの要点 |
| --- | --- | --- | --- |
| 承認 `POST /social/posts/{id}/approve` | `approveSocialPost`（`social-use-cases.ts:1512-1614`） | `social.approve` | 承認待ちでなければ 422 `status` → `updatedAt` が違えば 409 → 時刻（`resolveApprovalSchedule`。手動投稿のみの SNS は常に即投稿、希望日時が無い・過ぎていれば 422 `scheduledAt`）→ 配信 Plugin の検査 → 条件付き更新（`approvePost`）→ `social.post.approved` → 監査 `approved` |
| 更新 `PATCH /social/posts/{id}` | `updateSocialPost`（`:1203-1426`） | `social.write` | 配信中のガード → 遷移 → 検査 → **承認済みの予約の内容・日時・配信方法を値として変えたら承認待ちへ戻す**（`revokesApproval`。`:1333`。048 裁定 10）→ 読んだ時点の状態・承認・着手印を条件に書く（048 §6.3.6） |
| 削除 `DELETE /social/posts/{id}` | `deleteSocialPost`（`:1428-1447`） | `social.delete` | 区画の外は 404。**状態を問わず消す**（配信済み・失敗・**配信中**も）。監査 `deleted`（`detail` なし）。イベントなし |

* 既定のロール：管理者は全部、**編集者は `social.read`・`social.write`・`social.approve`（`social.delete` は無い）**、閲覧者は `social.read`
  （`migrations/001_initial.sql:163-169`、`025_social_post_approval.sql`）
* 削除するとキャンペーンとの紐づけも消える（`campaign_social_posts.social_post_id … ON DELETE CASCADE`。`018_campaign_social_posts.sql:17`）
* 配信ジョブの取り出し条件は `status = 'scheduled' AND delivery_mode = 'auto' AND publish_started_at IS NULL AND scheduled_at <= now() AND (next_attempt_at IS NULL OR next_attempt_at <= now())`
  （`dueForAutoPublish`。`social-repository.ts:353-364`。`049`）。手動投稿待ちは `status = 'scheduled' AND delivery_mode = 'manual' AND scheduled_at <= now()`

## 4. スコープ

### 4.1 やること

1. 投稿一覧に **「登録元」の列**（トークンの名前／「管理画面」／失効・削除の印）（§5.6・§9.1）
2. 投稿一覧の**絞り込み**：状態・アカウント・登録元・表示件数（20／50／100。要裁定 ④）。URL のクエリで持ち、ページ送りでも保つ（§5.7・§9.2）
3. 行の**チェックボックス**と、見出しの**一括選択**（表示中のページの行）（§5.3・§9.3）
4. **一括送信（承認）**：承認待ちは承認（「即投稿」か「それぞれの希望日時に投稿」を押したときに選ぶ）、予約済み（未来）は「即投稿」のとき**今すぐ送る**（§8.2・§8.3・§9.5）
5. **一括取り消し**：選んだ投稿を削除する（下書き・承認待ち・予約済み。配信中・配信済み・失敗は対象外。要裁定 ②）（§8.4・§9.6）
6. 一括の 3 つの操作 `POST /social/posts/bulk/approve`・`/bulk/publish-now`・`/bulk/delete`（セッションだけ・100 件まで・項目ごとの結果）（§8）
7. 項目ごとの結果を画面に出す（全部成功なら Toast、1 件でも対象外・失敗があれば一覧のダイアログ）（§9.7）
8. 登録したトークンの名前の写しを投稿に残す列とマイグレーション `027`（要裁定 ①(A)）（§7）
9. 設定 → API の発行フォームに「名前は SNS 画面の投稿一覧に登録元として表示されます」の説明（§9.9）
10. OpenAPI・仕様書・手順書・関連設計の書き戻し（§15）

### 4.2 やらないこと

* **「承認待ち」「手動投稿待ち」の区画を変えること**（ユーザー裁定 1）。区画の「API」／「画面」の表示もそのまま（§17.2 の 1）
* **絞り込みに合う全件を選ぶこと**（他のページの行まで選ぶ）（§5.3）
* **下書きの一括送信**（下書きを予約にする・承認を依頼する）。要望は承認と今すぐ送るで、下書きは 1 件ずつ編集する
* **一括の「下書きへ戻す」（取りやめ）**。ユーザー裁定 4 で取り消しは削除と決まった
* **期限の来た予約・再試行待ち・支度待ちの予約を「今すぐ」送り直すこと**（`035` 裁定 #14-a の待ち時刻と 3 回上限を崩さない。§5.4）
* **API トークンからの一括操作**（§5.1）。外部アプリは今までどおり 1 件ずつの操作を使う
* **公開 API（`GET /social/posts`）への登録元の絞り込み・応答への登録元の項目**（§5.6）
* **本文の検索・日付の範囲の絞り込み・並び替えの切り替え**（§5.7）
* **投稿一覧のサイトでの絞り込み**（要裁定 ③(A)。`053` 裁定 9 のまま）
* **1 件の `DELETE /social/posts/{id}` の振る舞いの変更**（配信中・配信済みも今までどおり消せる。§17.2 の 2）
* Plugin API・イベント・Webhook の変更（§11）

### 4.3 全体の流れ

```text
/social「投稿」
  [状態▾] [アカウント▾] [登録元▾] [表示件数▾]  条件をクリア      ← URL のクエリ（postStatus 等）。Server Component が絞る
  ☑ 3 件を選択中   [一括送信（承認）…] [一括取り消し…]
  ┌☑┬アカウント┬本文┬登録元┬予約日時┬配信方法┬状態┬操作┐
  │☑│…        │…  │ブログ連携│…   │自動    │承認待ち│編集 削除│
  └─┴────┴──┴────┴───┴────┴───┴────┘

[一括送信（承認）…] → ダイアログで「即投稿」か「それぞれの希望日時に投稿」を選ぶ
   承認待ちの行   → POST /social/posts/bulk/approve      { publishTiming, items[{id, expectedUpdatedAt}] }
   予約済み（未来）→ POST /social/posts/bulk/publish-now  { items[...] }   ※「即投稿」を選んだときだけ
[一括取り消し…]   → 確認 → POST /social/posts/bulk/delete { ids }
                 → 200 { results[項目ごとの成否] } → Toast か結果のダイアログ → router.refresh()
```

## 5. 決めたこと

### 5.1 一括の操作は新しい API にし、セッションだけにする

| 案 | 内容 | 評価 |
| --- | --- | --- |
| (a) | 画面が既存の 1 件の操作（`approve`・`DELETE`）を件数分くり返す | 「今すぐ送る」は既存の操作で表せない（`PATCH { scheduledAt }` は承認を外す。§5.4）ので、新しい操作は結局要る。100 件で 100 往復、途中で画面を閉じると半端に終わる。対象外の判定が画面と API に分かれる |
| **(b)（採用）** | **一括の操作を 3 つ新設**し、サーバが項目ごとに既存の UseCase を呼んで結果をまとめて返す | 1 回の確認 → 1 回（一括送信は最大 2 回）の要求 → 1 つの結果。対象外の判定・監査・イベントは**既存の 1 件の UseCase のまま**（同じ規則が二重にならない） |
| (c) | 1 つの操作 `POST /social/posts/bulk` に `action` を持たせる | 操作ごとに必要な Permission が違う（承認・送信・削除）ので、ルートの `permission`（1 つ）と OpenAPI の `x-required-permission` で表せない |

**操作を分ける理由**：`defineRoute` の Permission は 1 つで、OpenAPI の `x-required-permission` にそのまま出る。
`social.approve`／`social.write`／`social.delete` を操作ごとに宣言できる形にする。

**セッションだけにする理由**（`sessionOnly: true`。トークンでは 401）：

* 一括操作は**人が画面で選んで行う操作**として要望された（ユーザー裁定 1）。外部アプリには 1 件ずつの操作がある
* **漏れたトークンの被害を広げない**。削除 100 件・承認 100 件を 1 要求で行える口をトークンに開ける理由が無い
* 区画（`053`）が絡まない：画面の文脈は常に区画 `all`。それでも UseCase は `scopeOf(context)` を通す（§6。経路に依存させない）
* 先例：トークンの発行・失効・サイトの変更（`021` §5・`053` §8.5.6）

将来トークンにも開ける場合は `sessionOnly` を外し、区画の 404 を項目の `not_found` に写すだけで済む（§17.2 の 3）。

### 5.2 項目ごとに独立して処理し、結果を項目ごとに返す（部分成功を認める）

* **全部か無しか、にしない。** 投稿は互いに独立していて、1 件の「見た後に変わっていた」で残りの 99 件を止める理由が無い。
  ユーザー裁定 2 も「投稿ごとに結果を知らせる」ことを求めている
* 項目ごとに**既存の 1 件の UseCase を呼ぶ**（それぞれが自分のトランザクション・条件付き更新・監査・イベントを持つ）。
  1 件の操作と一括の操作で、対象外の判定と記録が食い違わない
* 処理は**要求の並びの順に 1 件ずつ**（並列にしない）。配信 Plugin の `validate()`（最長 5 秒）を同時に何本も走らせない
* 要求の**形の誤り**（空・101 件以上・ID の重複・項目の形）だけは要求全体の 422 にする（何も処理しない）
* 1 件の想定外の例外（DB の一時的な失敗など）も、その項目の `internal_error` にして残りを続ける。全体を 500 にすると、
  それまでに成功した項目が画面に伝わらない
* **時間の予算**（§8.6）：1 要求の処理に `BULK_BUDGET_MS`（25 秒）を超えたら、まだ始めていない項目を `timeout` で返す

### 5.3 一括選択は表示中のページの行だけ

* 見出しのチェックボックスは**いま表に出ている行**（最大で表示件数＝100 件）を選ぶ。ページを移る・絞り込みを変えると選択は消える
* **絞り込みに合う全件を選ばない理由**：
  1. **承認は画面で見た内容に対して行う**（`048` §6.4.3）。見ていない他のページの投稿をまとめて承認すると、この約束が崩れる
  2. 項目ごとに `expectedUpdatedAt`（画面が読んだ `updatedAt`）が要るが、画面は他のページの行を読んでいない
  3. 1 要求 100 件と時間の予算（§8.6）に収まる単位にする
* 足りない分は**絞り込みと表示件数**で補う（例：状態「承認待ち」＋登録元「ブログ連携」＋100 件表示 → 一括選択）
* 一括選択の横に「このページの n 件を選択中（全 N 件）」と出し、全件ではないことを明示する（§9.3）

### 5.4 「今すぐ送る」と 048 裁定 10（決めたこと）

**「今すぐ送る」は `PATCH` ではなく別の操作**（UseCase `publishSocialPostNow`）にする。

| 論点 | 決めたこと | 理由 |
| --- | --- | --- |
| 承認を外すか | **外さない**（`approved_at` も `status` も変えない） | 048 裁定 10 は「承認の後に**内容・日時・配信方法が書き換えられた**ら、人が承認していないものが出る」ことを防ぐ規則。今すぐ送るは、(1) **内容を変えない**、(2) 画面で見た内容のまま（`expectedUpdatedAt` が一致しないと送らない）、(3) **承認の権限を持つ人が画面で選んだ時刻**で、1 件の承認で「即投稿」を選ぶのと同じ判断になる。外すと、承認者が自分で承認し直す手間だけが増える |
| 承認済みの予約を送れる人 | **`social.approve` を持つ人だけ**（`social.write` だけなら、その項目は `approval_required`） | 承認は「この内容を**この時刻に**出してよい」という判断（048 §1 の 3）。承認の権限の無い人が時刻を早められると、承認者が選んだ時刻が黙って変わる。既定のロールでは `social.write` を持つ編集者・管理者はどちらも `social.approve` を持つので、今の運用では差が出ない（ロールを編集できるようになったときの約束） |
| 承認を経ていない予約 | `social.write` で送れる。`approved_at` は NULL のまま（**今すぐ送っても「承認済み」にはならない**） | 承認済みの印（`approvedAt`）は承認の操作でだけ付く（048 §6.6.3） |
| 対象 | **`status = 'scheduled'` で、`scheduled_at` が未来か NULL** | 期限の来た予約は既に配信の順番を待っている。再試行待ち・支度待ちの待ち時刻（`next_attempt_at`）を「今すぐ」で消すと、`035` 裁定 #14-a（予約し直しでは待ちも回数も消えない。3 回上限の回避路を閉じる）と §6.5 の再試行の間隔を崩す。過去日時を「いますぐ」と読まない `035` §11 #21 とも揃う |
| 配信中 | 対象外（`publishing`） | 着手印がある行を書き換えない（048 §6.3.6・049）。未来の予約は着手されないが、読んでから書くまでの間の着手も条件付き更新で断る |
| 手動投稿（`deliveryMode: "manual"`） | **送れる**。予約日時がいまになり、すぐ**「手動投稿待ち」に並ぶ**（結果の `effect: "manual_pending"`） | 手動投稿は人が SNS で出す。Torifune が自動で送ることはできないので、「今すぐ送る」は「いま手動投稿待ちに並べる」になる。結果とダイアログでそう知らせる（§9.5） |
| 書くもの | `scheduled_at = いま`、`next_attempt_at = NULL`、`updated_at = いま`。`skip_count` / `skip_reason` / `attempt_count` / `approved_at` は触らない | 未来の予約を早めるだけ。待ち時刻は未来の予約には通常付いていないが、付いていれば消す（`clearsSkipWait` と同じ考え方） |
| 配信 Plugin の検査 | 掛ける（`checkSchedulable`・`checkPublisherRules`・手動投稿なら `checkManualSupport`） | 予約になる更新と同じ（`035` §6.2）。予約日時に依る検査があっても、新しい日時で検査する |
| 実際の送信 | **次の定期実行（既定 1 分以内）**。その場で配信 Plugin を呼ばない | 1 件の承認の「即投稿」と同じ意味（048 §6.1.1）。配信の手動実行（`POST /social/publish`）は `system.manage` の運用向けで、画面の一括操作から呼ばない |
| イベント | 出さない | 予約の更新にもともとイベントが無い（048 §6.8 と同じ判断） |

**`PATCH` で表さない理由**：`PATCH { scheduledAt }` は 048 裁定 10 で承認を外す。「今すぐ送る」のために `PATCH` に例外を作ると、
外部アプリの `PATCH` でも承認を外さずに日時を変えられる穴になる。別の操作にして、セッションだけ・`expectedUpdatedAt` 必須・
未来の予約だけ、に閉じる。**単独の API（`POST /social/posts/{id}/publish-now`）は作らない**（一括の操作からだけ届く。§17.2 の 4）。

### 5.5 一括取り消し＝削除の対象（ユーザー裁定 4。要裁定 ②(A)）

| 状態 | 一括取り消し | 理由 |
| --- | --- | --- |
| `draft` | 消す | 出す前の投稿 |
| `awaiting_approval` | 消す | 依頼を受けたが出していない投稿。外部アプリは次の `GET` で 404 を受け取る（§12） |
| `scheduled`（配信中でない。自動・手動とも） | 消す | 予約を取り消す。手動投稿待ちに並んでいるものも消える |
| `scheduled`（**配信中**：`auto` で着手印あり） | **対象外**（`publishing`） | 配信 Plugin が SNS へ送っている最中。消すと結果が記録できず、SNS には出たのに Torifune に記録が無くなる |
| `published` / `failed` | **対象外**（`not_applicable`）。要裁定 ② | 「取り消し」は出す前の投稿を止める操作と読む。配信済みを Torifune から消しても **SNS 上の投稿は消えない**ので、「取り消した」つもりで実際には出たまま、になる。履歴（`/social/history`）とキャンペーンの紐づけも失う。消したいときは今までどおり行の「削除」で 1 件ずつ |

* 削除は**条件付き**で行う：`DELETE … WHERE id = $id AND status = $読んだ状態 AND publish_started_at IS NULL`。
  読んでから消すまでの間に配信ジョブが着手・確定した行は消さず、`stale` を返す
* `expectedUpdatedAt` は**取らない**。取り消しは「この投稿を出さない」という判断で、外部アプリが本文を直していても判断は変わらない。
  状態が変わった（承認された・配信された）ときは上の条件で止まる
* 確認ダイアログ（§9.6）は件数・対象外の件数・「この操作は取り消せません」・キャンペーンの紐づけも消えることを出す

### 5.6 登録元の表示（要裁定 ①(A)）

| 投稿 | 表示 | 判定 |
| --- | --- | --- |
| トークンで登録、トークンが有効 | トークンの名前（例「ブログ連携」） | `created_by_token_id` があり、`api_tokens` の行がある |
| 同、トークンが失効 | 「ブログ連携（失効）」 | 行の `revoked_at` がある |
| 同、トークンの行が消えた（所有者のユーザーを削除） | 「ブログ連携（削除済み）」 | `created_by_token_id` が NULL で、**`created_by_token_name`（新しい列。§7）がある** |
| 画面（セッション）で登録 | 「**管理画面**」 | `created_by_token_id` も `created_by_token_name` も NULL |

* **名前の写しを投稿に持つ理由**（要裁定 ①(A)）：トークンの行は所有者の削除で消え、投稿の `created_by_token_id` は NULL になる。
  写しが無いと、その投稿は「管理画面」と**誤って**表示され、登録元「管理画面」の絞り込みにも入る（外部アプリの投稿を自分たちの下書きと
  取り違えて一括取り消しする、が起きうる）。`053` が `origin_site_scoped` を足したのと同じ「`SET NULL` で失われる事実を行に残す」判断。
  トークンの名前は発行後に変えられない（§3.4）ので、写しが古くなることは無い
* **同じ名前のトークン**（名前は一意ではない）：絞り込みの選択肢で名前が重なるときだけ、それぞれに「（発行 2026-10-01）」を添えて見分ける。
  列の表示は名前のまま
* **見せる範囲**：`social.read` を持つ人（閲覧者を含む）に、**投稿を登録したトークンの名前と失効の有無だけ**を見せる。
  所有者・識別子（prefix）・Scope・サイトは見せない。トークンの名前は運用者が外部アプリを見分けるために付けるもので、
  それを投稿一覧で見せることが要望そのもの。設定 → API の発行フォームに「名前は投稿一覧に表示される」と書く（§9.9）
* **トークンの ID を画面へ渡すのは、登録元の絞り込みの選択肢の値だけ**（`postSource=token:<id>`）。行には ID を渡さない。
  `035` §6.1.4 が応答から外したのは「**外部アプリ（トークン）**に他のアプリのトークン ID を見せない」ためで、画面はログインした人の
  セッションだけが見る。トークンの ID だけでは何もできない（トークンの操作は所有者のセッションと `token.manage` が要る）
* **公開 API には足さない**：`GET /social/posts` に登録元の絞り込み・応答に名前を足すと、サイトのトークンにまで他のアプリの名前が
  見え（区画をまたぐ情報）、`035` §6.1.4 の判断を崩す。外部アプリは自分の登録を `externalRef` で引ける
* **トークンのサイト（`053`）は列に出さない**：投稿のサイトはアカウントの「サイト」列（`053` §9.1.1）で分かる。列を増やすと狭い画面で読みにくい

### 5.7 絞り込みの選定（決めたこと）

| 絞り込み | 入れる | 理由 |
| --- | --- | --- |
| **状態** | 入れる | 一括操作は状態で対象が決まる（承認待ちを承認・予約を今すぐ送る・下書きを消す）。UseCase に既にある |
| **アカウント** | 入れる | 「この SNS アカウントの予約を止めたい」。UseCase に既にある |
| **登録元** | 入れる（新規） | 要望の中心（どのアプリから来たか）。「このアプリの承認待ちをまとめて承認」が絞り込み＋一括選択でできる |
| **表示件数**（20・50・100） | 入れる（要裁定 ④(A)） | 一括選択は表示中のページだけ（§5.3）。20 件では 1 回で捌ける量が少ない。上限 100 は API の `perPage` の上限・一括の上限と同じ |
| 本文の検索 | 入れない | 一括操作の対象の選び方として要望に無い。部分一致の検索は索引が無く、件数が増えると遅い |
| 日付の範囲 | 入れない | 同上。予約日時・作成日時のどちらで絞るかの判断も要る。後から足せる（§17.2 の 5） |
| サイト | 入れない（要裁定 ③(A)） | `053` 裁定 9 で `/social` のサイトの絞り込みはアカウント一覧だけと決まった |

* 絞り込みは**サーバで掛ける**（URL のクエリ → Server Component → UseCase）。手元で絞ると、表示中のページの中でしか絞れない
* 状態は**単一の選択**（今の UseCase と同じ）

## 7. データモデル（要裁定 ①(A)）

### 7.1 マイグレーション `migrations/027_social_post_token_name.sql`

```sql
-- SNS 投稿を登録したトークンの名前の写し（054-bulk-post-actions 設計 §5.6・§7）。
--
-- 投稿一覧の「登録元」に出す。トークンの行は所有者のユーザーを削除すると消え、
-- created_by_token_id は ON DELETE SET NULL で NULL になる（022）。写しが無いと、その投稿は
-- 画面（セッション）で登録した投稿と見分けられなくなる。トークンの名前は発行後に変えられない（053 §8.5.6）。
--
-- 既存行：トークンの行が残っている投稿はその名前で埋める。既に NULL の投稿は NULL のまま（見分けようが無い）。
--
-- **戻すとき**:
--   ALTER TABLE social_posts DROP CONSTRAINT social_posts_created_by_token_name_check,
--     DROP COLUMN created_by_token_name;
ALTER TABLE social_posts
    ADD COLUMN created_by_token_name text;

UPDATE social_posts AS p
   SET created_by_token_name = t.name
  FROM api_tokens AS t
 WHERE p.created_by_token_id = t.id;

ALTER TABLE social_posts
    -- トークンで登録した投稿は必ず名前を持つ。空白だけの名前は api_tokens でも断っている（011）。
    ADD CONSTRAINT social_posts_created_by_token_name_check
        CHECK ((created_by_token_id IS NULL OR created_by_token_name IS NOT NULL)
               AND (created_by_token_name IS NULL OR btrim(created_by_token_name) <> ''));
```

* 埋め戻しの `UPDATE` は投稿の件数ぶんの行ロックで、起動時の 1 回（`048` §5.1 と同じ規模の判断）
* CHECK は埋め戻しの**後**に足す（埋め戻す前の行で落ちない）。`NOT VALID` にはしない
* **索引は足さない**：登録元「管理画面」「削除されたトークン」の絞り込みは `created_by_token_id IS NULL` の行を見る。人が捌く画面の
  1 ページ分の問い合わせで、件数は SNS 投稿の数に留まる。トークンでの絞り込みは既存の部分索引 `social_posts_created_by_token_idx` に乗る

## 8. API

### 8.1 共通

| 項目 | 3 つの操作に共通 |
| --- | --- |
| 認証 | **セッションだけ**（`sessionOnly: true`。Bearer は 401 `UNAUTHENTICATED`）。CSRF を検証する（`csrfToken`） |
| 件数 | 1〜**`BULK_MAX_ITEMS`（100）**。0 件・101 件以上・**同じ ID の重複**は 422（キーは `items` / `ids`）で、何も処理しない |
| 処理 | 要求の並びの順に 1 件ずつ、項目ごとに独立（§5.2）。時間の予算 §8.6 |
| 応答 | **200**（全項目が失敗でも 200）。`{ data: { bulkId, results: BulkItemResult[] } }`。`results` は要求の並びと同じ順・同じ数 |
| Rate Limit | **60 秒に 30 回**（操作 × 送信元 IP。既定の 300 回より厳しい。1 回で 100 件動かせるため） |
| API Version | `v1`。追加だけ |
| 区画 | セッションなので常に `all`。項目の UseCase は `scopeOf(context)` を通す（区画の外は `not_found`） |

```ts
// domain/social/bulk.ts
export const BULK_MAX_ITEMS = 100;          // MAX_PER_PAGE（api/query.ts）と同じ値
export const BULK_BUDGET_MS = 25_000;

export const BULK_FAILURE_REASONS = [
  'not_found',            // 無い・区画の外・UUID の形でない
  'not_applicable',       // その操作の対象の状態でない（承認待ちでない・予約でない・配信済み など）
  'already_due',          // 今すぐ送る：予約日時が既に来ている（配信待ち・再試行待ち・支度待ち）
  'publishing',           // 配信中（着手印あり）
  'approval_required',    // 今すぐ送る：承認済みの予約で、操作した人が social.approve を持たない
  'stale',                // 見た後に内容か状態が変わった（409 相当）
  'no_desired_time',      // 承認（希望日時）：希望日時が無い
  'desired_time_passed',  // 承認（希望日時）：希望日時を過ぎている
  'validation',           // 配信 Plugin の規則など、その他の 422 相当
  'timeout',              // 時間の予算を超え、処理しなかった
  'internal_error',       // 想定外の失敗
] as const;

export const BULK_EFFECTS = [
  'approved_now',         // 承認・即投稿
  'approved_scheduled',   // 承認・希望日時で予約
  'approved_forced_now',  // 承認・希望日時を選んだが、手動投稿のみの SNS のため即投稿（048 裁定 5）
  'queued',               // 今すぐ送る：次の定期実行で配信
  'manual_pending',       // 今すぐ送る：手動投稿待ちに並んだ
  'deleted',              // 取り消し（削除）
] as const;

export type BulkItemResult =
  | { readonly id: string; readonly ok: true; readonly effect: BulkEffect; readonly post: SocialPost | null }
  | { readonly id: string; readonly ok: false; readonly reason: BulkFailureReason;
      readonly message: string; readonly field: string | null };
```

* `post` は成功した承認・今すぐ送るの**処理後の投稿**（応答では `postResponseSchema` の形）。削除は `null`
* `message` は**1 件の操作が返すのと同じ文言**（例：希望日時を過ぎていれば 048 の「指定の日時を過ぎています。即投稿を選ぶか、未来の日時を指定してください。」）。
  `field` は 422 の `details` のキーにあたるもの（無ければ `null`）
* `bulkId` はサーバが要求ごとに作る UUID。各項目の監査の `detail.bulkId` と同じ値（§8.10）

#### 8.1.1 例外から理由への写し（`bulk-post-use-cases.ts`）

| 項目の UseCase が投げたもの | `reason` |
| --- | --- |
| `NotFoundError` | `not_found` |
| `SocialPostIneligibleError`（新。`reason` を持つ） | その `reason`（`not_applicable` / `already_due` / `publishing` / `approval_required`） |
| `ValidationError` で `field === 'status'`（例：承認待ちでない） | `not_applicable` |
| `ApprovalScheduleError`（新）で `reason: 'missing'` / `'past'` | `no_desired_time` / `desired_time_passed` |
| `StaleSocialPostError` / `SocialPostStateChangedError` | `stale` |
| それ以外の `ValidationError`（`ApprovalScheduleError` の `out_of_range` を含む） | `validation`（`field` と `message` をそのまま） |
| それ以外（`ForbiddenError` を含む） | `internal_error`（`message` は「処理中にエラーが発生しました。」。原因はサーバのログに投稿 ID と残し、応答に載せない） |

* `ApprovalScheduleError` と `SocialPostIneligibleError` は `ValidationError` の派生にする。**1 件の承認の応答（422 `scheduledAt` と文言）は変わらない**
* `ForbiddenError` は、ルートが操作の Permission を先に検査するので通常は起きない（今すぐ送るの承認の権限は `approval_required` で表す）

### 8.2 一括承認 `POST /api/v1/social/posts/bulk/approve`（`social.approve`）

**要求**

| 項目 | 型 | 必須 | 制約（違反は 422。キーはその項目名） |
| --- | --- | --- | --- |
| `publishTiming` | `'now' \| 'scheduled'` | **必須** | `now`＝即投稿、`scheduled`＝**それぞれの登録された希望日時**に投稿（`after_approval` も 422） |
| `items` | `{ id: string; expectedUpdatedAt: string }[]` | **必須** | 1〜100 件、`id` の重複なし。`id` は 1 文字以上の文字列（UUID の形でなければその項目が `not_found`）。`expectedUpdatedAt` は ISO 8601（`approvePostSchema` と同じ検査） |
| `csrfToken` | string | 任意 | 画面用 |

* **`scheduledAt`（日時の指定し直し）は取らない**。一括では「即投稿」か「それぞれの希望日時」のどちらか（ユーザー裁定 2）。日時を選び直したい投稿は
  1 件の承認（区画の「承認する」）で行う

**UseCase `bulkApproveSocialPosts`**（`social.post.bulkApprove`、Permission `social.approve`、監査なし＝項目ごとに残る）

1. 項目ごとに `approveSocialPost(context, { id, publishTiming, expectedUpdatedAt, bulkId })`（`scheduledAt` は渡さない ＝ `scheduled` なら登録された希望日時）
2. 成功：`effect` は `effectiveTiming === 'scheduled'` → `approved_scheduled`、`approvalForced` → `approved_forced_now`、それ以外 → `approved_now`
3. 失敗：§8.1.1 で写す

| 起きること | 項目の結果 |
| --- | --- |
| 承認待ち・`now` | `approved_now`（予約・`scheduledAt` ≒ いま・`approvedAt` あり）。`social.post.approved` が 1 回 |
| 承認待ち・`scheduled`・希望日時が未来 | `approved_scheduled`（`scheduledAt` ＝ 希望日時） |
| 同・希望日時が無い | `no_desired_time`（承認待ちのまま） |
| 同・希望日時が過ぎている（いまと等しいも含む） | `desired_time_passed`（承認待ちのまま） |
| 手動投稿のみの SNS・`scheduled` | `approved_forced_now`（048 裁定 5） |
| 承認待ちでない（承認済み・下書き・配信済み など） | `not_applicable`（`message`「承認待ちの投稿ではありません（いまの状態：scheduled）。」） |
| `updatedAt` が違う | `stale` |
| 配信 Plugin の検査で 422 | `validation` |
| 無い・区画の外 | `not_found` |

### 8.3 今すぐ送る `POST /api/v1/social/posts/bulk/publish-now`（`social.write`）

**要求**：`items`（§8.2 と同じ形・制約）、`csrfToken`。

**UseCase `publishSocialPostNow`**（新。`social.post.publishNow`、Permission `social.write`、監査 `updated`。**単独のルートは無い**）

| 順 | 検査 | 失敗 |
| ---: | --- | --- |
| 1 | `findPostById(id, scopeOf(context))` | `NotFoundError` |
| 2 | `publishNowEligibility(post, now)`（Domain。下の表） | `SocialPostIneligibleError`（`not_applicable` / `publishing` / `already_due`） |
| 3 | `updatedAt`（ミリ秒）が `expectedUpdatedAt` と一致 | `StaleSocialPostError` |
| 4 | `post.approvedAt !== null` なら `context.permissions` に `social.approve` | `SocialPostIneligibleError`（`approval_required`。「承認済みの予約を今すぐ送るには、承認の権限が要ります。」） |
| 5 | アカウントを引く（無ければ 422 `socialAccountId`） | `ValidationError` |
| 6 | `assertPostIsDeliverable({ …post, status: 'scheduled', scheduledAt: now }, account, { checkSchedulable: true, checkPublisherRules: true, checkManualSupport: post.deliveryMode === 'manual' })` | `ValidationError`（配信 Plugin のキー） |
| 7 | 条件付き更新 `publishNow`（§8.3.1）。0 行なら 1〜3 をやり直して該当の誤りを投げ、どれにも当たらなければ `SocialPostStateChangedError` | — |

`publishNowEligibility(post, now)`（並びは判定の順）：

| 条件 | 結果 |
| --- | --- |
| `status !== 'scheduled'` | `not_applicable`（「予約済みの投稿ではありません（いまの状態：draft）。」） |
| `deliveryMode === 'auto'` かつ `publishStartedAt !== null` | `publishing`（「配信を開始しているため変更できません。結果が記録されるまで待ってください。」＝既存の配信中の文言） |
| `scheduledAt !== null` かつ `scheduledAt <= now` | `already_due`（「予約日時を過ぎているため、既に配信の順番を待っています。」） |
| それ以外（未来・NULL） | 対象 |

**成功**：`effect` は `deliveryMode === 'manual'` → `manual_pending`、それ以外 → `queued`。

#### 8.3.1 条件付き更新（Repository `publishNow`）

```sql
UPDATE social_posts
   SET scheduled_at = $now, next_attempt_at = NULL, updated_at = $now
 WHERE id = $id
   AND status = 'scheduled'
   AND publish_started_at IS NULL
   AND (scheduled_at IS NULL OR scheduled_at > $now)
   AND date_trunc('milliseconds', updated_at) = $expectedUpdatedAt
RETURNING *;
```

* `approved_at`・`skip_count`・`skip_reason`・`attempt_count`・本文などは書かない（§5.4）
* 読んでから書くまでに承認が外れた（外部アプリの `PATCH` で承認待ちへ戻った）・取りやめられた・配信ジョブが着手した行には当たらない
  （`status`・着手印・`updated_at` のどれかが変わる）。読み直して `not_applicable` / `publishing` / `stale` のどれかになる
* 区画の条件は足さない（`053` §8.3.3 と同じ。区画は読み出しの時点で判定済み）

**`bulkPublishSocialPostsNow`**（`social.post.bulkPublishNow`、Permission `social.write`）は項目ごとに `publishSocialPostNow(context, { id, expectedUpdatedAt, bulkId })` を呼ぶ。

### 8.4 一括取り消し `POST /api/v1/social/posts/bulk/delete`（`social.delete`）

**要求**

### 8.6 時間の予算

* 一括の UseCase は始めた時刻を覚え、**各項目を始める前に** `BULK_BUDGET_MS`（25 秒）を過ぎていないかを見る。過ぎていれば、残りの項目は
  処理せず `timeout`（「時間内に処理できませんでした。もう一度操作してください。」）にする。始めた項目は最後まで処理する
* 予算は入力で差し替えられる（`budgetMs`。テスト用。既定は `BULK_BUDGET_MS`）
* **理由**：承認と今すぐ送るは項目ごとに配信 Plugin の `validate()`（最長 5 秒）を呼ぶ。100 件で最悪 500 秒になり、HTTP の要求が
  途中の仕組み（逆プロキシなど）に切られると、どこまで処理したかが画面に伝わらない。手動投稿の区画の予算（§3.6）と同じ考え方。
  通常の `validate()` は手元の検査で、100 件は予算に十分収まる

### 8.8 登録元の一覧 `listSocialPostSources`（新。`social.post.listSources`、Permission `social.read`。画面だけ）

```ts
export interface SocialPostSources {
  /** 区画から見える投稿を登録したトークン（失効を含む）。名前 → 発行日時 → ID の順。 */
  readonly tokens: readonly { readonly id: string; readonly name: string; readonly revoked: boolean; readonly createdAt: Date }[];
  /** 画面（トークンを経ない）で登録した投稿があるか。 */
  readonly hasScreenPosts: boolean;
  /** トークンの行が消えた投稿があるか。 */
  readonly hasDeletedTokenPosts: boolean;
}
```

* Repository `listPostSourceTokens(connection, scope)`：区画を掛けた投稿（`scopedPosts`）の `DISTINCT created_by_token_id` を `api_tokens` と結合する
  （既存の部分索引に乗る）。2 つの真偽は同じく区画を掛けた `EXISTS`
* **トークンの所有者を問わない**（`GET /api-tokens` は自分のトークンだけだが、ここは「投稿を登録したもの」の名前を出す。§5.6）
* 画面は**行の登録元の表示**（`postSourceOf` に渡す対応表）と**絞り込みの選択肢**の両方にこれを使う

`postSourceOf(post, tokens)`（Domain の純関数）：`createdByTokenId` があり対応表にあれば `token`（名前と失効は対応表から）、
対応表に無ければ `token`（名前は `createdByTokenName`、失効は偽）、`createdByTokenId` が NULL で名前があれば `deleted_token`、両方 NULL なら `screen`。

| `bulkApproveSocialPosts` | `POST /social/posts/bulk/approve` | `social.approve` | `[{ session: [] }]` | 200・401・403・422・429・500 |
| `bulkPublishSocialPostsNow` | `POST /social/posts/bulk/publish-now` | `social.write` | 同 | 同 |
| `bulkDeleteSocialPosts` | `POST /social/posts/bulk/delete` | `social.delete` | 同 | 同 |

* **404・409 は宣言しない**（項目ごとの結果は 200 の本文。§5.2）
* 要求：`items`（`minItems: 1`・`maxItems: 100`）、`publishTiming`（`enum: ['now', 'scheduled']`）、`ids`（同じ件数の制約）。
  重複の禁止は `description` に書く（JSON Schema の `uniqueItems` は配列の要素の値全体の一意で、`items` の `id` の一意を表せない）
* 応答：`results` の要素は `ok` で分かれる 2 つの形（`oneOf`）。`reason` の `enum` は `BULK_FAILURE_REASONS`、`effect` の `enum` は `BULK_EFFECTS`。
  `post` は `postResponseSchema`（`nullable`）
* 各操作の `description` に「画面（セッション）専用。API トークンでは 401。」
* `listSocialPosts`・`postResponseSchema` は**変えない**

### 8.10 監査

| 操作 | `action` | `detail` |
| --- | --- | --- |
| 一括承認の各項目 | `approved`（既存） | 既存（048 §6.9）に **`bulkId`** を足す（一括のときだけ） |
| 今すぐ送るの各項目 | `updated`（既存） | `{ operation: 'publish_now', changed: ['scheduledAt'], status: 'scheduled', previousScheduledAt（ISO か null）, approvalKept（承認済みだったか）, deliveryMode, bulkId }` |
| 一括取り消しの各項目 | `deleted`（既存） | **`{ status（消す前の状態）, bulkId }`** |
| 1 件の削除（`DELETE /social/posts/{id}`） | `deleted`（既存） | **`{ status }`** を足す（今は `detail` なし）。`bulkId` は無い |

* **項目ごとに 1 行**。一括の要求そのものの行は作らない（`bulkId` で束ねられる）。失敗した項目は残さない（失敗は記録しない既存の方針。`use-case.ts`）
* 新しい `action` は足さない（`AUDIT_ACTIONS` は変わらない）。今すぐ送るは「予約日時の更新」なので `updated` で、`operation` で見分ける
* 操作した人は `actorUserId`（セッションのユーザー）。本文は残さない（既存の方針）

### 8.11 イベント・Webhook

* 一括承認：成功した項目ごとに既存の **`social.post.approved`** が 1 回（`approveSocialPost` が出す）。購読している Webhook には件数分届く
* 今すぐ送る・取り消し：**イベントなし**（予約の更新・削除にもともとイベントが無い）
* 一括をまとめたイベントは足さない

### 9.3 選択と一括選択

* 選択は Client Component の状態（ID の集合）。ページ・絞り込みを変えると読み込み直すので消える。一括操作の後も `router.refresh()` で消える（§9.7）
* 見出しのチェックボックス（`aria-label`「このページの投稿をすべて選択」）：
  * 0 件選択 → 未チェック。全行選択 → チェック。一部 → **`indeterminate`**

* 一括の帯の左に「**n 件を選択中**」。表示中の行が `total` より少なく、全行を選んでいるときは「このページの n 件を選択中（全 N 件）」
* 行の 1 件の「削除」で行が消えたら、その ID を選択からも外す

* 内訳は純関数 **`sendPlanOf(rows, timing, permissions)`**（`ui/social/bulk-plan.ts`）が作る：

| 行 | `now` | `scheduled`（希望日時） |
| --- | --- | --- |
| 承認待ち・`canApprove` | 承認（`approve`） | 承認（`approve`）。`desiredPast` / 希望日時なしは**送るが**警告の件数に数える（結果はサーバが返す） |

* 2 本目の要求が要求ごと失敗した（401・403・422・429・500・通信の失敗）ときも、1 本目の結果は捨てずに §9.7 の結果に並べ、

### 9.7 結果の表示

* 純関数 **`summarizeBulkResults(results, rows)`** が、成功の件数（`effect` ごと）と、失敗の一覧（行の本文の抜粋・理由の表示名・`message`）を作る
* **全件成功**：`Toast`（success）。例「6 件を処理しました（承認 4・今すぐ送る 2）。」「4 件を削除しました。」→ **`router.refresh()`**
* **1 件でも失敗・対象外・要求の失敗がある**：`Modal`「一括操作の結果」

  ```text

  │ 2 件は処理されませんでした。                                │
  │ ・「新製品のお知らせ…」 希望日時を過ぎています。              │
  │     指定の日時を過ぎています。即投稿を選ぶか、…               │
  │ ・「秋のセール…」 内容が変わっています。読み込み直して…       │
  │                                           [閉じる] │
  └─────────────────────────────────────┘
  ```

  「閉じる」で `router.refresh()`。理由の表示名は `BULK_REASON_LABEL`（§9.10）、その下に `message`（サーバの文言）
* 要求ごと失敗し、1 件も処理していない（例：401・429）：`Toast`（danger）にエラーの文言。読み込み直さない（選択は残る）
* **読み込み直すと選択は消える**。処理されなかった投稿を選び直すには絞り込みを使う（例：承認待ちのまま残った投稿は、状態「承認待ち」で絞れば

* 既定のロールでは：**管理者**はすべて、**編集者**は一括送信だけ（`social.delete` が無いので一括取り消しは出ない）、**閲覧者**は登録元と絞り込みだけ
* 一括の UseCase は、ルートの検査に頼らず `defineUseCase` の Permission で**最初に**検査する（1 件も処理しない）。項目の UseCase も自分の Permission を検査する

### 10.2 新しい Permission を作らない理由

一括は既存の操作をまとめて行うだけで、できることは増えない（承認・今すぐ送る・削除は、それぞれ既存の Permission の範囲）。
「今すぐ送る」の承認済みの予約への制限（§5.4）も既存の `social.approve` で表す。

### 10.3 ID の差し替え

投稿は利用者ごとの所有物ではない（`035` §8.1）。他人が登録した投稿をまとめて承認・削除できるのは、その Permission を持つ人の正当な操作である。
検証するのは「存在しない ID・UUID の形でない ID は `not_found`」「対象外の状態は `not_applicable`」（§13）。
