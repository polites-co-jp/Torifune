### 確定事項（設計書から。プランで蒸し返さない）

* 置き場は `/social` の既存の「投稿」一覧。「承認待ち」「手動投稿待ち」の区画は変えない（ユーザー裁定 1。設計 §4.2）
* 一括の操作は**新しい 3 つ**：`POST /social/posts/bulk/approve`（`social.approve`）・`/bulk/publish-now`（`social.write`）・`/bulk/delete`（`social.delete`）。**`sessionOnly`**（Bearer は 401）、CSRF を検証、1〜**100 件**、ID の重複・0 件・101 件以上・項目の形の誤りは要求全体の 422（何も処理しない。検証 1 回目で、件数が外れたら要素を見ない・`id` は 100 文字まで・重複は小文字にそろえて比べる、を足した。設計 §8.1.2・G12）、**項目ごとに独立して順に処理し 200 で項目ごとの結果**、Rate Limit は **60 秒 30 回**（設計 §5.1・§5.2・§8.1）
* 一括の UseCase は**既存の 1 件の UseCase を呼ぶだけ**（Repository を直接触らない。設計 §6・#56）。例外 → `reason` の写しは設計 §8.1.1 の表
* 一括承認は `publishTiming: 'now' | 'scheduled'`（`scheduledAt` は取らない）。結果の `effect` は `approved_now` / `approved_scheduled` / `approved_forced_now`（ユーザー裁定 2。設計 §8.2）
* **今すぐ送る**は UseCase `publishSocialPostNow`（単独のルートは無い）。承認を外さない。承認済みの予約は `social.approve` を持つ人だけ（無ければ `approval_required`）。対象は `scheduled` で `scheduledAt` が未来か NULL だけ（期限の来た・再試行待ち・配信中は対象外）。書くのは `scheduled_at = いま`・`next_attempt_at = NULL`・`updated_at`（ユーザー裁定 3。設計 §5.4・§8.3）
* **一括取り消し＝削除**。消せるのは `draft` / `awaiting_approval` / `scheduled`（配信中を除く）だけ。条件付き削除（`status` と着手印）。`expectedUpdatedAt` は取らない（ユーザー裁定 4・6。設計 §5.5・§8.4）。1 件の `DELETE /social/posts/{id}` の振る舞いは変えない（監査の `detail` に `{ status }` が増えるだけ）
* 登録元は**トークンの名前**（失効は「（失効）」、トークンの行が消えた投稿は名前の写しで「（削除済み）」、トークンを経ない登録は「管理画面」）。名前の写しは**マイグレーション `027`** の `social_posts.created_by_token_name`（ユーザー裁定 5。設計 §5.6・§7）
* 絞り込みは**画面だけ**（状態・アカウント・登録元・表示件数 20／50／100）。URL のクエリ `postStatus` / `postAccount` / `postSource` / `postPerPage` / `postPage`、誤った値は無視（ユーザー裁定 7・8。設計 §5.7・§9.2）。**`GET /social/posts` と `postResponseSchema` は変えない**
* 一括選択は**表示中のページの行だけ**（設計 §5.3）
* 監査は項目ごとに既存の `action`（`approved` / `updated` / `deleted`）、同じ要求を `detail.bulkId` で束ねる。新しい Permission・`action`・イベントは作らない。**`PLUGIN_API_VERSION` は 1 のまま**（設計 §8.10・§10・§11）
* 共通部品 `Table` の `Column.header` を `string` から `ReactNode` に広げる（設計 §6・§11）
* 文書の書き戻しは設計 §15 の範囲。**`docs/仕様書/` は変えない**
* 検証は **`spec-verifier` / `boundary-guardian` / `security-reviewer` の 3 つ**（公開 HTTP API・認可・監査・マイグレーションを変えるため）
* **SaaS 固有機能（テナント・課金・コンテナ管理）に触るタスクは本プランに無い**

## 3. タスク分解

原則：**1 タスク = 1 コミット**。各タスクは「テストを書いて失敗を確認 → 実装 → 通す」の順。

**test-writer → implementer への受け渡しの単位は G（まとまり）。** test-writer は G の中の全タスクのテスト（と既存テストの追従）を先に書いて、新しいテストが**期待どおりの理由で**赤いことを確かめ、`test:` でコミットする（`pnpm typecheck` / `pnpm lint` / `pnpm format:check` は通る状態で。未実装のモジュール・ルートは動的 import）。implementer は G の中のタスクを順に通し、タスクごとに `feat:`（文書は `docs:`）でコミットする。
**implementer はテストを書き換えない。** テストが設計と食い違うと判断したら、設計書のどこと食い違うかを報告して止まる。

**プッシュの約束（test-writer・implementer とも）**：プッシュの前に必ず `pnpm test` を**全件**流す（postgres-test、`DATABASE_URL=postgresql://torifune:torifune@localhost:21701/torifune_test`、CI と同じテスト用の `TORIFUNE_ENCRYPTION_KEY`）。**既存のテストと、すでに実装したタスクのテストが 1 件でも赤ならプッシュしない。** 赤くてよいのは、いま取り組んでいる G のまだ実装していないタスクのテストだけ。`main` / `master` へはプッシュしない、マージしない、`--force` は使わない。

**着手順の骨子**：DB と名前の写し → Domain の純関数 → 一覧の登録元・絞り込み → 一括承認 → 今すぐ送る → 一括取り消し → 時間の予算と OpenAPI → UI の部品 → 画面の組み立てと E2E → 文書 → 最終確認と 3 つの検証。
**G は前の G に依存する**（G2 は G1、G3 は G2、G4 は G3、G5 は G4、G6 は G5、G7 は G6、G8 は G3 と G7 の API の形、G9 は G8）。G10 は G7 の後ならいつでもよいが、振る舞いが入ってから書く。

## 7. リスクと注意点

1. **一括の UseCase に規則を二重に書かない（T11・T16・T20）。** 区画・権限・条件付き更新・監査・イベントは項目の UseCase のまま。一括の側で状態を先に判定して飛ばすと、1 件の操作と結果が食い違う（#56 が import で守る）
2. **項目の例外を全体に漏らさない（T11）。** `internal_error` に写すのは「それ以外」の例外だけで、§8.1.1 の表の順（`SocialPostIneligibleError` / `ApprovalScheduleError` を `ValidationError` より先に判定）を守る。`internal_error` の `message` に例外の文言を入れない（#46）
3. **1 件の承認の監査の `detail` を変えない（T10）。** `bulkId` は入力にあるときだけ足す（既存の #47 がキー集合をちょうど見ている。§8 の 11）
4. **条件付き更新・削除の 1 文（T14・T18）。** 読んだ時点の判定と書く条件を分けない。`publishNow` は `date_trunc('milliseconds', updated_at)` で比べる（`approvePost` と同じ。作成直後の投稿が合わなくならないように）
5. **`publish.ts` と取り出し条件に触らない（T14〜T16）。** 「今すぐ」はその場で配信しない（次の定期実行。設計 §5.4）。`POST /social/publish` を画面から呼ばない
6. **422 のキー（T12・T16・T20）。** 要素の誤りも `items` / `ids` に集める（§8 の 6）。OpenAPI の `items` の要素の形はなるべく残す
7. **Rate Limit がテストに掛かる（T9・T13・T17）。** 1 ファイルで同じ操作を 30 回より多く叩くので、件ごとに `x-forwarded-for` を変える（#52 だけ同じ IP）
8. **`useRouter` と既存の単体テスト（T23・T26）。** `social-posts.test.ts` の差し替えを G8 の test-writer が入れる（§8 の 4）。差し替えずに `SocialPosts` に `useRouter` を足すと既存の全件が落ちる
9. **既存の E2E の locator（T26・T29）。** 一括の帯のボタンに「削除」を含めない（`social.spec.ts`）。ダイアログは閉じている間は描かない（`social-approval.spec.ts` の `getByRole('dialog')`・`getByLabel(/即投稿/)` と取り違えない）。絞り込みのラベル（「状態」「アカウント」「登録元」「表示件数」）は `/social` の既存の `getByLabel`（「サイトで絞り込む」など）と部分一致しない
10. **E2E の後片付けと順序（T28）。** `social-bulk-actions.spec.ts` は `social-approval.spec.ts`・`social-account-id.spec.ts` の後、`social-credentials.spec.ts`・`social-publishing.spec.ts`・`social.spec.ts` の前に走る。承認待ち・Plugin・アカウントを残すと後の spec の前提を壊す。トークンは消せないので失効させる
11. **E2E の定期実行（T28）。** E2E のサーバは配信の定期実行が有効で、即投稿した予約は 1 分以内に配信されうる（§8 の 23）
12. **`GET /api/v1/auth/csrf` とログインの Rate Limit（T28）。** API での準備を最小にし、トークンとアカウントは spec の中で使い回す。#87 の 21 件の登録は 1 回の `beforeAll` か件の中でまとめて行う
13. **文書の静的検査の文字列を消さない（T30）。** `static-checks.test.ts` #81・`text-input-docs-static-checks.test.ts`
14. **公開リポジトリ（全コミット）。** コメント・コミットメッセージ・文書に外部の製品名・運営側の事情・作業機の事情を書かない
15. **`verify-container-rebuild.sh` は Docker が要る（T31）。** 無い環境では飛ばし、検証レポートへ申し送る。E2E・`pnpm test` と同時に流さない
