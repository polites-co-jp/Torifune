# 053 SNS アカウントと API トークンを Web サイトに紐づける 設計

> 利用者からの要望（2026-10-08）：「Torifune の SNS アカウントを **Web サイトごとに管理**したい。外部のアプリが API で

## 1. 目的（背景）

1. **外部アプリごとに、触れる SNS アカウントを限る。** いまの Torifune では API トークンは「どのアプリが登録したか」の
   **名前空間**にすぎず、`social.write` を持つトークンは**どのアカウントにも投稿でき、他のアプリが登録した投稿を読み書きでき、
   他のアカウントの資格情報を上書きできる**（`docs/マニュアル/SNS投稿API仕様.md` §2.3、手順書 §1「トークンは名前空間であって、分離境界ではない」）。
   1 つの Torifune で複数の Web サイトを運用し、サイトごとに別の外部アプリ（記事を公開したら SNS へ流す仕組みなど）を
   つなぐと、**あるサイトのアプリの不具合や漏えいが、別のサイトの SNS アカウントから任意の文章を出す**ことに直結する
2. **SNS アカウントを Web サイトの単位で整理する。** Torifune はもともと「Web サイト・SNS 等を一元管理する」アプリで、
   サイト（`sites`）は既にある。どのアカウントがどのサイトのものかを Torifune が知れば、画面で見分けられ、
   トークンの範囲もそれで決められる
3. **既存の運用を壊さない**（裁定 4）。紐づけをしない限り、既存のトークン・アカウント・投稿の振る舞いは変わらない

**上位仕様との矛盾は無い。**

**マルチテナントのデータ分割ではない**（`CLAUDE.md`「絶対に守る境界」、`04` §29、`05` §32）。テナントは「別の顧客・別の DB」を分ける単位で、
Torifune はそれを持たない。本設計の区画は、**1 つの運用者が、自分の Web サイトの 1 つのために外部アプリへ渡すトークンの範囲を狭める**
最小権限の道具で、`05` §38 の Scope（権限の種類で狭める）と同じ側にある。

* **人（ユーザー）はサイトに紐づかない。** 画面のセッションは区画で絞らず、すべてのサイトのアカウントと投稿を扱える（§5.4）。
  「サイトの担当者」「サイトごとのロール」は作らない（§18.3 の 6）
* データは 1 つの DB の同じ表にあり、Database Provider も接続先も変わらない
* サイトは Torifune が元から持つ業務上の対象（`02` §5.3・`06` §11）で、SaaS の運営のための概念ではない

### 3.2 認可

* 認可の文脈 `AuthorizationContext` は `identity`・`permissions`・`connection`・`request` と、トークン認証のときだけ
  **`apiToken: { id, name }`** を持つ（`apps/web/src/application/authorization/authorize.ts:44-67`、`:66`）。
  `apiToken` は「どのアプリが登録したか」の名前空間で、**認可には使っていない**（`035` §6.1.3）
* トークンの文脈は `buildApiTokenContext` が組み立てる（`apps/web/src/application/authorization/context.ts:67-118`）。
  失効・期限切れ・所有者の無効化は「未認証」に倒し、理由を返さない（`:80`）。実効 Permission は所有者の Permission ∩ Scope（`:111`）。
  `apiToken` はトークン行から積む（`:115`）
* Permission の検査は `defineUseCase` が行う（`apps/web/src/application/authorization/use-case.ts:79-81`）。
  **リソース単位の絞り込みの仕組みは無い**
* トークンの発行・失効は**セッションからだけ**（`apps/web/src/app/api/v1/api-tokens/route.ts:37`、`[id]/route.ts:16`。
  トークンで叩くと 401。`apps/web/src/api/route.ts:345-349`）。発行は監査に残っていない（`apps/web/src/application/api-token/api-token-use-cases.ts:38-88`。

## 4. スコープ

### 4.1 やること

1. `social_accounts.site_id`・`api_tokens.site_id` / `site_scoped`・`social_posts.origin_site_id` / `origin_site_scoped` を足すマイグレーション `026`（§7）
2. 区画 `AccessScope` と、アカウント・投稿が見えるか・変えられるかを決める Domain の純関数（§5・§6）
3. トークンの文脈に区画を積む。サイトのトークンは**サイトが消えた・アーカイブされたら未認証**（§8.5.3。アーカイブは裁定 8）
4. SNS の全 UseCase を区画で絞る（一覧は SQL で、ID 指定は 404 で。§8.2〜§8.4）
5. API：アカウントの `siteId`（応答・作成・更新）、トークンの `siteId` / `siteScoped`（発行・応答）、サイトの削除の 409（§8）
6. サイトのトークンに付けられる Scope を SNS の 4 つに限る（裁定 6。DB の CHECK でも守る。§7.2）
7. **トークンのサイトの変更** `PATCH /api-tokens/{id}`（裁定 7。§8.5.6）と、変更に合わせた投稿の登録元の区画の付け替え（要裁定 ⑥）
8. 監査：トークンの発行（新たに残す）・トークンのサイトの変更・アカウントのサイトの変更・サイトの削除で失効させたトークンの数（§8.9）
9. 画面：`/social` のサイトの列・追加時のサイト・「サイト」の操作・アカウント一覧のサイトでの絞り込み（裁定 9）、設定 → API の発行のサイトと「サイトを変える」、サイトの削除の失敗の文言（§9）
10. OpenAPI・API 仕様書・手順書・関連設計の書き戻し（§15）

### 4.2 やらないこと

* **人（ユーザー）をサイトに紐づけること・サイトごとのロール**（§2。テナント的な分割に近づく。§18.3 の 6）
* **SNS 以外の API（サイト・キャンペーン・アナリティクス・Webhook など）をサイトで絞ること**。サイトのトークンはそもそも
  SNS の Scope しか持てない（裁定 6）ので届かない。共通のトークンでのキャンペーンの投稿の紐づけは §17 の R4
* **トークンの Scope を広げること・名前や有効期限を変えること**。変更の操作（§8.5.6）で変えられるのはサイトと、それに伴う Scope の**絞り込み**だけ
* **トークンが作ったアカウントをトークンと一緒に移すこと**（アカウントはサイトの持ち物。付け替えは画面で行う。§8.5.6）
* **Webhook をサイトで絞ること、Event の Payload に `siteId` を足すこと**（§11.3・§18.3 の 1）
* **Plugin API の変更**（`SocialAccountView` に `siteId` を足さない。§11.1）
* **`GET /social/accounts` の `siteId` での絞り込み（クエリ）**。サイトのトークンには区画が効くので要らず、画面は手元で絞る（§18.3 の 3）
* **配信ジョブ・手動投稿・承認の画面の振る舞いの変更**（区画 `all`。§5.4）
* サイトの一覧・編集画面に、紐づいたアカウント・トークンを並べること（§18.3 の 4）

### 4.3 全体の流れ

```text
運用者（画面のセッション。区画 all：すべて見える）
  1. Web サイト「A」を登録する                     /sites/new
  2. SNS アカウントを「A」に紐づける               /social「+ アカウントを追加」の「サイト」か、行の「サイト」
  3. 「A」に紐づけたトークンを発行する             /settings?tab=api「サイト：A」（Scope は SNS の 4 つだけ）

外部アプリ A（トークン A。区画 site:A）
  GET  /social/accounts      → A のアカウント ＋ 共通のアカウント
  POST /social/posts         → A のアカウント・共通のアカウントへは 201、B のアカウントへは 422 socialAccountId（「見つかりません」）
  GET  /social/posts         → A の区画の投稿だけ

外部アプリ（紐づけない既存のトークン。区画 common）
  GET  /social/accounts      → 共通のアカウントだけ（A・B のアカウントは見えない。裁定 5）
  POST /social/posts         → 共通のアカウントへは今までどおり 201。A のアカウントへは 422 socialAccountId（裁定 4）
```

## 5. 決めたこと：区画のモデル

### 5.1 用語

| 用語 | 意味 |
| --- | --- |
| **サイト専用のアカウント** | `site_id` が入っているアカウント（裁定 1 の「サイトに紐づいたアカウント」） |
| **共通のアカウント** | `site_id` が NULL のアカウント（裁定 1 の「何からでも使える」アカウント）。**既存のアカウントはすべてこれ** |
| **サイトのトークン** | `site_scoped = true` のトークン（裁定 2）。発行時にサイトを決め、**画面から別のサイト・共通へ変えられる**（裁定 7。§8.5.6） |
| **共通のトークン** | `site_scoped = false` のトークン。**既存のトークンはすべてこれ** |
| **区画**（`AccessScope`） | 要求が「どこまで見えて使えるか」。`all` / `common` / `site(サイト ID)` の 3 種（§5.2） |

### 5.2 区画と、見える・使える範囲（裁定 5）

```ts
// domain/social/access-scope.ts（新規。DB 製品にも Plugin API にも依存しない）
export type AccessScope =
  | { readonly kind: 'all' } // 画面のセッション・配信ジョブ・Plugin（区画で絞らない。§5.4）
  | { readonly kind: 'common' } // 共通のトークン
  | { readonly kind: 'site'; readonly siteId: string }; // サイトのトークン
```

**アカウント**（`accountSiteId` はアカウントの `site_id`）。

| アカウント | `all` | `common` | `site:A` |
| --- | --- | --- | --- |
| 共通（`site_id` NULL） | 見える・使える・変えられる | 見える・使える・変えられる | **見える・使える**（裁定 1）。**変更・削除は 403**（§5.5） |
| サイト A 専用 | 見える・使える・変えられる | **見えない（404）**（裁定 5）。投稿先にできない（裁定 4） | 見える・使える・変えられる |
| サイト B 専用 | 見える・使える・変えられる | 見えない（404） | **見えない（404）**（裁定 2・3） |

「使える」＝投稿の登録の `socialAccountId` にできる。「変えられる」＝`PATCH` / `DELETE /social/accounts/{id}`。

**投稿の区画**は次の順で決める（§7.3 の列を使う）。

1. アカウントがサイト専用なら、**そのサイト**（登録したのが誰でも。サイトのアカウントの投稿はサイトのもの）
2. アカウントが共通なら、**登録元の区画**：サイトのトークンが登録した投稿はそのサイト、それ以外（共通のトークン・画面・Plugin）は**共通**。
   登録したトークンのサイトを後から変えると、その投稿の登録元の区画も**トークンと一緒に移る**（要裁定 ⑥ の推奨。§8.5.6）
3. 2 のサイトが削除された投稿は**どの区画にも属さない**（どのトークンからも見えない。画面からは見える。§7.3）

| 投稿 | `all` | `common` | `site:A` |
| --- | --- | --- | --- |
| A 専用アカウントの投稿（登録者を問わない） | 見える・変えられる | 見えない | 見える・変えられる |
| 共通アカウントの投稿で、A のトークンが登録 | 見える・変えられる | **見えない** | 見える・変えられる |
| 共通アカウントの投稿で、共通のトークン・画面・Plugin が登録 | 見える・変えられる | 見える・変えられる（今までどおり） | **見えない**（裁定 3） |
| 共通アカウントの投稿で、削除されたサイトのトークンが登録 | 見える・変えられる | 見えない | 見えない |
| B 専用アカウントの投稿 | 見える・変えられる | 見えない | 見えない |

* 投稿は**見えれば変えられる**（`PATCH` / `DELETE` / 承認。Permission は今までどおり別に要る）。見えない投稿はすべて 404
* **区画は対称**：サイト A のトークンは B と共通の投稿を見られず、共通のトークンは A・B の投稿を見られない。
  共通のトークンどうしは今までどおり分かれない（共通の区画の中は名前空間のまま。§15 の仕様書 §2.3）

### 5.3 裁定 4（既存は今までどおり）との関係

* マイグレーションの直後、**アカウントはすべて共通、トークンはすべて共通、投稿はすべて共通の区画**になる。
  共通のトークンから見えるもの・できることは**何も変わらない**（共通の区画＝今までの全体）
* 変わるのは、運用者が**アカウントをサイトに紐づけた**ときと、**サイトのトークンを発行した**ときだけ。
  紐づけたアカウントは共通の区画を出て、そのサイトの区画に入る（裁定 4 の「そのサイトのトークンからの投稿しか受け付けない」）

### 5.4 人・Plugin・配信ジョブは絞らない（決めたこと）

| 呼び出し元 | 区画 | 理由 |
| --- | --- | --- |
| 画面のセッション（Server Component・画面からの `/api/v1`） | `all` | 運用者はすべてのサイトを管理する。サイトのアカウントの承認待ち（`048`）を画面で確かめて承認・差し戻し・編集するのも運用者である。人をサイトで絞ると「サイトの担当者」という概念が要り、§2 の境界に近づく |
| 配信ジョブ・中断の判定・手動投稿の区画 | `all`（`AuthorizationContext` を使わない内部処理） | サイト専用のアカウントの予約も今までどおり配信する |
| Plugin（Data API） | 渡された文脈のまま | 起動時は匿名（権限が無いので何も読めない）、画面では見ている人のセッション（`all`）。**区画の判定は UseCase にある**ので、将来トークンの文脈が Data API に渡っても自動で効く |

裁定 1 の「そのサイトからしか使えない」は、外部アプリ（API トークン）についての規則と読む。要望が「外部のアプリから API で送るときに
限定したい」である。画面の運用者は「サイトから」ではなく Torifune 全体の管理者として操作する。

### 5.5 サイトのトークンは共通のアカウントを変えられない（決めたこと）

* 共通のアカウントは**すべての区画が投稿先に使う**。サイト A のアプリが資格情報を差し替えれば、B や共通の区画の投稿が
  別の SNS アカウントから出る。削除すれば、他の区画の投稿まで `CASCADE` で消える
* 裁定 1 の「何からでも**使える**」は投稿先にできることで、管理できることではない
* 見えているもの（一覧に出る）なので 404 ではなく **403 `FORBIDDEN`**（§8.7）。共通のアカウントの管理は共通のトークンと画面が行う

### 5.6 サイトの付け替えは画面だけ（決めたこと）

* アカウントの `siteId` を**変えられるのはセッション（画面）だけ**。トークン（共通・サイトとも）は、作成時に自分の区画のとおりに決まるだけで、
  後から変えられない（422 `siteId`）
* **理由**：付け替えは区画を移す操作で、外部アプリに任せると、サイト A のアプリが共通のアカウントを A に取り込み（他の区画から使えなくする）、
  共通のトークンが A のアカウントを作る（作った直後に自分から見えなくなる）、といった不揃いが生まれる。
  紐づけは運用者が決める統制なので、人の操作と監査（§8.9）に寄せる

## 7. データモデル

### 7.1 マイグレーション `migrations/026_site_scoped_social.sql`

```sql
-- SNS アカウントと API トークンを Web サイトに紐づける（053-site-scoped-social 設計 §7）。
--
-- 1. social_accounts.site_id：アカウントが属するサイト。NULL は共通（どのサイトのトークンからも使える）。
--    **サイトの削除を断る（RESTRICT）。** CASCADE だと SNS アカウントと投稿が黙って消え、
--    SET NULL だとサイト専用のアカウントが黙って共通に化ける（範囲が広がる）。
-- 2. api_tokens.site_id / site_scoped：サイトのトークン。発行時に決まり、画面の変更の操作でだけ変わる（設計 §8.5.6）。
--    **サイトを消すと site_id は NULL になるが site_scoped は残る**ので、全体用（共通）のトークンには化けない
--    （アプリは site_scoped で site_id が NULL のトークンを使えないものとして扱う。設計 §8.5.3）。
--    失効しても行は消さない（011）ので、RESTRICT にすると失効済みのトークンが永久にサイトの削除を止める。
--    サイトのトークンの Scope は SNS の 4 つに限る（設計 §7.2・裁定 6）。
-- 3. social_posts.origin_site_id / origin_site_scoped：登録した区画（共通のアカウントの投稿の区画に使う。設計 §5.2）。
--    トークンの行に頼らないのは、トークンの所有者を消すとトークンの行が消え（011 の CASCADE）、
--    created_by_token_id が NULL になって投稿が共通の区画へ化けるため。
--
-- 既存行はすべて site_id = NULL・site_scoped = false・origin_site_id = NULL・origin_site_scoped = false になり、
-- 意味は変わらない（設計 §5.3）。新しい Permission は作らない。
--
-- **戻すとき**（手で戻す場合）:
--   ALTER TABLE social_posts DROP CONSTRAINT social_posts_origin_site_check,
--     DROP COLUMN origin_site_scoped, DROP COLUMN origin_site_id;
--   ALTER TABLE api_tokens DROP CONSTRAINT api_tokens_site_scopes_check, DROP CONSTRAINT api_tokens_site_scoped_check,
--     DROP COLUMN site_scoped, DROP COLUMN site_id;
--   ALTER TABLE social_accounts DROP COLUMN site_id;
--   （索引は列と一緒に落ちる。**サイトのトークンが残っていれば、先に失効させてから戻す**。戻すと全体用に化ける）
ALTER TABLE social_accounts
    ADD COLUMN site_id uuid REFERENCES sites (id) ON DELETE RESTRICT;

CREATE INDEX social_accounts_site_idx ON social_accounts (site_id) WHERE site_id IS NOT NULL;

ALTER TABLE api_tokens
    ADD COLUMN site_id     uuid    REFERENCES sites (id) ON DELETE SET NULL,
    ADD COLUMN site_scoped boolean NOT NULL DEFAULT false,
    -- サイトを持つトークンは必ずサイトのトークン。逆（site_scoped でサイトが NULL）はサイトが消えたあとの形。
    ADD CONSTRAINT api_tokens_site_scoped_check CHECK (site_id IS NULL OR site_scoped),
    -- サイトのトークンは SNS の権限しか持てない（設計 §7.2）。domain/api-token.ts の SITE_TOKEN_SCOPES と一致させる。
    ADD CONSTRAINT api_tokens_site_scopes_check CHECK (
        NOT site_scoped
        OR scopes <@ ARRAY['social.read', 'social.write', 'social.delete', 'social.approve']::text[]
    );

CREATE INDEX api_tokens_site_idx ON api_tokens (site_id) WHERE site_id IS NOT NULL;

ALTER TABLE social_posts
    ADD COLUMN origin_site_id     uuid    REFERENCES sites (id) ON DELETE SET NULL,
    ADD COLUMN origin_site_scoped boolean NOT NULL DEFAULT false,
    ADD CONSTRAINT social_posts_origin_site_check CHECK (origin_site_id IS NULL OR origin_site_scoped);

CREATE INDEX social_posts_origin_site_idx ON social_posts (origin_site_id) WHERE origin_site_id IS NOT NULL;
```

* 列の追加はどれも NULL 可か定数の既定値なので、表の書き直しは起きない（PostgreSQL 11 以降）。外部キーの検証は全行 NULL の列に対する走査で済む
* **外部キーの参照側の索引**（`019` と同じ理由）：サイトの削除のたびに 3 表を全走査しないよう、部分索引を張る（`site_id = $1` の検査に使える）。
  `social_accounts_site_idx` は区画の絞り込み（§7.4）にも効く
* `site_id` / `site_scoped` / `scopes` を書き換えるのは `apiTokenRepository.changeSite` だけ（失効したトークンには書かない）。受け入れ条件 #60 の静的検査で見る

### 7.2 サイトのトークンの Scope を SNS の 4 つに限る理由（裁定 6）

`SITE_TOKEN_SCOPES = ['social.read', 'social.write', 'social.delete', 'social.approve']`（`domain/api-token.ts`）。

| サイトのトークンに付けられたら | 何が漏れるか |
| --- | --- |
| `token.manage` | 所有者のトークンの一覧（`GET /api-tokens`）が読める。発行はセッションだけなので作れないが、名前・Scope・サイトが見える |
| `system.manage` | Webhook を登録して**全サイトの** SNS イベントを受け取れる。配信の手動実行も呼べる |
| `campaign.read` / `campaign.write` | キャンペーンの `socialPostIds` で他の区画の投稿の ID が読め、紐づけられる |
| `site.*` / `analytics.read` / `user.manage` / `plugin.manage` / Plugin の Permission | サイトで絞られない（本設計は SNS だけを絞る） |

**区画は SNS の UseCase にしか無い**ので、SNS 以外の Scope を許すと「サイトに限定したトークン」が SNS 以外では全体に届く。
発行時（422 `scopes`）、使用時（実効 Permission を `SITE_TOKEN_SCOPES` と交差。§8.5.3）、DB（`api_tokens_site_scopes_check`）の 3 か所で守る。
SNS 以外のサイト単位の API をサイトのトークンに開くのは §18.3 の 2。

### 7.3 投稿の `origin_site_id` / `origin_site_scoped`（決めたこと）

* **意味は「登録したトークンのいまの区画」**（トークンの行が消えた後は、消えた時点の値の写し）。トークン以外（画面・Plugin）が登録した投稿は `(NULL, false)`
* **書くのは 2 か所だけ**：
  * **登録**：トークンで登録するときは、`insertPostIdempotent` のトランザクションの中で
    `SELECT site_id, site_scoped FROM api_tokens WHERE id = :tokenId FOR SHARE` を読み、その値を書く（文脈の区画の写しは使わない）。
    トークン以外は `originOf(scope)`（`all` → `(NULL, false)`）
  * **トークンのサイトの変更**（§8.5.6）：`changeSite` が、トークンの行を書き換えたのと同じトランザクションで、そのトークンが登録した投稿
    （`created_by_token_id = :tokenId`。アカウントが共通かどうかを問わない）の `origin_*` を変更後の値に書き換える（要裁定 ⑥ の推奨）
  * 更新・承認・配信では変えない
* **共有ロックの理由**：変更はトークンの行を `UPDATE` してから投稿を書き換える。登録が行を `FOR SHARE` で読むので、変更のコミットを待ってから
  変更後の値を読む（READ COMMITTED の再読み）。逆順（登録が先）なら、変更の `UPDATE` が登録のコミットを待ち、登録した投稿も書き換えの対象に入る。
  どちらの順でも「トークンの区画」と投稿の `origin_*` が食い違わない（受け入れ条件 #89）
* 区画の判定（アカウントが見えるか）は要求の始めに作った文脈で行う。変更と同時に進む 1 要求は変更前の区画で判定される（§17 の R6 と同じ窓）
* 投稿の区画（§5.2）は、アカウントがサイト専用ならアカウントのサイト、共通なら `origin_*` で決まる。
  **アカウントのサイトを付け替えると、そのアカウントの投稿は付け替え先の区画へ移る**（導出なので書き換えは要らない。§8.2.4）
* `origin_site_scoped = true` かつ `origin_site_id IS NULL`（登録したサイトが消えた）の投稿は、どのトークンからも見えない（§5.2 の 3）。
  消えたサイトのアプリが共通のアカウントへ出した投稿の本文が、共通の区画のアプリへ出るのを防ぐ
* 応答には出さない（§8.8。外部アプリには自分に見えるかどうかがすべてで、区画の内部表現を公開契約にしない）

### 7.4 区画の SQL の述語（Infrastructure の 1 つの関数）

| 区画 | アカウント（`a`） | 投稿（`p` ＋ `JOIN social_accounts a`） |
| --- | --- | --- |
| `all` | 条件なし | 条件なし |
| `common` | `a.site_id IS NULL` | `a.site_id IS NULL AND p.origin_site_scoped = false` |
| `site:A` | `a.site_id IS NULL OR a.site_id = :A` | `a.site_id = :A OR (a.site_id IS NULL AND p.origin_site_id = :A)` |

* 投稿の一覧（`listPosts`）・ID 指定（`findPostById`）・まとめて引く（`findPostsByIds`）・承認待ち／手動投稿待ちの一覧は、`social_accounts` と
  内部結合して述語を掛ける（投稿は必ずアカウントを持つ。`ON DELETE CASCADE`）
* 区画 `all` のときは結合を省いてよい（画面・ジョブの性能を変えない）
* 述語は `scopePredicate(scope)` の 1 か所に置き、各メソッドはそれを呼ぶ（受け入れ条件 #61）

#### 8.2.3 作成 `POST /social/accounts`（要求に `siteId` を足す）

| 項目 | 型 | 必須 | 制約（違反は 422 `siteId`） |
| --- | --- | --- | --- |

`resolveAccountSiteOnCreate(scope, requested)`（`requested` は省略＝`undefined`）：

| 区画 | 省略 | `null` | 自分のサイト `A` | 別のサイト `B` | 存在しないサイト |
| --- | --- | --- | --- | --- | --- |
| `all`（画面） | 共通 | 共通 | A | B | **422**「Webサイトが見つかりません。」 |
| `common` | 共通 | 共通 | **422**「APIトークンではアカウントをサイトに紐づけられません。管理画面で紐づけてください。」 | 同左 | 同左 |

  サイトのトークンでもそのまま使え、作ったアカウントは他の区画から使えない
* `site:A` の 422 の文言は、指定したサイトが存在してもしなくても同じ（サイトの存在を教えない）
* 検査の順：Zod（形）→ 既存の `provider`・`displayName` → **`siteId`** → 資格情報。存在の確認は `siteRepository.findById`（`site.read` は要求しない。
  画面の運用者は `social.write` でアカウントを作る）。アーカイブしたサイトにも紐づけられる（画面の選択肢には出さない。§9.1）
* 挿入の時点でサイトが消えていた（外部キー違反）ら 422 `siteId`「Webサイトが見つかりません。」に写す

#### 8.2.4 更新 `PATCH /social/accounts/{id}`（要求に `siteId` を足す）

**まず区画で対象を決める**（`accountManageable`）：`not_found` → 404、`forbidden` → 403（§5.5）。次に `siteId` を送っていれば
`checkAccountSiteChange(scope, currentSiteId, requested)`：

| 区画 | 今と同じ値 | 違う値（サイト→別サイト・サイト→共通・共通→サイト） |
| --- | --- | --- |
| `all`（画面） | 200 | **200**（存在しないサイトは 422「Webサイトが見つかりません。」） |
| `common` / `site:A` | 200（何も変わらない） | **422**「APIトークンではアカウントのサイトを変えられません。管理画面で変えてください。」 |

* **付け替えると、そのアカウントの投稿は付け替え先の区画へ移る**（§7.3）。登録済みの予約・承認待ちはそのまま残り、配信ジョブは今までどおり配信する。
  付け替え前の区画のトークンからは 404 になる。画面は付け替えの Modal でこれを知らせる（§9.1.3）
* 付け替えを断る条件（他の区画の予約が残っている など）は設けない。統制は運用者の判断と監査（§8.9）に置く

#### 8.2.5 削除 `DELETE /social/accounts/{id}`

`accountManageable`：`not_found` → 404、`forbidden` → 403、`ok` → 今までどおり（投稿も `CASCADE` で消える）。

### 8.3 SNS 投稿

#### 8.3.1 登録 `POST /social/posts`

既存の検査の順（仕様書 §4.4 の表）の **3（アカウントの存在）を「存在して、区画から見える」** に変える。

| 順 | 検査 | 422 の `details` |
| ---: | --- | --- |
| 3 | `socialAccountId` のアカウントが存在し、**`accountVisible(scope, account.siteId)`** | `socialAccountId`「SNSアカウントが見つかりません。」（**存在しない場合と同じ文言**） |
| — | `externalRef` の再送（`findByExternalRef(tokenId, ref)`）。既存の投稿が**区画から見えれば** 200 で返す。**見えなければ 422** | `externalRef`「この externalRef は既に使われています。別の externalRef で登録してください。」 |

* 区画 `common` からサイト専用のアカウントへは 422 `socialAccountId`（**裁定 4**）。区画 `site:A` から B 専用へも 422（裁定 2）
* 再送で見えなくなるのは、1 回目の登録の後に運用者がアカウントを別の区画へ付け替えた場合だけ。冪等キーの一意索引
  `(created_by_token_id, external_ref)` は変えないので、同じキーで新しい投稿は作れない。黙って 2 つ目を作らず、既存を見せもしない
* 挿入では `origin_*` に、トークンの行を `FOR SHARE` で読んだ値（トークン以外は `originOf(scope)`）を書く（§7.3）
* 挿入の直前に `FOR SHARE` で読んだトークンの行が**失効している**か、**サイトのトークンでサイトが消えている**（`site_scoped` で `site_id` が NULL）なら、
  トークンが使えなくなったのと同じく **401** にする（Repository が `SiteGoneError` を投げ、ルートが `UNAUTHENTICATED` に写す）。
  要求の始めには使えたトークンが、サイトの削除と同時に進んだ場合の窓を閉じる。読んだ値で書くので `origin_site_id` の外部キー違反は起きない

#### 8.3.2 一覧 `GET /social/posts`・取得 `GET /social/posts/{id}`

* 一覧は §7.4 の述語で絞る。`accountId` の絞り込みは区画の中で掛かる（区画の外のアカウントの UUID は今までどおり **200 で空**。存在を教えない）
* 取得は区画の外なら **404**（本文は存在しない ID と同じ）

#### 8.3.3 更新・削除・承認

| 操作 | 区画の外 | 区画の中 |
| --- | --- | --- |
| `PATCH /social/posts/{id}` | **404**（行は変わらない） | 今までどおり（048 の遷移・承認の取り消し・409 を含む） |
| `DELETE /social/posts/{id}` | **404**（行は残る） | 今までどおり |
| `POST /social/posts/{id}/approve` | **404**（承認待ちのまま） | 今までどおり |

* 区画の判定は**読み出しの時点**（`findPostById(id, scope)`）。`PATCH` の条件付き更新（048 §6.3.6）は今までどおりで、区画の条件は足さない。
  読んだ後に運用者がアカウントを付け替えた場合の書き込みは、付け替えの前に始まった操作として通す（付け替えと同時に進む 1 要求の窓。§17 の R6）
* 承認待ちの投稿の承認の 409 / 422 の判定順（048 §6.4.4）は、区画の 404 の後に掛かる

### 8.5 API トークン

#### 8.5.1 発行 `POST /api-tokens`（`token.manage`・セッションだけ。現行どおり）

| 項目 | 型 | 必須 | 制約 |
| --- | --- | --- | --- |
| `siteId` | string（UUID）\| null | 任意 | 省略・`null` は共通のトークン（今までどおり）。UUID の形でなければ 422 `siteId` |

`siteId` を指定したときの検査（UseCase `createApiToken`。既存の `name` → `scopes`（形・所有者の Permission）→ `expiresAt` の後に足す）：

1. サイトが存在する → 無ければ 422 `siteId`「Webサイトが見つかりません。」
2. **サイトがアーカイブされていない** → されていれば 422 `siteId`「アーカイブしたサイトにはトークンを発行できません。」（裁定 8）
3. **`scopes` がすべて `SITE_TOKEN_SCOPES` に入る** → 外れたものがあれば 422 `scopes`「サイトに紐づけるトークンには SNS の権限（social.read・social.write・social.delete・social.approve）だけを指定できます: <最初の 1 つ>」（裁定 6）
4. 挿入：`site_id = siteId`、`site_scoped = true`。挿入の時点でサイトが消えていた（外部キー違反）ら 1 と同じ 422

#### 8.5.2 応答（`GET /api-tokens`・発行の応答。差分）

| 項目 | 型 | 説明 |
| --- | --- | --- |
| `siteId` | string（UUID）\| null | 紐づいたサイト |
| `siteScoped` | boolean | サイトのトークンか。**`true` で `siteId: null` はサイトが削除されたトークン**（使えない。画面は「削除されたサイト」と出す） |

#### 8.5.3 認証（`buildApiTokenContext`。差分）

既存の判定（存在・失効・期限・所有者の状態）の後に、**サイトのトークンなら**次を見る。どれかに当たれば**未認証**（理由は返さない。既存と同じ方針）。

1. `siteScoped && siteId === null`（サイトが削除された）
2. サイトが存在しない（1 と同じ。行の削除と外部キーの間の窓）
3. サイトの状態が **`archived`**（裁定 8。`paused` は影響しない）

使えるときは、実効 Permission を **`所有者の Permission ∩ Scope ∩ SITE_TOKEN_SCOPES`** にし（DB の CHECK と二重に守る）、
`apiToken: { id, name, siteId }` を積む。判定は Domain の純関数 `siteTokenUsable({ siteScoped, siteId, siteStatus })` と
`effectiveSiteTokenPermissions(owner, scopes)` に置く。

* アーカイブを戻せば（`archived` → `active` / `paused`）そのトークンは再び使える。失効させるなら画面で失効させる
* 1 要求の中で文脈は 1 回だけ作るので、要求の途中でアーカイブされても、その要求は最後まで通る

#### 8.5.4 失効

変えない（セッションだけ・自分のトークンだけ・`deleted` の監査）。サイトの削除による失効は §8.6。

#### 8.5.5 監査（新たに残す）

| 操作 | `action` | `resourceType` | `detail` |
| --- | --- | --- | --- |
| 発行 | `created`（**これまで残していなかった**） | `api_token` | `{ siteId, scopes, expiresAt（ISO か null） }`。平文・ハッシュ・`prefix` は残さない |

**理由**：サイトのトークンの発行は「どの外部アプリにどのサイトを任せたか」の統制の記録で、トークンの行の `site_id` はサイトを消すと NULL になる。
発行の監査に残しておけば、後から追える。

#### 8.5.6 トークンのサイトの変更 `PATCH /api-tokens/{id}`（新規。ユーザー裁定 7）

**操作の形。** 既存のトークンの API（`/api-tokens`・`/api-tokens/{id}` の `DELETE`）に `PATCH` を足す。発行・失効と同じく
**セッションだけ**（`sessionOnly`。トークンで叩くと 401）・**`token.manage`**・**自分のトークンだけ**（他人のトークン・存在しない・UUID の形でない ID は 404。
`revokeApiToken` と同じく存在を教えない）。operationId は `changeApiTokenSite`、UseCase は `apiToken.changeSite`。

| 項目 | 型 | 必須 | 制約（違反は 422。キーはその項目名） |
| --- | --- | --- | --- |
| `siteId` | string（UUID）\| null | **必須** | `null` は共通にする。UUID の形でなければ 422 `siteId` |
| `scopes` | string[] | 任意 | **いまの Scope の部分集合だけ**（狭めるだけ。広げられない）。省略すると今のまま |

**検査と結果**（Domain の純関数 `resolveTokenSiteChange({ current, requestedSiteId, requestedScopes, site })` が決める）：

| 順 | 条件 | 結果 |
| ---: | --- | --- |
| 1 | トークンが無い・他人のもの | 404 |
| 2 | **失効している** | 422 `siteId`「失効したトークンは変えられません。」（失効は取り消せない。サイトの削除で失効したトークンを含む） |
| 3 | `scopes` にいまの Scope に無いものがある | 422 `scopes`「権限を広げることはできません: <最初の 1 つ>」 |
| 4 | `siteId` が存在しないサイト | 422 `siteId`「Webサイトが見つかりません。」 |
| 5 | `siteId` が**アーカイブしたサイト** | 422 `siteId`「アーカイブしたサイトにはトークンを紐づけられません。」（発行と同じ。裁定 8） |
| 6 | `siteId` がサイトで、変更後の Scope（`scopes` を送ればそれ、送らなければ今の Scope）に `SITE_TOKEN_SCOPES` に無いものがある | 422 `scopes`「サイトに紐づけるトークンには SNS の権限だけを指定できます。外す権限を scopes で指定し直してください: <外れるもの全部>」（裁定 6） |
| 7 | それ以外 | 200。`site_id = siteId`、`site_scoped = (siteId !== null)`、`scopes` は変更後。応答はトークンの形（§8.5.2。平文は無い） |

* **変更の向きはすべて許す**：サイト A → サイト B、サイト → 共通、共通 → サイト、同じサイト（何も変わらないが 200）。
  サイト → 共通は範囲が広がる操作だが、裁定 7 の「変えられる」に含み、`token.manage` の運用者の判断と監査（§8.5.7）に置く
* **共通 → サイトで SNS 以外の Scope を持つとき（決めたこと）**：**黙って外さず、断る**（6）。同じ要求で `scopes` を SNS の範囲に**狭めて**送れば通る。
  画面は外れる権限を見せてから狭めた `scopes` を送る（§9.2.1）。理由：`021` §2.3 の「黙って削らない（指定したのに効かない、より指定できない）」に揃える。
  先に Scope だけを狭める別の操作を作らないのは、Scope の編集を一般の機能として足すことになるため（狭めるのはサイトの変更の要求の中だけで足りる）
* **サイトが消えたトークン（`site_scoped = true`・`site_id = NULL`）**：サイトの削除と同時に失効させる（§8.6）ので、2 で断られる。
  失効していない同じ形（DB を直接書き換えた場合だけ）は 4〜7 のとおりに扱う（どこかへ紐づけ直すか共通にする。使えない状態から戻す操作になる）
* **アーカイブしたサイトのトークン**（使えない。裁定 8）を別のサイト・共通へ変えるのは 7 のとおり 200（再び使えるようになる）

**変更の後に起きること**（1 つのトランザクション。`apiTokenRepository.changeSite`）：

1. トークンの行を書き換える（`WHERE id = :id AND user_id = :owner AND revoked_at IS NULL`。当たらなければ読み直して 404 / 422）
2. **そのトークンが登録した投稿の `origin_site_id` / `origin_site_scoped` を変更後の値に書き換える**（`created_by_token_id = :id` のすべて。要裁定 ⑥ の推奨。§7.3）
3. 次の要求から新しい区画で認証される（文脈は要求ごとに作る。§8.5.3）

| 対象 | 変更後 | 理由 |
| --- | --- | --- |
| そのトークンが**共通のアカウント**に登録した投稿 | **トークンと一緒に新しい区画へ移る**（要裁定 ⑥ の推奨） | トークン＝外部アプリ 1 つ（`035` §6.1.3）で、その投稿はアプリのもの。アプリは変更の後も自分の投稿の結果を `GET /social/posts/{id}` で読め、`externalRef` の再送が既存の投稿を 200 で返せる（冪等が途切れない） |
| そのトークンが**サイト専用のアカウント**に登録した投稿 | **アカウントのサイトに残る**（`origin_*` は書き換えるが、区画はアカウントのサイトで決まる。§5.2 の 1） | サイトのアカウントの投稿はサイトのもの。変更後の区画から旧サイトのアカウントが見えなければ、その投稿も見えない |
| そのトークンが**作ったアカウント**（作成時に旧サイトへ自動で紐づいたもの） | **旧サイトに残る**（アカウントは移さない） | アカウントはサイトの持ち物で、付け替えは画面の判断（§5.6）。アカウントに作成者のトークンの記録も無い。移したければ画面で付け替える |
| 冪等キー（`externalRef`） | **トークンごとの名前空間のまま**（変えない） | 下の表 |

**変更の後の再送**（冪等キーはトークンごと。一意索引は変えない）：

| 1 回目の登録 | 変更後に同じ `externalRef` で再送 | 結果 |
| --- | --- | --- |
| 共通のアカウントへ | 同じアカウントへ | 投稿はトークンと一緒に移っているので見える → **200 で既存**（重複しない） |
| 旧サイトのアカウントへ | 同じアカウントへ | 検査 3（アカウントが区画から見える）で **422 `socialAccountId`**。重複しない |
| 旧サイトのアカウントへ | 新しい区画から見えるアカウントへ | 既存の投稿（旧サイトのアカウント）が見えないので **422 `externalRef`**（§8.3.1）。重複しない |

* **裁定 5（共通のトークンからサイトの投稿は見えない）との関係**：変更は「そのトークンの区画」を移すだけで、区画の規則（§5.2）は変えない。
  サイト A → 共通にしたトークンは、A のアカウントとその投稿が見えなくなり、共通のアカウントへ自分が登録した投稿は共通の区画へ移る
  （他の共通のトークンからも見える）。共通 → サイト A では、そのトークンが共通のアカウントへ登録した投稿は A へ移り、他の共通のトークンから見えなくなる
* 変更と同時に進む要求は §7.3 のとおり食い違わない

| 操作 | `action` | `resourceType` | `detail` |
| --- | --- | --- | --- |
| サイトの変更 | `updated` | `api_token` | `{ siteId（変更後）, previousSiteId, scopes（変更後）, removedScopes, movedPosts（`origin_*` を書き換えた投稿の数） }`。平文・ハッシュは残さない |

### 8.6 サイトの削除 `DELETE /sites/{id}`（`site.delete`。差分）

UseCase `deleteSite` の手順（1 つのトランザクション）：

1. サイトが無ければ 404（今までどおり）
2. **紐づいたアカウントがあれば 409 `CONFLICT`**：`details.socialAccounts`「このサイトに紐づいた SNS アカウントが n 件あります。アカウントのサイトを変えるか削除してから、サイトを削除してください。」。何も変えない
3. 紐づいた**失効していない**トークンを失効させる（`revoked_at = now()`。既に失効しているものの時刻は変えない）
4. サイトを削除する。外部キー（`social_accounts.site_id` の RESTRICT）に当たったら（2 と 4 の間に紐づけられた）2 と同じ 409
5. `site.deleted` イベント（今までどおり）。監査 `deleted` の `detail` に `{ revokedApiTokens: n }`

* **アカウントは断り、トークンは失効させる理由**：アカウントには投稿と資格情報が載っており、消す（`CASCADE`）か共通に戻す（範囲が広がる）かは
  運用者が決めることである。トークンは失効させても失うデータが無く、消えたサイトのトークンには使い道が無い
* 失効は DB の `site_scoped` の印（§7.1）と二重の守り：失効の処理が漏れても、サイトの消えたサイトのトークンは使えない（§8.5.3 の 1）
* `SiteInUseError`（Domain）を `api/route.ts` が **`ConflictError` より前に**写す（文言を添える。`JobBusyError` と同じ扱い）
* Plugin の Data API の `sites.delete` も同じ UseCase を通るので、同じ条件で reject される

### 8.7 404 / 403 / 422 の選び方（決めたこと）

| 場面 | 応答 | 理由 |
| --- | --- | --- |
| 区画の外のアカウント・投稿を ID で指定（GET / PATCH / DELETE / approve） | **404** | 存在を教えない（他のサイトのアカウント・投稿の ID を総当たりで確かめられない）。本文は存在しない ID と同じ |
| 区画の外のアカウントを投稿先に指定 | **422 `socialAccountId`**「SNSアカウントが見つかりません。」 | 既存の「存在しないアカウントは 422（404 ではない）」に揃え、文言も同じにする |
| サイトのトークンが共通のアカウントを変更・削除 | **403 `FORBIDDEN`** | 一覧に見えている（隠しても意味が無い）。権限が足りないのと同じ形で返す（`ForbiddenError`。理由は応答に出さない） |
| トークンで `siteId` を付け替え・別の区画を指定 | **422 `siteId`** | 入力の誤り。文言で直し方（管理画面で）を示す |
| サイトの消えた・アーカイブされたサイトのトークン | **401** | 使えないトークンは未認証（既存の失効・期限切れと同じ） |

### 8.8 OpenAPI

* `accountResponseSchema` に `siteId`（`string`・`format: uuid`・`nullable`、`description`「属するサイト。null は共通（どのサイトのトークンからも使える）。」）
* `createAccountSchema` / `updateAccountSchema` に `siteId`（`z.guid().nullable().optional()`、`description`「サイトに紐づける。省略すると、画面では共通、サイトのトークンではそのサイト。APIトークンでは変えられない。」）
* `createApiTokenSchema` に `siteId`、`apiTokenResponseSchema` に `siteId` と `siteScoped`
* **`changeApiTokenSite`**（新）：`PATCH /api-tokens/{id}`、`x-required-permission: token.manage`、要求は `siteId`（必須・`nullable`・`format: uuid`）と
  `scopes`（任意・文字列の配列。`description`「いまの Scope の部分集合だけ。狭めるだけで広げられない。」）、応答はトークンの形（`token` を持たない）、
  `additionalResponses` に 404（「トークンが存在しない、または自分のトークンでない（UUID の形でない ID を含む）」）
* `deleteSite` の `additionalResponses` に **409**（`description`「このサイトに紐づいた SNS アカウントがある。`details.socialAccounts` に理由」）

  404 の `description` に「このトークンからは見えない（別のサイトの区画）ものを含む」を足す。**応答のキー（ステータス）は増やさない**（403 は既定で宣言済み）
* **投稿の応答（`postResponseSchema`）は変えない**（§7.3）

## 10. 権限（Permission）

### 10.1 対応表

| 操作 | Permission | 権限なし | 未認証 |
| --- | --- | --- | --- |
| アカウントの `siteId` を作成で決める・更新で変える | `social.write`（現行どおり）。付け替えはセッションだけ（§5.6） | 403 | 401 / 403 `CSRF_FAILED`（仕様書 §2.1） |
| トークンの発行で `siteId` を決める | `token.manage`（現行どおり。セッションだけ） | 403 | トークンで叩くと 401（現行の `sessionOnly`） |
| **トークンのサイトを変える**（`PATCH /api-tokens/{id}`） | `token.manage`（セッションだけ・自分のトークンだけ） | 403 | トークンで叩くと 401。`Authorization` もセッションも無い → 403 `CSRF_FAILED` |
| サイトの削除 | `site.delete`（現行どおり） | 403 | 401 / 403 `CSRF_FAILED` |
| 画面のサイトの一覧（選択肢・名前） | `site.read`（表示のため。無ければ「共通」だけ） | 選択肢を出さない | — |
| SNS の各操作 | 現行どおり ＋ 区画（§8.7。404 / 403 / 422） | 403 | 401 |

### 10.2 新しい Permission を作らない理由（決めたこと）

* トークンのサイトは**トークンの属性**で、トークンを作れる人（`token.manage`。高い権限）が決め・変えるのが自然（変更も自分のトークンだけ。他人のトークンの区画を動かせない）
* アカウントのサイトは**アカウントの属性**で、アカウントを作り・変えられる人（`social.write`）が決める。編集者は今も資格情報を差し替えられる
* `social.site.manage` のような権限を分けても、いまのロールは固定の 3 つで、管理者と編集者の両方に付けることになり、何も変わらない

### 10.3 ID の差し替え

* サイト A のトークンで B 専用のアカウント・B の区画の投稿の ID を指定すると 404、投稿先にすると 422（受け入れ条件 #28・#34・#36）
* 共通のトークンでサイト専用のアカウント・投稿の ID を指定すると 404（同 #29・#36）
* 一覧の `accountId` に区画の外の UUID を入れると 200 で空（同 #40）

## 11. Plugin API・イベント・Webhook への影響

### 11.1 Plugin API

**変えない。** `SocialAccountView` / `SocialPostView` に項目を足さない。`PLUGIN_API_VERSION` は `1` のまま。

* Plugin は信頼されたコードで、Data API は匿名か見ている人の文脈で動く（§3.4）。区画は UseCase にあるので Data API を変えずに済む
* `socialAccounts.list` は画面の文脈では全件を返す（今までどおり）。Plugin がサイトを知る必要が出たら、`siteId` を**足す**（追加は互換。§18.3 の 5）

### 11.2 イベント

**Payload を変えない。** `social.account.connected` / `social.post.*` に `siteId` を載せない。新しいイベントも足さない
（アカウントの付け替えはイベントにしない。アカウントの更新にもともとイベントが無い）。

### 11.3 Webhook

* Webhook は**トークンにもサイトにも紐づかず**、登録は `system.manage`（§3.1）。**サイトのトークンは `system.manage` を持てない**（§7.2）ので、
  サイトのトークンから他の区画のイベントを購読する経路は無い
* 運用者が登録した Webhook には**全サイトの**イベントが届く（今までどおり）。受け手がサイトで振り分けるには、Payload の `accountId` を
  そのサイトのトークンで `GET /social/accounts/{id}` する（見えればそのサイトか共通）。Webhook のサイトでの絞り込みは §18.3 の 1

## 12. 互換性（外部アプリへの影響）

API のバージョンは **`v1` のまま**。

| 変更 | 既存の外部アプリへの影響 |
| --- | --- |
| アカウントの応答に `siteId` | 追加だけ。既存のアカウントはすべて `null` |
| アカウントの作成・更新の `siteId` | 送らなければ今までどおり。共通のトークンが値を送ると 422（新しい項目なので、送っていた既存のアプリは無い） |
| 共通のトークンからサイト専用のアカウント・その投稿が見えない・使えない | **運用者がアカウントをサイトに紐づけたときだけ**起きる（裁定 4）。紐づけたアカウントへの登録は 422 `socialAccountId`、そのアカウントの投稿の取得・更新は 404。運用者は紐づける前に、そのアカウントを使っている外部アプリへサイトのトークンを渡す（手順書に書く） |
| 共通のアカウントで、サイトのトークンが登録した投稿が共通のトークンから見えない | サイトのトークンが発行されたときだけ。既存の投稿はすべて共通の区画のまま |
| トークンの応答に `siteId` / `siteScoped`、発行の `siteId` | 追加だけ（画面・運用者向けの API） |
| 新しい操作 `PATCH /api-tokens/{id}`（トークンのサイトの変更） | 追加だけ（セッションだけ）。**運用者がトークンのサイトを変えると、そのトークンを使う外部アプリから見える範囲が次の要求から変わる**（§8.5.6）。既存のトークンを差し替えずにサイトのトークンへ移せる |
| サイトの削除の 409 | 紐づいたアカウントがあるときだけ（新しい状態でだけ起きる） |
| トークンの発行が監査ログに残る | 監査ログの行が増える（`GET` の公開 API は無い） |
| 仕様書 §2.3 の「分離境界ではない」 | **共通のトークンどうしは今までどおり分離境界ではない。** サイトのトークンは自分の区画に閉じる（§15） |
| Plugin API・イベント・Webhook | 変わらない |

### 15.2 `docs/マニュアル/SNS投稿の外部連携.md`（手順書）

* §1：発行フォームの「サイト」。**外部アプリには、そのアプリが受け持つサイトに紐づけたトークンを渡す**（推奨）。Scope は SNS の 4 つだけ。

* §2：アカウントのサイト（画面の「サイト」列と操作、サイトのトークンで作ると自動でそのサイトに紐づく）。**紐づける前に、そのアカウントを使っている外部アプリへサイトのトークンを渡す**（共通のトークンからは使えなくなる）

| R9 | 画面のサイトの選択肢は 100 件まで（`listSites` の `perPage` の上限） | サイトが 100 を超える運用は想定しない。超えたら選択肢を検索式にする（§18.3 の 8） |
| R10 | サイトの削除と紐づけが同時に起きる | 外部キーが守り、どちらかが 409 / 422 になる（§8.2.3・§8.6）。500 にしない |

**裁定 ③ を受けて設計で決めたこと**（§8.5.6）：

* 操作は `PATCH /api-tokens/{id}`（セッションだけ・`token.manage`・自分のトークンだけ）。**失効したトークンは変えられない**（サイトの削除で失効したものを含む。`site_scoped = true`・`site_id = NULL` は失効と組でしか生じない）
* 変更の向きはすべて許す（サイト ↔ サイト・サイト ↔ 共通）。アーカイブしたサイトへは 422（発行と同じ）。アーカイブで使えなくなったトークンを別のサイトへ移すのは可
* 共通 → サイトで SNS 以外の Scope を持つときは**断り**、同じ要求で `scopes` を**狭めて**送れば通す（黙って外さない。`021` §2.3）。Scope を広げる操作は作らない
* トークンが作ったアカウントは**旧サイトに残す**（アカウントはサイトの持ち物。付け替えは画面）
* 冪等キーはトークンの名前空間のまま。投稿の登録元の区画は登録時にトークンの行を共有ロックで読み、変更と食い違わない

### 18.2 要裁定（新規。本設計は推奨案で書いた）

#### ⑥ トークンのサイトを変えたとき、そのトークンが登録した投稿はトークンと一緒に移るか

対象は**共通のアカウント**への投稿（サイト専用のアカウントへの投稿は、どちらの案でもアカウントのサイトに残る。§5.2 の 1）。

| 案 | 内容 | 帰結 |
| --- | --- | --- |
| **(B) 一緒に移る（推奨）** | 変更と同じトランザクションで、そのトークンが登録した投稿の `origin_*` を変更後の値に書き換える | 外部アプリは変更の後も自分の投稿を `GET /social/posts/{id}` で読め、`externalRef` の再送が 200 で既存を返す（**冪等と結果の確認が途切れない**）。既存の共通のトークンをサイトのトークンへ移す（裁定 7 の主な使い道）がそのまま成り立つ。代わりに、トークンを**別のアプリ**へ使い回すと、前のアプリの投稿が新しい区画に見える（§17 の R8） |
| (A) 登録時の区画に残る | `origin_*` は登録時の値のまま。変更は以後の登録にだけ効く | 区画の中身が後から増減しない（サイト A の区画にあった投稿は A に残り続ける）。代わりに、変更の後はそのトークンから自分の投稿が見えなくなり（404）、同じ `externalRef` の再送は 422 `externalRef` になる。共通のトークンをサイトのトークンへ移すと、移す前に登録した投稿の結果を外部アプリが読めなくなる |

**推奨 (B) の理由**：トークンは「外部アプリ 1 つ」（`035` §6.1.3）で、そのアプリが登録した投稿はアプリのもの。区画を変えるのは「このアプリの担当を変える」操作で、
アプリの履歴ごと移るのが自然であり、冪等の約束（仕様書 §3.5）を守れる。別のアプリには新しいトークンを発行する（手順書に書く）。
(A) を選ぶと、§5.2 の 2・§7.3 の「書くのは 2 か所」の 2 つ目・§8.5.6 の「変更の後に起きること」の 2 と表・§8.5.7 の `movedPosts`・§9.2.1 の注意の文言、
受け入れ条件 #86〜#90 を直す（#86・#88 は「移らない」に、#87 の 1 つ目は 422 `externalRef` に、#89 は登録時のトークンの値を書くことに）。

### 18.3 設計で決めず、後の判断に回すもの

1. **Webhook のサイトでの絞り込み・Event の Payload の `siteId`**：受け手がサイトで振り分けるのに `GET` が要る（§11.3）。足すなら `webhooks.site_id`（任意）と Payload の追加（互換）

3. **`GET /social/accounts?siteId=` の絞り込み**：画面は手元で絞り、サイトのトークンには区画が効くので、いまは要らない
4. **サイトの画面に、紐づいたアカウント・トークンを並べること**

6. **人（ユーザー）をサイトに紐づけること・サイトごとのロール**：§2 のとおり、本設計の範囲外（テナント的な分割に近づくので、要るなら境界の判断から始める）
7. **キャンペーンの投稿の紐づけ（`socialPostIds`）を区画で検査すること**（§17 の R4）
8. **サイトの選択肢が 100 件を超える場合の検索式の選択**（§17 の R9）
