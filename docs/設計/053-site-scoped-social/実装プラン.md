### 確定事項（設計書から。プランで蒸し返さない）

* **区画 `AccessScope`** は `all`（画面のセッション・内部処理・Plugin の文脈）／`common`（サイトに紐づかないトークン）／`site(siteId)`（サイトのトークン）の 3 種。区画を決めるのは **`application/social/access-scope.ts` の `scopeOf(context)` だけ**で、`context.apiToken.siteId`（トークン行から積んだ値）からだけ決める（設計 §5.2・§8.1）
* 見える・使える・変えられるの表は設計 §5.2（アカウント 3 行 × 区画 3、投稿 5 行 × 区画 3）。**共通のトークンからサイト専用のアカウントとサイトの区画の投稿は見えない**（裁定 5）。**サイトのトークンは共通のアカウントを変更・削除できない（403）**（設計 §5.5）
* 区画の外の ID 指定は **404**、区画の外のアカウントを投稿先にすると **422 `socialAccountId`**（存在しない場合と同じ文言）、トークンからの `siteId` の付け替えは **422 `siteId`**、サイトの消えた・アーカイブされたサイトのトークンは **401**（設計 §8.7）
* マイグレーション **`026_site_scoped_social.sql`** は設計 §7.1 の SQL のとおり。`social_accounts.site_id`（`RESTRICT`）、`api_tokens.site_id`（`SET NULL`）/ `site_scoped`、`social_posts.origin_site_id`（`SET NULL`）/ `origin_site_scoped`、CHECK 3 つ、部分索引 3 つ。新しい Permission は作らない
* **`SITE_TOKEN_SCOPES = ['social.read', 'social.write', 'social.delete', 'social.approve']`**。発行時 422・使用時の交差・DB の CHECK の 3 か所で守る（裁定 6。設計 §7.2）
* **アーカイブしたサイトのトークンは 401**、`paused` は影響しない。戻せば再び使える（裁定 8。設計 §8.5.3）
* 投稿の登録元の区画（`origin_*`）は、トークンで登録するとき**トークンの行を `FOR SHARE` で読んだ値**を書く。トークン以外は `originOf(scope)`（設計 §7.3）
* **トークンのサイトの変更** `PATCH /api-tokens/{id}`（operationId `changeApiTokenSite`、UseCase `apiToken.changeSite`、`sessionOnly`・`token.manage`・自分のトークンだけ）。判定は Domain の純関数 `resolveTokenSiteChange`（設計 §8.5.6 の 2〜7）。**`apiTokenRepository.changeSite` がトークンの行と、そのトークンが登録した投稿の `origin_*` を 1 つのトランザクションで書き換える**（裁定 7・10）
* サイトの削除：紐づいたアカウントがあれば **409 `CONFLICT`・`details.socialAccounts`**、紐づいた失効していないトークンは**失効**、監査 `deleted` の `detail` に `{ revokedApiTokens }`（設計 §8.6）
* 監査：トークンの発行 `created`（新たに残す）、トークンのサイトの変更 `updated`、アカウントの作成・更新の `siteId`、サイトの削除の `revokedApiTokens`（設計 §8.9）
* **Plugin API・イベントの Payload・Webhook は変えない。`PLUGIN_API_VERSION` は 1 のまま。HTTP は `v1` のまま**（設計 §11・§12）
* 画面：`/social` のサイトの列・追加時のサイト・「サイト」の Modal・アカウント一覧だけの絞り込み（裁定 9）、設定 → API の発行のサイト・一覧のサイトの列・「サイトを変える」の Modal、サイトの削除の 409 の文言、サイトの編集フォームのアーカイブの説明（設計 §9）
* 文書の書き戻しは設計 §15 の範囲。**`docs/仕様書/` は変えない**
* 検証は **`spec-verifier` / `boundary-guardian` / `security-reviewer` の 3 つ**（公開 HTTP API・認可の範囲・トークン・マイグレーションを変えるため）
* **SaaS 固有機能（テナント・課金・コンテナ管理）に触るタスクは本プランに無い。** 人（ユーザー）をサイトに紐づけるタスクも無い（設計 §2・§18.3 の 6）

## 3. タスク分解

原則：**1 タスク = 1 コミット**。各タスクは「テストを書いて失敗を確認 → 実装 → 通す」の順。
各まとまり（G1〜G10）の最後で `pnpm test` / `pnpm typecheck` / `pnpm lint` / `pnpm format:check` が通る。E2E は T30 でだけ全件流す（§4 の注）。

**test-writer → implementer への受け渡しの単位は G（まとまり）。** test-writer は G の中の全タスクのテスト（と既存テストの追従）を先に書いて失敗を確かめ、`test:` でコミットする。implementer は G の中のタスクを順に通し、タスクごとに `feat:`（文書は `docs:`）でコミットする。
**implementer はテストを書き換えない。** テストが設計と食い違うと判断したら、設計書のどこと食い違うかを報告して止まる。

**着手順の骨子**：DB → Domain の純関数 → トークン（発行・認証）→ アカウントの区画 → 投稿の区画 → サイトの削除 → トークンのサイトの変更 →（051 の取り込みの確認）→ UI の部品 → 画面の組み立てと E2E → 文書 → 最終確認と 3 つの検証。
**G は前の G に依存する**（G2 は G1、G3 は G2、G4 は G3、G5 は G4、G6 は G5、G7 は G6、G8 は G7 の API の形、G9 は G8）。G10 は G7 の後ならいつでもよいが、振る舞いが入ってから書く。

### 破壊的変更の有無

**破壊的変更は無い。**

* 公開 Plugin API の型・関数・Payload を 1 つも変えない。`PLUGIN_API_VERSION` も動かない
* 公開 HTTP API は `v1` のまま。追加の項目・操作・応答だけで、紐づけをしない限り既存の外部アプリの振る舞いは変わらない（裁定 4）
* マイグレーションは既存の行の意味を変えない

**SaaS 固有機能への踏み込み：無し。** 区画は 1 つの DB・1 つの運用者の中で外部アプリのトークンの範囲を狭める最小権限の道具で、テナントのデータ分割ではない（設計 §2）。人（ユーザー）をサイトに紐づけるタスクは無い。

## 7. リスクと注意点

1. **区画の判定を経路に依存させない（T12・T15）。** API で届かない UseCase（`listSocialPostHistory`・`readSocialCredential` など）にも `scopeOf` を掛ける（設計 §8.3.4。#61 が守る）。ルートで絞らない（`CLAUDE.md`「認可を書く場所」）
2. **区画 `all` で結合しない（T14）。** 画面・ジョブの一覧の問い合わせを変えない（設計 §7.4・R7）。結合を足すのは `common` / `site` のときだけ
3. **`origin_*` はトークンの行から読む（T14）。** 文脈の区画の写しで書くと、トークンのサイトの変更と同時に進んだ登録が食い違う（#89）。`FOR SHARE` は `insertPostIdempotent` のトランザクションの中で取る
4. **`SiteGoneError` と 401（T14・T15）。** 要求の始めに使えたトークンがサイトの削除と同時に進む窓を閉じる。`ConflictError` などと取り違えて 409 / 500 にしない
5. **`SiteInUseError` を `ConflictError` より前に写す（T18）。** 既定文言「すでに使用されています。」では直し方が伝わらない（`JobBusyError` と同じ扱い）
6. **`touch` の位置（T9）。** サイトの検査を `touch` の前に置き、使えないトークンの `last_used_at` を進めない（§8 の 9）
7. **Repository のメソッドの書き方（T11・T14）。** `approval-static-checks.test.ts` #64 は `^  async <name>\(` でメソッドの本文を切り出す。`listManualPending` などに `scope` を足すときも、オブジェクトリテラルのメソッドの形を保つ。`scopePredicate` はモジュールの関数に置く
8. **任意の引数と `exactOptionalPropertyTypes`（T11・T12・T14）。** ルートは `siteId` が `undefined` ならキーごと渡さない。`null`（共通にする）と省略（変えない）を取り違えない
9. **`readSocialCredential` の 403（T12）。** 区画 `site` から共通のアカウントの資格情報を読む経路は今は無いが、将来トークンの文脈が届いたときに 403 になる形にしておく（設計 §8.3.4）
10. **監査の値の運び方（T8・T18・T21）。** `detail` は `(input, output)` だけを受ける。発行の `detail` に `output.plaintext` を入れない（`sanitizeAuditDetail` は `token` を含むキーを落とすが、キー名に頼らない）
11. **E2E の後片付けと順序（T27）。** `site-scoped-social.spec.ts` は `sites.spec.ts`・`social*.spec.ts` より前に走る。サイト・アカウント・投稿を残すと後の spec の前提を壊す。トークンは消せないので失効させる（失効したトークンが残っても後の spec には出ない）
12. **`GET /api/v1/auth/csrf` の Rate Limit（1 分 300 回）（T27）。** API での準備を最小にし、トークンとサイトは spec の中で使い回す
13. **051 との衝突（G8）。** 取り込みはユーザーの確認を取ってから。`social-accounts.tsx` の `columns`・import と `labels.ts` の末尾以外に衝突が出たら、解かずに報告する
14. **文書の静的検査の文字列を消さない（T29）。** `static-checks.test.ts` #81 の見出しと文、`text-input-docs-static-checks.test.ts` の §1.3 / §1.4 の語（§8 の 16）
15. **公開リポジトリ（全コミット）。** コメント・コミットメッセージ・文書に外部の製品名・運営側の事情・作業機の事情を書かない
16. **`verify-container-rebuild.sh` は Docker が要る（T30）。** 無い環境では飛ばし、検証レポートへ申し送る。E2E・`pnpm test` と同時に流さない
