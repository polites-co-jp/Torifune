## 1. 目的

### 1.1 直すもの

キャンペーンの 2 つの入力が、検査を通らずに PostgreSQL まで届いて例外になり、**500 `INTERNAL_ERROR`** を返している。

| # | 入力 | いまの振る舞い | 困ること |
| --- | --- | --- | --- |
| ① | `GET /campaigns?activeOn=` に暦に無い日付（`2026-02-30`・`2026-13-01`・うるう年でない年の `02-29` など） | 形（`YYYY-MM-DD`）だけを見て通し、`::date` で Postgres が断る → **500** | 打ち間違いが 500 に見え、利用者にも外部アプリにも原因が分からない |
| ② | `POST /campaigns`・`PATCH /campaigns/{id}` の `siteIds` / `socialPostIds` に、存在しない ID・UUID の形でない値・同じ ID の大文字と小文字 | そのまま `campaign_sites` / `campaign_social_posts` へ書き、外部キー・`uuid` 型・主キーの例外 → **500**。Data API の `campaigns.create` / `update` は Postgres の例外がそのまま Plugin へ上がる | 画面を開いたあとに対象のサイト・投稿が消されると、**保存が 500 で失敗する**（編集画面は開いた時点のサイト・投稿を送る）。どの項目が悪いかが返らない |

### 1.2 調査の結果（2026-09-24。実際に投げて確かめた）

`useScratchDatabase` の使い捨ての DB に、`app/api/v1/**/route.ts` の Route Handler・UseCase・`createPluginDataApi` を直接呼んだ（CI と同じ `DATABASE_URL` の形・テスト用の `TORIFUNE_ENCRYPTION_KEY`。調査用のテストはリポジトリに残していない）。
原因は `api/route.ts` の `unhandled error in route` のログの `reason` と、例外の `code`（SQLSTATE）で確かめた。

**500 になったもの（本設計で直す）**

| 入力 | 結果 | 原因 |
| --- | --- | --- |
| `GET /campaigns?activeOn=2026-02-30`・`2026-13-01`・`2026-00-10`・`2026-01-00`・`2026-02-29`・`0000-01-01` | **500** | `date/time field value out of range`（`22008`）。`campaign-repository.ts` の `listConditions` の `::date` |
| `POST /campaigns` の `siteIds` に UUID の形で存在しない ID（新しい UUID・`00000000-…`・**実在する SNS 投稿の ID**・1 万件の無作為な UUID） | **500** | `campaign_sites_site_id_fkey` の外部キー違反（`23503`） |
| 同じく `socialPostIds` に存在しない ID（実在するサイトの ID を含む） | **500** | `campaign_social_posts_social_post_id_fkey`（`23503`） |
| `siteIds` / `socialPostIds` に `'abc'`・`''`・10 万文字の文字列 | **500** | `invalid input syntax for type uuid`（`22P02`） |
| `siteIds` に `'\u0000'` | **500** | `invalid byte sequence for encoding "UTF8": 0x00`（`22021`） |
| `siteIds` に実在する ID と、**その大文字**（またはハイフンを除いた形） | **500** | 主キー `campaign_sites_pkey` の重複（`23505`）。重複の除去（`new Set`）は文字列で比べ、Postgres は同じ UUID と読む |
| `socialPostIds` に実在する ID とその大文字 | **500** | `campaign_social_posts_pkey`（`23505`） |
| `PATCH /campaigns/{id}` に上の `siteIds` / `socialPostIds`（存在しない ID・`'abc'`・大文字との重複） | **500** | 同上 |
| Data API `campaigns.create` / `update` に上と同じ `siteIds` / `socialPostIds`、`siteIds: [123]`、`siteIds: 'abc'`（配列でない） | Postgres の `DatabaseError` がそのまま reject される | 同上（`'abc'` は 1 文字ずつに分かれて `22P02`） |
| UseCase `listCampaigns` に `activeOn: '2026-02-30'` | `DatabaseError`（`22008`） | 同上。画面・Data API は `activeOn: null` しか渡さないので、届く経路は HTTP だけ |

**500 にならなかったもの（証拠として。本設計の前後で変わらないものを含む）**

| 入力 | 結果 |
| --- | --- |
| `activeOn=2024-02-29`（うるう年）・`9999-12-31` | 200 |
| `activeOn=abc`・`2026-1-1`・`99999-01-01`・非常に長い文字列 | 422 `activeOn`（形の検査） |
| `siteIds` に実在する ID（1 件・同じ値の重複・1000 件の同じ値・10 万件の同じ値） | 201（重複は除かれる） |
| `siteIds` に実在する ID の大文字だけ・ハイフンなし・`{…}` で囲んだ形 | **201**（Postgres が UUID として読む。**応答の `siteIds` は送った形のまま**で、後の `GET` は小文字。§6.3 で扱う） |
| `siteIds: [123]`・`null`・`'abc'`（HTTP） | 422（Zod） |
| `startsOn` / `endsOn` に暦に無い日付（`2026-02-30` など） | 422（UseCase の `isValidPeriod`。キーは **`endsOn`**。§11 の 3） |
| `PATCH /campaigns/{UUID の形で存在しない ID}` に `siteIds: ['abc']` / 存在しない ID | 404（行の更新が先に空振りし、紐づけに届かない） |
| 失敗した `POST` の後のキャンペーンの件数・失敗した `PATCH` の後のキャンペーン | 増えていない・変わっていない（トランザクションで戻る） |
| 本文が配列・壊れた JSON・`null` | 422 |
| `status` が列挙外 | 422 |

**所有者の概念**：サイト・SNS 投稿・キャンペーンは利用者ごとの所有を持たない（Permission だけで守る。`01` の単一インスタンスの前提）。
「他の利用者のサイトを紐づける」という到達の問題は無い。

### 1.3 広く投げて見つかった、別の型の 500（本設計では扱わない。§11 の 1）

`/api/v1` の書き込みとクエリの全体に、日付・列挙・本文の ID・数・文字列の境界値を投げた。次は **500 になる**が、原因がキャンペーンの紐づけ・`activeOn` とは別の型で、直す場所も別になる。

| # | 入力 | 結果 | 原因 |
| --- | --- | --- | --- |
| B1 | 文字列の入力に **NUL 文字（U+0000）**：`GET /sites`・`/campaigns`・`/users` の `?q=%00`、`POST /sites` の `name` / `url`、`PATCH /sites/{id}` の `description`、`POST` / `PATCH /campaigns` の `name` / `description`、`POST /social/accounts` の `displayName`、`POST` / `PATCH /social/posts` の `body`、`POST /webhooks` の `name`、`GET /analytics`・`/analytics/breakdown` の `source` / `key`、`PUT /settings` の `serviceName`（`jsonb` で `unsupported Unicode escape sequence`）、**認証の要らない** `POST /auth/login` の `loginId`・`POST /auth/password-reset/request` の `email`・`POST /collect` の `key` | **500** | `invalid byte sequence for encoding "UTF8": 0x00`（`22021`）。Postgres の `text` は NUL を持てない。Data API・UseCase を直接呼ぶ経路（`campaigns.create` の `name`、`createApiToken` の `name` など）も同じ |
| B2 | `GET /analytics?from=0000-01-01&to=0000-01-02` | **500** | `isCalendarDate` は西暦 0 年を通すが、Postgres の `date` は 0 年を持たない（`22008`） |
| B3 | `POST` / `PATCH /social/posts` の `scheduledAt` に `-8.64e15`・`'-010000-01-01T00:00:00Z'`（紀元前 4714 年より前） | **500** | `timestamp out of range`。`z.coerce.date()` は JavaScript の範囲を通す |
| B4 | `POST /analytics/rollup` の `pruneOlderThanDays` に `3000000` 以上 | **500** | `timestamp out of range`・`interval field value out of range`。下限 1 だけで上限が無い |

500 にならなかったもの（抜粋）：`/users` の `roles` に無いロール（422）・`loginId` の NUL（422。形の検査）、`/webhooks` の `events` に無いイベント（422）、`/settings/timezone` の不正なタイムゾーン（422）、
`/settings/access-log-ips` の不正な行・NUL（422）、`/social/posts` の `socialAccountId` に存在しない ID・`'abc'`（422）、`/analytics` の暦に無い `from`（422）、`page=1e400`・`page=99999999999999999999`（422）、
`/plugins` の `pluginId` に NUL・`../x`（404）、`/collect` の `path` / `referrer` の NUL（204）、`/auth/login` の 10 万文字の `loginId`（401）。

## 3. スコープ

### やること

1. `GET /campaigns?activeOn=` の暦に無い日付を **422 `activeOn`** にする（§6.2）
2. キャンペーンの作成・更新の `siteIds` / `socialPostIds` を DB へ書く前に検査し、形の誤り・件数超過・存在しない ID を **422 `siteIds` / `socialPostIds`** にする。大文字と小文字の違いは同じ ID として扱う（§6.3）
3. 検査から書き込みまでの間に対象が消される競合を、行の共有ロックで閉じる（§6.4）
4. Data API の `campaigns.create` / `update` を同じ規則にし、Postgres の例外ではなく `ValidationError` で reject する（§9.2）
5. キャンペーンの作成・編集画面で、`siteIds` / `socialPostIds` の誤りをそれぞれの欄の下に出す（§7）
6. 文書の書き戻し（§12）

### やらないこと（理由つき）

| 対象 | 理由 |
| --- | --- |
| §1.3 の B1〜B4（NUL 文字・西暦 0 年の `/analytics`・範囲外の `scheduledAt`・`pruneOlderThanDays` の上限） | 裁定の対象（`043` §11 の 3）の外で、型も直す場所も違う（B1 は全エンドポイントと Data API にまたがる共通の規則を要する）。**扱いを裁定に仰ぐ**（§11 の 1） |
| キャンペーンの `name` / `description` の NUL 文字 | B1 の一部。B1 と一緒に判断する |
| `startsOn` の暦の誤りが `details.endsOn` で返ること | 500 ではない（422 は返る）。キーの誤りは別の論点（§11 の 3） |
| 外部キー違反（`23503`）を 422 へ写す仕組み | §6.4 のロックで競合が閉じるので要らない。残った外部キー違反は不具合として 500 のままにする（隠さない） |
| `campaign.write` だけを持つ利用者が、`site.read` / `social.read` 無しでサイト・投稿を紐づけられること | 既存の権限の設計（`017`・`026`）。本設計は Permission を変えない（§8） |
| `GET /analytics?siteId=abc`（200 で空） | `043` §11 の 6 で記録済み |

## 6. API

### 6.1 変更の一覧

| エンドポイント | 変わる点 |
| --- | --- |
| `GET /campaigns` | `activeOn` が暦に無い日付なら 500 → **422 `activeOn`** |
| `POST /campaigns`・`PATCH /campaigns/{id}` | `siteIds` / `socialPostIds` の形の誤り・存在しない ID・大文字との重複が 500 → **422 `siteIds` / `socialPostIds`**（大文字との重複は 201 / 200）。1001 件以上は 422 |
| OpenAPI | `createCampaign` / `updateCampaign` の `siteIds` / `socialPostIds` に `maxItems: 1000` と `description`。`listCampaigns` の `activeOn` に `description`。**追加の応答（`additionalResponses`）は足さない**（422 は生成器が出す。`043` §6.4 の網羅の表は変わらない） |

### 6.2 `GET /campaigns` の `activeOn`（①）

規則：**`YYYY-MM-DD` の形で、かつ暦にある日付**（`isValidDateOnly`。キャンペーンの `startsOn` / `endsOn` と同じ判定）。

| 送った値 | 変更前 | 変更後 |
| --- | --- | --- |
| 省略 | 絞り込みなし | 同じ |
| `2024-02-29`・`2026-04-15`・`9999-12-31` | 200 | 同じ |
| `abc`・`2026-1-1`・`99999-01-01` | 422 `activeOn`（`YYYY-MM-DD の形式で入力してください。`） | 同じ |
| `2026-02-30`・`2026-13-01`・`2026-00-10`・`2026-01-00`・`2026-02-29`・`0000-01-01` | **500** | **422 `activeOn`**（`存在しない日付です。`） |
| `0001-01-01`〜`0099-12-31`（西暦 1〜99 年） | 200 | **422 `activeOn`**（`isValidDateOnly` が `Date.UTC` の 2 桁の年の扱いで偽を返す。`startsOn` と同じ扱いにそろう。実用上の影響は無い） |

形の検査（Zod の正規表現）は変えず、暦の検査は `listCampaigns`（UseCase）が行う。`ValidationError` は `api/route.ts` が 422 に写す（既存）。
**認可は検査より先**（`api/route.ts` の順序どおり。`defineUseCase` も Permission を先に見る）。

### 6.3 `siteIds` / `socialPostIds`（②）

**規則**（`POST` と、`PATCH` で指定したとき。`socialPostIds` も同じ）：

1. **配列であること。** 要素は **UUID の形**（`isUuidShape`：8-4-4-4-12 の 16 進、大文字・小文字を問わない、版と variant を見ない）。
   空文字・数値・ハイフンなし・`{…}` で囲んだ形・NUL を含む値は形の誤り
2. **件数は 1000 件まで**（重複を除く前の要素数で数える）。**件数を形より先に見る**（1001 件以上なら要素の形を見ずに件数の誤りにする）
3. 形が正しければ**小文字にそろえ、重複を除き、昇順に並べる**。応答の `siteIds` / `socialPostIds` はこの値（後の `GET` と同じ）
4. そろえた ID が**すべて存在すること**（`siteIds` は `sites`、`socialPostIds` は `social_posts` に）。存在しない ID が 1 つでもあれば全体を断る（何も書かない）
5. 空の配列は「紐づけない」（既存どおり）。`PATCH` で省略すれば変えない（既存どおり）

| 送った値（`siteIds`） | 変更前 | 変更後 |
| --- | --- | --- |
| `[]`・省略 | 201 | 同じ |
| 実在する ID（重複を含む） | 201 | 同じ |
| 実在する ID の大文字だけ | 201。**応答は大文字**、後の `GET` は小文字 | 201。応答も小文字 |
| 実在する ID とその大文字 | **500**（主キー） | 201。1 件になる |
| UUID の形で存在しない ID・別の種類の実在する ID（SNS 投稿の ID） | **500**（外部キー） | **422 `siteIds`**（`存在しないWebサイトが含まれています。`） |
| `'abc'`・`''`・長い文字列・`'\u0000'` | **500** | **422 `siteIds`**（`UUID の形で指定してください。`） |
| 実在する ID のハイフンなし・`{…}` | 201 | **422 `siteIds`**（`UUID の形で指定してください。`） |
| 1001 件以上（同じ ID の繰り返しを含む） | 201（重複なら）／**500**（別々の存在しない ID なら） | **422 `siteIds`**（`1000件以内で指定してください。`） |
| `[123]`・`null`・`'abc'`（配列でない） | 422（Zod。キーは `siteIds.0` / `siteIds`） | 同じ（HTTP では Zod が先に断る） |

`socialPostIds` の存在しない ID の文言は `存在しないSNS投稿が含まれています。`。

**422 にする理由（黙って落とさない理由）**：`listSocialPostsByIds` は存在しない ID を黙って落とすが、それは**読み出し**の話で、書き込みで落とすと「紐づけたつもりが紐づいていない」を利用者が気づけない（`043` が直した「黙って困る」と同じ型）。
SNS 投稿の作成も、存在しない `socialAccountId` を 422 `socialAccountId`（`SNSアカウントが見つかりません。`）で断っている。**404 にしない理由**：404 はパスが指すリソース（`{id}`）が無いときに使う（`05` §9・`043` §6.4）。本文の中の参照先の誤りは入力の誤り。

**形を厳しくする理由**：ハイフンなし・`{…}` は Postgres が読めるだけで、応答にその形が返り、後の `GET`（小文字の正規形）と食い違う。
一覧の絞り込み（`043` §6.3 の `siteId`、`042` の `accountId`）と同じ判定にそろえる。

**上限を置く理由**：存在の確かめは `IN (…)` で要素ごとに 1 つのパラメータを使い、書き込みも要素ごとに行を作る。上限が無いと 1 回の要求で何万ものパラメータ・行を作れる。
画面が選ばせるのはサイト・投稿それぞれ 100 件まで（`campaigns/new`・`[id]/edit` の `perPage: 100`）で、1000 はそれより十分に大きい。

**応答の `details` に値を入れない**：どの ID が無かったかは返さない（`043` の値を載せない規則。画面は欄の下に文言を出すだけで足りる）。`message` は既存の固定の文言（`入力内容を確認してください。`）。

**検査の順序**（テストで確かめる）：

1. 認証 → Permission（`campaign.write`）→ Zod（本文の型・`name` などの上限・配列の件数）。ここまでは既存
2. UseCase：既存の名前・期間の検査（`assertValid`・`assertPeriod`）→ `siteIds` / `socialPostIds` の形と件数（DB を読まない）
3. トランザクションの中：（`PATCH` のみ）キャンペーンが存在しなければ **404**。→ 紐づけ先の存在（§6.4）→ 書き込み

* 両方の配列に誤りがあれば、`details` に `siteIds` と `socialPostIds` の両方を入れる（同じ段の誤りはまとめて返す。形と存在は段が違うので、形の誤りがあれば存在は確かめない）
* `PATCH /campaigns/{UUID の形で存在しない ID}` に存在しない `siteIds` → **404**（従来どおり）。`siteIds: ['abc']` → **422**（本文の形の誤りは 404 より先。Zod の本文の誤りが 404 より先に返るのと同じ）。
  **ただしこれは期間（`startsOn` / `endsOn`）を送らないときに限る**（2026-09-25 検証の指摘 spec 軽微-3 で補った）。期間を送ると、2 の期間の検査がいまの値と突き合わせるために
  トランザクションの外でキャンペーンを読み（`findById`）、存在しなければその場で **404** を返すので、`siteIds: ['abc']` の形の誤りより 404 が先になる（既存の順序。本設計では変えない）

### 6.4 検査と書き込みの間の競合

画面で保存を押した瞬間に、別の利用者がそのサイトを消すことがある。「存在を確かめてから書く」だけでは、その間に消されると外部キー違反で 500 になる。

**対処：存在の確かめを書き込みと同じトランザクションで行い、見つかった行を `FOR KEY SHARE` で押さえる。**

* `FOR KEY SHARE` は、その行の `DELETE`（と主キーの更新）を、こちらのトランザクションが終わるまで待たせる。外部キーの検査が内部で取るロックと同じ強さで、サイト・投稿の通常の更新（名前など）は妨げない
* 先に始まっていた削除がある場合は、こちらの `SELECT` がその終わりを待ち、削除が確定すればその行は見つからず **422** になる（`READ COMMITTED`）
* このため外部キー違反を 422 へ写す仕組みは作らない。Infrastructure に Postgres のエラーコードの解釈を持ち込まずに済み、残った外部キー違反は想定外（不具合）として 500 のまま見える

> **（2026-09-25 追記。検証の指摘 security 低-1・spec 軽微-1 への処置）**
>
> * **`PATCH` はキャンペーンの行を先に押さえる。** 紐づけを指定した `PATCH` は、トランザクションの中で
>   `CampaignRepository.lockForUpdate`（`campaigns` の行を `FOR NO KEY UPDATE`。`UPDATE campaigns` が取るのと同じロック）を
>   **`lockExistingLinks` より先に**呼ぶ。存在しなければ 404（§6.3 の順序は変わらない）。
>   以前は「紐づけ先を `FOR KEY SHARE` → キャンペーンの行の `UPDATE`」の順で、同じキャンペーンへの `PATCH` が重なると、
>   後の `PATCH` は紐づけ先を押さえたままキャンペーンの行を待ち、その間サイト・投稿の削除を待たせていた。
>   いまは後の `PATCH` はキャンペーンの行で待ち、紐づけ先は順番が来てから押さえる（その間に消えたものは 422）。
>   `PATCH` どうしのロックの順序は「キャンペーン → 紐づけ先」で一定になる（アカウントの削除の CASCADE との組は §11 の 5）。
>   `campaign_sites` などの INSERT の外部キーの検査（`campaigns` の `FOR KEY SHARE`）は `FOR NO KEY UPDATE` と衝突しない
> * **テスト**：`application/campaign/campaign-link-concurrency.integration.test.ts`。
>   ① `campaign_sites` の BEFORE INSERT トリガで保存を止め（advisory lock。`sleep` に頼らない）、その間に別の接続から対象のサイトを `DELETE` する。
>   `createCampaign` / `updateCampaign` は成功（または 422）で `23503` にならず、`DELETE` は保存が終わるまで待つ。
>   存在の確かめをトランザクションの外（`context.connection`）で行う変異はこれで落ちる。
>   ② 別の接続がキャンペーンの行を押さえている間に同じキャンペーンへ `PATCH` を始め、行を待っている間に対象のサイトを
>   `lock_timeout = '200ms'` で `DELETE` すると成功する（順番待ちの `PATCH` はサイトを押さえていない）。順番が来た `PATCH` は 422 `siteIds`。
>   トリガと関数はテストの後で消す

## 8. 権限（Permission）

Permission の定義は変えない。**認可は入力の検査より先**（HTTP は `api/route.ts`、UseCase は `defineUseCase`、Data API は Manifest の宣言 → UseCase の Permission）。

| 経路 | 必要な Permission | 権限なし | 未認証 |
| --- | --- | --- | --- |
| `GET /campaigns`（`activeOn` の 422 を含む） | `campaign.read` | 403 | 401 |
| `POST /campaigns`・`PATCH /campaigns/{id}`（`siteIds` / `socialPostIds` の 422 を含む） | `campaign.write` | 403 | 401 |
| Data API `campaigns.create` / `update` | Manifest の `campaign.write` と、利用者の `campaign.write` | 宣言なし → `PluginPermissionError`。利用者が持たない → `ForbiddenError`。**どちらも `ValidationError` より先** | 既存どおり |

* 存在の確かめは `site.read` / `social.read` を求めない（紐づけに `campaign.write` だけを求める既存の設計のまま）。
  このため `campaign.write` だけを持つ利用者は、ある UUID のサイト・投稿が存在するかを 422 か 201 かで知れる。**いまも 500 か 201 かで同じことが分かり**、新しく漏れるものは無い（ID は推測の難しい UUID v7）
* 応答にも例外にも、送った ID を載せない（§6.3）

## 13. リスク

4. **競合のテスト（#24）の揺らぎ**：`lock_timeout` を使い、待ちの時間ではなく「時間切れで失敗する」ことを見る。`sleep` に頼らない
