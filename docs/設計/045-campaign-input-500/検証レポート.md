# 045 キャンペーンの入力で 500 になるものの修正 検証レポート

`043` §11 に記録した「コードから推定した 500」を直した作業単位。**ユーザー裁定（2026-09-24）「入力で 500 になる残り」を進める。**
設計の段階で実際の Route Handler・UseCase・Data API に入力を投げて 500 を確かめ、確かめたものだけを直した。

**ユーザー裁定（2026-09-25）**

1. 存在しないサイト・SNS 投稿の ID を紐づけようとしたら **422 で断る**（黙って落とさない）
2. 調査で見つかった別の型の 500（B1 NUL 文字・B2 西暦 0 年の `/analytics`・B3 範囲外の `scheduledAt`・B4 `pruneOlderThanDays` の上限）は **045 の直後に `046` で直す**

## 1. 直したもの

| 入力 | 変更前 | 変更後 |
| --- | --- | --- |
| `GET /campaigns?activeOn=2026-02-30` など暦に無い日付 | 500（`::date` の範囲外） | 422 `activeOn`「存在しない日付です。」 |
| キャンペーンの作成・更新の `siteIds` / `socialPostIds` に存在しない ID | 500（外部キー違反） | 422（存在しない） |
| 同じく `abc`・空文字・NUL・ハイフンなし・`{…}` | 500 か、形の食い違った 201 | 422（形） |
| 実在の ID とその大文字を一緒に | 500（主キーの重複） | 小文字にそろえ、重複を除き、昇順に並べて 201 |
| 1001 件以上 | 201（上限なし） | 422（件数。形より先に、DB より前に断る） |
| Data API の `campaigns.create` / `update` に同じ値 | Plugin へ `DatabaseError` | Core の `ValidationError`（`field` あり、値は載せない） |

画面のキャンペーンの作成・編集フォームは、「対象サイト」「関連するSNS投稿」の欄の下に誤りを出す。
存在の確認は、書き込みと同じトランザクションの中で紐づけ先を `FOR KEY SHARE` で押さえて行い、確認と書き込みの間の削除を防ぐ（外部キー違反を 422 に写す仕組みは作らない）。
公開 Plugin API は TSDoc の変更だけ。HTTP API は v1 のまま（公開前。`042` / `043` と同じ判断）。

## 2. 検証で確かめたこと

* `spec-verifier` は全件のテストを流し、**12 通りの変異**を入れた。さらに本物の Route Handler と Data API に設計 §1 の入力（1 万件の無作為な UUID、10 万個の同じ ID、10 万文字など）を投げ、**500 が 1 件も無い**ことを確かめた。
  範囲外の B1〜B4 は触られておらず、今も 500 であることも確かめた（`046` の対象）
* 生き残った変異は 1 つ：**存在の確認を書き込みと別の接続で行っても、UseCase のどのテストも落ちなかった**（Repository の層のロックのテストはあった）。
  `spec-verifier` がトリガを使った捨てテストで、その場合に競合で `23503`（500）になることを実際に確かめた → §3 の 1 で処置
* `security-reviewer` は、1000 件の上限が DB より前にあること、途中までの書き込みが起きないこと、応答にも例外にも入力の値が出ないこと、認可が検査より先であることを確かめた
* `boundary-guardian` は、公開 Plugin API の差分がコメントだけであること、`FOR KEY SHARE` が Infrastructure の中だけにあること、Data API の振る舞いの変更が `010` §9 の枠で説明されていることを確かめた
* `boundary-guardian` と `security-reviewer` は**テストを 1 本も実行していない**（DB の競合を避けるため）

## 3. 指摘と処置

| # | 指摘 | 処置 |
| --- | --- | --- |
| spec 軽微-1 | 「存在の確認を書き込みと同じトランザクションで行う」を守るテストが UseCase の層に無い（変異 M6b が生き残った） | トリガと advisory lock で保存を止め、その間に別の接続からサイトを消すテストを足した。M6b で 4 件落ちることを確かめた |
| security 低-1 | PATCH が紐づけ先の KEY SHARE を持ったままキャンペーン行を待つので、同じキャンペーンへの PATCH を送り続けるとサイトの削除を先延ばしにできる | キャンペーン行を先に `FOR NO KEY UPDATE` で押さえてから紐づけ先を押さえる順にした。テストで、待っている PATCH がサイトの削除を妨げないことを確かめた |
| security 低-2 | 穴のある配列（`new Array(2)` の一部だけ埋めたもの）が形の検査を通る（Data API 経由だけ） | 添字で回し、穴を形の誤りとして断る |
| spec 軽微-2 | Data API の `create({ siteIds: null })` が成功して `[]` になる（`update` は断る） | 省略（`undefined`）だけを「紐づけない」とし、`null` は `ValidationError` にそろえた |
| spec 軽微-3 | 設計 §6.3 の「形の誤りは 404 より先」は、期間を送らないときに限る | 設計を直した |
| boundary 低 | TSDoc とガイドが export していない `ValidationError` の `name` と `field` を約束した | 将来の公開の例外はこの 2 つを保つか、保たないなら動作の変更として扱う、と設計 §11 に書いた |
| boundary 情報 | 存在しないキャンペーンに形の誤った ID を渡す `update` が `NotFoundError` から `ValidationError` に変わった／TSDoc とガイドの書き方の差 | 設計 §9.2 に行を足し、TSDoc に「重複なし・昇順」を足した |
| security 情報 | `campaign.write` だけの主体が 422 で存在を知れる（以前も 500 で分かった）／アカウントの削除の連鎖とのデッドロック（以前からある）／本文の JSON が認証の前に読まれる（以前からある） | 設計 §11 に記録のみ |
