## 1. 目的

### 1.1 何が起きるか

1. 管理画面で同梱 Plugin（イメージに焼かれた `plugins/` の Plugin。いまは `example-plugin`・`sns-bluesky`・`sns-instagram`・`sns-threads`・`sns-x-api`・`sns-x-manual`）を
   **ファイルごと削除する**（`uninstallPluginUseCase` の `deleteFiles`）と、削除そのものの再ビルドが落ちる。あるいは、plugins の Volume に同梱 Plugin のフォルダが無い状態で起動したコンテナでも同じことが起きる
2. 以後、**どの Plugin を導入・削除しても、監視ループの中の再ビルドが毎回落ちる**。entrypoint は直前の成功ビルドへ巻き戻して起動するので、アプリは動き続けるが、
   **導入した Plugin はビルドに入らず、削除した Plugin はビルドに残る**。導入の操作なら、起動後のアプリは操作を `failed` にしてその Plugin を隔離する（`012` §7.2）。
   原因はその Plugin ではないので、利用者は何を直せばよいか分からない
3. 運用者が直すには、消えた同梱 Plugin のフォルダを手で戻すしかない（`050` が入れば、次の起動で同期が戻す。`050` 設計 §6.3 の 1）。監視ループの再ビルドは同期しないので、起動の後に消した場合は次の起動までこの状態が続く

### 1.2 調査の結果（2026-10-02。コードを読み、コンテナで再現して確かめた）

1. **再ビルドは `pnpm build` を走らせる。** `docker/entrypoint.sh:19-41` の `rebuild()` が `${TORIFUNE_BUILD_CMD:-pnpm build}`（`:30`）を実行し、失敗すれば `.next` を退避から戻す（`:35-39`）。
   `pnpm build` はルートの `package.json:17` で `pnpm generate:plugins && pnpm -r build`、web の `build` は `next build`（`apps/web/package.json:8`）。
   イメージのビルドも同じ `next build` を `pnpm --filter @torifune/web build` で走らせる（`Dockerfile:43-45`）
2. **`next build` は型の誤りでビルドを止める設定になっている。** `apps/web/next.config.ts:6-7` が `typescript: { ignoreBuildErrors: false }`（「Domain 層の型崩れをビルドで止める」）。
   `typescript.tsconfigPath` は設定していないので、型検査は `apps/web/tsconfig.json` で行う
3. **`apps/web/tsconfig.json` はテストファイルを含む。** `include` が `["next-env.d.ts", "**/*.ts", "**/*.tsx", ".next/types/**/*.ts"]`、`exclude` が `["node_modules", "e2e"]`（`:12-13`）。
   `src/` の下の `*.test.ts`（結合テストの `*.integration.test.ts` を含む）・`src/test-support/`・`playwright.config.ts` がすべて root files に入る。
   TypeScript の API で数えると、root files は 602、プログラムのファイルは 1,732（`node_modules` の型定義を含む）
4. **Next.js 16.3.2 の型検査は既定で `tsc` の CLI を使い、テストファイルの誤りも捨てない。**
   * `experimental.useTypeScriptCli` の既定が `true`（`next/dist/server/config-shared.js:257`）。このとき型検査は
     `tsc --project <tsconfigPath> --noEmit --declarationMap false --emitDeclarationOnly false`（`incremental` なら `--tsBuildInfoFile .next/cache/.tsbuildinfo` を足す）を走らせ、
     終了コードが 0 でなければビルドを落とす（`next/dist/lib/typescript/runTypeCheckCli.js:19-51`）
   * `<tsconfigPath>` は `typescript.tsconfigPath`、無ければ `tsconfig.json`（`next/dist/lib/verify-typescript-setup.js:106-107`・`:207-216`）
   * もう一方の API 方式（`useTypeScriptCli: false`）は、`*.test.*`・`*.spec.*`・`__tests__`・`__mocks__` のファイルの誤りを捨てる（`next/dist/lib/typescript/runTypeCheck.js:114-121`）。
     **既定ではこちらは使われない。** 同じ条件を API 方式で再現すると（Next.js の `runTypeCheck` を、`plugins/sns-threads` が無いように見せて直接呼ぶ）通る。CLI 方式では落ちる（下の 7）
   * `next build` は ESLint を走らせない（`next/dist/build/index.js` に lint の段が無い。`next.config.ts` にも `eslint` の設定が無い）。**ビルドの中の lint に同じ問題は無い**
5. **テストファイルのうち 27 個が同梱 Plugin のソースを相対パスで import する。** すべて `apps/web/src/plugin/` の下にある（`../../../../plugins/<id>/<file>`）。
   Plugin ごとには `sns-bluesky` 7・`sns-instagram` 8・`sns-threads` 8・`sns-x-api` 6・`sns-x-manual` 4（重なりあり）。`example-plugin` を import するテストは無い（`fs` で読むだけ）。
   例：`sns-threads.test.ts:10`・`sns-threads-publish.test.ts:40`・`help-guides-static-checks.test.ts:11-14`・`sns-x-api.test.ts:10-13`
6. **レジストリの生成は、ある Plugin しか並べない。** `scripts/generate-plugin-registry.mjs:36-75` の `discover()` は `plugins/` の直下のディレクトリのうち、
   隔離マークが無く（`:47`）、`plugin.json`（`:52`）と `index.ts(x)`（`:56-57`）があるものだけを返し、`generate()`（`:77`）がそれぞれを
   `import pluginN from '../../../../plugins/<dir>/index'` として書く（いまの生成物は `apps/web/src/plugin/generated-registry.ts:17-22`）。
   `pnpm build` は生成を先に走らせるので、**フォルダが無い Plugin はレジストリに現れず、レジストリが原因で落ちることは無い**
7. **コンテナで再現した。** 本番と同じ `Dockerfile` で作ったイメージ（`apps/web` の設定とテストは `main` と同じ）で、`rm -rf /app/plugins/sns-threads && cd /app && pnpm build` を走らせると：
   Turbopack のコンパイルは通り（`✓ Compiled successfully`）、続く `Running TypeScript` で **8 つのテストファイルに 21 件の誤り**（`TS2307 Cannot find module '../../../../plugins/sns-threads/…'` 14 件、
   解決できない型から連鎖した `TS7006` 7 件）が `file(line,col): error TS…` の形（`tsc` の CLI の出力）で出て、`Failed to type check.`・終了コード 1 になる
8. **テストを外した設定なら通ることも、同じイメージで確かめた**（コミットしない使い捨ての変更）。§6.1 の `tsconfig.build.json` を置き、`next.config.ts` に `tsconfigPath: 'tsconfig.build.json'` を足して：
   * `sns-threads` を消し、テストファイル（`src/security-headers.test.ts`）の末尾に型の誤りを足して `pnpm build` → **終了コード 0**。生成されたレジストリに `sns-threads` は無い
   * 続けて同梱 Plugin のエントリ（`plugins/sns-x-manual/index.ts`）の末尾に型の誤りを足して `pnpm build` → **終了コード 1**、`../../plugins/sns-x-manual/index.ts(22,7): error TS2322`。
     **Plugin のコードは今までどおりビルドで型検査される**
   * TypeScript の API で数えると、その設定の root files は 329、プログラムのファイルは 1,386。プログラムに名前が `.test.`・`.spec.` のファイルは 0 で、
     同梱 Plugin の `.ts`・`.tsx` 30 個はすべてレジストリから辿られて入る。誤りは 0 件。同梱 Plugin を 1 つずつ隠しても（6 通り）、すべて隠して空のレジストリにしても 0 件
9. **リポジトリに同じ形の前例がある。** `packages/cli` は `tsconfig.build.json`（`extends: "./tsconfig.json"`、`exclude: ["src/**/*.test.ts"]`）でビルドし（`packages/cli/package.json:13`）、
   `typecheck` は `tsconfig.json` でテストまで見る

### 1.3 本番のコードから同梱 Plugin のソースを直接 import している箇所

`apps/web` の `.ts`・`.tsx`・`.mts`・`.js`・`.mjs`（`node_modules`・`.next` を除く）について、import 指定子（静的 import・`export … from`・`import()`・`require()`）の
解決先が `plugins/` の下になるものを洗い出した。

| ファイル | 種類 | 同梱 Plugin のフォルダが無いとき |
| --- | --- | --- |
| `apps/web/src/plugin/generated-registry.ts` | 本番（生成物） | 落ちない。生成がある Plugin しか並べない（§1.2 の 6） |
| `apps/web/src/plugin/*.test.ts` の 27 個 | テスト | **落ちる**（§1.2 の 7）。本設計でビルドの型検査から外す |
| `apps/web/e2e/*.spec.ts` | E2E | 文字列（URL・コメント）に現れるだけで import は無い。もともと `exclude` 済み |
| `apps/web/src/test-support/*.ts` | テスト支援 | import しない（`threads-api.ts:9` などが「`plugins/…` を import しない」と明記）。テストからしか import されない（本番のコードからの import は 0） |

同梱 Plugin どうしも互いを import しない（`plugins/` の下の外部 import は `@torifune/plugin-api` と `react` だけ）。**本番のコードで同梱 Plugin のフォルダの有無に左右されるのはレジストリだけで、
レジストリは生成で追従する。** テストファイルをビルドの型検査から外せば、フォルダが無くてもビルドは通る。

### やること

### やらないこと（理由つき）

* **`apps/web/tsconfig.json` を変えない。** `pnpm typecheck`（CI の `check` ジョブ）とエディタはこれを使い、テストファイルまで型検査し続ける（§6.4）
* **テストの置き場所・import のしかたを変えない。** 同梱 Plugin のテストを `apps/web/src/plugin` に置き、Plugin のソースを相対パスで import する構成は、
  `036` 以降のすべての Plugin の作業単位が前提にしている。裁定は「ビルドの型検査から外す」で、テストの書き換えではない
* **`experimental.useTypeScriptCli` を切り替えない。** 理由は §6.5 の (a)
* **`Dockerfile`・`docker/entrypoint.sh`・`.github/workflows/ci.yml`・`scripts/container-verify/driver.mjs` を変えない。** イメージのビルドも再ビルドも `next build` を通るので、
  `next.config.ts` を変えれば両方に効く。CI と検証ドライバは `050` が変えている（§11.3）
* **`packages/plugin-api`・`packages/cli` のビルドを変えない。** `packages/plugin-api` の `build`（`tsc --noEmit`）はテストまで見るが、同梱 Plugin を参照しないので本件は起きない（§11.2 の 1）。
  `packages/cli` は既にテストを外している（§1.2 の 9）
* **消えた同梱 Plugin のフォルダを戻す仕組みは作らない。** それは `050` の同期の役目。本設計は「フォルダが無くても再ビルドが通る」ことだけを扱う

## 6. ビルドの型検査の設定（決めたこと）

### 6.1 `apps/web/tsconfig.build.json`

```json
{
  "extends": "./tsconfig.json",
  "exclude": [
    "node_modules",
    "e2e",
    "playwright.config.ts",
    "src/test-support",
    "**/*.test.ts",
    "**/*.test.tsx",
    "**/*.spec.ts",
    "**/*.spec.tsx"
  ]
}
```

* **`extends` と `exclude` だけを持つ。** `compilerOptions`・`include`・`files`・`references` を書かない。コンパイラの設定（`strict`・`paths`・`plugins` ほか）と
  `include` は `tsconfig.json` から受け継ぐので、**本番のコードは `pnpm typecheck` と同じ設定で検査される**。違うのは対象のファイルだけ
* **`exclude` は `tsconfig.json` の `exclude` を置き換える**（TypeScript は継承した `exclude` と足し合わせない）。そのため `node_modules` と `e2e` を書き直す
* パターンは `tsconfig.build.json` のあるディレクトリ（`apps/web`）からの相対。`include` も同じディレクトリの `tsconfig.json` から受け継ぐので、基準のずれは無い
* コメントを書かない（`packages/cli/tsconfig.build.json` に揃える）。理由は `next.config.ts` のコメント（§6.2）とこの設計書に置く
* `exclude` は「root files に入れない」だけで、**本番のコードから import されたファイルはプログラムに入る**。本番のコードがテストやテスト支援を import しないことは
  受け入れ条件 #7 で固定する（今は 0 件。§1.3。`@torifune/cli` を本番のコードから引くことは ESLint も止めている。`eslint.config.mjs:104`）

### 6.2 `apps/web/next.config.ts`

`typescript` を次のようにする（コメントは要旨。文言は実装で決める）。

```ts
  // Domain 層の型崩れをビルドで止める。
  // ただし本番のビルド（コンテナ内の再ビルドを含む）はテストファイルを型検査しない。
  // テストは同梱 Plugin のソースを直接 import するので、そのフォルダが無いと再ビルドが落ちる。
  // テストの型は `pnpm typecheck`（tsconfig.json）が見る。詳細: docs/設計/052-rebuild-without-tests/設計.md
  typescript: { ignoreBuildErrors: false, tsconfigPath: 'tsconfig.build.json' },
```

* `tsconfigPath` は `apps/web` からの相対（Next.js は `path.join(dir, tsconfigPath)` で解決する。§1.2 の 4）
* **`tsconfigPath` は型検査のほかに、モジュール解決の `paths`（`@/*`）にも使われる**（`next/dist/build/load-jsconfig.js:105-150`）。`tsconfig.build.json` は `paths` を
  `tsconfig.json` から受け継ぎ、Next.js は継承した `paths` の基準を定義元のディレクトリ（`pathsBasePath`）で取るので、`next dev`・`next build` の `@/` の解決は変わらない
* **Next.js は `tsconfig.build.json` を書き換えない。** 型検査の前の自動設定（`writeConfigurationDefaults`）は、`extends` を持つ設定を見ると何もせず戻る
  （`next/dist/lib/typescript/writeConfigurationDefaults.js:237-240`）。いまの `tsconfig.json` も `extends` を持つので同じ扱いを受けている
* `experimental.useTypeScriptCli` は書かない（既定の `true` のまま）。CLI 方式でも API 方式でも `tsconfigPath` を使うので、既定が将来変わっても本設計の効き目は変わらない

### 6.3 外すもの・外さないもの

| 対象 | ビルドの型検査 | 理由 |
| --- | --- | --- |

### 6.5 却下した案

| 案 | 却下の理由 |
| --- | --- |
| (a) `experimental.useTypeScriptCli: false`（API 方式に戻す） | 今の版では効く（§1.2 の 4）。しかし実験的な設定と Next.js 内部の正規表現（誤りの捨て方）に頼る。テストファイルは引き続きプログラムに入り（型検査の時間は減らない）、名前が `.test.` でないテスト支援の誤りは捨てられない。Next.js 自身が CLI 方式を既定にし、TypeScript 7 では API 方式が使えない旨の案内を持っている（`runTypeScriptCli.js` の `getTypeScriptApiMissingError`） |
| (b) `ignoreBuildErrors: true` にし、型検査を別の手順にする | 「Domain 層の型崩れをビルドで止める」を失う。再ビルドで Plugin の型の誤りを止められなくなり、巻き戻しと隔離が働かない |
| (c) `tsconfig.json` からテストを外し、テスト用に `tsconfig.test.json` を足して `typecheck` をそちらへ向ける | エディタは `tsconfig.json` しか読まないので、テストファイルが推測のプロジェクトに落ち、`@/` の解決・`strict` などの設定を失う |
| (d) テストを同梱 Plugin のフォルダの中へ移す・動的 import に変える | 27 ファイルの書き換え。Plugin のフォルダは Volume に入るので、テストを利用者の環境へ配ることになる。裁定の方向（ビルドから外す）とも違う |
| (e) entrypoint で再ビルドの前に消えた同梱 Plugin を戻す | `050` の同期と役目が重なり、「同梱 Plugin を消したい」という利用者の操作を打ち消す。テストが原因でビルドが落ちるという根本は残る |
