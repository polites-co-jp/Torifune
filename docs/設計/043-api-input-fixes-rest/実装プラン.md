### 確定事項（設計書から。プランで蒸し返さない）

* **ユーザー裁定（2026-09-24）「042 §11 の 1〜3 を 043 としてまとめて直す」**。範囲は ① `/sites`・`/users`・`/campaigns` の `page` / `perPage`、② `/campaigns?siteId=`、③ Data API の 5 つの一覧、④ SNS 以外の 27 操作の OpenAPI の追加の応答、⑤ `ManualHandoff.url` の上限（文書だけ）、と UUID の形でない ID で 500 になる 3 操作（設計 冒頭・§3）
* ① は **422 にせず丸める**。部品は 042 が `api/schemas/social.ts` に置いたものを `api/query.ts` へ `pageQuerySchema` / `perPageQuerySchema` として移す（**中身は同じ**。SNS の振る舞いと OpenAPI は変わらない）（設計 §4・§6.2）
* ② は `z.guid('UUID の形で指定してください。')`。空文字も 422 `siteId`（設計 §6.3）
* ③ **ユーザー裁定 1**：`page` / `perPage` は `normalizePagination` で丸め、丸めた値を `Page.page` / `Page.perPage` に返す。`socialPosts.list` の `accountId`・`campaigns.list` の `siteId` が `undefined` / `null` 以外で UUID の形でなければ、**公開 Plugin API に足す `PluginDataInputError` で reject する**。検査の順は **Manifest の宣言 → 利用者の Permission（`requirePermission`）→ 形の検査 → `normalizePagination` → UseCase**（設計 §8・§9.2）。`analytics.list({ siteId })` と `get(id)` は変えない
* `PluginDataInputError(pluginId, field)`：`Error` を直接継承、`name` は `'PluginDataInputError'`、`message` は `Data API の引数 ${field} の形が正しくない`（**値を含めない**）（設計 §9.2 のコード片）。`PLUGIN_API_VERSION` / `SUPPORTED_API_VERSIONS` は変えない（設計 §9.3）
* ④ `AdditionalResponse.status` を `200 | 401 | 404 | 409` に広げ、`defineRoute` は **`permission` が `null` でない操作に `status: 401` を書いたら `RouteDefinitionError`**。書く値は設計 §6.4 の表の 27 操作。表に無い 30 操作と 042 の 8 操作は変えない（設計 §6.4）
* **ユーザー裁定 2**：`revokeApiToken`・`deleteWebhook`・`getPluginOperation` の UUID の形でない ID を 404 にする。守りは Infrastructure（と `plugin/operations.ts`）に足し、API・Application 層は変えない（設計 §6.6）
* ⑤ は文書だけ（TSDoc と Plugin 開発ガイド。設計 §9.4）
* **データモデル・画面・Permission の定義・Application 層・Database・Authentication・UI は変えない**（設計 §4・§5・§7・§8）。UseCase・Repository のページングは変えない（画面は `perPage: 200` などを意図して使う）
* **既存テストで変えてよいのは `apps/web/src/api/social-openapi.test.ts` の #37 の 1 件だけ**（設計 §10.9）。ほかに変えないと通らないテストが見つかったら、実装者は直さずに報告する
* 検証は **`spec-verifier` / `boundary-guardian` / `security-reviewer` の 3 つ**。**`boundary-guardian` は必須**（公開 Plugin API に `PluginDataInputError` を足し、Data API の動作を変える）
* **SaaS 固有機能（テナント・課金・コンテナ管理）に触るタスクは本プランに無い**

## 3. タスク分解

原則：**1 タスク = 1 コミット**。各タスクは「テストを書いて失敗を確認 → 実装 → 通す」の順。
**test-writer → implementer への受け渡しの単位は G（まとまり）。** test-writer は G の中の全タスクのテストを先に書いて失敗を確かめてコミットし（1 G = 1 コミット）、implementer が G の中のタスクを順に通す。
**implementer はテストを書き換えない。** テストが設計と食い違うと判断したら、設計書のどこと食い違うかを報告して止まる。
各 G の最後で `pnpm test` / `pnpm typecheck` / `pnpm lint` / `pnpm format:check` が通る。

**着手順の骨子**：HTTP の一覧の丸め → `siteId` → Data API → 500 の 3 操作 → OpenAPI の宣言 → 文書 → 最終確認と 3 つの検証。
**G1 → G2 は同じスキーマとテストファイルを触るので直列。** G3・G4 は他に依存しない。**G5 は G4 の後**（404 の description に「UUID の形でない ID を含む」と書くので、その振る舞いが先に成り立っているべき）。G6 は G1〜G5 がすべて緑になってから。推奨の順は **G1 → G2 → G3 → G4 → G5 → G6 → G7**。

## 7. リスクと注意点

1. **部品を移すときに SNS の OpenAPI が変わる（T1 / #12）。** `.default()` と `transform` の順、`.meta()` の中身を変えると `default` や `minimum` / `maximum` が出入りする。移すだけにし、`social-openapi.test.ts` #25 と #12 の深い等しさで守る
2. **`campaign.ts` の `siteId` に `.max()` を足す（T3 / #14）。** 1000 文字で `details.siteId` に 2 つの文言が並び、「ちょうど 1 件」に反する
3. **Data API の検査の順（T7 / #31）。** 形の検査を `requirePermission` より先に置くと、権限の無い Plugin・利用者に入力の誤りを教える。①宣言 → ②Permission → ③形 → ④丸め → ⑤UseCase を崩さない
4. **`PluginDataInputError` の `message` に値を入れる（T6 / #29）。** ログにそのまま残る。コード片の固定の文にする
5. **`page: 1e300` の `OFFSET`（T4 / #26）。** `(Number.MAX_SAFE_INTEGER - 1) × perPage` は Postgres の bigint に収まる（`perPage` が 100 でも約 9.0e17 < 9.2e18）。`Number` の文字列化で指数表記にならない（1e21 未満）。#26 が DB を通して確かめる
6. **`normalizePagination` の引数の型を広げる（T4）。** `data-api.ts` の `options`（`ListOptions`）はそのまま渡せる。広げずにテストで型を外すと、Data API の側で JavaScript の Plugin が渡す `'3'`・`NaN` の扱いが型の上で見えなくなる（§8 の 2）
7. **`packages/plugin-api` への差分の混入（T6・T12 / #49）。** テスト・整形のついでの変更を入れない。`index.ts` は 1 行の追加だけ
8. **401 の宣言を認可のある操作に書く（T11）。** T10 の守りでモジュールの読み込み時に落ちる（`import '@/api/endpoints'` のテストが全部落ちる）。表の 401 は `permission: null` の 3 操作（`login`・`confirmPasswordReset`・`getCurrentUser`）だけ
9. **網羅のテスト（#39）の保守。** 表はテストに持つ。操作を足すたびに表の更新が要る（設計 §13 の 3。意図した手間）
10. **C 群の件数の検査の干渉（G1・G2）。** 同じファイルの前のテストが作ったサイト・ユーザー・キャンペーンが `meta.total` に混ざる。`afterEach` で消す。ユーザーは Token の持ち主を残す
11. **#35 の文脈の権限。** `social.read` を持たない利用者の文脈で組むと `ForbiddenError` が先に出て、`PluginDataInputError` のログにならない
12. **#42 の `POST /setup`。** 管理者がいる状態で 404 になることを見るので、scratch DB に管理者を作ってから叩く。CSRF の要る経路なので Cookie とヘッダを付ける（付けないと 403 で 404 を確かめられない）
13. **ガイドの既存の文言（T13）。** `application/social/static-checks.test.ts` #81 などが文言を固定している。書き足すだけにする
14. **公開リポジトリである（全コミット）。** コミットメッセージ・コメント・公開文書に運営側の事情を書かない。公開 API の TSDoc とガイドに作業単位の番号を書かない
