## 1. 目的

外部アプリと Plugin が API を仕様どおりに使ったとき、次の「黙って困る」振る舞いを無くす。

| # | いまの振る舞い | 困ること |
| --- | --- | --- |
| ① | `GET /sites`・`/users`・`/campaigns` の `page` / `perPage` に範囲の検査が無い | `perPage=-1`・`page=0` が **500**。`perPage=100000000` がそのまま通り、**全行をメモリへ読む**（042 の検証で `security-reviewer` が指摘）。`004` の受け入れ条件 17・18 とも食い違う |
| ② | `GET /campaigns?siteId=` は UUID の形でない値だと絞り込みが外れる | **全キャンペーンが返る**。打ち間違いに気づけない |
| ③ | Data API の `sites.list` など 5 つの一覧が `page` / `perPage` を素通しする。`socialPosts.list({ accountId })`・`campaigns.list({ siteId })` は UUID の形でない値で絞り込みが外れる | Plugin が不正な値を渡すと DB の例外、または上限なしの読み込み。**別のアカウントの投稿が返り**、Plugin がそれに `markPublished` / `markFailed` を掛けうる |
| ④ | OpenAPI に SNS 以外の 404・409 と、認可の無い操作の 401 が宣言されていない | 生成したクライアントが、実際に返る応答を想定外として扱う |
| ⑤ | `ManualHandoff.url` の説明に長さの上限が無い | 2048 文字を超える URL を返すと、手動投稿待ちの行が「Plugin が返した URL を開けません」になる。配信 Plugin の作者は Core を読まないと上限を知れない |

## 3. スコープ

### やること

1. `GET /sites`・`GET /users`・`GET /campaigns` の `page` / `perPage` を、042 で SNS に使った規則（丸める）に揃える（§6.2）
2. `GET /campaigns` の `siteId` を UUID の形に限り、それ以外を 422 `siteId` にする（§6.3）
3. Data API の 5 つの一覧（`sites`・`campaigns`・`socialAccounts`・`socialPosts`・`users`）の `page` / `perPage` を丸め、
   `socialPosts.list` の `accountId`・`campaigns.list` の `siteId` が UUID の形でなければ、公開 Plugin API に足す
   **`PluginDataInputError`** を投げる（§9.2）
4. `additionalResponses` の `status` に 401 を足し、SNS 以外の 27 操作に 401・404・409 を宣言する（§6.4）
5. UUID の形でない ID で 500 になる 3 操作（`revokeApiToken`・`deleteWebhook`・`getPluginOperation`）を 404 にする（§6.6）
6. `ManualHandoff.url` の TSDoc と Plugin 開発ガイドに 2048 文字の上限を書く（§9.4。文書だけ）
7. 文書の書き戻し（§12）

### やらないこと（理由つき）

| 対象 | 理由 |
| --- | --- |
| `GET /analytics`・`/analytics/breakdown` の `page` / `perPage` | **既にルートで丸めている**（`perPage` は 1〜100、`page` は 1 以上）。OpenAPI の `description` に丸めることが書かれていないだけで、上限なしの読み込みは起きない。§11 の 4 |
| `GET /analytics?siteId=`・`/analytics/breakdown?siteId=`、Data API の `analytics.list({ siteId })` | UUID の形でなければ **200 で空**（`analytics-repository.ts` が `false` の条件にする）。**絞り込みは外れない**。`analytics.list` は期間（400 日まで）で上限がある。Data API の `analytics.list` だけを `PluginDataInputError` に揃えると HTTP の `/analytics` と食い違うので、揃えるなら両方を一緒に判断する（§11 の 6） |
| Data API の `get(id)`（`sites`・`campaigns`・`socialAccounts`・`socialPosts`・`users`） | 形の誤った ID も「存在しない」として `null` を返す約束を既に持ち、テストもある（`data-api.integration.test.ts`）。絞り込みではなく参照なので、外れて別のものが返ることは無い。変えない |
| `GET /social/accounts?provider=` | 042 §6.3 で判断済み（外れない） |
| `GET /plugins/registry?q=` | 検索語（200 文字まで）。絞り込みが外れる型の問題ではない |
| `GET /api-tokens`・`/webhooks`・`/jobs`・`/plugins`・`/permissions`・`/roles` | ページングを持たない一覧。件数は運用者が作ったものに限られる（Token は自分の分、Webhook・Plugin は管理者が登録した分、ジョブ・Permission・ロールは固定に近い） |
| `GET /campaigns?activeOn=2026-02-30` のような暦に無い日付、キャンペーンの作成・更新の `siteIds` / `socialPostIds` に存在しない ID | どちらも **500**（コードからの推定。§11 の 3）。「絞り込みが黙って外れる」「上限なしのページング」とは別の型なので、本設計では扱わない |
| **UseCase と画面の経路のページング** | 画面は UseCase を直接呼び、`perPage: 200`（`/campaigns/{id}/analytics` のサイト名の対応表）のように 100 を超える値を意図して使っている。丸めは **HTTP と Data API の入口**に置き、UseCase・Repository のページングは変えない |
| SNS 以外の HTTP API の利用者向けの変更履歴を新しく作ること | 外部アプリ向けの変更履歴を持つのは SNS 投稿 API 仕様書だけで、SNS 以外の HTTP API には無い。本設計の記録（この文書と検証レポート）を正とする（§6.5） |

## 6. API

### 6.1 変更の一覧

| エンドポイント | 変わる点 |
| --- | --- |
| `GET /sites`・`GET /users`・`GET /campaigns` | `page` / `perPage` の範囲外を丸める |
| `GET /campaigns` | `siteId` が UUID の形でなければ 422 |
| `DELETE /api-tokens/{id}`・`DELETE /webhooks/{id}`・`GET /plugins/operations/{id}` | UUID の形でない ID で 500 → 404（§6.6） |
| OpenAPI（`GET /api/v1/openapi.json`） | 27 操作の `responses` に 401・404・409 が足される。上の 3 つの一覧の `page` / `perPage` の parameter に丸めの説明が付き、`siteId` に `format: uuid` と `pattern` が付く |

### 6.2 `page` / `perPage`（①）

**規則は 042 §6.2 と同じ（丸める）。** 部品も同じもの（§4）。

| 送った値 | 変更前 | 変更後 |
| --- | --- | --- |
| 省略 | `page=1`・`perPage=20` | 同じ |
| `page=0`・`page=-3` | **500 `INTERNAL_ERROR`**（`OFFSET` が負） | 200。`meta.page` は `1` |
| `perPage=-1` | **500 `INTERNAL_ERROR`**（`LIMIT` が負） | 200。`meta.perPage` は `1` |
| `perPage=0` | 200、`data` は空、`meta.perPage` は `0` | 200。`meta.perPage` は `1` |
| `perPage=1`〜`100` | そのまま | 同じ |
| `perPage=101`・`100000000` | そのまま通り、その件数まで返る | 200。`meta.perPage` は `100` |
| `page` が最終ページより先 | 200、`data` は空 | 同じ（`meta.total` は全件数） |
| `perPage=abc`・`perPage=1.5` | 422 `perPage` | 同じ |
| `page=`・`perPage=`（空文字） | `0` と解釈され、上の `0` の行と同じ | `0` と解釈され、丸めて `1` |

丸める理由（422 にしない理由）は 042 §6.2 のとおり。加えて、**これは新しい規則ではなく `004` が初めから定めていた規則**
（受け入れ条件 17・18）で、3 つの一覧はそれを適用し忘れていた。

OpenAPI の parameter は 042 と同じ形（`type: 'integer'`、`default`、丸めることを書いた `description`、`minimum` / `maximum` なし）。

### 6.3 `GET /campaigns` の `siteId`（②）

**規則は 042 §6.3 の `accountId` と同じ。** UUID の形（8-4-4-4-12 の 16 進、大文字・小文字を問わない、版と variant を見ない）でなければ
422 `siteId`（「UUID の形で指定してください。」）。判定は `campaign-repository.ts` の `UUID_PATTERN` と同じで、`z.guid()` を使う。

| 送った値 | 変更前 | 変更後 |
| --- | --- | --- |
| 省略 | 全件 | 同じ |
| 存在するサイトの UUID（大文字を含んでもよい） | そのサイトを対象に含むキャンペーン | 同じ |
| UUID の形だが存在しない | 200、`data` は空 | 同じ |
| `abc`・36 文字で 16 進でない文字を含む値・ハイフンなし | **絞り込みが外れて全件** | **422 `siteId`** |
| 空文字（`siteId=`） | **絞り込みが外れて全件** | **422 `siteId`** |
| 非常に長い値 | **絞り込みが外れて全件**（長さの上限も無い） | **422 `siteId`** |

同じ一覧のほかの絞り込み（`status` は列挙外で 422、`q` は 200 文字まで、`sort` はホワイトリスト外で 422、`activeOn` は `YYYY-MM-DD` の形でなければ 422）は変えない
（`activeOn` の暦に無い日付は §11 の 3）。

### 6.4 OpenAPI の追加の応答（④）

**042 §6.4 の `additionalResponses` をそのまま使う。** 変えるのは次の 2 点だけ。

1. `AdditionalResponse.status` を `200 | 401 | 404 | 409` にする。401 の `content` は 404 / 409 と同じエラーの形（`errorEnvelopeSchema`）
2. `defineRoute` の検査に 1 つ足す：**`permission` が `null` でない操作に `status: 401` を書いたら `RouteDefinitionError`**
   （生成器が既に 401 を出している。二重に書くと description が上書きされ、どちらが正か分からなくなる）

生成器が推し量らない方針（042 §6.4）は変えない。すべてルートの定義に書く。

**調べ方**：`app/api/v1/**/route.ts` の全 65 の公開操作（`documented: false` の 3 つを除く）について、ハンドラとそれが呼ぶ UseCase が
`NotFoundError`・`ConflictError`・`JobBusyError` を投げるか、ハンドラが `errorResponse()` を直接返すかをコードから追った。
生成器が既に出す応答（成功・422・429・500、認可があれば 401・403、GET 以外は 403）に無いものだけを足す。

**書く値（SNS 以外の 27 操作）：**

| operationId | 追加する応答 | description | 出どころ |
| --- | --- | --- | --- |
| `getSite`・`updateSite`・`deleteSite`・`regenerateSitePublicKey` | 404 | サイトが存在しない（UUID の形でない ID を含む） | `site-use-cases.ts`（Repository が UUID の形でない ID を null にする） |
| `getUser`・`deleteUser` | 404 | ユーザーが存在しない（UUID の形でない ID を含む） | `user-use-cases.ts` |
| `updateUser` | 404・409 | 404：同上。409：メールアドレスが既に使われている | `user-use-cases.ts`（`ConflictError('User', 'email')`） |
| `createUser` | 409 | ログイン ID またはメールアドレスが既に使われている | `user-use-cases.ts`（`ConflictError`） |
| `getCampaign`・`updateCampaign`・`deleteCampaign` | 404 | キャンペーンが存在しない（UUID の形でない ID を含む） | `campaign-use-cases.ts` |
| `revokeApiToken` | 404 | Token が存在しない、または自分の Token でない（UUID の形でない ID を含む。§6.6） | `api-token-use-cases.ts`（他人の Token も同じ扱い） |
| `deleteWebhook` | 404 | Webhook が存在しない（UUID の形でない ID を含む。§6.6） | `webhook-use-cases.ts` |
| `getPluginOperation` | 404 | Plugin の操作が存在しない（UUID の形でない ID を含む。§6.6） | `plugin-use-cases.ts` |

| `enablePlugin`・`disablePlugin` | 404 | Plugin が配置されていない、または導入されていない | `plugin-use-cases.ts` |
| `uninstallPlugin` | 404 | Plugin が導入されていない | `plugin-use-cases.ts` |
| `installFromRegistry` | 404 | Registry に指定した Plugin が無い | `plugin-use-cases.ts` |
| `getPluginSettings`・`savePluginSettings` | 404 | Plugin が読み込まれていない、または設定を持たない | `plugin-settings-use-cases.ts`（`requireSettings`） |
| `deliverWebhooks` | 409 | 他の配信処理が実行中（`details.job` と `Retry-After: 10` が付く） | ルート（`JobBusyError`） |
| `rollupAnalytics` | 409 | 他の集計が実行中（`details.job` と `Retry-After: 10` が付く） | ルート（`JobBusyError`） |
| `login` | 401 | ログイン ID またはパスワードが正しくない | ルート（`INVALID_CREDENTIALS`） |
| `confirmPasswordReset` | 401 | 再設定のトークンが無効または期限切れ | ルート（`INVALID_CREDENTIALS`） |
| `getCurrentUser` | 401 | ログインしていない | UseCase（`requireAuthenticated`） |
| `completeSetup` | 404・409 | 404：セットアップは済んでいる（管理者が既にいる）。409：ログイン ID またはメールアドレスが既に使われている | ルート（`errorResponse` を直接返す） |

**042 で書いた SNS の 8 操作**（`createSocialPost` の 200、`{id}` の 6 操作の 404、`publishSocialPosts` の 409）は変えない。
**上の表と 042 §6.4 の表に無い 30 操作には何も足さない**（`listSites`・`createSite`・`listCampaigns`・`createCampaign`・`listUsers`・
`listApiTokens`・`createApiToken`・`listWebhooks`・`createWebhook`・`listPlugins`・`listRegistryPlugins`・`inspectPluginPackage`・
`installPluginPackage`・`listAnalytics`・`listAnalyticsBreakdown`・`rebuildAnalyticsTimeZone`・`listJobStatuses`・`listPermissions`・`listRoles`・
`getSystemSettings`・`updateSystemSettings`・`updateAccessLogIpExclusions`・`previewAnalyticsTimeZone`・`updateAnalyticsTimeZone`・
`issueCsrfToken`・`logout`・`requestPasswordReset`、SNS の `listSocialAccounts`・`listSocialPosts`・`createSocialAccount`）。

足さないと判断した主なもの：

* `createCampaign`・`updateCampaign` で存在しない `siteIds` を渡したときは 404 ではなく 500（§11 の 3）。宣言しない
* `rebuildAnalyticsTimeZone` は実行中でも 409 を返さない（200 で `started: false`）
* `login` の 429（試行回数の上限）は、生成器が既に 429 を宣言している（description は「Rate Limit 超過」のまま。§11 の 5）
* `installPluginPackage` の 422（ファイルの問題）は生成器の 422 に含まれる
* 不正な Bearer は認可の無い操作では匿名として扱われ、401 にならない（`buildApiTokenContext`）

**網羅を静的に守る**（042 §13 の 4 のリスクへの手当て）：受け入れ条件 39 で、**全公開操作の追加の応答を上の 2 つの表と突き合わせる**。
操作を足したときに表へ載せなければテストが落ち、宣言の要否を必ず判断させる。あわせて、パスに `{id}` を持つ公開操作はすべて 404 を宣言していることを確かめる（受け入れ条件 41）。

### 6.5 互換性（外部アプリへの影響）

| 変更 | 外部アプリから見た変化 | 破壊的か |
| --- | --- | --- |
| ① `page` ≤ 0・`perPage` ≤ -1 | 500 → 200 | 破壊的でない（誤りの修正） |
| ① `perPage=0` | 200 で空 → 200 で 1 件 | 破壊的でない（空を期待する使い方に意味が無い） |
| ① `perPage` ≥ 101 | 要求した件数まで → **100 件まで** | **動作の変更。** `meta.perPage` が `100` になるので検知でき、`meta.total` までページを送れば全件取れる |
| ② `siteId` の形の誤り（空文字を含む） | 200 で全件 → **422** | **動作の変更。** 従来の応答は「絞り込んだつもりの全件」で誤っていた |
| ② OpenAPI の `siteId` に `format: uuid` | 生成クライアントで引数の型が変わりうる（Java の `UUID`、C# の `Guid` など） | 042 の `accountId` と同じ扱い |
| ④ OpenAPI | `responses` にキーが増えるだけ | 破壊的でない（追加） |

**API Version は v1 のまま出す**（042 §6.5 と同じ判断）。根拠は強い順に：

1. **API をまだ公開していない。** OSS は最初の公開前で、`docs/移行手引き/README.md` のとおり互換性を保つべき外部の利用者がまだ存在しない
2. **規則は `004-api-foundation`（受け入れ条件 17・18）が初めから定めていた**。3 つの一覧はその適用漏れで、直すのは実装を契約へ戻すこと
3. 変わる応答はどれも誤り（500、誤った全件）か、共通の規則からの逸脱だった

SNS 以外の HTTP API には外部アプリ向けの変更履歴が無いので、本設計の記録（この文書と検証レポート）を正とする。

### 6.6 UUID の形でない ID で 500 になる 3 操作（ユーザー裁定 2 で含めた）

## 9. Plugin API への影響

### 9.1 公開 Plugin API の型

**追加だけ。** `packages/plugin-api` に `PluginDataInputError`（クラス）を足し、入口（`index.ts`）から export する。
既存の型・値・export は変えない。ほかは `data.ts` と `social.ts` の TSDoc（§9.2〜§9.4）。
`PLUGIN_API_VERSION` / `SUPPORTED_API_VERSIONS` は変えない（§9.3）。

### 9.2 Data API の一覧の振る舞い（③）

#### `page` / `perPage`（ユーザー裁定 1 で承認）

**規則：Core の HTTP と同じく丸める。例外にしない。** `data-api.ts` の 5 つの一覧が `normalizePagination`（`domain/repository.ts`）を通し、
**丸めた後の値を `Page.page` / `Page.perPage` に返す**。

`normalizePagination` の規則（既存の規則を広げる。既存の単体テストはそのまま通る）：

1. `undefined` / `null` は省略（`page` は 1、`perPage` は 20）
2. それ以外は `Number(値)` で数にする。**有限の数にならない値**（`NaN`・`Infinity`・`-Infinity`・`'abc'`）は**省略と同じ**
3. 小数は切り捨てる（`Math.trunc`）
4. `page` は 1 以上 `Number.MAX_SAFE_INTEGER` 以下、`perPage` は 1〜100 に丸める

| Plugin が渡した値 | 変更前 | 変更後 |
| --- | --- | --- |
| 省略 | 1 / 20 | 同じ |
| `page: 0`・`page: -1` | **DB の例外**（`OFFSET` が負） | `page` は 1 |
| `perPage: -1` | **DB の例外**（`LIMIT` が負） | `perPage` は 1 |
| `perPage: 0` | 空の `items`、`perPage` は 0 | `perPage` は 1 |
| `perPage: 1000` | 1000 件まで返る | **100 件まで**。`Page.perPage` は 100 |
| `page: 2.9`・`perPage: 10.7` | DB の例外になりうる（`LIMIT` に小数） | 2 / 10 |
| `page: '3'`（JavaScript で書いた Plugin） | 通る（DB が文字列を数に読む） | 3（同じ） |
| `page: NaN`・`perPage: Infinity` | **DB の例外** | 1 / 20（省略と同じ） |
| `page: 1e300` | **DB の例外**（範囲外） | `Number.MAX_SAFE_INTEGER`。`items` は空 |

数の誤りを例外にしない理由：範囲外の数は意図が明らかで、丸めればどの値でも一覧が返り、`Page.page` / `Page.perPage` で何が採られたか分かる
（HTTP でも範囲外の整数は丸める。042 §6.2）。

#### `socialPosts.list({ accountId })` と `campaigns.list({ siteId })`（ユーザー裁定 1：例外を投げる）

**規則：`accountId` / `siteId` が `undefined` / `null` なら絞り込みなし（従来どおり）。それ以外で UUID の形でなければ、
返す `Promise` を `PluginDataInputError` で reject する**（同期では投げない。一覧はどれも `async`）。

「UUID の形」は HTTP（`z.guid()`）と同じ緩い判定：**文字列であり、8-4-4-4-12 の 16 進、大文字・小文字を問わない、版と variant を見ない**。
判定は `domain/id.ts` の `isUuidShape` に置く（§4）。空文字・数値・オブジェクトは形の誤り。

| Plugin が渡した値 | 変更前 | 変更後 |
| --- | --- | --- |
| 省略・`null` | 全件 | 同じ |
| 存在する ID（大文字を含んでもよい） | その ID で絞る | 同じ |
| UUID の形だが存在しない（版 0 などを含む） | 空 | 同じ |
| `'abc'`・`''`（空文字）・37 文字・数値など | **絞り込みが外れて全件** | **`PluginDataInputError`**（`field` は `'accountId'` / `'siteId'`） |

**検査の順序**（§8）：①Manifest の宣言（`requireDeclared` → `PluginPermissionError`）、②利用者の Permission
（`requirePermission(context, 'social.read' / 'campaign.read')` → `ForbiddenError` など。UseCase が中で行うものと同じ関数を先に呼ぶ）、
③形の検査（→ `PluginDataInputError`）、④`normalizePagination`、⑤UseCase。HTTP の 042 / 043（認証 → Permission → 422）と同じく、
**権限の無い呼び出しに入力の誤りを教えない**。

**例外を投げる引数の範囲**：Data API で「ID で一覧を絞る」引数は `socialPosts.list` の `accountId` と `campaigns.list` の `siteId` の 2 つだけで、この 2 つに揃える。
次は**投げない**（§3「やらないこと」）：

* `analytics.list({ siteId })`：形の誤りは従来どおり空の配列。絞り込みは外れず、HTTP の `/analytics` と同じ振る舞いを保つ（揃えるかは §11 の 6）
* `get(id)` の 5 つ：形の誤りも「存在しない」として `null`（既存の約束とテストのまま）
* `page` / `perPage`：丸める（上の節）
* 作成・更新の引数（`siteIds` など）：本設計の範囲外（§11 の 3）

#### `PluginDataInputError`（公開 Plugin API に足す）

`packages/plugin-api/src/data.ts` の `PluginPermissionError` の隣に置き、`index.ts` から export する。既存の Plugin 向けの例外
（`PluginPermissionError(pluginId, permission)`・`PluginStoreError(message, key)`・`PluginExtensionNotDeclaredError(pluginId, kind)`）の流儀に揃え、
`Error` を直接継承し、`name` を固定し、判定に使う項目を `readonly` で持つ。

```ts
/**
 * Data API に渡した引数の形が正しくない（例：`socialPosts.list({ accountId: 'abc' })`）。
 *
 * **渡した値は `message` にも項目にも含めない**（ログにそのまま残るため）。
 * 誤っていた引数の名前は `field` で分かる。
 */
export class PluginDataInputError extends Error {
  constructor(
    readonly pluginId: string,
    /** 誤っていた引数の名前（`'accountId'` / `'siteId'`）。 */
    readonly field: string,
  ) {
    super(`Data API の引数 ${field} の形が正しくない`);
    this.name = 'PluginDataInputError';
  }
}
```

| 論点 | 決めたこと | 理由 |
| --- | --- | --- |
| 名前 | `PluginDataInputError` | `Plugin` で始まる既存の例外の命名に揃え、Data API の入力の誤りだと分かる名前にする |
| 項目 | `pluginId`・`field` | `PluginPermissionError` と同じく「どの Plugin が」を持つ（ログで切り分けるため）。`field` は `PluginStoreError.key` にあたる。**値は持たない** |
| `message` | 引数名だけを埋めた固定の文（`Data API の引数 accountId の形が正しくない`） | Core のログ（`plugin render failed`・`event handler failed`）は `message` だけを残すので、引数名が無いと切り分けられない。引数名は Core が決めた固定の集合で、入力を反射しない |
| `field` の型 | `string` | 開いた集合にしておき、将来ほかの引数に広げても型を変えずに済む（足すことは破壊的でない） |
| 判定 | `error instanceof PluginDataInputError`（`name === 'PluginDataInputError'` でもよい） | Plugin は Core と一緒にビルドされ、同じ `@torifune/plugin-api` を import する（Plugin に独自の `package.json` は無い）ので `instanceof` が効く。`name` は固定 |
| 既存の例外との関係 | `PluginPermissionError` を継承しない・させない。Core 内部の `ValidationError` とも無関係 | 権限の誤りと入力の誤りは別の対処を要する。`ValidationError` は公開 API ではない |

**Plugin が捕まえなかったとき**（Core に新しい捕まえ口は足さない。既存の扱いのまま）：

| 呼んだ場所 | 起きること | 残るログ |
| --- | --- | --- |
| Plugin のページ・Widget・拡張点の描画 | `PluginBoundary` がその枠だけを落とし「表示できませんでした」。画面全体は 200 のまま | `plugin render failed`（`pluginId`、`reason` に `message`） |
| イベントのハンドラ | 握られ、発火元は成功する | `event handler failed`（`event`・`pluginId`・`reason`） |
| `activate()` | その Plugin は `disabled` に落ちる（ガイド §2） | 既存の起動失敗のログ |
| 配信 Plugin の `validate()` | 登録時は 500、配信直前は `failed`（未送信）（ガイド §9 の表） | 既存のログ |
| 配信 Plugin の `publish()` | `failed`（結果不明）。再試行されない（ガイド §9） | 既存のログ |
| 配信 Plugin の `manual()` | その行が「Plugin でエラーが起きました」 | `social publisher manual failed` |

Plugin が HTTP のエンドポイントを持つ仕組み（`027-plugin-http-api` §3.1）は**実装されていない**（027 の検証レポート）。
実装するときに、捕まえられなかった `PluginDataInputError` を 422 に写すかを決める（§11 の 7）。いまは HTTP の状態コードへの写し方を決めない。

**同梱の Plugin への影響**：Data API の一覧を呼ぶのは `plugins/example-plugin/ui/pages.tsx` の `sites.list({ page: 1, perPage: 5 })` だけ（`plugins/` を検索した）。
`accountId` / `siteId` を渡す同梱の Plugin は無く、`sns-*` の 5 つは Data API の一覧を呼ばない。**対応は要らない。**

### 9.3 Plugin API の互換性の判断

| 変更 | 既存の Plugin から見た変化 | 判断 |
| --- | --- | --- |
| `PluginDataInputError` の追加・export | 型と値が 1 つ増える | 破壊的でない（追加） |
| `page` ≤ 0・`perPage` ≤ -1・`NaN` など | 例外 → 一覧が返る | 破壊的でない（失敗が成功になるだけ） |
| `perPage: 0` | 空 → 1 件 | 破壊的でない |
| `perPage` ≥ 101 | 要求した件数まで → **100 件まで** | **動作の変更。** `Page.perPage` が 100 になり、`Page.total` までページを送れば全件取れる |
| 形の誤った `accountId` / `siteId`（空文字を含む） | 全件が返る → **`PluginDataInputError` で失敗する** | **動作の変更（成功していた呼び出しが失敗になる）。** ただし従来の成功は誤った全件を返しており、正しい使い方（省略か実在の ID）では何も変わらない |

* **`010-plugin-api` 設計 §9 の破壊的変更の列挙（削除・必須の引数の追加・戻り値の型を狭める・Payload の変更・Extension Point の削除・Manifest の必須項目の追加）のどれにも当たらない。**
  型の変更は追加だけで、戻り値の形も同じ。ただし「成功していた呼び出しが失敗になる」は列挙に無い種類の動作の変更なので、`010` §9 に判断を追記して記録する（§12）
* **`PLUGIN_API_VERSION` は `1` のまま据え置く。** 理由：
  1. **版を上げても何も伝わらず、壊すものだけがある。** `PLUGIN_API_VERSION` は `context.apiVersion` として実行時に Plugin へ渡り、型 `PluginApiVersion` にもなっている。
     上げると、`context.apiVersion === 1` で分岐している Plugin の挙動と `1` を期待する型が、今回の変更と無関係な Plugin まで一律に変わる（`010` §9 の 2026-09-06 の追記、032 の先例）。
     一方で失敗に変わるのは「形の誤った ID を渡す」呼び出しだけで、版数の変化からそれを知る手段は無い。**版数はインターフェイスの記述子であって、振る舞いの修正を伝える器ではない**（同追記）
  2. **失敗に変わる呼び出しは、元から誤った結果を受け取っていた。** 正しく使っている Plugin には影響が無い
  3. **影響を受ける Plugin が今は無い。** 同梱の Plugin は該当しない（§9.2）。OSS は公開前で、第三者の Plugin もまだ無い（`docs/移行手引き/README.md`）
  4. 032 は Core のイベントを足して版を上げなかった。本設計も足すのは例外クラス 1 つで、同じ扱いになる
* **移行手引きは書かない。** 07 §47 は移行手引きを「互換性を保つべき外部の利用者」のために置き、`docs/移行手引き/README.md` は最初の公開前には置かないと定めている。
  **公開後に同じ種類の変更（成功していた呼び出しを例外に変える）をするときは移行手引きの対象にする**ことを、`010` §9 の追記に書く
* 伝え方：TSDoc（下）、Plugin 開発ガイド §4、`010` §9 の追記（§12）

TSDoc に書く内容：

* `ListOptions`：「`page` は 1 以上、`perPage` は 1〜100。範囲外・小数・数にならない値は丸める（数にならない値は省略と同じ）。採った値は `Page.page` / `Page.perPage` に返る。全件が要るときは `Page.total` までページを送る」
* `Page.perPage`：「丸めた後の値（要求した値とは限らない）」
* `socialPosts.list` の `accountId`・`campaigns.list` の `siteId`：「UUID の形（8-4-4-4-12 の 16 進）で渡す。形が違えば（空文字を含む）`PluginDataInputError` で reject される。
  絞らないときは省略する。UUID の形で存在しない ID は空の `Page`」
* `PluginDataInputError`：上のコード片のとおり

### 9.4 `ManualHandoff.url` の上限（⑤。文書だけ）

`packages/plugin-api/src/social.ts` の `ManualHandoff.url` の TSDoc に次を足す（型は変えない）。

* **https の絶対 URL は 2048 文字以内。** 超えると Torifune は使えない URL として扱い（`isValidManualUrl`）、手動投稿待ちの行が
  「Plugin が返した URL を開けません」になる
* 本文を URL に埋め込む Plugin は、`validate()` で**手動投稿のときに URL の長さを検査して登録時に断る**
  （同梱の X・Threads・Bluesky の Plugin がそうしている。日本語 1 文字は URL の中で 9 文字）
* `/` で始まる Torifune 内のパスには、いま長さの検査が無い。**同じく 2048 文字以内に収める**（将来検査を足しても壊れないように）

Plugin 開発ガイド §9 の「SNS 配信（`social`）」の表の `manual` の行と、`manual()` の例の近くに同じ趣旨を 1〜2 文で書く。
互換性：文書だけで、振る舞いは変わらない。

## 13. リスク

6. **`message` に引数名を入れること**：引数名は Core が決めた固定の集合なので入力の反射にはならない。**値は入れない**（受け入れ条件 29 で確かめる）
