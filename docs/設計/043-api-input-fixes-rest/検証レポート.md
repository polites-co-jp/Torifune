# 043 SNS 以外の API の入力検査と OpenAPI の宣言の修正 検証レポート

`042`（SNS の API の入力検査）の検証で見つかった、SNS 以外の同種の不具合を直した作業単位。

**ユーザー裁定（2026-09-24）**

1. SNS 以外の同種の不具合は `042` の後に `043` としてまとめて直す
2. Plugin の Data API で形の誤った `accountId` / `siteId` は**例外を投げる**（`PluginDataInputError`）。Data API の `perPage` も 100 に丸める
3. UUID の形でない ID で 500 になる 3 操作（API トークンの削除・Webhook の削除・Plugin の操作の取得）も含める

実装完了時点（`3c1b208`）に対し、3 つの検証エージェントを**互いの結果を見せずに独立して**走らせた。

| 担当 | 判定 |
| --- | --- |
| `spec-verifier`（設計との整合） | **条件付き合格**（重大 0・中 0・文書 1。「文書を 1 か所直せばマージしてよい」） |
| `boundary-guardian`（境界） | **合格**（違反 0。低 3・情報 1） |
| `security-reviewer`（セキュリティ） | **合格**（重大・高・中 0。低 1（範囲外）・情報 3） |

処置（`75cd0c0`）は文書だけ。処置の前の全件は **9,198 件全通過**、typecheck / lint / format:check / `next build` 通過。
処置で触れた文書の静的検査 15 件は処置の後も通過。画面を変えていないので E2E は流していない。

## 1. 直したもの

| 区分 | 変更前 | 変更後 |
| --- | --- | --- |
| `/sites`・`/users`・`/campaigns` の `page` / `perPage` | `perPage=-1`・`page=0` が 500、`perPage=100000000` で全行をメモリへ読める | `042` と同じ部品で丸める（`page` は 1 以上、`perPage` は 1〜100） |
| `/campaigns?siteId=` | UUID の形でないと絞り込みが黙って外れ全件 | 422 `siteId` |
| Plugin の Data API の一覧（5 つ） | `page` / `perPage` を検査せず、`NaN` などで DB の例外 | Core と同じ規則で丸める |
| Data API の `socialPosts.list` の `accountId`、`campaigns.list` の `siteId` | 形が誤ると全件（Plugin が別のアカウントの投稿を書き換えうる） | **`PluginDataInputError` で reject**（渡した値は例外に載せない。Manifest の宣言と利用者の Permission の検査の後） |
| API トークンの削除・Webhook の削除・Plugin の操作の取得 | UUID の形でない ID で 500 | 404 |
| OpenAPI | SNS 以外の 404・409・401 が宣言されていない | 27 操作に宣言。認可のある操作に 401 を書くと起動時に断る |
| 公開 Plugin API の説明 | 手動投稿の URL の上限 2048 が書かれていない | `ManualHandoff.url` の TSDoc と Plugin 開発ガイド §9 に書いた |

**公開 Plugin API は型の追加だけ**（`PluginDataInputError` と export 1 行）。`PLUGIN_API_VERSION` は 1 のまま（`010` §9 に判断を追記。`boundary-guardian` が正当と判定）。
動作の変更は 2 つ（形の誤った ID で reject、`perPage` 101 以上で 100 件まで）で、TSDoc・Plugin 開発ガイド §4・`010` §9 に書いた。同梱の Plugin への影響は無い。

## 2. 検証で確かめたこと

* `spec-verifier` は全件のテストを流し、**14 件の変異をすべて検出**した。さらに本物のルートに境界値（一覧の 21 通り、`siteId`、3 つの ID のエンドポイントに `abc`・NUL・3000 文字など）を投げ、500 が 1 件も無いことを確かめた。
  `a975ccb` と HEAD の OpenAPI を操作ごとに比べ、変わったのが設計の表の 27 操作と 3 つの一覧の parameter だけで、**SNS の操作は 1 つも変わっていない**ことを確かめた
* `security-reviewer` は、丸めた後の値で OFFSET が int64 に収まること、巨大な `perPage` でメモリを食わせられないこと、Data API の検査の順で Plugin が権限を超えて探れないこと、
  例外にもログにも渡した値が出ないこと、他の管理者の API トークンの UUID では 404 になることを確かめた
* `boundary-guardian` と `security-reviewer` は**テストを 1 本も実行していない**（DB の競合を避けるため）

## 3. 指摘と処置

| # | 指摘 | 処置 |
| --- | --- | --- |
| spec 文書-1 | 手動投稿の URL の上限の段落が、Plugin 開発ガイドの Database Provider の節に入っていた（静的検査は SNS の節に `2048` があるかしか見ておらず通していた） | SNS 配信の節の `manual()` の例の直後へ移した |
| boundary 低-1 | `instanceof PluginDataInputError` は `@torifune/plugin-api` の実体が 1 つであることが前提。将来 npm で公開して第三者が別の実体を持つと黙って false になる | ガイド §4 に「`error.name` で判定するのが将来も確実」と書いた |
| boundary 低-2 | `010` §9 の「`032` と同じ扱い」は、例外クラスの追加の部分しか裏づけない | 限定の語句を足した |
| boundary 低-3 | 公開後に同種の変更をするとき、移行手引きを書くことと版を上げることの関係が決まっていない | 「移行手引きは製品の版で切る。`PLUGIN_API_VERSION` を上げるのは §9 の列挙に当たる破壊に限る」と明記した |
| boundary 情報 | UUID の形の判定が `domain/id.ts` とファイルごとの定数に分かれている | 記録のみ（判定は同じ。今後触るときに寄せる） |
| security 低-1（範囲外） | 画面の URL の `?page=` に `Infinity`・`1.01`・`1e18` を付けると、その利用者の画面が 500 になる（5 画面。漏れるものは無い） | **未修正。ユーザーに扱いを確認する**（§5） |
| security 情報 | `normalizePagination` に `Symbol` を渡すと落ちる／OpenAPI の説明文が状態の違いを書く／Repository の守りは入口で止めているので実害なし | 記録のみ |
| spec 軽微（範囲外） | 同じクエリのキーが重なると後の値が勝つ（採られた値は検査される）／422 の文言が Zod の既定の英文 | 記録のみ（既存の振る舞い） |
