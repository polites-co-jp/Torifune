# 018-analytics 設計

## 1. 目的

アクセス・分析データ（`02_データベース設計.md` §5.8、`05_API設計.md` §20、
`06_画面設計.md` §15）。`002-Torifune機能完成` T6。

## 2. 最初に決めること：収集方式

`02` §5.8 は「**Webサイトや外部サービスから取得した**マーケティングデータを
管理する」としか書いておらず、**誰が集めるのかが未確定**だった。
これを先に裁定する。

### 候補

| 案 | 内容 | 問題 |
| --- | --- | --- |
| (a) Torifune が全アクセスを集める | 計測タグを配って自分で受ける | 受け口が増える。運用が重い |
| (b) 外部解析サービスから取り込む | Plugin が GA 等から集計値を引く | **外部サービスを使わない人が何も見られない** |
| (c) 両方を同じ受け皿へ入れる | Core が両方の置き場と API を持つ | 設計が増える |

### 決定：(c) 両方。ただし役割を分ける

`01_アーキテクチャ設計.md` §12 は「外部サービス連携は可能な限り Plugin」と
しているが、**それは「外部サービス」の話であって「自分のサイトのアクセス」の話ではない。**

Torifune は「マーケティング活動を一元管理する」ものであり、
アクセス解析のために別サービスを必須にするのは、その目的に反する。
一方で、既に GA 等を使っている利用者の数値も同じ画面で見たい。

したがって、

* **`access_logs`**：Torifune 自身が計測タグで受ける**生のアクセス**。Core の責務
* **`analytics`**：**日次の集計値**。Core の集計と、Plugin が外部サービスから
  取り込んだ値の**両方**が入る（`source` で区別する）

2テーブルに分ける形は `02` §5.8 の記述（`analytics` と `access_logs`）と一致する。

## 3. 計測の設計

### 3.1 受け口は認証しない。サイトキーで識別する

計測タグは**閲覧者のブラウザから**叩かれる。認証はできない。

`sites` に `public_key`（推測できない文字列）を足し、
`POST /api/v1/collect` はそれでサイトを識別する。

**キーが漏れても被害は「偽のアクセスを送られる」に留める。**
キーで読み出せるものを作らない（書き込み専用）。

### 3.2 個人を特定しうる値を保存しない

**IPアドレスと User-Agent の生値を保存しない。**

* 訪問者の識別は `sha256(日付ソルト + サイトID + IP + UA)` の先頭に短縮したハッシュ
* **ソルトは日ごとに変える。** 変えないと、ハッシュが恒久的な識別子になり、
  日をまたいで同じ人を追跡できてしまう
* 日をまたぐと同じ訪問者を数えられなくなるが、**追跡できないことのほうが重要**

保存するのは：サイト / 日時 / パス / リファラの**ホストだけ** /
訪問者ハッシュ / デバイス種別（`desktop` / `mobile` / `tablet` / `bot`）。

> クエリ文字列を保存しない。トークンや個人情報が URL に入ることがある。

> 2026-09-04 追記（`028`）：制御文字（`0x00`〜`0x1f`、`0x7f`）を含むパスは `normalizePath` が `null` にして記録しない。
> パスは集計の内訳キーとして画面に出るため（`028` §5.3.6）。

### 3.3 Bot を数えない（が、捨てもしない）

User-Agent から Bot を判定し、`device = 'bot'` として記録する。
**集計からは除く。** 除かないと、数字が実態から離れる。

捨てないのは、「急に増えた」ときに Bot かどうかを確かめられるようにするため。

### 3.4 計測タグは Torifune が配る

`GET /t.js` が計測スクリプトを返す。利用者はサイトへ1行貼るだけにする。

**スクリプトは最小にする。** Cookie も localStorage も使わず、`sendBeacon` で叩くだけ。
Cookie を使うと同意取得の話が乗ってきて、導入の敷居が上がる。1KB を目安に収める。

#### 3.4.1 SPA のクライアント遷移でも送る（2026-09-03 追記）

当初はロード時に1回送るだけだった。Next.js App Router のような SPA では、
リンクを辿っても `<head>` が再描画されずスクリプトが再実行されないため、
**サイト内回遊の PV が丸ごと欠けていた**（記録されるのは直リンク・検索流入・
リロード・別タブだけ）。

Plausible / Umami と同じく、History API をフックして **pathname が変わるたびに送る**。

* `history.pushState` / `replaceState` を包み、`popstate` を聞く。
  包みは元の挙動を変えない（戻り値・`this`・引数をそのまま通す）。
  送信は元関数を呼んだ**後**に行う（URL が変わってから読む）。
  送信側の例外は try/catch で閉じ、ホストサイトのナビゲーションを壊さない
* **公開キー（`data-site`）は初回実行時に閉じ込める。** `document.currentScript` は
  後続のコールバック内では `null` になるため、遷移時に読み直すと壊れる
* **pathname が実際に変わったときだけ送る。** SPA はスクロール復元やクエリ更新で
  `replaceState` を連発する。受け口は query を捨てて path だけを保存するので、
  判定も pathname で行う。ハッシュだけの変化（`hashchange`）も数えない
* **タグが2回貼られても二重に入らない。** `window.__torifune` で多重インストールを防ぐ
* **遷移時の `referrer` は `null` で送る。** `document.referrer` は SPA セッションの間
  ずっと外部流入元のままなので、遷移ごとに送ると流入元が実数以上に膨らむ。
  受け口は referrer のホストだけを保存するため、自サイトを送っても自己参照ノイズになる。
  初回ロードだけ従来どおり `document.referrer` を送る。
  → 流入元の集計は「セッションの入口1回」のままで、この変更で変わらない
* **bfcache からの復帰（`pageshow` の `persisted`）は数えない。** 戻った先はすでに
  数えたページであり、スクリプトの状態（直前の pathname）も凍結されたまま戻るので、
  何もしなくても増えない。数える判断をするならここを変える

受け口 `POST /api/v1/collect` のペイロード（`{key, path, referrer}`）と DB スキーマは変えない。

**送信は `text/plain` で行う。** 計測タグは他所のサイトに貼られるため、
受け口とは必ず別オリジンになる。`application/json` は CORS のセーフリスト外で、
送るたびにプリフライト（`OPTIONS`）が飛ぶ。CORS は既定で無効なので
（`05_API設計.md` §43）、**貼ったサイトのオリジンを `TORIFUNE_CORS_ORIGINS` へ
足さない限り、計測がまるごと落ちる**。

計測のために CORS を開かせない。開かせると、そのオリジンから `/api/v1` の
参照系まで開くことになり、計測の代償として広すぎる。
セーフリストの `text/plain` なら単純リクエストになり、プリフライトが起きない。
受け口は Content-Type を見ずに本文を JSON として読むため、受け側は変えない。

### 3.5 大量の書き込みを受ける前提にしない

いまの規模で必要なのは「動くこと」であり、秒間数万を捌くことではない。
`access_logs` へ素直に INSERT する。

**限界を明記する**：高トラフィックのサイトではこのままでは足りない。
足りなくなったら、受け口とDBの間にキューを挟む。
`POST /api/v1/collect` の形は変えずに済む。

## 4. 集計

### 4.1 日次のロールアップを CLI で行う

`torifune analytics rollup` が `access_logs` を日ごとに集計して
`analytics` へ **upsert** する。

**画面から生ログを集計しない。** 期間が延びるほど遅くなり、
「1年分を見たら固まる」という壊れ方をする。

**再実行できる**（同じ日を何度集計しても結果が同じ）。
一度きりの処理にすると、失敗したときに手で直すことになる。

#### 4.1 への追記（2026-09-04、`028-analytics-dashboard-redesign`）

* **CLI は無い。** 実装は `POST /api/v1/analytics/rollup`（cron から API トークンで叩く）だけであり、
  集計 SQL を CLI と本体で二重に持たないため CLI は追加しない。画面の案内文もこの API に合わせる
* 集計はセッション化を行う。同一 `(site, 集計日, visitor_hash)` の PV を 30 分無操作で区切り、
  日をまたがない。`sessions` の定義はこれに変わる（旧定義は visitors と同値の仮置きだった）。
  **マイグレーション後、保持している生ログの期間でロールアップを流し直す**（§4.1.1 と同じ扱い）
* `bounces` / `dwell_ms` / `dwell_samples` / `bot_pageviews` / `bot_visitors` と、
  `key` 付きの内訳（時間帯・デバイス・ランディング・参照元・パス別）を出す。一覧は `028` §5.2
* 冪等性は upsert ではなく **(site, day) ごとの `source = 'core'` 行の差し替え**で保証する。
  前回あって今回無い key の行を残さないため。Plugin の行には触らない
* 集計した範囲の `max(occurred_at)`（Bot 含む）を `sites.analytics_last_seen_at` へ書き戻す（`GREATEST` で巻き戻さない）

#### 4.1 への追記（2026-09-04、`029-scheduled-jobs`）

* **集計は本体の中の定期実行が既定で回す**（15 分ごと。`TORIFUNE_ROLLUP_INTERVAL_MINUTES`）。
  外部 cron を前提にしない（「タグを貼れば数字が出る」を既定にする）
* 定期実行の対象期間は「最後に成功した実行の開始日から今日まで、ただし最大 7 日さかのぼる」。
  数日の停止は次の実行が人手なしで埋める。7 日を超える停止は API で流し直す
* `POST /api/v1/analytics/rollup` は**残る。** 応答の形も変えない。
  `TORIFUNE_SCHEDULER=off` で本体の定期実行を止め、外部スケジューラから叩く運用もできる
* 定期実行と手動 API は**同じ排他と同じ記録**に載る。ジョブ名ごとの PostgreSQL advisory lock で
  1 プロセスだけが走り、実行は `job_runs` に残る。詳細は `029` §6

### 4.1.1 1日の境目は運用タイムゾーンで決める（2026-09-03 追記）

当初は集計を UTC 固定（`occurred_at AT TIME ZONE 'UTC'`）で畳み、
画面とソルトはサーバーのローカル日付を使っていた。**この2つがずれていた。**

JST の 00:00〜09:00 に見る「今日」は、まだ UTC の前日であるため常に空になり、
ソルトが1つの集計日の途中（JST 09:00）で回るため同じ訪問者が2人と数えられていた。

`TORIFUNE_TIMEZONE`（IANA 名、既定 `UTC`）を1つ置き、次の3つをそろえる。

| 使う場所 | 実装 |
| --- | --- |
| 日次集計 | `(occurred_at AT TIME ZONE <tz>)::date` と期間の境界 |
| 画面・ロールアップの既定期間 | `daysAgoInTimeZone` / `todayInTimeZone` |
| 訪問者ハッシュのソルト | 同じ境目で回す |

**サイトごと・ユーザーごとにはしない。** 同じ集計値が見る人によって違う日に
属することになり、保存した日次の値を説明できなくなる。

**変更したら過去の期間はロールアップを流し直す。** 保存済みの
`metric_date` は前の境目で畳まれたままで、勝手には直らない。

期間の絞り込みでも `occurred_at >= '...'::date` と書かない。
`timestamptz` と `date` の比較は接続の TimeZone 設定に左右され、
同じ SQL が環境ごとに別の範囲を指す。

### 4.2 `analytics` は「日 × サイト × 出所 × 指標」の値

```text
analytics(site_id, metric_date, source, metric, value)
```

`source` は `core`（Torifune 自身の集計）か Plugin ID。
Plugin が外部サービスの値を同じ形で入れられる。

指標は `pageviews` / `visitors` / `sessions` を Core が出す。
**指標名を固定の列にしない。** 列にすると、Plugin が別の指標を持てない。

#### 4.2 への追記（2026-09-04、`028-analytics-dashboard-redesign`）

```text
analytics(site_id, metric_date, source, metric, key, value)
```

内訳キー `key`（既定 `''`）を足し、PK を 5 列にした。参照元ホスト・パス・時間帯のように
値の種類が開いているものは `metric` 名に埋め込めない（`isValidMetricName`）ので `key` に置く。
キーを持たない指標は `key = ''` のまま。Plugin の `record` は `key` 省略で従来どおり動く。

### 4.3 保持期間

生ログは増え続ける。`torifune analytics prune --days=N` で古い生ログを消す。
**集計値は消さない。** 集計値は小さく、過去との比較に要る。

#### 4.3 への追記（2026-09-04）

実装は CLI ではなく `POST /api/v1/analytics/rollup` の `pruneOlderThanDays`（`system.manage` を要求）。
保持日数は画面に出さない。

## 5. 画面（`06` §15）

* 期間（開始日・終了日）とサイトで絞る
* 日次の推移（数値の表。**チャートは `014-dashboard` で共通部品を作ってから**）
* 上位ページ（`access_logs` から直接。期間を区切るので重くならない）

`analytics.read` Permission を足す。

#### 5 への追記（2026-09-04、`028-analytics-dashboard-redesign`）

* 画面は **1 サイトずつ**表示する（合算の「すべて」は無い）。期間プリセット（7日 / 30日 / 90日 / 今月 / 前月 / カスタム）と
  同じ長さの直前期間との比較、「Bot を集計に含める」スイッチを持つ
* サイトの下に 概要 / ページ / 参照元 / 訪問者 / 設定 の 5 タブ。計測タグは「設定」タブへ移し、公開キーの再発行（`site.write`、監査ログ）を置く
* **上位ページも `analytics`（`path_pageviews`）から引く。** 生ログを読む経路は画面にも API にも残さない。
  `GET /analytics?kind=topPaths` は互換のため残す（`deprecated` は付けない。エンドポイント単位で `kind=points` まで
  非推奨になってしまうため）。OpenAPI の `kind` の説明で `GET /analytics/breakdown` へ誘導する
* チャートは `014` の Chart を複数系列・軸ラベル・目盛り・凡例つきに拡張したものを使う

#### 5 への追記（2026-09-04、`029-scheduled-jobs`）

* 「設定」タブの受信状況を **4 状態**（未受信 / 受信中（集計待ち） / Bot のみ受信 / 受信中）にし、
  未集計の受信件数・生ログの最終受信・最終集計（全体）・定期実行の状態を並べる。
  「届いているが未集計」「Bot だけ届いている」を管理画面だけで切り分けられるようにするため
* **「生ログを画面から集計しない」原則は変えない。** 画面が生ログへ出す問い合わせは
  「最終受信の 1 行」と「未集計件数（上限 1000 行で打ち切り）」の 2 つだけで、期間で集計するものは無い。
  詳細は `029` §6.4 / §7.1

## 6. Plugin から

Data API に `analytics` を足す。

* `list`：集計値を読む
* `record`：**集計値を書く**（外部サービスから取り込んだ値を入れる）

生ログ（`access_logs`）は Plugin へ出さない。個人の行動に近く、
出す理由が「一覧したい」しか無い割に危険が大きい。

## 7. やらないこと

* リアルタイム集計。日次で足りる
* コンバージョン、ファネル、セグメント。**何を目標とするかは利用者ごとに違う**
* 地域・言語の推定。IP から地域を引くにはデータベースが要り、
  「IPを保存しない」方針とも噛み合わない
* チャート描画（`014-dashboard` で共通部品として作る）

#### 7 への追記（2026-09-04）

* 地域・言語の推定はやらない、を維持する（`028` 裁定 #2。モックの「国別のアクセス」は出さない）
* セッション・直帰率・平均滞在は「やらないこと」ではなくなった（`028` §5.3）。滞在時間は計測タグを変えずに
  PV 間隔から出すため、セッション最後のページは含まれない
* チャートの拡張は `014` §3.1 の追記を参照

## 8. 受け入れ条件

1. 計測タグを貼ったページからアクセスが記録される
2. **IPアドレスと User-Agent の生値が保存されていない**
3. 訪問者ハッシュが日をまたぐと変わる
4. 不正なサイトキーでは記録されない
5. Bot は記録されるが集計に含まれない
6. ロールアップを2回流しても値が二重にならない
7. 画面で期間とサイトを絞って日次の値を見られる
8. Plugin が集計値を読み書きできる。生ログは読めない
9. `analytics.read` が無ければ 403
10. **別オリジンのサイトに貼っても、CORS の設定を足さずに記録される**
    （計測タグがプリフライトを起こさない）
