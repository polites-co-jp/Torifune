## 1. 目的

1. **チェックを付けやすくする。** 今は 16px 四方のチェックボックスにしか当たらない。行を見分ける「状態」のセルと、チェックボックスのセルの全体で切り替えられるようにする（ユーザー裁定 2）
2. **選んだ投稿を 1 回の操作で投稿する。** 今は自動の予約・承認待ちは「一括送信（承認）」、手動投稿は「選んだ手動投稿を順に投稿」と別の操作で、手動投稿は 1 件ごとに
   「投稿画面を開く」→ SNS で投稿 →「投稿した」→ 次の件の「投稿画面を開く」と押す。送信待ちタブでは「一括投稿」1 つにまとめ（ユーザー裁定 3）、
   承認待ちは承認して投稿し（ユーザー裁定 4）、手動投稿は「投稿した」「投稿しなかった」を選ぶと次の投稿画面が開くようにする
3. **これまでの約束を崩さない。** 承認待ちは承認を経ずに SNS へ出さない（`048` §7.2・`055` §5.5）、見た内容に対して記録する（`055` §5.6 の `expectedUpdatedAt`）、
   開いた外部の画面から `window.opener` でとりふねへ戻れない（`035` §7.2）、開くのは人のクリックだけ（`055` §9.5.2）

### 3.3 手動投稿の URL と窓（`ui/social/manual-handoff.ts`・`application/social/social-use-cases.ts`）

* URL は **Server Component が描画時に**手動の予約の行だけ `resolveManualHandoff` で作る（`handoff`）。**承認待ちの行には渡さない**（`not_scheduled`。`055` §5.5）。
  押してから問い合わせると `window.open` がクリックの同期処理の外になりブロックされるため（`035` §7.2）
* `openManualWindow(url)`＝`window.open(url, 'torifune-manual-post', 'popup=yes,width=600,height=720,noopener=yes,noreferrer=yes')`。`noopener` なので**戻り値は常に `null`**（開けたか判別できない）。
  同じ URL の「別のタブで開く」（`rel="noopener noreferrer"`）を併置。`window.open` を呼ぶのはこのファイルだけ（`055` #39）
* `resolveManualHandoff`（`social.read`）：手動でなければ 422（`deliveryMode`）、無い・区画の外は 404、Plugin が無ければ `unsupported`、予約でなければ `manual()` を呼ばず `not_scheduled`、
  `manual()` は `MANUAL_TIMEOUT_MS`（2 秒）で打ち切り `plugin_error`、URL の検査に落ちれば `invalid_url`。**単独の HTTP の口は無い**（画面の描画からだけ呼ばれる）
* 配信 Plugin の `manual()` の URL：`sns-x-api`・`sns-x-manual` は `https://x.com/intent/tweet`、`sns-threads` は `https://www.threads.com/intent/post`、`sns-bluesky` は `https://bsky.app/intent/compose`、

## 5. 決めたこと

### 5.1 チェックの当たり判定（ユーザー裁定 2）

**作り：`Table` の列の任意の `onCellClick?: (row: T) => void`。** 渡した列の `<td>` に `onClick` と `cursor: pointer` を付ける。

| 対象 | 決めたこと |
| --- | --- |
| 切り替わるセル | 送信待ちタブ・投稿タブの**選択の列のセル**と**状態のセル**（1 段目）。2 段目（本文）・アカウント・登録元・日時・配信方法・操作のセルには付けない |
| 切り替えの意味 | チェックボックスを押したのと同じ（`toggleRow`）。選べない行（`updatedAt` が無い）・一括の処理中は何もしない（チェックボックスが `disabled` のときと同じ） |
| 出す条件 | 選択の列を描くとき（`canApprove \|\| canWrite \|\| canDelete`）。閲覧者の状態のセルには `onClick` も `cursor` も付けない |
| 二重の切り替えを防ぐ | `Table` のセルの `onClick` は、**押した要素からセルまでの間に操作できる要素があれば `onCellClick` を呼ばない**。操作できる要素は定数 `CELL_CLICK_IGNORE_SELECTOR`＝`a[href], button, input, select, textarea, label, summary, [role="button"], [role="link"], [role="checkbox"], [contenteditable="true"]`。チェックボックス自身を押したときはブラウザの既定（`change`）だけが切り替え、セルは何もしない。状態のセルのリンク（投稿タブの補足）は遷移だけする |
| 判定の関数 | `isCellClickIgnored(target, cell)`（`table.tsx` から export）：`target` が `closest` を持たなければ偽。`target.closest(CELL_CLICK_IGNORE_SELECTOR)` が `cell` の中（`cell.contains`）にあれば真 |
| 見た目 | `cursor: pointer` だけ。色・枠は変えない |
| アクセシビリティ | キーボード・支援技術の操作は今のまま**チェックボックス**（Tab で止まり Space で切り替え。名前は「この投稿を選択：<抜粋>」）。セルに `tabindex`・`role` を足さない（同じ操作の止まり先が二重になり、セルがボタンと読まれる）。セルのクリックはポインタで押しやすくするための補助 |

却下した案：

| 案 | 却下の理由 |
| --- | --- |
| チェックボックスを `<label>` で包む（状態のセルも `<label htmlFor>` にする） | `<label>` はセルの余白（`padding`）を覆わず、当たり判定が広がりきらない。余白まで覆うには表のセルの余白の仕組みを崩す。状態のセルを `<label>` にすると、その文字（補足・Badge・リンク）がチェックボックスに結びつき、リンクを含むラベルという読みづらい形になる |
| 各部品の `render` の中で、セルいっぱいの `<div onClick>` を置く | `<td>` の余白を覆えないのは同じ。`Table` の外で同じ作りを 2 部品に二重に書く |
| 行（`<tr>`・`<tbody>`）全体のクリック | ユーザー裁定 2（本文・ボタンでは切り替えない） |

### 5.2 一括投稿（ユーザー裁定 3・4）

送信待ちタブの帯は **「一括投稿…」「一括取り消し…」** の 2 つ（この順）。投稿タブの帯は 054 のまま。

**一括投稿の振り分け**（UI の純関数 `bulkPostPlanOf(selectedRows, { canApprove, canWrite })`。表示中の行の順で渡す）：

| 選んだ行 | 権限 | 扱い |
| --- | --- | --- |
| 承認待ち・自動 | `canApprove` | **承認（即投稿）**。次の定期実行で配信される |
| 承認待ち・手動 | `canApprove` かつ `canWrite` | **承認（即投稿）→ 投稿画面の URL を取る → 順に開く**（予約済みの手動の後ろ） |
| 承認待ち（自動・手動） | `canApprove` が無い | 対象外「承認の権限なし」 |
| 承認待ち・手動 | `canApprove` はあるが `canWrite` が無い | 対象外「投稿の権限なし」（承認しても記録できない） |
| 予約済み・自動・予約日時が未来か無い・配信中でない | `canWrite`（承認済みなら `canApprove` も） | **今すぐ送る**（`publish-now`） |
| 同上 | `canWrite` が無い／承認済みで `canApprove` が無い | 対象外「投稿の権限なし」／「承認の権限なし」 |
| 予約済み・自動・期限が来ている（配信待ち・再試行待ち・支度待ち）か配信中 | — | 対象外「配信待ち・配信中」（すでに配信の順番を待っている） |
| 予約済み・手動（予約時刻の前後を問わない）・`handoff.ok` | `canWrite` | **順に開く**（先頭から。今すぐ送るには回さない） |
| 予約済み・手動・`handoff` が開けない | `canWrite` | 対象外「投稿画面を開けない」 |
| 予約済み・手動 | `canWrite` が無い | 対象外「投稿の権限なし」 |

* 送信待ちタブには下書き・配信済み・失敗が無い（055 裁定 3）。渡されたら数えずに捨てる（純関数は送信待ちの区分だけを見る）
* 「一括投稿…」は `canApprove || canWrite` のとき出す。対象が 0 件（選択 0 件・対象外だけ）なら `disabled`
* 対象外の理由のキーと表示名：`no_approve_permission`「承認の権限なし」・`no_write_permission`「投稿の権限なし」・`due_or_publishing`「配信待ち・配信中」・`handoff_unavailable`「投稿画面を開けない」（この順）
* **手動の予約に `publish-now` を掛けない**：`manual-outcome` は予約時刻の前の手動の予約も受ける（`055` 裁定 4）ので早める必要が無く、早めると `updatedAt` が変わり描画時の `updatedAt` で記録できなくなる
* **時機は即投稿だけ**（承認の `publishTiming: 'now'`）。「一括投稿」は「いま投稿する」操作で、時機を選ばせる 054 の画面と分ける

### 5.3 承認した手動投稿の URL の得方

承認待ちの手動投稿は描画時に URL を持たない（`055` §5.5。承認を経ずに SNS へ出す手がかりを画面に置かない）。承認した後の URL の得方を比べた。

| 案 | 判断 | 理由 |
| --- | --- | --- |
| (a) 承認の後に読み込み直し（`router.refresh()`）、新しい行の `handoff` を使う | 却下 | 読み込み直しが終わったことを部品が知る口が無い。承認した行は並び（手が要るもの順の先頭の「手動投稿待ち」）が変わり、表示中のページから外れうる（そうなると URL が取れない） |
| (b) 承認の応答に URL を載せる | 却下 | 承認（1 件・一括）は API トークンも使う公開の操作で、応答の形を変える。承認の UseCase が Plugin の `manual()` を呼ぶことになり、一括の時間の予算（`BULK_BUDGET_MS`）に `manual()` が乗る |
| (c) **画面専用の取得の口 `GET /social/posts/{id}/manual-handoff`** | **採用** | 既存の `resolveManualHandoff`（`social.read`。予約でなければ `not_scheduled`）をそのまま HTTP に出すだけで、承認の約束（承認を経ずに URL を作らない）はサーバが守る。承認の結果を受け取った直後に取り、**窓を開くクリックより前に URL が手元にある**ので、開くのは常にクリックの同期処理の中になる |
| (d) クリックで空の窓を先に開き、URL を取ってから移す | 却下 | 窓の参照が要り `noopener` をやめることになる（§5.4）。空の窓が見え、取れなかったときに閉じる処理が要る |

* 取る時機：一括投稿の「投稿する」の後、`bulk/approve` の結果が返った直後に、承認できた手動投稿ぶんを**並行に**取る（最大で表示件数＝100 件。Rate Limit の既定 60 秒 300 回に収まる）
* 記録の `expectedUpdatedAt` は**承認の応答の `post.updatedAt`**（行の `updatedAt` は承認の前の値）。取った後に誰かが本文を直していれば、記録は 409（`055` R3 と同じ守り）
* 取れなかった（要求の失敗・`ok: false`）承認済みの手動投稿は順に開かず、終わりの表示に「承認しましたが投稿画面を開けませんでした（手動投稿待ちに残ります）」として件数と抜粋を出す

### 5.4 窓の開き方と「戻ってきた」の検知

| 論点 | 決めたこと | 理由 |
| --- | --- | --- |
| 開き方 | **`openManualWindow`（035 の `noopener=yes,noreferrer=yes`）のまま変えない** | 窓の参照を持っても閉じたことは知れない（§3.4）。参照を持たなければ `window.opener` は最初から無く（逆タブナビング対策）、Referer も送らない |
| 検討した前提 | `noopener` をやめて戻り値を持ち、開いた直後に `win.opener = null` で逆参照を切り、`win.closed` を監視する案 | X・Threads の COOP（`same-origin-allow-popups`）で開いた直後から `closed === true` になり、閉じたのか読み込んだだけかを見分けられない（§3.4）。さらに `noreferrer` を外すと、とりふねのオリジンが Referer で X へ渡る（とりふねは `Referrer-Policy` を付けておらず、既定の `strict-origin-when-cross-origin` でオリジンが送られる） |
| 「閉じた」の代わり | **とりふねの画面に戻ってきたこと**：窓を開いた後に、とりふねの `window` が `blur` するか `document.visibilityState` が `hidden` になり（離れた）、その後 `focus` するか `visible` に戻ったら（戻った）、記録のボタンを出す。子の窓（`popup=yes`）を閉じると開き手へフォーカスが戻る。狭い画面で子がタブで開くときはタブを戻すと `visible` になる | COOP に左右されず、利用者の「閉じたら次へ」の手順に沿う。窓を閉じずにとりふねへ戻っても出る（戻ったのは記録するためなので困らない） |
| 聞き始めるとき | 窓を開いたクリックの処理で段を「開いた」にし、聞く処理（`useEffect`）を付けた時点で**すでに離れていれば**（`document.hidden` か `!document.hasFocus()`）「離れた」として数える | 窓はクリックの中で同期で開き、`blur` は描画の確定より先に届きうる |
| 監視の間隔 | **無い**（イベントで知る。定期的な確認をしない） | — |
| 閉じずに記録する手段 | **「記録へ進む」ボタン**を、窓を開く前（「開いていない」段）と開いた後（「開いた」段）に出す。押すと記録のボタンが出る | 窓がブロックされた・別のタブで開いた・別の端末で投稿した・Playwright のようにフォーカスが動かない環境でも先へ進める。要るかを検知の確かさに賭けない |
| ポップアップがブロックされたとき | `noopener` では戻り値が `null` で判別できない（今と同じ）。「開いた」段の案内に「窓が開かないときは『別のタブで開く』を使ってください」と書き、「別のタブで開く」のリンク（`rel="noopener noreferrer"`）を常に出す。リンクを押しても段を「開いた」にする | 判別のために `noopener` をやめない（上の理由） |
| 次の窓 | 「投稿した」・「失敗にする」（「投稿しなかった」の確認）の**クリックの同期処理の中で、記録の要求を送るより先に**次の件の URL を `openManualWindow` で開く。次の件の段は「開いた」から始まる | 記録の要求を待ってから開くとクリックの外になりブロックされうる。URL は手元にある（§5.3） |
| 最初の窓 | 一括投稿の確認の「投稿する」のクリックで、**順に開く先頭が予約済みの手動投稿（URL が手元にある）なら**その窓を開く。先頭が承認する手動投稿しか無いときは、承認と URL の取得の後に順に投稿の 1 件目を「開いていない」段で出し、「投稿画面を開く」を押させる | 利用者の「一括投稿すると順番に X の投稿画面」に沿う。承認した手動投稿の URL はクリックの後でないと取れない（§5.3） |
| 最後の 1 件の後 | 次の窓を開かない。記録が通ったら終わりの表示 | — |
| 窓の名前 | 今の `torifune-manual-post` のまま。`noopener` なので名前による窓の使い回しは効かず、毎回新しい窓が開く（`manual-handoff.ts` の注記のとおり）。前の窓は利用者が閉じる | — |

**段**（順に投稿の今の件の状態。純関数 `windowStageAfter(stage, event)` で移す）：

| 段 | 意味 | 出すもの |
| --- | --- | --- |
| `ready`（開いていない） | まだこの件の窓を開いていない | 「投稿画面を開く」「別のタブで開く」「記録へ進む」「やめる」。記録のボタン（投稿した・投稿しなかった）と URL の欄は出さない |
| `opened`（開いた） | 窓を開いた。戻るのを待つ | 案内「SNS の窓で投稿したら、窓を閉じてこの画面に戻ってください。戻ると記録のボタンが出ます。窓が開かないときは『別のタブで開く』を使ってください。」、「投稿画面を開く」（開き直し）「別のタブで開く」「記録へ進む」「やめる」 |
| `returned`（戻った） | 記録できる | URL の欄（任意）、「投稿画面を開く」「別のタブで開く」、「やめる」「投稿しなかった」「投稿した」。次の件があれば案内「選ぶと次の投稿画面が開きます。」 |

| 出来事 | `ready` | `opened`（離れていない） | `opened`（離れた） | `returned` |
| --- | --- | --- | --- | --- |
| `open`（開いた・リンクを押した） | `opened` | `opened` | `opened`（離れたかを数え直す） | `opened` |
| `left`（`blur`・`hidden`） | 変えない | 離れた | 離れた | 変えない |
| `back`（`focus`・`visible`） | 変えない | 変えない | `returned` | 変えない |
| `recordNow`（「記録へ進む」） | `returned` | `returned` | `returned` | 変えない |

### 5.5 投稿タブ

当たり判定（§5.1）だけを足す。一括送信（承認）・一括取り消し・行の操作は 054・056 のまま。

## 6. API：`GET /api/v1/social/posts/{id}/manual-handoff`（新）

| 項目 | 内容 |
| --- | --- |
| 目的 | 手動投稿の投稿画面の URL を作る（画面が承認した後の手動投稿に使う。§5.3） |
| 認証 | **セッションだけ**（`sessionOnly: true`。Bearer は有効なトークンでも 401 `UNAUTHENTICATED`）。`GET` なので CSRF は掛からない。セッションも無ければ 401 |
| Permission | `social.read`（`resolveManualHandoff` の Permission。新しい Permission は作らない） |
| Rate Limit | 既定（操作 × 送信元 IP ごとに 60 秒 300 回） |
| パス | `{id}` が UUID の形でなければ 404 |
| 処理 | 既存の UseCase **`resolveManualHandoff(context, { id })`**（行ごとの上限 `MANUAL_TIMEOUT_MS`。`deadline` は渡さない＝1 件の要求なので描画の予算は要らない）。新しい UseCase は作らない |
| 200 | `{ data: { ok: true, url: string, note: string \| null } }` か `{ data: { ok: false, reason: 'unsupported' \| 'invalid_url' \| 'plugin_error' \| 'not_scheduled' } }`（`changed` は返さない。`settleManualHandoff` は使わない＝変わった行は 404 / 422 で返す） |
| 404 | 投稿が無い・区画の外・UUID の形でない（`NotFoundError`。アカウントが無いときも 404） |
| 422 | 自動配信の投稿（キー `deliveryMode`「手動投稿ではありません。」。今の UseCase の文言） |
| 401 / 403 | 401：未認証・Bearer。403：`social.read` が無い |
| `operationId` | `getSocialPostManualHandoff` |
| `description` | 「画面（セッション）専用。API トークンでは 401。手動投稿の予約の投稿画面の URL を配信 Plugin に作らせる。予約でない（承認待ち・下書き・配信済み・失敗）ときは URL を作らず `not_scheduled` を返す。」 |
| 監査・イベント | 残さない・出さない（読むだけ。描画の `resolveManualHandoff` と同じ） |

* 応答のスキーマ `manualHandoffResponseSchema`（`api/schemas/social.ts`）：`ok` で分かれる 2 つの形（`ok: true` は `url`・`note`、`ok: false` は `reason` の `enum`）。`strict`
* ルートの `additionalResponses` に 404・422 を宣言する（`GET` に本文が無いので 422 が既定の応答に入らない。実装プランで `route.ts` の既定を確かめる）
* **資格情報は渡らない・返さない**（`resolveManualHandoff` のまま。`note` は `redactSecrets` 済み）
* 承認待ちの投稿の URL は作らない（`not_scheduled`）。**この口で承認を経ずに URL を得ることはできない**
* 公開の Data API・API トークン向けの一覧（`social-openapi.test.ts` の `SOCIAL_OPERATIONS`）には入れない（`055` の `manual-outcome` と同じ扱い）

**変えない API**：一括の 3 操作・`approve`・`manual-outcome`・`PATCH`・`DELETE`・`GET /social/posts`。

## 7. 画面

### 7.1 選択（両タブ）

§5.1。選択の列のセルと状態のセルが `cursor: pointer` になり、押すとその行のチェックが切り替わり、帯の「n 件を選択中」も変わる。

### 7.2 送信待ちタブの帯

```text
☑ 3 件を選択中  [一括投稿…]  [一括取り消し…]
```

* 「一括送信（承認）…」と「選んだ手動投稿を順に投稿…」は**出さない**（ユーザー裁定 3）。「一括取り消し…」の出し分け・確認は 054 のまま
* 「一括投稿…」の出し分け：`canApprove || canWrite`。押せるのは `bulkPostPlanOf` の対象が 1 件以上で、一括の処理中でないとき

### 7.3 確認（`Modal`、題「一括投稿」）

```text
┌ 一括投稿 ───────────────────────────────┐
│ 選んだ 6 件のうち、次の 5 件を投稿します。                     │
│ ・自動配信の予約 1 件を今すぐ送ります                          │
│ ・承認待ち 2 件を承認して投稿します（自動 1・手動 1）           │
│ ・手動投稿 3 件を順に投稿画面で開きます                        │
│ ⓘ 手動投稿の投稿画面は 1 件ずつ開きます。SNS で投稿したら窓を閉じて │
│   この画面に戻り、「投稿した」か「投稿しなかった」を選ぶと次が開きます。│
│ 対象外 1 件（配信待ち・配信中 1）                              │
│                               [キャンセル] [投稿する] │
└─────────────────────────────────────┘
```

* 書き出し `BULK_POST_LEAD(選んだ件数, 対象の件数)`。対象の件数＝今すぐ送る＋承認する（自動・手動）＋予約済みの手動
* 行は 0 件のものを出さない。「手動投稿 c 件」の c は予約済みの手動＋承認する手動
* 手動投稿があるときだけ案内（`Alert` の `info`）
* 対象外は `BULK_EXCLUDED_TEXT`（054 の「対象外 n 件（内訳）」）で、内訳は §5.2 の理由の順
* 時機のラジオは無い（即投稿だけ。§5.2）。「投稿する」は対象が 0 件なら `disabled`

### 7.4 実行

「投稿する」の押下で：

1. **同期で**：順に開く先頭が予約済みの手動投稿なら、その URL を `openManualWindow` で開き、その件の段を `opened` にする（§5.4）
2. ダイアログを「処理中」（`Spinner` と「投稿しています…」。× と「投稿する」は無効）にする。手動の窓を開いていれば「1 件目の投稿画面を開きました。」も出す
3. 承認する行があれば `POST /social/posts/bulk/approve`（`{ publishTiming: 'now', items: [{ id, expectedUpdatedAt }] }`。自動・手動を表の順に 1 本で）
4. 今すぐ送る行があれば `POST /social/posts/bulk/publish-now`（054 と同じ本文）
5. 承認できた手動投稿ごとに `GET /social/posts/{id}/manual-handoff` を並行に送る
6. 順に開く対象＝予約済みの手動（表の順）＋ 承認できて URL の取れた手動（表の順）
7. 対象が無ければ、054 の終え方：要求ごと失敗して 1 件も処理していなければ Toast（`danger`）、全件成功なら Toast（`BULK_RESULT_SUCCEEDED`）と読み込み直し、それ以外は終わりの表示（§7.5 の結果の部分だけ）
8. 対象があれば順に投稿（§5.4 の段）へ進む

* 承認を先、今すぐ送るを次（054 §9.5 と同じ。2 本目が要求ごと失敗しても 1 本目の結果は捨てない）
* **部分的な失敗**：項目ごとの失敗（`stale`・`not_applicable`・`approval_required` など）と要求ごとの失敗は 054 の `summarizeBulkResults` で集め、終わりの表示に出す。
  承認に失敗した手動投稿は順に開かない。今すぐ送る・承認の失敗があっても、予約済みの手動投稿の順に投稿は続ける（互いに独立）

### 7.5 順に投稿と終わりの表示（`ManualSequence` を作り直す）

```text
┌ 手動投稿（2 / 3 件目） ──────────────────────────┐
│ X（@torifune）  予約 10/27 10:00                             │
│ 新製品のお知らせです。……（本文の全文）                         │
│ [投稿画面を開く]  別のタブで開く                                │
│ SNS の窓で投稿したら、窓を閉じてこの画面に戻ってください。……   │   ← opened
│ 記録済み 1 件（投稿した 1）                                     │
│                                  [やめる] [記録へ進む] │
└────────────────────────────────────┘
                          ↓ 戻ってくる（または「記録へ進む」）
│ 投稿の URL（任意）[https://          ]                         │   ← returned
│ 選ぶと次の投稿画面が開きます。                                  │
│                    [やめる] [投稿しなかった] [投稿した] │
```

* 本文は全文（`white-space: pre-wrap`・`overflow-wrap: anywhere`）、`note` があれば本文の下（055 のまま）
* 「投稿した」：次の件があれば次の URL を開く（同期）→ `manual-outcome { outcome: 'posted', expectedUpdatedAt, externalUrl? }`。通れば次の件（段は `opened`）、最後なら終わりの表示
* 「投稿しなかった」→ ダイアログの中で確認（055 の文言・「戻る」「失敗にする」）→「失敗にする」で次を開き（同期）→ `manual-outcome { outcome: 'not_posted', expectedUpdatedAt }`
* 保存中はボタンを `disabled`。**記録の失敗**（409・422・404・429・通信の失敗）：その件に `Alert`（`danger`。409 は `MANUAL_SEQUENCE_STALE_MESSAGE`、他はサーバの文言）、ボタンは「飛ばして次へ」「やめる」。
  次の窓を開いていれば、案内「次の投稿画面は開いています。」を添え、「飛ばして次へ」で次の件を `opened` で出す（開き直さない）。開いていなければ `ready`
* 「やめる」（とダイアログの ×）：**まだ記録していない件は何も変えない**（055 裁定 6）。終わりの表示（途中でやめた旨）へ移る
* **終わりの表示**（題「一括投稿の結果」）：
  * 今すぐ送る・承認の成功の内訳（`BULK_RESULT_SUCCEEDED`。054 の効果の表示名）
  * 手動投稿の記録（「投稿した n・投稿しなかった n・飛ばした n」。0 件の結果は書かない）
  * 途中でやめたときは「記録していない手動投稿 n 件は送信待ちに残ります。」
  * 承認したが URL の取れなかった手動投稿（§5.3）と、054 の失敗の一覧（抜粋・理由・文言）
  * 「閉じる」
* 「閉じる」の後：**1 段目（承認・今すぐ送る）で 1 件でも成功したか、「投稿した」「投稿しなかった」を 1 件でも保存した**なら、選択を空にして読み込み直す（Toast は出さない。終わりの表示で伝えた）。

### 12.1 `Table` のセルのクリック（A）

1. どの列にも `onCellClick` を渡さない `Table` の出力（`renderToStaticMarkup`）が今と同じ（`detail` の有無の両方。`cursor` の指定が無い）

### 12.3 一括投稿の振り分け（A。純関数 `bulkPostPlanOf`）

13. 管理者の権限（`canApprove`・`canWrite`）で §5.2 の表の各行のとおり振り分ける：承認待ちの自動 → `approve`、承認待ちの手動 → `approve`（手動）、未来の自動の予約（承認済みを含む）・予約日時の無い自動の予約 → `publishNow`、
    期限の来た自動の予約・配信中 → 対象外 `due_or_publishing`、予約済みの手動（予約時刻の前・後・承認済み）で `handoff.ok` → `manual`、`handoff` が開けない → 対象外 `handoff_unavailable`
14. `canApprove` が無い：承認待ち（自動・手動）と承認済みの未来の自動の予約は `no_approve_permission`、未承認の未来の自動の予約は `publishNow`、手動の予約は `manual`
15. `canWrite` が無い（`canApprove` だけ）：承認待ちの自動は `approve`、承認待ちの手動・未来の自動の予約・手動の予約は `no_write_permission`
16. `manual` は渡した順の予約済みの手動、承認する手動は `approve` の中で渡した順。`approve` は自動・手動を渡した順のまま 1 つの列
17. 対象外は理由ごとの件数で、並びは `no_approve_permission`・`no_write_permission`・`due_or_publishing`・`handoff_unavailable`、0 件の理由を含めない。選択 0 件 → 対象も対象外も 0
18. 承認の本文 `bulkPostApproveRequestBody(rows)` が `{ publishTiming: 'now', items: [{ id, expectedUpdatedAt: row.updatedAt }] }`（渡した順）
19. 承認した手動の対象の組み立て `approvedManualTargetsOf(results, rows, handoffs)`：`ok` の結果で、行が手動のものだけ。`updatedAt`・`scheduledAt` は**結果の `post` の値**、`handoff.ok` のものが対象、
    `ok: false` の `handoff`・取れなかったものは「URL の取れなかった件」として返す。`ok: false` の結果・自動の行は含めない
20. 終わりの表示の要約 `bulkPostOutcomeOf(...)`：054 の `summarizeBulkResults` の成功の内訳と失敗の一覧、記録の件数（投稿した・投稿しなかった・飛ばした）、記録していない件数、URL の取れなかった件。
    「閉じた後に読み込み直すか」は、1 段目の成功が 1 件以上か「投稿した」「投稿しなかった」が 1 件以上のときだけ真

### 12.4 窓の段（A。純関数 `windowStageAfter`）

### 12.5 一括投稿の画面（A。`SocialPending` を描画器・`renderToStaticMarkup` で）

### 12.6 順に投稿（A。`ManualSequence` を描画器で）

29. `ready`：見出し「手動投稿（1 / n 件目）」、本文の全文、「投稿画面を開く」「別のタブで開く」（同じ URL・`rel="noopener noreferrer"`）「記録へ進む」「やめる」。「投稿した」「投稿しなかった」・URL の欄が無い。描画しただけでは `open` が呼ばれない
30. `ready` で「投稿画面を開く」→ `open` が 1 回、段が `opened`：`MANUAL_SEQUENCE_OPENED_GUIDE` と「記録へ進む」があり「投稿した」が無い
31. 「記録へ進む」（`ready`・`opened` から）→ `returned`：URL の欄・「投稿した」「投稿しなかった」「やめる」。次の件があれば `MANUAL_SEQUENCE_NEXT_GUIDE`
32. `returned` で「投稿した」→ 次の件の URL で `open` が 1 回、**`manual-outcome` の要求より先に**呼ばれる。要求は `{ outcome: 'posted', expectedUpdatedAt: 対象の updatedAt }`（URL を入れれば `externalUrl`）。成功で「（2 / n 件目）」が `opened`
33. 「投稿しなかった」→ 確認（055 の文言・「戻る」「失敗にする」）。「戻る」では `open` も要求も無い。「失敗にする」で 32 と同じ順に `open` と `{ outcome: 'not_posted', expectedUpdatedAt }`（`externalUrl` なし）
34. 最後の件の「投稿した」：`open` は呼ばれず、記録の後に終わりの表示
35. 記録が 409：`MANUAL_SEQUENCE_STALE_MESSAGE` と「飛ばして次へ」「やめる」、次の窓を開いていれば `MANUAL_SEQUENCE_NEXT_OPENED`。「飛ばして次へ」で次の件が `opened` で出て、`open` の回数は増えない。409 以外の失敗はサーバの文言
36. 承認した手動投稿の件の `expectedUpdatedAt` は承認の結果の `post.updatedAt`（行の `updatedAt` ではない）
37. 保存中は「投稿した」「投稿しなかった」「やめる」（確認では「戻る」「失敗にする」）が `disabled`
38. 「やめる」→ 終わりの表示に「記録していない手動投稿 n 件は送信待ちに残ります。」。「閉じる」で、記録か 1 段目の成功があれば選択を空にして読み込み直す（`RefreshOnMount` が描かれる）。飛ばしただけで閉じたら読み込み直さず、選択もそのまま
39. 終わりの表示：1 段目の成功の内訳・記録の件数（投稿した・投稿しなかった・飛ばした）・失敗の一覧・「閉じる」。「投稿画面を開く」「投稿した」が無い

### 12.8 取得の口（C）

準備：`055` §13 の偽物の publisher（`manual` を持つ）の provider のアカウント、自動だけの provider のアカウント、管理者・閲覧者・`social.read` の無いロールのセッション、API トークン（`social.read`）。

43. 管理者・閲覧者で予約済みの手動投稿（予約時刻の前・後）→ 200 `{ data: { ok: true, url, note } }`。偽物の `manual()` が呼ばれる
44. 承認待ち・下書き・配信済み・失敗の手動投稿 → 200 `{ data: { ok: false, reason: 'not_scheduled' } }`。`manual()` は呼ばれない
45. 自動配信の投稿 → 422（キー `deliveryMode`）。存在しない UUID・UUID の形でない `{id}` → 404
46. Plugin の無い provider → `{ ok: false, reason: 'unsupported' }`。`manual()` が例外を投げる → `plugin_error`（例外の文言を応答に載せない）
47. 有効な API トークン（Bearer）→ 401。セッションも Bearer も無い → 401。`social.read` の無いセッション → 403
48. 承認待ちの手動投稿を `POST /social/posts/bulk/approve`（`publishTiming: 'now'`）で承認した後に同じ投稿を `GET` → `ok: true` で URL が本文を含む（承認の後に URL が取れる）。承認の前は `not_scheduled`
49. OpenAPI（A）：`GET /social/posts/{id}/manual-handoff` が載り、`operationId` `getSocialPostManualHandoff`、`security` が `[{ session: [] }]`、`x-required-permission` が `social.read`、応答に 200・401・403・404・422・429、
    `description` に「画面（セッション）専用」、200 の `data` が `ok` で分かれる 2 つの形（`reason` の `enum` が 4 つ）

    2 段目（本文）とアカウントのセルを押しても変わらない
51. 投稿タブ：状態のセルを押すとチェックが付く。承認待ちの行の状態のセルのリンク「（送信待ちで承認）」を押すと `/social?pendingStatus=awaiting_approval` へ移る
52. 一括投稿の通し：未来の自動の予約 1・承認待ちの自動 1・予約済みの手動 2（A・B）・承認待ちの手動 1（C）を選び「一括投稿…」→ 確認に「自動配信の予約 1 件」「承認待ち 2 件を承認して投稿します（自動 1・手動 1）」「手動投稿 3 件」→「投稿する」→
    子の窓が 1 つ開き URL の `text` が A の本文 → 子を閉じ、とりふねのページで `blur`・`focus` を起こす →「投稿した」→ 子の窓が 2 つ目（B）→ 閉じて `blur`・`focus` →「投稿しなかった」→「失敗にする」→ 子の窓が 3 つ目（C の本文）→「記録へ進む」→「投稿した」→
    「一括投稿の結果」→「閉じる」。子の窓は合わせてちょうど 3 つ。API で A・C は `published`、B は `failed`（`MANUAL_NOT_POSTED_REASON`）、承認待ちの自動は `scheduled` か `published`、未来の自動の予約は予約日時がいま以前（か `published`）。送信待ちに 5 件とも「承認待ち」「予約済み」で残らず、選択が外れる
53. 戻る前は記録のボタンが出ない：「投稿する」で子の窓が開いた後、ダイアログに「記録へ進む」があり「投稿した」が無い。子の窓の `window.opener` が `null`
54. 途中でやめる：予約済みの手動 3 件で一括投稿 → 1 件目を記録 → 2 件目（`opened`）で「やめる」→ 結果に「記録していない手動投稿 2 件は送信待ちに残ります。」→「閉じる」→ 2・3 件目は送信待ちに残り、選択が外れる
55. 409：予約済みの手動 3 件で一括投稿 → 1 件目を「投稿した」（2 件目の窓が開く）→ API で 2 件目の本文を `PATCH` →「記録へ進む」→「投稿した」→「内容が変わっています。この投稿は飛ばして次へ進めます。」→「飛ばして次へ」→ 3 件目が出る（子の窓は増えない）。2 件目は `scheduled` のまま
56. 承認待ちの自動 2 件だけで一括投稿 →「投稿する」→ 子の窓は開かず、Toast「2 件を処理しました」、2 件が承認待ちでなくなる（`scheduled` か `published`）
57. 幅 375px：一括投稿の確認と順に投稿（`returned`）のダイアログが画面幅に収まり、ページ全体が横へスクロールしない。帯の「一括投稿…」が見える
58. 送信待ちタブの帯に「一括送信（承認）」「選んだ手動投稿を順に投稿」が無く、投稿タブの帯には「一括送信（承認）…」がある（ユーザー裁定 3）
