## 2. 設計上の判断

### 2.1 一覧と件数で同じ条件式を使う

片方だけ直すと「1件も出ないのに total が 100」のような食い違いが起きる。
条件を1つの関数にまとめ、両方から呼ぶ。

### 2.2 並び順に id を足す

並び替えキーが同値のとき順序が揺れる。揺れると**ページ送りで同じ行が2回出たり、
抜けたりする**。最後に `id` を足して安定させる。

### 2.3 `LIKE` のワイルドカードを打ち消す

利用者が入力した `%` や `_` をそのまま渡すと、意図しない広さで一致する。
`ESCAPE` 句とあわせてエスケープする。

### 2.4 UUID でない ID は「見つからない」扱いにする

PostgreSQL は不正な UUID でエラーを返す。そのままだと 500 になる。
**利用者の打ち間違いで 500 を返すのは不適切**なので、リポジトリで形を確かめて `null` を返す。

### 2.5 URL の検証を Domain に置く

`javascript:` や `data:` を通すと、一覧のリンクから任意のスクリプトを実行させられる。
`http` / `https` に限る。

さらに**認証情報つきの URL を拒否する**（`https://user:pass@example.com`）。
保存すると、一覧やログに資格情報が載る。

### 2.6 イベントをトランザクションの外で発火する

購読側（Plugin）の失敗で作成が取り消されると、
**Plugin を入れた瞬間にサイトが作れなくなる**、という壊れ方をする。

`emit` 自体も購読側の例外を握る。二重の防御にする。

### 2.7 UseCase 側でも入力を検証する

API Layer の Zod でも検証しているが、**UseCase を直接呼ぶ経路がある**
（Server Component、Plugin の Data API）。API を通らない経路で検証が抜けると意味がない。

## 4. E2E のテスト設計を見直した

サイトの E2E を足したところ、**ログインの Rate Limit にテストが当たって落ちた**。
テストごとにログインしていたため。

これは製品の不具合ではなく、テストの設計の問題。
`globalSetup` で1回ログインし、`storageState` として共有する形へ変えた。

* テストは既定でログイン済み
* 未認証を試すテストは `clearCookies()` か `Cookie: ''` を使う
* **ログアウトを試すテストは自前でログインする。**
  共有セッションでログアウトすると、サーバー側でそれが失効し、
  他のテストファイルまで巻き添えになる

副次的に、E2E 全体が 1.4 分から 11 秒へ短縮された。

## 5. リスク

| リスク | 対応 |
| --- | --- |
| 一覧のクエリが遅くなる | `status` と `lower(name)` に索引を張った。件数が増えたら実測する |
| `ILIKE` が索引を使えない | 件数が問題になったら全文検索（pg_trgm 等）を検討する |
| Server Component から UseCase を呼ぶ経路で認可が漏れる | `defineUseCase` が必ず検証する。画面側の権限判定は表示制御のみ |
