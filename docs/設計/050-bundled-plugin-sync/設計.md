# 050 同梱 Plugin をコンテナの起動時に plugins の Volume へ反映する — 設計

> 実際の運用環境で見つかった不具合を直す作業単位。コンテナイメージは `VOLUME ["/app/plugins"]` を宣言しており、
> 運用では `/app/plugins` に**名前付き Volume** を付ける。Docker がイメージの中身を Volume へ写すのは **Volume を初めて作ったときだけ**で、
> 後から新しいイメージで起動しても Volume の中の同梱 Plugin は古いまま残る。画面は新しいイメージのビルドに焼き込まれた Manifest を見せるのに、
> 手順書は Volume から読むので「この手順書を読み込めませんでした」になる。さらに Plugin の導入・削除で**コンテナ内の再ビルドが古い Volume の
> ソースから走り、同梱 Plugin のコードと Manifest を黙って古い版へ戻す**。
> **データモデル・HTTP API・OpenAPI・Permission・公開 Plugin API・画面は変えない。** 変えるのはコンテナイメージ（`Dockerfile`）・
> `docker/entrypoint.sh`・`torifune` CLI・レジストリ生成スクリプトと、その文書。
>

## 1. 目的

### 1.1 何が起きるか

1. 同梱 Plugin（`plugins/` に入れてイメージへ焼く Plugin。いまは `example-plugin`・`sns-bluesky`・`sns-instagram`・`sns-threads`・`sns-x-api`・`sns-x-manual`）に
   新しいファイルを足したイメージで、既にある Volume のままコンテナを作り直すと、**画面は新しい Manifest を見せるのに、ファイルは古い**。
   `041` で足した手順書（`help/`）がその例で、`/plugins/<id>/help/<docId>` は「この手順書を読み込めませんでした」になる
2. その状態で、どれかの Plugin を導入・削除すると、**コンテナ内の再ビルドが Volume の古いソースから走る**。同梱 Plugin のコードと Manifest が
   黙って古い版へ戻り、画面からも手順書の宣言が消える。直したはずの不具合が再び出る
3. いまは運用者が Volume を手で直すしかない。直し方は文書に無い

### 1.2 調査の結果（2026-10-02。コードを読んで確かめた）

1. **イメージは `/app/plugins` を Volume にしている。** `Dockerfile:48` の `VOLUME ["/app/plugins"]`。`Dockerfile:13` が `TORIFUNE_PLUGINS_DIR=/app/plugins` を明示する。
   名前付き Volume を付けると、イメージの層にある `/app/plugins` は覆い隠され、**Volume を初めて作ったときに一度だけ**中身が写される（Docker の仕様）
2. **ビルドはイメージの `plugins/` から作られる。** `Dockerfile:41-43` が `pnpm generate:plugins` で `apps/web/src/plugin/generated-registry.ts` を作り、
   各 Plugin の Manifest（JSON をそのまま埋め込む）とコード（静的 import）を `.next` に焼く。画面（`/plugins` の一覧、手順書の目次）は
   `discoverPlugins()`（`apps/web/src/plugin/loader.ts`）経由でこの焼き込まれた Manifest を読む
3. **手順書は要求のたびに Volume から読む。** `application/plugin/plugin-help-use-cases.ts:142` が `readPluginHelpFile(pluginDir(id), doc.path)` を呼び、
   `pluginDir()` は `TORIFUNE_PLUGINS_DIR`（＝Volume）を指す（`plugin/paths.ts`）。焼き込まれた Manifest が宣言する `help/…md` が Volume に無ければ `not_found` になり、
   画面は `ui/help/labels.ts:39` の文言を出す
4. **コンテナ内の再ビルドは Volume から作る。** 導入・削除はアプリが sentinel を書いて終了コード 75 で落ち（`plugin/rebuild.ts`）、`docker/entrypoint.sh:19-41` の
   `rebuild()` が `pnpm build`（`generate:plugins` を含む）を走らせる。`generate-plugin-registry.mjs` は `plugins/`（＝Volume）を走査するので、
   **Volume に残った古い同梱 Plugin がそのままビルドに入る**
5. **同梱 Plugin の版番号は中身が変わっても上がっていない。** 6 つとも `plugin.json` の `version` は `1.0.0` のまま。たとえば `sns-bluesky` は `036` の骨格から
   `041` の手順書の追加まで `1.0.0` で、`git log -p` で `version` の行が変わったことは一度も無い。**版番号を比べても古い写しを見分けられない**
6. **Plugin Package・Registry からの導入は、同梱 Plugin と同じ ID のフォルダへも書く。** `installPluginPackage`・`installFromRegistry`
   （`application/plugin/plugin-use-cases.ts:436`・`:720`）は `extractPackage(inspected, { pluginsDir })` を `overwrite` なしで呼び、
   既存のフォルダの上へファイルを書き足す（`plugin/package.ts:257-274`。消えたファイルは残る）。DB に行があれば `assertUpgradable` が**新しい版だけ**を通す（`:213`）。
   つまり「同梱 Plugin を利用者が Registry の新しい版で更新した」状態は、**同じフォルダの中身が同梱の版と違う**という形で Volume に現れる
7. **隔離マーク**（`.torifune-quarantine`）は再ビルドに失敗した Plugin のフォルダに本体が置く（`plugin/reconcile.ts`）。生成スクリプトはそのフォルダを飛ばす
   （`generate-plugin-registry.mjs:47`）
8. **Plugin の導入状態は DB にある。** `plugins` テーブルに行が無ければ、ファイルがあっても動かない（`plugin/runtime.ts`・`plugin/lifecycle.ts`）。
   削除（`uninstallPluginUseCase`）は行を消し、`deleteFiles` のときだけフォルダも消す（`plugin-use-cases.ts:540`）。
   **フォルダを戻しても、行が無ければ「検出済み」に出るだけで動かない**
9. 生成スクリプトはトップレベルの**ディレクトリ**だけを見る（`:43`）。`plugin.json` が無いディレクトリは飛ばすが、名前が `.` で始まるディレクトリも
   `plugin.json` があれば読む。Plugin ID は `^[a-z][a-z0-9-]{1,63}$`（`packages/plugin-api/src/manifest.ts:81`）なので、`.` で始まるディレクトリが Plugin として動くことは無い
10. **（2026-10-02、T7 の後のコンテナでの検証で判明。記録のみ）同梱 Plugin のフォルダが Volume に無いと、監視ループの中の再ビルドが失敗する。**
    web のビルド（`next build`）は `apps/web/src` の下のテストファイルも型検査し、`apps/web/src/plugin` のテストの一部は同梱 Plugin のソース
    （`../../../../plugins/sns-threads/social` など）を import する。フォルダが無いと `TS2307 Cannot find module` で落ち、`rebuild FAILED - rolling back` になる。
    `050` より前からある問題で、本設計では直さない（扱いはユーザーへ別に上げている）。起動時の同期（§6.5）が消えたフォルダを戻すので、
    **作り直し・再起動の後**の再ビルドは通る。監視ループの再ビルドは同期しない（§6.5・§6.7.3）ので、起動の後に消した場合は次の起動までこの状態が続く（§6.3 の理由 1 (b)）

### 1.3 関連する別の穴：コンテナを作り直すと、利用者が導入した Plugin がビルドから消える

コンテナ内の再ビルドの成果物（`apps/web/.next`）・直前の成功ビルドの退避（`/app/.torifune-build-state`）・sentinel（`/app/.torifune-rebuild-request`）は
**どれもコンテナの書き込み層にあり、Volume に無い**（`entrypoint.sh:12-13`・`:25`）。コンテナを**作り直す**（新しいイメージへの更新、`docker compose up --force-recreate`、
`down` → `up`）と、`.next` はイメージに焼かれたもの、つまり**イメージの `plugins/` だけから作ったビルド**に戻る。`docker restart` のように同じコンテナを起こし直す場合は書き込み層が残るので起きない。

* 利用者が Package・Registry・ローカル配置で導入した Plugin のファイルは Volume に残り、DB の行も `enabled` のまま残る
* ところが新しいビルドにはその Plugin が入っていないので、`discoverPlugins()` に現れず、起動時に有効化されない（`runtime.ts` は焼き込まれたものしか回さない）
* 一覧では「ファイルが見つからない」と出る（`plugin-use-cases.ts:160`。ファイルは実際にはある）。操作記録は閉じているので `reconcileOperations` も何もしない
* 利用者が Registry の新しい版で更新した同梱 Plugin は、**イメージに焼かれた同梱の版のコードで動く**（DB の版は新しいまま）

本設計の同期（§6.2〜§6.6）は**同梱 Plugin のフォルダ**を直すが、この穴は塞がない。同期と同じ「Volume とビルドの突き合わせ」で塞げるので、§6.7 に設計し、
作業単位に含めるかを要裁定とする（§11.1 #1。推奨は含める）。

## 3. スコープ

### やること

1. イメージのビルドで、同梱 Plugin の写しを Volume の外（`/app/.torifune-bundled-plugins`）へ残す。場所を `TORIFUNE_BUNDLED_PLUGINS_DIR` で宣言する（§6.1）
2. CLI に `torifune plugins sync-bundled` を足す。同梱の写しと Volume を突き合わせ、同梱 Plugin のフォルダだけを原子的に更新する（§6.2〜§6.4）
3. CLI に `torifune plugins fingerprint` を足す。Plugin のソースの指紋を出す（§6.7.1）
4. `entrypoint.sh` の最初に同期を 1 回走らせる（§6.5）
5. **（要裁定 #1 の (a) のとき）** 起動時に Volume の指紋と、いまのビルドの指紋を比べ、食い違えば最初の起動の前に 1 回だけ再ビルドする。
   ビルドが成功したら、そのビルドの指紋を `.next` の中に書く（§6.7）
6. `generate-plugin-registry.mjs` が名前が `.` で始まるディレクトリを飛ばす（同期の作業用ディレクトリをビルドへ入れないため。§6.4.3）
7. コンテナでの検証スクリプト `scripts/verify-bundled-plugin-sync.sh` を足し、CI の `container` ジョブで走らせる（§10.6）
8. 文書（運用手順・`plugins/README.md`・`012` 設計・決定事項ほか）を書き戻す。既存の運用環境向けの注記を書く（§12）

### やらないこと（理由つき）

* **利用者が導入した Plugin のフォルダを書き換えない・消さない。** 裁定のとおり。同梱 Plugin の ID でも、利用者が中身を変えたもの（Package での更新・手での編集）には触れない（§6.3）
* **DB を読まない・書かない。** 同期はアプリより前に、DB に繋がずに走る。導入状態（`plugins` の行・版）は変えない。DB の版と Manifest の版のずれは §11.2 の 2 に記録する
* **同梱から外れた Plugin を消さない。** 新しいイメージに無くなった同梱 Plugin のフォルダは、利用者が使い続けているかもしれないので残す（§6.3 の 7）
* **同梱 Plugin の版番号の付け方を変えない。** 同期は版番号に頼らずハッシュで判定する（§6.2）。版を上げる運用の提案は §11.2 の 1
* **同じ Volume を複数のコンテナで共有する構成を支えない。** 再ビルド（D-02）が既に「plugins の Volume 1 つにコンテナ 1 つ」を前提にしている（§13 R5）
* **開発環境（`pnpm dev`）・ホストで直接動かす構成は変えない。** `plugins/` がリポジトリそのもので、`git pull` で同梱 Plugin が更新される。同期の写しの場所が無ければ同期は何もしない（§6.5）
* **アプリの画面・一覧の文言（「ファイルが見つからない」）は変えない。** §6.7 を入れれば実際には起きなくなる。§11.2 の 3
* **起動時の再ビルドに失敗した原因の Plugin を自動で隔離しない。** どの Plugin が壊したかを起動時には特定できない（§6.7.4・§11.2 の 4）

## 6. 仕組み（決めたこと）

### 6.1 同梱の写し（正）

* `Dockerfile` は、`COPY . .` と `pnpm generate:plugins` ／ CLI ／ web のビルドの**後**、`VOLUME` の**前**に、`/app/plugins` を `/app/.torifune-bundled-plugins` へ写す（`cp -a`）
* `ENV TORIFUNE_BUNDLED_PLUGINS_DIR=/app/.torifune-bundled-plugins` を宣言する
* **「同梱 Plugin」とは、この写しのトップレベルにある、名前が `.` で始まらないディレクトリ**のこと。イメージを作る人が `plugins/` に自分の Plugin を足してビルドすれば、
  それも同梱 Plugin として扱われる（自前のイメージを配る正当な使い方）
* 焼き込まれたビルド（`.next`）は同じ `/app/plugins` から作るので、**写しとビルドは同じソースから出来ている**（#43 で固定する）
* 版の一覧のような別のファイルは作らない。写しそのものが一覧で、ハッシュは同期のたびに写しから計算する（6 個・数百 KB で、計算は一瞬）。
  一覧を別に持つと写しとずれる余地が生まれる

### 6.2 見分け方：同期の印と中身のハッシュ

#### 6.2.1 木のハッシュ（`hashPluginTree(dir)`）

フォルダの中身を 1 つの値にする。同梱の写しと Volume のフォルダを比べるのに使う。

* 対象：フォルダの下を再帰的にたどった**通常のファイル**と**シンボリックリンク**。ディレクトリそのもの・空のディレクトリ・それ以外の種別（FIFO など）は含めない
* 除くもの：**フォルダの直下にある** `.torifune-bundled` と `.torifune-quarantine`（本体と同期が置く印。下の階層にある同名のファイルは除かない）
* 各項目を `<種別>\0<相対パス>\0<SHA-256 の 16 進>\n` にする。種別はファイルが `f`（中身のハッシュ）、シンボリックリンクが `l`（**リンク先の文字列のハッシュ。辿らない**）。
  相対パスの区切りは `/`
* 項目を相対パスの昇順（JavaScript の文字列比較）に並べて連結し、SHA-256 を取って `sha256:<16 進>` にする
* 実行ビット・所有者・時刻は含めない

#### 6.2.2 同梱の印（`.torifune-bundled`）

同期が同梱 Plugin のフォルダを書いた（または、イメージと同じだと確かめた）ときに、そのフォルダの直下に置く。

```json
{
  "schema": 1,
  "note": "Torifune が同梱 Plugin の更新に使う印。このフォルダの中身を変えると、以後このフォルダは自動では更新されない。",
  "hash": "sha256:<同期が書いた時点の木のハッシュ>",
  "version": "<同期が書いた時点の plugin.json の version>",
  "syncedAt": "<ISO 8601>"
}
```

* **有効な印**：JSON として読めて、`hash` が `^sha256:[0-9a-f]{64}$` に合うもの。読めない・形が違う印は「印が無い」として扱う（判定表の #6〜#8）
* **印が中身と一致する**（木のハッシュ＝印の `hash`）なら、そのフォルダは**同期が書いたまま誰も触っていない**。一致しなければ、同期の後に誰かが中身を変えた
  （Package・Registry での更新、手での編集）
* 印は Plugin の**フォルダの中**に置く。中央の台帳にしないのは、置き換え（§6.4）で中身と印を**同じ rename で一緒に**入れ替えられるから。
  台帳だと中身と台帳の書き込みの間で落ちたときに食い違う
* Package の展開（`extractPackage`）は既存のフォルダの上へ書き足すので、利用者が同梱 Plugin を Package で更新しても印は残り、中身だけが変わる → 「一致しない」になる（§1.2 の 6）

### 6.3 判定表（同梱 Plugin の ID ごと）

同梱の写しにある ID ごとに、Volume の `<plugins>/<id>` を見て、**上から順に最初に当たった行**の処理をする。
`H` = Volume のフォルダの木のハッシュ、`I` = 同梱の写しの木のハッシュ、`M` = 有効な印の `hash`。

| # | Volume の状態 | 処理 | ログの結果 |
| --- | --- | --- | --- |
| 1 | フォルダが無い | 写しを置く（印つき）。§6.4 | `restored` |
| 2 | 隔離マーク（`.torifune-quarantine`）がある | 何もしない | `skipped: quarantined` |
| 3 | `H = I` | 中身は触らない。印が無い・`M ≠ I` なら印だけ書く | 印を書けば `adopted`、そうでなければ `unchanged` |
| 4 | 有効な印があり `H = M`（`≠ I`） | 写しで置き換える（印つき）。退避しない。§6.4 | `updated` |
| 5 | 有効な印があり `H ≠ M`（`≠ I`） | 何もしない | `skipped: modified` |
| 6 | 印が無く、`plugin.json` が読めない・`version` が文字列でない | 何もしない。警告 | `skipped: unreadable manifest` |
| 7 | 印が無く、Volume の `version` がイメージの `version` より新しい | 何もしない | `skipped: newer version <Volume の版> installed` |
| 8 | 印が無く、Volume の `version` がイメージと同じか古い | 中身を退避してから写しで置き換える（印つき）。§6.3 の補足・§6.4 | `updated: legacy (backup: .torifune-bundled-backup/<id>)` |

加えて、同梱の写しに**無い** ID の扱い：

| # | Volume の状態 | 処理 | ログ |
| --- | --- | --- | --- |
| 9 | 有効な印がある（以前は同梱だった） | 何もしない | `kept: no longer bundled` |
| 10 | 印が無い（利用者の Plugin） | 何もしない | 個別には出さず、要約の `untouched` に数える |

各行の理由：

1. **消えたフォルダは戻す。** 区別のつかない 2 つの場合がある。(a) 新しいイメージで**初めて同梱された** Plugin、(b) 利用者が削除で**ファイルごと消した**同梱 Plugin。
   (a) は置かなければ直らない。(b) を戻しても DB に行が無いので「検出済み」に出るだけで動かない（§1.2 の 8）。しかも同梱 Plugin は**イメージに焼かれたビルドに必ず入っている**ので、
   今でもコンテナを作り直せば（ファイルが無いまま）「検出済み」に出る。戻すことでファイルとビルドが揃う。「消したものを覚えておく」墓標は作らない（戻す手段が要り、仕組みが増える）。
   DB の行が残っていてファイルだけ無い（手で消した）場合は、戻すことで Plugin が再び動く。
   **注（2026-10-02、記録のみ）**：(b) で消してから次の起動までの間は、監視ループの中の再ビルド（他の Plugin の導入・削除）が失敗する。
   web のビルドが、同梱 Plugin のソースを import するテストファイルも型検査するため（§1.2 の 10。`050` より前からの問題で、本設計では直さない）
2. **隔離されたものは触らない。** 隔離マークは「原因を調べるためにファイルを残す」約束（`012` §7.2）。置き換えると調べられなくなる。運用者がマークを消せば、次の起動で通常の判定に戻る
3. **中身が同梱と同じなら印を付けて管理下に入れる。** Docker が Volume を初めて作ったときに写した中身（印が無い）も、ここで印が付く
4. **同期が書いたまま誰も触っていないものだけ、黙って更新する。** 利用者の変更が無いことを印で確かめられるので、退避は要らない
5. **同期の後に中身が変わったものは利用者のもの。** Package・Registry での更新（新しい版）も、手での編集もここに入る。裁定「利用者が導入した Plugin には触れない」をここで守る。
   **同梱の版に戻したいときは、フォルダを消して再起動する**（→ #1 で戻る。§12 の運用手順に書く）
6. **印の無い古い Volume（`050` より前に作られた Volume）は、版番号で補う。** 中身と同梱が違うとき、それが「古いイメージの同梱 Plugin」なのか「利用者が入れたもの」なのかは印では分からない。
   * Volume の版が**新しい**なら、利用者が Package・Registry で更新したもの（同梱の版を上回る版は同梱からは来ない）→ 触らない（#7）。**版を下げない**
   * 版が**同じか古い**なら、古いイメージから写された同梱 Plugin とみなして置き換える（#8）。同梱 Plugin の版は上がってこなかった（§1.2 の 5）ので、実際の古い写しはすべて「同じ」に当たる。
     利用者が `050` より前に同梱 Plugin のファイルを手で編集していた場合もここに入るので、**置き換える前に退避する**（#8。§6.3 の補足）
   * `plugin.json` が読めないものは判断の材料が無いので触らない（#6）。運用者はログを見て、フォルダを消せば #1 で戻る
7. **同梱から外れた Plugin は残す。** 利用者が有効にして使い続けているかもしれない。消すと「ファイルが見つからない」になる。以後は利用者のものとして扱う（印は残るが、同梱の写しに無い ID の印は見ない）

**補足：退避（#8）**

* 置き換える前の中身を `<plugins>/.torifune-bundled-backup/<id>/` へ移す（同じファイルシステムの中の rename）。**ID ごとに最新の 1 つだけ**残し、前の退避は消す
* #4 では退避しない（中身は以前のイメージの同梱そのもので、利用者の変更は無い）
* 退避のディレクトリ名は `.` で始まるので、生成スクリプトも指紋も読まない（§6.4.3・§6.7.1）

### 6.4 置き換えの手順（原子性）

#### 6.4.1 手順

対象 `<plugins>/<id>`（以下 `D`）を写し `S` で置き換える（#1・#4・#8）。作業用のパスは `T = <plugins>/.torifune-sync-<id>.tmp`、`O = <plugins>/.torifune-sync-<id>.old`。

1. `T` があれば消す。`S` を `T` へ再帰的に写す
2. `T` の木のハッシュが `I` と等しいことを確かめる（写しの途中で欠けていないか）。等しくなければ `T` を消して失敗
3. `T/.torifune-bundled` に印（`hash = I`、`version` は `S/plugin.json` の版）を書く
4. `D` があれば：#8 なら退避先（既存の退避を消してから）へ、#4 なら `O`（あれば消してから）へ、`D` を rename する
5. `T` を `D` へ rename する。失敗したら、4 で動かしたものを `D` へ rename して戻し、`T` を消して失敗
6. `O` があれば消す

* **rename は同じファイルシステムの中で原子的。** 作業用・退避のディレクトリを Volume の中（`<plugins>` 直下）に置くのはそのため。POSIX の rename は空でないディレクトリの上へ上書きできないので、4 と 5 の 2 段にする
* **どこで失敗しても、`D` は古い中身のまま残るか、新しい中身になっているかのどちらか。** 半分だけ書き換わった `D` は生じない
* 4 と 5 の間でプロセスが落ちると `D` が無い状態が残る。次の起動の同期は #1（フォルダが無い）で写しを置くので直る。#8 の退避は残る

#### 6.4.2 前回の残骸の片付け

同期の最初に、`<plugins>` 直下の `.torifune-sync-*.tmp` と `.torifune-sync-*.old` を消す。どちらも利用者の中身を含まない（`.old` に入るのは #4 の「同梱そのもの」だけで、利用者の中身は退避先へ行く）。

#### 6.4.3 生成スクリプトが `.` で始まるディレクトリを飛ばす

`generate-plugin-registry.mjs` の走査（`:42-44`）で、名前が `.` で始まるディレクトリを飛ばす。

* 作業用の `T` は `plugin.json` を持つので、万一ビルドと重なるとビルドに入ってしまう。同期はビルドより前に終わり、残骸も片付ける（§6.4.2）が、二重の守りとして入れる
* Plugin ID は `.` で始まれない（§1.2 の 9）ので、今まで読めていた Plugin が読めなくなることは無い

### 6.5 いつ・どこで走るか

`entrypoint.sh` の監視ループに入る**前に 1 回**。

```sh
PLUGINS_DIR="${TORIFUNE_PLUGINS_DIR:-/app/plugins}"
BUNDLED_DIR="${TORIFUNE_BUNDLED_PLUGINS_DIR:-}"
CLI="${TORIFUNE_CLI_CMD:-node /app/packages/cli/dist/main.js}"

if [ -n "$BUNDLED_DIR" ]; then
  if ! $CLI plugins sync-bundled --bundled-dir="$BUNDLED_DIR" --plugins-dir="$PLUGINS_DIR"; then
    echo "[torifune] bundled plugin sync FAILED - continuing with the current plugins" >&2
  fi
fi
```

* **起動のたびに走る**（作り直しでも `docker restart` でも）。イメージはコンテナが動いている間に変わらないので、起動時の 1 回で足りる。同期の後の再ビルドは必ず更新済みのソースを使う
* **アプリが動く前**なので、同期中に Plugin のファイルを読んでいる処理は無い（`.next` は Volume のファイルを手順書の読み込みのときしか触らない）
* **同期が失敗しても起動は止めない。** 失敗した ID は置き換え前のまま（§6.4）で、`050` より前と同じ状態で動く。Torifune 全体を止めるほどの理由にならない（`runtime.ts` が
  「Plugin ひとつの不具合で全体を止めない」としているのと同じ考え）
* `TORIFUNE_BUNDLED_PLUGINS_DIR` が空・未設定、または指す先が無いときは何もしない（イメージの外で entrypoint を使う場合）
* `TORIFUNE_CLI_CMD` はテストでスタブへ差し替えるための口（既存の `TORIFUNE_START_CMD`・`TORIFUNE_BUILD_CMD` と同じ流儀）

### 6.6 CLI

#### 6.6.1 `torifune plugins sync-bundled`

```text
torifune plugins sync-bundled [--bundled-dir=<path>] [--plugins-dir=<path>]
```

* 既定値：`--bundled-dir` は `$TORIFUNE_BUNDLED_PLUGINS_DIR`、`--plugins-dir` は `$TORIFUNE_PLUGINS_DIR`（空・未設定なら `/app/plugins`）
* 同梱の場所が空・存在しない → `[torifune] bundled plugins: no bundled directory, skipped` を出して終了コード 0
* plugins の場所が無い → 作る（空の Volume・ホストのディレクトリを付けた場合。全部が #1 で置かれる）
* 未知のオプション → 既存のコマンドと同じく、エラーと使い方を出して終了コード 1
* **終了コード**：すべての ID を処理できたら 0（`skipped` を含む）。1 つでも I/O で失敗したら 1。**失敗した ID があっても残りの ID は処理する**
* 判定（§6.3）は**純関数**（Volume と写しの観測値 → 処理）に切り出し、ファイルシステムへの適用（§6.4）と分ける。適用はファイル操作を差し替えられるようにする（失敗の注入のため。#29・#30）

#### 6.6.2 ログ

標準出力に、同梱の写しにある ID ごとに 1 行と、最後に要約を 1 行。`docker logs` で読む前提で、接頭辞は entrypoint と同じ `[torifune]`。

```text
[torifune] bundled plugins: example-plugin unchanged
[torifune] bundled plugins: sns-bluesky updated: legacy (backup: .torifune-bundled-backup/sns-bluesky)
[torifune] bundled plugins: sns-threads restored
[torifune] bundled plugins: sns-x-manual skipped: modified
[torifune] bundled plugins: old-bundled kept: no longer bundled
[torifune] bundled plugins: summary updated=1 restored=1 adopted=0 unchanged=1 skipped=1 kept=1 failed=0 untouched=2
```

* `updated` の行には、置き換え前と後の木のハッシュの先頭 12 桁を添えてよい（実装で決める）
* 失敗は標準エラーに `[torifune] bundled plugins: <id> FAILED: <理由>` を出す。理由は OS のエラーコード（`ENOSPC` など）までとし、スタックは出さない
* 利用者の Plugin（#10）は ID を出さず件数だけ（`untouched`）

#### 6.6.3 `torifune plugins fingerprint`

```text
torifune plugins fingerprint [--plugins-dir=<path>]
```

§6.7.1 の指紋を標準出力に 1 行（`sha256:<64 桁>` と改行）で出す。読めないファイルがあれば標準出力には何も出さず、標準エラーに理由を出して終了コード 1。

#### 6.6.4 使い方の表示

`usage()` に `plugins sync-bundled` と `plugins fingerprint` を足す。`COMMANDS` に `plugins` を足し、サブコマンドが無い・未知なら使い方を出して終了コード 1。

### 6.7 起動時の突き合わせと再ビルド（§1.3 の穴。要裁定 #1 の (a) のとき）

#### 6.7.1 指紋（`fingerprintPlugins(pluginsDir)`）

「ビルドに入りうる Plugin のソース全体」を 1 つの値にする。

* 対象：`<plugins>` のトップレベルの**ディレクトリ**のうち、名前が `.` で始まらず、直下に `.torifune-quarantine` が無いもの（生成スクリプトが走査する範囲と同じ。
  `plugin.json` や `index.ts` の有無では絞らない。絞らなくても、そうしたディレクトリはビルドの後の指紋にも同じく入るので食い違わない）
* 対象ごとに `<ディレクトリ名>\0<木のハッシュ（§6.2.1）>\n` を作り、名前の昇順に連結して SHA-256 を取る → `sha256:<16 進>`
* トップレベルのファイル（`plugins/README.md` など）は含めない
* 木のハッシュが印（`.torifune-bundled`）と隔離マークを除くので、**同期が印を書いても指紋は変わらない**

#### 6.7.2 ビルドの指紋をビルドと一緒に置く

* **ビルドの指紋は `.next` の中**（`apps/web/.next/torifune-plugin-sources`）に置く。`rebuild()` の巻き戻しは `.next` をまるごと写し戻す（`entrypoint.sh:23-39`）ので、
  **指紋も自動でビルドと一緒に戻る**。別の場所に置くと巻き戻しのたびに合わせ直す必要がある
* `Dockerfile`：ビルドの後に `fingerprint --plugins-dir=/app/plugins` の出力を書く。焼いたビルドの指紋になる
* `entrypoint.sh` の `rebuild()`：**ビルドの前に**指紋を計算して覚えておき、**ビルドが成功したら**書く。失敗したら書かない（巻き戻しで前の指紋が戻る）。
  ビルドの最中はアプリが落ちているので、計算からビルドまでの間にソースが変わることは無い。指紋の計算に失敗したら、ビルドはするが指紋は書かない（次の起動で食い違いとして扱われる）

#### 6.7.3 起動時の判定

同期（§6.5）の後、監視ループの前に 1 回。

| 条件 | 処理 | ログ |
| --- | --- | --- |
| sentinel がある | sentinel を消し、再ビルドを 1 回 | 既存の `[torifune] rebuilding after plugin change...` |
| いまの指紋を計算できない | 再ビルドしない | `[torifune] could not fingerprint plugins - starting with the current build`（標準エラー） |
| ビルドの指紋が無い、またはいまの指紋と違う | 再ビルドを 1 回 | `[torifune] plugin sources differ from the build - rebuilding before start` |
| 同じ | 何もしない | 出さない |

* 再ビルドは既存の `rebuild()`（失敗したら直前の成功ビルドへ戻す）をそのまま使う。**起動時の再ビルドは多くても 1 回**（sentinel と食い違いが重なっても 1 回）
* 監視ループの中の再ビルド（sentinel による。`entrypoint.sh:43-47`）は**今までどおり指紋を見ずに必ず走る**。既に Volume にある Plugin を導入する場合
  （`verify-container-rebuild.sh` の #32 の `install-example`）は、指紋で間引くと再ビルドされず、検証の約束（BUILD_ID が変わる）が崩れる
* 結果として、**新しいイメージ + 同梱 Plugin だけの Volume** は、同期の後の Volume がイメージと同じになるので**再ビルドしない**（起動の時間は今と同じ）。
  利用者の Plugin がある Volume は、作り直しのたびに 1 回再ビルドする（§13 R2）

#### 6.7.4 起動時の再ビルドが失敗したとき

* `rebuild()` が直前の成功ビルド（＝イメージに焼かれたビルド）へ戻し、そのまま起動する。利用者の Plugin はビルドに入らない（`050` より前と同じ状態）。標準エラーに既存の
  `rebuild FAILED - rolling back to the last good build` が出る
* 操作記録は無いので `reconcileOperations` は何もせず、隔離もしない（どの Plugin が壊したかを特定できない。§11.2 の 4）
* 指紋は食い違ったままなので、**次の起動でもう一度試す**（起動のたびに 1 回。落ち続けるループにはならない）

### 6.8 互換性

| 対象 | 影響 |
| --- | --- |
| HTTP API・OpenAPI・Permission・画面 | 変わらない |
| 公開 Plugin API・Manifest | 変わらない（§9）。Plugin のフォルダに `.torifune-bundled` が置かれることがあるが、Plugin のコードはそれを読まない |
| DB | 変わらない（マイグレーション無し） |
| 既存の Volume（`050` より前） | 最初の起動で、古い同梱 Plugin が置き換わる（退避つき）。利用者の Plugin・版が新しいものは触らない。**手での復旧は要らない**（§12.2） |
| 新しく作る Volume | Docker が写した中身に印が付くだけ（判定表の #3、`adopted`）。再ビルドしない |
| ホストのディレクトリを付けた構成（bind mount） | Docker は中身を写さないので、今まで空のままだった。今後は同期が同梱 Plugin を置く |
| 開発環境・ホストで直接動かす構成 | 変わらない（同梱の写しの場所が無いので同期しない。`entrypoint.sh` を使わない） |
| 利用者の Plugin がある環境で、コンテナを作り直したとき（§6.7） | 今までは利用者の Plugin が黙って動かなくなっていた。今後は起動前に 1 回再ビルドする（数分かかる。§13 R2） |
| `verify-container-rebuild.sh`（#30〜#33） | 変わらない。初回の起動は Volume がイメージと同じなので再ビルドせず、BUILD_ID の比較の前提が保たれる（#45） |

## 7. 画面

変えない。同期の結果は画面に出さない（運用者は `docker logs` で見る）。
同期の後は、手順書（`/plugins/<id>/help/<docId>`）が焼き込まれた Manifest のとおりに読めるようになる。

## 8. 権限（Permission）

変えない。同期と突き合わせはアプリの外（コンテナの起動手順）で、利用者の操作でも HTTP の経路でもない。
同期はコンテナの中の `/app/plugins` に書く権限（今もアプリと再ビルドが持つもの）だけで動く。新しい秘密情報は扱わない。

## 9. Plugin API への影響

**無い。** `packages/plugin-api` を変えない。`PLUGIN_API_VERSION` は `1` のまま。

* Plugin のフォルダの直下に `.torifune-bundled` が置かれる（同梱 Plugin のみ）。`.torifune-quarantine` と同じく本体の印で、Plugin は読まない・書かない。
  `docs/Plugin開発ガイド.md` に、名前が `.torifune-` で始まるファイルは本体が使うことを書く（§12）
* Plugin の作者から見た変化：同梱 Plugin を Volume の中で直接編集すると、以後その Plugin は自動で更新されなくなる（§6.3 の 5）

## 10. 受け入れ条件

番号は実装プラン・テストで参照する。**A = 単体（Vitest。`packages/cli`、一時ディレクトリ）、B = 単体（`apps/web` 側から CLI を読む突き合わせ）、
S = シェル（`entrypoint.sh` をスタブで動かす Vitest。`sh` の無い環境では飛ばす）、C = コンテナ（`scripts/verify-bundled-plugin-sync.sh`）、E = 静的検査。**

* 「写し」「Volume」：テストが一時ディレクトリに作る同梱の写しと plugins のディレクトリ
* 「印が一致」：`.torifune-bundled` の `hash` が、そのフォルダの木のハッシュと等しい
* **§6.7 に属する条件（#36〜#42、#43 のうち `.next/torifune-plugin-sources` の比較、#48 の後半、#49 の最後の文）は、要裁定 #1 で (a) 以外が選ばれたら外す**

### 10.1 木のハッシュと指紋（A）

1. 同じファイル（パス・中身）を別の順序で作った 2 つのフォルダは、木のハッシュが等しい。形は `^sha256:[0-9a-f]{64}$`
2. ファイルの中身を 1 バイト変える・ファイルを足す・消す・名前を変える・下の階層へ動かす、のどれでも木のハッシュが変わる
3. フォルダ直下の `.torifune-bundled`・`.torifune-quarantine` を足しても変えても木のハッシュは変わらない。**下の階層**にある同名のファイルは変わる
4. 空のディレクトリを足しても変わらない。シンボリックリンクはリンク先の文字列で数え、**辿らない**（フォルダの外を指すリンクでも外のファイルを読まない。リンク先の文字列を変えると変わる）。シンボリックリンクを作れない環境では飛ばす
5. 指紋：トップレベルの通常のディレクトリを足す・その中のファイルを変えると変わる。`.` で始まるディレクトリ・隔離マークのあるディレクトリ・トップレベルのファイルを足しても変わらない。各フォルダに印を書いても変わらない
6. 指紋は、ディレクトリの列挙順に依らず同じ値になる（同じ中身を別の順に作った 2 つの plugins で等しい）

### 10.2 判定表（A。純関数）

7. フォルダが無い → `restored`（§6.3 #1）
8. 隔離マークがある → `skipped: quarantined`。`H = I` でも、有効な印があっても同じ（#2 が #3 より先）
9. `H = I` で印が一致（`M = I`）→ `unchanged`、書き込みなし。`H = I` で印が無い・`M ≠ I`・印が壊れている → `adopted`（印だけ書く）
10. 有効な印、`H = M ≠ I` → `updated`（退避なし）
11. 有効な印、`H ≠ M`、`H ≠ I` → `skipped: modified`
12. 印なし、Volume の `version` が新しい（`1.1.0` 対 `1.0.0`、`1.10.0` 対 `1.9.0`）→ `skipped: newer version …`
13. 印なし、版が同じ（`1.0.0` 対 `1.0.0`、`1.2` 対 `1.2.0`）・古い → `updated: legacy`（退避あり）
14. 印なし、`plugin.json` が無い・JSON でない・`version` が文字列でない → `skipped: unreadable manifest`
15. 印が JSON でない・`hash` の形が違う（`sha256:` の無い値、63 桁）→ 印なしとして 12〜14 の判定になる
16. 同梱の写しに無い ID で、有効な印がある → `kept: no longer bundled`。印が無い → `untouched` に数え、行を出さない

### 10.3 適用（A。一時ディレクトリ）

17. `restored`：`D` ができ、木のハッシュが `I`、印の `hash` が `I`・`version` が写しの版。`.torifune-sync-*` が残らない
18. `updated`（印つき）：写しで消えたファイルは `D` から消え、足したファイルは現れる（足し合わせにならない）。印が新しい `I`。退避は作られない
19. `updated: legacy`：退避先 `.torifune-bundled-backup/<id>` の木のハッシュが置き換え前の `H` と等しい。同じ ID をもう一度 legacy で置き換えると、退避は**新しい方の 1 つだけ**になる
20. **（B）** CLI の版の比較と `apps/web/src/domain/plugin/version-order.ts` の `compareVersions` が、表（`1.0.0`/`1.0.0`、`1.2`/`1.2.0`、`1.10.0`/`1.9.0`、`2.0.0`/`1.99.99`、`1.0.0-beta`/`1.0.0`、`abc`/`0.0.0`）のすべてで同じ符号を返す
21. 利用者の Plugin（写しに無い ID、印なし）は、同期の前後で木のハッシュが等しく、印が足されない
22. `skipped: modified`・`skipped: newer version`・`skipped: unreadable manifest`・`skipped: quarantined`・`kept` のフォルダは、前後で木のハッシュも印の中身も（印があれば `syncedAt` も）変わらない
23. 冪等：同期を 2 回続けて走らせると、2 回目はすべての同梱 ID が `unchanged`（または `skipped`/`kept`）で、どのフォルダの木のハッシュも印の `syncedAt` も変わらない
24. 同梱の場所が空・存在しない → 何もせず終了コード 0、`no bundled directory` の行を出す
25. plugins の場所が存在しない → 作られ、すべての同梱 ID が `restored`
26. ログ：写しの ID ごとに 1 行（§6.6.2 の形）と要約 1 行。要約の各件数が判定の結果と一致する。利用者の Plugin の ID はログに出ない
27. CLI：`plugins sync-bundled --unknown` は終了コード 1 と使い方。`plugins` だけ・`plugins foo` も終了コード 1。`plugins fingerprint` は 1 行（`sha256:` + 64 桁 + 改行）を出して 0
28. `--bundled-dir`・`--plugins-dir` を省くと `TORIFUNE_BUNDLED_PLUGINS_DIR`・`TORIFUNE_PLUGINS_DIR` を使う。`TORIFUNE_PLUGINS_DIR` が空なら `/app/plugins`（`run()` に渡す `env` で確かめる）

### 10.4 失敗と残骸（A。ファイル操作を差し替えて失敗を注入する）

29. 写し（§6.4.1 の 1）の途中で失敗 → `D` の木のハッシュは前のまま、`T` は残らない、その ID は `FAILED`、**他の ID は処理され**、終了コードは 1
30. 最後の rename（5）で失敗 → 4 で動かした中身が `D` に戻り（木のハッシュが前と等しい）、`T` は残らない、終了コード 1
31. 写した `T` の木のハッシュが `I` と違う（写しが欠けたことを注入）→ 置き換えず、`D` は前のまま、`FAILED`
32. 前回の残骸：`.torifune-sync-<id>.tmp` と `.torifune-sync-<id>.old` があり `D` が無い → 残骸は消え、`D` は写しで `restored`。退避（`.torifune-bundled-backup`）は残る
33. `FAILED` の行の理由に、絶対パスやスタックトレースを含めない（OS のエラーコードまで）

### 10.5 entrypoint（S。`TORIFUNE_CLI_CMD`・`TORIFUNE_BUILD_CMD`・`TORIFUNE_START_CMD` をスタブにし、`.next`・状態・sentinel の場所を一時ディレクトリへ向ける）

## 11. 未決事項

### 11.1 要裁定

**#1 起動時の突き合わせと再ビルド（§6.7）を `050` に含めるか**

§1.3 の穴（コンテナを作り直すと、利用者が導入した Plugin がビルドから消えて動かなくなる）は、裁定の範囲（同梱 Plugin の更新）の外にある、`050` より前からの不具合。
同期だけでは塞がらない。範囲を広げる判断なので裁定を仰ぐ。

| 選択肢 | 結果 |
| --- | --- |
| **(a) `050` に含める（推奨）** | 同期と同じ起動手順・同じハッシュで作れ、コンテナでの検証（#48・#49）も同じスクリプトに載る。作り直しても利用者の Plugin が動き続け、Registry で更新した同梱 Plugin も更新した版のコードで動く。代わりに、**利用者の Plugin がある環境では作り直しのたびに起動前の再ビルド（数分・1〜2GB のメモリ）**が入る（§13 R2）。同梱 Plugin だけの環境は再ビルドしない |
| (b) 別の作業単位に分ける | `050` は同期だけで終わる（#36〜#42・#43 のうち `.next` の指紋の比較・#48 の後半・#49 の最後の文を外す。`fingerprint` のコマンドは #43 の前半の検査に使うので残す）。それまでの間、利用者の Plugin がある環境では、更新のたびに Plugin を導入し直す（再ビルドを起こす）運用が要る。運用手順にそう書く |
| (c) 直さない | (b) の運用を恒久のものとして文書にする |

**ユーザー裁定（2026-10-02）：(a) `050` に含める。**

推奨は (a)。理由：同期を入れると「新しいイメージへ更新すれば Plugin のファイルが揃う」と運用者は期待するが、利用者の Plugin だけが黙って止まる状態が残る。
しかも §6.7 が無いと、Registry で新しい版にした同梱 Plugin が、作り直しのたびにイメージの古い版のコードで動く（版を下げないという約束を、ファイルではなく実行のほうで破る）。

### 11.2 設計で決めず、後の判断に回すもの（記録のみ）

1. **同梱 Plugin の版を、中身を変えたら上げるか**：同期はハッシュで判定するので要らない。ただし DB の版・Registry の互換判定・Package の `assertUpgradable` は版を見るので、
   上げたほうが運用者に変化が伝わる。上げる場合は `docs/Plugin開発ガイド.md` の版の節に同梱 Plugin の約束として書く
2. **DB の `plugins.version` と Manifest の版のずれ**：同期で同梱 Plugin の版が上がっても、`plugins` の行の版は導入した時のまま。一覧は Manifest の版を見せるので見た目は正しいが、
   Registry の互換判定（`evaluateRegistryEntry`）は行の版を使う。起動時に行の版を Manifest へ合わせるかは、`install()` の呼び直し（`020` §2.5）との関係を含めて別に決める
3. **一覧の「ファイルが見つからない」**：ビルドに入っていないだけでファイルはある場合も同じ文言になる（§1.3）。§6.7 を入れれば実際には起きなくなる。(b)・(c) を選ぶなら文言を直す価値がある
4. **起動時の再ビルドを壊した Plugin の特定と隔離**：操作記録が無いので、今の `reconcileOperations` の隔離は効かない（§6.7.4）。Core を上げて利用者の Plugin が新しい Plugin API に合わなくなった場合に起きうる。
   起動のたびに試して巻き戻すので、Torifune は動き続ける（利用者の Plugin は止まったまま）。運用で多いようなら、1 つずつ外して試す仕組みを別に設計する
5. **Package の展開が古いファイルを残す**：`extractPackage` は `overwrite` なしで呼ばれ、新しい版で消えたファイルが残る（§1.2 の 6）。本設計の範囲外（同期は自分で置き換えるので関係しない）

## 12. 文書への書き戻し

実装と同じ作業単位で直す。

| 文書 | 節 | 書くこと |
| --- | --- | --- |

## 13. リスク

| R1 | 印の無い古い Volume で、利用者が `050` より前に同梱 Plugin を手で直していた中身を、同梱の版で置き換える | 置き換える前に退避する（§6.3 #8）。ログに退避の場所を出し、運用文書に取り出し方を書く。版を上げた更新（Registry・Package）は版で見分けて触らない |
| R2 | §6.7 で、利用者の Plugin がある環境ではコンテナを作り直すたびに起動前の再ビルド（数分、1〜2GB のメモリ）が入る。その間ヘルスチェックに応答しないので、起動の猶予が短い基盤ではコンテナが殺されうる | 今の導入・削除の再ビルドと同じ資源で足りる（R-01）。運用文書に「作り直しの後の起動には再ビルドの時間がかかりうる。ヘルスチェックの開始猶予をそれに合わせる」と書く。同梱 Plugin だけの環境では起きない（§6.7.3） |
| R3 | 起動時の再ビルドが毎回失敗し、起動のたびに数分を費やす | 巻き戻して起動するので Torifune は使える（§6.7.4）。ログの `rebuild FAILED` と運用文書の手順（原因の Plugin のフォルダを外す・隔離マークを置く）で対処する（§11.2 の 4） |
| R4 | 同期が写しの途中で落ち、Plugin が壊れた状態で残る | 写しは作業用ディレクトリへ作り、ハッシュを確かめてから rename で入れ替える（§6.4）。途中で落ちても、古い中身が残るか、次の起動で写しから戻る（#29〜#32） |
