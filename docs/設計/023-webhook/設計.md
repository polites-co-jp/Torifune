# 023-webhook 設計

## 1. 目的

Webhook（`05_API設計.md` §39）。`002-Torifune機能完成` T9。

仕様は「必要になった場合に実装する」「詳細仕様は別途定義する」としており、
**要求すべきものが決まっていない**。ここで決める。

## 2. 何のために要るか

Torifune で起きたことを、**Torifune が知らない相手へ伝える**ため。

Plugin（同一プロセス）で足りる場合は Plugin を使えばよい
（`03_プラグイン設計.md` §6 の Event API）。Webhook が要るのは、

* 受け手が別のシステム（Slack、社内の集計基盤、iPaaS）
* 受け手が Torifune のコードを持てない

という場合に限る。**Plugin の代わりに使うものではない。**

## 3. 決めたこと

### 3.1 送るのは Core イベントだけ

`CORE_EVENTS`（`site.*` / `social.*` / `campaign.*`）を対象にする。
Plugin が発火したイベントは送らない。

Plugin のイベントは名前も中身も Plugin 次第で、
**Core が「これを外へ送ってよい」と判断できない**。
必要なら Plugin が自分で送る（Plugin は任意のコードを実行できる）。

### 3.2 署名は HMAC-SHA256。時刻も署名に含める

受け手が「本当に Torifune から来たか」を確かめられるようにする。

```
X-Torifune-Signature: sha256=<hex>
X-Torifune-Timestamp: <unix秒>
X-Torifune-Delivery: <uuid>
```

* 署名の対象は `<timestamp>.<body>`。**本文だけに署名しない。**
  本文だけだと、古い正当な配信をそのまま送りつけられる（リプレイ）
* 受け手は timestamp が現在から離れすぎていないことを見る。
  **その確認は受け手の責任**であり、送る側は材料を渡すだけ

### 3.3 Secret は暗号化して保存し、画面に平文を出さない

既存の Secret の扱いにそろえる（`02_データベース設計.md` §13）。
**発行時に一度だけ見せる。** API Token と同じ。

### 3.4 再試行は「予約して、あとで送る」

送信を発火の場でやり切らない。**受け手が落ちていると、
Torifune の操作そのものが遅くなる／失敗する**。

* イベント発火時は `webhook_deliveries` へ**予約だけ**する
* 送信は `POST /api/v1/webhooks/deliver` が担う（cron から API Token で叩く）
* 失敗したら指数的に間隔を空けて再試行する。上限を超えたら諦める（`failed`）

`018-analytics` のロールアップと同じ形にそろえる。
**同じ性質のものを違う形で作らない。**

### 3.5 重複配信は「配信ID」で受け手に判断させる

`X-Torifune-Delivery` は再試行でも変わらない。
受け手はこの ID で二重処理を避けられる。

**送る側で「1回だけ」を保証しない。** 保証するには受け手との合意が要り、
ネットワーク越しには原理的に「少なくとも1回」しか作れない。

### 3.6 タイムアウトは短く

10秒。受け手が遅いと、送信の処理が詰まる。
**受け取ったら即座に 2xx を返し、処理は受け手側で非同期に**、が正しい形で、
それを促すためにも短くする。

### 3.7 送信先は HTTPS に限る（localhost を除く）

平文で送ると、署名があっても中身は読まれる。

**内部ネットワークへの送信は止めない。** 自己ホストで社内の受け手へ送るのは
正当な用途で、それを塞ぐと使えない。SSRF の懸念は残るが、
**設定できるのは `system.manage` を持つ管理者だけ**であり、
その人は既にもっと強い操作ができる。

## 4. データ

```sql
webhooks(id, name, url, secret, events[], status, created_at, updated_at)
webhook_deliveries(id, webhook_id, event, payload, status, attempts,
                   last_error, next_attempt_at, delivered_at, created_at)
```

## 5. やらないこと

* 受け手ごとの詳細な整形（テンプレート）。中身は Core のイベント payload をそのまま
* 配信履歴の長期保管。古いものは消せるようにする
* Plugin イベントの中継（§3.1）

## 6. 受け入れ条件

1. Webhook を登録でき、Secret が発行時に一度だけ返る
2. DB に Secret の平文が無い。一覧に平文が出ない
3. Core イベントが起きると配信が予約される
4. 予約された配信を送ると、署名つきで届く
5. 署名が `timestamp.body` の HMAC-SHA256 である
6. 失敗すると再試行され、上限を超えると諦める
7. 再試行でも配信IDが変わらない
8. HTTP の URL を登録できない（localhost を除く）
9. `system.manage` が無ければ登録できない
