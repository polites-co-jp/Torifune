`defineRoute` が返す応答のすべて（成功・誤り・Rate Limit・CSRF、どのメソッドも）に `Cache-Control: no-store` を付け、

**ユーザー裁定 1**（057 では直さず 058 で、認証した API の応答に一律で）と **U1 (b)・U2 (a)** は設計の冒頭の表と §11 にある。

### 1.3 `route.ts` の全出口

内側の `respond` の `return` を 1 つずつ数え、対応する件と照らした。どの出口も外側の 1 か所を通る構造なので、件が無い出口も付与からは漏れない。

| 出口 | 件 |
| --- | --- |
| 429（Rate Limit） | #1 |
| 403 `CSRF_FAILED`（文字列でない／検証に落ちる） | #3・#2（Origin つき #5、非推奨つき #6） |
| 401（`sessionOnly` と Bearer） | #4 |
| 422（保存できない文字・本文の Zod・クエリの Zod） | #21・#20（クエリの Zod は件無し。同じ `errorResponse` で同じ出口） |
| 成功（ハンドラの応答。`cors` を `set`） | #11〜#16・#19・#27・#28・#30・#31・#32 |
| `catch`：`authorizationErrorResponse`（401・403、`cors` 無し） | #17・#18・#29・#30・#31 の 401 |
| `catch`：`SiteGoneError` の 401・並び替えの 422・`ValidationError` の 422 | 件無し（同じ出口） |
| `catch`：404・`JobBusyError` の 409・`ConflictError` の 409 | #22・#24・#23 |
| `catch`：`StaleSocialPostError`・`SiteInUseError`・`SocialPostStateChangedError` の 409 | 件無し（同じ出口） |
| `catch`：500 | #25 |
| リダイレクト・`Set-Cookie` のある応答 | #16（302＋`Set-Cookie`）・#31（ログインの `Set-Cookie`） |

`respond` が `throw` するのは `corsHeaders` の設定の誤り（`try` の外）だけで、設計 §4.2・§14 の R2 で範囲外と決めてある。ハンドラが返したヘッダの変えられない応答は、
Origin つきなら `try` の中の `cors` の `set` で `catch` の 500 に落ち、Origin 無しなら外側の `set` で `TypeError` になる（R1）。どちらも今は起きない（#34 が `Response.redirect(`・`Response.error(` を、
`grep` で `return fetch(` の素通しが無いことを確かめた）。

### 1.4 指摘事項

#### 重大・中・低

無し。

#### 軽微

* **軽微-1 #33 はファイル単位で、`defineRoute(` を使うファイルに素の Route Handler を混ぜると素通りする。**
  `app/api/v1/auth/csrf/route.ts` に `export async function POST() { return new Response(null); }` を足す変異（V23）は、`pnpm test` の全件（354 ファイル・14127 件）で生き残った。
  その POST の応答には `no-store` が付かない。条件 #33 の字面（「`defineRoute(` を使わないもの」の一覧が一致）は満たしており、今の 51 ファイルはどれも
  `export const <METHOD> = defineRoute(` だけを export しているので、**現状の漏れは無い**。閉じるなら、各 `route.ts` の `export` が `export const (GET|POST|PUT|PATCH|DELETE) = defineRoute(` の形だけであることを
  見る件を #33 に添える形が考えられる（設計 §5.5 の「新しいルートが付与の外に出たら落ちる」の意図に近い）
* **軽微-2 `SNS投稿API仕様.md` §9 の変更履歴に 058 の行が無い。** このマニュアルは API の振る舞いが変わるたびに §9 に行を足してきた（2026-09-24〜2026-10-24 の各行）。
  058 は §3.1 に 1 行足しただけで、変更履歴・関連文書（`058-api-no-store` の設計）が無い。設計 §13 が書き戻しを §3.1 の 1 行に限っているので**設計どおり**で、§1.10 に設計側の不足として挙げる
* **軽微-3 マニュアル §3.1 の「すべての応答（成功・エラーとも）」は、`defineRoute` を通らない応答まで含むように読める。** `proxy.ts` が返す `/api/` の `OPTIONS`（CORS の Preflight、204・本文なし）と、
  存在しないパスへの Next.js の 404、R2 の 500 には付かない。どれも利用者のデータを載せず、外部アプリが保存を気にする応答ではないので実害は無い。字面を合わせるなら「API の応答（Preflight を除く）」程度

### 1.5 オーケストレータが直した `083785f` の妥当性

**妥当。** 実装と期待値を変えず、#36 の文脈の作り方だけを直している。

* Playwright Test の中の `playwright.request.newContext()` は config の `use`（`baseURL`・`storageState: './e2e/.auth/admin.json'`。`playwright.config.ts` L17・L21）を引き継ぐ。
