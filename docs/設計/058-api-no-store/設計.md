## 1. 目的

`/api/v1` の応答は、セッション（Cookie）や API トークン（Bearer）で認証した利用者のデータ（投稿の本文・アカウント・利用者・設定・トークンの一覧など）を載せる。
いまは応答に `Cache-Control` が無いので、ブラウザの HTTP キャッシュ（ディスク）や途中の共有のキャッシュが保存してよい状態にある。
共有の PC で後から使った人や、プロキシを共有する人に、ログアウトした後も応答が残りうる。

すべての API の応答に `Cache-Control: no-store` を付け、保存させない（ユーザー裁定 1）。

## 3. 現状の調査（`7897c53`）

### 3.1 `defineRoute`（`apps/web/src/api/route.ts`）の流れ

`defineRoute(definition)` は定義を検査して登録し、`handle(request, args)` を返す。`handle` の中は次の順。

1. `cors = { ...corsHeaders(request), ...deprecation }`（**`try` の外**）
2. `try` の中：Rate Limit（429。`Retry-After`）→ Bearer の取り出し → 安全でないメソッドは本文を読み CSRF（403 `CSRF_FAILED`）→ `sessionOnly` と Bearer（401）→ 認可の文脈（DB）→ `requirePermission` → 保存できない文字（422）→ Zod（422）→ `handler` → **成功の応答にだけ `cors` を `headers.set`**
3. `catch`：`authorizationErrorResponse(error)`（401 / 403 / 500。**`cors` を付けずに返す**）→ `SiteGoneError`（401）→ 並び替え・`ValidationError`（422）→ `NotFoundError`（404）→ `JobBusyError`（409＋`Retry-After`）・競合（409）→ それ以外は `log.error` して 500

出口は `return` が 20 か所近くあり、**どの `return` にも `Cache-Control` は無い**。誤りの応答は `errorResponse(code, details, extraHeaders)`（`api/errors.ts`）が `Response.json` で作る。

### 3.2 応答の部品（`apps/web/src/api/response.ts`・`errors.ts`）

`dataResponse`・`pageResponse`・`createdResponse`・`noContentResponse`・`errorResponse` は、渡された `headers` だけを付ける。`Cache-Control` は無い。
ルートのハンドラが自分で `new Response(...)` を作るのは `auth/authorize`（302）と `auth/callback`（302＋`Set-Cookie`）の 2 つ。**`Response.redirect()`・`Response.error()`（ヘッダが変えられない応答）を使うルートは無い。**

## 4. スコープ

### 4.1 やること

* `defineRoute` が返す応答の**すべて**（成功・誤り・Rate Limit・CSRF、どのメソッドも）に `Cache-Control: no-store` を付ける
* `defineRoute` を通らないルートを許可の一覧で固定する静的検査（新しいルートが付与の外に出たら落ちる）

* `proxy.ts`・`next.config.ts` に付けること（§5.2）
* `Pragma`・`Expires`・`private` を足すこと（§5.3）
* `try` の外で投げられた例外（`corsHeaders` の設定の誤り）に付けること。Next.js が自分の 500 を返す経路で、`defineRoute` の応答ではない（§14 の R2）
* Plugin API・データ・Permission・画面・OpenAPI の生成物を変えること

## 5. 決めたこと

### 5.1 対象の範囲：`defineRoute` を通る応答のすべて

* **認証の有無で分けない。** 認証したかどうかは認可の文脈を作るまで分からず、作る前に返る応答（429・CSRF の 403）もある。`permission: null` のルートも、`auth/me`（利用者と Permission）・`auth/csrf`（CSRF トークン）・`login`・`callback`（`Set-Cookie`）のように、保存させたくない応答を返す。`collect`（計測のビーコン）は保存させても得が無い。分ける規則を足すより、一律のほうが漏れない（ユーザー裁定 1 の「一律」）
* **成功と誤りで分けない。** 401・403・422 の本文に利用者のデータは載らないが、422 の `details` は送った項目名を返す。誤りの応答を保存させる理由も無い。`deprecation.ts` が非推奨の告知を誤りの応答にも付けているのと同じ考え方
* **メソッドで分けない。** POST・PATCH・DELETE の応答も作った・変えた資源の本文を返す。ブラウザは既定で POST の応答を保存しないが、ヘッダで言い切るほうが読み手が迷わない

### 5.2 付ける場所：`defineRoute` の出口 1 か所

`defineRoute` が返す関数を 2 段にする。今の `handle` の中身（`try`／`catch` の全体）を内側の関数にし、外側の関数は内側が返した応答に `Cache-Control` を付けて返す。

```ts
// 形だけ（名前は実装に任せる）
return async function handle(request, args) {
  const response = await respond(request, args); // 今の handle の中身。try/catch で必ず Response を返す
  response.headers.set('Cache-Control', API_CACHE_CONTROL);
  return response;
};
```

* 20 近くある `return` の 1 つ 1 つに足さない。`catch` の `authorizationErrorResponse` のように `cors` すら付けていない出口があり、足す場所を数えると次に足したときに漏れる（`route.ts` の冒頭の「各ルートで手順を並べると、いつか1つ抜ける」）
* `response.ts`・`errors.ts` の部品には足さない。部品はハンドラの外でも使われうるし、ハンドラが自分で `new Response` を作る 302 の 2 つを取りこぼす
* `proxy.ts` には置かない。`proxy.ts` は画面と API に共通のヘッダの場所で、ここで `/api/` を見分けて付けると、vitest で直接ルートを叩くテスト（結合・API）が付与を見られない。`next.config.ts` の `headers()` も同じ理由で使わない
* 値は `apps/web/src/api/` の 1 か所に定数で置く（例：`API_CACHE_CONTROL = 'no-store'`）。`openapi.json` のルートは変えない（§5.5）

### 5.3 値：`no-store` だけ

* `no-store` は「どのキャッシュも応答のどの部分も保存しない」（RFC 9111 §5.2.2.5）。共有のキャッシュにも私的なキャッシュ（ブラウザ）にも効くので、`private` を足しても意味が増えない
* `Pragma: no-cache` は HTTP/1.0 の**要求**の指示で、応答に付けても今のキャッシュは見ない。古いプロキシへの対策は足さない
* `no-cache`・`max-age=0`・`must-revalidate` は「保存してよいが使う前に確かめる」で、保存そのものは止めない。目的（残さない）には `no-store` が当たる
* 既存の `openapi.json` も `no-store` で、値が揃う

### 5.4 ハンドラが付けた `Cache-Control`：上書きする

* いま `defineRoute` のハンドラで `Cache-Control` を付けているものは**無い**（§3.3）
* 外側で `headers.set` するので、ハンドラが何を付けても `no-store` になる。保存させてよい API が将来要るなら、`rateLimit: 'none'` と同じく `defineRoute` の定義に理由つきの明示の項目を足す別の作業単位にする。058 では足さない（使う口が無い）
* ハンドラが付けた他のヘッダ（`Location`・`Set-Cookie`・`Retry-After`・CORS・`Deprecation`／`Sunset`／`Link`）は変えない

### 5.5 `defineRoute` を通らないルート：変えない

| ルート | 扱い | 理由 |
| --- | --- | --- |
| `/api/health` | 変えない（`Cache-Control` 無しのまま） | 認証が無く、返すのは `{ status: 'ok' }` だけ。裁定の「認証した API の応答」の外 |
| `/api/ready` | 変えない | 認証が無く、返すのは DB への到達の真偽だけ |
| `/api/v1/openapi.json` | 変えない（`no-store` のまま） | 既に付いている |
| `/t.js` | 変えない（`public, max-age=3600` のまま） | 測る側のサイトの全ページから読まれる配布物で、保存させるのが意図（018 設計 §3.4）。認証も利用者のデータも無い |

この 4 つを**許可の一覧**として静的検査で固定する（#33）。`defineRoute` を使わない `route.ts` を新しく足すと、一覧に足して理由を書くまで落ちる。

## 10. 受け入れ条件

番号は実装プラン・テストで参照する。**A = 単体（DB に届く前に返る経路と、`defineRoute` を通らないルート）、B = 結合（テスト用の `defineRoute` のルートと scratch DB）、C = API（実際のルートを scratch DB で叩く）、D = 画面（E2E。`next start` の実機）、E = 静的検査。**
「`no-store` が付く」は `response.headers.get('cache-control') === 'no-store'`（値が `no-store` ちょうど。他の指示が混ざらない）で見る。

### 10.1 `defineRoute` の DB に届く前の出口（A）

1. Rate Limit を超えた要求の 429 に `no-store` が付き、`Retry-After` は今のまま
2. CSRF トークンの無い POST の 403（`CSRF_FAILED`）に `no-store` が付く
3. 本文の `csrfToken` が文字列でない POST の 403 に `no-store` が付く
4. `sessionOnly` のルートを Bearer で叩いた 401 に `no-store` が付く
5. 許可された Origin（`TORIFUNE_CORS_ORIGINS`）からの要求の 403 に、`Access-Control-Allow-Origin`・`Access-Control-Allow-Credentials`・`Vary` と `no-store` の両方が付く
