## 3. タスク分解

原則：**1 タスク = 1 コミット**。各タスクは「テストを書いて失敗を確認 → 実装 → 通す」の順。

**test-writer → implementer への受け渡しの単位は G。** test-writer は G の中の全テストを先に書き、新しいテストが**期待どおりの理由で**赤いことを確かめて `test:` でコミットする（`pnpm typecheck` / `pnpm lint` / `pnpm format:check` は通る状態で）。implementer は G の中のタスクを順に通し、`feat:` でコミットする。
**implementer はテストを書き換えない。** 食い違いは設計書のどこと食い違うかを報告して止まる。

**プッシュの約束**：プッシュの前に `pnpm test` を**全件**流す（postgres-test、`DATABASE_URL=postgresql://torifune:torifune@localhost:21701/torifune_test`、`TORIFUNE_ENCRYPTION_KEY=dGVzdC1vbmx5LWtleS1kby1ub3QtdXNlLWluLXByb2Q=`）。赤くてよいのは、いま取り組んでいる G のまだ実装していないタスクのテストだけ。`main` へプッシュしない、マージしない、`--force` は使わない。

**着手順の骨子**：テスト（A・B・C・E・D）→ `defineRoute` の出口 → 文書 → 最終確認と 3 つの検証。G2 は G1、G3 は G2 に依存する。

## 7. リスクと注意点

1. **内側へ移すときに出口を変えない（T2）。** 今の `handle` の中身は 1 文字も変えずに内側へ移す（`cors` を付けていない `authorizationErrorResponse` の出口も、そのまま）。058 で CORS の付け漏れを直すことはしない（設計の範囲外。見つけた事実として検証へ渡す）
2. **2 つの静的検査（T2）。** `route.ts` のソースに `redactSecrets`・`unhandled error in route`・`reason:` が残ること。`logReasonOf` を別のファイルへ移さない
3. **ヘッダの変えられない応答（T2・#34）。** 外側の `headers.set` は、`Response.redirect()` の応答で `TypeError` を投げる。今は使っていない（#34 が固定）。implementer が 302 を足す場面は無い
4. **Rate Limit の状態（T1・#1）。** limiter は `defineRoute` の呼び出しごとに作られる。テスト用ルートは `operationId` を一意にし、`rateLimit: { windowMs: 60_000, max: 1 }` で 2 回目を 429 にする。`resetEndpointRegistry` を `afterEach` で呼ぶ
5. **環境変数（T1・#5）。** `TORIFUNE_CORS_ORIGINS` は `vi.stubEnv` で立て、`afterEach` で `vi.unstubAllEnvs`。他のテストへ漏らさない
6. **ログイン・計測の Rate Limit（T1・#31・#32）。** `login` は 1 分 30 回、`collect` は 600 回。`requestInfoOf` が見る送信元を件ごとに変え（`nul-public-input.integration.test.ts` の `nextIp` の形）、`login_attempts` を片付ける
7. **E2E の順序（T1・#35〜#37）。** `z-rate-limit.spec.ts` が最後に流れる前提を崩さない（spec 名は `api-no-store.spec.ts`）。ログインは既定の `storageState`（`./e2e/.auth/admin.json`）を使い、未認証は `storageState` を空にした `request` の文脈で叩く
