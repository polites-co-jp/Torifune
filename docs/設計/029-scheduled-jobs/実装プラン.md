### 確定事項（設計書から。プランで蒸し返さない）

* 定期実行は Application 層（`application/jobs/`）。DB 製品に触るのは `infrastructure/job-lock.ts` と `job-run-repository.ts` だけ（§4.1）
* 起動は `apps/web/src/instrumentation.ts` の `register()`。`NEXT_RUNTIME !== 'nodejs'` では何もしない。`bootScheduler` は `NODE_ENV === 'test'` で何もしない（§6.1.1）
* 登録するジョブは `analytics.rollup`（15 分）と `webhook.deliver`（1 分）の 2 つ。Plugin からのジョブ登録は無い（§6.2 / §9）
* 定期ロールアップの `from` は「最後に成功した実行の開始日、ただし今日 − 7 日より前にしない、成功が無ければ昨日」（裁定 #5、`scheduledRollupFrom`）
* 既存 API（`POST /analytics/rollup` / `POST /webhooks/deliver`）は `runJob` 経由にし、応答の形は変えない。ロックが取れなければ 10 秒待って 409 `CONFLICT` + `Retry-After: 10`（§6.3）
* `job_runs` はジョブごとに最新 50 件（`JOB_RUN_RETENTION`）。`skipped` も記録する（§5.2）
* 新しい Permission は作らない。`listJobStatuses` / `GET /jobs` / 設定画面の区画は `system.manage`（§6.6）
* `AnalyticsStatus` に `lastReceivedAt` / `pending` / `rollup` を足し、`lastRollupAt` / `analyticsLastSeenAt` は残す（§5.4、裁定 #7）
* 受信状況は 4 状態（`diagnoseReception`）。判定順は §5.5 の表のとおり
* Plugin API は変更なし。`PLUGIN_API_VERSION` は上げない（§9）
* E2E は `playwright.config.ts` の `webServer.env` に `TORIFUNE_ROLLUP_INTERVAL_MINUTES: '1'` を足し、**定期実行が動いている状態で既存 E2E が通ること**自体が受け入れ条件（§10 末尾）

### テストの方法（設計書に無い、プラン側で決める手段）

* **UI 部品（#53〜#55）**：028 と同じく `.test.ts` で `createElement` + `renderToStaticMarkup`。
  `settings-tab.tsx` / `not-tracked.tsx` は `useRouter` を使うので、`vi.mock('next/navigation', () => ({ useRouter: () => ({ push: vi.fn(), refresh: vi.fn() }) }))` を先頭に置く。
  `useState` / `useEffect` は SSR で問題なく通る（効果は走らない）。文言は静的 HTML の文字列一致で見る
* **周期実行（#23〜#31）**：`vi.useFakeTimers()` と `execute` の差し替え。`tick` は `withConnection` を通るので、
  `setDatabaseProvider({ connect: async () => fakeConnection, disconnect: async () => {}, healthCheck: async () => true })`
  で**偽の Provider** を差し、`afterEach` で `setDatabaseProvider(null)` に戻す。`fakeConnection` は `{ db: {} as never, transaction: (fn) => fn(fakeConnection) }` で足りる（`execute` が差し替わっているので `db` には触れない）
* **`bootScheduler` の「2 回呼んでも 1 回」（#30）**：Vitest は `NODE_ENV=test` なので既定では何もしない。この検査だけ `vi.stubEnv('NODE_ENV', 'production')` と `vi.stubEnv('TORIFUNE_SCHEDULER', 'on')` で有効にし、
  2 回呼んで `vi.getTimerCount()` がジョブ数（2）のままであること、`schedulerSnapshot().booted === true` を見る。後始末は `resetSchedulerForTests()`（`stop()` してホルダを空にし、`process.removeListener` で SIGTERM / SIGINT のハンドラを外す）と `vi.unstubAllEnvs()`
* **警告は 1 回だけ（#31）**：`config.ts` に `resetSchedulerConfig()`（`analytics/timezone.ts` の `resetTimeZoneWarning` と同じ役目）を置き、`afterEach` で呼ぶ
* **ロック（#12〜#16、#19、#43）**：「別の保持者」は `new pg.Client({ connectionString: scratch.connectionString })` で `SELECT pg_try_advisory_lock($1, $2)` を直接叩く。鍵は `jobLockKey(name)` を import する（E2E は `node:crypto` で同じ計算を 4 行で書く：`createHash('sha256').update(name).digest().readInt32BE(0)`）

## 7. リスクと注意点

1. **定期実行が動いている状態で既存 E2E が通ること（T8）**。E2E は `TORIFUNE_ROLLUP_INTERVAL_MINUTES=1` で走る。気にすべき経路：
   * `rollupToday`（手動 API）と定期ロールアップが同じロックに載る。定期側は待たずに `skipped`、手動側は最大 10 秒待つ。1 分ごとの定期ロールアップは E2E の DB では数十 ms で終わるので、10 秒待って 409 になることは無い。ただし **#43 でロックを 10 秒以上保持するテスト中は、定期側が `skipped` を記録する**（`triggered_by` で絞って読む）
   * `webhook.deliver` が 1 分ごとに走る。E2E に `POST /webhooks/deliver` の件数を見るテストは無い（`grep` 済み）
   * `prepare` が Plugin を匿名で起動する。`plugin-runtime.spec.ts` / `plugin-manager.spec.ts` / `plugin-example.spec.ts` が「最初のリクエストで起動する」前提に依存していないかを T8 の全件実行で確かめる。落ちたら、その spec の前提を確認したうえで報告する（本体の挙動は設計どおりなので変えない）
   * `reuseExistingServer: !CI` のとき、ローカルでは**古いビルドのサーバーが残っている**と定期実行が無い状態で E2E が走る。T8 以降は一度サーバーを止めてから流す
2. **`job-lock.ts` の接続の固定**：`db.connection().execute(cb)` は `cb` の終了で接続を返すため、`acquire` が返った後も `cb` を終わらせてはいけない。deferred を握って `release()` まで待つ構造にする。`cb` の中で例外が出たら必ずロック解放を試みてから抜ける。`waitMs > 0` の `55P03` は `ROLLBACK` を忘れると接続が aborted のまま Pool に戻る
3. **`SchedulerOptions.jobs: readonly JobDefinition<undefined>[]` と `ROLLUP_JOB: JobDefinition<{ from; to } | undefined>`**：`run` をメソッド構文で宣言しているので代入できる（メソッドは双変）。プロパティ構文（`run: (…) => …`）にすると型が合わなくなるので、設計 §6.1.3 のとおりメソッド構文にする
4. **`bootScheduler` と `processState`**：`processState` は消せない。`{ instance: Scheduler | null }` のホルダを置き、`resetSchedulerForTests()` はホルダの中身を空にする。`process.once('SIGTERM')` の登録は**ホルダに初めて入れたときだけ**行う（2 回目の `bootScheduler` で二重登録しない）
5. **`analytics.integration.test.ts` の既存テストが落ちる**（T12）：`describe('受信状況')` の 2 件が `toEqual` で全項目を固定している。型を足した瞬間に落ちるので、T12 のテスト書き換えと実装を同じコミットにする。`afterEach` に `job_runs` の削除も足す（`runJob` で流すテストの行が次のテストの `since` に効く）
6. **`SettingsData` の型追加で `page.tsx` の typecheck が落ちる**（T13 → T15）：T13 の時点で `page.tsx` が新項目を渡す最小の追随を入れるか、T13〜T15 を連続して進めて G4 の途中でコミットしない。プランでは前者（T13 に `page.tsx` の値の組み立てを含める。判定の切り替え `untracked = state !== 'receiving'` は T15）
7. **UI 部品テストと `useRouter`**：`settings-tab.tsx` / `not-tracked.tsx` は `next/navigation` を `vi.mock` する。`apiRequest`（`ui/client/api-client`）は import されるだけで呼ばれない。`Toast` / `ConfirmDialog` が `renderToStaticMarkup` で描けない場合は、それらも `vi.mock('@/ui/components', async (importOriginal) => …)` で該当部品だけ差し替える（文言の検査には影響しない）
8. **E2E #57 の緩さ**：`collect` 直後に画面を開いたとき、定期ロールアップが先に走っていれば概要に数字が出る。設計 §11 #10 のとおり「アクセスは届いています」または Stat「ページビュー」のどちらかで通す。厳密な判定は #6〜#10 / #53〜#54 で担保
9. **E2E #60 / #61 の待ち時間**：初回遅延 15 秒 + 間隔 1 分。`expect.poll` の `timeout` は 120 秒 / 60 秒、`intervals` は 5 秒。Playwright の既定 `test.timeout`（30 秒）を超えるので `test.setTimeout(150_000)` / `(90_000)` を付ける
10. **`job_runs` の残骸**：`global-setup.ts` に `DELETE FROM job_runs` を足さないと、前回の E2E 実行の `ok` 行で #61 が空振りで通る。T8 で足す
11. **`hostname:pid` の `runner`**：`node:os` は Application 層の `config.ts` から使う（禁止されていない）。Domain には入れない
12. **409 の `details`**：`api/errors.ts` の注意書き（フィールド単位の入力エラーのためだけ）と食い違うが、設計 §11 #9 で承知のうえの判断。`errors.ts` の注意書きは触らない（触るなら設計側の話）
13. **`countAccessSince` の `since = null`**：`WHERE` を付けずに `LIMIT 1000`。`access_logs_site_time_idx (site_id, occurred_at DESC)` で `ORDER BY occurred_at DESC LIMIT 1000` が索引順で止まることを、#49 の 1001 件で（時間ではなく）件数だけ確かめる。性能は要件 §2.2 の「目に見えて遅くならない」で足りる
14. **`Retry-After` と CORS ヘッダ**：`errorResponse` の第 3 引数に `{ ...cors, 'Retry-After': '10' }` を渡す。`cors` を落とすと CORS 経由の 409 が読めなくなる
15. **`next dev` の HMR**：`register()` が複数回呼ばれても `processState` で 1 つ。`instrumentation.ts` 自体の HMR は Next が扱う。開発時に `stop()` が呼ばれないままモジュールが差し替わっても、ホルダが `globalThis` にあるので古いタイマーが増え続けることは無い
16. **SaaS 固有機能への踏み込み**：無し。テナント・課金・コンテナ管理・デプロイ基盤に関わるタスクは無い。compose に cron コンテナは足さない
