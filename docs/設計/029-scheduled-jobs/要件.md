# 029 本体内の定期実行とアクセス解析の診断表示 — 要件と裁定

設計書（`設計.md`）を書くための入力。導入先で「計測タグを貼っただけでは数字が出ない」事象が
起きた原因の調査結果と、ユーザーが裁定した方針をまとめる。
**この裁定は決定事項であり、設計書はこれに従う。**

## 1. 背景と事実（2026-09-04）

外部サイト（Next.js App Router の SPA）に計測タグを導入し、`t.js` の SPA 対応
（`fix: 計測スクリプトを SPA のクライアント遷移に対応させる`）は本番で期待どおり動いている。
Chromium で `/api/v1/collect` へのリクエストを全数捕捉し、初回ロード・`pushState`・
サイト内リンク遷移のそれぞれで 1 件ずつ、正しいペイロード（`{key, path, referrer}`、
`text/plain`）が **204** で受け付けられていることを確認した。

それでも導入側のアナリティクス画面に数字が出ない。原因は計測タグではなく、製品側の作りにある。

1. 画面（日次 / 期間合計 / 上位ページ）は `analytics`（ロールアップ済みの集計値）しか読まない
   （`018` §4.1「生ログを画面から集計しない」。`028` で上位ページも集計値へ載せ替えた）
2. ロールアップは `POST /api/v1/analytics/rollup` を叩いたときだけ走る。
   本体にスケジューラは無く、`node-cron` 等の依存も無い
3. したがって **運用者が自前で cron を組まない限り、画面は空のまま**
   （`docs/マニュアル/アクセス解析設置.md` §4 にもそう明記されている）
4. 受け口は成功・失敗を問わず 204 を返す（キーの当たりを探らせないため）。
   `site === null` / `archived` / パス不正のいずれでも 204 なので、**204 は記録された証明にならない**
5. User-Agent が空、または `bot|crawler|spider|curl|headless` 等を含むと Bot 判定になり、
   上位ページからも日次からも黙って除外される
6. 028 の「設定」タブにある受信状況の **最終受信は rollup 時に書き戻される**
   （`sites.analytics_last_seen_at`）ため、集計が止まっていると「届いているか」も分からない

`CLAUDE.md` は「Torifune は単体でインストール・起動・利用できなければならない」と定めている。
いまの状態は、本体を入れただけの人にはアクセス解析が完成しないことを意味し、この原則に反する。

## 2. やってほしいこと（優先順）

### 2.1 集計が既定で回るようにする（最優先）

「タグを貼れば数字が出る」を既定にする。

- **compose に cron コンテナを足す形は本体の解決にならない**（コンテナ管理・デプロイ基盤は
  TorifuneHub 側の責務であり、OSS 本体はそれを前提にできない）。本体内で定期実行を持つ
- 定期実行が要るエンドポイントは analytics だけではない。`POST /api/v1/webhooks/deliver` も
  「cron から API Token で叩く前提」になっている
- ロールアップは同じ日を何度流しても差し替えられる冪等な処理で、多重起動の実害は小さい。
  Webhook 配信は冪等とは限らないので、共通基盤にするなら排他（DB のアドバイザリロック等）を入れる
- 既定は「有効」。環境変数で無効化できる（外部スケジューラを既に持っている運用者を縛らない）

**受け入れ条件**

- 本体を起動しただけの環境で、計測タグを貼ったサイトの数字が、人手を介さず画面へ出る
- 環境変数で定期実行を止められ、止めた場合は従来どおり API を叩いて集計できる
- 集計が二重に走っても保存値が壊れない（既存の冪等性を壊さない）
- 定期実行の有無・前回実行時刻が運用者から確認できる

### 2.2 「届いているが、まだ集計されていない」を画面で切り分けられるようにする

現状の空表示（`EmptyState` / 「計測タグ未設置」の導線）では、「タグ側が悪いのか、集計が止まっているのか、
Bot 除外なのか」を切り分けられず、結局 DB を直接見るしかない。

アナリティクス画面に、少なくとも次が分かる表示がほしい。

- そのサイトの **生ログの最終受信時刻**（＝タグは届いているのか。rollup を待たず、生ログから直接）
- **最後にロールアップが走った時刻**（＝集計は回っているのか）
- その期間に **Bot として除外した件数**（＝UA 起因で消えていないか）

「生ログを画面から集計しない」設計の趣旨は、期間全体を毎回集計して重くなるのを避けること。
上記は件数・時刻の軽い問い合わせで足りるはずなので、その趣旨は壊さない範囲で実現する
（重くなるなら別案でよい）。

**受け入れ条件**

- 「タグは届いているが集計が未実行」の状態が、DB を見ずに管理画面だけで判定できる
- 「Bot 判定で除外されている」ケースも管理画面だけで気づける
- 追加表示によって、期間を広く取ったときの画面表示が目に見えて遅くならない

### 2.3 導入手順の更新

- `docs/マニュアル/アクセス解析設置.md` §4 を「cron を組まないと出ない」から
  「既定で回る／止めたい人だけ設定する」に直す
- `docs/仕様書/外部サイト導入手順.md` にも、確認手順として 2.2 の画面表示を使う形で反映する

## 3. 制約・やらないこと

- **`t.js` の再修正は不要。** SPA 対応は実測で正しく動いている
- 受け口 `/api/v1/collect` が理由を返さない設計は**維持する**。診断性は管理画面側で担保する
- `text/plain` の単純リクエスト／CORS を開かない前提も維持する
- Cookie・localStorage を使わない前提も維持する
- 日付の区切り（`TORIFUNE_TIMEZONE`）の既定 UTC は**今回変更しない**
- SaaS 前提のもの（テナント管理・課金・デプロイ基盤）は本体に入れない

## 4. 裁定（ユーザー決定、2026-09-04）

| # | 論点 | 裁定 |
| --- | --- | --- |
| 1 | ブランチ | 028（main 未マージ）に依存するため、`feature/028-analytics-dashboard-redesign` から `feature/029-scheduled-jobs` を切る。マージ順は 028 → 029 |
| 2 | 定期実行の置き場 | **共通基盤にする。** Next.js のサーバー起動フック（`instrumentation.ts`）から起動するジョブ実行基盤を 1 つ置き、analytics ロールアップと **Webhook 配信の 2 ジョブを既定で登録する**。ジョブごとに PostgreSQL の advisory lock で排他し、複数プロセスで同時に走らない。既存の API（`POST /analytics/rollup`、`POST /webhooks/deliver`）は残し、外部 cron からも従来どおり叩ける |
| 3 | ロールアップの間隔 | **15 分ごと**（対象は「昨日と今日」。冪等な差し替え）。間隔は環境変数で変えられるようにする |
| 4 | 実行状況の確認 | **DB に記録し、画面に出す。** `job_runs` 相当の小さなテーブル（ジョブ名・開始/終了時刻・結果・エラー）を足し、複数プロセス構成や再起動後でも前回実行が分かるようにする。アナリティクスの「設定」タブ（受信状況）と設定画面に出す。受信状況の「最終集計」もここから引く。ログにも常に出す |
| 5 | 定期ロールアップの対象期間（設計書提示後の裁定） | **最後に成功したロールアップの開始日（`TORIFUNE_TIMEZONE`）から今日まで。ただし最大 7 日さかのぼる。** 成功の記録が無ければ「昨日と今日」。短い停止は人手なしで埋まり、長い停止は従来どおり API で流し直す |
| 6 | 手動 API とロックの関係（同上） | 手動 API（`POST /analytics/rollup` / `POST /webhooks/deliver`）も同じロックに載せ、他が実行中なら最大 10 秒待ってから **409 CONFLICT**（`Retry-After: 10`）を返す |
| 7 | 「設定」タブの「最終集計」（同上） | **両方出す。** 「最終集計（全体）」= `job_runs` の最後に成功したロールアップ、「このサイトの集計値の最終更新」= そのサイトの `analytics.updated_at` の最大（028 の `lastRollupAt` を残す） |

## 5. 設計側で決めてよいこと（要件からの補足）

- Webhook 配信ジョブの間隔（配信の再試行間隔 `retryDelayMs` と整合させる）
- 「生ログの最終受信」は `access_logs` の `(site_id, occurred_at DESC)` 索引（`access_logs_site_time_idx`）で
  引ける `max(occurred_at)` の 1 行問い合わせで足りる想定。期間全体を舐める問い合わせは足さない
- 「期間に Bot として除外した件数」は集計値 `bot_pageviews`（028 で追加済み）から出してよい。
  集計前の分は「未集計の受信件数（うち Bot n 件）」のような、直近の短い範囲に閉じた軽い問い合わせで補う
- `instrumentation.ts` は `next build` 時には走らず、`next dev` の HMR で多重に起動しうるため、
  `processState`（`infrastructure/process-state.ts`）でプロセスに 1 つに抑える
- 環境変数名（例：`TORIFUNE_SCHEDULER=off`、`TORIFUNE_ROLLUP_INTERVAL_MINUTES`）は `.env.example` の書き方にそろえる
