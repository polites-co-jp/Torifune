# 029 本体内の定期実行（スケジューラ）とアクセス解析の診断表示 設計

入力は同ディレクトリの [`要件.md`](要件.md)（ユーザー裁定済み）だけ。
**この設計書は現行実装（`018-analytics` / `023-webhook` / `028-analytics-dashboard-redesign`）からの差分として書く。**
差分の基準となる現行のファイルは §4 に列挙する。

## 1. 目的

1. **「タグを貼れば数字が出る」を既定にする。** いまは `POST /api/v1/analytics/rollup` を外から叩かない限り
   画面が空のままで、`CLAUDE.md` の「単体でインストール・起動・利用できる」に反する。
   本体の中に定期実行の基盤を 1 つ置き、analytics ロールアップと Webhook 配信の 2 ジョブを既定で回す
   （裁定 #2〜#3、#5）。既存の API は残し、外部スケジューラを持つ運用者は環境変数で本体の定期実行を止められる
2. **実行状況を DB に記録して画面に出す**（裁定 #4）。複数プロセス構成でも再起動後でも「前回いつ・どう終わったか」が分かる
3. **「届いているが未集計」「Bot だけ届いている」を管理画面だけで切り分けられるようにする**（要件 §2.2）。
   受け口が理由を返さない設計（204）は維持し、診断性は管理画面側で担保する。
   「生ログを画面から集計しない」原則（`018` §4.1）は、**時刻 1 行・件数（上限つき）の軽い問い合わせ**に閉じることで守る
4. 導入手順を「既定で回る／止めたい人だけ設定する」に直す（要件 §2.3）

### 4.1 スケジューラを Application に置く理由

置き場の候補は Application と Infrastructure の 2 つ。**Application に置く。**

* スケジューラがやることは「決まった時刻に UseCase 相当の処理（`rollupAnalytics` / `deliverPendingWebhooks`）を
  呼び、結果を Repository で記録する」であり、`01` §5 が Application の責務とする
  「ユースケースの実行・トランザクション制御・Repository / Provider の呼び出し」そのもの
* ジョブの定義（何を・どの間隔で）は業務の判断であり、Infrastructure（DB・外部サービスとの接続）ではない
* `application/events.ts` がプロセス内の購読状態を `processState` で持っているのと同じ形で、
  タイマーとスナップショットも Application が持つ
* **DB 製品に依存する部分だけ Infrastructure に切る**：advisory lock（`job-lock.ts`）と `job_runs` の SQL
  （`job-run-repository.ts`）。Application 層は `connection.db` に触れない（ESLint の既存規則）

Domain（`domain/jobs/job.ts`、`domain/analytics/reception.ts`）は型と純関数だけで、`pg` / `kysely` / タイマー / 環境変数を知らない。
`instrumentation.ts` は Next.js が要求する場所（`src/` 直下）に置く。`app/` と同じく「フレームワークの入口」であり、
中身は Application の起動関数を呼ぶだけにする。

依存の向きは変えない。`application/jobs/*` → `infrastructure/*`、`domain/*`。`plugin/runtime.ts` は
Application から import しない。Plugin の起動（`ensurePluginsStartedAnonymously`）は `instrumentation.ts` が
`prepare` として注入する（§6.1.4）。

## 5. データモデル

### 5.1 マイグレーション `migrations/021_job_runs.sql`

`020_analytics_breakdown.sql` の次の連番。

```sql
-- 定期実行ジョブの実行記録（029-scheduled-jobs 設計 §5）。
--
-- ジョブごとに最新 50 件だけ持つ（古い行はアプリが消す。§5.3）。
-- 監視・診断のための小さな表であり、履歴の長期保管はしない。
CREATE TABLE job_runs (
    id            uuid        PRIMARY KEY,
    -- 'analytics.rollup' / 'webhook.deliver'（domain/jobs/job.ts の JOB_NAMES）
    job_name      text        NOT NULL,
    -- 'scheduled'（本体の定期実行）/ 'manual'（API から）
    triggered_by  text        NOT NULL,
    -- 'running' → 'ok' / 'error'。ロックが取れなかったときは 'skipped'
    status        text        NOT NULL,
    started_at    timestamptz NOT NULL DEFAULT now(),
    finished_at   timestamptz,
    -- 例外のメッセージだけ。スタックトレース・SQL・接続文字列を入れない
    -- （宣言で終わらせず、書く前に redactSecrets → truncateError を通す。設計 §6.1.7）
    error         text,
    -- 結果の概要（rollup: from / to / days / points、webhook: attempted / delivered / failed）
    summary       jsonb       NOT NULL DEFAULT '{}'::jsonb,
    -- 実行したプロセス（hostname:pid）。複数プロセス構成でどれが動いたかを見る
    runner        text,

    CONSTRAINT job_runs_job_name_not_blank CHECK (btrim(job_name) <> ''),
    CONSTRAINT job_runs_triggered_by_check CHECK (triggered_by IN ('scheduled', 'manual')),
    CONSTRAINT job_runs_status_check CHECK (status IN ('running', 'ok', 'error', 'skipped')),
    CONSTRAINT job_runs_finished_after_started CHECK (finished_at IS NULL OR finished_at >= started_at),
    CONSTRAINT job_runs_error_length CHECK (error IS NULL OR char_length(error) <= 2000)
);

-- 「ジョブ × 新しい順」で引く。前回の実行・前回の成功・保持件数の切り詰めがすべてこれを使う。
CREATE INDEX job_runs_job_started_idx ON job_runs (job_name, started_at DESC);
```

* 列名は `trigger` にしない（PostgreSQL のキーワード）。`triggered_by` にする
* 新しい Permission は作らない（`INSERT INTO permissions` は無い）
* `apps/web/src/database/schema.ts`：

```ts
export interface JobRunsTable {
  id: string;
  job_name: string;
  triggered_by: string;
  status: string;
  started_at: CreatedAt;
  finished_at: ColumnType<Date | null, Date | string | null | undefined, Date | string | null>;
  error: string | null;
  summary: JSONColumnType<Record<string, unknown>, string | undefined, string>;
  runner: string | null;
}
```

### 5.2 保持の形：ジョブごとに最新 50 件（履歴 + 切り詰め）

「最新 1 行を upsert」ではなく **履歴を持って件数で切る**。

* 「前回の実行」（失敗も含む）と「前回の成功」は別に要る。最新 1 行だと、直近が失敗したとき
  「最後にいつ集計できたか」（受信状況の「最終集計」）が消える
* 直近のエラーを数件並べられると、断続的に失敗しているジョブに気づける
* 行数は `JOB_RUN_RETENTION = 50` × ジョブ数で頭打ち。切り詰めは各実行の記録の直後に
  `DELETE FROM job_runs WHERE job_name = ? AND id NOT IN (SELECT id FROM job_runs WHERE job_name = ? ORDER BY started_at DESC, id DESC LIMIT 50)` で行う
  （表が小さいので索引 1 本で足りる）
* `skipped` も記録する。複数プロセス構成で「排他が効いている」ことを DB から確かめられる。
  画面の「前回の実行」は最新の行をそのまま出し、「前回の成功」は `status = 'ok'` の最新を出す

### 5.3 Domain の型（`domain/jobs/job.ts`）

```ts
export const JOB_NAMES = ['analytics.rollup', 'webhook.deliver'] as const;
export type JobName = (typeof JOB_NAMES)[number];
export function isJobName(value: string): value is JobName;

export type JobTrigger = 'scheduled' | 'manual';
export type JobRunStatus = 'running' | 'ok' | 'error' | 'skipped';

export interface JobRun {
  readonly id: string;
  readonly jobName: JobName;
  readonly triggeredBy: JobTrigger;
  readonly status: JobRunStatus;
  readonly startedAt: Date;
  readonly finishedAt: Date | null;
  readonly error: string | null;
  readonly summary: Readonly<Record<string, unknown>>;
  readonly runner: string | null;
}

export const JOB_RUN_RETENTION = 50;
export const JOB_ERROR_MAX_LENGTH = 2000;

/** 環境変数の解釈。不正なら null（呼ぶ側が既定に落として警告する）。 */
export function parseSchedulerSwitch(raw: string | undefined): boolean | null;   // undefined / '' / 'on' → true、'off' → false（大文字小文字を問わない）、他 → null
export function parseIntervalMinutes(raw: string | undefined): number | null;    // undefined / '' → null（既定を使う）、1〜1440 の整数 → その値、他 → NaN を返さず null
export function truncateError(message: string): string;                          // 2000 文字で切る（コードポイント単位。§5.3.1）

/** 定期ロールアップの from（裁定 #5）。日付は `YYYY-MM-DD`。最後の成功の開始日から、ただし today − 7 日より前にしない。成功が無ければ昨日 */
export const ROLLUP_MAX_LOOKBACK_DAYS = 7;
export function scheduledRollupFrom(input: { readonly lastSucceededStartedAt: string | null; readonly today: string }): string;
```

`parseIntervalMinutes` は「未設定」と「不正」を区別しない（どちらも null）。区別が要るのは警告を出すかどうかだけなので、
`application/jobs/config.ts` が「未設定でないのに null」のときだけ `log.warn` する。

#### 5.3.1 `truncateError` は**コードポイント単位**で切る（検証の反映）

`slice(0, 2000)` は UTF-16 コードユニット単位で切るため、絵文字・一部の漢字（サロゲートペア）の途中で切れると
孤立サロゲートが残り、画面と JSON で文字が壊れる。`[...message].slice(0, JOB_ERROR_MAX_LENGTH).join('')` の要領で
**コードポイントの列にしてから切る**（切断位置がペアの途中なら 1 つ手前で止まる）。
PostgreSQL の `char_length` も文字単位なので、`job_runs_error_length`（2000）の制約とも一致する。


「最終集計」は**両方出す**（裁定 #7）。`rollup.lastSucceededAt`（`job_runs`。全体）は「集計は回っているか」に答え、
サイトに生ログが無くても「回っている」と分かる。`lastRollupAt`（`analytics.updated_at`。サイトごと）は
「このサイトの集計値がいつ書き換わったか」に答え、Plugin の行は数えない（`source = 'core'`）。役目が違うので片方に寄せない。

### 5.5 受信状況の 4 状態（`domain/analytics/reception.ts`）

```ts
export type ReceptionState =
  | 'not-received'     // 一度も届いていない → 「計測タグ未設置」
  | 'pending-rollup'   // 届いているが、この期間に集計値が無く、未集計に人のアクセスがある
  | 'bots-only'        // 届いているが、未集計がすべて Bot
  | 'receiving';       // 通常表示（集計値がある、過去の期間、いまは届いていない）

export interface ReceptionInput {
  readonly lastReceivedAt: Date | null;
  readonly pending: { readonly total: number; readonly bots: number };
  /** 当期に `key = ''` の点が 1 つでもあるか */
  readonly hasPointsInPeriod: boolean;
  /** 当期の `to` が今日以降か。過去の期間に「集計待ち」は出さない */
  readonly periodIncludesToday: boolean;
}

export function diagnoseReception(input: ReceptionInput): ReceptionState;
/** 集計済みの当期が「人の PV は 0、Bot の PV は 1 以上」か。概要タブの警告に使う */
export function botsOnlyInPeriod(summary: { readonly pageviews: number; readonly botPageviews: number }): boolean;
```

判定は上から順に最初に当たったもの：

| 条件 | 状態 |
| --- | --- |
| `lastReceivedAt === null` | `not-received` |
| `hasPointsInPeriod` | `receiving` |
| `!periodIncludesToday` | `receiving` |
| `pending.total === 0` | `receiving` |
| `pending.bots === pending.total` | `bots-only` |
| それ以外（人のアクセスが未集計） | `pending-rollup` |

`hasPointsInPeriod` が真なら常にタブを出す（集計済みで Bot だけの期間は、概要タブの警告 `botsOnlyInPeriod` で示す。
訪問者タブの「Bot のアクセス」を見られるようにするため）。
`pending` は上限 1000 件で打ち切った値で判定してよい（最新 1000 件がすべて Bot なら Bot だけとみなす）。

#### 6.1.1 起動（`apps/web/src/instrumentation.ts`）

```ts

```

* `register()` は `next start` / `next dev` のサーバー起動時に 1 回呼ばれ、`next build` では呼ばれない
* `bootScheduler` は `processState('jobs.scheduler', …)` で**プロセスに 1 つ**のインスタンスを作り、
  2 回呼ばれても（`next dev` の HMR）タイマーを重ねない
* `register()` の中で DB に触らない（DB が起動待ちでも本体の起動を止めない）。最初の実行は §6.1.3 の初回遅延の後
* Vitest は `instrumentation.ts` を読まない（Next.js のサーバーだけが呼ぶ）ので、テストで勝手に起動しない。
  加えて `bootScheduler` は `NODE_ENV === 'test'` のとき何もしない（`log.debug` だけ）。
  基盤のテストは `createScheduler(...)` を明示的に作り、`vi.useFakeTimers()` で時間を進める

#### 6.1.2 環境変数（`application/jobs/config.ts`、`.env.example` へ追記）

| 変数 | 既定 | 意味 |
| --- | --- | --- |
| `TORIFUNE_SCHEDULER` | `on` | `off` で本体の定期実行を止める（外部スケジューラから API を叩く運用向け）。それ以外の値は警告して `on` |

#### 6.1.3 周期実行（`application/jobs/scheduler.ts`）

```ts
export interface JobDefinition<TInput = undefined> {
  readonly name: JobName;
  readonly intervalMs: number;
  /** 起動からの初回遅延。既定 15 秒 */
  readonly initialDelayMs?: number;
  /** 実行本体。戻り値が job_runs.summary になる */
  run(connection: Connection, input: TInput): Promise<Readonly<Record<string, unknown>>>;
}

export interface SchedulerOptions {
  readonly jobs: readonly JobDefinition<undefined>[];
  /** 各実行の前に呼ぶ（Plugin の起動）。失敗したらその回は走らせない */
  readonly prepare?: () => Promise<unknown>;
  readonly enabled: boolean;
  /** テスト用。既定は runJob（§6.1.5） */
  readonly execute?: typeof runJob;
}

export interface JobSnapshot {
  readonly name: JobName;
  readonly intervalMinutes: number;
  readonly nextRunAt: Date | null;
  readonly running: boolean;
}
export interface SchedulerSnapshot {
  /** register() が基盤を初期化したか（テスト・未起動との区別） */
  readonly booted: boolean;
  readonly enabled: boolean;
  readonly jobs: readonly JobSnapshot[];
}

export function createScheduler(options: SchedulerOptions): { start(): void; stop(): void; snapshot(): SchedulerSnapshot; tick(name: JobName): Promise<void> };
export function bootScheduler(options: { prepare: () => Promise<unknown> }): void;   // processState で 1 つ。env を読んで createScheduler → start
export function schedulerSnapshot(): SchedulerSnapshot;                                 // 未起動なら { booted: false, enabled: false, jobs: [] }
```

* **`setTimeout` の連鎖**にする（`setInterval` にしない）。実行が終わってから `intervalMs` 後に次を予約するので、
  同一プロセス内で同じジョブが重ならない。タイマーは `unref()` してプロセスの終了を妨げない
* 初回は `start()` から `initialDelayMs`（既定 15 秒）後。起動直後に DB が間に合っていなくても、
  失敗はログに出して次の周期に回す（再試行の短縮はしない。§11）
* 1 回の実行（`tick`）：`prepare()` → `withConnection((c) => execute(c, job, { trigger: 'scheduled', wait: false }))`。
  **どこで例外が出ても基盤は止めない。** `log.error('job tick failed', { job, reason })` を出して次を予約する
* `stop()`：全タイマーを消し、以降 `tick` を予約しない。実行中のジョブは待たない（Next.js が SIGTERM で
  プロセスを閉じる。ロックは接続が閉じれば落ち、`job_runs` の `running` 行は残る。§11）。
  `bootScheduler` は `process.once('SIGTERM' | 'SIGINT', stop)` を登録する。2 回呼んでも安全
* `enabled: false` のときは `start()` がタイマーを 1 つも作らない。`snapshot()` は `enabled: false`、`nextRunAt: null`
* `snapshot()` は画面と API が使う。`nextRunAt` は**このプロセス**の予定。複数プロセス構成では
  プロセスごとに違う値になる（画面にその旨を注記する。§7.2）

#### 6.1.4 Plugin の起動との関係

Database Provider を差し替える Plugin や `analytics.rolledUp` を購読する Plugin は、
最初のリクエストが来るまで起動していない（`plugin/runtime.ts`）。定期実行が Plugin より先に走ると、
標準 Provider で集計してしまう。**各実行の前に `prepare`（= `ensurePluginsStartedAnonymously`）を呼ぶ。**
`prepare` が失敗した回は実行しない（ログだけ）。Application から `plugin/` を import しないよう、
`instrumentation.ts` が関数を注入する。

#### 6.1.5 1 回の実行（`application/jobs/run-job.ts`）

```ts
export type RunOutcome =
  | { readonly outcome: 'ok'; readonly run: JobRun }
  | { readonly outcome: 'skipped'; readonly run: JobRun | null }   // ロック競合（他が実行中／待機枠が埋まっている）
  | { readonly outcome: 'error'; readonly run: JobRun | null; readonly error: unknown };  // ジョブの失敗、またはロック取得そのものの失敗

export async function runJob<TInput>(
  connection: Connection,
  job: JobDefinition<TInput>,
  options: { readonly trigger: JobTrigger; readonly wait: boolean; readonly input: TInput },
): Promise<RunOutcome>;
```

手順：

1. `jobLock.acquire(connection, job.name, { waitMs: options.wait ? MANUAL_LOCK_WAIT_MS : 0 })`（§6.1.6）。
   結果は 3 通りで、**競合と失敗を区別する**（検証の反映。A-3）：
   * `{ ok: false, reason: 'busy' }`（他が保持している／このプロセスの待機枠が埋まっている）→ `job_runs` に
     `status = 'skipped'`（`finished_at = started_at`）を 1 行入れ、`log.info('job skipped', { job, trigger })`、`outcome: 'skipped'`
   * `{ ok: false, reason: 'failed', error }`（Pool 枯渇・DB 停止・権限エラーなど、ロックのセッション自体の失敗）→
     `job_runs` に `status = 'error'`、`error = jobErrorText(error)`（§6.1.7）の行を 1 行入れ、
     `log.error('job lock failed', { job, trigger, reason })`、`outcome: 'error'`。**手動 API はこれを 409 にしない**（500。§6.3）
   * `{ ok: true, lock }` → 手順 2 へ
   どちらの記録でも、直後に `trimHistory` を呼ぶ（手順 5 と同じ。検証の反映。A-4）。
   **`acquire` の呼び出し自体を `try` で包む**（検証 2 巡目の反映。L-3）。`connection.db.connection()` が
   **同期的に**投げる Provider（差し替えた Plugin の実装）だと、例外が `try` の外を素通りして
   `job_runs` に何も残らないまま `runJob` が投げてしまう。捕まえて `{ ok: false, reason: 'failed', error }` と同じ経路に落とす
2. `job_runs` に `status = 'running'` の行を入れる（`id = uuidv7()`、`runner = hostname:pid`）。`log.info('job started')`
3. `job.run(connection, input)` を呼ぶ。**ロックの接続とは別の（通常の）接続を渡す**。ジョブの中のトランザクションは従来どおり
4. 成功：`status = 'ok'`、`finished_at = now()`、`summary = 戻り値` に更新。`log.info('job finished', { job, trigger, runId, durationMs, summary })`
   失敗：`status = 'error'`、`error = jobErrorText(error)`。`log.error('job failed', { job, trigger, runId, reason: jobErrorText(error) })`。
   `outcome: 'error'`（例外は握って返す。投げない）
5. `finally` でロックを解放し、`jobRunRepository.trimHistory(connection, job.name, JOB_RUN_RETENTION)` を呼ぶ。
   **`release()` は `try/catch` で包む**（検証の反映。A-5）。ロックのセッション本体が既に失敗している場合だけ `release()` は投げうるので、
   包まないと「例外は握って返す」契約が破れる。捕まえたら `log.warn('job lock release failed', { job, reason })` を出して結果は変えない
6. 記録（1 / 2 / 4 / 5）自体が失敗した場合はログに出し、**ジョブの結果は変えない**（記録できないことと集計できないことは別）

`MANUAL_LOCK_WAIT_MS = 10_000`。API から呼ぶときだけ待つ（§6.3）。定期実行は待たずにスキップする
（次の周期にまた来る。待つと周期がずれていく）。

`skipped` の記録は、待機枠に入れず即座に弾かれた呼び出しにも 1 行書く。行数は §5.2 の切り詰め（50 件）と
既定 Rate Limit で頭打ちになる。

#### 6.1.6 排他（`infrastructure/job-lock.ts`）

```ts
export interface JobLockHandle {
  /** 通常は投げない。ロックのセッション本体が既に失敗していた場合だけ投げうる（呼ぶ側が握る。§6.1.5 手順 5） */
  release(): Promise<void>;
}

export type LockOutcome =
  | { readonly ok: true; readonly lock: JobLockHandle }
  /** 他が保持している、または**このプロセスの待機枠が埋まっている**。接続は pin していない */
  | { readonly ok: false; readonly reason: 'busy' }
  /** ロックのセッション自体が失敗した（Pool 枯渇・DB 停止・権限エラーなど）。競合ではない */
  | { readonly ok: false; readonly reason: 'failed'; readonly error: unknown };

export const jobLock = {
  acquire(connection: Connection, name: JobName, options: { readonly waitMs: number }): Promise<LockOutcome>;
};
```

* **セッションレベルの advisory lock を、Pool から 1 本だけ確保した専用の接続で取る。**
  Kysely の `connection.db.connection().execute(async (pinned) => …)` で 1 接続に固定し、
  その接続の中で `SELECT pg_try_advisory_lock($1, $2)` → ジョブ実行を待つ → `SELECT pg_advisory_unlock($1, $2)` → 接続を Pool に返す。
  トランザクションレベル（`pg_advisory_xact_lock`）にしないのは、ロールアップが (site, day) ごとに
  トランザクションを張り、Webhook 配信が HTTP を待つため。1 つの長いトランザクションで包みたくない
* キーは 2 引数形 `(JOB_LOCK_NAMESPACE, keyOf(name))`。`JOB_LOCK_NAMESPACE = 7_602_931`（固定）、
  `keyOf(name)` は `sha256(name)` の先頭 4 バイトを符号付き 32bit 整数にしたもの。
  マイグレーションのロック（`packages/cli/src/migrate/lock.ts`、1 引数の 64bit 形）とは別の鍵空間なので衝突しない
* `waitMs === 0`：`SELECT pg_try_advisory_lock($1, $2)`。`false` なら `{ ok: false, reason: 'busy' }` を返して
  **すぐ pin を解く**（往復 1 回ぶんしか占有しない）
* `waitMs > 0`：専用接続で `BEGIN; SET LOCAL lock_timeout = '<waitMs>ms'; SELECT pg_advisory_lock($1, $2); COMMIT;`。
  `lock_timeout` で待ちを打ち切り（例外 `55P03` → `{ ok: false, reason: 'busy' }`）、`SET LOCAL` はコミットで戻るので接続を汚さない。
  セッションレベルのロックはコミット後も保持される。**`COMMIT` も同じ `try` の中に入れる**（検証の反映。A-5）。
  `COMMIT` が失敗すると、ロックを取得済みのまま接続が Pool へ戻り、そのジョブが誰にも取れなくなる。
  失敗したら `pg_advisory_unlock` を試してから `{ ok: false, reason: 'failed', error }` を返す
* **競合（`busy`）とセッションの失敗（`failed`）を必ず分ける**（検証の反映。A-3）。
  「取れなかった」に丸めると、DB 停止や Pool 枯渇が「他が実行中」（`skipped` / 409）として記録され、
  監視できるようにするという 029 の目的が崩れる。`55P03`（`lock_timeout`）と `pg_try_advisory_lock = false` だけが `busy`、
  それ以外の例外はすべて `failed`
* `release()` は解放クエリの失敗を握り（`migrate/lock.ts` と同じ。接続を閉じればロックは落ちる）、`log.warn` を出す。
  ただし**ロックのセッション本体が既に失敗している場合だけ投げうる**ので、呼ぶ側（§6.1.5 手順 5）が `try/catch` で包む

##### 待機枠のゲート（検証の反映。A-1）

`pg_advisory_lock` の待ちは専用接続を pin したままブロックする。`POST /api/v1/analytics/rollup` の Permission は
`analytics.read` で**閲覧者ロールも持つ**（`migrations/014_analytics.sql`）ため、1 アカウントが並列に叩くだけで
待機中の pin が積み上がり、Pool（既定 `max = 10`）を使い切ってログイン・画面描画まで止められる。

**ジョブごとに「ロック待ちに入れるのは 1 本まで」というプロセス内のゲートを置く**（ユーザー裁定）。

```ts
// 置き場は infrastructure/job-lock.ts。プロセスに 1 つ（infrastructure/process-state.ts）
const waiting = processState('jobs.lock-waiting', () => new Set<JobName>());
```

* `waitMs > 0` の `acquire` は、`waiting` に同じ `name` があれば**接続を取らずに** `{ ok: false, reason: 'busy' }` を返す。
  無ければ `add` してから待ち、`finally` で `delete` する
* **置き場を `job-lock.ts`（Infrastructure）にした理由**：守っている資源は「DB 接続 Pool の pin」であり、
  待てる本数はロックの取得契約そのもの。`run-job.ts`（Application）に置くと、将来ロックを直接使う経路ができたときに素通りする。
  Application 層は「待つか待たないか」（`wait`）だけを決め、待ち方の上限は Infrastructure が持つ
* これでロック待ちで pin される接続は**ジョブごとに最大 1 本**。保持者 1 + 待機者 1 = ジョブごと 2、2 ジョブで最大 4 になり、
  Pool 上限 10（テストは 4）を待機だけで使い切れない。弾かれた呼び出しは即座に `skipped` → 409 で返る
* **複数プロセス構成ではプロセスごとに 1 本**（ゲートはプロセス内の状態）。プロセス数ぶんは待機しうるが、
  各プロセスの Pool は別なので、あるプロセスの Pool が待機で埋まることはない
* `waitMs === 0`（定期実行）はそもそも待たないのでゲートを通さない

##### Database Provider への暗黙の要求（boundary-guardian の指摘）

この排他は **`connection.db.connection()` が 1 つの物理セッションに親和すること**を前提にしている。
標準の PostgreSQL Provider（`database/postgres-provider.ts`）はこれを満たす。
Plugin が Database Provider を差し替え、その実装が要求ごとに別の接続へ振り分ける（プロキシ・プール分散）作りだと、
**`pg_try_advisory_lock` を取ったセッションと `pg_advisory_unlock` を呼ぶセッションが別になり、排他が例外も警告も出さずに効かなくなる。**
差し替える Provider は**セッション親和性を保つこと**を要求する（§9 に明記）。
`DatabaseProvider` の型でこれを強制する（`session()` を契約に足す等）のは Provider 契約そのものの変更であり、
029 のスコープ外とする（§11）。

#### 6.1.7 例外メッセージの秘匿（検証の反映。A-7）

`job_runs.error` とログの `reason` には例外のメッセージがそのまま入る。Database Provider を差し替えた Plugin の例外は
任意の文字列になりうる（接続文字列・トークンを含みうる）。「入れない」をコメントで宣言するだけでは守られない。

**既存の秘匿処理はそのままでは再利用できない。** `database/postgres-provider.ts` の `redact(error, connectionString)` は
モジュール内の私有関数で、引数に接続文字列を要求し、戻り値が `Error`（スタックを差し替える）。
`run-job.ts` は接続文字列を知らない（`DatabaseProvider` は公開していないし、差し替え後は `DATABASE_URL` とも限らない）。
`infrastructure/logging.ts` の `maskSecrets` はキー名で落とす仕組みで、自由文には効かない。

そこで**同じ考え方を小さな純粋関数として切り出す**。`infrastructure/secret-text.ts`：

```ts
/** 自由文から接続情報らしきものを伏せる。入力を変えずに新しい文字列を返す */
export function redactSecrets(text: string): string;
```

* (a) `scheme://user:password@host` 形式の URL を見つけたら credential 部を `***` にする（Provider を問わず効く）
* (b) `process.env['DATABASE_URL']` が設定されていれば、その全体と、URL として解釈できるならその password 部分の
  完全一致を `***` にする（標準構成の取りこぼしを塞ぐ）

`run-job.ts` は `jobErrorText(error) = truncateError(redactSecrets(message))` の順で通す。
**伏せてから切る。** 逆にすると、途中で切れた接続文字列が (b) の完全一致に掛からず残る。
`job_runs.summary` は各ジョブが組み立てる固定キーの数値・日付だけなので、この経路には入らない。

##### 原則：自由文をログへ載せる経路すべてに通す（検証 2 巡目の反映。M-2）

`job_runs` だけを伏せても意味が無い。**同じ例外が別経路からログへ無加工で出ていた。**

* `api/route.ts` の catch-all（`log.error('unhandled error in route', { reason: error.message })`）。
  両ジョブ API は生の例外を投げるので、ロック取得やジョブの失敗がここへ来る
* `application/jobs/scheduler.ts` の `reasonOf`（`log.error('job tick failed', …)`）。こちらは
  **Plugin が差し替えた Provider の例外**を受ける。標準 Provider の `redact()` を通らないため、接続文字列が素で出うる

どちらも `redactSecrets` に通す。`logging.ts` の `maskSecrets` は**キー名**で落とす仕組みなので、
`reason` という名前の値の中身は素通りする（キー名判定と自由文の秘匿は別の仕事で、片方では足りない）。
**自由文（例外メッセージ・外部からの文字列）をログや DB へ載せるときは `redactSecrets` を通す**、を原則にする。
応答本文は従来どおり何も出さない（`05` §11）。

##### 接続断をログに出す（検証 2 巡目の反映。L-2）と `postgres-provider.ts` の変更

`database/postgres-provider.ts` は Pool の `error` を `() => undefined` で握りつぶしており、
**接続断が完全に無音**だった。029 の主題（障害を `busy` に丸めず見えるようにする）と一貫しないので、
`log.warn('database connection error', { reason: redactSecrets(…) })` を出す。

あわせて、**貸出中クライアントの `error` も購読する**（ユーザー裁定により 029 に含める）。

* pg-pool は接続を貸し出している間だけ自前の `error` 監視を外す。その最中にサーバー側で接続が切られると
  （フェイルオーバー、`idle_session_timeout`、`pg_terminate_backend`）購読者が居なくなり、
  Node が `uncaughtException` を投げて**プロセスごと落ちる**
* 029 のロック専用接続は 1 本を長く借りたままにするため、この窓が実運用の長さになって顕在化した
* pg-pool 3.14.0 / pg 8.23.0 のソースで、(1) リスナがリークしないこと、(2) 実行中クエリの失敗は
  `emit` の前に reject されること（購読しても既存のエラー経路を変えない）、(3) 死んだ接続は `_release` で
  Pool から除かれること、を確認済み
* **この備えは `createPostgresProvider` の中にあるので、独自に `pg.Pool` を作る Plugin の Database Provider には効かない**（§9）

`postgres-provider.ts` の私有関数 `redact()`（例外の再構築とスタックの差し替えまで行う）を `redactSecrets` へ寄せるのは
別の関心なので**今回は触らない**（§11 #13）。

### 6.2 登録するジョブ（`application/jobs/definitions.ts`）

| 名前 | 間隔（既定） | 実行 | summary |
| --- | --- | --- | --- |
| `analytics.rollup` | 15 分 | `rollupAnalytics(connection, input ?? await scheduledRollupRange(connection))`（下記）。日付は `TORIFUNE_TIMEZONE` で（`rollup/route.ts` と同じ `daysAgoInTimeZone` / `dateInTimeZone`） | `{ from, to, days, points }` |
| `webhook.deliver` | 1 分 | `deliverPendingWebhooks(connection)` | `{ attempted, delivered, failed }` |

* **定期ロールアップの対象期間（裁定 #5）**：`to = 今日`。`from` は
  `jobRunRepository.findLatestSucceeded(connection, 'analytics.rollup')` の `started_at` を `TORIFUNE_TIMEZONE` で日付にしたもの。
  ただし `today − 7` 日より前にはしない（**最大 7 日さかのぼる**）。成功の記録が無ければ従来どおり `from = 昨日`。
  計算は `domain/jobs/job.ts` の純関数 `scheduledRollupFrom({ lastSucceededStartedAt: string | null, today: string }): string`
  （`max(lastSucceededStartedAt ?? shiftDays(today, -1), shiftDays(today, -7))`）に置き、`ROLLUP_JOB.run` が
  `findLatestSucceeded` の結果と `todayInTimeZone` を渡す。短い停止（数日）は次の定期実行が人手なしで埋め、
  7 日を超える停止は API で流し直す（マニュアル §4）。手動 API（`input` あり）はこの計算を通らない
* 境界日（最後の成功の開始日）を含めて流し直すのは、その日の集計が開始時刻までの生ログしか含んでいないため。冪等な差し替えなので二重にならない
* Webhook の間隔 1 分の根拠：`retryDelayMs` は 1 → 2 → 4 → 8 分で、最短の再試行間隔が 1 分。
  周期が 1 分なら予約どおりの時刻に送れる。1 回の実行は `BATCH_SIZE = 50` 件までで、
  `webhook_deliveries_pending_idx (status, next_attempt_at)` で引くので、配信が無いときの 1 分ごとのコストは索引 1 回
* `rollupAnalytics` / `deliverPendingWebhooks` 自体は変えない。`analytics.rolledUp` の発火も従来どおり
  （集計が済んだ単位で 1 回。定期実行でも同じ。`01` §10.3）
* Plugin からのジョブ登録は無い（§9 / §11）

### 6.3 既存 API を同じ経路に載せる

#### `POST /api/v1/analytics/rollup`（`analytics.read`、`pruneOlderThanDays` は `system.manage`。現行どおり）

```ts
assertRollupRange(from, to);   // 期間の検査（下記。検証の反映。A-2）
const outcome = await runJob(context.connection, ROLLUP_JOB, { trigger: 'manual', wait: true, input: { from, to } });
if (outcome.outcome === 'skipped') throw new JobBusyError(ROLLUP_JOB.name);   // ロック競合だけ 409
if (outcome.outcome === 'error') throw outcome.error;                         // ジョブの失敗もロックの失敗も 500
// prune はロックの外で現行どおり
```

* 応答の形 `{ from, to, days, points, pruned }` は変えない。`job_runs` に `triggered_by = 'manual'` で記録される
  （外部 cron 運用でも「最終集計（全体）」が動く）
* body で `from` / `to` を省略したときの既定は現行どおり「昨日と今日」（API の互換）。§6.2 の「最後の成功から最大 7 日」は
  定期実行（`input` 無し）だけの規則。API 側は常に `input` を渡す
* **期間の幅を検査する（検証の反映。A-2）。** 現行は形式（`YYYY-MM-DD`）しか見ておらず、
  `{"from":"1000-01-01","to":"9999-12-31"}` で生ログの全期間を走査でき、029 以降はその間ロックを握って定期集計まで止まる。
  `domain/analytics/analytics.ts` の `isValidRange` / `rangeDays` / `MAX_RANGE_DAYS`（400）を使い、
  逆転なら `ValidationError('Analytics', 'to', '期間を確認してください（開始日以降にする）。')`、
  400 日超なら `ValidationError('Analytics', 'from', '期間が長すぎます（400日以内にしてください）。')` を投げる。
  `api/route.ts` が 422 に写す。**画面の期間上限（`listAnalytics` / `listAnalyticsBreakdown` と同じ 400 日）と、
  マニュアル §4 の「400 日を超える場合は分割する」に揃う。** 400 日ちょうどは通す
* **`isValidRange` に実在日付の検査を足す（検証 2 巡目の反映。M-1）。**
  現行の `isValidRange` は正規表現と文字列比較だけ、`rangeDays` は `Date.parse` 依存で、
  `0000-00-00` / `9999-99-99` / `2026-02-30` は形式検査を通るのに `Date.parse` が `NaN` を返す。
  `NaN > MAX_RANGE_DAYS` は `false` なので、**上の幅の検査を素通りしていた**。
  閲覧者（`analytics.read` だけ）がロックを取得したうえで `job_runs` に任意の `error` 行を積め、
  `GET /api/v1/jobs` の監視信号を汚せる。
  * `domain/analytics/analytics.ts` に私有関数 `isCalendarDate(value)`（年・月・日を数値で取り出し、
    月ごとの日数と閏年で実在を判定する）を足し、`isValidRange` の中で両端に掛ける。**シグネチャは変えない**
  * `Date.UTC` を使わずに数値で判定する。`Date.UTC` は 0〜99 年を 1900 年代へ写すため、
    `0099-01-01` のような入力で判定が狂う
  * `rangeDays` は `Date.parse` 依存のままにし、**「`isValidRange` を通した値だけを渡す」ことを JSDoc の契約**として書く
  * **入口 1 か所で塞ぐので、029 の範囲外にも及ぶ。** `assertRollupRange`（`POST /analytics/rollup`）だけでなく、
    既存の `assertRange`（`listAnalytics` / `listAnalyticsPage` / `listAnalyticsBreakdown` / `listTopPathsPage` / `recordAnalytics`）と
    `app/analytics/page.tsx` の `custom` 期間（`isCalendarDate` を自前で持っていた箇所）が同じ判定に乗る。
    `GET /analytics` 系は 422 が増える方向の変更で、通っていた要求が落ちるのは**元々不正だった日付だけ**
* **ロック競合（`skipped`）のときだけ 409 `CONFLICT`**。`JobBusyError`（`domain/jobs/job.ts`）を
  `api/route.ts` が `errorResponse('CONFLICT', { job: ['実行中のため受け付けられません。しばらくしてからやり直してください。'] }, { 'Retry-After': '10' })` に写す。
  `details` を添えるのは、`CONFLICT` の既定文言「すでに使用されています。」では運用者に理由が伝わらないため。
  待機枠が埋まっている（§6.1.6）ときも同じ 409 だが、**待たずに即座**に返る
* **ロックのセッション自体の失敗（`failed`）は 409 にしない。** 500（`INTERNAL_ERROR`。内容は応答に出さない）とし、
  `job_runs` には `status = 'error'` が残る。DB 停止や Pool 枯渇を「他が実行中」と表示しないため（A-3）
* 定期実行と手動が同じ日を同時に流すと、`replaceCorePoints` の DELETE → INSERT が PK 違反で片方失敗しうる。
  同じロックに載せることで起きなくなる（要件 §2.1「二重に走っても保存値が壊れない」の担保）

#### `POST /api/v1/webhooks/deliver`（`system.manage`。現行どおり）

同じ形。`runJob(connection, WEBHOOK_JOB, { trigger: 'manual', wait: true, input: undefined })`。
応答 `{ attempted, delivered, failed }` は変えない。引数を取らないので期間の検査は無い。

### 6.4 `getAnalyticsStatus` の拡張（`analytics.read`、UseCase 名 `analytics.status`）

`{ siteId }` → `AnalyticsStatus`（§5.4）。問い合わせは次の 6 項目
（**DB を使う 5 項目＝SQL 6 本**と、メモリ参照の `schedulerSnapshot()` 1 項目）で、**生ログの期間全体を舐めるものは無い**。

| 値 | 問い合わせ | 使う索引 | 行数 |
| --- | --- | --- | --- |
| `analyticsLastSeenAt` | `findSiteLastSeen`（既存） | `sites_pkey` | 1 |
| `lastRollupAt` | `findLastRollupAt`（既存。残す）：`SELECT max(updated_at) FROM analytics WHERE site_id = ? AND source = 'core'` | `analytics_site_metric_idx (site_id, metric, metric_date DESC)` の `site_id` 先頭で絞る（集計値の表。生ログではない） | 集計 1 行 |
| `lastReceivedAt` | `analyticsRepository.findLatestAccessAt(siteId)`：`SELECT occurred_at FROM access_logs WHERE site_id = ? ORDER BY occurred_at DESC LIMIT 1` | `access_logs_site_time_idx (site_id, occurred_at DESC)` | 1 |
| `pending` | `analyticsRepository.countAccessSince(siteId, since, 1000)`：`SELECT count(*) AS total, count(*) FILTER (WHERE device = 'bot') AS bots FROM (SELECT device FROM access_logs WHERE site_id = ? [AND occurred_at >= ?] ORDER BY occurred_at DESC LIMIT 1000) t`。`capped = total === 1000` | 同上 | ≤ 1000 |
| `rollup.lastSucceededAt` / `lastRun` | `jobRunRepository.findLatest('analytics.rollup')` と `findLatestSucceeded('analytics.rollup')`（`WHERE job_name = ? [AND status = 'ok'] ORDER BY started_at DESC LIMIT 1`） | `job_runs_job_started_idx` | 1 + 1 |
| `rollup.scheduled` / `intervalMinutes` / `nextRunAt` | `schedulerSnapshot()`（メモリ） | — | — |

* `since` = 最後に成功したロールアップの `started_at`。実行中に届いた分を「集計済み」に数えないよう終了時刻ではなく開始時刻を境にする（数件の過大評価はある）。
  成功したことが無ければ `since = null`（全件。ただし 1000 件で打ち切る）
* `siteId` が UUID でない・サイトが無い → `NotFoundError`（現行どおり）。`countAccessSince` / `findLatestAccessAt` も
  `UUID_PATTERN` で弾いて 500 にしない（`findSiteLastSeen` と同じ）
* `findLastRollupAt`（`analytics.updated_at` の最大）は**残す**（裁定 #7）。`analytics` の行を `site_id` で絞って `max` を取るもので、
  生ログには触らない。現行どおり `UUID_PATTERN` で弾く
* `analytics-repository.ts` で `access_logs` に触る関数は
  `aggregateDailyBreakdown` / `maxOccurredAtBySite` / `deleteAccessLogsOlderThan` / `recordAccess` / `findSiteByPublicKey` に
  **`findLatestAccessAt` / `countAccessSince` を足した 7 つ**になる（`028` #40 の改訂。§12）。
  足す 2 つは `LIMIT` で行数を固定した診断用の読み取りで、期間で集計するものではない

### 6.5 `listJobStatuses`（新規。`system.manage`、UseCase 名 `jobs.status`）と `GET /api/v1/jobs`

```ts
export interface JobStatus {
  readonly name: JobName;
  readonly scheduled: boolean;         // このプロセスで定期実行が有効か
  readonly intervalMinutes: number;
  readonly nextRunAt: Date | null;     // このプロセスの予定
  readonly running: boolean;           // このプロセスで実行中か
  readonly lastRun: JobRun | null;     // 直近の実行（skipped 含む）
  readonly lastSuccess: JobRun | null; // status = 'ok' の直近
  readonly recentErrors: readonly JobRun[];   // status = 'error' の直近 5 件（新しい順）
}
export const listJobStatuses = defineUseCase<Record<string, never>, readonly JobStatus[]>({ name: 'jobs.status', permission: 'system.manage', … });
```

`JOB_NAMES` の順で常に 2 件返す（未登録・未実行でも `lastRun: null` で返す）。
Repository：`findLatest` / `findLatestSucceeded` / `listRecentErrors(name, 5)`。すべて `job_runs_job_started_idx`。

API：`GET /api/v1/jobs`

* `operationId: listJobStatuses`、`summary: '定期実行ジョブの状態を返す'`、Permission `system.manage`
* 200 `{ data: JobStatus[] }`（`listEnvelope(jobStatusSchema)`）。日時は ISO 8601 文字列。`JobRun` は
  `{ id, jobName, triggeredBy, status, startedAt, finishedAt, error, summary, runner }`
* 応答スキーマを宣言する（`openapi-coverage.test.ts` の「未宣言の一覧」を増やさない）
* 未認証 401、権限不足 403。Rate Limit は既定
* 監視から叩く用途（「最後の成功が N 分より古ければ警告」）。画面の受信状況（`getAnalyticsStatus`）は API に出さない（`028` §6.4 のまま。要るのは運用者であり、`/jobs` で足りる）

## 9. Plugin API への影響

**変更なし。`PLUGIN_API_VERSION` は上げない。**

| 場所 | 変更 |
| --- | --- |
| `analytics.rolledUp` | ペイロード `{ from, to, points }` は同じ。発火の契機が「API」から「API または定期実行」に増えるだけ |
| Data API / Event API / UI API | 変更なし |
| Database Provider（接続断への備え） | `createPostgresProvider` が入れる備え（Pool と**貸出中クライアント**の `error` 購読。§6.1.7）は標準 Provider の中にあり、**独自に `pg.Pool` を作る Plugin の Provider には効かない**。長く借りたままの接続（ロック専用接続）を持つ実装は、貸出中の `error` を自分で購読すること。購読者が居ないと Node の `uncaughtException` でプロセスごと落ちる |
| Database Provider | 定期実行も `getConnection()` 経由で Provider を使う。Plugin が差し替えた Provider は `prepare` の後に使われる（§6.1.4）。**差し替える Provider は `db.connection()` のセッション親和性を保つこと**（1 つの `connection()` スコープ内のクエリが同じ物理セッションで実行されること）。要求ごとに別接続へ振り分ける実装だと、advisory lock による排他が**例外も警告も出さずに効かなくなる**（§6.1.6）。`DatabaseProvider` の型でこれを強制するのは Provider 契約そのものの変更なので 029 では行わない（§11） |
| Plugin からのジョブ登録 | 提供しない（§11）。Plugin は `activate()` で自分のタイマーを持てる |

### 検証結果の反映（2026-09-04。spec-verifier / boundary-guardian / security-reviewer）

66. (B) **待機枠のゲート（A-1）**：別の `pg.Client` がロックを保持している状態で `jobLock.acquire(…, { waitMs: 5000 })` を
    2 本同時に呼ぶと、1 本目は待ち、2 本目は**即座に**（100ms 以内）`{ ok: false, reason: 'busy' }` を返す。
    2 本目が返った時点でロックは保持側のままで、`pg_stat_activity` から数えたこの Pool の接続数が 1 本目の待機中と変わらない
    （待機で pin されるのはジョブごとに 1 本）。1 本目が `busy`（`lock_timeout`）で抜けた後は、次の `acquire` がまた待機に入れる
67. (C) 同（API 側）：ロック保持中に `POST /api/v1/analytics/rollup` を 5 本同時に投げると、**1 本だけが約 10 秒後**に 409 を返し、
    残り 4 本は 1 秒以内に 409 を返す。その間に別のリクエスト（`GET /api/v1/auth/me`）が 200 を返す（Pool が待機で埋まらない）
68. (B) `waitMs === 0`（定期実行）はゲートを通らない：ロック保持中に `runJob(…, { wait: false })` を 5 本同時に呼ぶと
    5 本とも `skipped` になり、待たない（全体が 1 秒以内に終わる）
69. (B) **競合と失敗の区別（A-3）**：ロック取得のクエリが失敗する状況（`job_runs` を持つ scratch DB の Provider を
    `disconnect()` 済みにする、または `db.connection()` が投げるよう差し替える）で `runJob` は `outcome: 'error'` を返し、
    `job_runs` に `status = 'error'` の行が残る。`skipped` にはならない
70. (C) 同（API 側）：ロック取得が失敗する状況の `POST /api/v1/analytics/rollup` は **409 ではなく 500**（`INTERNAL_ERROR`）を返し、
    応答本文に例外の内容・SQL・接続文字列が含まれない
71. (B) **skipped も切り詰める（A-4）**：ロック保持中に `runJob(…, { wait: false })` を 60 回呼ぶと、その `job_name` の
    `job_runs` は 50 件で、すべて `skipped`。`ok` の行が混ざっていても合計 50 件を超えない
72. (B) **`release()` の例外を握る（A-5）**：`release()` が投げるロックハンドルを注入しても `runJob` は例外を投げずに
    `outcome: 'ok'` を返し、`job_runs` の行は `ok` のまま。ログに `level: 'warn'`、`message: 'job lock release failed'` が出る
73. (B) 同（`COMMIT` の保護）：`waitMs > 0` の取得で `COMMIT` が失敗する状況を作ると `{ ok: false, reason: 'failed' }` が返り、
    その後**別の接続から同じ鍵の `pg_try_advisory_lock` が取れる**（ロックを握ったまま接続が Pool へ戻らない）
74. (A) **秘匿（A-7）**：`redactSecrets` が `postgresql://torifune:s3cret@db:5432/torifune` を含む文字列の credential を `***` にし、
    `DATABASE_URL` を設定した状態でその値そのもの・その password 部分を `***` にする。無関係な文字列は変えない
75. (B) 同（経路）：例外メッセージに `DATABASE_URL` の値を含むジョブを実行すると、`job_runs.error` にも

76. (C) **期間の検査（A-2）**：`POST /api/v1/analytics/rollup` に `{"from":"1000-01-01","to":"9999-12-31"}` は 422、

### 再検証の反映（2026-09-04。security-reviewer 2 巡目）

前回【重大】としたロック待ちの Pool 枯渇（§6.1.6 の待機枠のゲート）は**解消**と判定された
