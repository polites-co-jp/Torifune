## 2. 責務境界（boundary-guardian 観点）

| 検査 | 結果 |
| --- | --- |
| 認可の判定が Application 層にある | ✅ `authorize.ts` / `use-case.ts`。API Layer は変換のみ |
| `domain/permission.ts` が上位層へ依存しない | ✅ import ゼロ |
| Permission が固定の union 型になっていない | ✅ 文字列＋実行時レジストリ。Plugin が足せる |
| `system.*` を Plugin に取らせない | ✅ 登録時に拒否。テストあり |
| `AuthorizationContext` の組み立て口が1つ | ✅ `buildAuthorizationContext` のみ。リクエストの値が入る経路が無い |
| SaaS 固有の概念 | ✅ なし |

### 新たに追加した境界検査

`apps/web` が `@torifune/cli` を**テスト支援以外から**参照することを ESLint で禁止した。
テストの使い捨てDB作成のために devDependency として追加したため、
本番コードへ紛れ込むとアプリに CLI が同梱される。規則が実際に発火することを確認済み。

### 指摘

#### F-1（記録）`declarePublicUseCase` は実行経路を持たない

ログインや初回セットアップは認証前に呼ばれるため `AuthorizationContext` を取れず、
`defineUseCase` の形に収まらない。無理に通すと引数が嘘になる。

そこで「宣言だけ」を登録する `declarePublicUseCase` を用意した。
**実行経路は従来どおり**で、監査の一覧にだけ載る。

弱点：新しい公開処理を作ったとき、**宣言し忘れると監査に載らない**。
`defineUseCase` の「呼び忘れが構造的に起きない」性質は、ここには及ばない。

対応：`007-sites` 以降のドメイン UseCase はすべて `defineUseCase` を通す。
認証系の公開処理は増えないため、実害は小さいと判断する。

## 3. セキュリティ（security-reviewer 観点）

| 観点 | 結果 |
| --- | --- |
| 未認証と権限不足を区別する | ✅ 401 / 403 |
| 未認証は Permission を持っていても 401 | ✅ 認証を先に見る。組み立て側の誤りが認可の穴にならない |
| エラーに Permission 名を出さない | ✅ 権限体系の探索に使われるため |
| クライアントの値で昇格できない | ✅ 組み立て口が1つ。テストあり |
| 既定で権限を持たせない | ✅ ロール未割り当ては 0 件 |
| Plugin による権限の詐取 | ✅ `system.*` を拒否 |
| 未登録 Permission の要求 | ✅ 例外。常に 403 になる実装ミスを黙認しない |
| 無効化の即時性（`002` から継続） | ✅ 毎リクエストで users とロールを引く |

### 指摘

#### S-1（記録）`unregisterPermissionsOf` は割り当て済みの権限を消さない

Plugin を無効化するとその Permission はレジストリから消えるが、
`role_permissions` に残った行はそのまま。再有効化すれば元に戻る。

**残っていても害はない**：`requirePermission` はレジストリを引くため、
未登録の Permission は要求できず、事実上失効する。
むしろ再有効化のたびに割り当て直させるほうが運用事故を招く。

`011-plugin-runtime` で Plugin のアンインストール時の扱いを設計する。

## 4. テスト基盤の改善（このスプリントで行った）

結合テストが**共有のテストデータベース**を使っており、
`auth.integration.test.ts` の後始末（`DELETE FROM users`）が
並列実行中の `authorization.integration.test.ts` の前提を壊していた。

**テストファイルごとに使い捨てのデータベースを作る**方式へ変更した
（`src/test-support/database.ts`）。マイグレーションを適用してから Provider を差し替える。

E2E も同様に、複数ファイルが「管理者0人」の状態を奪い合っていた。
`globalSetup` で既知の管理者を1人だけ用意し、E2E は常に「管理者がいる状態」から始める。
「管理者が0人のときの挙動」は結合テスト側が持つ（そちらは DB を自分で制御できる）。

**S7 以降で結合テストが増えるため、ここで直しておく必要があった。**
