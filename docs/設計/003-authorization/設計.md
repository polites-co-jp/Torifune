# 認可 設計

## 1. 目的

認証済みユーザーが「何をしてよいか」を判定する仕組みを作る。

満たすべきことは4つ。

1. **認可を Application 層（UseCase）で強制する。**
   画面から直接呼んでも REST 経由でも Plugin 経由でも、同じ判定が働くようにする
2. **Permission チェックを持たない UseCase を作れなくする。**
   規約に頼ると、いつか抜ける。機械的に検出できる形にする
3. **Plugin が独自の Permission を登録できる余地を残す。**
   固定の enum にすると、Plugin の Permission を後から足せない
4. **UI の表示制御を、認可そのものと取り違えない構造にする。**
   「ボタンを隠す」は認可ではない

## 3. スコープ

### やること

* Permission レジストリ（本体の Permission ＋ Plugin が足す Permission）
* ユーザーの実効 Permission を求める仕組み（User → Role → Permission）
* UseCase が Permission を要求する共通の仕組み
* 未認証 401 / 権限不足 403 の区別
* 「現在のユーザーが持つ Permission」を返す API
* Permission チェックを持たない UseCase を検出する仕組み
* ロール管理の最小限（一覧・ユーザーへの割り当て）
* `002-authentication` の未検証項目（試行制限の閾値・時間窓）のユニットテスト

### やらないこと

* ロール・権限の管理画面（`015-settings`）
* リソース単位の細かい権限（「このサイトだけ編集可」）。
  今回は機能単位の Permission のみ
* Plugin による Permission の実登録（`011-plugin-runtime`）。契約と器だけ作る

```text

│   ├── permission.ts              Permission 名の型と検証
│   ├── role.ts                    Role
│   └── role-repository.ts         Repository Interface
├── application/
│   └── authorization/

│       ├── authorize.ts           requirePermission / 認可エラー
│       ├── effective-permissions.ts ユーザーの実効 Permission
│       └── use-case.ts            Permission を要求する UseCase の定義形式

    └── authorize.ts               認可エラー → 401/403 の変換
```

**認可の判定は Application 層に置く。** API Layer には「エラーを HTTP に写す」だけを置く。

## 5. データモデル

`001_initial.sql` の `roles` / `permissions` / `user_roles` / `role_permissions` を使う。
新しいテーブルは作らない。

### 実効 Permission の求め方

```sql
SELECT DISTINCT rp.permission_name
FROM user_roles ur
JOIN role_permissions rp ON rp.role_id = ur.role_id
WHERE ur.user_id = $1
```

**ロールを持たないユーザーは Permission を1つも持たない。**
既定で何か持たせると、ロールの割り当てを忘れたユーザーが操作できてしまう。

## 6. API

| メソッド | パス | 認証 | Permission | 説明 |
| --- | --- | --- | --- | --- |
| GET | `/api/v1/auth/me` | 必要 | — | 既存。**`permissions` を追加する** |
| GET | `/api/v1/roles` | 必要 | `user.manage` | ロール一覧 |
| GET | `/api/v1/permissions` | 必要 | `user.manage` | 登録済み Permission 一覧 |

`/api/v1/auth/me` の応答:

```jsonc
{
  "data": {
    "id": "…", "loginId": "alice", "displayName": "Alice", "email": "…",
    "permissions": ["content.read", "content.write", "site.read"]
  }
}
```

**この配列を UI の表示制御に使う。認可には使わない。**
クライアントが書き換えられる値なので、サーバー側の判定とは無関係であること。

## 7. 画面

このスプリントでは画面を作らない。
`005-ui-shell` が `permissions` を受け取って表示制御するときに使う。

## 8. 権限（Permission）

### Permission 名の規約

```text
<resource>.<action>
```

* `resource` は英小文字・数字・アンダースコア。先頭は英字
* Plugin が足す Permission は Plugin ID を接頭辞にする（例：`seo.report.read`）
* 予約：`system.*` は本体のみ

### 本体の Permission（`001_initial.sql` で投入済み）

```text
site.read     site.write     site.delete
content.read  content.write  content.delete
social.read   social.write   social.delete
user.manage   plugin.manage  system.manage
```

### 認可エラーの扱い

| 状況 | 例外 | HTTP |
| --- | --- | --- |
| 未認証 | `UnauthenticatedError` | 401 |
| 認証済みだが Permission 不足 | `ForbiddenError` | 403 |

**この2つを取り違えない。**
未認証に 403 を返すとログインを促せず、権限不足に 401 を返すと再ログインを促してしまう。

## 9. Plugin API への影響

`packages/plugin-api` にはまだ公開しない。ただし次を S10 の下敷きにする。

* `PermissionName` 型（文字列の別名ではなく、形式を検証した型）
* Plugin が Manifest で Permission を宣言し、レジストリへ登録する契約
* `requirePermission` に相当する、Plugin から使える認可関数

Permission を固定の union 型にしない。**Plugin が足せなくなる。**

## 10. 受け入れ条件

### Permission レジストリ

1. 本体の Permission 12 種が登録されている
2. 未登録の Permission 名を要求すると、**起動時ではなく呼び出し時に**エラーになる
3. 形式が不正な Permission 名（大文字・ドット無し・先頭が数字）の登録が拒否される
4. 同じ名前を二重に登録しようとすると拒否される
5. Plugin が登録した Permission が一覧に含まれる

### 実効 Permission

6. `administrator` ロールのユーザーが 12 種すべてを持つ
7. `viewer` ロールのユーザーが read 系 3 種だけを持つ
8. **ロールを持たないユーザーは Permission を1つも持たない**
9. 複数ロールを持つユーザーは、和集合を持つ
10. 同じ Permission を複数ロールから得ても重複しない
11. 存在しないユーザーの Permission は空

### 認可

12. Permission を持つユーザーの UseCase 呼び出しが成功する
13. Permission を持たないユーザーの呼び出しが `ForbiddenError` になる
14. 未認証の呼び出しが `UnauthenticatedError` になる
15. `UnauthenticatedError` が 401 に、`ForbiddenError` が 403 に写る
16. **エラー応答に、要求された Permission 名が含まれない**
    （どの権限が足りないかを未認証の相手へ教えない）

### 検出

17. Permission を要求せずに定義された UseCase を列挙できる
18. **保護対象の UseCase がすべて Permission を要求している**ことをテストで確認できる

### API

19. `/api/v1/auth/me` が `permissions` を返す
20. `permissions` が実効 Permission と一致する
21. `/api/v1/roles` が `user.manage` を要求する（無い場合 403、未認証 401）
22. `/api/v1/permissions` も同様

### 権限昇格

23. **リクエストボディに `permissions` を入れても、判定に影響しない**
24. **リクエストボディに `roles` を入れても、判定に影響しない**
25. 他ユーザーの ID を指定しても、そのユーザーの権限で実行されない

### 試行制限（`002-authentication` からの持ち越し）

26. IP 単位の閾値に到達すると弾かれる（ポリシーを注入して検証）
27. 時間窓を過ぎると再び試行できる（時計を注入して検証）
