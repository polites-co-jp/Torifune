## 2. 設計上の判断

### 2.1 「Permission を要求しない UseCase」を検出する方法

規約（「必ず `requirePermission` を呼ぶ」）に頼ると、いつか抜ける。
**UseCase を定義する形式そのものに Permission を含める。**

```ts
export const listSites = defineUseCase({
  name: 'site.list',
  permission: 'site.read',
  handler: async (ctx, input) => { … },
});
```

`defineUseCase` が返すオブジェクトは `permission` を必ず持つ。
`permission: null` を明示したものだけが認可なしになり、
**その一覧をテストで検査できる**（意図しない `null` が増えたら落ちる）。

これなら「呼び忘れ」が構造的に起きない。呼ぶのは `defineUseCase` の中だから。

### 2.2 認可の文脈（AuthorizationContext）

```ts
interface AuthorizationContext {
  readonly identity: UserIdentity | null;   // null = 未認証
  readonly permissions: ReadonlySet<PermissionName>;
  readonly connection: Connection;
}
```

**`permissions` はサーバー側で組み立てたものだけを入れる。**
リクエストから受け取った値をここへ入れる経路を作らない。
型で防げないので、組み立てる関数を1つに絞る（`buildAuthorizationContext`）。

### 2.3 レジストリを実行時に持つ理由

Permission を TypeScript の union 型にすると、Plugin が足せない。
文字列 ＋ 実行時レジストリにする。

未登録の Permission を要求したら**呼び出し時にエラー**にする。
起動時に検証しないのは、Plugin が後から登録するため。

### 2.4 既存 UseCase の移行

`002-authentication` の UseCase（login / logout / setup / password-reset）は
**認証前に呼ばれる**ため、Permission を要求しない。
`permission: null` を明示し、その理由をコメントに書く。

`getCurrentUser` も同様（認証状態を調べる処理そのもの）。

### 2.5 試行制限のテスト（持ち越し分）

`createRateLimiter` はポリシーを引数で取れる。時計は `now` を引数で受けている。
**インメモリの `LoginAttemptRepository` を用意**してユニットテストにする。
DB を使わないので、時間窓の経過も自由に作れる。

**破壊的変更：なし**

## 5. リスク

| リスク | 対応 |
| --- | --- |
| `defineUseCase` が窮屈で、結局使われない | 引数を最小にする。既存 UseCase を全部移行して実用性を確かめる |
| 実効 Permission の取得が毎リクエスト走り遅くなる | 1クエリで済む。`user_roles` と `role_permissions` に索引あり |
| レジストリがモジュール状態になり、テスト間で漏れる | リセット関数を用意し、テストで使う |
