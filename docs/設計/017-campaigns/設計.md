# 017-campaigns 設計

## 1. 目的

キャンペーン（`02_データベース設計.md` §5.7、`05_API設計.md` §19、
`06_画面設計.md` §14）。`002-Torifune機能完成` T5。

`001` が「次の計画へ送るもの」として外していたドメイン。
コード全体で `campaign` の文字列が1件もヒットしない状態から始める。

## 2. 仕様が言っていること

仕様の記述は**薄い**。

* §5.7：「マーケティングキャンペーンを管理する」、テーブル名 `campaigns`
* §19：`/api/v1/campaigns` の CRUD
* §14：一覧 / 新規作成 / 編集 / 分析。
  「キャンペーンとWebサイト、SNS投稿等を関連付けられる構造を想定する」

**具体的な項目は決まっていない。** ここで決める。

## 3. 決めたこと

### 3.1 キャンペーンは「期間を持った取り組み」とする

持たせる項目は次に絞る。

| 項目 | 理由 |
| --- | --- |
| 名前 | 見分けるため |
| 説明 | 何のための取り組みかを残すため |
| 状態（下書き / 実施中 / 終了 / 中止） | 一覧で絞るため |
| 開始日・終了日 | **キャンペーンを他と分けるのは期間**であるため |
| 対象サイト | §14 の「Webサイトと関連付けられる構造」 |

**予算・目標値・実績は持たない。** 何を指標にするかは利用者ごとに違い、
決め打つと合わない人が使えなくなる（`CLAUDE.md` の「汎用性」）。
必要なら Plugin が `plugin_store` に持つ。

### 3.2 サイトとの関連は「多対多」にする

1つのキャンペーンが複数サイトにまたがるのは普通で、
逆に1サイトが複数キャンペーンの対象になるのも普通。
片方向にすると、どちらかの運用でほぼ確実に足りなくなる。

中間テーブル `campaign_sites` を置く。

### 3.3 SNS投稿との関連は今回入れない

§14 は「SNS投稿等を関連付けられる構造を想定する」と書いているが、
**「想定する」であって要求ではない。**

サイトとの関連だけを先に入れる。投稿との関連は、
「キャンペーン単位で投稿を絞りたい」という要求が具体化してから足す。
関連の形（1投稿が複数キャンペーンに属してよいか等）は要求で変わる。

### 3.4 「分析」サブ画面は `018-analytics` と一緒に作る

§14 の4つ目「分析」は、アクセスデータが無い状態では作りようがない。
**空の画面を先に作らない**（`001` でダッシュボードがそうなった）。
`018-analytics` の完了後に、キャンペーン単位の絞り込みとして足す。

### 3.5 期間は日付（date）で持つ

時刻まで持たせない。キャンペーンの開始・終了を分単位で管理する運用は
考えにくく、タイムゾーンの扱いが増えるだけになる。

**終了日は開始日以降**を強制する。逆転を許すと、一覧の並びも期間の計算も壊れる。

## 4. データ

```sql
campaigns
  id, name, description, status, starts_on, ends_on,
  created_at, updated_at, created_by

campaign_sites
  campaign_id, site_id  (PK は両方)
```

* `ends_on` は NULL を許す（終わりを決めずに始める運用がある）
* サイトを消したら関連も消える（`ON DELETE CASCADE`）。
  **キャンペーン自体は残す。** 対象が減っただけで、取り組みの記録は消さない

## 5. Permission

`campaign.read` / `campaign.write` / `campaign.delete` を足す。
`site.*` と同じ粒度にそろえる。editor には read / write を、
viewer には read を与える（既存の割り当てと同じ考え方）。

## 6. 構成

`007-sites` と同じ並びにする。**同じ形のものを違う形で作らない。**

```text
migrations/013_campaigns.sql
apps/web/src/
├── domain/campaign/campaign.ts
├── domain/campaign/campaign-repository.ts
├── infrastructure/campaign-repository.ts
├── application/campaign/campaign-use-cases.ts
├── api/schemas/campaign.ts
├── app/api/v1/campaigns/
├── app/campaigns/
└── plugin/data-api.ts        campaigns を足す
```

## 7. 受け入れ条件

1. CRUD が画面と API の両方から通る。権限あり200 / なし403 / 未認証401
2. 対象サイトを複数選べ、保存して読み直せる
3. サイトを削除しても、そのサイトを対象にしていたキャンペーンは残る
4. 終了日が開始日より前なら 422
5. 一覧を状態と期間で絞り込める
6. `campaign.*` イベントが発火し、Plugin が購読できる
7. Plugin が Data API から Campaigns を読み書きできる
8. 作成・更新・削除が監査ログに残る
