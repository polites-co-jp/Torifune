## 2. 見つかった欠陥と処置

### 1. 046 自身が持ち込んだ 500 の退行（1 回目 security 中 2 件）

* **M1**：最上位のキーが `__proto__`・`constructor`・`toString` などだと、誤りをまとめる処理が継承された関数を配列と取り違えて TypeError になり、**認証の要らない口を含むすべての JSON の口とクエリで 500** になっていた（046 の前は 422）
* **M2**：誤りを探す処理が再帰で、約 5000 段の入れ子の JSON（約 10KB、認証なしで送れる）でスタックがあふれて 500 になっていた

**処置**：`Map` に集めて `Object.fromEntries` で返す形にし、探索を明示のスタックでたどる形（線形・循環でも止まる）に書き直した。
2 回目の検証で、8 種の原型の名前、100 万段の入れ子、10 万キーの本文、循環参照をすべて処理できることを確かめた。

`spec-verifier` の約 2,169 件の再プローブは 500 を 0 件と報告していたが、特別なキー名と深い入れ子は試していなかった。**同じ「入力で 500」を別の観点で探した `security-reviewer` だけが見つけた。**

### 2. 既存コードの、認証の要らない口の 500（2 回目 security 中）

本文の `csrfToken` を `String()` で文字列にしていたので、オブジェクトや深い入れ子の配列を送ると `/auth/login` などが 500 になっていた（046 の検査より前の処理）。
**処置**：文字列のときだけ使い、それ以外は 403 `CSRF_FAILED`。あわせて、`["<トークン>"]` のように配列で包んだトークンが文字列化で一致して CSRF を通っていた穴も塞がった。

## 3. 検証の方法

* `spec-verifier` は全件のテストを流し、**52 通りの変異のうち 51 を検出**した（残る 1 つは振る舞いが変わらない変異）。約 2,169 件の入力を本物のハンドラ・UseCase・Data API・Store・配信・ジョブに投げ直し、対象範囲の 500 と `DatabaseError` が 0 件であることを確かめた
* `security-reviewer` は 1 回目も 2 回目も**テストを実行せず**、純関数をスクラッチパッドに写して Node で直接呼んで確かめた
* `boundary-guardian` は**テストを実行していない**
