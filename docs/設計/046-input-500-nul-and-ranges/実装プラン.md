### 確定事項（設計書から。プランで蒸し返さない）

* **文字の規則**（設計 §6.2）：NUL（U+0000）と**対になっていないサロゲート**を含む文字列（値・キー・入れ子）は断る（ユーザー裁定 1・2）。
  422 の `details` のキーは**最上位の項目名**（本文の最上位のキーに含むとき・本文がオブジェクトでないときは `_`）。値は NUL なら `使用できない文字（NUL）が含まれています。`、
  片割れなら `使用できない文字（対になっていないサロゲート）が含まれています。`（同じ項目に両方あれば NUL が先の 2 つ）。送った値を載せない。Zod より先
* **検出**：片割れは正規表現 `/[\uD800-\uDBFF](?![\uDC00-\uDFFF])|(?<![\uD800-\uDBFF])[\uDC00-\uDFFF]/`（`u` フラグなし）。`isWellFormed` / `toWellFormed` は `lib`（`ES2023`）に型が無いので使わず、`lib` も変えない（設計 §6.2）
* **置き場は 4 つ**（設計 §4）：L1 `api/route.ts`（認証・Permission の後、Zod の前。`body` を宣言し `bodyKind` が `json` の本文と、`query` を宣言したルートのクエリ）、
  L2 UseCase（設計 §4.2 の **45 組**。`analytics.record` の `key` だけは既存の検査の後で片割れだけを見る）、L3 `plugin/store.ts`、L4 `publish.ts`・`run-job.ts`（**断らずに U+FFFD に置き換えて記録**）。
  パスの `{id}`・ヘッダ・`/auth/callback` のクエリ・`bodyKind: 'raw'` は見ない
* **L1 は本文を置き換えない**（断るだけ。本文はそのまま Zod へ）。L2 も値を返さない（`assertUsableText` は検査だけ）
* **L2 は `defineUseCase` に一律に置かない**。ID の項目・既に形の規則で両方を断る項目（`loginId`・`status`・`metric`・作成の `provider` など）は対象外（設計 §4.2・§4.3）
* 認証の要らない口（`login`・`password-reset` の 2 つ・`setup`・`collect`・`authorize`）も **422**（設計 §6.3）
* Data API は `data-api.ts` を変えない（UseCase の `ValidationError` がそのまま reject になる）。`analytics.record` の `siteId` は UseCase が `isUuidShape` で見る（設計 §9.2）

* Store は NUL と片割れを `PluginStoreError`（`JSON として保存できない文字（NUL・対になっていないサロゲート）を含む値`）、`keys(NUL か片割れを含む接頭辞)` は `[]`。`setSecret` は変えない（設計 §9.3）

## 3. タスク分解

各グループは「テストを書く（赤）→ 実装する（緑）」の順。コミットは `test:` と `fix:` / `feat:` / `docs:` を分ける（テストだけのコミットが赤になるのは `045` と同じく許す。§8 に記録する）。

### G1. 文字の規則の純関数（設計 §4.1・§6.2・§10.1 の #1〜#5）

#### T1. テストを書く（赤）

* **何をするか**：`domain/text.test.ts`。#2 は片割れの場所（先頭・途中・末尾・逆順・絵文字の直後）を表で回す。#3 は戻り値のキーの順・文言の順（NUL が先）・同じ項目で文言が重ならないことを見る。
  #4 は置き換え前後の `length` の一致と、絵文字（対）が変わらないことを見る。**テストの中の文字列は `\ud800` などのエスケープで書き、U+FFFD と絵文字は `String.fromCodePoint(0xfffd)`・`String.fromCodePoint(0x1f44d)` で作る**（ソースに壊れた文字を置かない）
* **完了条件**：`domain/text.ts` が無いので全件が赤
* **依存**：無し

#### T2. `domain/text.ts` を足す（緑）

* **何をするか**：6 つを足す。`unusableTextDetailsOf` は最上位がプレーンなオブジェクトならキーごとに（キー自体に含むときは `_`）、配列・文字列・その他は `_`。入れ子はプレーンなオブジェクト（`Object.getPrototypeOf` が `Object.prototype` か `null`）と配列だけをたどる。
  片割れの判定は §1 の正規表現（`u` フラグなし）。`toStorableText` は NUL と片割れを U+FFFD に置き換える（片割れは同じ正規表現に `g` を付けたもの）
* **完了条件**：#1〜#5 が緑。`pnpm typecheck`・`pnpm lint`（Domain が他の層に依存しない）
* **依存**：T1

## 7. リスクと注意点

1. **裁定は出ている（2026-09-25、ユーザー裁定 1〜4）。** 初版で「裁定待ち」としていた G3・G4 のコミット前の確かめは要らない。裁定 2 で片割れを断るので、L1・L2 に**置き換えの処理を作らない**（初版の `withWellFormedText` は無い）

5. **テストのソースの文字**：U+FFFD と絵文字は `String.fromCodePoint` で作り、片割れは `\ud800` のエスケープで書く。ソースに U+FFFD の文字そのものを書くと、置き換えの結果と区別がつかない

### 8.2 実装時に決めたこと

1. **L1 のクエリの集め方**：宣言したルートだけ `searchParams` を 1 回集め（`rawQuery`）、使えない文字の検査と Zod の両方に渡す。宣言していないルート（`/auth/callback`）は集めない（設計 §6.2）。
   本文とクエリの誤りは `mergeUnusableTextDetails` で本文 → クエリの順にまとめ、同じキーは文言を重ねない
2. **`unusableTextDetailsOf`**：最上位がプレーンなオブジェクトのとき、キーごとに「キー自体（→ `_`）」「値の中（→ そのキー）」を見る。キーの順は本文の順（`_` は最初に出た位置）。
   入れ子はプレーンなオブジェクトと配列だけをたどる（`Date`・`Uint8Array` は見ない）。文言の順は出た順によらず NUL → 片割れ
3. **ソースに NUL・U+FFFD を書かない**：`domain/text.ts` の NUL と U+FFFD は `String.fromCharCode(0)` / `String.fromCharCode(0xfffd)` で作る
   （正規表現の `\u0000` は ESLint の `no-control-regex` に当たるため、NUL の置き換えは `replaceAll`）。片割れの正規表現だけは `\uD800` などのエスケープで書く（`u` フラグなし）
4. **L2 の位置**：ハンドラの先頭。ただし `user.create` / `user.update` / `apiToken.create` は既存の `requireAuthenticated`（認証の確かめで、入力の検査ではない）の直後。
   `plugin.settings.save` は `requireSettings`（Plugin の有無）より前。`rangeOf`・`breakdownPage` は先頭（`assertRange` より前）。
   `analytics.record` の `key` は `isValidBreakdownKey` の直後、`value` の検査の前
5. **N1 の位置**：作成は L2 と既存の `name` / `url`（サイト）・`name`・期間（キャンペーン）の検査の直後。更新は `status` を指定したときだけ、既存の `name`（と `url`）の検査の直後
6. **N2・N3・`siteId` の形の順**：`value` の下限 → `siteId` の形（`isUuidShape`）→ `value` の上限（`Math.floor` の後）→ トランザクションの中で `siteRepository.findById` → `putPoint`。
