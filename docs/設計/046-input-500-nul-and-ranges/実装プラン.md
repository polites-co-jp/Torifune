### 確定事項（設計書から。プランで蒸し返さない）

* **文字の規則**（設計 §6.2）：NUL（U+0000）を含む文字列（値・キー・入れ子）は断る。対になっていないサロゲートは U+FFFD に置き換える（**裁定待ち・推奨で進める**。§7 の 1）。
  422 の `details` のキーは**最上位の項目名**（本文の最上位のキーの NUL・本文がオブジェクトでないときは `_`）、値は `['使用できない文字（NUL）が含まれています。']`。送った値を載せない
* **置き場は 4 つ**（設計 §4）：L1 `api/route.ts`（認証・Permission の後、Zod の前。`body` を宣言し `bodyKind` が `json` の本文と、`query` を宣言したルートのクエリ）、
  L2 UseCase（設計 §4.2 の **44 組**）、L3 `plugin/store.ts`、L4 `publish.ts`・`run-job.ts`（置き換えて記録）。パスの `{id}`・ヘッダ・`/auth/callback` のクエリ・`bodyKind: 'raw'` は見ない
* **L2 は `defineUseCase` に一律に置かない**。ID の項目・既に形の規則で NUL を断る項目（`loginId`・`keys`・`analytics.record` の `key` など）は対象外（設計 §4.2・§4.3）
* 認証の要らない口（`login`・`password-reset` の 2 つ・`setup`・`collect`・`authorize`）の NUL も **422**（設計 §6.3）
* Data API は `data-api.ts` を変えない（UseCase の `ValidationError` がそのまま reject になる）。`analytics.record` の `siteId` は UseCase が `isUuidShape` で見る（設計 §9.2）
* Store は NUL と対になっていないサロゲートを `PluginStoreError`（`JSON として保存できない文字（NUL・対になっていないサロゲート）を含む値`）、`keys(NUL を含む接頭辞)` は `[]`。`setSecret` は変えない（設計 §9.3）
* L4：`toStorableText` は秘匿の**後**、長さの切り詰めの**前**。`externalUrl` と `manual()` の URL の NUL は `isValidExternalHttpsUrl` が偽にして捨てる（設計 §9.4）
* B2：`isCalendarDate` が年 `0000` を偽に。422 のキーは既存の `to` / `metricDate`（設計 §6.4）
* B3：`SCHEDULED_AT_MIN_MS = -62135596800000`・`SCHEDULED_AT_MAX_MS = 253402300799999`、`isValidScheduledAt`、UseCase で `ValidationError('SocialPost', 'scheduledAt', '0001-01-01T00:00:00Z から 9999-12-31T23:59:59.999Z までの日時を指定してください。')`。Zod は `.describe()` だけ（設計 §6.5）
* B4：`ACCESS_LOG_PRUNE_MAX_DAYS = 36500`、Zod `.max(36500, '36500以下で指定してください。')`、`pruneAccessLogs` も同じ上限（設計 §6.6）
* **公開 Plugin API は TSDoc だけ**（`store.ts`・`social.ts`・`data.ts`）。`PLUGIN_API_VERSION` は変えない（設計 §9）
* **画面は変えない。E2E は足さず、流さない**（設計 §7・§10.14）
* **既存テストの変更は 1 行だけ**：`api/campaign-link-input.integration.test.ts` の `MALFORMED` の `['NUL 文字', () => '\u0000']` の行を外す（設計 §10.13）。他の既存テストは変えない
* マイグレーションは無し

## 6. 影響範囲

* **HTTP API**：設計 §6.7。NUL で 500・409 だった 45 件が 422 に、NUL で 2xx・401・400 だったものが 422 に（動作の変更）、NUL で既に 422 だったものは文言が変わる。
  サロゲートの `jsonb` の 500 が 2xx に。西暦 0 年・`scheduledAt` の範囲外・`pruneOlderThanDays` の 36501 以上が 422 に。OpenAPI に `maximum`・`description` が増える。**v1 のまま**
* **Data API**：NUL・`analytics.record` の `siteId` の形・西暦 0 年の `DatabaseError` が `ValidationError` に（設計 §9.2）。型は変えない
* **Plugin Store**：`set` の `DatabaseError` が `PluginStoreError` に、`keys` の NUL が `[]` に（設計 §9.3）
* **配信**：NUL を含む戻り値でも結果が記録される。`manual()` の NUL を含む URL が `invalid_url` に（設計 §9.4）
* **画面**：変わらない（保存の 422 の `details` のキーは既存の欄の名前）
* **公開 Plugin API の型**：変わらない。**破壊的変更は無い**（振る舞いの変更は設計 §9.5 で判断済み）
* **既存テスト**：1 行（設計 §10.13）

## 7. リスクと注意点

1. **裁定待ちの 2 点で書き換えが出る**：設計 §11 の 1（サロゲートを断るなら #3・#4・#18〜#21・#24 の期待と L1・L2 の置き換えが「検出して断る」に変わる）、§11 の 2（自由文を取り除くなら §4.2 の項目と #7・#22・#26 が分かれる）。
   **G1〜G10 は推奨で進めてよいが、G3・G4 のコミットの前に裁定の結果を確かめる**（裁定が変われば T5・T7 の表を直してから実装する）。G11・G12 は裁定が「含める」まで着手しない
2. **L1 の位置**：`requirePermission` より前に置くと、権限の無い要求に入力の誤りを返す（#10 で落ちる）。Zod より後に置くと、#9 の「Zod を走らせない」と `siteIds` の文言が崩れる
3. **置き換えた本文を Zod に渡す**：`validate` に元の `rawBody` を渡すと `jsonb` の 500 が残る（#18・#19 で落ちる）。CSRF の `bodyToken` は元の `rawBody` から読んだままでよい（`csrfToken` に NUL・サロゲートは入らない想定で、入っても照合に落ちるだけ）
4. **L2 の返り値を使う**：`checkText` の戻り値（置き換えた写し）ではなく元の `input` を Repository に渡すと、UseCase を直接呼ぶ経路の `jsonb` が 500 のまま（#24 で落ちる）。監査の `detail` も写しから作る
5. **正規表現**：`replaceLoneSurrogates` の後読み（`(?<!…)`）は Node 22 で使える。`u` フラグを付けると単独のサロゲートに一致しなくなるので**付けない**。入力の長さに対して線形（量指定子の入れ子が無い）
6. **#7 の表の作り方**：36 件の本文は「通る本文」を土台に 1 か所だけ NUL を足す。土台が他の理由で 422 になると NUL の検査を確かめていないのと同じになるので、**土台だけを送ると 2xx になること**を同じファイルの 1 件目で確かめる
7. **`/setup` のテスト**：利用者が 0 人でないと開かない。使い捨ての DB でも、他のテストが作った利用者を各ケースの前に消す（外部キーの順：`user_roles` → `auth_audit_logs` → `sessions` → `users`）
8. **#13 の「記録なし」**：`login_attempts` と `auth_audit_logs` の行数を前後で比べる。ルートの Rate Limit（1 分 30 回）に当たらないよう、1 ファイルの `/auth/login` の呼び出しは 30 回未満にする（`X-Forwarded-For` をケースごとに変えてもよい）
9. **#36 のジョブ名**：`job_runs.job_name` に入る名前は `run-job.integration.test.ts` の作り方に従う（`JobName` の型）
10. **#44 と `system.manage`**：36500 以下の 200 を見るときは `system.manage` を持つ利用者で叩く（持たないと集計の後に 403）
