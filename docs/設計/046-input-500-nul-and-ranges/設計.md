## 1. 目的

### 1.1 直すもの

| # | 入力 | いまの振る舞い | 困ること |
| --- | --- | --- | --- |
| B1 | 文字列の入力に **NUL（U+0000）** | 検査を通り、PostgreSQL が断る（`text` は `22021 invalid byte sequence for encoding "UTF8": 0x00`、`jsonb` は `22P05 unsupported Unicode escape sequence`）→ **500**。Data API・Plugin Store は Postgres の例外がそのまま Plugin へ上がる。配信 Plugin の戻り値に NUL があると**配信の結果が記録されない** | **認証の要らない** `POST /auth/login`・`/auth/password-reset/request`・`/collect` から誰でも 500 とエラーログを起こせる。どの項目が悪いかが返らない |
| B2 | `GET /analytics?from=0000-01-01` など、**西暦 0 年**の日付 | 形と暦（うるう年）だけを見て通し、Postgres の `date` が断る（`22008`）→ **500** | 打ち間違いが 500 に見える |
| B3 | `POST` / `PATCH /social/posts` の `scheduledAt` に**紀元前 4714 年 11 月 24 日（UTC）より前** | `z.coerce.date()` は JavaScript の範囲（±8.64e15 ms）を通し、Postgres の `timestamptz` が断る → **500** | 同上 |
| B4 | `POST /analytics/rollup` の `pruneOlderThanDays` に**今日のユリウス通日以上**（2026-09-25 では 2,461,309 以上） | 下限 1 だけで上限が無く、`now() - N days` が範囲外 → **500**（集計は済んだ後） | 同上。境目が日ごとに動く |

#### 1.2.2 対になっていないサロゲート

JSON の `"\ud800"` は、JSON として正しく、`JSON.parse` で**対になっていないサロゲートを含む JS の文字列**になる（クエリ文字列では起きない。パーセント符号化の不正なバイトは U+FFFD になる）。

* **`text` 列**：Node が UTF-8 へ符号化するときに U+FFFD に置き換わり、**エラーにならずに U+FFFD が保存される**（`POST /sites` の `name`、`/social/posts` の `body`・`externalRef`、`/setup` の `displayName` / `email`、配信の `reason` などで確かめた）。
  **ただし SNS 投稿の `body`・`link` は、配信 Plugin の事前検査（`validate()`）が先に断るものがある**：`sns-x-api`（自動・手動）・`sns-x-manual`・`sns-threads`（`037`・`040`）と `sns-bluesky` の手動投稿（`042` §9.2 の 7）は
  422 `body`（`本文に扱えない文字が含まれています。`）。`sns-bluesky` の自動投稿・`sns-instagram`・検査の無い provider は 201（U+FFFD で保存）。調査の数値は検査の無い偽の provider で取った
* **`jsonb` 列**：`JSON.stringify` が `\ud800` のエスケープを書き、Postgres が `22P02 invalid input syntax for type json` で断る → **500 が 10 件**：
  `POST /social/posts` の `media[].url`・`media[].alt`・`providerOptions` の値（入れ子を含む）・キー、`PATCH /social/posts/{id}` の `media[].url`・`media[].alt`・`providerOptions`、
  `PUT /settings` の `serviceName`、`PUT /plugins/{id}/settings` の text の項目。UseCase `updateSystemSettings`・`createSocialPost` も同じ。Plugin Store の `set` は 3 件
* **黙って失敗するもの**：`POST /webhooks` の `url` に含めると 201 だが、**監査ログ（`audit_logs.detail` は `jsonb`）の記録が失敗する**（`failed to record audit log`）
* 本文を UTF-16 の長さで切る JavaScript のクライアントは、絵文字を半分に切って `\ud83d` を送りうる（**実際に起きうる入力**。SNS の本文の文字数の上限のため）

`jsonb` の列は 8 つ：`social_posts.media`・`provider_options`、`system_settings.value`、`plugin_store.value`、`audit_logs.detail`、`auth_audit_logs.detail`、`webhook_deliveries.payload`、`job_runs.summary`。

#### 1.2.3 B2 — 日付の範囲

| 入力 | 結果 |
| --- | --- |
| `GET /analytics`・`GET /analytics/breakdown`・`POST /analytics/rollup` の `from` / `to` に `0000-01-01`〜`0000-12-31`（`0000-02-29` を含む） | **500**（`22008`）。`rollup` は `job_runs` に失敗の行を残す |
| Data API `analytics.list({ from: '0000-…' })`・`analytics.record({ metricDate: '0000-…' })` | **`DatabaseError`**（`22008`） |
| 同じく `0001-01-01`・`0099-12-31`〜`0100-01-01`・`1000-01-01`・`9999-12-30`〜`9999-12-31` | 200 / 成功 |

原因：`domain/analytics/analytics.ts` の `isCalendarDate` は 4 桁の年・月・日（うるう年）を見るが年の下限が無い。Postgres の `date` は西暦 0 年を持たない（紀元前 1 年の次が西暦 1 年）。
上限は形（4 桁）で `9999-12-31` に決まる。画面（`/analytics` の `period=custom`）は `ui/analytics/analytics-query.ts` の判定が西暦 0〜99 年を「不正」として既定の期間へ戻すので 500 にならない。

#### 1.2.4 B3・B4 — 日時・日数の範囲

**`scheduledAt`**（`z.coerce.date()`。文字列・数値・真偽値を `new Date()` に通す）

| 値 | 結果 |
| --- | --- |
| `-8.64e15`（数値）・`'-271821-04-20T00:00:00Z'`・`'-010000-01-01T00:00:00Z'`・`'-004714-01-01T00:00:00Z'`・`'-004713-11-23T00:00:00Z'` | **500**（`timestamp out of range`） |
| `'-004713-11-24T00:00:00Z'`（紀元前 4714 年 11 月 24 日 UTC）・`'-004713-11-23T23:59:59Z'`・`'0000-01-01T00:00:00Z'`・`'0001-01-01T00:00:00Z'`・`'9999-12-31T23:59:59Z'`・`'+010000-01-01T00:00:00Z'`・`8.64e15`（`+275760-09-13`） | 201 / 200 |
| `'-8.64e15'`（文字列）・`1e20`・`''` | 422（`Invalid date`） |
| `true`・`'1'`・`0`・`-1` | 201（`z.coerce.date()` の解釈。§11 の記録） |

JavaScript の `Date` は ±8.64e15 ms（−271821-04-20〜+275760-09-13）、Postgres の `timestamptz` は紀元前 4714-11-24 00:00 UTC〜294276-12-31。
**下の境目はサーバの Node のタイムゾーンで動く**：node-postgres は `Date` をプロセスのローカル時刻とオフセットで送り、古い日付では地方平均時のオフセット（JST なら `+09:18:59`）になるため、
`-004713-11-23T23:59:59Z` が通って `-004713-11-23T00:00:00Z` が断られた（JST で実行）。上の境目は JavaScript のほうが狭い（Postgres に届く前に止まる）。

**`pruneOlderThanDays`**（`z.coerce.number().int().min(1)`。`access_logs` を `occurred_at < now() - (N || ' days')::interval` で消す）

| 値 | 結果（2026-09-25 JST） |
| --- | --- |
| `1`・`36500`・`2400000`・`2461308` | 200 |
| `2461309`〜`2147483647` | **500**（`timestamp out of range`）。境目は**今日のユリウス通日**で、1 日に 1 ずつ上がる |
| `2147483648`〜`9007199254740991` | **500**（`interval field value out of range`） |
| `1e20` | 422（安全な整数でない） |

いずれも 500 は**集計（ロールアップ）が成功した後**に起きる（集計は記録され、応答だけが 500）。

**同じ型を調べて 500 でなかったもの**：キャンペーンの `startsOn` / `endsOn` / `activeOn`（`045`。西暦 1〜99 年を含めて 422）、`/api-tokens` の `expiresAt`（`z.string().datetime()` が 4 桁の年だけを通し、過去は 422）、
`/analytics` の `page` / `perPage` / `limit`（丸める）、一覧の `page`（安全な整数を丸める。`1e300` は 422）、Data API `analytics.record` の `value` の `NaN`・`Infinity`（422 相当の `ValidationError`）。

## 3. スコープ

### やること

1. **文字の規則**を決め、HTTP の本文・クエリ、UseCase、Plugin Store、Core が書く Plugin 由来・システム由来の文字列に適用する（§4・§6.2）
   * NUL と対になっていないサロゲートを含む入力を断る（HTTP 422、UseCase・Data API は `ValidationError`、Store は `PluginStoreError`）。文言は 2 つに分ける
   * Core が書く Plugin 由来・システム由来の文字列（配信の理由・例外の文言・`externalId`、ジョブの失敗の文言）は NUL とサロゲートを U+FFFD に置き換えて記録する
   * URL の判定（`isValidExternalUrl` など）が NUL を含む値を断る
2. Data API `analytics.record` の `siteId` を UUID の形に限る（NUL を含む ID の `DatabaseError` を直す。§9.2）
3. B2：アナリティクスの日付を `0001-01-01`〜`9999-12-31` に限る（§6.4）
4. B3：`scheduledAt` を `0001-01-01T00:00:00.000Z`〜`9999-12-31T23:59:59.999Z` に限る（§6.5）
5. B4：`pruneOlderThanDays` を `36500` 以下に限る（§6.6）
6. 公開 Plugin API の TSDoc・`Plugin開発ガイド`・`SNS投稿API仕様`・`010` §9 の追記（§12）
7. N1〜N3：Data API の列挙外の `status`、`analytics.record` の存在しない `siteId`・`value` の上限を `ValidationError` にする（ユーザー裁定 3。§9.2）
8. N4：年が 1000 未満の日付の応答を 4 桁の年にそろえる（ユーザー裁定 4。§6.4）

### やらないこと（理由つき）

| 対象 | 理由 |
| --- | --- |
| パスの `{id}` の NUL | すでにすべて 404（§1.2.1 表 P）。変えない |
| ヘッダ（`user-agent`・`x-forwarded-for` など）・Cookie の NUL | 実行環境が NUL を含むヘッダを断り、届かない（表 X） |
| `GET /auth/callback` のクエリ | ルートが `query` を宣言しておらず（方式ごとに違う値を素通しで Plugin へ渡す）、`state` はハッシュで引くので 500 にならない。L1 はクエリを宣言したルートだけを見る（§6.2） |

| NUL 以外の制御文字（U+0001〜U+001F・U+007F） | Postgres は保存でき、500 にならない。項目ごとの意味の規則（パス・内訳キーは既に断る）であり、本設計の「保存できない文字」の規則とは別 |

| Webhook の配信の失敗の文言（`webhook_deliveries.last_error`） | Core の文言（`受け手が 500 を返した`）と `fetch` の例外の文言だけで、外から NUL を入れる経路が無い |

### 4.2 L2 の対象（UseCase × 項目）

**保存または検索の条件として DB へ渡す文字列の項目のうち、いまの検査を NUL か対になっていないサロゲートが通り抜けるもの。** ID（`id`・`socialAccountId`・`siteIds` など）は含めない（形の検査が「存在しない」として扱う。`get*` の `NotFoundError`・Data API の `get()` の `null` を変えないため）。

### 4.3 置き場の理由

* **L1（`api/route.ts`）を置く理由**：HTTP の入口は 1 か所に集まっていて（`CLAUDE.md`「各ルートで手順を並べると、いつか 1 つ抜ける」）、**認証の要らない 5 つの口**（`login`・`password-reset` の 2 つ・`setup`・`collect`）は UseCase（`defineUseCase`）を通らない。
  ここで断れば、ルートを足しても抜けない。`details` のキーを**クライアントが送った項目名**（`q`・`media`・`providerOptions`）で返せるのもここだけ（UseCase の項目名は `keyword` など HTTP と違う）
* **L2（UseCase）を置く理由**：HTTP 以外の入口（Data API・画面の Server Component・Core の内部）は UseCase を通る。認可を UseCase に置いたのと同じ理由（`CLAUDE.md`「経路ごとに漏れる」）。
  `045` §4 も同じ理由で検査を UseCase に置いた。HTTP の要求は L1 で先に断られるので L2 は**二重の守り**になる
* **L2 を `defineUseCase` に一律に置かない理由**：入力の全体を見ると、`{id}` に NUL を含む `getSite` が `NotFoundError` から `ValidationError` に変わり、
  編集画面の `notFound()` が落ちて 500 の画面になり、Data API の `get(id)` の「`null` を返す」約束（`043` §3）も破る。ID は形の検査が扱う
* **項目ごとの Zod に置かない理由**：40 を超える項目に同じ `refine` を書くことになり、足した項目で必ず抜ける。Data API と認証の要らない口にも効かない
* **DB の境界（Kysely のプラグイン・`pg` の直前）に置かない理由**：どの項目かが分からず 422 の `details` を作れない。Database Provider は Plugin が差し替えうるので、そこに置くと守りが Provider ごとになる。
  L1・L2 が漏れたときに「500 とログ」で見えるほうが、黙って別の誤りに変えるよりよい（`045` §3 の外部キー違反と同じ判断）
* **L3（Store）**：`PluginStore` は UseCase を通らない Plugin の口。既に「JSON にできない値」「大きすぎる値」を `PluginStoreError` で断っており、同じ場所で同じ例外にする
* **L4（Core が書く Plugin 由来・システム由来の文字列）で断らずに置き換える理由**（オーケストレーター判断。§11 の 2）：断る相手がいない（要求を返す先が無く、Plugin は配信を終えた後）。断ると**起きたことの記録が消える**
  （`ok: true` なら SNS に出たのに記録が残らず、二重投稿の防止が効かない）。これらは診断のための文字列で、置き換えても意味は保たれる。サロゲートは `text` 列でも結局 U+FFFD になるので、置き換えは保存の結果を変えず、`jsonb`・監査ログの失敗だけを防ぐ
* Domain に足すのは純関数と定数だけで、DB 製品・Zod への依存は増えない。Postgres のエラーコードの解釈はどこにも持ち込まない

## 5. データモデル

変更なし。マイグレーションは要らない。既に保存されている値（U+FFFD を含む行）は変えない。

### 6.2 文字の規則（B1）

**規則**

1. **NUL（U+0000）を含む文字列は受け付けない。** 値でもオブジェクトのキーでも、入れ子の深さを問わない
2. **対になっていないサロゲートを含む文字列も受け付けない**（ユーザー裁定 2）。対になっていないサロゲートは、U+D800〜U+DBFF の後に U+DC00〜U+DFFF が続かないもの、U+DC00〜U+DFFF の前に U+D800〜U+DBFF が無いもの。
   対になったサロゲート（絵文字など）は受け付ける。値とキーの両方、入れ子の深さを問わない
3. **422 の `details` のキーは、使えない文字を含む値がある最上位の項目名**（本文のプロパティ名・クエリの名前）。`media[0].alt` なら `media`、`providerOptions` の中のキーなら `providerOptions`。
   本文の最上位の**キー**に含むとき、本文がオブジェクトでないときは `_`（Zod のルートの誤りと同じ。`api/validation.ts`）。
   値は、その項目に NUL があれば `使用できない文字（NUL）が含まれています。`、対になっていないサロゲートがあれば `使用できない文字（対になっていないサロゲート）が含まれています。`（両方あれば**この順で 2 つ**）。
   該当する項目が複数あれば**すべてのキー**を入れる（本文の順、クエリはその後）。**送った値は `details`・`message`・ログに載せない**
4. **この検査は Zod より先。** 1 つでもあれば Zod を走らせず、この誤りだけを返す（他の項目の型の誤りは直した次の要求で返る）

**（2026-09-25 追記。検証の指摘への処置）**

* **`details` のキーは先頭の 50 個まで**（security L2）。本文 → クエリの順で、51 個目からは返さない（直した後の次の要求で返る。規則 4 と同じ扱い）。
  項目の数だけキーと文言を返すと、認証の要らない口へ小さな項目を並べるだけで応答を送った本文の何倍にも膨らませられる。上限は `api/route.ts` の定数
* **項目名は送った側が決める**（M1）。`__proto__`・`constructor`・`toString`・`valueOf`・`hasOwnProperty` のような `Object.prototype` の名前でも、
  その名前をキーにした 422 を返す（`details` の自分のプロパティとして返す）。クエリの名前も同じ（`?__proto__=` が検査から漏れない）
* **入れ子の深さを問わない**（M2）。本文の入れ子は再帰せずにたどる（`JSON.parse` は 1 万段の入れ子を読めるので、再帰すると 10KB ほどの本文で 500 になる）

**文言を NUL と分ける理由**：直し方が違う。NUL は入力に紛れた制御文字で、消せばよい。対になっていないサロゲートは、文字列を UTF-16 の長さで切った（絵文字を半分に切った）クライアントの不具合であることが多く、
切り方を直す必要がある。分けておけば、外部アプリの開発者が原因に当たりを付けられる。どちらも値は載せない。

**検出の方法**：正規表現 `/[\uD800-\uDBFF](?![\uDC00-\uDFFF])|(?<![\uD800-\uDBFF])[\uDC00-\uDFFF]/`（`u` フラグを付けない）。
`String.prototype.isWellFormed` / `toWellFormed` は ES2024 で、`tsconfig` の `lib`（`ES2023`）に型が無い。`lib` は変えない（`037` 設計 §9.4 の `x-text.ts`・`040` の `threads-text.ts` と同じ先例）。

**適用する入力**

| 入力 | 適用 | 理由 |
| --- | --- | --- |
| JSON の本文（`body` を宣言し `bodyKind` が `json` のルート） | 1〜4 | — |
| クエリ（`query` を宣言したルート） | 1〜4 | 2 は実際には起きない（パーセント符号化の不正なバイトは U+FFFD になる）が、同じ関数で見る |
| パスの `{id}` | しない | すでに 404（§1.2.1 表 P） |
| `query` を宣言しないルートのクエリ（`/auth/callback`） | しない | ルートが入力として宣言していない |
| `bodyKind: 'raw'` の本文 | しない | バイト列 |

**順序**：Rate Limit → CSRF → 認証 → Permission → **使えない文字の検査（本文 → クエリ）** → Zod（本文 → クエリ）→ ハンドラ（→ UseCase の L2 → 配信 Plugin の `validate()`）。
`api/route.ts` の既存の順序（認可は検査より先）に、Zod の直前の 1 段を足す。

**NUL を断る理由（取り除かない理由）**

* Postgres の `text` は NUL を持てない。取り除くと**送った値と違うものが黙って保存される**（`043`・`045` が直した「黙って困る」と同じ型）
* 識別に使う値で、取り除いた値が**別のものと一致する**：`loginId`・`email`・冪等キー `externalRef`・Webhook の `url` の `admin\u0000` が `admin` になる
* 画面の入力欄・キーボードから NUL は入らない。届くのはクライアントの不具合か探りで、422 で気づかせるほうがよい
* 規則が 1 行で書ける（「NUL を含む文字列は 422」）。自由文だけ取り除く案は採らなかった（§11 の 1。ユーザー裁定 1）

**サロゲートを断る理由（ユーザー裁定 2）**

* **送った値と保存される値が黙って違う**のを無くす。いまは `text` 列で U+FFFD に置き換わり、`jsonb` 列では 500 になる。どちらも送った側は気づけない
* 別々の不正な値が同じ値になる（冪等キー `externalRef` の `x\ud800` と `x\ud801` が 1 行にまとまる）ことが無くなる
* 配信 Plugin（`037`・`040`・`042`）は既に本文の片割れを断っており、Core の規則がそれにそろう
* **代わりに、いま 2xx の要求が 422 に変わる**（§6.7。動作の変更）。絵文字を UTF-16 の長さで半分に切るクライアントは、切り方を直す必要がある（`SNS投稿API仕様.md` の変更履歴に書く）

### 6.3 認証の要らない口

NUL と対になっていないサロゲートを同じに扱う（下の表の「NUL」はどちらも指す）。

| 口 | NUL のとき | 理由 |
| --- | --- | --- |
| `POST /auth/login`（`loginId`・`password`） | **422**（`details.loginId` / `details.password`） | 判定は**入力の文字だけ**で決まり、利用者の有無に依存しない（存在する ID の後ろに NUL を足しても、存在しない ID でも同じ 422）。空の `loginId` は既に 422（Zod の `min(1)`）で、同じ扱い。ログイン試行の記録（`login_attempts`）と `auth_audit_logs` には書かない（NUL を含む ID に一致する利用者は存在しえず、総当たりの数え方に影響しない）。ルートの Rate Limit（1 分 30 回）は従来どおり数える |
| `POST /auth/password-reset/request`（`email`） | **422** | 同上。登録の有無で応答を変えない規則（204）は、NUL を含まない要求について従来どおり |
| `POST /auth/password-reset/confirm`（`token`・`newPassword`） | **422** | 同上（いまは 401） |
| `POST /setup` | **422**（開いていても閉じていても） | NUL の検査はハンドラの前なので、閉じているかどうかを漏らさない |
| `POST /collect`（`key`・`path`・`referrer`） | **422**。何も記録しない | 「結果を出し分けない」（`018` §3.1）は**キーの当たり**（サイトの有無・停止中・除外 IP）の話で、入力の形の誤りは既に 422（`key` の空・201 文字以上）。NUL の有無はキーの当たりと関係が無い。計測タグ（`sendBeacon`）は応答を読まないので、ブラウザの振る舞いは変わらない。`path` / `referrer` の NUL はブラウザからは来ない（`location.pathname` は `%00` に符号化される） |
| `GET /auth/authorize`（`returnTo`） | **422** | `query` を宣言している。いまは往復型の Provider が無ければ 400、有れば `/` に丸めて 302 |

**401・204 にしない理由**：401 にするには `login()` まで通して DB を引かずに 401 を作る特別扱いが要り、L1 の「1 か所で断る」が崩れる。422 は利用者の有無・キーの当たりを何も教えない。

**パスワードの片割れ**：これまで API で対になっていないサロゲートを含むパスワードを設定した利用者がいれば（ハッシュの前に U+FFFD になっていた）、同じ文字列でのログインは 422 になる。
U+FFFD を打てばログインできる（保存されたハッシュは U+FFFD のもの）。画面の入力欄からは片割れは入らないので、影響は API で設定した場合に限る（§6.7）。

### 6.4 B2 — アナリティクスの日付

規則：**`YYYY-MM-DD` の形で、暦にあり、年が `0001` 以上**（`0001-01-01`〜`9999-12-31`）。`isCalendarDate` を直すので、`isValidRange` を使う経路がすべて変わる。

| 経路 | 西暦 0 年のとき（変更前 → 変更後） |
| --- | --- |
| `GET /analytics`・`GET /analytics/breakdown` の `from` / `to` | 500 → **422 `to`**（`期間を確認してください（開始日以降にする）。`。暦の誤り（`2026-02-30`）と同じキー・文言） |
| `POST /analytics/rollup` の `from` / `to` | 500（`job_runs` に失敗の行）→ **422 `to`**（同じ文言）。ロックを取らず `job_runs` に行を増やさない（`assertRollupRange` の既存の位置） |
| Data API `analytics.list` | `DatabaseError` → **`ValidationError`（`field` は `'to'`）** |
| Data API `analytics.record` の `metricDate` | `DatabaseError` → **`ValidationError`（`field` は `'metricDate'`、`日付の形式が不正です。`）** |
| 西暦 1〜9999 年 | 変わらない（200 / 成功） |

**キーを `to` のままにする理由**：`from` の暦の誤りをいまも `to` で返しており（`assertRange`）、B2 だけ `from` にすると同じ種類の誤りでキーが割れる。キーの直し方は `045` §11 の 3 と同じ論点として §11 の記録 1 に残す。
画面（`ui/analytics/analytics-query.ts`）は変えない（西暦 0〜99 年を既定の期間へ戻す既存の振る舞いのまま）。

**N4（ユーザー裁定 4）**：応答の日付（`/analytics` の `metricDate`、キャンペーンの `startsOn` / `endsOn`、Data API の同じ項目）の年を **4 桁にそろえる**（`"1-01-01"` → `"0001-01-01"`、`"100-01-01"` → `"0100-01-01"`）。
`dateOnly`（`domain/analytics/day.ts`）と `toDateOnly`（`infrastructure/campaign-repository.ts`）の年を `padStart(4, '0')` にする。年が 1000 以上の値は変わらない。

### 6.5 B3 — `scheduledAt`

規則：`null` でなければ **`0001-01-01T00:00:00.000Z` 以上 `9999-12-31T23:59:59.999Z` 以下**（エポックミリ秒で `-62135596800000`〜`253402300799999`）。検査は UseCase（`createSocialPost` / `updateSocialPost`）。

| 送った値 | 変更前 | 変更後 |
| --- | --- | --- |
| 省略・`null` | 従来どおり | 同じ |
| `'2030-01-01T09:00:00+09:00'`・`'0001-01-01T00:00:00Z'`・`'9999-12-31T23:59:59.999Z'` | 201 / 200 | 同じ |
| `-8.64e15`（数値）・`'-271821-04-20T00:00:00Z'`・`'-010000-01-01T00:00:00Z'` | **500** | **422 `scheduledAt`**（`0001-01-01T00:00:00Z から 9999-12-31T23:59:59.999Z までの日時を指定してください。`） |
| `'-004713-11-24T00:00:00Z'`〜`'0000-12-31T23:59:59.999Z'` | 201 | **422 `scheduledAt`** |
| `'+010000-01-01T00:00:00Z'`〜`8.64e15`（数値） | 201 | **422 `scheduledAt`** |
| `'abc'`・`''`・`1e20` | 422（`Invalid date`） | 同じ（Zod が先） |

**この範囲にする理由**：

* 下の境目を Postgres の限界に合わせると、**サーバの Node のタイムゾーンで境目が動く**（§1.2.4）。十分内側に固定する
* 応答は `toISOString()` で、年が 0〜9999 の外だと `+010000-…` / `-000001-…` の拡張形式になり、多くのクライアントが読めない
* 日付の入力（`YYYY-MM-DD`）が 4 桁の年に限られているのとそろう。過去の日時（すぐ配信）は従来どおり受け付ける

検査を UseCase に置く理由は §4.3 と同じ（HTTP の Zod だけでは UseCase を直接呼ぶ経路が漏れる）。Zod は `.describe()` だけ（OpenAPI の `date-time` に範囲を表す仕組みが無い）。
**検査の位置**：`createSocialPost` は本文の検査（a）の直後、アカウントの存在（b）の前。`updateSocialPost` は `scheduledAt` を指定したときだけ、本文の検査の直後。どちらも L2 の後。

### 6.6 B4 — `pruneOlderThanDays`

規則：**1 以上 36500 以下の整数**（約 100 年）。

| 値 | 変更前 | 変更後 |
| --- | --- | --- |
| `1`〜`36500` | 200 | 同じ |
| `36501`〜今日のユリウス通日 − 1（2026-09-25 では 2461308） | 200（何も消えない） | **422 `pruneOlderThanDays`**（`36500以下で指定してください。`） |
| 今日のユリウス通日以上 | **500**（集計の後） | **422**（Zod。集計の前に返り、`job_runs` に行を増やさない） |
| `0`・`-1`・`1.5`・`1e20` | 422 | 同じ |

**36500 にする理由**：生ログをそれより長く残す運用は無く、それより大きい値は「何も消さない」と同じ。Postgres の限界（日ごとに動くユリウス通日、`interval` の `2^31`）より十分内側で、日付が進んでも変わらない。
`pruneAccessLogs` にも同じ上限を置く（HTTP 以外の呼び出しの守り）。**認可との順序**：Zod の上限は `analytics.read` の後・集計の前に効くので、`system.manage` を持たない利用者も 36501 以上には 403 ではなく 422 を受け取る（下限 1 の既存の 422 と同じ位置）。

保存できない値・送った値と違う値で保存していたもの・実用の外の値を受けていたもの。SNS 投稿 API の分は `SNS投稿API仕様.md` §9 の変更履歴に**動作の変更として**書く（§12）。

### 6.8 配信 Plugin の片割れの検査との関係

`037`（`sns-x-api`・`sns-x-manual` の `x-text.ts`）・`040`（`sns-threads` の `threads-text.ts`）・`042` §9.2 の 7（`sns-bluesky` の手動投稿）は、
`validate()` で本文（と `link`）の対になっていないサロゲートを `body` の問題（`本文に扱えない文字が含まれています。`）として返し、Web Intent の URL を作るときは U+FFFD に置き換えてから符号化する（`encodeURIComponent` は片割れで例外を投げる）。

**046 の後、Core の経路からはこの検査に届かない**：

| 経路 | 片割れを含む `body` / `link` | Plugin の `validate()` に届くか |
| --- | --- | --- |
| HTTP（`POST` / `PATCH /social/posts`） | L1 が 422 で断る | 届かない |
| UseCase を直接（`createSocialPost` / `updateSocialPost`） | L2 が `ValidationError` で断る（§4.2 の `body`・`link`） | 届かない |
| Data API | 投稿の本文を作る・変える口が無い（`markPublished` / `markFailed` だけ） | 経路が無い |
| 配信の直前の再検査（`publish.ts`） | 本文は DB から読む。`text` 列は片割れを持てない（046 の前に保存された行も U+FFFD になっている） | 届かない |

**それでも Plugin の検査を残す（変えない）理由**：

1. **Plugin は Core の内部の規則に依存しない**（`CLAUDE.md`「Plugin は本体の内部クラスに直接依存しない」）。`validate()` の契約は「整った文字列が来る」ことを約束しておらず、
   配信先（X・Threads・Bluesky）の制約を Plugin が自分で守るのが正しい
2. **同じ Plugin が 046 より前の Core でも動く**（`PLUGIN_API_VERSION` は `1` のまま）。前の Core は片割れを `validate()` まで通す
3. URL を作るときの U+FFFD への置き換えは、`encodeURIComponent` の例外を防ぐ安い守りで、外すと Plugin の単体テスト（片割れを直接渡す）の前提が崩れる
4. `plugins/` を変えないことで、本件の差分を Core に閉じる（#53）

**違い**：届かなくなることで、これらの provider の片割れの 422 は**文言が Core のもの**に、`link` の片割れは**キーが `link`** に変わる（§6.7）。
Plugin の文言（`本文に扱えない文字が含まれています。`）は、046 の前の Core で動くときと Plugin の単体テストでだけ使われる。

## 7. 画面

**変えない。** 画面の保存は `/api/v1` を叩き、422 の `details` を項目の欄の下に出す（キーは最上位の項目名で、各フォームが既に使っているもの）。
画面の入力欄から NUL・対になっていないサロゲートは入らず（ブラウザの入力は整った文字列）、画面が URL から UseCase へ渡す文字列は 500 にならない（§1.2.1 表 S）。E2E は足さない。

## 8. 権限（Permission）

Permission の定義は変えない。**認可は入力の検査より先**（既存の規則）。以下の「使えない文字」は NUL と対になっていないサロゲート。

| 経路 | 順序 | 権限なし | 未認証 |
| --- | --- | --- | --- |
| 認証のある HTTP の操作 | 認証 → Permission → 使えない文字 → Zod → UseCase（L2 → 既存の検査） | 403（使えない文字を含んでいても） | 401（同） |
| 認証の要らない口（§6.3） | CSRF（`/collect` を除く）→ 使えない文字 → Zod | — | — |
| Data API | Manifest の宣言 → 利用者の Permission（`defineUseCase`、または一覧の `requirePermission`）→ L2 | 宣言なし → `PluginPermissionError`、利用者に無し → `ForbiddenError`（どちらも `ValidationError` より先） | 既存どおり |
| UseCase を直接呼ぶ経路 | `defineUseCase` の Permission → L2 | `ForbiddenError` | 既存どおり |
| Plugin Store | 自分の名前空間だけ（既存）→ L3 | — | — |
| `POST /analytics/rollup` の `pruneOlderThanDays` | `analytics.read` → Zod（上限）→ 集計 → `system.manage` → 削除 | `analytics.read` 無し → 403。`system.manage` 無しで 1〜36500 → 集計の後 403（既存） | 401 |

## 10. 受け入れ条件

**A = 単体（純関数・Zod スキーマ・`buildOpenApiDocument`）、B = 結合（DB を通す。UseCase・Data API・Store・配信・ジョブ）、C = API（Route Handler を直接呼ぶ。DB あり）、D = 画面（E2E。本設計では無し）、E = 静的検査。**
「NUL の文言」は `使用できない文字（NUL）が含まれています。`、「サロゲートの文言」は `使用できない文字（対になっていないサロゲート）が含まれています。`。
「片割れ」は対になっていないサロゲート（例 `'\ud800'`・`'\udc00'`）。**絵文字は対になったサロゲート**（U+1F44D など）で、片割れではない。

### 10.1 文字の規則の純関数（A）

1. (A) `containsNul`：`''`・`'abc'`・`'a\u0001'`・絵文字 → 偽。`'\u0000'`・`'a\u0000b'` → 真
2. (A) `containsLoneSurrogate`：`'a\ud800b'`・`'\udc00'`・`'x\ud83d'`（末尾の上位）・`'\ude00\ud83d'`（下位が先の逆順）・絵文字の後ろに `'\ud800'` → 真。`''`・`'abc'`・絵文字・`'\u0000'` → 偽
3. (A) `unusableTextDetailsOf`：`{ a: 'x', b: 'y\u0000' }` → `{ b: [NUL の文言] }`。`{ b: 'y\ud800' }` → `{ b: [サロゲートの文言] }`。`{ b: 'y\u0000\ud800' }` → `{ b: [NUL の文言, サロゲートの文言] }`（この順）。
   `{ p: { q: ['ok', 'n\u0000', 'm\u0000'] } }` → `{ p: [NUL の文言] }`（重複しない）。`{ p: { 'k\ud800': 1 } }` → `{ p: [サロゲートの文言] }`。`{ 'k\u0000': 1 }` → `{ _: [NUL の文言] }`。`['a\u0000']`・`'a\u0000'` → `{ _: … }`。
   `{ a: 'x\u0000', b: 'y\ud800' }` → キーの順が `a`・`b`。何も無ければ `{}`。`Date`・`Uint8Array` の中は見ない
4. (A) `toStorableText`：`'r\u0000'`・`'r\ud800'` の NUL・片割れが U+FFFD になり、`length` が変わらない。絵文字・通常の文は変わらない
5. (A) `NUL_MESSAGE` と `LONE_SURROGATE_MESSAGE` がそれぞれ上の文言と等しい
6. (A) `isValidExternalUrl`・`isValidMediaUrl`・`isValidLink`・`isValidManualUrl` が `'https://x.example.com/p\u0000'` を偽にする（NUL の無い同じ URL は真のまま）

### 10.2 HTTP の本文・クエリ（L1。C）

7. (C) §1.2.1 **表 H の 36 件すべて**を、値に NUL を足したものと片割れを足したものの 2 通りで送ると、どちらも 422 `VALIDATION_ERROR`、`details` が**ちょうど 1 つのキー**（その最上位の項目名。`media[].alt` は `media`、`providerOptions` のキーは `providerOptions`）で、
   値がそれぞれ `[NUL の文言]` / `[サロゲートの文言]`。作成は件数が増えず、更新は対象が変わっていない
8. (C) クエリ：`GET /sites?q=`・`/campaigns?q=`・`/users?q=`・`/social/accounts?provider=`・`/analytics/breakdown?source=`・`/analytics?source=`・`/plugins/registry?q=` に `%00` を含む値 → 422、`details` が `{ <名前>: [NUL の文言] }` だけ
9. (C) 複数・入れ子：`POST /sites` の `name` に NUL、`description` に片割れ → `details` に 2 つのキー（それぞれの文言）。`name` に NUL と片割れの両方 → `details.name` が 2 つの文言（NUL が先）。
   `POST /campaigns` の `siteIds: ['\u0000']` → `details.siteIds` が NUL の文言（UUID の文言ではない）。本文の最上位に NUL を含むキー（`{ 'na\u0000me': 'x', name: 'N', url: … }`）→ `details._`。`name` に NUL で `status: 'bogus'` → `details` は `name` だけ（Zod を走らせない）
10. (C) 認可が先：`POST /sites` の `name` に NUL を、認証なし（Cookie の無いブラウザ・CSRF は通す）で → 401。`site.write` を持たない Token で → 403。CSRF を付けないセッションで → 403 `CSRF_FAILED`。`GET /sites?q=%00` を認証なしで → 401、`site.read` を持たない Token で → 403
11. (C) 422 の応答の本文（JSON 全体）に、送った値（`'marker-046'` に NUL・片割れを足したもの）の `marker-046` が含まれない。`unhandled error in route` のログが出ない。
    **（2026-09-25 追記。検証の指摘 spec 軽微 1）422 を返すまでの、どのレベルのログにも `marker-046` が含まれない**
12. (C) 変わらないもの：`GET /sites/{id}`・`DELETE /webhooks/{id}`・`GET /plugins/operations/{id}`・`PUT /plugins/{id}/settings` の `{id}` に NUL → 404。`GET /auth/callback?state=%00&code=%00` → 302（`/login?error=authorization_failed`）

### 10.3 認証の要らない口（C）

## 13. リスク

1. **動作の変更の影響**：片割れを含む要求を 2xx で保存していた外部アプリ（絵文字を UTF-16 の長さで切るもの）が 422 を受け取る（ユーザー裁定 2）。公開前で、変更履歴と §1.3 に回避（コードポイント単位で切る）を書く
2. **L1 が要求の本文をたどる**：本文は既に JSON として読まれた値で、大きさは実行環境の上限の内側（`045` §11 の 6）。1000 件の配列でも数ミリ秒に収まる。正規表現は量指定子の入れ子が無く、入力の長さに対して線形。
   **（2026-09-25 追記。検証の指摘 M1・M2）** 初版の実装は入れ子を再帰でたどり、1 万段の入れ子（`JSON.parse` は読める）で `RangeError`、
   `Object.prototype` の名前の項目で `TypeError` になって、認証の要らない口を含むすべての JSON の口が 500 を返した。再帰しないたどり方と、項目名を `Map` に積む作りに直した。
   **入力の項目名と深さは送った側が決める**ことを、同じ種類の検査を足すときに忘れない
3. **L2 の対象の項目の漏れ**：§4.2 の表に無い項目を将来足すと、UseCase を直接呼ぶ経路で NUL が 500 になり、片割れが U+FFFD で保存されうる。HTTP は L1 が守る。#22 は表の全件を回すので、表と実装の食い違いは見つかる。新しい項目を足す設計は §4.2 を見ること。
   **（2026-09-25 追記）** §4.2 の末尾の注記のとおり、列挙の値とアナリティクスの出所（`status`・`deliveryMode`・`source`）は、UseCase を直接呼ぶと NUL で `DatabaseError` になる（外から届く経路は無い。記録だけ）
4. **`toStorableText` と秘匿の順序**：秘匿（資格情報の値の伏せ字）の前に置き換えると、NUL・片割れを含む資格情報の値が完全一致の伏せ字に掛からなくなる。秘匿の後に掛ける（§9.4）
5. **`isValidExternalHttpsUrl` の変更は HTTP の `link`・`media[].url`・`externalUrl` にも効く**：NUL は L1 が先に断るので、HTTP の応答は変わらない
6. **N2 の競合**：`analytics.record` の `siteId` の存在を確かめてから書くまでにサイトが消されると、外部キー違反（500 / `DatabaseError`）が残りうる。`045` §6.4 の `FOR KEY SHARE` は使わない（集計値の 1 行の書き込みで、サイトの削除と重なる頻度が低く、残っても不具合として見える）
7. **既存テストの変更**：§10.13。テストを弱めるのではなく、規則の変更に伴う期待の置き換え
