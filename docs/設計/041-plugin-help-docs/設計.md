## 1. 目的

SNS 配信 Plugin（`036` Bluesky・`037` X・`038` Instagram・`040` Threads）を使うには、利用者が各 SNS の開発者向け画面でトークンを発行し、
Torifune の `/social` へ入れる必要がある。いまその手順は各 Plugin の `README.md` に数行ずつ書かれているだけで、

1. **Torifune の画面からは読めない。** `README.md` は Plugin のフォルダに置かれたファイルで、画面のどこにもリンクが無い。
   資格情報の欄の下の説明（`credentialFields[].description`。`039` §7.1.2）は 1〜2 文で、手順の全体は書けない
2. **初心者には粗すぎる。** 「Meta for Developers で App を作り、Instagram API を追加します」の 1 行の裏に、開発者アカウントの登録・App の種類の選択・
   テスターの招待と承認・トークンの生成が隠れている。どこで何を押し、何をどの欄へ写すかが書かれていない

本設計は、次の 3 つを行う。

* **Plugin が手順書（Markdown）を同梱し、Manifest で宣言できるようにする。** Core はそれを `/plugins/<id>/help/<docId>` に描く（汎用の仕組み。SNS 専用にしない）
* **資格情報を入れる場所と Plugin の設定画面から、その手順書へ飛べるようにする**（ヘルプボタン）
* **4 つの SNS 配信 Plugin に、初心者向けの細かい手順書を書く**（§12）

あわせて、`/plugins` の「設定」ボタンが 404 に飛ぶ不具合を直す（ユーザー裁定 3。§7.6）。

## 3. スコープ

### 3.1 やること

* **Plugin API：** `PluginManifest` に省略できる `help`（手順書の一覧）を足す。形の誤りは Manifest を拒否せず、**`help` を無いものとして扱い警告を返す**（§9.2）
* **Plugin 層：** 宣言された手順書のファイルを、**その Plugin のフォルダの中に限って**実行時に読む（§6.2）
* **Application 層：** 手順書を読む UseCase（認可を含む）と、provider → 手順書のリンクを引く関数（§6.3）
* **画面：**
  * 手順書の画面 `/plugins/<id>/help`（一覧）と `/plugins/<id>/help/<docId>`（本文）（§7.2・§7.3）
  * Markdown を**サーバで React の要素に**描く部品（HTML を通さない。§7.3）
  * `/social` の 2 つの Modal に手順書へのリンク（§7.4）
  * Plugin の設定画面に手順書の一覧。設定を持たず手順書だけを持つ Plugin にも設定画面を出す（§7.5）
  * `/plugins` の「設定」を実在する行き先だけにする（§7.6）
* **依存の追加：** `react-markdown`・`remark-gfm`・`rehype-slug`（選定理由は §4.2）
* **手順書の中身：** `sns-bluesky`・`sns-x-api`・`sns-instagram`・`sns-threads` の 4 つに、初心者向けの資格情報の手順書を 1 つずつ（§12）。
  `example-plugin` に仕組みの見本の手順書を 2 つ（§12.6。E2E の題材）
* README を「要約＋手順書へのリンク」に改め、詳しい手順を手順書へ移す（§12.7）
* `docs/Plugin開発ガイド.md` に手順書の書き方を足す（§13）
* **`sns-instagram`：ユーザー ID の欄に `auto` を入れれば、配信の入口で `/me` を問い合わせて数字の ID を補い、成功したら書き戻す**（ユーザー裁定 U1。§6.4）
* **`sns-bluesky`：App Password の形でない値（ログイン用のパスワードなど）を Bluesky へ送らずに断る**（ユーザー裁定 U2。§6.5）

### 3.2 やらないこと

| やらないこと | 理由 |
| --- | --- |
| 画像（スクリーンショット）を手順書に載せる・同梱の画像を配る経路 | §12.2。画像を配る経路は種類の判定（SVG は script を含みうる）と CSP の設計が要り、SNS の画面は変わりやすく古い画像は誤解を招く |
| 手順書の中の生の HTML を描く | §7.3.2。Plugin は信頼されたコードだが、文書に HTML を通す理由が無い。通せば描画の安全を Plugin 作者の注意に預けることになる |
| 外部サイトの手順書へのリンクだけで済ませる | ユーザー裁定 1 |
| `/plugins` のカードにヘルプボタンを置く | ユーザー裁定 2 |

### 4.1 ファイルを実行時に読む（ビルド時に埋め込まない）

**決めたこと：Core は、要求のたびに `pluginsDir()/<id>/<path>` を読む。埋め込みもキャッシュもしない。**

| 案 | 採否 | 理由 |
| --- | --- | --- |
| **実行時に読む（採用）** | 採る | 開発中・コンテナ・zip 導入のどれでもファイルはディスクにある（§2.1 の 3）。**手順書を直して再読み込みすれば反映される**（作者が再ビルドせずに確かめられる）。登録簿の生成スクリプトを変えずに済む |
| 生成スクリプトで `generated-registry.ts` に文字列として埋め込む | 採らない | 手順書の 1 文字の直しに `pnpm generate:plugins` と再起動が要る。生成スクリプト（`.mjs`。検証の部品を持たない）にパスの確認を二重に持つことになる。全 Plugin の手順書がサーバのバンドルに常に載る |
| 読んだ結果をプロセスに持つ（キャッシュ） | 採らない | 手順書の画面はめったに開かれず、ファイルは 256 KiB 以下（§6.2）、描画はミリ秒の単位。キャッシュは消し時（Plugin の入れ替え・ファイルの更新）の考慮を増やすだけ。要るようになったら §11 #6 |

* Manifest（`help` の宣言）は従来どおり**ビルド時の登録簿**から読む。`help` の宣言を足した・変えたときは `pnpm generate:plugins` と再起動が要る（Manifest の他の項目と同じ）。**本文の直しは再起動が要らない**。開発ガイドに書く（§13）
* 生成スクリプトは `<repoRoot>/plugins` を、実行時は `pluginsDir()`（`TORIFUNE_PLUGINS_DIR`）を見る。両者が別の場所を指す構成では手順書が「読み込めません」になる（§11 リスク 4）

### 4.2 依存の選定（`CLAUDE.md`「新たな選定が必要になったら…選定理由を残してから」）

**採用：`react-markdown`（MIT）＋ `remark-gfm`（MIT）＋ `rehype-slug`（MIT）。** 版は実装の時点の最新の安定版（2026-09-24 の npm の表示で `react-markdown` 10.1.0、`remark-gfm` 4.0.1）。

| 候補 | 出力 | 採否 | 理由 |
| --- | --- | --- | --- |
| **`react-markdown`** ＋ `remark-gfm` ＋ `rehype-slug` | **React の要素** | **採る** | **`dangerouslySetInnerHTML` を使わずに済む**（HTML の文字列を経由しない）。生の HTML は既定で解釈しない（`rehype-raw` を入れない限り）。リンク・画像・見出しを `components` で差し替えられ、§7.3 の規則をすべて React の要素の側で書ける。フックを使わない同期の部品なので **Server Component で描け、ブラウザへ JS を送らない**。unified（remark / rehype）の系統で保守が続いている。表（GFM）は `remark-gfm`、見出しの `id` は `rehype-slug`（GitHub と同じ `github-slugger` の規則）で足せる |
| `markdown-it`（MIT） | HTML の文字列 | 採らない | `html: false` で安全な既定を持つが、出力は文字列で **`dangerouslySetInnerHTML` が要る**。リンクに `target` / `rel` を足すには描画の規則の差し替えが要り、安全の確かめが文字列の上になる |
| `marked`（MIT） | HTML の文字列 | 採らない | 生の HTML をそのまま通すのが既定で、無害化の部品（DOMPurify。サーバでは jsdom が要る）を別に足す必要がある |
| `micromark`（MIT） | HTML の文字列 | 採らない | 安全な既定だが文字列の出力。リンクの属性の差し替えが後処理になる |
| 自前の小さな Markdown の解釈 | — | 採らない | 表・入れ子のリスト・コードの囲みを正しく解釈するのは小さくない。解釈の誤りは描画の誤り（ひいては安全の誤り）になる |

* 3 つとも **MIT**（`rehype-slug` の依存 `github-slugger` は ISC）。Torifune（MIT）と両立する
* 依存の木は unified の小さなパッケージの集まりになる（`mdast-util-*` / `micromark-*` など）。**すべてサーバでだけ動き、ブラウザのバンドルに入らない**（`MarkdownView` を `'use client'` の部品から import しない。#65 の静的検査）
* CLAUDE.md の「UI ライブラリは導入しない」には当たらない（見た目の部品を持たない解釈器である。見た目は Torifune の CSS 変数で付ける）
* 依存の追加は**確定**（2026-09-24 オーケストレーター判断。§11.1 #2）

### 6.1 Manifest の `help`（`packages/plugin-api/src/manifest.ts`）

```ts
/** Plugin が同梱する手順書 1 本（041 設計 §6.1）。 */
export interface PluginHelpDoc {
  /** URL の一部（`/plugins/<plugin-id>/help/<id>`）。英小文字・数字・ハイフン、1〜64 文字、先頭は英小文字か数字。 */
  readonly id: string;
  /** 画面に出す題名。前後の空白を除いて 1〜80 文字。 */
  readonly title: string;
  /** Plugin のフォルダからの相対パス（`/` 区切り）。`.md` で終わる。 */
  readonly path: string;
}

export interface PluginManifest {
  // …既存の項目…
  /**
   * 同梱する手順書（041 設計）。**並びが画面の並び。先頭が「最初に読む手順書」**で、
   * SNS 配信 Plugin では資格情報の手順書を先頭に置く（`/social` のヘルプボタンが先頭を開く。§7.4）。
   * 形が誤っていれば本体は `help` を無いものとして扱う（Manifest そのものは拒否しない）。
   */
  readonly help?: readonly PluginHelpDoc[];
}

export const PLUGIN_HELP_LIMITS = {
  maxDocs: 10,
  maxTitleLength: 80,
  maxPathLength: 200,
  /** ファイルの大きさの上限（バイト）。本体が読むときに確かめる。 */
  maxFileBytes: 262_144,
} as const;

export type ManifestValidation =
  | {
      readonly ok: true;
      readonly manifest: PluginManifest;
      /** Manifest を拒否しない誤り（041 設計 §9.2。いまは `help` だけ）。無ければ省略または空。 */
      readonly warnings?: readonly ManifestProblem[];
    }
  | { readonly ok: false; readonly problems: readonly ManifestProblem[] };
```

**`help` の形の規則**（1 つでも破れば `help` 全体を無いものとして扱い、`warnings` に `{ field: 'help', message }` を 1 件足す。**全部か無しか**にするのは、作者が誤りに気づくため：一部だけ出ると誤りが見えにくい）

| 対象 | 規則 |
| --- | --- |
| `help` | 配列。`[]` は「宣言なし」と同じ（警告しない）。`maxDocs` 件まで |
| 要素 | オブジェクト。**未知のキーは許す**（前方互換。後から `lang` などを足せる） |
| `id` | `/^[a-z0-9][a-z0-9-]{0,63}$/`。同じ `help` の中で重複しない |
| `title` | 文字列。`trim()` の後が 1〜`maxTitleLength` 文字 |
| `path` | 文字列、1〜`maxPathLength` 文字。`/^[A-Za-z0-9_-][A-Za-z0-9._-]*(\/[A-Za-z0-9_-][A-Za-z0-9._-]*)*\.md$/`（**`/` 区切りの相対パス。各区切りの先頭は `.` にできない**＝ `..`・`.`・隠しファイル・隠しフォルダを拒む。先頭の `/`、`\`、ドライブ名（`C:`）、空の区切り（`//`）、URL（`https:`）はこの形に合わない）。拡張子は小文字の `.md` だけ。同じ `help` の中で重複しない |

* 他の項目の誤りで `ok: false` になるときは、`help` の誤りを `problems` に**混ぜない**（従来どおりの `problems`）
* `ok: true` の `manifest` は、`help` が誤っていれば **`help` のキーを持たない**（型が嘘にならないように）。正しければ入力の値をそのまま持つ
* `warnings` は `help` に誤りが無ければ**キーごと省略**する（既存のテストが `ok: true` の結果を丸ごと比べていても変わらないように）

### 6.2 ファイルを読む（`apps/web/src/plugin/help-files.ts`）

```ts
export type HelpFileFailure =
  | 'not_found'           // 無い
  | 'not_file'            // フォルダなど、通常のファイルでない
  | 'outside_plugin_dir'  // 実体が Plugin のフォルダの外（シンボリックリンク・.. など）
  | 'too_large'           // PLUGIN_HELP_LIMITS.maxFileBytes を超える
  | 'invalid_encoding';   // UTF-8 として読めない

export type HelpFileResult =
  | { readonly ok: true; readonly markdown: string }
  | { readonly ok: false; readonly reason: HelpFileFailure };

/** pluginDirectory の中の relativePath を読む。テストのためにフォルダを引数で受ける。 */
export function readPluginHelpFile(pluginDirectory: string, relativePath: string): Promise<HelpFileResult>;
```

手順（上から順。**Manifest の検査（§6.1）を通った `path` しか渡らないが、ここでも独立に確かめる**。検証を 1 か所に頼ると、そこを直したときに気づけない。`extractPackage` の二重の確認と同じ考え）：

1. `base = realpath(pluginDirectory)`（Plugin のフォルダそのものがシンボリックリンクでもよい。開発で `plugins/` を張ることがある）
2. `candidate = resolve(base, relativePath)`。`candidate` が `base + sep` で始まらなければ `outside_plugin_dir`（**ファイルに触れる前に**止める）
3. `real = realpath(candidate)`。無ければ `not_found`。`real` が `base + sep` で始まらなければ `outside_plugin_dir`（フォルダの中のシンボリックリンクが外を指す場合）
4. `stat(real)` が通常のファイルでなければ `not_file`。大きさが `maxFileBytes` を超えれば `too_large`（**読む前に**大きさで断る）
5. 読んで `TextDecoder('utf-8', { fatal: true })` で文字にする。失敗すれば `invalid_encoding`。先頭の BOM（U+FEFF）を除く
6. 読んでいる間に大きくなった場合に備え、読んだバイト数も `maxFileBytes` と比べる（超えれば `too_large`）

* **例外を投げない**（`EACCES` など上に無い失敗は `not_found` に寄せる）。理由のコードだけを返し、パスや OS のエラー文言を返さない
* 読み出しは `pluginDir(pluginId)`（`paths.ts`）を `pluginDirectory` に渡して行う（呼び出しは §6.3 の UseCase）

### 6.3 UseCase とリンクの関数（`application/plugin/plugin-help-use-cases.ts`）

```ts
export interface HelpDocSummary {
  readonly id: string;
  readonly title: string;
  /** `/plugins/<pluginId>/help/<id>` */
  readonly href: string;
}

export interface PluginHelpIndex {
  readonly pluginId: string;
  readonly pluginName: string;
  readonly pluginVersion: string;
  /** Manifest の宣言の順。1 件以上。 */
  readonly docs: readonly HelpDocSummary[];
  /** 読み込まれて動いているか（画面の注記に使う。§7.3.1） */
  readonly loaded: boolean;
}

export type PluginHelpDocResult = Omit<PluginHelpIndex, 'docs'> & {
  /**
   * 同じ Plugin の手順書の宣言（宣言の順）。**本文の中の相対リンクの解決に使うため `path` を含める**
   * （2026-09-24。D9：実装にあった `helpDocPathsOf` を消し、認可を通った結果だけから引く）。
   */
  readonly docs: readonly (HelpDocSummary & { readonly path: string })[];
  readonly doc: HelpDocSummary & { readonly path: string };
  /** 読めたときは本文、読めなければ理由のコード（§6.2）。 */
  readonly content:
    | { readonly ok: true; readonly markdown: string }
    | { readonly ok: false; readonly reason: HelpFileFailure };
};

/** 手順書の一覧。name: 'plugin.help.index'。 */
export const getPluginHelpIndex: UseCase<{ pluginId: string }, PluginHelpIndex>;

/** 手順書の本文。name: 'plugin.help.get'。 */
export const getPluginHelpDoc: UseCase<{ pluginId: string; docId: string }, PluginHelpDocResult>;

/**
 * provider → 先頭の手順書のリンク（§7.4）。いま publisher を登録している Plugin だけを見る。
 * 認可を持たない純粋な引き当て：返すのは「読み込まれた Plugin の手順書の題名と URL」で、
 * それは認証済みの誰でも読める（§8）。呼ぶのは `/social` の Server Component（認証済み）だけ。
 */
export function helpLinkOfPlugin(pluginId: string): HelpDocSummary | null;
```

両 UseCase は `permission: null`（理由：「読み込まれた Plugin の手順書は認証済みの誰でも読む。読み込まれていない Plugin だけ `plugin.manage` を中で求める」）とし、中で次の順に判定する。

1. `requireAuthenticated`（未認証は `UnauthenticatedError`）
2. **ビルドの登録簿（`discoverPlugins().plugins`）に `pluginId` が無い → `NotFoundError`**（読み込めなかった Plugin・隔離・ファイルが消えた Plugin・存在しない ID。`plugin.manage` を持っていても同じ）
3. `loadedPlugin(pluginId) !== null`（読み込まれて動いている）→ 次へ
   それ以外（検出済み・導入済みで無効・有効だが再起動待ち）→ `plugin.manage` を持たなければ **`NotFoundError`**（`ForbiddenError` にしない。§8）
4. Manifest の `help` が無い・空 → `NotFoundError`
5. （本文のみ）`docId` が宣言の `id` のどれとも一致しない → `NotFoundError`。**`docId` をパスとして使わない**（宣言の `path` だけを読む。`..` などを入れても宣言と一致しないので読まれない）
6. （本文のみ）`readPluginHelpFile(pluginDir(pluginId), doc.path)`。失敗は例外にせず `content: { ok: false, reason }` で返し、
   `log.warn('plugin help could not be read', { pluginId, docId, reason })` を 1 回出す（**パス・OS のエラー文言を載せない**）

`helpLinkOfPlugin` は `loadedPlugin(pluginId)?.manifest.help?.[0]` から組む。読み込まれていなければ `null`。ファイルの有無は見ない（`/social` を描くたびにファイルを触らない。無ければ手順書の画面が §7.3.5 のエラーで出る）。

**宣言の `path` を画面へ渡す口は `getPluginHelpDoc` の結果だけにする**（D9）。実装にあった `helpDocPathsOf(pluginId)`（認可を持たずに宣言を引く関数）は**消す**。
本文の画面は結果の `docs`（`path` つき）から `HelpLinkContext.docs` を組む。一覧（`getPluginHelpIndex`）の `docs` は `path` を持たない（一覧の画面は相対リンクを解決しない）。

### 6.4 `sns-instagram`：ユーザー ID を Torifune が補う（ユーザー裁定 U1）

**Plugin の中だけの変更。Core・Plugin API・`039` の画面は変えない。**

#### 6.4.1 何を入れるか

* 「Instagram ユーザー ID」の欄（`igUserId`）に **`auto`** を入れられるようにする。英字の大文字・小文字は問わない（`/^auto$/i`）。前後の空白は許さない（`039` の画面は値をそのまま送り、空白を含む値は従来どおり形の誤り）
* **空欄にしない理由。** `039` の画面は全項目の入力を求める（`setCredentialBody` の「すべての項目を入力してください」）。空欄は画面から送れない。
  `accessTokenExpiresAt` の `unknown`（`038` §5.2）と同じ「分からなければ決まった語を入れる」形に揃える
* 欄の `label` は変えない（「Instagram ユーザー ID」。#66 (c) が手順書と突き合わせている）。`description` を次にする：
  「Instagram のプロアカウント（ビジネスまたはクリエイター）の ID。数字だけの文字列です。@ で始まるユーザーネームではありません。
  **分からなければ auto と入れてください。** 次の配信のとき、Torifune がアクセストークンから ID を確かめて保存し直します。」
* `placeholder` は `'auto'` にする（`039` の画面は `placeholder` を出さないが、宣言として揃える）

#### 6.4.2 配信の入口での問い合わせ（R0）

`publish()` の P0（入力の検査）で、`igUserId` が `auto` なら**従来の `CREDENTIAL_REASON` で断らず**、準備（`prepare`）の最初に R0 を送る。

| 項目 | 決めたこと |
| --- | --- |
| 要求 | `GET https://graph.instagram.com/<GRAPH_API_VERSION>/me?fields=user_id`（`GRAPH_API_VERSION` は `graph.ts` の定数 `v26.0`。URL は `new URL(path, GRAPH_API_BASE_URL)` で組む） |
| トークンの渡し方 | **R1〜R5 と同じ `Authorization: Bearer <accessToken>`。URL のクエリに `access_token` を載せない**（`038` §6.2）。`redirect: 'manual'`、応答の本体は `RESPONSE_BODY_MAX_BYTES` まで（`sendGraphRequest` をそのまま使う） |
| `038` §11 #9 との関係 | `graph.instagram.com` が Bearer を受けることは実機で確かめていない（`038` §11 #9）。受けなければ R0 も R1 も `token` / `permission` の失敗で `retryable: false` になり、**最初の実機の疎通で分かる。** そのとき GET のクエリへ切り替えるなら、R0 も R5（permalink）と同じく **URL をログ・`reason` に載せない原則（`038` §6.11）の下で**切り替える |
| 制限時間 | **`ME_TIMEOUT_MS = 3_000`**（`graph.ts` の定数。`PERMALINK_TIMEOUT_MS` / `REFRESH_TIMEOUT_MS` と同じ、読むだけの要求の長さ）。**準備の期限（`PREPARE_BUDGET_MS`）の中で**、準備の signal の下で送る（R1 以降の時間を食うが、合計の期限は変えない） |
| 応答の形 | 本体の `user_id` が **文字列で `isValidIgUserId`（数字だけ・64 桁まで）に合う**ときだけ使う。数値（JSON の number）で返った場合は `Number.isSafeInteger` なら `String(値)` を使い、**安全な整数を超える値は使わない**（JSON の解釈で下の桁が失われている。Instagram の ID は 17 桁前後で安全な整数を超えうる）。無い・空・形に合わない → 下の「形の誤り」 |
| 成功 | 得た ID をこの配信の R1〜R5 に使う（`session.igUserId`）。ログは `log('instagram user id resolved', 'me')` の 1 行で、**ID の値を載せない** |

**失敗の分類（`retryable`）。** R0 は R4（公開）の前の要求なので、`038` の「送る前の相」の規則（既定で `true`、直らないものだけ `false`）に従う。`retryableFor` に相 `me` を足し、R1（`container`）と同じ扱いにする。

| R0 の失敗 | `retryable` | `reason` |
| --- | --- | --- |
| 接続できない・制限時間・5xx | `true` | R1 と同じ文言の対応（「接続できませんでした」「一時的に応答できませんでした」） |
| レート制限（429・既知のレート制限のコード） | `true`（`retryAfterMs` があれば付ける） | R1 と同じ（レート制限の文言） |
| トークンが無効・期限切れ（既知のコード） | `false` | 既存の「アクセストークンが無効か期限切れです」 |
| 権限が足りない | `false` | 既存の「権限が足りません」 |
| 3xx・その他の 4xx | R1 と同じ分類 | R1 と同じ対応 |
| **応答の形の誤り**（`user_id` が無い・形に合わない・安全な整数を超える数値） | **`false`** | **新しい文言** `ID_UNRESOLVED_REASON`：「Instagram のユーザー ID を自動で確かめられませんでした。「資格情報を設定」で、ユーザー ID の欄に数字だけの ID を入れてください。」 |
| 呼び出し側の打ち切り | 既存のとおり（`ABORTED_REASON`） | 既存のとおり |

* 形の誤りを `false` にする理由：成功の応答が期待しない形なのは再試行で直らない（Graph API の仕様の変更か、別の窓口のトークン）。人が数字の ID を入れれば直る
* **`reason`・ログに、トークン・応答の本体・得た ID・要求の URL を載せない**（`038` §6.11 と同じ。ログに渡すのは既存の `failureFields` の素性だけ）
* R0 が失敗したら R1 以降を送らない（何も公開していない）

#### 6.4.3 書き戻し（`rotatedCredential`）

公開（R4）に**成功したときだけ** `rotatedCredential` を返す（Plugin API の約束：`rotatedCredential` は `ok: true` のときだけ。`035` §9.2）。

| その配信で起きたこと | 返す `rotatedCredential` |
| --- | --- |
| `auto` を R0 で解決し、トークンの延長はしなかった | `{ igUserId: <得た数字>, accessToken: <入っていた値>, accessTokenExpiresAt: <入っていた値そのまま（unknown を含む）> }` ちょうど |
| `auto` を解決し、延長もした | `{ igUserId: <得た数字>, accessToken: <延長後>, accessTokenExpiresAt: <延長後の期限> }`（既存の延長の書き戻しの `igUserId` が得た数字になる） |
| 数字の ID で配信した | **従来どおり**（延長したときだけ返す） |

* **3 項目を明示して組む**（`...credential` で写さない。`038` §6.7 の既存の約束）
* **書き戻しは捨てられうる。** Core は `039` §6.1 の比較更新で書き戻す：配信の間に運用者が資格情報を入れ直した・消した場合は書き戻さない。その場合、運用者の値が `auto` のままなら次の配信でもう一度 R0 を送る
* **公開に失敗した配信では書き戻せない**（`ok: false` に `rotatedCredential` を載せられない。`037` §11 #2）。次の配信でもう一度 R0 を送る。R0 は 1 回の配信につき 1 回まで
* 書き戻しの後の配信は数字の ID を使い、R0 を送らない

#### 6.4.4 変えないこと

* **`igUserId` が数字のときの挙動は変えない**（R0 を送らない。要求の列・`reason`・`retryable`・書き戻しの条件が 041 より前と同じ）
* `auto` でも数字でもない値（`@name`・空白を含む値など）は従来どおり P0 で `CREDENTIAL_REASON`（`retryable: false`、`fetch` を呼ばない）
* 資格情報の形（3 項目・キー名）は変えない（`038` §5.2 の「後から足せない」を守る）

### 6.5 `sns-bluesky`：ログイン用のパスワードを送らずに断る（ユーザー裁定 U2）

**Plugin の中だけの変更。Core・Plugin API は変えない。**

#### 6.5.1 事実の訂正

AT Protocol の `com.atproto.server.createSession` は、App Password だけでなく**アカウントのパスワードも受け付け、そのときは全権限のセッションになる**（041 の検証 spec 軽微-3）。
したがって「ログイン用のパスワードを入れると配信が失敗する」は誤りで、**ログイン用のパスワードを入れても配信は成功し、Torifune に全権限の資格情報を預けることになる。**
`036` の手順書・README・`social.ts` の 401 の文言（「ログイン用のパスワードでは配信できません」）はこの誤りに立っていた。

#### 6.5.2 形の規則（根拠と確かめられなかった部分）

| 根拠（2026-09-24 に確認） | 分かったこと |
| --- | --- |
| `https://github.com/bluesky-social/atproto-ecosystem/blob/main/app-passwords.md`（Bluesky の公式リポジトリの説明） | 「App passwords are of the form `xxxx-xxxx-xxxx-xxxx`」。サービスが App Password でログインしているか（アカウントのパスワードでないか）を**簡単に確かめる**ことを勧めている。正規表現は示していない |
| `https://raw.githubusercontent.com/bluesky-social/atproto/main/packages/pds/src/account-manager/helpers/password.ts`（参照実装の PDS） | `randomStr(16, 'base32')` の 16 文字を 4 文字ずつ `-` で繋いで作る。base32 の文字は英小文字と数字（RFC 4648 の小文字の字母は `a-z` と `2-7`） |

**決めた形：`/^[A-Za-z0-9]{4}-[A-Za-z0-9]{4}-[A-Za-z0-9]{4}-[A-Za-z0-9]{4}$/`**（英数字 4 文字 × 4 組を `-` で繋いだ 19 文字）。

* 参照実装が作るのは英小文字と `2-7` だけだが、**許す幅を英数字（大文字を含む）に広げる**：
  * 自前の PDS（`README`「PDS の URL」）が参照実装と違う字母で作る可能性を、公式の説明では確かめられなかった
  * 写すときに大文字になった値をここで断ると、原因が「ログイン用のパスワード」でないのにそう案内することになる。送った先の PDS が判断する
* **確かめられなかったこと（明記する）：** 参照実装以外の PDS の実装がすべてこの形で App Password を作ること。この形でない App Password を作る PDS の利用者は、この Plugin で配信できなくなる（§11.2 #12）
* **防げないこと：** ログイン用のパスワードが偶然この形なら送られる。形の確認は「間違えて入れた」を防ぐためのもので、完全な判別ではない

#### 6.5.3 動き

* `publish()` の入口（PDS の URL の解決の後、`createSession` の前）で `credential['appPassword']` を上の形と比べる。合わなければ **`fetch` を 1 度も呼ばずに**
  `{ ok: false, retryable: false, reason: APP_PASSWORD_SHAPE_REASON }` を返す：
  「App Password（アプリパスワード）の形ではありません。ログイン用のパスワードは送らずに止めました。Bluesky の「設定 → プライバシーとセキュリティ → アプリパスワード」で発行した xxxx-xxxx-xxxx-xxxx の形の値を、「資格情報を設定」から入れてください。」
* ログは `logger.warn('app password shape rejected', { postId, attempt, phase: 'credential' })`。**入れた値・長さ・どこが違うかを載せない**
* `retryable: false`：人が直すまで直らない
* 401 の文言から「（ログイン用のパスワードでは配信できません）」を消し、「App Password を確認してください（取り消されていないか、写し間違いがないか）」にする
* 欄の `description`（`appPassword`）を「…xxxx-xxxx-xxxx-xxxx の形（英数字 4 文字を 4 組、ハイフンで繋ぐ）の文字列を入れます。**ログイン用のパスワードは入れないでください（この形でない値は Bluesky へ送らずに止めます）。**…」に改める
* `identifier`（ハンドル）の扱いは変えない

## 7. 画面

### 7.1 画面の一覧と遷移

```text

        └ 「資格情報を設定」の Modal ──┤  ヘルプボタン（新しいタブ）
/plugins/<id>/settings ─ 手順書の一覧 ─┘
                                        ↓

                                        ↑

/plugins ─ 「設定」（有効かつ読み込まれ、設定か手順書を持つときだけ）→ /plugins/<id>/settings
```

### 7.2 経路の決め方

**`/plugins/<id>/help`（一覧）と `/plugins/<id>/help/<docId>`（本文）にする。**

* `app/plugins/[pluginId]/help/page.tsx` と `app/plugins/[pluginId]/help/[docId]/page.tsx` を置く。Next.js は静的なセグメント（`help`）を catch-all（`[[...rest]]`）より先に選ぶ（`settings` と同じ）
* **Core の画面が優先される。** Plugin が `registerPage({ route: '/plugins/<id>/help' })` を登録していても Core の手順書が出る（`settings` と同じ扱い）。
  同梱の Plugin にこのルートを登録しているものは無い。開発ガイドに「`/plugins/<id>/settings` と `/plugins/<id>/help` は Core が使う」と書く（§13）
* **実際の挙動（2026-09-24 に確かめた。D11）：** `/plugins/<id>/help` と、その **1 段下** `/plugins/<id>/help/<x>` は Core の経路である。**`help` を宣言しない Plugin でも Core が受けて 404 を返す**（Plugin のページへは落ちない）。
  **2 段下** `/plugins/<id>/help/<x>/<y>` から先だけが Core の経路に合わず、catch-all（Plugin のページ）へ届く（`/plugins/<id>/settings/<下>` と同じ既存の挙動）
* 経路を `/plugins/` の外（例 `/help/plugins/<id>`）に置く案は採らない：Plugin に関わる画面は `/plugins/<id>/…` にまとめてあり、利用者が URL から Plugin を読み取れるほうがよい

#### 7.3.2 Markdown の描画（`ui/help/markdown-view.tsx`）

* 本文の文字列を変えずに描く（Core は本文を検査・加工しない。先頭の見出し 1 の省略だけが例外）

#### 7.3.4 リンクの解決（`ui/help/help-links.ts`。純関数）

```ts
export interface HelpLinkContext {
  readonly pluginId: string;
  /** いま描いている手順書の path（Manifest の値） */
  readonly currentPath: string;
  /** 同じ Plugin の宣言（id と path） */
  readonly docs: readonly { readonly id: string; readonly path: string }[];
}

export type ResolvedHelpLink =
  | { readonly kind: 'external'; readonly href: string }  // 新しいタブ
  | { readonly kind: 'internal'; readonly href: string }  // 同じタブ（Torifune の中）
  | { readonly kind: 'none' };                            // リンクにしない（文字だけ）

export function resolveHelpLink(href: string, context: HelpLinkContext): ResolvedHelpLink;
```

判定（上から順。前後の空白を除き、制御文字（U+0000〜U+001F・U+007F）を含むものは `none`）：

| 入力 | 結果 |
| --- | --- |
| `https:` / `http:` で始まる絶対 URL（大文字・小文字を問わない。`new URL` で解釈でき、ホストがある） | `external`（`href` は `URL#href`） |
| `#<断片>` | `internal`、`href` は `#help-<断片>`（本文の見出しの `id` に合わせる。断片が百分率符号化されていれば戻してから足す） |
| `//` または `/\` で始まる（プロトコル相対） | `none` |
| `/` で始まる（Torifune の中の絶対パス。例 `/social`） | `internal`、`href` はそのまま |
| 相対パス（`./x.md`・`x.md`・`../help/x.md`。`#断片` つきを含む） | `currentPath` のフォルダを基準に POSIX で正規化する。**途中で Plugin のフォルダより上へ出る `..` があれば、その後で戻ってきても `none`**（丸めない。D2）。正規化した結果が**宣言の `path` のどれかと一致すれば** `internal`（`/plugins/<pluginId>/help/<id>`、断片があれば `#help-<断片>` を足す）。一致しない（`README.md`・Plugin のフォルダの外・宣言していない `.md`・画像など）は `none` |
| それ以外（`javascript:`・`data:`・`vbscript:`・`file:`・`mailto:`・未知のスキーム） | `none` |

脚注の参照・戻りのリンクは、この関数を通さない（§7.3.2。D10）。

描き方：

* `external`：`<a href target="_blank" rel="noopener noreferrer">文言<span aria-hidden="true"> ↗</span><span class="tf-visually-hidden">（新しいタブで開きます）</span></a>`
  （`noopener`：開いた先から `window.opener` で戻らせない。`noreferrer`：手順書の URL を相手へ渡さない。`manual-pending.tsx` の前例に揃える。視覚的に隠す class が無ければ `ui/help` の CSS に足す）
* `internal`：`<a href>`（`target` なし）。**Next.js の `Link` は使わない**（手順書の中のリンクは数が少なく、先読みの要求を増やさない）
* `none`：リンクの文言だけを `<span>` で出す（`href` を HTML に出さない）

| --- | --- |

| 本文が読めない（`content.ok === false`） | h1 と注記は出し、本文の代わりに `Alert tone="danger"`「この手順書を読み込めませんでした。Plugin の配布物に手順書のファイルが含まれているか、管理者に確かめてください。」。**理由のコード・パスは画面に出さない**（ログにだけ残る）。HTTP は 200 |

### 7.4 `/social` のヘルプボタン（ユーザー裁定 2 の (a)）

#### 7.4.1 どの provider に出すか

`ProviderOption`（`ui/social/social-accounts.tsx`）に省略できる項目を 1 つ足す。

```ts

  /** この provider の publisher を登録している Plugin の、先頭の手順書（041 設計 §7.4）。無ければ省略。 */
  readonly help?: { readonly href: string; readonly title: string };
```

`buildProviderOptions`（`provider-options.ts`）に**省略できる第 2 引数** `helpOf?: (pluginId: string) => { href: string; title: string } | null` を足し、
`PublisherOptionSource` に**省略できる** `pluginId?: string` を足す（`listPublishers()` の要素は既に `pluginId` を持つ）。

| 入力の形（`039` §7.1） | ヘルプボタン | 理由 |
| --- | --- | --- |
| `fields`（publisher が項目を宣言） | その publisher の Plugin が手順書を宣言していれば**出す** | 本設計の主な対象 |

* 第 2 引数を省略した呼び出し（`039` の既存のテスト）では `help` を持たない（`039` #5〜#8・#32 が変更なしで通る）
* `help` が付くのは登録簿にある provider だけ。`KNOWN_PROVIDERS` にだけある provider には付かない

## 8. 権限（Permission）

**新しい Permission を作らない。**

| 操作 | 必要なもの | 満たす | 満たさない | 未認証 |
| --- | --- | --- | --- | --- |
| 手順書（一覧・本文）を読む：**読み込まれた** Plugin | 認証だけ | 200 | — | ログイン画面へ（UseCase は `UnauthenticatedError`） |
| 手順書を読む：**読み込まれていない** Plugin（検出済み・無効・再起動待ち） | `plugin.manage` | 200 | **404**（存在を明かさない） | ログイン画面へ |
| 手順書を読む：ビルドに入っていない ID・宣言の無い `docId` | — | 404 | 404 | ログイン画面へ |
| `/social` のヘルプボタンを見る | Modal を開ける＝`social.write`（表示制御） | 出る | Modal ごと出ない | — |
| 設定画面（手順書の一覧を含む）を開く | `plugin.manage`（従来どおり） | 200 | 「権限がありません」（`AsyncState forbidden`。従来どおり） | ログイン画面へ |
| `/plugins` の「設定」を見る | `/plugins` を開ける＝`plugin.manage` | 条件（§7.6）を満たせば出る | 画面ごと forbidden | — |

**読み込まれた Plugin の手順書を「認証済みなら誰でも」とする理由。**

* 資格情報を入れるのは `social.write` の利用者で、多くは `plugin.manage` を持たない。`plugin.manage` を求めると、ヘルプボタンを押した人が読めない
* `social.write` を求めると、SNS に限らない汎用の仕組み（§1）が 1 つの業務の Permission に縛られる。SNS 以外の Plugin の手順書を読む人を決められない
* 中身は **Plugin に同梱された配布物**で、インストールのデータ（利用者・投稿・資格情報）を含まない。公開の Plugin なら同じ文書が公開のリポジトリにもある
* 読み込まれた Plugin の存在は、メニューや `/social` のサービスの選択肢として、既に認証済みの利用者に見えている

**読み込まれていない Plugin で 404 にする理由。** catch-all（§2.1 の 7）と同じく、無効・未導入の Plugin の存在を未認可の相手に教えない。
`plugin.manage` を持つ管理者には読ませる（**ビルドに取り込まれた後＝導入の再ビルドの後**から。`plugins/` に置いただけでビルドに入っていない Plugin は、登録簿に無いので 404。D11）：**有効にする前に資格情報を用意する**（例：`sns-x-manual` を使いながら `sns-x-api` の 4 つの値を先に用意する。`037` §7.2）ために要る。**画面からの入口は作らない**（確定。2026-09-24 オーケストレーター判断。§11.1 #4）。管理者は URL `/plugins/<id>/help/<docId>` で読み、README にその URL を書く（§12.7）。

* **ID の差し替え：** 手順書は利用者ごとのデータではない。`pluginId` / `docId` を変えて読めるのは、上の表の条件を満たす手順書だけである。
  **宣言した `.md` 以外のファイル（`plugin.json`・`index.ts`・`README.md`・フォルダの外）は、どの `docId` でも読めない**（§6.3 の 5、§6.2）
* 監査：読むことは記録しない（§5）。読めない手順書は `log.warn` に Plugin ID・`docId`・理由のコードだけを残す

## 9. Plugin API への影響

### 9.1 公開するもの（追加のみ）

| 追加 | 種類 |
| --- | --- |
| `PluginManifest.help?: readonly PluginHelpDoc[]` | 省略できる項目 |
| `PluginHelpDoc` | 型 |
| `PLUGIN_HELP_LIMITS` | 定数 |
| `ManifestValidation` の `ok: true` の `warnings?` | 省略できる項目 |

**`PLUGIN_API_VERSION` は `1` のまま。** 足したのは省略できる項目だけで、既存の Plugin は何も変えずに同じ意味で動く。

| 組み合わせ | 起きること |
| --- | --- |
| 新しい本体 × `help` を持たない Plugin | 何も変わらない（`help` が無いだけ） |
| 古い本体 × `help` を持つ Plugin | `validateManifest` が未知の項目として読み飛ばす（§2.1 の 1）。手順書が画面に出ないだけで、Plugin は動く |
| 新しい本体 × `help` の形が誤った Plugin | **Plugin は動く。** `help` だけが無いものとして扱われ、ログに警告が出る（§9.2） |

### 9.2 形の誤りで Manifest を拒否しない理由

既存の項目（`permissions` / `dependencies` / `extensions`）は形が誤れば Manifest ごと拒否する。`help` はそうしない。

* **041 より前、`help` は未知の項目で、どんな値でも通っていた。** 第三者の Plugin が独自の意味（例 `"help": "https://…"`）で使っていた場合、拒否にすると**本体を更新しただけでその Plugin が「読み込めなかった Plugin」に落ちる**。これは破壊的変更にあたる
* 手順書は Plugin の動作に要らない。誤っていても失うのは手順書の表示だけである
* 誤りに気づけるように、`warnings` を返し、本体は Plugin の読み込み（`discoverPlugins`）のときに `log.warn('plugin manifest has warnings', { pluginId, fields: ['help'], messages })` を出す。
  **ログは プロセスごと・Plugin ごとに 1 回だけ**（D8。`discoverPlugins` は `/plugins` の表示や手順書の画面のたびに呼ばれるので、毎回出すとログが埋まる。出した Plugin ID をプロセスの状態（`processState`）に覚える）（`messages` は `validateManifest` の `message`。値そのもの（パス）を含みうるが、配布物の宣言で秘密ではない）。
  zip の導入（`inspectPackage`）は `warnings` を見ない（導入は通す）

### 9.3 名前空間

`/plugins/<id>/help` とその 1 段下は Core が使う（`/plugins/<id>/settings` と同じ。§7.2）。Plugin がこれらのルートに `registerPage` しても Core の画面（`help` を宣言しなければ 404）が出る。
**登録を拒否しない**（既存の Plugin の有効化を失敗させない）。開発ガイドに書き（§13）、`packages/plugin-api/src/ui.ts` の `PageRegistration.route` の JSDoc に予約の注記を足してよい（コメントだけの変更。D11。型・値は変えない）。

## 10. 受け入れ条件

**A = 単体（純関数・一時フォルダでのファイル読み出し・`renderToStaticMarkup`）、B = 結合（DB・登録簿・Plugin の有効化を通す）、C = API（Route Handler を直接呼ぶ）、
D = 画面（E2E。`plugins/example-plugin` を有効にして走らせる）、E = 静的検査。**

### 10.1 Manifest の `help`（A。`packages/plugin-api`）

1. (A) `validateManifest` に正しい `help`（2 件）を持つ Manifest → `ok: true`、`manifest.help` が入力と同じ（深く等しい）、**`warnings` のキーが無い**
2. (A) `help` を持たない Manifest、`help: []` の Manifest → `ok: true`、`warnings` のキーが無い。`help` を持たない Manifest の結果は 041 より前と深く等しい
3. (A) 次のそれぞれで `ok: true`、**`manifest` に `help` のキーが無い**、`warnings` がちょうど 1 件で `field === 'help'`：
   (a) `help` が文字列 `"https://example.com"`、(b) オブジェクト、(c) 11 件、(d) 要素が文字列、
   (e) `id` が `''`・`'Token'`・`'-a'`・65 文字・重複、(f) `title` が無い・`'   '`・81 文字・数値、
   (g) `path` が `'/help/a.md'`・`'C:/a.md'`・`'help\\a.md'`・`'../a.md'`・`'help/../a.md'`・`'./a.md'`・`'.hidden/a.md'`・`'help/.a.md'`・`'help//a.md'`・`'a.txt'`・`'a.MD'`・`'a.md.exe'`・`'https://x/a.md'`・`''`・201 文字・重複
4. (A) 要素に未知のキー（`lang: 'ja'`）があっても `ok: true`・`help` が残り・`warnings` が無い（前方互換）
5. (A) `help` が誤りで、かつ `id` も誤り → `ok: false`、`problems` に `help` が**含まれない**（従来の `problems` と同じ）
6. (A) `PLUGIN_API_VERSION === 1`。`PLUGIN_HELP_LIMITS` が `{ maxDocs: 10, maxTitleLength: 80, maxPathLength: 200, maxFileBytes: 262144 }`。`@torifune/plugin-api` の公開の出口から `PLUGIN_HELP_LIMITS` を import できる
7. (A) `packages/plugin-api` の既存のテストが変更なしで通る

### 10.2 ファイルの読み出し（A。`plugin/help-files.ts`。一時フォルダ）

8. (A) `help/a.md`（UTF-8、BOM つき）→ `ok: true`、`markdown` が BOM を除いた本文ちょうど
9. (A) 無いファイル → `not_found`。フォルダ（`help/a.md` という名のフォルダ）→ `not_file`

## 12. 手順書の内容計画

### 12.1 誰に向けて・何を書くか

* **読者：** SNS の開発者向け画面を初めて触る人。「App」「トークン」「API」の言葉を知らない前提で、出てきた言葉をその場で 1 行で説明する
* **目的：** 手順書の最後まで進めば、Torifune の欄に入れる値がすべて手元にそろい、どの値をどの欄へ貼るかが分かる
* **粒度：** 1 つの手順 = 1 つの操作（開く・押す・選ぶ・入れる・写す）。各手順に「開く画面」「押すもの（ボタン・メニューの名前を「」で）」「確かめること（成功したときに見えるもの）」を書く
* **日本語**。画面の名前は、SNS 側の画面が英語ならその英語の表記をそのまま「」で書き、初出で日本語の意味を添える（例：「Keys and tokens（キーとトークン）」）
* 手順書の作者（実装の担当）は、**各手順を §12.5 の公式文書の現行の版と突き合わせてから書く。** 突き合わせられなかった手順は「この手順は公式文書で確かめられませんでした」と明記し、推測で埋めない。確かめた日を「最終確認日」に書く

### 12.2 スクリーンショットを載せない（決めたこと）

* **SNS 側の画面は予告なく変わり、古い画像は文字より強く誤解を招く**（画像の中の配置を探して見つからない）。文字の手順は画面の名前で探せる
* 画像には**自分のアカウント名・App の ID・トークンの一部が写りやすい。** 公開のリポジトリに置く配布物に写り込むと取り消せない
* SNS 側の画面の画像の再配布の扱いが SNS ごとに異なり、確かめる手間に見合わない
* Torifune は手順書の画像を描かない（§7.3.2）

各手順書の冒頭に次の注記を置く（文言は §12.3 のひな形）：「スクリーンショットは載せていません。画面の名前や配置は SNS 側の変更で変わることがあります。見つからないときは、この手順書の最後の『公式の説明』を開いてください」。

### 12.3 手順書のひな形（4 本で共通。見出しの順を揃える）

```markdown
# <Manifest の title と同じ題名>

最終確認日：YYYY-MM-DD（この日に公式の説明と突き合わせました）

> この手順書は、<SNS名> で <値の名前> を用意し、Torifune に入れるまでを説明します。
> スクリーンショットは載せていません。画面の名前や配置は <SNS名> 側の変更で変わることがあります。
> 見つからないときは、最後の「公式の説明」を開いてください。

## 目次                    ← 作者が書く（#見出し のリンク。GitHub と同じ規則）
## この手順書でそろうもの   ← Torifune の欄の名前（credentialFields の label ちょうど）と、それぞれ何か。表
## 始める前に用意するもの   ← アカウントの種類、ログインできる端末（PC のブラウザを推奨する理由）、メモの置き場所の注意
## 全体の流れ               ← 番号付き 3〜6 行の概要
## 手順 1 …                 ← 1 手順 1 操作。「開く画面」「押すもの」「確かめること」
## 手順 N：Torifune に入れる ← /social の「SNSアカウントを追加」（新しく作る場合）と「資格情報を設定」（既にある場合）の両方。欄 ↔ 値の対応の表
## うまく入ったか確かめる   ← テスト用の投稿の予約のしかた、履歴で見る場所
## よくある間違い           ← 症状 → 原因 → 直し方 の表（配信の失敗の理由の文言と結ぶ）
## 期限と更新               ← 有効期限、Torifune の自動延長の有無、入れ直しの手順
## 安全のために             ← 後述の共通の注意＋SNS ごとの注意
## 画面が違うとき           ← 画面の名前が変わった場合の探し方（公式の説明の見出しの名前で探す）
## 公式の説明               ← §12.5 の URL（https のリンク）
```

**すべての手順書に書く共通の注意（「安全のために」）**

* 値は**この画面（Torifune）以外に貼らない**。チャット・メール・共有のメモ・AI のチャット・「トークンを確かめる」ような第三者のサイトに貼らない
* **SNS にログインするパスワードは Torifune に入れない**（入れる欄は無い。求められたら手順を誤っている）
* 値は発行した画面で一度しか表示されないものがある。写すまで画面を閉じない。写した値は、Torifune に入れ終えたら手元のメモから消す
* **入れ終えたら、クリップボードの履歴からも消す**（Windows の「クリップボードの履歴」、スマートフォンの入力の履歴、クリップボードを同期するアプリ）（D7）
* **画面の写真（スクリーンショット）を人に送る前に、値が写っていないか確かめる**（トークン・App Secret・ユーザー ID・App Password）（D7）
* 値をコマンドラインに直書きしない（シェルの履歴に残る）。本手順書はコマンドを使わない手順を先に書く（§12.4）
* 値が漏れたと思ったら、SNS 側で取り消し（再発行）てから、Torifune で「資格情報を設定」から入れ直す
* Torifune に保存した値は暗号化され、画面に再表示されない。**入れ直すときはすべての欄を入れ直す**（一部だけは変えられない。`039` §7.3.2）

#### `sns-bluesky`

* **そろうもの：** 「ハンドルまたはメールアドレス」「App Password（アプリパスワード）」
* **前提：** Bluesky のアカウント（`bsky.social` でも自分の PDS でもよい）。自分で PDS を運用している場合だけ、Plugin の設定画面の PDS の URL を変える（`README`「PDS の URL」）
* **手順（公式の説明で確かめて書く）：** Bluesky（Web なら `https://bsky.app`）にログイン → 「設定」→「プライバシーとセキュリティ」→「アプリパスワード」→ 追加 → 名前（例：`Torifune`）を付ける → **ダイレクトメッセージへのアクセスを許すかの選択肢があれば、許さない**（Torifune は DM を使わない）→ 表示された `xxxx-xxxx-xxxx-xxxx` を写す（再表示されない）→ ハンドルを確かめる（プロフィールの `@` の後ろ。**`@` は書かない**。独自ドメインのハンドルもそのまま）
* **よくある間違い：** ログイン用のパスワードを入れる（**Torifune が Bluesky へ送らずに止め、履歴に「App Password（アプリパスワード）の形ではありません」が出る**。U2。§6.5）、`@` を付ける、写すときに末尾が欠ける・空白が入る（同じく形の誤りで止まる）、アプリパスワードを取り消した（「ログインに失敗しました」）
* **訂正して書くこと（U2）：** Bluesky はログイン用のパスワードでもログインを受け付け、全権限のセッションになる。だから**ログイン用のパスワードは「失敗する」のではなく「危ない」**。Torifune は形で見分けて送らない、と書く（「ログイン用のパスワードを入れると失敗する」と書かない。#92）
* **期限と更新：** 有効期限は無い。取り消すまで使える。取り消すとこの Plugin からの配信だけが止まる
* **必ず書くこと（#67）：** 「ログイン用のパスワードではありません」の旨、「アプリパスワード」、「@」の扱い

#### `sns-x-api`

* **そろうもの：** 「API Key（Consumer Key）」「API Key Secret（Consumer Secret）」「Access Token」「Access Token Secret」
* **前提：** X のアカウント、X の開発者アカウント（Developer Console）、**従量課金のクレジット**（料金の額は書かない。料金表へのリンクだけ。`037` §6.1）。無料で使いたい場合は `sns-x-manual`（手動投稿）を案内する
* **手順：** Developer Console（`https://console.x.com`）にログイン → 開発者の規約に同意 → App を作る（名前・説明・使い道）→ **API Key と API Key Secret を写す（一度しか表示されないことがある）** → App の設定の「User authentication settings」で **App permissions を「Read and write」**にする（求められる他の欄の埋め方は公式の説明で確かめて書く）→ 「Keys and tokens」で **Access Token and Secret を生成**（自分のアカウント用）→ 表示が「Read and write」で作られたことを確かめて写す → クレジットを購入する
* **強調すること：** **権限を「Read and write」にした後で Access Token を生成する。** 先に生成したトークンは読み取り専用のままで、投稿が HTTP 403 で断られる（発行し直す）。OAuth 2.0 の値（Client ID / Client Secret / Bearer Token）は使わない
* **Torifune に入れる：** 4 つの欄の名前と値の対応。**API Key を作り直すと Access Token も作り直しが要る**場合があること（公式の説明で確かめて書く）。入れ直しは 4 つとも
* **よくある間違い：** 403（読み取り専用のトークン。**クレジットが無いときに 403 になるかは公式の説明で確かめられませんでした**、と添える。D3）、
  **402（X API が「支払いが要る」と返したとき。クレジットの残高を確かめる。履歴には「X が投稿の要求を受け付けませんでした（投稿、HTTP 402）」または「X が画像を受け付けませんでした（画像のアップロード、HTTP 402）」が出る**。D3）、
  401（値の取り違え・Key と Secret の入れ違い・**サーバの時計のずれ**）、Bearer Token を入れた、値に空白・改行
* **期限と更新：** 有効期限は無い。X 側で権限を変えた・作り直したら入れ直す
* **無料版から移るとき：** `sns-x-api` の README の「入れ替え」の手順への案内（手順書の中では概要だけ。README へのリンクは相対パスで書けない（宣言した `.md` だけがリンクになる。§7.3.4）ので、`/plugins` での操作の順序を 3 行で書く）
* **必ず書くこと（#67）：** 「Read and write」「OAuth 2.0」「Bearer Token」を使わないこと、「4 つとも」入れ直すこと、「従量課金」

#### `sns-instagram`

* **そろうもの：** 「Instagram ユーザー ID」「長期アクセストークン」「トークンの有効期限」
* **前提：** **Instagram のプロアカウント（ビジネスまたはクリエイター）**（個人アカウントからの切り替えの手順を書く）、Meta for Developers の開発者アカウント
* **手順（コマンドを使わない道を先に書く）：** Meta for Developers で App を作る（使い道に Instagram の API を選ぶ）→ 「Instagram ログインによる API の設定」の画面を開く → 投稿に使うアカウントを **Instagram のテスター**として App に加え、**Instagram 側で招待を承認する**（承認の場所を書く）→ App の画面でそのアカウントの**アクセストークンを生成**する（画面で長期のトークンが出る場合はそれを使う。出ない場合の交換の手順は公式の説明で確かめて別の節に書く）→ 権限 `instagram_business_basic` と `instagram_business_content_publish` を許可したことを確かめる → **ユーザー ID の欄には `auto` と入れる**（U1。Torifune が次の配信で確かめて数字の ID に書き換える。App の画面で数字の ID が分かればそれを入れてもよい）→ 有効期限を決める（発行日の 60 日後を `YYYY-MM-DDT00:00:00Z` の形で、分からなければ `unknown`）
* **強調すること：** ユーザー ID は `@` のユーザーネームではない（分からなければ `auto`）。**App Secret（App の秘密の鍵）は Torifune に入れない。**
  **トークンをブラウザのアドレス欄に入れて ID を確かめる方法（旧い確かめ方 B）は書かない**（U1。ブラウザの同期・拡張機能・最近閉じたタブ・クリップボードの履歴から漏れうる。security 中-1）。Graph API の版（`v26.0` など）も書かない（D5。版を書く手順が無くなる）
* **`auto` の説明：** 保存後の最初の配信で Torifune が Instagram に問い合わせ、成功した配信の後に数字の ID に書き換える。確かめられなかったときは履歴に「Instagram のユーザー ID を自動で確かめられませんでした…」が出るので、数字の ID を入れる（App の画面で探す場所を書く。見つからなければ公式の説明へ）
* **うまく入ったか確かめる：** テスト投稿には画像が要り、`/social` の投稿の画面には画像の欄が無いので API で予約する（§11.2 #10）。API Token をコマンドラインに直書きしない注意を添える
* **期限と更新：** 60 日。Torifune は配信が成功したときに残りが 30 日を切っていれば延長する。**30 日以上配信しないと失効しうる**。失効したら発行し直して「資格情報を設定」から入れ直す（`038` README）
* **よくある間違い：** 個人アカウント（「権限が足りません」）、ユーザーネームを入れた（`auto` にすれば避けられる）、Facebook ログイン用のトークンを入れた（公式の説明で確かめてから書く）、テスターの招待を承認していない、期限の形の誤り
* **必ず書くこと（#67・#87）：** 「プロアカウント」「数字だけ」「unknown」「60日」「App Secret」「auto」

#### `sns-threads`

* **そろうもの：** 「Threads ユーザー ID」「長期アクセストークン」「トークンの有効期限」
* **前提：** Threads のアカウント、Meta for Developers の開発者アカウント
* **手順（コマンドを使わない道を先に書く）：** Meta for Developers で App を作る（使い道に Threads API を選ぶ）→ 権限に `threads_basic` と `threads_content_publish` を加える → 投稿に使うアカウントを **Threads のテスター**として加え、**Threads 側で招待を承認する** → App の使い道の設定の **ユーザートークンの生成（User Token Generator）** で長期アクセストークンを発行する（2026-09-24 の検索で、テスターのアカウントには交換も App Secret も要らずに長期トークンが出るとの説明がある。**公式の説明で確かめてから書く**）→ 数字だけのユーザー ID を確かめる → 有効期限（60 日後、または `unknown`）
* **上の道が使えない場合：** 認可コード → 短期トークン → `th_exchange_token` の交換（上級者向けの別の節。**App Secret が要り、URL に秘密の値が載る**ので、コマンドラインに直書きしない・記録させない注意を README から写す。宛先のホスト名は書かず公式の説明へ案内する（§11 #9））。
  **禁止の形で書く（D6）：「App Secret やトークンを含む URL を、ブラウザのアドレス欄に貼らないでください」。** 認可の後に戻る先（受け取り先の URL）は**自分が管理するサーバのものだけ**にする（他人のサービスの URL にすると、認可コードがそこへ渡る）
* **強調すること：** App Secret は Torifune に入れない。**延長できるのは発行から 24 時間以上たったトークンだけ**（期限に `unknown` を入れて発行直後に配信すると、最初の延長は失敗しうるが投稿は成功する）
* **期限と更新：** 60 日。自動延長の条件は Instagram と同じ（`040` README）。失効したトークンは延長できない。
  **許可の期間（D4。公式の説明どおりに書く）：** 公開のプロフィールでは、アプリへの許可は 90 日で切れるが、**トークンを延長すると延びる**。非公開のプロフィールでは**延長しても延びず**、90 日で切れたら**許可し直す**（手順のテスターの承認とトークンの発行をやり直す）。
  書く前に公式の説明で確かめ、旧い記述「非公開のアカウントでこの期間が過ぎたときに Torifune の配信がどうなるかは確かめていません」を置き換える
* **Plugin を無効にしている間の注意：** 無効な間は「資格情報を設定」に 3 つの欄ではなく汎用の欄が出る（`040` README）。**有効にしてから入れる**
* **必ず書くこと（#67）：** 「threads_basic」「threads_content_publish」「数字だけ」「unknown」「60日」「App Secret」「24 時間」

### 12.7 README との分担（決めたこと）

**README は要約を残し、詳しい手順は手順書だけに書く**（同じ内容を 2 か所に持つと、片方だけ直されて食い違う）。

* 各 SNS の README の「〜を用意する」の節を次の形に改める：
  1. 1〜3 行の要約（何を用意するか。例：「Bluesky の設定からアプリパスワードを発行し、ハンドルと一緒に入れます」）
  2. **「詳しい手順は [help/credentials.md](help/credentials.md) にあります。Torifune では、`/social` のヘルプボタン、または `/plugins/<id>/help/credentials` から読めます（有効にする前は、導入の再ビルドの後から `plugin.manage` を持つ管理者だけが読めます）」**（D11：`plugins/` に置いただけではビルドに入っておらず読めない）

  4. 「Torifune に入れる N 項目」の表は README に残す（項目名と 1 行の説明。既存の検査が語を見ている）
* 手順の番号付きの細かい操作（画面の名前・押すもの）は README から消し、手順書だけに置く
* 手順書から README の節へはリンクできない（§7.3.4。宣言していない `.md` は `none`）。手順書は README に頼らず完結させる
