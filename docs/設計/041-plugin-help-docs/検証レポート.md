## 2. 見つかった欠陥と処置

### 1. 手順書が初心者にトークンをブラウザのアドレス欄へ入れさせていた（1 回目 security 中-1）

Instagram の手順書は、数字のユーザー ID を確かめる確実な方法として「`/me?…&access_token=…` をアドレス欄に入れる」を案内していた。
履歴を消しても、ブラウザの同期・拡張機能・「最近閉じたタブ」・クリップボード履歴から漏れうる。漏れたトークンは 60 日有効で、延長もできる。

**処置（ユーザー裁定 4）**：ユーザー ID の欄に `auto` を入れると、Plugin が配信の入口で `/me` に問い合わせて数字の ID を得る（トークンは Authorization ヘッダだけで送り、URL に載せない）。
公開に成功したときだけ `rotatedCredential` で 3 項目を書き戻し、`039` の比較更新にそのまま乗る。手順書からアドレス欄の手順を消した。**Core は変えていない**（`038` の Plugin の変更）。

### 2. Bluesky はログイン用のパスワードでも配信でき、全権限で動いていた（1 回目 spec 軽微-3）

AT Protocol の `createSession` はアカウントのパスワードも受け付ける。手順書と Plugin の失敗の文言は「ログイン用のパスワードでは失敗する」と**誤っていた**（`036` から持ち越した誤り）。

**処置（ユーザー裁定 5）**：アプリパスワードの形（`xxxx-xxxx-xxxx-xxxx`。公式の説明と参照実装の PDS のソースで確認）でない値は、Bluesky へ 1 度も送らずに断る。
手順書・README・失敗の文言を直し、以前の版でログイン用のパスワードのまま配信できていた人にはパスワードの変更を勧めた。
**防げないこと**：ログイン用のパスワードが偶然この形なら送られる。違う形のアプリパスワードを発行する独自の PDS では配信できなくなる（README に記載、設計 §11.2 #12）。

## 3. 検証の方法

* `spec-verifier` は 2 回とも全件のテストを流し、1 回目 56 通り・2 回目 33 通りの変異で判別力を確かめた（2 回目に生き残ったのは本文の相対リンクの配線 1 つで、処置した）
* `boundary-guardian` と `security-reviewer` は**テストを 1 本も実行していない**（DB の競合を避けるため）。判定はコードの読解に基づく
* 手順書の中身は `spec-verifier` が Plugin のコード（欄の名前・期限の形・失敗の文言）と突き合わせ、一部を公式の説明と照らした
* 2 回目の後の処置の後に検証は回し直していない。処置した側が変異で落ちることを確かめた
