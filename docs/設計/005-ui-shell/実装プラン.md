## 2. 設計上の判断

### 2.1 トークンの遵守を lint ではなくテストで守る

ESLint で CSS-in-JS の値を検査するのは難しい。
**コンポーネントのソースを読んで、生の hex 値と px 直書きが無いことをテストする。**

`1px`（境界線）だけは許す。トークン化しても意味が薄い。

さらに「参照しているトークンがすべて定義されている」ことも検査する。
綴りを間違えると、CSS 変数は黙って無効になり、見た目が崩れたまま気づけない。

### 2.2 `FormField` を render prop にする

`id` と `aria-invalid` / `aria-describedby` を入力要素へ差し込む必要がある。
子要素を関数で受け取れば、どの入力部品でも結び付けられる。

見た目だけでエラーを示すと、スクリーンリーダーの利用者に伝わらない。

### 2.3 表示文言をサーバーではなく画面側で持つ

サーバーの `message` をそのまま出す手もあるが、
画面側で持てば「内部事情が混ざった文言が出る」経路が構造的に無くなる。
将来の国際化もここだけで済む。

**サーバーのエラーコードをすべて網羅していることをテストで検査する。**
コードを増やして文言を忘れると落ちる。

### 2.4 `SecretField` に平文を渡さない

props は `configured: boolean` だけ。設定済みの値を受け取らない。
受け取ると、いつか DOM に載り、開発者ツールから読める。

### 2.5 `PermissionGate` に「認可ではない」と書き、それをテストする

コメントは消える。**コメントが存在することをテストで固定する。**
表示制御を認可の代わりに使わせないための歯止め。

## 3. 影響範囲

| 対象 | 影響 |
| --- | --- |
| `/setup` `/login` `/password-reset` | 共通コンポーネントへ載せ替え。**振る舞いは変えない** |
| `globals.css` | トークンを `ui/tokens.css` へ切り出して import する |
| 新規画面 | `/dashboard` `/logout` |

**破壊的変更：なし**

## 4. リスク

| リスク | 対応 |
| --- | --- |
| CSS-in-JS がデザイン変更で使いにくい | トークンに集約しているため、値の差し替えは可能。CSS Modules への移行余地は残る |
| コンポーネントが増えすぎる | 13 種で打ち止めにし、`DatePicker` / `Chart` は必要になるまで作らない |
| Plugin が個別ファイルを import する | `components/index.ts` を唯一の入口とし、S10 で契約として固定する |
