### 2.1 テストの形を変えた 2 件（意図と理由）

* **#60**（`POST /api/v1/collect` が除外の有無にかかわらず 204）
  … ルートハンドラを直接叩く形にしていない。受け口は `collectAccess` の戻り値を
  **見ずに** `noContentResponse()` を返す実装であり（`app/api/v1/collect/route.ts`）、
  この設計で**その行を触っていない**。「除外されたことが応答から読めない」ことは
  `collectAccess` が `{ ok: false }` を返すこと（#55）と、受け口が戻り値を見ないことの
  組み合わせで担保されている。前者はテストで固定してある
* **#70〜#74**（ルートの権限・スキーマ・`GET` の不在）
  … ルートを実行するのではなく `listEndpoints()` の登録内容を検査した。認可は
  Application 層（UseCase）で行う規約なので（CLAUDE.md）、**実際の 403 / 401 は
  UseCase の検査（#61 / #62）で見ている**。ルート側で見るべきは「宣言が設計どおりか」だけ。
  #73（形式不正が 422）は `ValidationError` を投げること（#64）で担保され、
  `ValidationError` → 422 の変換は `defineRoute` の共通処理で既存のテストが押さえている

## 4. 設計に対する変更（1 件）

### C-1 除外IPの読み出しを専用の射影にした（設計 §5.2 を新設）

**何が起きたか。** 実装当初、`application/analytics/ip-exclusion.ts` と
`ip-exclusion-use-cases.ts` が `toSystemSettings`（全項目）を import した。
これで **032 が置いた静的検査**（`timezone-static-checks.test.ts` の
「全項目を import している製品ファイルは `application/analytics/timezone.ts` だけ」）が落ちた。

**どう直したか。** 許可リストへ 2 ファイルを足すのではなく、
Domain に `accessLogExcludedIpsOf(stored)` を export し、そちらを使うようにした。
032 の固定を緩めずに済む。設計 §5.2 に理由ごと記録した。

**なぜ許可リストを広げなかったか。** あの検査は「設定が増えたとき、それを要らない経路まで
自動的に運ばない」ための仕掛けである。今回の 2 ファイルは正当な利用だが、
一度緩めると次の 1 件も同じ理由で通る。射影を足すほうが、判断の跡が残りやすい。

## 5. 設計が「やらない」と書いたことの確認

以下は**実装していない**。要件 §5 / 設計 §11 のとおり。

* 過去のログの遡及削除（`access_logs` に IP は無く、日次ソルトも残らないため不可能）
* 保存済み集計値の再計算（除外は今後の記録にだけ効く）
* サイトごとの除外リスト（裁定 §3.1。全体設定を残したまま後から足せる）
* IP 詐称への防御（`x-forwarded-for` は信頼できる Proxy の背後にいることが前提）

**画面でこの 3 点を断っている**（#80、および `access-log-ip-settings.tsx` の注意文）。

## 6. 残っている検討事項（今回のスコープ外。次に扱うなら）

いずれも**設計に含まれておらず、実装しないことがこの設計の判断**である。
必要になった時点で別の設計として起こす。

1. **除外の効き目を画面で確かめる手段が無い。** 「設定したのに記録されている」と
   思ったとき、いま確かめられるのは「自分の IP がリストに載っているか」までである。
   直近で除外した件数のカウンタなどは持っていない
2. **他プロセスへの反映は TTL 30 秒の pull だけ。** 複数プロセスで動かしている場合、
   保存から最大 30 秒は古いリストで判定される（032 と同じ性質。設計 §6.1）
3. **除外リストの上限は 100 件・1 行 64 文字。** 判定コストの上限として決めた値であり、
   これを超える規模の運用は想定していない
