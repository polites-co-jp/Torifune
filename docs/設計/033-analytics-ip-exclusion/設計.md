# 033 アクセスログの除外IP設定 — 設計

入力は `要件.md`（裁定は決定事項）。**この設計書が後続（テスト・実装・検証）の唯一の入力である。**

## 1. 目的

設定画面から「アクセスログに入れない IP」を登録できるようにし、
一致する送信元からの計測を **`access_logs` へ書く前に落とす**。

## 2. 前提（設計の土台になっている事実）

* **後から消す道は無い。** `access_logs` に IP は保存されず、`visitor_hash` の材料である
  日次ソルトも保存されない（要件 §2.1）。除外は**記録の手前**でしか実現できない
* **`collect` は認証しない公開の受け口**である。除外されたかどうかを応答から読み取れてはならない
* **除外リストは秘密である。** 社内の IP 帯・VPN の出口が書かれる。
  未認証で読める口（`GET /api/v1/settings`）に載せてはならない

## 3. 全体像

```text
POST /api/v1/collect
  └ requestInfoOf(request)            api/cookies.ts  … x-forwarded-for → x-real-ip
      └ collectAccess()               application/analytics/collect.ts
          ├ normalizePath()                                    ← 既存
          ├ isAccessLogExcluded(ip)   application/analytics/ip-exclusion.ts   ★新規
          │   └ TTL キャッシュ（processState）→ system_settings
          │        └ matchesAnyIpExclusion()  domain/analytics/ip-exclusion.ts ★新規
          │   一致したら **ここで打ち切る**（サイトの照会もしない）
          ├ findSiteByPublicKey()                              ← 既存
          └ recordAccess()                                     ← 既存
```

設定側：

```text
設定 → 一般
  └ AccessLogIpSettings              ui/settings/access-log-ip-settings.tsx  ★新規
      └ PUT /api/v1/settings/access-log-ips                                  ★新規
          └ updateAccessLogIpExclusions()
                application/analytics/ip-exclusion-use-cases.ts              ★新規
              └ system_settings 'analytics.access_log_excluded_ips'
```

## 4. 判定は Domain 層に置く（`domain/analytics/ip-exclusion.ts`）

DB も HTTP も知らない。文字列を受けて真偽を返すだけにする。

### 4.1 アドレスの解釈 `parseIpAddress(text): ParsedIp | null`

```ts
export type IpFamily = 'v4' | 'v6';
export interface ParsedIp {
  readonly family: IpFamily;
  /** v4 は 4 バイト、v6 は 16 バイト。 */
  readonly bytes: Uint8Array;
}
```

* **IPv4** … ドット区切りちょうど 4 組。各組は 1〜3 桁の 10 進で 0〜255。
  **先頭ゼロを認めない**（`010` を 8 と読む実装があり、表記ごとに別物になる）
* **IPv6** … `::` による省略は 1 回まで。末尾に IPv4 表記を埋め込む形
  （`::ffff:203.0.113.10`）を認める。ゾーン ID（`%eth0`）は落としてから解釈する
* **IPv4 射影アドレス（`::ffff:a.b.c.d`）は v4 の 4 バイトへ畳む。**
  これをしないと、同じ端末が Proxy の設定次第で `203.0.113.10` にも
  `::ffff:203.0.113.10` にもなり、**片方だけ除外される**
* 解釈できなければ `null`。**例外を投げない**（この関数は計測のホットパスから呼ばれる）

### 4.2 送信元アドレスの正規化 `normalizeClientIp(raw): string | null`

`x-forwarded-for` / `x-real-ip` に入ってくる値は Proxy の実装ごとに揺れる。
判定の前にここで揃える。

| 入力 | 出力 |
| --- | --- |
| `" 203.0.113.10 "` | `203.0.113.10` |
| `203.0.113.10:51234` | `203.0.113.10` |
| `[2001:db8::1]:443` | `2001:db8::1` |
| `[2001:db8::1]` | `2001:db8::1` |
| `fe80::1%eth0` | `fe80::1` |
| `::ffff:203.0.113.10` | `203.0.113.10` |
| 読めない値・空文字・`null` | `null` |

**ポートを落とすのは曖昧さが無いときだけ。** コロンが 1 個で、その前が IPv4 として
読めるときに限る。素の IPv6（コロンが複数）からは落とさない。

**この正規化を `visitorHash` の入力には持ち込まない。** ハッシュの材料は現状のまま
（`requestInfoOf` が返した生値）にする。材料を変えると、その日の訪問者ハッシュが
途中で変わり、同じ人が 2 人と数えられる。除外判定の中だけで正規化する。

### 4.3 ルールの解釈 `parseIpExclusionRule(text): IpExclusionRule | null`

```ts
export interface IpExclusionRule {
  readonly family: IpFamily;
  readonly bytes: Uint8Array;   // ホスト部を 0 でマスク済み
  readonly prefixLength: number;
  /** 正規表記。保存と画面表示はこの形にそろえる。 */
  readonly text: string;
}
```

* 形は「アドレス」または「アドレス/プレフィックス長」
* プレフィックス長は 10 進整数（先頭ゼロ不可）。v4 は 0〜32、v6 は 0〜128
* 省略時はホスト長（v4 = 32、v6 = 128）とみなす
* **ホスト部はマスクして正規化する。** `203.0.113.10/24` は `203.0.113.0/24` として扱い、
  そう保存する。書いた人の意図（帯を指す）と保存された値をそろえ、
  「同じ帯を 2 通りに書いて 2 行になる」ことを防ぐ
* **正規表記**
  * v4 … ドット 10 進。`/32` は落として `203.0.113.10`
  * v6 … 小文字。ゼロの最長連（2 組以上）を `::` へ 1 回だけ畳む。`/128` は落とす
* 解釈できなければ `null`

### 4.4 一致 `matchesIpExclusionRule(rule, ip)` / `matchesAnyIpExclusion(rules, ip)`

* **family が違えば一致しない。** IPv4 射影は §4.1 で v4 に畳んであるので取りこぼさない
* 先頭 `prefixLength` ビットが等しければ一致。バイト単位＋端数ビットはマスクで比べる
* `prefixLength = 0` は全一致（`0.0.0.0/0` / `::/0`）。**禁止しない。**
  「全部止める」は設定として筋が通っており、画面には注意書きだけ出す

### 4.5 リストの解釈 `parseIpExclusionRules(inputs)`

```ts
export interface IpExclusionParseResult {
  readonly rules: readonly IpExclusionRule[];   // 正規化・重複除去済み。入力順
  readonly invalid: readonly string[];          // 解釈できなかった行（入力のまま）
}
```

* 空行と前後の空白は落とす
* **重複は正規表記で判定して落とす。** `203.0.113.0/24` と `203.0.113.10/24` は同じ 1 行になる
* 上限 `IP_EXCLUSION_MAX_RULES = 100`、1 行 `IP_EXCLUSION_RULE_MAX_LENGTH = 64` 文字。
  上限は判定コストの上限でもある（計測 1 件ごとに最大 100 回の比較で済む）

## 5. 保存（`domain/system-settings.ts`）

```ts
export const SYSTEM_SETTING_KEYS = {
  // ...
  accessLogExcludedIps: 'analytics.access_log_excluded_ips',
} as const;
```

* `SystemSettings` に `readonly accessLogExcludedIps: readonly string[]` を足す。既定は `[]`
* **`PublicSystemSettings` には足さない。** ここに載せないことが「未認証へ公開しない」という
  判断そのものである（032 設計 §6.5.1）。`GET /api/v1/settings` は `permission: null` で
  Cookie 無しでも叩けるため、載せると社内の IP 帯が 1 リクエストで読める
* **マイグレーションは要らない。** `system_settings` は key-value で、
  行が無ければ既定（空）になる

### 5.1 壊れた値の扱い — **行ごとに落とす**

`toSystemSettings` は他の項目では「壊れていたら既定へ落とす」。
このリストは **配列でなければ空、配列なら解釈できない要素だけを落とす**。

**リスト全体を捨てない。** 1 行の壊れで除外が丸ごと無効になると、
除外したかった IP が黙って記録される。書いた本人は画面で気づけるが、
記録された分は §2 のとおり後から消せない。

### 5.2 読み出しは**除外IPだけの射影**を通す（`accessLogExcludedIpsOf`）

Application から読むときに `toSystemSettings`（全項目）を呼ばない。
`accessLogExcludedIpsOf(stored)` を Domain から export し、そちらを使う。

* 032 が `timezone-static-checks.test.ts` で**全項目の import 元を 1 ファイルに固定**している。
  全項目を取れる場所を増やすと、次に設定が増えたとき、それが要らない経路まで一緒に運ばれる
  （032 設計 §6.5.1 が `PublicSystemSettings` で塞いだのと同じ問題）
* この射影があることで、**その固定を緩めずに済む**。許可リストへ足すという選択肢もあるが、
  緩めずに済むならそちらがよい
* 向きは `toPublicSystemSettings` と同じ（載せる範囲を狭めるだけで、読み方は変えない）

## 6. 参照（`application/analytics/ip-exclusion.ts`）

### 6.1 TTL キャッシュ。形は `timezone.ts` にそろえる

* 置き場は `processState('analytics.ip-exclusion', ...)`。
  **モジュール変数にしない**（Next.js が Route Handler と Server Component を
  別バンドルへ分けると「画面で変えたのに `collect` に効かない」が起きる）
* TTL は 30 秒（`timezone.ts` と同じ）。他プロセスへ push する仕組みは持たない
* 保存直後は `primeAccessLogIpExclusions(rules)` でそのプロセスへ即時反映する

### 6.2 `collect` からは **待って**読む（`timezone` と違う点）

`timezone.ts` の `analyticsTimeZone()` は同期でキャッシュを読むだけ・古くても待たない。
**除外はこれと同じにしない。**

* タイムゾーンは「ずれても、後から洗い替えれば直る」。
  **除外は、取りこぼした 1 件を後から消せない**（前提 §2）
* 起動直後（キャッシュ未読み込み）に待たない設計にすると、
  **プロセスが立ち上がるたびに、最初の数件が必ず記録される**

したがって `resolveAccessLogIpExclusions()` は **非同期のみ**とし、
キャッシュが古ければ読み直しを待つ。`collectAccess` は既に `async` なので同期版は要らない。

読み直しは 30 秒に 1 本で、全リクエストが待つわけではない。

### 6.3 読み直しに失敗したら **記録する側へ倒す**（fail-open）

DB が一時的に読めないとき、直前のキャッシュ（未読み込みなら空リスト）で続行し、
`redactSecrets` を通した理由を `log.warn` する。

**除外できずに記録するほうを選ぶ。** 逆（読めないなら全部落とす）にすると、
DB の不調がそのまま計測の全損になり、後から復元できない。
記録しすぎは数値の誤差だが、記録しないことは欠損である。

（`redactSecrets` を通す理由は 029 §6.1.7 と同じ。`withConnection` は
Database Provider を差し替えた Plugin の例外を運びうる。）

### 6.4 `isAccessLogExcluded(rawIp): Promise<boolean>`

1. `rawIp` が `null` / 空 → **`false`**（除外しない）。
   **IP が分からないものを落とさない。** 落とすと、Proxy の設定ミスで計測が全損する
2. `normalizeClientIp` が `null` → `false`（同上）
3. 現在のリストと突き合わせ、一致すれば `true`

## 7. 収集側の変更（`application/analytics/collect.ts`）

`collectAccess` の中で、`normalizePath` の直後・`withConnection` の前に判定する。

```ts
if (await isAccessLogExcluded(input.ipAddress)) {
  return { ok: false };
}
```

* **`{ ok: false }` を返す。** 受け口は成功・失敗を問わず 204 を返すので、
  除外されたことは送信側から見えない（既存の「理由を伝えない」方針のまま）
* サイトの照会もしない。除外された送信元に、公開キーの当たり判定を与えない
* **`recordAccess` に条件分岐を足さない。** 呼ばれた時点で記録することを変えない

## 8. API（`app/api/v1/settings/access-log-ips/route.ts`）

`PUT /api/v1/settings/access-log-ips` の 1 本だけ。

| 項目 | 値 |
| --- | --- |
| `operationId` | `updateAccessLogIpExclusions` |
| `permission` | `system.manage` |
| body | `rules`（文字列の配列。各 64 文字以内・最大 100 件）と `csrfToken`（任意） |
| 応答 | `{ data: { rules: string[] } }`（**正規化後**のリスト） |

* **`PUT /api/v1/settings`（表示名と同じ口）へ足さない。**
  あの口の応答は `PublicSystemSettings` であり、除外リストを返せない。
  入力だけ相乗りさせると「送ったものが応答に無い」形になる
* **`GET` を作らない。** 画面は Server Component から UseCase を直接呼ぶ（決定事項 D-06）。
  秘密を返す口は、要るまで生やさない
* Zod の検査は**長さと件数だけ**。形式（IP として読めるか）は UseCase が Domain に委ねる。
  判定を 2 か所に置かない

## 9. UseCase（`application/analytics/ip-exclusion-use-cases.ts`）

### 9.1 `getAccessLogIpExclusions`

* `permission: 'system.manage'`。**参照にも権限を要求する**（§2 のとおり秘密である）
* 戻り値は `rules`（正規化済みの文字列配列）

### 9.2 `updateAccessLogIpExclusions`

* `permission: 'system.manage'`
* 監査は `action: 'updated'` / `resourceType: 'system_settings'` / `detail` は設定キーと件数
  * **IP そのものを監査ログに書かない。** 除外リストは `system.manage` でしか読めない設定であり、
    監査ログはそれとは別の経路で読まれ・持ち出されうる。件数だけ残す
* 解釈できない行があれば `ValidationError`。**保存しない**（一部だけ通さない）。
  メッセージには**先頭 3 件まで**を挙げる（全部並べると読めない）
* 件数が上限を超えていれば `ValidationError`
* 保存後に `primeAccessLogIpExclusions` を呼び、正規化後のリストを返す

## 10. 画面（`ui/settings/access-log-ip-settings.tsx`）

設定 → 一般の、基準タイムゾーンの下に置く。**タブは足さない**（06_画面設計.md §16）。

```text
┌ アクセスログの除外IP ─────────────────────────┐
│ 指定した送信元からのアクセスを記録しません。       │
│                                                │
│ 現在のあなたのアクセス元IP：203.0.113.10 [追加]  │
│                                                │
│ 除外するIP（1行に1件）                          │
│ ┌────────────────────────────────────────────┐ │
│ │203.0.113.10                                │ │
│ │198.51.100.0/24                             │ │
│ │2001:db8::/32                               │ │
│ └────────────────────────────────────────────┘ │
│ [保存する]                                      │
│                                                │
│ ※ 設定は今後の記録にだけ効きます。すでに記録済み  │
│   のアクセスは消えません（アクセスログにIPを     │
│   保存していないため、後から探して消せません）。  │
└────────────────────────────────────────────────┘
```

* **`system.manage` が無い人にはこの区画ごと出さない。**
  表示名・タイムゾーンは「表示は誰でも、変更は `system.manage`」だが、
  **除外リストは表示自体が漏洩**である。`app/settings/page.tsx` 側で描画を分ける
  （これは表示制御であり、認可は UseCase 側の `system.manage` が行う）
* 「現在のあなたのアクセス元 IP」は **Server Component が `headers()` から取る**。
  取れないときは「判別できません（プロキシの設定を確認してください）」と出す
* 「追加」は入力欄の末尾へ 1 行足すだけ。保存は「保存する」を押したとき
  （既に含まれていれば押せない）
* 保存に失敗したら `Alert`、成功したら `Toast`。画面の再読み込みはしない
  （ヘッダの表示に関わらないため。`GeneralSettings` の `location.reload()` は真似しない）

### 10.1 送信元 IP の取り出しを 1 か所にする（`api/cookies.ts`）

`requestInfoOf` の中にある取り出しを `clientIpOf(headers)` として切り出し、
`requestInfoOf` と設定画面の両方がこれを使う。

```ts
export function clientIpOf(headers: Pick<Headers, 'get'>): string | null;
```

`Request` の `headers` も Next.js の `headers()` の戻り値も `get` を持つので、両方から渡せる。
**取り出しが 2 か所にあると、画面に出る IP と実際に判定される IP がずれる。**

## 11. 満たさないこと（実装しない。要件 §5 の再掲）

* 過去のログの遡及削除（原理的に不可能）
* 保存済み集計値の再計算（除外は今後の記録にだけ効く）
* サイトごとの除外リスト（裁定 §3.1。全体設定を残したまま後から足せる）
* IP 詐称への防御（`x-forwarded-for` は信頼できる Proxy の背後にいることが前提）

## 12. 検証の観点（テストで必ず押さえる）

1. `parseIpAddress` … v4 / v6 / IPv4 射影 / 先頭ゼロ / 不正入力
2. `normalizeClientIp` … §4.2 の表をそのまま
3. `parseIpExclusionRule` … マスク正規化 / プレフィックス長の境界（0・32・33・128・129）/ 不正
4. `matchesAnyIpExclusion` … 一致・不一致・family 違い・`/0`・端数ビット
5. `parseIpExclusionRules` … 重複除去 / 空行 / 上限 / 不正行の切り分け
6. `toSystemSettings` … 壊れた要素だけ落ちること、`PublicSystemSettings` に**出ない**こと
7. `collectAccess` … 除外 IP は `access_logs` に **1 行も入らない**こと、応答が変わらないこと、
   IP が `null` のときは記録されること
8. `updateAccessLogIpExclusions` … 権限（200 / 403 / 401）、正規化、不正行で保存されないこと
9. キャッシュ … 保存直後に `collect` へ効くこと（`prime`）、DB 失敗時に fail-open すること
