## 3. タスク分解

原則：**1 タスク = 1 コミット**。各タスクは「テストを書いて失敗を確認 → 実装 → 通す」の順。

**test-writer → implementer への受け渡しの単位は G。** test-writer は G の中の全タスクのテスト（と既存テストの追従）を先に書き、新しいテストが**期待どおりの理由で**赤いことを確かめて `test:` でコミットする（`pnpm typecheck` / `pnpm lint` / `pnpm format:check` は通る状態で。未実装のモジュールは動的 import、未実装の props は型をテストの中で写す）。implementer は G の中のタスクを順に通し、タスクごとに `feat:` でコミットする。
**implementer はテストを書き換えない。** 食い違いは設計書のどこと食い違うかを報告して止まる。

**プッシュの約束**：プッシュの前に `pnpm test` を**全件**流す（postgres-test、`DATABASE_URL=postgresql://torifune:torifune@localhost:21701/torifune_test`、`TORIFUNE_ENCRYPTION_KEY=dGVzdC1vbmx5LWtleS1kby1ub3QtdXNlLWluLXByb2Q=`）。赤くてよいのは、いま取り組んでいる G のまだ実装していないタスクのテスト（と、その G で追従した既存テストのうち実装を待つもの）だけ。`main` へプッシュしない、マージしない、`--force` は使わない。

**着手順の骨子**：共通部品（`Table`・本文の部品）→ 2 つの表 → 文書 → 最終確認と 3 つの検証。G2 は G1、G3 は G2、G4 は G3 に依存する。

## 7. リスクと注意点

1. **`<tbody>` を行の数だけ並べる（T2）。** HTML として正しい（`<table>` は複数の `<tbody>` を持てる）。`key` は `<tbody>` に付ける。`detail` なしの分岐は今のコードをそのまま残し、出力を 1 文字も変えない（#1）
2. **1 段目の下線を消す範囲（T2）。** `detail` ありのときの 1 段目だけ。右寄せの列（`NUMERIC_CELL`）の扱いは変えない
3. **本文の要素とその外（T5・T6）。** `note`・「投稿を見る ↗」を本文の `<span>` の中に入れると `pre-wrap` が効き、本文と補足の境目も DOM で分からなくなる。本文の要素の後の別のブロック（`display: block` の `<span>`）にする
4. **E2E の行グループ（T4）。** `getByRole('table').locator('tbody')` は `<thead>` を拾わない。件数（`toHaveCount`）は投稿の数で、期待値は変えない。`getByRole('rowgroup')` は `<thead>` も拾うので使わない
5. **`excerptOf` を残す（T5・T6）。** チェックボックスのラベル・削除の確認・一括の結果は 60 字の抜粋のまま。既存の E2E の `rowCheckbox`（`この投稿を選択：<本文>`）が保たれる
6. **長い本文で行が高くなる（設計 §14 R1）。** ユーザー裁定 4 の帰結として受け入れ、対策は足さない。E2E は高さを判定しない（初版の「2 行に収まる」「行グループ 200px 以下」は裁定 4 で外した）
