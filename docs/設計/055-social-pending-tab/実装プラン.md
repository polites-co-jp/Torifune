### 確定事項（設計書から。プランで蒸し返さない）

* `/social` は **4 つのタブ**：送信待ち（既定・`tab` を書かない）／投稿（`?tab=posts`）／アカウント（`?tab=accounts`）／配信履歴（`?tab=history`）。知らない値・配列は送信待ち。どのタブも `social.read`。タブを移ると他のタブの条件は落とす。読み込むのは選んだタブの分だけ（ユーザー裁定 1。設計 §5.1・§9.1）
* `/social/history` は `redirect()`（307）だけ。`status` → `historyStatus`、`page`（`normalizePage`）の 2 以上 → `historyPage`。セッションを見ずに転送する（設計 §9.7）
* 送信待ちの対象は承認待ち・予約済み（自動・手動）・手動投稿待ちで、**1 つの表**。区画（`approval-pending.tsx`・`manual-pending.tsx`）は消す（ユーザー裁定 3。設計 §5.2・§9.3）
* 並びは `pendingSort`（`action`＝手が要るもの順〔既定〕／`time`＝予定の時刻順）。件数（`counts`）はアカウント・登録元を掛けた後、状態を掛ける前（ユーザー裁定 7。設計 §5.3・§8.1）
* 054 の一括操作（一括送信（承認）・一括取り消し＝削除）は**送信待ちと投稿の両方**に同じ部品で出す。一括の API は変えない（ユーザー裁定 2・5。設計 §5.4・§9.4）
* 「投稿画面を開く」は**予約済みの手動投稿なら予約時刻の前でも**出す。承認待ちには出さず、`resolveManualHandoff` も `status !== 'scheduled'` で `manual()` を呼ばずに `not_scheduled`（ユーザー裁定 4。設計 §5.5・§8.3）
* 手動投稿の結果は新しい **`POST /social/posts/{id}/manual-outcome`**（`sessionOnly`・`social.write`・`expectedUpdatedAt` 必須）と UseCase `recordManualOutcome`。`posted` → `published`、`not_posted` → `failed`（`failure_reason = MANUAL_NOT_POSTED_REASON`）。予約日時と承認の記録は書き換えない。イベントは既存の `social.post.published` / `social.post.failed`、監査は `updated`（`detail.manualOutcome`）。`PATCH` の振る舞いは変えない（ユーザー裁定 6。設計 §5.6・§8.2）
* 「選んだ手動投稿を順に投稿」のダイアログ。開くのは人のクリックだけ。「投稿しなかった」は確認を挟んで `failed`。途中でやめられる（ユーザー裁定 6。設計 §9.5）
* 送信待ちの行にも「削除」（投稿タブと同じ確認と `DELETE`）。操作のセルは `flex-wrap: wrap`、「削除」は常に最後（ユーザー裁定 8。設計 §9.3.4）
* 投稿フォームの戻り先は `returnTo`（`?from=pending` なら `/social`、それ以外は `/social?tab=posts`。許す値は 2 つだけ）（設計 §5.7）
* 新しい Permission・監査の `action`・イベント・状態は作らない。**`PLUGIN_API_VERSION` は 1 のまま。マイグレーションなし**（設計 §7・§10・§11）
* 文書の書き戻しは設計 §15 の範囲。**`docs/仕様書/` は変えない**
* 検証は **`spec-verifier` / `boundary-guardian` / `security-reviewer` の 3 つ**（公開 HTTP API・認可・監査を変えるため）
* **SaaS 固有機能（テナント・課金・コンテナ管理）に触るタスクは本プランに無い**

原則：**1 タスク = 1 コミット**。各タスクは「テストを書いて失敗を確認 → 実装 → 通す」の順。

**test-writer → implementer への受け渡しの単位は G（まとまり）。** test-writer は G の中の全タスクのテスト（と既存テストの追従）を先に書いて、新しいテストが**期待どおりの理由で**赤いことを確かめ、`test:` でコミットする（`pnpm typecheck` / `pnpm lint` / `pnpm format:check` は通る状態で。未実装のモジュール・ルート・export は動的 import）。implementer は G の中のタスクを順に通し、タスクごとに `feat:`（切り出しは `refactor:`、文書は `docs:`）でコミットする。
**implementer はテストを書き換えない。** テストが設計と食い違うと判断したら、設計書のどこと食い違うかを報告して止まる。

**プッシュの約束（test-writer・implementer とも）**：プッシュの前に必ず `pnpm test` を**全件**流す（postgres-test、`DATABASE_URL=postgresql://torifune:torifune@localhost:21701/torifune_test`、CI と同じテスト用の `TORIFUNE_ENCRYPTION_KEY=dGVzdC1vbmx5LWtleS1kby1ub3QtdXNlLWluLXByb2Q=`）。**既存のテストと、すでに実装したタスクのテストが 1 件でも赤ならプッシュしない。** 赤くてよいのは、いま取り組んでいる G のまだ実装していないタスクのテスト（と、その G で追従した既存テストのうち実装を待つもの）だけ。`main` / `master` へはプッシュしない、マージしない、`--force` は使わない。

**着手順の骨子**：Domain の純関数 → 送信待ちの一覧 → 手動投稿の結果の API → `resolveManualHandoff` → URL と計画の純関数・文言 → 部品の切り出し → 送信待ちの表と順に投稿 → タブの中身と戻り先 → 画面の組み立てと E2E → 文書 → 最終確認と 3 つの検証。
**G は前の G に依存する**（G2 は G1、G3 は G2、G4 は G3、G5 は G4、G6 は G5、G7 は G6、G8 は G5、G9 は G7 と G8）。G10 は G9 の後（振る舞いが入ってから書く）。
