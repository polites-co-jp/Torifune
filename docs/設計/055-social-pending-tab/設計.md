## 1. 目的（背景）

1. **SNS 画面の役割を分け、「これから出るもの」を最初に見せる。** 今の `/social` は 1 枚にアカウント・承認待ち・手動投稿待ち・投稿一覧
   （全状態）を縦に積んでおり（`apps/web/src/app/social/page.tsx:309-382`）、送信を捌きたい人は下書きや配信済みに混ざった中から探すことになる
2. **手動投稿（X など）に迷わず辿り着けるようにする。** 手動投稿待ちの区画は**予約時刻を過ぎた手動投稿だけ**を出し
   （`isManualPending`。`domain/social/social.ts:325-336`）、0 件なら何も描かない（`ui/social/manual-pending.tsx:258-261`）。
   予約時刻の前は操作の場所そのものが画面に無く、「どこから投稿画面を開くのか分からない」状態だった
3. **手動投稿をまとめて捌けるようにする**（ユーザー裁定 6）。今は 1 件ずつ「投稿画面を開く」→ SNS で送る →「投稿した」→ 記録のダイアログ、を繰り返す。
   選んだ手動投稿を順に開き、1 件ごとに「投稿した／投稿しなかった」を押して進められるようにする
4. **054 の一括操作と、1 件の操作で守ってきた約束を崩さない。** 承認するのは画面で見た内容（`048` §6.4.3）、承認待ちは承認を経ずに SNS へ出さない
   （`048` §7.2）、配信中の行は書き換えない（`049`）、ポップアップのブロックを避ける（`035` §7.2）

## 4. スコープ

### 4.1 やること

1. `/social` を **4 つのタブ**（送信待ち〔既定〕・投稿・アカウント・配信履歴）に分ける。h1「SNS」と Plugin の操作はタブの上に置く（§9.1）
2. **送信待ちの表**：承認待ち・手動投稿待ち・予約済み（自動・手動）を 1 つの表に。状態・アカウント・登録元の絞り込みと表示件数、選択と 054 の一括の帯、行ごとの操作（§9.3）
3. 承認待ちの区画・手動投稿待ちの区画を**消し**、承認のダイアログ（全文の確認つき）・投稿画面を開く・投稿した・取りやめ・差し戻しを表の行の操作へ移す（§9.3.4）
4. 手動投稿の「投稿画面を開く」を**予約時刻の前の予約にも**出す。承認待ちには出さない（ユーザー裁定 4。§5.5）
5. **選んだ手動投稿を順に投稿**するダイアログ（「投稿画面を開く」→「投稿した」／「投稿しなかった」→ 次へ。途中でやめられる）（ユーザー裁定 6。§9.5）
6. 手動投稿の結果を記録する操作 `POST /social/posts/{id}/manual-outcome` と UseCase `recordManualOutcome`（§8.2）
7. 送信待ちを読む UseCase `listSocialPendingPosts`（§8.1）
8. `/social/history` を配信履歴タブへ転送し、履歴をタブの中に移す（§9.7）
9. 既存のリンク（ダッシュボード・投稿一覧の補足・投稿フォームの戻り先）を新しいタブへ向け直す（§9.8）
10. 054 の一括の部品（選択・一括の帯・ダイアログ・結果）と絞り込みの帯を、投稿タブと送信待ちタブで共有できる形に切り出す（作りを二重にしない。ユーザー裁定 2）（§9.4）
11. OpenAPI・手順書・Plugin の README・関連設計の書き戻し（§15）

### 4.2 やらないこと

* **新しい状態（アーカイブなど）**（ユーザー裁定 5）。一括の「アーカイブ」は 054 の一括取り消し（削除）で代える
* **1 件の `PATCH` の振る舞いの変更**（`published → published` を許すことも含め、外部アプリから見た `PATCH` は変えない。§12・§17.2 の 2）
* **手動投稿の結果の操作を API トークンに開くこと**（外部アプリは今までどおり `PATCH`。§5.6）
* **「投稿しなかった」を行の 1 件の操作として出すこと**（順に投稿のダイアログで 1 件だけ選べば同じことができる。§17.2 の 3）
* **一括の「取りやめ（下書きへ戻す）」**（054 §4.2 のまま）
* 予約時刻の前の手動投稿を「今すぐ投稿したことにする」ために予約日時を書き換えること（§5.6）
* 古いアンカー（`/social#posts` など）を読んで別のタブへ移す仕掛け（§9.8）
* タブの見出しに件数を出すこと（毎回すべてのタブの件数を数える問い合わせが要る）
* Plugin API・イベントの名前と Payload・Webhook の変更（§11）
* 配信履歴の中身（列・絞り込みの選択肢・並び）の変更（置き場所だけ移す）

## 5. 決めたこと

### 5.1 タブと URL（ユーザー裁定 1）

| タブ | `key` | URL | 中身 |
| --- | --- | --- | --- |
| **送信待ち**（既定） | `pending` | `/social`（`tab` を書かない） | 送信待ちの表（§9.3） |
| 投稿 | `posts` | `/social?tab=posts` | 054 の投稿一覧（全状態）。承認待ち・手動投稿待ちの区画は無い（ユーザー裁定 3） |
| アカウント | `accounts` | `/social?tab=accounts` | 今の `SocialAccounts`（h1 を除く） |
| 配信履歴 | `history` | `/social?tab=history` | 今の `SocialHistory`（h1 と「SNSへ戻る」を除く） |

* **クエリにする理由**：設定・Plugin 管理・アナリティクスがすべて `?tab=` で、既定のタブを書かない画面もある（§3.2）。パス（`/social/pending` など）にすると
  ナビの `/social` の「選択中」の判定・既存の `/social/posts/{id}/edit` のパスと混ざり、`/social/history` の移し替えも二重になる
* `tab` の値が 4 つのどれでもない（`?tab=xxx`・配列）ときは**送信待ち**を出す（設定の `toTab` と同じ。200 で描く）
* **どのタブも `social.read` で見える**（今の `/social` と同じ）。`social.read` が無ければ今までどおり 403 の表示（`AsyncState forbidden`）
* **タブを移ると他のタブの条件は落とす**（`hrefFor` は `tab` だけを書く。Plugin 管理と同じ）。タブごとのクエリは別の名前にする（§9.2・§9.6）ので、
  手で混ぜた URL でも互いに干渉しない
* **読み込むのは選んだタブの分だけ**（アカウントの一覧は名前の表示にどのタブでも使うので常に読む）。今は描画のたびに承認待ち・手動投稿待ち・投稿・サイトを全部読んでいる

### 5.2 送信待ちの対象（ユーザー裁定 3）

区分 `PendingKind`（Domain の純関数 `pendingKindOf(post, now)`）：

| 区分 | 条件 | 表示名 |
| --- | --- | --- |
| `manual_pending` | `status = 'scheduled'` かつ `deliveryMode = 'manual'` かつ `scheduledAt` があり `<= now`（＝今の `isManualPending`） | 手動投稿待ち |
| `awaiting_approval` | `status = 'awaiting_approval'`（自動・手動とも） | 承認待ち |
| `scheduled` | それ以外の `status = 'scheduled'`（自動のすべて＝未来・期限が来た・配信中・再試行待ち・支度待ち、手動の予約時刻前、予約日時の無い予約） | 予約済み |
| （対象外） | `draft`・`published`・`failed` | — |

* **配信中・再試行待ち・支度待ちの自動の予約も出す**：まだ出ていない投稿で、運用者が気にかけるもの（支度の Badge・残り回数を見て直す）。行の操作は「編集」と「削除」（§9.3.4）
* 承認済みの予約（`approvedAt` あり）は `scheduled` / `manual_pending` に入る（補足「承認済み」）

### 5.3 送信待ちの並び・ページ送り・件数

* **並びは利用者が選ぶ**（ユーザー裁定 7。並び順の `Select`。§9.2）。型 `PendingSort`＝`'action' | 'time'`、定数 `PENDING_SORTS`（`['action', 'time']`）・既定 `DEFAULT_PENDING_SORT`＝`'action'`（Domain `pending.ts`）
  * **(A) 手が要るもの順 `action`（既定）**
    1. `manual_pending`（予約時刻の古い順。人が送らない限り出ない・遅れている）
    2. `awaiting_approval`（依頼の古い順＝`created_at`。今の承認待ちの区画と同じ。`048` §6.5）
    3. `scheduled`（予約日時の近い順。予約日時の無いものは最後）
    4. 同じ値なら `id`
  * **(B) 予定の時刻順 `time`**：区分を混ぜ、**予定の時刻**（予約済み・手動投稿待ちは予約日時、承認待ちは希望日時）の早い順。
    予定の時刻の無いもの（予約日時の無い予約・希望日時の無い承認待ち）は最後。同じ値なら `created_at`、次に `id`
  * **経緯**：初版は (A) に固定し、(B) との選択を §17.1 の ① で裁定に回した。(A) は 1 ページ目で捌ける、(B) は「いつ何が出るか」が読みやすい、とどちらにも
    使い道があるので、ユーザー裁定 7 で両方を選べる形にし、既定を (A) にした
  * 件数（`counts`）・区分の判定・ページの大きさは並びに依らない
* **ページ送り**：054 と同じ表示件数（20・50・100。既定 20）とページ（`normalizePage`）。区画のような「先頭 50 件で打ち切り」はしない
* **件数**：状態の絞り込みの選択肢に区分ごとの件数を添える（「承認待ち（3）」）。件数は**アカウント・登録元の絞り込みを掛けた後、状態の絞り込みを掛ける前**の数
  （状態を選び替える前にどこに何件あるか分かるように）。「すべて」には合計を添える
* 一括選択は 054 と同じく**表示中のページの行だけ**（054 §5.3）

### 5.4 054 の一括操作の使い回し（ユーザー裁定 2・5）

* 送信待ちタブにも投稿タブにも、054 の**選択の列・一括選択・一括の帯（一括送信（承認）・一括取り消し）・確認のダイアログ・結果の表示**を出す。
  **同じ部品**（§9.4 で切り出す `BulkPostActions`）を使い、対象の判定は 054 の純関数（`sendPlanOf`・`deletePlanOf`・`summarizeBulkResults`）のまま
* 一括の「アーカイブ」は作らない。**一括取り消し（削除）がそれにあたる**（ユーザー裁定 5）。送信待ちには下書き・配信済み・失敗が無いので、
  対象外になるのは配信中だけ
* 一括の API（`/social/posts/bulk/*`）・権限・結果の理由は 054 のまま。**API の変更は無い**
* 送信待ちタブだけ、一括の帯に「**選んだ手動投稿を順に投稿…**」を足す（§9.5）

### 5.5 手動投稿の「投稿画面を開く」の範囲（ユーザー裁定 4）

| 行 | 投稿画面を開く | 投稿した・取りやめ |
| --- | --- | --- |
| 手動投稿待ち（予約時刻を過ぎた予約） | 出す | 出す（`social.write`） |
| **予約済みの手動投稿（予約時刻の前・承認済みを含む・予約日時なし）** | **出す（新）** | **出す（新）** |
| 承認待ちの手動投稿 | **出さない**。補足「承認すると投稿画面を開けます」 | 出さない（承認か差し戻し） |
| 自動配信の行 | 出さない | 出さない |

* **サーバでも閉じる**：`resolveManualHandoff` は `status !== 'scheduled'` の投稿に **`manual()` を呼ばず** `{ ok: false, reason: 'not_scheduled' }` を返す
  （新しい理由）。画面は承認待ちの行に URL を問い合わせない（HTML に URL が載らない）。承認を経ずに SNS へ出す手がかりを画面に残さない（`048` §7.2）
* 判定の純関数 **`canOpenManualHandoff(post)`**＝`deliveryMode = 'manual'` かつ `status = 'scheduled'`（Domain）。画面と UseCase の両方が使う
* **描画の予算**：URL を問い合わせるのは**表示中のページの、手動の予約の行だけ**（最大で表示件数＝100 行）。打ち切り時刻は今までどおり 1 回だけ作って全行へ渡す
  （`MANUAL_HANDOFF_BUDGET_MS`＝10 秒は変えない）。手動投稿待ちの区画の 50 行より多くなりうるが、`manual()` は URL の組み立てで、行ごとの上限
  （`MANUAL_TIMEOUT_MS`）と絶対の締切があるので**画面は必ず返る**。締切に間に合わなかった行は今までどおり「Plugin でエラーが起きました」で開けない
  （「投稿した」は押せる）。送信待ち以外のタブでは問い合わせない

### 5.6 手動投稿の結果の記録（ユーザー裁定 6）

**新しい操作 `POST /social/posts/{id}/manual-outcome`**（UseCase `recordManualOutcome`）にする。`PATCH` は使わない。

| 論点 | 決めたこと | 理由 |
| --- | --- | --- |
| 操作の形 | `{ outcome: 'posted' \| 'not_posted', expectedUpdatedAt, externalUrl? }`。**セッションだけ**（`sessionOnly`）。Permission **`social.write`** | 「投稿した」は今 `social.write` の `PATCH` で行っている。新しい Permission は要らない（できることは増えない）。外部アプリには `PATCH` がある |
| `PATCH` を使わない理由 | `PATCH` は画面が見た時点の `updatedAt` を条件にできない（§3.3）。順に投稿では、描画時に作った URL（描画時の本文）で SNS へ出すので、**見た後に本文が直されていたら記録しない**（409）必要がある。また `PATCH` は `published → published` を許し、二人が同じ行を「投稿した」にすると `published_at` が書き換わりイベントが 2 回出る | 承認（`048` §6.4.3）・今すぐ送る（`054` §5.4）と同じ「見た内容に対して行う」約束。`PATCH` を変えると外部アプリの振る舞いが変わる（§4.2） |
| 対象 | `status = 'scheduled'` かつ `deliveryMode = 'manual'`（予約時刻の前後を問わない。ユーザー裁定 4）。純関数 `manualOutcomeEligibility(post)` | 承認待ちは対象外（承認を経ずに出さない）。自動配信の行は配信ジョブが結果を書く |
| `posted` で書くもの | `status = 'published'`、`published_at = いま`、`external_url`（送られたときだけ。`isValidExternalUrl`）、`next_attempt_at = NULL`、`updated_at = いま` | 今の「投稿した」（`PATCH { status: 'published', externalUrl? }`）と同じ結果 |
| `not_posted` で書くもの | `status = 'failed'`、`failed_at = いま`、`failure_reason = MANUAL_NOT_POSTED_REASON`（固定の文言「手動投稿で『投稿しなかった』が選ばれました。」）、`next_attempt_at = NULL`、`updated_at = いま`。`externalUrl` を送ると 422 | ユーザー裁定 6（失敗で確定。配信履歴に出る）。理由を固定にすると、履歴の「失敗の理由」で配信の失敗と見分けられる。`failed` は終端なので、やり直しは新しい投稿を作る |
| 予約日時 | **書き換えない**（予約時刻の前に投稿しても `scheduled_at` はそのまま） | 事実の時刻は `published_at` / `failed_at`。配信履歴は結果の時刻で並ぶ（`listSocialPostHistory`）。予約日時を書き換えると「いつの予定だったか」が消える |
| 承認の記録 | `approved_at` は触らない | 承認済みの予約の結果として残す（DB の CHECK も `published` / `failed` の承認の記録を許す） |
| 配信ジョブとの競合 | **起きない**：ジョブは `delivery_mode = 'auto'` の行しか取り出さない。ただし更新は**条件付き**（`status = 'scheduled' AND delivery_mode = 'manual' AND updated_at = expectedUpdatedAt`）にし、読んでから書くまでに配信方法を自動へ変えられた・取りやめられた・今すぐ送られた・他の人が記録した行には当てない | 人同士・編集・054 の一括操作との競合を 409 で止める |
| 判定の順 | 区画の外・無い → 404 → `updatedAt` が違う → **409** → 対象外（手動の予約でない）→ 422 `status` → 条件付き更新が当たらない → 読み直して無ければ 404、あれば 409 | 見た後に他の人が記録した行（`published` になった行）は「状態が違う」より「見た後に変わった」のほうが状況の説明になる |
| イベント | `posted` → **`social.post.published`**、`not_posted` → **`social.post.failed`**。Payload は今の `PATCH` と同じ `{ postId, accountId, status }` | 既存のイベントに揃える（通知 Plugin・Webhook が今までどおり拾う）。理由は載せない（`PATCH` の `failed` と同じ） |
| 監査 | `action: 'updated'`・`resourceType: 'social_post'`、`detail: { changed: ['status', …], status, manualOutcome: 'posted' \| 'not_posted' }` | `PATCH` の監査と同じ `action`。新しい `action` を作らない（054 と同じ判断）。`manualOutcome` で人の判断と分かる。`changed` は `PATCH` の `changed`（送った項目）に揃え、`['status']` に、`externalUrl` を送ったときだけ `'externalUrl'` を足す（実装プラン §8 の 17。条件 20 は `changed` を見ない） |

### 5.7 投稿フォームの戻り先

* 保存・キャンセルで戻る先を、**開いたタブ**にする。送信待ちタブの「編集」「+ 投稿を作成」は `?from=pending` を付け、投稿タブからは付けない
* 編集・新規の Server Component が `from` を読み、`pending` なら `/social`、それ以外（無い・知らない値）は `/social?tab=posts` を `SocialPostForm` の新しい props `returnTo` に渡す
  （**許す値は 2 つだけ**。任意の URL を受け取らない＝オープンリダイレクトにしない）
* 新規作成でアカウントが無いときの「SNS画面へ」は `/social?tab=accounts`
* **理由**：今の戻り先 `/social` は送信待ちタブになる。投稿タブで下書きを直して保存すると、下書きの出ない送信待ちタブへ戻り、直した投稿を見失う

    * `awaiting_approval`：`status = 'awaiting_approval'`

    * `action`：`CASE <manual_pending の条件> THEN 0 WHEN status = 'awaiting_approval' THEN 1 ELSE 2 END ASC`、

### 8.2 手動投稿の結果 `POST /api/v1/social/posts/{id}/manual-outcome`（`social.write`）

| 項目 | 内容 |
| --- | --- |
| 認証 | **セッションだけ**（`sessionOnly: true`。Bearer は 401 `UNAUTHENTICATED`）。CSRF を検証する |
| Rate Limit | 既定（操作 × 送信元 IP ごとに 60 秒 300 回） |
| パス | `{id}` が UUID の形でなければ 404（既存の `{id}` の操作と同じ） |
| 要求 | `outcome`：`'posted'` \| `'not_posted'`（必須）。`expectedUpdatedAt`：ISO 8601（必須）。`externalUrl`：文字列か null（任意。`posted` のときだけ。https・`EXTERNAL_URL_MAX_LENGTH` 以内）。他のキーは 422（`strict`） |
| 200 | 更新後の投稿（既存の `postResponseSchema`） |
| 404 | 投稿が無い・区画の外 |
| 409 | `expectedUpdatedAt` が今の `updatedAt`（ミリ秒）と違う（`StaleSocialPostError`）・条件付き更新が当たらなかった（`SocialPostStateChangedError`） |
| 422 | 形の誤り。`not_posted` に `externalUrl`（キー `externalUrl`「投稿しなかったときは URL を送れません。」）。`externalUrl` が https でない・長すぎる（`PATCH` と同じ文言）。手動の予約でない（キー `status`「手動投稿の予約ではありません。」。承認待ち・下書き・配信済み・失敗・自動配信） |
| 403 | `social.write` が無い・CSRF |
| `operationId` | **`recordSocialPostManualOutcome`**（既存の `approveSocialPost`・`bulkPublishSocialPostsNow` の流儀。初版は名前を決めていなかった。実装プラン §8 の 2） |

UseCase `recordManualOutcome`（`social.post.recordManualOutcome`。`defineUseCase`・`permission: 'social.write'`）：

1. `assertUsableText`（`externalUrl`）
2. `findPostById(…, scopeOf(context))` → 無ければ `NotFoundError`
3. `post.updatedAt`（ミリ秒）≠ `expectedUpdatedAt` → `StaleSocialPostError`
4. `manualOutcomeEligibility(post)` が偽 → `ValidationError('SocialPost', 'status', …)`
5. `externalUrl` の検査（`not_posted` なら送られた時点で 422、`posted` なら `isValidExternalUrl`）
6. `context.connection.transaction` の中で Repository `recordManualOutcome({ id, outcome, externalUrl, now, expectedUpdatedAt })`：

   ```sql
   UPDATE social_posts SET status = …, published_at | failed_at = $now, external_url = …, failure_reason = …,
          next_attempt_at = NULL, updated_at = $now
    WHERE id = $id AND status = 'scheduled' AND delivery_mode = 'manual'
      AND date_trunc('milliseconds', updated_at) = $expectedUpdatedAt
   RETURNING …
   ```

   当たらなければ読み直し、無ければ `NotFoundError`、あれば `SocialPostStateChangedError`
7. イベント（§5.6）→ 監査（§5.6）

### 8.3 `resolveManualHandoff` の変更

* 手動投稿でなければ 422（今のまま）。**`status !== 'scheduled'` なら `manual()` を呼ばず `{ ok: false, reason: 'not_scheduled' }`**（新。区画・Plugin の検査より後、締切の検査より前）
* 画面の文言 `MANUAL_HANDOFF_REASON_LABEL.not_scheduled`「承認すると投稿画面を開けます」
* 他（締切・行ごとの上限・URL の検査・`note` の伏せ字）は変えない
* **描画の途中で行が変わったとき（検証 1 回目 security S1）**：一覧を読んでから `resolveManualHandoff` が読み直すまでに、その行の配信方法が自動へ変わる
  （`ValidationError`）か、行・アカウントが消される（`NotFoundError`）と、UseCase は例外を投げる。`app/social/page.tsx` は行ごとの呼び出しを `Promise.all` で
  並べているので、**1 行の例外で送信待ちタブ全体がエラー画面になる**（035 からある形だが、055 で対象がすべての手動の予約に広がった）。
  * **決めたこと**：行ごとの呼び出しを、例外を結果に読み替える小さな関数 **`settleManualHandoff(pending: Promise<ManualHandoffOutcome>): Promise<ManualHandoffOutcome>`**
    （`apps/web/src/application/social/manual-handoff-settle.ts`。新規）で包む。`ValidationError`（その派生を含む）と `NotFoundError` は
    **`{ ok: false, reason: 'changed' }`** に読み替え、結果はそのまま返す。**それ以外の例外はそのまま投げ直す**（認可の失敗・DB の障害を「開けない行」に隠さない）
  * `ManualHandoffOutcome` の `reason` に **`'changed'`** を足す（`resolveManualHandoff` 自身は返さない。読み替えた結果だけ）。画面の文言は
    `MANUAL_HANDOFF_REASON_LABEL.changed`「投稿が変わりました。読み込み直してください」（§9.9）
  * **新しい理由にした理由**：既存の 4 つはどれも事実と違う説明になる（`plugin_error`「Plugin でエラーが起きました」は Plugin の不調と読ませ、
    `not_scheduled`「承認すると投稿画面を開けます」は承認を促す）。読み込み直せば行は自動の予約として描かれるか消えるので、それを促す文言にする
  * 呼ぶ側の形は `settleManualHandoff(resolveManualHandoff(context, { id, deadline }))`。締切の作り方（035 #105 (e)：1 か所・`Promise.all` より前・
    `resolveManualHandoff(` の近くに `deadline`）と「送信待ちの行の組み立てを別のファイルへ出さない」（実装プラン §7 の 3）は変えない
  * 読み替えた行は表に残り、§9.3.4 の開けない行と同じく「投稿画面を開く」が `disabled` で理由が出る。「投稿した」は押せるが、`manual-outcome` が
    409 / 422 / 404 で断る（今の判定のまま）。順に投稿の計画では「投稿画面を開けない」に数える（`manualSequencePlanOf` は `handoff.ok` を見るだけ。変えない）

    登録元のほうが「どのトークンから来たか」まで分かるので、実装プラン（§8 の 8）の読みのとおり登録元だけにした。`approval-pending.test.ts` の「API」「画面」の件は移さない（§14）
* 「差し戻す」は今のまま（確認 → `PATCH { status: 'draft' }`）
* 「編集」は `/social/posts/{id}/edit?from=pending`
* 1 件の操作が成功したら、**操作の後に送信待ちから出ていく行**（差し戻す・投稿した・取りやめ・削除）は行を手元で隠し、Toast、`router.refresh()`（今の区画と同じ。選択からも外す）。

    （検証 1 回目 spec 低-3。画面の振る舞いは実装のまま）

  状態の列に「⚠ 投稿が変わりました。読み込み直してください。」を出す。**表の他の行・絞り込み・一括の帯は今までどおり描く**（1 行の変化でタブ全体をエラー画面にしない）

  確認と削除の処理は投稿タブと同じもの（§9.4 で切り出す 1 件の削除の部品）を使い、二重に書かない
  * **経緯**：初版は「行の削除は出さない（一括取り消しで 1 件だけ選べば消せる）」としたが、ユーザー裁定 8 で投稿タブと同じく行に出すことにした
* **ボタンの並べ方**（ユーザー裁定 8。手動の行は最大 5 つのボタンと 1 つのリンクになる）：

  * 並びの順は**主な操作 → 記録・判断 → 編集 → 削除**（上の表の左から）。主な操作（「投稿画面を開く」「承認する…」）だけ `primary`、他は `secondary` / `ghost`。

  * 「別のタブで開く」は「投稿画面を開く」の直後に小さい文字のリンクで置く（今の区画と同じ）
  * 幅 375px では表は今までどおり表の中で横に動き（`.tf-table-scroll`）、操作のセルの中で折り返す。ボタンは押せる大きさのまま縮めない

#### 9.3.5 行の型（`PendingRow`）

054 の `PostRow` に足す（Server Component が作る）：

```ts
interface PendingRow extends PostRow {
  readonly kind: PendingKind;
  readonly elapsedText?: string;                   // manual_pending のとき
  readonly handoff?: ManualHandoffOutcome;          // 手動の予約（scheduled・manual）のときだけ
  readonly link: string | null;                     // 承認のダイアログの全文確認
  readonly media: readonly { url: string; alt: string | null }[];
  readonly requestedAt: string;                     // createdAt
  readonly warning: 'no_publisher' | 'credential_missing' | null;  // 承認待ちの自動の行
}
```

**承認待ちの行に `handoff` を渡さない**（§5.5）。トークンの ID は渡さない（054 §5.6）。

### 9.5 選んだ手動投稿を順に投稿（ユーザー裁定 6。`ui/social/manual-sequence.tsx`）

#### 9.5.1 始め方

* 送信待ちタブの一括の帯に「**選んだ手動投稿を順に投稿…**」（`social.write` のとき）。純関数 **`manualSequencePlanOf(selectedRows)`** の対象が 0 件なら `disabled`
* `manualSequencePlanOf`：表の並びの順に、`deliveryMode = 'manual'` かつ `status = 'scheduled'` かつ `handoff.ok` の行が対象。対象外は理由ごとに数える：
  「承認待ち」（承認してから）・「投稿画面を開けない」（`handoff` が開けない）・「自動配信」

#### 9.5.2 ダイアログ（`Modal`）

```text
┌ 手動投稿（2 / 5 件目） ─────────────────────────┐
│ X（@torifune）  予約 10/24 10:00                      │
│ 新製品のお知らせです。……（本文の全文）                  │
│ [投稿画面を開く]  別のタブで開く                         │
│ 投稿の URL（任意）[https://            ]               │
│ ─────────────────────────────────── │
│ 記録済み 1 件（投稿した 1）  対象外 1 件（承認待ち 1）     │
│                [やめる] [投稿しなかった] [投稿した] │
└───────────────────────────────────┘
```

* **開くのは人のクリックだけ**：「投稿画面を開く」の `onClick` の同期処理で `openManualWindow`。ダイアログを開いたとき・記録の後に自動で開かない
  （`window.open` はクリックの同期処理の外ではポップアップとしてブロックされる。§3.3）。窓の名前は今と同じなので、2 件目も同じ窓に開く
* 「投稿した」：`manual-outcome { outcome: 'posted', expectedUpdatedAt, externalUrl? }`。成功したら記録に足し、**次の件を表示して止まる**（次の「投稿画面を開く」を押すまで開かない）
* 「投稿しなかった」：ダイアログの中で確認に切り替える（06 §37）。

  ```text
  「新製品のお知らせ…」を失敗として確定しますか？
  配信履歴に「失敗」として残ります。やり直すには新しい投稿を作ります。この操作は取り消せません。
                                      [戻る] [失敗にする]
  ```

  「失敗にする」で `manual-outcome { outcome: 'not_posted', expectedUpdatedAt }`。成功したら次の件へ
* 「別のタブで開く」（開けないときのリンク）は行と同じ `MANUAL_PENDING_FALLBACK_LABEL`
* 押している間（保存中）は 3 つのボタンを `disabled`
* **保存に失敗したとき**（409・422・404・429・通信の失敗）：その件の上に `Alert`（danger）でサーバの文言（409 は `MANUAL_SEQUENCE_STALE_MESSAGE`「内容が変わっています。この投稿は飛ばして次へ進めます。」。§9.9）。
  ボタンは「**飛ばして次へ**」（その投稿は変えずに次の件へ。最後の件なら終わりの表示）と「やめる」。飛ばした件は記録に「飛ばした」として数える
* 「やめる」（とダイアログの ×）：いつでも閉じる。**まだ記録していない件は何も変えない**（待ちのまま。ユーザー裁定 6）
* 最後の件を記録したら「すべての手動投稿を記録しました（投稿した n・投稿しなかった n・飛ばした n）。」と「閉じる」
* 閉じたとき、1 件でも記録していれば Toast（「n 件を記録しました（投稿した n・投稿しなかった n）。」）と `router.refresh()`、選択を空にする。0 件なら何もしない
  * ここで「記録した」は**「投稿した」「投稿しなかった」で保存した件**で、「飛ばした」は数えない。**「飛ばした」だけで閉じたときは何もしない**（Toast も読み込み直しも出さず、選択もそのまま）。
    飛ばした件は投稿を変えていないので、知らせることも描き直すことも無い。上の「飛ばした件は記録に『飛ばした』として数える」は、ダイアログの中の進み具合と終わりの表示の内訳のこと
  * **経緯**：初版は「飛ばした件は記録に数える」と「1 件でも記録していれば Toast」を並べ、飛ばしただけのときの扱いが字面から一意に決まらなかった。実装プラン（§8 の 71）の読みのとおりにした
    （検証 1 回目 spec 軽微-3。画面の振る舞いは実装のまま）
* 本文は全文（`overflow-wrap: anywhere`）。`note`（Plugin の補足）があれば本文の下に出す
* 単体テストのために `initialIndex`・`initialRecords`・`initialConfirming` を受け取る（既定は 0・空・偽）。`open` は今の `manual-pending.tsx` と同じく差し替えの口を持つ

### 9.6 配信履歴タブ

* 「投稿しなかった」の行は「失敗」で、「失敗の理由」に `MANUAL_NOT_POSTED_REASON` が出る（今の列のまま）

### 9.7 `/social/history` の転送

* `app/social/history/page.tsx` は **`redirect()`（307）だけ**にする。`status` が `published` / `failed` なら `historyStatus` に、`page` は `normalizePage(params['page'])` で読み 2 以上なら `historyPage` に写す

## 13. 受け入れ条件

番号は実装プラン・テストで参照する。**A = 単体（Domain 純関数・UI 部品）、B = 結合（DB・UseCase。publisher はテストが登録する偽物）、
C = API（ルートを直接叩く結合）、D = 画面（E2E）、E = 静的検査。**

共通の準備（B・C）：`manual` と `publish` を持つ偽物の publisher の provider のアカウント `acc`、自動だけの provider のアカウント `accAuto`、
管理者・編集者・閲覧者のセッション（CSRF トークン付き）、API トークン（`social.read` + `social.write`）。
テストの手段（準備の作り方・UI 部品で押す操作の見方・E2E の隔離と子ウィンドウの拾い方）は実装プラン §2「テストの方法」と §8 の 14・15・20〜22・29〜35 に従う。

### 13.1 Domain 純関数（A）

1. `pendingKindOf(post, now = T)`：`scheduled`・`manual`・`scheduledAt = T` → `manual_pending`。`T−1m` → `manual_pending`。`T+1m` → `scheduled`。`scheduledAt = null` → `scheduled`。
   `scheduled`・`auto`（`T−1m`・着手印あり・失敗理由あり、それぞれ）→ `scheduled`。`awaiting_approval`（自動・手動）→ `awaiting_approval`。`draft` / `published` / `failed` → `null`
2. `PENDING_KINDS` が `['manual_pending', 'awaiting_approval', 'scheduled']`。`isPendingKind`：この 3 つ → 真、`'draft'`・`''`・`'MANUAL_PENDING'` → 偽
3. `canOpenManualHandoff`：`manual`・`scheduled` → 真（予約日時の過去・未来・null、`approvedAt` の有無を問わない）。`manual`・`awaiting_approval` / `draft` / `published` / `failed` → 偽。`auto`・`scheduled` → 偽
4. `manualOutcomeEligibility`：3 と同じ真偽
5. `MANUAL_NOT_POSTED_REASON` が「手動投稿で『投稿しなかった』が選ばれました。」

### 13.2 送信待ちの一覧（B）

準備：`acc` に手動の予約（予約 `now−2h`＝P1、`now−1h`＝P2、`now+1h`＝S1、予約日時 null＝S0）、`accAuto` に自動の予約（`now+2h`＝S2、`now−1m` で着手印あり＝S3）、
承認待ち（作成の古い順に A1・A2。A1 は `accAuto` で自動・希望日時 `now+30m`、A2 は `acc` で手動・希望日時なし）、下書き D、配信済み X、失敗 F（D・X・F は `acc`）。
作成の順は P1・P2・S1・S0・S2・S3・A1・A2・D・X・F（後ほど `created_at` が新しい）。
作成の検査が断る形（S0 の予約日時なし）と UseCase で作れない状態（S3 の着手印、X・F の状態）は、作った後に SQL で書く（`created_at` は崩さない）。
**経緯**：初版は A1 のアカウントを決めていなかった。条件 10（アカウントの絞り込み）が承認待ちにも掛かることを見られるよう、実装プラン（§8 の 13・14）の読みのとおり A1 を `accAuto` にした。

6. `kind: null`・`sort` 省略 → 並びがちょうど `P1, P2, A1, A2, S3, S1, S2, S0`（(A) 手が要るもの順。区分の順、区分の中は §5.3）。`sort: 'action'` でも同じ。D・X・F を含まない。`total` が 8
7. `counts` が `{ manual_pending: 2, awaiting_approval: 2, scheduled: 4 }`。`kind: 'awaiting_approval'` でも `counts` は同じで、`items` は `A1, A2`・`total` 2

   **作成順と希望日時の順が逆の承認待ちの組**（先に作った B1 の希望日時が後に作った B2 より遅い。別のアカウントで足し、終わったら消す）では、`sort: 'action'` は `B1, B2`（依頼の古い順＝`created_at`）、
   `sort: 'time'` は `B2, B1`（**経緯**：§13.2 の A1・A2 は作成順と希望日時の順が同じで、承認待ちの並びの鍵を見分けられなかった。検証 1 回目 spec 中-2）
9. 区分の境目は入力の `now`：`now = P2 の予約日時ちょうど` で P2 は `manual_pending`、`now = P2 の予約日時 − 1ms` で `scheduled`（`items` と `counts` の両方）
10. `socialAccountId = accAuto` → 並びがちょうど `A1, S3, S2`（`action`）。`counts` もアカウントを掛けた数で `{ manual_pending: 0, awaiting_approval: 1, scheduled: 2 }`

12. `perPage: 3, page: 2` → `A2, S3, S1`（`total` は 8 のまま）。`sort: 'time'` で `perPage: 3, page: 2` → `A1, S1, S2`（#75 の並びの 4〜6 件目）

14. 閲覧者（`social.read`）で呼べる。`social.read` の無い文脈 → 403（`ForbiddenError`）

### 13.3 手動投稿の結果（C）

15. 管理者が手動の予約（予約時刻の**後**）に `{ outcome: 'posted', expectedUpdatedAt }` → 200。`status: 'published'`・`publishedAt` がいま・`scheduledAt` は変わらない
16. 予約時刻の**前**の手動の予約に `posted`（`externalUrl: 'https://x.com/i/status/1'`）→ 200。`externalUrl` が入り、`scheduledAt` は未来のまま、`publishedAt` はいま
17. 承認済み（`approvedAt` あり）の手動の予約に `posted` → 200、`approvedAt` は変わらない
18. `{ outcome: 'not_posted', expectedUpdatedAt }` → 200。`status: 'failed'`・`failedAt` がいま・`failureReason` が `MANUAL_NOT_POSTED_REASON`・`scheduledAt` は変わらない。`listSocialPostHistory` に出る
19. イベント：`posted` で `social.post.published`（`{ postId, accountId, status: 'published' }`）が 1 回、`not_posted` で `social.post.failed`（`status: 'failed'`）が 1 回。それ以外のイベントは出ない
20. 監査：`action: 'updated'`・`resourceType: 'social_post'`・`resourceId` が投稿の ID、`detail.manualOutcome` が `posted` / `not_posted`、`detail.status` が `published` / `failed`
21. `expectedUpdatedAt` が 1ms 違う → 409。行・監査・イベントは変わらない
22. 2 回目：`posted` で 200 になった投稿に、同じ `expectedUpdatedAt` でもう一度 `posted` → 409（`publishedAt` は 1 回目のまま、イベントは増えない）。今の `updatedAt` で送り直すと 422 `status`
23. 対象外 → 422（キー `status`「手動投稿の予約ではありません。」）：承認待ちの手動投稿・下書きの手動投稿・自動配信の予約・配信済み・失敗（どれも今の `updatedAt` で送る）。行は変わらない
24. `not_posted` に `externalUrl` → 422（キー `externalUrl`）。`posted` に `externalUrl: 'http://…'` → 422（キー `externalUrl`）。`outcome: 'skip'`・`outcome` なし・`expectedUpdatedAt` なし・ISO でない・未知のキー → 422
25. 存在しない UUID → 404。UUID の形でない `{id}` → 404
26. 競合（B）：Repository の `recordManualOutcome` を、読んだ後に配信方法を `auto` に変えた行・`draft` にした行で呼ぶと `null`（更新されない）。UseCase は 409 `SocialPostStateChangedError`
27. 配信ジョブ（B）：予約時刻を過ぎた手動の予約は `publishDuePosts` の対象にならない（今のまま）。`posted` の後に `publishDuePosts` を走らせても `published_at` は変わらない

### 13.4 `resolveManualHandoff`（B）

### 17.2 設計で決めず、後の判断に回すもの

1. **タブの見出しに件数**（「送信待ち（12）」）：どのタブでも送信待ちを数える問い合わせが要る。`countPendingByKind` があるので足せる

3. **行の 1 件の「投稿しなかった」**：順に投稿で 1 件だけ選べば同じことができる。行に足すなら `manual-outcome { outcome: 'not_posted' }` と確認を使い回すだけ
