### 1.3 指摘事項

#### 重大

無い。

#### 中

* **中-1 行の「投稿した」が `manual-outcome` を使うことをどのテストも見ていない。**
  場所：`apps/web/src/ui/social/social-pending.tsx` の `confirmDone`。根拠：設計の裁定の記録（「行の 1 件の『投稿した』もこれに替える」）・§5.6（`PATCH` は画面が見た `updatedAt` を条件にできず、
  `published → published` を許す）・§9.3.4。実装は設計どおりだが、`PATCH /social/posts/{id} { status: 'published' }` に戻す変異（M1）で `ui/social/` の全テストが通り、
  E2E #63 も API の状態（`published`）と Toast `/記録しました/` しか見ないので通る見込み。409 の Toast を `MANUAL_OUTCOME_STALE_MESSAGE` からサーバの文言に替える変異（M2）も通る。
  **直し方**：`pend` に、捕まえた「記録する」の `onClick` で `apiRequest` が `('/api/v1/social/posts/{id}/manual-outcome', { method: 'POST', body: { outcome: 'posted', expectedUpdatedAt: row.updatedAt } })` で 1 回呼ばれる件を足す（`seq` #55 と同じ見方）。
  409 の Toast は描画の後の状態なので、純関数に切り出すか E2E で見る
* **中-2 手が要るもの順で、承認待ちを依頼の古い順（`created_at`）に並べることを見分けるテストが無い。**
  場所：`apps/web/src/infrastructure/social-repository.ts` の `listPendingPosts` の 2 つ目の `orderBy`。根拠：設計 §5.3 (A) の 2「`awaiting_approval`（依頼の古い順＝`created_at`）」・§8.1。
  §13.2 の準備は A1（先に作成・希望日時 `now+30m`）と A2（後に作成・希望日時なし）で、作成順と「希望日時の早い順・無いものは最後」が同じ並びになる。
  承認待ちも `scheduled_at` で並べる変異（M5）で `plist` が全件通った。E2E #62 は承認待ちが 1 件だけ。
  **直し方**：`plist` に、先に作った承認待ちほど希望日時が遅い（または後に作った方だけ希望日時がある）組で `kind: 'awaiting_approval'`・`sort: 'action'` の並びを見る件を足す（§13.2 の準備は崩さず、#11・#13 と同じく最後の describe で足して消す）
