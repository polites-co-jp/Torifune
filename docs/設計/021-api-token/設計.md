# 021-api-token 設計

## 1. 目的

外部クライアント向けの認証（`05_API設計.md` §37-38、§12）。
`002-Torifune機能完成` T3。想定ID `016-api-token` は `016-home-routing` と
衝突したため `021` へ改番した。

いまは認証経路がセッション Cookie 一択で、`Authorization` ヘッダを読む分岐も
差し込み点も無い（§12 が「部分的」な直接の原因）。

## 2. 決めたこと

### 2.1 Token は「発行者自身のもの」に限る

**他人のための Token を作れないようにする。** 作れると、権限の貸し出しになり、
監査で「誰がやったか」が追えなくなる。

Token の所有者は常に発行した本人。`userId` を入力で受け取らない。

### 2.2 Scope は「発行時に固定し、使用時に交差させる」

Token には Scope（Permission の部分集合）を持たせる。
**ただし実効権限は、使用時に「所有者のいまの Permission ∩ Scope」で求める。**

固定した Scope をそのまま信じると、

* ロールを外されたユーザーの Token が、外す前の権限で動き続ける
* 権限を落としても Token 経由で元の操作ができる

という穴になる。**Token は権限を増やせない。絞るだけ。**

### 2.3 発行時に Scope が所有者の権限を超えていたら拒否する

使用時に交差させるので実害は無いが、**黙って削ると発行者が誤解する。**
「指定したのに効かない」より「指定できない」ほうがよい。

### 2.4 平文は発行時に一度だけ返す

DB には SHA-256 ハッシュだけを保存する（セッショントークンと同じ扱い）。
一覧・詳細で平文を返す経路を作らない。**作れば必ず漏れる。**

識別のために先頭8文字（`prefix`）だけを別カラムで保存し、一覧に出す。
どの Token かを人が見分けられないと、失効させる対象を選べない。

### 2.5 Bearer 認証では CSRF を検証しない

CSRF は「ブラウザが Cookie を自動送信すること」への対策。
`Authorization` ヘッダは自動送信されないため、検証する意味が無い。

**検証したままにすると、API クライアントが更新系を一切呼べない。**
セッション Cookie 経由のときだけ検証する。

> Cookie と Bearer が**両方**付いている要求は、Bearer を優先する。
> 「どちらでも通る」にすると、CSRF 検証を Bearer で迂回できてしまう。

### 2.6 Permission は `token.manage` を足す

Token の発行はアカウントの分身を作る操作で、誰にでも許す性質ではない。
既定では administrator にだけ与える。

### 2.7 有効期限は任意。無期限を許す

自動実行の連携で期限切れに気づけず止まるほうが害が大きい場面がある。
ただし**既定は期限あり**にして、無期限は明示させる。

## 3. データ

```sql
api_tokens
  id, user_id, name, token_hash (unique), prefix,
  scopes text[], expires_at, last_used_at, revoked_at, created_at
```

* `user_id` は `ON DELETE CASCADE`。ユーザーが消えたら Token も消す
* `revoked_at` は行を消さずに失効させる。**消すと監査が追えない**
* `last_used_at` は最後に使われた時刻。使われていない Token を見つけるため

## 4. 認証の流れ

```text
Authorization: Bearer <token>
  → SHA-256 → api_tokens を引く
  → revoked / expired を弾く
  → 所有者を引く（status=active でなければ弾く）
  → permissions = 所有者の実効Permission ∩ Token の Scope
  → last_used_at を更新（失敗しても認証は通す）
```

`AuthorizationContext` の作り方は `application/authorization/context.ts` に
集約されているので、そこへ足す。**別経路を作らない。**

## 5. API

```text
POST   /api/v1/api-tokens         発行（平文はここでだけ返る）
GET    /api/v1/api-tokens         自分の Token 一覧
DELETE /api/v1/api-tokens/{id}    失効
```

**Token 認証で Token を発行できないようにする。** できると、
Scope を絞った Token から、より広い Token を作れてしまう
（Scope の意味が無くなる）。発行・失効はセッション認証でだけ許す。

## 6. Rate Limit

`05_API設計.md` §36 が重点対象に挙げる「Token発行」「API Token認証」へ
既定より厳しい上限をかける。発行は総当たりの対象ではないが、
**認証失敗は総当たりの対象**になる。

## 7. やらないこと

* Token の更新（名前や Scope の変更）。作り直せばよい。
  変更を許すと「いつからその Scope だったか」が追えなくなる
* Token 一覧の他人分の閲覧（`user.manage` があっても見せない）。
  失効だけは管理者にも許したくなるが、**今回は入れない**。
  必要になったら、そのときの要求と合わせて設計する
* 設定画面のAPIタブ（`06_画面設計.md` §16）。`015b-settings`（T4）で作る

## 8. 受け入れ条件

1. Token で保護APIを叩ける。Scope 外は 403、失効後・期限切れは 401
2. 所有者のロールを外すと、Token の実効権限も狭まる
3. DB に平文が無い。一覧・詳細に平文が出ない
4. Bearer 認証では CSRF ヘッダ無しで更新系が通る
5. Cookie と Bearer が両方あるとき、Bearer が使われる
6. Token 認証では Token を発行できない
7. 所有者の権限を超える Scope を指定した発行が拒否される
8. 発行・認証失敗に Rate Limit がかかる
