# 034 アナリティクスの期間プリセット「昨日」と期間の適用範囲 — 設計

入力は `要件.md`（裁定は決定事項）。**この設計書が後続（プラン・テスト・実装・検証）の唯一の入力である。**

## 1. 目的

アナリティクス画面について、次の 2 つを満たす。

1. 期間プリセットに **「昨日」** を足す（「7日」の左）。`[昨日, 昨日]` の 1 日を**確定値**から出す
2. **選んだ期間がどの区画にも効いていることを、画面から読み取れるようにする**

2 は「効くようにする」ではない。**すでに効いている**（§2.1）。効いていることが
画面のどこにも書かれていないので、利用者からは 1 枚のカードにしか効いていないように見えている。
本設計で変えるのは**表示**であり、問い合わせと集計は変えない。

## 2. 前提（実物を読んで確かめた事実）

`要件.md` §2 の確認結果を、設計担当としても実物で裏を取った。**食い違いは無かった。**
以下は設計の土台になる事実である。

### 2.1 期間はすでに画面全体へ効いている

`apps/web/src/app/analytics/page.tsx` は `resolvePeriod` が決めた 1 つの期間
（`period.from` / `period.to`）を**すべての問い合わせに渡している**。

| 表示 | データ源 | 期間の渡り方 |
| --- | --- | --- |
| 上部 5 タイル（PV / 訪問者 / セッション / 直帰率 / 平均滞在） | `currentPoints` | `keyless(period.from, period.to)` |
| 日次の推移 | 同じ `currentPoints` | 同上 |
| 上位ページ / 参照元 / 時間帯別 / デバイス | `breakdownOf(...)` | `breakdown(context, { ...range, ... })`（`range = { siteId, period.from, period.to }`） |
| ページ / 参照元 / 訪問者タブ | 同じ `breakdownOf` / `valuesByKeyOf` / `currentPoints` | 同上 |

`apps/web/src/infrastructure/analytics-repository.ts` の共通条件も
`metric_date >= ${filter.from}::date` / `metric_date <= ${filter.to}::date` で必ず絞っている
（一覧・件数の両方。L88-89 / L126-127）。

**「日次の推移にしか効いていない」という状態はコード上に無い。**

### 2.2 期間を画面に出しているのは 1 か所だけ

期間（`YYYY-MM-DD 〜 YYYY-MM-DD`）を文字として出しているのは、概要タブの
「日次の推移」カードの見出し右（`OverviewTab` の `SectionHeader aside={rangeText(from, to)}`。
`overview-tab.tsx` L208）**だけ**である。

* ヘッダ行（`analyticsHeaderText`）は「前期間（…）と比較 · 集計は前日まで · 日付の区切りは …」で、
  **当期そのものの日付を出していない**
* 上位ページ・参照元・時間帯別・デバイス・ページ／参照元／訪問者タブには期間の表示が無い
* 日付入力（`DateField` 2 つ）には当期の日付が入っているが、期間セグメントの右にある
  小さな入力であって、「どこに効いているか」の表示としては読まれない

「どの数字がどの期間のものか」を画面から確かめられるのが 1 枚のカードだけ、という状態である。

### 2.3 1 日の期間の折れ線は、いま**空の枠**が出ている

`Chart` は `chartLayout` を通り、`points.length === 1` のとき `step = 0`
（`chart-geometry.ts` L60）。`<polyline>` に点が 1 つだけ渡ると**線分が 1 本も引けない**ので、
グリッド線だけの箱が出る。`fallback`（＝ `<details>` の代替表）は `figcaption` に出るので、
値そのものは読めるが、**折れ線としては空の枠**である。

現状 `period=custom&from=X&to=X` はこの状態になる（E2E の `todayUrl` がまさにこの形。
`analytics.spec.ts` L171-172）。`period=today` は `daily = null` にしてカードごと出していない
（030 §7.3）。

### 2.4 期間プリセットの現状

* `domain/analytics/day.ts` … `PeriodPreset = '7d' | '30d' | '90d' | 'month' | 'prev-month'`、
  `PERIOD_PRESETS` がその並び。`presetRange(preset, today)` は `DateRange | null`
  （`null` は今月 1 日の `month` だけ）
* `ui/analytics/labels.ts` … `AnalyticsPeriod = PeriodPreset | 'today' | 'custom'`、
  `ANALYTICS_PERIODS` が画面の並び（6 個）、`PERIOD_LABEL` が表示名
* `today` は `PeriodPreset` に入っていない（030 §7.1.2）。`SegmentedControl` も期間とは別に置いている
* すべてのプリセットは末尾が昨日（030 の裁定）

### 2.5 `presetRange` / プリセットの呼び出し元は 1 か所しかない

`grep` の結果、`presetRange` を呼ぶ実装は `ui/analytics/analytics-query.ts` の
`resolvePeriod` **だけ**（L133 / L148）。`app/dashboard/page.tsx` は自前で範囲を組んでおり、
`static-checks.test.ts` が「`presetRange` を import していない」ことを固定している。

**API には期間プリセットの概念が無い。** `GET /api/v1/analytics` と
`GET /api/v1/analytics/breakdown` は `from` / `to` を受けるだけで、`period` を受けない
（`api/schemas/analytics.ts` / 各 `route.ts`）。

## 5. データモデル

**変更なし。マイグレーションを足さない。**

根拠：

* 「昨日」は既存の `analytics` テーブルを `metric_date` で絞るだけで、新しい列も指標も要らない

## 7. 画面

### 7.1 期間プリセット「昨日」（030 §7.1.1 / §7.1.2 の改訂）

#### 7.1.1 `PeriodPreset` に入れる

**`today` と違い、`yesterday` は `PeriodPreset` に入れる。**

```ts
export type PeriodPreset = 'yesterday' | '7d' | '30d' | '90d' | 'month' | 'prev-month';

export const PERIOD_PRESETS: readonly PeriodPreset[] = [
  'yesterday', '7d', '30d', '90d', 'month', 'prev-month',
];
```

| preset | from | to | `null` になるか |
| --- | --- | --- | --- |
| **`yesterday`** | `today − 1` | `today − 1` | **ならない** |
| `7d` / `30d` / `90d` | `today − 7 / 30 / 90` | `today − 1` | ならない |
| `month` | 今月 1 日 | `today − 1` | 今日が月の 1 日のとき `null` |
| `prev-month` | 前月 1 日 | 前月末日 | ならない |

**理由**：`PeriodPreset` の契約は「`presetRange(preset, today)` で**確定値のある** `DateRange` が
求まるもの」である（030 §7.1.2）。`yesterday` はこの契約をそのまま満たす。

* 昨日は `analytics`（確定値）から出す。既存プリセットの `to` はすべて昨日なので、
  `yesterday` は「その末尾の 1 日だけを見る」ものであり、規則が 1 つ増えない
* `today`（当日）は生ログをその場で集計する別経路なので契約に入らない。
  **`today` を `PeriodPreset` に入れないという 030 の判断は変えない**

**`null` を返す分岐を増やさない。** `yesterday` は `today` が何日であっても必ず範囲が求まる。
月の 1 日でも前月末日という確定した 1 日が出る（`month` の空状態とは無関係）。

#### 7.1.2 画面の並びと表示名

```ts
export const ANALYTICS_PERIODS: readonly AnalyticsPeriod[] = [
  'yesterday', '7d', '30d', '90d', 'month', 'prev-month', 'custom',
];

export const PERIOD_LABEL = { ..., yesterday: '昨日', ... };
```

* 「昨日」は**期間の `SegmentedControl` の先頭**（＝「7日」の左）に入る（裁定 3.1）
* **「当日」の `SegmentedControl` には入れない**（裁定 3.1）。左のグループは
  「確定値ではない速報値」1 つだけを持つ群であり、そこに確定値を混ぜると
  群の意味（030 §7.1.3 の 2 グループ）が壊れる
* 画面の並びは `[当日] [昨日 7日 30日 90日 今月 前月 カスタム]` になる

```text
[SegmentedControl: 当日]  [SegmentedControl: 昨日 7日 30日 90日 今月 前月 カスタム]  [from] – [to]
```

**共通部品（`SegmentedControl`）は変えない。** 項目が 1 つ増えるだけである。

#### 7.1.3 影響範囲（`要件.md` §4-6 の答え）

| 観点 | 影響 |
| --- | --- |
| `presetRange` の呼び出し元 | `resolvePeriod` のみ（§2.5）。分岐を 1 つ足すだけで届く |
| `isPeriodPreset` を通る URL | `?period=yesterday` が**自動的に**通る。`resolvePeriod` に変更は要らない |
| `analyticsHref` | 変更なし。`DEFAULT_PERIOD`（`30d`）以外なので `period=yesterday` が書かれる |
| API | 影響なし（§6） |
| ダッシュボード | 影響なし。`presetRange` を使っていない（`static-checks.test.ts` が固定） |
| `timezone-static-checks.test.ts` | 影響なし。`presetRange` の export が残ることだけを見ている |
| 受信状況の診断 | `periodMayLackRollup = period.to >= yesterday` が `yesterday` では **true**。昨日のロールアップがまだなら「集計待ち」の導線が出る。**正しい挙動なので判定を変えない**（030 §9.1 のまま） |
| Plugin が入れた点 | `yesterday` は `analytics` を読むので、`source <> 'core'` の昨日の点も**出る**。当日（生ログのみ）との違いは 030 §9.0 のまま |

#### 7.1.4 前期間比（`要件.md` §4-5 の答え）

`previousRange('2026-09-08', '2026-09-08')` は `{ from: '2026-09-07', to: '2026-09-07' }`
（一昨日）になる。`previousRange` は**変えない**。

* 「昨日 vs 一昨日」は前期間比として素直に読める。日数（1 日）が前後で揃っている
* ヘッダ行は既存のまま「前期間（2026-09-07 〜 2026-09-07）と比較」と出る。
  **ここを 1 日表記に縮めない**（§7.4 に理由）

### 7.2 期間が 1 日のときの区画（`要件.md` §4-1 / §4-2 の答え）

**「当日だから出さない」を「期間が 1 日だから出さない」へ一般化する。**

| 区画 | 現行の条件 | 本設計の条件 |
| --- | --- | --- |
| 概要「日次の推移」カード（`OverviewData.daily = null`） | `period === 'today'` | **`rangeDays(from, to) === 1`** |
| 訪問者タブ「1日あたり訪問者」（`VisitorsData.perDay = null`） | `period === 'today'` | **`rangeDays(from, to) === 1`** |
| 直帰率・平均滞在の注記（`bounceRateNote` / `dwellAvgNote`） | `period === 'today'` | **変えない**（`period === 'today'` のまま） |

`period === 'today'` は `from = to = 今日` なので、この一般化に**当日も含まれる**。
030 §7.3 の結論（当日ではこの 2 つを出さない）は保たれる。

**理由**：

* 030 が「出さない」と決めた根拠は 2 つとも**「1 日しかない」**ことである
  （「1 日の折れ線に意味が無い」「1 日あたり訪問者は訪問者と同じ数になる」。030 §7.3）。
  根拠が期間の長さなのだから、条件も期間の長さで書く
* 実際、1 日の期間では折れ線が**空の枠**として描かれている（§2.3）。
  `period=yesterday` を足すと、既定の入口からこの状態へ簡単に到達できてしまう
* 直帰率・平均滞在の注記は「進行中のセッションを含む」ことの説明であり、
  **確定値である「昨日」には当てはまらない**。だから条件を一般化しない。
  ここを一般化すると、確定値に対して嘘の注記が出る

**副作用：`period=custom&from=X&to=X`（1 日のカスタム期間）でも、この 2 つが出なくなる。**
**月の 2 日に `period=month` を選んだときも 1 日期間（今月 1 日 〜 昨日）なので、同じく消える。**
これは 030 §7.3 の適用範囲を広げる変更であり、§12 に改訂として記録する。

* 失うのは「点が 1 つで線が引けない折れ線の枠」と「訪問者と同じ数のタイル」だけである
* 1 日の期間では、030 が当日について書いたとおり**時間帯別のページビューが「推移」の役割を担う**
  （030 §7.3）。同じ 1 日を見ているのだから、当日と確定値で見え方が変わらないほうがよい
* 既存 E2E への影響を確認した。`todayUrl`（`period=custom&from=今日&to=今日`）を使う
  データ系テストは多いが、**「日次の推移」カードと「1日あたり訪問者」の存在を主張している
  テストは 1 つも無い**（存在しないことを主張するテストは `?period=today` に対してのみ。
  `analytics.spec.ts` L1951 / L1962）。031 のツールチップ E2E は `weekUrl`（7 日）を使っており無関係

### 7.3 適用中の期間の表示（裁定 3.2）

#### 7.3.1 文言（`要件.md` §4-4 の答え）

`ui/analytics/labels.ts` に 2 つ足す。**画面の各所で書き分けない。**

```ts
/** 1 日なら日付 1 つ、複数日なら「from 〜 to」。 */
export function dateRangeText(from: string, to: string): string;

/** 適用中の期間の 1 行。 */
export function appliedPeriodText(input: {
  readonly period: AnalyticsPeriod;
  readonly from: string;
  readonly to: string;
}): string;
```

| 期間 | `appliedPeriodText` |
| --- | --- |
| `7d`（`2026-09-02` 〜 `2026-09-08`） | `期間 2026-09-02 〜 2026-09-08（7 日間）` |
| `yesterday`（`2026-09-08`） | `期間 2026-09-08` |
| `custom` で 1 日（`2026-09-08`） | `期間 2026-09-08` |
| `today`（`2026-09-09`） | **`期間 当日（2026-09-09）`** |

決めたことと理由：

* **1 日のときは日付を 1 つだけ出す。** `2026-09-08 〜 2026-09-08` は同じ日付が 2 回並ぶだけで、
  読み手に何も足さない
* **当日だけは「当日（日付）」と書く。** 当日（`period=today`、生ログの速報値）と
  1 日のカスタム（`period=custom&from=to=今日`、集計値）は**同じ日付を指すのに値が違いうる**
  （030 §7.1.4）。日付だけを出すと、この 2 つが画面上で見分けられなくなる。
  ここは「日付 1 つ」ではなく**ラベル付き**にする
* **複数日には日数を添える。** `7日` というラベルの範囲が `[today−7, yesterday]` であることは
  030 未決 #4 の混乱点である。`（7 日間）` を出すと、ラベルと実際の日数が画面で照合できる。
  1 日のときは `（1 日間）` を出さない（日付 1 つで自明）
* **`rangeText` は変えない。** ヘッダ行の「前期間（… 〜 …）」は 030 §7.4.1 が定めた形で、
  E2E（`analytics.spec.ts` L1046 / L1056）が固定している。**当期の表示のためだけに
  既存の契約を動かさない**

`staleRangeNoticeText`（§7.5.1 の案内）の「この期間（…）」は `dateRangeText` を使う形へ直す。
1 日の期間で案内が出たとき、そこだけ `〜` を挟んだ形になるのを避ける。
（文言のこの部分を主張しているテストは無いことを確認済み。）

#### 7.3.2 場所 1：タブの直下に 1 つ（`PeriodBar`）

`analytics-view.tsx` から named export する部品を 1 つ足し、**`Tabs` の直下**に置く。

```ts
// ui/analytics/analytics-view.tsx
export function PeriodBar(props: {
  readonly text: string;   // appliedPeriodText の結果
  readonly from: string;   // data 属性用（E2E が文言に依存しないため）
  readonly to: string;
}): JSX.Element
```

* `<p data-analytics-period={`${from}/${to}`}>` の 1 行。本文サイズ・`font-weight: 600`・
  `--tf-color-text`。囲みは作らない（カードが増えたように見せない）
* **`StaleRangeNotice` / `EmptyPeriodNotice` と同じく named export にする。**
  部品として単独で描画できれば、画面全体を組み上げずに決定的に確かめられる（030 §7.2 と同じ理由）
* `data-analytics-period` を置くのは、ヘッダ行の `data-analytics-timezone`（既存）と同じ理由。
  E2E が文言の言い回しに依存せずに期間を読める

**なぜタブの直下か**：

* タブの下は**すべてのタブの中身の直前**であり、「ここから下は全部この期間」と位置で読める。
  裁定 3.2 の「1 か所で全体に効いていると読める位置」がこれである
* 上部 5 タイル（`StatGrid`）と訪問者タブの 4 タイルには見出しが無い。
  **タイル群のために見出しを新設しない**（028 §7.3.6 の並びを変えることになる）。
  直上にこの 1 行があれば、見出しを足さずに期間が示せる
* 期間セグメントの近く（画面のもっと上）ではなく、数字の直前に置く。
  「選ぶところ」ではなく「効いているところ」に出したいため

**出す条件**：

| 状態 | 出すか | 理由 |
| --- | --- | --- |
| 概要 / ページ / 参照元 / 訪問者タブ | 出す | 中身が期間に依存する |
| `not-tracked`（導線） | 出す | 「どの期間に記録が無いのか」が分かる |
| 設定タブ | **出さない** | 期間に依存しない（030 §7.3 のとおり） |
| `empty-period`（月の 1 日の `month`） | **出さない** | 確定期間が存在しない。`page.tsx` の代替値（`{ today, today }`）は**問い合わせに 1 度も使っていない値**であり、画面に出すと嘘になる |

並び順は `Tabs` → `PeriodBar` → 各種 `Alert`（当日バナー / 今日を含む custom / §7.5.1 の案内）→ タブの中身。
期間は「いま何を見ているか」の説明なので、状態を説明する `Alert` より先に置く。

#### 7.3.3 場所 2：期間に依存する各カードに 1 行（`SectionHeader` の `caption`）

`SectionHeader`（`parts.tsx`）に**`aside` とは別のスロット**を足す。

```ts
export function SectionHeader(props: {
  readonly title: string;
  /** 見出しの下に出す小さな補足。期間を出す（034 §7.3.3）。 */
  readonly caption?: ReactNode;
  /** 見出しの右。導線・件数など（既存）。 */
  readonly aside?: ReactNode;
}): JSX.Element
```

* `caption` は**タイトルの下**に `CAPTION` 様式（`--tf-text-caption` / `--tf-color-text-subtle`）で出す
* `aside` は現行どおり右のベースライン。**`aside` を上書きしない**（`要件.md` §4-3）。
  上位ページ・参照元の「すべて →」、ページタブの「N ページ · ページビュー順」、
  参照元タブの説明、Bot のアクセスのスイッチ状態は、いまのまま右に残る
* 両方省略したときの見た目は現行と同じ（`caption` が無ければ行を作らない）

`caption` に期間を出すカード：

| タブ | カード | 現行の `aside` |
| --- | --- | --- |
| 概要 | 日次の推移 | **`rangeText` をやめる**（下記） |
| 概要 | 上位ページ | 「すべて →」（そのまま） |
| 概要 | 参照元 | 「すべて →」（そのまま） |
| 概要 / 訪問者 | 時間帯別のページビュー | 無し |
| 概要 / 訪問者 | デバイス | 無し |
| ページ | ページ | 「N ページ · ページビュー順」（そのまま） |
| 参照元 | 参照元 | 説明文（そのまま） |
| 訪問者 | Bot のアクセス | スイッチの状態（そのまま） |

* **「日次の推移」の期間は `aside` から `caption` へ移す。** 同じ期間が同じカードに
  2 か所出るのを避け、他のカードと表示位置をそろえる。`aside` は空になる
* 設定タブのカードには `caption` を出さない（期間に依存しない）

#### 7.3.4 期間の文字列は 1 回だけ組み立てて配る

`AnalyticsView` が `appliedPeriodText` を **1 回**呼び、その文字列を
`PeriodBar` と各タブへ `periodCaption: string` として渡す。

* タブ（`OverviewTab` / `PagesTab` / `ReferrersTab` / `VisitorsTab`）と
  共通部品（`HourlyPageviews` / `DeviceBreakdown`）は `periodCaption` を受け取り、
  `SectionHeader caption={periodCaption}` に渡すだけ。**タブは文字列を組み立てない**
  （028 §7.3.6「数を計算しない・並べるだけ」を保つ）
* `OverviewTab` の `from` / `to` プロパティは `periodCaption` に**置き換える**。
  現行の用途は「日次の推移」の `aside` に渡す `rangeText` だけで、他に使っていない
* `empty-period` / 設定タブでは `periodCaption` を使わない

これで「期間の表し方」を変えるときに触る場所が `labels.ts` の 1 関数に閉じる。

### 7.4 ヘッダ行（`analyticsHeaderText`）は変えない

030 §7.4.1 の表（当日 / 今日を含まない期間 / 今日を含む `custom`）をそのまま保つ。

* 出し分けの基準は「当期が今日を含むか」（`rangeIncludesToday`）だけ、というのが 030 の設計である。
  `yesterday` は今日を含まないので**既存の 2 行目にそのまま当てはまる**
  （「前期間（2026-09-07 〜 2026-09-07）と比較 · 集計は前日まで · 日付の区切りは …」）。
  プリセットの種類で分岐を足さない
* 当期の日付はヘッダ行ではなく `PeriodBar` が持つ。**同じ情報を 2 か所に置かない**
* 「集計は前日まで」は画面全体の集計の規則であり、`yesterday` でも正しい
