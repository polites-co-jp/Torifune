### 確定事項（設計書から。プランで蒸し返さない）

* **データの取得範囲を変えない**（裁定 3.2 / 設計 §3）。`page.tsx` の問い合わせ・Repository の SQL・

* `presetRange('yesterday', …)` は **`null` を返さない**（§7.1.1）。`null` を返す分岐を増やさない

  **`rangeDays(from, to) === 1`** へ一般化する（§7.2）。**直帰率・平均滞在の注記は当日のみのまま**
* 適用中の期間は **`PeriodBar`（タブの直下に 1 つ）と `SectionHeader` の `caption`（期間に依存する各カード）**に出す（§7.3）
* 期間の文字列は **`AnalyticsView` が 1 回だけ組み立てて配る**（§7.3.4）。タブは文字列を組み立てない
* **`aside` を上書きしない**（§7.3.3）。「すべて →」「N ページ · ページビュー順」等はいまのまま右に残る

## 7. リスクと注意点

1. **E2E は同時に 1 つしか流せない。**（実測）`playwright.config.ts` は `reuseExistingServer: !CI` で、
   `apps/web/.next/lock` を共有する。**2 つ目の `pnpm test:e2e` を並行して起動しない。**
   T9 / T10 / T12 の「全件流す」はそれぞれ**直列に**行う。前の実行が終わってから次を始める
2. **E2E を無闇に増やすと、無関係な spec が 429 で落ちる。**（実測）`apps/web/e2e/` の全ファイルが
   `GET /api/v1/auth/csrf` の Rate Limit（**300 回/60 秒・キーは `operationId:IP`**）を共有しており、
   余裕が少ない（030 の doc に「当日の 36 件だけで 40 回以上を消費し、後続の jobs / api-token / social が
   429 で落ちた」と実測が残っている）。**034 の対策**：
   * **新しく作るサイトは `periodScopeSite` の 1 つだけ。** 030 の `pristineSite` / `rolledUpTodaySite` は**読むだけ**で使い回す
   * **新しい利用者（`contextWithoutPermissions`）を作らない。** H #65 / #66 / #67 / #71 は
     030 の既存テストへ `?period=yesterday` の 1 往復を足す形にする
   * **同じ URL を見る条件は 1 本のテストにまとめる**（031 の先例）。まとめた中でも `expect` は条件ごとに分けて書く
   * 下ごしらえ（`seedAnalytics`）は `withDatabase` 経由で CSRF を消費しない。**期間の検査は DB 直挿しに寄せる**
   * T9 / T10 / T12 のあと**必ず `pnpm test:e2e` を全件**流し、`analytics.spec.ts` 以外が 429 で落ちていないかを見る。
     落ちたらテストを緩めず、**下ごしらえの共有をさらに進める**（サイトを増やす方向へは戻さない）
3. **1 日のカスタム期間で 2 区画が消えるのは、既存 E2E に当たりうる。**
   データ系の E2E の大半が `todayUrl`（`period=custom&from=今日&to=今日`）を使う。設計 §7.2 は
   「『日次の推移』と『1日あたり訪問者』の**存在**を主張しているテストは 1 つも無い」ことを確認済みだが、
   T7 のあと **`pnpm test:e2e` 全件で実地に確かめる**。落ちたら
   **「テストの前提が設計書のどこと食い違うか」を報告して止まる。E2E の期待値を勝手に緩めない**
4. **#68（昨日の集計値が 0 件）は 1 分周期のロールアップと競合しうる。** `rolledUpTodaySite` は
   今日の生ログを集計済みなので、昨日には行が無い。ただし定期実行が走るタイミング次第で
   `pending` が 0 か 1 以上かが揺れ、`receiving`（0 が並ぶ通常タブ）と `pending-rollup`（導線）の
   どちらにもなりうる。030 #63 と同じく **`.or()` で許容し、決定的な担保はユニット側で取る**
5. **`presetRange` の `null` の扱いを広げない。** `yesterday` は必ず範囲を返す。
   `ResolvedPeriod.range` の `null` は今も `month`（今日が月の 1 日）だけであり、
   T1 で分岐を足すときに `month` の条件へ手を入れない。触ると 030 #61 / #84 の空状態が壊れる
6. **`?period=yesterday` の `PeriodBar` は「昨日の日付」であって「昨日」という語ではない。**
   #44 は `data-analytics-period` が `${昨日}/${昨日}` であることを見る。E2E では
   `shiftDate(today(), -1)` で作り、**実行マシンのローカル日付を使わない**（`SERVER_TIME_ZONE` の既存ヘルパを使う）
7. **`seedAnalytics` の広げ方で本体を変えない。** key 付きの指標を入れられるようにするのは
   **E2E の補助関数だけ**（設計 §11 #5）。`apps/web/src/` に差分が出たら設計違反として止まる。
   主キー `(site_id, metric_date, source, metric, key)` の重複に注意する（同じ (metric, key) を 2 回入れない）
8. **`aside` を消さない。** 設計 §7.3.3 は「`aside` を上書きしない」と明示している。
   F #47〜#50 はそれぞれ別のタブの `aside` が残ることを見ており、**1 つでも消えたら落ちる**ように書く。
   例外は「日次の推移」の `aside`（期間）だけで、これは `caption` へ**移す**（#52 で 2 回出ないことを見る）
9. **期間の文字列は 1 回だけ組み立てる。** `AnalyticsView` が `appliedPeriodText` を 1 回呼び、
   タブへは組み立て済みの文字列を配る（§7.3.4）。**タブの中で `appliedPeriodText` を呼ばない**。
   呼ぶと「数を計算しない・並べるだけ」（028 §7.3.6）が崩れ、期間の表し方を変えるときに触る場所が増える
10. **`PeriodBar` の出し分けを画面の中に散らさない。** `shouldShowPeriodBar` に閉じる（§8 #2）。
    散らすと `empty-period`（実行日が月の 1 日でないと E2E で作れない）の分岐を決定的に確かめられなくなる
11. **静的検査に寄せた条件は「実行時に見られない」ものだけにする。** (a)〜(e) は
    「描く箇所が 1 つだけ」「分岐の根拠が `days` である」「import が消えた」といった**構造**の話で、
    描画からは見分けられない。値や文言の検査を静的検査へ逃がさない
12. **SaaS 固有機能への踏み込み：無し。** 期間の保存・共有・テナントごとの既定値といった話は
    設計 §3 が明示的に除外している。プランでも足さない
13. **公開リポジトリである。** コミットメッセージ・コードコメント・設計書のいずれにも、
    特定の導入環境やテスト実行環境の接続情報（DB の URL・鍵）を書かない。
    §2 に挙げた env はプランの手順であって、リポジトリへ入れる値ではない
14. **ブランチは `feature/034-analytics-period-scope`**（要件 §3.3。`main` から分岐済み）。
    **`main` へ直接プッシュしない。** 各タスク＝1 コミットで、G1〜G5 の区切りごとにプッシュする
