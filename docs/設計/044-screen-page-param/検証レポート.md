# 044 画面の `?page=` の読み取りの修正 検証レポート

`043` のセキュリティ検証（低-1、範囲外）で見つかった「画面の URL の `?page=` に `Infinity`・小数・巨大な値を付けると、その利用者の画面が 500 になる」を直した作業単位。
**ユーザー裁定（2026-09-24）「直す」。**

実装完了時点（`a8b8d0e`）に対し、2 つの検証エージェントを**互いの結果を見せずに独立して**走らせた。

| 担当 | 判定 |
| --- | --- |
| `spec-verifier`（設計との整合） | **合格**（「マージしてよい」。軽微 3、いずれも記録のみ） |
| `security-reviewer`（セキュリティ） | **合格**（重大・高・中・低 0。情報 2） |
| `boundary-guardian` | **回していない**（レイヤの問題が出なかったため。`app/` から `domain/` への依存は既存） |

ユニット・結合 **9,345 件全通過**、typecheck / lint / format:check / `next build` 通過。
E2E は全件 **494 件通過**（作業機のポート 3000 が別のアプリに使われているため Playwright のコンテナで流した。`039` §8 #35 の手順）。

---

## 1. 直したもの

`domain/repository.ts` に `normalizePage` を足し（`normalizePagination` の `page` の部分を切り出したもの。振る舞いは変えていない）、
URL の `page` を読む 6 画面をこれに揃えた。有限の数でなければ 1、小数は切り捨て、1〜`Number.MAX_SAFE_INTEGER` に丸める。

| 画面 | 変更前 | 変更後 |
| --- | --- | --- |
| `/sites`・`/campaigns`・`/settings?tab=users`・`/social/history`・`/social`（`postPage`） | `Infinity`・`1.01`・`1e18` などで 500 | 1 ページ目か、丸めたページ（最後のページより先なら空）を 200 で返す |
| `/analytics` の表（ページ・参照元） | `Infinity`・小数は 1 になっていたが、`1e18` のような巨大な整数で 500（設計で推定し、テストで実際に確かめた） | 同上 |

設計の段階で、依頼にあった 5 画面のほかに `/analytics` の表が同じ問題を持つことが分かり、裁定の「同じ読み方の画面がほかにあれば含める」に従って含めた。
画面の `perPage` とページ送りの部品は変えていない（100 を超える値を意図して使う画面があるため）。

## 2. 検証で確かめたこと

* `spec-verifier` は全件のテストを流し、**10 通りの変異をすべて検出**した（有限かの検査・切り捨て・上限を外す、画面を `Number(...)` に戻す、`normalizePagination` の振る舞いを変える、`/analytics` を元に戻す）。
  上限を外す変異では、結合テストで PostgreSQL が bigint の範囲外として実際に拒否した
* 25 の画面と UI の部品を検索し、URL のクエリを数に変える画面が今回の 6 か所のほかに無いことを確かめた
* `security-reviewer` は、6 画面と `/analytics` の DB 経由・メモリ上の両経路で 500 の経路が塞がったこと、OFFSET の最大（約 4.5×10^17）が int64 に収まること、
  ほかのクエリ（`tab`・`status`・`siteId`・`period` など）が照合か検査を通っていることを確かめた。**テストは実行していない**
