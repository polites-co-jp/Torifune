## 6. 影響範囲

* **画面**：6 画面で `?page=`（`/social` は `?postPage=`）の範囲外の値が 500 でなく 200 になる。正しい値（1 以上の整数）の振る舞いは変わらない

## 7. リスクと注意点

1. **`normalizePagination` を書き換えるときの振る舞いの変化**：`page` の式を `normalizePage` の呼び出しに替えるだけにする。`integerOr` と `perPage` の式は触らない。既存の `normalize-pagination.test.ts` が緑であることで確かめる
2. **#18 の正規表現の過不足**：`params['tab']` などの `page` を含まないキーは対象外、`postPage` は対象になる。コメントを除いてから走査する（`withoutComments` を写す）。検査が 1 件も当たらなければ失敗させる（空振りで緑にしない。`normalizePage(` の出現が 6 以上あることも見る）
3. **D の #16 の準備**：既定の期間（`30d`）では今日のヒットだけのサイトは表を読まない（設計 §10.3 #16）。`period=custom&from=今日&to=今日` と `rollupToday` を使う。`analytics.spec.ts` の関数は import せず写す
4. **E2E の共有 DB**：他の spec が作った行が残る。#11 は作ったサイトの名前に一意の接尾辞を付け、1 ページ目は `created_at` の降順で先頭に来ることを使う
5. **`/analytics` の `asString` を消さない**：`tab`・`siteId`・`bots` が使っている。消すのは `parsePage` だけ
