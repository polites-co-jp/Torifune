### 確定事項（設計書から。プランで蒸し返さない）

* **ユーザー裁定（2026-09-23）：Core も直す**（`037` §11 #15）。**`credentialFields[].description` の表示も本件に含める**（初版 §11 #1 の (a)）
* **変えるのは Core の画面**：`app/social/page.tsx`、`ui/social/`（新規 2 ファイル＋`social-accounts.tsx`＋`labels.ts`）、`ui/components/overlays.tsx` の `SecretField`（設計 §4）
* **と、配信ジョブの `rotatedCredential` の書き戻し**（2026-09-23 改訂。ユーザー裁定「`035` §11 #25 を 039 で直す」）：`application/social/publish.ts`、`domain/social/social.ts`、`domain/social/social-repository.ts`、`infrastructure/social-repository.ts` の 4 ファイルだけ（設計 §4 / §6.1）
* **`packages/plugin-api`・`migrations`・`/api/v1`（`app/api/`）は 1 行も変えない。** Application は `publish.ts` だけ（UseCase の `social-use-cases.ts` は変えない）、Domain / Infrastructure は SNS の型と Repository の 3 ファイルだけ（設計 §3.2 / §4 / §5 / §6 / §9。#43 で確かめる）
* **比較更新**：書き戻しは「配信の前に読んだ暗号文（`credentialVersion`）」と DB の `credential` が同じときだけ、1 文の `UPDATE … WHERE id = ? AND credential = ?`（`replaceCredentialIfUnchanged`）。`updated_at` を版に使わない。`credentialVersion` は `PublishInput` に入れない・復号しない・ログ／監査／summary に載せない（設計 §6.1）
* **書き戻しを捨てても・失敗しても投稿の結果は変えない。** 例外は `rotateCredential` の中で受け止める（`unrecorded` にしない）。監査 `rotated: true` は書き戻したときだけ（設計 §6.1 の 4・5）
* **`credentialFields: []` の publisher が返した `rotatedCredential` は捨てる**（設計で「オーケストレーターの判断」とされ、**2026-09-23 に承認済み**。設計 §6.1 の 4）
* `SecretField` の password の入力は両方の枝で **`autoComplete="new-password"`**（オーケストレーターの判断。設計 §7.1.3）。`kind: 'text'` の `Input` は `off` のまま
* **部品が送る本文は `buildCreateAccountRequest` / `buildSetCredentialRequest` / `buildClearCredentialRequest` だけを通す**（設計 §7.7.1。名前はテストが import するので設計のとおり）。部品は `createCredentialBody` / `setCredentialBody` / `clearCredentialBody` を直接呼ばない（#74）
* **画面はサーバの `message` を出さない**（`apiRequest` の `messageFor` の固定文言。設計 §6 の 2026-09-23 訂正）。本プランの T13 の「応答の `message`」は、この固定文言を指すと読み替える（§8 の 23）
* 入力の形は 3 つ：`fields`（publisher あり・項目あり）/ `none`（publisher あり・`[]`）/ `free`（publisher なし）。判定は `credentialInputOf` の表のとおり（設計 §7.1）。**`publisherRegistered` の省略は `false`**（後方互換）
* **`none` のアカウント追加は資格情報を送らず `status: 'connected'`**（オーケストレーター承認、2026-09-23。設計 §7.2）
* 入れ直しは既存の `PATCH /api/v1/social/accounts/{id}`。**丸ごと置き換え**。`fields` は宣言のキーちょうど、全項目必須。消去は `{ credentials: {} }`（`fields` / `free` は `status: 'disconnected'` を添え、`none` は `status` を送らない）（設計 §6 / §7.3 / §7.4）
* **保存済みの値は読まない・表示しない。** Modal は開くときに要求を出さず、欄は常に空で始まる（設計 §7.3.1 / §7.3.2）
* 投稿一覧の Badge は **`router.refresh()`** で追従させる。部品同士で状態を持ち回る仕組みは足さない（設計 §7.3.4）
* `description` は `fields` の欄の下にテキストとして出す。`SecretField` に省略できる `description?` を足し、**省略したときの HTML は現行と同じ**（設計 §7.1.2）
* ファイル名・関数名（`credential-form.ts` / `provider-options.ts`、`credentialInputOf` / `createCredentialBody` / `setCredentialBody` / `clearCredentialBody` / `buildProviderOptions`）は**設計のとおり**（テストが import する。設計 §7.7）
* 文言は `labels.ts` に置き、部品に直書きしない（設計 §7.8。#46）
* **新しい Permission を作らない。** 表示は `social.write`、認可・CSRF・監査は既存の `PATCH` の経路（設計 §8）
* **E2E で `none` を見ない**（`sns-x-*` を E2E で導入しない。`example-plugin` に `[]` の publisher を足さない。設計 §10.7 の注）
* 検証は **`spec-verifier` / `boundary-guardian` / `security-reviewer` の 3 つ**を回す（Core を変えるため。設計 冒頭）
* **SaaS 固有機能（テナント・課金・コンテナ管理）に触るタスクは本プランに無い**

## 3. タスク分解

原則：**1 タスク = 1 コミット**。各タスクは「テストを書いて失敗を確認 → 実装 → 通す」の順。
各まとまり（G1〜G11）の最後で `pnpm test` / `pnpm typecheck` / `pnpm lint` / `pnpm format:check` が通る。
E2E（`pnpm test:e2e`）は **G5 の終わり・T16・T25** で全件流す。

> **2026-09-23 の改訂。** G1〜G7 は済み（§1 の「進捗」）。設計 `efee288` で足した #55〜#74 と書き戻しを **G8〜G10** に、処置後の最終確認と 3 つの検証のやり直しを **G11** に置いた。
> **G8（配信ジョブ）と G9（画面）は互いに依存しない**ので、どちらから着手してもよい。G10 は G8・G9 の後、G11 は最後。

**test-writer → implementer への受け渡しの単位は G（まとまり）。** test-writer は G の中の全タスクのテストを先に書いて失敗を確かめてコミットし、implementer が G の中のタスクを順に通す。
**implementer はテストを書き換えない。** テストが設計と食い違うと判断したら、設計書のどこと食い違うかを報告して止まる。

**着手順の骨子**：純関数（判定と本文）→ その本文を API と登録簿に通す結合（既存の API の挙動を固定する）→ `SecretField` の説明 → 部品の描画 → Server Component と画面の動作（E2E）→ 文書の書き戻しと `037` の検査の書き換え → 最終確認と 3 つの検証。
