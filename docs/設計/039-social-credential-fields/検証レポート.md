## 2. 見つかった欠陥と処置

### 1. 配信の後の書き戻しで、投稿済みが `failed` になる経路（設計の段階で発見）

`035` §11 #25 を設計する途中で見つかった。書き戻しが例外を投げると、その投稿は記録されないまま（`unrecorded`）になり、
次の実行で「中断」として `failed` になる。**実際には投稿済みなので、運用者が出し直すと二重投稿になる。**

**処置**：例外は `rotateCredential` の中で受け止め、`log.error`（SQLSTATE だけ。例外の文言は載せない）にする。投稿は `published` と記録される（#61）。
2 回目の検証で、**`try` の外に残っていた経路**（宣言との突き合わせと `JSON.stringify` が `try` より前にあった。型に反した値、例えば `1n` を返す Plugin で抜ける）が見つかり、
関数の本体全体を受け止める範囲に広げた（#75。直す前は 10 件が落ちることを確かめた）。

### 2. 無料版（`none`）のときに画面が送る本文がどの層でも固定されていなかった（1 回目 spec 中-1）

関数単体と描画はテストされていたが、「部品が正しい形でその関数を呼ぶ」ことを見るテストが無かった。
`none` を `free` として送る変異、消去を `fields` 固定にする変異が、全件緑のまま生き残った。

**処置**：本文の組み立てを `buildCreateAccountRequest` / `buildSetCredentialRequest` / `buildClearCredentialRequest` の純関数に寄せ、部品はそれを呼ぶだけにした（#67〜#71）。
静的検査で、部品が低水準の関数を直接呼ばないこと（#74）と、第 1 引数が `props.providers` そのままであること（2 回目 軽微-2）を固定した。

### 3. 資格情報の欄をパスワードマネージャーが埋める（1 回目 security 低-1）

`autocomplete="off"` は password の欄では無視され、**Torifune のログインパスワードが SNS の資格情報の欄に自動入力されうる**。
気づかず保存すると、配信のたびに Torifune のパスワードが外部の SNS へ送られる。

**処置**：`SecretField` の 2 つの枝とも `new-password`（既存の設定画面と同じ）。#47 は 039 より前の HTML を文字列として固定し、この 1 属性の違いだけを許す（1 回目 spec 軽微-2 の処置を兼ねる）。

### 4. テストの前提が DB の制約と矛盾していた（実装中に発見）

#64 の「列が `''` のとき」の 1 件は、テスト自身の INSERT が `migrations/005` の CHECK で落ち、実装をどう変えても通らなかった。
`''` は DB に書けないので、実装の `''` の分岐は防御のためのコードで、到達を確かめられない。**到達できない分岐を検証済みと名乗らせない**方針で外した（`c742205`）。

## 4. 検証の方法

* `spec-verifier` は 2 回とも全件のテストを流し、変異を入れて判別力を確かめた。
  2 回目は比較更新の条件を消す・捨てたときに監査を書く・例外を投げ直す・`[]` の分岐を消す・autocomplete を戻す、などすべてが検出された。
  生き残ったのは部品が選択肢を書き換える作為的な変異 1 つで、処置した（§2 の 2）
* `boundary-guardian` と `security-reviewer` は**テストを 1 本も実行していない**（DB の競合を避けるため）。判定はコードの読解に基づく
* `security-reviewer` は競合が閉じたことを、1 文の UPDATE と PostgreSQL（READ COMMITTED）の再評価の挙動、IV が毎回変わる暗号文、`credential` を書くほかの経路（2 つ。どちらも比較を迂回しない）から確かめた
* 2 回目の後の処置（#75、#74 の引数、文書）の後に検証は回し直していない。#75 は直す前に落ちることを、#74 は書き換えた写しで落ちることを、処置した側が確かめた
