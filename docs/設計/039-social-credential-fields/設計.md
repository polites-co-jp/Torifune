## 1. 目的

`/social` の SNS アカウントの資格情報について、次の 2 つを直す。

1. **資格情報を使わないと宣言した配信 Plugin の provider で、資格情報の欄を出さない。**
   いまは `credentialFields: []` を宣言した publisher（例：`sns-x-manual`）でも、アカウント追加の画面に
   汎用の欄「資格情報（アクセストークン等）」が出る。ここへ入れた値は保存されるが**どこからも読まれない**（§2.1 の 3）。
   そのうえ後で同じ provider の別の Plugin（例：`sns-x-api`）へ入れ替えると「資格情報 設定済み」と扱われ、
   形が合わないので自動の予約は「未設定」で待たずに**直ちに `failed`** になる（`037` 設計 §7 の注）
2. **既存のアカウントの資格情報を画面で入れ直せる・消せるようにする。**
   いまは `PATCH /api/v1/social/accounts/{id}` でしか入れ直せない。`037` の無料版 → 有料版の入れ替え（`037` §7.2 の 4）、
   Instagram のトークンの失効（`038`）、Plugin を後から入れたアカウントの形の食い違い（`035` §5.7）の直し方が、
   どれも画面では完結しない

どちらも「画面で見えている資格情報の状態と、配信が実際に使う資格情報を食い違わせない」ためのものである。

## 3. スコープ

### 3.1 やること

* **資格情報の入力の形（以下「入力の形」）を provider ごとに 3 つに分ける**（§7.1）
  * `fields`：publisher が登録されていて `credentialFields` が空でない → 項目ごとの欄
  * `none`：publisher が登録されていて `credentialFields` が空 → **欄を出さない**
  * `free`：publisher が登録されていない → 従来どおり汎用の欄 1 つ（§7.1.1 で残す理由）
* アカウント追加の Modal を入力の形に従わせる（`none` では欄を出さず、資格情報を送らない。§7.2）
* アカウントの行に「資格情報を設定」を足し、**既存のアカウントの資格情報を入れ直す・消す** Modal を作る（§7.3〜§7.5）。
  送り先は既存の `PATCH /api/v1/social/accounts/{id}`
* 保存・消去の後、投稿一覧の「資格情報 未設定」の Badge が画面の再読み込みなしで追従する（§7.3.4）
* **publisher が宣言した `credentialFields[].description` を、アカウント追加と入れ直しの両方で欄の下に出す**（ユーザー裁定。§7.1.2）
* **配信ジョブの `rotatedCredential` の書き戻しを比較更新にする**（`035` §11 #25。ユーザー裁定。§6.1）
* `SecretField` の入力を `autoComplete="new-password"` にする（§7.1.3）
* 部品が送る本文を、`providers`・対象・入力値から本文を返す純関数に寄せる（§7.7。039 の検証 spec 中-1）
* `037` の 2 つの README と `037` 設計の該当箇所、関連する文書を画面の手順に書き換える（§12）

## 6. API

**新しいエンドポイント・項目は作らない。API Version（`v1`）・OpenAPI は変わらない。**

画面が送る要求は次の 3 通りで、どれも既存の `PATCH /api/v1/social/accounts/{id}`（`035` §6.4）で受けられる。

| 操作 | 本文 | 期待する応答 |
| --- | --- | --- |
| 入れ直す（`fields`） | `{ "credentials": { <宣言のキーすべて>: "…" }, "status": "connected" }` | 200。`credentialConfigured: true` |
| 入れ直す（`free`） | `{ "credential": "…", "status": "connected" }` | 200。同上 |
| 消す（`fields` / `free`） | `{ "credentials": {}, "status": "disconnected" }` | 200。`credentialConfigured: false` |
| 消す（`none`） | `{ "credentials": {} }` | 200。`credentialConfigured: false`（`status` は変えない。§7.4） |

エラーは既存のまま：宣言と合わない `credentials` は 422（`details.credentials`。**API の応答の** `message` / `details` にはキー名が入る）、4096 文字超は 422、
`social.write` なしは 403、未認証は 401、CSRF なしは 403（`CSRF_FAILED`）、無い ID は 404。

**画面はサーバの `message` を出さない。** `apiRequest` は失敗のとき `code` ごとの固定の文言（`messageFor`）を返す（§2.1 の 13。
内部の事情が混ざった文言を画面へ出さないための既存の約束）。Modal の中に出るのはその文言で、422 なら「入力内容を確認してください。」である。
**キー名は画面に出ない。** これを変えない（2026-09-23 に訂正。初版は「画面は 422 の `message` を出す」「キー名が文言に出る」と書いていた。039 の検証 security 情報-1）。

> `fields` の本文は**画面を描いた時点の宣言**で組む。描いてから保存までに Plugin が入れ替わると、
> サーバはいまの宣言と突き合わせて 422 を返し、画面には「入力内容を確認してください。」が出る。画面を開き直せば新しい宣言で出る（§11 のリスク 2）。

### 6.1 配信ジョブの `rotatedCredential` の書き戻しを比較更新にする（ユーザー裁定 2026-09-23。`035` §11 #25）

**直すこと。** `rotateCredential`（`application/social/publish.ts`）は、Plugin が返した `rotatedCredential` を `WHERE id = ?` だけで書き戻す（§2.1 の 12）。
配信が飛んでいる間（最悪 30 秒）に運用者が資格情報を差し替える・消すと、その後に配信が成功して書き戻しが走り、
**配信の前に読んだ古い資格情報から作った値が運用者の変更を上書きする**（`035` §11 #25。`038` の延長が最初の利用者）。
039 で画面から入れ直し・消去ができるようになり、この重なりは起きやすくなる。

**決めたこと**

1. **比べる値は「配信の前に読んだ暗号文」そのもの。** 書き戻しは、DB の `social_accounts.credential` が読んだときの暗号文と**同じときだけ**行う（比較更新）。
   `updated_at` を版に使わない：
   * `updated_at` は表示名・ハンドル・状態の変更でも動く。資格情報に触れない変更で書き戻しを捨てることになる
   * 書き込み側の精度が揃っていない（挿入は DB の `now()`、更新は JS の `Date`）。読んだ値と等値で比べると、一致すべきときに一致しないことがある
   * 暗号文は IV を毎回変えて作る（`infrastructure/crypto/cipher.ts`）ので、**運用者が同じ値を入れ直しても暗号文は変わる。** 比べて違えば、
     運用者が触ったことが確実に分かる（同じ値の入れ直しでも書き戻しは捨てる。運用者の操作を優先する）
2. **Repository の口を 1 つ足す（Infrastructure の変更が要る）。** 既存の口では書けない：`findAccountWithCredential` は復号した `Secret` しか返さず読んだ暗号文が
   Application に渡らない。`updateAccount` は `WHERE id = ?` だけで条件を足せない。

   ```ts
   // domain/social/social.ts
   export interface SocialAccountWithCredential extends SocialAccount {
     readonly credential: Secret | null;
     /**
      * 読んだ時点の資格情報の版（039 設計 §6.1）。比較更新にだけ使う不透明な値で、中身は保存されている暗号文。
      * **復号しない・ログ／監査／summary／Plugin へ渡さない。** 保存されていなければ null。
      */
     readonly credentialVersion: string | null;
   }

   // domain/social/social-repository.ts
   /**
    * 資格情報を、保存されている版が expectedVersion のときだけ置き換える（039 設計 §6.1）。
    * 置き換えたら true。版が違う（その間に人が変えた・消した）、アカウントが無い、id の形が不正なら false で、何も変えない。
    */
   replaceCredentialIfUnchanged(
     connection: Connection,
     id: string,
     expectedVersion: string,
     encryptedCredential: string,
   ): Promise<boolean>;
   ```

   実装は 1 文の `UPDATE social_accounts SET credential = <新>, updated_at = <今> WHERE id = <id> AND credential = <expectedVersion>` で、
   更新行数が 1 なら `true`。1 文なので読みと書きの間に他の書き込みが割り込まない（別のトランザクションやロックは要らない）。
   `credentialVersion` は `findAccountWithCredential` が同じ行から読んだ暗号文を載せる（**復号に失敗した場合も載せる**。ただしその場合は配信に進まない）
3. **`resolveCredential` が版を持ち回る。** 戻り値の `ok: true` に `version`（`credentialVersion`）を足し、`publishOne` が `rotateCredential` に渡す。
   **`publish()` に渡す `PublishInput` には入れない**（`035` §6.5.5 の「渡す形」を変えない）
4. **`rotateCredential` の手順**（上から順。どこで止まっても**投稿の結果は変えない**）：

   | 条件 | 動き | 監査（`rotated: true` の `updated`） | ログ |
   | --- | --- | --- | --- |
   | publisher の `credentialFields` が空 | 書かない | 出さない | `log.warn('rotated credential ignored for publisher without credential fields', { accountId, pluginId })` |
   | 宣言と合わない・4096 文字超 | 書かない（現行） | 出さない | 現行の `log.warn` |
   | 読んだ版が `null` | 書かない（`credentialFields` が空でなければ未設定は a で飛ばしてあり、通常は起きない） | 出さない | `log.warn('rotated credential was discarded', { accountId, pluginId })` |
   | `replaceCredentialIfUnchanged` が `true` | 書き戻した | **出す**（現行の形 `{ changed: ['credential'], rotated: true, pluginId }`） | — |
   | 同 `false` | **捨てる** | **出さない**（何も変わっていない。運用者の変更は、その要求の監査 `updated` が既に残している） | `log.warn('rotated credential was discarded because the account credential changed during publish', { accountId, pluginId })` |
   | 同が例外を投げた（DB の障害など） | 捨てる | 出さない | `log.error('rotated credential could not be saved', { accountId, pluginId, code })`（`code` は例外に SQLSTATE があればそれだけ。**例外の文言は載せない**。DB のエラーの文言は SQL の値を含みうる） |
   | 上のどの手順でも例外が出た（型に反する `rotatedCredential` で突き合わせ・JSON 化が投げる、暗号化が投げるなど。2026-09-24 に追加） | 捨てる | 出さない | 1 つ上の行と同じ `log.error`（例外の文言は載せない） |

   * **ログ・監査・`summary` に載せるのは `accountId` / `pluginId`（と SQLSTATE）だけ。** 資格情報の値・暗号文・版を載せない
   * **例外を `rotateCredential` の中で受け止める。** いまは例外が `publishOne` の外へ出て、その行は `unrecorded` になり、投稿は着手印が立ったまま残って
     次の実行で「中断」として `failed` になる（`publish.ts` の `publishDuePosts` が `publishOne` の例外を受け止めて `unrecorded` に数え、次の実行の冒頭の中断行の処理が `failed` に落とす）。**実際には投稿されたのに `failed` と記録され、出し直すと二重投稿になる。**
     書き戻しは投稿の結果の付け足しであって、失敗しても投稿の記録を止めない
   * **2026-09-24 追記（039 の検証 2 回目 軽微-1）：受け止める範囲は `rotateCredential` の本体全体である。** 宣言との突き合わせ・`JSON.stringify`・長さの確認・
     暗号化・比較更新・監査のすべてを 1 つの `try` の中に置く（実装プラン §8 の 28 を広げた）。Plugin は JavaScript なので、型の上では `Record<string, string>` の
     `rotatedCredential` が、実際には型に反する値（`BigInt` の値、読むと投げる getter など）を持ちうる。突き合わせや JSON 化がそれで投げると、例外が `publishOne` の外へ出て
     上と同じく `unrecorded` → 次の実行で「中断」の `failed` → 出し直して二重投稿、になる。どこで投げても表の最後の行のとおり、書かず・監査を出さず・
     例外の文言を載せない `log.error` を 1 回出して、投稿の記録へ進む（#75）
   * **`credentialFields` が空の publisher の `rotatedCredential` は捨てる**（これまでは宣言との突き合わせが常に通り、何でも保存された）。
     `[]` は「資格情報を使わない」宣言で（§7.1）、読まない値を保存すると本設計の問題 1 と同じ食い違いを作る。比べる版も読んでいない。
     `036` / `037` / `038` にこの形の Plugin は無い
5. **配信の結果は変えない。** `published` の投稿は、書き戻しを捨てても・失敗しても `published` と記録される。順序（書き戻しを投稿の書き戻しより先に、
   別に行う。`035` §6.5.6）も変えない
6. **マイグレーションは要らない。** 既存の `credential`（`text`）の等値比較と主キーで書ける（§5）

**捨てた値のその後。** 捨てた `rotatedCredential`（例：延長した Instagram のトークン）は保存されない。運用者は自分の値に置き換えた・消したので、それが正である。
延長で古いトークンが失効する SNS では、延長前のトークンで投稿し続けることは無い（運用者の値が使われる）。

## 7. 画面

### 7.1 入力の形（`credential-form.ts` の `credentialInputOf`）

`ProviderOption`（`social-accounts.tsx`）に**省略できる**項目を 1 つ足す。

```ts
export interface ProviderCredentialField {
  readonly key: string;
  readonly label: string;
  readonly kind: 'text' | 'secret';
  /** publisher が宣言した説明。欄の下に出す（039 設計 §7.1.2）。省略・空文字なら出さない。 */
  readonly description?: string;
}

export interface ProviderOption {
  readonly value: string;
  readonly label: string;
  readonly credentialFields: readonly ProviderCredentialField[];
  /** この provider に publisher が登録されているか。省略は false（039 設計 §7.1）。 */
  readonly publisherRegistered?: boolean;
}

export type CredentialInput = 'fields' | 'none' | 'free';

/** provider の入力の形。option が無い（一覧に無い provider）ときは 'free'。 */
export function credentialInputOf(option: ProviderOption | undefined): CredentialInput;
```

| 条件（上から順に判定） | 入力の形 |
| --- | --- |
| `option` が無い（アカウントの provider が選択肢に無い） | `free` |
| `credentialFields.length > 0` | `fields` |
| `publisherRegistered === true` | `none` |
| それ以外 | `free` |

* **省略を `false` と読むのは後方互換のため。** 既存の単体テストの `ProviderOption`（`{ value: 'x', credentialFields: [] }`）は
  いままでどおり `free`（汎用の欄）の意味のまま通る
* `buildProviderOptions`（`provider-options.ts`）は、`KNOWN_PROVIDERS` と登録簿の provider を合わせた一覧に対し、
  登録簿にある provider では `publisherRegistered: true` と宣言の項目（`key` / `label` / `kind` / `description`、宣言の順。`placeholder` は持ち込まない）を、無い provider では
  `publisherRegistered: false` と `[]` を持たせる。並びと `label` の決め方は現行（`page.tsx` L120-139）と同じ

#### 7.1.1 「publisher が無い」ときに汎用の欄を残す（決めたこと）

**残す。** `none` と同じく出さない案は採らない。

* **「無い」は「要らない」ではない。** Plugin を入れる前にアカウントを作るのは正しい運用で（`035` §6.4 の「publisher が無い → そのまま保存」）、
  そのとき Core にはどの形が要るかが分からない。`[]` の宣言は「要らない」と Plugin が**明示した**ときだけ成り立つ
* 外部アプリ（API）や、Plugin を使わない運用で資格情報を預けている利用者がいる（`035` §3.1 以前からの `credential`）。
  画面から預ける口を消すと、その運用の画面の経路が無くなる
* 後から Plugin を入れて形が合わなかった場合の直し方が、本設計で**画面にできる**（§7.3）。`035` §5.7 が「登録し直せば直る」とした
  直し方が、アカウントを消さずに行えるようになる
* 既存の E2E（`035` #76「provider `x` では汎用の欄が出る」。E2E は X の Plugin を有効にしない）がそのまま通る

形の食い違いを減らすため、**入れ直しの Modal の `free` には「形式を確かめずに保存する」ことを書く**（§7.3.2）。
アカウント追加の `free` の欄の見た目は変えない。

#### 7.1.2 項目の説明（`description`）を欄の下に出す（ユーザー裁定 2026-09-23）

`fields` の各項目に `description` があれば、**アカウント追加と入れ直しの両方で、その欄の下に説明として出す。**
Plugin 作者はここに「どこで発行するか」「どの権限で発行するか」を書いている（§2.1 の 10）。入力の時点で読めないと、
X では読み取り専用のトークンを入れて配信が 403 で落ちる。

* `kind: 'text'`：既存の `FormField` の `description` に渡す（`aria-describedby` で入力と結ばれる。既存の部品の挙動）
* `kind: 'secret'`：`SecretField` に**省略できる** `description?: string` を足し、ラベルの下・入力の上（`FormField` と同じ位置と見た目）に出して
  `aria-describedby` で入力と結ぶ。**省略したときの HTML は現行と同じ**にする（既存の呼び出し元の見た目を変えない。ただし `autocomplete` の値は §7.1.3 で変える）
* `description` が無い・空文字のときは説明の要素を描かない（空の要素や `aria-describedby` の空参照を残さない）
* 文字列はそのまま**テキストとして**描く（HTML として解釈しない。React の既定のエスケープ）。Plugin は信頼されたコードだが、
  説明に HTML を通す理由が無い
* `free`（汎用の欄）と `none` には `description` が無い（宣言が無い・空）ので出るものは無い
* Core は `description` の中身を検査・加工しない（長さの上限も置かない。宣言は Plugin のコードにある固定の文字列）

#### 7.1.3 `SecretField` の入力を `autoComplete="new-password"` にする（2026-09-23。039 の検証 security 低-1）

`SecretField` の `type="password"` の入力は、いま `autoComplete="off"` である（説明の有無の両方の枝）。Chrome などは password の欄で `off` を無視するため、
**Torifune のログインのパスワードが SNS の資格情報の欄へ自動で入る**、また**入れた SNS のトークンがブラウザのパスワードマネージャーに保存される**ことがある。
既存の前例（`ui/plugin/plugin-settings-form.tsx` L109 の `secret`、`ui/settings/user-list.tsx` L298）に揃え、**両方の枝で `autoComplete="new-password"`** にする。

* 変えるのはこの 1 属性だけ。`kind: 'text'` の欄（`Input`、`autoComplete="off"`）は変えない（password の欄ではなく、前例も `off`）
* これにより「`description` を省略したときの HTML は現行と同じ」（§7.1.2）は、**`autocomplete` の値の 1 か所を除いて同じ**に改める（#47）

### 7.2 アカウント追加（`social-accounts.tsx` の追加の Modal）

| 入力の形 | 欄 | 送る資格情報 | 送る `status` |
| --- | --- | --- | --- |
| `fields` | 項目ごと（現行）。**`description` があれば欄の下に出す**（§7.1.2） | `credentials`（入れた項目だけ。現行） | 1 つでも入れたら `connected`、無ければ `disconnected`（現行） |
| `free` | 「資格情報（アクセストークン等）」1 つ（現行） | `credential`（現行） | 入れたら `connected`、空なら `disconnected`（現行） |
| **`none`** | **出さない。** 代わりに 1 行の説明「この SNS の配信 Plugin は資格情報を使いません。入力は要りません。」 | **`credential` も `credentials` も送らない** | **`connected`** |

* **`none` の `status` は `connected`（確定。2026-09-23 にオーケストレーターが承認）。** 理由：
  * アカウント追加の `status` は「配信に要る資格情報が揃ったか」を表している（§2.1 の 9）。要らない provider では追加した時点で揃っている
  * いまの挙動（`disconnected`＝「未接続」）は、手動投稿が問題なく動くのに一覧が「未接続」と出て、**利用者に「何かが足りない」と誤解させる**
  * `status` は表示のための列で、配信の判定（`publishDuePosts`）は見ていない。`connected` にしても配信の挙動は変わらない
* 「サービス」を切り替えたら入力値を捨てる（現行）。`fields` / `free` → `none` に切り替えた後で、前の入力が送られてはならない
* 本文の組み立ては `credential-form.ts` の `createCredentialBody` に出す（§7.7）

### 7.3 入れ直し（行の「資格情報を設定」と Modal）

#### 7.3.1 入口

* アカウント一覧の「操作」列に、`social.write` を持つときだけ **「資格情報を設定」**（`variant="ghost"`）を出す。並びは「資格情報を設定」「削除」の順
  （「削除」は現行どおり `social.delete`）
* `social.read` だけの利用者には出ない。**表示制御であって認可ではない**（`06` §29）
* 列の幅は 2 つのボタンが収まるように広げる。狭い画面では表の中で横に動く（`.tf-table-scroll`。ページ全体は横に動かない）
* 押すと Modal が開く。**開くときに要求を出さない**（状態は一覧が持つ `credentialConfigured` を使う。資格情報は読まない）

#### 7.3.2 Modal の中身

タイトルは固定の **「資格情報を設定」**。本文の先頭に対象を出す：「対象：<表示名>（<サービスの表示名>）」、
続けて **「現在の状態：設定済み」** または **「現在の状態：未設定」**（`credentialConfigured` から）。

| 入力の形 | 説明（`Alert tone="info"`） | 欄 | ボタン |
| --- | --- | --- | --- |
| `fields` | 「保存済みの値は表示しません。保存すると、保存済みの資格情報はすべてここで入力した値に置き換わります（一部の項目だけを変えることはできません）。」 | 宣言の順に項目ごと。`kind: 'text'` は `Input`（`autoComplete="off"`）、`'secret'` は `SecretField`（`configured={false}`）。**すべて空で始まる。** 各項目の `description` を欄の下に出す（§7.1.2） | 「資格情報を消す」（設定済みのときだけ）／「キャンセル」／「保存」 |
| `free` | 「この SNS の配信 Plugin が有効になっていないため、入力した値を形式を確かめずにそのまま保存します。配信 Plugin を有効にした後は、その Plugin の項目で入れ直してください。」 | 「資格情報（アクセストークン等）」の `SecretField`（`configured={false}`）1 つ | 同上 |
| `none` | 「この SNS の配信 Plugin は資格情報を使いません。入力は要りません。」 | **出さない** | 「資格情報を消す」（設定済みのときだけ）／「閉じる」 |

`none` で**設定済み**のときは、説明の下に `Alert tone="warning"` を足す：

> 保存済みの資格情報がありますが、いまの配信 Plugin では使われません。
> 同じ SNS の別の配信 Plugin に入れ替えるとその Plugin が読み、形式が合わなければ自動配信が失敗します。不要なら消してください。

* 項目ごとの状態（どの項目が入っているか）は**出さない。** 保存は丸ごと 1 つの暗号文で、Core は項目ごとの状態を持たない（`035` §5.7）
* `SecretField` を `configured={false}` で使うのは、欄を常に空の入力欄として出すため（「••••」＋「変更する」の 2 段にしない。状態は上の 1 行が持つ）
* 表示名・ハンドル・状態の欄は出さない（§3.2）

#### 7.3.3 保存

1. 画面で確かめる（UX のため。正はサーバ。`06` §33）：
   * `fields`：宣言の項目が 1 つでも空（長さ 0）なら要求を出さず、Modal に `Alert tone="danger"`「すべての項目を入力してください。」
   * `free`：空なら要求を出さず「資格情報を入力してください。」
2. `PATCH /api/v1/social/accounts/{id}` に §6 の本文を送る（`apiRequest`。CSRF トークンが付く）。`fields` の `credentials` は**宣言のキーちょうど**
3. 成功（200）：
   * 一覧の行を応答（`credentialConfigured` / `status`）で置き換える。資格情報の列が「••••••••」、状態が「接続済み」になる
   * Modal を閉じ、**入力値を捨てる**
   * Toast「資格情報を保存しました。」（`tone="success"`）
   * `router.refresh()` で Server Component を描き直す（§7.3.4）
4. 失敗：`apiRequest` が返す固定の文言（`code` ごと。422 なら「入力内容を確認してください。」。サーバの `message` ではない。§6）を Modal の中に `Alert tone="danger"` で出す。
   **入力値は残す**（直して送り直せる）。一覧は変えない（2026-09-24 に §6 に揃えた。初版は「応答の `message`」と書いていた）

#### 7.3.4 投稿一覧の Badge を追従させる（決めたこと）

投稿一覧の「資格情報 未設定」は Server Component が渡す値で描かれる（§2.1 の 8）。保存・消去の後に `router.refresh()` を呼び、
**再読み込みなしで Badge が消える・出る**ようにする。部品同士で状態を持ち回る仕組みは足さない（`next/navigation` の既存の使い方。`ui/analytics`）。

### 7.4 消す

1. 「資格情報を消す」→ 確認ダイアログ（`ConfirmDialog`。`06` §37）
   * タイトル「資格情報を消しますか？」
   * 本文「「<表示名>」の保存済みの資格情報を消します。消した値は元に戻せません。」
   * 確定のボタン「消す」
2. `PATCH` に §6 の本文を送る（`fields` / `free` は `status: 'disconnected'` を添える。`none` は `status` を送らない）
3. 成功：行を応答で置き換える（資格情報の列が「未設定」）。Modal を閉じる。Toast「資格情報を消しました。」。`router.refresh()`
4. 失敗：Toast（`tone="danger"`）に `apiRequest` が返す固定の文言（サーバの `message` ではない。§6）。Modal は開いたまま（2026-09-24 に §6 に揃えた）

* `none` で `status` を変えないのは、その provider では資格情報の有無が配信の支度に関わらないため（§7.2 と同じ理由）
* 消す権限は `social.write`（API と同じ。§8）。`social.delete` はアカウントそのものの削除の権限で、資格情報の消去には使わない

### 7.5 保存済みの値と、いまの宣言の形が違うとき（決めたこと）

| 場面 | 起きること | 本設計での扱い |
| --- | --- | --- |
| `fields` で入れ直す | 保存済みの値（別の形・自由文字列を含む）は**丸ごと置き換わる。** 古いキーは残らない | 置き換えを説明に書く（§7.3.2）。混ぜない |
| `fields` で設定済みだが、保存済みの形が合っていない（例：`free` の間に入れた自由文字列） | 画面は「設定済み」としか出せない。配信のときに `failed`（理由に要るキー名。`035` §5.7） | **画面で形を確かめない**（復号が要る。§3.2）。`failed` の理由を見て入れ直す口が、この Modal である |
| `none` で設定済み | 使われない。別の Plugin へ入れ替えると読まれる | 警告と「資格情報を消す」（§7.3.2） |
| `free` で入れ直す | 自由文字列で置き換わる | 「形式を確かめずに保存」を説明に書く（§7.3.2） |

### 7.6 入れ替え（`037` §7.2）を画面で通す

**無料版（`sns-x-manual`）→ 有料版（`sns-x-api`）**

```text
1. /plugins で sns-x-api を「導入」（再ビルドと再起動）
2. /plugins で sns-x-manual を「無効化」
3. /plugins で sns-x-api を「有効化」
4. /social → X のアカウントの行の「資格情報を設定」→ 4 つの欄（API Key（Consumer Key）／API Key Secret（Consumer Secret）／
   Access Token／Access Token Secret）に入れて「保存」→ 行が「••••••••」「接続済み」。
   各欄の下に `sns-x-api` の説明（Access Token の欄には「Read and write」にしてから発行すること）が出る（§7.1.2）
5. 以後の予約で「自動」を選ぶ
```

* **`sns-x-manual` の間は欄が出ない**（`none`）ので、無料版の間に汎用の欄へ値が入る経路が画面から無くなる（問題 1）
* 無料版の間に**先に 4 値を入れておく**ことは画面ではできない（`none` の Modal に欄が無い）。API（`037` #80）では引き続きできる。
  画面でそれを足さないのは、`none` の間は Core に 4 値の形を知る手段が無い（宣言しているのは有効な Plugin だけ）ため。
  `sns-x-manual` の間は `auto` の予約が作れない（`037` §9.3）ので、3 と 4 の間に待たされる予約は通常できない
* 4 の前の状態が「設定済み」（API で入れた値、`039` 以前に汎用の欄へ入れた値）でも、4 で丸ごと置き換わる（§7.5）
* 2〜3 の数秒は publisher が無いので、この間に開いた Modal は `free` になる。開き直せば `fields` で出る

**有料版 → 無料版**：`sns-x-manual` を有効にした後、X のアカウントの Modal は `none` で、4 値が残っていれば警告と「資格情報を消す」が出る（`037` §7.2 の「消したければ PATCH」を画面で行える）。

### 7.7 送る本文の組み立て（`credential-form.ts`）

**ファイル名・関数名（`credentialInputOf` / `createCredentialBody` / `setCredentialBody` / `clearCredentialBody` / `buildProviderOptions`）は

#### 7.7.1 部品が送る本文は「providers・対象・入力値 → 本文」の純関数で組む（2026-09-23。039 の検証 spec 中-1）

**直すこと。** 上の 3 つの関数は「入力の形」を引数に取るので、**入力の形を決めるところ（部品の中の `credentialInputOf(optionOf(…))`）が固定されていない。**
部品で `none` を `free` 扱いにする・消去の形を `fields` に固定する、という変異を入れても全件が通ることを検証が確かめている。
`none` の追加（資格情報を送らない）と `none` の消去（`status` を送らない）は、問題 1 の要であるのに**どの層でも固定されていない。**

**直し方。** 入力の形を決めるところから本文までを 1 つの純関数にまとめ、**部品はそれを呼ぶだけ**にする（`credential-form.ts` に置く）。

```ts
/** アカウント追加の要求の本文（POST /api/v1/social/accounts）。選んだ provider の入力の形を providers から決める。 */
export function buildCreateAccountRequest(
```

* 中身は「`providers` から `value === provider` の選択肢を引く → `credentialInputOf` → 入力の形が `fields` ならその項目、それ以外は `[]` → 上の 3 つの関数」である。
  **選択肢に無い provider は `free`**（§7.1）
* 部品（`social-accounts.tsx`）の `submitCreate` / `submitEdit` / `confirmClear` は、**`apiRequest` の `body` にこの 3 つの戻り値（追加は戻り値そのもの、
  入れ直しは `ok: true` の `body`）だけを渡す。** 部品の中で `createCredentialBody` / `setCredentialBody` / `clearCredentialBody` を直接呼ばない（#74 の静的検査）
* **3 つの関数の第 1 引数には、部品の props の `providers`（Server Component が `buildProviderOptions` で組んだ選択肢）を `props.providers` のまま渡す**
  （2026-09-24 に追加。039 の検証 2 回目 軽微-2）。部品で書き換えた一覧（例：`publisherRegistered` を偽にした写し）を渡すと、`none` の provider が `free` として送られ、
  関数に寄せた意味が無くなる。#74 の静的検査が第 1 引数の字面を見る
* 描画のための `credentialInputOf` の呼び出し（欄の出し分け）は部品に残してよい。送る本文は必ずこの 3 つを通る
* 部品は `FormData` から表示名・ハンドルを取り、状態から入力値を渡すだけにする（本文の形の判断を部品に置かない）

## 8. 権限（Permission）

**新しい Permission を作らない。** 画面の更新は既存の `PATCH` を通るので、認可・CSRF・監査・検証は API の経路と**同じもの**である。

| 操作 | Permission | 権限あり | 権限なし | 未認証 |
| --- | --- | --- | --- | --- |
| `/social` を開く（一覧・状態の表示） | `social.read` | 200（一覧） | 画面は「権限がありません」（`AsyncState forbidden`。現行） | ログインへ（現行） |
| 「資格情報を設定」「資格情報を消す」を表示 | `social.write`（表示制御） | 出る | 出ない | — |
| 入れ直し・消去（`PATCH /api/v1/social/accounts/{id}`） | `social.write`（UseCase `social.account.update`） | 200 | **403**、行は変わらない | **401** |
| 同、Cookie セッションで CSRF トークンなし | — | — | **403**（`CSRF_FAILED`）、行は変わらない | — |
| 同、API Token（Bearer） | 所有者の Permission ∩ scope に `social.write` | 200（CSRF の対象外。現行） | 403 | 401 |

* **ID の差し替え。** SNS アカウントは installation の共有資源で、利用者ごとの持ち主を持たない（`009`）。
  `social.write` を持つ利用者は ID を変えれば別のアカウントの資格情報を**上書き・消去できる**が、それは API と同じ権限の範囲である。
  **読み出しはどの経路でもできない**（応答は `credentialConfigured` だけ。画面は値を持たない）。無い ID は 404
* 監査：保存・消去のたびに `audit_logs` へ `updated`（`resource_type = 'social_account'`、操作者、`detail.changed` に `credentials` / `credential` と `status`）が 1 行。
  **値は残らない。** 更新の経路は復号しないので `credential_read` は出ない

## 9. Plugin API への影響

**無し。`packages/plugin-api` を 1 行も変えない。**

* `PublisherRegistration.credentialFields` の型・意味は変わらない。`[]` は従来から「資格情報なしで `publish()` が呼ばれる（`credential` は `{}`）」であり（`035` §9.2）、
  Core は `[]` の publisher に保存済みの資格情報を渡したことが無い（§2.1 の 3）。**画面で欄を出さなくなっても、どの Plugin も受け取っていたものを失わない**
* 変わるのは Core の画面の出し分けだけで、Plugin 作者から見た差は「`[]` を宣言すると `/social` に欄が出ない」ことである。
  `docs/Plugin開発ガイド.md` §9 の `credentialFields` の説明にこれを書き足す（§12）
* **後から Plugin API を広げない理由。** 「宣言が空」と「登録が無い」は Core が登録簿で見分けられる。
  `credentialMode: 'none'` のような新しい宣言を足すと、`[]` と二重の言い方になる
* **`PublishResult.rotatedCredential` の型も変えない**（§6.1）。変わるのは Core が書き戻す条件だけで、Plugin から見た差は次の 2 つである。
  どちらも `035` §9.2 の「更新が要るときは `rotatedCredential` で返す。Torifune が書き戻す」の範囲の中の、Core 側の判断である
  * 配信の間に運用者が資格情報を変えた・消した場合、返した値は保存されない（運用者の値を優先する）
  * `credentialFields: []` の publisher が返した値は保存されない（`036`〜`038` にこの形の Plugin は無い）

### 10.5 API の経路（C。画面が送る本文そのもの）

25. (C) 自由文字列 `'old-free-text'` を `credential` で保存したアカウントに、`PATCH { credentials: { handle, appPassword }, status: 'connected' }` → 200、

26. (C) `PATCH { credentials: {}, status: 'disconnected' }` → 200、`credentialConfigured: false`、`status: 'disconnected'`、DB の `credential` が `NULL`

**リスク**

1. **`router.refresh()` は `/social` の Server Component を描き直す。** 手動投稿待ちの `manual()` の呼び出し（最大 50 行、合計の上限 `MANUAL_HANDOFF_BUDGET_MS`）も走り直す。
   画面遷移 1 回分と同じ費用で、保存・消去のときだけ起きる
2. **画面を描いてから保存するまでに Plugin が入れ替わる**と、`fields` の本文が新しい宣言と合わず 422。API の応答にはキー名が入るが、**画面には固定の文言「入力内容を確認してください。」が出る**（§6）。`free` で描いた画面から保存すると、
   新しい publisher の宣言と突き合わされない自由文字列が入る（#2 の経路）。どちらも Plugin の入れ替えの数秒に限られ、Modal を開き直せば直る
3. **`fields` の入れ直しは全項目の入力が要る。** 見えていた `text` の項目（例：API Key）も、保存済みの値を画面に戻さないので打ち直しになる（`06` §38 を優先した結果）
4. Plugin の有効化に失敗した provider（`disabled`）は publisher が無いので `free` になり、汎用の欄が出る。「無い」ときの挙動としては正しい（§7.1.1）
