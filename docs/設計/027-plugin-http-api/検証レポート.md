## なぜ §3.2 を先に入れたか

**こちらは実害が出ていて、しかも後から直すのが難しいため。**

`registry` は形式上まったく正当な Plugin ID である。その ID の Plugin を導入すると、
Next.js が静的セグメントを `[id]` より先に解決するため、その Plugin に対する
有効化・無効化・設定・削除の経路がすべて Core のルートに食われる。
**一覧には出るのに操作できない Plugin ができ、導入した後で気づくことになる。**
その時点では API から消せない。

一方 §3.1 は「まだ無い機能」であり、無いことによる実害は
「コンテンツ系 Plugin が自分の API を持てない」に留まる。

## 残した理由（§3.1）

規模が大きい。少なくとも次が要る。

* `PluginContext` への経路登録 API（公開契約の追加。後方互換の検討を伴う）
* catch-all ルートと、Plugin ごとの経路表の解決
* 認証・認可・CSRF・Rate Limit・例外整形を Core が受け持つ配線
* Manifest で宣言していない Permission を要求する経路を拒む検査
* 無効化された Plugin の経路を止める仕組み

`defineRoute` / `api/route.ts` の構造に手を入れることになり、
既存の57エンドポイントすべてに影響しうる。**実装計画002 の完了判定の途中で
片手間に入れる規模ではない**と判断した。
