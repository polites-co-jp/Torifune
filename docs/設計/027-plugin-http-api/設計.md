# 027 Plugin の HTTP API 名前空間

## 1. 背景

`05_API設計.md` §17 は、Plugin が自身の API を次の名前空間で提供すると定めている。

> コンテンツを扱うPluginは、自身のAPIを `/api/v1/plugins/<plugin-id>/...` の
> 名前空間で提供する。Coreは `/api/v1/contents` を持たない。

**この名前空間は実装されていない。** Plugin が HTTP のエンドポイントを生やす手段が無い。

Core はコンテンツ管理を Plugin の責務として外した（`改訂履歴.md` 2026-08-24）。
その代わりに Plugin へ渡すはずだった口の1つがこれで、
**Core が機能を落とした分を Plugin が埋められない**状態になっている。

## 2. 併せて見つかった不具合：Plugin ID と Core のルートが衝突する

Plugin ID の形式は `^[a-z][a-z0-9-]{1,63}$`（`packages/plugin-api/src/manifest.ts:44`）。
ドットもスラッシュも要らず、**1語の英小文字がそのまま有効な ID になる。**

一方 Core は `/api/v1/plugins/` の直下に次の静的ルートを持っている。

| パス | 役割 |
| --- | --- |
| `/api/v1/plugins/registry` | Registry の参照・導入 |
| `/api/v1/plugins/package` | zip の検査・導入 |
| `/api/v1/plugins/operations` | 導入操作の進行状況 |

Next.js App Router は**静的セグメントを動的セグメント（`[id]`）より先に解決する。**

したがって `registry` / `package` / `operations` という ID の Plugin を入れると、
その Plugin に対する

* `GET /api/v1/plugins/registry`（Plugin の情報）
* `POST /api/v1/plugins/registry/enable` / `/disable`
* `PUT /api/v1/plugins/registry/settings`
* `DELETE /api/v1/plugins/registry`

が**すべて Core のルートに食われる。** 画面からは一覧に出るのに、
有効化も無効化も設定も削除もできない Plugin ができあがる。
**導入した後で気づくことになり、その時点では API で消せない。**

これは仮定の話ではない。`registry` は形式上まったく正当な Plugin ID である。

## 3. 決めたこと

### 3.1 Plugin の API は `/api/v1/plugins/<plugin-id>/api/...` に置く

§17 が言う「`/api/v1/plugins/<plugin-id>/...` の名前空間」を、
**`/api/v1/plugins/<plugin-id>/api/` 以下**として具体化する。

**なぜ1段挟むか。** 挟まないと、Core が Plugin リソースに対して持つ操作
（`enable` / `disable` / `settings`）と Plugin 自身の経路が同じ階層に並ぶ。
`enable` という名前の経路を作りたい Plugin が作れない、という制約が永久に残る。
1段挟めば、`api/` 以下は**まるごと Plugin のもの**になり、
Core が将来 `/api/v1/plugins/{id}/xxx` を足しても Plugin 側は一切影響を受けない。

仕様書 §17 の記述はこの形へ改訂する。名前空間を狭めるのではなく、
**Core と Plugin の境界がどこにあるかを明示する**ための変更である。

### 3.2 Core が使う ID を予約語にする

`registry` / `package` / `operations` を Plugin ID として使えないようにする。

**Manifest の検証で弾く。** 導入してから壊れるのではなく、
導入しようとした時点で理由つきで断る。

予約語はコード上の1か所（`packages/plugin-api/src/manifest.ts`）に置き、
**Core が `/api/v1/plugins/` 直下へ静的ルートを足したらそこへ足す**という対応関係にする。
対応が破れていないことをテストで固定する（§5）。

**既に導入済みの Plugin は弾かない。** 検証は導入時に働くもので、
すでに DB にある行を後から無効にはしない。予約語と同じ ID の Plugin が
既に入っている環境は現実には無い（この名前空間はまだ誰にも使わせていない）。

### 3.3 Plugin の経路にも Core の防御をそのまま効かせる

Plugin が生やした経路でも、次は Core が受け持つ。**Plugin ごとに書かせない。**

| 項目 | 扱い |
| --- | --- |
| 認証 | Core のセッション / Bearer トークンをそのまま使う |
| 認可 | 経路ごとに Permission を宣言させ、**Core が判定する** |
| 宣言済み Permission との突き合わせ | Plugin が Manifest で宣言していない Permission は要求できない |
| CSRF | Core の判定をそのまま通す |
| Rate Limit | Core の既定を適用する |
| 例外 | Core の `api/errors.ts` で包む。Plugin の例外を素で外へ出さない |

Plugin に渡すのは「この要求を処理して応答を返す」ところだけにする。
`03_プラグイン設計.md` §21（Plugin API 設計原則）と、
`plugin/data-api.ts` が Permission を強制しているのと同じ考え方である。

## 4. やらないこと

* **Plugin の経路を OpenAPI に載せない。** Core の OpenAPI は Core の契約を表すもので、
  導入された Plugin によって中身が変わる文書は「仕様」として使えない。
  Plugin が自分の仕様を配りたい場合は、自分の経路で配ればよい。
* **Plugin ごとの API バージョニングを Core が持たない。** `/api/v1/` の `v1` は
  Core の API バージョン（`07_開発者向けガイド.md` §12）。
  Plugin が自分の版を切りたければ `api/v2/...` のように自分の名前空間の中で切る。

## 5. 受け入れ条件

1. Plugin が経路を登録でき、`/api/v1/plugins/<plugin-id>/api/...` で応答が返る。
2. 登録していない経路は 404。
3. 未認証は 401、Permission が足りなければ 403。
4. **Manifest で宣言していない Permission を要求する経路は登録できない。**
5. `registry` / `package` / `operations` を ID とする Manifest が検証で弾かれる。
6. **予約語の一覧と、`app/api/v1/plugins/` 直下の実際のディレクトリ名が一致することを
   テストで固定する。** 片方だけ増えたら落ちる。
7. 無効化された Plugin の経路は応答しない。
8. Plugin の中で例外が起きても、Core の形式のエラー応答になる（内部例外を素で返さない）。
