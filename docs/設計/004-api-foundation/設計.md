# API 基盤 設計

## 1. 目的

`/api/v1` の形を1本に固め、以降のドメインが同じ型で API を増やせるようにする。

満たすべきことは4つ。

1. **リクエストの検証を型と1対1にする。** 検証を通ったら型が保証されている状態にする
2. **応答の形を1箇所で決める。** 各ルートで組み立てると、いつか内部例外がそのまま出る
3. **一覧の Pagination / Filtering / Sorting を共通化する。**
   とくに Sorting は、任意のカラム名を受け付けない形にする
4. **API 仕様を実装から生成する。** 手で書いた仕様は必ず実装とずれる

## 3. スコープ

### やること

* Zod による Request/Response スキーマと、その検証
* 統一応答（`{ data }` / `{ data, meta }` / `{ error }`）
* Pagination / Filtering / Sorting の共通実装
* Rate Limit（汎用。ログイン以外にも掛けられる形）
* エラーハンドリング（内部例外を漏らさない）
* OpenAPI 生成と `/api/v1/openapi.json`
* CORS（既定は無効。設定で許可 Origin を指定）
* ルートを組み立てる共通ヘルパ（認証・認可・検証・応答を一箇所に）

### やらないこと

* API Token（`016-api-token`）
* Webhook（`05_API設計.md` §39）
* Cursor Pagination（大量データを扱う `018-analytics` で検討）
* GraphQL 等の別方式

## 4. レイヤ配置

```text
apps/web/src/api/
├── errors.ts          既存。ErrorCode を拡張する
├── response.ts        成功応答（data / meta）
├── query.ts           Pagination / Filtering / Sorting の解釈
├── validation.ts      Zod スキーマの適用と 422 への変換
├── rate-limit.ts      汎用 Rate Limit
├── route.ts           ルートを組み立てる共通ヘルパ
├── openapi.ts         OpenAPI 文書の組み立て
└── registry.ts        エンドポイントの登録（OpenAPI 生成の入力）
```

**API Layer に業務ロジックを置かない**（`07_開発者向けガイド.md` §11）。
ここにあるのは「HTTP と Application 層の間の変換」だけ。

## 5. データモデル

新しいテーブルは作らない。

Rate Limit は `login_attempts` を汎用化せず、**インメモリの実装**にする。

> 理由：ログイン試行制限は「攻撃の記録として残す価値がある」ため DB に置いた。
> 一般 API の Rate Limit は記録に価値がなく、DB への書き込みがかえって負荷になる。
> 単一プロセス前提でよい。複数インスタンスで厳密に効かせたくなったら、
> その時点で共有ストアへ差し替える（インターフェースは分けておく）。

## 6. API

### 6.1 成功応答

```jsonc
// 単体
{ "data": { "id": "…", "name": "…" } }

// 一覧
{
  "data": [ … ],
  "meta": { "page": 1, "perPage": 20, "total": 100 }
}
```

### 6.2 エラー応答

```jsonc
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "入力内容を確認してください。",
    "details": { "name": ["必須です。"] }
  }
}
```

`code` はプログラムから判定できる固定値。`message` は表示用。
**`details` は入力エラーのフィールド単位の説明にだけ使う。**

### 6.3 一覧のクエリパラメータ

| 名前 | 既定 | 制約 |
| --- | --- | --- |
| `page` | 1 | 1 以上の整数 |
| `perPage` | 20 | 1〜100 |
| `sort` | API ごと | **ホワイトリストにある名前のみ**。先頭の `-` で降順 |
| その他 | — | API ごとに Zod で定義した Filter のみ |

`sort=-createdAt` のように書く。
**未許可のフィールドは 422。** DB のカラム名を直接指定させない。

### 6.4 OpenAPI

`GET /api/v1/openapi.json` で OpenAPI 3.1 文書を返す。
登録されたエンドポイントの Zod スキーマから生成する。

**手で書かない。** 手で書いた仕様は必ず実装とずれる。

## 7. 画面

なし。

## 8. 権限（Permission）

このスプリント自体は Permission を持つエンドポイントを追加しない。
`openapi.json` は**認証不要**とする（API の形は秘密ではなく、
隠しても攻撃者には効かない。むしろ利用者の役に立つ）。

ただし OpenAPI 文書に**内部エンドポイントを含めない**。

## 9. Plugin API への影響

`packages/plugin-api` にはまだ公開しない。S10 で次を公開する。

* `defineEndpoint` に相当する、Plugin が API を足すための契約
* 応答とエラーの形（Plugin が独自形式を返さないように）

## 10. 受け入れ条件

### 応答の形

1. 単体の成功応答が `{ data }` の形である
2. 一覧の成功応答が `{ data, meta }` の形で、`meta` に `page` / `perPage` / `total` を含む
3. エラー応答が `{ error: { code, message } }` の形である
4. 入力エラーで `details` にフィールド単位の説明が入る
5. **内部例外の詳細・Stack Trace・SQL が応答に含まれない**
6. 想定外の例外が 500 になり、内容が漏れない

### ステータスコード

7. 400 / 401 / 403 / 404 / 409 / 422 / 429 / 500 が仕様どおり返る
8. 作成成功が 201 を返す
9. 本文なしの成功が 204 を返す

### 検証

10. Zod スキーマに合わない入力が 422 になる
11. 型が違う値（数値のところへ文字列）が 422 になる
12. 未知のフィールドを送っても無視される（拒否しない）
13. 必須フィールドが無ければ 422 で、そのフィールド名が `details` に出る
14. 検証を通った値が、型として保証されている

### Pagination

15. `page` / `perPage` を指定できる
16. 未指定なら 1 / 20 になる
17. `perPage` が 100 を超えると 100 に丸められる
18. `page` が 0 以下なら 1 に丸められる
19. 数値でない値を渡すと 422
20. `meta.total` が全件数（そのページの件数ではない）を返す

### Sorting

21. `sort=name` で昇順、`sort=-name` で降順になる
22. **ホワイトリストに無いフィールドは 422**
23. DB のカラム名（`created_at` 等）を直接指定しても通らない
24. 複数指定（`sort=name,-createdAt`）ができる
25. 未指定なら API ごとの既定順になる

### Filtering

26. Zod で定義した Filter が効く
27. 定義していないクエリパラメータは無視される
28. **SQL 断片を渡しても解釈されない**

### Rate Limit

29. 制限を超えると 429 になる
30. 429 の応答に `Retry-After` が付く
31. 時間窓を過ぎると再び通る
32. 別のキー（別の IP）は独立して数えられる

### OpenAPI

33. `/api/v1/openapi.json` が 200 を返す
34. OpenAPI 3.1 の構造を持つ
35. 登録したエンドポイントが `paths` に含まれる
36. 各エンドポイントに Request/Response スキーマが含まれる
37. **内部エンドポイントが含まれない**

### CORS

38. 既定では `Access-Control-Allow-Origin` を返さない
39. 許可した Origin にだけ返す
40. **`*` を設定できない**（設定されていたら起動時に落とす）
