### 指摘

#### F-1（記録）`registerEndpoint` は後勝ちにしている

同じ `operationId` の二重登録を例外にせず、後勝ちにした。
開発中のホットリロードでモジュールが再評価されると、例外にすると起動できなくなるため。

弱点：`operationId` を取り違えると、片方が黙って消える。
OpenAPI の `paths` を E2E で完全一致検証しているため、消えれば気づける。

#### F-2（記録）OpenAPI はエンドポイント登録に依存する

`defineRoute` の副作用で登録されるため、**モジュールが評価されていないと仕様に出ない**。
Next.js は要求されたルートしか読み込まないので、`api/endpoints.ts` で明示的に import している。

新しいエンドポイントを足したら、そこへ1行足す必要がある。忘れると仕様に出ない（動作はする）。
E2E が `paths` を完全一致で検証しているため、忘れれば落ちる。

| --- | --- |
| 内部例外を応答へ出さない | ✅ |
| 任意のカラムで並び替えできない | ✅ ホワイトリスト。SQL 断片・プロトタイプ名も拒否 |

| Rate Limit のメモリ枯渇 | ✅ 期限切れを掃除し、追跡キー数に上限を設ける |
| Rate Limit の回避（キー大量生成） | ✅ 上限超過時は**新しいキーを通す**。拒否すると、キーを大量生成するだけで正規利用者を締め出せる |
| 認可の呼び忘れ | ✅ `defineRoute` が `permission` を必須にし、null には理由を要求する |

### 指摘

#### S-1（記録）Rate Limit は単一プロセス前提

インメモリのため、複数インスタンスでは各プロセスごとに数える。
**認証の総当たり対策は DB 側（`authentication/rate-limit.ts`）が担う**ため、
そちらは複数インスタンスでも効く。ここで守るのは「1プロセスへの物量」だけ。

厳密に効かせたくなったら `RateLimiter` インターフェースのまま共有ストア実装へ差し替える。
