## 2. 設計上の判断

### 2.1 OpenAPI をどう生成するか

`zod-to-json-schema` 相当の変換を**自前で書かない**。Zod v4 は `z.toJSONSchema()` を
標準で持つため、それを使う。外部ライブラリを1つ減らせる。

エンドポイントは `registerEndpoint()` で登録する。登録の副作用として OpenAPI に載る。
**登録し忘れたエンドポイントは仕様に出ない**が、動作はする。
「仕様に出ないと困る」のは公開 API だけなので、これで足りる。

### 2.2 Sorting のホワイトリスト

API ごとに「公開名 → 内部の並び替えキー」の対応表を持つ。

```ts
const SITE_SORT = { name: 'name', createdAt: 'created_at' } as const;
```

クエリの `sort` は**公開名だけ**を受け付ける。
これにより、DB のカラム名が変わっても API の契約が変わらない。
また、任意のカラムを指定して情報を推測されることも防げる。

### 2.3 Rate Limit をインメモリにする

一般 API の Rate Limit は記録に価値がなく、DB 書き込みが負荷になる。
単一プロセス前提のインメモリ実装にし、インターフェースだけ分けておく。

**掃除を忘れると際限なくメモリを食う。** 期限切れのエントリを
アクセスのついでに落とす。

### 2.4 ルート組み立てヘルパ

```ts
export const GET = defineRoute({
  operationId: 'listSites',
  permission: 'site.read',
  query: SiteListQuery,
  handler: async ({ context, query }) => { … },
});
```

認証・認可・検証・応答・エラー変換を1箇所に集める。
**各ルートで手順を並べると、いつか1つ抜ける。**

### 2.5 未知のフィールドを拒否しない

Zod の既定（strip）に従い、未知のフィールドは無視する。
拒否（strict）にすると、クライアントが将来のフィールドを送ったときに壊れ、
API の前方互換性が失われる。

## 4. 影響範囲

| 対象 | 影響 |
| --- | --- |
| 既存の `/api/v1/auth/*` | 応答の形は変えない。組み立て方を共通ヘルパへ寄せる |
| `/api/v1/roles` `/api/v1/permissions` | 同上 |
| Plugin API | まだ公開しない |

**破壊的変更：なし**（応答の形を変えないため）

## 5. リスク

| リスク | 対応 |
| --- | --- |
| `defineRoute` が窮屈で使われない | 既存ルートを全部移行して実用性を確かめる |
| Zod v4 の `toJSONSchema` が期待どおり動かない | 動かなければ最小限の自前変換に落とす。テストで検出する |
| インメモリ Rate Limit がメモリを食う | 期限切れをアクセス時に掃除する。上限件数も設ける |
