## 1. 目的

1. アクセス解析の指標を、モックが要求する範囲まで**バックエンドから**広げる
   （セッション・直帰率・平均滞在・Bot・時間帯・デバイス・参照元・ランディング・パス別）。
   画面が生ログを集計しない原則（`018` §4.1）は維持する
2. `/analytics` を「1サイトずつ、期間プリセットと前期間比較つき、5タブ」の構成に改める。
   計測タグの案内を各サイトの「設定」タブへ移す
3. `/dashboard` を「直近7日固定」のまま、前期間比・直帰率・サイト別行・実施中のキャンペーンを足す
4. デザイントークンを差し替え、共通部品を新しい見た目に更新する。
   フォントは `next/font/local` でリポジトリに同梱してセルフホストし、実行時にもビルド時にも外部へ取りに行かない
5. 計測タグの公開キーを再発行できるようにする（`site.write`、監査ログ）

### 5.3 ロールアップの再設計（`rollup.ts` / `analytics-repository.ts`）

#### 5.3.1 セッションの定義

* 同一 `(site_id, 集計日, visitor_hash)` の PV を `occurred_at` 順に並べ、
  **直前の PV から 30 分を超えて空いたら新しいセッション**。最初の PV は必ずセッション開始
* **日をまたがない。** 訪問者ハッシュは日ごとにソルトが変わる（`018` §3.2）ので実際にはまたげないが、
  SQL でも集計日をパーティションに含めて保証する（ソルトの回り方に依存しない）
* 境界：間隔がちょうど 30 分（1800000 ms）は**同じセッション**。30 分 + 1 ms で別セッション
* `dwell_ms` は「同じセッション内の次の PV までの間隔」。セッション最後の PV は標本に入らない
  （画面に「実際より短め」と注記する）
* Bot（`device = 'bot'`）はセッション化の対象外。`bot_pageviews` / `bot_visitors` にだけ数える

**指標名 `sessions` は変えない。** `rollup.ts` の現行コメントは「定義を変えるときは指標名も変える」と
しているが、旧定義は「visitors と同値の仮置き」であって過去との比較に意味のある値ではない。
`018` §4.1.1（タイムゾーン変更）と同じ扱いにする：**マイグレーション後、保持している生ログの期間で
ロールアップを流し直す**運用手順を README とマイグレーションのコメントに書く。
流し直せない（生ログを消した）期間の `sessions` は旧定義のまま残り、`bounces` 等は存在しない。

#### 5.3.2 SQL の方針

Repository に `aggregateDailyBreakdown(connection, { from, to, timeZone })` を置き、
1 本の SQL で「サイト × 日 × metric × key → value」の行を返す。CTE の骨格：

```sql
WITH logs AS (
  SELECT id, site_id, occurred_at, path, referrer_host, visitor_hash, device,
         (occurred_at AT TIME ZONE :tz)::date AS day,
         to_char(occurred_at AT TIME ZONE :tz, 'HH24') AS hour
  FROM access_logs
  WHERE occurred_at >= (:from::date::timestamp AT TIME ZONE :tz)
    AND occurred_at <  ((:to::date + interval '1 day')::timestamp AT TIME ZONE :tz)
),
human AS (SELECT * FROM logs WHERE device <> 'bot'),
ordered AS (
  SELECT *,
         lag(occurred_at)  OVER w AS prev_at,
         lead(occurred_at) OVER w AS next_at
  FROM human
  WINDOW w AS (PARTITION BY site_id, day, visitor_hash ORDER BY occurred_at, id)
),
marked AS (
  SELECT *,
         CASE WHEN prev_at IS NULL OR occurred_at - prev_at > interval '30 minutes' THEN 1 ELSE 0 END AS starts,
         CASE WHEN next_at IS NOT NULL AND next_at - occurred_at <= interval '30 minutes'
              THEN floor(extract(epoch FROM (next_at - occurred_at)) * 1000)::bigint END AS dwell_ms
  FROM ordered
),
numbered AS (
  SELECT *, sum(starts) OVER (PARTITION BY site_id, day, visitor_hash ORDER BY occurred_at, id
                              ROWS UNBOUNDED PRECEDING) AS session_no
  FROM marked
),
sessions AS (
  SELECT site_id, day, visitor_hash, session_no,
         count(*) AS pv,
         (array_agg(path ORDER BY occurred_at, id))[1] AS landing_path,
         coalesce((array_agg(referrer_host ORDER BY occurred_at, id))[1], '(direct)') AS referrer
  FROM numbered
  GROUP BY site_id, day, visitor_hash, session_no
)
-- 以下、指標ごとの SELECT を UNION ALL で並べる（metric, key, value）
```

各指標の元：

| 指標 | 元 |
| --- | --- |
| `pageviews` / `visitors` / `pageviews_hour` / `pageviews_device` / `path_pageviews` / `path_visitors` | `human` |
| `sessions` / `bounces`（`pv = 1`）/ `landing` / `referrer` / `referrer_visitors` / `referrer_bounces` / `path_bounces` | `sessions` |
| `dwell_ms` / `dwell_samples` / `path_dwell_ms` / `path_dwell_samples` | `numbered`（`dwell_ms IS NOT NULL`） |
| `bot_pageviews` / `bot_visitors` | `logs WHERE device = 'bot'` |

* **タイムゾーン**：`018` §4.1.1 のとおり `TORIFUNE_TIMEZONE` を 1 箇所で読み、日付境界・`day`・`hour` に同じ値を使う。
  `occurred_at >= :date::date` のような接続 TimeZone 依存の比較を書かない
* **出力の規則**：`key = ''` の 8 指標は、その (site, day) に**1 行でも生ログがあれば 0 でも出す**
  （「集計したが 0 だった」と「集計していない」を区別できるように）。キー付き指標は値 > 0 の key だけ出す
* 生ログが 1 行も無い (site, day) には何も書かない（現行と同じ。消された生ログの日を 0 で上書きしない）

#### 5.3.3 冪等な差し替え

現行の `putPoint`（upsert）だけでは、**前回あって今回無くなった key の行が残る**
（例：パスの正規化を変えた、生ログを一部消した）。
(site, day) ごとに 1 トランザクションで次を行う `replaceCorePoints(connection, siteId, metricDate, points)` を足す。

1. `DELETE FROM analytics WHERE site_id = ? AND metric_date = ? AND source = 'core'`
2. 新しい行を多行 `INSERT`（500 行ずつに分ける）

同じ生ログに対して何度流しても結果が同じになる。`source <> 'core'`（Plugin の値）には触らない。
`putPoint` は Plugin の `record` 用に残す（`onConflict` の列に `key` を足す）。

#### 5.3.4 最終受信の書き戻し

集計した範囲について、サイトごとに `max(occurred_at)`（**Bot を含む**。届いているかの確認が目的）を
Repository の `maxOccurredAtBySite(connection, { from, to, timeZone })` で読み、
`touchLastSeen(connection, siteId, seenAt)` が
`UPDATE sites SET analytics_last_seen_at = GREATEST(coalesce(analytics_last_seen_at, '-infinity'), ?)` を行う。
`GREATEST` にするのは、過去の期間を流し直しても値が巻き戻らないようにするため。
`maxOccurredAtBySite` はロールアップ内部の読み取りであり、画面・API からは呼ばない。

##### 5.3.4 への追記（2026-09-04、`029-scheduled-jobs`）

`analytics_last_seen_at` は**残る**。サイト選択肢の「（未設置）」判定は引き続きこの値で行う
（定期実行が回れば最大 15 分の遅れで済む）。

一方、**画面のヘッダと「設定」タブに出す「最終受信」は生ログから直接引く**
（`findLatestAccessAt`。1 行）。集計を待たずに「届いたか」を見せるため。`029` §6.4。

#### 5.3.5 `RollupResult` と Event

`{ days, points }` の意味は変えない（`days` = 書いた (site, day) の数、`points` = 書いた行数）。
`analytics.rolledUp` のペイロード `{ from, to, points }` も変えない。

#### 5.3.6 制御文字を含むパスの扱い（2026-09-04 追記、セキュリティ検証の反映）

パスが `key` として `analytics` に入り、画面に表示され、`keys` として UseCase へ戻る経路ができる。
制御文字（`0x00`〜`0x1f`、`0x7f`）を含むパスは、3 段で止める。

* (a) **受け口**：`normalizePath` は制御文字を含むパスを `null` にして記録しない（`018` §3.2 の追記）
* (b) **ロールアップ**：`aggregateDailyBreakdown` はキー付き指標（`path_*` / `landing`）の key に
  制御文字を含むパスを出さない（(a) 以前に記録された生ログへの防御。`pageviews` 等の合計には数える）
* (c) **画面**：読んだ key を `isValidBreakdownKey` で濾してから `keys` に渡し、無効な key の行は表示しない

### 6.1 `listAnalytics` / `listAnalyticsPage` の絞り込み追加

`AnalyticsRangeInput` に任意項目を足す。省略時の挙動は現行どおり（全指標・全 key）。

| 項目 | 型 | 意味 |
| --- | --- | --- |
| `metrics?` | `readonly string[]` | 指標名で絞る（最大 20 個、各 `isValidMetricName`） |
| `key?` | `string` | key で絞る。`''` を渡すとキー無しの行だけ |

`GET /api/v1/analytics` にも `metric`（1 つ）と `key` のクエリを足す。応答の `analyticsPointSchema` に `key: string` を足す。

uuid 型の列に不正な文字列を渡して 500 にしない。2026-09-04 追記）。

### 6.2 `listAnalyticsBreakdown`（新規）

```ts

  siteId: string | null;   // null は全サイト合算
  from: string; to: string;
  metric: string;
  source: string | null;   // null は全出所を合算

  keys?: readonly string[];   // 画面用。指定した key に限る（最大 100）
}
```

* Permission `analytics.read`。UseCase 名 `analytics.breakdown`
* 検証：期間は `assertRange`（逆転 422、400 日超 422）。`metric` は `isValidMetricName` でなければ 422。

  `total` は `count(DISTINCT key)`。`analytics_site_metric_idx` を使う
* API：`GET /api/v1/analytics/breakdown?siteId&from&to&metric&source&page&perPage`。

### 6.3 `kind=topPaths` の扱い：残して `analytics` へ載せ替える（互換維持）

* `GET /api/v1/analytics?kind=topPaths` は**残す**（`05` §41。既に叩いているクライアントを壊さない）。
  応答の形 `{ path, pageviews }` も変えない
* 実装は `listAnalyticsBreakdown(metric = 'path_pageviews', source = 'core')` の結果を
  `{ path: key, pageviews: value }` に写す。**生ログを読む `topPaths` / `countTopPaths` は削除**する。
  これで API と画面のどこからも `access_logs` を読まなくなる（`018` §4.1 の原則を API にも広げる）
* **`defineRoute` の `deprecated` は付けない。** `deprecated` はエンドポイント単位（`api/route.ts` / `api/deprecation.ts`）で、
  付けると `kind=points` を含む `GET /analytics` 全体に `Deprecation` ヘッダと OpenAPI の `deprecated: true` が出てしまう。
  `kind` の値だけを非推奨にする仕組みは無い（`openapi-coverage.test.ts` も「非推奨のエンドポイントは無い」を検査している）。
  代わりに `analyticsListQuerySchema` の `kind` の `description` に
  「`topPaths` は `/analytics/breakdown?metric=path_pageviews` で置き換えられる。互換のため残す」と書き、OpenAPI に出す
* `listTopPaths`（非ページ版 UseCase）は画面でしか使っていないので削除。`listTopPathsPage` は API 用に残す

`{ siteId }` → `AnalyticsStatus`。Permission `analytics.read`。UseCase 名 `analytics.status`。

### 6.6 `regenerateSitePublicKey`（新規）

#### 7.3.4 「Bot を集計に含める」の計算規則（`domain/analytics/summary.ts`）

Bot は「1 アクセス = 1 セッション = 直帰」として数える（クローラは連続閲覧の間隔を持たない）。

| 指標 | オフ | オン |
| --- | --- | --- |
| ページビュー | `pageviews` | `pageviews + bot_pageviews` |
| 訪問者 | `visitors` | `visitors + bot_visitors` |
| セッション | `sessions` | `sessions + bot_pageviews` |
| 直帰率 | `bounces / sessions` | `(bounces + bot_pageviews) / (sessions + bot_pageviews)` |
| 平均滞在 | `dwell_ms / dwell_samples` | 同左（Bot は標本に入らない） |
| 日次推移の PV / 訪問者 | 上と同じ規則を日ごとに | |
| デバイス | 3 行 | 3 行 + 「Bot」行（`bot_pageviews`）。割合の分母も Bot 込み |
| 時間帯 / 上位ページ / 参照元 / ページタブ / 参照元タブ | Bot を含めない（スイッチに関係なく） | 同左。区画に「Bot は含めていません」の注記 |
| 「Bot のアクセス」（訪問者タブ） | スイッチに左右されない | |

分母が 0 の率は「—」。「Bot のアクセス」：Bot の PV = `bot_pageviews`、人の PV = `pageviews`、
割合 = `bot_pageviews / (pageviews + bot_pageviews)`、最も多かった日 = 日次 `bot_pageviews` の最大の日（同数なら早い日）。

#### 7.3.5 前期間比較の規則（`domain/analytics/summary.ts`）

```ts
delta(cur, prev, lowerIsBetter = false)     // 件数・平均など
  prev === 0            → { text: '—', tone: 'muted' }
  d = (cur − prev) / prev
  text = (d ≥ 0 ? '+' : '−') + |d × 100| を小数 1 桁 + '%'
  tone = |d| < 0.0005 ? 'muted' : (lowerIsBetter ? d < 0 : d > 0) ? 'success' : 'danger'

deltaPt(cur, prev, lowerIsBetter = true)    // 率（直帰率）。cur / prev は 0〜1
  前期の分母（sessions）が 0 → '—'
  当期の分母（sessions）が 0 → '—'（muted。2026-09-04 追記：当期に率が無いときも比較しない）
  d = (cur − prev) × 100
  text = (d ≥ 0 ? '+' : '−') + |d| を小数 1 桁 + 'pt'
  tone = |d| < 0.05 ? 'muted' : (lowerIsBetter ? d < 0 : d > 0) ? 'success' : 'danger'
```

色：`success` → `--tf-color-success`、`danger` → `--tf-color-danger`、`muted` → `--tf-color-text-subtle`。
直帰率だけ `lowerIsBetter`。訪問者あたり PV・1 日あたり訪問者・平均滞在は `delta`（上がると緑）。

#### 7.3.6 タブの中身

**概要**
* Stat × 5：ページビュー / 訪問者 / セッション / 直帰率 / 平均滞在時間（値 + 前期間比）
* 日次の推移：`Chart` 2 系列（ページビュー = chart-1、訪問者 = chart-2）、Y 軸ラベル（max / mid / 0）、X 軸目盛り、凡例。代替表（日付 / PV / 訪問者）
* 上位ページ 5（パス、Meter、PV）「すべて →」→ `tab=pages`。参照元 5（ホスト、Meter、セッション）「すべて →」→ `tab=referrers`
* 時間帯別 PV：`BarChart` 24 本（最大の時間帯を強調）、「最も多い時間帯は N 時台」。デバイス：Meter × 3（+ Bot 行）と注記「Bot と判定したアクセス n 件は集計に含めていません／含めています」

**ページ**：表（ページ / PV / 訪問者 / ランディング / 直帰率 / 平均滞在）、PV 順、50 件ごとの Pagination、
見出し脇に「N ページ · ページビュー順」（N = total）。注記「平均滞在は…セッション最後のページは測れないため、実際より短めに出ます。」
直帰率 = `path_bounces / landing`、平均滞在 = `path_dwell_ms / path_dwell_samples`（分母 0 は「—」）。

**参照元**：表（参照元 / セッション / 訪問者 / 直帰率 / 割合(Meter + %)）、セッション順、Pagination。
直帰率 = `referrer_bounces / referrer`、割合 = `referrer / sessions`（Bot 抜きの sessions）。注記「参照元はホスト名だけを保存しています。」

**訪問者**：Stat × 4（訪問者 / セッション / 訪問者あたりページビュー（小数 2 桁）/ 1 日あたり訪問者）、デバイス、時間帯別、
「Bot のアクセス」（4 値 + 注記「この欄の数値は「Bot を集計に含める」スイッチに左右されません」）。

**設定**（`site.read` があるときだけ）
* 計測タグ：`<pre data-tracking-snippet data-site-id={id}>`（既存 E2E の locator を保つ）。src は絶対 URL（現行どおり `originFromHeaders`。取れなければ警告 Alert）
* 「タグをコピー」（`navigator.clipboard.writeText`、成功したら 2 秒間「コピーしました」）
* 「公開キーを再発行」（`site.write` があるときだけ描画。Button secondary）→ `ConfirmDialog`
  （title「公開キーを再発行しますか？」、message「いまのキーで貼ってある計測タグは無効になり、貼り直すまでアクセスは記録されません。」、confirmLabel「再発行する」）→
  `POST /api/v1/sites/{id}/public-key` → 成功で Toast「公開キーを再発行しました」と `router.refresh()`（新しいタグを Server Component から読み直す）。失敗は `error-message.ts` の文言で Toast(danger)
* 受信状況：状態（`analyticsLastSeenAt` があれば「受信中」success 色、無ければ「未受信」subtle 色）/ 最終受信 / 最終集計 / 日付の区切り。**保持日数の行は出さない**
* 注記「集計は `POST /api/v1/analytics/rollup` を cron から毎日実行します（API トークンで叩けます）。集計値は消しません。」

##### 7.3.6 への追記（2026-09-04、`029-scheduled-jobs`）

#### 7.4.1 Chart の拡張（`chart.tsx` / `chart-geometry.ts`）

```ts

  series?: readonly ChartSeries[];       // 複数系列

```

* `points` だけを渡す既存の呼び出しは、見た目も座標計算（`chartPolyline`）も変えない（公開契約）。`height` の数値指定も受け付け続ける（型は `number | 'sm' | 'md' | 'lg'`）

* 目盛りとラベルの計算は `chart-geometry.ts` に純関数で置く（`chartLayout(series)` → 各系列の `points` 文字列、`yMax`、`ticks[{ xPercent, label }]`）。NaN・0 除算・全部同じ値・1 点だけ・空配列を通す
* 線の色はトークン `--tf-color-chart-1` / `--tf-color-chart-2`。格子線は `--tf-color-border-weak`、基線は `--tf-color-border`
* 代替表（`fallback`）は従来どおり必ず描く。凡例・軸ラベルは装飾であり、表が唯一の読み上げ経路

### ロールアップ：セッションと指標

7. (B) 同一訪問者の PV が 3 件、間隔 10 分・10 分 → `sessions = 1`、`bounces = 0`、`dwell_samples = 2`、`dwell_ms = 1,200,000`
8. (B) 同一訪問者の PV 2 件の間隔が **ちょうど 30 分** → `sessions = 1`（境界は同じセッション）
9. (B) 同一訪問者の PV 2 件の間隔が 30 分 + 1 秒 → `sessions = 2`、`bounces = 2`、`dwell_samples = 0`
10. (B) `TORIFUNE_TIMEZONE` の日付境界をまたぐ 2 件（23:50 と 翌 00:05、同じ `visitor_hash` を直接挿入）→ 各日に `sessions = 1`、両日とも `dwell_samples = 0`（日をまたがない）
11. (B) PV 1 件だけの訪問者が 2 人、3 件見た訪問者が 1 人 → `pageviews = 5`、`visitors = 3`、`sessions = 3`、`bounces = 2`
12. (B) `device = 'bot'` の PV 4 件（2 つの `visitor_hash`）と人の PV 1 件 → `bot_pageviews = 4`、`bot_visitors = 2`、`pageviews = 1`、`sessions = 1`。Bot は `pageviews_hour` / `pageviews_device` / `path_*` / `referrer` / `landing` に現れない
13. (B) Bot の PV しか無い日 → `pageviews = 0`、`visitors = 0`、`sessions = 0`、`bounces = 0` の行が出て、`bot_pageviews > 0`
14. (B) `TORIFUNE_TIMEZONE=Asia/Tokyo` で UTC 23:30 の PV → `pageviews_hour` の key が `'08'`、`metric_date` が翌日
15. (B) `desktop` 2 件・`mobile` 1 件 → `pageviews_device` が `desktop = 2`、`mobile = 1`、`tablet` の行は無い（値 0 の key は出さない）
16. (B) セッション最初の PV の `referrer_host` が `NULL` → `referrer` の key `'(direct)'` に数えられる。2 件目以降の referrer はセッションの参照元に影響しない
17. (B) `/a` → `/b` の順に見たセッション → `landing['/a'] = 1`、`landing['/b']` 無し、`path_pageviews['/a'] = 1`、`path_pageviews['/b'] = 1`、`path_dwell_samples['/a'] = 1`、`path_dwell_samples['/b']` 無し
18. (B) `/a` だけ見て離脱したセッション → `path_bounces['/a'] = 1`、`bounces = 1`
19. (B) 参照元 `www.example.com` から始まる 2 セッション（訪問者は同一、1 つは直帰）→ `referrer = 2`、`referrer_visitors = 1`、`referrer_bounces = 1`
