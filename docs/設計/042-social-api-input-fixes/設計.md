## 1. 目的

外部アプリが SNS 投稿 API を仕様書どおりに使ったとき、次の 4 つの「黙って困る」振る舞いを無くす。

| # | いまの振る舞い | 困ること |
| --- | --- | --- |
| ① | Bluesky の手動投稿は、本文が日本語で約 224 文字以上でも登録が通る | 予約時刻が来てから画面の「投稿画面を開く」が失敗する（Core の `isValidManualUrl` が 2048 文字で断る）。X と Threads は登録時に 422 で断っている |
| ② | `GET /social/accounts`・`GET /social/posts` の `page` / `perPage` に範囲の検査が無い | `perPage=-1`・`page=0` が **500**。`perPage=1000` がそのまま通る。`perPage=0` は 200 で空 |
| ③ | `GET /social/posts?accountId=` は 64 文字以内で UUID の形でない値だと絞り込みが外れる | **全アカウントの投稿が返る**。打ち間違いに気づけないまま、別のアカウントの投稿を処理しうる |
| ④ | OpenAPI に `createSocialPost` の 200（`externalRef` の再送）と、404・409 が宣言されていない | OpenAPI から生成したクライアントが、仕様どおりの応答を想定外として扱う |

## 3. スコープ

### やること

1. `plugins/sns-bluesky`：手動投稿のとき、Web Intent の URL が 2048 文字を超える本文を `validate()` で 422 `body` にする。
   あわせて、手動投稿で対になっていないサロゲートを 422 `body` にし、`manual()` がそれで例外を投げないようにする（§9.2）
2. `GET /social/accounts`・`GET /social/posts` の `page` / `perPage` を共通の `paginationSchema`（`api/query.ts`）に揃える（§6.2）
3. `GET /social/posts` の `accountId` を UUID の形に限り、それ以外を 422 `accountId` にする（§6.3）
4. ルートの定義に「追加の応答」の欄を足し、SNS の 8 操作に 200（再送）・404・409 を宣言する（§6.4）
5. 文書の書き戻し（§12）

### やらないこと

* **SNS 以外の一覧 API（`/sites`・`/users`・`/campaigns`）の `page` / `perPage`。** 調べたところ、SNS と同じく
  範囲を検査していない（`api/schemas/site.ts`・`user.ts`・`campaign.ts` が `paginationSchema` を使っていない）。
  ユーザー裁定の範囲外なので §11 の 1 に回す。**仕様書 §10.1 の 1 の「他の一覧 API は 1〜100 に丸めている」は誤り**で、
  §12 の書き戻しで直す（丸めているのは `/analytics`・`/analytics/breakdown` のルートだけ）
* **Plugin の Data API**（`socialPosts.list` / `socialAccounts.list` の `page` / `perPage` / `accountId`）。
  UseCase と Repository を変えないので振る舞いは変わらない。同じ種類の問題として §11 の 2 に回す
* **Repository の `accountId` の守り**（`infrastructure/social-repository.ts` の `listPosts` で UUID の形でなければ条件を足さない）。
  画面と Data API の経路の振る舞いを変えないため、手を付けない。API の経路は §6.3 の検査で Repository まで届かなくなる
* `GET /social/accounts?provider=` の絞り込み。**黙って外れることは無い**（32 文字以内の完全一致で、合わなければ 200 で空）ので変えない
* SNS 以外のエンドポイントの 404・409 の宣言（§11 の 3）。429 の `Retry-After` ヘッダの宣言
* Bluesky の自動配信（`auto`）での片割れのサロゲートの検査（§11 の 4）
* 登録済みの投稿の手直し（マイグレーション・一括更新）。§13 の 2
* 画面の変更。手動投稿の登録で 422 になったときは、既存の画面の入力エラーの表示にそのまま出る

## 6. API

### 6.1 変更の一覧

| エンドポイント | 変わる点 |
| --- | --- |
| `GET /social/accounts` | `page` / `perPage` の範囲外を丸める |
| `GET /social/posts` | `page` / `perPage` の範囲外を丸める。`accountId` が UUID の形でなければ 422 |
| `POST /social/posts`・`PATCH /social/posts/{id}` | provider `bluesky` の手動投稿で、URL が長すぎる本文・片割れのサロゲートを 422 `body`（配信 Plugin の検査。§9.2） |
| OpenAPI（`GET /api/v1/openapi.json`） | SNS の 8 操作の `responses` に 200・404・409 が足される |

### 6.2 `page` / `perPage`（②）

**規則：丸める。** `api/query.ts` の `paginationSchema` をそのまま使う。

| 送った値 | 変更前 | 変更後 |
| --- | --- | --- |
| 省略 | `page=1`・`perPage=20` | 同じ |
| `page=0`・`page=-3` | **500 `INTERNAL_ERROR`** | 200。`page=1` として返し、`meta.page` は `1` |
| `perPage=-1` | **500 `INTERNAL_ERROR`** | 200。`perPage=1` として返し、`meta.perPage` は `1` |
| `perPage=0` | 200、`data` は空、`meta.perPage` は `0` | 200。`perPage=1` として返し、`meta.perPage` は `1` |
| `perPage=1`〜`100` | そのまま | 同じ |
| `perPage=101`・`1000` | そのまま通り、その件数まで返る | 200。`perPage=100` として返し、`meta.perPage` は `100` |
| `page` が最終ページより先 | 200、`data` は空 | 同じ（`meta.total` は全件数） |
| `perPage=abc`・`perPage=1.5` | 422 `perPage`（`1.5` は「整数を指定してください。」、`abc` は Zod の既定の英文。2026-09-24 に検証で訂正） | 同じ |
| `page=`・`perPage=`（空文字） | `0` と解釈され、上の `0` の行と同じ | `0` と解釈され、丸めて `1` |

**丸める理由（422 にしない理由）**

1. **共通の規則として既に決まっている。** `004-api-foundation` 設計の受け入れ条件 17・18（`perPage` が 100 を超えると 100、
   `page` が 0 以下なら 1）、`api/query.ts` の `paginationSchema` のコメント（「0 ページ目や 10 万件の要求は、拒否よりも丸めるほうが親切」）、
   `domain/repository.ts` の `normalizePagination`、`/analytics`・`/analytics/breakdown` のルートがすべて丸めている。
   SNS の一覧（と `/sites`・`/users`・`/campaigns`）はこれを適用し忘れていた。**新しい規則を作らず、既にある規則に揃える**
2. **いま `perPage=1000` を送っているクライアントを壊さない。** 422 にすると、そのクライアントは一覧を 1 件も取れなくなる。
   丸めれば先頭の 100 件が返り、`meta.perPage`（100）と `meta.total` から続きのページがあることが分かる
3. 整数でない値は従来どおり 422。**打ち間違い（`perPage=abc`）は丸めずに断る**（`paginationSchema` のコメントのとおり、
   黙って既定値へ落とすと気づけない）。範囲外の整数は「意図は明らかで、上限だけが違う」ので丸める

`meta.page` / `meta.perPage` には**丸めた後の値**を返す（ルートは `query.page` / `query.perPage` をそのまま `meta` に載せており、
`paginationSchema` の変換の後の値になる）。

OpenAPI の `page` / `perPage` の parameter は、型（整数）と既定値のほか、`description` に
「1 以上。範囲外は 1 に丸める」「1〜100。範囲外は 1〜100 に丸める」と書く。**`minimum` / `maximum` は書かない**
（書くと、範囲外を送ったら断られると読めてしまい、実際の振る舞い（丸める）と食い違う）。

### 6.3 `accountId`（③）

**規則：UUID の形でない値は 422 `accountId`。**

「UUID の形」は `infrastructure/social-repository.ts` の `UUID_PATTERN` と同じ判定にする：
**8-4-4-4-12 の 16 進、大文字・小文字を問わない、版（version）と variant は見ない。**
API が受け付ける値と Repository が絞り込みに使う値を一致させるため（Zod の `z.uuid()` は版と variant を見るので、
Repository が絞り込める ID を API が断りうる。`z.guid()` は同じ判定なので使ってよい）。

| 送った値 | 変更前 | 変更後 |
| --- | --- | --- |
| 省略 | 全件 | 同じ |
| 存在するアカウントの UUID（大文字を含んでもよい） | そのアカウントの投稿 | 同じ |
| UUID の形だが存在しない | 200、`data` は空 | 同じ |
| `abc`・`123`・36 文字で 16 進でない文字を含む値 | **絞り込みが外れて全件** | **422 `accountId`**（「UUID の形で指定してください。」） |
| 空文字（`accountId=`） | **絞り込みが外れて全件** | **422 `accountId`** |
| 65 文字以上 | 422 `accountId`（Zod の既定の英文） | 422 `accountId`（上と同じ文言） |

**422 にする理由（200 で空にしない理由）**

* `api/query.ts` の方針（「黙って既定値へ落とすと、打ち間違いに気づけない」「無視しない」）と、同じ一覧の `status`
  （列挙外は 422）に揃う。**絞り込みの値の形の誤りは入力の誤り**であり、「該当なし」とは区別して返す
* 200 で空（`/analytics` の `siteId` の扱い）にすると、外部アプリは「そのアカウントにはまだ投稿が無い」と読み違える
* **空文字も 422 にする。** 「空なら未指定」という例外を 1 つ作るより、「値を送ったら UUID の形」という 1 つの規則のほうが
  外部アプリが迷わない。同じ一覧の `status=`（空文字）も既に 422 である

**同じ種類の問題がほかの絞り込みに無いか**：SNS の 2 つの一覧を見た結果は次のとおりで、③のほかに直すものは無い。

| 絞り込み | いまの振る舞い | 判断 |
| --- | --- | --- |
| `GET /social/posts?status=` | 列挙外は 422 `status` | 変えない |
| `GET /social/accounts?provider=` | 32 文字以内の完全一致。合わなければ 200 で空。33 文字以上は 422 | 変えない（絞り込みは外れない。provider は Plugin が増やせる開いた集合なので、形の検査も足さない） |
| `{id}`（パス） | UUID の形でなければ 404 | 変えない（仕様書 §3.3 に書いてある） |

### 6.4 OpenAPI の追加の応答（④）

**ルートの定義で明示する。** 生成器が「パスに `{id}` があれば 404」のように推し量る案は採らない
（SNS 以外のエンドポイントの文書まで変わり、裁定の範囲を越える。推し量りは実態とずれうる）。

`RouteDefinition`（`api/route.ts`）と `EndpointSpec`（`api/registry.ts`）に任意の欄を足す。

```ts
/** 成功・共通のエラー以外に、この操作が返しうる応答（05_API設計.md §40）。 */
readonly additionalResponses?: readonly {
  readonly status: 200 | 404 | 409;
  /** OpenAPI の description にそのまま出す。 */
  readonly description: string;
}[];
```

* `openapi.ts` の `responsesFor` は、`additionalResponses` の各要素を `responses[String(status)]` に足す
  * **200** の `content` は、その操作の `response`（成功の応答スキーマ）と同じ
  * **404 / 409** の `content` は、既存の 422 などと同じエラーの形（`errorEnvelopeSchema`）
* `defineRoute` は次のとき `RouteDefinitionError` を投げる（定義の誤りを起動時に見つける）
  * `status` が `successStatus`（既定 200）と同じ
  * 同じ `status` が 2 回ある
  * `status: 200` なのに `response` が無い
* 欄を書かない操作の `responses` は**変わらない**（既存の全エンドポイントの OpenAPI は 042 の前と同じ）

SNS の 11 操作に書く値：

| operationId | 追加する応答 | description |
| --- | --- | --- |
| `createSocialPost` | 200 | 同じ `externalRef` の再送。既存の投稿を返す（新しい投稿は作らない） |
| `getSocialAccount`・`updateSocialAccount`・`deleteSocialAccount` | 404 | アカウントが存在しない（UUID の形でない ID を含む） |
| `getSocialPost`・`updateSocialPost`・`deleteSocialPost` | 404 | 投稿が存在しない（UUID の形でない ID を含む） |
| `publishSocialPosts` | 409 | 他の配信処理が実行中（`details.job` と `Retry-After: 10` が付く） |
| `listSocialAccounts`・`listSocialPosts`・`createSocialAccount` | なし | — |

* `POST /social/posts` で `socialAccountId` が存在しないときは 422（404 ではない）なので、`createSocialPost` に 404 は足さない
* 409 は `JobBusyError` からだけ出る。SNS の Use Case は `ConflictError` を投げない（調べた）ので、`publishSocialPosts` 以外に 409 は足さない
* `summary` の「（同じ externalRef の再送は 200 で既存を返す）」は残す。`posts/route.ts` の
  「`successStatus` は 1 つしか宣言できないので、OpenAPI は 201 のまま。」のコメントは実態に合わせて直す
* `openapi-coverage.test.ts` の `RESPONSE_SCHEMA_PENDING`（応答スキーマが未宣言の操作の一覧）は**変わらない**
  （SNS の 11 操作はすでに応答スキーマを持つ。この一覧はエラー応答の宣言を見ていない）

### 6.5 互換性（外部アプリへの影響）

| 変更 | 外部アプリから見た変化 | 破壊的か |
| --- | --- | --- |
| ① Bluesky 手動投稿の URL の長さ・片割れ | いままで 201 だった登録が 422 `body` になる | **破壊的としない。** 通っていた登録は「投稿画面を開く」が必ず失敗する投稿を作っていた。失敗が予約時刻から登録時へ前倒しになるだけ |
| ② `page` ≤ 0・`perPage` ≤ -1 | 500 → 200 | 破壊的でない（誤りの修正） |
| ② `perPage=0` | 200 で空 → 200 で 1 件 | 破壊的でない（空を期待する使い方に意味が無い） |
| ② `perPage` ≥ 101 | 要求した件数まで → **100 件まで** | **動作の変更。** 1 回で全件を取る前提のクライアントは 101 件目以降を取りこぼす。`meta.perPage` が 100 になるので検知でき、`meta.total` までページを送れば全件取れる。仕様書は初版から「1〜100 で送る」と書いている |
| ③ `accountId` の形の誤り（空文字を含む） | 200 で全件 → **422** | **動作の変更。** ただし従来の応答は「絞り込んだつもりの全件」で誤っていた。仕様書は初版から「送る前に UUID の形を確かめる」と書いている |
| ④ OpenAPI | `responses` にキーが増えるだけ | 破壊的でない（追加） |

* **API Version は v1 のまま出す**（`05_API設計.md` §41 の「新しい Version を出す」には当たらないと判断する）。
  ②の 101 以上と③は応答が変わるが、どちらも仕様書が初版（2026-09-24）から禁じていた送り方で、
  かつ従来の応答が誤り（500・誤った全件）か共通の規則からの逸脱だったため。
