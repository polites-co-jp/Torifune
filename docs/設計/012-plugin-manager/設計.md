# Plugin Manager 設計

## 1. 目的

管理画面から Plugin を扱えるようにする。

`011-plugin-runtime` で Plugin は動くようになったが、**導入・有効化する手段が
DB を直接触る以外に無い**。運用できる状態にする。

D-02 で決めたとおり、Plugin の読み込みはビルド時に固定される。
そのため導入・削除は**再ビルドと再起動を伴う**。この重さを画面の設計に織り込む。

## 3. スコープ

### やること

* Plugin 管理画面（`/plugins`）
  * インストール済みの一覧（名前 / バージョン / 状態 / 要求 Permission）
  * 検出済み・未導入の一覧（`plugins/` にあるが `plugins` テーブルに行が無いもの）
  * 読み込めなかったものと、その理由
* 有効化・無効化・削除
* **Plugin Package（zip）のアップロードによる導入**
* 要求 Permission の導入前表示と同意
* 再ビルド・再起動の進行状況と、失敗時の表示
* ビルドに失敗したときに直前の成功状態へ戻ること
* 削除時に「Plugin 本体 / データ」を区別し、データ削除に明示的な確認を要求する
* Plugin の設定画面への導線

### やらないこと

| 対象 | 理由 |
| --- | --- |
| Plugin Registry（マーケット）からの取得 | 仕様書 03 §14.1。取得元の信頼性を検証する仕組みが要る |
| Git からの取得 | 同 §14.3。同上 |
| Plugin Package の署名検証 | 上の2つとまとめて設計する |
| Plugin の設定画面そのもの | Plugin 側が `registerPage` で作る。→ `013` |
| Plugin の更新（バージョン上げ） | 導入と同じ経路だが、データ移行の設計が別に要る |

## 4. インストール経路（2つ）

決定：**ZIP アップロードとローカル配置の2つ**を実装する。

```text
(A) ZIP アップロード           (B) ローカル配置
    管理画面から選択                plugins/ へ直接置く
         │                              │
         ▼                              │
    展開して plugins/ へ                │
         │                              │
         └──────────┬───────────────────┘
                    ▼
            Manifest 検証     ← ここで落ちたらビルドに入らない
                    ▼
          要求 Permission の表示
                    ▼
                  同意
                    ▼
          plugins テーブルへ行を作る（installed）
                    ▼
             再ビルド要求 → 終了コード 75
                    ▼
       entrypoint がレジストリ再生成 → 再ビルド → 再起動
```

(B) は開発者向け。仕様書 03 §14.2 の「ローカル Plugin」にあたる。

## 5. レイヤ配置

```text
app/plugins/page.tsx                     一覧・操作
app/plugins/upload/page.tsx              追加（アップロード）
ui/plugin/plugin-manager.tsx             一覧の描画
ui/plugin/permission-consent.tsx         要求 Permission の表示と同意
ui/plugin/rebuild-progress.tsx           進行状況（再起動を跨ぐ）
api/v1/plugins/**                        操作の API
application/plugin/plugin-use-cases.ts   認可つき UseCase
plugin/package.ts                        Plugin Package の展開と検証
plugin/operations.ts                     操作の記録（再起動を跨いで結果を伝える）
plugin/rebuild.ts                        再ビルド要求
```

**Plugin Package の展開は `plugin/` に置く。** `infrastructure/` ではない。
Plugin の形式を知っているのは Plugin 層だけにする。

## 6. データモデル

### `plugin_operations`（`migrations/009_plugin_operations.sql`）

**再起動を跨いで結果を伝えるために要る。**
再ビルドの最中はプロセスが落ちているため、メモリ上の進行状況は消える。

```sql
CREATE TABLE plugin_operations (
    id          uuid        PRIMARY KEY,
    plugin_id   text        NOT NULL,
    kind        text        NOT NULL,   -- install | uninstall
    status      text        NOT NULL,   -- pending | restarting | succeeded | failed
    message     text,
    requested_by uuid       NOT NULL REFERENCES users (id),
    started_at  timestamptz NOT NULL DEFAULT now(),
    finished_at timestamptz
);
```

`enable` / `disable` はここに載せない。**再ビルドが要らない**（レジストリは
すでにビルドに含まれている）ため、その場で終わる。

### 状態の流れ

```text
pending ──ファイル配置と検証が済んだ──→ restarting ──再起動後の確認──→ succeeded
   │                                          │
   └──検証で落ちた──→ failed                  └──ビルドが失敗していた──→ failed
```

## 7. 再ビルドと再起動

### 7.1 誰が何をするか

| 担当 | すること |
| --- | --- |
| アプリ | ファイルを `plugins/` へ置く。DB へ行と操作を書く。sentinel を書いて終了コード 75 |
| entrypoint | レジストリ再生成 → ビルド → 失敗したら直前の成功ビルドへ戻す → 起動 |
| アプリ（起動後） | `restarting` のまま残った操作を見て、成否を判定して閉じる |

**アプリはレジストリを生成しない。** 生成の実体は
`scripts/generate-plugin-registry.mjs` ひとつに保つ。2箇所にあると必ずずれる。

### 7.2 ビルドが失敗したとき

entrypoint は直前の成功ビルドへ戻して起動する。
戻ったビルドには**新しい Plugin が含まれていない**。

起動後、アプリは `restarting` の操作を見つけ、対象の Plugin が
読み込まれているかを確かめる。読み込まれていなければビルドが失敗したと判断し、

1. 操作を `failed` にする
2. **その Plugin を隔離する**（`plugins/<id>/.torifune-quarantine` を置く）
3. `plugins` テーブルの行を消す

隔離しないと、**次の再ビルドも同じ Plugin で失敗し続ける**。
ファイルは消さずに残す。原因を調べられなくなる。

`scripts/generate-plugin-registry.mjs` は隔離マークのあるディレクトリを飛ばす。

### 7.3 開発環境

`next dev` には entrypoint の監視ループが無い。
自分を落としても誰も起こしてくれない。

環境変数 `TORIFUNE_SELF_RESTART` が `1` のときだけ終了コード 75 で落ちる。
そうでなければ操作を `pending` のままにして、
画面に「`pnpm dev` を再起動してください」と出す。

`pnpm dev` は `generate:plugins` を先に走らせるため、再起動すれば反映される。

## 8. Plugin Package（zip）

### 8.1 形式

```text
example-plugin.zip
└── example-plugin/      ← ディレクトリ名 = Plugin ID
    ├── plugin.json
    ├── index.ts
    └── ...
```

**単一のトップレベルディレクトリを要求する。** 複数あると、どれが Plugin か
決められない。ディレクトリ名と `plugin.json` の `id` の一致は `011` と同じ規則。

### 8.2 展開時に拒否するもの

**Plugin の導入は実質的にアプリへのコード導入**であり、実行するコードの中身は
信頼する前提に立つ。ただし**展開そのもの**は攻撃面になるため、
Plugin の外へ書き込ませない。

| 拒否するもの | 理由 |
| --- | --- |
| `..` を含むパス | `plugins/` の外へ書き込める |
| 絶対パス（`/x`、`C:\x`） | 同上 |
| シンボリックリンク | 展開後にリンク経由で外を読み書きできる |
| 展開後の合計サイズが上限超え | zip bomb でディスクを埋められる |
| ファイル数が上限超え | 同上 |
| トップレベルが1ディレクトリでない | どれが Plugin か決められない |
| すでに同じ ID がある | 黙って上書きすると、動いている Plugin が入れ替わる |

**すべての名前を検証してから、1バイトも書かない。**
途中まで書いてから弾くと、壊れた状態が残る。

上限は `TORIFUNE_PLUGIN_MAX_BYTES`（既定 32 MiB）と
`TORIFUNE_PLUGIN_MAX_FILES`（既定 2000）。

## 9. API

すべて `plugin.manage` を要求する。認可は UseCase 側（D-06）。

| メソッド | パス | 内容 |
| --- | --- | --- |
| GET | `/api/v1/plugins` | 一覧（インストール済み / 検出済み / 読み込めなかったもの） |
| POST | `/api/v1/plugins` | 導入（`pluginId` を指定。ファイルは配置済み） |
| POST | `/api/v1/plugins/upload` | Plugin Package の受け取りと展開。**導入はしない** |
| POST | `/api/v1/plugins/{id}/enable` | 有効化 |
| POST | `/api/v1/plugins/{id}/disable` | 無効化 |
| DELETE | `/api/v1/plugins/{id}` | 削除（`deleteData` を指定） |
| GET | `/api/v1/plugins/operations/{id}` | 操作の状況 |

`upload` と `install` を分ける。**要求 Permission を見せてから同意させる**ため、
展開して Manifest を読む段階と、導入を確定する段階を分ける必要がある。

## 10. 画面

### 10.1 一覧（`/plugins`）

```text
Plugin管理                              [Pluginを追加]

インストール済み
┌────────────────────────────────────────────────┐
│ とりふねSEO  1.2.0   有効   [無効化] [設定] [削除] │
│   要求: site.read, seo-plugin.report.read       │
├────────────────────────────────────────────────┤
│ サンプル      0.1.0   無効   [有効化]      [削除] │
└────────────────────────────────────────────────┘

検出済み（plugins/ にあるが未導入）
┌────────────────────────────────────────────────┐
│ 新しいPlugin 0.1.0          [導入]              │
└────────────────────────────────────────────────┘

読み込めなかったPlugin
┌────────────────────────────────────────────────┐
│ broken   id: 形式が不正                          │
└────────────────────────────────────────────────┘
```

読み込めなかったものを**画面に出す**。黙って消すと、
「置いたはずの Plugin が出てこない」理由が分からない。

### 10.2 導入（要求 Permission の同意）

`06_画面設計.md` §39 のとおり、導入前に要求 Permission を見せる。

```text
とりふねSEO 1.2.0 を導入します

この Plugin は次の権限を要求しています。

  site.read                 Webサイトの閲覧
  seo-plugin.report.read    （この Plugin が定義する権限）

導入すると Torifune は再ビルドと再起動を行います。
その間、数分ほど利用できません。

[キャンセル] [同意して導入]
```

**「再起動する」ことを先に伝える。** 押したあとに落ちると障害に見える。

### 10.3 進行状況

```text
再ビルド中…

  ✓ ファイルを配置した
  ✓ Manifest を検証した
  ● 再ビルドしています（数分かかります）

このページは自動で更新されます。
```

`/api/v1/plugins/operations/{id}` を一定間隔で叩く。
**再ビルド中は応答が返らない**ため、通信の失敗は「まだ落ちている」とみなして
待ち続ける。一定時間で諦め、確認を促す。

### 10.4 削除

`06_画面設計.md` §37・§41。

```text
サンプル を削除します

  ☐ この Plugin が保存したデータも削除する
     （設定・保存内容がすべて消えます。元に戻せません）

削除するには Plugin 名を入力してください
  [                    ]

[キャンセル] [削除]
```

データ削除は**既定でチェックしない**。押し間違いで消えるものを既定にしない。

## 11. 権限

`plugin.manage` のみ。`010`・`011` で追加はしない。

**`plugin.manage` はインスタンス管理者の権限である。**
Plugin の導入はアプリへのコード導入にあたるため、
サイト運用者に配ってよいものではない。

## 12. 受け入れ条件

### 認可

1. `plugin.manage` を持たないユーザーが `/plugins` を開けない
2. 同 API がすべて 403
3. 未認証がすべて 401
4. ID を差し替えても他の操作の状況が見えない

### 一覧

5. インストール済みの Plugin が名前・バージョン・状態つきで出る
6. 検出済み・未導入の Plugin が出る
7. 読み込めなかった Plugin が理由つきで出る
8. 各 Plugin の要求 Permission が出る

### 有効化・無効化

9. 有効化すると `enabled` になり、画面に反映される
10. 無効化すると `disabled` になる
11. **有効化・無効化では再ビルドが起きない**
12. 依存を満たさない Plugin を有効化できない
13. 依存されている Plugin の無効化で、依存元も無効化されることが画面に出る

### 導入

14. 不正な Manifest の Plugin は**ビルドに入る前に**拒否される
15. 要求 Permission が導入前に表示される
16. 同意しなければ導入されない
17. 導入すると `plugins` に `installed` の行ができる
18. 導入は再ビルドを要求する
19. `TORIFUNE_SELF_RESTART` が無い環境では落ちず、案内が出る

### Plugin Package

20. 正しい zip を展開できる
21. `..` を含むパスを拒否する
22. 絶対パスを拒否する
23. シンボリックリンクを拒否する
24. 合計サイズの上限を超える zip を拒否する
25. ファイル数の上限を超える zip を拒否する
26. トップレベルが1ディレクトリでない zip を拒否する
27. すでにある Plugin ID を拒否する
28. **拒否したとき、1バイトも書かれていない**
29. ディレクトリ名と Plugin ID の不一致を拒否する

### 再ビルドの失敗

30. ビルドに失敗しても、再起動後に直前の正常な状態で立ち上がる
31. 失敗した操作が `failed` として画面に出る
32. **失敗した Plugin が隔離され、次の再ビルドを壊さない**
33. 隔離された Plugin のファイルは消えていない

### 削除

34. 削除すると `plugins` から行が消える
35. データを残す指定なら `plugin_store` が消えない
36. データを消す指定なら `plugin_store` も消える
37. データ削除には明示的な確認が要る
38. 有効な Plugin を削除すると、先に無効化される
