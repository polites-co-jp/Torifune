# 04_認証設計.md

## 1. 目的

本ドキュメントでは、Torifune OSSにおける認証・認可の基本方針と、認証方式を拡張するための仕組みを定義する。

Torifune OSSは単体で利用可能な認証機能を標準提供するとともに、Pluginによって外部認証基盤へ接続できる構造とする。

---

## 2. 基本方針

Torifune OSSでは、以下を基本方針とする。

1. Torifune単体でログイン・ログアウトが完結すること
2. 認証処理をTorifuneの各機能から分離すること
3. 認証方式をAuthentication Providerとして抽象化すること
4. Pluginによって認証方式を差し替えられること
5. 認証済みユーザーの識別情報を、Torifune内部で統一的に扱えること
6. 認証と認可を分離すること
7. パスワードや認証Token等の機密情報を安全に管理すること

---

## 3. 認証と認可

認証（Authentication）と認可（Authorization）は別の責務として扱う。

### 認証

「誰であるか」を確認する処理。

```text
ユーザー
  ↓
ログイン
  ↓
Authentication Provider
  ↓
認証成功
  ↓
User Identity
```

### 認可

「そのユーザーが何をしてよいか」を判定する処理。

```text
User Identity
     ↓
Authorization
     ↓
Permission / Role
     ↓
操作を許可・拒否
```

認証方式を変更しても、Torifune内部の認可処理は可能な限り変更せずに利用できる構造とする。

---

## 4. 認証アーキテクチャ

認証処理はAuthentication Provider Interfaceを介して利用する。

```text
┌──────────────────────────────┐
│       Torifune Core      │
│                              │
│ Application / Authorization  │
└──────────────┬───────────────┘
               │
               ▼
     Authentication Interface
               │
       ┌───────┴────────┐
       ▼                ▼
Default Provider   Plugin Provider
       │                │
       ▼                ▼
   Local Auth       OIDC / OAuth
```

Torifune Coreは、具体的な認証方式を直接認識しない。

---

## 5. 標準認証

Torifune OSSは、外部認証サービスを必要としない標準認証を提供する。

標準認証では、Torifuneがユーザー情報および認証情報を管理する。

基本的な認証フローは以下とする。

```text
Browser
   │
   │ Login
   ▼
Torifune
   │
   │ Credentials
   ▼
Authentication Provider
   │
   │ Verify
   ▼
User Database
   │
   ▼
Authenticated User
   │
   ▼
Session
```

---

## 6. パスワード管理

ユーザーのパスワードは平文で保存しない。

データベースには、安全なPassword Hashのみを保存する。

```text
Password
   │
   ▼
Password Hash Function
   │
   ▼
Password Hash
   │
   ▼
Database
```

パスワードハッシュアルゴリズムは、実装時点で十分な安全性を持つ方式を採用する。

候補としてArgon2id等を検討する。

パスワード検証時には、入力されたパスワードを同じ方式で検証し、保存されたHashと比較する。

---

## 7. セッション管理

認証成功後は、ユーザーの認証状態を維持するためのセッションを作成する。

基本構成は以下とする。

```text
Browser
   │
   │ Secure Cookie
   ▼
Torifune
   │
   ▼
Session
   │
   ▼
User Identity
```

セッションCookieには、ユーザー情報そのものやデータベース接続情報等を格納しない。

Cookieには、セッションを特定するためのランダムで推測困難な識別子のみを保持する方式を基本とする。

---

## 8. セッションCookie

認証セッションに使用するCookieには、以下の属性を設定する。

* `Secure`
* `HttpOnly`
* `SameSite`

HTTPS環境では必ず`Secure`を利用する。

`HttpOnly`を設定することで、JavaScriptからセッションCookieを直接取得できないようにする。

`SameSite`については、Torifuneの利用形態に応じて適切な値を設定する。

---

## 9. セッション固定攻撃対策

ログイン前後で同一のセッション識別子を使用し続けることは避ける。

ログイン成功時にはセッションIDを再生成する。

```text
Before Login
     │
     ▼
Session ID A
     │
   Login
     │
     ▼
Session ID B
     │
     ▼
Authenticated Session
```

これにより、Session Fixation攻撃への対策とする。

---

## 10. ログアウト

ログアウト時には、サーバー側の認証セッションを無効化する。

```text
Authenticated Session
        │
        ▼
      Logout
        │
        ▼
Session Revoked
```

ブラウザ側のセッションCookieも削除する。

---

## 11. セッション有効期限

セッションには有効期限を設定する。

最低限、以下を区別できる設計とする。

* セッションの有効期限
* アイドルタイムアウト
* Remember Me等の長期ログイン

長期セッションを利用する場合は、通常のセッションとは異なるToken管理方式を検討する。

---

## 12. CSRF対策

Cookieベースの認証を利用する場合、CSRF対策を実装する。

基本的には、状態を変更するHTTPリクエストに対してCSRF Tokenを利用する。

```text
Browser
   │
   ├── Session Cookie
   │
   └── CSRF Token
          │
          ▼
      Torifune
```

GET等の安全なHTTPメソッドと、POST/PUT/PATCH/DELETE等の状態変更処理を適切に区別する。

---

## 13. XSS対策

認証セッションを保護するため、XSS対策を実施する。

特に以下を基本とする。

* セッションCookieへの`HttpOnly`設定
* ユーザー入力値の適切なエスケープ
* HTMLへの直接出力を避ける
* Content Security Policy（CSP）の導入を検討する
* JavaScriptへ機密情報を渡さない

Pluginによって追加された画面についても、同じセキュリティ原則を適用する。

---

## 14. 認可

認証されたユーザーに対して、Torifune内部の権限モデルに基づいて操作可否を判定する。

基本構成はRBAC（Role-Based Access Control）を採用する。

```text
User
  │
  ▼
Role
  │
  ▼
Permission
```

例えば、

```text
Administrator
├── user.manage
├── site.manage
├── content.manage
├── social.manage
└── system.manage

Editor
├── site.read
├── content.read
├── content.write
└── social.write
```

具体的なRoleおよびPermissionは、機能要件に応じて定義する。

---

## 15. Authentication Provider

Authentication Providerは、Torifuneの認証方式を抽象化するためのPlugin Extension Pointである。

基本的なInterfaceとして、以下のような責務を想定する。

```text
AuthenticationProvider
├── authenticate()
├── logout()
├── getIdentity()
└── refresh()
```

実際のInterface名・メソッド名は実装言語およびフレームワーク確定後に決定する。

Authentication Providerは、認証処理を実行した結果をTorifune共通のUser Identityへ変換する。

---

## 16. User Identity

認証方式にかかわらず、Torifune内部では統一されたUser Identityを利用する。

```text
Local Authentication
       │
       ▼
   User Identity
       ▲
       │
OIDC Authentication
```

User Identityには、例えば以下の情報を持たせる。

* Torifune User ID
* 外部認証Provider ID
* 外部ユーザーID
* 表示名
* メールアドレス
* 認証済み状態

ただし、外部Provider固有の情報をTorifune Coreが直接扱うことは避ける。

---

## 17. OpenID Connect

外部認証との連携では、OpenID Connect（OIDC）を第一候補とする。

SaaS版では、ユーザー管理アプリケーションをOIDC Providerとして動作させ、Torifune側にOIDC Authentication Provider Pluginを実装する構成を想定する。

```text
┌──────────────────┐
│ User Browser     │
└────────┬─────────┘
         │
         │ Authentication
         ▼
┌──────────────────┐
│ User Management  │
│ OIDC Provider    │
└────────┬─────────┘
         │
         │ ID Token / Authorization Code
         ▼
┌──────────────────┐
│ Torifune     │
│ OIDC Plugin      │
└──────────────────┘
```

Torifuneは、ユーザー管理アプリケーションの認証情報そのものを保持せず、OIDCによって認証結果を受け取る。

---

## 18. OAuth 2.0との関係

OAuth 2.0は主に「認可」を扱うプロトコルであり、ユーザー認証そのものを目的としたプロトコルではない。

そのため、Torifuneのユーザー認証に外部Identity Providerを利用する場合は、OAuth 2.0単体ではなく、OpenID Connectを利用することを基本とする。

```text
OAuth 2.0
  └── Authorization

OpenID Connect
  └── Authentication
```

外部サービスのAPIアクセス権を取得する目的では、OAuth 2.0を利用するPluginを別途実装できる。

---

## 19. SaaS版における認証

Torifune SaaSでは、SaaS側のユーザー管理システムをIdentity Providerとして利用する。

```text
Torifune SaaS
│
├── User Management
│
├── OIDC Provider
│
└── Torifune
      │
      └── OIDC Authentication Plugin
```

Torifune OSS本体には、SaaS固有のユーザー管理ロジックを実装しない。

---

## 20. 認証とDatabase選択の分離

Torifune OSSでは、認証とDatabase接続を別の責務として扱う。

```text
Authentication
      │
      ▼
User Identity
      │
      ├──────────────────┐
      │                  │
      ▼                  ▼
Authorization      Database Provider
```

SaaS版では、認証されたUser IdentityやTenant情報を利用してDatabase Providerが接続先を決定することが可能となる。

ただし、Torifune Coreの認証処理が直接Databaseを選択することはない。

この分離により、OSS版では単一Databaseを利用し、SaaS版ではPluginによってTenant単位のDatabase構成へ拡張できる。

---

## 21. 認証情報の受け渡し

Torifune SaaSとTorifune OSSの間で認証情報を連携する場合、認証情報そのものを独自方式で受け渡すのではなく、標準プロトコルを利用する。

第一候補はOpenID Connectとする。

```text
Browser
   │
   │ 1. Login Request
   ▼
User Management / OIDC Provider
   │
   │ 2. Authentication
   │
   │ 3. Authorization Code
   ▼
Browser
   │
   │ 4. Callback
   ▼
Torifune OIDC Plugin
   │
   │ 5. Token Exchange
   ▼
OIDC Provider
   │
   │ 6. ID Token / UserInfo
   ▼
Torifune
```

Torifuneがユーザー管理アプリケーションのセッションCookieを直接受け取ったり、セッション情報を共有したりする方式は採用しない。

---

## 22. Token管理

外部認証で利用するTokenは、用途を明確に区別する。

### ID Token

ユーザーが誰であるかを確認するために利用する。

### Access Token

外部APIへのアクセス権を利用するために使用する。

### Refresh Token

Access Tokenを更新するために使用する。

Torifuneのログイン処理では、ID Tokenをユーザー認証結果として利用し、Torifune自身のセッションを確立する方式を基本とする。

---

## 23. Token検証

OIDC等の外部認証を利用する場合、受け取ったTokenを無条件に信頼しない。

少なくとも以下を検証する。

* 発行者（Issuer）
* Audience
* 有効期限
* 署名
* nonce等、フローに応じた検証項目
* 必要なClaim

OIDC DiscoveryおよびJWKSを利用して、Providerの公開鍵情報を取得・管理する方式を基本とする。

---

## 24. パスワードリセット

標準認証では、パスワードを忘れたユーザーが安全にパスワードを再設定できる機能を提供する。

基本フロー：

```text
Login Page
    │
    ▼
Forgot Password
    │
    ▼
Reset Token発行
    │
    ▼
メール等による通知
    │
    ▼
Reset Token検証
    │
    ▼
新しいパスワード設定
```

Password Reset Tokenは、

* 十分なランダム性を持つ
* 有効期限を持つ
* 一度使用したら無効になる
* 平文で永続保存しない

ことを基本とする。

---

## 25. ログイン試行制限

総当たり攻撃やCredential Stuffingへの対策として、ログイン試行回数を制限する。

例えば以下を検討する。

* IPアドレス単位のRate Limit
* アカウント単位のRate Limit
* 一定回数失敗後の遅延
* CAPTCHA等の追加認証
* 異常なログイン試行の記録

具体的な閾値は運用環境および実装時に決定する。

---

## 26. セキュリティログ

認証・認可に関する重要な操作を監査ログとして記録する。

対象例：

* ログイン成功
* ログイン失敗
* ログアウト
* パスワード変更
* パスワードリセット
* ユーザー作成
* ユーザー無効化
* Role変更
* Permission変更
* 外部認証連携設定変更

ログにはパスワード、Access Token、Refresh Token等の機密情報を記録しない。

---

## 27. Plugin Security

Authentication Provider Pluginは、Torifuneの認証処理を担う高権限Pluginである。

そのため、通常のPluginよりも厳格に扱う。

Authentication Provider Pluginでは特に以下を考慮する。

* 認証結果の改ざん防止
* Token検証
* Redirect URI検証
* CSRF対策
* State検証
* OIDCの場合のNonce検証
* Secretの安全な管理
* HTTPSの利用

---

## 28. 権限昇格対策

認証済みユーザーのIdentity情報を、ユーザーから自由に変更できる情報として扱わない。

特に以下はサーバー側で管理する。

* User ID
* Role
* Permission
* Tenant ID
* Authentication Provider
* 外部ユーザーID

クライアントから送信されたUser IDやRoleをそのまま信頼して認可判定を行ってはならない。

---

## 29. SaaS環境でのTenant分離

Torifune OSS自体は、マルチテナント構成を必須としない。

SaaS版でTenant単位のDatabaseを利用する場合は、Authentication Providerによって確定したIdentityと、SaaS側で管理するTenant情報を利用してDatabase Providerが接続先を決定する。

```text
User
 │
 ▼
OIDC Authentication
 │
 ▼
User Identity
 │
 ▼
Tenant Resolution
 │
 ▼
Database Provider
 │
 ▼
Tenant Database
```

重要なのは、**クライアントから送信されたTenant IDだけを根拠にDatabaseを選択しないこと**である。

TenantとUserの関係は、信頼された認証情報およびSaaS側の管理情報からサーバー側で確定する。

---

## 31. 設計上の原則

Torifune OSSの認証設計では、以下を原則とする。

1. Torifune単体で認証できること
2. AuthenticationとAuthorizationを分離すること
3. 認証方式をAuthentication Providerとして抽象化すること
4. 認証後のユーザー識別情報をUser Identityとして統一すること
5. パスワードを平文で保存しないこと
6. セッションCookieをSecure・HttpOnly等の適切な属性で保護すること
7. ログイン時にセッションIDを再生成すること
8. Cookieベースの認証ではCSRF対策を行うこと
9. 外部認証には原則としてOpenID Connectを利用すること
10. OAuth 2.0とOpenID Connectの用途を混同しないこと
11. 外部認証Tokenを無条件に信頼しないこと
12. 認証情報とDatabase接続方式を分離すること
13. クライアントから送信されたUser IDやTenant IDをそのまま信頼しないこと
14. SaaS固有の認証・Tenant管理をTorifune OSS本体に持ち込まないこと
15. Authentication Providerを高権限Pluginとして扱うこと
