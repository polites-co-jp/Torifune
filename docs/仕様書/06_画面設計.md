# 06_画面設計.md

## 1. 目的

本ドキュメントでは、Torifune OSSのWeb画面に関する基本設計を定義する。

Torifuneは、標準機能だけでなくPluginによって画面を追加・拡張できる構造とする。

そのため、画面そのものの設計だけでなく、Pluginが既存のナビゲーション、メニュー、ページ、ウィジェット等へ安全にアクセスできる仕組みを定義する。

---

## 2. 基本方針

Torifuneの画面は以下を基本方針とする。

1. Torifune単体で基本的な操作が完結すること
2. Web UIとAPIを分離すること
3. Pluginによって画面を追加できること
4. Pluginが既存画面へUI要素を追加できること
5. Plugin独自の設定画面を追加できること
6. ユーザーのPermissionに応じて表示・操作可能なUIを制御すること
7. 画面から直接Databaseへアクセスしないこと
8. 共通UIコンポーネントを利用することで、PluginによるUI追加でも統一感を維持すること
9. OSS版とSaaS版で基本UIを共有できる構造とすること
10. SaaS固有の画面はPluginによって追加できる構造とすること
11. 画面表示で日本語を表示する場合、サービス名はひらがなで「とりふね」とすること

---

## 3. 画面アーキテクチャ

画面は以下のレイヤーで構成する。

```text
┌──────────────────────────────┐
│          Browser             │
└──────────────┬───────────────┘
               │
               ▼
┌──────────────────────────────┐
│          Web UI              │
│                              │
│ Layout                       │
│ Pages                        │
│ Components                   │
│ Plugin UI                    │
└──────────────┬───────────────┘
               │
               ▼
┌──────────────────────────────┐
│          API Layer           │
└──────────────┬───────────────┘
               │
               ▼
┌──────────────────────────────┐
│      Application Layer       │
└──────────────────────────────┘
```

画面コンポーネントからDatabaseへ直接アクセスすることは原則として禁止する。

---

## 4. 画面構成

Torifuneの基本画面は以下を想定する。

```text
Torifune
├── ログイン
├── ダッシュボード
├── Webサイト
├── SNS
├── キャンペーン
├── アナリティクス
├── 設定
└── Plugin
```

具体的な機能・画面は実装の進行に応じて追加する。

---

## 5. ログイン画面

標準認証を利用する場合、ログイン画面を提供する。

```text
┌─────────────────────────┐
│        とりふね         │
│                         │
│  ログインID             │
│  [___________________]  │
│                         │
│  パスワード             │
│  [___________________]  │
│                         │
│ [ ] ログインしたままにする│
│                         │
│  [      ログイン      ] │
│                         │
│  パスワードを忘れた場合 │
└─────────────────────────┘
```

**識別子はメールアドレスではなく「ログインID」とする。**
メールアドレスを識別子にすると、変更のたびにログイン手段が変わり、
外部の認証Pluginが持つ識別子との対応付けも壊れやすい。
メールアドレスは通知の宛先として別に持つ。

「ログインしたままにする」（Remember Me）は管理者が禁止でき、
禁止されている場合はこの項目自体を出さない（§16 認証タブ）。

ログイン画面には、認証方式に応じてPluginが追加のログイン手段を提供できる。

例えばOIDC Pluginによって、

```text
[ Googleでログイン ]
[ SSOでログイン ]
```

等を追加できる構造とする。

---

## 6. ログイン画面とAuthentication Provider

ログイン画面はAuthentication Providerの具体的な実装を直接扱わない。

```text
Login UI
   │
   ▼
Authentication Service
   │
   ▼
Authentication Provider
```

これにより、標準認証からOIDC等へ変更しても画面側の基本構造を維持できる。

## 10. Widget

PluginはDashboard等の既存画面へWidgetを追加できる。

```text
Dashboard
├── Core Widget
│   ├── Access Summary
│   └── Recent Activity
│
└── Plugin Widget
    ├── SNS Analytics
    └── External Service Status
```

WidgetはPlugin APIを通じてTorifuneのデータを取得する。

Widgetから直接Databaseへアクセスしてはならない。

## 11. Webサイト画面

Webサイトを管理する画面。

```text
Webサイト
├── 一覧
├── 新規作成
└── 編集
```

> **「設定」は「編集」へ統合した**（2026-09-01 改訂。`改訂履歴.md` を参照）。
>
> Coreが持つWebサイトの属性は 名前 / URL / 説明 / 状態 の4つだけで、
> このうち「設定」として切り出せるものが無い。4項目を2画面に割ると、
> 利用者は毎回どちらに入っているかを探すことになる。
>
> サイト単位の追加設定は、そもそもCoreの責務ではない。
> Pluginがサイトごとの設定を持つ場合は Extension Point `site.edit.sidebar`（§21, §26）、
> Plugin自身の設定は `registerSettings` と `/plugins/<id>/settings`（§27）を使う。
> Coreに「Webサイトの設定」画面を置くと、Pluginが持つべき設定をCoreへ引き寄せる
> 置き場になってしまう。
>
> なお、アクセス計測タグ（サイトごとの公開キー）はアナリティクス画面（§15）で表示する。
> 利用者が入力する値ではなく、Torifuneが自動採番して配るものであるため。

一覧画面では、登録されているWebサイトを表示する。

```text
┌────────────────────────────────────────┐
│ Webサイト                    [+ 新規]  │
├────────────────────────────────────────┤
│ Name             URL           Status  │
│────────────────────────────────────────│
│ Example Site     example.com   Active  │
│ Sample Site      sample.com    Draft   │
└────────────────────────────────────────┘
```

## 12. コンテンツ画面（Coreでは提供しない）

コンテンツ管理はPluginの責務とする（2026-08-24 改訂。`改訂履歴.md` を参照）。

「コンテンツ」が何であるかは利用者ごとに大きく違うため、Coreは形を決めない。
代わりに、コンテンツを扱うPluginが画面を作れるよう、次を提供する。

* Page API / Menu API / Widget API（§24-25）
* UI Extension Point（§22）
* 共通UI Component（§32）
* Plugin Data API（`05_API設計.md` §22）

Pluginが追加する画面は `/plugins/<plugin-id>/` の名前空間を持つ（§20）。

## 18. Pluginのインストール

PluginはWeb UIからインストールできる仕組みを基本方針とする。

```text
Plugin管理
     │
     ▼
[Plugin追加]
     │
     ▼
Plugin Package選択
     │
     ▼
検証
     │
     ▼
インストール
     │
     ▼
有効化
```

ただし、任意のPluginコードを無条件に実行できるようにすることはセキュリティ上の重大なリスクとなる。

そのため、Plugin Packageの署名・出所・権限等を検証できる仕組みを設計する。

---

## 19. Plugin Package

Pluginは一定のディレクトリ構造およびManifestを持つ。

例：

```text
my-plugin/
├── plugin.json      必須。ディレクトリ名と id を一致させる
├── index.tsx        必須（index.ts でも可）。Plugin を default export する
└── README.md
```

**必須なのは `plugin.json` と `index.ts` / `index.tsx` の2つだけ**であり、
それ以外のファイル構成はPlugin作者に委ねる（`07_開発者向けガイド.md` §14）。

`plugin.json`にはPluginの基本情報を定義する。

例：

```json
{
  "id": "example-plugin",
  "name": "Example Plugin",
  "version": "1.0.0",
  "apiVersion": 1,
  "permissions": [
    "site.read"
  ]
}
```

実際のManifest仕様は`03_プラグイン設計.md`と整合させる。

---

## 20. Pluginによる画面追加

Pluginは画面を追加できる。

例えば、

```text
Plugin: SEO Extension
```

がインストールされると、

```text
Navigation
└── SEO
     ├── Overview
     ├── Settings
     └── Reports
```

のような画面を追加できる。

Pluginは独自URL Namespaceを持つことを基本とする。

例：

```text
/plugins/example-plugin/
```

---

## 21. Pluginによる既存画面の拡張

Pluginは独立したページを追加するだけでなく、既存画面へUIを追加できる。

例：

```text
Content Edit
├── Basic Information
├── Content Editor
├── Publishing
│
└── SEO Plugin
    ├── SEO Title
    ├── Description
    └── Score
```

この仕組みはUI Extension Pointとして提供する。

---

## 22. UI Extension Point

Torifune Coreでは、Pluginが拡張可能なUI Extension Pointを定義する。

例：

```text
dashboard.before
dashboard.after

site.edit.sidebar
site.list.actions

settings.tabs
```

Pluginは**自身の画面にExtension Pointを定義**し、他のPluginへ公開できる。
例えばコンテンツ管理Pluginが `content.edit.sidebar` を定義すれば、
SEO Pluginがそこへ項目を足せる。**Coreはこれらを定義しない。**

PluginはExtension PointへUI Componentを登録する。

---

## 23. Menu API

PluginはMenu APIを利用してNavigationへ項目を追加できる。

概念例：

```text
registerMenu({
  location: "main",
  label: "SEO",
  route: "/plugins/seo",
  icon: "search",
  permission: "seo.read"
})
```

Menu ItemにはPermissionを設定できる。

---

## 24. Page API

PluginはPage APIを利用して独自ページを登録する。

概念例：

```text
registerPage({
  route: "/plugins/seo",
  component: SeoDashboard,
  permission: "seo.read"
})
```

ページへのアクセス時にはサーバー側でもPermissionを検証する。

画面上でメニューを非表示にするだけでは認可対策とはしない。

---

## 25. Widget API

PluginはWidget APIを利用してDashboard等へWidgetを登録する。

概念例：

```text
registerWidget({
  location: "dashboard",
  component: SeoSummary,
  permission: "seo.read"
})
```

Widgetの表示可否はPermissionによって制御する。

---

## 26. Action API

Pluginは既存画面にActionを追加できる。

例：

```text
Content List
├── 編集
├── 複製
├── 削除
└── SEOチェック
```

Actionは、対象リソースとPermissionを定義する。

---

## 27. 設定画面の拡張

Pluginは自身の設定画面をTorifuneの設定画面へ追加できる。

```text
設定
├── 一般
├── ユーザー
├── API
├── Plugin
│
└── SEO Plugin
      └── SEO設定
```

Pluginの設定値はPlugin Configuration APIを利用して保存する。

---

## 28. Plugin UIとAPI

Plugin UIは、原則としてTorifune APIまたはPlugin APIを利用してデータを取得・更新する。

```text
Plugin UI
   │
   ▼
Plugin API / Public API
   │
   ▼
Application Layer
   │
   ▼
Data Provider
```

Plugin UIからDatabaseへ直接アクセスする設計は採用しない。

---

## 29. PermissionによるUI制御

PermissionによってUIを制御する。

例えば、

```text
site.read
site.write
site.delete
```

の場合、

```text
site.read
    ↓
Webサイト一覧を表示

site.write
    ↓
「新規作成」「編集」を表示

site.delete
    ↓
「削除」を表示
```

とする。

ただし、**UI上でボタンを非表示にすることだけを認可対策としてはならない。**

実際のAPI処理でもPermissionを検証する。

---

## 30. URLアクセス制御

ユーザーが直接URLを入力した場合でも、Permissionを検証する。

例えば、

```text
/plugins/example/admin
```

へ直接アクセスされた場合、

```text
Request
   ↓
Authentication
   ↓
Authorization
   ↓
Permission Check
   ↓
Page
```

の順序で処理する。

---

## 31. レスポンシブ対応

TorifuneのWeb UIはPCブラウザを主要ターゲットとする。

ただし、基本的な画面についてはタブレット・スマートフォンでも利用可能なレスポンシブ構造とする。

特に、

* Dashboard
* Webサイト一覧
* Webサイト編集
* SNS投稿管理

等についてはモバイル表示を考慮する。

---

## 32. UI Component

Torifuneは共通UI Componentを提供する。

例：

```text
Button
Input
Select
Checkbox
Modal
Dialog
Table
Pagination
Tabs
Card
Alert
Toast
Form
DatePicker
Chart
```

Pluginは可能な限りTorifuneの共通Componentを利用する。

これにより、PluginによるUI追加でもTorifune全体のデザイン統一を維持する。

---

## 33. Form

フォーム入力値はクライアント側だけでなく、必ずサーバー側でもValidationする。

```text
Browser Validation
       │
       ▼
API Request
       │
       ▼
Server Validation
       │
       ▼
Application
```

クライアント側ValidationはUX向上を目的とし、セキュリティ上のValidationとしては扱わない。

---

## 34. エラー表示

APIから返されたError CodeをUIで適切に表示する。

例：

```text
入力エラー

サイト名を入力してください。
```

内部ExceptionやStack Trace等をユーザーへ表示しない。

---

## 35. Loading / Empty / Error State

一覧・Dashboard等では、最低限以下の状態を設計する。

```text
Loading
Empty
Success
Error
```

例えば一覧が空の場合、

```text
Webサイトが登録されていません。

[新しいWebサイトを登録]
```

のように、ユーザーが次に行う操作を提示できる構造とする。

---

## 36. 通知

ユーザー操作の結果をToast等で通知する。

例：

```text
[保存しました]
[削除しました]
[接続に失敗しました]
```

重要な操作についてはToastだけでなく、画面上に明示的な状態を表示する。

---

## 37. 危険な操作

削除等の不可逆操作については確認ダイアログを表示する。

```text
┌──────────────────────────────┐
│ Webサイトを削除しますか？    │
│                              │
│ この操作は取り消せません。    │
│                              │
│ [キャンセル] [削除する]       │
└──────────────────────────────┘
```

ただし、確認ダイアログはセキュリティ対策ではなく、誤操作防止を目的とする。

---

## 38. Secret情報の表示

以下のような情報は原則として画面上に平文で再表示しない。

* Password
* Access Token
* Refresh Token
* API Secret
* Client Secret
* Webhook Secret
* Database Password

新規登録時に入力されたSecretを保存した後は、必要に応じてマスク表示する。

例：

```text
API Secret
••••••••••••••••
```

---

## 39. Plugin権限の表示

Pluginをインストールする際には、Pluginが要求する権限をユーザーに表示する。

例：

```text
このPluginは以下の権限を要求しています。

✓ Webサイトの読み取り
✓ SNSアカウントの読み取り
✓ 外部APIへの接続

[キャンセル] [インストール]
```

高い権限を要求するPluginについては、より明確な警告を表示する。

---

## 40. Pluginの有効化・無効化

Pluginは管理画面から有効・無効を切り替えられる構造とする。

```text
Plugin
├── Installed
│
├── Enabled
│
└── Disabled
```

Pluginを無効化すると、そのPluginが提供する画面・API・Event Handler等も無効化する。

---

## 41. Pluginのアンインストール

Pluginのアンインストールでは、Plugin本体とPlugin設定を区別する。

```text
Plugin Uninstall
├── Plugin Code
├── Plugin Configuration
└── Plugin Data
```

Plugin Dataを自動削除するかどうかは、アンインストール時に明示的に選択できる仕組みを検討する。

特にデータ削除を伴う場合は確認を要求する。

---

## 42. SaaS版による画面拡張

SaaS版ではTorifune OSSの標準画面をベースとして、SaaS固有の画面をPluginによって追加する。

例：

```text
Torifune
├── Dashboard
├── Sites
├── SNS
├── Analytics
│
└── SaaS
    ├── Account
    ├── Subscription
    └── Tenant
```

Torifune OSS本体にSaaS固有の画面を実装することは避ける。

---

## 43. 画面とTenant

SaaS版でTenantを利用する場合、画面上のTenant Contextは認証済みUser Identityからサーバー側で確定する。

クライアント側で、

```text
tenantId=tenant_123
```

を変更しただけで別Tenantの画面やデータへアクセスできる構造にしてはならない。

画面表示だけでなく、APIおよびDatabaseアクセス側でもTenant境界を検証する。

## 45. 画面設計上の原則

Torifune OSSの画面設計では、以下を原則とする。

1. Web UIはAPIを介してApplication Layerを利用する
2. UIからDatabaseへ直接アクセスしない
3. Pluginから独自ページを追加できる
4. PluginからNavigationを追加できる
5. PluginからDashboard等へWidgetを追加できる
6. Pluginから既存画面へUI Componentを追加できる
7. Pluginから設定画面を追加できる
8. PermissionによってUIの表示・操作を制御する
9. UI上の制御だけでなくAPI側でも必ず認可を行う
10. Pluginの要求Permissionをインストール時に表示する
11. Secret情報を画面へ平文表示しない
12. Plugin UIはPlugin APIまたはPublic APIを利用する
13. OSS本体にSaaS固有の画面を実装しない
14. SaaS固有のUIはPluginによって拡張できる構造とする
15. Pluginによる拡張を前提として、CoreのUI Extension Pointを設計する
