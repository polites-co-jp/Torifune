# Torifune OSS データベース設計

## 1. 目的

本ドキュメントでは、Torifune OSSが利用するデータベースの基本方針、構成、接続方式、初期化、マイグレーションおよびデータ管理方針を定義する。

Torifune OSSではPostgreSQLを標準データベースとして採用する。

---

## 2. 基本方針

### 2.1 PostgreSQLを使用する

Torifune OSSの標準データベースにはPostgreSQLを使用する。

PostgreSQLを採用する理由は以下とする。

* OSSとして広く利用されている
* トランザクション機能が充実している
* JSON/JSONB等の柔軟なデータ型を利用できる
* 大規模なデータにも対応可能
* Docker環境との親和性が高い
* 将来的なSaaS化や大規模運用にも対応しやすい

### 2.2 TorifuneとDatabaseは1対1を基本とする

Torifune OSSの標準構成では、1つのTorifuneインスタンスが1つのDatabaseを利用する。

```text
Torifune Instance
        │
        │ Database Connection
        ▼
PostgreSQL Database
```

Torifune本体は、複数のユーザーやテナントを識別してDatabaseを切り替えることを前提としない。

複数テナント環境など、標準構成とは異なるDatabase接続方式が必要な場合は、Database Provider Pluginによって拡張する。

---

## 3. PostgreSQL構成

PostgreSQLは、Torifune専用のDatabaseを使用する。

```text
PostgreSQL
└── torifune
    ├── users
    ├── roles
    ├── sites
    ├── social_accounts
    ├── social_posts
    ├── campaigns
    ├── analytics
    └── ...
```

Database名は環境変数等によって変更可能とする。

例：

```text
DATABASE_URL=postgresql://user:password@postgres:5432/torifune
```

実際の環境変数名および接続設定については、実装時に確定する。

---

## 4. Schema方針

Torifune OSSでは、基本的にPostgreSQLのDatabase内にTorifune用のSchemaを構築する。

標準では`public` Schemaを利用する。

ただし、将来的にPluginが独自のデータを保持できるよう、PluginごとのSchema利用については拡張可能な設計とする。

例えば以下のような構成を想定する。

```text
torifune
├── public
│   ├── users
│   ├── sites
│   └── ...
│
├── plugin_x
│   └── ...
│
└── plugin_y
    └── ...
```

Pluginのデータ管理方式については、Plugin設計で詳細を定義する。

---

## 5. データモデル

Torifuneのデータモデルは、Torifuneの基本機能を構成するドメインモデルを中心に設計する。

現時点では、以下のようなデータを想定する。

### 5.1 ユーザー

Torifuneを利用するユーザー情報を管理する。

```text
users
```

想定項目：

* ID
* ログイン識別子
* 表示名
* メールアドレス
* パスワード情報
* ステータス
* 作成日時
* 更新日時
* 最終ログイン日時

パスワードは平文で保存せず、安全なPassword Hashとして保存する。

### 5.2 権限・ロール

ユーザーの権限を管理する。

```text
roles
permissions
user_roles
role_permissions
```

Torifuneの機能単位で権限を制御できる構造を基本とする。

### 5.3 Webサイト

Torifuneで管理するWebサイトを保持する。

```text
sites
```

### 5.4 コンテンツ（Coreの責務としない）

コンテンツ管理はPluginの責務とする（2026-08-24 改訂。`改訂履歴.md` を参照）。

「コンテンツ」が何であるかは利用者ごとに大きく違う（ブログ記事／LPの原稿／メール文面、
本文がMarkdownかブロック構造か外部CMSへの参照か、公開に承認が要るか）。
Coreが特定の形を決めると、それに合わない利用者はCoreを使えなくなる。

Torifuneは形を決めず、**決められる仕組み**を提供する。

* 画面を作るためのPlugin機構（Page / Menu / Widget / Extension Point）
* デザインを揃えるための共通UI ComponentとCSSトークン
* データへアクセスするためのAPI

Pluginが独自データを持つ場合の方式は §6 の「Pluginデータ」に従う。

### 5.5 SNSアカウント

外部SNSサービスとの連携情報を管理する。

```text
social_accounts
```

認証トークン等の機密情報は、平文で保存せず、暗号化または安全なSecret Management方式を利用する。

### 5.6 SNS投稿

SNSへの投稿情報を管理する。

```text
social_posts
```

### 5.7 キャンペーン

マーケティングキャンペーンを管理する。

```text
campaigns
```

### 5.8 アクセス・分析データ

Webサイトや外部サービスから取得したマーケティングデータを管理する。

```text
analytics
access_logs
```

具体的なデータ構造は、利用するデータソースおよび機能要件に応じて設計する。

---

## 6. Pluginデータ

Pluginが独自データを必要とする場合、Torifune本体のテーブルへ直接カラムを追加することは原則として避ける。

Plugin専用のデータ構造を持つことを基本とする。

```text
Torifune Core
    │
    ├── Core Tables
    │
    └── Plugin Tables
          ├── Plugin A
          ├── Plugin B
          └── Plugin C
```

Pluginのデータ管理方式として、以下を想定する。

* Plugin専用Schema
* Plugin専用Table
* Torifune Data API経由のデータ利用

PluginがTorifune内部のテーブル構造へ直接依存することは避ける。

---

## 7. データベースアクセス

アプリケーションからのデータベースアクセスは、Application LayerまたはDomain Layerから直接SQLを実行するのではなく、Repository等の抽象化されたデータアクセス層を利用する。

```text
Presentation
      │
      ▼
Application
      │
      ▼
Domain
      │
      ▼
Repository / Data Access
      │
      ▼
Database Provider
      │
      ▼
PostgreSQL
```

Database Providerは、データベース接続方法を抽象化する。

標準構成ではPostgreSQL Providerを使用する。

---

## 8. Database Provider

Database Providerは、Torifuneとデータベースの接続方式を分離するための拡張ポイントである。

```text
Torifune
      │
      ▼
Database Provider Interface
      │
      ├── PostgreSQL Provider
      │
      └── Plugin Database Provider
```

標準構成ではPostgreSQL Providerを使用する。

SaaS版などでユーザー・テナント単位のDatabase切り替えが必要になった場合は、SaaS側でDatabase Provider Pluginを実装する。

Torifuneのビジネスロジックは、具体的なDatabase選択方式を認識しないものとする。

---

## 9. Database初期化

Torifune OSSには、PostgreSQL Databaseを初期化するためのプログラムまたはスクリプトを含める。

初期化処理では、以下を実施する。

1. Database接続確認
2. 必要なSchemaの作成
3. 必要なテーブルの作成
4. Indexの作成
5. 初期データの投入
6. Migration Versionの記録

初期化処理は繰り返し実行しても既存データを破壊しない設計とする。

---

## 10. マイグレーション

データベース構造の変更は、Migrationによって管理する。

Migrationにはバージョンを付与し、適用状況をデータベース上で管理する。

```text
Migration 001
     ↓
Migration 002
     ↓
Migration 003
     ↓
Migration 004
```

Migrationの適用順序を保証し、既に適用済みのMigrationを再実行しない。

### 10.1 Migrationの原則

* 本番環境で直接DDLを変更しない
* MigrationファイルをGit管理する
* Migrationの適用状態を管理する
* 原則として既存データを破壊しない
* 大量データを扱う変更では移行手順を別途定義する

---

## 11. トランザクション

データの整合性が必要な処理では、PostgreSQLのTransactionを利用する。

特に以下の処理では、複数のデータ変更を一つのTransactionとして扱うことを基本とする。

* Webサイト登録・更新
* SNS投稿情報の登録
* キャンペーン更新
* Pluginによる複数データ更新
* その他、複数テーブルを一貫して変更する処理

---

## 12. Index

検索条件、JOIN、ソート等で頻繁に利用するカラムには適切なIndexを設定する。

ただし、Indexを過剰に作成するとINSERT、UPDATEおよびストレージ使用量に影響するため、実際のクエリパターンに基づいて設計する。

特に以下を考慮する。

* Primary Key
* Foreign Key
* 一意制約
* 検索条件
* 時系列データ
* 大量データの検索
* Pluginが利用する検索条件

---

## 13. 機密情報

以下のような情報は、原則として平文で保存しない。

* パスワード
* OAuthアクセストークン
* OAuthリフレッシュトークン
* APIキー
* 外部サービスのSecret
* その他認証情報

必要に応じて暗号化して保存する。

暗号鍵自体をDatabaseへ保存してはならない。

暗号鍵やアプリケーションSecretは、環境変数またはSecret Management機構によって管理する。

---

## 14. バックアップ

TorifuneのデータはPostgreSQLのバックアップ機構を利用して保護する。

最低限、以下を考慮する。

* 定期バックアップ
* バックアップの世代管理
* バックアップの保存場所
* リストア手順
* バックアップからの復旧テスト

バックアップ方式はTorifune OSSの必須機能として固定せず、利用環境に応じて選択できるものとする。

---

## 15. データベースの責務境界

Torifune OSSでは、データベースに関する責務を以下のように分離する。

| 項目           | Torifune Core | Database Provider | Plugin | SaaS |
| ------------ | ----------------- | ----------------- | ------ | ---- |
| データモデル       | ○                 |                   |        |      |
| Repository   | ○                 |                   |        |      |
| PostgreSQL接続 |                   | ○                 |        |      |
| DB接続方式変更     |                   | ○                 | ○      |      |
| Plugin独自データ  |                   |                   | ○      |      |
| テナントDB管理     |                   |                   |        | ○    |
| ユーザーごとのDB割当  |                   |                   |        | ○    |
| DBコンテナ管理     |                   |                   |        | ○    |
| バックアップ運用     |                   |                   |        | ○    |

SaaS環境におけるユーザー・テナント単位のDatabase管理はTorifune OSSの責務としない。

---

## 16. 設計上の原則

Torifune OSSのデータベース設計では、以下を基本原則とする。

1. PostgreSQLを標準データベースとする
2. TorifuneインスタンスとDatabaseを1対1とする
3. データベース接続方式をDatabase Providerで抽象化する
4. TorifuneのビジネスロジックからDB接続方式を分離する
5. PluginがTorifune本体のテーブル構造へ直接依存することを避ける
6. Plugin固有データはPlugin自身が管理する
7. Database変更はMigrationで管理する
8. 機密情報を平文で保存しない
9. データ整合性が必要な処理ではTransactionを利用する
10. SaaS固有のテナントDB管理をTorifune OSS本体に持ち込まない
