# Torifune OSS プラグイン設計

## 1. 目的

本ドキュメントでは、Torifune OSSのプラグイン機構について定義する。

Torifuneの基本機能をコアアプリケーションとして提供し、追加機能・外部サービス連携・認証方式・データベース接続方式などをプラグインとして拡張可能にする。

プラグイン機構により、Torifune本体のソースコードを変更することなく、第三者が独自の機能を開発・追加できる構造を実現する。

---

## 2. 基本方針

### 2.1 Plugin First

Torifuneに新しい機能を追加する場合、コア機能として実装する必要がないものは、原則としてプラグインとして実装する。

特に以下はプラグインによる拡張を基本とする。

* 外部サービス連携
* SNS連携
* 広告サービス連携
* アクセス解析サービス連携
* 追加画面
* 追加レポート
* 認証方式
* データベース接続方式
* SaaS固有機能

### 2.2 CoreとPluginの責務を明確にする

Torifune Coreは、Torifuneとして最低限必要となる基本機能を提供する。

Pluginは、Coreが提供するPlugin APIを利用して機能を拡張する。

```text
┌──────────────────────────────────────┐
│          Torifune Core           │
│                                      │
│  Business Logic                      │
│  Web UI                              │
│  API                                 │
│  Authentication Interface            │
│  Database Interface                  │
│                                      │
│          Plugin API                  │
└──────────────────┬───────────────────┘
                   │
        ┌──────────┼──────────┐
        ▼          ▼          ▼
     Plugin A   Plugin B   Plugin C
```

PluginはCoreの内部実装に直接依存しない。

### 2.3 Plugin APIを公開された契約とする

Pluginが利用できる機能は、Plugin APIとして明示的に定義する。

Core内部のクラス、関数、テーブル等を直接利用することは、公開APIとして保証しない。

これにより、Coreの内部実装を変更してもPlugin APIの互換性を維持できる限り、既存Pluginを継続して利用できる構造とする。

---

## 3. Pluginの分類

Torifuneでは、Pluginを役割ごとに分類する。

```text
Plugin
├── UI Plugin
├── Data Plugin
├── Event Plugin
├── Authentication Provider
├── Database Provider
└── External Service Plugin
```

1つのPluginが複数の拡張ポイントを実装することも可能とする。

---

## 4. UI Plugin

UI Pluginは、TorifuneのWeb画面を拡張する。

### 4.1 拡張可能なUI

以下のUIをPluginから追加可能とする。

* メインメニュー
* サブメニュー
* 管理画面
* 設定画面
* ダッシュボードウィジェット
* 詳細画面
* モーダル
* 操作ボタン
* データ表示

### 4.2 UI登録

Pluginは、定義されたUI Extension APIを利用して画面を登録する。

```text
Plugin
   │
   ▼
UI Extension API
   │
   ├── Menu
   ├── Page
   ├── Widget
   └── Action
```

PluginがTorifuneのテンプレートや内部HTMLを直接書き換える方式は採用しない。

---

## 5. Data API

PluginからTorifuneが管理するデータを利用するためのAPIを提供する。

Pluginは原則として、Torifuneのデータベースへ直接SQLを発行しない。

```text
Plugin
  │
  ▼
Data API
  │
  ▼
Application / Domain
  │
  ▼
Repository
  │
  ▼
Database
```

これにより、データベース構造の変更によるPluginへの影響を抑える。

### 5.1 Data APIの例

```text
Site API
SNS API
Campaign API
Analytics API
User API
```

> コンテンツはCoreの責務ではない（`改訂履歴.md` 2026-08-24）。
> コンテンツを扱うPluginは、自身のデータをPlugin Database APIで管理する。

具体的なAPI仕様は`05_API設計.md`で定義する。

---

## 6. Event API

Torifune内部で発生するイベントをPluginが購読できるようにする。

例えば以下のイベントを想定する。

```text
content.created
content.updated
content.deleted

social.post.created
social.post.published
social.post.failed

campaign.created
campaign.updated

analytics.received
```

> ここに挙げた `content.*` は**Coreが発火するものではない**。
> コンテンツ管理はPluginの責務であり（`改訂履歴.md` 2026-08-24）、
> これらは「Pluginがこういうイベントを定義・発火できる」という例である。
> Pluginは自身のイベントを定義し、他のPluginへ公開できる。

Pluginはイベントを購読し、イベント発生時に独自処理を実行できる。

```text
Torifune
     │
     │ Event
     ▼
Event Dispatcher
     │
     ├── Plugin A
     ├── Plugin B
     └── Plugin C
```

---

## 7. Authentication Provider

認証処理はAuthentication Providerとして抽象化する。

```text
Application
     │
     ▼
Authentication Interface
     │
     ├── Default Authentication Provider
     │
     └── Plugin Authentication Provider
```

### 7.1 標準認証

Torifune OSSは、標準状態で独立して利用可能な認証方式を提供する。

### 7.2 外部認証

Pluginによって外部認証方式を追加できる。

例えば、

* OpenID Connect
* OAuth 2.0 / OpenID Connectを利用した認証サービス
* その他の認証基盤

などを想定する。

### 7.3 SaaSでの利用

Torifune SaaSでは、SaaS側の認証基盤とTorifuneを接続するAuthentication Provider Pluginを利用する。

Torifune Coreは、SaaS側の認証基盤を直接認識しない。

---

## 8. Database Provider

データベース接続はDatabase Providerとして抽象化する。

```text
Application
     │
     ▼
Database Interface
     │
     ├── PostgreSQL Provider
     │
     └── Plugin Database Provider
```

### 8.1 標準Database Provider

Torifune OSSでは、PostgreSQL Providerを標準提供する。

### 8.2 PluginによるDatabase Provider

PluginによってDatabase Providerを差し替えることを可能とする。

例えばSaaS環境では、認証されたユーザーやテナントに応じて接続先Databaseを決定するProviderを実装できる。

Torifune Coreは、具体的なDatabase選択方式を認識しない。

---

## 9. External Service Plugin

外部サービスとの連携は、原則としてPluginとして実装する。

例えば以下を想定する。

```text
External Service Plugin
├── X Plugin
├── Instagram Plugin
├── Facebook Plugin
├── Google Analytics Plugin
├── Google Ads Plugin
└── Other Service Plugin
```

外部サービスのAPI変更が発生した場合でも、該当Pluginを更新することで対応できる構造とする。

---

## 10. Plugin構造

Pluginは、Torifuneが定義する一定のディレクトリ構造およびファイル命名規則に従う。

例：

```text
plugins/
└── example-plugin/
    ├── plugin.json
    ├── src/
    │   ├── Plugin.php
    │   ├── Api/
    │   ├── Ui/
    │   ├── Events/
    │   └── Providers/
    ├── migrations/
    ├── assets/
    └── README.md
```

具体的なディレクトリ構造およびファイル形式は、実装言語・フレームワーク確定後に詳細化する。

---

## 11. Plugin Manifest

各Pluginは、Pluginの基本情報を定義するManifestを持つ。

例：

```json
{
  "name": "example-plugin",
  "displayName": "Example Plugin",
  "version": "1.0.0",
  "description": "Example Torifune Plugin",
  "author": "Example Author",
  "apiVersion": "1.0",
  "dependencies": [],
  "extensions": [
    "ui",
    "events"
  ]
}
```

Manifestでは最低限、以下を定義する。

* Plugin ID
* Plugin名
* バージョン
* 説明
* 作者
* Plugin APIバージョン
* 依存Plugin
* 提供するExtension Point

---

## 12. Plugin Lifecycle

Pluginには明確なライフサイクルを定義する。

```text
Install
   │
   ▼
Register
   │
   ▼
Enable
   │
   ▼
Active
   │
   ▼
Disable
   │
   ▼
Uninstall
```

### 12.1 Install

PluginファイルをTorifuneへ導入する。

### 12.2 Register

Manifestを読み込み、PluginをTorifuneへ登録する。

### 12.3 Enable

Pluginを有効化する。

必要に応じて以下を実行する。

* 初期設定
* Database Migration
* UI登録
* Event Handler登録
* Provider登録

### 12.4 Disable

Pluginを無効化する。

Plugin自体を削除せず、機能だけを停止する。

### 12.5 Uninstall

PluginをTorifuneから削除する。

Plugin独自データを削除する場合は、ユーザーに明示的な確認を要求する。

Pluginの管理機能をTorifuneの標準機能として提供する。

Web UIから以下の操作を可能とする。

* Plugin一覧表示
* Pluginインストール
* Plugin有効化
* Plugin無効化
* Plugin削除
* Plugin更新
* Plugin設定
* Plugin情報表示
* Plugin依存関係確認

┌─────────────────────────────┐
│       Plugin Manager        │

│ Example Plugin      Enabled │

## 14. Pluginのインストール方法

Pluginは、将来的に複数の方法でインストール可能とする。

### 14.1 Web UIからのインストール

WordPressのように、管理画面からPluginを検索してインストールできる仕組みを想定する。

```text
Plugin Registry
      │
      ▼
Torifune Plugin Manager
      │
      ▼
Install
      │
      ▼
Enable
```

### 14.2 ローカルPlugin

開発者がローカルPluginを配置して利用できる仕組みを提供する。

```text
plugins/
└── my-plugin/
```

### 14.3 Git等からのインストール

将来的にGit Repository等からPluginを導入できる方式も検討する。

ただし、任意の外部Repositoryから自動的にコードを取得して実行することは、セキュリティ上のリスクが高いため、導入元の信頼性を検証する仕組みを設ける。

---

## 15. Plugin Registry

Pluginの検索・配布を行うためのPlugin Registryを提供できる構造とする。

Registryには以下の情報を保持する。

* Plugin ID
* Plugin名
* 説明
* 作者
* バージョン
* Plugin API Version
* ダウンロード情報
* 依存関係
* 対応Torifune Version
* 更新日時

将来的には、公式Registryだけでなく、第三者が独自Registryを提供できる構造も検討する。

---

## 16. Plugin API Version

Plugin APIにはバージョンを設定する。

Pluginは、対応するPlugin API VersionをManifestに定義する。

```text
Torifune 1.x
Plugin API 1.x
```

Torifune本体のバージョンとPlugin APIのバージョンを分離する。

これにより、Torifune本体の内部実装を変更しても、Plugin APIの互換性を維持できる。

---

## 17. Plugin Dependency

Pluginは、他のPluginへの依存関係を定義できる。

例えば、

```text
Plugin A
 └── requires Plugin B >= 1.2.0
```

TorifuneはPluginの有効化時に依存関係を検証する。

依存Pluginが存在しない場合や、対応バージョンを満たさない場合は、Pluginを有効化しない。

---

## 18. Plugin設定

Pluginは独自の設定項目を持つことができる。

Plugin設定画面はPlugin自身がUI Extension APIを利用して提供する。

設定値の保存にはTorifuneが提供するPlugin Configuration APIを利用する。

APIキー、Secret、OAuth Token等の機密情報は、通常の設定値と区別して安全に管理する。

---

## 19. Pluginデータベース

PluginはTorifune Coreのテーブルへ直接カラムを追加することを禁止する。

Pluginが独自データを持つ場合は、**Torifuneが提供するPlugin Store**を利用する。
Plugin Storeは、Plugin IDで名前空間を区切ったKey-Value領域である。

```text
PostgreSQL
├── Core Tables
│
└── plugin_store
      ├── plugin_a / key → value
      ├── plugin_b / key → value
      └── plugin_c / key → value
```

Pluginは自身の名前空間の外を読み書きできない。
Plugin IDはPlugin自身が指定するのではなく、Torifuneが渡すContextに閉じ込める。

APIキー、Secret、OAuth Token等は通常の値と区別して暗号化して保存する（§18）。

### 19.1 Plugin Storeで足りる範囲

Plugin Storeが扱えるのは、**設定と少量のデータ**までとする。

| できること | できないこと |
| --- | --- |
| キーによる読み書き、接頭辞での一覧 | 任意の項目での検索・並べ替え・集計 |
| Secretの暗号化保存と「設定済み」の判定 | 一意制約、外部キー、複数行にまたがる整合の保証 |
| アンインストール時の一括削除 | 大きな値の保存（1値あたりの上限がある） |

**設定のために毎回Migrationを書かせない**ことを優先してこの形を選んだ。
Plugin作者にDDLを書かせると、その分だけ導入の失敗経路が増える。

### 19.2 Plugin専用のテーブル・Schema（将来課題）

Plugin専用のテーブルやSchemaを持たせ、Plugin自身がMigrationを提供する方式は、
**現時点では提供しない。**

行数が増えるデータや検索が要るデータを扱うPluginは、Plugin Storeでは書けない。
それが実際に必要になった時点で、以下を決めたうえで設計する。

* Coreとは分けた適用履歴の管理（版番号の衝突を避ける）
* 適用のタイミング（Install時 / 有効化時 / 再ビルド後の起動時）と、
  再ビルドを伴う導入フローとの噛み合わせ
* 適用に失敗したときに何をどこまで戻すか
* アンインストール時に、Pluginが作ったテーブル・Schemaを消すかどうか
* PluginにDDLを許す範囲。Plugin専用Schemaへ閉じ込め、その作成と権限付与は
  Coreが行う（§20、`05_API設計.md` §27「一般Pluginに自由なSQL実行権限を与えない」）

**使われる形が分かる前にインターフェースを固めない。**
先に固めると、実際の要求に合わない形をPlugin作者へ押し付けることになる。

## 20. Plugin Security

PluginはTorifuneのアプリケーションコードとして実行される。

そのため、Pluginには高い権限が与えられる。

特に以下のPluginは重要な権限を持つ。

* Authentication Provider
* Database Provider
* 外部サービス連携Plugin
* Data APIを利用するPlugin

したがって、Pluginのインストールは信頼できるコードを導入する操作として扱う。

### 20.1 Plugin Registryの信頼性

公式Registryを提供する場合は、以下の対策を検討する。

* Plugin Packageの署名
* Checksum検証
* 作者情報
* Version管理
* セキュリティレビュー
* 脆弱性情報
* 不正Pluginの公開停止

### 20.2 Plugin権限

将来的にはPluginごとに必要な権限をManifestで宣言できる仕組みを検討する。

例：

```text
permissions:
  - data.read
  - ui.menu
  - events.subscribe
```

ユーザーはPluginの要求権限を確認したうえでインストールできるようにする。

## 21. Plugin API設計原則

Plugin APIは以下の原則に従う。

1. 公開APIと内部APIを明確に分離する
2. 内部クラスへの直接依存を避ける
3. Interfaceを契約として定義する
4. API Versionを管理する
5. 後方互換性を重視する
6. Pluginが必要以上の権限を取得しない設計を目指す
7. Plugin固有データをCoreのDB構造から分離する
8. Pluginから直接SQLを実行させない
9. UI拡張は定義されたUI Extension APIを利用する
10. Authentication Provider、Database Provider等の高権限APIは特に慎重に設計する

---

## 22. SaaS版への利用

Torifune SaaSでは、Torifune OSSが提供するPlugin機構を利用してSaaS固有機能を追加する。

想定されるPluginは以下とする。

```text
Torifune SaaS
│
├── SaaS Authentication Plugin
│   └── OpenID Connect
│
├── SaaS Database Plugin
│   └── Tenant Database Routing
│
└── SaaS UI Plugin
    └── SaaS-specific Functions
```

SaaS側のPluginはTorifune OSS本体とは別Repositoryで管理する。

Torifune OSSは、これらのPluginが存在することを前提としない。

## 25. 設計上の重要事項

TorifuneのPlugin Systemは単なる「追加ファイルを読み込む仕組み」ではなく、Torifuneの将来的な拡張性を支える正式なAPIとして設計する。

特に以下の4つを最重要Extension Pointとする。

```text
UI Extension
Data API
Authentication Provider
Database Provider
```

この4つを明確なInterfaceとして定義することで、Torifune OSS本体を変更することなく、第三者による機能追加やTorifune SaaSへの統合を可能とする。

また、Plugin APIはTorifune内部実装との境界となるため、初期実装時からAPI Versioningと後方互換性を考慮する。
