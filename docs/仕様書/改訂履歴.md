## 2026-09-01 Webサイト画面の「設定」を「編集」へ統合する

### 決定

`06_画面設計.md` §11 のサブ画面から「設定」を外し、`一覧 / 新規作成 / 編集` にする。
統合した理由と、サイト単位の追加設定がPlugin側の責務であることを本文に書き足した。

### 理由

**「設定」として切り出せる中身が1つも無かった。**

CoreがWebサイトについて持つ属性は 名前 / URL / 説明 / 状態 の4つだけである。
どれも「サイトそのものが何であるか」を表すもので、
「サイトをどう扱うかの設定」に当たるものは無い。
4項目しかない画面を2枚に割ると、利用者は毎回どちらに入っているかを探すことになる。

`sites` テーブルには他に `public_key`（アクセス計測タグの公開キー）があるが、
これは利用者が入力する値ではなく、DB側の既定値でTorifuneが自動採番するものである。
表示はすでにアナリティクス画面（§15）が「計測タグ」として受け持っている。

さらに、サイト単位の追加設定はそもそもCoreの責務ではない。
Pluginがサイトごとの設定を持つなら Extension Point `site.edit.sidebar`（§21, §26）、
Plugin自身の設定なら `registerSettings` と `/plugins/<id>/settings`（§27）がある。
Coreに「Webサイトの設定」という名前の画面を置くと、
**Pluginが持つべき設定をCoreへ引き寄せる置き場**になってしまう。

**画面を増やして仕様に形だけ合わせるのではなく、成立しない区分を取り下げた。**

### 変更した節

| 文書 | 節 | 変更内容 |
| --- | --- | --- |
| `06_画面設計.md` | §11 | サブ画面から「設定」を削除。統合の理由、Plugin側の設定経路、計測タグの表示場所を追記 |

### 実装への影響

無し。`/sites` の画面構成は現状のまま（一覧・新規作成・編集）。

## 2026-09-01 Analytics APIから `GET /{id}` を外し、Paginationを明記する

### 決定

`05_API設計.md` §20 から `GET /api/v1/analytics/{id}` を削除する。
代わりに §20.1 を新設し、**単一リソース取得を提供しない理由**を書く。
あわせて、一覧が `{ data, meta }`（`page` / `perPage` / `total`）を返すことを明記する。

### 理由

**AnalyticsにはリソースIDが存在しない。**

`analytics` テーブルの主キーは `(site_id, metric_date, source, metric)` の複合キーであり、
保持しているのは個々のレコードではなく「どのサイトの・いつの・どの出所の・どの指標か」で
一意に定まる集計値である。1件を指す単一のIDを持たない。

ここへ人工的なIDを与えると、次のどちらかになる。

1. 集計をやり直すたびにIDが変わる。
   Analyticsのロールアップは**再実行できること**を前提に作ってある
   （同じ期間を何度集計しても結果が同じになる）。再集計でIDが変わるなら、
   IDを外部から保持する意味が無い。
2. 集計値とIDの対応表を別に持つ。
   集計値そのものより大きな管理対象が増え、参照する側に利点が無い。

**仕様を実装に合わせて薄くしたのではなく、成立しない仕様を取り下げた。**
1件だけが必要な場合は、期間・サイト・出所による絞り込みで表現できる。

Paginationのほうは仕様が正しく、実装が欠けていたので**実装を足した**。
`page` / `perPage` と `meta.total` を、他の一覧API（`/users` `/sites` `/social/accounts`）と
同じ形にそろえた。旧名 `limit` は §41（後方互換）に従い当面受け付ける。

### 変更した節

| 文書 | 節 | 変更内容 |
| --- | --- | --- |
| `05_API設計.md` | §20 | エンドポイント一覧から `GET /api/v1/analytics/{id}` を削除。Response形式（`{ data, meta }`）と Pagination のクエリ例を追記 |
| `05_API設計.md` | §20.1（新設） | 単一リソース取得を提供しない理由を明記。Analytics以外の資源は従来どおり `GET /{id}` を提供することも併記 |

### 実装への影響

* `GET /api/v1/analytics` に `page` / `perPage` を追加し、`{ data, meta }` を返すようにした。
* `analytics.listPage` / `analytics.topPathsPage` UseCase と、
  `analyticsRepository.countPoints` / `countTopPaths` を追加した。
* 既存の `analytics.list` / `analytics.topPaths`（全件を返す）は、
  画面と Plugin Data API が使うため残してある。

## 2026-09-01 Pluginの基本構造を実装に合わせる

### 決定

`07_開発者向けガイド.md` §14 が示すPluginの基本構造を、
`backend/ frontend/ assets/` から **`plugin.json` ＋ `index.ts`/`index.tsx`** へ改める。

### 理由

実装（`scripts/generate-plugin-registry.mjs`）が読み込みの条件としているのは次の3つだけである。

1. `plugins/<id>/plugin.json` が存在する
2. `plugins/<id>/index.ts` または `index.tsx` が存在する
3. `plugin.json` の `id` がディレクトリ名と一致する（`plugin/loader.ts`）

`backend/` `frontend/` `assets/` はどこからも参照されておらず、
実在する `plugins/example-plugin/` も `plugin.json` ＋ `index.tsx` ＋ `ui/` という
別の構成を採っている。**仕様書の構造に従ったPluginは読み込まれない。**

2026-08-31 の改訂で §14 から `migrations/` を削除したが、
**そのとき `backend/ frontend/ assets/` を残したため、実装との食い違いが残っていた。**

Coreが構造を強制しない方針そのものは変えない。
規模の違うPluginに同じディレクトリ構成を要求する理由が無く、
強制するにはビルド側で構造を検証する仕組みが要る。

### 変更した節

| 文書 | 節 | 変更内容 |
| --- | --- | --- |
| `07_開発者向けガイド.md` | §14 | 基本構造を `plugin.json` ＋ `index.ts(x)` へ差し替え。必須が2つだけであることと、それ以外は自由であることを明記 |

### 仕様書以外で直したもの

`README.md`「プラグイン / Plugins」の構造例も同じ誤りを持っており、
さらに **2026-08-31 に削除したはずの `migrations/` が残っていた**（外し漏れ）。
§14 と同じ内容へ揃えた。

### 実装への影響

**無い。** 実装は既に `plugin.json` ＋ `index.ts(x)` だけを見ており、
この改訂は仕様と文書を実装に合わせるものである。

## 2026-08-31 Pluginのデータ保存を Plugin Store に確定し、「メディア」を画面構成から外す

### 決定

**1. Plugin が独自のテーブル・Schema・Migration を持つ方式は提供しない。**
Plugin のデータは Plugin Store（Plugin ID で名前空間を区切った Key-Value 領域）へ保存する。

**2. `06_画面設計.md` §4 の画面構成から「メディア」を外す。**

### 理由

#### Plugin Store に確定する理由

`010-plugin-api` の実装で、Plugin のデータ置き場として `plugin_store` を作った。
**設定と少量のデータのために毎回 Migration を書かせるのは重い**ためで、
Plugin 作者に DDL を書かせると、その分だけ導入の失敗経路が増える。

一方で §19 と §39 は Plugin 専用テーブルと Plugin 独自 Migration を求めており、
**仕様と実装が食い違ったまま残っていた。**

Plugin 専用テーブルを実装するには、以下をすべて決める必要がある。

* Core とは分けた適用履歴の管理（版番号の衝突を避ける）
* 適用のタイミングと、再ビルドを伴う導入フローとの噛み合わせ
* 適用に失敗したときに何をどこまで戻すか（隔離はビルド失敗にしか効かない）
* アンインストール時に Plugin が作ったテーブル・Schema を消すかどうか
* Plugin に DDL を許す範囲（`05_API設計.md` §27 は自由な SQL 実行を認めていない）

**使われる形が分かる前にこれを固めない。**
固めると、実際の要求に合わない形を Plugin 作者へ押し付けることになる。
Plugin Store で実際に困る Plugin が出た時点で、その要求と合わせて設計する。
Authentication Provider の登録口を保留にしているのと同じ判断である
（`docs/実装計画/001-Torifune単体稼働/03_リスクと未決事項.md` S-6）。

#### 「メディア」を外す理由

§4 の画面構成ツリーに1行あるだけで、**§5 以降のどの節にも定義が無い。**
他の画面（ログイン / Dashboard / Webサイト / SNS / キャンペーン /
アナリティクス / 設定 / Plugin管理）はすべて節を持っている。
データベース設計にもメディア用テーブルの記述が無く、
`007-sites` は「サイトに紐づくファイル・メディア管理」を明示的に対象外としている。

2026-08-24 にコンテンツを Core から外したとき、§4 から「コンテンツ」は消したが
**「メディア」が残った。** メディアはコンテンツと一体で使われるものであり、
外し漏れと判断する。

必要になったときは、ファイルストレージの抽象と Plugin からの利用まで含めて
改めて定義する。**定義の無い項目を一覧に残しておくと、実装の指針にならないまま
「やることになっている」とだけ読まれる。**

## 2026-08-24 コンテンツを Core の責務から外す

### 決定

**`contents` を Torifune Core のドメイン・テーブル・API・画面から外す。**

コンテンツ管理は Plugin の責務とし、Torifune は次の3つを提供するに留める。

1. 画面を作るための Plugin 機構（Page / Menu / Widget / Extension Point）
2. デザインを揃えるための共通 UI Component と CSS トークン
3. データへアクセスするための API（Public API / Plugin Data API）

### 理由

Torifune の価値は**汎用性**にある（`CLAUDE.md`「絶対に守る境界」）。
「コンテンツ」が何であるかは利用者ごとに大きく違う。

* ブログ記事なのか、LP の原稿なのか、メール文面なのか
* 本文は Markdown なのか、ブロック構造なのか、外部 CMS への参照なのか
* 公開フローに承認が要るのか

Core が特定の形を決めると、それに合わない利用者は Core を使えず、
合う利用者にとっても中途半端なものになる。
**形を決めずに、決められる仕組みだけを提供する**ほうが、
Plugin First の方針（`03_プラグイン設計.md` §2.1）と一貫する。

Sites / SNS / Campaigns / Analytics は「マーケティング活動の対象と実績」であり、
形が利用者によって大きく変わらないため Core に残す。

## 2026-09-01（3）Plugin の HTTP API 名前空間を具体化した（設計 027）

`05_API設計.md` §17 が定める `/api/v1/plugins/<plugin-id>/...` の名前空間は、
**実装されていなかった。** Plugin が HTTP のエンドポイントを生やす手段が無い。

Core はコンテンツ管理を Plugin の責務として外した（2026-08-24 の改訂）。
その代わりに Plugin へ渡すはずだった口の1つがこれである。

### 見つかった不具合

Plugin ID の形式は `^[a-z][a-z0-9-]{1,63}$` で、**1語の英小文字がそのまま有効な ID になる。**
一方 Core は `/api/v1/plugins/` の直下に `registry` / `package` / `operations` を持つ。

Next.js は静的セグメントを動的セグメント（`[id]`）より先に解決するため、
`registry` という ID の Plugin を入れると、その Plugin に対する
有効化・無効化・設定・削除の経路が**すべて Core のルートに食われる。**
一覧には出るのに操作できない Plugin ができ、**導入した後で気づくことになる。**

### 改訂

| 対象 | 節 | 変更 |
| --- | --- | --- |
| `05_API設計.md` | §17 | Plugin の API を `/api/v1/plugins/<plugin-id>/api/...` と具体化。Core と Plugin の境界、Core が受け持つ防御、Plugin ID の予約語を明記 |

### 実装

| 対象 | 内容 |
| --- | --- |
| `packages/plugin-api/src/manifest.ts` | `RESERVED_PLUGIN_IDS` を追加し、Manifest の検証で断る。**形式の誤りとして返さない**（形は正しいので作者が直しようがない） |
| `apps/web/src/plugin/plugin-route-namespace.test.ts` | 予約語の一覧と `app/api/v1/plugins/` 直下の実際のディレクトリ名が**双方向で一致する**ことを固定。Core が静的ルートを足して予約し忘れたら落ちる |

| §17 | 認可開始（`GET /api/v1/auth/authorize`）とコールバック（`GET /api/v1/auth/callback`）を Core が提供すること。`login.methods` から辿る形 |
| §21 | §21 の流れ図の各段を、Core と Plugin のどちらが担うかの表 |

| §27 | §27 が挙げる項目を「Core が実装する／Plugin が実装する」に振り分けた表。コールバックで通常の CSRF 検証が効かず、State 検証が代替する理由 |

### なぜ書いたか

実装計画002の完了判定の再監査で、**仕様書が第一候補として繰り返し挙げる OIDC が、
「Plugin の責務だから Core は未実装でよい」のではなく、Plugin 側でも実装できない**
状態だったことが分かった。

* `PluginAuthenticationProvider.authenticate()` が受け取るのは `{ loginId, password }` だけで、
  Authorization Code → Callback → Token Exchange の往復を表現する口が無かった
* コールバックを受ける API ルートが無かった
* State / Nonce を保管する場所が無かった
* 一方で `06_画面設計.md` §5 は「Googleでログイン」を OIDC Plugin の例として挙げ、
  そのための `login.methods` 拡張点は実装・描画されていた。**UI の受け口だけがあった**

§27 は Redirect URI 検証・CSRF 対策・State 検証・Nonce 検証を
「Authentication Provider Plugin が考慮する」項目として並べていたが、
**どこまでを Plugin に書かせるのかを決めていなかった。**
Plugin ごとに書かせると、どれか1つの Plugin の実装ミスが認証全体の穴になる。
ここで **State / Redirect URI / CSRF は Core が持つ**と決め、表にした。

設計は `docs/設計/025-redirect-authentication/設計.md`。
