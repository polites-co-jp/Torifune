# Torifune OSS アーキテクチャ設計

## 1. 目的

本ドキュメントでは、Torifune OSSのソフトウェアアーキテクチャを定義する。

Torifune OSSは、単体で動作するマーケティング管理アプリケーションとして設計し、特定のSaaS基盤、ユーザー管理サービス、マルチテナント基盤等に依存しないことを基本とする。

また、認証、データベース接続、UI、外部サービス連携等の一部機能をPlugin APIによって拡張できる構造とする。

---

## 2. アーキテクチャ方針

### 2.1 単体アプリケーションとして成立すること

Torifune OSSは、外部の管理システムを必要とせず、単体でインストール・起動・利用できるものとする。

標準構成では、以下の関係とする。

```text
Torifune
     │
     ▼
PostgreSQL
```

Torifuneは1つのデータベースに接続して動作する。

### 2.2 コア機能と拡張機能を分離する

Torifune本体には、マーケティング管理に必要な基本機能を実装する。

一方、特定の利用環境に依存する機能や、第三者が追加する機能についてはPluginとして実装する。

```text
┌──────────────────────────────────────┐
│            Torifune              │
│                                      │
│  ┌────────────────────────────────┐  │
│  │          Core Application       │  │
│  │                                │  │
│  │  Web UI                        │  │
│  │  API                           │  │
│  │  Marketing Functions           │  │
│  │  Authentication Interface      │  │
│  │  Database Interface             │  │
│  └────────────────┬───────────────┘  │
│                   │                  │
│              Plugin API              │
│                   │                  │
│  ┌────────────────┴───────────────┐  │
│  │             Plugins             │  │
│  │                                │  │
│  │  UI Plugin                     │  │
│  │  Authentication Provider       │  │
│  │  Database Provider              │  │
│  │  External Service Plugin       │  │
│  └────────────────────────────────┘  │
└──────────────────────────────────────┘
```

### 2.3 内部実装への直接依存を避ける

Pluginは、Torifuneの内部クラス、内部DB構造、内部サービス等へ直接依存しない。

Torifuneが提供するPlugin APIおよび定義済みインターフェースを利用する。

これにより、Torifune本体の内部実装を変更しても、公開されたPlugin APIの互換性を維持する限り、既存Pluginへの影響を抑えられる構造とする。

---

## 3. 論理アーキテクチャ

Torifuneは、以下の論理レイヤーで構成する。

```text
┌──────────────────────────────────────┐
│              Presentation            │
│                                      │
│ Web UI / API                         │
└──────────────────┬───────────────────┘
                   │
┌──────────────────▼───────────────────┐
│            Application               │
│                                      │
│ Use Case / Business Workflow         │
└──────────────────┬───────────────────┘
                   │
┌──────────────────▼───────────────────┐
│              Domain                  │
│                                      │
│ Marketing Domain / Business Rules    │
└──────────────────┬───────────────────┘
                   │
┌──────────────────▼───────────────────┐
│          Infrastructure              │
│                                      │
│ Database / External Services         │
└──────────────────────────────────────┘
```

Plugin APIは、これらのレイヤーに対して定義された拡張ポイントを提供する。

---

## 4. Presentation Layer

Presentation Layerは、ユーザーがTorifuneを操作するためのWeb UIおよびAPIを提供する。

### 4.1 Web UI

Web UIでは、以下を提供する。

* ダッシュボード
* マーケティング機能の管理画面
* 設定画面
* ユーザー操作画面
* Pluginによって追加された画面

### 4.2 API

APIでは、Web UIおよびPluginから利用するためのインターフェースを提供する。

APIは、Presentation Layerから直接データベースを操作せず、Application Layerを経由して処理する。

---

## 5. Application Layer

Application Layerは、ユーザー操作やAPI要求をユースケースとして処理する。

主な責務は以下とする。

* ユースケースの実行
* トランザクション制御
* 認証状態の確認
* 権限確認
* Domain Layerの呼び出し
* Repository / Providerの呼び出し
* Plugin APIとの連携

Business Ruleそのものは可能な限りDomain Layerに配置し、Application Layerが肥大化しないようにする。

---

## 6. Domain Layer

Domain LayerはTorifuneの中核となるビジネスロジックを管理する。

具体的には、以下のようなTorifune固有の概念を管理する。

* Webサイト
* SNS投稿
* キャンペーン
* アクセス情報
* マーケティングデータ
* その他Torifuneが提供する基本機能

Domain Layerは、特定のデータベース製品、認証サービス、外部API等に直接依存しないことを基本とする。

---

## 7. Infrastructure Layer

Infrastructure Layerは、外部システムとの接続を担当する。

主な対象は以下とする。

* PostgreSQL
* 外部API
* ファイルストレージ
* メールサービス
* SNSサービス
* アクセス解析サービス

Infrastructure Layerへの依存は、可能な限りインターフェースによって抽象化する。

---

## 8. Authentication Architecture

認証処理は、Torifune本体の各機能から直接利用するのではなく、Authentication Providerとして抽象化する。

```text
Application
     │
     ▼
Authentication Interface
     │
     ├── Default Authentication Provider
     │
     └── Plugin Authentication Provider
```

標準状態ではTorifune OSSが提供する標準認証を利用する。

一方、Pluginによって外部認証を利用することも可能とする。

例えば、SaaS版ではOpenID Connectを利用した認証ProviderをPluginとして提供できる。

Torifune本体は、特定の認証サービスや認証基盤の存在を前提としない。

---

## 9. Database Architecture

データベースへのアクセスは、Database ProviderまたはRepository等の抽象化されたインターフェースを経由する。

```text
Application / Domain
          │
          ▼
   Database Interface
          │
          ▼
   Database Provider
          │
          ▼
      PostgreSQL
```

標準構成では、Torifuneが直接PostgreSQLへ接続する。

PluginによってDatabase Providerを差し替えることで、異なる接続方式やデータ配置方式を実装できるものとする。

ただし、Torifune本体のビジネスロジックが、具体的なデータベース接続方式を意識してはならない。

---

## 10. Plugin Architecture

Plugin SystemはTorifuneの主要な拡張機構とする。

Pluginは、Torifuneが公開するPlugin APIを通して機能を拡張する。

主な拡張ポイントは以下とする。

```text
Plugin
├── UI Extension
├── Data Access
├── Event Handling
├── Authentication Provider
├── Database Provider
└── External Service Integration
```

### 10.1 UI Extension

PluginからTorifuneの管理画面へ以下を追加できるものとする。

* メニュー
* ページ
* ダッシュボードウィジェット
* 設定画面
* 操作用UI

### 10.2 Data Access

PluginからTorifuneが管理するデータへアクセスするためのAPIを提供する。

Pluginは原則として、Torifuneのデータベースへ直接SQLを発行しない。

### 10.3 Event Handling

Torifune内部で発生するイベントをPluginが購読できるようにする。

例：

* Webサイト登録
* Webサイト更新
* SNS投稿
* キャンペーンの作成・更新・削除
* アクセスデータの日次集計の完了

イベント名とPayloadの一覧は [`docs/Eventリファレンス.md`](../Eventリファレンス.md)。

**1アクセスごとのイベントは提供しない。** アクセスの発生を都度通知すると、
秒間に何度も呼ばれる口をPluginへ渡すことになり、
遅いPluginが計測そのものを詰まらせる。
アクセスについては**集計が済んだ単位で1回**知らせる（`analytics.rolledUp`）。

**ユーザー操作のイベントも提供しない。** 誰が何をしたかの記録は監査ログ
（`05_API設計.md` §42）の役目で、そこに閲覧の権限（`system.manage`）を置いている。
同じ内容をイベントとして配ると、権限の外から同じ情報が取れることになる。

### 10.4 Authentication Provider

標準認証を置き換えるためのProviderを提供する。

### 10.5 Database Provider

標準のデータベース接続方式を置き換えるためのProviderを提供する。

---

## 11. Plugin Manager

Pluginの登録、インストール、有効化、無効化、削除等を管理する仕組みを提供する。

基本的なライフサイクルは以下とする。

```text
Plugin Package
      │
      ▼
   Install
      │
      ▼
   Register
      │
      ▼
    Enable
      │
      ▼
     Use
      │
      ▼
   Disable
      │
      ▼
   Uninstall
```

Plugin Managerは、Pluginのメタデータ、バージョン、依存関係、状態等を管理する。

---

## 12. 外部サービス連携

SNS、広告、アクセス解析等の外部サービスとの連携は、可能な限りPluginとして実装する。

Torifune本体に特定サービスへの依存を組み込むことを避ける。

```text
Torifune
      │
      └── Plugin API
            ├── SNS Plugin
            ├── Analytics Plugin
            ├── Advertising Plugin
            └── Other Service Plugin
```

これにより、第三者が独自の外部サービス連携Pluginを開発できる構造とする。

---

## 13. SaaS版との統合

Torifune SaaSでは、Torifune OSSを変更せず、Plugin APIを利用してSaaS固有機能を統合する。

想定される構成は以下とする。

```text
┌──────────────────────────────────────┐
│         Torifune SaaS           │
│                                      │
│ User Management                      │
│ Tenant Management                    │
│ Container Management                 │
│ Database Management                  │
│                                      │
│ ┌──────────────────────────────────┐ │
│ │ SaaS Integration Plugins         │ │
│ │                                  │ │
│ │ Authentication Provider          │ │
│ │ Database Provider                │ │
│ │ SaaS-specific UI                 │ │
│ └────────────────┬─────────────────┘ │
└──────────────────┼───────────────────┘
                   │
                   ▼
┌──────────────────────────────────────┐
│          Torifune OSS            │
│                                      │
│ Core / UI / API / Plugin System      │
└──────────────────────────────────────┘
```

SaaS側のユーザー管理、テナント管理、課金、コンテナ管理等はTorifune OSSのコアコードには含めない。

---

## 14. セキュリティ境界

PluginはTorifuneの内部機能へアクセスできるため、Pluginは信頼されたコードとして扱う。

特に以下のProviderは高い権限を持つ。

* Authentication Provider
* Database Provider

そのため、Pluginのインストール元、署名、バージョン、依存関係等について、将来的なセキュリティ対策を可能とする設計にする。

Pluginをインストールすることは、実質的にTorifuneアプリケーションへ追加コードを導入することであるため、Pluginの安全性を検証する仕組みを将来的に導入できる構造とする。

---

## 15. アーキテクチャ上の原則

Torifune OSSでは、以下を基本原則とする。

1. Torifune単体で動作可能であること
2. Torifune本体を特定のSaaS基盤に依存させないこと
3. コア機能と拡張機能を分離すること
4. Pluginから内部実装へ直接依存させないこと
5. 拡張ポイントには明確なInterfaceを定義すること
6. 認証方式をAuthentication Providerとして抽象化すること
7. データベース接続方式をDatabase Providerとして抽象化すること
8. 外部サービス連携を可能な限りPluginとして実装すること
9. Plugin APIの後方互換性を重視すること
10. SaaS固有の機能をTorifune OSS本体へ持ち込まないこと

これらの原則を維持することで、Torifune OSSを独立したオープンソースプロダクトとして提供しながら、SaaS版や第三者による独自拡張にも対応できるアーキテクチャを実現する。
