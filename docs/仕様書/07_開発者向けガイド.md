# 07_開発者向けガイド.md

## 1. 目的

本ドキュメントでは、Torifune OSSの開発に参加する開発者、およびTorifune Pluginを開発する開発者向けに、開発環境、プロジェクト構成、開発ルール、Plugin開発、API利用、UI拡張、テスト等の基本方針を定義する。

TorifuneはOSSとして公開されるため、Torifune本体の開発者と、外部Pluginを開発する開発者の双方が理解しやすい構造を目指す。

---

## 2. 開発対象

Torifuneの開発対象は大きく以下に分類する。

```text
Torifune OSS
├── Core
│   ├── Backend
│   ├── Frontend
│   ├── API
│   ├── Database
│   └── Authentication
│
└── Plugin
    ├── Backend Extension
    ├── Frontend Extension
    ├── API Extension
    ├── UI Extension
    └── Event Extension
```

---

## 3. 開発者の分類

Torifuneでは開発者を大きく2種類に分類する。

### 3.1 Core Developer

Torifune本体を開発する開発者。

以下を変更できる。

* Core
* API
* Database Layer
* Authentication Layer
* Plugin Framework
* UI Framework

### 3.2 Plugin Developer

Torifune Pluginを開発する開発者。

原則としてTorifune Coreの内部実装には依存せず、公開されたPlugin APIを利用する。

---

## 4. 開発環境

Torifune OSSの開発環境は、可能な限りDockerを利用して統一する。

基本構成：

```text
Developer PC
│
├── Torifune
│
├── PostgreSQL
│
└── Development Tools
```

開発環境の起動方法は、プロジェクトルートのREADMEに記載する。

## 6. 環境変数

環境依存の設定は環境変数で管理する。

例：

```text
APP_ENV
APP_URL
DATABASE_HOST
DATABASE_PORT
DATABASE_NAME
DATABASE_USER

```

`.env.example`等を提供し、必要な環境変数を明示する。

## 7. ソースコード構成

Torifune本体の具体的なディレクトリ構造は実装言語・Frameworkに応じて決定する。

概念的には以下の責務分離を行う。

```text
src/
├── API/
├── Application/
├── Domain/
├── Infrastructure/
├── Plugin/
├── Authentication/
├── Database/
└── UI/
```

各Layerの責務を明確にし、異なるLayerの責務を混在させない。

---

## 8. Layerの責務

### API Layer

* HTTP Requestの受付
* Request Validation
* Authentication
* Authorization
* Response生成

### Application Layer

* Use Caseの実装
* Transaction境界
* Domain Serviceの呼び出し

### Domain Layer

* 業務ルール
* Entity
* Value Object
* Domain Service

### Infrastructure Layer

* Database
* 外部サービス
* File System
* Queue等

### UI Layer

* Page
* Component
* Form
* API Client
* Plugin UI

---

## 9. Databaseアクセス

Application LayerやDomain Layerから直接Database実装へ依存することを避ける。

基本構造：

```text
Application
    │
    ▼
Repository Interface
    │
    ▼
Database Provider
```

Database Providerの具体的な実装を差し替え可能な構造とする。

これはSaaS版において、Database接続方式をPluginで拡張するためにも重要である。

---

## 10. Authentication

AuthenticationはAuthentication Providerを介して実装する。

```text
Application
    │
    ▼
Authentication Interface
    │
    ├── Default Provider
    ├── OIDC Provider
    └── SaaS Provider
```

CoreのApplication Layerが特定の認証サービスへ直接依存しないようにする。

詳細は`04_認証設計.md`を参照する。

---

## 11. API開発

APIを追加する場合は以下の順序で設計する。

```text
Resource
  ↓
Endpoint
  ↓
Request
  ↓
Validation
  ↓
Authorization
  ↓
Application Service
  ↓
Response
```

API Layerに業務ロジックを大量に記述しない。

---

## 12. API Version

既存APIを変更する場合、後方互換性を確認する。

破壊的変更が必要な場合はAPI Versionを更新する。

```text
/api/v1/...
/api/v2/...
```

既存Pluginが利用しているAPIを変更する場合は特に注意する。

---

## 13. API仕様

Public APIおよびPlugin APIはOpenAPI等の機械可読な形式で仕様を管理する。

APIを実装した場合は、

* Endpoint
* HTTP Method
* Request
* Response
* Error
* Authentication
* Permission

をドキュメントへ反映する。

## 14. Plugin開発

Torifuneの拡張は可能な限りPluginとして実装する。

Pluginの基本構造：

```text
my-plugin/
├── plugin.json      必須。ディレクトリ名と id を一致させる
├── index.tsx        必須（index.ts でも可）。Plugin を default export する
└── README.md
```

**必須なのは `plugin.json` と `index.ts` / `index.tsx` の2つだけ**であり、
それ以外のファイル構成はPlugin作者に委ねる。
Torifuneは`plugin.json`とエントリポイントの有無だけを見て読み込む。

サーバー側とクライアント側でディレクトリを分けるか、UIを`ui/`へまとめるかは、
Plugin作者が決めてよい。Coreが構造を強制すると、規模の違うPluginに
同じ形を押し付けることになる。

Pluginのデータは Plugin Store へ保存する（§39）。
Plugin独自のテーブル・Migrationを持つ方式は提供しない。

PluginはTorifune Coreと明確な境界を持つ。

---

## 15. Plugin Manifest

PluginにはManifestを配置する。

例：

```json
{
  "id": "example.plugin",
  "name": "Example Plugin",
  "version": "1.0.0",
  "apiVersion": 1,
  "permissions": [
    "site.read"
  ]
}
```

Manifestには最低限以下を定義する。

* Plugin ID
* Plugin Name
* Version
* API Version
* Required Permission

必要に応じて依存Plugin、最低Torifune Version等も定義する。

---

## 16. Plugin ID

Plugin IDは一意でなければならない。

例：

```text
example.plugin
vendor.product
com.example.analytics
```

Plugin IDをPlugin内部の設定、Route、Database Namespace等の識別子として利用できる構造とする。

---

## 17. Plugin Lifecycle

PluginにはLifecycleを設ける。

```text
Install
   ↓
Initialize
   ↓
Enable
   ↓
Running
   ↓
Disable
   ↓
Uninstall
```

Lifecycle HookをPluginへ提供する。

例：

```text
install()
activate()
deactivate()
uninstall()
```

---

## 18. Plugin API

PluginはTorifuneが提供する公開Interfaceを利用する。

概念的には以下のAPIを提供する。

```text
Torifune Plugin SDK
├── Data API
├── UI API
├── Event API
├── Configuration API
├── Authentication API
└── Database API
```

PluginはCore内部の未公開ClassやDatabase Tableへ直接依存しない。

---

## 19. Pluginによる画面追加

Pluginから独自画面を登録できる。

概念例：

```text
registerPage({
    route: "/plugins/example",
    component: ExamplePage,
    permission: "example.read"
})
```

登録したPageはTorifuneの共通Layout内で表示される。

---

## 20. PluginによるMenu追加

PluginはNavigation Menuへ項目を追加できる。

概念例：

```text
registerMenu({
    label: "Example",
    route: "/plugins/example",
    permission: "example.read"
})
```

Permissionを持たないユーザーにはMenuを表示しない。

ただし、URLへの直接アクセスに対する認可も必ずサーバー側で実施する。

---

## 21. PluginによるWidget追加

Dashboard等にWidgetを追加できる。

概念例：

```text
registerWidget({
    location: "dashboard",
    component: ExampleWidget,
    permission: "example.read"
})
```

WidgetはTorifuneの共通UI Componentを利用することを推奨する。

---

## 22. Pluginによる既存画面の拡張

Pluginは既存画面のExtension PointへUIを追加できる。

例：

```text
site.edit.sidebar
site.list.actions
dashboard.after
settings.tabs
```

> Pluginは自身の画面にExtension Pointを定義し、他のPluginへ公開できる。
> `content.*` のような拡張点は、コンテンツ管理Pluginが定義するものであり、
> **Coreは定義しない**（`改訂履歴.md` 2026-08-24）。

これにより、Coreのソースコードを変更せずに機能を追加できる。

---

## 23. Event Hook

PluginはTorifuneのイベントを購読できる。

例：

```text
site.created
site.updated
site.deleted

social.post.created
social.post.published
```

PluginはEvent Handlerを登録する。

```text
subscribe(
    "site.created",
    handler
)
```

Event Payloadの仕様はPlugin APIのVersion管理対象とする。

---

## 24. Pluginからのデータアクセス

Pluginは原則としてData APIを利用する。

```text
Plugin
   │
   ▼
Data API
   │
   ▼
Application
   │
   ▼
Repository
   │
   ▼
Database
```

Pluginから直接SQLを実行することは原則として禁止する。

これにより、Database実装を変更してもPluginへの影響を最小限にできる。

---

## 25. Plugin Database

Pluginが独自データを保存する必要がある場合は、Plugin Store（Plugin IDで
名前空間を区切ったKey-Value領域）を利用する。扱える範囲は`03_プラグイン設計.md` §19。

Pluginは他PluginのTableやCoreの内部Tableへ直接アクセスしない。

概念的には、

```text
Core Data
Plugin Data
Other Plugin Data
```

の境界を維持する。

---

## 26. Plugin Configuration

Plugin固有の設定はConfiguration APIを利用する。

```text
Plugin
   │
   ▼
Configuration API
   │
   ▼
Plugin Configuration Storage
```

API Secret等の機密設定はSecretとして扱う。

---

## 27. Permission

Pluginは必要なPermissionをManifestへ宣言する。

例：

```json
{
  "permissions": [
    "site.read",
    "site.write",
    "analytics.read"
  ]
}
```

Pluginは必要以上のPermissionを要求しない。

---

## 28. Permissionの原則

PluginのPermissionは最小権限を原則とする。

例えばWebサイトの読み取りだけが必要なPluginに、

```text
site.write
site.delete
user.manage
```

等の権限を与えてはならない。

---

## 29. Plugin Security

PluginはTorifuneと同一プロセス内で実行される可能性がある。

そのため、Pluginは**信頼できないコードを安全に隔離するためのSandboxではない**ことを明確にする。

Pluginをインストールすることは、基本的にそのPluginへTorifune内部でのコード実行権限を与えることを意味する。

したがって、Pluginの出所や配布元を確認できる仕組みを提供する。

---

## 30. Plugin Packageの検証

Pluginインストール時には可能な限り以下を検証する。

* Manifestの形式
* Plugin ID
* Version
* API Version
* Dependency
* Permission
* Package Integrity
* Signature

将来的にPlugin Repositoryを提供する場合は、Repository側でPluginの検証情報を提供する。

---

## 31. Frontend開発

FrontendではTorifuneの共通UI Componentを利用する。

Plugin独自のCSSやJavaScriptがTorifune全体へ影響を与えないよう、Namespace等を利用してスタイル・コードの衝突を避ける。

---

## 32. Frontend API Client

FrontendからAPIを呼び出す場合は、可能な限り共通API Clientを利用する。

```text
UI Component
    │
    ▼
API Client
    │
    ▼
Torifune API
```

各画面で個別にHTTP Clientを実装することを避ける。

---

## 33. XSS対策

ユーザー入力や外部サービスから取得したHTMLを画面へ表示する場合は、適切にSanitizeする。

特に以下に注意する。

* HTML
* Markdown
* SNS投稿
* Pluginが提供するデータ

ユーザー入力をそのままHTMLとして出力しない。

---

## 34. CSRF対策

CookieによるSession認証を利用するAPIではCSRF対策を実装する。

特に以下のようなState Changing Requestを保護する。

```text
POST
PUT
PATCH
DELETE
```

GET Requestによってデータ変更を行う設計は避ける。

---

## 35. Secret管理

以下をGit Repositoryへコミットしてはならない。

```text
.env
API Token
Password
Private Key
Client Secret
Database Password
Webhook Secret
```

開発用SecretについてもRepositoryへ直接記載しない。

---

## 36. Logging

アプリケーションログには、デバッグに必要な情報を記録する。

ただし、以下をログへ出力してはならない。

* Password
* Access Token
* Refresh Token
* API Secret
* Cookie
* Session ID
* Database Password

User ID等の識別情報についても、必要性を考慮して記録する。

---

## 37. Error Handling

アプリケーション内部で発生したExceptionは、ユーザー向けResponseと内部ログを分離する。

```text
Exception
   ├── User Response
   │      └── Safe Error Message
   │
   └── Server Log
          └── Debug Information
```

Stack Trace等をユーザーへ返さない。

---

## 38. Database Migration

Database Schemaの変更はMigrationとして管理する。

```text
migrations/
├── 001_initial.sql
├── 002_add_sites.sql
└── 003_add_social.sql
```

Migrationは順番に適用できる状態を維持する。

既存データを破壊するMigrationについては特に慎重に扱う。

---

## 39. Pluginのデータ保存

Pluginが独自データを持つ場合は、Plugin Store（Key-Value）を使う。

```ts
await context.store.set('last-synced-at', new Date().toISOString());
const value = await context.store.get<string>('last-synced-at');

// Secret は暗号化して保存され、get() では取り出せない
await context.store.setSecret('api-token', token);
```

自分の名前空間の外は読み書きできない。Plugin IDはContextが閉じ込める。

**Plugin専用のテーブルやMigrationは、現時点では提供しない**
（`03_プラグイン設計.md` §19.2）。
行数が増えるデータや検索が要るデータを扱いたい場合は、
先にIssueで用途を挙げてほしい。使われる形が分かってから設計する。

アンインストール時のデータ削除は、Plugin Storeの範囲でCoreが行う。
「Plugin本体 / 設定 / データ」を区別し、データ削除は明示的な確認を要求する。

## 47. Breaking Change

以下の変更はBreaking Changeとして扱う可能性がある。

* Public APIの変更
* Plugin APIの変更
* Database Provider Interfaceの変更
* Authentication Provider Interfaceの変更
* UI Extension Pointの削除
* Event Payloadの変更
* Permission仕様の変更

Breaking Changeを行う場合は、Migration Guideを提供する。

Migration Guideは `docs/移行手引き/<変更後のバージョン>.md` に置く。

置き場を決めておくのは、**書く場所が決まっていないと書かれないため**である。
「Migration Guideを提供する」とだけ書いてあった間、実際に提供されたものは無かった。

Migration Guideには最低限、次を書く。

* 何が変わったか（変更前と変更後を並べる）
* なぜ変えたか
* Plugin作者・利用者が何をすればよいか（具体的な手順）
* 移行しなかった場合に何が起きるか

Plugin APIの破壊的変更を伴う場合は、`packages/plugin-api` の
Plugin API Version（§48）を上げ、Migration Guideからその番号を参照する。

---

## 48. Plugin API Compatibility

Plugin APIはTorifune OSSの重要な公開Interfaceである。

Core内部のRefactoringによってPluginが壊れないよう、Plugin APIとCore内部実装を分離する。

```text
Plugin
   │
   ▼
Public Plugin Interface
   │
   ▼
Adapter
   │
   ▼
Core Implementation
```

PluginはCore内部Classへ直接依存しない。

---

## 49. 開発時に避けるべき実装

以下の実装は原則として避ける。

### Core内部への直接依存

```text
Plugin
  ↓
InternalClass
```

### Databaseへの直接アクセス

```text
Plugin
  ↓
SQL
  ↓
Core Table
```

### 認証情報の直接操作

```text
Plugin
  ↓
Password / Session Storage
```

### クライアント入力による権限決定

```text
Request
  ↓
userId / role / tenantId
  ↓
そのまま信頼
```

これらは将来的な拡張性とセキュリティを損なう。

---

## 50. 推奨される拡張方法

新しい機能を追加する場合、以下の順序で検討する。

```text
1. Core機能として必要か？
        │
        ├── Yes → Coreへ実装
        │
        └── No
             ↓
2. Pluginとして実装できるか？
             │
             ├── Yes → Plugin
             │
             └── No
                  ↓
3. Core API / Extension Pointを追加
                  ↓
4. Pluginとして実装
```

Coreを変更する前に、Plugin Extension Pointで実現できないか検討する。

## 56. 開発者向け設計原則

Torifuneの開発では、以下を基本原則とする。

1. CoreとPluginの責務を明確に分離する
2. Pluginは公開されたInterfaceを利用する
3. Core内部実装へのPluginからの直接依存を避ける
4. Databaseへの直接アクセスを避ける
5. Authentication Providerを抽象化する
6. Database Providerを抽象化する
7. APIを安定した公開Interfaceとして扱う
8. UI Extension Pointを利用して画面を拡張する
9. Permissionを最小権限で設計する
10. Client側の制御をSecurity Boundaryにしない
11. Secret情報をコード・ログ・UIへ不用意に露出しない
12. Breaking Changeを可能な限り避ける
13. 新機能はPlugin化できないか検討する
14. OSS CoreへSaaS固有の概念を持ち込まない
15. Architecture、API、Plugin仕様を実装と同時に更新する
