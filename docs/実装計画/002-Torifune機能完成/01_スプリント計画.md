# スプリント計画

1スプリント = `/feature` 1回 = `docs/設計/<ID>-<slug>/` 1ディレクトリ。

## 全体像と依存関係

```text
T1 022-hardening ──────────────────────────┐  横断。先にやる
 │                                          │  （後続がロギング基盤と監査ログに乗る）
 ├─→ T2 019-notification                    │
 │                                          │
 ├─→ T3 021-api-token ──→ T4 015b-settings  │
 │                              │            │
 ├─→ T5 017-campaigns           │            │
 │        │                     │            │
 │        └─→ T6 018-analytics ─┴─→ T7 014-dashboard
 │                                          │
 ├─→ T8 020-plugin-registry                 │
 ├─→ T9 023-webhook                         │
 └─→ T10 024-responsive ────────────────────┘
```

**T1 を最初に置く理由**：ロギング基盤と一般API操作の監査ログは横断的で、
後から入れると既存の全 UseCase を触り直すことになる。
先に土台を作り、以降のスプリントはそこへ乗せる。

**T7 が最後寄りな理由**：ダッシュボードの KPI とアクセス推移チャートは
`018-analytics` のデータが無いと作れない。器だけ先に作ると二度手間になる
（`001` で実際にそうなった）。

## T1. `022-hardening`

**目的**：横断的な土台と、仕様にありながら誰も拾っていなかった穴を埋める。

| 対象 | 仕様 | いま無いもの |
| --- | --- | --- |
| ロギング基盤 | `07` §36 | `api/route.ts` が生の `console.error` を呼ぶ。共通の口が無い |
| 一般API操作の監査ログ | `05` §42 | `auth_audit_logs` は認証イベント限定。サイト削除・Plugin導入が残らない |
| CSP | `04` §13 | `next.config.ts` に headers 設定が無く `middleware.ts` も無い |
| HTTPS強制・HSTS | `05` §42 | 同上 |
| CORS Preflight | `05` §43 | `OPTIONS` ハンドラが無く `Allow-Methods` / `Allow-Headers` を返さない |
| Rate Limit の適用範囲 | `05` §36 | login と password-reset の3本のみ。一覧APIに未適用 |
| Plugin の CSS/JS 名前空間隔離 | `07` §31 | グローバルCSSの衝突を防ぐ機構が無い |
| 高権限Pluginへの強調警告 | `06` §39 | 権限コードを生で並べるだけ |
| バックアップ・リストア手順 | `02` §14 | スクリプトも文書も無い |
| CONTRIBUTING の Issue / Code Review 節、PR・Issueテンプレート | `07` §46 §54 | 無い |
| README の Installation 節 | `07` §53 | 開発セットアップのみ |

**受け入れ条件**

* `x-csrf-token` を伴うクロスオリジン更新がプリフライトを通る（E2E）
* 一覧APIに Rate Limit がかかり、超過で429と `Retry-After` を返す
* サイト削除・Plugin導入が監査ログに残り、Secretが混ざらない
* CSP と HSTS が応答ヘッダに出る。CSP違反でアプリが壊れない
* 2つのPluginが同名CSSクラスを使っても互いの描画を壊さない

## T2. `019-notification`

**目的**：パスワードリセットのフローを完結させる（S-8 #1）。

* `Notifier` の実送信実装（SMTP。設定が無ければ `loggingNotifier` のまま）
* **トークンを受けて新パスワードを設定する画面**（`/password-reset/confirm`）
* リセットメールの本文（トークン入りURL）

**受け入れ条件**

* 要求 → メール受信 → リンク → 再設定 → 旧セッション全失効、が E2E で通る
* トークンは単回使用。期限切れ・使用済み・改竄で同じエラーになる
* SMTP 未設定でも起動し、`torifune reset-password` で復旧できる状態は保つ

> **注意**：画面だけ、メールだけを入れても使えない。**両方を同時に入れる。**

---

## T3. `021-api-token`

**目的**：外部クライアント向けの認証（`05` §37-38、§12）。

* `api_tokens` テーブル（所有ユーザー／有効期限／作成・最終利用日時／無効化状態）
* Token のハッシュ保存。平文は発行時に1度だけ返す
* Scope（Permission の部分集合）と、その検証
* `Authorization` ヘッダによる認証経路を `api/route.ts` に足す
* 発行・一覧・失効の API

**受け入れ条件**

* Token で保護APIを叩ける。Scope外は403、失効後は401
* Token はDBに平文で無い。一覧に平文が出ない
* Token発行と Token認証に Rate Limit がかかる（`05` §36 の重点対象）

## T4. `015b-settings`

**目的**：`001` から送られた設定画面の残り（`06` §16）。

* 設定画面の **一般 / 認証 / API** タブ
* `system.manage` を要求する UseCase（一般タブが消費する）
* Remember Me（**方式はセッション延長で決定済み**。`001/00_決定事項.md`）
* Data API の Users（`03` §5.1、`05` §22）
* 監査ログ：Permission変更 / 外部認証連携設定変更（`04` §26）
* 共通 Tabs コンポーネント（`06` §32。いまは Link でその場実装）

**受け入れ条件**

* 4タブすべてが Permission で出し分けされ、権限なしは403
* Remember Me を有効にしたセッションが、既定より長く生きる
* Plugin が Data API から Users を読める（宣言外は `PluginPermissionError`）

## T5. `017-campaigns`

**目的**：キャンペーン（`02` §5.7、`05` §19、`06` §14）。

* `campaigns` テーブル、Domain、Repository、UseCase、API、画面
* `campaign.read` / `campaign.write` / `campaign.delete` Permission
* Data API の Campaigns、`campaign.*` イベント
* ナビゲーションへ追加

**受け入れ条件**

* CRUD が画面とAPIの両方から通る。権限あり200／なし403／未認証401
* サイトとの関連が引ける（キャンペーンは対象サイトを持つ）

## T6. `018-analytics`

**目的**：アクセス・分析データ（`02` §5.8、`05` §20、`06` §15）。

> **最初に決めること**：`02` §5.8 は「Webサイトや外部サービスから取得した」と
> 両様に読め、収集方式が未確定。**設計書の冒頭でこれを裁定する。**
> 候補は (a) Torifune 自身が計測タグを配って全アクセスを集める、
> (b) 外部解析サービスから集計値を取り込む、(c) 両方を同じテーブルへ正規化する。
> `01_アーキテクチャ設計.md` §12 は外部解析サービス連携をPlugin責務としており、
> **Core は受け皿（テーブルとAPI）を持ち、収集はPluginが担う**のが素直。

* `analytics` / `access_logs` テーブル、Domain、UseCase、API、画面
* 期間・サイトでの絞り込み、Pagination
* `analytics.read` Permission
* Data API の Analytics（Pluginが書き込む口を含む）

**受け入れ条件**

* 期間とサイトで絞り込める。大量データでも一覧が破綻しない
* Plugin が収集したデータを Data API 経由で書き込める
* 収集方式の裁定が設計書に理由つきで残っている

## T7. `014-dashboard`

**目的**：ダッシュボードの中身（`06` §9-10）。

* Core Widget：KPI（アクセス数・投稿数・PV）、アクセス推移チャート、
  最近の投稿、最近の活動
* 共通コンポーネント：Chart、DatePicker（`06` §32）

**受け入れ条件**

* Permission に応じて Widget が出し分けされる
* データが無いときに空状態を出す（`06` §35）
* Plugin Widget と Core Widget が同じ枠組みで並ぶ

## T8. `020-plugin-registry`

**目的**：Plugin の配布と検証（`03` §14.1 §15 §20.1、`06` §18、`07` §29-30）。

* Registry クライアント（検索・取得・インストール）
* Package の署名検証・Checksum 照合・出所（配布元）検証
* **Plugin の更新**（同IDの再導入が `ValidationError` で拒否される。`03` §13）
* **`install()` / `uninstall()` フックの呼び出し**（S-8 #3）
* 依存関係を一覧に表示する（`03` §13）

> **決めること**：`install()` をいつ呼ぶか。導入は再ビルドを伴い、
> 再ビルド前は Plugin のコードを読み込めない。
> 「再ビルド後の初回起動で1度だけ」が有力。設計書で裁定する。

**受け入れ条件**

* 署名の無い／壊れたPackageを拒否する
* 更新でデータを失わない。失敗したら前の版へ戻る
* `install()` が導入時に1度だけ、`uninstall()` が削除時に呼ばれる

## T10. `024-responsive`

**目的**：レスポンシブ対応（`06` §31）。

`001` は「本格的なデザイン、レスポンシブの作り込み」を範囲外としたが、
§31 は実装対象の§であり、`002` の完了条件（193§）に含まれる。

* `@media` が全コードに0件。`app-shell.tsx` のサイドバーが220px固定
* `layout.tsx` に viewport 指定が無い

**受け入れ条件**

* 幅375pxでナビゲーションと主要画面が破綻しない
* テーブルが横スクロールで収まる（`06` §32）
