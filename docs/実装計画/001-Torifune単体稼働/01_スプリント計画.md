## S0. 雛形整備（設計書なし）

**目的**：以降のスプリントが `/feature` のフローに乗れる状態を作る。

**やること**

* pnpm workspace（D-01 の構成）、Next.js、TypeScript strict、ESLint、Prettier
* Vitest / Playwright の設定と、それぞれ1本ずつのサンプルテスト
* GitHub Actions（lint / typecheck / test / build。結合テスト用 `services: postgres`）
* 開発用 `compose.yaml`（PostgreSQL のみ）と `.env.example`
* `LICENSE`（MIT）、`README.md`、`CONTRIBUTING.md`、`SECURITY.md`
* `CLAUDE.md` の「ディレクトリ構成」節を D-01 の構成に、「コマンド」節を実際の
  `package.json` のスクリプト名に更新する
* **スパイク：Plugin 再ビルド方式の実現性検証**（→ `03_リスクと未決事項.md` R-01）
  コンテナ内で `next build` → プロセス終了 → restart policy で復帰、が成立するかを
  最小構成で確かめる。ここで成立しなければ D-02 を見直す

**完了条件**：`pnpm install && pnpm lint && pnpm typecheck && pnpm test && pnpm build` が
クリーンな環境で通り、CI が緑になる。スパイクの結果が `03_リスクと未決事項.md` に反映されている。

## S1. `001-database-foundation`

**目的**：Domain 層がDB製品を知らないままデータを永続化できる土台を作る。

**やること**

* Database Provider Interface（`connect` / `transaction` / `query` / `healthCheck`）
  — `05_API設計.md` §27 の形に合わせる
* PostgreSQL Provider（pg Pool ベース）。接続先は環境変数から
* Repository Interface を Domain 層に、実装を Infrastructure 層に置く分割の基準を確立する
* トランザクション境界を Application 層（UseCase）に置く仕組み
* マイグレーションランナー（連番SQL、`schema_migrations`、advisory lock、冪等）
* `migrations/001_initial.sql`：`users` / `roles` / `permissions` / `user_roles` /
  `role_permissions` / `sessions` / `auth_audit_logs`
* `torifune migrate --database-url` CLI（D-11）

**受け入れ条件の骨子**

* 同じマイグレーションを2回流しても既存データが壊れず、2回目は何も適用されない
* 空のDBに対して `torifune migrate --database-url` が全スキーマを構築できる
* 2プロセスから同時にマイグレーションを実行しても二重適用が起きない
* Domain 層のファイルが `pg` / `kysely` を import していない（boundary-guardian の検査対象）

## S2. `002-authentication`

**目的**：Torifune 単体でログイン・ログアウトが完結する。

**やること**

* Authentication Provider Interface（`authenticate` / `getIdentity` / `logout` / `refresh`）
* 標準認証 Provider（Argon2id）
* User Identity（認証方式によらない統一表現。`04_認証設計.md` §16）
* セッション管理（DB永続、識別子はハッシュ保存、ログイン時に再生成、有効期限とアイドルタイムアウト）
* Cookie 属性、CSRF 対策、ログイン試行制限（IP単位・アカウント単位）
* 認証監査ログ（`04_認証設計.md` §26 の対象イベント）
* `/setup` 初回セットアップ画面（D-10）、ログイン画面、ログアウト
* パスワードリセットは**トークン発行・検証・再設定まで実装**し、通知は Notifier
  インターフェース越しの「ログ出力実装」で止める（実メール送信は次計画）

**受け入れ条件の骨子**

* 管理者が0人のとき `/setup` が開き、1人作られた後は `/setup` が 404 になる
* 管理者が存在する状態で `/setup` へ POST しても必ず拒否される
* ログイン前後でセッションIDが変わる
* ログアウト後、同じCookieでの保護ページアクセスが 401 になる
* セッションCookieに `HttpOnly` が付いている（JavaScript から読めない）
* CSRF トークンなしの POST が拒否される
* 同一アカウントへの連続失敗が閾値でブロックされ、監査ログに残る
* 監査ログにパスワード・トークンが記録されていない

## S3. `003-authorization`

**目的**：Permission による認可を UseCase 層で強制する（D-06）。

**やること**

* Role / Permission モデルと初期データ（Administrator / Editor / Viewer）
* Permission 名の体系を確定させる。最低限：
  `site.read` `site.write` `site.delete` / `content.read` `content.write` `content.delete` /
  `social.read` `social.write` `social.delete` / `user.manage` / `plugin.manage` / `system.manage`
* UseCase が Permission を要求する共通の仕組み（未認証→401、権限不足→403）
* UI 側の表示制御用に「現在のユーザーが持つ Permission」を返す口

**受け入れ条件の骨子**

* Permission を要求する UseCase が、未認証で 401、権限なしで 403、権限ありで成功する
* UI でボタンを隠しただけの状態でも、直接呼び出せば 403 になる
* Permission チェックを持たない UseCase が存在しないことを検査できる（一覧テスト）

## S4. `004-api-foundation`

**目的**：`/api/v1` の形を1本に固め、以降のドメインが同じ型で増やせるようにする。

**やること**

* ルーティング規約、Zod による Request/Response バリデーション
* 統一レスポンス形式（`{ data, meta }`）とエラー形式（`{ error: { code, message, details } }`）
  — `05_API設計.md` §10-11
* Pagination（`page` / `perPage`）、Filtering、Sorting の共通実装。
  **Sort 可能なフィールドはAPIごとにホワイトリスト化**する（`05` §35）
* Rate Limit（ログイン・パスワードリセットを重点的に。超過は 429）
* エラーハンドリング（Stack Trace / SQL を絶対にレスポンスへ出さない）
* Zod スキーマからの OpenAPI 生成と `/api/v1/openapi.json` の配信

**受け入れ条件の骨子**

* 400 / 401 / 403 / 404 / 409 / 422 / 429 / 500 が仕様どおりの形で返る
* 内部例外の詳細がレスポンスに含まれない
* `sort` に未許可のフィールドを渡すと 422 になり、DBカラム名を直接指定できない
* 生成された OpenAPI が実装と一致する（スキーマからの生成なので構造的に担保）

## S5. `005-ui-shell`

**目的**：機能を載せるための最低限の器を作る。詳細は `02_画面デザイン方針.md`。

**やること**

* デザイントークン（CSS変数）と Tailwind の接続
* 共通レイアウト：ヘッダー（「とりふね」＋ユーザーメニュー）／左ナビ／メイン／フッター
* 共通コンポーネント（`02_画面デザイン方針.md` の一覧）
* Loading / Empty / Error / 権限なし の4状態
* Toast、確認ダイアログ（削除等の不可逆操作用）
* 共通 API Client（エラーコード→表示メッセージの変換を1箇所に集約）
* Permission による表示制御（**認可対策ではない**ことをコメントで明示する）

**受け入れ条件の骨子**

* 全コンポーネントが色・余白・角丸・フォントを CSS 変数経由でのみ参照している
  （生の hex 値やピクセル直書きがない）
* 一覧画面が Loading / Empty / Error / 正常 の4状態をすべて描画できる
* トークンの値を差し替えるだけで全画面の見た目が変わる

## S6. `006-secret-storage`

**目的**：Secret を平文で持たない共通基盤。SNS の Access Token と Plugin の Secret 設定で共用する。

**やること**

* 暗号化サービス（AES-256-GCM、鍵は環境変数、暗号文に鍵IDを併記）
* 「保存はできるが読み出しはアプリ内部のみ、APIレスポンスと画面には返さない」型の設計
  （型レベルで平文が外へ出ないようにする）
* マスク表示のための「設定済みかどうか」だけを返す口

**受け入れ条件の骨子**

* 暗号化した値がDB上で平文になっていない
* Secret 型の値を含むオブジェクトを JSON 化しても平文が出ない
* 鍵が未設定・不正のときは起動時に落ちる（黙って平文保存に落ちない）

## S7. `007-sites` / S8. `008-contents` / S9. `009-social`

3つとも同じ型で作る。**S7 で型を確立し、S8・S9 はそれを踏襲する。**

各スプリントの構成：

| レイヤ | 中身 |
| --- | --- |
| Domain | Entity、Value Object、業務ルール、Repository Interface |
| Application | UseCase（一覧 / 取得 / 作成 / 更新 / 削除）、トランザクション境界、Permission 要求 |
| Infrastructure | Repository 実装、マイグレーション |
| API | `/api/v1/sites` 等の Route Handler、Zod スキーマ |
| UI | 一覧（Table＋Pagination）、作成・編集フォーム、削除の確認ダイアログ |
| Event | `site.created` `content.created` 等の発火（購読側は S11 で動く） |

**S7 `007-sites`**：`sites`（name / url / status）

**S8 `008-contents`**：`contents`（site_id / title / body / status: draft|published / published_at）。
サイトに従属する親子関係と、公開状態の遷移を扱う。

**S9 `009-social`**：`social_accounts`（provider / 表示名 / 暗号化トークン）、
`social_posts`（content_id 任意 / body / scheduled_at / status / 履歴）。
**外部SNSとの実連携は Plugin の責務**（`01_アーキテクチャ設計.md` §12）であり、
Core が持つのはデータの箱と状態管理まで。S6 の暗号化を必ず通す。

**受け入れ条件の骨子（3スプリント共通）**

* CRUD が正常に動く
* 未認証で 401、権限なしで 403
* **他ユーザー／他リソースのIDを差し替えても取得・更新・削除ができない**
* バリデーションエラーが 422 で、フィールド単位の詳細が返る
* 存在しないIDで 404
* 一覧が Pagination / Filtering / Sorting に対応し、未許可の sort フィールドを弾く
* （S9）Access Token が API レスポンスにも画面にも平文で出ない
* （S9）SNSアカウント削除時に紐づく投稿の扱いが定義どおり

## S10. `010-plugin-api`

**目的**：Plugin の公開契約を `packages/plugin-api` として確定させる（D-09）。

**やること**

* Manifest スキーマ（`plugin.json`）：id / name / version / apiVersion / description /
  author / license / dependencies / extensions / permissions
* `PluginContext`（Plugin に渡す唯一の入口）
* UI API：`registerMenu` / `registerPage` / `registerWidget` / `registerAction` /
  `registerSettingPage` / Extension Point への登録
* Extension Point の初期セット：`dashboard.before` `dashboard.after`
  `content.edit.sidebar` `content.list.actions` `site.edit.sidebar` `settings.tabs`
* Event API：`subscribe(eventName, handler)` とイベントペイロードの型
* Configuration API：一般設定と Secret 設定を型で分離
* Data API：Sites / Contents / Social への読み書き（**Permission を通る**）
* Authentication Provider / Database Provider のインターフェース
* Plugin API Version（初期 `1`）と、後方互換性の判断基準を文書化する

**受け入れ条件の骨子**

* `packages/plugin-api` が `apps/web` へ一切依存していない（依存の向きをビルドで検査）
* Manifest の不正な値（不明な apiVersion、未定義の Permission 等）が検証で弾かれる
* Data API 経由の読み書きが呼び出し元 Plugin の Permission に従う
* 標準認証と PostgreSQL Provider が、公開した Provider 契約の形で登録されている

## S11. `011-plugin-runtime`

**目的**：Plugin が実際に動く。

**やること**

* ビルド時の `plugins/` 走査とレジストリ生成
* Lifecycle（install / register / enable / disable / uninstall）と状態のDB管理
* 依存関係の検証（依存Pluginが無い・バージョン不一致なら有効化しない）
* catch-all ルート（D-07）と、そこでの Permission 検証
* Menu / Widget / Action / Extension Point の描画側実装
* Event Dispatcher と購読の登録。**Plugin のハンドラが落ちても本体の処理を巻き込まない**
* Configuration API の永続化（Secret は S6 経由）

**受け入れ条件の骨子**

* 無効化した Plugin のページへ直接URLアクセスすると 404 になる
* Permission を持たないユーザーが Plugin ページへ直接アクセスすると 403 になる
* 依存を満たさない Plugin が有効化できない
* Plugin の Event ハンドラが例外を投げても、発火元の UseCase が成功する
* 無効化すると、その Plugin のメニュー・ページ・Widget・Event ハンドラがすべて止まる

---

## S12. `012-plugin-manager`

**目的**：管理画面から Plugin を扱える。

**やること**

* Plugin 一覧（名前 / バージョン / 状態）、有効化・無効化、設定画面への導線
* 導入フロー（D-02）：取得 → 配置 → Manifest 検証 → **要求Permissionの表示と同意** →
  レジストリ再生成 → 再ビルド → 再起動。進行状況と失敗時の表示
* ビルド失敗時に直前の成功状態へ戻せること
* アンインストール時に「Plugin 本体 / 設定 / データ」を区別し、データ削除は明示的な確認を要求する

**受け入れ条件の骨子**

* `plugin.manage` を持たないユーザーは Plugin 管理画面にも API にも到達できない
* 不正な Manifest の Plugin を導入しようとすると、ビルドに入る前に拒否される
* 要求 Permission がインストール前に表示される（`06_画面設計.md` §39）
* ビルドに失敗しても、再起動後に直前の正常な状態で立ち上がる

## S13. `013-example-plugin`

**目的**：Plugin API が本当に使えることを、Torifune 自身のコードを1行も変えずに示す。

**やること**：`plugins/example-plugin/` に以下をすべて含むサンプルを作る。

* 左ナビへの項目追加と独自ページ（`/plugins/example-plugin`）
* ダッシュボードへの Widget 追加
* コンテンツ一覧への Action 追加（`content.list.actions`）
* コンテンツ編集画面のサイドバーへのUI追加（`content.edit.sidebar`）
* `content.created` の購読
* 設定画面（一般設定＋Secret設定を1つずつ）
* Data API で Contents を読む
* ログを出すだけのダミー Database Provider（差し替えが成立することの実証）

**受け入れ条件の骨子**

* サンプルPluginのコードが `apps/web` の内部モジュールを一切 import していない
* 導入 → 有効化で、上記すべてが画面に現れる
* 無効化で、上記すべてが消える
* `docs/` にサンプルを題材にした Plugin 開発の手引きがある
