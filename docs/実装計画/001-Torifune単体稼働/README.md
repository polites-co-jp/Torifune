# 実装計画 001 — Torifune単体稼働

## 1. この計画のゴール

Torifune を **TorifuneHub なしで完結して動く状態**にする。
まっさらな環境で以下がすべて通ることをもって完了とする。

1. `docker compose up` 後にブラウザで開くと `/setup` へ誘導され、最初の管理者を作成できる
2. その管理者でログインでき、ログアウトでサーバー側セッションが失効する
3. Webサイト → コンテンツ → SNSアカウント／SNS投稿 を作成・編集・削除できる
4. `plugins/` にサンプルPluginを置いて管理画面から「読み込む」を押すと、再ビルド・再起動を経て
   左ナビに項目が増え、ダッシュボードにWidgetが出て、`content.created` を購読したPluginが反応する
5. すべての保護APIで「権限あり→200 / 権限なし→403 / 未認証→401」がテストで確認できる
6. `torifune migrate --database-url=...` が任意の空DBへスキーマを適用できる
   （TorifuneHub がテナントDBを払い出すための前提。この計画時点では OSS 単体の初期化機能として実装する）

## 2. この計画に含めないもの

### 責務としてTorifuneに入れないもの（`CLAUDE.md`「絶対に守る境界」）

マルチテナント、SaaSとしてのユーザー登録・管理、テナントDB管理、課金、コンテナ運用基盤。
すべて TorifuneHub の責務であり、必要になったら Plugin API の拡張ポイントとして提供する。

### 次の計画へ送るもの（Torifuneの責務ではあるが今回やらない）

* Campaigns / Analytics ドメイン
* API Token（外部クライアント向け認証。`05_API設計.md` §37-38）
* Plugin Registry、Plugin Package の署名検証、依存関係の自動解決
* パスワードリセットのメール送信（Provider インターフェースだけ用意し、実送信は次計画）
* Webhook（`05_API設計.md` §39）
* 本格的なデザイン、レスポンシブの作り込み、アニメーション（→ `02_画面デザイン方針.md`）

## 4. 進め方

* 1スプリント = `/feature` 1回 = `docs/設計/<ID>-<slug>/` 1ディレクトリ
* スプリント0（雛形整備）だけは設計書を伴わない。それ以降はすべて
  design-writer → impl-planner → test-writer → implementer → 検証3種 の順を守る
* design-writer は設計書を書く前に `00_決定事項.md` を読むこと。
  ここで確定した選定を設計書側で蒸し返さない
* `docs/仕様書/` は上位仕様であり、この計画から勝手に書き換えない。
  矛盾を見つけたら、どの文書のどの節と食い違うかを明示して判断を仰ぐ
