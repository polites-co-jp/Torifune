## D-01. リポジトリ構成 — pnpm workspace 化する

**決定**

```text
Torifune/
├── package.json              pnpm workspace ルート
├── pnpm-workspace.yaml
├── apps/
│   └── web/                  Next.js 本体
│       └── src/
│           ├── api/              API Layer（Route Handler、Zodスキーマ、Response整形）
│           ├── application/      UseCase、トランザクション境界、認可の強制点
│           ├── domain/           Entity / Value Object / Domain Service / Repository Interface
│           ├── infrastructure/   Repository実装、外部サービス、ファイル
│           ├── plugin/           Plugin Runtime、レジストリ、Extension Point の実装
│           ├── authentication/   Authentication Provider Interface と標準実装
│           ├── database/         Database Provider Interface と PostgreSQL 実装
│           └── ui/               Layout / Component / API Client
├── packages/
│   ├── plugin-api/           公開Plugin API（型とインターフェースのみ）。将来 @torifune/plugin-api として npm 公開
│   └── cli/                  torifune CLI（migrate 等）
├── plugins/                  ローカルPlugin配置先
├── migrations/               連番SQL
└── docs/
```

**理由**

* Plugin API の契約は、別リポジトリの TorifuneHub と第三者プラグイン作者が参照する。
  アプリ内部のディレクトリに置いたままでは、契約と内部実装の境界がコード上で表現できず、
  `03_プラグイン設計.md` §21「公開APIと内部APIを明確に分離する」を満たせない
* `packages/plugin-api` を独立パッケージにしておけば、そこに `apps/web` への import が
  1つでも生まれた時点でビルドが壊れる。**境界を人間の注意力ではなくビルドで守れる**
* CLI をパッケージとして切り出すのは、TorifuneHub が `torifune migrate` を叩く（D-11）ため

**却下した案**

* ルート直下 `src/` の単一アプリ（現行 `CLAUDE.md` の記述）
  → TorifuneHub 側が型を手写しするか Torifune を git 依存として引く必要があり、契約の二重管理になる

**追随して必要な作業**：`CLAUDE.md`「ディレクトリ構成」節をこの構成に更新する（スプリント0）

## D-02. Plugin のロード方式 — ビルド時ロード ＋ 管理者操作による再ビルド

**決定**

* `plugins/` 配下を**ビルド時に走査してレジストリを生成**する。実行時の動的 import は使わない
* Plugin の**導入**（ファイル配置 → 再ビルド → 自己再起動）は**インスタンス管理者の操作**とする
* Plugin の**有効化/無効化**は DB のフラグで実行時に切り替える（再ビルドを伴わない）
* 導入フロー：マーケット/URL から取得 → `plugins/<plugin-id>/` へ展開 → Manifest 検証 →
  レジストリ再生成 → `next build` → プロセス終了 → コンテナの restart policy で復帰

**理由**

* Next.js で UI 拡張を実行時ロードするには Module Federation か iframe が要り、
  ビルド基盤・セキュリティ・型安全性のすべてでコストが跳ね上がる
* 「導入＝管理者操作、有効化＝利用者操作」に分けることで、TorifuneHub の
  `06_コンテナ設計.md` §6「MarketingHub コンテナは全テナントで1つを共有」と衝突しない。
  テナントがプラグインを入れるたびに全テナントが再起動する事態を構造的に避けられる

**却下した案**

* サーバー側のみ実行時ロード（UI はビルド時）→ ロード経路が2系統になり、Manifest の解釈が二重化する
* 完全実行時ロード（WordPress 型）→ 最初のマイルストーンが大幅に遠のく

**この決定が持ち込む制約**（→ `03_リスクと未決事項.md` R-01）

* イメージにビルドツールチェーンを同梱する必要があり、Next.js の standalone 出力が使えない
* `plugins/` を書き込み可能な永続ボリュームにする必要がある
* ビルド中のメモリ確保とビルド失敗時のロールバックを設計しなければならない

## D-03. DBアクセス層 — node-postgres + Kysely

**決定**：`pg`（node-postgres）の Pool の上に Kysely を薄くかぶせる。ORM は使わない。

**理由**

* Database Provider は**リクエストごとに接続先DBを差し替える**（TorifuneHub のテナントDB）。
  接続ごとにクエリビルダのインスタンスを軽く作れることが必須条件になる
* Kysely は接続オブジェクトを受け取るだけの薄い層なので、この要件と正面から噛み合う
* 型はマイグレーションSQLから生成できるため、スキーマ定義の二重管理が発生しない

**却下した案**

* Prisma → DBごとに Client インスタンスとエンジンが必要で、動的なDB切り替えに構造的に不向き
* Drizzle ORM → 「TSスキーマが正」と「連番SQLが正」の二重管理になりやすい（D-04と衝突）
* 生SQLのみ → テーブル数が増えたときの型安全性とリファクタ耐性が落ちる

## D-04. マイグレーション — 連番SQL ＋ 自前ランナー

**決定**

* `migrations/001_initial.sql` 形式の連番SQLを正とする
* 適用状況は対象DB内の `schema_migrations` テーブルで管理する
* 適用時に PostgreSQL の advisory lock を取り、多重起動でも二重適用しない
* 繰り返し実行しても既存データを壊さない（`02_データベース設計.md` §9）

**理由**：仕様書が形式を明示しており（`02` §10、`07` §38）、かつ TorifuneHub が
テナントDBへプログラムから適用する必要があるため、CLI 前提のツールでは要件を満たせない。

## D-05. UI — Tailwind CSS ＋ 自前ミニマルコンポーネント

**決定**：Tailwind を入れ、共通コンポーネントは自前で薄く作る。UIライブラリは導入しない。
詳細は `02_画面デザイン方針.md`。

**理由**：`06_画面設計.md` §32 は「Plugin は Torifune の共通 Component を利用する」と定めており、
共通コンポーネントは**実質的に公開契約**になる。外部ライブラリの仕様に契約を引きずられると、
そのライブラリのメジャーバージョンアップが Plugin API の破壊的変更に化ける。

**却下した案**：shadcn/ui（Radix）、MUI

## D-06. UI からデータを取る経路 — 読みは直呼び、書きは REST

**決定**

* **認可は API Layer ではなく UseCase（Application Layer）で強制する**
* 一覧・詳細の初期描画は Server Component から UseCase を直接呼ぶ
* 作成・更新・削除は `/api/v1/...` の REST を叩く
* Plugin と外部クライアントは同じ `/api/v1` と Data API を使う

**理由**

* `05_API設計.md` §29 が「同一プロセス内で利用できる Service Interface があればそれを利用する」と
  明示的に許容している
* 認可を UseCase 層に置けば、どの経路（Server Component / REST / Plugin Data API）から
  来ても同じ判定が働く。API Layer に置くと経路ごとに漏れが生じる

**却下した案**

* 常に `/api/v1` 経由 → 初期表示が遅く、自分自身へのHTTP呼び出しと認証Cookieの中継が冗長
* Server Actions 中心 → Next.js 固有機能への依存が深くなり、同じ操作が2経路に重複実装される

## D-07. Plugin ページのルーティング — catch-all ルート

**決定**：`apps/web/src/app/plugins/[pluginId]/[[...rest]]/page.tsx` を1枚だけ置き、
ビルド時生成したレジストリから Plugin のページコンポーネントを解決して描画する。

**理由**

* ルートファイルの自動生成が不要になり、Plugin 導入フロー（D-02）が「レジストリ再生成 → ビルド」の
  2ステップで済む
* 未登録・無効化済み・Permission 不足の判定を**この1箇所に集約**できる。
  `06_画面設計.md` §30「URL直接アクセスでも Permission を検証する」を構造的に守れる

## D-08. 認証 — DB永続セッション ＋ HttpOnly Cookie、Argon2id

**決定**

* パスワードハッシュは Argon2id（`@node-rs/argon2`）
* セッションは DB に永続化し、Cookie にはセッション識別子（256bit の乱数）のみを入れる。
  DBには識別子のハッシュを保存する
* Cookie 属性：`HttpOnly` / `SameSite=Lax` / 本番は `Secure`
* ログイン成功時にセッションIDを再生成する（`04_認証設計.md` §9）
* ログアウトでサーバー側セッションを失効させる
* CSRF は Origin / Sec-Fetch-Site 検証 ＋ 二重送信トークンの併用
* ログイン試行制限は IP 単位とアカウント単位の両方

**理由**：`04_認証設計.md` §7 が「Cookie には識別子のみ」、§10 が「ログアウト時にサーバー側セッションを
無効化」と定めており、ステートレスな署名付きトークンでは §10 を満たせない。

## D-09. Plugin API の初期スコープ — 最重要4拡張点をすべて確定させる

**決定**：`packages/plugin-api` に以下を公開する。

| 契約 | この計画での実装 |
| --- | --- |
| UI Extension（Menu / Page / Widget / Action / Extension Point） | 実装する |
| Event API（subscribe とペイロード定義） | 実装する |
| Configuration API（一般設定とSecret設定を分離） | 実装する |
| Data API（Sites / Contents / Social への読み書き） | 実装する |
| Authentication Provider | **インターフェースを公開**し、標準認証をその契約で登録する |
| Database Provider | **インターフェースを公開**し、PostgreSQL Provider をその契約で登録する |

**理由**：`03_プラグイン設計.md` §25 が上記のうち UI / Data / Authentication Provider /
Database Provider の4つを最重要としており、後ろ2つは TorifuneHub が直接依存する。
契約を後回しにすると、TorifuneHub 着手時に Torifune 側の再設計が発生する。

差し替えの実証は、ログを出すだけのダミー Provider をサンプルPluginに同梱して安く済ませる。

## D-10. 初期管理者の作成 — 初回セットアップ画面

**決定**：管理者が1人もいない間だけ `/setup` を開放し、そこで最初の管理者を登録する。
1人作られた時点で `/setup` は自動的に閉じる（以後は 404）。

**理由**：環境変数にもイメージにも初期Credentialを置かずに済み、OSS を初めて試す人の体験が最も良い。
`06_コンテナ設計.md` §77「初回セットアップ」とも整合する。

**注意**：`/setup` の開放判定は必ずサーバー側で行い、管理者が存在する状態でPOSTされても
必ず拒否すること（レースコンディションはDBの一意制約で塞ぐ）。

## D-11. TorifuneHub へのスキーマ提供 — migrate CLI を同梱する

**決定**：`torifune migrate --database-url=<url>` を提供し、連番SQLをイメージに同梱する。

**理由**：OSS 単体でもDB初期化に必要な機能であり、SaaS固有の概念を一切持ち込まない。
TorifuneHub の Provisioning はこのCLIを叩くだけで済む。

**却下した案**

* マイグレーションSQLを npm パッケージで公開 → イメージ版とパッケージ版のバージョン一致を常に担保する必要
* 管理APIで受け付ける → 接続先DBを外部から指定できるAPIを公開することになり、
  `04_認証設計.md` §14 / `05_API設計.md` §30「クライアントから Database を指定させない」に正面から衝突
