## R-01. Plugin の「再ビルド＆自己再起動」方式が本番構成と噛み合うか（**要検証・最優先**）

D-02 で採用した導入方式は、以下をコンテナ構成に要求する。

| 要求 | 衝突しうる規定 |
| --- | --- |
| イメージにビルドツールチェーンを同梱する（Next.js の standalone 出力が使えない） | イメージサイズと攻撃面が増える |
| `plugins/` を書き込み可能な永続ボリュームにする | `06_コンテナ設計.md` §71「Read-only Filesystem」 |
| ビルド時に 1〜2GB のメモリを確保できる | 本番のリソース設計 |
| ビルド中〜再起動中はサービスが停止する | `07_デプロイ設計.md` §75「Maintenance Mode」 |
| ビルド失敗時に直前の成功状態へ戻せる | `07_デプロイ設計.md` §51「Application Rollback」 |

**対応**：スプリント0でスパイクを行い、成立を確認してから S12 へ進む。
成立しなければ D-02 を「ファイルを配置してコンテナを再作成する運用手順」に格下げし、
管理画面からは検証と手順の提示までに留める。

**現時点の緩和案**

* 書き込み可能にするのは `plugins/` ボリュームと `.next/` の出力先だけに限定し、
  それ以外は read-only を維持する
* ビルド成果物を世代管理し、失敗したら直前の世代で起動する
* ビルド中はメンテナンス表示を返す（Reverse Proxy 側ではなくアプリ側で 503 ＋ 案内）

## R-02. 「マーケット」（Plugin Registry）が未定義

D-02 の導入フローの起点である「マーケットからダウンロード」の**出所が決まっていない**。
`03_プラグイン設計.md` §15 は Plugin Registry を将来構想として書いているだけで、
実体・URL・配布形式・署名方式のいずれも未定。

**この計画での扱い**：マイルストーンAでは以下だけを実装する。

* ローカル配置（`plugins/<plugin-id>/` に人が置く）
* URL または ZIP ファイル指定による取り込み（**署名検証なし**）

**未決**：公式 Registry を作るのか、GitHub Releases 等を使うのか、
第三者 Registry を許すのか。Registry と署名検証は `020-plugin-registry` として次計画へ送る。
それまでは管理画面に「導入元の信頼性は利用者の責任である」旨を明示する。

## R-05. Permission 体系の具体値が仕様書に無い

`04_認証設計.md` §14 と `05_API設計.md` §14 は「機能実装時に定義する」としている。
S3（`003-authorization`）で確定させ、以降のスプリントはそれに従う。

**注意点**：Plugin が Manifest で要求する Permission も同じ名前空間を使う
（`03_プラグイン設計.md` §20.2）。Plugin 独自の Permission を後から追加できるよう、
Permission を固定の enum ではなくレジストリで管理する。

## R-06. SNS ドメインが「箱」に留まること

S9 で作る `social_accounts` / `social_posts` には、
**外部SNSとの実連携が入らない**（`01_アーキテクチャ設計.md` §12 により Plugin の責務）。
そのため、マイルストーンA の時点では「投稿を登録できるが実際には投稿されない」状態になる。

これは仕様どおりだが、デモや説明の際に誤解を招きやすい。
画面上に「連携Pluginが未導入のため実際の配信は行われません」を明示する。

## R-07. Server Component からの UseCase 直呼びと認可の一貫性

D-06 により、同じ UseCase が Server Component 経由と REST 経由の両方から呼ばれる。
**認可を UseCase に置く**ことでこれを担保する設計だが、
実装が進むと「Server Component では認証済み前提だから」と認可を省く誘惑が生じる。

**対応**：S3 の受け入れ条件に「Permission チェックを持たない UseCase が存在しない」
という一覧テストを含める。security-reviewer と boundary-guardian の常設チェック項目にする。

## R-08. TorifuneHub 側との同期タイミング

TorifuneHub の `006-torifune-auth-plugin` と `007-torifune-database-plugin` は、
Torifune の S10（`010-plugin-api`）が完了して `packages/plugin-api` が固まるまで着手できない。

**S10 完了時点で TorifuneHub 側へ通知する。**
それまで TorifuneHub 側は S0〜S5（雛形・コンテナ・System DB・OIDC・テナント管理）を進める。
TorifuneHub 側で Plugin API の不足を見つけた場合は、Hub 側で回避策を書かず、
Torifune 側の別セッションで拡張ポイントを追加する（両リポジトリの `CLAUDE.md` の規定）。
