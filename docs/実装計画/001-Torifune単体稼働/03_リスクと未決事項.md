## R-01. Plugin の「再ビルド＆自己再起動」方式が本番構成と噛み合うか（**検証済み：成立**）

> **スパイク結果（S0 で実施）**
>
> `Dockerfile` と `docker/entrypoint.sh` を実装し、コンテナ内で以下を確認した。
>
> | 検証項目 | 結果 |
> | --- | --- |
> | 稼働中のコンテナ内で `next build` が完走するか | ○ 成功（雛形アプリで 3 秒） |
> | 再ビルドで増えたページが再起動後に配信されるか | ○ 新規ページが 200 で返った |
> | 終了コード 75 を受けて supervisor が再ビルド→再起動するか | ○ ループが期待どおり動作 |
> | ビルド失敗時に直前の成功ビルドへ戻るか | ○ 退避した `.next` から復帰し、旧ビルドで配信を継続 |
> | ビルド時のピークメモリ | 約 **1.1 GiB**（雛形アプリの時点） |
> | イメージサイズ | 約 **1.3 GB**（devDependencies とツールチェーンを含むため） |
>
> **結論：D-02 の方式は成立する。** 以下は残る制約として引き続き扱う。
>
> * アプリの規模が大きくなるとビルド時間とメモリが増える。**S13 完了時点で再計測する**
> * 本番のコンテナにメモリ上限を設ける場合、ビルド分を見込む必要がある
> * ビルド〜再起動の間はサービスが停止する。メンテナンス表示が要る

### 当初の懸念（記録として残す）

D-02 で採用した導入方式は、以下をコンテナ構成に要求する。

| 要求 | 衝突しうる規定 |
| --- | --- |
| イメージにビルドツールチェーンを同梱する（Next.js の standalone 出力が使えない） | イメージサイズと攻撃面が増える |
| `plugins/` を書き込み可能な永続ボリュームにする | `06_コンテナ設計.md` §71「Read-only Filesystem」 |
| ビルド時に 1〜2GB のメモリを確保できる | 本番のリソース設計 |
| ビルド中〜再起動中はサービスが停止する | `07_デプロイ設計.md` §75「Maintenance Mode」 |
| ビルド失敗時に直前の成功状態へ戻せる | `07_デプロイ設計.md` §51「Application Rollback」 |

**採用した緩和策**（`Dockerfile` / `docker/entrypoint.sh` に実装済み）

* 書き込み可能にするのは `plugins/` ボリュームとビルド出力先だけに限定し、
  それ以外は read-only を維持できる構成にした
* ビルド前に `.next` を退避し、失敗したら書き戻して直前の成功ビルドで起動を続ける（実装済み）
* ビルド中はメンテナンス表示を返す（S12 で実装する）

`docker/entrypoint.sh` は起動・ビルドのコマンドを環境変数で差し替えられるようにしてある。
スタブを渡すことで、実際に Next.js をビルドせずにループとロールバックの挙動を検証できる。

## S-4（2026-08-24 追加・**2026-09-01 解消**）Plugin の描画が例外を投げたときの扱い

`011-plugin-runtime` の検証で挙がった。

Plugin の Widget・拡張点は本体の Server Component と同じ文脈で描画する。
Plugin の描画が例外を投げると、**その画面が白くなる**（他の画面には波及しない）。

Error Boundary で Plugin の枠だけを落とす案があるが、Server Component では
Error Boundary が使えない。Plugin の枠を Client Component にする必要がある。

**`013-example-plugin` で実際の壊れ方を見てから決める。**
先に仕組みだけ作ると、要らない制約を Plugin 作者へ押し付けることになる。

> **2026-09-01 解消。** `ui/plugin/plugin-boundary.tsx` で枠だけを落とすようにした。
> **Client Component の Error Boundary だけでは足りず、Suspense が要った**
> （包まないとページ全体の描画が中断され 500 になる。E2E で実際に踏んだ）。
> Suspense を挟めば Plugin の部品は Server Component のままでよく、
> **心配していた「Plugin 作者への制約」は発生しなかった。**

## S-5（2026-08-24 追加）Plugin Package のアップロード上限と同時実行

`012-plugin-manager` の検証で挙がった。

`inspectPackage` は zip 全体をメモリへ載せる。上限（既定 32 MiB、
`TORIFUNE_PLUGIN_MAX_BYTES`）× 同時アップロード数だけ確保されうる。

`plugin.manage` を持つインスタンス管理者しか叩けないため実害は小さいが、
**上限を上げる運用では同時実行を絞る必要がある。**

決めるべきこと：

* 上限を上げてよい範囲の目安をドキュメントに書くか
* ストリーム展開へ変えるか（yauzl は対応している。検証を先に済ませる設計と
  両立させるには、一時ディレクトリへ出してから検証する形になる）

**急がない。** 既定の上限で困る Plugin が出てから決める。

## S-6（2026-08-24 追加・**2026-09-01 解消**）Authentication Provider の差し替え口が無い

`013-example-plugin` の検証で挙がった。

`PLUGIN_EXTENSION_KINDS` は `authentication` を含み、Manifest で宣言できるが、
**`PluginContext` に登録の口が無い。宣言しても使えない。**

`database` と同じ形で足せる。

```ts
context.authentication.registerProvider(provider);
```

**差し替えを実際に使うサンプルが無いまま口だけ作らない。**
使われない形を先に固めることになる。
外部認証（OIDC / LDAP 等）の Plugin を作るときに、その要求と合わせて決める。

それまでの間、`extensions: ['authentication']` を宣言した Plugin は
検証を通るが何もできない。

> **2026-09-01 解消。** `context.authentication.registerProvider` を実装した。
>
> 保留していた理由（使う実物が無いうちに形を固めない）に対しては、
> **セッションの発行を Core に残す**ことで、Plugin 側へ委ねる範囲を
> 「誰か」を決めるところだけに絞った。ここは外部認証の方式が変わっても動かない。
>
> 実装の途中で、公開契約に `issue` が無いために**そのままでは差し込めない**
> ことと、**最初のログインより前に Plugin が起動していない**ことが分かった。
> どちらも口を作ってみるまで見えなかった。詳細は文末の 2026-09-01 の節。

  標準入力から読むか、`--generate` で生成して1度だけ表示する
* **無効化されたユーザーには適用しない。** 適用できると、無効化したはずの
  アカウントを復活させる裏口になる。存在しないユーザーと区別せず同じエラーを返す
* **Torifune 本体（`apps/web`）を import しない。** アプリが起動しない状態でも
  動かせる必要があるため。その代償として、パスワードの規則（空・1024バイト上限）と
  Argon2id によるハッシュ化は `authentication/password.ts` と**二重に持っている**。
  片方だけ変えると復旧経路だけ規則がずれるので、変更時は両方を直す

## R-09（2026-08-31 追加・**解消済み**）本番ビルドでだけ壊れる経路があった

`012-plugin-manager` #30 の実機確認を行ったときに見つかった。

### 何が起きていたか

`plugin/paths.ts` の `pluginsDir()` が `import.meta.dirname` から相対解決していたが、
**Next.js の本番サーバーバンドルでは `import.meta.dirname` が `undefined` になる。**
`join(undefined, ...)` が投げ、Plugin Package の導入が 422
「Plugin を配置できなかった」で失敗していた。
実際の理由は操作の記録にだけ残る
（`The "path" argument must be of type string. Received undefined`）。

**`06_画面設計.md` §18「Web UIからのインストール」が本番構成で機能していなかった。**

### なぜ気づけなかったか

`import.meta.dirname` は dev サーバーでも Vitest でも値が入る。
**`pnpm test` と `pnpm test:e2e` は本番ビルドのサーバーバンドルを通らない。**
E2E は `pnpm build && pnpm start` を使うが、Plugin Package の導入は
再ビルドを伴うため E2E に載っていなかった。

### 直したもの

| 対象 | 内容 |
| --- | --- |
| `plugin/paths.ts` | 解決を `resolvePluginsDir()` として切り出し、`dirname` が無いときは cwd から解決する |
| `plugin/paths.test.ts` | 環境から切り離して、`dirname` が `undefined` の経路を検査する |
| `Dockerfile` | `TORIFUNE_PLUGINS_DIR=/app/plugins` と `TORIFUNE_SELF_RESTART=1` を明示 |
| `scripts/verify-container-rebuild.sh` | 本番イメージで通しの確認を行う。CI の `container` ジョブ |

### 残る教訓

**「dev と Vitest では動くが本番ビルドで壊れる」は、この構成では常に起きうる。**
Next.js のサーバーバンドルは `import.meta` を書き換える。
ファイルシステムを触る処理を足すときは、`container` ジョブが通ることを確かめる。

### S-6：セッションの発行は Core に残した

公開契約 `PluginAuthenticationProvider` には `issue`（セッション発行）が無い一方、
本体が使う Provider 型は `AuthenticationProvider & SessionIssuer` で、
`login()` が `provider.issue()` を呼ぶ。**そのままでは差し込めなかった。**

`plugin/authentication-adapter.ts` で橋渡しし、**セッションの発行は
差し替え前の Provider（標準認証）のものを使い続ける**形にした。
`04_認証設計.md` §22「Torifune自身のセッションを確立する方式を基本とする」に従う。
Session Fixation 対策・ハッシュ保存・有効期限・アイドルタイムアウトが
Plugin ごとにばらけるのを避けるため。

**Plugin が名乗った `userId` は実在を確かめる。** 確かめないと、Plugin が
任意の ID を名乗るだけでそのユーザーとしてセッションが発行される。
実在しなければ資格情報の誤りとして扱い、理由は呼び出し元へ返さない
（「そのユーザーは居ない」と返すと、外部の識別子から利用者を探れる）。

**JIT プロビジョニングは実装していない。** 新規ユーザーへどのロールを
与えるかが仕様に無いため。必要になった時点で決める。

### 認証を通す前に Plugin を起動する必要があった

`ensurePluginsStarted` は認証済みの画面からしか呼ばれておらず、
**最初のログインの時点では Plugin が起動していなかった。**
起動していなければ `getAuthenticationProvider()` は標準認証を返し、
差し替えたはずの Provider を誰も通らない。

`ensurePluginsStartedAnonymously()` を足し、ログイン画面とログイン API から呼ぶ。
**匿名の認可文脈で起動する。** `activate()` が受け取る Data API は権限を持たない。
認証済みの誰かの権限で起動するより安全で、
「最初に画面を開いた人が誰か」で Plugin の起動条件が変わることも無くなった。

### S-4：Suspense が要った

Error Boundary（Client Component）だけでは足りなかった。
**Suspense で包まないと、Plugin の描画が投げたときにページ全体の描画が中断され
500 になる。** 実際に E2E で 500 を踏んで分かった。

Suspense があると本体の骨組みを先に送れるため、失敗を枠の中で受け取れる。
結果として **Plugin 作者への制約は無い。** Plugin の部品は
Server Component のままでよく、Data API もサーバー側に留まる。

`03_リスクと未決事項.md` S-4 が心配していた「Plugin の枠を Client Component に
する必要がある」は、**Suspense を挟むことで回避できた。**
